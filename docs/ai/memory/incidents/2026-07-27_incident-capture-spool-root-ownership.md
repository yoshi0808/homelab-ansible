# Incident: 証拠捕捉のspoolディレクトリがroot所有で作られ、捕捉が無音で永久停止しうる状態だった

日付: 2026-07-27
状態: 解決済み
対象: `roles/incident_capture/tasks/main.yml`(証拠バンドル収集器の配備)
種別: 未遂
原因分類: #製造ミス #テスト不足 #運用考慮ミス

## 症状

`incident_capture` roleが `reports/incidents/_spool/` を作るタスクに `owner:` が無く、`become: true` だけが付いていた。兄タスク `Ensure reports/incidents/ exists` には `owner: yoshi` が明示されていたのに、このタスクだけ抜けていた。

W0観測で `reports/incidents/` は**未作成**と実測済みであり、配備playbookがT1(`roles/common_slack/tasks/capture.yml`)より先に走る経路は現実に存在した。その場合 `_spool/` が `root:root mode 0755` で作られ、`become: false` で動くT1は**以後永久に書き込めない**。

本番適用前に独立レビューで検出したため、実害は無い。

## 原因

**単独の欠陥は小さいが、3つの独立した設計判断が重なって「全体が盲目になる」状態を作っていた。**

1. **T1の失敗は自身の `block`/`rescue` が吸収する** — 意図的な設計。「観測が被観測を壊さない」(requirement R3/AC4)ため、捕捉の失敗で本番の通知経路を止めない。したがって書き込み失敗は無音になる。
2. **R5b(捕捉が止まっていることの検出)は「新規失敗ジョブがある周期」でしか発火しない** — 既存の名前付き操作 `homelab-semaphore-query recent-failed` が error/stopped 限定であることに由来する実装上の制約。
3. **正常時に成果物が何も残らなかった** — run-reportを `collection_errors` がある場合のみ生成する設計。ファイル増殖を避ける意図。

結果として、**捕捉が最初から一度も動いていないのに、失敗ジョブが発生するまで誰も気づかない**。①②③はそれぞれ単独では正当な理由を持ち、別々に見ている限り欠陥に見えない。

テスト側も抜けていた。実装時のfixture検証は「`_spool/` が既に存在する」前提で組まれており、**配備playbookがT1より先に走る順序を一度も試していなかった**。

## 修正内容

- `Ensure reports/incidents/_spool/ exists` に `owner: yoshi` を追加(兄タスクと同じ理由をコメントに明記)。
- あわせて、同タスクの既存コメント「`state: directory` は既存ディレクトリの owner/mode を変えない」が不正確だったため訂正(`mode:` を明示していれば既存ディレクトリのmodeは上書きされる)。
- **上記③を解消**: `_heartbeat.json` を追加し、正常時も含め毎周期無条件で上書きする。単一ファイルの上書きなのでサイズは増えず、当初の「ファイル増殖を避けたい」という意図と両立する。
- 上記②は**直さないと判断**した。T1が壊れていても失敗が起きていない間は実害が無く、実害が出る局面(失敗発生時にT1が壊れている)では `recent-failed` に失敗が出てspoolが空になるため必ず検出される。**直さない理由をコード側にも明記**し、将来の読み手が善意で直そうとしないようにした。

## 確認方法

- 修正後、fixtureで5シナリオを再実行し、正常時・スキーマ不一致・R5b発火・新規イベント無しの全周期で `_heartbeat.json` が書かれることを確認。
- 実ホスト(quory)での配備順序ケース(配備playbookを先に実行 → T1経由のplaybook実行 → spoolファイルが作られる)の実地確認は**未実施**。W5のTester項目として残る。

## 再利用可能な知見

**「無音であること」を個別に正当化した判断が複数あると、合成された結果は誰の意図でもない全体沈黙になる。** 本件では①が設計上正しく、②が制約として妥当で、③が意図として理解できる。にもかかわらず合成結果は「壊れていることが原理的に分からない」だった。

無音化の判断を1つ入れるたびに、**「これが3つ重なったら何が見えなくなるか」を問う**必要がある。個別レビューでは各判断の正当性しか問われないため、この問いは合成を見る立場(Coordinator、または全体を見る独立レビュー)が持つべきものである。
