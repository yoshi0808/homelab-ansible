# Incident: 非ASCIIファイル名でcommit前の秘密ファイル検査をすり抜けられた

日付: 2026-07-27
状態: 解決済み
対象: `scripts/git-pre-commit-check.sh`(commit前検査)
種別: 未遂
原因分類: #製造ミス #テスト不足

## 症状

`scripts/git-pre-commit-check.sh` は `git diff --cached --name-only --diff-filter=ACMR` の出力を `staged_files` として3つの検査で共有していた。gitは既定(`core.quotepath=true`)で**非ASCIIを含むパスを8進エスケープし引用符で包んで**返す。

```
$ git diff --cached --name-only --diff-filter=ACMR
"\346\227\245\346\234\254\350\252\236dir/main.yml"
```

このため、名前による突き合わせを行う検査が**すべて無音でスキップ**されていた。

| 検査 | 非ASCIIファイル名で |
|---|---|
| 秘密ファイルのブロック(`.key` / `.pem` / `id_rsa` 等) | **すり抜ける** |
| vault未暗号化の検出 | **すり抜ける**(`[[ -f "$file" ]]` がエスケープ名で偽になり `continue`) |
| IPv4リテラルの検出 | 影響なし(pathspec経由でgit自身が名前を解決し、grepは差分内容に掛かるため) |

**このリポジトリは公開前提**であり、`秘密dir/id_rsa` のような名前で秘密鍵をcommitできる状態だった。実際にそのようなcommitが行われた形跡は無い。

**この欠陥は今回の変更で入ったものではなく、元から存在していた。** 2026-07-27に別件(動的include向けのYAML構文検査の追加)のレビューで、新設した検査が同じ理由で機能しないことが指摘され、Coordinatorが範囲を広げて調べたところ既存2検査にも同じ穴があると判明した。

## 原因

**検査が動かなかったこと自体が観測できない形になっていた。** `grep` が0件マッチしても `|| true` で握られ、`case` が一致しなくても何も起きず、`[[ -f ]]` が偽なら `continue` する。いずれも「該当なし」と「判定できなかった」を区別しない。

テスト側の抜けは明確で、**非ASCIIファイル名という入力が一度も試されていなかった**。ASCII名でのみ検証していれば、この検査群は完全に正常に見える。

## 修正内容

- `staged_files` の生成を `git -c core.quotepath=false diff --cached --name-only --diff-filter=ACMR` に変更。**1箇所の修正で消費側3系統がすべて直る**(根本原因側の修正)。
- **fail-closedのガードを追加**。`core.quotepath=false` でも、改行・引用符・バックスラッシュを含むパスはgitが引用符付きで返す。先頭が `"` のパスが1件でもあれば、明確なメッセージを出して非ゼロ終了する。配置は「staged無し」の早期exit直後、gitleaksより前。
- 判断の根拠をコード内に明記: **この検査群の目的からして、読めない名前は「安全」ではなく「判定不能」である。**

## 確認方法

- 使い捨てgitリポジトリで、非ASCIIディレクトリ配下の `id_rsa` をstageして実際に `scripts/git-pre-commit-check.sh` を実行し、`ERROR: dangerous secret-like file staged: 秘密dir/id_rsa` / `rc=1` で停止することをCoordinatorが独立に再現した(修正前は素通り)。
- 非ASCII名の壊れたYAML、非ASCII名の未暗号化vaultファイルについても検出されることを確認。
- ASCII名の従来ケース(検出すべきもの/通すべきもの)が全て従来どおり動くことを確認。リポジトリ内158 YAMLの再掃引で誤検知0件。
- 速度は150ファイルでgitleaks込み約0.53秒、修正前と同水準。

## 未修正のまま残る同クラスの問題

**vault未暗号化検査は作業ツリーを読んでいる**(`head -n 1 "$file"`)。indexではないため、未暗号化のままstageして作業ツリー側だけ暗号化すれば通過する。本件の修正範囲外として触っていないが、**「検査対象が実際にcommitされる内容と一致していない」という同じクラスの穴**である。

## 再利用可能な知見

**ゲートは、動かなかったときに「合格」と区別がつかない形で書かれがちである。** `grep` の0件、`case` の不一致、`[[ -f ]]` の偽は、いずれも「該当しない」と「判定できない」を同じ経路に落とす。検査を書くときは**判定不能を明示的に失敗させる**(fail-closed)ことを既定にする。

そして**検査そのものは、異常な入力で試されない限り正常に見える**。ASCII名しか試さなければ、この検査群は何年でも正常に見え続けた。ゲートの検証では、守ろうとしている対象ではなく**ゲートを迂回しうる入力**を作って試す。

同日に同じ構造の欠陥がもう1件出ている([[2026-07-27_incident-capture-spool-root-ownership]])。そちらは新規実装側で、無音化の判断が3つ重なって全体が盲目になっていた。**1日のうちに独立な2箇所で同じクラスが出たことは、これが個別のうっかりではなく設計習慣の問題であることを示唆する。**
