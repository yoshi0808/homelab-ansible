# 推測を規律で止めようとせず、観測できるようにする

決定日: 2026-08-25 / 決定者: Yoshinobu / 記録: Coordinator

## 決めたこと

**観測手段が無いことに起因して推測が入った箇所は、規範や作法ではなく、read-only のアクセス追加で対応する。** 第一手は forced command dispatch の能力を上げること。それで届かない場合に quory 側 Operator へ回す。

## 原因は2クラスに分かれる。混ぜると対応を誤る

2026-08-25の月次Knowledge振り返りで挙がった不具合を、原因で分けるとこうなる。**事象としてはどれも「誤った断定」に見えるが、原因が違う。**

### 作りの問題

`community.general.slack` は宛先が `slack.com` / `slack-gov.com` にハードコードされており、`domain` 引数を無視する。**URL やドメインを差し替える形の decoy は、このモジュールに対して原理的に成立しない。** それを知らずに宛先を差し替える decoy を4回組み、4回とも実 Slack へ出た(`incidents/` の 2026-07-26 / 2026-08-01 / 2026-08-02 / 2026-08-07)。

**これはモジュールの実装を読めば分かることで、アクセス権とは何の関係もない。** 対応は実装の差し替えであり、観測を足しても直らない。

### 観測できないことに起因する推測

見る手段が無い対象について、断定するか、そこで止まるかしかない状況がある。

- **一次調査の先読みファイルが書けない件**(2026-08-25判明)。role は対象ディレクトリを `owner:` 指定で作る建付けなのに、本番では `EACCES` が出る。**開発側からそのディレクトリの所有者と権限を見る手段が無い**ため、「repo の意図と本番の現物が食い違っている」までしか言えず、原因を断定できていない。
- **`semaphore-db` の ACL**。`dev-investigate` が traverse を失ったため、「ACLが付け直されていないか」を開発側から観測する手段が恒久的に失われている(`docs/ai/status.md` に既載)。

`acl-status` は operand からパスを組まず固定の name→path 表で引く作りで(`roles/dev_investigate/files/recovery-investigate-dispatch-quory.sh`)、**表に無いパスは観測できない。表に無いことは、開発側からは「見えない」としか現れない。**

## Operator 経路が在ることは、この判断を変えない

quory 側 Operator へ問えば答えは得られる。**経路はあり、能力の不在ではない。**

**にもかかわらず実際には問われていない。** これは規律の問題として現れるのではなく、傾向として現れる(Yoshinobu、2026-08-25)。

**そして傾向を規範で直す手は、この環境で繰り返し退けられている。** 「破ろうと思えば自分が破れる対策は対策でなく願望」であり、取れるのは①能力を消す②別体に検査させる③設計要件として積む、の3つだけ(`lessons/permission-boundaries-must-be-designed-not-prompted.md`、`lessons/measure-whether-the-risk-has-ever-materialized.md`)。「Operatorへ聞くようにする」はそのどれでもない。

**したがって、傾向が直らなくても結果が変わる形を採る。** 推測せざるを得ない状況そのものを消す。

## なぜ read-only のアクセス追加なのか

- **`docs/ai/core.md` が明示している側にある。** 「読み取り(情報共有)は持たせてよい。状態を変えるものは、forced commandであっても持たせない。」観測の追加は前者であり、境界の設計思想に反しない。
- **増えるものが限定されている。** dispatch は operand からパスを組まないため、足しても増えるのは「読めるパスが1つ」だけで、新しい語彙は増えない。
- **直す対象が振る舞いではなく前提である。** 見えるようになれば、断定するか止まるかの二択自体が消える。

## 足し方には設計論点が残っている

**1本ずつ足すと3回目が来る。** `semaphore-db` で1回、先読みディレクトリで2回目である。表へ個別に足す運用のままだと、repo 側で新しいパスを管理し始めるたびに観測の穴が開き、**穴が開いたこと自体も見えない。**

論点は「**repo が `owner:` / `acl` を設定しているパスは観測できる**」という形にできるかであり、個別のパスを1つ足すかどうかではない。

## この決定が変えたもの

再発記録11行のうち9行が「確認せず推測で断定した」型であることを測ったとき、Coordinator は「集めた先の出口(3回で Skill 化)がこの誤りには行き止まりだから、受け皿を作らないほうが素直」と述べた。**この見立ては、9行を原因で分けずに事象でまとめたことの帰結であり、誤っていた。**

9行には「確認手段があったのに確認しなかった」と「確認手段が無くて推測した」が混ざっている。**後者は本決定で消える。** 行き止まりなのは前者だけである。

**分類は未実施である。** これを分けることが、本決定が効いたかどうかの検証そのものになる。

## 見直し条件

- **read-only を超える要求(書込・実行)が出たとき。** そのときは本決定の射程外であり、`docs/ai/core.md` の「状態を変えるものは持たせない」が優先する。
- **観測手段を足しても「観測できなくて推測した」が減らないとき。** 原因の断定が誤っていたことになる。
- **Operator 経路が実際に使われるようになったとき。** 前提(経路は在るが使われない)が崩れるため、アクセスを足す理由の一部が消える。
