# ansyから本番の状態を変えない — 配備の自動起動2案を却下する

決定日: 2026-08-04 / 決定者: Yoshinobu / 起案: Coordinator

## 決定

**ansyが本番の状態を変える経路を作らない。** ansyがquoryへ触れること自体は禁じず、線は「触れるか」ではなく「**状態を変えるか**」で引く。

規範として適用する本文は `docs/ai/core.md`「人間の権限と安全境界」「開発と本番の境界」が正本であり、**本ファイルへ複製しない**(判定に使うときはそちらを読むこと)。日常の運用としての帰結は `docs/ai/context/operations/code-delivery-to-production.md` §1.1。以下は、その規範がなぜこの形になったかだけを扱う。

## なぜこうしたか

`git push` から本番の配備物が更新されるまでの間に、**人がSemaphoreのボタンを押す**という区間が残る。押し忘れは日次ドリフト検査が翌朝に拾うが、通知を受けてから直すまでの往復が残るため、「ansy側から配備を起動できるようにしてはどうか」という提案が自然に出る。実際に2026-08-04、2案を検討した。

いずれも却下したが、**理由が残っていないと同種の提案は繰り返し出る**。安く実装できてしまう形をしているため、理由の側を記録する。

### C案 — Semaphoreのscheduleでsetup系playbookを自動適用する

実行は本番側で完結し、ansyに新しい能力を1つも足さない。それでも却下した。**コードが人の都度判断を経ずに本番へ入る**ことになるためである。

Yoshinobuの言葉では「**そもそも区別した境界を曖昧にするから**」。押す回数を減らす案ではなく、押す行為そのものを消す案だった。

### D案 — 引数を取らないforced commandがsystemd unitを起動し、unitが配備playbookを流す

forced commandは引数を取らないため「自分の知らないコマンドを叩かれる余地は無い」という形をしている。sudoers 1行で実装でき、dispatchの語彙も1つしか増えない。

却下理由は、**ansyに「本番へのroot適用を発火する能力」を与えること**にある。ansyがpve1 / pve2 / authy / quory / sophos-fw の認証情報を1つも持たないことで作った境界が、この1点で消える。**安く見えることが、この案の危険な点である。**

## 前提の変更を伴っている

Yoshinobuは従来、**「調査は forced command で担保されているので、自分がリスクとして認める限り ansy からのコマンドは可」**という認識を持っていた。根拠は、引数を取らない forced command には自分の知らないコマンドを叩かれる余地が無いこと。この認識のままなら D案は通りえた。

迷った末、**今回は境界を明確にすることを優先した**。言葉どおりに徹すれば forced command そのものを認めないことになるが、そこまでやると運用が回らないため、**「情報共有は可能」という位置づけ**に留める。

つまりこの決定は、forced command の安全性の評価を変えたのではなく、**判定の軸を「叩かれる余地があるか」から「本番の状態が変わるか」へ移した**ものである。

## 引き受けたリスク

配備の押し忘れは残る。検出は翌00:40の日次ドリフト検査だけで、直すまで毎朝再通知される(エッジ抑止が無い)。**この遅延は欠陥ではなく、人間のゲートを残した代償として引き受けたものである。**

## 見直し条件

- 押し忘れが実際に運用の障害を生んだ場合(現時点では未発生)。
- ansy以外に、本番へ届く開発側の主体が増えた場合。境界をホストで引いている前提が変わる。
- forced command dispatch に、読み取りと状態変更の区別が曖昧な動詞を足したくなった場合。その動詞を足す前に本ファイルへ戻る。
