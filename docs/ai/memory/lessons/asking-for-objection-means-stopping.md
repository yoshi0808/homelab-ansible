# 異論を求めたら、そのターンで先へ進まない

## 教訓

**承認・異論・判断を求める文を書いたら、そのターンはそこで終える。** 同じターンでsubagentを起動しない、依頼を送らない、repoを変更しない。

「異論があれば言ってください」と書いた直後に着手すると、**相手には読む時間が無い。** 求めた形だけが残り、実質は事後報告になる。

## 根拠(2026-09-06、案件B `semaphore_upgrade_dryrun_unification`)

`dry_run`の改名について、対象範囲を`semaphore_upgrade`だけに絞る判断を書き、「**この線引きでrequirementを書きます。異論があれば言ってください、書き直します**」と述べた。**その同じターンでrequirementを書き、Implementerへ送信した。**

続けて前提の誤り(「`--check`は何も起きないのが大前提」)が示されたあとも同じことをした。requirementを全面改訂し、Implementerが入れた変更をコードごと戻し、改訂版で再依頼するまでを一息で行った。**改訂した設計をYoshinobuは一度も見ていない。**

Yoshinobu「**異論があれば言ってという割にはなんで勝手に進めるかな**」。

実害: Implementerが誤った契約に忠実な実装を92行分書き、破棄した。**破棄そのものより、「合意したことになっている」状態が2回できたことが問題である。**

## なぜ起きるか

**推奨を添える規範と、着手前の合意を取る規範が、両立しているように見えて衝突する。**

- `docs/ai/policies/execution_boundary_policy.md` EXEC-061「迷ったら上げてよい。ただし必ず推奨を添える」
- `docs/ai/roles/coordinator.md`「着手前の計画は必ず出し、合意してから着手する」

推奨を書くと、**書いた側は既に判断を終えている。** そこから止まるには意識的な停止が要る。推奨の質が高いほど、止まる理由が薄く感じられる。**「推奨を書いた」は「合意を得た」ではない。**

## 適用

- **承認・異論・判断を求める文を書いたら、そのターンでtoolを呼ばない。**
- 「〜でよければ進めます」と書いて実際に進めてよいのは、**既に合意済みの計画の内側にいるとき**だけである。計画そのものへの同意をまだ得ていないなら、内側ではない。
- **合意済みの計画に沿ったsubagentの起動は確認不要**(auto-memory `feedback_subagent_launch_needs_no_approval`)。**この教訓はそれと矛盾しない** — 問題は起動したことではなく、**まだ合意されていない契約で起動したこと**である。
- 既に流してしまったら、止めて、何がどこまで入ったかを報告する。**止めた事実を黙って回収しない。**
