# 境界を主張するなら、境界の外側を測る

## 教訓

「この操作は技術的に禁止してある」と書くとき、**禁止した対象が通らないことの確認は検証ではない**。検証すべきは**禁止していないつもりの領域**、つまり境界の外側である。

見落としは3つの層で独立に起きる。上から順に発見が難しい。

| 層 | 見落としの形 | 確かめ方 |
|---|---|---|
| **軸** | 塞ぐべき軸自体を思いつかなかった | 「他にどの経路で同じ被害が起きるか」を列挙する |
| **列挙** | 軸は合っているが項目に漏れがある | 列挙**していない**ものを試す |
| **機構** | ルールが作用していない | 列挙した1件を試せば足りる |

「機構が効く」の実測は「列挙が網羅的」の証拠にならず、「列挙が網羅的」でも軸を1本忘れていれば封じ込めは成立しない。そして**列挙漏れも軸の欠落も、作った本人には見えない**(「自分が検索しなかったものは、自分では検索漏れとして見えない」のと同じ構造)。独立した目でしか埋まらない。

実務上の3点。

- **境界の検証は「外側が拒否される」と「内側が通る」を対で測る。** 片方だけでは、封じ込めか機能不全かを区別できない。**安全側に倒しすぎて仕事ができないのも欠陥である。**
- **検証環境が既に許可を持っていないか確認する。** 許可の緩い場所で「拒否されるはず」を測ると、拒否されない理由が実装なのか環境なのか切り分けられない。
- **denylistを選ぶ前に、allowlistにできないか考える。** 列挙漏れが素通りする方式と、列挙漏れが機能不全として現れる方式では、失敗の向きが逆になる。

## 根拠(2026-07-27、月次Knowledge振り返りの無人実行)

無人`claude -p`の境界を作る過程で、独立レビュー3巡がそれぞれ**別の層**の見落としを検出した。実装者は毎巡「確認済み」と報告していた。

**1巡目 — 機構の不在**: promptに「書いてはいけない場所」を文章で書き、技術的な強制を何も入れていなかった。止めるものはモデルの自制だけだった。

**2巡目 — 列挙漏れ**: `--disallowedTools`に禁止パスを列挙し、「denyがallowに勝つか」をdecoy環境で実測して「実測で確認済み」と報告した。測ったのは**機構が効くこと**(列挙した`docs/ai/policies/`が拒否される)だけで、**列挙の網羅性**は測っていない。レビュアーが列挙外を実機で試し、`CLAUDE.md`・`AGENTS.md`・`docs/ai/`直下の正本群・`docs/ai/reviews/**`の計9ファイルへ**実際に書き込めた**。`CLAUDE.md`と`AGENTS.md`は全セッションが起動時に読む入口文書で、汚染されれば以後の全Role・全subagentの指示系統に波及する。

**3巡目 — 軸の欠落**: allowlist方式へ反転し、9ファイルの拒否を実証した。しかし塞いだのは**書込だけ**で、`Read`/`Glob`/`Grep`は無制限のままだった。ansyユーザーが読める全ファイル(vaultのパスワードファイル、SSHキー)へ到達でき、書込先が**公開GitHubリポジトリのgit管理下**であることと組み合わさると、機密混入の経路になる。「書込境界」という問題設定自体が半分しか見ていなかった。

**測定の無効化**: 修正時、測り直しの初回を`/tmp`配下で行ったが、この環境では`/tmp`が追加作業ディレクトリとして既に広く許可されており、**テスト場所自体が測定を無効化していた**。実行したagentが「追加作業ディレクトリに`/tmp`が丸ごと入っている」と報告して発覚した。`$HOME`配下へ移して測り直した。
