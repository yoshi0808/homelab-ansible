# ブロックされたら、通る経路ではなく検証方法そのものを作り直す

## 教訓

安全機構が発火したとき、止められた側に見えている選択肢は普通2つしかない — **通る形を探す**か、**止まって上げる**かである。だが実際にはもう1つある。

**その操作が、目的にとって本当に必要かを問い直す。**

必要でなければ、迂回でも停止でもなく、**操作を要らなくする形へ検証設計を組み替える**のが正解になる。これは「別の手段で同じ結果へ到達する」こととは別物である — 到達すべき結果の側を、より小さいものへ引き直している。

判別は次で付く。

| 取った行動 | 何が変わったか | 可否 |
|---|---|---|
| 別のツール・別の分割・別の書き方で**同じ結果**へ到達した | 形だけ | **不可**。止めて上げる |
| **その結果を必要としない**検証設計へ作り直した | 目的の側 | 可。ただし**必ず報告する** |

後者を取れるのは、ブロックされた操作が目的の本質でなかったときに限る。**本質かどうかを都合よく判定しないための担保が「必ず報告する」である** — 報告があれば、判定の是非をCoordinatorが後から検算できる。黙って作り直せば、迂回と区別がつかない。

[[permission-boundaries-must-be-designed-not-prompted]] は逸脱側(形を変えて通した例)を扱う。本ファイルはその対照例であり、**同じ「ブロックされた」入口から正しい側の分岐へ抜けた記録**である。

## 根拠(2026-07-28、`incident_auto_capture` Step 2 の U2)

Implementer(subagent)が decoy の git 検証用に使い捨てリポジトリを `git init` した際、`git config` に続けて `git commit` まで行う手順を1つの Bash コマンドとして投げたところ、**ツール呼び出し自体が拒否された**(対象は repo 外のscratchpad上の使い捨てリポジトリで、本番commitではない)。

Implementer は**別の形で同じ結果へ迂回せず**、`git commit` を伴わない構成(`git init` のみで、コミットなしに `git status --porcelain` の挙動を検証する)へ**検証方法自体を作り直した**。commit はこのテストの本質的要件ではなかったため、作り直しで自己検証の目的は損なわれていない。

そして**この事実を implement 記録の §0(安全境界の遵守)と §5(Coordinatorの判断を要する事項)の両方へ書き、最終報告にも載せた。** 成功だけを記録に残す形にしていない。
