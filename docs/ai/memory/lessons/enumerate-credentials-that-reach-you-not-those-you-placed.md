# 境界を閉じるとき数えるのは、自分が置いた資格情報ではなく、自分から届く資格情報

## 教訓

**能力の不在で境界を作る設計は、能力の列挙が完全であることに全面的に依存する。** 列挙が漏れれば、設計としてどれだけ正しくても境界は成立しない。そして**漏れは「動いてしまう」という形でしか現れない** — 文書をいくら読んでも見つからない。

列挙を誤る主因は起点の取り方である。

| 起点 | 何を数えるか | 漏れるもの |
|---|---|---|
| 自分の設定ファイル・inventory・自動化の経路 | **自分が置いた**資格情報 | 人が手で作った資格情報、別のユーザー名義の受け口 |
| **相手側の受け口**(`authorized_keys`、許可ユーザー、開いているポート) | **自分から届く**資格情報 | — |

この2つは、接続identityを1つに統一している環境では一致して見える。**一致するのは統一が守られている範囲だけであり、人の利便のために作られた資格情報はその外側にある。** 「自動化の経路をすべて追えば網羅できる」という前提は成り立たない。

実務上の3点。

- **列挙の単位は `(資格情報) × (相手ホスト) × (相手側ユーザー)` の直積で取る。** 相手側ユーザーを固定して数えると、別ユーザー名義の受け口が丸ごと視界から消える。
- **相手側の受け口が共有されていないか確かめる。** 1箇所を消せば全体から消えることもあれば(pmxcfs のようにクラスタ共有)、ホストごとに独立していることもある。共有の有無は、1本の鍵で複数ホストへ入れてしまう理由でもある。
- **閉じる作業では、検証手段を最後に手放す。** 穴を早く塞ぐことを優先して先に自分側の手段を消すと、除去が効いたことを自分で測れなくなる。順序は「相手側の受け口を消す → 到達しないことを測る → 自分側の資格情報を消す」。

[[verify-the-outside-of-a-claimed-boundary]] は列挙**漏れがあること**を検証の層として扱う。本ファイルはその一段手前 — **列挙の起点をどこに置くか**を扱う。起点が誤っていると、外側を測ろうとしても「外側」の定義自体が間違っている。

## 根拠(2026-08-03、開発と運用の境界 Phase 4)

ansy から保護対象ホストへ届かなくするため、4ホストの `~ann/.ssh/authorized_keys` から `ann@homelab-ansible` を削除した。削除は成功し、`ann` としての認証は全ホストで成立しなくなった。

**それでも ansy から pve1 / pve2 へ root で入れた。** `~/.ssh/id_ansible`(コメント `ansy-to-proxmox`、2026-05-23 作成)は requirement にも plan にも一度も登場しない鍵で、forced command も付いておらず、**無制限の root シェル**が得られた。

見落とした理由は列挙の単位である。requirement は「保護対象3ホストの `~ann/.ssh/authorized_keys` には既に2エントリある」と書き、**`root` の側を一度も見ていなかった**。この鍵は repo のどの inventory / group_vars からも参照されておらず、Yoshinobu が ansy を踏み台として使うために手で作ったものだった。自動化の経路を追っても出てこない。

対処では手順も誤った。**ansy 側の秘密鍵を先に消し、pve 側の公開鍵除去を後から依頼した。** その結果、除去が効いたことを実測する手段を自分で失い(dispatch のカタログに `root` の `authorized_keys` を読むチェックは無い)、伝播の確認は人の目視に依存した。なお `/root/.ssh/authorized_keys` は `/etc/pve/priv/` 配下へのシンボリックリンクで pmxcfs によりクラスタ全体で共有されており、1本の鍵で両ノードへ入れていたのも同じ理由である。

最終的に**全鍵 × 全保護対象ホスト × (root / ann) の直積を掃引し、到達ゼロを実測**して閉じた。
