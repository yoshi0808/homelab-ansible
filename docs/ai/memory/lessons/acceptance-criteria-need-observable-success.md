# 受入条件には「成功」の観測方法まで書く

## 教訓

受入条件に「エラー終了しない」「正常に完了する」と書くだけでは足りない。**その成否を運用上どこで観測するのか**(プロセスの終了コード、スケジューラのジョブ色、通知の有無、レポートの生成)まで書く。書かれていない観測点は検査項目にならず、実行して初めて発覚する。

## 根拠(2026-07-26、proxmox_patch_dryrun単一ノード対応)

AC1は「playbookはエラー終了せず、pve2のみを対象とするdry-run結果を生成し、通知でpve1未到達を明示する」と定義されていた。実装・レビュー・実ホスト検証を通過し、機能要件は5点すべてPASSした。

しかし実ホスト実行の終了コードは`0`ではなく**`4`**(`RUN_UNREACHABLE_HOSTS`)だった。タスク失敗はゼロで、到達不能なhostが1台あることだけが理由である。この機能の目的は「pve1が停止する夏季平日も日次dry-runを継続する」ことだったが、Semaphoreは終了コードでジョブの成否を判定するため、**毎営業日ジョブが赤くなる**。赤が常態化すれば本物の障害と区別できなくなり、目的は実質的に未達だった。

「エラー終了せず」を機能の意味で読めばPASS、終了コードの意味で読めばFAIL。この曖昧さが、実装・レビュー・検証を1周した後にもう1サイクル(実装→レビュー→実ホスト再検証)を要した直接の原因である。

## 適用

requirement作成時、Given/When/Thenの`Then`に次を含める。

- 終了コードの期待値(`0`か、非ゼロならその値と意味)。特に**スケジューラから起動されるplaybook**では必須。
- 通知が飛ぶのか飛ばないのか、飛ぶなら何チャンネルか。
- 生成される成果物ファイルの有無。
- 部分的な成功(一部ホストのみ処理)を成功とみなすのか失敗とみなすのか。

異常系のACでも同じで、「明確なメッセージで停止する」と書くなら終了コードも添える。
