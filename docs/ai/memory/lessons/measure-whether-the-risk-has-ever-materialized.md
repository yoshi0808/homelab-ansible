# 顕在化の可能性を測らずに仕組みを作らない

2026-08-24、Semaphore の schedule に付いていた**有効化ゲート**を撤去した。Yoshinobu の決定であり、退けられたのは実装の出来ではなく、**その仕組みを作った判断そのもの**である。

## 何が起きていたか

新しい schedule はカタログに `active: true` と書いても、**必ず `active: false` で作られる**。走らせるには、別途「実行ごとの明示許可」を立てて **もう一度** setup を押す必要があった。許可は `-e` でしか渡せず、Semaphore のボタンには渡す口が無いため、**既定値を `true` にする commit を立て、押した後に `false` へ戻す commit で畳む**という運用になっていた。

**守ろうとしていたのは「カタログに書くこと」と「本番で走り出させること」を別の行為に分けること**である。

## なぜ退けられたか

**その危険が顕在化したことが一度も無かった。**

実際に起こりうるのは「登録した直後に発火する」ことだけで、それは**登録時刻と発火時刻が近いときに限る**。この日の登録では**次回の起動が16日先**だった。

> **なんとなくリスクがあるから、そのリスクが顕在化する可能性を考えずに仕組みだけは作る。これは俺が一番嫌いなパターンだ**(Yoshinobu、2026-08-24)

> **守れないのは許すよ、そういう時もあるさ。だけど、到底守れないのに意味なく仕組みを作り込むのは許せない**(同)

## 仕組みが払わせていた代価

- schedule を1件登録するのに**押下2回・commit 2回**
- **Coordinator が説明に3往復を要し、それでも伝わらなかった。** 説明の巧拙ではなく、**説明を要する形をしていた**ことの現れである
- **畳み忘れても何も鳴らない。** 立ったままであることを検出する仕組みは無く、**保護は静かに消える**
- **人の関与はもともと2箇所あった** — カタログへ書く commit のレビューと、ボタンの押下。ゲートはその上へもう1段を積んでいた

## 撤去のとき、同じ穴を掘りかけた

Coordinator は撤去の requirement に「**代わりに置くもの — 実装ではなく作法**」として、「schedule を追加するときは押していただく前に次回の起動時刻を必ず伝える」と書いた。**これも撤回された。**

- **顕在化の可能性を測っていない。** 撤去する機構とまったく同じ穴である
- **Coordinator が破ろうと思えば破れる。** 自分で破れる対策は対策ではない([[permission-boundaries-must-be-designed-not-prompted]])
- **「作法だから実装より軽い」は理由にならない。** 軽いから足してよいのではなく、**足す理由が無いなら足さない**

**何も置かないのが正解だった。** 実際に「登録直後に発火した」が起きたときに考える。

## 判断の順序

仕組みを足したくなったとき、**破れるかどうかより手前**で問う。

1. **その危険は起きたことがあるか。** 無いなら足さない
2. 起きたことがあるなら、**自分で破れない形か**。破れるなら、能力を消すか、別体に検査させるか、設計要件として積むかの3つしかない
3. **後から読んだ人が、何を守っているか分かるか。** 分からないなら、仕組みは残っても目的は残らない
