# 検証の参照先を誤ると、検証自体が正しくても結論が狂う

**分類**: Lesson
**由来**: Policy見直し作業(2026-07-25)でCoordinator(claude)が同一クラスの誤りを1日に4回踏んだ教訓。いずれも実害はPolicy/報告の不正確さに留まり、本番影響はゼロ。

## 失敗の分類

4件すべてが「検証手段は正しく動いたが、当てた対象(referent)が間違っていた」という同一クラスである。

1. **文書内位置の伝達に行番号を使った**。変更箇所を「L278とL301」とユーザーへ伝えたが、当該文書は`<!-- AR-nnn -->`という安定マーカーで参照する設計だった。行番号は正しかったが読み手が辿れず、「見当たらない」という指摘を受けた。正しくはAR-045とAR-069。
2. **「残存なし」の確認grepが狭すぎた**。レビュー観点に「`Mode A` / `Mode B`が消えたことをgrepで確認」と特定文字列を名指しで書いたため、汎用形の「Mode別」がPolicy本文とContext見出しに残存したまま「残存なし」と報告された。Reviewerは指示に忠実であり、観点の書き方が誤りだった。
3. **構造化マーカーを素の文字列で数えた**。`grep -c "SB-049"`で退番済み番号がまだ存在すると誤読したが、実際は変更履歴行が退番の経緯を(意図通り)記録していただけだった。マーカー実体は`<!-- SB-049 -->`形式で数えるべきで、危うく実装担当の正しい報告を誤りと決めつけるところだった。
4. **同名機能の別経路を見て「存在しない」と断定した**。mute TTL上限240分を`roles/recovery_mute/`(Ansible経路)で探して見つからず、自分のメモリを不正確と断定した。実際の上限は`roles/recovery_exec/files/homelab-mute-set`(Slack/Codex経路)にあり、メモリにも「**Codex経由**TTL上限240分」と経路が明記されていた。メモリは正しく、見た経路が違った。

## 学び

検証手段(grep、コード読解、実測)が正しく機能していても、当てる対象を誤れば結論は反転する。この型は「検証した」という感覚が伴うため自己検出が難しく、**慎重さでは防げない**。防げるのは参照方式を機械的に固定した場合だけである。

特に危険なのは4のように「無いことの確認」で経路を誤るケースで、否定的結論は追加検証の動機が湧かないため、そのまま断定へ進みやすい。

## 適用条件

1. **文書内の位置を他者へ伝えるときは、その文書自身が持つ安定識別子を使う**。`SB-nnn` / `AR-nnn` / `UV-nnn` / `BRV-nnn` / `LOG-nnn`が存在する文書では行番号を使わない。行番号は編集で動き、読み手の環境でも一致しない。
2. **「Xが消えたか」ではなく「参照されている用語に定義があるか」をチェックリスト項目にする**。特定文字列の名指しは、その語の派生形・汎用形を取りこぼす。同様に、削除対象への被参照確認はmarkdownリンク形式だけでなく散文中の言及もgrepする(`[Repository Context](...)`と「Repository Contextを正本とする」は別物として両方掃く)。
3. **マーカー等の構造化要素を数えるときはマーカー形式で数える**。`SB-049`ではなく`<!-- SB-049 -->`。変更履歴・移行記録における「言及」と、規範としての「実体」を数の上で混同しない。
4. **同名の機能が複数経路に存在し得る領域(mute、通知、認証、実行許可)では、片方で「無い」ことを確認しても他経路の存在を否定しない**。メモリや文書が経路を明記している場合は、その経路を実際に見るまで否定的結論を出さない。
5. 上記1〜4の作法と、反復検出されている欠陥クラス(宙ぶらりん参照・規範の消失・撤回した根拠の残存・判定ラダーの全域性/一意性・文書内の自己整合・追跡表のドリフト・適用範囲の広狭変化)は、**`skills/document-norm-review/SKILL.md`へSkill新設済み**(2026-07-27の月次Knowledge振り返り)。規範文書のレビュー手順の正本はそちらで、本Lessonは失敗事例(根拠)側として残す。
