# requirement: Loki調査語彙の追加と、調査手段の所在の是正

日付: 2026-09-01
状態: 起案(Yoshinobu合意済み、2026-09-01)

## 1. 背景

2026-09-01、Yoshinobuから「monnieのLokiにwarning/errorが溜まっているが誰も見ていない」という提起があった。Coordinatorが調査したところ、**読み取り経路は既に存在した**(`monnie-investigate` の `loki-count` / `loki-window`、AR-095〜AR-101、2026-07-29導入)。実際にその場で24時間分のlevel別件数を取得できている。

**問題は2つ出た。**

### 欠陥1: 到達可能な調査手段が、正本のカタログに載っていない

`EXEC-043` は「Coordinator自身が使える手段はdispatchが公開する名前付きチェックだけである。**一覧は `docs/ai/reviews/dev_prod_boundary/2026-08-03_008_phase3_check_catalog.md`**」と定める。

そのカタログに `loki-helper` は載っているが、**`deployed-hash` の照合対象(配備物のハッシュを見る先)としてのみ**である。**問い合わせ語彙である `loki-count` / `loki-window` は載っていない。** Loki横断調査の導入は2026-07-29、カタログの最終更新は2026-08-08であり、追加時に反映されなかった。

`EXEC-003` の `monnie` 行は「読み取り専用の名前付きチェックは `monnie-investigate` で今も通る」とだけ書き、**何ができるかを書いていない**。

結果として、**Coordinatorは自分が使える手段を知らないまま「測定用playbookを新規に作る」計画を立てた**(2026-09-01、Yoshinobuの指摘で気づいた)。規範や機能が存在しても、読み手が辿れる場所に無ければ無いのと同じ、という2026-08-25の監査と同じ欠陥クラスである。

### 欠陥2: errorの横断調査に語彙が足りない

`loki-window` の窓は最大 `1h`(AR-098の出力量制限)。24時間分のerrorを見るには **job数 × 24回** の呼び出しが要る。実測ではerrorは1日7件しかなく、量の問題ではなく**語彙の形の問題**である。

## 2. 目的

1. **error行を横断・長時間窓で取得できる語彙を1つ足す**
2. **到達可能な調査手段の一覧を、正本のカタログと `EXEC-003` へ反映する**

**本案件は検知(alerting)を実装しない。** syslog系統の週次ダイジェストは別案件(`docs/ai/reviews/syslog_weekly_digest/`)として保留中である。

## 3. 追加する語彙

```
loki-errors <since> <window>
```

- `<since>`: `YYYY-MM-DDTHH:MM`(分精度、常にJST。既存2語と同じ)
- `<window>`: `1h` / `6h` / `12h` / `24h`
- **全jobを横断**して `level="error"` の行を時刻昇順で返す

## 4. 受入条件

- **AC1**: `monnie-investigate "loki-errors <since> 24h"` が、全jobのerror行を時刻昇順で返す
- **AC2**: **既存の出力量制限(`QUERY_LIMIT` / `MAX_LINES` / `MAX_LINE_LENGTH`)を緩めない。** 新語彙のために定数を大きくしない
- **AC3**: 上限で切り詰めたとき、**`loki-window` と同じ形式で「要求した窓のうちどこまで実際に読めたか」を出力する。** 行数だけの通知にしない(2026-07-29の事故 — 窓の前半だけ読んで「errorなし」と結論した — と同じ形を作らない)
- **AC4**: **`level` ラベルを持たない行はこの語彙では取得できない**ことを、**出力自身が明示する**。`network-devices`(実測7,471行/日)は全行がlevel無しであり、`loki-errors` の結果だけを見て「環境全体でerrorはN件だった」と結論できてしまう経路を塞ぐ
- **AC5**: 引数検証は既存2語と同じ規律に従う — dispatch側で正規表現/allowlist検証を行い、helperへは**位置渡し**する(`eval`・シェル文字列の再解釈を経由しない、AR-097/AR-048)。helper側でも同じallowlistを再確認する(防御の重複)
- **AC6**: 不正な `since` / `window` / 余分なoperandは `denied:` で拒否され、helperが起動しない
- **AC7**: カタログ(`2026-08-03_008_phase3_check_catalog.md`)に、**問い合わせ語彙として** `loki-count` / `loki-window` / `loki-errors` が載る。既存の `loki-helper`(deployed-hash対象)の行と混同しない形にする
- **AC8**: `EXEC-003` の `monnie` 行から、**何ができるか**(Lokiの横断ログ調査を含む)とカタログへのポインタが辿れる

## 5. 制約

- **実装の正本はdispatch。** `roles/recovery_exec/templates/recovery-investigate-dispatch.sh.j2` と `roles/recovery_exec/files/recovery-loki-helper` の両方を変更する
- **quory側wrapper(`homelab-investigate.sh.j2`)の扱いを確認すること。** 既存2語がwrapperにも登録されているなら同じ規律で追加する。**wrapperがoperand形式の事前検証だけを行いLokiへ問い合わせない**という現行の設計(helperのdocstring)を崩さない
- 既存の `loki-count` / `loki-window` の挙動を変更しない
- **配備しない。** 本案件は実装とドキュメントまで。配備はquoryのSemaphore(Yoshinobu起動)で別途行う
- IPアドレス・秘密情報を出力しない

## 6. 検証の制約

- **ansyからmonnieへAnsibleは到達できない**(`id_ann` は削除済み)。実装者は実機で検証できない
- 到達性の検証はCoordinatorが配備後に `monnie-investigate` で行う
- 実装段階での検証は、**dispatchの引数検証ロジック(bash)とhelper(Python)の単体レベル**に限る
