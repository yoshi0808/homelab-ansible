# Requirement: Proxmoxクラスタ状態調査(read-only investigate)

会話(walk-through)を経て確定した最終設計。pve1/pve2はSlack/Codex経由でのProxmoxクラスタ/HA状態の調査(read-only)のみ対象とし、復旧アクションは一切追加しない。

## 前提

- pve1/pve2は自律復旧アクション(自己回復・pingベースのラダー)の対象外(既存policy §2)。この点は変更しない。今回追加するのはread-only investigateのみ。
- Codex別identityは作らない。既存recovery-execの枠組みに収める。

## 確定要件

1. **鍵**: `ann`の鍵は使わない。quory recovery-exec用の投資gate鍵を新規1本(`id_recovery_investigate_pve`)作成し、既存の`id_recovery_investigate`(authy/monnie用)とは分離。pve1/pve2両方の`authorized_keys`に同一鍵を登録(片方が落ちていてももう片方から見るため)。
2. **着地**: pve1/pve2両方に`recovery-exec`着地アカウント(forced commandのみ)を新規作成。`ann`とは別アカウント。
3. **dispatch script**: 既存`recovery-investigate-dispatch.sh`と同設計。許可リストは`pvesh get`/`ha-manager status`系のみ。create/set/delete系は一切含めない。
4. **named check(3つ、完全固定・実績あり)**:
   - `cluster-status` → `pvesh get /cluster/status --output-format json`(実績: `roles/recovery_ha_failover/tasks/main.yml`)
   - `cluster-resources` → `pvesh get /cluster/resources --output-format json`(実績: 多数のrole)
   - `ha-status` → `ha-manager status`(実績: `roles/proxmox_evacuate_node`, `roles/proxmox_restore_vm_placement`)
   - node-status(`/nodes/<node>/status`)は本リポジトリに実績が無く、`cluster-resources`の`type=node`エントリで代替できるため見送り。可変パラメータ・パラメータ照合ロジックは無し(3つとも完全固定named check)。
5. **sudoers**: 完成形3本を1:1で列挙(ワイルドカード無し)。このsudoはpve1/pve2上のSSHセッション内(sshd経由)で完結するため、quory側Codexサンドボックスの`no_new_privileges`問題には該当しない。
6. **実装前提の確認事項**: pve着地アカウントでforced command経由(tty無し)のsudoが通るか(`requiretty`等で弾かれないか)を、実機デプロイ後の最初の確認として残す。Proxmox(Debian系)のsudoersデフォルトがauthy/monnie(Ubuntu)と異なる可能性があるため。段取り: 着地アカウント作成 → `cluster-status`1本のみでtty無しsudoの疎通を確認 → 通ったら残り2本を含めて検証。
7. **policy文言**: `autonomous_recovery_policy.md`は既存§1〜§11構成。§2に一文追加(番号は増やさない)、新設は**§4.6**として追加。
8. **AGENTS.md**: 「pve1/pve2への復旧アクションは追加しない、調査のみ」を明示。Prohibitionsのツール一覧にも追加。

## スコープ外(今回やらないこと)

- node-status系(`/nodes/<node>/status`)
- pve1/pve2への復旧アクション・action_services
- 別Codex identityの新設
- quory/pve1/pve2への実機デプロイ・実機テスト(本requirement/implementはコード追加+syntax確認まで)
