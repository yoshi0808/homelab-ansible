## 指摘

### 1. [must-fix] authoritative host が extra vars で上書き可能であり、quory に固定されていない

対象:

- `roles/recovery_exec/defaults/main.yml:28-35`
- `roles/recovery_exec/tasks/main.yml:314-337`

`recovery_exec_setup_authoritative_host: quory` は role defaults なので、Ansible の変数優先順位上、
次のような extra var で容易に上書きできる。

```text
ansible-playbook playbooks/recovery_exec_setup.yml -l ansy \
  -e recovery_exec_setup_authoritative_host=ansy
```

この場合、assert は `ansy in ['ansy']` で通過し、include の
`inventory_hostname == recovery_exec_setup_authoritative_host` も true になるため、ansy の
鍵を targets へ排他配布できる。これは 2026-07-08 の事故経路そのものであり、コメントの
「Pinned to quory」「sole host whose keys may ever be distributed」と実際の保証が一致しない。

安全境界となる配布元は、通常の設定用 default として公開しないこと。少なくとも assert
と include の許可条件は上書き不能なリテラル `quory` に固定する必要がある。名前を
一元化したい場合でも、ユーザーが `-e` で変更可能な値だけを信頼してはならず、
`recovery_exec_setup_authoritative_host == 'quory'` を別途 assert してから利用するなど、
最終的な trust anchor はコード上の固定値にすること。

## 前回指摘の確認

### 全体実行の退行

**解消。** targets=true では正規配布元が play 全対象に含まれることを全ホストで確認し、
target_setup は authoritative host だけが include する2段構造になった。現行 default の
ままなら、次の挙動になる。

- `-l ansy`: assert fail、targets 配布なし
- `-l ansy -e recovery_exec_setup_targets=false`: assert pass、include skip
- `-l quory`: assert pass、quory が include
- 制限なし: ansy/quory とも assert pass、ansy は skip、quory だけ include

### 許可主体の quory 固定

**一部解消だが未完了。** `control_nodes` group membership への依存は除去され、将来同 group
に別ホストを追加しただけでは配布権限は増えない。一方、default 変数が extra vars で
変更可能なため、must-fix 1の経路が残る。

### tester-gate 理由文

**解消。** ガードの保証範囲を target authorized_keys の横方向上書き防止に限定し、
前段のローカル変更は従来どおり実行されることを明記している。risk-accepted 継続理由が

## `ansible_play_hosts_all` の確認

今回の「limit 適用後、この play が対象とする全ホスト集合に quory が含まれるか」の
判定には `ansible_play_hosts_all` が適切である。

- `-l ansy` では ansy のみ、`-l quory` では quory のみ、制限なしでは ansy/quory を含む。
- 実行途中でホストが failed/unreachable になっても、そのホストは
  `ansible_play_hosts_all` から除外されない。これは `ansible_play_hosts` と異なる。
- `serial` を指定した場合も現在バッチだけではなく play 全体の対象を表すため、先の
  バッチが ansy、後のバッチが quory でも ansy 側の集合判定は通る。ansy は include
  条件で配布しないため安全で、後の quory バッチが配布する。
- quory が配布前に failed/unreachable になった場合、集合判定自体は通り得るが、quory
  以外は include できず target は変更されない。play は quory の失敗を保持するため、
  silent success や ansy 鍵配布にはならない。

このため `ansible_play_hosts_all` を `ansible_play_hosts` や batch 集合へ変更する必要はない。
