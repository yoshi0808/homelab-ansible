## 結論

`playbooks/recovery_exec_setup.yml` の `# tester-gate: risk-accepted` を確認し、
Yoshinobu 承認済みの方針に従って quory へ通常実行した。play recap は
`ok=51 changed=8 unreachable=0 failed=0` で、pve1/pve2 上の
`visudo -cf` validate は双方で成功した。

ただし、実機 preflight で次の2件を検出したため、Phase 2 は確定不可と判定する。

1. pve1/pve2 の `qm` 実パスはともに `/usr/sbin/qm` だが、dispatch と sudoers は
   `/usr/bin/qm` を固定している。このため `vm-status` / `vm-config` は双方で
   `sudo: /usr/bin/qm: command not found`（rc=1）となる。
2. pve1/pve2 とも `pvesr.service` は `LoadState=not-found` である。
   他の4 unit は loaded だが、要件の「全5 journal unit 実在」を満たさない。
   `journal-unit pvesr <window>` は rc=0 + `-- No entries --` となり、まさに要件が
   警戒した silent failure になる。

上記は検出時点で `claude` へ agmsg で速報済み。復旧アクション、書込系コマンド、
本番 VM 操作は一切実行していない。

## tester-gate と実行方針

- marker: `risk-accepted`
- STEP 1 は承認済みの通常実行とし、`--check` は付けなかった。
- `tester_mode` / `-e tester_mode=true` は使用していない。
- STEP 2 は read-only の wrapper、Ansible ad-hoc、forced-command dispatch のみを使用した。
- 実 VMID / storage / job-id / UPID はこのファイルではすべて一般化した。実値・IP は
  コミット対象へ残していない。

### forced-command invalid matrix

wrapper の一次フィルタだけでなく本ゲートを検証するため、quory の
`recovery-exec` から pve 専用鍵で forced-command SSH を直接呼び、requirement の
invalid matrix を pve1/pve2 双方へ投入した。接続先、鍵、known_hosts は配備済み
wrapper と同じ固定値を用いた。

```text
vm-status -h
vm-status --help
task-log -x
vm-conf-stat 0
vm-conf-stat 1/../../etc/shadow
replication-read <VALID_SHAPE_JOB_ID>;id
storage-status-one a b
vm-tasks <VALID_VMID> 99999
journal-unit sshd 2h
journal-unit pvesr 99h
vm-status <VALID_VMID> extra
```

この置換理由は、通常 wrapper 経由では wrapper 自身が先に拒否し、pve 側 dispatch
（本来の権限境界）を実機検証できないためである。すべて read-only の拒否確認であり、
sudo コマンドは実行されていない。

## 結果詳細

### PASS

- pve1/pve2 の target-side `visudo -cf`: PASS。
- forced-command + `ssh -T`（no-pty）+ `sudo -n`: PASS。
  `cluster-status` を含む全既存 check が tty 要求で失敗しなかった。
- 既存12 check: pve1/pve2 双方ですべて rc=0。cluster/HA/quorum、replication、
  storage/ZFS、journal の期待する read-only 出力を確認した。
- 新9 check のうち次は pve1/pve2 双方で PASS:
  - `replication-read`
  - `vm-tasks`
  - `task-log`
  - `storage-status-one`
  - `zfs-list-vm`
  - `vm-conf-stat`
  - `journal-unit`（実在する `pvestatd` を使用）
- `vm-conf-stat` / `zfs-list-vm` は各ノードにローカルな VMID を選び直して PASS。
  最初に pve1 からリモートノード所属 VM の local config path を指定した際の
  `No such file` は実装不具合ではなく operand 選択の誤りだった。
- invalid matrix: 11/11 を pve1/pve2 双方で rc=1 + `denied:` として拒否。
  option injection、traversal/metachar、limit 超過、unit/window allowlist 外、
  過剰トークンを dispatch が sudo 到達前に拒否した。
- `sudo -l -U recovery-exec`: Phase 2 rule は固定 read-only 動詞 + operand wildcard
  の形で列挙され、`qm *` / `pvenode task *` / `journalctl -u *` のような動詞・unit
  wildcard は存在しなかった。
- 配備済み AGENTS.md に新 check と、VM replication 障害時の
  `replication-read` → `vm-status` → `vm-tasks` → `task-log` の調査順を確認した。
- quory に `homelab-recover-pve1` / `homelab-recover-pve2` は存在しなかった。
- `--syntax-check`, `bash -n`, tester-gate lint（33 playbooks）, `git diff --check`: PASS。
