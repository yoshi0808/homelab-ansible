## 1. デプロイ状態確認

```bash
ansible pve1 -b -m ansible.builtin.command -a "id recovery-exec"
ansible pve2 -b -m ansible.builtin.command -a "id recovery-exec"
```

結果:
- pve1: `uid=1002(recovery-exec) gid=1002(recovery-exec) groups=1002(recovery-exec)`
- pve2: `uid=1002(recovery-exec) gid=1002(recovery-exec) groups=1002(recovery-exec)`

補足:
- Claude Code の最初のメッセージでは uid/gid 1004 と例示されていたが、実機では pve1/pve2 とも 1002。
- `recovery-exec` ユーザー/グループ自体は両ノードで存在する。

```bash
ansible pve1 -b -m ansible.builtin.command -a "visudo -cf /etc/sudoers.d/recovery-exec-pve"
ansible pve2 -b -m ansible.builtin.command -a "visudo -cf /etc/sudoers.d/recovery-exec-pve"
```

結果:
- pve1: `/etc/sudoers.d/recovery-exec-pve: parsed OK`
- pve2: `/etc/sudoers.d/recovery-exec-pve: parsed OK`

```bash
ansible pve1 -b -m ansible.builtin.command -a "which ha-manager"
ansible pve2 -b -m ansible.builtin.command -a "which ha-manager"
```

結果:
- pve1: `/usr/sbin/ha-manager`
- pve2: `/usr/sbin/ha-manager`

判定:
- `ha-manager` の実パスは sudoers 側の想定パスと一致。
- パス不一致による停止条件には該当しない。

## 2. forced command 経路の段階的 sudo 疎通確認

まず test_plan 指定どおり、`cluster-status` 1本のみを quory 起点で確認した。

```bash
ansible quory -b -m ansible.builtin.command -a "sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve1 cluster-status"
```

結果:

```text
sudo: '/usr/local/bin/homelab-investigate-pve1': command not found
```

quory にはこの時点で `homelab-investigate-pve1` が未配備だったため、test_plan の指示どおり ansy 起点へフォールバックした。

```bash
ansible ansy -b -m ansible.builtin.command -a "sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve1 cluster-status"
```

結果:
- 成功。
- cluster は `quorate=1`。
- ノード数は2。
- pve1 / pve2 はどちらも `online=1`。
- `requiretty` 等による sudo 失敗は発生しなかった。

判定:
- ansy 起点では、`homelab-investigate-pve1` → SSH forced command → pve1 側 dispatch → tty無し sudo の経路が成功。
- 残りの `cluster-resources` / `ha-status` へ進める条件を満たした。

## 4. 拒否系確認

```bash
ansible ansy -b -m ansible.builtin.command -a "sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve1 node-status"
```

結果:

```text
denied: unknown check 'node-status'
```

```bash
ansible ansy -b -m ansible.builtin.command -a "sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve1 'cluster-status; id'"
```

結果:

```text
denied: unknown check 'cluster-status; id'
```

判定:
- requirement で見送り済みの `node-status` は拒否された。
- シェル注入風の文字列も拒否された。
- いずれも ansy 側 wrapper の allowlist で止まり、pve1 への実SSH接続前に拒否される設計どおり。

## 結論

Phase 1(ansy起点)の Proxmoxクラスタ状態調査 read-only investigate 確認は完了。

- pve1/pve2 の `recovery-exec` ユーザーは存在。
- pve1/pve2 の sudoers は `visudo -cf` を通過。
- `ha-manager` パスは両ノードとも `/usr/sbin/ha-manager`。
- quory 起点では wrapper 未配備のため `command not found`。test_plan 指示どおり ansy 起点へフォールバック。
- ansy 起点の `cluster-status` は成功し、tty無し sudo 疎通は確認済み。
- `cluster-resources` / `ha-status` は pve1/pve2 両方で成功。
- 拒否系は期待通り `denied: unknown check`。

注意点:
- pve1/pve2 の uid/gid は 1002 であり、Claude Code の初回メッセージにあった 1004 ではなかった。実運用上問題かどうかは Claude Code / Yoshinobu 側で判断が必要。
