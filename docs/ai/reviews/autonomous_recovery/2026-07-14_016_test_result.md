結果:

- recovery_io: `ok=17 changed=2 failed=0`。
- unit template changed 後、handler で daemon reload と `recovery-io` restart が実行された。
- 最終的に `recovery-io.service` は active。

### writable scope / ACL

live state:

```text
ProtectSystem=strict
ReadWritePaths=/home/recovery-exec /var/lib/recovery-exec/workspace /var/lib/homelab-recovery/mute
writable_roots=[/var/lib/homelab-recovery/mute]
```

- recovery-io の mount namespace 内で mute directory は rw。
- Codex の追加 writable root は mute directory 1 箇所だけ。
- Codex config は `default_policy = deny` と mute wrapper 3 本の allow を維持。
- mute directory ACL:
  - `user:recovery-exec:rwx`
  - `group::r-x`
  - `mask::rwx`
  - `other::r-x`
- `recovery-io` user 自身の `test -w` は失敗（期待どおり）。systemd の
  `ReadWritePaths` は DAC/ACL を迂回せず、write 主体は recovery-exec に限定されたまま。

### 実 Codex set/status/clear

Slack listener 自体にはローカル CLI が無いため、active な `recovery-io.service` の MainPID の
mount namespace に `nsenter -m` し、その中で本番と同じ
`sudo -H -u recovery-exec codex-exec-wrapper exec --cd <workspace> <message>` を実行した。
これにより T1 の対象である systemd mount namespace と Codex bwrap sandbox の 2 層を
実プロセスで同時に通した（Slack Socket Mode の外部メッセージ配送部分は対象外）。

Codex 起動表示:

```text
sandbox: workspace-write [workdir, /tmp, $TMPDIR, /var/lib/homelab-recovery/mute]
```

実行結果:

1. `homelab-mute-set monnie 1 sandbox-retest`: 成功、残り 1 分を表示。
2. `homelab-mute-status`: `monnie MUTED(1m)` と reason を確認。
3. `homelab-mute-clear monnie`: 成功。

前回の read-only filesystem エラーは再現しなかった。最後に monnie mute file が無いことを確認。

`/tmp` 配下へ変更し、SSH は repository wrapper と同じ `-F /dev/null` を使用した。

内で本番と同じ Codex wrapper/user/arguments を実行する方法へ置換した。これは外部投稿を伴わず、
修正対象の systemd namespace と bwrap writable-root を両方検証するための置換である。
