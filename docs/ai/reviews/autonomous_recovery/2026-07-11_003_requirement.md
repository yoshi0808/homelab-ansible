# recovery_exec_setup の安全化（横方向クロバー再発防止）— 要求仕様

- 日付: 2026-07-11
- 起案: claude（要件定義・ハブ役）/ 承認: Yoshinobu（2026-07-11 開発フロー投入を承認済み。本文の最終確認は claude→implementer 送付前に実施）
- 優先度: 通常（緊急修復は 2026-07-11_002 で完了済み。本件は構造的な再発防止）

## 目的

`recovery_exec_setup.yml` を `-l` 等で対象制限して実行した場合（特にテスト目的の
非本番制御ノードでの実行）でも、本番制御ノード（quory）の recovery-exec 公開鍵が
対象ホスト（monnie / pve1 / pve2）の authorized_keys から除去・置換されないようにする。

## 背景（インシデント要約）

2026-07-08 のバッチテストで `-l ansy` の通常実行が `recovery_exec_setup_targets=true`
（default）のまま動き、targets の authorized_keys を「ansy の鍵のみ」で排他上書き
（drift-safe）した。結果、quory からの investigate SSH が全ホストで
`Permission denied (publickey)` となり、2026-07-11 の Proxmox パッチ作業中に発覚するまで
自律復旧の調査能力が停止していた。詳細:
`docs/ai/reviews/autonomous_recovery/2026-07-11_002_ssh_key_investigation.md`

## 対象ホスト / 対象ファイル

- `playbooks/recovery_exec_setup.yml` および配下の該当 role（鍵配布タスク周辺）
- 対象ホストへの影響範囲: quory（本番制御ノード）、ansy（開発/テスト）、
  monnie / pve1 / pve2（配布先 targets）

## 実施項目

1. 「対象を制限した実行が、制限外の正規制御ノードの鍵を targets から消す」ことを
   構造的に不可能にする。**方式は実装判断に委ねる**が、候補と選定理由を implement に
   記載すること。候補例（これに限らない）:
   - targets への鍵配布の default を無効化し、明示フラグ指定時のみ配布する
   - 配布内容を「本番として意図された制御ノード集合の鍵」に固定し、実行時の
     `-l` に依存させない
   - quory を含まない実行での targets 配布を assert で拒否する
2. tester-gate 分類（現在 risk-accepted）の理由文を再評価し、必要なら更新する。
   今回の事故は「本番影響ゼロ/軽微」判断が横方向の影響（他制御ノードの資格情報の
   置換）を見落とした実例であるため、理由文にこの観点を反映する。

## 確認項目

- `-l ansy` 相当の制限実行（または --check とコード検査の組み合わせ）で、
  targets の quory 鍵が失われないこと
- quory からの正規実行（`-l quory` または全体実行）は従来通り機能すること
- 修復済みの現行本番状態（quory 鍵のみが targets に登録）を壊さないこと

## 制約

- 秘密鍵の内容を読まない・扱わない（公開鍵と fingerprint のみ）
- IP アドレスをリポジトリに書かない
- shell は収集・実行のみ、判定・制御は Ansible tasks 側（core.md §7）
- 実ホスト検証は tester 工程で行う（implementer は実ホストに触れない）
