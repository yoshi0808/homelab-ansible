# recovery_exec_setup の安全化(横方向クロバー再発防止)— 実装報告

対象要求仕様: `2026-07-11_003_requirement.md`(インシデント調査:
`2026-07-11_002_ssh_key_investigation.md`)

## 実装概要

`recovery_exec_setup.yml` の target(authy/monnie/pve1/pve2)への鍵配布処理に、
「実行元ホストが `control_nodes` グループ(quory)に属する場合のみ許可する」
`assert` を追加した。これにより `-l ansy` のような対象制限実行が targets の
authorized_keys を書き換えることが構造的に不可能になる。

## 方式の選定

要求仕様の候補例3つを検討した。

| 候補 | 検討結果 |
| --- | --- |
| 1. targetsへの鍵配布のdefaultを無効化し、明示フラグ指定時のみ配布 | 有効だが単独では不十分。デフォルトを`false`にしても、誰かが `-l ansy -e recovery_exec_setup_targets=true` を明示的に(誤って)指定すれば元のインシデントと同じ事故を再現できてしまう。「構造的に不可能にする」には至らない |
| 2. 配布内容を「本番として意図された制御ノード集合の鍵」に固定し、実行時の`-l`に依存させない | 実装が重い。現状 `target_setup.yml` は実行中ホストの `.pub` を毎回 slurp する設計(`authorized_keys.j2` は「実行元ホストの鍵で完全上書き」という drift-safe ポリシー)であり、これを「quory固定の鍵」に変えるには slurp元を`delegate_to: quory`にするなどの構造変更が要る。初回実装で除外された「鍵管理の再設計」に踏み込みかねない |
| **3. quoryを含まない実行でのtargets配布をassertで拒否する(採用)** | 実行元ホストの `inventory_hostname` が `control_nodes` グループに属するかどうかは inventory から直接判定できる。`recovery_exec_setup_targets` のデフォルト値に関係なく、常にこの assert がゲートになるため「構造的に不可能」を最も直接的に満たす。実装量も最小 |

**採用**: 候補3(assert によるホスト所属チェック)。単独で「対象制限実行が正規制御
ノードの鍵を消すことを構造的に不可能にする」という要求を満たすため、候補1・2は
併用しなかった(単純さを優先。候補1のデフォルト変更は、既存の `-l ansy -e
recovery_exec_setup_targets=false` という確立済みの運用パターン
[`docs/ai/prompts/autonomous_recovery_deploy_runbook.md`] に対して意味のある
追加保護を与えない一方、"targetsのデフォルトがいつの間にかfalseになった"という
別の混乱を生みかねないため見送った)。

## 作成・更新したファイル

- `roles/recovery_exec/tasks/main.yml`
  - 「Setup recovery-exec on target nodes」タスクの直前に
    `Assert target node key distribution only runs from a production control node`
    を追加。`recovery_exec_setup_targets` が true の場合のみ
    `inventory_hostname in groups['control_nodes']` を要求し、falseの場合は
    ホストに関わらず何もしない(既存の「targetsをスキップする」用途は維持)
  - コメントでインシデントの経緯と、なぜ drift-safe な
    `authorized_keys.j2`/`authorized_keys-pve.j2` の設計(実行中ホストの鍵で
    完全上書き)がこの脆弱性を生んだかを明記
- `roles/recovery_exec/defaults/main.yml`
  - `recovery_exec_setup_targets` のコメントを更新し、デフォルト`true`のままでも
    上記assertがcontrol_nodes以外への配布を防ぐことを明記
- `playbooks/recovery_exec_setup.yml`
  - `tester-gate: risk-accepted` の理由文に2026-07-11の追記を追加。旧理由文は
    「単一ホストへの影響」のみを評価しており、target authorized_keysの排他上書き
    という横方向の影響を見落としていたことを明記。新しいassertにより単一ホスト・
    横方向いずれの影響も生じないことが保証されるため、risk-accepted分類自体は
    継続する旨を記載(要求仕様の実施項目2への対応)

## 動作確認(ローカル、実ホスト非依存)

`groups['control_nodes']` / `groups['dev_nodes']` の実際のinventory所属を
read-onlyで確認:

```
$ ansible-inventory -i inventories/homelab/hosts.yml --graph
  |--@control_nodes:
  |  |--quory
  |--@dev_nodes:
  |  |--ansy
```

assertの論理式そのものを、実inventoryに対し `connection: local` (実SSH接続なし)・
`gather_facts: false` の使い捨てplaybookで検証(確認後に削除):

```
TASK [Assert target node key distribution only runs from a production control node]
fatal: [ansy]: FAILED! => ... "evaluated_to": false ...   # 期待通りブロック
ok: [quory]                                                # 期待通り通過
```

`ansy` ではブロック、`quory` では通過することを確認した。

1. **`-l ansy` 相当の制限実行でのブロック確認**: `-l ansy`(recovery_exec_setup_targets

   変更されないことを実地確認

   鍵生成・wrapper配置のみ行われ、assertはスキップされること)
3. **`-l quory` の正規実行確認**: assertを通過し、これまで通りtargetsへの配布が
   行われること(現行本番状態を壊さないこと)
4. **現行本番状態の非破壊確認**: 2026-07-11の修復で復元済みの
   quory鍵のみが登録されている状態が、今回の変更後も変わらないこと
