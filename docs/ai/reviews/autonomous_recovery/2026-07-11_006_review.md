## 結論

**要修正（must-fix 2件、suggestion 1件）。**

現在の assert は `-l ansy` かつ targets=true の事故経路を遮断し、変数未定義時も
安全側へ倒れる。一方、要件で維持対象とされた制限なしの全体実行が失敗するほか、
許可主体を quory ではなく `control_nodes` 所属全体に広げているため、将来の inventory
変更で同型事故が再発し得る。

## 指摘

### 1. [must-fix] 制限なしの全体実行が ansy の assert で失敗する

対象: `roles/recovery_exec/tasks/main.yml:300-317`

play は `hosts: dev_nodes:control_nodes` であり、制限なしでは ansy と quory の両方が
role を実行する。targets の既定値は true なので、ansy では
`inventory_hostname in groups['control_nodes']` が false となり assert が失敗する。
quory 側が後続処理を継続できても play 全体は failed となるため、要求仕様の確認項目
「quory からの正規実行（`-l quory` または全体実行）は従来通り機能すること」を
満たさない。

全体実行時は、targets 配布を quory の1ホストだけが実行し、ansy はローカル setup 後に
targets 配布をスキップする構造が必要である。一方、quory を含まない `-l ansy` かつ
targets=true は明示的に fail させる必要がある。たとえば次の2段階を分離する。

1. targets=true の場合、play の実行対象集合に正規配布元 quory が含まれることを assert
2. target_setup include は `inventory_hostname == 'quory'` の場合だけ実行

この構造なら `-l ansy` は fail、`-l ansy -e recovery_exec_setup_targets=false` は成功、
`-l quory` と全体実行は成功し、全体実行でも ansy 鍵は配布されない。

### 2. [must-fix] `control_nodes` の任意ホストを配布元として許可し、再発防止が inventory 構成に依存している

対象: `roles/recovery_exec/tasks/main.yml:296-303`

要件とインシデントの保護対象・正規配布元は quory である。しかし現在の条件は
`inventory_hostname in groups['control_nodes']` なので、将来 `control_nodes` に別ホストを
追加すると、そのホスト自身の別鍵で targets の authorized_keys を排他上書きできる。
これは ansy が同じことをした今回の事故と同型であり、「構造的に不可能」という目的を
長期的には満たさない。

正規配布元を明示的に quory（または default が quory の専用変数）へ固定し、targets の
include もその1ホストだけに限定すること。グループ所属は inventory の役割分類であり、
排他的 credential の正本を一意に選ぶ条件としては弱い。

### 3. [suggestion] tester-gate 理由文の「単一ホストへの影響もない」は実際の挙動に合わせて修正する

対象: `playbooks/recovery_exec_setup.yml:38-42`

assert は role の末尾近くにあり、`-l ansy` かつ targets=true でも assert 到達前に
recovery-exec ユーザー、鍵、wrapper、sudoers、ACL 等のローカル変更は通常実行される。
したがって「単一ホストへの影響も他制御ノードへの横方向影響もない状態が保証される」
は過大な表現である。既存理由が受容している限定的なローカル変更は残る一方、今回の
ガードで排他的 authorized_keys の横方向上書きを防ぐ、という説明にすると実態と
要求仕様の実施項目2に整合する。

## 指定観点の確認

### assert 条件

- 変数未定義: `recovery_exec_setup_targets | default(true) | bool` により true と扱われ、
  ansy は拒否、現行 inventory の quory は許可される。安全側の挙動。
- `control_nodes` group/key が存在しない場合: `groups['control_nodes'] | default([])` により
  空集合として扱う意図で、targets=true の配布を許可しない。構文チェックは通過。
- `--check`: playbook の role import に `check_mode: false` があるため、assert を含め
  通常実行と同じゲートが働く。ただしローカル・target の変更も check mode では
  抑止されない既存仕様である。
- `-l ansy`, targets=true: assert で拒否し、target_setup より前に止まるため、今回の
  target authorized_keys 上書きは防ぐ。
- 全体実行: ansy が assert 失敗するため NG。
- 将来 control_nodes に別ホスト追加: そのホストの配布を許すため NG。

### 既存運用

- `-l quory`: 現行 inventory では assert を通過し、従来どおり target_setup を実行する。
- `-e recovery_exec_setup_targets=false`: assert の左辺で許可され、include も skip される。
- 制限なしの全体実行: 退行あり（指摘1）。

### tester-gate 理由文

インシデントと横方向影響を明記した点、および risk-accepted を再評価した点はよい。
ただしガードの保証範囲を過大に記載している（指摘3）。
