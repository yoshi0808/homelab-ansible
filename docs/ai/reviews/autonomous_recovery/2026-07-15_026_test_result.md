### STEP 2b-d: wrapper 実機確認

quory から次の形式で実行した。

```bash
sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve1 vm-status <VMID_PVE1>
sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve1 vm-config <VMID_PVE1>

sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve2 vm-config <VMID_PVE2>

sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve<N> \
  journal-unit <UNIT> 30m
```

`<UNIT>` は次の5種を pve1/pve2 双方で確認した。

```text
pvescheduler pvestatd pve-cluster corosync pvedaemon
```

結果:

- `vm-status`: 双方 rc=0、node-local VM の runtime status を取得。
- `vm-config`: 双方 rc=0、node-local VM の read-only config を取得。
- `journal-unit`: 5 unit × 2 nodes がすべて rc=0。
  直近30分に entry が無い unit は `-- No entries --` だが、unit 自体の
  `LoadState=loaded` は preflight で別途確認済み。
- `journal-unit pvesr 30m`: pve1/pve2 wrapper 双方で rc=1 + `denied`。

旧 unit が wrapper だけでなく target 側の権限境界からも除去されたことを確認するため、
配備済み pve 専用鍵の固定接続条件で forced-command dispatch へ直接
`journal-unit pvesr 30m` を送った。pve1/pve2 双方で rc=1 + `denied` となり、
sudo には到達しなかった。この置換は wrapper が先に拒否して dispatch を検証できないため。
