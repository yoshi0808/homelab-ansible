## 前提・制約

- pve1/pve2は本番Proxmoxホストであり、devの複製は存在しない。着地アカウント作成・sudoers・authorized_keys配置を含め、実機に触れる操作はrequirementで既にYoshinobuが合意した段取り(着地アカウント作成 → `cluster-status`1本でtty無しsudo疎通確認 → 残り2本)に沿って進める。
- 復旧アクション(VM reboot / HA failover / maintenance mode等)はこの機能に一切存在しない。tester・Claude Codeとも実行しない。
- `recovery_exec_setup.yml`の`target_setup.yml`は、pve1/pve2への着地アカウント・dispatch・sudoers・authorized_keys配置を`delegate_to`で行うため、**`-l ansy`実行時点で既に実機pve1/pve2へ反映される**(authy/monnieと同じ既存の挙動)。「ansy起点」とは、quory側資材(鍵生成・wrapperスクリプト・codex-config)をどちらの制御ホストに配備するかの違いであり、pve1/pve2自体への反映タイミングを分けるものではない。
- `authorized_keys-pve.j2`は1鍵のみを書く「drift-safe」設計(既存のauthy/monnie用authorized_keys.j2と同じ思想)。そのため`-l ansy`実行後に`-l quory`を実行すると、pve1/pve2の`authorized_keys`はquoryの鍵に置き換わり、ansyの鍵は使えなくなる。これは想定通りの挙動であり、既存authy/monnieでも同じ振る舞いをする。

## tester の実行義務

- playbook実行(実デプロイ)は、tester_mode常時付与ルールにより**tester自身は行わない**。Yoshinobuが`ansible-playbook playbooks/recovery_exec_setup.yml -l ansy`(その後`-l quory`)を実行し、完了をtesterに伝えてから確認作業に入る。
- 確認作業はread-onlyのみ(pvesh get系・ha-manager status系・アカウント/sudoers/鍵配備状況の確認)。
- 本機能はquory側でsudoを一切使わない(SSH clientの実行のみ)ため、②③で必要だった「実Codexサンドボックス経由での確認」は本質的には不要(no_new_privilegesの影響を受ける箇所が無い)。ただし、AGENTS.md/execpolicyへの反映確認は行う。

## Phase 0: 静的確認(実施済み、抜き取り再確認可)

```bash
ansible-playbook playbooks/recovery_exec_setup.yml --syntax-check
bash -n roles/recovery_exec/templates/homelab-investigate-pve.sh.j2 roles/recovery_exec/templates/recovery-investigate-dispatch-pve.sh.j2
bash scripts/check-tester-gate.sh
```

## Phase 1: ansy起点でのデプロイ(pve1/pve2への実反映を含む)

Yoshinobuが以下を実行:
```bash
ansible-playbook playbooks/recovery_exec_setup.yml -l ansy
```

### 1-1. デプロイ状態の確認(tester、read-only)

```bash
ansible pve1 -b -m ansible.builtin.command -a "id recovery-exec"
ansible pve2 -b -m ansible.builtin.command -a "id recovery-exec"
ansible pve1 -b -m ansible.builtin.command -a "visudo -cf /etc/sudoers.d/recovery-exec-pve"
ansible pve2 -b -m ansible.builtin.command -a "visudo -cf /etc/sudoers.d/recovery-exec-pve"
ansible pve1 -b -m ansible.builtin.command -a "which ha-manager"
ansible pve2 -b -m ansible.builtin.command -a "which ha-manager"
```
`which ha-manager`の結果が`/usr/sbin/ha-manager`と異なる場合、sudoers内のパスと不一致になるため直ちに報告する(実装側の修正が必要になる)。

### 1-2. 段階的sudo疎通確認(最重要・この順序を守ること)

まず**`cluster-status`1本のみ**を実際のforced command経路で実行する:
```bash
ansible quory -b -m ansible.builtin.command -a "sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve1 cluster-status"
```
(quoryでこの時点で`homelab-investigate-pve1`が無ければ、ansyの`recovery-exec`から同様に実行して構わない。ansy自身が`-l ansy`のデプロイ先であるため。)

- 成功した場合のみ、続けて`cluster-resources`・`ha-status`を確認する。
- `requiretty`等でsudoが失敗した場合は、**残りを試さずに直ちに停止し、Claude Code/Yoshinobuへ報告する**(sudoers設定の見直しが必要になる可能性があるため、自己判断で対処しない)。

```bash
# cluster-status成功後のみ実施
ansible quory -b -m ansible.builtin.command -a "sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve1 cluster-resources"
ansible quory -b -m ansible.builtin.command -a "sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve1 ha-status"
```

### 1-3. pve2側からの同様の確認

```bash
ansible quory -b -m ansible.builtin.command -a "sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve2 cluster-status"
ansible quory -b -m ansible.builtin.command -a "sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve2 cluster-resources"
ansible quory -b -m ansible.builtin.command -a "sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve2 ha-status"
```

### 1-4. 拒否系確認

```bash
ansible quory -b -m ansible.builtin.command -a "sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve1 node-status"
ansible quory -b -m ansible.builtin.command -a "sudo -u recovery-exec /usr/local/bin/homelab-investigate-pve1 'cluster-status; id'"
```
いずれも`denied: unknown check`で拒否され、pve1への実SSH接続自体が発生しないことを確認する。

## Phase 2: quory反映(別GO)

Yoshinobuの確認後、以下を実行:
```bash
ansible-playbook playbooks/recovery_exec_setup.yml -l quory
```
完了後、1-1〜1-4と同様の確認をquory起点で実施する(ansyの鍵は置き換わるため、ansy起点の確認は失敗するようになるが、これは想定通り)。

## Phase 3: 周辺確認

```bash
ansible quory -b -m ansible.builtin.command -a "grep -A2 homelab-investigate-pve /home/recovery-exec/.codex/config.toml"
ansible quory -b -m ansible.builtin.command -a "grep -A5 'Proxmox cluster' /var/lib/recovery-exec/workspace/AGENTS.md"
```
execpolicyとAGENTS.mdに新規コマンドが反映されていることを確認する。
