## 問題(tester 実測)

quory 上で `recovery-exec` として wrapper を直接呼ぶ場合は POSIX ACL(F1)により set/status/clear
とも成功する。しかし本番相当の `codex-exec-wrapper` から Codex を起動すると、sandbox 表示が
`workspace-write [workdir, /tmp, $TMPDIR]` であり mute directory が書き込み対象外で、
`homelab-mute-set` と `homelab-mute-clear` が read-only filesystem で失敗した(status は
read-only なので成功)。OS ACL(F1)とは別の、**Codex 自身の sandbox mount 層**の問題。

## 原因の特定(2層あることを確認)

Codex 実行経路には、OS の POSIX ACL とは独立に、書き込み可否を制御する層が **2つ** ある。
このうち mute dir はどちらにも登録されていなかった。

### 層 1: Codex 自身の bwrap sandbox(`sandbox_workspace_write.writable_roots`)

`--sandbox workspace-write` は既定で **workdir(`--cd` 先)+ `/tmp` + `$TMPDIR`** のみを
書き込み可能にする。既存の `[sandbox_workspace_write]` には `network_access` しか無く、
明示的な `writable_roots` エントリが無かった。既存の `/var/lib/recovery-exec`(recovery-exec の
home/workspace)がこれまで書けていたのは、`--cd $WORKSPACE` の **workdir 自体**がそこに
含まれ、既定の書き込み対象に自動的に入っていたため(明示指定不要だった)。mute dir
(`/var/lib/homelab-recovery/mute`)は workdir ではないため、既定の書き込み対象に入らず、
明示的な `writable_roots` 追加が必要。

キー名の確認方法(実機の codex-cli 0.144.1 バイナリで直接検証。憶測を避けるため):

- npm でインストール済みの実バイナリ
  (`/usr/lib/node_modules/@openai/codex/node_modules/@openai/codex-linux-x64/vendor/x86_64-unknown-linux-musl/bin/codex`、
  `codex --version` = `codex-cli 0.144.1`、recovery_exec_codex_bin と同一想定バージョン)から
  `strings` でシンボルを抽出したところ、`SandboxWorkspaceWrite` 構造体のフィールドとして
  `writable_roots`, `network_access`, `exclude_tmpdir_env_var`, `exclude_slash_tmp` が
  埋め込まれていることを確認。
- 実際に `writable_roots = ["/var/lib/homelab-recovery/mute"]` を追加した config.toml を
  `codex --strict-config doctor` に読ませ、`config.toml parse ok` / `config loaded` を確認
  (`--strict-config` は未知フィールドがあればここでエラーになる。認証エラーのみで
  config パースエラーは出なかった)。
- **実装している production の `codex-config.toml.j2` をそのまま Jinja レンダリングした結果**
  を上記 doctor に通し、execpolicy ルール一式(mute 3本含む)+ 新規 `writable_roots` を
  含む完全な本番相当ファイルが `--strict-config` を通ることを確認。

### 層 2: systemd `ProtectSystem=strict` の mount namespace(`recovery-io.service` の `ReadWritePaths`)

Slack 経由の経路(`recovery-io.service` → `sudo -H -u recovery-exec codex-exec-wrapper`)は、
`recovery-io.service.j2` の `ProtectSystem=strict` + `ReadWritePaths` で保護された mount
namespace の中で動く。bwrap は「呼び出し元プロセスから見えているファイルシステム」を
元に書き込み可能 bind mount を作るため、**このユニットの mount namespace 自体が
mute dir を read-only にしていれば**、Codex 側で `writable_roots` を設定しても、
Slack 経由の実行では依然として read-only になり得る(既存コメントが
`/var/lib/recovery-exec` について同じパターンを明記していた前例と同一)。

push 経路(authy/monnie の OnFailure → SSH forced command `recovery-push-dispatch.sh` →
`codex-exec-wrapper`)は sshd 配下の通常プロセスとして動作し、対応する systemd unit の
`ProtectSystem`/`ReadWritePaths` は存在しない(確認済み。recovery_push / recovery_exec に
該当 unit なし)。したがって層2の影響を受けるのは `recovery-io.service`(Slack 経路)のみ。

## 修正

- `roles/recovery_exec/templates/codex-config.toml.j2`
  - `[sandbox_workspace_write]` に `writable_roots = ["/var/lib/homelab-recovery/mute"]` を追加。
  - コメントを更新: workdir が既定で書き込み可能なため mute dir だけ明示指定が必要な理由、
    キー名を `--strict-config doctor` で確認した根拠を記載。
- `roles/recovery_io/templates/recovery-io.service.j2`
  - `ReadWritePaths` に `/var/lib/homelab-recovery/mute` を追加
    (`{{ recovery_io_exec_home }} {{ recovery_io_exec_workspace }} /var/lib/homelab-recovery/mute`)。
  - コメントを追加: このユニットの mount namespace が Codex の bwrap sandbox の書き込み可能
    root の元になるため、層1だけでは Slack 経路が救えない旨を明記。

execpolicy(mute wrapper 3本のみ許可、default deny)、POSIX ACL(F1)、flock(F2)には
変更なし。今回の変更は「sandbox がそもそも書き込みを試みられるか」という別層の話であり、
これらとは独立。

  新しい permission-profile 方式のコマンドで、named profile 定義が別途必要なため今回は
  見送り(wrapper の実際の呼び出し経路と異なる機構を検証しても意味が薄いと判断)。
  実際の bwrap 書き込み可否は tester の実 Codex 経路再テストで確認する。
- `systemd-analyze verify` をレンダリング済み `recovery-io.service` に対して実行し、
  当該ファイルに起因するエラーが無いことを確認(既存の2パス空白区切り構文を3パスに
  拡張しただけで、構文パターン自体は変更していない)。
