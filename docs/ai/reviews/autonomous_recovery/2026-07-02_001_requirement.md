## 要求 1: pull 検知 — quory 常駐 probe サービス(recovery-probe)

### 検知対象と信号

| 対象 | probe 信号 | 補足 |
|---|---|---|
| sophos-fw | LAN 側 IP への ICMP + DNS クエリ応答(内部 DNS の生死を直接見る) | IP は /etc/hosts / 実行時解決。リポジトリに IP リテラルを書かない(core.md §3) |
| authy | ICMP + RADIUS ポート応答 | サービスレベル probe の深さは実装時に判断(まず ICMP+ポートで開始) |
| monnie | ICMP + HTTP(:3000) | 同上 |

### 判定ロジック

1. **閾値: 60 秒間隔 × 5 回連続失敗**(検知まで約 5 分)。
   - 根拠: mute を忘れて Sophos の GUI パッチを開始した場合でも、通常のパッチリブート
     (2〜3 分)なら発火前に復帰するマージンを取る(Yoshinobu 判断 2026-07-02)。
   - 残存リスク: 5 分超の無応答を伴うパッチではラダーが発火し得る。運用上は mute CLI の
     使用を正とし、閾値はセーフティネットと位置づける。
2. **ISP 切り分け(sophos-fw)**: LAN 応答あり・外部到達性なし → ISP 障害。発火しない
   (ローカルログ + 復旧後に遅延通知)。LAN 無応答のときのみ次へ。
3. **ハイパーバイザ確証**: quory → pve(/etc/hosts 解決)で `pvesh get` により VM 状態を確認。
   - running なのに LAN 無応答 → ハング → ラダー起動(sophos-fw: reboot → failover)
   - stopped → reboot ではなく start
   - pve クラスタ到達不能 → エスカレーション(ローカル記録、通知は復旧後)
4. **起動前チェック**は §8.4 どおり: allowlist / 実行中ロック / mute / flapping。

### mute との連動(誤爆防止の第一防御)

- probe は**判定の前に** mute ファイル(`/var/lib/homelab-recovery/mute/<target>.json`)を確認し、
  mute 中は**カウント自体を行わない**+連続失敗カウンタをリセットする(Yoshinobu 判断)。
  mute 明けにカウント持ち越しで即発火する事故を防ぐ。
- パイプライン入口(§8.4)の mute チェックは二重防御として維持。
- mute は必ず TTL 付き。恒久 OFF は作らない。
- probe は mute 状態を定期ログに可視化する(「現在 mute: sophos-fw 残 42 分 (reason)」)。
  監視が黙って止まっている状態を作らない。

### mute の抑制範囲(Yoshinobu 確認済み 2026-07-02)

- **mute は全自律経路を常に抑制する**: pull(probe はカウント自体をしない)/
  push(OnFailure 通報は届くがパイプライン入口 §8.4 で停止)/
  Slack 手動メンション(mute 中は実行せず「mute 中です(残 N 分、reason)」と返答する。
  実行したい場合は `homelab-mute clear` してから依頼する。force オプションは作らない)。
- **直接実行は抑制対象外(仕様)**: 人間や Semaphore タイマーによる ansible-playbook の直接実行、
  Sophos GUI からのパッチ適用等の手作業は mute と無関係に動く。mute は「自律側を黙らせる」
  機構であり、システム変更のロックではない。メンテ作業の前に自律側を mute するのが正しい運用。

### 常駐形態

- recovery-io とは別の systemd サービス `recovery-probe` として quory に常駐(§3.1 分離の基準)。
- 連続失敗カウンタを保持する daemon 方式(recovery-io と同様の Python + systemd unit)。
- 全体停止は `systemctl stop recovery-probe` で可能だが非常用。通常は per-target mute を使う。

### 設計制約: sophos-fw 経路は LLM 非依存の決定論実装とする(E-1a 調査で確定)

既存パイプラインの実体は「recovery-io → codex-exec-wrapper → **Codex(LLM)**が
AGENTS.md に従い investigate/recover wrapper を実行」する構成である。しかし
**sophos-fw 障害 = インターネット断 = Codex(OpenAI API)自体が使えない**ため、
sophos-fw の検知→ラダー起動は LLM を経由せず、recovery-probe 内の決定論スクリプトで
直接 `recovery_vm_reboot.yml` / `recovery_ha_failover.yml` を実行する。
§8.4 チェック(allowlist / lock / mute / flapping)も probe 側で決定論的に実装する。

また現行 AGENTS.md のラダーはサービス restart(Ladder 1)までしか Codex に公開されて
いない。authy / monnie の VM reboot 以降の自動化は E-2 以降で扱う。

### E-1 のスコープ確定

- sophos-fw: 検知 → 確証 → ラダー起動(reboot → failover)まで**フル実装**
- authy / monnie: pull 検知 → **通知のみ**(インターネットは生きているので Slack 通知可能。
  ラダー自動起動は E-2 の OnFailure/パイプライン統合と合わせて実装)

### 通知(インターネット断中の扱い)

- sophos-fw 障害中は Slack/メールに到達できない。通知はローカルにキューし、
  外部到達性の回復を検知したらまとめて送信する(発生時刻・実施アクション・結果)。
- パイプライン内の既存 Slack 通知は best-effort(失敗してもラダーを止めない)を保証する。

## 要求 2: push 検知 — systemd OnFailure(§8.1)

- 対象ユニット: authy = freeradius.service / monnie = grafana-server, prometheus, loki, unpoller
- 実装: 既存ユニットへの drop-in(`OnFailure=recovery-trigger@%n.service`)+
  通報ユニットが SSH forced command で quory の recovery-exec 宛に通知(policy §8.1 の設計どおり)。
- 配布は Ansible role(新規 or recovery_exec 拡張)。tester_mode ゲート/マーカーの lint 規約に従う。
- push はサービスクラッシュの即時検知を担い、pull(60s×5)はハング・VM 死の遅い安全網と役割分担する。

## 要求 3: mute CLI(手動メンテ用の手軽な On/Off)

- quory に配布する小さなシェルスクリプト(Ansible 不要で直接実行):

```text
homelab-mute set <target> <minutes> [reason]   # TTL 付き mute(既存窓を短縮しない)
homelab-mute status                            # 全対象の mute 状態表示
homelab-mute clear <target>                    # mute 解除
```

- 既存 mute ファイル形式(recovery_mute role と同一)を読み書きし、双方から互換。
- Slack 経由の mute 操作(`@Homelab mute sophos-fw 60`)は**次期要求**(recovery-io 改修)として分離。
  CLI を先行する(Yoshinobu 判断)。

## 要求 4: drill モード(全経路のエンドツーエンドテスト)

正常稼働中のホストで実サービスを壊さずにトリガ経路をテストする仕組み:

- push 側: 常に fail するダミーユニット(recovery-drill.service)に同じ OnFailure フックを
  付けて発火 → 通報 → パイプラインが drill と判定
- pull 側: recovery-probe に模擬障害注入(drill フラグ)を持たせる
- drill 時のラダーは **`-e tester_mode=true` で実行**(P1 で L2 化済みのため、pvesh 実データの
  タグ検証・対象解決まで動いて変更系直前で停止する = 実害ゼロで全経路検証)
- drill の Slack 通知は「drill である」ことを明示する

## 要求 5: mute 設定追記の監査(残タスク G)

probe 導入により誤爆し得る変更系 playbook を洗い出し、mute 設定を追加する。
最低限の確認対象: cert_renew(grafana/pveproxy/semaphore を再起動 → monnie/pve の probe に
かかり得る)、time_sync_ntp_reference(chrony 再起動)、その他 service restart を含む playbook。

## 受け入れ基準(概要)

1. sophos-fw の LAN/DNS 無応答(drill 注入)で、mute なしなら約 5 分後に drill ラダーが
   tester_mode で起動し、mute ありなら起動しない
2. ISP 障害シミュレーション(外部のみ NG)では発火しない
3. mute CLI の set/status/clear が recovery_mute role と相互運用できる
4. OnFailure ダミーユニットの発火が quory に到達し、§8.4 チェックを通ってパイプラインに入る
5. 通知キューがインターネット断中に溜まり、回復後に送信される
