## Findings

### 1. [must-fix] `0775` は ACL 未設定時に owning group へ実 write を広げる

対象:

- `roles/recovery_exec/tasks/main.yml:263-288`
- `roles/recovery_mute/tasks/deploy_cli.yml:5-13`
- `roles/recovery_mute/tasks/set.yml:22-30`
- `roles/recovery_mute/files/homelab-mute:88-95`

POSIX ACL に `ACL_MASK` が存在する場合、mode の group bits が mask に対応するため、
`group::r-x` / `mask::rwx` の ACL 上で `chmod 0775` を行っても owning group の effective
permission は `r-x` のまま、named user `recovery-exec:rwx` は実効 `rwx` になる。この部分の
説明は正しい。

しかし ACL が無い場合、mode の group bits は通常どおり `ACL_GROUP_OBJ` に対応するため、
`0775` は owning group そのものへ `rwx` を付与する。これは仮定上の一瞬だけではない。
`playbooks/recovery_probe_setup.yml` は `dev_nodes:control_nodes` を対象に
`recovery_mute/tasks/deploy_cli.yml` を実行し、ansy には recovery-exec 用 named ACL を付与する
`recovery_exec_setup` が無いため、ansy の mute directory は恒常的に `root:root 0775` となる。
また quory でも ACL task より前、または recovery_exec setup 未適用時には同じ状態になる。

したがって 006 implement の「0775 でも group:: は r-x のまま」「唯一の write 主体は root と
ACL recovery-exec」という主張は、extended ACL が既に存在する場合にしか成立しない。
前回 F1 の目的は ACL mask の維持であり、通常 group permission の拡張ではない。

推奨修正:

- recovery_exec setup は directory を `0755` で作成/整形した後、named ACL を付与して
  `mask::rwx` を成立させる（最終 ACL は `group::r-x`, `mask::rwx`）。
- 後から走る `deploy_cli.yml` / `set.yml` は、既存 directory に mode を再適用しない。
  新規作成時だけ 0755 になるようにし、既存 ACL の mask を chmod で触らない。
- 人間 CLI も毎回の `chmod` を削除し、`mkdir -p` で既存 directory の ACL/mode を保持する。

別方式を採る場合でも、最終状態を ansy（ACL 無し）と quory（named ACL 有り）の両方で確認し、
以下を満たすこと:

```text
ansy:  root:root, group effective r-x, other r-x
quory: root:root, group::r-x, mask::rwx,
       user:recovery-exec:rwx (effective rwx), other::r-x
```

### 2. [nit] lock の open/create 説明と fallback ownership が実コードと一致しない

対象:

- `roles/recovery_exec/files/homelab-mute-set:59-70`
- `roles/recovery_exec/files/homelab-mute-clear:29-37`
- `roles/recovery_mute/files/homelab-mute:59-70`

実コードは、無ければ `: > "$lf"` が lock file を作成し、その後 shell の
`exec 9<"$lf"` が O_RDONLY で開き、`flock 9` は既存 fd を lock する。`flock(1) が
O_RDONLY|O_CREAT で開く`わけではない。Linux の local filesystem では exclusive flock は
fd の open mode に関係なく取得できるため、動作は妥当。

また通常は recovery_exec setup が 0644 root:root で事前作成するが、wrapper fallback が先に
作ると recovery-exec 所有となり、後続の `recovery_mute/tasks/set.yml` は owner/group を指定
しないのでそのまま残る。排他性・安全性への実害は無いが、コメント/implement の
「常に 0644 root:root」とは一致しない。説明を実コードに合わせることを推奨する。

### F2 shared flock: 解消

以下は同じ `/var/lib/homelab-recovery/mute/.<target>.lock` を exclusive flock している。

- Codex wrapper set: read → max → temp write → rename
- Codex wrapper clear: existence check → rm
- 人間 CLI set/clear: 同上
- Ansible auto-mute `set.yml`: read → max → temp write → rename

全 writer が target 検証後に同じ target-specific inode を lock し、critical section の外で
mute JSON を read/write/clear していない。set×set は後から lock を取得した側が最新 until を
再読込するため lost-update しない。set×clear は lock 取得順に「set後clear」または
「clear後set」として直列化され、clear の途中へ set が割り込んで残存/消失するレースも無い。

lock file の同時初回作成でも、同じ pathname の既存 inode を最終的に read-open してから lock
する。fallback create の片方が permission error になってもそれを許容した後に read-open する
ため、通常の競合で別 inode に分岐しない。directory write 権限を持つ任意プロセスが lock file
を意図的に unlink/replace するケースは advisory lock の一般的制約だが、execpolicy 上の許可
wrapper はその操作を提供していない。

`set.yml` を CLI 呼び出しへ寄せず自己完結させた判断も許容する。patch/evacuate の安全機構を
CLI 配備順へ依存させない利点があり、排他の相互運用性は共通 pathname で担保される。ただし
今後 max/JSON format を変更する場合は3実装を同時更新する必要がある。

### F4 replication journal unit: 解消（実出力は tester 確認）

`pvescheduler` は現行 Proxmox で replication / vzdump の scheduled job を起動する daemon
であり、廃止済み `pvesr.service` から `pvescheduler` への差し替えは妥当。fork した child は
通常 systemd unit の cgroup を継承するため、`journalctl -u pvescheduler` を主要候補とする
判断も妥当。`pvestatd` の併記は固定 read-only check として害はない。

最終的に replication job の必要な log line が `pvescheduler` unit へ出るか、pve1/pve2 の
実出力で確認し、必要なら identifier/unit を調整するという tester 委譲も適切。

- `https://lore.proxmox.com/pve-devel/20211007082727.1385888-3-d.csapak%40proxmox.com/`
