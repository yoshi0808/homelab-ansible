# pve1/pve2 レプリケーション・ストレージ調査コマンド追加（Phase 1: パラメータ無し）— 要求仕様

- 日付: 2026-07-14
- 起案: claude（要件定義・ハブ役）/ 承認: Yoshinobu（本文の最終確認は claude→implementer 送付前に実施）
- 優先度: 通常（残タスク。monnie 復元時のレプリケーション障害を recovery.io から調べられなかった件への対応）

## 目的

Proxmox（pve1/pve2）の **レプリケーション / ストレージ / ZFS / クラスタ quorum** の状態を
Slack/Codex から read-only で調べられるようにする。一昨日（2026-07-12）monnie を
バックアップから戻した際にレプリケーションがエラーになったが、recovery.io 経由では
状況を確認できなかった。これは §4.6 の pve investigate 系（現状は `cluster-status` /
`cluster-resources` / `ha-status` の3チェックのみ）に、調査用の read-only named check を
足すことで解消する。

**本 Phase 1 はパラメータを取らない固定コマンドのみ**を追加する（Yoshinobu 承認済みの
段階分割・2026-07-14）。`qm status <vmid>` / `pvesr read <job-id>` /
`pvenode task log <UPID>` / `pvesm status --storage <s>` 等の **パラメータ系は Phase 2**
（別 requirement）とし、そこで forced-command の引数検証と sudoers ワイルドカード化の
設計・レビュー・テストをまとめて行う。

## スコープ（Phase 1 に含める named check）

いずれも pve1/pve2 両ノードに同一で追加する（レプリケーションは pve1↔pve2 のペア動作の
ため、両側から見えることが必要）。命名は既存の hyphen 形式（`cluster-status` 等）に揃える。

| named check（案） | 実コマンド（案） | 目的 |
|---|---|---|
| `replication-status` | `pvesr status` | レプリケーションジョブ一覧と各ジョブの成否/最終同期/エラー |
| `replication-list` | `pvesr list` | 定義済みレプリケーションジョブの一覧 |
| `cluster-quorum` | `pvecm status` | corosync quorum / ノード membership（既存 `cluster-status`=pvesh とは別視点） |
| `storage-status` | `pvesm status` | 全ストレージの有効/容量/種別（`--storage` 指定は Phase 2） |
| `zpool-health` | `zpool status -x` | ZFS プールの異常のみ簡潔表示（正常なら "all pools are healthy"） |
| `zfs-list` | `zfs list` | データセット/ボリューム一覧（レプリケーション先の存在確認に有用） |
| `journal-replication` | `journalctl -u pvesr -u pvestatd --since '-2 hours' -n 200 --no-pager`（案） | レプリケーション関連ユニットの直近ログ |
| `journal-system` | `journalctl --since '-2 hours' -n 300 --no-pager`（案） | ノード全体の直近システムログ（authy/monnie の `journal-system` と同パターン） |
| `journal-cluster` | `journalctl -u pve-cluster -u corosync -u pvedaemon --since '-2 hours' -n 200 --no-pager`（案） | クラスタスタックの直近ログ（quorum/membership 障害の切り分け） |

（journal 系の範囲: `replication + system + cluster` の3本を Phase 1 で追加。Yoshinobu 承認・2026-07-14）

- named check 名・実コマンドの最終形と、各 journal チェックの対象ユニットは実装判断に
  委ねるが、選定理由を implement に記載すること。対象ユニットは「pve 上に実在し、
  切り分けに寄与する」ものに限定する（候補: `pvesr` / `pvestatd` / `pve-cluster` /
  `corosync` / `pvedaemon`。実在確認は tester 工程）。
- **journal 3チェックはいずれも対象ユニット・時間窓・行数を固定**し、client から
  ユニット/期間/行数を受け取らない（Phase 1 の「パラメータ無し」原則を守るため）。
  任意ユニット指定（`journalctl -u <任意>`）や可変期間は Phase 2 の引数検証で扱う。

## 対象ファイル

- `roles/recovery_exec/templates/recovery-investigate-dispatch-pve.sh.j2`
  （pve ノード側 forced-command dispatch。case に新 named check を追加）
- `roles/recovery_exec/templates/homelab-investigate-pve.sh.j2`
  （quory 側 wrapper。allowlist の case を dispatch とミラー）
- `roles/recovery_exec/templates/sudoers-recovery-exec-pve-target.j2`
  （新コマンドを **1:1 の完全固定行** で列挙。ワイルドカードは使わない）
- `roles/recovery_exec/templates/AGENTS.md.j2`
  （pve セクションに新チェックの説明を追記。追記しないと Codex が存在を認識しない）
- `playbooks/recovery_exec_setup.yml -l quory` で配備・反映（policy §4.1.1 の手順）

## 実施項目

1. 上表の named check を dispatch / quory wrapper / sudoers / AGENTS.md の4箇所へ整合して
   追加する（4箇所の allowlist が一致していること）。
2. 各コマンドは `sudo -n <絶対パス> <固定引数>` の形で、sudoers に**フルパス・完全固定**で
   列挙する（既存3チェックと同じ方式。§4.6 の no-wildcard を維持）。
3. **バイナリ絶対パスと引数の実在確認**を pre-deploy チェック項目として明記する
   （既存の `ha-manager` パス NOTE と同様）。特に確認対象:
   - `pvesr` / `pvecm` / `pvesm` / `pvesh` の絶対パス（`/usr/bin` 想定だが要確認）
   - `zpool` / `zfs` の絶対パス（`/usr/sbin` か `/sbin` かノード差あり得る）
   - `journalctl` の絶対パスと、`-u <unit>` 対象ユニットの実在
   - forced-command + no-pty での `sudo -n` 成功（既存3チェックで実績あり。同経路）
4. tester-gate 分類は既存の `recovery_exec_setup.yml` の現状を踏襲する（read-only
   investigate の追加であり本番影響の性質は変わらない）。理由文の更新要否は実装時に判断。

## 確認項目（tester 工程で検証）

- pve1/pve2 双方で新9チェック（replication-status/list, cluster-quorum, storage-status,
  zpool-health, zfs-list, journal-replication/system/cluster）が
  `homelab-investigate-pve{1,2} <check>` で成功し、
  read-only の期待出力を返すこと（特に `replication-status` がジョブ状態を返すこと）。
- allowlist 外の値（例: `pvesr read 211-0` のような未対応パラメータ付き）は
  依然 `denied` で拒否されること（Phase 1 では未実装のため）。
- sudoers にワイルドカードが増えていないこと（`sudo -l` 相当で完全固定行のみ）。
- 既存3チェック（`cluster-status`/`cluster-resources`/`ha-status`）が回帰していないこと。
- Codex（Slack）から自然言語で「monnie のレプリケーションが失敗している、状況を見て」と
  依頼したとき、Codex が新チェックを使って一次切り分けできること
  （= AGENTS.md への追記が効いていること）。

## 制約

- pve1/pve2 に復旧アクション（`homelab-recover-*` 相当）を一切追加しない。調査のみ（§2/§4.6）。
- `ann` の鍵・権限は使わない。pve 専用鍵 `id_recovery_investigate_pve` 経路のまま（§4.6）。
- client から引数を受け取らない（Phase 1）。パラメータ系は Phase 2 の引数検証で扱う。
- 秘密情報・IP をリポジトリに書かない。実ホスト検証は tester 工程。

## 初回実装で含める範囲

- 実施項目 1〜4（パラメータ無しの固定 named check の追加）。

## 初回実装では除外する範囲（→ Phase 2 別 requirement）

- パラメータ系: `pvesr read <job-id>` / `qm status <vmid>` / `qm config <vmid>` /
  `pvenode task list --vmid <vmid> --limit <N>` / `pvenode task log <UPID>` /
  `pvesm status --storage <storage>` / `stat /etc/pve/qemu-server/<vmid>.conf` /
  可変期間の journal。
- Phase 2 では forced-command dispatch を「check 名 + 検証済みパラメータ」に拡張し、
  vmid/UPID/storage/job-id を regex・allowlist で検証、sudoers は該当コマンドのみ
  ワイルドカード化する（§4.6 の原則緩和を明示的にレビュー・承認する）。
