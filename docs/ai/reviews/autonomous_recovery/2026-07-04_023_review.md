## 指摘

### must-fix: `recovery_exec_setup.yml -l ansy` が authy/monnie の authorized_keys を ansy 鍵で上書きしうる

`docs/ai/prompts/autonomous_recovery_deploy_runbook.md:19` から `:24` は、quory と ansy の両方で `recovery_exec_setup.yml` を通常実行する手順になっている。

しかし `recovery_exec_setup.yml` は既定で `recovery_exec_setup_targets=true` のため、対象ホスト authy/monnie の setup まで実行する。`roles/recovery_exec/tasks/target_setup.yml` は、実行元ホストで生成された investigate/action 公開鍵を slurp し、authy/monnie の `authorized_keys` を template で上書きする。

- `roles/recovery_exec/tasks/target_setup.yml:10`
- `roles/recovery_exec/tasks/target_setup.yml:15`
- `roles/recovery_exec/tasks/target_setup.yml:83`
- `roles/recovery_exec/templates/authorized_keys.j2:1`

つまり、runbook の順に quory へ本番鍵を配ったあと ansy でも通常実行すると、authy/monnie 側の `authorized_keys` が ansy の鍵2本だけになり、quory の `recovery-exec` からの investigate/recover が通らなくなる。

修正案:

```bash
# quory 本番: target 側も含めてセットアップ
ansible-playbook playbooks/recovery_exec_setup.yml -l quory

# ansy 開発: target 側 authorized_keys は触らない
ansible-playbook playbooks/recovery_exec_setup.yml -l ansy \
  -e recovery_exec_setup_targets=false
```

または、ansy から authy/monnie への実疎通が必要な開発時は「本番 quory の復旧経路を一時的に置き換える操作」であることを明記し、終了後に必ず quory 側で再実行して authorized_keys を戻す手順を書く必要がある。

### must-fix: `recovery_io` の runbook は active を期待しているが、role は enable のみで start しない

`docs/ai/prompts/autonomous_recovery_deploy_runbook.md:85` から `:96` は、quory で `recovery_io_service_enabled=true` を付けて実行すれば `recovery-io` が `Active: active (running)` になる前提で書かれている。

しかし現行 role の最後は `enabled` を設定するだけで、`state: started` は指定していない。

- `roles/recovery_io/tasks/main.yml:144`
- `roles/recovery_io/tasks/main.yml:145`
- `roles/recovery_io/tasks/main.yml:147`

初回配置や unit/env/script が changed した場合は handler の `Restart recovery-io` で起動されうるが、既存配置に対して「quory で自動起動ONへ切り替える」だけの再実行では、service が enable されても現在のプロセスは start されない。

runbook を正にするなら、デプロイ後に明示 start を入れる。

```bash
sudo systemctl enable --now recovery-io
sudo systemctl status recovery-io
```

または role 側を `enabled: "{{ recovery_io_service_enabled }}"` + `state: "{{ 'started' if recovery_io_service_enabled | bool else omit }}"` に直す。

`recovery_probe` は `roles/recovery_probe/tasks/main.yml` で `enabled: true` と `state: started` を同時に指定しているため、この問題は `recovery_io` 側だけ。

### must-fix: ansy で `recovery-probe` を手動起動した場合の停止コマンドが `recovery-io` 固定になっている

`docs/ai/prompts/autonomous_recovery_deploy_runbook.md:165` から `:170` は、`recovery-io` または `recovery-probe` を起動できると書きつつ、検証後の停止例が `sudo systemctl stop recovery-io` 固定になっている。

このままでは、ansy で `recovery-probe` を起動したケースで停止漏れが起き、quory の本番 pull 監視と二重稼働する。runbook の前提で同時稼働禁止を強調している箇所と矛盾する。

修正案:

```bash
sudo systemctl start recovery-io      # または recovery-probe
sudo systemctl status recovery-io     # 起動した service 名に置き換える

# 検証後
sudo systemctl stop recovery-io       # または recovery-probe
sudo systemctl is-active recovery-io  # inactive を確認
```

あるいは service ごとに別ブロックへ分ける。

### suggestion: `homelab-mute set` は `sudo` 付きで書く

`docs/ai/prompts/autonomous_recovery_deploy_runbook.md:120` は、probe で `FAIL` が出た場合の一時抑制として `homelab-mute set <target> <分> <理由>` と書いている。

実装上、`set` と `clear` は root 必須。

- `roles/recovery_mute/files/homelab-mute:9`
- `roles/recovery_mute/files/homelab-mute:26`
- `roles/recovery_mute/files/homelab-mute:47`

手順書としては次のように `sudo` を明記した方がよい。

```bash
sudo homelab-mute set <target> <分> <理由>
homelab-mute status
sudo homelab-mute clear <target>
```

### suggestion: `recovery_exec` の疎通確認は、どのホストの鍵を確認しているか明記する

`docs/ai/prompts/autonomous_recovery_deploy_runbook.md:67` から `:79` の SSH 疎通確認は、実行したホスト上の `/home/recovery-exec/.ssh/id_recovery_investigate` を使う。

上記 must-fix の authorized_keys 問題を避けるなら、本番 runbook では「quory 上で実行する確認」として書くのが安全。ansy 側で確認する場合は、ansy の鍵が target 側に入っている必要があり、本番 quory 鍵との排他関係を説明する必要がある。

### nit: OS 権限確認の期待結果は対象ごとに少し分けると読みやすい

`docs/ai/prompts/autonomous_recovery_deploy_runbook.md:63` は「全て `0600` + 専用ユーザー所有」とまとめているが、`cat` 失敗確認コマンド自体はファイルの mode を表示しない。

実運用上の問題ではないが、以下のように分けると誤読が減る。

- `stat` 対象: `0600` + 期待 owner を確認
- `cat` 対象: `Permission denied` を確認
