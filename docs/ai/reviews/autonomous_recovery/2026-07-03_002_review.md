## 指摘

### must-fix: quory 側 `recovery-exec` が `/usr/sbin/nologin` のため SSH forced command 経路が成立しない

- 対象: `roles/recovery_push/templates/push-authorized_keys.j2:2`
- 関連: `roles/recovery_push/files/recovery-push.sh:17`, `roles/recovery_exec/tasks/main.yml:15`

E-2 は authy / monnie から `recovery-exec@quory.internal` に SSH し、quory 側 `authorized_keys` の forced command で `recovery-push-dispatch.sh` を実行する設計です。

しかし既存の quory 側 `recovery-exec` ユーザーは `roles/recovery_exec/tasks/main.yml` で `shell: /usr/sbin/nologin` として作成されています。OpenSSH の forced command は対象ユーザーのログイン shell 経由で実行されるため、`nologin` のままでは incoming SSH push が dispatcher まで到達できません。

この状態だと OnFailure は `recovery-push.sh` までは起動しても、SSH 接続先で forced command が実行できず、Codex 調査・復旧パイプラインに入れません。E-2 の中核経路が不成立です。

対応案:

- quory の `recovery-exec` を incoming forced command 用に `/bin/sh` など実行可能 shell にする。その場合、authorized_keys の forced command / no-pty / no-forwarding 制約で権限を閉じる前提を docs に明記する。
- もしくは push 受信用の別ユーザーを作り、shell / authorized_keys / forced command をそのユーザーに限定する。
- どちらの場合も、実機テストで `ssh -T -i /etc/homelab-recovery/push-key recovery-exec@quory.internal` 相当が dispatch log まで到達することを確認してください。

## レビュー観点への回答

1. `authorized_keys` が既存 outgoing SSH 経路を壊さないか
   既存の target 側 `authorized_keys` とは別物であり、quory 側 incoming 用として分離されている点は妥当です。ただし上記 shell 問題により実行経路が成立していません。

2. push session lock
   `mkdir` によるロック取得と `EXIT` trap の組み合わせは妥当です。`exec` 成功時も Bash の EXIT trap は実行されることを確認しました。

3. monnie の 4 サービス同時クラッシュ
   target 単位 lock と `homelab-recover-monnie` 一括 restart の方針は、Yoshinobu 確認済みの設計と整合しています。

4. `DefaultDependencies=yes`
   明示的に変更しておらず、OnFailure 起動専用の oneshot として妥当です。

5. tester_mode gate
   `recovery_push_setup.yml` は role 実行前に `tester_gate` で停止するため、key 生成・drop-in 配置には到達しません。
