## 修正内容

### F3 [must-fix]: `storage-status` の `pvesm` 絶対パス誤り

`/usr/bin/pvesm` → `/usr/sbin/pvesm` に修正（dispatch と sudoers の両方）。
Proxmox VE は `pvesm` を `/usr/sbin` に配置する（review 引用の Proxmox forum で確認）。
旧 004 実装の「pvesr/pvecm/pvesm は pvesh と同じ `/usr/bin` 想定」という一括りの想定が
`pvesm` について誤りだった。

あわせて他の新規バイナリの想定パスを既知標準に照らして再確認し、pre-deploy NOTE を
バイナリ別の正確な想定に書き換えた:

| バイナリ | 修正後の想定パス | 由来 |
|---|---|---|
| `pvesr` | `/usr/bin/pvesr` | pve-manager（pvesh と同系） |
| `pvecm` | `/usr/bin/pvecm` | pve-cluster |
| `pvesm` | `/usr/sbin/pvesm` | **pve-storage（F3 の修正点）** |
| `zpool` / `zfs` | `/usr/sbin/zpool` `/usr/sbin/zfs` | zfsutils（`/sbin` の可能性はノード差として NOTE 継続） |
| `journalctl` | `/usr/bin/journalctl` | systemd |
| `ha-manager` | `/usr/sbin/ha-manager` | 既存（変更なし） |

最終的な実在確認は tester の `command -v pvesr pvecm pvesm zpool zfs journalctl` に委ねる旨は
NOTE に残した（差異があれば dispatch と sudoers の該当行を同時修正）。

### F4 [must-fix]: `journal-replication` が廃止済み `pvesr.service` を対象

現行 Proxmox VE（PVE7/2021 以降）では replication / vzdump のスケジュール起動は
`pvescheduler` が担い、`pvesr.service` / `pvesr.timer` は削除済み。`journalctl -u pvesr` は
存在しない unit を静かに無視（exit 0・空出力）するため、replication 障害調査の主要ログを
取りこぼす。

修正:

- dispatch / sudoers の `journal-replication` を
  `journalctl -u pvesr -u pvestatd ...` → `journalctl -u pvescheduler -u pvestatd ...` に変更。
- AGENTS.md の説明を「`pvescheduler` がレプリケーションジョブを実行、`pvestatd` が状態報告」に
  訂正（旧「pvesr がレプリケーション本体」「pvestatd がスケジューリングを担う」は現行構成と
  不一致だったため撤回）。
- sudoers NOTE に、pvesr.service 廃止の経緯と「tester は pve1/pve2 実機で
  replication ジョブのログが実際にどの unit に出るか確認し、必要なら unit セットを
  調整する」ことを明記。

**設計上の補足（unit セット選定の理由）**: `pvescheduler` daemon は `pvesr run` を fork して
replication ジョブを実行するため、その子プロセスの出力は systemd journal 上
`pvescheduler` の unit（cgroup）配下に集約される。したがって `journalctl -u pvescheduler` が
現行の replication 実行ログの主経路になる想定。`pvestatd` は replication の状態算出・報告を
担うため、障害時の status メッセージ取得用に併記した。**この想定の実機確認は tester 工程**
（下記 確認委譲項目）。

**注意**: F4 は journal の「対象 unit」に関する指摘であり、`replication-status`（`pvesr status`）
/ `replication-list`（`pvesr list`）の **`pvesr` CLI コマンド自体は現行でも有効**なため変更
していない（廃止されたのは systemd unit であって CLI ではない）。

### S5 [suggestion, 採用]: `journal-system` に priority filter

`journalctl --since "-2 hours" -n 300 --no-pager`
→ `journalctl -p warning..err --since "-2 hours" -n 300 --no-pager`（時間窓 2h / 300 行は維持）。

priority 無しだと稼働量の多い pve で info の直近300行が2時間より大幅に短い区間を占め、
warning/error が押し出されるため。replication / cluster の info は専用2チェックで取得できる。
`-p warning..err` は authy/monnie の `journal-system` と同じ proven 形（`recovery-investigate-dispatch.sh.j2`）。
AGENTS.md の journal-system 説明も「node-wide warnings/errors (priority warning..err)」に更新。

（これで 004 で残していたトリアージ論点＝journal-system の priority filter 有無は、
S5 採用により決着。dispatch・sudoers・AGENTS.md の3箇所を更新済み。）
