## 指摘

### suggestion: §8 の「無条件に実行」は、実装上の safety gate と矛盾して読める

`docs/ai/prompts/autonomous_recovery_policy.md:156` は、手動レイヤーについて「`target=` が指定されれば無条件に実行する」と書いている。

ただし実装では、入口の target allowlist に加えて role 内でタグ・VM存在・HA登録などを再検証する。

- `playbooks/recovery_vm_reboot.yml:41`
- `roles/recovery_vm_reboot/tasks/main.yml:37`
- `roles/recovery_vm_reboot/tasks/main.yml:42`
- `roles/recovery_ha_failover/tasks/main.yml:37`
- `roles/recovery_ha_failover/tasks/main.yml:69`

意図は「probe の成否やサービス健全性を前提条件にせず、人間判断でそのレイヤーを直接起動できる」だと読める。その意味なら妥当。

推奨表現:

```text
いずれも probe の現在状態やサービス健全性を発火条件にはせず、target= が妥当なら人間判断で直接起動できる。
ただし、対象 allowlist・タグ再検証・VM存在確認・HA登録確認などの safety gate は実装側で維持する。
```

### suggestion: §2 の「ping無応答は常にVM reboot」は少し強すぎる

`docs/ai/prompts/autonomous_recovery_policy.md:33` では「ping無応答は常にVM reboot」と説明している。

詳細フローの §5.1 では正しく書かれている通り、実際には以下の分岐がある。

- pve 到達不能なら critical 通知のみ
- VM stopped なら reboot ではなく start
- VM not-found なら critical 通知のみ
- flapping ならラダーを止めて通知のみ
- running なのに probe 失敗の場合に VM reboot へ進む

§5.1 が正なので重大な齟齬ではないが、§2 の要約だけ読むと運用者が「ping失敗 = 必ず reboot」と誤解しうる。

推奨表現:

```text
pingベースのラダーはVM単位の生死判定であり、pveshで状態を確証したうえで、
runningのまま無応答ならVM reboot、hacriticalかつ未復旧ならfailoverへ進む。
```

### nit: §5.3 の sudo 呼び出しは `-H` 付きに揃えると正確

`docs/ai/prompts/autonomous_recovery_policy.md:113` は `sudo -u recovery-exec ...` と書いているが、実装は `sudo -H -u recovery-exec ...`。

- `roles/recovery_io/templates/recovery-io.py.j2:31`

`-H` は recovery-exec の `~/.codex` を使ううえで意味があるため、policy も `sudo -H -u recovery-exec ...` に揃えるとよい。

### nit: §6 の「Bash/Write/Edit/Read等のツール」は運用上の言い方としては妥当だが、execpolicy の説明に寄せるとより正確

`docs/ai/prompts/autonomous_recovery_policy.md:119` は「Bash/Write/Edit/Read等のツールを渡さない」と書いている。

現行実装では Codex CLI 自体を起動しつつ、`execpolicy default_policy="deny"` で実行可能コマンドを wrapper 群だけに絞っている、という構造が正本。

このままでも安全方針としては伝わるが、より厳密には以下のような表現がよい。

```text
Codex 側で任意コマンドを実行できないよう、execpolicy default_policy="deny" とし、
許可する外部コマンドを homelab-* wrapper のみに限定する。
```

## §8 について

§8 の位置づけは妥当。

push は systemd failed、pull は ping/tcp/dns probe の連続失敗を扱うため、「systemd は active、ping も通るがアプリケーションとして壊れている」状態は検知範囲外になりうる。この穴を Semaphore の手動レイヤーで埋める整理は実装と合っている。

また、手動レイヤーが Codex の判断を介さない点も妥当。VM reboot / HA failover は Codex execpolicy に含めず、人間判断または pull 経路の決定論ラダーに限定する現在の安全設計と整合している。
