## 設計要点

### probe daemon(recovery-probe.py)

- 60 秒間隔 × 5 回連続失敗で発火。成功でカウンタリセット
- **mute は判定前に確認**し、skip + カウンタリセット(第一防御)。残り時間をログに可視化
- probe 種別: icmp / dns(dig、NOERROR 判定)/ tcp:PORT。対象ホスト名は /etc/hosts 解決
- sophos-fw 発火時(action: ladder、決定論・LLM 非依存):
  1. 実行中ロック(state_dir/ladder.lock、mkdir でアトミック)
  2. flapping(直近 24h の発火記録 ≥3 → エスカレーション通知のみ)
  3. pvesh 確証(`ansible pve1 -m command` 経由、read-only):
     running → reboot ラダー / stopped → エスカレーション(HA 補完前提、reboot 適用外) /
     not-found・pve 到達不能 → エスカレーション
  4. `recovery_vm_reboot.yml -e target=sophos-fw` → 回復ポーリング(300s)→
     未回復なら `recovery_ha_failover.yml` → 未回復ならエスカレーション
- authy / monnie 発火時(action: notify): エスカレーション通知のみ
- **drill**: `state_dir/drill/<target>` ファイルで強制障害扱い。ラダーは
  `-e tester_mode=true` 付き(P1 の L2 ゲートで実変更ゼロ)。通知に [drill] 明示。実行後フラグ自動削除
- **通知キュー**: state_dir/notify-queue/*.json に積み、外部到達性回復後に
  `recovery_probe_notify.yml -e @<file>` で送信(検知時刻と送信時刻を両方表示)
- **外部到達性の状態遷移監視**: ISP/FW 断を検知してもラダーは発火しない。回復時に
  「いつから外部到達不能だったか」を遅延通知
- 外部チェックは HTTP 応答が返れば到達ありとみなす(HTTPError=403 等も到達扱い。
  Cloudflare が Python UA に 403 を返すことを実機で確認済み)

### ISP 切り分けの整理

sophos-fw の probe(icmp / dns)はすべて LAN 側なので、ISP 断では失敗しない =
ISP 断で誤発火しない構造。外部到達性チェックは通知 flush と状態遷移監視にのみ使う。

## レビュー観点(お願い)

1. probe daemon のロジック(カウンタ・ロック・flapping・pvesh 確証の分岐)に穴がないか
2. セキュリティ: サービスは User=yoshi(repo・vault・SSH 鍵所持者)で実行。
   CLI は root 必須。config/daemon は root 所有 0644/0755。この構成の妥当性

4. sophos-fw stopped 時に「HA 補完前提でエスカレーションのみ」とした判断
   (HA 登録済み VM が stopped = HA が動かなかった異常ケースであり、自動 start は E-1 では見送り)

6. playbook の lint 準拠(setup=tester_gate、notify=role-guarded)と、
   drill 時に notify playbook が tester_mode ガードで抑止される点の整合
   (drill 通知は tester_mode **なし**で送るため抑止されない — probe は通知 playbook に
   tester_mode を渡さない)
