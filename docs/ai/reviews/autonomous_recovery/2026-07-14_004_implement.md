## 実装概要

pve1/pve2 の read-only 調査系（`homelab-investigate-pve{1,2}`）に、レプリケーション /
ストレージ / ZFS / クラスタ quorum / journal の **named check を 9 種追加**した。
いずれもパラメータを取らない固定コマンドで（Phase 1 の原則）、既存 3 チェック
（`cluster-status` / `cluster-resources` / `ha-status`）と同じ
`sudo -n <絶対パス> <固定引数>` 方式・sudoers 完全固定行（ワイルドカード無し）で実装した。
復旧アクション（`homelab-recover-*` 相当）は一切追加していない（§2 / §4.6 の
「pve は調査のみ」を維持）。

追加した 9 チェック:

| named check | 実コマンド | 分類 |
|---|---|---|
| `replication-status` | `pvesr status` | レプリケーション |
| `replication-list` | `pvesr list` | レプリケーション |
| `cluster-quorum` | `pvecm status` | クラスタ quorum（corosync 視点） |
| `storage-status` | `pvesm status` | ストレージ一覧 |
| `zpool-health` | `zpool status -x` | ZFS プール異常のみ |
| `zfs-list` | `zfs list` | データセット/ボリューム一覧 |
| `journal-replication` | `journalctl -u pvesr -u pvestatd --since "-2 hours" -n 200 --no-pager` | 直近ログ |
| `journal-system` | `journalctl --since "-2 hours" -n 300 --no-pager` | 直近ログ |
| `journal-cluster` | `journalctl -u pve-cluster -u corosync -u pvedaemon --since "-2 hours" -n 200 --no-pager` | 直近ログ |

## 変更内容の要約

### 1) dispatch（対象ホスト側 forced command）

`$SSH_ORIGINAL_COMMAND` を照合する case に 9 arm を追加。各 arm は
`sudo -n <絶対パス> <固定引数>` を 1 コマンド実行するのみ。パラメータは受け取らない。
ヘッダに Phase 1（パラメータ無し）・sudoers 1:1 対応・journalctl 時間窓イディオムの
出所（authy/monnie dispatch のミラー）・pre-deploy チェック項目の所在を明記。

### 2) wrapper（quory 側 allowlist）

case alternation を 12 チェック（既存 3 + 新 9）に拡張。バックスラッシュ継続で
複数行にしつつ、継続行はインデント無し（`case` パターンにインデント空白が
混入しないようにするため。bash の `|`+改行だけの継続は構文エラーになることを
ローカル検証で確認済み、後述）。

### 3) sudoers（完全固定行）

9 行を追記（合計 12 行）。ワイルドカードは一切無し。追加した pre-deploy NOTE:

- **sudo の引数照合は「空白連結した 1 本の文字列」に対する fnmatch であり、
  トークン単位ではない**旨を明記。これにより dispatch 側の
  `--since "-2 hours"`（空白を含む 1 argv）が sudoers 側の `--since -2 hours`
  （クォート無し）と一致する（両者を空白連結すると同一文字列）。
  「クォートを足して直す」のは誤り（sudoers はシェルのようにデクォートしないため、
  リテラルの `"` を要求してしまい壊れる）ことを警告として残した。
- 新バイナリの絶対パス・journalctl 対象ユニットの実在確認手順を NOTE 化。

### 4) AGENTS.md（pve セクションのみ）

新 9 チェックをカテゴリ別（Cluster/HA・Replication・Storage/ZFS・Recent logs）に
記載し、「VM のレプリケーションが失敗している時は pve1/pve2 双方から
`replication-status`（＋`journal-replication`）→ `cluster-quorum`/`zpool-health`/`zfs-list`
で局所化」という一次切り分け手順を追記。調査のみ・pve への復旧操作禁止の既存文言は維持。

## 実装上の判断と根拠

### named check 名・実コマンドの選定

- 命名は既存 hyphen 形式（`cluster-status` 等）に統一。
- 実コマンドは Proxmox / ZFS / journalctl の標準 read-only 呼び出し。API パスは
  推測せず、`pvesh get /cluster/*` は既存実績（`roles/recovery_ha_failover` 他）を踏襲。

### journal 対象ユニットの選定（要件で実装判断に委ねられた点）

- `journal-replication` → `pvesr`（レプリケーション本体の service/timer）＋
  `pvestatd`（Proxmox status daemon。レプリケーションのスケジューリング/状態更新を担う）。
- `journal-cluster` → `pve-cluster`（pmxcfs クラスタ FS）＋ `corosync`（membership/quorum の
  トランスポート）＋ `pvedaemon`（API daemon）。quorum/membership 障害の切り分けに直結。
- いずれも requirement の候補ユニット（pvesr/pvestatd/pve-cluster/corosync/pvedaemon）の
  範囲内。**実在確認は tester 工程**（後述の pre-deploy チェック）。

### journal-system の形（要検討点として明記）

requirement の「案」は `journalctl --since "-2 hours" -n 300 --no-pager`（priority
フィルタ無し）で、purpose は「authy/monnie の journal-system と同パターン」。一方
authy/monnie の実際の `journal-system` は `journalctl -p warning..err -n 50 --no-pager`
（priority フィルタ有り）。両者は厳密には異なる。

**判断**: requirement が明示した「案」のコマンド（priority フィルタ無し・2h 窓・300 行）を
採用した。理由は、レプリケーション復旧の一次切り分けでは warning/err に限らず
informational なレプリケーション/状態メッセージも読みたいケースが多く、フィルタ無しの
直近ログの方が有用と判断したため。ただし「authy/monnie と揃えて `-p warning..err` に
する」案も合理的なので、**reviewer / Yoshinobu の判断で `-p warning..err` 付与に
差し替え可能**な論点として残す。差し替える場合は dispatch と sudoers の当該 1 行のみ更新。

### 時間窓イディオム

`--since "-2 hours"` は authy/monnie dispatch（`recovery-investigate-dispatch.sh.j2` の
`--since "-1 hour"` / `--since "-1 day"`）で実績のある形をミラー。ただし authy/monnie では
journalctl を **sudo 無し**で実行しており（recovery-exec が journal 読取グループに所属して
いる前提）、今回は要件どおり **sudo 経由**にした点が唯一の新規要素。この差分に伴う
sudo 引数照合の妥当性は上記 NOTE とローカル検証（後述）で担保した。

## 実行した確認コマンド（ローカル、実ホスト非接触・副作用なし）

すべて ansy 上で、テンプレートを Jinja プレースホルダをダミー値に置換して
mock render した上での静的検証。実ホスト接続・ansible-playbook 実行・sudo 実行は
一切していない。

1. **bash 構文チェック（mock render 後）**: `bash -n` を dispatch / wrapper に対して実行 → 両方 OK。
2. **bash case 継続記法の検証**: `|` + 改行だけの継続は構文エラー、
   バックスラッシュ継続（継続行インデント無し）は正しくパースされることを確認し、後者を採用。
3. **wrapper allowlist 挙動**: 12 チェックすべて ALLOWED、`bogus` / `pvesr read 211-0`
   （Phase 2 のパラメータ付き想定）/ 空文字 → いずれも `denied`。
4. **visudo 構文検証（mock render 後の sudoers）**: `visudo -cf` → `parsed OK`
   （空白を含む journalctl 行も sudoers 構文として妥当）。
5. **4 箇所 allowlist 一致検証**（Python）: dispatch の case arm 名・wrapper の
   alternation トークン・AGENTS.md の bullet 名が **完全一致（各 12 件）**。
6. **sudo 照合の完全性検証**（Python + shlex）: dispatch の各 `sudo -n <cmd>` を
   シェルと同じくトークン化し空白連結した文字列が、sudoers の固定行と **12/12 一致**。
   → 全 dispatch コマンドがワイルドカード無しの固定 sudoers 行でカバーされることを確認。

## 実行結果

- 上記 1〜6 すべて期待どおり（allowlist 一致 True、sudo 照合 12/12、visudo OK、
  denied 判定正常）。
- 静的検証の範囲では、要件の確認項目のうち「allowlist 外の値は denied」「ワイルドカードが
  増えていない（完全固定行のみ）」「既存 3 チェックの回帰なし（12 件に既存 3 件を含む）」を
  満たすことを確認済み。
