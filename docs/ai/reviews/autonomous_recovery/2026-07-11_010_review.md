## 前回指摘の確認

### authoritative host の `-e` 上書き経路

**解消。** `recovery_exec_setup_authoritative_host` は role defaults から削除され、
安全判定には参照されていない。

- assert: `'quory' in ansible_play_hosts_all`
- include: `inventory_hostname == 'quory'`

両チェックが同じリテラル `quory` を trust anchor として使うため、次の extra var を
渡しても挙動は変化しない。

```text
-e recovery_exec_setup_authoritative_host=ansy
```

この名前の変数は条件式から完全に除去されており、`-l ansy` では引き続き
`'quory' in ['ansy']` が false となる。ansy が target_setup を include する経路もない。

## 最終的な安全条件

targets 配布には次の両条件が必要である。

1. targets が有効であり、当該 play の limit 適用後の全対象に quory が含まれること
2. 現在 role を実行しているホスト自身が quory であること

これにより、主要経路は次のとおりとなる。

- `-l ansy`: assert fail、target変更なし
- `-l ansy -e recovery_exec_setup_targets=false`: assert pass、include skip
- `-l ansy -e recovery_exec_setup_authoritative_host=ansy`: 未使用変数のため影響せず assert fail
- `-l quory`: assert pass、quory が include
- 制限なし: ansy/quory が assert pass、ansy は include skip、quory のみ include
- control_nodes に将来別ホストを追加: group所属だけでは include 条件を満たさない

`ansible_play_hosts_all` は limit 適用後の play 全対象を表し、failed/unreachable 後も
対象を保持し、serial の現在バッチだけには縮まらない。今回の「この run に quory が
含まれるか」という集合判定に適している。quory が配布前に失敗した場合でも、他ホストは
リテラル include 条件を満たせず、非正規鍵は配布されない。

## 文書・コメント

- defaults は配布主体を意図的に変数化しない理由と extra vars の危険を説明している。
- tasks は group membership、上書き可能な role default、リテラル固定の選定経緯を
  実際の条件と一致する形で説明している。
- tester-gate 理由文は、ガードが防ぐ横方向上書きと、従来どおり発生するローカル変更を
  区別しており、保証範囲を過大評価していない。
