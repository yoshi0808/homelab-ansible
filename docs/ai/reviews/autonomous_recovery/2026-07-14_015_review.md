## T1: Codex sandbox からの mute set/clear

### 層1 — Codex workspace-write sandbox

`roles/recovery_exec/templates/codex-config.toml.j2` は
`[sandbox_workspace_write]` に次の1パスだけを追加している。

```toml
writable_roots = ["/var/lib/homelab-recovery/mute"]
```

- wrapper は引き続き `--sandbox workspace-write` を固定し、呼出元から sandbox/approval
  option を受け取らない。
- workspace 自体や `/tmp` 以外に追加された writable root は mute directory だけ。
- execpolicy は `default_policy = "deny"` と mute wrapper 3本の明示 allow を維持し、
  sandbox write 許可が任意コマンド実行許可へ波及しない。
- 現在の公式 Codex manual の configuration reference は
  `sandbox_workspace_write.writable_roots` を「cwd 以外の additional writable roots」として
  記載している。
- この環境の production 想定と同じ `codex-cli 0.144.1` でも、`--strict-config doctor` に
  同設定を渡して Configuration の `config loaded` / `config.toml parse ok` を確認した。
  doctor 全体の exit は sandbox 内の state DB access と外部 reachability により非0だったが、
  unknown field / config parse error は無い。

したがってキー名・table・用途は 0.144.1 と一致する。

### 層2 — recovery-io.service mount namespace

`roles/recovery_io/templates/recovery-io.service.j2` は、既存の
`ProtectSystem=strict` を維持したまま、次の `ReadWritePaths` だけを追加している。

```text
/var/lib/homelab-recovery/mute
```

- systemd 側で広い `/var/lib` や `/var/lib/homelab-recovery` 全体を writable にしていない。
- `ReadWritePaths` は mount namespace の read-only 制約を開くだけで DAC を回避しない。
  directory の POSIX ACL は `recovery-exec` だけへ write を付与するため、service 本体の
  `recovery-io` user に直接の file write は増えない。
- Slack 経路の child は既存どおり sudoers で固定された `codex-exec-wrapper` のみを
  `recovery-exec` として起動する。sudo/setuid を Codex sandbox 内へ持ち込む変更は無い。
- push 経路は `recovery-io.service` 配下ではなく sshd/forced-command 配下なので、
  systemd のこの層は非該当という整理で正しい。層1、ACL、execpolicy は共通して有効。
- unit template の handler は daemon reload と service restart を行うため、quory 適用後に
  新しい mount namespace が反映される。

レンダリング結果でも、既存2パスと mute directory の3パスだけが `ReadWritePaths` に出力された。

## T2: PVE replication log 取得元

`roles/recovery_exec/templates/recovery-investigate-dispatch-pve.sh.j2` の
`journal-replication` は `/var/log/pve/replicate/*` の regular file を列挙し、各ファイルを
`/usr/bin/tail -n 200 -- "$replication_log"` で読む固定実装になった。

- path と line cap は server-side script 内で固定され、client/NL 由来の path、job ID、
  option を受け取らない。
- glob 結果は `[[ -f ... ]]` で regular file に限定し、`tail` の path は quote され、
  option 終端 `--` もある。
- 対象が無い場合は説明を出して exit 0。対象 file の read/tail failure は
  `set -euo pipefail` により成功扱いにしない。
- tester は pve2 で当該 directory の job log と world-readable permission を実測済み。
  Proxmox の upstream source history でも replication log directory と job-id file は
  `/var/log/pve/replicate` と定義されている。
  参考: `https://lists.proxmox.com/pipermail/pve-devel/2017-June/026941.html`
- direct read に sudo は不要なため、sudoers から旧 replication `journalctl` 2-unit 行を
  削除したのは least privilege の改善。新しい wildcard sudo rule は無い。
- wrapper/dispatch の二重 allowlistは `journal-replication` を維持し、AGENTS は check 名を
  保持しつつ取得元が systemd journal ではないことを明記している。

## 回帰・010 からの境界

- T2 の機能差分は replication check の取得元、対応 sudoers 行の削除、AGENTS の説明。

  `journal-cluster` の3 units は維持。
- `AGENTS.md.j2` は Proxmox 節と per-target mute 節の両方を維持。
- PVE recovery/action wrapper は追加されていない。
