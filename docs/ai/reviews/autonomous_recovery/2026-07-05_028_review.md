## 結論

must-fix はありません。

read-only 調査コマンド拡充として、危険な復旧操作の追加、任意 SSH / 任意 SQL / 任意パス読み取りに直結する変更は見当たりません。`homelab-investigate-*` の allowlist、reports helper の固定 base path + 再検証、Semaphore query の固定 SQL + 整数パラメータ化、Codex execpolicy への調査系追加は、requirement と `autonomous_recovery_policy.md` の安全設計に概ね沿っています。

## 指摘

### suggestion: `homelab-reports` が既存の自律復旧レポート階層を読めない

- `roles/recovery_exec/files/recovery-reports-helper:30`
- `roles/recovery_exec/files/recovery-reports-helper:43`
- `roles/recovery_service_restart/defaults/main.yml:7`
- `roles/recovery_vm_reboot/defaults/main.yml:36`
- `roles/recovery_ha_failover/defaults/main.yml:43`

`homelab-reports` は `reports/<playbook>/<filename>` の1階層だけを扱います。一方、自律復旧系のレポート保存先は `reports/recovery_investigations/<target>/...json` です。

そのため、現在の実装だと `homelab-reports list-playbooks` には `recovery_investigations` が出ますが、`homelab-reports list-reports recovery_investigations` は直下の通常ファイルだけを見るため、`sophos-fw` / `authy` / `monnie` 配下の復旧レポートを列挙できません。`show-report recovery_investigations 20260702_113322Z.json` のような指定も実ファイルが1階層下にあるため失敗します。

requirement のコマンド仕様自体は `reports/<playbook>/` 前提なので、厳密には実装逸脱ではありません。ただし今回の対象が自律復旧パイプラインの調査拡充である以上、既存の復旧レポートを読めない制約は運用上かなり目立ちます。

対応案:
- 今回のまま commit する場合は、未対応事項として「ネストした `reports/recovery_investigations/<target>/` は対象外」と明記する。
- 取り込む場合は、`list-reports <playbook> [target]` / `show-report <playbook> [target] <filename>` のように、許可済みの追加 path segment を1つだけ扱える形にする。`target` も `[a-zA-Z0-9_-]+` で検証し、`realpath` の under-base 確認を維持する。

### suggestion: `list-reports` は JSON 以外も列挙する

- `roles/recovery_exec/files/recovery-reports-helper:36`

`list-reports` は `find "$dir" -type f` で通常ファイルをすべて出しますが、`show-report` は `^[a-zA-Z0-9_-]+\.json$` だけを許可します。実際に `reports/radius-health/README.md` のような非 JSON ファイルがあり、`list-reports radius-health` では表示され得ますが、`show-report` では拒否されます。

安全性の問題ではありませんが、AGENTS.md では JSON レポート参照ツールとして説明されているため、`list-reports` 側も `*.json` だけに絞る方が自然です。

### nit: privileged helper 側も引数個数を厳密化すると説明と揃う

- `roles/recovery_exec/files/recovery-reports-helper:26`

Codex-facing wrapper の `homelab-reports` はサブコマンドごとに引数個数を検証していますが、sudoers で直接許可される `recovery-reports-helper` 側は `list-playbooks extra` や `list-reports proxmox-health extra` の余剰引数を無視します。

現状でも path 検証と固定 base path により読み取り範囲は広がらないため、セキュリティ上の must-fix ではありません。ただし implement に「helper が同じ正規表現で再検証」とあるので、個数検証も helper 側で揃えると監査しやすくなります。

## 確認したこと

- 新規 shell 3本に `bash -n` を実行し、syntax error なし。
- `homelab-reports` / `recovery-reports-helper` の path 検証は、固定 base path、`NAME_RE` / `FILE_RE`、`realpath -e` の under-base 判定で構成されており、スラッシュや `..` を通す経路は見当たりません。
- `homelab-semaphore-query` はクエリ名を case で固定し、パラメータを整数に制限しています。SQL文字列は `sh -c` ではなく `sqlite3` の argv として渡されており、要求仕様の「自由SQLをCodexに書かせない」に沿っています。
- Codex execpolicy は `homelab-reports` / `homelab-semaphore-query` を調査系として追加し、recover 系とはコメント上も分離されています。
- `dmesg` を `journalctl -k` に置き換える判断は、read-only かつ sudoers 追加を避ける方針として妥当です。
