## Review details

### 1. The replacements are display/audit-only

The diff contains exactly these timestamp substitutions:

- `recovery_ha_failover`: `started_at` and report `completed_at`.
- `recovery_vm_reboot`: `started_at` and report `completed_at`.
- `ubuntu_vm_full_upgrade/reboot_local.yml`: reboot-failure Slack `Time`.
- `ubuntu_vm_full_upgrade/reboot_quory.yml`: pending-flag informational timestamp and scheduling-failure Slack `Time`.
- `quory-post-upgrade-check.sh`: Slack `Time`.

The surrounding task conditions, blocks/rescue paths, result facts, notification channels/statuses, command execution, and failure handling are unchanged.

The quory pending flag is consumed as an existence gate (`-f`) and its timestamp text is not parsed. Changing the timestamp embedded in its content therefore has no control-flow effect.

### 2. Recovery report filenames remain safe and consistent

`_rhf_started_at` and `_rvr_started_at` are also used for report filenames through this unchanged chain:

```text
replace(':', '') | replace('-', '') | replace('T', '_')
```

For a JST timestamp such as `2026-07-13T20:15:30+09:00`, the result is `20260713_201530+0900.json`. This is the same input format and replacement chain already used by `recovery_service_restart`. The conversion shifts the displayed wall-clock hour and adds the explicit offset suffix, while retaining second-level uniqueness and chronological filename ordering.

### 3. Repository-wide `date -u` scan

A scan excluding documentation and generated reports found no remaining `date -u` or `date --utc` calls under runtime `roles/`, `scripts/`, `playbooks/`, or `inventories/`. Thus no Slack/report/flag path using that UTC command form was missed.

The change did not touch epoch timestamps (`date +%s` / `date +%s%3N`), certificate naming dates, or other timestamps that were not using `date -u`; those retain their existing semantics.

### Out-of-scope observation

`roles/proxmox_patch_dryrun/files/proxmox-dryrun-collect.sh` contains the pre-existing expression:

```bash
date +"%Y-%m-%dT%H:%M:%SZ"
```

It does not use `-u`, so on a JST host it produces local wall-clock time with a literal UTC `Z` suffix. This is not a missed `date -u` replacement and is outside the five-file review scope, but it is a separate timestamp-label inconsistency worth triaging in a future change.
