## 各wrapperの引数検証ロジック

### ① investigate 拡充(既存の2層構成に追記)

- 検証ポイントは2箇所: quory側 `homelab-investigate-<node>`(`case "${1:-status}" in <許可リスト>)`)→ SSH forced command → 対象ホスト側 `recovery-investigate-dispatch.sh`(`case "$SSH_ORIGINAL_COMMAND" in <許可リスト>)`)。
- 追加した値(`dmesg`, `journal-<svc>-1h`, `journal-<svc>-24h`, `journal-<svc>-err`, `journal-<svc>-warn`)は両方の case 文に**固定文字列**として追加(`recovery_exec_targets` のループで生成されるが、期間・優先度は Jinja テンプレート側にハードコードした4パターンのみで、呼び出し側が期間・優先度を自由記述することはできない)。一致しない文字列は両層とも `denied` で拒否。
- `dmesg` は `dmesg -T` ではなく `journalctl -k -n 50 --no-pager` を採用(設計判断・下記参照)。

### ② `homelab-reports` → `recovery-reports-helper`

- `homelab-reports`(非特権、quory上でrecovery-execとして実行): サブコマンドと引数の**個数**・`playbook`/`filename` の正規表現を検証してから `exec sudo -n -u yoshi recovery-reports-helper "$@"`。
  - `playbook`: `^[a-zA-Z0-9_-]+$`
  - `filename`: `^[a-zA-Z0-9_-]+\.json$`(スラッシュ・ドット文字は上記正規表現に含まれないため、単体では絶対にパストラバーサルを構成できない)
- `recovery-reports-helper`(sudo経由でyoshiとして実行): 呼び出し元の検証を信用せず**同じ正規表現で再検証**。さらに `realpath -e` で解決した実パスが `BASE`(`/home/yoshi/homelab-ansible/reports`、引数からは絶対に受け取らない固定定数)配下に収まっているかを最終確認してから `find`/`cat` を実行。ベースパスの外に出るケースは構造的に存在しない(正規表現がスラッシュを許可しないため)が、シンボリックリンク対策として `realpath` チェックも二重に入れている。
- 昇格先は `root` ではなく `yoshi`(ファイル所有者)のみ。sudoers: `recovery-exec ALL=(yoshi) NOPASSWD: /usr/local/sbin/recovery-reports-helper *`。

### ③ `homelab-semaphore-query`

- クエリ名(`recent-failed`/`task-errors`/`task-hosts`/`task-output`)を case で照合。SQL本文はスクリプト内の固定文字列で、Codexから渡された文字列がSQLに混入することはない。
- パラメータは `is_uint()`(`^[0-9]+$` の正規表現マッチのみ)で整数以外を拒否。`recent-failed` の `n` はさらに `10#$param` でbase-10算術評価し 1-200 の範囲チェック(先頭ゼロの誤ったoctal解釈を防止するため `10#` プレフィックスを使用)。
- 完成したSQL文字列は `exec sudo -n /usr/bin/sqlite3 -readonly "$DB" "$sql"` として**単一のargv要素**でsqlite3に渡す(シェル文字列連結・`sh -c` を経由しない。要求仕様に明記された「Sophosの教訓」と同じ考え方)。
- sudoers: `recovery-exec ALL=(root) NOPASSWD: /usr/bin/sqlite3 -readonly /var/lib/semaphore/semaphore.db *`(要求仕様に明記された通り、パス・`-readonly` を固定。`*` は末尾のSQL文字列1個のみをカバーし、`-readonly` があるため万一SQL側に細工があっても書き込みはSQLiteエンジンが拒否する)。

## 設計判断(要確認・レビュー対象)

1. **`dmesg -T` ではなく `journalctl -k` を採用**: このホストではおそらく `kernel.dmesg_restrict=1` により非rootの `dmesg` 直接実行が権限エラーになる(既存の `memory` チェックが同じ理由で `journalctl -k` を使っている前例に合わせた)。sudoers への新規エントリを増やさずに済む。もし実機で `dmesg_restrict=0` であることが判明していれば `dmesg -T` に戻すことも可能。
2. **② の昇格先を `yoshi` にした**: 要求仕様は権限方式を明示していなかったため、least-privilege と `recovery_io` の既存sudoers(`(recovery_io_exec_user)` という非root昇格の前例)に合わせて `(yoshi)` を選択した。`root` にする方が実装は単純だが、reports/ 以外への波及が(理論上は)一切ないという点で `yoshi` の方が安全域が狭い。
3. **journal since/priority の組み合わせ**: `1h`/`24h` × `err`/`warn` の4パターン固定(自由な期間・優先度指定はできない)。要求仕様の「期間・優先度はwrapper側で許可リスト照合」を、離散的な named check として実装した(既存コードベースの一貫した書き方に合わせた)。
