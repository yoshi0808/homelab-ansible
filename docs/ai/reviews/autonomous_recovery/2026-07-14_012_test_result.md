## 結論

静的検証、ACL、wrapper 直実行、入力検証、並行 writer、probe/push の mute 尊重、
pve2 の path/unit/no-pty sudo/allowlist は期待どおりだった。

ただし、実際の Codex sandbox 経路では mute directory が read-only になり、
`homelab-mute-set` と `homelab-mute-clear` の両方が失敗した。また pve2 では
replication job が直近に成功している一方、`journal-replication` が空だった。
どちらも requirement/test_plan の主要確認項目を満たさないため、このまま確定不可。

pve2 で journal 差異を検出した時点で stop 条件に従い、pve1 への配備・実行は行っていない。

## Findings

### T1 — must-fix: 実 Codex sandbox から mute set/clear ができない

quory 上で `recovery-exec` として wrapper を直接呼ぶ場合、POSIX ACL により set/status/clear は
成功する。しかし本番相当の `codex-exec-wrapper` から Codex を起動すると、sandbox 表示は
`workspace-write [workdir, /tmp, $TMPDIR]` であり、mute directory は書き込み対象外だった。

- Codex から set: mute JSON の作成時に read-only filesystem で失敗。
- 既存 mute を用意して Codex から clear: `rm` が read-only filesystem で失敗。
- status は read-only のため成功。
- 直接 wrapper の ACL テストは成功するため、OS ACL ではなく sandbox mount/write-root 境界の問題。

requirement の「Slack/Codex から set + status + clear」を満たさない。sandbox の writable root
設定、または sandbox 内から安全に書ける別経路の設計が必要。

### T2 — must-fix: journal-replication が実際の replication log を返さない

pve2 では以下を確認した。

- `pvescheduler`, `pvestatd`, `pve-cluster`, `corosync`, `pvedaemon` は unit が存在し active。
- `replication-status` は直近に成功した複数 job を表示。
- それにもかかわらず `journal-replication` は `-- No entries --`。
- pve2 上で `pvescheduler` / `pvestatd` の直近 2 時間 journal を直接確認しても空。

unit の存在だけでは requirement の「実際の replication 関連ログ」を満たさない。
replication 実行ログの実保存先を再調査し、named check の取得元を修正する必要がある。

### ACL / mode

期待どおり。

- quory: `group::r-x`, `mask::rwx`, `user:recovery-exec:rwx`（effective rwx）, `other::r-x`。
  `stat` の 0775 は ACL mask を group bits に表示したもの。
- `/var/lib/homelab-recovery` 以下で `recovery-exec` named ACL は mute directory のみに存在。
- probe CLI 再配備、human CLI の反復実行、並行テスト後も mask/effective rwx は維持。

### wrapper 直実行（recovery-exec、wrapper 内 sudo なし）

成功:

- `homelab-mute-set monnie 5`: 実効残り 5 分を表示。
- JSON file: `0644`。
- status: 3 target を表示。

- `0`, `241`, 非整数, unknown target: 全て非 0 で理由付き拒否。

### 並行 writer / max semantics

quory 上で human CLI の 120 分 set と Codex wrapper の 5 分 set を並行起動し、10 回反復。

- 10/10 で最終残り時間は約 7198〜7199 秒（長い 120 分側）。
- ACL mask/effective rwx は反復後も維持。
- 最後に monnie mute を clear 済み。

current worktree の `set.yml` と quory checkout の checksum は不一致だったため、quory checkout の
stale な `set.yml` は live coverage として採用しなかった。ansy から一時 test playbook で
current `set.yml` を include したところ、設計どおり `delegate_to: localhost` により ansy に書いた。
これは production 起点（quory 上の Ansible）とは異なるため有効な live test とせず、作成した
ansy の monnie mute は直ちに clear した。current `set.yml` の live quory 実行は未検証。

### probe 連携

controlled drill で次の順序を journal で確認。

1. `PROBE monnie: FAIL ['drill'] (1/5)`
2. mute 設定後の次 cycle: `PROBE monnie: muted ... — skip`
3. mute/marker cleanup 後に再度 drill: `FAIL ['drill'] (1/5)`

3 が `(2/5)` ではなく `(1/5)` のため、mute cycle で連続失敗 counter が reset されたことを確認。
drill marker と monnie mute は cleanup 済み。

### push 連携

- dispatch log は 1 行だけ増加。
- 内容は `muted ... — skip`。
- Codex recovery session は発火しなかった。
- mute は cleanup 済み。

### execpolicy / 実 Codex 経路

- Codex から `homelab-mute-status`: 成功（allow を実確認）。

## 実行方法の置換・環境対応

1. sandbox では `~/.ansible/tmp` と `~/.ansible/cp` が書き込み不可だったため、
   `ANSIBLE_LOCAL_TEMP`, `ANSIBLE_REMOTE_TEMP`, `ANSIBLE_SSH_CONTROL_PATH_DIR` を `/tmp` 配下へ変更。
2. system SSH config drop-in が sandbox UID mapping で permission error になったため、
   repository wrapper と同じ `ANSIBLE_SSH_ARGS='-F /dev/null ...'` を使用。host key checking と
   inventory の `id_ann` は維持。
3. sandbox の network 制限後は、承認済み live test を escalated execution で実行。
4. 長時間化した Ansible ad-hoc wrapper test は中断し、lock/process を read-only 確認したうえで、
   core.md 指定の `ssh -F /dev/null -i ~/.ssh/id_ann ann@quory.internal` 経路に置換。
   中断で残った hidden temp file は削除済み。
5. pve2-first を厳密に守るため target list を一時的に pve2 のみにし、確認後に pve1へ進む計画だった。
   T2 により pve1 は停止し、quory local config だけ full list に復元した。

これらは controller transport/scratch または target 順序の変更であり、tester-gate 分類や
playbook の処理内容を弱めていない。legacy `tester_mode` は playbook 自身が拒否するため使用していない。
