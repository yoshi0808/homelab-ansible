## Phase 1: mute(quory 配備 + ACL + 並行 + probe)

配備:

1. `recovery_exec_setup.yml` を quory へ適用(wrapper 配備・ACL・execpolicy・AGENTS・lock 事前作成)。
2. `recovery_probe_setup.yml` を適用(homelab-mute CLI / deploy_cli)。ansy にも deploy_cli が流れる経路を含む。

ACL 最終状態(F1 の要):

3. **quory**: `getfacl /var/lib/homelab-recovery/mute` で
   `group::r-x` / `mask::rwx` / `user:recovery-exec:rwx`(`#effective:r-x` でない=実効 rwx)/ `other::r-x`。`stat` が 0755(mask 有り表示)。
4. **ansy**(ACL 無し): `root:root 0755`、group/other は r-x、**group write が無い**こと(mask 無し)。
5. deploy_cli / set.yml / 人間 CLI を quory で**再適用**しても mask::rwx と recovery-exec 実効 rwx が**リセットされない**こと。

wrapper 動作(recovery-exec として sudo 無し):

6. recovery-exec で `homelab-mute-set monnie 5` → 成功、mute file 0644 生成、出力が**実効残り分数**を返す。
7. `homelab-mute-status` が 3 target を表示、`homelab-mute-clear monnie` で解除。
8. 入力検証: `0` / `241` / 非整数 / 未知 target → いずれも拒否(exit 非0・理由表示)。
9. **短縮しない(並行)**: 長い自動 mute(例 set.yml で 120 分)有効中に短い Codex set(5 分)→ 最終 `until` が 120 分側のまま。
10. execpolicy: Codex が `homelab-mute-set/status/clear` を呼べ、mute 以外の新規コマンドは依然 deny。

probe/push 連携:

11. mute 有効中、`recovery-probe` が該当 target を `muted — skip` し、連続失敗カウンタをリセットすること(ログ確認)。
12. push 経路(`recovery-push-dispatch.sh`)が同 mute file を発火前に尊重すること。
13. mute dir 以外に recovery-exec の ACL/write が増えていないこと(`getfacl` で mute dir 限定)。

## Phase 2: pve 調査(pve2 先行 → pve1)

配備:

1. `recovery_exec_setup.yml` の pve 配備分(dispatch / sudoers / authorized_keys-pve)を **pve2 先行**で適用 → 確認後 pve1。

パス・unit 実在(F3/F4 の要):

2. pve2/pve1 で `command -v pvesr pvecm pvesm zpool zfs journalctl` → dispatch/sudoers の絶対パスと一致(特に `pvesm=/usr/sbin`)。差異あれば該当行修正が必要(要フィードバック)。
3. journal 対象 unit の実在: `pvescheduler` / `pvestatd` / `pve-cluster` / `corosync` / `pvedaemon`。**とりわけ replication ジョブのログが実際に `pvescheduler` unit に出るか**を実出力で確認。出なければ unit セット調整が必要(要フィードバック)。

9 チェック実行(quory の recovery-exec から、read-only):

4. `homelab-investigate-pve2 <check>` を 12 チェック(既存3+新9)全て実行 → 各成功・期待 read-only 出力。特に:
   - `replication-status` がレプリケーションジョブ状態を返す。
   - `journal-replication` が実際に replication 関連ログを返す(空でない/取りこぼしなし)。
   - `storage-status`(`/usr/sbin/pvesm status`)が動く。
5. `sudo -n`(no-pty / forced command)が新コマンド(特に `pvesm`/`zpool`/`journalctl`)で `requiretty` 等に阻まれず成功。
6. allowlist 外は `denied`: 例 `pvesr read 211-0`(Phase 2 用パラメータ付き)/ `bogus` / 空。
7. 既存3チェック(cluster-status / cluster-resources / ha-status)の回帰なし。
8. pve1 でも 4〜7 を再確認。

Codex 経由の一次切り分け(AGENTS.md 反映確認):

9. Slack もしくは codex-exec 経由で「monnie のレプリケーションが失敗、状況を見て」と自然言語依頼 → Codex が新チェック(replication-status + journal-replication → cluster-quorum/zpool-health/zfs-list)で局所化できること。
