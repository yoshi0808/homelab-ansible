## Findings

### 1. [must-fix] 既存の `chmod 0755` が mute directory の ACL mask から write を落とす

対象:

- `roles/recovery_exec/tasks/main.yml:263-279`
- `roles/recovery_mute/files/homelab-mute:75-76`
- `roles/recovery_mute/tasks/set.yml:14-20`

今回の role は `/var/lib/homelab-recovery/mute` を `0755` にした後、named user
`recovery-exec:rwx` ACL を追加するため、配備直後は wrapper が書ける。しかし既存の人間用
CLI は set ごとに同 directory へ `chmod 0755` を行い、playbook 自動 mute も
`ansible.builtin.file(mode: "0755")` を毎回通る。

POSIX ACL では named user/group の effective permission は ACL mask に制約され、directory
の group class mode bits はその mask に対応する。したがって後続の `chmod 0755` は mask を
`r-x` に戻し、ACL entry 自体が `rwx` と表示されても `recovery-exec` の effective permission
は `r-x` となる。以後 `homelab-mute-set` の `mktemp` と `homelab-mute-clear` の `rm` は
permission denied になる。自動 mute または人間用 set を一度使うだけで Slack/Codex 経路が
壊れるため、requirement の「sudo 無し ACL 経路」を満たさない。

既存の全 directory writer が ACL を保持するようにすること。少なくとも人間 CLI の
`chmod 0755` と `recovery_mute/tasks/set.yml` の mode 管理を、named ACL の mask を
`rwx` のまま保つ設計へ揃える必要がある。修正後は以下の順序を tester で確認すること:

1. recovery_exec_setup 適用
2. playbook 自動 mute または人間用 `homelab-mute set`
3. `getfacl` で `recovery-exec` の effective `rwx` を確認
4. recovery-exec として sudo 無しの set/clear を実行

### 2. [must-fix] 複数 writer の read-modify-write 競合で長い mute を短縮できる

対象:

- `roles/recovery_exec/files/homelab-mute-set:76-96`
- `roles/recovery_mute/files/homelab-mute:78-95`
- `roles/recovery_mute/tasks/set.yml:22-52`

`mktemp` → `mv` は reader に不完全 JSON を見せないという意味では atomic だが、
`existing_until` の read → `max()` 計算 → rename 全体は排他されていない。例えば Codex が
短い TTL を読み取った直後に playbook が長い evacuate mute を書き、その後 Codex が古い計算
結果を rename すると、長い自動 mute を短縮する。逆順でも同じ lost-update が起こる。

これは requirement が安全上明記する「`max(existing, now + N)` で短縮しない」を並行実行時に
破る。atomic write と atomic read-modify-write は別である。人間 CLI、playbook 自動 mute、
新 wrapper の全 writer で target ごとの共通 lock を使用し、read/max/write を同じ critical
section に入れること。少なくとも短い Codex set と長い自動 mute を並行させ、最終 `until` が
常に長い方になるテストを追加すること。

### 3. [must-fix] `storage-status` の `pvesm` 絶対パスが誤っている

対象:

- `roles/recovery_exec/templates/recovery-investigate-dispatch-pve.sh.j2:46-48`
- `roles/recovery_exec/templates/sudoers-recovery-exec-pve-target.j2:43`

実装は `/usr/bin/pvesm status` を呼び、sudoers も同じ誤ったパスを許可している。
Proxmox VE の `pvesm` は `/usr/sbin/pvesm` に配置される。現在の形では dispatch が
`sudo: /usr/bin/pvesm: command not found`（または rule 不一致）となり、要求された
`storage-status` は動かない。

dispatch と sudoers の双方を `/usr/sbin/pvesm status` に揃えること。implement の
「pvesr/pvecm/pvesm は pvesh と同じ `/usr/bin` 想定」は誤り。pre-deploy NOTE に先送り
せず、既知の標準パスはコード側で直す必要がある。

参考: Proxmox staff が `/usr/sbin/pvesm` を示している
`https://forum.proxmox.com/threads/disable-pvestatd-for-cifs-samba.125140/`。

### 4. [must-fix] `journal-replication` が廃止済みの `pvesr.service` を対象にしている

対象:

- `roles/recovery_exec/templates/recovery-investigate-dispatch-pve.sh.j2:57-59`
- `roles/recovery_exec/templates/sudoers-recovery-exec-pve-target.j2:46`
- `roles/recovery_exec/templates/AGENTS.md.j2:103-105`

現在の Proxmox VE では replication / vzdump のスケジュール起動は `pvescheduler` が担い、
旧 `pvesr.service` / `pvesr.timer` は 2021年に削除されている。実装説明の
「`pvesr` はレプリケーション本体の service/timer」「`pvestatd` がスケジューリングを担う」
は現行構成と一致しない。`journalctl -u pvesr` は存在しない unit を静かに無視し得るため、
この named check は成功扱いのまま replication の主要ログを欠落させる。

pve1/pve2 の実 unit を tester 工程で確認した上で、少なくとも現行標準の
`pvescheduler` を対象に含め、dispatch・sudoers・AGENTS・implement の説明を一致させること。
必要なら replication job のログが実際にどの unit / identifier に記録されるかも実出力で確認
すること。

参考: Proxmox の変更記録
`https://lists.proxmox.com/pipermail/pve-devel/2021-October/050292.html`、現行
`pvescheduler` の説明 `https://pve.proxmox.com/pve-docs/pvescheduler.8.html`。

### 5. [suggestion] `journal-system` は priority filter を付ける方が一次切り分けに有効

対象:

- `roles/recovery_exec/templates/recovery-investigate-dispatch-pve.sh.j2:60-62`
- `roles/recovery_exec/templates/sudoers-recovery-exec-pve-target.j2:47`

priority 無しの node-wide journal を `-n 300` で切ると、稼働量の多い pve では info の
直近300行が2時間より大幅に短い区間を占め、warning/error が押し出される可能性が高い。
replication / cluster の info は専用2チェックで取得できるため、system 横断の異常抽出は既存
authy/monnie と同じ `-p warning..err` を付ける方が役割分担が明確。requirement の実コマンドは
「案」で実装判断対象なので commit blocker にはしないが、差し替えを推奨する。

## 重点確認への回答

### sudo の `--since "-2 hours"` 照合

**指摘なし。implementer2 の結論が正しい。** classic sudo は command arguments を
token ごとではなく、空白で連結した単一文字列として照合する。dispatch の argv が
`["--since", "-2 hours", ...]` でも、sudoers の `--since -2 hours ...` と同じ文字列に
なるため一致する。sudoers に `"` を足すと literal quote を要求するため不適切。

ただし、この性質は異なる argv 境界も同一視する。今回の SSH forced-command dispatch は
client 値を固定 case に落としてから固定 argv で sudo を呼ぶため、追加の任意引数経路には
なっていない。Phase 2 で可変引数を導入する際は、この連結照合を安全境界として過信しないこと。

根拠: sudo 公式 `sudoers(5)` の “Command line arguments are matched as a single,
concatenated string.”
`https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf`。

### 共有 `AGENTS.md.j2`

**指摘なし。** pve の新12チェック・調査のみの禁止事項は `:78-120`、mute の3能力・TTL上限・
global pause との使い分けは `:175-201`、許可 tool 列挙は `:228` に共存している。片方の
欠落や上書きはない。

### mute wrapper のその他の要件

以下は妥当:

- target allowlist は `authy` / `monnie` / `sophos-fw` に固定
- minutes は数字のみ、1..240、超過時は明示拒否
- reason は shell 再解釈せず Python `json.dumps` へ argv データとして渡す
- set は通常の逐次実行では既存 until との max を取り、実効残り分数を返す
- temp file を同一 directory に作り、0644 後に rename するため reader 視点で atomic
- Codex 経路に sudo/setuid を追加していない
- execpolicy は3 wrapper のみ追加し default deny を維持

ただし Findings 1/2 のため、実運用での ACL write と「決して短縮しない」はまだ保証されない。
