## 0. 大前提(Anthropic公式知見)

- マルチエージェント構成は通常のchatの約15倍のトークンを消費する。「その分の価値がある案件にだけ使う」。
- 効率スケーリングの目安(公式): 単純な事実確認=1エージェント・3〜10ツール呼び出し、直接比較=2〜4サブエージェント・各10〜15呼び出し、複雑な調査=10以上のサブエージェント。
- 委任時は毎回「objective・output format・使うツール/対象範囲・明確なタスク境界」を明示する。曖昧な指示は重複調査・抜け漏れを招く。

## 1. 着手前の仕分け(Tech Leadが依頼を受けた最初の一手)

依頼を受けたら、実装・レビュー・テストへ進む前に、必ず次の全ての問いを自問する。**複数の行に該当してよい。該当した行の中で最も重いTierを最終的に採用する**(例: 安全境界に触れ、かつ複数システムにまたがる場合はTier4を採用する。「最初にYesの行で終了」方式だと、複合的に危険な案件が軽い方のTierで打ち切られてしまうため採らない)。

| 問い | 該当時の目安Tier |
|---|---|
| 削除・sudo・外部公開・秘密情報・影響不明など安全境界に触れるか？ | Tier 3(下限。他の行の方が重ければそちらを採用) |
| 複数の**Ansibleロール**(`roles/`配下)・複数システムにまたがり、かつ各所で個別の判断や相互作用の確認が必要(単純な同種・機械的コピーでは済まない)か、または影響範囲が事前に読めないか？ | Tier 4 |
| 実行時の挙動を変えない(コメント/文書/設定値の**説明文**のみで、実行値そのものは変えない)、かつ単一ファイル・少量か？ | Tier 1 |
| 実行時の挙動を変えないが、複数ファイルにまたがる同種・機械的な変更か？ | Tier 2 |
| 実行時の挙動を変える(新しい判定・分岐・閾値の追加等)か？単一ファイルでも該当する | Tier 3 |

迷ったら一段重い方を選ぶ(過小工程による品質事故の方が、過大工程による時間浪費より悪い)。

**Tier4行と依頼Bの関係(注記)**: 依頼B(7 playbook、7つの異なるAnsibleロールにまたがるコメント整合)は複数ロール・複数システムにまたがるが、各所の編集が独立した同一パターンの機械的コピーで相互作用の確認を要さないため、Tier4行には該当せずTier2行(挙動不変・複数ファイル同種)が採用される。ロール間の依存関係を読む必要がある変更(例: あるroleの出力を別roleが参照する処理の変更)であれば、たとえ機械的に見えてもTier4行に該当する。

## 2. Tier別の標準工程

### Tier 1: 直接対応(委任しない)

対象: typo修正、1ファイルの1〜数行のコメント/文書修正、事実確認だけで完結する軽微な訂正。

- Tech Lead(またはCoordinator)が**自分で**編集し、diffを自分で読んで確認する。Implementer/Reviewer/Testerへの委任は行わない。
- Anthropicの「単純な事実確認は1エージェントで足りる」に対応。委任コスト(メッセージ往復・待機・polling)がタスク自体より大きくなる規模。
- 唯一の例外: 秘密情報/本番影響/削除など安全境界に触れる場合は、規模に関わらずTier 3以上を使う(軽量さより安全確認を優先)。

### Tier 2: 軽量レーン(Owner中心・呼出人数は選択制)

対象: 複数ファイルにまたがるが同種・機械的な変更で、挙動を変えない(例: 2026-07-22のtester-gateコメント7本整合)。

- 棚卸し・実装はOwner(Implementer役)1名が必須で担当する。それ以外のRoleは必要な場合のみ呼ぶ(§5の「常駐ロースター固定・呼出人数のみ可変」と整合させる)。
  - Reviewerは、Ownerでは代替できない**意味論の独立確認**が必要な場合のみ呼ぶ(差分と、その差分が依存する実態だけを確認し、独立した再調査はしない)。
  - Testerは、Ownerでは代替できない**機械検査**(lint、diff-check、対象限定確認等)が必要な場合のみ呼ぶ。独立harnessでの再現テストは行わない。
  - どちらの条件にも該当しなければOwner単独で完結してよい。両方に該当する場合のみ3 Role構成にする。
- 複数ファイルの同種変更は1バッチ、中間成果物を作らず最終記録1件に統合する。
- 着手時に時間/コンテキストの上限を決める。上限の半分を超えた時点でCoordinatorへ状況報告する(Tech Lead自身の自己申告だけに頼らない外部チェックポイントを設け、依頼Bのような見落としの再発を防ぐ)。上限超過時は工程自体を見直す。
- **上位Tierへの昇格条件(いずれか1つでも該当したら即座に切り替える)**: 作業中に実行時の挙動変更を発見した/安全境界に接触した/実態の根拠が確認できない/Reviewerのmust-fixが実ロジックへ波及する。該当したら§1の全項目を再評価し、最も重いTierへ切り替える(通常はTier3だが、実態の根拠が確認できず影響範囲が読めない場合は§1のTier4行に該当するためTier4)。

### Tier 3: 標準trioフロー

対象: 実ロジック変更(新しい判定・分岐・閾値追加等)。単一role・単一ファイルでも対象。

- Implementer→Reviewer→Testerの独立フロー(現行の3 pilotで実証済みの標準工程)。各roleは自分の持ち場だけを見て、他roleの調査を重複しない。
- Reviewerには「何を確認すべきか」「何は対象外か」を明示する(pilot1〜3のsetupメモが良い実例)。
- 通常1往復で完了を目指すが、must-fixが出れば素直に反復する。

### Tier 4: 複合案件

対象: 複数のAnsibleロール・複数システムにまたがり、各所で個別の判断や相互作用の確認が必要(単純な同種・機械的コピーでは済まない)、または影響範囲が事前に読めない変更。

- Tech Leadは着手前にextended thinking相当で分解方針を立て、各roleの役割・境界・出力形式を明文化してから委任する(Anthropic「detailed task specification」)。
- 必要なら段階的に分割し(例: 調査フェーズ→設計フェーズ→実装フェーズ)、各フェーズの完了を確認してから次へ進む。
- cross-trio(techleadとtechlead2の両trioにまたがる)が必要な場合は、role-routing-index.mdの合意手順に従う。

## 3. 委任時の必須記載事項(Tier 2〜4共通)

Anthropic「detailed task specification」に対応。委任メッセージには最低限次を含める。

- **objective**: 何を達成するか(完了条件を含む)。
- **output format**: 成果物の形式・保存先。
- **scope**: 対象ファイル・対象外(「Xは対象外、Yの担当」等、他roleとの境界を明示)。
- **参照範囲**: 読むべきContext/Policyと、読まなくてよい範囲。

すでにTech Lead側でこの水準の委任(objective/scope明示)は概ね実施できている。今回の不足は主にTier判定(1.)を省略し、常にTier3〜4相当の工程を適用していた点にある。

## 5. 現行AI構成への含意(2026-07-22、Yoshinobuとの議論を反映。恒久原則ではなく現行構成上の選択)

「可変」は**エージェントの動的な起動・削除**ではなく、**常駐ロースターは固定したまま、案件ごとに呼び出すRoleの人数を変える**という形で実現する。これは現時点の運用選択であり、構成が変われば見直してよい。

- Codexベースの6体(implementer/reviewer/tester × 2trio)は、agmsg monitorでの受信だけでなく、ASK承認プロンプトに対話端末からYを押す必要があるため、**tmux(または同等の対話端末)は引き続き必須**である。これはTier制と独立した制約で、Skillでは解消できない。既存の`tmux-ask-watch.sh`はASK検出を通知するだけで、それ自体が承認・入力を行うわけではない。代理入力ができるのは案件ownerが事前にGO済みと明示した安全カテゴリの範囲に限られ、techlead2固有の権限ではない(techlead2は監視対象ペインの管轄上その通知を受けているに過ぎない)。この負担軽減の位置づけであり、tmux基盤自体をなくす話ではない。
- Tier1/2は、動的なagent join/leave・tmux pane作成/破棄・bridge再接続を一切必要としない。単に「そのTierで不要なRoleにはメッセージを送らない」だけで済む(未使用のペインは今まで通り待機したまま)。
- したがって、常駐する9体(Coordinator/techlead/techlead2 + 6 Codex role)というロースターの規模自体を変える必要はない。変わるのは「毎回全員を働かせるか、必要な人にだけ振るか」という運用判断だけである。
- 動的なagent数の増減(新しいRoleを一時的に増やす/減らす等)は、別の大きな検討課題として切り離す。今回のSkill草案の範囲外とし、必要になった時点で別途Yoshinobuと相談する。
