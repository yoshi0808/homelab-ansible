# requirement: Proxmox read-only点検3本の単一ノード対応

作成: 2026-07-30 / Coordinator
Tier 3(軸A=3: 本番でscheduleされているplaybookの実ロジック変更かつ複数ホストのorchestration / 軸B=Tier 3はReviewerを工程内に含むため`+R`は付けない)

## 1. 問題定義

夏季の室温対策でpve1を平日日中シャットダウンしている(pve2は常時稼働)。その間、Proxmoxのread-only点検playbookがSemaphoreで毎回`error`になる。

実測(2026-07-30、`homelab-semaphore-query recent-failed 25`。時刻はSemaphore保存値=UTC):

| Semaphore template | playbook | 発火 | 直近のerror |
|---|---|---|---|
| `SAFE: Proxmox healthcheck` | `playbooks/proxmox_healthcheck.yml` | 毎日 20:40 | 07-22 / 23 / 25 / 26 / 27 / 28 / 29 すべて |
| `SAFE: Proxmox hardware check` | `playbooks/proxmox_hw_check.yml` | 毎日 20:45 | 07-22 / 23 / 25 / 26 / 27 / 28 / 29 すべて |
| `SAFE:Proxmox snapshot check` | `playbooks/proxmox_snapshot_check.yml` | 木 09:00 | #420(07-23)、#482(07-30) |

`SAFE: Time sync check`は07-25で止まっており(以降errorなし)、2026-07-26の対応で解決済みである。

**壊れているのは点検機能ではなく終了コードだけである。** 3 roleはいずれも集約を`ansible_play_hosts`(到達したホストの動的リスト)で行っており、ノード数に依存しない — `roles/proxmox_healthcheck/tasks/main.yml:142`・`:165`、`roles/proxmox_hw_check/tasks/main.yml:109`・`:125`、`roles/proxmox_snapshot_check/tasks/main.yml:116`。pve1がUNREACHABLEになるとpve1はplayから外れ、pve2の点検・report・summary・通知は正しく実行される。しかしAnsibleの終了コードが`4`(`RUN_UNREACHABLE_HOSTS`)になり、Semaphoreは非ゼロ終了をタスク失敗として表示する。

これは2026-07-26に`proxmox_patch_dryrun`で特定・解決済みの欠陥クラス(「赤い成功」)の**未掃引分**である。当時の解決策は`ignore_unreachable: true`と直後の3タスク(到達判定・全滅時の明示fail・到達不能ノードのplayからの除外)を1組で入れる形で、`playbooks/proxmox_patch_dryrun.yml:32`・`:55-79`にある。同playbookの冒頭コメントに「`ignore_unreachable`を1行だけ足すと壊れる」理由が記録されている。

実害は「毎営業日3本が赤く、本物の障害と区別できない」ことである。2026-07-30の#482は、この赤の1つが本物かどうかを人が調査して切り分けている(調査結果: `pve1.internal:22`への経路断であり、snapshotの内容不良ではない)。

## 2. ゴール

1. 3本のplaybookがpve1停止中も**終了コード0**で完走し、到達できたノードの点検結果(summary・report JSON・通知)を出す。
2. 出力に**点検できなかったノードが明示される**。片肺の`Result=OK`を、全ノードを見た`OK`と読み違えないようにする。
3. 全候補ノードが到達不能なときは明確なメッセージで**非ゼロ停止**する(空report・サイレント成功にしない)。
4. 4本目に同じ欠陥を作らないよう、機構をコピーせず共通roleへ括り出す。

## 3. 非ゴール

- **変更系playbookは対象外**(`playbooks/cert_renew.yml:79`、`playbooks/ca_trust_deploy.yml:21`、`playbooks/time_sync_ntp_reference.yml:45`)。配布・適用が片方のノードへ届かなかったことは静かに許容してはならないため、意図的に厳格なまま残す。この線引きはADR-008に記録する。
- **`playbooks/proxmox_patch_dryrun.yml`のinline実装を共通roleへ寄せ替えない**(P1へ)。weekly full chainのゲート(`playbooks/proxmox_patch_weekly_full.yml:134`)が消費する経路であり、実データでのapply gate通過が未観測(`docs/ai/status.md` Watch)の段階で作り直すと回帰の切り分けができない。
- `playbooks/proxmox_patch_weekly_full.yml:46`の`hosts: "{{ groups['proxmox'][0] }}"`(ADR-006の決め打ち除去の残り)は対象外。U3がこの箇所と衝突しないことだけ確認する。
- apply側の両ノード要求(SB-027 / SB-028 / SB-032)は変更しない。**read-only点検が片肺で続くことと、applyが両ノードを要求することは別軸である。**
- `monitoring_healthcheck` / `radius_healthcheck`(対象が単一ホストでこの欠陥クラスに当たらない)、`time_sync_check`(2026-07-26に対応済み)は対象外。

## 4. ユーザーストーリー

- 運用者(Yoshinobu)として、平日にSemaphoreを開いたとき、赤いジョブが本物の障害だけであってほしい。今は毎日3本が赤で、本物の障害がその中に埋もれる。
- 運用者として、pve1停止中の点検結果を見たとき、それが「pve2だけを見た結果」であると出力から分かってほしい。
- 次にProxmox点検playbookを足す者として、同じ落とし穴を再発明せずに済むよう、機構が1箇所にあってほしい。

## 6. 成功指標

- pve1停止中の平日、Semaphoreの3本が`success`で並ぶ(次の平日発火: healthcheck / hw_check は当日20:40・20:45、snapshot checkは木曜09:00)。
