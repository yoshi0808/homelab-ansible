# audit: Proxmox read-only点検3本の単一ノード対応

作成: 2026-07-30 / Auditor
検査対象: `docs/ai/reviews/proxmox_readonly_check_single_node/`(001〜006)、`docs/ai/adr/008-proxmox-readonly-check-unreachable-node.md`、`git diff --cached` / `git diff`(working tree)、`docs/ai/status.md`、`docs/ai/effort-baseline.md`。
起点: `2026-07-30_001_requirement.md`。

## 0. 再構成できたか

**再構成できた。** requirement→plan→plan_review(Request Changes 1件)→plan改訂→implement→review(初回 Request Changes 1件)→review再照合(Approve)→implementコメント修正→test_result(AC1〜AC7 PASS)という一連の流れは、各ファイルの相互参照(file:line、AC番号、Critical/Suggestion番号)がすべて現物と一致し、詰まる箇所なく辿れた。要求→設計→実装→レビュー→検証の対応も一貫している。

ただし、**「今この記録が指し示す状態」と「`git diff --cached`が実際に持っている内容」が一致しない**箇所が2件見つかった。これは案件の経緯そのものではなく、経緯を確定させたあとの記録の保存操作(`git add`)が追いついていないという、別種の問題である。詳細を指摘1・2に記す。

## 1. 指摘

### 指摘1: staged済みの`001_requirement.md`・`005_review.md`が、案件が到達した最終状態より古い内容のまま止まっている(クローズを妨げる)

`git status --short`は両ファイルを`AM`(staged追加 + 未staged変更)と報告している。`git diff <path>`(working tree側の差分)で中身を確認すると:

- `2026-07-30_001_requirement.md`: workspaceには「実行元について(2026-07-30訂正)」の節があるが、**staged側にはこの訂正がなく**「終了コードを明示する...実行はquoryから」という、Testerが構造的に不可能と判定し訂正した記述のまま残っている。
- `2026-07-30_005_review.md`: workspaceにはVerdict **Approve**(再照合ログ、Critical #1・Suggestion #1のResolved化)が書かれているが、**staged側は初回のVerdict Request Changes(Critical 1件・Suggestion 1件、いずれもblocking)のまま**である。

test_result.md(§0ヘッダ)は「差分レビュー: Approve済み(blocking無し、Coordinator指示より)」を前提にAC1〜AC7を実施しているが、これは**working tree側の内容**を前提にした記述であり、staged側の内容とは矛盾する。

**このまま`git commit`されると**、commit履歴に残るのは「Request Changesで止まったレビュー」と「quoryから実行できるという誤った前提のrequirement」であり、実際に案件が到達した状態(Approve・実行元の訂正)がgit上から消える。これは`docs/ai/core.md`「現在の変更内容は作業ツリーとdiffを正本とする」の対象外になる領域(commit後はcommitが正本になる)であるため、**commit前に`git add`で解消しておく必要がある**。

### 指摘2: `2026-07-30_006_test_result.md`が`git add`されておらず、staged 16ファイルに含まれていない(クローズを妨げる)

`git status --short`で`?? docs/ai/reviews/proxmox_readonly_check_single_node/2026-07-30_006_test_result.md`(untracked)。案件の最終成果物であり、AC1〜AC7全PASSの唯一の記録であるこのファイルが、現在のstaging areaに一切含まれていない。

このまま`git commit`されると、commit履歴には「Approveレビューまでで止まり、Testerが本実行した記録が存在しない」状態になる。指摘1と合わせると、**現在staged中の16ファイルをそのままcommitした場合の記録は、requirement=訂正前、review=Request Changes、test_result=存在しない、という案件のどの時点の状態とも一致しない**キメラになる。

### 指摘3(非blocking): `docs/ai/status.md`に本案件の記載が一切ない

`docs/ai/status.md`のNowテーブルは空、Watchテーブルにも本案件への言及がない。本案件は次の2点でYoshinobuの判断を待っている状態である。

- Q1: SB-095(Policy改訂)の承認(`2026-07-30_001_requirement.md` §8、`2026-07-30_004_implement.md`「未解決事項」2)
- commit / push(plan §2「工程上の待ち」)

加えて、commit/push後には次の観測点が発生する(いずれも一次記録に明記済みで、消えているわけではない):
- quoryでの`git pull --ff-only`後、Semaphore定期発火が`success`になることの確認(requirement §7訂正、plan §2)
- AC5・AC7の両ノード実機回帰は週末発火で自然確認(test_result §6・plan §4)
- 次回snapshot_check発火は2026-08-06(requirement §9)

これらは他の進行中案件(pve1夏季シャットダウン、Grafana AC4など)と同じ性質の「将来の時点でしか確かめられないこと」であり、`docs/ai/status.md`の設計(規律1「置き場が他に無い状態」)に照らすとWatch/Nowに載る性質の情報に見える。ただし本案件がまだcommit前(Auditor起動が「クローズ前」の1回であり、commit/push自体はこの後の工程)であるため、**現時点でこの行が無いこと自体を欠陥と断定はしない** — Coordinatorがこのあとの工程(commit承認取得、push、quory反映確認)を進める過程で追加すればよい性質であり、クローズを妨げるものではない。指摘1・2の解消と合わせてCoordinatorが判断すること。

## 2. 指摘に該当しなかった主な確認事項

- 決定の追跡: plan_reviewのCritical #1(snapshot_check挿入spec不能)→plan §1-4修正、差分レビューのCritical #1(`--limit`回帰)→plan §1-1改訂・T1緩和・AC7新設、Suggestion #1(T2 become非対称)→T2に`become: false`明示、のいずれも「誰が・いつ・何を根拠に」変更したかがfile:line単位で追跡できた。
- 根拠の実在: 各ファイルが引用するfile:line(`roles/proxmox_reachable_nodes/tasks/main.yml`のT1〜T6、`docs/ai/policies/proxmox_patch_policy.md`のSB-094/SB-095、`playbooks/proxmox_patch_weekly_full.yml`のStep 1b等)を現物で確認し、内容の食い違いはなかった。review.md内の一部file:line引用(T1の"51-52"、T2の"64-68")はタスクブロックの厳密な開始行とは数行ずれているが、plan_reviewが既に同種の引用精度の粗さを非blocking Suggestionとして記録済みであり、対象タスク自体は一意に特定できるため新規の指摘とはしない。
- ADR-008: Status「Proposed」はQ1(SB-095)未承認・未commitの現状と整合している(implement.md「未解決事項」3で「Status更新はscope外」と明記済み、黙って落ちている項目ではない)。
- 受入条件の充足: AC1〜AC7すべてに対し、test_result.mdが実測結果(rc、summary文字列、report JSON、PLAY RECAP)を提示しており、根拠不足のACはない。AC5・AC7の両ノード実機確認が今回decoy代替であることも、plan §4・test_result §9で明示済み。
- 未解決の明示: Q1(Policy承認)、Q2(decoy確認結果=機能する)、`ANSIBLE_LOCAL_TEMP`/`REMOTE_TEMP`未設定、broken-sudoケース未検証など、「やらなかったこと」とその理由が各ファイルに明記されている。黙って落ちている項目は見当たらなかった。
- 記録どうしの矛盾(内容面): 指摘1・2以外に、requirement/plan/ADR-008/review/test_resultの間で同一事実について異なる主張をしている箇所はなかった(非ゴール範囲、AC番号、file:line引用は相互に一致)。
- `docs/ai/effort-baseline.md`: 本案件の記帳はない。`docs/ai/effort-baseline.md`の方針(2026-07-29に実績記帳を義務からCoordinator裁量へ変更)により、記帳の欠落単独ではクローズを妨げない(auditor.md「記帳の遅れ...それ単独では『クローズを妨げる指摘』に当たらない」)。

## 3. 判定

**条件付き受入。**

指摘1・2(staged内容が案件の最終状態と食い違う/最終成果物が丸ごとstageされていない)を反映すればクローズしてよい。反映方法は機械的である — `git add`で現在のworking tree内容(訂正済みrequirement、Approve済みreview、test_result.md)をstageし直すこと。この操作自体に技術的判断は不要であり、再監査を前提としない。

指摘3は非blocking。commit/push以降の工程でCoordinatorが`docs/ai/status.md`へ観測待ちを追加するかを判断すればよい。

**Coordinatorへの申し送り**: 本案件はTier 3の「工程上の待ち」(計画§2)として、SB-095のPolicy改訂承認と、その後のcommit/pushをYoshinobuに仰ぐ段階にある。指摘1・2の`git add`はその前に行うこと — 現状のまま`git diff --cached`をYoshinobuの承認材料として提示すると、Approve済みの差分レビューやTesterのPASS結果が見えず、判断を誤らせる。

## 4. クローズ判断(Coordinator、2026-07-30)

**条件付き受入を受けてクローズする。** 指摘1・2は監査直後に反映済み(`git add` により訂正済みrequirement / Approve済みreview / test_result / 本監査ファイルをstage。stagedは18ファイル)。指摘3も同時に反映し、`docs/ai/status.md` のWatchへ2行(本番Semaphoreが緑になることの確認、両ノード到達可能時の回帰)、Nextへ3行(`proxmox_exec_node`のT1が`--limit`を拒否する件、P1-1のdryrun寄せ替え、P1-2のSB-020記載漏れ)を追加した。**無条件受入の取得を目的とした再監査は行わない**(`docs/ai/roles/coordinator.md`「Auditorの受入と、クローズの判断」)。

残る工程は工程上の待ちだけである — **SB-095のPolicy改訂承認とcommit / pushはYoshinobu**、その後のquoryでの `git pull --ff-only` と本番Semaphoreの緑化確認はWatchが持つ。

指摘1が指していた状態(stagedが案件の最終状態より古い)は、**subagentが成果物を書いた後にCoordinatorがstageし直さなければ必ず起こる**。今回は差し戻しでreviewとrequirementが後から変わったため差が開いた。監査が最終成果物(test_result)のstage漏れまで捕まえた点は、この工程順(Auditorをcommit前に置く)が機能した実例である。
