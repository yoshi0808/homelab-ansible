# plan: Proxmox read-only点検3本の単一ノード対応

作成: 2026-07-30 / Coordinator
requirement: `docs/ai/reviews/proxmox_readonly_check_single_node/2026-07-30_001_requirement.md`
Tier 3。この計画はReviewerの計画査読(層1・層2)を経てからImplementerへ渡す。

## 0. 方針

`proxmox_patch_dryrun`で2026-07-26に確立した「`ignore_unreachable` + 到達判定 + 全滅時fail + playからの除外」の1組を、**4本目のコピーにせず共通roleへ括り出す**。到達性の判定方法はADR-006の`roles/proxmox_exec_node`に倣い、fact gatheringの結果ではなく**明示的な`ping` probe**とする(fact cachingが有効な実行環境でも誤判定しないため)。

`proxmox_exec_node`(到達可能な候補から**1台を選ぶ**)と本role(到達不能な候補を**playから落として残り全部で続ける**)は、probeまでは同じだが出力が違う。両者を1つのroleへ統合しない理由はADR-008に記録する。

**単位はU1〜U4で、U1〜U3は同一のImplementer 1セッションで実施する。** U1で新設するroleの契約を、U2・U3が同じセッション内で消費するため。**未決定の設計判断はU1=0件、U2=0件、U3=0件、U4=1件(Q1のPolicy置き場、Yoshinobu承認事項)。** U1には条件分岐が1つある(下記Q2)。分岐先はここで確定済みで、Implementerに発明させない。

## 1. 設計(逐語仕様)

### 1-1. 新role `roles/proxmox_reachable_nodes`

`tasks/main.yml`と`defaults/main.yml`のみ。handlers / templates / filesは持たない。

**呼び出し規約**: 候補ノード全体を`hosts:`に持つPlayから、**`roles:`リストの先頭**で呼ぶ。呼び出し側Playには**play-levelの`ignore_unreachable: true`が必須**(roleはplay-levelキーワードを設定できないため、この前提はT1でassertできない — 設定漏れは「rcが4のまま」という形で現れ、AC1〜AC3が検出する)。

| 変数 | 既定 | 意味 |
|---|---|---|
| `prn_candidate_group` | `proxmox` | 候補ノードのinventory group名。呼び出し側Playの`hosts:`と一致させる |
| `prn_caller` | (必須) | 失敗メッセージの先頭に付ける呼び出し元識別子 |

**出力**

| 出力 | 内容 |
|---|---|
| per-host fact `prn_reachable` (bool) | 全候補ノードに立つ。**到達不能ノードにも立つ**(`set_fact`はcontroller側で完結するため、`ignore_unreachable`でplayに残ったホストにも実行される。2026-07-26実機確認: `docs/ai/reviews/proxmox_patch_dryrun/2026-07-26_005_test_result.md` §14-4) |
| fact `prn_reachable_nodes` (list) | 到達できたノード名。inventory定義順 |
| fact `prn_unreachable_nodes` (list) | 到達できなかったノード名。inventory定義順。**呼び出し側roleのsummaryはこれを読む** |
| playからの除外 | 到達不能ノードは`meta: end_host`でplayから落ちる。以降のroleのタスクは実行されない |

**タスク構成**(この順序を変えない)

| # | タスク | 要点 |
|---|---|---|
| T1 | 入力assert | `prn_caller`が非空、**playのhostsが候補groupの部分集合であること**(`ansible_play_hosts_all \| difference(groups[prn_candidate_group]) \| length == 0` かつ `ansible_play_hosts_all \| length > 0`)。`run_once: true` + `delegate_to: localhost` + **`become: false`** + `quiet: true`。**厳密一致にしない** — 下記「T1を部分集合にする理由」 |
| T2 | `ansible.builtin.ping` | `register: prn_ping` + `ignore_unreachable: true` + `ignore_errors: true` + **`become: false`**。到達性のprobeであり、rootを要さない。下記「T2を`become: false`にする理由」 |
| T3 | `set_fact: prn_reachable` | `{{ not (prn_ping.unreachable \| default(false) \| bool) and not (prn_ping is failed) }}`。`roles/proxmox_exec_node/tasks/main.yml:55-59`と同一式 |
| T4 | `set_fact: prn_reachable_nodes` / `prn_unreachable_nodes` | 下記の式。**全ホスト(到達不能ノードを含む)で実行する** — U3のweekly fullゲートが到達不能ノード側のhostvarsも読めるようにするため |
| T5 | 全滅時のfail | `run_once: true` + `delegate_to: localhost` + `become: false`。`when:` は到達可能ノードが0件。msgに`prn_caller`と**候補ノードごとの到達性**を列挙する。**T6より前に置く** — T6が到達不能ノードを落とした後では、両ノード到達不能時に`run_once`を担うホストが残らずガードがdead codeになる(`playbooks/proxmox_patch_dryrun.yml:59-65`に同じ理由の記録がある) |
| T6 | `ansible.builtin.meta: end_host` | `when: not prn_reachable` |

**T1・T5に`become: false`を明示する理由**(計画査読 Suggestion 1への回答): 転用元の`roles/proxmox_exec_node`の同種タスクは`delegate_to: localhost`だけで`become`を持たないが、あちらの呼び出し側Playはすべて`become: false`である。本roleの呼び出し側3本は**play-levelが`become: true`**であり、そのままではlocalhostへの委譲でもsudoを要求する。既存の3 roleがlocalhostへ`delegate_to`するタスクで一貫して`become: false`を併記しているのと同じ理由である(例: `roles/proxmox_snapshot_check/tasks/main.yml:102-104`・`:109-110`)。この非対称性は意図的なものであり、`proxmox_exec_node`側を揃える変更は行わない。

**T1を部分集合にする理由**(差分レビュー Critical #1、2026-07-30): 厳密一致(`==`)にすると `ansible-playbook playbooks/proxmox_healthcheck.yml --limit pve2` が必ずassertで落ちる。**`--limit`による単一node healthcheckはSB-021が明示的に許可している既存の運用能力**(`docs/ai/policies/proxmox_patch_policy.md:93`)であり、本案件以前は動いていた。したがってroleの呼び出し規約は「playのhostsが候補groupの部分集合であること」であり、`--limit`で縮まった集合もその範囲に収まる。**部分集合に緩めても、roleが守りたい前提(候補group外のホストがplayに混じっていないこと、playが空でないこと)は保たれる。** `--limit`で1台だけを指定した場合、そのノードが到達不能ならT5の全滅判定が発火して明確に停止する(サイレント成功にならない)。

なお`roles/proxmox_exec_node`のT1も同じ厳密一致を持つが、**そちらは本案件の非ゴールであり触れない。** 同roleの呼び出し側5本で`--limit`が許可されているかはPolicyを見ないと言えず、独立した確認を要する。申し送りとして`docs/ai/status.md`へ残す。

**T2を`become: false`にする理由**(差分レビュー Suggestion 1、2026-07-30): 呼び出し側Playは`become: true`のため、指定しないとprobeがsudo経由になる。その場合**sudoの失敗が「到達不能」へ畳み込まれ**、健全なホストが点検対象から外れて`Unchecked=`に並ぶ。`ping`はrootを要さないため`become: false`とし、probeを純粋な接続性判定に保つ。SSHは通るがsudoが壊れているノードは、点検role本体のタスクで失敗する — **それは「未点検」ではなく本物の障害であり、そちらの形で出るのが正しい。**

T4の式(`ansible_play_hosts_all`はinventory定義順を保つ):

```jinja
prn_reachable_nodes: >-
  {{ ansible_play_hosts_all
     | map('extract', hostvars)
     | selectattr('prn_reachable', 'equalto', true)
     | map(attribute='inventory_hostname')
     | list }}
prn_unreachable_nodes: >-
  {{ ansible_play_hosts_all | difference(<上と同じ式の結果>) }}
```

`selectattr(..., 'equalto', true)`は`roles/proxmox_exec_node/tasks/main.yml:77-79`・`:88-93`で実地PASSしている形をそのまま使う(`set_fact`が`'True'`文字列でなくboolになることに依存する箇所であり、実証済みの形から離れない)。同じ式を2回書くのを避けるため`vars:`へ括り出してよい。

### 1-2. Q2 の分岐(`meta: end_host`がrole内で機能するか)

repo内の`end_host`の前例2つ(`playbooks/ubuntu_nightly.yml:82`・`:367`、`playbooks/proxmox_patch_dryrun.yml:78`)はいずれもplaybook直書きで、**role内の前例が無い**。`roles:`セクションのroleはplayへ静的に展開されるため機能する見込みだが、実装の**最初に**decoyで確かめる。

- **機能した場合**: 本計画どおり進める。
- **機能しなかった場合**: roleへ寄せる形を捨て、3本のplaybookの`pre_tasks:`へT2〜T6相当を直接書く(3箇所の重複を受け入れる)fallbackへ切り替える。**この切り替えはCoordinatorへ差し戻してから行う** — 重複3箇所を作る判断はImplementerの裁量に置かない。

decoyの作り方は`docs/ai/reviews/proxmox_patch_dryrun/`および`docs/ai/reviews/proxmox_exec_node_selection/2026-07-29_007_test_result_step1.md`の既存手法(closed portのホストをunreachable、`ansible_connection: local`のホストをreachableとして扱うdecoy inventory)に倣う。**実ホストのpve1 / pve2をdecoyの対象にしない。**

### 1-3. 3本のplaybookへの適用(U2)

`playbooks/proxmox_healthcheck.yml`・`playbooks/proxmox_hw_check.yml`・`playbooks/proxmox_snapshot_check.yml`の3本を、次の形にする(例は snapshot check。`prn_caller`と既存roleの名前だけが違う):

```yaml
- name: Proxmox snapshot check
  hosts: proxmox
  gather_facts: true
  become: true
  ignore_unreachable: true          # 追加

  roles:
    - role: proxmox_reachable_nodes  # 追加

        prn_caller: proxmox_snapshot_check
    - proxmox_snapshot_check          # 既存(変更しない)
```

`tester-gate`コメント行は分類が変わらないため文言を変えない。**`ignore_unreachable`とguard roleを1組で入れる理由を各playbookの冒頭コメントへ1〜2行で書き、詳細はADR-008を参照させる**(`proxmox_patch_dryrun.yml`のような長い経緯コメントは複製しない)。

### 1-4. summary 1行への未点検ノードの明示(U2)

3 roleとも、既存のsummary文字列に**到達不能ノードがあるときだけ** `Unchecked=<ノード名,...>` を足す。無いときは表記自体を出さない(AC5の回帰条件)。

| role | 挿入位置 |
|---|---|
| `roles/proxmox_healthcheck/tasks/main.yml` | `:157`(`Result=`のappend)の直後に条件付きappend |
| `roles/proxmox_hw_check/tasks/main.yml` | `:119`(同)の直後に条件付きappend |
| `roles/proxmox_snapshot_check/tasks/main.yml` | `:124`の`{% endfor -%}`と`:125`のsummary文字列行(下記) |

healthcheck / hw_checkの挿入形(`summary.parts`は`join(' | ')`される):

```jinja
{% if (prn_unreachable_nodes | default([])) | length > 0 -%}
{% set _ = summary.parts.append('Unchecked=' ~ (prn_unreachable_nodes | join(','))) -%}
{% endif -%}
```

**snapshot_checkは構造が違う**(`summary.parts`のようなリストを持たず、`:125`の1行で文字列を組み立てている)。上のappend形は使えないため、次の形にする — `:124`の`{% endfor -%}`の直後に`{% set %}`を1行足し、`:125`を差し替える:

```jinja
{% endfor -%}
{% set _unchecked = prn_unreachable_nodes | default([]) -%}
SUMMARY proxmox_snapshot_check | Result={{ ns.result }}{% if _unchecked | length > 0 %} | Unchecked={{ _unchecked | join(',') }}{% endif %} | {{ ns.lines | join(' | ') }} | Threshold={{ proxmox_snapshot_check_threshold_seconds | int // 86400 }}d
```

`{% if %}`をSUMMARY行の内側にインラインで置く(トリムマーカー`-`は付けない)。到達不能ノードが無いときは`| Unchecked=`ごと出力されず、既存の1行と完全に一致する(AC5)。

**`| default([])`は必須である。** `roles/proxmox_healthcheck`は`playbooks/proxmox_patch_dryrun.yml:84-86`から`include_role`でも呼ばれており、その経路には`prn_unreachable_nodes`が存在しない(dryrunは自前の`_node_reachable`機構を持つ)。`default([])`により**dryrun経路の出力は変わらない** — これはP1-1(dryrunの寄せ替え)を今回やらないことの帰結であり、意図した挙動である。

### 1-5. weekly full の明示ゲート(U3)

`playbooks/proxmox_patch_weekly_full.yml:115-125`のStep 1b(`hosts: proxmox` / `any_errors_fatal: true`)の**既存タスクより前**へ、次の1タスクを足す。

```yaml
    - name: Fail if any candidate node was unreachable during healthcheck
      ansible.builtin.fail:
        msg: >-
          weekly full patch requires every node in group 'proxmox' to be
          reachable, but {{ _wf_unreachable | join(', ') }} did not answer
          during the healthcheck play. Apply-side drift avoidance
          (SB-027 / SB-028 / SB-032) requires the full fixed pair.
      vars:
        _wf_unreachable: >-
          {{ ansible_play_hosts_all
             | map('extract', hostvars)
             | selectattr('prn_reachable', 'defined')
             | selectattr('prn_reachable', 'equalto', false)
             | map(attribute='inventory_hostname') | list }}
      run_once: true
      delegate_to: localhost
      become: false
      when: _wf_unreachable | length > 0
```

**なぜ必要か**: `proxmox_healthcheck.yml`が片肺で完走するようになると、weekly full(`:112`で`import_playbook`)のStep 1bには到達不能ノードが**playに残ったまま**入ってくる(`ignore_unreachable`はホストをunreachable扱いにしないため、後続playからも除外されない)。そのノードには`proxmox_report`が無いので、既存タスクの`when: proxmox_report.result.status != 'OK'`が未定義変数エラーになる。**停止すること自体は正しい**(apply側は両ノードを要求する)が、理由が読めない形で止まる。この1タスクは停止条件を変えず、**メッセージを読めるようにするだけ**である。

`:46`の`hosts: "{{ groups['proxmox'][0] }}"`(ADR-006の決め打ち除去の残り、非ゴール)には触れない。pve1停止中はそのpreflightで先に止まるため、U3のゲートが実ホストで発火するのはpve2側が落ちた場合に限られる — だからAC6はdecoyで確認する。

### 1-6. Policy(U4)

`docs/ai/policies/proxmox_patch_policy.md` §3.2 の SB-094 の直後へ SB-095 を新設する(採番: 現在の最大がSB-094)。**文面はこのとおり入れる:**

> <!-- SB-095 -->
> read-only点検(`proxmox_healthcheck.yml`、`proxmox_hw_check.yml`)は、到達可能なnodeが1node以上あれば実行し、到達不能なnodeを対象から除外して継続する。除外したnodeはSemaphore summaryへ明示し、点検できた範囲を読み取れる状態にする。全nodeが到達不能な場合は明確なエラーで停止する(空reportやサイレント成功にしない)。到達不能による除外は点検結果の`OK`を保証しない — 除外されたnodeの状態は未確認である。applyの前提(SB-027、SB-028、SB-032が要求する両node揃った状態)は本項で緩めない。

**Yoshinobu承認が必要**(Policy改訂)。承認前でも差分として作成してよいが、commitはYoshinobuが行う。

`proxmox_snapshot_check`は本Policyの対象領域(patch)外であり、Policyの置き場が無い。同一挙動の根拠はADR-008と当該playbookの冒頭コメントに置く(新規Policyファイルは作らない)。この判断もQ1としてYoshinobuへ上げる。
