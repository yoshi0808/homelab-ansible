## 層1(数えるだけで判定できるもの)

計画の自己申告: U1=0 / U2=0 / U3=0 / U4=1(Q1、Yoshinobu承認事項)。

数え直した結果: **U2は実質1件の未確定/誤り箇所を含み、申告どおりの0ではない**(下記Critical Issues #1)。理由: `roles/proxmox_snapshot_check/tasks/main.yml`のsummary生成は、healthcheck/hw_checkが使う`summary.parts.append(...)`形のリスト構造を持たず、`SUMMARY ... | Result={{ ns.result }} | ...`という単一行Jinja式である。計画§1-4が示す挿入snippet(`summary.parts.append('Unchecked=' ~ ...)`)はこのファイルには適用できず、代替のsnippetも与えられていない。file:line引用(`:122`)も実際の`Result=`行(`:125`)と一致しない。

この1件は「1単位に2件以上」の閾値(層1基準#1)には届かないため、この基準単体では機械的な差し戻し対象にならない。しかし層2(技術的前提の反証)としては、AC3(P0-3のsnapshot_check側)を実装できる形の仕様がU2に欠落しているという実質的な欠陥であり、下記のとおりblockingとして扱う。

U1(§1-1・§1-2)、U3(§1-5)、U4(§1-6)は申告どおり0/0/1で相違なし。

**独立に検証した因果モデル**(計画に明記の無い推論を自分で埋めて確認したもの):

- `set_fact`はcontroller側で完結するため、guard role内で`prn_reachable`/`prn_unreachable_nodes`をpve1(到達不能ノード)にも設定でき、かつそのhostvarはplay境界を越えて(Step 1a→Step 1bへ)持続する。これはU3のゲート実装が依拠する前提であり、正しい。
- `roles/proxmox_backup_restore_verify.yml`・`recovery_vm_reboot.yml`・`recovery_service_restart.yml`・`unifi_backup_fetch.yml`・`recovery_ha_failover.yml`はいずれも`hosts: proxmox`の選定playを持つが、`gather_facts: false`かつ`proxmox_exec_node`のping probeタスク(task-levelの`ignore_unreachable`)のみが接続を伴うため、play-levelの`ignore_unreachable`を要さない。2026-07-29の実機テスト記録(`docs/ai/reviews/proxmox_exec_node_selection/2026-07-29_007_test_result_step1.md`)でrc=0を確認済みであり、この défaultクラスの対象から漏れているのではなく、構造的に対象外であることを確認した。requirement/ADRはこれらを名指しで非ゴールに挙げていないが、範囲漏れではない。

### Critical Issues(blocking)

1. **`roles/proxmox_snapshot_check/tasks/main.yml`のsummary挿入spec(plan §1-4、U2)が実装不能な形で書かれている。**
   - file:line引用の誤り: plan は`:122`を挿入位置とするが、実際の`:122`は`{% endif -%}`(WARNING/CRITICAL分岐の終端)であり、`Result={{ ns.result }}`は`:125`にある。
   - 構造の誤り: plan §1-4が与える挿入snippet(`{% set _ = summary.parts.append('Unchecked=' ~ ...) %}`)はhealthcheck/hw_checkの`summary.parts`(リスト+`join(' | ')`)構造専用であり、snapshot_checkには存在しない。snapshot_checkの実際の出力式は`SUMMARY proxmox_snapshot_check | Result={{ ns.result }} | {{ ns.lines | join(' | ') }} | Threshold=...d`という単一のJinja式(`:125`)であり、"append"できるリストが無い。
   - 影響: このままImplementerに渡すと、AC3(「summaryに未点検ノードpve1」)を満たす具体的な変更方法がsnapshot_checkについてだけ規定されておらず、Implementerが独自に形式を発明することになる(要求分解の趣旨=「Implementerに発明させない」に反する)。
   - 必要な修正: `:125`の単一行式を、`{% if (prn_unreachable_nodes | default([])) | length > 0 %}`で`| Unchecked=...`相当を条件付き連結する形に書き換えるsnippetをCoordinatorが用意し直す(healthcheck/hw_checki同様`| default([])`必須、AC5回帰条件=表記なしも維持すること)。

### Suggestions(non-blocking)

1. 新role T1(`assert`)・T5(`fail`)は明示的に`become: false`を付与しているが、転用元の`roles/proxmox_exec_node`の同種タスク(`tasks/main.yml:27-48`、`:61-79`)には`become: false`が無い(`delegate_to: localhost`のみ)。転用元は実機PASS済みのため機能上の問題ではないが、片方だけ明示している非対称性がある。挙動差は無い認識で良いか、Implementerが実装時に一言触れておくと後続の混乱を防げる。
2. `roles/proxmox_exec_node/tasks/main.yml:77-79`・`:88-93`の引用は該当式を含む範囲として妥当だが、`selectattr(...)`の行そのものはそれぞれ`:78`・`:92`に位置し、引用範囲がやや広め(前後1〜2行を含む)。実害はないが、次にfile:line引用を使う案件のために「範囲引用は式の開始行だけでなく該当行そのものを含むか」を確認する習慣を残しておきたい。

### What Looks Good

- 4本目の欠陥再発を防ぐという動機(ADR-008 Decision (a))が、実際にrepo内で確認できる「同一機構が2026-07-26時点で1箇所(dryrun)にしか直っておらず、3本(healthcheck/hw_check/snapshot_check)に同型の欠陥が残っていた」という事実(requirement §1の実測表)と整合している。
- `ignore_unreachable`単体では不十分で3タスク1組が必要、という計画の中核前提は、`proxmox_patch_dryrun.yml`のヘッダコメントおよび2026-07-26の実機テスト記録によって裏付けられている。
- T5(全滅時fail)をT6(`end_host`)より前に置く理由(`run_once`の担い手が消える)は、dryrunの`:59-65`と同一の論理であり、独自の思いつきではなく実証済みパターンの転用である。
- `prn_unreachable_nodes | default([])`によるdryrun経路(`include_role`)への非波及の説明は、dryrunが自前の`_node_reachable`機構を持ち`prn_unreachable_nodes`を一切設定しないという事実と整合しており、正しい。
- weekly full Step 1bの「未定義変数エラー→読めるメッセージ」という変更理由は、`fail`/`assert`がaction-onlyでSSH接続を要さないという一般的なAnsible挙動に照らして技術的に成立する(計画には明記されていない前提だが、独立に検証して破綻していないことを確認した)。
- 対象範囲の線引き(read-only 3本を含め、変更系3本・`proxmox_patch_dryrun.yml`のinline実装・`proxmox_exec_node`ベースの5 playbook・`time_sync_check`を除外)は、除外側それぞれについて構造的な根拠(接続要否、既存の別機構での対応済み)があり、漏れは確認できなかった。
- 受入条件(AC1〜AC6)はすべて終了コードまで明記しており(`skills/requirements-analysis/SKILL.md`の要求を充足)、AC4・AC6のdecoy割り当ても、pve2停止が許可範囲外という制約と整合した妥当な判断である。

### Verdict

**Request Changes(差し戻し)。**

理由: Critical Issues #1は、U2(3 playbookへの適用)の一部であるP0-3(AC3=snapshot_checkのsummary表記)を実装可能な形で規定できていない、実質的な仕様欠落である。差し戻し範囲は狭く、Coordinatorが`roles/proxmox_snapshot_check/tasks/main.yml:125`向けの正しいsnippetとfile:lineを§1-4へ補えば、U1・U3・U4を含む計画全体の再作成は不要である。U1・U3・U4および層2で検証したその他の技術的前提(`ignore_unreachable`+3タスクの因果、`meta: end_host`の前例状況、weekly fullゲートの未定義変数エラー機序、対象範囲の線引き)には、実装を止めるべき誤りは見つからなかった。
