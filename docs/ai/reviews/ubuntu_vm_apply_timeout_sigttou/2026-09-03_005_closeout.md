# closeout: `timeout` の SIGTTOU 停止

日付: 2026-09-03
対象: requirement `2026-09-03_001_requirement.md`
状態: **クローズ**

## 1. 結論

**apply の apt 実行を `setsid -w` の内側へ移し、`timeout` は既定モードのまま使う形で解いた**(commit `41a55ae`)。制御端末を持たせないので job control signal そのものが発生せず、`timeout` は既定モードのままなのでプロセスグループごと閉じられる。

実装記録 `_003` が最後に残していた未確認は「**本番の apt で成立することは未確認。次の apply が初回である**」の1点だった。**これは本番3台で埋まった。**

## 4. 本番3台の完走が証明していないこと

**「修正が無ければ止まっていた」ことの証明にはならない。** quory / authy / ansy の apt が実際に端末へ触ったかどうかは測っていない。触らなければ修正の有無にかかわらず完走する。**機構が効くことの根拠は sandbox の実測(`_003` §3.1〜3.2)であって、本番の完走ではない。** 本番が示したのは「修正を入れて後退が無かった」ことである。

## 5. 引き継ぐ残存項目

- **S1(レビューの non-blocking 指摘): 回帰テストはプロセス木側だけを見ている。** `setsid -w` を削除して素の `timeout` に戻しても localhost では3ケースとも通る。**直接原因の再導入を機械では検出できない。** 擬似TTYの回帰ケースか、端末分離 wrapper の存在を見る静的 precondition が要る
- **`setsid` で apt が制御端末を持たなくなったことによる進捗表示の変化は未測定。** ansy の term.log は `Log ended` まで完全で、trigger 処理と initramfs 生成の行も通常どおり出ている。**ただし見え方そのものは比較していない** — 比較対象になる「`setsid` 無しで本番 apt を通した term.log」は #938 の途中で止まったものしか無い
- **`--force-confold` は手動管理の設定をメジャー版更新でも黙って保持する。** monnie の unpoller は 4.x → 5.x をまたいで旧設定のまま動いたが、**観測であって保証ではない**。`MAJOR_UPGRADE_DETECTED` は codename drift / 合計100超 / remove 30超の3信号だけで、個々のパッケージのメジャー版差は見ていない(守備範囲の違いであり欠陥ではない)
- **Operator は apt のログを読めない**(`root:adm 0640`、`ann` では拒否)。本番で apt が止まったとき、運用側から中身を確かめる手段が無い。**#938 のときに実際に効いた制約である**
- **`NEEDRESTART_MODE=l` は再起動しない。** authy は `libpam` 系が入ったが `freeradius` は旧ライブラリのまま動いている(再起動不要と出ており、急がない)
- **同じ形(`become: true` + 長時間コマンド + `timeout`)が他にあるか。** requirement §6 の時点で repo 内の `timeout` 使用は当該1箇所だけと確認済み。**組み合わせが将来増えたときに再発しうる**

## 5.1 requirement §6 の未決のうち、扱わなかったもの(監査の指摘を受けて明記)

**「上限値(3600秒)を見直すか」は見直していない。** ACのいずれも見直しを求めておらず、本番の実測(apt 単体で ansy 43秒、ジョブ全体で 88〜116秒)は上限に対して桁が2つ違う。**判断材料が無いので触らない。** 上限が実際に効くこと自体は AC2 で確かめてある。
