## 2. なぜ `--foreground` では駄目か

**2つの性質を同時に満たす必要がある。**

| 性質 | 素の `timeout` | `--foreground` | `setsid -w` + 素の `timeout` |
|---|---|---|---|
| TTY の job control で停止しない | **× 停止する** | ○ | ○(制御端末を持たないため signal 自体が発生しない) |
| 上限でプロセス木ごと閉じ、Ansible の task が期限内に返る | ○ | **× 子孫が残り、`run_command()` が pipe を読み続ける** | ○ |

`--foreground` は新しいプロセスグループを作らないので停止は消えるが、**signal が COMMAND だけに送られる**(man の記載: "children of COMMAND will not be timed out")。apt-get を閉じても dpkg が残り、それが出力する限り Ansible の module は返らない。**上限が実効しない。**

## 3. 検証 — すべて実際の `ansible.builtin.command` 経由で測った

**3度目なので、直す前に「壊れることを再現できる場所」を先に作った。** 本番の apt には一切触れていない。

### 3.1 前提と、TTY 経路の再現(sandbox)

`become: true` で sandbox へ流し、`tty=/dev/pts/1`、`STAT S+` を実測。**monnie と同じ形**である。

`timeout 20 sh -c 'stty sane; echo done'` で再現:

```
3527590 3527590 T    timeout 20 sh -c stty sane; echo done
3527591 3527590 T    sh -c stty sane; echo done
3527592 3527590 T    stty sane
```

**3プロセスとも `T`、同一 PGID。25秒後も playbook は走ったままで、20秒の上限は発火しなかった。** apt を1行も使わずに、本番と同じ無期限停止が起きる。

### 3.2 方式の比較(sandbox、`become: true`)

| # | 形 | 結果 |
|---|---|---|
| a | `setsid -w timeout --kill-after=2 3` + 出力し続ける子 | **rc=124 / 3.007秒** |
| b | 同上 + 孫が `sleep 30` | **rc=124 / 3.107秒** |
| c | 同上 + 子が TERM を無視 | rc=137 / 6.008秒 |
| d | 同上 + 端末に触る(`stty sane`) | **rc=0 / 0.104秒。停止しない** |
| **e** | **負のコントロール `--foreground`** + 出力し続ける子 | **rc=124 だが 6.074秒 — 3秒の上限を超過(F1 の再現)** |

**c の約1秒超過には理由がある** — `trap "" TERM` が設定する SIG_IGN は **exec した子へ継承される**ため、`sleep` も TERM を無視して KILL まで生き残る。予算は 3+2=5 秒で、観測は 6.0 秒である。

### 3.3 回帰テスト

`scripts/tests/apply_timeout/run-tests.sh` — **pass=5 fail=0**。

**wrapper は `apply.yml` の `Run apt full-upgrade` から argv を読み取り、`apt-get` の手前までを試験対象にする。** ここへ値を写していないので、`apply.yml` だけが変わったときにテストが素通りしない。

**抽出は fail-closed である**(独立レビュー F2)。番兵 `apt-get` が見つからないまま argv を読み切ったら、**何も実行せずに落ちる**。見つからないときに argv 全体を wrapper として採用すると、`-y full-upgrade` を含む**本番の argv をこのホストで起動しうる**。二重の歯止めとして、取り出した wrapper に `apt` / `upgrade` を含む要素があっても停止する。未解決の Jinja 変数が残っていた場合も停止する。

| # | 見たもの | 上限 |
|---|---|---|
| 1 | **番兵を絶対パス(`/usr/bin/apt-get`)へ変えたら抽出が停止する** | — |
| 2 | **番兵を別名(`apt-fast`)へ変えたら抽出が停止する** | — |
| 3 | 出力し続ける子がいても上限で閉じる | `LIMIT + 2` = 5秒 |
| 4 | 孫が残っていても上限で閉じる | 同上 |
| 5 | TERM を無視しても `kill-after` で閉じる | `LIMIT + KILL_AFTER + 2` = 7秒 |

**1と2は実行を伴わない** — 抽出関数だけを偽の `apply.yml` に対して呼び、非0で落ちることを見る。`ansible-playbook` は一度も起動しない。

1. `apply.yml` を `--foreground` 版へ戻した偽ツリーで走らせると、**ケース3が 12.14秒 で FAIL する**(子のループを待ち切っている)。**ケース4・5は `--foreground` でも通る** — 判別しているのは「出力し続ける子」の1件で、F1 が指していたのもそこである
2. **fail-closed の歯止め(番兵の発見と apt 語の検査)を外した複製では、ケース1と2だけが FAIL する。** negative test が正しい理由で通っていることの確認である。あわせて `sed` が実際に `apply.yml:130` の `- apt-get` を置換していることも確かめた
