## Code Review: ubuntu_vm_full_upgrade healthcheck scope是正

### Summary

U1・U2・U4・U5(停止側)・U6・AC2・AC4・AC5は差分どおりに満たされている。一方、**`healthcheck.yml`のwarnings生成に含まれる正規表現置換が実際には失敗unit名を出力せず、リテラル文字列`\1`を出力する**ことを実行検証で確認した。この1点により、AC1(「本文に失敗unit名が入る」)とU3の実質(「失敗unit名を隠さない」)の両方が成立していない。AC3も、両方存在するケースでcriticalの通知本文にwarning内容が載らないため未充足。

### What Looks Good

- **U1・U4**: 失敗unitをcriticalsから外しwarningsへ、ディスク使用率90%以上はcriticalsのまま、という切り分けは差分どおり実装されている(healthcheck.yml 79-84行目)。
- **U2**: warningsのみの場合に処理が継続すること（healthcheckを理由にfailしない経路）は、main.yml側の`when: ... criticals | length > 0`のblockとは独立した`when: ... warnings ... length > 0`の通知専用task(fail相当のtaskを伴わない)により構造的に保証されている。
- **U5(停止側)**: criticalsが非空の場合は既存のfail blockが先に実行され、warnings通知task(113行目)へは到達しない。二重通知や到達順序の逆転は確認できなかった(使い捨てplaybookでのロジック再現でも、この分岐自体は問題なし)。
- **U6**: `ubuntu_vm_full_upgrade_generic_health.systemd_failed_units`は`ubuntu_vm_full_upgrade_systemd_failed_raw.stdout_lines | default([])`のままで、生の失敗unit一覧の内容自体は変更していない(78行目、未変更)。per-host reportのJSON(main.yml 234-254行目)にはこの値自体が含まれておらず、この点は今回の変更の影響範囲外。
- **AC2**: ディスク使用率90%以上のcriticals判定はそのまま残っており(healthcheck.yml 79-81行目)、main.ymlのfail block(103-107行目)は未変更。従来どおりaptに触れる前に停止する経路を維持している。
- **AC4**: warnings・criticalsとも空のときは両方のnotify task(critical用・warning用)の`when`条件が満たされずskipされる。「healthcheck起因の通知が1本も出ない」という要求を構造的に満たす。
- **AC5**: `radius_healthcheck` / `monitoring_healthcheck`が返す`radius_criticals` / `monitoring_criticals`はconsolidate task内で参照されるだけで、これらのroleのcheck.yml自体には触れていない。両roleとも`*_warnings`相当を返さない現状のため、authy/monnieの`ubuntu_vm_full_upgrade_healthcheck_warnings`は常に`[]`になる(healthcheck.yml内のコメント93-95行目の記述どおり)。
- **`ubuntu_vm_full_upgrade_healthcheck_warnings`の未定義化リスク**: `Generic healthcheck (ansy/quory)`blockがauthy/monnieでは丸ごとskipされ`ubuntu_vm_full_upgrade_generic_health`自体が未定義になるが、後続の`Consolidate healthcheck warnings`taskは`ubuntu_vm_full_upgrade_generic_health.warnings | default([])`という、未定義変数への属性アクセス→`default`という既存criticalsの節と同型のパターンを使っている。**実行検証**（未定義変数への`.attr | default([])`アクセスを再現するplaybookをlocalhost/connection: localで完走)で、これがエラーにならず`[]`を返すことを確認した。新規に未定義化する経路は見つからなかった。
- **型(文字列化)の懸念**: `>-`で式を分割した`criticals:`と`warnings:`は、それぞれ単独の`{{ ... }}`式であるため、Ansibleのtemplarはこれをネイティブ型(list)として返す。実行検証で`is string`が両方`False`であることを確認し、この分割によって型が文字列化する事故は再現しなかった。
- **`--check`での通知実行**: 新設の"Notify healthcheck warnings without aborting" taskは`check_mode: false`が掛かったblockの内側にあるが、`common_slack/tasks/notify.yml`自体が`ansible_check_mode`を独立した抑止条件として持つ(2026-07-31 R3、`docs/ai/reviews/check_mode_semantics/2026-07-31_001_requirement.md`)ため、`--check`実行時は実送信されずdebug表示に落ちる。これは新規実装ではなく既存の仕組みへ乗った結果であり、コメント(main.yml 70-79行目)の記述も現物と一致している。
- **Policy整合**: `docs/ai/policies/ubuntu_vm_patch_policy.md`に、失敗unitの有無を根拠にfull-upgradeを止めることを義務付ける規範は見当たらない(UV-055〜UV-057、UV-071〜UV-073はhealthcheckのWARNING/CRITICAL判定と通知の要否を定めるのみで、対象は「何をcritical/warningとするか」まで指定していない)。したがって本requirementがU1で行った「失敗unitをcriticalからwarningへ落とす」再分類はPolicyの規定と衝突しない。UV-072/UV-073(WARNINGなら通知/CRITICALなら通知)とも整合している。
- **参照の実在確認**: healthcheck.yml・main.ymlのコメントが参照する`docs/ai/reviews/ubuntu_upgrade_healthcheck_scope/2026-08-01_001_requirement.md`の節番号(U1・U3・U4・U5・§6)、および`docs/ai/reviews/check_mode_semantics/2026-07-31_001_requirement.md`(R3・R5)は、いずれも現物のファイルと節見出しで確認できた。`ansible-playbook playbooks/ubuntu_vm_full_upgrade.yml --syntax-check`もPASSした。

## Coordinatorの判断(2026-08-01)

**Finding #1・#2ともに受け入れて修正した。**

- **#1(`\\1` が後方参照として効かない)**: Coordinatorも独立に実測して確認した(折り畳みスカラ `>-` + `set_fact` で `\\1` → `unit: \1` というリテラル、`\1` → 実際のunit名)。**この式は変更前の `criticals` 側から引き継いだもので、本差分が持ち込んだ欠陥ではない** — したがって従来から、healthcheck起因で停止したときの通知本文は `systemd failed unit: \1` としか出ていなかった。停止条件は「リストが空でないこと」なので停止自体は機能しており、**通知本文だけが無意味な文字列という形で、誰にも気づかれずに残っていた**。指摘は静的読解ではなく実行によって出ている。
- **#2(criticalとwarningの併記)**: critical通知の本文へwarningsを条件付きで追加した。

## 「修正後は別セッションで再レビュー」という推奨を採らなかった理由

Reviewerは自己実装分の独立レビュー原則から再レビューを推奨した。**採らずに、Testerによる修正後の再検証で代替した。** 理由は3つ。

1. 修正内容が**レビューが処方したものそのもの**であり、設計判断の余地が無い(1文字の削除と、指摘どおりの本文追加)。
2. 両方の欠陥は**出力に直接現れる**種類のもので、Testerが実ホストのデータ(ansyの `grub2-common.service`)とfixtureで描画結果を観測すれば、静的レビューより強く確かめられる。**#1を最初に確定させたのも実行であって読解ではない。**
3. 本日中にYoshinobuがこのplaybookを実行する予定があり、工程の重さを変更のリスクに合わせる判断として、ここは実測を優先した。

**この判断はCoordinatorのものであり、Reviewerの推奨を誤りとするものではない。** 再検証でAC1/AC3がPASSしない場合、または修正が他のACを壊していた場合は、この判断が誤っていたことになる。
