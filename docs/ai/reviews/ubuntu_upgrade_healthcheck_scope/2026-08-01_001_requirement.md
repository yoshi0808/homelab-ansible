# requirement: ubuntu_vm_full_upgrade の汎用healthcheckが広すぎる件の是正

日付: 2026-08-01
状態: **確定**(2026-08-01 Yoshinobu指示「ubuntuのplaybookは修正して下さい」)
関連: `docs/ai/policies/ubuntu_vm_patch_policy.md`、`docs/ai/context/operations/ubuntu-vm-patch.md`

## 1. 問題定義

`roles/ubuntu_vm_full_upgrade/tasks/healthcheck.yml` の汎用healthcheck(ansy / quory が対象)は、`systemctl --failed` が返した**失敗unitを1件残らず critical に変える**。`roles/ubuntu_vm_full_upgrade/tasks/main.yml` は criticals が非空なら **aptに触れる前にそのホストを fail させる**。

**結果として、パッチの安全性と無関係な失敗unitが、そのホストのパッチを止める。**

2026-08-01に実際に踏んだ。ansyで `grub2-common.service`(GRUBの起動成功記録。`grub-editenv: error: invalid environment block`)が **2026-07-25から6日間** failed のまま残っており、この状態でupgradeを流すと**ansyはaptに触れる前に中断する**。**翌2026-08-02の月次自動発火でも、同じ理由で止まることになる**(この記述は2026-08-01時点のものであり、その発火はまだ起きていない)。

## 2. ゴール

**パッチの安全性に関係しない失敗unitが、パッチを止めないようにする。** ただしその存在を隠さない。

## 3. 非ゴール

- **失敗unitの検査そのものをやめること。** 情報は残す。
- **無視するunitのallowlistを作ること。** 維持が要り、かつ「登録したものは二度と見えない」形になる。
- **ディスク逼迫の判定を緩めること。** これはaptを実際に壊すので従来どおり止める。
- `radius_healthcheck` / `monitoring_healthcheck` が返す criticals の扱いの変更。**触らない。**
- ansyの `grub2-common.service` そのものの修復。**別の作業**であり、この変更は「壊れていることを報告し続ける」側に倒す。

## 4. 要件

| # | 要件 |
|---|---|
| U1 | `systemctl --failed` が返した失敗unitを **critical から外し、warning として扱う** |
| U2 | warning は**パッチを止めない**。criticals が空なら処理は継続する |
| U3 | warning が1件以上あるとき、**その事実をSlackへ通知する**(隠さない)。通知はホスト単位で、本文に失敗unit名を含む |
| U4 | ディスク使用率90%以上は**従来どおり critical** であり、aptに触れる前に停止する |
| U5 | criticals と warnings が**同時にある**とき、従来どおり停止する(criticalが優先) |
| U6 | 既存の成果物・レポートに含まれる `systemd_failed_units` の内容を変えない |

## 5. 受入条件

### AC1 — 失敗unitだけがある場合、止まらない

- **Given** 対象ホストに失敗unitが1件以上あり、ディスク使用率は90%未満
- **When** `playbooks/ubuntu_vm_full_upgrade.yml` を実行する
- **Then** healthcheckを理由に停止しない。**そのホストの処理が継続する**。`#alerts` にwarningが1本出て、本文に失敗unit名が入る

### AC2 — ディスク逼迫は止める

- **Given** 対象ホストのディスク使用率が90%以上
- **When** 同上
- **Then** 従来どおり `#alerts` にcriticalが出て、**aptに触れる前にそのホストが fail する**

### AC3 — 両方ある場合は止める

- **Given** ディスク90%以上かつ失敗unitあり
- **When** 同上
- **Then** critical として停止する。本文にはcriticalとwarningの両方が判別できる形で載る

### AC4 — 失敗unitが無い場合、通知が増えない

- **Given** 失敗unitが無くディスクも正常
- **When** 同上
- **Then** healthcheck起因の通知は**1本も出ない**(この変更で通知が常時増えることがない)

### AC5 — 他のノード種別に影響しない

- **Given** `authy`(radius)/ `monnie`(monitoring)
- **When** 同上
- **Then** それぞれのroleが返す criticals の扱いが従来と変わらない

## 6. この変更が受け入れる代償

**「失敗unitがある状態でパッチが進む」ことを許す。** 従来はそれを止めていた。引き受ける理由は、**止めていた実績が「無関係な6日前の失敗で月次パッチが止まる」という形でしか現れていない**ことにある。

**本当に必要な事前ゲートは別にある。** パッケージ系が壊れているかを見るなら `dpkg --audit` や dpkg lock の状態を見るべきで、「失敗unitがあるか」は代理指標として粗い。**今回はそこまで作らない**(スコープを広げると今日の実行に間に合わない)。次に同種の検査を足す人はこれを踏まえること。

## 7. タイムライン考慮

**2026-08-01当日にYoshinobuがubuntu upgradeを実行する予定**があり、この修正が入らないとansyがaptに触れる前に中断する。次の月次自動発火は2026-08-02。
