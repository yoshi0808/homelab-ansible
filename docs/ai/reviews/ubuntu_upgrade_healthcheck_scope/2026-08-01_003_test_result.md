## AC別結果

### AC1 — 失敗unitだけがある場合、止まらない: **FAIL(部分)**

- **実測**: ansyで`--check -e dry_run=true -l ansy`を実行。ansyは実際に`grub2-common.service`が failed(観測されている事実どおり)、disk_used_percent=52%。
  - healthcheckを理由に停止しないこと: **確認できた**。`Fail this host`タスクは実行されず(criticals=[])、`Deploy full-upgrade simulation script`以降のapt判定処理まで到達し、Statusが`REVIEW_REQUIRED`として最後まで完走した(PLAY RECAP: `failed=0`)。
  - `#alerts`にwarningが1本出て、本文に失敗unit名が入ること: **NG**。`Notify healthcheck warnings without aborting`は発火したが、本文は
    ```
    Warnings:
    - systemd failed unit: \1
    ```
    であり、実際のunit名(`grub2-common.service ...`)が入っていない。原因を切り分けるため、実測されたraw値(`"grub2-common.service loaded failed failed Record successful boot for GRUB"`)をそのまま使い、`healthcheck.yml`79-84行目の`Build generic healthcheck report`タスクを**逐語再現**したところ同じ`\1`が再現した(`/tmp/.../scratchpad/regex_probe3.yml`)。一方、同じ式を`ansible.builtin.debug`のmsgへ直接書いた場合は正しく展開される(`/tmp/.../scratchpad/regex_probe.yml`、`regex_probe2.yml`)。**`set_fact`経由でネストしたdictへ`{{ ... | regex_replace('^(.*)$', 'systemd failed unit: \\1') }}`を代入する経路でのみ後方参照`\1`が展開されず文字通りの`\1`になる**、という挙動を実行で確認した(原因はAnsibleのtemplar側の挙動差であり、この診断は実測に基づく事実。深追いはスコープ外)。
  - この式(`\\1`)自体は**このdiffで新規に書かれたものではなく、旧`criticals`行から変更なくコピーされた**もの(既存レビュー`2026-08-01_002_review.md` Finding #1と同一指摘)。今回のdiffが`warnings`という新しい到達経路を作ったことで、Slackへ出る本文として初めて可視化された。
