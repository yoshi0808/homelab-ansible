# requirement: `tester_mode` の完全撤廃

日付: 2026-08-02 (JST)
起点: Yoshinobu「playbook, policy関連ドキュメントから `tester_mode` は完全に無くしましょう」(2026-08-02)

## 1. 問題定義

`tester_mode` は2026-07-06〜07に廃止され、ゲート機構は `--check`(`ansible_check_mode`)へ、通知抑止は `skip_notifications` へ分離された(`docs/ai/policies/ansible_test_safety_policy.md` TS-003)。**移行が完了していない。**

同じ変数名が現在4つの異なる意味を持つ。

| 場所 | 現在の意味 |
|---|---|
| Policy TS-003 | 「廃止済み」 |
| 29本のplaybookのassert | 渡されたら停止する(移行ガード。task名が `[migration]`) |
| `roles/common_slack/tasks/notify.yml` | 通知抑止フラグとして**有効** |
| `inventories/homelab/group_vars/all.yml` | 「実変更・外部副作用ゼロを保証する不変条件フラグ」(旧方針の記述) |

この重なりが実際に3つの害を生んでいる。

1. **移行ガードを持たないplaybookへ `-e tester_mode=true` を渡すと、Slack通知だけが黙ったまま本番へ適用される。** `alloy_setup.yml`(monnie)、`grafana_provisioning.yml`(monnie)、`rsyslog_forward_to_monnie.yml`(**保護対象の `authy` を含む**)、`incident_sync.yml` が該当する。通知が消える分、気づく手がかりも消える。
2. **`recovery-probe` の drill が機能していない。** drill はラダー実行時に `-e tester_mode=true` を付けて `recovery_vm_reboot.yml` を呼ぶが、同playbookはその変数で停止するassertを持つ。drill はassertで落ちながら `status: ok` の「drill 完了」通知を出す(`docs/ai/memory/incidents/2026-08-02_recovery-probe-drill-blocked-by-tester-mode-assert.md`)。
3. 規範を読む側が「廃止済み」と「現役」のどちらを信じればよいか決められない。2026-08-02に実際に、Role文書が `tester_mode` の使用を案内していることをレビューが指摘した(`docs/ai/reviews/agent_definition_dedup/2026-08-02_004_review_post_move.md` Suggestion 2)。

## 2. ゴール

**`tester_mode` という識別子を、実行に影響するすべての経路と、現在の状態を述べるすべての規範文書から消す。** 撤廃後は、この変数を渡しても何も起こらない(Ansibleは未使用のextra varを無視する)。

- Testerが実行時に付けるのは `--check` である(TS-023)。
- `--check` を付けずに本適用しつつ通知だけ止めるのは `skip_notifications=true` である(TS-031)。

## 3. 非ゴール

- **`docs/ai/reviews/` 配下の案件記録を書き換えない。** 過去の作業の一次記録であり、当時 `tester_mode` が現役だった事実は正しい。
- **`docs/ai/memory/incidents/` と `docs/ai/memory/lessons/` の本文を書き換えない。** 同じ理由。**ただしIncidentの `状態` / `原因` / `修正内容` / `確認方法` は例外で、修正が確認できた時点で更新する** — `skills/incident-recording/SKILL.md` が「捕捉した時点で起票し、原因判明後に同じファイルを完成させる2段階」と定める生きたフィールドであり、過去の記録として凍結する対象ではない(2026-08-02、Auditorの指摘により追記)。
- **`docs/ai/adr/004-notify-capture-insertion.md` を書き換えない。** ADRは決定時点の記録である。
- **Policyの「変更履歴」節を書き換えない。** 履歴として `tester_mode` の廃止を述べている記述は正しい。
- `--check` / `ansible_check_mode` / `skip_notifications` の意味そのものは変えない。
- **`recovery_push` の drill には一切触れない。** リポジトリには「drill」と呼ばれる仕組みが**2つ**あり、削除するのは前者だけである。

  | drill | 実体 | 本案件 |
  |---|---|---|
  | **probe drill** | `roles/recovery_probe/files/recovery-probe.py`。`state_dir/drill/<target>` を置くとprobeを強制的に障害扱いしラダーを発火させる | **削除する** |
  | **push drill** | `playbooks/recovery_push_drill_setup.yml`、`roles/recovery_push/tasks/drill_setup.yml`。`authy` / `monnie` へ必ず失敗するdummy unitを配備し、OnFailure → push → quory Codex の経路を試す | **触れない** |

  `docs/ai/policies/autonomous_recovery_policy.md` L53、`playbooks/README.md` L71、`skills/ansible-implementation-style/SKILL.md` L73、`roles/recovery_exec/templates/AGENTS.md.j2` L200 の「drill」はすべて後者か英語の慣用表現であり、**変更対象ではない**(2026-08-02にCoordinatorが現物で確認)。
- 29本の移行assertを**この案件では外さない**(下記P1で扱う。外す条件が別途ある)。

## 4. ユーザーストーリー

- Testerとして、playbookのヘッダマーカーを見れば `--check` を付けるべきか判断でき、それ以外のフラグを覚えなくてよい。
- 運用者として、drillを起動したらラダーが実際に検証され、成功/失敗が通知の見出しで区別できる。
- 規範を読む者として、`tester_mode` を検索しても現行の指示としては1件も出てこない。

### AC5の改訂(2026-08-02、Coordinator判断)

当初のAC5は「`tester_mode` は『変更履歴』節にのみ現れる」と書いていたが、**この案件の完了時点では成立しない**。29本の移行assertが残る限り、Policyはそれが何であるかを説明する責任を負うためである。TS-004(`# tester-gate:` マーカーと `tester_mode` を混同しない)は、両者の名前が似ていることによる誤解を防ぐための現行の指示であり、識別子を名指しせずには書けない。

したがってAC5は「**現に使える手段として現れないこと**」へ改める。日付つき経緯と廃止理由の説明はTS-003から除去済みで、残るのは読み手がいま行動するために要る事実だけである。

**R10(29本のassert撤去)を実施したときは、TS-003もあわせて削除できる。** その時点で識別子はリポジトリ内のどこからも消え、Policyが説明すべき対象が無くなる。
| AC5 | **Given** 撤廃後のPolicy **When** `ansible_test_safety_policy.md` を読む **Then** `tester_mode` が**現に使える手段として現れない**。TS-003 / TS-004 の「背景」節が識別子を名指しするのは可(下記) |
| AC6 | **Given** 撤廃後の作業ツリー **When** `scripts/git-pre-commit-check.sh` を通す **Then** `check-tester-gate.sh` を含め全チェックがOKで終わる |

### OQ1の決定(2026-08-02、Yoshinobu)

**probe drill機構を削除する。** `--check` へ移して残す案も検討したが採らなかった。

判断の根拠は、drillが **2026-07-08 から約4週間、壊れたまま気づかれていなかった**ことである。`740f8fe`(2026-07-02)でdrillが入り、`f925905`(2026-07-08、`Replace tester_mode/tester_gate with native ansible_check_mode`)がそれを拒否するassertを入れた。以後drillはassertで落ちるが、**rcによらず `status: ok` の「drill 完了」を送る**ため失敗が表に出ない。つまり現状は「何も検証していないのに成功と報告する仕組み」であり、無いより悪い。

Yoshinobuの判断(2026-08-02): 「**ここまでで随分Playbookは整備されたので、本番で検証する機会も減っている。**」`recovery_probe_setup.yml` は `hosts: dev_nodes:control_nodes`(`ansy` と `quory`)へ配備しており、**ansyから本体まで含めた冪等でない検証は行わない**。

**`pvesh` が関わる本番への検証方法は、別途Coordinatorと相談して決める。** 本案件では扱わない。
