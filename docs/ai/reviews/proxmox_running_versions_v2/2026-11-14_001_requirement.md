# requirement: 「Proxmox Watch: 稼働バージョン」ページを v2 書式にする(パッケージ・再起動待ち・Ubuntuホスト)

作成日: 2026-11-14
起案: Yoshinobu(2026-11-14)。読み手(Proxmox Watch の定期タスク、別の Claude セッション)の要望を Yoshinobu 経由で受け取り、Coordinator が整理した。v1 は `docs/ai/reviews/proxmox_running_versions/2026-10-16_001_requirement.md`。

## 1. 問題定義

v1 のページは kernel・pve-manager・pve-qemu-kvm の版しか持たない。そのため:

- 2026-10-30〜11-10、PSA 11件(libpve-common-perl・pve-container・qemu-server・pve-cluster・apt 等が修正版)が、読み手から見て毎日「比較不可(要確認)」のまま残った。閉じるには開発側が `pkg-list` で突き合わせる必要があった。
- 新しい PSA では、事前に予想できないパッケージ名が出る(読み手の報告: 今週だけで libpve-network-api-perl、libpve-rs-perl、librust-proxmox-oci-dev、libpve-http-server-perl)。
- 版が上がっても、古いライブラリを掴んだまま動くサービスが残る。2026-11-14 の週次パッチ後、pve1/pve2 の pmxcfs・pveproxy・sshd 等が更新前の zlib のまま動いていた(`stale-libs` で観測、`docs/ai/reviews/dispatch_host_state_vocabulary/`)。ページはこれを表現できない。
- 読み手は「apply 後だから入った可能性が高い」としか書けない(直近 apply で上がったパッケージが無い)。
- quory などの Ubuntu ホストの版が無い(CVE-2026-109518 の apt、CVE-2026-98432 の Ubuntu カーネル)。
- 書式上の読みにくさ: 日時書式の不統一(`last_apply_at: 20261114T061533`)、`reboot_done: false` が「不要」と「失敗」の両方に読める、`note:` に推測が入っている、リポジトリ名が無い、キー名の版管理が無い、fetch が途中で切れたかを判定できない。

## 2. ゴール

読み手が、Proxmox Watch のエントリごとに「修正版が入っているか」「入っているが再起動待ちか」「修正版が出ているのに入っていないか」「そのホストに当たるか」を、ページだけから判定できるようにする。

## 3. 非ゴール

- 版の比較・該当判定(読み手の仕事。v1 と同じ)。
- Proxmox Watch DB の行の作成・更新(v1 と同じ)。
- 週次パッチ(`proxmox_patch_weekly_full.yml` と import 先、`roles/proxmox_patch_apply_node`)の変更。再起動待ちを週次パッチのリブート判定へ入れる話は別案件として Yoshinobu が後で検討する。
- ansy を対象に入れること(開発機。Yoshinobu 判断 2026-11-14)。
- 版ごとのカーネル実体パッケージ(`proxmox-kernel-<ABI>-pve` / `-signed`)を一覧に載せること(Yoshinobu 判断 2026-11-14。版は `kernel_running` / `kernel_installed` で足りる)。
- needrestart の利用・導入(pve には未導入。全ホストで判定基準を揃える)。
- 読み手のプロンプトの変更(Yoshinobu が読み手側で行う。v1/v2 両対応を先に入れる)。
- スケジュール(毎日 07:00)の変更。
- 履歴の保持(v1 と同じく毎回上書き)。

## 4. ユーザーストーリー

- 読み手として、PSA の修正版パッケージ名がページの一覧にあれば、インストール版・候補版と比べて「対応済 / 未導入 / 未公開」を判定したい。名前が一覧に無ければ「Proxmox 由来のパッケージは全部載っているので、未導入」と判定できる。
- 読み手として、該当ライブラリを掴んだまま動くプロセスと unit を見て、再起動待ちの重み(外部公開の pveproxy か内部プロセスか)を判断したい。
- 読み手として、ノードの `role` を見て、PVE のパッケージの脆弱性を quory に当てないようにしたい。
- Yoshinobu として、ページを開けば直近 apply で何が上がり、何が再起動待ちかが分かる。

## 5. 要件

### P0

- **R1 対象ホスト**: v1 の `proxmox` グループ(pve1 / pve2)に加え、quory・authy・monnie。ホストの状態を変えない(読み取りのみ。root 権限での読み取りは可)。到達不能ホストの扱いは v1 R1 と同じ方式(片系の到達不能だけで rc 4 にしない)。
- **R2 ヘッダ**(先頭のコードブロック): `schema_version: 2` / `state` / `updated_at` / `status` / `node_count`。v1 の `note:` は削除する(推測を書かない)。`state` と `status` の意味と更新手順(updating → 本文 → complete)は v1 R4 と同じ。
- **R3 ノードブロック**(ノードごとに1つ。順序は pve1, pve2, quory, authy, monnie)。キーの集合と順序は固定し、値が無くても行を省かない。
  - `node` / `status`(`ok` / `unreachable` / `error`)/ `os`(例 `debian-13`、`ubuntu-26.04`)/ `role` / `repo`
  - `role` の値は固定する(計画査読 #4 を受けて確定。役割の出どころは `docs/ai/context/system/ubuntu-vm-patch.md` の表と inventory の group): pve1・pve2 = `pve`、quory = `qdevice`、authy = `radius`、monnie = `monitoring`。対応表は role の defaults 等に持ち、ホスト名から推測しない。`repo`(pve のみ。`enterprise` / `no-subscription` / `test` の該当するもの。複数あれば併記。非 pve は `n/a`)
  - `kernel_running`(`uname -r`)/ `kernel_installed`(起動可能なカーネル実体のうち最新。pve は v1 R2 の規則、Ubuntu は `linux-image-*` の実体から同等に)/ `kernel_reboot_required`(`true` / `false`。稼働中より新しいカーネルが入っている、または `/run/reboot-required` がある)
  - `services_restart_required`: `ライブラリ -> プロセス(unit), ...` を1ライブラリ1行(値が複数行になる場合の書き方は Implementer が決め、記録する)。判定は `roles/recovery_exec/files/homelab-stale-libs` と**同じ判定契約**(`docs/ai/reviews/dispatch_host_state_vocabulary/2026-11-14_001_requirement.md` P0-4、`/dev/` 除外を含む)。unit は `/proc/<pid>/cgroup` 等から引き、引けなければ unit を省く。行数上限を設け、超えたら末尾に `(+N more)`。該当なしは `none`、取得できなければ `unknown`。
  - `last_apply_at`(タイムゾーン付き ISO 8601)/ `last_apply_result` / `reboot_required` / `reboot_done`。pve の apply レポートから。非 pve は4キーとも `n/a`。
    - apply レポートは `reboot_required` を持たない(持つのは `reboot_done` と `reboot_trigger`。`roles/proxmox_patch_apply_node/tasks/main.yml` のレポート生成)。週次パッチ側は変えないので、`reboot_required` は `reboot_trigger` から導く: `none` → `false`、`reboot-required-file` または `kernel-version-mismatch:` で始まる値 → `true`、キーが無い・空・それ以外の値 → `unknown`(計画査読 #3)。
    - レポート自体が無い・読めないときは4キーとも `unknown`(v1 と同じ)。
  - `last_apply_upgraded`: `last_apply_at` 以降の apt 履歴(`/var/log/apt/history.log` と、ローテート直後に備えて `history.log.1.gz`)から、`パッケージ 旧->新` をカンマ区切り。手動の apt 実行が混ざってよい。行数上限と `(+N more)` は同上。該当なしは `none`、取得できなければ `unknown`。非 pve(apply レポートが無い)は `n/a`。
  - `vms_on_old_qemu`(pve のみ): 稼働中 VM のうち、動いている QEMU が古いものの数。1件以上なら VMID を併記(例 `2 (101,105)`)。取得できなければ `unknown`。非 pve は `n/a`。
    - **「古い」の定義**(差分再査読 N1 を受けて確定、2026-11-14): その VM の QEMU プロセスの実行ファイル(`/proc/<pid>/exe` の参照先)が ` (deleted)` になっている=起動後に QEMU のバイナリが置き換えられた、こと。パッケージの版の文字列比較はしない(上流の QEMU 版だけでは Debian の改訂の違いを見分けられず、生きているパスを所有パッケージで引くと常に現行版になるため)。
    - この値の取得失敗は `vms_on_old_qemu: unknown` に留め、`pve_manager`・`repo` など他の値へ波及させない。
  - `pve_manager`(pve のみ、非 pve は `n/a`)/ `collected_at`(ISO 8601)/ `package_count`(このノードのパッケージブロックの行数合計)
- **R4 パッケージブロック**(ノードごとに別のコードブロック)。
  - pve: Proxmox のリポジトリ由来の installed パッケージすべて(origin で判定)。ただし版ごとのカーネル実体パッケージは除外し、メタパッケージ `proxmox-default-kernel` と `proxmox-kernel-7.0`(系列が変わればその系列のもの)は残す。加えて Debian 側の固定一覧: apt、openssh-server、libssl3t64、libc6、zlib1g、corosync、systemd、sudo。
  - Ubuntu: カーネルのメタパッケージ(`linux-image-generic` 等、実在するもの)、apt、openssh-server、corosync-qnetd(入っていれば)、libssl3t64、libc6、zlib1g、systemd、sudo。固定一覧のうち入っていないものは載せない。
  - 1行1パッケージ: `名前: インストール版`。候補版がインストール版と異なるときだけ `名前: インストール版 (candidate 候補版)`。
  - 1ブロックに収まらないときは複数ブロックに分け、各ブロックの1行目に `part: i/n` を入れる。`part` 行を除いた行数の合計が `package_count` と一致すること。
  - 「Proxmox のリポジトリ由来」の定義(計画査読 S3): installed パッケージのうち、apt のメタデータ上、**インストール版または候補版のどちらかが Proxmox の origin から提供されている**もの。インストール版がどのメタデータにも無い(旧版で消えた・ローカル導入)場合でも、候補版が Proxmox origin なら含める。どちらも Proxmox origin でなければ含めない。origin の判定方法・候補版の取得方法は Implementer が決め、根拠を記録する。apt のメタデータ更新は行わない(読み取りのみ。候補版は既存のメタデータ時点のもの)。
- **R5 ノードの status**: v1 と同じく、到達不能は `unreachable`(版のキーはすべて `unknown`、パッケージブロックは空で `package_count: 0`)。必須の値(kernel・パッケージ一覧)が取れない・解析できないときは `error`。補助の値(`services_restart_required`・`last_apply_upgraded`・`vms_on_old_qemu`・`repo`)が取れないだけでは `error` にせず、その値を `unknown` にする。
- **R6 全体の status と rc・通知**(計画査読 #2 を受けて確定。v1 R7 と SB-020 の「全系の到達不能は非0」を保つ):
  - 5ノードとも `ok`: `status: ok`、rc 0、通知なし。
  - いずれかのノードが `error`: `status: error`(全体)、rc 非0、`#alerts` 1通。
  - pve1・pve2 の**両方**が `ok` でない(到達不能を含む): `status: error`、rc 非0、`#alerts` 1通(Proxmox の全系到達不能)。
  - 5ノードとも `ok` でない: 同上。
  - 上記以外で `ok` でないノードがすべて `unreachable`: `status: partial`、rc 0、通知なし。
  - Notion 更新失敗の扱いと「1回の実行で `#alerts` は1通」は v1 R7 と同じ。
- **R7 v1 から引き継ぐもの**: 認証情報(v1 R5)、抑止(v1 R6: `--check` / `skip_notifications` / AI セッション検出で Notion へ送らず本文を表示)、check-mode 分類(`check-mode-native`)、lock。
- **R8 索引・Policy**: `playbooks/README.md` の行を更新する(対象ホスト・内容)。`docs/ai/policies/proxmox_operations_policy.md` の表の行(`proxmox_running_versions.yml`)は対象ホストが増えるため文言を直す必要がある。**Policy 改訂なので文案を Yoshinobu へ提示して承認を得てから入れる**(Implementer は文案を実装記録に書くだけで Policy を編集しない)。

- **R9 キー一覧**(計画査読 S1 を受けて P0 へ): 新しいキーの一覧(キー・意味・値域・`n/a` / `none` / `unknown` の使い分け)を `docs/ai/reviews/proxmox_running_versions_v2/key_reference.md` に1枚にまとめる。Implementer が実装と同時に書く。読み手のプロンプト改訂に Yoshinobu が渡す資料になる。

### P1

- なし。

## 6. 受入条件

- **AC1** Given 5ホストに到達でき、When 通常実行(quory の Semaphore で手動)、Then rc 0、Slack 通知なし。Notion の読み戻しで、ヘッダが `schema_version: 2` / `state: complete` / `status: ok`、5ノードとも `status: ok`。各ノードの `kernel_running` が `uname -r` と一致する(Tester が `kernel-status` 語彙で突き合わせる)。5ノードの `role` が R3 の固定値(pve1・pve2 = `pve`、quory = `qdevice`、authy = `radius`、monnie = `monitoring`)と一致する。
- **AC2** Given pve1、When ページのパッケージブロックを読む、Then `pkg-list` 語彙で得た installed パッケージのうち Proxmox 由来の代表(pve-manager、libpve-common-perl、pve-container、qemu-server、pve-cluster、pve-xtermjs、libpve-cluster-perl)と Debian 固定一覧の版が一致し、版ごとのカーネル実体が無く、`proxmox-default-kernel` と `proxmox-kernel-7.0` がある。`part` 行を除いた行数の合計が `package_count` と一致する。
- **AC3** Given pve1 / pve2、When `services_restart_required` を読む、Then 同時刻帯に `stale-libs` 語彙で得たライブラリとプロセスと矛盾しない(該当があれば `ライブラリ -> プロセス(unit)` で載り、無ければ `none`)。
- **AC4** Given fixture(origin 混在の一覧、候補版が異なるパッケージ、版ごとのカーネル実体とメタパッケージ、上限超過の再起動待ち、`history.log` と `history.log.1.gz` にまたがる apply 履歴、空の履歴、読めない履歴、running-qemu が古い VM 2台)、When 整形処理を通す、Then それぞれ R3/R4 どおり(`(candidate x)`、除外と残留、`(+N more)`、両ファイルからの抽出、`none`、`unknown`、`2 (VMID,VMID)`)に出る。
- **AC4a** Given 生の apt の origin 情報の fixture(Proxmox origin と Debian origin の混在、インストール版がメタデータから消えて候補版だけが Proxmox origin のもの、どちらも Proxmox でないもの)、When 選別処理を通す、Then R4 の定義どおりに含める/含めないが決まる(Debian origin のものが紛れ込まないことの負例を含む)。
- **AC4b** Given apply レポートの fixture(`reboot_trigger` が `none` / `reboot-required-file` / `kernel-version-mismatch:...` / 空 / キー無し / 想定外の値)、When 整形、Then `reboot_required` がそれぞれ `false` / `true` / `true` / `unknown` / `unknown` / `unknown`、`last_apply_at` がタイムゾーン付き ISO 8601。
- **AC5** Given 1ノードのパッケージが1ブロックに収まらない fixture、When 整形、Then `part: i/n` 付きの複数ブロックになり、`part` 行を除いた行数の合計が `package_count` と一致する。
- **AC6** Given authy が到達不能(decoy または fixture)、When 実行、Then rc 0、通知なし、ヘッダ `status: partial`、authy は `status: unreachable` で版のキーが `unknown`、`package_count: 0`。
- **AC6a** Given pve1・pve2 の両方が到達不能(Ubuntu 3台は到達可)、When 実行、Then rc 非0、`#alerts` 1通(本番 Slack へは送らず通知 capture で観測)、ヘッダ `status: error`。
- **AC6b** Given 5ノードとも到達不能、When 実行、Then rc 非0、`#alerts` 1通、ヘッダ `status: error`。
- **AC7** Given 補助の値の取得だけが失敗するノード(fixture)、When 実行、Then そのノードは `status: ok` のままで、該当キーが `unknown`、rc 0。
- **AC8**(計画査読 #5 を受けて、リポジトリに残る再現可能な検査として足す。v1 の検査は `/tmp` 上の一時物で残っていない)
  - **AC8a** Given `--check` / `skip_notifications=true` / AI セッション検出のそれぞれ、When 実行、Then トークンファイルを読まず、Notion API へ1回も送らず、本文全体が出力に表示される。
  - **AC8b** Given fake の Notion API が 401 / 404 を返す、When 実行、Then rc 非0、`#alerts` 1通(capture)、出力・通知にトークンが出ない。
  - **AC8c** Given fake の Notion API が本文書き換え(②)または complete 化(③)で失敗する、When 実行、Then rc 非0、ヘッダが `state: updating` のまま。続けて正常な fake で実行すると `state: complete` に戻る。
- **AC9** 週次パッチの関連ファイル(`playbooks/proxmox_patch_weekly_full.yml` と import 先・`roles/proxmox_patch_apply_node`)に差分が無い。
- **AC10** `last_apply_at`・`collected_at`・`updated_at` がすべてタイムゾーン付き ISO 8601 で書かれている。

## 8. タイムライン考慮

- **工程の順序**(計画査読 #1 を受けて確定): ① Implementer 実装 → ② 差分Reviewer → ③ Coordinator が Policy 表(SB-020 の `proxmox_running_versions.yml` 行)の文案を Yoshinobu へ提示し承認を得る → ④ Coordinator が Policy を編集し、規範差分を差分Reviewer が確認する → ⑤ 実装と Policy を同じ commit にして Yoshinobu の承認で commit・push → ⑥ quory の Semaphore で手動実行(Yoshinobu)→ ⑦ Tester。**Policy の改訂が承認・反映される前に本番で手動実行しない。** 毎朝 07:00 の定期実行も v2 のコードで動くため、⑤は⑥と同じ扱いになる(Policy 未反映のまま commit しない)。

- 読み手は v1/v2 両対応のプロンプトを先に入れる(Yoshinobu、2026-11-14)。切り替え日を合わせる必要は無い。commit → 手動実行で v2 になったら、R9 のキー一覧を Yoshinobu へ渡す。
- 実行時間が伸びる(5ホスト、パッケージ一覧)。Notion「バッチ処理工程管理表」の 07:00 の行は、実測の所要時間が大きく変わったときだけ更新する(手動実行で測る)。
