## 0. 先に決めるべきこと

### 0.1 未解決の設計論点(新規。requirement作成後に判明)

**`sandbox` VM は pve2 上に置くため、それを操作すると harness 上は「保護対象ホスト pve2 への非冪等操作」に当たる。**

`.claude/settings.json` の `autoMode.soft_deny` は境界をホストで引いており、`sandbox` のラダー検証(`pvesh` による shutdown / start / stop)は pve2 に対して発行される。**中身がどれだけ無害でも、harnessはこれを止める。**

さらに Phase 4 完了後は、ansy から quory へも到達できなくなるため、**検証用probeインスタンスの起動・停止・状態確認の手段も失われる。**

| 案 | 内容 | 評価 |
|---|---|---|
| A | Yoshinobu が sandbox の検証を実行する | 確実だが手数が増え続ける。**Phase 4 後は結局これが常態になる** |
| B | `autoMode` に「対象VMが `sandbox` である非冪等操作」の許可を足す | 手数は最小。ただし**設定に依存した抑止**を増やす方向で、本案件のゴール2と逆行する |
| C | Semaphore に sandbox 検証用テンプレートを作り、Yoshinobu が起動、Claude Code は結果を読む | Phase 4 後の姿と一致する。**OQ7(テンプレート設計)が前倒しで必要になる** |

**推奨は C。** 理由は、Phase 4 後にどのみち C の形になるため、Phase 1 から C で組めば「Phase 1 で作った検証手段が Phase 4 で使えなくなる」事態を避けられる。A は Phase 1〜3 の暫定としては成立する。B は境界の作り方として本案件の趣旨に反するため採らない。

**2026-08-02、Yoshinobu が C を承認。** 以降の記述は C を前提とする。

#### C を採った場合に作るテンプレート(既存playbookに `-e target=sandbox` を付けるだけ。新規playbookは作らない)

| 検証したいこと | 起動するもの |
|---|---|
| ラダー第2段の全Phase(ACPI shutdown → 停止待ち → start) | `playbooks/recovery_vm_reboot.yml -e target=sandbox` |
| **強制電源断フォールバック** | 同上を、ゲストのACPI応答を止めた状態で実行 |
| ラダー第3段の Phase 1-2(タグ・HA登録・移行先選定) | `playbooks/recovery_ha_failover.yml -e target=sandbox --check` |
| サービス再起動段 | `playbooks/recovery_service_restart.yml -e target=sandbox` |
| **probe→ラダー連結 / `stopped`→start / flapping** | **テンプレートではない。** 第2インスタンスのprobe daemonが検知する。起動操作は「`sandbox` VMを停止する」ことそのもの(PVE GUIで1操作) |

**作る場所は quory の Semaphore**(本番実行基盤であり、`ann@quory` を使うため Phase 4 の影響を受けない)。

**playbookファイルはコピーしない。** 複製するのは Semaphore の**テンプレート定義だけ**で、`playbook:` は既存と同一パスを指す。コードを複製した時点で「本番と同一コードを撃つ」という前提が崩れる。

既存テンプレートは `arguments: []` / `task_params: {}` で、**変数はすべて `survey_vars` の extra vars として渡している**(この環境に `arguments` の使用実績はゼロ)。したがって sandbox 用も survey_vars を使い、**enum の値を `sandbox` 1個だけにする**。選択肢が1つしかないため、そのテンプレートから本番を撃つ経路が存在しない。既存の本番テンプレートの enum には手を触れない。

| 作るテンプレート | playbook | survey |
|---|---|---|
| `SANDBOX: Recovery vm reboot` | `playbooks/recovery_vm_reboot.yml` | `target` = enum `[sandbox]` |
| `SANDBOX: Recovery ha failover (check)` | `playbooks/recovery_ha_failover.yml` ← **`.yml` を忘れない** | 同上 |
| `SANDBOX: Recovery service restart` | `playbooks/recovery_service_restart.yml` | 同上 |

**`--check` の扱い**: この環境に `--check` を渡した実績が無い(`ubuntu_vm_full_upgrade` の dry_run は playbook 変数であって `--check` ではない)。`arguments: ["--check"]` が効くかを Phase 1 で確かめ、効けばテンプレートに焼き込む(**テンプレート自体が relocate 不能になる**)。効かない場合は起動時の dry-run 指定で代替してよい — `target` が `sandbox` に固定されている以上、`--check` を付け忘れて実relocateしても対象は使い捨てVMであり、pve1 停止中なら Phase 2 の assert が安全に失敗する。

**結果の読み方**: ラダー系playbookは `reports_base_dir` 配下へJSONレポートを書き、Slackへ通知する。**Phase 4 後は Claude Code が quory のファイルシステムを直接読めないため、レポートを返す名前付きチェックが Phase 3 に必要**(requirement R13b)。これが無いと「検証は起動できるが結果が読めない」状態になる。

**先に直すもの**: 既存の `UN-SAFE:Recovery ha failover(Manual)` は `playbook: playbooks/recovery_ha_failover` と `.yml` を欠いており、**手動起動が失敗する**(quory / ansy 両方。2026-08-02 発見)。自律ラダーからの呼び出しは `recovery-probe.py` が文字列を自前で組むため無傷。sandbox 用テンプレートを作る前に直す。

## 1. 全体構成

```
Phase 1  検証環境(sandbox)        能力を増やすだけ。失うもの無し
Phase 2  配備物ドリフト検出        能力を増やすだけ。失うもの無し
Phase 3  調査面(dispatch)の拡張    能力を増やすだけ。失うもの無し
─────────────────────────────── ここまでは途中で止めても安全
Phase 4  ann@homelab-ansible 削除  ここで初めて能力を失う
```

**Phase 4 の着手条件**: requirement の成功指標 S2(ドリフト検出が実際に版ずれを捉えた実績)と S3(ラダー各分岐の実行記録)が揃っていること。**揃っていなければ Phase 4 へ進まない。**

Phase 2 と Phase 3 は互いに独立で、並行して進められる。

## 2. Phase 1 — 検証環境(sandbox)

**目的**: ラダー・pvesh・強制電源断・flapping を、本番VMに触れず本番と同一のコードで撃てるようにする。

| 担当 | 作業 |
|---|---|
| **Yoshinobu** | ① pve2 上に `sandbox` VM を作成(既存Ubuntuテンプレートから。2GB / 10GB 目安)<br>② タグ `sandbox` を付与。**`prefer*` タグは付けない**<br>③ `/etc/pve/ha/resources.cfg` へ `state: ignored` で登録<br>④ D1でCを選んだ場合: Semaphore に検証用テンプレートを作成<br>⑤ commit |
| **Coordinator / Implementer** | ① `recovery_vm_reboot` / `recovery_ha_failover` / `recovery_service_restart` の assert へタグリテラルを追加(**変数化しない**)<br>② `recovery_probe` を、別 `state_dir` / 別 config の**第2インスタンスとして配備できるよう**にする<br>③ 検証側の `recovery_probe_targets` を設定として分離 |
| **Reviewer** | 差分の独立レビュー。特に「タグ追加が本番の到達範囲を広げていないこと」と「probe の lock 分離」 |
| **Tester** | decoy inventory での経路確認。実機ACはD1の決定に従う |

**完了判定**: AC1 / AC2 / AC3 / AC4 / AC5 / AC14 / AC15 / AC17 / AC18
**後追い可**: failover(`--check`)は pve1 稼働が要るため週末。Phase 1 の完了条件から外す(リスク8)

**前提の確認は完了済み**(0.3 U2)。`/cluster/ha/resources` は `state` で絞り込まないため、`state: ignored` でも sid つきで返る。R3 の設計は成立する。

## 4. Phase 3 — 調査面(dispatch)の拡張

**目的**: 保護対象ホストと quory の「現在値」を、鍵の全権を持たずに読めるようにする。Codex の調査面と同一物にする。

| 担当 | 作業 |
|---|---|
| **Coordinator** | 追加する read チェックの提案(`sha256sum` / `pvesh get` / `systemctl status` / `systemctl cat` / `journalctl -u`、およびバンドル参照系)。**防御層の現状確認は完了済み**(0.3 U4 — forced command が唯一の授権境界) |
| **Yoshinobu** | ① **チェック追加の承認**(D5)<br>② Claude Code 用鍵の生成と配備<br>③ 保護対象ホストへの dispatch 配備<br>④ commit |
| **Implementer** | dispatch script とテンプレートへのチェック追加。class ごとの分割を踏襲 |
| **Reviewer** | **書込系が1つも露出していないこと**を独立に検査 |

**完了判定**: AC8 / AC9 / AC10
**必須要件**:
- 配備物のハッシュを返すチェック(これが無いと Phase 4 で検出力が落ちる)
- ラダーの実行レポートを返すチェック(R13b。無いと `sandbox` の検証を起動できても結果が読めない)
- **障害バンドル・`_investigations/` の参照チェック**(R14c。`incident_sync` 退役の前提)

**`incident_sync` の削除はこのPhaseの最後に行う。** AC19(原本と一致する内容を取得できる)と AC20(operand検証が効く)を通してから。
