## 1. 問題定義

### 1.1 開発側が本番へ無制限に到達できる

ansy 上の Claude Code は `ann@homelab-ansible` 鍵で quory / pve2 / authy / monnie へ接続でき、いずれのホストでも `NOPASSWD: ALL` を持つ。forced command は無い。**実効的には fleet 全体の root である。**

これを抑えているのは `.claude/settings.json` の `autoMode` だけであり、`docs/ai/memory/lessons/permission-boundaries-must-be-designed-not-prompted.md` が「危うい」と指摘している形 — 設計された境界ではなく設定による抑止 — にそのまま当たる。`docs/ai/core.md` は「実効的な境界は文章ではなく、能力の不在(鍵・到達先・wrapperが存在しないこと)で作る」と定めているが、現状はそうなっていない。

### 1.2 単純に閉じると検出力が消える

2026-08-02、`ssh` での状態を変えない確認からしか出てこなかった発見が2件あった。

| 発見 | 性質 |
|---|---|
| `incident-capture-collector.py` が配備物として旧版のまま | 実害の窓が開いていた |
| `recovery-probe.py` の drill が生存していた | 潜在経路。約4週間、壊れたまま「成功」を報告し続けていた |

**どちらもWatchでは拾えず、実機を見て気づいた。** 書込系を締めるのと読取まで締まるのとでは検出力が変わる。

### 1.3 sudoers では読取と書込を分離できない

Ansible の become が発行するのは `sudo -H -S -n -u root /bin/sh -c '… AnsiballZ_*.py'` である。**Ansibleは `cat` も `systemctl` も打たず、rootで `/bin/sh -c <任意>` を実行する。** したがって「読むだけのplaybookならsudoを許す」というsudoersは書けない。becomeを1つでも許すことは無制限rootを許すことと同義である。

**「`ann` の sudo を絞る」は成立しない。** `ann` はAnsibleのサービスアカウントであり、`NOPASSWD: ALL` は全playbookの `become: true` を成立させている土台である。絞れば Claude Code ではなく本番のAnsibleが止まる。

### 1.4 本番の複製が無いため、検証手段が本番にしか無い

pvesh が関わる経路(probe → pveノード選定 → pvesh確証 → ラダー)を訓練する手段が、probe drill の削除により失われた。drill は「本番の sophos-fw に偽の障害を起こす」仕組みであり、そもそも設計として無理があった。一方、本番の複製環境は存在しない。

### 1.5 Codexの調査能力はYoshinobuが要望を出したときしか伸びない

`homelab-investigate-*` の許可リストは運用側の要望駆動で増える。開発側が必要とする確認は、現在は Claude Code が生の ssh で打っており、**運用側の調査面には一切還元されていない。**

### 2.1 境界を「能力の不在」で作る

`ann@homelab-ansible` 鍵を pve1 / pve2 / authy / **quory** の `~ann/.ssh/authorized_keys` から削除する。`.claude/settings.json` を書き換えても到達範囲は戻らない状態にする。

**実現手段**: Phase 4(R15〜R17)。**確認**: AC11(`ssh pve2 'id'` 相当が成立しない)、AC12(`ann@quory` 経路は無傷)、AC13(設定と文書が実測と一致)。

### 2.2 検出力を落とさない

1.2 の2件が、鍵を失った後にどう検出されるかを具体化する。

| 1.2 の発見 | 鍵を失った後の検出手段 | 検出のタイミング |
|---|---|---|
| `incident-capture-collector.py` が旧版 | Phase 2 のハッシュ突合 | **定期。人の訪問を待たない** |
| `recovery-probe.py` の drill 生存 | 同上 | 同上 |
| (今後)setup系playbookが未適用で unit / timer が登録されていない | Phase 2 の**登録状態突合**(R8) | 同上 |
| (今後)保護対象ホストの unit が落ちている等の現在値 | Phase 3 の名前付きチェック | 必要時 |

**検出力は「同等」ではなく「上がる」**。2件はどちらも、たまたま見に行った人がいたから見つかった。定期突合はそれを常時にする。

**実現手段**: Phase 2(R7〜R10)+ Phase 3(R11〜R13)。**確認**: AC6 / AC7 と成功指標 S2。

### 2.3 検証手段を先に用意してから閉じる

**実現手段**: Phase順そのもの。Phase 1〜3 は能力を増やすだけで何も失わない。**Phase 4 の着手条件を S2(ドリフト検出が実際に版ずれを捉えた実績)と S3(ラダー各分岐の実行記録)とし、揃わなければ進めない。**

### 2.4 開発側の要求が、運用側(Codex)の調査能力を押し上げる

Phase 3 で Claude Code 用に足すチェックは、**Codex が使っているのと同じ dispatch script・同じ許可リスト**に入る。したがって Claude Code が「これが見たい」と要求するたびに、Codex が障害調査で使える項目が1つ増える。

**現状**: 許可リストは Yoshinobu が要望を出したときだけ増える(1.5)。開発側が生の ssh で打っている確認は、運用側へ一切還元されていない。

**実現手段**: Phase 3(R11 / R13、4.5)。**確認**: 成功指標 S4(許可リスト項目数が Claude Code 由来の追加を含んで増加)。

**引き換え**: チェック追加の審査基準が本番のものになる(リスク5)。これは受容する。

## 3. 非ゴール

- **`ann@quory` 鍵に触れない。** 本番Ansibleの実行経路であり、本案件の対象外。
- **`recovery-action.sh`(action面)を共用しない。** サービス再起動は運用上の復旧アクションであり、`docs/ai/core.md`「開発は Claude Code、運用は Codex。役割を兼ねさせない」が適用される。Claude Code は action 鍵を持たない。
- **本番の複製環境を作らない。** 直近で実際に壊れていた3件(配備物の版ずれ / drill の4週間死亡 / pvesh配線の未訓練)は、いずれも「本番の現状がrepoと違う」種類の欠陥であり、複製環境では原理的に検出できない。
- **Codex を「エージェントとして」開発側の目にしない。** Codex の報告はエージェントが書いた要約であり、`docs/ai/core.md`「受信側は報告の説明だけを信頼せず、指定されたファイルと現在のdiffを読む」を満たせない。共用するのは**仕組み**(dispatch と許可リスト)であって推論ではない。
- **monnie / quory / ansy への非保護扱いを変えない。** ただし quory は 1.1 のとおり保護対象への鍵を保管しているため、鍵削除の対象には含める(4.2 参照)。
- **`recovery_push` の drill に触れない。** 削除済みの probe drill とは別物。
- **`proxmox_evacuate_node` と `proxmox_restore_vm_placement` を `sandbox` で検証できるようにしない。** この2本は対象をタグの集合で選ぶため、実行すれば必ず本番VM(sophos-fw / authy)を掴む。`sandbox` を足しても検証可能にはならず、**この2本は引き続き本番でしか動かない**。ラダー3本(`recovery_vm_reboot` / `recovery_ha_failover` / `recovery_service_restart`)が `name` で単一VMを選ぶのとは性質が異なる。
- **`.claude/settings.json` の `autoMode` を緩めない。** 本案件は設定による抑止を能力の不在で置き換えるものであり、設定を外す根拠にはしない。
- **nested Proxmox クラスタを常設しない**(2026-08-02 検討、見送り)。pve2 で nested virt は有効(0節で確認済)であり技術的には可能である。解消できる課題も実在し、**それは本案件が非ゴールとした `proxmox_evacuate_node` / `proxmox_restore_vm_placement`、および `proxmox_patch_weekly_full` のチェーン全体とノード停止時の挙動**という、リポジトリ内で最も未検証かつ影響の大きい領域である。それでも常設しない理由は3つ。

  1. **本案件のゴールに効かない。** 境界(Phase 2〜4)は nested があってもなくても同じ作業量であり、`ann@homelab-ansible` の到達範囲は1ミリも変わらない。
  2. **資源が pve1 停止時の受け皿と競合する。** pve2 の空きは22GB(sophos-fw と authy が `failback 0` により既に pve2 へ寄っている状態での値)。`sandbox` + `sandbox-mon` で6GB、意味のある nested クラスタ(nested PVE 2ノード + QDevice + 内部ゲスト)で13GB前後を見込むと、残りは数GBになる。
  3. **常設した検証環境はドリフトし、偽の確信を報告する。** 実ハードウェア(ZFS プール、SMART、温度)を持たず、Proxmox の版も本番と別々に動く。「検証したつもりで実は別物を検証していた」は削除した probe drill と同じ失敗であり、常設するほどこの危険は増える。

  **将来やるなら常設ではなく使い捨てで建てる。** 建てて、目的の1件を検証し、壊す。ドリフトは構造的に起きない。**着手のトリガは「Proxmox のメジャーバージョン更新を控えたとき」または「`proxmox_patch_weekly_full` のチェーンに手を入れるとき」**であり、それ以外の時期に常設環境として作る根拠は無い。

## 4. 設計の骨子

### 4.1 絞る対象は user でも sudoers でもなく authorized_keys の1行

保護対象3ホストの `~ann/.ssh/authorized_keys` には既に2エントリある。

```
ssh-ed25519 … ann@homelab-ansible   ← ansy。Claude Code が使う。本案件で削除する
ssh-ed25519 … ann@quory             ← 本番Ansible。触れない
```

**鍵が分かれているため、本番に一切触れずに開発側だけを閉じられる。**

### 4.2 quory を制限側に含めなければ境界は成立しない

quory は非保護ホストだが、`/home/yoshi/.ssh/id_ann`(= `ann@quory` 秘密鍵)を保管している。ansy から quory へ root で到達できる限り、保護対象ホストへの無制限到達は残る。**保護対象ホスト側だけを閉じても意味がない。**

### 4.3 失う能力と、その代替

| 失うもの | 代替 | Phase |
|---|---|---|
| ラダー・pvesh・強制電源断・flapping の検証 | **sandbox VM**(本物のpve2へ本物のpveshが飛ぶ) | 1 |
| 配備物の版ずれの検出 | **push型ドリフト検出**(quory が自らハッシュを出す) | 2 |
| 保護対象ホストの現在値(unit / journal / cluster状態) | **dispatch の名前付き read チェック**(Codexと共用) | 3 |
| playbook の構文・変数解決・分岐の検証 | decoy inventory(実ホスト不要。現状のまま) | — |
| 監視スタックの upgrade・抽出リハーサル | **sandbox-mon VM**(非保護、フルアクセス) | P1 |
| **pve / authy 固有playbook(≈15本)の実ホスト `--check`** | **代替なし。手放す** | — |

最後の1行は意図的な受容である。1.3 のとおり、Ansible の become を許すことと無制限rootを許すことは同義であり、`--check` だけを残す方法は存在しない。うち healthcheck 系は read チェックで代替でき、残りは Semaphore 経由(Yoshinobu起動)へ寄せる。

### 4.4 テスト専用タグは、本番の許可リストへのリテラル追加として実装する

sandbox VM をラダーの的にするには適格判定を通す必要がある。**呼び出し元(Claude Code か本番daemonか)で判定を切り替えない。**

- 実行時に枝が変わる仕組みは、本番の配備物に両方の枝を残し、誤判定が「実障害でラダーが対象外と判定して静かに何もしない」という**気づけない壊れ方**に倒れる。撤廃した `tester_mode` と同じ形になる。
- ラダーを起動するのは quory の systemd daemon(`User=yoshi`)であり、Claude Code は本番経路に登場しない。呼び出し元で分けると、sandbox で検証する経路が本番の経路と別物になる — 削除した probe drill と同じ欠陥。

したがってタグは assert のリテラルに追加する。**この許可リストを role default の変数へ括り出さない** — `-e` で上書きでき、任意のVMをラダー対象にできてしまう(`roles/recovery_exec/defaults/main.yml` に同型の指摘の前例がある)。

タグを広げても本番が撃てる相手は増えない。適格判定は2枚目のゲートであり、1枚目は `target` 名の指名(本番quoryでは `recovery_probe_targets` の3件)だからである。

### 4.8 sophos-fw と UniFi 機器は forced command で縛れない(実測)

`recovery_exec_targets` は authy / monnie、`recovery_exec_pve_targets` は pve1 / pve2 のみで、**sophos-fw と UniFi へは Codex が「コマンドを実行する」経路を持たない**。一方 ansy は `id_rsa_sophos`(user `admin`)と CloudKey の vault パスワード(user `root`)を持つ。

**ただしログは既に見えている。** `roles/alloy/defaults/main.yml` は `sophos_fw` を syslog source として定義し(`/var/log/sophos-fw.log` を `job: sophos-fw` ラベルで Loki へ送出)、Grafana の `infra_syslog_all_nodes.json` にも組み込まれている。Codex は `loki-count` / `loki-window` を持つため、**sophos-fw の一次情報へは追加作業ゼロで到達できる**。UniFi の CEF ログも同様に Loki へ着信している。

したがって欠けているのは**「コマンドを実行する経路」だけ**であり、一次調査の多くはログで足りる。**syslog / Loki を当面の代替とする**(2026-08-02 Yoshinobu 判断)。

しかし forced command による解決は **sophos-fw では不可能**である。

```
$ ssh -T sophos-fw 'echo MARKER; id'
% Error: Unknown Parameter 'echo'
```

Sophos はメニュー駆動のコンソールであり POSIX シェルを与えない。**`authorized_keys` に `command=` を仕込む余地も、dispatch script を配置する場所も無い。** 既存の `sophos_trim` も「SSH接続 → メニュー遷移 → RCマーカーのパース」という形で*メニューを操作*している。

したがって取りうる形は次の3つで、性質が異なる。

| 案 | 内容 | 強度 |
|---|---|---|
| S1 | 送信側(quory)に許可リスト付き wrapper を置く | **弱い。** dispatch のヘッダが「wrapper は first-line filter に過ぎず、authorization boundary は target 側の forced command」と明言している形の、target 側が無い版 |
| S2 | **ansy から `id_rsa_sophos` を削除**し、Sophos 関連の作業を quory Semaphore 経由に限定する | **強い。** 能力の不在そのもの。ただし粒度は全か無か |
| S3 | 現状維持 | — |

CloudKey は UniFi OS(Debian系)であり forced command は技術的に可能と思われるが、**ファームウェア更新で `authorized_keys` が初期化される可能性があり未検証**。

**本案件のPhase 4は、この2つに一切触れていない。** したがって Phase 4 完了後も、ansy は firewall に `admin`、CloudKey に `root` で到達できる状態が残る。**これは境界の穴として認識し、OQ9 で扱う。**

### 4.5 forced command の investigate 面は Codex と共用し、内容を同一にする

dispatch script の入力は `SSH_ORIGINAL_COMMAND` のみで、**呼び出し元を識別する手段が構造上ない。** これは維持すべき性質である。

| 単位 | 方針 |
|---|---|
| script 実装 | **同一**。class ごとに1本(`recovery-investigate-dispatch.sh` / `-pve.sh`) |
| 許可リスト内容 | **同一** |
| 鍵材 | **別**。独立に失効でき、authorized_keys のどのエントリで入ったかが残る |
| class の分割 | 現行の2分割(pve / authy・monnie)を踏襲する |
| action 面 | **共用しない**(3節) |

内容を同一にすることが、許可リストが腐らないことの担保である。開発専用の許可リストは probe drill と同じ経路をたどる。引き換えに、チェックを足す際の審査基準は本番のものになる。

### 4.6 HA failover は `--check` までしか検証しない(実relocateを行わない)

`recovery_ha_failover` で**未実証なのは relocate コマンドそのものではない**。`ha-manager crm-command relocate` は `proxmox_evacuate_node` と `proxmox_restore_vm_placement` が週次パッチで本物のHAサービス(authy / sophos-fw)に対して発行しており、**毎週実証されている**。sandbox で撃ち直しても新しい情報は得られない。

未実証なのは `recovery_ha_failover` 固有の配線であり、その大半は `--check` で実データのまま通る。

| 検証対象 | 必要な操作 | 週次パッチで通るか |
|---|---|---|
| Phase 1: タグ再検証・HA登録assert | **`--check` で足りる** | 通らない |
| Phase 2: 移行先選定(`/cluster/status` のオンライン非現在ノード) | **`--check` で足りる** | 通らない |
| Phase 3: `ha-manager crm-command relocate` の発行 | 実relocate | **通る(週次で実証済)** |
| Phase 4: target-node で running になるまでの待機 | 実relocate | 部分的に通る |
| ラダーからの遷移(vm_reboot失敗 → failover起動) | **vm_rebootを失敗させれば足りる**(呼び出し側は `r2.returncode` を見るだけ) | 通らない |

したがって**実relocateの限界価値は小さく、クラスタ共有設定への変更(HAルール新設)を伴う分だけ割に合わない**。実relocateはP2(任意)へ落とす。

### 4.7 sophos-fw が巻き添えを受けない根拠は3層ある

| 層 | 根拠 | 確認 |
|---|---|---|
| relocate は単一sidにのみ作用する | `roles/recovery_ha_failover/tasks/main.yml` L124-129 は `relocate vm:{{ _rhf_vmid }} {{ _rhf_target_node }}` を1回発行するのみ。ループでも集合でもない | 確認済 |
| **既存2サービスは `failback 0`** | CRMが再評価しても高優先ノード(`pve1:2`)へ勝手に戻らない。**最も効く保護** | `/etc/pve/ha/resources.cfg` で確認済 |
| HAルールはリソースを明示列挙 | authy と sophos-fw は別々の `node-affinity` ルールを持ち、共有されるメンバーシップが無い | `/etc/pve/ha/rules.cfg` で確認済 |

**残る唯一の実リスクは「クラスタ共有設定ファイルを編集する行為そのもの」**である。`/etc/pve/ha/{resources,rules}.cfg` は pmxcfs によりクラスタ全体へ複製されるため、追記の失敗はHA全体に及びうる。R3で追加を `resources.cfg` の1エントリに限り、AC15で既存2本の定義が変更前と同一であることを検査する。

## 11. タイムライン考慮

- **Phase順が安全機構である。** Phase 1〜3 は能力を増やすだけで何も失わない。失うのは Phase 4 のみ。したがって途中で止めても安全であり、Phase 4 の前に S2 の実績を必ず要求する。
- **Phase 1 の failover 検証は週末に限られる**(pve1 の平日シャットダウン運用)。Phase 1 の完了条件から failover を外し、後追いとする(リスク8)。
- Phase 2 とPhase 3 は独立に進められる。Phase 3 は R13(防御層の現状確認)の結果次第で範囲が変わる。
- 本案件はコード変更を伴うが、**着手時点では設計判断のみ確定しており、実装は Phase ごとに別途 plan を切る。**
