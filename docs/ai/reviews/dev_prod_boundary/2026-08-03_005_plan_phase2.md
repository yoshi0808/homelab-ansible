## 1. 設計判断: `--check --diff` を流用しない

**最初に検討して却下した案を明記する。** 「配備 playbook を `--check --diff` で定期実行し、`changed` が出たらドリフト」という案は、この repo では**機能しない**。

配備タスクの多くが `when: not ansible_check_mode` でブロックごとゲートされているため(TS-014 / TS-015)、`--check` では**タスクが評価されずスキップされる**。配備物が実際にずれていても `changed=0` と出る。

```
roles/recovery_probe/tasks/main.yml L89-91
  - name: Deploy, activate, and verify the probe unit (destructive; TS-015 chain)
    when: not ansible_check_mode        ← template / copy がまとめてスキップされる
```

`recovery_probe` / `incident_capture` / `recovery_io` など、検出したい対象ほどこの形になっている。**したがって独立した検査を書く。**

## 2. 検出対象と実現手段

| # | クラス | 期待値の出どころ | 実現 |
|---|---|---|---|
| ① | **`copy` 配備物の内容** | repo の `roles/*/files/*` を直接ハッシュ | **Tier 1** |
| ② | **systemd unit / timer の存在・`enabled`・`active`** | 対象一覧をrole defaultsに明示 | **Tier 1** |
| ③ | **timer のスケジュール** | 同上(`OnCalendar` の期待値) | **Tier 1** |
| ④ | **`reports/` 配下の所有権** | 「`reports/` 直下は全て同一所有者」という不変条件 | **Tier 1** |
| ⑤ | **quory の `/etc/hosts`** | inventory のホスト名が全て引けること(IPは比較しない) | **Tier 1** |
| ⑥ | **`recovery-exec` の `authorized_keys`** | **構造検査** — 全エントリが `command=` で始まること、エントリ数 | **Tier 1** |
| ⑦ | `template` 配備物の内容(dispatch / sudoers / unit本体) | テンプレートを同じ変数で描画して比較 | **Tier 2(後続)** |

**⑥が Tier 1 に入る理由**: 内容一致は Tier 2 だが、「forced command の付いていない鍵が1本増えている」という**最も危険なドリフト**は構造検査だけで捕まる。Phase 3/4 の前提そのものなので先に置く。

**⑦を後回しにする理由**: 期待値を得るにはテンプレート描画が要り、変数解決を配備時と一致させる必要がある(2026-08-02 に `recovery-probe.json.j2` で手動実施し成立を確認済み)。作れるが、Tier 1 だけで Phase 1 の実例3件すべてを捕まえられるため、S2 の達成を待たせない。

## 3. 実行場所と経路

```
quory の Semaphore(日次スケジュール)
  → ansible-playbook playbooks/deployment_drift_check.yml
     hosts: 全管理対象(quory / ansy / monnie / authy / pve1 / pve2)
     接続は ann@quory  ← Phase 4 の影響を受けない
  → 収集 → repo の期待値と突合 → reports/drift/ へJSON
  → ドリフト時のみ Slack 通知。正常時は無通知・終了コード0
```

- **ansy を経路に入れない**(requirement の制約)。ansy は対象ホストとしてのみ登場する
- pve1 が停止していても**赤くしない** — 到達不能は「未確認」として記録し、終了コードは0(`proxmox_patch_dryrun` の rc=4 で学んだ形)
