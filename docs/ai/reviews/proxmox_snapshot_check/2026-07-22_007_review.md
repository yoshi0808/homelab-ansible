## Finding

### suggestion: Clarify whether `critical` means severity or Ansible failure in the shared Context

`docs/ai/context/operations/healthcheck.md` §2 describes the two stages as
`warning=注意喚起` and `critical=fail相当`. In this role, the specific setup and the
existing confirmed design define CRITICAL through report status, Semaphore summary,
and Slack severity, while the role remains notification/report-only. The phrase can
therefore be read as requiring a new `ansible.builtin.fail` task even when the
role-specific requirement does not request that operational side effect.

For a future Context revision, distinguish severity (`result.status == 'CRITICAL'`)
from playbook termination (`ansible.builtin.fail`) and state that termination remains
role/requirement-specific. This is a documentation/process improvement and does not
block the current implementation.

## Acceptance criteria review

- A role-prefixed critical threshold variable was added in seconds with a 30-day
  default. The value is longer than the existing 7-day warning threshold and the
  reason is recorded in the implement result.
- An assert rejects configurations where the critical threshold is not greater than
  the warning threshold.
- Existing `_stale_entries` remains the complete 7-day-or-older set, preserving
  `stale_count` and `stale_snapshots` semantics.
- The warning list uses `snaptime > critical_threshold_epoch`; the critical list uses
  `snaptime <= critical_threshold_epoch`. Because both are selected from the existing
  warning-threshold-filtered stale list, they are exhaustive and mutually exclusive.
- Boundary semantics are correct: just before 7 days is OK, 7 days through just
  before 30 days is WARNING, and 30 days or more is CRITICAL.
- Collection failure remains WARNING unless a genuinely critical snapshot is also
  present. It is not incorrectly promoted by this change.
- Report status gives CRITICAL precedence over WARNING, and the run-once multi-host
  summary cannot be downgraded by a later WARNING host.
- Slack status/title/body and notification condition handle WARNING and CRITICAL,
  while OK remains silent.
- The collector shell has no diff. Collection/JSON formatting remain in shell and
  threshold classification remains in Ansible.

## CRITICAL without a new fail task

The decision not to add a new fail task is **appropriate for this change**.

- The current pilot3 acceptance criteria explicitly require CRITICAL report status,
  summary aggregation, and Slack severity, but do not require a non-zero play result.
- The role's existing confirmed behavior is warning/report/notification-only. Its
  original implementation explicitly omitted fail behavior.
- Adding `ansible.builtin.fail` would change timer/Semaphore exit behavior and is a
  new operational side effect, not a necessary consequence of adding severity to
  the report.
- Other healthcheck roles that fail on CRITICAL do not override this role-specific
  requirement and established behavior.

If operators want stale snapshots of 30 days or more to fail the playbook, that
should be a separate explicit requirement with its downstream timer/Semaphore impact
reviewed. It is not a must-fix for pilot3.

## New Context impact

The new `docs/ai/context/operations/healthcheck.md` improved review quality by putting
three relevant checks next to each other: collector/classifier responsibility,
exclusive warning/critical ranges, and marker-to-guard verification. It reduced the
time needed to identify the exact reference patterns and helped ensure the review did
not focus only on the new threshold expression.

For this small diff, setup and Context repeat some of the same facts, so the speed
gain was modest rather than dramatic. Sections 1--3 were directly useful; report
storage in §4 was only a quick regression reminder, and the `df` percentage warning
in §5 did not apply. The ambiguous `critical=fail相当` phrase required additional
reading of the role's original requirement and prior accepted review, partially
offsetting the speed gain. With the suggested clarification, the Context would be a
useful compact entry point rather than excessive documentation.
