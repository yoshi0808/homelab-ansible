1. `/tasks/{id}/output`の各エントリは1エントリ=1ログ行だが、末尾に`\n`を持つとは限らない(ansy task 20実測: 74エントリ中9個のみ末尾`\n`あり)。空文字列で連結していたため大半が1行へ潰れ、行単位マッチ(`PLAY RECAP`/`fatal:`)が機能しなかった。修正: 各エントリの既存の末尾`\n`を`rstrip`してから`"\n"`で連結する(sqlite3のlist modeが「1行=1出力行」を保証していた旧挙動と同じ形にする)。

### 2.7 旧ACLの明示的な撤去(独立レビュー2026-08-19_003 High #1)

`ansible.posix.acl`の`state: present`は指定したentity/etype/pathの1エントリを作るだけで、**別pathにある既存エントリには一切触れない。** そのため2026-08-19の最初の実装(token file ACLへの置換)は、新token ACLを付与する一方で、**既に配備済みのホストが持つ旧`semaphore.db` read ACL・`/var/lib/semaphore` traverse ACLをそのまま残していた。** コメントで「former grants are gone」と書いていたのはコード上grantタスクが無くなったという意味で、**配備先ホストの実状態を指していなかった**(Coordinatorがdispatchの`acl-status`でquoryの実ACLを読み、3識別子とも旧ACLを保持していることを確認)。

修正: 3 roleそれぞれに、token file ACL付与taskの直後へ`state: absent`のtaskを2つ(`semaphore.db` read・`/var/lib/semaphore` traverse)追加した。**順序は新規付与→旧撤去。** 途中で失敗して再実行された場合、新規付与は冪等(既にあれば何もしない)、旧撤去も対象が既に無ければ冪等に成功するため、どの時点で止まっても再実行で「新token ACLのみ持ち、旧ACLは持たない」状態へ収束する。逆順(旧撤去→新規付与)だと、失敗が両taskの間で起きた場合に新旧どちらの経路でも読めない空白期間ができてしまうため採らなかった。

### 2.8 API応答の厳密な検証(独立レビュー2026-08-19_003 High #2)

最初の実装は、配列を期待するendpointへ単一objectが返ってもそれを1件配列として受理する`as_list()`(`roles/semaphore_templates/tasks/resolve.yml`の、真に配列/単一objectどちらもありうるendpoint向けの防御的分岐を、配列であることが確定している別のendpointへもそのまま流用したもの)と、task entryのフィールド欠落を空文字へ読み替える緩いフォールバックを持っていた。Coordinatorが`api_get`だけを差し替えて実測したところ、`{"error": "unexpected-object"}`という異常応答をそのまま標準出力へ流して`exit 0`にする、`[{"id": 9}]`(status等が全欠落)から`9|unknown||||`という**6フィールドとして成立してしまう行**を作る、という2つの実際の不具合が出た。

修正は`as_list()`を撤去し、`require_array()`(配列以外は無条件で失敗)・`require_int()`・`require_str()`という専用の検証関数へ置き換え、endpointごとに次を必須とした。

- `/projects`: 配列。各要素はobject。project idは整数(URLへ埋め込む前に検証、boolはintのサブクラスなので明示的に除外)。
- `/project/{id}/tasks`: 配列。各要素はobjectで、`id`が整数・`status`が空でない文字列であること。`start`/`end`/`playbook`/`tpl_alias`等は元々値の欠落がありうる項目のため引き続き空文字へフォールバックする(§2.6のplaybookフィールドと同じ理由)。
- `/project/{id}/tasks/{id}/output`: 配列。各要素はobjectで`output`が文字列であること。
- `/project/{id}/templates`: 配列。各要素はobjectで`id`が整数であること。

いずれも**該当queryの標準出力へ1行でも書く前に、応答全体を検証してから処理する**(`fetch_tasks()`/`fetch_output_text()`が全件検証してから返す設計のため、途中まで出力してから失敗する経路が無い — Reviewerの`What Looks Good`で「1 invocation内の後段API失敗で部分stdoutを正常結果として残す経路は見つからなかった」と評価された性質を、この修正後も維持している)。

### 2.9 `task-hosts`のPLAY RECAP欠落を非ゼロ終了に(独立レビュー2026-08-19_003 High #3、requirement RSK2)

完了したAnsible playbook実行のジョブ出力には、成功・失敗を問わず必ず`PLAY RECAP`セクションが付く。見つからないことは「ホストが0件だった」ではなく「導出が期待した形の入力を得られなかった」ことを意味するため、旧実装の`if start is None: return`(空出力・exit 0)を`die()`(非ゼロ終了・stderrへ理由)へ変更した。

**`task-errors`は変更していない。** `fatal:`行が0件であることは、対象タスクに個別のAnsibleタスク失敗が無かったことを意味しうる正当な結果であり(例: SSH到達不能などplaybook開始前の失敗)、`task-hosts`のPLAY RECAPとは性質が違う。requirement RSK2も「`PLAY RECAP`の導出が失敗したら」という限定でこの扱いを求めており、`task-errors`には触れていない。

**`incident-capture-collector.py`側の変更は不要だった。** `build_semaphore_bundle()`は元から`task-hosts`/`task-errors`の`rc != 0`を`bundle_errors`(→`summary["collection_errors"]`)へ積む設計になっており(既存コード、今回変更していない)、`main()`側の集計(`any_bundle_errors = any(s.get("collection_errors") for s, _r, _h in pending_bundles)`、`has_errors = bool(collection_errors) or any_bundle_errors or not semaphore_query_ok`)がそのままheartbeatの`has_errors`と終了コードへ反映する。したがって`cmd_task_hosts`側の`die()`化だけで、収集器側は自動的に「PLAY RECAP欠落を検知エラーとして記録する」形になった。現物を読んで確認した(コード変更はしていない)。

### 2.10 HTTP redirectの拒否(独立レビュー2026-08-19_003 Medium #4)

Pythonの`urllib.request`は既定で`HTTPRedirectHandler`を持ち、3xx応答を受けると`Authorization`ヘッダを含む非content系ヘッダをそのまま新しいURLへ転送して追随する。この転送先が別originであっても止める仕組みが標準では無いため、Semaphore側(またはその手前のリバースプロキシ)が3xxを返す状況では、guestトークンが想定外のoriginへ送られうる。

修正: `HTTPRedirectHandler.redirect_request()`をoverrideして常に`None`を返す`_NoRedirectHandler`を定義し、`urllib.request.build_opener(_NoRedirectHandler())`で作った専用openerを`urlopen()`の代わりに使う。`redirect_request()`が`None`を返すと、そのハンドラは3xxを処理しなかったことになり、`urllib`標準の`HTTPErrorProcessor`が最終的に`HTTPError`を送出する(Python標準の「redirectを拒否する」実装パターン)。これは`api_get()`の既存の`except urllib.error.HTTPError`にそのまま捕まり、非ゼロ終了・stderrへ理由という既存の失敗経路へ合流する。**同一origin向けのredirectだけ許可する案(Reviewerが提示したもう一方の選択肢)ではなく、全redirectを拒否する方を採った** — `api_base()`が返すorigin自体が固定値であり、Semaphore REST APIがGETをredirectで返す正当な理由が無いため、複雑な同一origin判定を実装する必要が無いと判断した。
