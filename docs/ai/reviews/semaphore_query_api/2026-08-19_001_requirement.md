# requirement: `homelab-semaphore-query` を SQLite 直読みから Semaphore API へ移す

作成: 2026-08-19 / Coordinator

## 1. 問題定義

**2026-08-18 の Semaphore 2.19.8 への版上げで、`homelab-semaphore-query` が動かなくなった。** 2.19.8 は SQLite を WAL モードで開くようになり、ACL の付かない補助ファイル(`-shm` / `-wal`)が必要になったため、`semaphore.db` に read の ACL を持つだけの識別子はデータベースを開けない(`unable to open database file (14)`)。**`recovery-exec` / `incident-inspect` / `dev-investigate` の3つとも不通である。**

**ファイル個別に ACL を足しても直らない。** 補助ファイルは起動のたびに ACL 無しで作り直される(ansy 実測)。

**そもそも SQLite の直読みは Semaphore がサポートする接し方ではない**(公開された口は API であり、ストレージの内部形式は上流が自由に変えてよい)。**直読みを復旧させる方向の対処は、次の版上げで別の形で壊れる。**

### 影響は調査経路だけではない

**`incident_capture` の収集器が同じツールを使っており、本番で現に劣化している。** `roles/incident_capture/files/incident-capture-collector.py` は `recent-failed` を起点に、`task-time` / `task-errors` / `task-hosts` / `task-output` で incident bundle を肉付けする。

**ただし黙って壊れてはいない。** クエリ失敗は `collection_errors` へ記録され、**終了コードは非ゼロ**、run report が書かれ、heartbeat に `has_errors: true` が載る。「取れなかった」と「何も無かった」は区別されている。

## 2. ゴール

**`homelab-semaphore-query` を Semaphore API 経由へ移し、`incident_capture` と調査経路を復旧させる。** 管理者権限の資格情報を読み取り経路へ置かないこと。

## 3. 非ゴール

- **SQLite 直読みの復旧。** ACL の拡張、ディレクトリへの書き込み許可、`journal_mode` の変更のいずれも採らない
- **特権側が読み取り専用スナップショットを配る案。** サポート外の依存を温存したまま覆いをかけるだけで、次の版上げでまた壊れる
- **dispatch の語彙を増やすこと。** `semaphore-query <enum> <整数>` の契約は変えない(§5 R1)
- **Operator が使っている guest トークンの流用。** 消費者が違えば独立に失効できるべきである(§5 R4)
- **`task-hosts` / `task-errors` の構造化。** API に対応物が無いことは quory の実タスクで確認済み(§8 決着済み)

## 4. ユーザーストーリー

Coordinator と自律復旧・incident 調査の各経路として、Semaphore のジョブ結果を読みたい。ただし **本番の制御平面に対する読み取りであり**、①管理者権限を持ち込まないこと ②上流の実装変更で再び壊れないこと ③読めなかったときにそれが分かること、を満たしたい。

## 5. 要件

### P0(Must)

| # | 要件 |
|---|---|
| R1 | **CLI 契約を変えない。** `homelab-semaphore-query <query> <整数>` の7クエリ(`recent-failed` / `running` / `task-errors` / `task-hosts` / `task-output` / `task-time` / `template-list`)をすべて維持する。**dispatch(`roles/dev_investigate/files/recovery-investigate-dispatch-quory.sh`)は1文字も変えない** |
| R2 | **出力形式の契約を維持する。** `recent-failed` は `id\|template\|playbook\|status\|start` の5フィールド、`task-time` は `id\|template\|playbook\|status\|start\|end` の6フィールド、いずれもパイプ区切り1行1件。**`incident_capture` の `parse_recent_failed` / `parse_task_time` がこの形を前提にしている** |
| R3 | **時刻は API が返す RFC3339 をそのまま出し、`incident_capture` 側のパースを同じ変更で追随させる。** DB の Go 形式(`... +0000 UTC`)を合成しない — **API が返さない形を作り出すことになるため。** 収集器は最終的に RFC3339 JST へ変換しており、RFC3339 を受け取る方が経路が短い |
| R4 | **admin ではない Semaphore ユーザーを作り、project role `guest`(読み取り専用)を与えた専用トークンを使う。** Operator が使っているトークンとは別に発行する |
| R5 | **project id を名前で解決する。** 固定値を持たない(ansy と quory で異なり、ansy は 2 から 3 へ変わった実績がある) |
| R6 | **`task-hosts` / `task-errors` はジョブ出力から導出する。** `PLAY RECAP` 行とホスト別の失敗行を出力テキストから拾う。**消費側は生テキストとして保存しており構造化パースをしない**ため、形式の厳密な再現は要求されない |
| R7 | **読めなかったことを、結果が無いことと区別できる形で終える。** API へ到達できない / トークンが読めない / 認証が拒否された / 応答が期待した形でない — いずれも**非ゼロ終了と標準エラーへの明示メッセージ**とし、**空の標準出力で正常終了しない。** 「0件だった」と「取れなかった」が呼び出し側から見分けられること |
| R8 | **トークンを標準出力・標準エラー・ログのどこにも出さない。** 失敗メッセージにも含めない |
| R13 | **`incident_investigate_run_user` にもトークンファイルの ACL read を与える**(Yoshinobu 決定、2026-08-19)。`incident-investigate.service` は `User=yoshi` で走り、`homelab-semaphore-query` を直接呼ぶ。**旧設計ではこの identity が `semaphore.db` の所有者だったため ACL が要らなかった** — 機構が変わって初めて現れた4人目の消費者であり、権限が広がるわけではない |
| R14 | **incident-inspect の codex sandbox を緩めない。Semaphore の情報は sandbox の外で先読みし、ファイルとして LLM へ渡す**(Yoshinobu 決定、2026-08-19)。**`--sandbox read-only` は外向き通信を塞ぐ**(実測: sandbox 内で `HTTP=000` / curl 終了コード7、外で `HTTP=200`)。`network_access` は `workspace-write` にしか効かないため、この設定のまま通信を許可する手段は無い。**`workspace-write` へ下げて解かない** — 通信のために書込能力まで渡すことになる。`incident-investigate.py` が既に `task-time` を sandbox の外で先読みしている形を広げ、**`AGENTS.md.j2` はコマンドではなく先読み済みのファイルを指すよう書き換える** |

## 6. 受入条件

**AC1 — 7クエリが低権限のトークンで通る**
> Given `guest` ロールのトークンだけを持つ状態で
> When 7つのクエリをそれぞれ実行する
> Then すべて終了コード `0` で、期待した形の出力を返す。**admin トークンを一度も使わない**

**AC2 — 出力形式が消費側の契約を満たす**
> Given 版上げ後の Semaphore に対し
> When `recent-failed` と `task-time` を実行する
> Then それぞれ5フィールド / 6フィールドのパイプ区切りで、`incident_capture` の `parse_recent_failed` / `parse_task_time` がエラーを出さずに解釈できる

**AC3 — 読めなかったときに非ゼロで終わる**
> Given トークンファイルを読めない、または API へ到達できない状態で
> When 任意のクエリを実行する
> Then **終了コードが非ゼロ**で、標準エラーに理由が出る。**標準出力は空で終了コード0にならない**

**AC4 — トークンが漏れない**
> Given 認証が拒否される状態で
> When クエリを実行する
> Then 標準出力・標準エラーのどこにもトークン文字列が現れない

**AC5 — dispatch が無変更で動く**
> Given dispatch を1文字も変えていない状態で
> When `ssh <調査用identity> "semaphore-query recent-failed 3"` を実行する
> Then 版上げ前と同じ形の出力が返る

**AC6 — incident capture が復旧する**
> Given 新しいツールを配備した状態で
> When 収集器を1周期実行する
> Then 終了コードが `0`(収集エラー無し)で、heartbeat の `has_errors` が `false`。失敗ジョブがあれば bundle が作られ、`semaphore-log.log` が空でない

**AC7 — 直読みへ戻らない**
> Given 新しいツールを配備した状態で
> When 実装を確認する
> Then `semaphore.db` を開くコードが1つも残っていない。`sqlite3` への依存が無い

**AC9 — `incident-investigate.py` の identity がトークンを読める**
> Given 新しい role を配備した状態で
> When `incident_investigate_run_user` の identity で `homelab-semaphore-query` を実行する
> Then トークンを読めて終了コード `0` で結果が返る。**「読めなかった」で非ゼロ終了しない**

**AC10 — sandbox を緩めずに、LLM が Semaphore の情報へ到達できる**
> Given incident-inspect の調査セッションを起動した状態で
> When LLM が Semaphore のジョブ結果を必要とする
> Then **先読み済みのファイルから読める**。`--sandbox read-only` と `network_access=false` は変更されていない。**`AGENTS.md.j2` がコマンドの実行を指示していない**(指示すれば sandbox 内で必ず失敗する)

## 7. 成功指標

- **incident bundle が版上げ前と同じ中身で作られる**(ジョブ出力全文が入る)
- **次の Semaphore 版上げで、このツールが壊れない**(API 契約に依存するため)

## 10. リスク

| # | リスク | 対応 |
|---|---|---|
| RSK1 | guest ロールの権限が足りず、一部クエリが 403 になる | 工程3で先に判明する。足りなければロールを上げるのではなく、**そのクエリを落とす**選択を先に検討する |
| RSK2 | `PLAY RECAP` の導出が壊れやすい | 消費側は生テキストとして保存しており構造化パースをしない。**導出が失敗したら空文字ではなく明示のエラーを返す**(R7) |
| RSK3 | トークンが読み取り経路の識別子から読める状態になる | forced command が唯一の授権境界であり、対話 shell は得られない。**現行の「DB 全体への read ACL」と比べて広がってはいない** |
| RSK4 | 移行中は incident capture が劣化したまま | 失敗は非ゼロ終了・run report・heartbeat で観測できる。**データが失われる形ではない** |
