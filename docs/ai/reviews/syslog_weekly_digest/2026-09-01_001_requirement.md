# requirement: syslog週次ダイジェスト

日付: 2026-09-01
状態: **未決を確定(2026-09-03)。Implementerへ渡せる**

## 1. 背景

`monnie` のLokiは2026-07-20のAlloy移行(Phase 2)以降、8系統のsyslogを蓄積している。**しかしこの内容は誰も定期的に見ていない。** `docs/ai/policies/log_observability_policy.md` §4 は syslog 系統の検知を **「未実装。蓄積内容の事後参照に留まる」** と明示しており、未実装の理由を「閾値の時期尚早な設定を避け実データの蓄積を待つため。**実装時期は蓄積状況を見て判断する**」としている。

Yoshinobu提起(2026-09-01)「warning, error を見ていないので何かあっても気づけていないかもしれない」。

## 2. 着手前の実測(2026-09-01、Coordinatorが `monnie-investigate` の `loki-count` / `loki-window` で実施)

直近24時間の level 別件数:

| level | 件数 |
|---|---|
| error | 7(pve2 2 / quory 2 / uckg2 3) |
| warning | 183(monnie 54 / quory 43 / ansy 42 / authy 40 / pve2 4) |
| info | 約22,700 |
| **level ラベル無し** | **7,471**(すべて `network-devices` = UniFi AP / スイッチ) |

この実測が要求を決めた3点:

1. **緊急に対処すべき異常は出ていない。** error は 1日7件。「見ていない間に壊れ続けている」状態ではない
2. **warning は大半がノイズ。** 直近1時間の実サンプルでは monnie の warning はほぼ全て Grafana プラグイン読み込み時の `Opening file ... failed, proceeding without lock`、ansy は `canonical-livepatch` の情報ログ。**level を発火条件にすると初日から無視される通知になる**
3. **`network-devices` の 7,457行/日 に level ラベルが無い。** level ベースの検知は最大のログ源を全て取りこぼす。(memory の `reference_unifi_cloudkey_cef_levelless.md` は CloudKey を level 無しとするが、**実測では uckg2 には level が付いており、無いのは AP / スイッチ側**だった。この記録は本requirementで訂正する)

## 3. 目的

**閾値を決めずに「見ていない」状態を解消する。** 週に1度、Lokiの中身の要約を Slack へ出す。

**本案件は検知(alerting)を実装しない。** Policy §4 の Phase 3(flapping・接続断のパターン検知)は別案件とし、本ダイジェストの運用で得られる「普段どのくらい出るか」の感覚をその設計入力とする。

## 4. 受入条件

- **AC1**: 週次で Slack `#info` へダイジェストが届く
- **AC2**: ダイジェストに次を含む — 対象期間、job×host×level の件数表、**error 行の全文**(件数が上限以下のとき)、level ラベルを持たない系統の件数
- **AC3**: error が上限を超えるときは、全文でなく件数と代表例に切り替え、**省略した事実を本文へ明示する**(黙って切らない)
- **AC4**: Loki への問い合わせが失敗したときに **緑で終わらせない**。取得できなかった事実が通知に出るか、ジョブが失敗する
- **AC5**: 収集期間に該当ログが 0 件でも「0件だった」と分かる形で届く(無通知にしない)
- **AC6**: `--check` で副作用なく完走する
- **AC7**: 本playbookは状態を変えない。Loki へは読み取りのみ

## 5. 制約

- **level を発火条件にしない。** 本案件は通知の閾値を持たない(ダイジェストであって alert ではない)
- **既存の `recovery-loki-helper` の出力量制限(query limit / 行数 / 行長)を回避しない。** 足りないならその事実を書く。**この制約はhelperを再利用しない場合も効く**(2026-09-04明確化) — §6.1でhelperを使わないと決めたのは窓の長さの都合であって、出力量の上限を緩める根拠ではない。独立レビューが `ERROR_QUERY_LIMIT=2000`(helperは300)を契約違反と判定し、Coordinatorはこれを受け入れた。**Coordinatorの当初の読み(「Slackへ出る量は文字数予算で縛られるので回避ではない」)は誤りである** — 予算が縛るのはfilter適用後の本文だけで、collectorのstdout・Ansibleのregister・Semaphoreのjob outputを通る未加工の量を縛らない
- 実行は quory の Semaphore。`hosts: monitoring_servers`
- **`# tester-gate: role-guarded`**(2026-09-04訂正。起案時は `safe-readonly` としていたが誤り — 本playbookは**毎回必ずSlackへ送る**のが目的であり、`TS-005` の `role-guarded`「副作用がSlack通知のみで、`roles/common_slack/tasks/notify.yml` の抑止guard(TS-031)で止まる」にそのまま該当する。`safe-readonly` は「完全read-only(収集・観測のみ)」で、常時送信はこれに当たらない。独立レビューが検出した)
- **秘匿の保証は「機械的に検出できるIPv4リテラル」に限る**(2026-09-04、Yoshinobu決定)。起案時は「IPアドレス・秘密情報を出力しない」と書いていたが、**error全文をSlackへ出す設計と両立しない** — 任意のログ本文に何が入るかを縛る手段が無く、秘密の識別規則も上流の保証も無い状態では、「未知の秘密を一切出さない」は証明できない。独立レビューがこの衝突を検出した。
  - **IPv4は送信前に一律で伏せる**(job / host / ログ本文のすべて、整形後の最終文字列に対して)。過剰検出を許容し、見逃しより誤検出を選ぶ
  - **IPv4以外のcredential / tokenがerror本文に混じって `#info` へ出る可能性は、残存リスクとして受容する。** 根拠は①宛先が内部Slackの `#info` であること②対象が管理下ホストのsyslogであること③「warning・errorを見ていない状態を解消する」という本案件の目的にはerror全文が要ること
  - **これは安全境界の緩和であり、`docs/ai/policies/execution_boundary_policy.md` EXEC-030 によりYoshinobuの判断で決めた。** Coordinatorが受容してよい範囲ではない
  - 採らなかった案: AC2を緩めてerror本文を先頭N文字へ落とす(ダイジェストの価値が落ちる) / `operator_request_channel` のDLPルールセットを流用する(**あれは「拒否」機構であって「マスク」機構ではなく、1行にtokenが混じるとダイジェスト全体が落ちる**。既知の誤検知14件も抱える) / 「syslogに秘密は入らない」保証を正本へ書く(**根拠を出せないため、確かめずに書けば「確認していないものを確認したと書く」ことになる**)

## 6. 確定した設計判断(2026-09-03、Coordinator)

### 6.1 Lokiへの問い合わせは、monnie上で直接 `http://localhost:3100` を叩く

**`recovery-loki-helper` は再利用しない。** 「SSH forced command経由の調査用だから」ではなく、**そもそも週次の窓を表現できない**ためである。

```
ALLOWED_COUNT_WINDOWS  = {5m, 10m, 15m, 30m, 1h, 3h, 6h, 12h, 24h}
ALLOWED_ERRORS_WINDOWS = {1h, 6h, 12h, 24h}
```

**最大24hで、7日を渡せない。** 使うには allowlist を広げるしかなく、それは**調査経路の認可境界そのものを変える**。ダイジェストの都合で触らない。

実装の形は次のとおり。

- monnie へ配る Python collector が **観測だけを行いJSONを返す**。判定・整形・通知はplaybook側が持つ(`skills/ansible-implementation-style`「check系shellの責務分離」)
- 通知は既存の `common_slack` を `slack_channel: info` で使う。**通知機構を新設しない**
- `--check` では `common_slack` が無条件に送信を抑止し、本文をdebugで表示する。AC6の通知側はこれで満たす
- **`uri` モジュールでform-urlencodedのGETをLokiへ送らない**(空queryが送られる既知のバグ)。collectorがPythonから直接叩くため該当しない

### 6.2 集計の粒度は `sum by (job, host, level)`

helper の `count` と同じ形にする。**level ラベルを持たない系列は `(no level label)` として同じ表に出す**(AC2)。

**日別内訳は入れない。** AC2の契約に無く、粒度を足すと最初から読まれない通知になる。必要になったら次の版で足す。

### 6.3 error全文の上限は、件数ではなく**文字数の予算**で持つ

実測はerror 7件/日、**週49件**である。件数で切ると50件では平常時ぎりぎり、20件では**毎週「省略しました」が出てAC2の「全文」が事実上死ぬ**。

- **合計6,000文字、かつ1行300文字**(1行の上限はhelperと同じ値)
- 予算を超えたら打ち切り、`N件中M件を表示、残りは省略` を本文へ明示する(AC3)

**6,000は保守的に置いた値で、根拠は薄い。** Slackのattachment textの実上限はrepoのどこにも記録が無く、**測っていない**。予算方式にしたのは、上限が分からなくても**こちら側で明示的に切る**ほうが「Slackに黙って切られる」よりAC3に忠実だからである。測れたら上げてよい。

### 6.4 実行時刻は **月曜 09:00 JST**(`0 9 * * 1`)

Notion「バッチ処理工程管理表」と突き合わせて選んだ。

| 区分 | 月曜09:00前後の状況 |
|---|---|
| 毎日 | 06:30(autonomous_recovery監視停止の警告)の次は12:00(Semaphore DB退避)。**空き** |
| 毎週 | 月曜は `fstrim` のみ。表は「月曜頃」としか書いていないため実測した — `OnCalendar=weekly` + `RandomizedDelaySec=100min` で**月00:00〜01:40**。**重ならない** |
| 毎月 | 1日00:05/00:10/00:35、2日18:15、10日20:00、28日18:30。**該当なし** |

**カタログへ足したら、Notionの表の「毎週」へも同じ行を足す**(時刻順の位置へ)。片方だけ更新すると、次に窓を選ぶ者が空いていると読む。
