## 2. 実装の骨格(requirement §6準拠、2026-09-04是正版)

- collector(`syslog-weekly-digest-collect.py`)はmonnie上で`http://localhost:3100`のLokiへ直接3種類のGETを行い、**観測結果だけをJSONで返す**。判定なし、非ゼロ終了なし(Loki問い合わせ失敗時も`ok: false`と`error`文字列を積んでexit 0 — 責務分離は`skills/ansible-implementation-style`「check系shellの責務分離」に従う)。
  - `sum by (job, host, level) (count_over_time({job=~".+"}[168h]))` — §6.2の集計粒度どおり。level無し系列は`(no level label)`。**`MAX_SERIES=500`(recovery-loki-helperと同値)で行数を切り詰め、`total_count`/`truncated`/`limit`を出力へ含める**(finding 1是正)。**`limit`フィールド(=`MAX_SERIES`定数の値そのもの)がSlack本文の「上限Nに到達」の唯一の情報源であり、`MAX_SERIES`定数はこのファイル1箇所にしか存在しない**(Coordinator再確認で二重化を指摘され是正、下記参照)。
  - `sum(count_over_time({job=~".+", level="error"}[168h]))` — error総数(正確な件数。下のentries一覧が上限で頭打ちになっても総数はこちらが正)。
  - `query_range` で `{job=~".+", level="error"}` の生ログ本文一覧。**`ERROR_QUERY_LIMIT`は300(recovery-loki-helperのQUERY_LIMITと同値)** — 是正前は2000であり、独立レビューが「既存helperの出力量制限を回避している」と判定、Coordinatorが受け入れて契約を訂正した(requirement §5)。1行300文字の切り詰めはここでも行うが、これは生データの流通量を早期に減らす予防策に過ぎず、AC3が求める「最終的に整形・マスクした1行を300文字以下にする」契約の判定点ではない(判定点はfilter側、下記)。CR/LF正規化はrecovery-loki-helperのcmd_errorsのC1修正と同じ理由で踏襲。
  - **fail-closed envelope検証(finding 3是正、1回目)**: 3つのqueryすべてで、Lokiの`status: "success"`・`data.resultType`(instant queryは`vector`、query_rangeは`streams`)・`data.result`がlistであること・count/timestampが数値としてparseできることを厳格に検証する`_validate_envelope()`/`_parse_count()`を新設した。**空の`result: []`は「本物の0件」として`ok: true`のまま許容するが**、`status`が`success`以外・`data`欠損・`resultType`不一致・`result`が非list・countや timestampが非数値・`metric`/`stream`/`values`が期待した型でない場合は、0やskipへフォールバックせず**そのqueryを丸ごとerror扱いにする**(`ok: false`)。旧版は`.get(...)`のデフォルト値経由で静かに0/[]へ倒れていた。
  - **fail-closedの残存クラッシュ経路の是正(finding 3是正、2回目、最重要)**: 再レビューがCoordinator側で`result: [null]`(vector要素がnon-object)を与えると`series.get(...)`/`result[0].get(...)`が`AttributeError`で未処理落ちすることを実際に再現し、加えて`_parse_count`の巨大指数・少数・負数、timestampの実在範囲、labelのstring型を「確認できていない」として名指しした。**依頼どおり、鵜呑みにも黙殺にもせず1件ずつ実機(python3で該当関数を直接叩く)で検証した**:
    - `result: [null]` → `series.get(...)`/`result[0].get(...)`が実際に`AttributeError`になることを確認。**修正した** — `collect_series`のループ先頭と`collect_error_total`の`result[0]`取得の直前に`isinstance(item, dict)`チェックを追加。
    - `_parse_count`の巨大指数(例: `"1e400"`) → `float("1e400")`はinfを返し例外にならないが、続く`int(inf)`が`OverflowError`になることを確認。**修正した** — `_parse_count`をinf/nan判定 → 負数判定 → 整数性判定 → `int()`の順に並べ替え、`int()`へは有限・非負・整数値であることを確認した後にしか到達しないようにした。
    - `_parse_count`の少数(例: `"3.7"`) → 例外にはならないがサイレントに`3`へ切り捨てていたことを確認。**修正した** — 非整数はmalformedとして拒否する(件数として意味をなさない値をそのまま出すのは、MAX_SERIES二重化と同種の「表示している数字が実際と違う」問題であるため)。
    - `_parse_count`の負数(例: `"-5"`) → 例外にはならないがそのまま`-5`として受理していたことを確認。**修正した** — 負のcountはmalformedとして拒否する。
    - timestampの実在範囲(例: `10**30`) → `int(ts_ns_raw)`自体は例外にならないが、後段の`datetime.fromtimestamp(ts_ns / 1e9, ...)`が`OverflowError`になることを確認。**修正した** — `collect_error_entries`が要求したquery window(`start`/`end`、前後300秒の余裕)を基準にした範囲チェックを追加し、範囲外のtimestampは`datetime.fromtimestamp()`へ到達する前にmalformedとして拒否する。念のため`datetime.fromtimestamp()`呼び出し自体も`try/except (OverflowError, OSError, ValueError)`で包んだ(境界チェックのロジックが将来誤って緩められた場合の保険)。
    - labelのstring型(例: `job`が文字列でなく数値・list・dict) → **2回目是正時、`str.format()`が暗黙に`str()`変換するため例外は発生しないことを確認し、「該当しない」と判定した。この切り分けは3回目是正で誤りと判明した**(下記参照)。
    すべての確認・修正内容は`roles/syslog_weekly_digest/files/syslog-weekly-digest-collect.py`のモジュールdocstringにも同じ一覧を明記した。**この一覧自体、3回目是正後も上記の撤回済み判断(「該当しない」)を現在形のまま残しており、後段の3回目是正コメントと矛盾していたことを5回目是正でCoordinatorが指摘した(Minor)。撤回の経緯と現在の対応を指す表現へ書き換えた**(このdocstring自身、上のこの文を含む)。
  - **「該当しない」判定の誤り、および大整数の丸めの是正(finding 3是正、3回目、Coordinator再現)**: 2回目是正時の「labelのstring型はstr.format()では落ちないので該当しない」という判定について、**Coordinatorが`metric.job`にint/strが混在するsuccess envelopeを与えると`rows.sort(key=lambda r: (r["job"], r["host"], r["level"]))`が`TypeError: '<' not supported between instances of 'int' and 'str'`で例外終了することを実際に再現した。** 誤りの本質は「format で落ちるかだけを見て、その値が sort を通ることを見ていなかった」ことであり、教訓として本節へ明記する: **指摘が当たっていないと判定するときは、指摘された経路だけでなく、その値が通る経路全体を見る。** 実際に確認して修正した — `collect_series`で`job`/`host`/`level`それぞれに`isinstance(..., str)`検証を追加し、`rows.sort()`へ到達する前に非string値をmalformedとして拒否する経路にした。

### 3.3 IPアドレスの扱いと秘密情報の契約(requirement §3・§5、2026-09-04是正・再確定)

error全文は生のLokiログ本文であり、送信元次第でIPv4リテラルを含みうる(Sophosのdrop行等)。**job/hostラベルもIP形式でありうる**(実測: network-devicesのAP/スイッチはhostラベルにIPアドレスを使うことがある — 独立レビューが「series/no-levelのjob・hostが無加工」と指摘した箇所)。**送信前に一律でマスクする方針**(`filter_plugins/syslog_weekly_digest.py`の`syslog_weekly_digest_redact_ipv4`、正規表現`(?<!\d)(?:\d{1,3}\.){3}\d{1,3}(?!\d)`を`[ip-redacted]`へ置換)は維持したが、**適用箇所を是正した**。

旧版はマスク対象を`entry.line`だけに適用し、series表・no-levelテーブルのjob/hostは無加工のままSlackへ渡していた。新版は`syslog_weekly_digest_render_message()`内で、series行・no-level行・error行のjob/host/line**すべて**をフォーマット時にマスクし、さらに組み立てた最終メッセージ全体にもう一度同じフィルタを通す(冪等な正規表現なので二重適用しても安全)。これは「個々のフィールドをマスクし忘れた場合の単一の取りこぼし防止層」であり、独立レビューが求めた「Slackへ渡る最終メッセージ全体を一箇所でsanitizeする」の実装でもある。

マスクの理由: (1) `feedback_no_ip_in_repo.md`はpublic GitHub repo自体への記載を対象とし、Slack #info への送信は文字どおりの対象外だが、Slackの内容は後からexport・スクリーンショット・転記されうる。(2) このrepo全体がIPリテラルを一切書かない運用を徹底しており、通知本文だけ例外にすると一貫性が崩れる。

既知の限界(`test_filters.py`の`test_known_limitation_version_like_4tuple_is_also_redacted`で意図的に固定): 単純な正規表現なのでIPv6・意図的な難読化は検出できず、逆にドット区切り4つの数値からなるバージョン文字列(例: ライブラリのバージョン表記)も誤ってマスクする。**見逃しより過剰検出を選んだ**(誤ってマスクされても情報損失は軽微だが、見逃すとIP露出が起きる)。

collector側では行わず、tasks/filter側(整形層)で行う設計は維持した — collectorは観測のみという責務分離に合わせ、`collect_error_entries()`が返す`line`は無加工の生データのまま(`test_collector.py`の`test_collector_returns_ok_and_expected_shape`で明示的に検証)。

**秘密情報一般(IPv4以外)の契約は、独立レビューの再指摘を受けてYoshinobuが確定した(2026-09-04、EXEC-030)**: 1回目是正の実装記録は「実装可能なallowlist/redaction契約の定義は本案件の範囲を超える、Coordinatorが受け入れ」としていたが、再レビューが「requirement §5を変更していない限り、実装記録の記載だけでは契約の未充足を解消できない」と指摘した。これを受けてYoshinobuがrequirement §5を書き換え、**「秘匿の保証は機械的に検出できるIPv4リテラルに限る。IPv4以外のcredential/tokenがerror本文に混じって#infoへ出る可能性は残存リスクとして受容する」**と明記した(安全境界の緩和はEXEC-030によりYoshinobuの判断事項、Coordinatorが受容してよい範囲を超えるため)。

**この実装(IPv4一律マスク+最終メッセージへの防止層の二重適用)は、変更なしにこの契約をそのまま満たす。** 追加の秘密検出は実装していない — 「範囲外だから実装しない」のではなく、「requirement §5がIPv4限定であると明示的に定めたので、実装済みの内容がそのまま契約充足そのもの」という状態である。`filter_plugins/syslog_weekly_digest.py`のモジュールdocstringと本節を、この確定した契約を指す表現へ書き直した(旧「Coordinatorが受け入れ、実装記録に残存リスクとして明記」という表現は、契約自体が未決着だった1回目是正時点のものであり、現在は不正確)。

**残存リスクとしてrequirement §5に明記された内容(実装側の対応は不要、記録として維持)**: 上記のマスクはIPv4アドレスのみを対象とし、ログ本文に含まれうるIPv4以外の秘密情報(credential・token等)は一切検出・マスクしない。万一syslogにIPv4以外の秘密情報が記録された場合、それはマスクされずSlack #info(と、そこから波及するexport/転記先)へ到達しうる。これはrequirement §5がYoshinobuの判断で受容すると明記した残存リスクであり、実装で埋めるべき欠落ではない。

### 3.4 remoteホストへ永続ファイルを置かない設計

`ansible.builtin.copy` + `ansible.builtin.command`(`monitoring_healthcheck`と同じ形)ではなく、**`ansible.builtin.script`を使い、monnie上に恒久的なscriptを残さない**設計にした。requirement AC7「本playbookは状態を変えない」を文字どおり満たすため — 冪等なscript配置(`monitoring_healthcheck`が採る形、TS-027が許容する副作用)より一段強い選択で、置かなくて済むなら置かない。

### 3.5 ローカルreportファイルを保存しない

`monitoring_healthcheck`や`proxmox_snapshot_check`はcontroller側へJSON reportを保存するが、本roleはそれを行っていない。requirementのAC群に保存要件が無く、`time_sync_check`(同じsafe-readonly収集系)もreportを持たない前例があるため、まずはSlack通知だけの最小構成にした。**必要になれば追加できる設計**(collectorのJSON出力自体は既に保存に足る形をしている)。
