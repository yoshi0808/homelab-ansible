# PMO役の退役と、体制の作り直し(2026-07-28)

状態: **決定**。Coordinatorが決定、Yoshinobuが体制の最終決定をCoordinatorへ委ねる旨を明示(2026-07-28)。

**適用は次の案件から。** 進行中の `incident_auto_capture`(`_spool/` のACL mask切り詰め)は**現行体制で完走する** — 走行中に体制を入れ替えると、その案件の実績が新旧どちらとも比較できなくなる。見積もり単位の変更で採った扱いと同じ。

前提となる記録: `2026-07-27_001_retrospective.md`(PMO新設の根拠)、`2026-07-27_002_review_pmo.md`、および `docs/ai/reviews/incident_auto_capture/` 一式(PMOの唯一の実走)。

## 何を変えるか

| 項目 | 旧(2026-07-27〜07-28) | 新 |
|---|---|---|
| 計画レビュー | PMO(技術判断を禁止、数と手続きのみ) | **2人目のTech Lead**。数えられる基準に加え**技術的前提の反証**まで行う |
| 走行中の工程管理 | PMOが CP1〜CP4 を定期的に点検 | **廃止。** 事象駆動のエスカレーション(逸脱・ブロック・波及)はCoordinatorが受け、必要ならTech Leadへ再照会する |
| 並行幅・単位の決定 | PMOの基準1・2として計画レビュー内で判定 | **Coordinatorが計画受領時に1回だけ適用するゲート**(`docs/ai/roles/coordinator.md`) |
| 案件クローズ | PMOの CP5 | **Auditor**(新設)。repoの成果物しか読まないコールドスタートの読み手 |
| PMO役 | 存在 | **退役。** `docs/ai/roles/pmo.md` と `.claude/agents/pmo.md` は削除(履歴はgitが持つ) |

## なぜ変えるか

### 1. PMOは、自分が作られた理由の問題を解けなかった

PMOの存在根拠は「Coordinatorには見えない逸脱を外から見る」ことだった(`2026-07-27_001` — 工程逸脱3件がいずれもCoordinator自身には検出できず、すべてYoshinobuの問いかけが起点だった)。

**2026-07-28の初回実走で、同じことが起きた。** 実行フェーズ中に `progress.md` が放置され、PMOの入力が空になっていた事実を検出したのは**Yoshinobu**である。PMOがCP2でそれを報告できたのは、**Coordinatorが依頼文へ「放置されていた」と書いて渡したから**にすぎない。PMOは検出していない。

しかもこれは構造的に不可避である。**PMOの入力は `progress.md` ただ一つで、壊れていたのがその `progress.md` だった。** 入力が壊れている状態を、その入力しか読めない役は検出できない。自己点検問題は解決ではなく**移動**した。

### 2. 実質的な誤りは、すべて技術Roleが捕まえた

同案件でCoordinatorおよび計画に実際に存在した誤りは3クラス。

| 誤り | 捕まえた者 |
|---|---|
| Coordinatorの因果仮説(真因は別だった) | **Tech Lead**(実測で反証) |
| 計画の技術的引用の誤り2件(`file.py` の論証反転、`command` のcheck mode挙動) | **Implementer / Reviewer**(現物確認) |
| Q-U2-1の根拠が事実に反していた | **Reviewer** |

PMOが返した findings 4件(P-1〜P-4)は**すべて記録の整合性**であり、判断ではない。PMOは技術判断を禁止されているため、上の3クラスには構造的に触れられない。

**PMO新設の前提は「Coordinatorの技術判断は独立レビューを通って1件も覆らなかった」だった。** 2026-07-28にはそれが2回覆っている。前提が1案件で崩れたとは言わないが、少なくとも自明ではなくなった。危険度は、記録の齟齬より誤った因果のほうが高い(後者は違うファイルを直す結果になる)。

### 3. 仕事の一部が自己生成していた

PMOのfindings 4件はすべて `progress.md` に関するもので、**`progress.md` はPMOのために存在する成果物**である。PMOが居なければあのファイルは要らず、あの4件も発生しない。

### 4. 人間のPMOが管理しているものが、この環境には存在しない

| 人間のPMOが要る理由 | この環境 |
|---|---|
| 状況が非同期で不可視。報告がないと分からない | subagentは数分で終わり、完全な報告が自動で届く |
| リソース競合(誰がいつ空くか) | 競合が無い。制約はCoordinatorのコンテキストのみ |
| 人は忘れる・病む・辞める。継続性の管理者が要る | 各agentはコールドスタートで**そもそも記憶を持たない設計** |
| コミュニケーションが不完全で遅い | 構造化された1回の受け渡し |
| 誤った計画の損害が数か月 | 約10分と再実行 |

残るのは**Coordinatorのコンテキスト劣化と盲点**だけであり、それは対等な常設監視役より別の道具が要る(→ Auditor)。

### 5. 費用が案件規模に比例しない

PMOは3回で9.7分、案件全体51.4分の**18.9%**を占め、システムを変える成果物はゼロだった。費用はチェックポイント単位でほぼ固定のため、**小さい案件ほど割高**になる(Tier 4規模=194分なら同じ3回で約5%)。

## 何を失うか(受容するリスク)

**`pmo.md` §6「Coordinatorの工程遵守の点検」を常設で行う者が居なくなる。**

受容する理由は、上記1のとおり**それが実際には機能していなかった**ため。代替は3つで、いずれも完全ではない。

1. **計画受領時のゲート**(Coordinatorが1回適用)— 着手前の1点に集中させる。走行中は見ない
2. **2人目のTech Leadによる計画査読** — 技術と手続きの両方を見られる
3. **Auditorによるクローズ時の受入** — 「この記録だけで再構成できるか」を問う。記録が次セッションへの唯一の引き継ぎである以上、ここが本当の受入検査になる

**残る穴**: 走行中のCoordinatorの逸脱は、依然としてYoshinobuの問いかけか、Auditorの事後検出でしか見つからない。**これは既知の残存リスクとして受容する。** 2026-07-27の設計はこの穴を埋めようとして常設役を置いたが、埋まらなかったうえに費用が付いた。事後検出のほうが安く、実効も劣らないと判断する。

## Auditorの位置づけ

PMOの**コールドスタート設計だけを継承**し、常設の工程管理を捨てた形。詳細は `docs/ai/roles/auditor.md`。

- 入力は**repoの成果物のみ**。Coordinatorの説明を受け取らない(受け取ると自己申告の清書になる。PMOの失敗がこれ)
- 問いは「**この記録だけで何が起きたか再構成できるか、辻褄は合っているか**」
- 起動は**案件クローズ時の1回**
- 技術的な正否は判定しない。ただし**記録どうしの矛盾**は技術内容であっても指摘する(それは読解で分かるため)
