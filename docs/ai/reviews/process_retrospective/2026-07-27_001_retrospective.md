対象: 2026-07-27の1セッション。案件は `status.md` 新設(Tier `1+R`)、障害の自動捕捉Step 1(Tier 4 + W6のTier 3)、commit前ゲートの既存欠陥修正4件。

## 4. 原因の構造

### 4-1. 上流が薄く、製造に手戻りとして現れた

Implementerの差し戻しは `capture.yml` だけで5回。うち2回はCoordinatorの指示の誤りと仕様の詰め不足が直接の原因である(`include_tasks` に `become` を付けるよう指示したが仕様上不可能、記録フィールドの妥当性を実装中に発見)。

**上流で決めなかったものが、製造の往復として計上されている。**

### 4-2. 工程で分けたが、機能で分けていない

Tech Leadの分解は W0(観測)→ W1(捕捉)→ W2(レビュー)→ W3(収集器)→ W4(レビュー)→ W5(テスト)という**フェーズの直列**だった。機能単位の並行ではない。

本来の切れ目は次のとおりで、**A と B が触れ合うのは spool レコードのスキーマだけ**である。先にインターフェースを固定すれば並行できた。

```
[設計] spoolレコードのスキーマを確定
   ├─ A: 捕捉(notify.yml + capture.yml) → UT
   └─ B: 収集器(spool + Semaphore → バンドル) → UT   ← 並行可能
[結合] A と B を繋いで検証
```

密結合だった証拠が3つ残っている。

1. **Bの実装者はAの「実装」を読んで契約を学んだ。** Coordinatorの依頼文が「`capture.yml` があなたの入力契約です」と書いている。仕様書ではなく実装が契約になっており、A の完成までB は着手できなかった
2. **インターフェースの決定が実装中に発生した。** 記録フィールドの採否は A の実装中に論点化し、後から requirement へ「W3はこれを入力契約として扱え」と追記した
3. **一度決めた契約を後で覆した。** ADR-004 は「T1はIDを決めない、収集器が確定する」と決めたが、R6(相関ID)で T1 側にIDが要ると判明し、spool ID を footer に載せる形へ変更した。**IDの所有者というインターフェースの中核**を、設計時に決めて実装後に覆している

### 4-3. 方法論を指定したぶんが、質問として返ってきた(反響仮説)

Yoshinobu提示の仮説「方法論を語れば、それがこだまのように帰ってくる」を、当日の差し戻し記録で検証した。

| 差し戻し | Coordinatorが方法を指定したか |
|---|---|
| `include_tasks` に `become`(仕様上不可能) | **指定した**(かつ誤っていた) |
| 記録フィールドが無意味 | **指定した** |
| include の block/rescue が構文エラーを救えない | **指定した** |
| footer の fact タイミング問題 | **指定した**(`footer:` という機構を選んだ) |
| spoolレコードの消費方式(削除か移動か) | **指定しなかった**(「決めて根拠を残せ」) |

**指定した4件は全て往復が発生し、指定しなかった1件は発生しなかった。** 仮説を支持する。

さらに悪循環があった。**失敗するたび指示を細かくした**ため、後半の依頼文は1本1,500語規模になり、反響がさらに増えた。

### 4-4. リセットされない唯一の役に、すべてが集中した

subagentは起動→終了で状態が0に戻る鋸歯状だが、Coordinatorだけが単調増加する。したがって:

- 増分をまたいだドリフトに気づけるのは Coordinator だけであり、**同時に Coordinator のドリフトに気づける者がいない**
- subagentは横方向に連携できず、全ての調整が Coordinator を経由する。**agentを1体増やすことは Coordinator の負荷を増やすこと**であり、「リソースは無尽蔵」は成立しない

**そして工程規律の逸脱は、コンテキストが50万を超えた後半に集中している。**

| 逸脱 | 時期 |
|---|---|
| Tier判定を明示した(`1+R`、Tier 4) | 前半 |
| Tech Leadを立てた | 前半 |
| **Tier判定を省いた(W6)** | **後半** |
| **Tech Leadを飛ばした(W6)** | **後半** |
| **Tech Leadが分けた線を再合成した(W6)** | **後半** |

**負荷と規律の劣化に時系列の相関がある。**

## 5. 検出経路の偏り

Coordinator自身の工程逸脱3件は、**いずれもCoordinatorには検出できず、すべてYoshinobuの問いかけが起点**だった(「w6の指示書は君が書いたものだよね?」等)。

一方、**実装の欠陥は独立レビューがよく捕らえている**(6本でCritical 3件)。

**実装は5回レビューされ、計画は0回レビューされた。** 参照モデルで要件定義・基本設計が日程35%を占めるのは、そこに高単価人材によるレビューサイクルが入っているためであり、今日の工程にはそれに当たるものが一切なかった。

## 6. 結論(次に変えること)

1. **上流に配分を寄せる。** 抑制ではなく配分。工程が重かったこと自体は誤りではない(Criticalが3件出て、うち2件は本番直前だった)。誤りは**重さを選んだ自覚と配分の根拠が無かった**こと
2. **見積もりを作る。** Tech Leadが出し、Coordinatorが妥当性を問う。実績を `docs/ai/effort-baseline.md` に蓄積し、次回の基準にする
3. **計画をレビューする工程を作る。** 実装だけ5回見て計画を0回は配分として破綻している
4. **機能で分け、インターフェースを実装より先に固定する。** 疎結合な切れ目でUTし、結合テストで繋ぐ
5. **依頼文には「何を満たすか」を書き、「どう作るか」を書かない。** 形を縛る必要がある場合はADRを参照させ、本文へ転記しない。反響を減らし、Coordinatorの負荷も直接下がる
6. **並列化の判断軸を「Coordinatorを経由するか」に置く。** 経由するものは並列化しても速くならない
7. **増分の切れ目でチェックポイントを置き、実績を測る。** コンテキスト増加率が平坦なら計画が足りていない信号として扱う
8. **計画外事象の扱いを規定する。** 局所収束なら流す/他工程へ波及するなら影響する工程だけ止める/逸脱10%超なら再計画。今日は4件中3件が結果的に基準どおりで、W6のみ基準違反だった

## 7. 未解決

- **PMO(工程管理役)の新設可否。** 責務は工程の組み立て・進捗確認・課題管理・逸脱検出、そして**Coordinatorの工程遵守の点検**。技術は一切解かない。§5のとおりCoordinatorの失敗は手続き側に集中しており、技術を解かない役とは守備範囲が補完する。ただし「見積もりの妥当性を技術を解かずに判断する」は過去実績の蓄積を要するため、第1段では持たせない。体制変更のためYoshinobuの承認事項
- **依頼文のSkill化。** 今日8本を書き、毎回同じ骨格(並行作業の境界、禁止事項、自己検証、報告形式)を書き直した。再利用可能な型として固まっている
- **Coordinatorを増分の切れ目で `/clear` する運用の実地検証。** 今日 `status.md` と案件フォルダを整備したにもかかわらず、439ターン一度もリセットしなかった。リセットを安全にする道具を作った当人が使っていない
