状態: **決定**。Yoshinobuが「人間が考える分担方式よりAIにとって最適な分担方法」を提案するようCoordinatorへ依頼し、Coordinatorの提案(本ファイル§2〜4)に「合っています。進めてください」と承認(2026-07-29)。

前提となる記録: `2026-07-28_003_pmo_retirement.md`(PMO退役)、`docs/ai/effort-baseline.md`(3件の実績データ)、同日のCoordinator自己レビュー(本会話で`core.md`・`role-routing-index.md`・`auditor.md`・`role-context-matrix.md`・`status.md`・auto-memory中の欠陥計6件超を検出・修正)。

## 1. 何を変えるか

| 項目 | 旧(〜2026-07-29) | 新 |
|---|---|---|
| 要求分解・ADR・リスク整理・見積もり | **Tech Lead**(subagent、案件最初に1回起動) | **Coordinator自身**が直接行う |
| 計画査読(層1=数える、層2=技術的前提の反証) | **別体の2人目のTech Lead** | **Reviewer**(`docs/ai/roles/reviewer.md`「計画査読」) |

| Implementer / Tester | Tech Leadの計画を受けて起動、Tech Leadへ返却 | **Coordinatorの計画を受けて起動、Coordinatorへ直接返却**(実質は既存の`+R`と同じ経路に統一) |
| Auditorのクローズ受入 | 変更なし | 変更なし |
| Tech Lead役 | 存在(`docs/ai/roles/techlead.md`、`.claude/agents/techlead.md`) | **廃止・削除**(履歴はgitが持つ) |

## 2. なぜ変えるか

### 2-1. 独立性が効くタスクと、蓄積文脈が効くタスクは別物である

Reviewer / Tester / Auditorが機能しているのは、**入力(diff、実ホストの状態、repoの成果物)が既に確定しており、コールドスタート(前提を持たない視点)がむしろ利点になる**検証タスクだからである。書いた本人が見落とした矛盾は、前提を共有しない読み手のほうが気づきやすい。

Tech Leadは逆の性質を要求される役だった。**曖昧な要求から構造(単位分解・インターフェース・見積もり)を合成する仕事**であり、これはセッションを通じて蓄積した文脈(実測値、Yoshinobuとのやり取り、過去の発見)が多いほど質が上がる。ところが`docs/ai/roles/techlead.md`(旧)が自ら記していた通り、**Tech Leadは案件の最初に1回だけ起動され、構造的に最も情報を持たない役でありながら計画を担う**設計だった。最も文脈が要る仕事を、最も文脈を持たない者にやらせていた。

### 2-2. 実測データが非対称を裏付けている

`docs/ai/effort-baseline.md`の2026-07-28(3件目)の記録: 「**ずれたのは製造(Implementer)だけで、レビューと検証はほぼ見積どおり**」(製造2.4〜4.4倍、レビュー0.90〜1.10倍)。検証系タスクは予測可能、計画・実装系タスクは予測不能という非対称が数字で出ている。

### 2-3. この会話自体が生きた実例だった

2026-07-29、Yoshinobuの依頼でCoordinatorが自らの規範文書群を再点検した結果、2026-07-28以降ずっと存在していた欠陥(Auditor起動条件と検査項目の自己矛盾、逸脱10%表記の不統一、core.mdの秘密情報記述の禁止列挙、auto-memory内の権限機構記述の食い違い)が複数見つかった。**いずれも人間が明示的にメタレビューを求めるまで、案件を経由する形では誰も検出していなかった。** Tech Lead・PMOのような「案件の入口で1回だけ計画を作る/点検する」役では構造的に拾えない欠陥クラスがあることの傍証である(この残存リスクは§4で扱う)。

## 3. 何を失うか(受容するリスク)

- **Tech Leadが担っていた「機能で分け、インターフェースを実装より先に確定させる」という規律**は、Coordinator自身が計画を書く際に引き続き守る必要がある。担い手が変わるだけで、規律自体は`docs/ai/roles/coordinator.md`へ引き継ぐ。
- **Tech Leadのコールドスタートが案件フォルダの自己文書化をテストする効能**(`docs/ai/roles/coordinator.md`旧「Coordinatorが起点になって切った増分では、Tech Leadを立て直す」)は、代替としてReviewerの計画査読を**初回だけでなく増分ごとに**適用することで引き継ぐ(Reviewerも都度コールドスタートするsubagentであるため、同じテスト効果を持つ)。
- **並行幅の確保はImplementerの複数並列起動で維持する。** Coordinator自身が実装まで抱えると`docs/ai/roles/coordinator.md`「実行フェーズでCoordinatorが忙しいのは、計画が仕事をしていない信号である」という既存原則に反するため、Implementerへの委任自体は維持する(Tech Leadの廃止とImplementerの廃止は別問題)。

## 4. 残る穴(既知の残存リスクとして受容)

**規範文書そのものが、案件を経由せずに古くなる問題は、この再設計だけでは解けない。** Auditorは案件クローズ時にしか起動しないため、案件が動いていない期間の規範ドリフトは拾えない。2026-07-29の本会話が唯一の検出手段だった。

対応は本件のスコープ外とし、`docs/ai/status.md`のNextへ着手候補として起票する(月次Knowledge振り返りの拡張、または規範文書間の突合を定期的に自動でかける仕組みの要否)。
