## S1 — JSON と MD の一時的不整合(案件A、既存 `write_artifact()` の性質)

**受け入れる(是正しない)。**

1回の起動で `write_artifact()` が2回呼ばれるため、JSON を書き替えてから MD を書き替えるまでの間、両者が食い違う瞬間がありうるという指摘。

- **今回の変更が作った性質ではない。** `write_artifact()` が JSON と MD を別々に書くのは元からで、本 diff はその呼び出しを1回増やしただけである。直すなら「2ファイルを1つの原子的単位として書く」機構の新設になり、本案件(計測の追加)の scope を超える。
- **不整合の窓が観測へ与える害が小さい。** 読み手は人か Coordinator であり、**JSON が正本**である(MD は R5 で「人が読む側にだけ出ないのは避ける」ために足した写しにすぎない)。窓の中で読んでしまった場合も、JSON を見れば正しい。
- **重要な不変条件のほうは崩れていない** — 「成果物 JSON が存在すること = 調査済み」(IC-039)は、`os.replace` による原子的置換で保たれることを Implementer・Reviewer の双方が独立に確認している。**再調査を誘発する壊れ方はしない。**

## S2 — `notification.attempted` が現状つねに `true` で情報量がない(案件A)

**受け入れる(フィールドを残す)。**

指摘は正しい。現在の呼び出し構造では `post_artifact_actions()` が必ず試行するため、`attempted` は定数である。それでも残す理由は1つ。

**`sent: false` だけでは「試みて失敗した」と「試行そのものが走らなかった」を区別できない。** これはこの案件が扱っている問題そのもの — 「鳴らない」が正常と故障の両方を意味する状態 — の再生産である。将来 `post_artifact_actions()` の手前に抑止条件が入ったり、例外の捕捉範囲が変わったりして試行が走らなくなったとき、**そのときに初めてスキーマを変えるのでは、まさに知りたい最初の1件が記録されない。**

つまりこのフィールドは、想定される機能追加のためではなく、**この計測自身が壊れたことを検出するため**に置いている。次に読む人が「常に true だから消してよい」と判断しないよう、この判断をここに残す。

## S3 — 修正が「両 playbook が同じディレクトリ深さにある」ことに暗黙依存する(案件B)

**受け入れる(是正しない)。**

`{{ playbook_dir }}/../roles/...` という形は、include する playbook が `playbooks/` 直下にあることを前提とする。

- **この diff 固有の弱点ではない。** リポジトリ内で同じ形を採る箇所は他に8つあり(`recovery_push/tasks/drill_setup.yml` を含む)、`playbooks/` 直下にすべての playbook を置くというリポジトリの構造そのものが前提を支えている。
- ここだけを構造非依存にすると、**同型の他8箇所と書き方が割れる**。割れたほうが、次に読む人にとっての危険が大きい。
- 前提が崩れるのは「playbook をサブディレクトリへ移す」変更のときであり、そのときは8箇所すべてが同時に壊れる。**1箇所だけ生き残る形にしても救いにならない。**
