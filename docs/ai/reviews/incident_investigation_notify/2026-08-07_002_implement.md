### 3-1. R4: 記録する文字列に秘密が入るかの実測、および`reports/`のGit管理範囲

**手順**: 本番の`playbooks/incident_investigate_notify.yml`を一切変更せず、decoy inventory(`/tmp/.../decoy/inventory/hosts.ini`、`ansible_connection: local`)と、実webhookを含まないdecoy `vars/slack.yml`(平文、vault不使用)を用意し、`cwd=/home/yoshi/homelab-ansible`から実際に`ansible-playbook`を起動して観察した。

1. **`community.general.slack`モジュールの罠を発見**: モジュールは`domain`引数を`validate_slack_domain()`で強制的に`slack.com`/`slack-gov.com`のいずれかへ丸め込む(`/usr/lib/python3/dist-packages/ansible_collections/community/general/plugins/modules/slack.py:386-387`)。つまり**decoyの`vars/slack.yml`にどんなURLを書いても、`token`にスラッシュが2個以上含まれる限り実際の接続先は常に本物の`hooks.slack.com`になる**(接続先を`vars`側だけで偽装できない実装)。最初の試行(token=偽URL全体)は実際に`hooks.slack.com`へ到達し、302を受けてモジュールが`ok`と誤判定する事故を自分の手元で再現した(`docs/ai/core.md`「decoyが成立していると仮定しない」の実例)。**この罠は本件のためだけに踏んだものであり、本番コードには影響していない**(通知playbook・webhookの扱いは一切変更していない)。
2. 対策として、token側のバリデーション自体で**ネットワークに一切出ない**ローカル失敗を作った(`token`にスラッシュを含めない文字列を渡すと、`do_notify_slack()`が`domain`未設定を理由に`module.fail_json()`する分岐に入る — `slack.py:429-433`)。これで本番の`playbooks/incident_investigate_notify.yml`(無変更)を実際に失敗させ、かつ実Slackへは一切到達しない検証ができた。
3. 実測結果(rc=2、実際のコマンド出力は本ファイルに転記しない):
   - **stdoutに全ての詳細が出る**(`[ERROR]: Task failed: Module failed: Slack has updated its webhook API...`という定型メッセージ、および最終的な`fatal:`行)。
   - **`fatal:`行は`{"censored": "the output has been hidden due to the fact that 'no_log: true' was specified for this result", "changed": false}`のみ**——送信taskの`no_log: true`(既存、変更なし)がAnsible callback側で正しく機能しており、payload・token等は一切表示されない。
   - **stderrは完全に空**。
   - 別途`-vvv`で確認したところ、`community.general.slack`の`token`引数自体が`argument_spec`で`no_log=True`(モジュール実装側、`slack.py:465`)を持ち、taskの`no_log`指定の有無に関わらず`invocation.module_args.token`は常に`"VALUE_SPECIFIED_IN_NO_LOG_PARAMETER"`に伏字化される。またモジュール自身の`fail_json`もwebhook失敗時にtoken部分を`"[obscured]"`に置換してから文字列化する(`slack.py:449-452`)——**二重の保護**がモジュール側に既にある。
4. 上記から、`send_investigation_notification()`が投げる`RuntimeError(f"notify playbook rc={result.returncode} stderr={result.stderr.strip()!r}")`の`stderr`部分は、**現行の`incident_investigate_notify.yml`が起こしうる現実的な失敗(タスク失敗全般)では構造的に空文字列になる**ことを確認した。したがって`str(e)`として記録される内容に秘密情報が含まれる余地は無い。
5. 別の失敗系統として`subprocess.TimeoutExpired`(通知playbookが`notify_timeout_s`を超過)も検証した(§3-3 AC5)。`TimeoutExpired.__str__()`はコマンド配列(`ansible-playbook`のパス・playbookの相対パス・`-e @<一時ファイルパス>`)とタイムアウト秒数のみを含み、payload本体(一時ファイルの中身)は含まれない——ペイロード自体もJSON一時ファイルへ書いてパスだけを`-e @<path>`で渡す既存の設計(`skills/ansible-implementation-style/SKILL.md`の作法どおり)のため、コマンドライン自体に秘密は乗らない。
6. **一つだけ注意点として記録する**: 自分のテストハーネス用decoy playbook(inventoryもansible.cfgも無い最小構成)を`ansible-playbook`に直接渡した場合、`[WARNING]: No inventory was parsed...`という**Ansibleエンジンレベルの警告がstderrに出る**ことを確認した(§3-3のAC2実行ログで観測)。これは変数展開前のエンジン警告であり秘密を含まないが、「stderrは常に空」という言い方はしない——**実際にstderrへ何かが出ることはあり得るが、それは設定/inventory起因の一般的な警告であり、task結果(no_logで保護される領域)とは別の系統である**という区別を残す。本番の`repo_dir`は`ansible.cfg`でinventoryが設定済みのため、この警告自体は本番では発生しない。
7. **`reports/`のGit管理範囲**: `git check-ignore -v reports/incidents/_investigations/foo.json` → `.gitignore:5:reports/incidents/`にマッチ(exit 0)。`git ls-files reports/`は`reports/radius-health/`配下の2ファイルのみを返し、`reports/incidents/`配下は0件——このディレクトリ全体がGit管理外であることを確認した(既存の`.gitignore`、今回変更していない)。

**結論(R4)**: 現行実装のまま`stderr`を記録先に選んでも秘密漏洩の経路は無い(モジュール側no_log + task側no_log + stderr自体が空、の三重防御)。ただし念のため`record_notification_result()`では`redact_ipv4()`(既存のLLM出力向け機構、IC-040)をこの文字列にも適用し、二次防御とした(IPv4リテラルが混入する具体的な経路は見つかっていないが、コストが低く既存パターンの再利用のため採用)。

### 3-4. R6: `schema_version`を上げるかの判断

**調べた範囲**:
- `roles/incident_investigate/files/incident-investigate.py`自身 — `artifact_already_exists()`は`os.path.isfile()`のみでJSON内容もschema_versionも見ない。
- `roles/recovery_exec/files/incident-bundle-helper`の`show-investigation`サブコマンド(`investigation-show`が最終的に到達する実体) — `cat -- "$path"`のみで、JSONのparseもフィールド検査も一切行わない生byte転送。
- `roles/dev_investigate/files/recovery-investigate-dispatch-quory.sh`の`investigation-show`分岐 — id/拡張子の正規表現検証のみ(`BUNDLE_ID_RE`・`md|json`)、成果物の中身には触れない。
- リポジトリ全体を`grep -rn "schema_version"`で横断 — ヒットしたのは(a)この成果物自身を書くコード3箇所(callback plugin・本ファイル×2箇所)、(b)`incident_sync`(既に退役)関連のPhase 2実装記録、(c)`docs/ai/reviews/incident_auto_investigation/2026-07-31_007_test_result.md`と`docs/ai/reviews/incident_investigate_trigger/2026-08-01_006_post_deploy_observation.md`——いずれも**一度きりの検証記録**(Tester/Coordinatorが手元でPythonのワンショットスクリプトを書いて突合した記録)であり、リポジトリに存在する継続稼働のコードではない。
- `roles/recovery_exec/templates/AGENTS.md.j2`(Codexが読む一次調査プロンプトの周辺文書)——`_investigations/<id>.{md,json}`への言及はあるが、フィールド集合やversionを検査する記述は無い。

**判断**: 成果物JSONを機械的にparseして厳密な検証(必須フィールド集合の一致・version番号の分岐)を行う、**継続稼働の読み手は見つからなかった**。唯一そうした検証をしていたのは、過去に人手/subagentが実施した一度きりの確認スクリプトであり、しかもそれらは「追加フィールドを拒否する」性質ではなく「必須フィールドが揃っているか」を見るものだった(今回はキーを追加するだけで既存14キーの意味・型はいずれも変えていない)。

→ **`schema_version`は1のまま据え置く**(R6充足)。将来、既存キーの意味を変える・必須キーを削る変更が入るときは、その時点で読み手を再度調べ直すべきこと(この判断は「今回追加した1キーについて」のみ有効)を明記しておく。
