# requirement: 一次調査結果のSlack通知と、quory→ansy同期の即時実行

日付: 2026-08-01
状態: **確定**(2026-08-01、Yoshinobuとの対話で要件・チャンネル・方針を確定)
関連: `docs/ai/adr/009-per-incident-investigation-runtime.md`(b) b-2 が予告していたSlack報告の実装。`docs/ai/policies/incident_capture_policy.md` §3.5 / §4

## 1. 問題定義

一次調査は2026-08-01に本番稼働へ入り、Semaphoreジョブの失敗ごとに `reports/incidents/_investigations/semaphore-<id>.{json,md}` を書いている。**しかし結果はどこにも通知されず、人が見に行かなければ存在に気づけない。**

これは当初の期待とずれている。2026-07-31のIncidentの発端は「エラーなら追ってCodexから原因が通知されると思ったが来ない」だった。起動契機の欠陥は解消したが、**通知が無いという意味では同じ「来ない」が残っている。**

あわせて、証拠と成果物がansyへ渡るのは毎時 :07 の同期であり、**通知を受け取ってから最大1時間、開発側は現物を読めない。**

## 2. ゴール

Semaphoreジョブの失敗が一次調査まで到達したら、**その結果がYoshinobuに届き、かつその時点でansy側に現物が揃っている**状態にする。

Yoshinobuはその通知を見て、**開発側へ調査を依頼するかどうかを判断する。**

## 3. 非ゴール

- **調査依頼そのものの自動化**(R15)。2026-08-01にやらないと決定済み。通知は判断の材料までで止める。
- **依頼された後の調べ方**(開発側がansyからどう調査するか)。別途扱う。
- **通知の集約・抑制・重要度の出し分け。** 状況をそのまま出す(2026-08-01 Yoshinobu)。**繰り返す事象は隠すのではなく、原因を取り除く対象として見えている方がよい。**
- **一次調査自身の成否によるステータス管理。** 通知はSemaphoreジョブの事象について出すものであり、調査側の状態機械を持ち込まない。
- 同期の**周期**の変更。即時起動を足すのと周期を詰めるのを同時に行わない。

## 4. ユーザーストーリー

Yoshinobuとして、Semaphoreのジョブが落ちたら、**Slackで所見まで含めて受け取りたい。** そして受け取った時点で、開発側へ「これを調べて」と渡せる状態になっていてほしい。

## 6. 受入条件

### AC1 — 通知が届く

- **Given** 一次調査が1件完了し、成果物が `status: new` で書かれた
- **When** その実行が終わる
- **Then** `#alerts` にテキスト1本が届く。本文にジョブ番号・テンプレート名・playbook・所見・確信度・既知条件の別・レポートのパスが含まれる。**終了コードは `0`**

### AC2 — Codexの失敗もそのまま届く

- **Given** Codexの呼び出しが失敗した(タイムアウト・非ゼロ終了・応答が構造化できない)
- **When** その実行が終わる
- **Then** 同じ形式で `#alerts` に届き、**呼び出しエラーの内容がそのまま本文に載る**。所見の欄は「取得できなかった」ことが分かる形になる。**この通知のために新しいIncident Reportを作らない**

### AC3 — 通知の失敗が調査を壊さない

- **Given** Slack通知が失敗する(webhook到達不可等)
- **When** 一次調査が実行される
- **Then** 成果物は通常どおり書かれ、**プロセスの終了コードは通知の成否に影響されない**。失敗した事実はjournalに残る

### AC4 — 同期が直ちに起動する

- **Given** 一次調査が成果物を書き終えた
- **When** その実行が終わる
- **Then** ansy側で `ansible-incident-sync.service` が**タイマーの定刻でないタイミングで**起動したことをjournalで観測できる。起動から数十秒以内に、当該 `semaphore-<id>` の**バンドルと成果物の両方**がansy側ミラーに現れる

### AC5 — 起動経路が引数を受け付けない(**非通過側**)

- **Given** 起動経路が配備されている
- **When** 任意のコマンド文字列を添えて起動を試みる
- **Then** **添えたコマンドは実行されず**、同期の起動だけが行われる

### AC6 — 起動経路が他のことをできない(**非通過側**)

- **Given** 同上
- **When** `ansible-incident-sync.service` 以外のunitの起動を試みる
- **Then** **拒否される**

### AC7 — ansyが応答しなくても調査は成功する

- **Given** ansyが停止している、または起動経路が失敗する
- **When** 一次調査が実行される
- **Then** 成果物は通常どおり書かれ、**終了コードは `0`**(調査自体が成功していれば)。失敗した事実はjournalに残る

### AC8 — 月次実行中の起動が静かにスキップする

- **Given** 月次Knowledge振り返りが外側flockを保持している
- **When** 同期の即時起動が行われる
- **Then** **exit 0 で静かにスキップし、`failed` にならない**(既存の `-E 0` の設計どおり)。取りこぼしは次の定刻同期が埋める
- **注**: この経路があるため、**「通知が届いた=必ずansyに現物がある」とは言い切れない。** 通知本文はそれを断定しない書き方にすること

### AC9 — 鍵がCodexから読めない(**非通過側**)

- **Given** 起動経路の鍵がquoryに配備されている
- **When** `recovery-exec` として読み取りを試みる
- **Then** **拒否される**

### AC10 — 索引

- **Given** `playbooks/README.md`
- **When** `playbooks/*.yml` と突き合わせる
- **Then** 未記載のplaybookが**0本**

## 7. 成功指標

- Semaphoreジョブの失敗から**10分以内**に、Yoshinobuが所見つきの通知を受け取る(内訳: 捕捉 最大5分 + 調査timer 1分 + Codex呼び出し 実測1分前後 + 同期・通知)。
- 通知を受け取った時点で、開発側がansy側の現物だけで調査を始められる。

- 本番反映にはYoshinobuの `git commit` / `push` と、**quory・ansy双方への配備**が要る(起動経路は両側に配備物がある)。

## 10. 確認済みの前提(実装で作り込まなくてよいこと)

- **一次調査のエラーは新しいIncident Reportを生まない。** 一次調査はquoryのsystemd unitであってSemaphoreジョブではなく、捕捉はSemaphoreのDBをポーリングしている。**捕捉の視界に構造的に入らない**ため、抑止の細工は不要である(2026-08-01確認)。
- **`#alerts` のwebhookは既に存在し、`roles/common_slack/tasks/notify.yml` が写像を持っている。** vaultの変更は不要。
  - **ただし同ファイルは未知のチャンネル名を黙って `alerts` へフォールバックする**(`.get(slack_channel, slack_webhook_alerts)`)。チャンネル名の綴りを誤ってもエラーにならない。
- **同期unitは外側flockを月次Knowledge振り返りと共有し、`-E 0` で「衝突は失敗ではない」としている**(`roles/incident_sync/templates/incident-sync.service.j2`)。AC8はこの既存設計の確認であって、新しく作る挙動ではない。
