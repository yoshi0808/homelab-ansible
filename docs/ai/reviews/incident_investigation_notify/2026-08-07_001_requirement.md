# requirement: 一次調査の通知の成否を、成果物へ残す

日付: 2026-08-07 (JST)
Role: Coordinator
承認: Yoshinobu(2026-08-07、「1、2の話ですね?着手してください」)
先行契約: `docs/ai/reviews/incident_investigation_notify/2026-08-01_001_requirement.md`(N1〜N11。**本件はこれを置き換えず、観測手段だけを足す**)

## 1. 問題定義

`roles/incident_investigate/files/incident-investigate.py` の `post_artifact_actions()` は、Slack通知の失敗を捕捉して **stderr(= systemd ジャーナル)へ1行書くだけ**にしている。成功したときは**何も残さない**(`2026-08-01_006_post_deploy_observation.md` AC1 節が「Slackに届いたことの確認が唯一の直接証拠」と明記している)。

この2つが合わさると、通知機構は**どちらの向きにも観測できない**。

2026-08-07 に実際に詰まった。8/1 の配備以降、一次調査の成果物は 512 / 533 / 535 / 552 / 553 / 554 / 561 / 607 の**8件**生成されているが、`docs/ai/status.md` の Watch「一次調査の通知が本番で実際に出るか」は満たされていない。つまり**通知は8回連続で出ていない**。にもかかわらず、その理由はどこにも残っていない —

- 成功記録が無いので「出たが見落とした」と区別できない
- 失敗記録はジャーナルにしか無く、`journal-unit` が遡れるのは1分timerのこのunitで**約100分**。10時間後には読めない

**「鳴らない」が正常と故障の両方を意味する状態**であり、`docs/ai/roles/coordinator.md`「無音化・例外吸収の判断が案件に複数入るとき、合成して何が見えなくなるかを問う」がまさに指している形になっている。

## 2. ゴール

**次に通知が落ちたとき、その理由が時間経過で消えない場所に残っていること。**

## 3. 非ゴール

- **通知が落ちている原因そのものの修正。** 原因はまだ分かっておらず(D8 の配備後にジャーナルを読んで初めて分かる)、**推測で直さない**。本件は計測の追加だけである。
- **通知の失敗を致命にすること。** N4 / AC3 / AC7 が「通知の失敗は成果物にも終了コードにも影響しない」と定めており、これは変えない。unit を `failed` にしない。
- **新しい dispatch check を足すこと。** 成果物は既存の `investigation-show <id> json` で読める。カタログ(D5)の改訂を要さない形に収めること。
- ジャーナルへの出力を減らすこと。現在の stderr 1行は残す(消さない)。

## 4. ユーザーストーリー

Coordinator として、Semaphore の失敗から半日たった後でも「一次調査の通知が出たのか、出ようとして何で落ちたのか」を `ssh quory-investigate "investigation-show semaphore-<id> json"` だけで言えるようにしたい。いま言えないため、実測の代わりに推測を並べることになっている。

## 5. 要件

| # | 優先度 | 内容 |
|---|---|---|
| R1 | **P0** | 通知の試行結果を成果物 JSON(`reports/incidents/_investigations/semaphore-<id>.json`)へ記録する。少なくとも「試行したか」「送れたか」「送れなかった理由(生文字列)」「その時刻(JST、`+09:00` 付き)」が分かること |
| R2 | **P0** | **成果物ファイルが、消えた・切れた・壊れた状態を経由しないこと。** このファイルの**存在そのものが「調査済み」の唯一の印**であり(IC-039、`artifact_already_exists()`)、失われるとバンドルが再調査され LLM が再度呼ばれる。更新は原子的に行うこと |
| R3 | **P0** | 通知の失敗も、**この記録処理自身の失敗も**、`process_bundle()` の戻り値と終了コードに影響しないこと。既存の「例外はここで必ず握りつぶし stderr へ書くだけ」という性質を、新しい処理にも同じく適用する |
| R4 | **P0** | **記録する文字列に秘密情報が入らないこと。** 失敗理由は `ansible-playbook` の stderr を含む。通知 playbook は webhook を `no_log: true` で扱っているが、**それは stdout の話であり stderr が同じ保証を持つかは別**である。実際に失敗させて出力を確認し、トークン片が入りうるなら載せない形にすること。あわせて `reports/` が Git 管理外であることを確認すること(入るなら公開前提のリポジトリへ秘密が入る) |
| R5 | P1 | 同じ内容を `.md` 側にも1行で出す。人が読む側にだけ出ないのは避ける |
| R6 | P1 | `schema_version` を上げるかどうかは、**成果物 JSON を読む側を実際に調べてから**決める。厳密に検証している読み手がいれば上げる、いなければ据え置く。調べた結果を実装記録へ書く |
| R7 | P2 | 「成功したときも記録が残る」ことがこの変更の要点である旨を、コード側のコメントに1〜2行で残す(次に読む人が「失敗時だけでよいのでは」と縮めないため) |

## 6. 受入条件

検証は decoy(実 Slack へ送らない形)で行う。**本番 `#alerts` へ通知が飛んだ状態で報告を返さないこと。**

- **AC1(成功側が残る)**: Given 通知 playbook が rc=0 で終わる状態、When 一次調査が1件完走する、Then 成果物 JSON に「送れた」ことと時刻が記録されており、**`process_bundle` の戻り値・終了コードが変更前と同じ**。
- **AC2(失敗側が残る)**: Given 通知 playbook が非0で終わる状態、When 一次調査が1件完走する、Then 成果物 JSON に「送れなかった」ことと理由の生文字列が記録されており、**終了コードは変更前と同じ**(通知失敗を理由に非0にならない)。
- **AC3(記録処理自身が落ちても壊れない)**: Given 記録処理が例外を投げる状態(書込先が読み取り専用など)、When 一次調査が1件完走する、Then **成果物 JSON は依然として存在し、`json.load` で読める**。stderr に1行残る。終了コードは変更前と同じ。
- **AC4(再調査を誘発しない)**: Given AC1〜AC3 のいずれかを通した後、When 同じバンドルに対して再度 `incident-investigate.py` を起動する、Then そのバンドルは**候補にならない**(LLM が呼ばれない)。
- **AC5(タイムアウト経路)**: Given 通知 playbook が `notify_timeout_s` を超える状態、When 一次調査が1件完走する、Then AC2 と同じ形で「送れなかった」と理由が残る(タイムアウトも失敗の一種として記録されること)。
- **AC6(give-up 経路)**: Given Semaphore の終了確定を待ちきれず Codex を呼ばずに諦める経路(`if not finalized:`)、When そこを通る、Then その経路でも R1 の記録が残る。**2つある呼び出し元の片方だけに付けない。**
- **AC7(秘密情報)**: Given AC2 / AC5 で記録された理由の文字列、When 目視と機械検査、Then webhook URL・トークン片・vault 平文が**1文字も含まれない**。
- **AC8(既存契約の不変)**: Given 変更後のスクリプト、When 既存の N1〜N11 と突き合わせ、Then 通知本文の項目・チャンネル・プレーンテキストである性質・`--check` 下で送らない性質が変わっていないこと。

## 7. オープンクエスチョン

- **OQ1**: 通知が**一度も成功していない**ことを、成果物が溜まる前に気づく仕組みは別に要るか。本件は「次に落ちたとき読める」までを担い、**「落ち続けていることに気づく」は担わない**。`docs/ai/status.md` の既存 Next「一次調査成果物の保持期間と、滞留の検知」と同じ層の話であり、そちらへ合流させるのが自然。**今回は足さない。**
- **OQ2**: 記録先を成果物 JSON にしたのは、既存の読み出し口(`investigation-show`)にそのまま乗るためである。別ファイル(sidecar)にすると新しい check が要り D5 の改訂になる。**この判断を覆すなら D5 の話になる**ことを、次に触る人へ残す。

## 8. タイムライン考慮

- 配備には Semaphore の `SEMI-SAFE:Incident investigate setup` 押下(Yoshinobu)が要る。**`git pull` では `/usr/local/sbin/incident-investigate.py` は入れ替わらない。**
- 配備後の確認手段: `ssh quory-investigate "deployed-hash incident-investigate"` が repo 側の `sha256sum` と一致すること。
- **本件が効くのは次に一次調査が発生したときである。** それまでは「配備された」までしか言えない。
