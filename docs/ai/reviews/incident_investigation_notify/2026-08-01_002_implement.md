## 3. 判断した点とその理由

### 3.1 `roles/common_slack/tasks/notify.yml` を再利用しなかった(2026-08-01、R4差し戻しで理由付けを全面改訂)

**本当の理由(主要因)は、経由すると自分の通知が証拠を汚すことである。** `roles/common_slack/tasks/notify.yml`は先頭で`roles/common_slack/tasks/capture.yml`を無条件includeする(IC-008「okを含む全ての通知を記録する」— この無条件性はADR-004の設計であり、`slack_status`やチャンネルで絞る余地が無い)。`capture.yml`は到達した通知1件ごとに`_spool/`へレコードを1件書き、それは収集器(`incident-capture-collector.py`、`recovery-exec`実行)によってバンドル(`spool-*`か、時間窓が重なった既存のSemaphoreジョブバンドル)へ取り込まれる。この一次調査完了通知は、Semaphore経由の実行(捕捉が前提とする実行形態)ではなく`incident-investigate.py`が直接`ansible-playbook`をsubprocess起動するだけであり、対応するSemaphoreジョブ行を持たない。したがって`capture.yml`を経由させると、**証拠パイプラインの外側から生まれたレコードが、無関係な既存Semaphoreジョブのバンドルへ紛れ込む、または宛先不明なまま漂う**ことになる。IC-016(証拠バンドルは非信頼データ、書き手を正確に扱う)・IC-032(証拠と判断を別の場所に置く)の精神に照らし、これは「自分の通知の副作用で証拠を汚す」実害であり、単なるスタイルの問題ではない。

副次的な理由として、N2(プレーンテキスト・色分けなし)もある。`notify.yml`の「Send Slack notification」taskは常に`attachments:`+`color:`(status→色のマッピング)を付ける構造になっており、これを条件分岐でスキップする改修は`common_slack`自体の変更を要求する(`roles/common_slack`は変更対象外)。この制約単独でも再利用不可という結論は変わらないが、**証拠汚染の回避の方が重い理由であり、こちらを主要因として記録する**(2026-08-01独立レビューS3/R4指摘のとおり、当初の実装記録はN2の衝突だけを理由として挙げており、この主要因を書き落としていた)。

そこで`playbooks/incident_investigate_notify.yml`は`community.general.slack`モジュールを直接呼び、`msg:`のみ・`color:`省略(モジュール既定値`normal`)で送る形にした。モジュール実装(`community/general/plugins/modules/slack.py`)を読み、`color=='normal' and text is not None`の分岐で`payload = dict(attachments=[...])`**ではなく**プレーンな`text`ペイロードになることを確認済み(§4)。

**引き受けたコスト**: webhookのロード(`include_vars: .../vars/slack.yml`)とtoken抽出(`replace('https://hooks.slack.com/services/', '')`)のロジックを`notify.yml`から複製している。将来`common_slack`側でこのロード・抽出方式が変わった場合、このplaybookは追随されない構造的リスクがある(このファイル自身をレビュー・変更対象に含めない限り検出できない、2026-08-01独立レビューS3指摘)。対応必須の欠陥ではないが、`docs/ai/role-context-matrix.md`または`common_slack`変更時のレビューチェックリストへ「`incident_investigate_notify.yml`も追随したか」を一言残すことを、次に`common_slack`のwebhookロード方式に触れる担当への申し送りとする(本差分の範囲では追加していない — scope外)。

**背景(この案件では対処しないが記録する価値がある事実、2026-08-01 Coordinator確認)**: Codexが起動できない状態は次の形でループしうる — 一次調査unitが`failed`終了 → `roles/ubuntu_vm_full_upgrade/tasks/healthcheck.yml`の汎用`systemctl --failed`検査(対象に`control_nodes`=quoryを含む)がcriticalとして拾う → Semaphoreジョブ失敗 → 捕捉(collector)がバンドル生成 → 一次調査が起動 → Codex呼び出し → また失敗。この経路は本差分が触れるファイルの外側にあり(`roles/ubuntu_vm_full_upgrade`は変更対象外)、この案件で塞ぐものではない。ただし、この通知機能が「Codex呼び出し失敗も同じ形式で毎回通知する」(N3)設計である以上、このループが発生すると**同じ内容の通知が繰り返し届きうる**。requirement §3は「通知の集約・抑制を行わない」ことを明示的に非ゴールとしており(Q2「集約しない」)、本実装もこれに従っているため、この繰り返し自体は契約違反ではないが、Codexの起動不能状態が長引いた場合の運用上の負荷として申し送る。

### 3.2 ansy側の受け口を専用ユーザーとして新設した(yoshiのauthorized_keysへの追記ではなく)

検討した代替案: yoshiの既存`authorized_keys`へ`ansible.posix.authorized_key`(`exclusive: false`)で1行追記する案。却下理由は2つ。

1. yoshiの`authorized_keys`の現在の中身をこの実装は把握していない(人間の対話ログイン鍵を含む可能性が高い)。追記自体は非排他なので理論上は安全だが、「個人のログイン鍵と自動化の鍵が同じ受け口に同居する」構造は、`feedback_setup_playbook_lateral_blast.md`が警告する横方向影響のクラスに近い曖昧さを持つ。
2. `roles/recovery_exec`・`roles/incident_inspect`のいずれも「専用の低権限ランディングアカウント + `command=`固定 + そのアカウント専用の`authorized_keys`(排他テンプレート)」という同型パターンを既に2回採用しており、これに追随する方が一貫性が高く、レビュー時の理解コストも低い。

新設アカウント`incident-sync-trigger`はホームディレクトリ以外に何も持たず、sudoersも`systemctl start --no-block ansible-incident-sync.service`という完全一致1行のみを許可する。IC-013(quoryにansyへの書込権を与えない)は、このアカウントが**ファイルを一切書かない**(唯一許されたアクションが既存unitの起動だけ)ことで保たれる。

### 3.3 クロスホストの鍵配布に新規playbookを作った(既存playbookへの合流ではなく)

`incident_sync_timer.yml`のヘッダは「対象: ansy(dev_nodes)のみ。quoryには何も配備しない」という不変条件を明記している。ここへ`hosts: quory`のplayを追加するとこの不変条件と矛盾するため、`incident_investigate_setup.yml`(hosts: quoryのみ)への合流も試みたが、こちらはansy側(dev_nodes)を対象に含められない。そのため、クロスホスト伝搬専用の新規playbook`incident_sync_trigger_setup.yml`を作った。構成は`playbooks/incident_sync.yml`の「play1でslurp・play2でhostvars越しに読む」という既存の2-play構成をそのまま踏襲している。

### 3.4 role defaultのhostvars可視性の罠を避ける設計

`roles/incident_sync/tasks/transfer.yml`のコメントが指摘する制約(role defaultはそのroleがそのホストへ一度importされて初めてhostvarsへ現れる)を踏まえ、`incident_sync_trigger_setup.yml`のplay1は`roles/incident_investigate/tasks/sync_trigger.yml`を**その場で`import_role: tasks_from: sync_trigger`として呼ぶ**ことで、quoryのhostvarsに`incident_investigate_sync_trigger_key`等のrole defaultを確実に載せてからslurpする設計にした。これにより、同じパス文字列を新規playbook側へ二重にハードコードする必要が無くなっている(唯一の例外はansy側の受け口ユーザー名`incident-sync-trigger`で、`roles/incident_investigate/defaults/main.yml`の`incident_investigate_sync_trigger_remote_user`と`roles/incident_sync/defaults/main.yml`の`incident_sync_trigger_user`という2つの変数として重複している — これは`incident_investigate_inspect_user`と同型の、越境時にこの2ファイル間でしか解決できない結合値であり、既存の設計慣行に倣った)。

### 3.5 `--no-block` を使った

forced commandが`systemctl start ansible-incident-sync.service`(`--no-block`無し)を実行すると、oneshot unitの実行完了(最大`TimeoutStartSec=300`秒、または月次評価と競合した場合の`flock -E 0`による即時exitのいずれか)まで呼び出し元のSSHセッションがブロックされる。`incident-investigate.py`側の`sync_trigger_timeout_s`(20秒)より長くなりうるため、`--no-block`でジョブの投入だけを行い即座に返る形にした。転送の成否自体は`_sync/last-sync.json`とfinalize.ymlのSlack通知(既存、変更なし)が別途扱う。

### 3.6 通知の実装に`assert`以外の失敗時ガードを持たせなかった

`playbooks/incident_investigate_notify.yml`自体は、Slack送信taskが失敗したら自然にplay全体が失敗しexit非ゼロで終わる(`rescue`で握りつぶさない)。AC3・N4が要求する「失敗を握りつぶさない」を`incident-investigate.py`側の`post_artifact_actions`(非ゼロ終了を`RuntimeError`として捕捉しstderrへ出す)に担わせ、playbook側は`IC-011`の精神どおり素直に失敗を表出する設計にした。

### 3.7 `tester-gate`を`role-guarded`→`check-mode-native`へ再分類した(2026-08-01、独立レビューM1/R1差し戻し)

当初`role-guarded`としていたが、`docs/ai/policies/ansible_test_safety_policy.md`(TS-005)の定義は「副作用がSlack通知のみで、`roles/common_slack/tasks/notify.yml`の抑止guard(`tester_mode`/`skip_notifications`/`ansible_check_mode`)で止まる」ことを要件とする。本playbookは§3.1の理由で`notify.yml`をincludeしないため、この要件を満たしていなかった。`role-guarded`はTS-022により`--check`無しの通常実行が許される分類であり、抑止guardが存在しないままこれを名乗ると、Testerが検証のため実行するたびに抑制手段が一切無く`#alerts`へ実送信される — TS-026が定義する「marker drift」(分類名・理由文・実際の抑止guard・実行経路の不一致)そのものだった。

`check-mode-native`へ再分類し、Slack送信task(唯一の外部副作用)へ`when: not ansible_check_mode`+`tags: [destructive]`を明示的に追加した(§4で`--check`実行時に当該taskが`skipping`になることを再確認済み)。`community.general.slack`は`check_mode: support full`のネイティブ実装を持ち、`--check`下では`do_notify_slack()`(実HTTP POST)へ到達しない分岐が存在する(モジュールソース確認済み、実装記録初版の自己検証もこれに依拠していた)が、レビューの指摘どおりこれだけに依存させず、他の`check-mode-native`playbook(`roles/incident_sync`等)と同じ明示ゲートの形に揃えた — モジュールの将来のバージョンでこの内部実装が変わっても、このリポジトリの慣行(TS-014)どおり安全側で止まる。

再分類に伴い、Testerへの実行指示も変わる: **`--check`を付けて検証すること**(TS-023)。`scripts/safe-ansible-check.sh playbooks/incident_investigate_notify.yml -e @<file> --check`を使う。

### 3.8 「Codex呼び出しエラー」と「Codexを呼ばず諦めた」を別引数・別見出しに分離した(2026-08-01、独立レビューS2/R2差し戻し)

`process_bundle`には2つの「調査が完了しなかった」経路がある。

1. `invoke_llm()`でCodexを実際に呼び出し、タイムアウト・非ゼロ終了・応答の構造化失敗のいずれかで失敗した経路(AC2が想定する経路)。
2. Semaphoreがジョブの終了(status/end)をまだDB確定していないまま`incident_investigate_bundle_wait_max_s`(既定1800秒)を超えて諦めた経路(`process_bundle`の`if not finalized:`分岐、`give_up_reason`)。**この経路はCodexを一度も呼び出していない。**

当初の実装は両者を`llm_error`という単一の文字列引数に畳み、`iv_llm_error`として通知本文の「Codex呼び出しエラー:」節にそのまま出していた。経路2でもこの見出しが出るため、読み手が「Codexが落ちた」と誤読しうる状態だった(2026-08-01独立レビューS2、Coordinator差し戻しR2)。

対応: `build_notify_payload` / `send_investigation_notification` / `post_artifact_actions`のシグネチャを`codex_error` / `wait_error`の2引数に分離した(`post_artifact_actions`はキーワード引数化、両方省略時は正常完了扱い)。`process_bundle`の呼び出し側で、経路1は`codex_error=llm_error`、経路2は`wait_error=give_up_reason`を渡す — **どちらの経路かを知っているのは`process_bundle`だけであり、後段(通知本文の組み立て)で判別し直すのではなく、呼び出し元に判別させた。** `playbooks/incident_investigate_notify.yml`側も`iv_codex_error`/`iv_wait_error`を別々の`{% if %}`ブロックとして扱い、見出しをそれぞれ「Codex呼び出しエラー:」「調査未実施の理由(Semaphoreジョブの終了確定を待ちきれなかったためCodexは呼んでいません):」に分けた。§4で両経路を`process_bundle`からエンドツーエンドで実行し、意図した方の引数だけが非空になることを確認済み。
