# followup: 記録した「理由」に理由が入っていなかった

日付: 2026-08-07 (JST)
Role: Coordinator(実装も Coordinator が行った)
契約: `2026-08-07_001_requirement.md` R1(送れなかった理由を記録する)/ R4(秘密情報が入らない)
レビュー: `2026-08-07_006_review.md`(独立、Approve / Critical なし)

## 1. 何が起きたか

commit `6185238` で「通知の成否を成果物へ残す」計測を配備した。その直後、D8 で読めるようになったジャーナルから **semaphore-607 の実際の失敗**を取得した。

```
8月 07 03:36:56 quory flock[41561]:
  incident-investigate: Slack notification failed for semaphore-607 (non-fatal):
  notify playbook rc=2 stderr=''
```

**配備したばかりの計測は、次に落ちてもこれと同じ文字列しか残さない。** `error` に入るのは `send_investigation_notification()` が投げる例外の文字列で、その中身は `rc` と **stderr** だけだったためである。

`ansible-playbook` は通常のtask失敗を callback 経由で **stdout** へ書き、プロセスの OS stderr は空のままにする(`rc=2` は「1つ以上のhostが失敗」)。**理由がある側を捨てて、空になる側だけを記録していた。**

**この性質は把握されていた。** 同じファイルの `record_notification_result()` の docstring に「playbookプロセスのOS stderrは通常のtask失敗では空になる(fatal表示はstdoutの callback 経由のため)」と書かれている。**正しく理解したうえで、空になる側を記録していた。**

### なぜレビューで止まらなかったか

独立レビューは2体とも Approve している。両者とも誤っていない — 契約は「送れなかった理由(生文字列)を記録する」であり、実装は既存の例外文字列を忠実に通していた。**欠けていたのは「その生文字列に理由が入っているか」という問いで、これは契約と実装のどちらを見ても出てこない。** 両方に加えて「実際に落ちたときのジャーナル」を突き合わせて初めて見える。

`docs/ai/roles/coordinator.md` の「無音化・例外吸収の判断が案件に複数入るとき、合成して何が見えなくなるかを問う」が指している形そのものである。個々の判断(`no_log` を付ける / 失敗を非致命にする / 例外文字列をそのまま記録する)はどれも正当で、**合成した結果だけが「壊れていることが原理的に分からない」になっていた。**

## 2. 直したもの

| ファイル | 変更 |
|---|---|
| `roles/incident_investigate/files/incident-investigate.py` | 失敗時に **stdout の末尾**(`NOTIFY_OUTPUT_CAPTURE_CHARS` = 2000文字)を捕捉して例外文字列へ載せる。載せる前に `redact_webhook_urls()` を通す(**切り詰めより先に** — 順序が逆だとURLの断片が末尾に残る) |
| `playbooks/incident_investigate_notify.yml` | 送信taskを `block` に入れ、`rescue` で **URLを落とした理由を出し直す**。再送出taskには `no_log` を付けない |

### stdout を載せてよい根拠(R4)

`no_log: true` を安全の根拠にしない。**実測すると、no_log を付けたtaskでも ansible は `[ERROR]: Task failed: Module failed: <モジュールのmsg>` を stdout へ出す**(censored になるのは `fatal:` の構造化出力だけ)。当初この事実から「モジュールのmsgにはURLが入るので危険」と考えたが、**それは誤りだった**(下記 S5)。現状の経路で実URLが出ることは確認できていない。redaction は多層防御として残す。

### 検証(すべて ansy、実Slackへの到達なし)

decoy はスラッシュを含まないトークンを使い、**モジュールの引数検証でネットワークへ出る前に落とす**形にした(URL差し替え型の decoy は `community.general.slack` に対して成立しない — `docs/ai/memory/incidents/2026-08-07_decoy-webhook-reached-real-slack-endpoint.md`)。

- 通常実行(失敗経路): `rescued=1` / `failed=1` / **rc=2**。理由の本文が出力に現れる
- `--check`: `ok=4` / `skipped=1` / `failed=0` / **`ignored=0`** / rc=0。送信されない(AC8 不変)
- 通し(`post_artifact_actions` まで): 成果物 JSON は壊れず `json.load` でき、`notification.sent=false`、`error` に理由の本文が入り、`hooks.slack.com/services/` を含まない
- `redact_webhook_urls()` 単体: URLとトークン片が消え、`HTTP Error 404: Not Found` の側は残る

## 3. レビュー指摘の処理(S4 / S5、いずれも是正済み)

### S4 — `ignore_errors: true` + 後続taskでの再送出は地雷

**是正した。** 当初は送信taskに `ignore_errors: true` を付け、直後の別taskで再送出していた。この形は、**再送出taskだけを「冗長」と判断して消すと `ignore_errors` が残り、通知の失敗が `rc=0`(=送れた)として観測される。** いま塞いでいる問題より悪い状態を、壊れ方が危険側に倒れる形で作る。

`block`/`rescue` へ変えた。**rescue を消しても失敗はそのまま伝播する**(安全側に倒れる)。`--check` 実行で `ignored=1` → `ignored=0` になったことを確認済み。

### S5 — コメントの事実誤認

**是正した。** 「`community.general.slack` は失敗時に webhook URL を含むメッセージを出す」と書いていたが、**本playbookが使う webhook形式トークンの経路では、モジュール自身が URL を `[obscured]` へ伏せてから `fail_json` する**(`slack.py:449-452`。伏せないのは `use_webapi` が真、つまり `xoxb` 形式トークンの場合だけで、ここは該当しない)。現物を読んで確認した。

redaction は残す。理由は①伏字化がモジュールの版に依存する ②**quory 側の collection の版を確認していない** ③`info['msg']` は素通しのテキストで中身を我々が決めていない、の3点。**誤った根拠のまま正しい対策が残る状態を避けるため、コメントを両ファイルとも書き直した。**
