# requirement: `loki-window` の埋め込み改行による出力量上限の回避を塞ぐ

日付: 2026-09-04
対象: `roles/recovery_exec/files/recovery-loki-helper` の `cmd_window`
発端: `docs/ai/reviews/loki_investigate_vocabulary/2026-09-01_003_review.md` finding #12(前案件のscope制約により未対応のままCoordinatorへ引き継がれた)

## 1. 問題定義

`cmd_window`(語彙 `loki-window`、2026-07-29導入・配備済み)は、stdout の行数予算を **entry 数**で組んでいる。

```python
truncated = len(entries) > MAX_LINES
if truncated:
    entries = entries[: MAX_LINES - 1]
```

1 entry の本文に埋め込み改行が含まれると、その entry は複数の物理行へ展開される。`MAX_LINE_LENGTH`(300)は**文字数**で切るだけなので改行では発火せず、1 entry は最大300物理行まで展開しうる。

**観測された事実**(2026-09-01、独立レビューが実測):

| 入力 | 物理stdout行数 |
|---|---|
| 本文 `a\nb` の 299 entries | 598行 |
| 本文 `a\nb` の 500 entries | 599行 |

`MAX_LINES` は300である。

**実害の本体は行数そのものではなく、切り詰め通知が出ないことである。** 「要求した窓のうちどこまで実際に読めたか」の開示(`_truncation_notice()`)は `len(entries) > MAX_LINES` で判定されるため、**物理行数で膨らんでいるときは通知が出ず、出力は「窓を全部読んだ」ように見える。** これは2026-07-29に実際に起きた事故(窓の前半だけを読んだ状態で「errorなし」と結論し、窓の後半に目的の事象があった)と同じ失敗の形である。切り詰め通知はその事故への対策として導入されたものであり、本欠陥はその対策を無効化しうる。

規範上は `docs/ai/policies/autonomous_recovery_policy.md` AR-098(出力量を対象host側で固定する)が成立していない。カタログ `docs/ai/reviews/dev_prod_boundary/2026-08-03_008_phase3_check_catalog.md` §9 と `roles/recovery_exec/templates/AGENTS.md.j2` の「最大300行」も、L2 については厳密には成立していない。

**同一の欠陥は `cmd_errors` にもあり、2026-09-01に修正済みである**(同レビュー finding #4)。本案件はその修正が届かなかった側を塞ぐ。

## 2. ゴール

1. `cmd_window` の stdout 物理行数が、entry 本文の内容によらず `MAX_LINES` を超えない。
2. 切り詰め通知が出る条件と、実際に出力を落とした事実とが一致する。

## 3. 非ゴール(やらないと決めたこと)

- **`cmd_count` は対象外。** `MAX_LINES` / `MAX_LINE_LENGTH` / `QUERY_LIMIT` を一つも参照せず、系列数を `MAX_SERIES` で制限する別設計である(カタログ §9)。
- **`cmd_errors` は触らない。** 2026-09-01に修正済みで、本案件で挙動を変えない。
- **定数値(`MAX_LINES` / `MAX_LINE_LENGTH` / `QUERY_LIMIT` = 300、`MAX_SERIES` = 500)の見直しをしない。**
- **切り詰め通知の文言・書式・数値を変えない。**
- **実機(monnie)への配備は本案件のscope外。** ただし §7 に配備要否を記録する。
- **operand検証・認可境界(dispatch / wrapper)に触れない。**
- **repoへ恒久的なテストを追加しない。** このroleにはテスト資産が無く、helper は Loki への HTTP 呼び出しをスタブしないと動かせない。テスト資産を起こすかどうかは、上限の単位で測り直す作法をどこへ据えるかの判断であり、本案件の差分(1関数の出力処理)より広い。自己検証は使い捨てのスクリプトで行い、**何をどう測ったかを実装記録へ書き残す**ことで代える。
- 前案件の finding #10(切り詰め通知の助言文)/ #11(AR-099とlevel絞り込み専用語彙の関係)は本案件では扱わない。

## 4. ユーザーストーリー

Codex が `loki-window` である窓を読み、その結果から「この窓に異常は無い」と結論しようとするとき、**窓の全部を読めたのか、途中までしか読めなかったのか**が出力自身から分かる。本文に埋め込み改行を含むログが混ざっていても、この性質が変わらない。

## 6. 受入条件(Given/When/Then)

前提: 検証は Loki をスタブ/モックした状態で行う。実機到達は無い(§7)。

**AC1(出力量の固定)**
Given `str.splitlines()` が分割する改行相当文字(LF / CRLF / 単独CR / VT / FF / NEL / LS / PS / FS / GS / RS / 先頭改行 / 末尾改行 / 混在)を本文に含む entry が、0 / 1 / 299 / 300 / 301 / 500 件返る
When `cmd_window` を実行する
Then すべての組み合わせで `len(stdout.splitlines()) <= 300` かつ `stdout.count("\n") <= 300`。プロセスの終了コードは `0`。

**AC2(切り詰め通知の成立)**
Given AC1 のうち entry が `MAX_LINES` を超える場合
When `cmd_window` を実行する
Then stdout の**末尾1行**が切り詰め通知であり、その文言・書式・数値(`earliest 299 of >300 lines` を含む)が HEAD 版と同一である。

**AC3(非退行 — `cmd_window` 自身)**
Given 本文に改行相当文字を**含まない** entry が 0 / 1 / 3 / 299 / 300 / 301 / 500 件返る
When HEAD 版と作業ツリー版の `cmd_window` をそれぞれ実行する
Then stdout が**完全一致**する。

**AC4(非退行 — 他の2語)**
Given `cmd_count`(level有り / 無し / 空文字列の3系列を含む)と `cmd_errors`(AC1と同じ本文集合)
When HEAD 版と作業ツリー版をそれぞれ実行する
Then stdout が**完全一致**する。

**AC5(正規化の副作用が無いこと)**
Given 本文に埋め込み改行を含む entry
When `cmd_window` を実行する
Then 本文中の改行相当文字は**半角スペース1つ**へ置換され、行頭の時刻表記(`%Y-%m-%dT%H:%M:%S+09:00`)、`[host]` の表示、時刻昇順の並び、切り詰め判定のいずれにも影響していない。

**AC6(構文)**
Given 変更後の作業ツリー
When `python3 -m py_compile roles/recovery_exec/files/recovery-loki-helper` を実行する
Then 終了コードが `0`。

**AC7(scope)**
Given 変更後の作業ツリー
When `git status --short --untracked-files=all` を見る
Then **実装者自身が変更したファイル**が `roles/recovery_exec/files/recovery-loki-helper` と本案件フォルダ配下の成果物だけである。

> 当初この AC は「作業ツリー全体で変更されているのが〜だけである」と書いていた。**制約の主語を作業ツリー全体に置くと、他者の未commit変更を消してその状態を作る経路を招く**(`skills/subagent-briefing/SKILL.md`「結果で書くときは、その結果へ破壊的手段で到達できないか確かめる」)。実際、着手前から `docs/ai/memory/lessons/verification-referent-and-path-mismatch.md` に SessionEnd hook 由来の未commit変更があり、Implementer はこれを消さずに「字義どおりでは未充足」と報告して返した。**判定は変更の主体で行う**ものとして、この AC を是正した(2026-09-04、Coordinator)。

## 8. オープンクエスチョン

- **埋め込み改行を含むログの実量は未測定である。** rsyslog 転送は通常1行1エントリで、影響は複数行を1エントリで送るアプリログに限られる。実測手段が無い(上記のとおり本番Lokiへ到達できない)ため、本案件は**実量に依らず上限が成立すること**だけを要求する。
- 正規化により複数行の stack trace は1行へ潰れて読まれる。`cmd_errors` で既に受け入れている性質だが、`loki-window` は「特定jobの本文を読む」語彙であり、潰れる影響は `cmd_errors` より大きい可能性がある。**原文の改行位置が必要な場面が実運用で出るかは未知。** 出た場合の対処(別語彙、別上限)は本案件で決めない。
