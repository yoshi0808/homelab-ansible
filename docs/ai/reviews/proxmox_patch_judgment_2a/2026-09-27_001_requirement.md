# requirement: Proxmoxパッチの判定を機械側へ戻す(案件2a)

作成: 2026-09-27 / Coordinator
起点: `docs/ai/reviews/playbook_catalog_policy_audit/2026-09-26_005_summary.md` 仕分けA のうち `_002` F02(前半)・F03・F07・F10。範囲と判断はYoshinobu合意済み(2026-09-27)。

## 1. 問題定義

1. **AIに渡すPolicy節が違う(F03)。** `scripts/codex-classify.sh` は `proxmox_operations_policy.md` の「## 3.」(対応するPlaybook)を抜き出して「Section 3: 判断軸」としてプロンプトに入れている。URGENT / HIGHの判断基準は「## 4. 判断軸」にあり、AIに届いていない
2. **`MAJOR_UPGRADE_DETECTED` をAIがそのまま決めている(F02前半)。** `roles/proxmox_patch_dryrun/tasks/main.yml` の最終Statusは `codex_output.status_inputs.major_upgrade_suspected` が真なら `MAJOR_UPGRADE_DETECTED` にする。Policy(SB-024「AI分類は補助に限り、最終Statusを直接決定しない」、SB-041のmajor疑いの条件)と食い違う。機械的に判定する処理は無い
3. **apply後のhealthcheckが見る項目が狭い(F07)。** `roles/proxmox_patch_apply_node/tasks/main.yml` の post-healthcheck 判定と `retry_healthcheck_once.yml` は、quorum・apt check・`pve-cluster` / `corosync` / `pvedaemon` だけを見る。healthcheckスクリプトはZFS・failed unit・root filesystem・`pveproxy` も収集しているのに使っていない。Policy SB-022(healthcheck失敗の条件)より狭い
4. **手動applyのcontrol node検査が `ansy` という名前を探している(F10)。** `proxmox_patch_apply_control_node_name: "ansy"` で対象node上のVM名を検索している。実行元はquoryであり、quoryが対象node上にいても止まらない。weekly fullは `hostname -s` で実行ホストを見ており、こちらは正しい

## 2. ゴール

- AIには判断軸(§4)が届き、URGENT / HIGHの候補を基準に照らして出せる
- `MAJOR_UPGRADE_DETECTED` は機械的な判定だけで決まる。AIの意見は参考として通知に載るが、Statusを動かさない
- apply後のhealthcheckは、`proxmox_healthcheck` roleと同じCRITICAL条件で判定する
- 手動applyは、実際に実行しているホストが対象node上のVMであれば止まる

## 3. 非ゴール

- **Urgencyの最終決定を機械化すること(F02後半)は扱わない。** 基準がAIに届くようにする(F03)までで、Urgencyの採用方法は変えない
- **apply後のhealthcheckがCRITICALでも、applyの終了コードは変えない**(Yoshinobu合意、2026-09-27)。weekly fullから呼ばれたとき非0で止まると、VM配置を戻す段へ進まなくなるため。weekly fullは後段の `proxmox_healthcheck` で止まる
- 退避失敗時の強制停止(F09)、`BLOCKED` 時のschedule停止(F05)は実装しない(Yoshinobu合意、2026-09-27)。Policyの記述を実態へ合わせる改訂の流れで扱う
- 通知の中身の不足(F08)は案件2bで扱う
- dry-run段に件数閾値を足さない(Policy SB-041「dry-run段は件数閾値を持たない」)
- `playbooks/proxmox_patch_weekly_full.yml` は変えない

## 4. ユーザーストーリー

- Yoshinobuとして、「majorを含むので別project化」という判断が、AIのその日の読みで出たり出なかったりしないでほしい
- Yoshinobuとして、手動でapplyした後、ZFSやGUI(`pveproxy`)が壊れていたら通知で分かってほしい
- Yoshinobuとして、quoryが対象node上に移っている状態で手動applyを押しても、止まってほしい

## 5. 要件

### P0

| # | 要件 |
|---|---|
| R1 | `scripts/codex-classify.sh` が抜き出してプロンプトへ入れる節を、`proxmox_operations_policy.md` の「## 4. 判断軸」にする。プロンプト内の見出し表記も実際の節に合わせる。抜き出しに失敗したら従来どおり異常終了する |
| R2 | dry-runの最終Statusの `MAJOR_UPGRADE_DETECTED` を、次の**機械的な判定**で決める。`codex_output.status_inputs.major_upgrade_suspected` はStatusの判定に使わない。<br>・`pve-manager` または `proxmox-ve` の installed と candidate で、major版(epochを除いた先頭の数字)が変わる<br>・`base-files` の installed と candidate で、major版が変わる(Debianのsuiteが変わる兆候)<br>版はdry-runが収集済みの `installed_version` / `candidate_version` を使い、**nodeごとに判定してclusterの結果はORとする。** 統合JSONは同名packageの2node目以降の版を捨てる(`proxmox-dryrun-merge.py`)ため、統合前のnode別の収集結果で判定するか、統合schemaにnode別の版を保持する(方式は実装の判断)。<br>**判定不能の扱い**: 対象3packageのいずれかが更新対象にあり、installed / candidate のどちらかが欠落・空、またはepochを除いた先頭が数字でないときは、「majorではない」に畳まず `MAJOR_UPGRADE_DETECTED` とし、理由に「版を判定できない」とpackage名・nodeを載せる(自動適用を止め人が判断する。`BLOCKED` ほど強く止めない。Coordinator判断、2026-09-27、計画査読 `_002` Major 3)。<br>**SB-041の他の条件との関係**: 「repository suiteを変更した直後」は、その結果として `base-files` / `pve-manager` / `proxmox-ve` の候補版のmajorが上がることで検出する(sourcesそのものは読まない)。「大量」の件数判定はdry-run段に持たず、apply段の既存の閾値だけとする(SB-041)。判定の優先順位は、案件 `patch_confirm_and_blocked_remove` で入れた置換先なし重要removeの `BLOCKED` の後、`MAINTENANCE_REQUIRED` の前(現行の並びを保つ) |
| R3 | AIの `major_upgrade_suspected` が真で、R2の機械判定が偽のときは、Statusを変えずに、通知本文に「AIはmajor upgradeの疑いを挙げたが、機械判定では該当しない」旨を載せる(参考表示) |
| R4 | apply直前の再dry-run(`roles/proxmox_patch_apply_node`)にも、R2と同じ版による判定を入れる。既存の件数閾値による判定(`proxmox_patch_apply_major_upgrade_threshold`)は残す。どちらかが真なら `MAJOR_UPGRADE_DETECTED`。再dry-runの版は `apt-get -s` の `Inst` 行(`Inst <pkg> [<installed>] (<candidate> ...)`)から取る。対象3packageの `Inst` 行から旧版・候補版を一意に取れないときは、R2と同じく判定不能として `MAJOR_UPGRADE_DETECTED` にする |
| R5 | apply後のhealthcheck判定(`main.yml` の post-healthcheck と `retry_healthcheck_once.yml`)のCRITICAL条件を、`roles/proxmox_healthcheck` のCRITICAL条件と同じにする(ZFSの収集失敗・DEGRADED / FAULTED、failed unit、root filesystem、`pveproxy` を含む)。**条件を2か所へ写すのでなく、`proxmox_healthcheck` 側の判定を再利用する形が望ましい。** 写す場合は、2か所が一致することを検証で示す |
| R6 | 手動applyのcontrol node検査を、実行ホストの `hostname -s` と対象node上のVM名の一致で行う(weekly fullの検査と同じ方式)。`proxmox_patch_apply_control_node_name` の既定値 `ansy` に依存しない |
