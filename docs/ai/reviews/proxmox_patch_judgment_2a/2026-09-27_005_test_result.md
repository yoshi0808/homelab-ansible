## 未確認とその理由

1. **AC8/AC8bのend-to-end実地流し(retry loop + 最終通知、実ホスト・実reboot・実`/usr/local/sbin/proxmox-healthcheck.sh`)は未実施。** 実施できない理由: (a) ansyからpveノードへの到達手段が無い(EXEC-010)、(b) `retry_healthcheck_once.yml`が呼ぶ`/usr/local/sbin/proxmox-healthcheck.sh`は絶対パス実行であり、PATH経由のモック手法(AC1で使った手法)が効かない。ここへ実際にスクリプトを書き込んで差し替えるのは、たとえ一時的でもテスト環境の実システムパスを汚す操作であり、Testerの安全境界(検証目的で対象実装を変更しない、の趣旨に反する)と判断し行わなかった。代わりに判定ロジック(初回判定・再試行判定・通知subject/body/status組み立て)は、role本体の式をverbatimコピーしたfixtureで全て実測した(2026-09-27追記分含む)。Implementer記録の「retry loopと最終通知はend-to-endで流していない」は妥当で、このTester作業でも同じ制約に当たった
2. **通知の実際のSlack送信(`roles/common_slack/tasks/notify.yml`のinclude自体の実行)は未確認。** `_notify_subject`/`_notify_body`/`_notify_status`の値がAC8bどおりに組み立てられることは`test_notify_warning_on_critical.yml`(2026-09-27追記)で実測したが、これらの値を受け取ってSlackへ送るタスク自体(`slack_title`/`slack_message`/`slack_status`への代入以降)は今回の変更が触れていない既存コードであり、かつSlack実送信はネットワーク到達を要するため対象外とした
3. **`codex_output.status_inputs.major_upgrade_suspected`が現物の本番codex実行でどう振る舞うか(AI側の判定精度)は非対象。** AC1は「プロンプトに正しい節が入ること」のみを要求しており、AIの応答内容の妥当性はこの案件のスコープ外
4. **apply側の`_redryrun_major_version_findings`のreason文字列に`node`が含まれない点は、AC5cの「dry-run findingsにnode名を含む」要求とは別文脈(apply roleは常に単一node実行)であり、欠陥ではなく確認事項として記録するに留めた。**

## 残存リスク

- `roles/proxmox_patch_apply_node/tests/_eval_one_scenario.yml`・`roles/proxmox_patch_dryrun/tests/_eval_one_scenario.yml`の2ファイルは、新設のR2/R4ロジックをstubで無効化したまま「verbatim」を名乗っている。次にR3(Urgency機械化)などでこれらのstub箇所へ手が入ったとき、stubの存在に気づかず本物のロジックとの乖離に気づかない恐れがある。各ファイルには既にコメントで意図が書かれているが、棚卸し時に読み落とされるリスクは残る
- `classify_critical.yml`の`include_role`経由呼び出しは、`proxmox_healthcheck`role自身のdefaults(`proxmox_healthcheck_root_fs_critical_pct`等)に暗黙依存する。`proxmox_patch_apply_node`側でこれらの変数を明示的に上書きしていないため、将来`proxmox_healthcheck`のdefaultsが変わると`proxmox_patch_apply_node`の閾値も追随して変わる(意図した「同じ判定を再利用する」の帰結だが、変更影響範囲が2roleにまたがることは明記しておく)
- 実ホストでの初回観測(次回金曜dry-run)まで、`hostvars[node].node_dryrun.updates`が本番の`_reached_nodes`ループで実際に正しいnodeキーを持つか(fixtureでは`add_host`で模擬)は最終確認できていない
- **2026-09-27追記**: 新規3fixture(`test_hc_collection_failure.yml`・`test_hc_collection_failure.sh`・`test_notify_warning_on_critical.yml`)は、role本体の該当式を手でコピーしている。コピー元との一致は各fixture内で`grep -F`により機械確認しているが、role側の該当箇所が書き換わってfixture側のコピーだけが古いまま残った場合、この`grep`確認自体が(コピー文字列を書き換えない限り)通り続けてしまう脆さがある。次にこの周辺へ手が入るときは、fixtureのコピー元コメントと`grep`対象文字列を合わせて更新する必要がある
