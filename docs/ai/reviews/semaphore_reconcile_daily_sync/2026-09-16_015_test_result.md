## 1. 最重要の発見: Critical — P0-14のbootstrap schedule行が、自分自身の実装のallowlistで拒否される

**FAIL(AC18の前提が成立しない。日次reconcileは、このカタログのままでは一度も成功しない)。**

### 再現手順

```
cd /home/yoshi/homelab-ansible
ansible-playbook playbooks/semaphore_templates_setup.yml \
  -e semaphore_target=ansy -e ansible_connection=local \
  -e semaphore_templates_report_dir=<書き込み可能なpath> \
  -e semaphore_schedules_report_dir=<書き込み可能なpath> \
  --check
```
(`--check`をつけたままでも、`--check`無しの実apply実行でも同一箇所で失敗する。preflightは
read-onlyで`--check`の有無に関わらず常に実行されるため。)

### 実測結果

`readset_preflight.yml`(`Fail before either resource type is written if any early preflight
failed`)が非ゼロで停止する:

```
schedule 'SEMI-SAFE: Semaphore reconcile daily': task_params task_params.environment.semaphore_templates_api_base_url
  は許可されていないキー(現状 force_renew / dry_run / debug_level /
  ubuntu_vm_full_upgrade_operation / prometheus_update_check_operation のみ許可)
schedule 'SEMI-SAFE: Semaphore reconcile daily': task_params task_params.environment.semaphore_templates_api_validate_certs
  は許可されていないキー(同上)
```

### 原因

- `roles/semaphore_templates/defaults/main.yml`のP0-14 bootstrap schedule行(1066-1071行)は
  `task_params.environment`を`{{ '' | semaphore_schedules_canonical_environment }}`で描画する。
- `filter_plugins/semaphore_schedules.py`の`semaphore_schedules_canonical_environment()`
  (971-976行)は`{"semaphore_templates_api_base_url": ..., "semaphore_templates_api_validate_certs": "true"}`
  というJSONを返す。
- 一方、同ファイルの`_ENVIRONMENT_ALLOWED_KEYS`(303-305行、`readset_preflight.yml`と
  `schedules_preflight.yml`の両方が使う「公開契約」のallowlist)は
  `force_renew` / `dry_run` / `debug_level` / `ubuntu_vm_full_upgrade_operation` /
  `prometheus_update_check_operation`の5つだけで、bootstrap行が使う2キーを含まない。
- `git diff`で確認したとおり、この差分は`semaphore_schedules_canonical_environment`を
  新設したが`_ENVIRONMENT_ALLOWED_KEYS`を更新していない。**カタログの正本(P0-14)と
  それを検査するモジュール自身の契約が、同じ差分の中で矛盾している。**

### 影響

- この矛盾は接続先(ansy/quory)、`--check`の有無、上限変数のいずれにも依存しない。**現状の
  カタログのまま`playbooks/semaphore_templates_setup.yml`をどのように実行しても、
  読み取り専用のpreflight段階で必ず停止する。** template側・schedule側とも一切の書き込みが
  行われない(write 0件、それ自体は安全側に倒れている)。
- したがってAC18(bootstrap)は前提から成立しない — Yoshinobuが手動templateを押しても、
  reconcileは毎回この地点で失敗し、04:00のscheduleは作成されない。
- P0-7/P0-15が想定する「templateとschedule両方の書き込みが起きる/起きない」という以降の
  ACの多く(AC9〜AC17、AC19)は、**このbootstrap行を除外すれば**正常に検証できる
  (実際に本レポートの他の節はすべてそのように検証した)。ただし本番のカタログには
  この行が実在するため、この除外は検証上の便法であり、実装の欠陥を相殺しない。

### 対処(私は行っていない)

実装を自分で直していない。修正候補は「`_ENVIRONMENT_ALLOWED_KEYS`(および
`_PARAMS_ALLOWED_KEYS`と対で管理されている契約)へ`semaphore_templates_api_base_url`/
`semaphore_templates_api_validate_certs`を追加する」または「bootstrap行のenvironmentの
持ち方自体を見直す」のいずれかだが、判断はImplementer/Reviewerに委ねる。

## 2. 追加で見つかった実装上の欠陥(AC番号に直接対応しないが記録する)

### 2.1 Minor: run report / marker の一時ファイルが publish 成功後も残り続ける

`roles/semaphore_templates/tasks/reconcile_finalize.yml`の「atomic publish」は
`ansible.builtin.copy`(`remote_src: true`)で`.{{ run_id }}.json.tmp` →
`{{ run_id }}.json`へ**コピー**しているが、コピー元の`.tmp`ファイルを削除する処理が
成功経路に無い(失敗時の`rescue`にだけ`state: absent`がある)。実測で、実行するたびに
`runs/`配下と`reconcile/`直下の両方に`.tmp`ファイルが1つずつ増え続けることを確認した
(4回実行→`.tmp`4個 + 本体4個が残存)。`copy`モジュール自体は内部でatomic renameを
行うため**atomicity自体は壊れていない**(要求どおり)が、毎日04:00に走る運用では
`.tmp`ファイルが無期限に蓄積する。安全上の実害は無いが、ディスク使用量とディレクトリの
可読性が長期的に劣化する。

### 2.2 Minor: `semaphore_reconcile_stale` findingの`actual`が常に`null`になる

`roles/deployment_drift_check/tasks/semaphore_probe.yml`の
`deployment_drift_check_reconcile_stale_findings`定義:

```
'actual': (deployment_drift_check_reconcile_freshness.error
           | default((deployment_drift_check_reconcile_freshness.age_seconds | string) ~ ' seconds')),
```

`semaphore_reconcile_marker_freshness()`は「エラーではない、単に古いだけ」のケースで
`error`キーへ**Python の `None`**を明示的に持たせる(`result = {'stale': True, 'error':
None, 'age_seconds': None}`を初期値とし、パース成功時は`error`を上書きしない)。Ansibleの
`default`フィルタは**Undefinedのときだけ**代替値を使い、値が`None`(null)のときは代替
しない。したがって「markerはあるが24時間以上古いだけ」という最も普通のstaleケースで、
`error`は`None`のまま`actual`へそのまま入り、JSON上`"actual": null`になる。

実機で確認した(marker完了時刻を意図的に44時間40分前へ書き換えて`deployment_drift_check`を
実行):

```json
{
  "category": "semaphore_reconcile_stale",
  "actual": null,
  "expected": "latest-success marker age < 24 hours",
  ...
}
```

`age_seconds`の値(何時間古いか)がfindingから読み取れない。安全側には倒れていない
(findingの発火自体は正しく起きる、AC16は成立)が、運用者が「どれだけ古いか」を
findingだけから判断できない情報欠落であり、修正候補としては`default(X, true)`
(falsy値も代替対象にする)へ変更するか、`error is none`を明示条件にする形が考えられる。
これも自分で直していない。
