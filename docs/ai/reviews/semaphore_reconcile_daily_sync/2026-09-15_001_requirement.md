## 1. 問題定義

**判断の余地が無いものを、人の手作業に変換している。** Semaphoreのtemplate / scheduleの望ましい状態は、このリポジトリのカタログが正本であり、そこに人の意向は入っていない。にもかかわらず現状は、日次ドリフト検査が**templateの食い違いを検知するだけ**で、修正はYoshinobuが `semaphore_templates_setup` を手で押すまで起きない。**注意喚起しておきながら自分では直さない。**

**手動applyは歯止めとしても成立していない。** quoryは1分ごとにgitをpullしており、**playbookの中身は無人で本番へ届き、次のscheduleでそのまま実行される**。手動applyが守っているのは「どのボタンがあるか・いつ走るか」というメタデータだけで、より危ない面(そのジョブが何をするか)は既に自動である。

**ただし、いまのreconcileは無人で回してよい状態にない。** 査読が2つの理由を示した。

1. **異常な応答を異常と判定しない。** 読み取りは応答が配列かどうかしか検査しない(`roles/semaphore_templates/tasks/read.yml:31-43`)。**HTTP 200で空または部分的な一覧が返ると、reconcileは全件を `new` と判定する**(`filter_plugins/semaphore_templates.py:220-258`)。schedule側も同様に、既存が無ければ新規作成し、そのときカタログの `active` を送る(`filter_plugins/semaphore_schedules.py:598-609,654-671`)。**結果はtemplateの重複作成と、activeなscheduleの多重登録** — 本番ジョブの多重起動である。手動なら差分を読む人が気づくが、無人applyでは誰も見ない。
2. **比較器が判定不能を一致へ倒しうる。** `_target_fields()` / `_observed_fields()` が両辺を `arguments or []` / `survey_vars or []` / `description or ''` で畳む(`semaphore_templates.py:127-149`)。型を確かめずにtruthinessで畳むため、**実際に違っていても `unchanged` を返しうる。** さらに正規化は `read.yml:58-72` のAPI応答整形と filter の**二層にまたがっている**。

**scheduleについては「検知を同期へ置き換える」ではない。** 現在のドリフトprobeが生成するカテゴリは `semaphore_probe_error` と `semaphore_template` だけで、**scheduleは読んでいない**(`roles/deployment_drift_check/tasks/semaphore_probe.yml:63-122`)。schedule の日次applyは**新規の無人書き込み経路**であり、そのリスクは置き換えではなく新設として評価する。

## 2. ゴール

**Phase 1 — 機械の判断を信用できるようにする。** 異常なwrite-setで書かずに止まること、比較がフィールドごとに定義された正規形で行われること。**これは日次化と独立に、今日の手動applyにも効く。**

**Phase 2 — 日次同期へ移す。** template / schedule のreconcileを1日1回のapplyとして回し、通知を判断が要るものに絞る。

## 3. 非ゴール(やらないと決めたこと)

- **既存scheduleの `active` は同期しない。** ここだけはYoshinobuの意思が入る。**土曜のProxmox full patchを、金曜のdry-run結果を見て「今週は止める」と判断する運用が現にある**(Yoshinobu、2026-09-15)。カタログが `active: true` を持つからといって機械が翌日戻してはならない。**新規作成時はカタログの値で作る**(従来どおり)。**ただし非canonical接続先では、新規作成・既存更新のいずれでも `active: false` として書く**(P0-15)。
- **配備物(`/usr/local/` のscript・unit)のドリフト検査は変えない。** 直すのに「配備する」という別種の行為が要り、人の判断に値する。
- **orphan template の自動削除はしない**(現行R5を維持)。消すか取り込むかは人が決める。
- **UIでの一時変更を禁止しない。** 1日で戻ってよい変更はUIで、長く効かせたいものはcommitする。
- **停止日数(N日)を持たない。** 金曜の一覧方式(§5 P0-6)を採ったため、履歴も永続状態も不要になった。
- 通知経路の再設計はしない(既存のSlack経路と、既存のtoken scrub済み経路をそのまま使う)。

## 4. ユーザーストーリー

- Yoshinobuとして、カタログを直したら、押さなくても本番が追従してほしい。
- Yoshinobuとして、**土曜のパッチを止めた週は、止まったままでいてほしい**。ただし**毎週金曜に「いま止まっているもの」を知らせてほしい**。
- Coordinatorとして、同期が効いていないときに**それが観測できてほしい**。黙って一致と言われるのが最も困る。

## 5. 要件

### Phase 1(先に実施。これ単体で完結し、手動applyにも効く)

- **P0-1 write-set preflight(査読 Critical 1)。** 書き込みの前に、読み取った一覧そのものを検査する。
  - **カタログが非空なのに観測が空**なら、**書き込み0件・rc非ゼロ・通知あり**で止める。
  - 各行の**identityとschemaを全件検証**する(id が整数であること、markerが解釈できること、**同じidentityが重複しないこと**)。1行でも壊れていれば止める。
  - **無人実行で1回に作成してよいtemplate / scheduleの上限**を設ける。既定値は小さくし、超えたら止める。**明示的な変数指定があるときだけ上限を超えられる**(正当な一括追加は人が押すときに起きる)。上限値と変数名は実装時に決め、defaultsへ置く。
- **P0-2 フィールド別の正規化契約(査読 Major 2)。** 「欠落 / `false` / `""` / `null` / `{}` を一括で同義」としない。**対象フィールドごとに、受理する入力型・正規形・同値とみなす対・拒否する型を表にして文書化し、実装をそれに合わせる。** 少なくとも次を個別に定める — `arguments` / template の `survey_vars` 本体 / survey要素の各キー(`required`、`default_value`、`type`、`values` 等)/ marker である `description` / schedule の detail と `task_params`。
- **P0-3 正規化の所有層を1つに決める(同 Major 2)。** API応答の型合わせ(`read.yml`)と比較用の正規化(filter)が現在二層にまたがっている。**どちらが何を所有するかを決め、二重に正規化しない。**
- **P0-4 truthinessで畳まない。** `x or []` の形を、型を確かめたうえでの正規化へ置き換える。**想定外の型は一致とみなさず、非ゼロで停止し、対象名とフィールドパスを出す**(`docs/ai/core.md`「判定できないときは止める」)。schedule側の `detail_by_id.get(sched_id) or {}`(`semaphore_schedules.py:613`)も**API detailの型検証欠落**として同じ観点で扱う(査読の指摘どおり、template側と因果は同一ではない)。

### Phase 2(Phase 1 完了。2026-09-15の計画査読 `_007` を反映して再査読へ)

- **P0-5 日次reconcile。** template / schedule のreconcileを **毎日 04:00 JST** に apply として実行する。実行基盤は **Semaphore schedule**。**既存scheduleの更新では `active` を書き換えない** — 書き込み直前のfresh GETの値をpayloadへ保存し、`active` 単独の差を通常の `changed` に数えない。新規作成は従来どおりカタログの値を使う(**非canonical接続先での扱いは P0-15 が上書きする**)。
- **P0-6 金曜の停止一覧。** **毎週金曜(`Asia/Tokyo` 基準)、実物で `active: false` のscheduleがあれば一覧で通知する。** 無ければ通知しない。**金曜以外は、停止があっても一覧を出さない。** 停止日数は数えない。
- **P0-7 更新数の上限(査読 Finding 1 / 再査読 Major 1)。** 無人実行で適用してよい**更新件数**に上限を設ける(template + schedule の合算)。超えたら**両資源とも書き込み0件・rc非ゼロ・通知試行あり**で止める。**明示的な変数指定があるときだけ超えられる**(作成上限と同型)。
  - **既定値は `semaphore_reconcile_max_updates: 4`(合算)。** 作成上限 `semaphore_reconcile_max_creates: 2` と同じ置き場(`roles/semaphore_templates/defaults/main.yml`)に置く。**カタログ規模(2026-09-16時点で template 57 / schedule 24)に依存しない固定値**とする — 規模に比例させると「全件changed」を止められないため。**1回のcommitが4件を超えるtemplate / scheduleを同時に変えるのは、カタログの一括置換か規約変更のときだけで、それは人が押す回である。**
  - **合算件数はtemplateのapplyより前に確定する。** 現行のtask順(template diff → report → apply → schedule read → diff → apply、`roles/semaphore_templates/tasks/main.yml:58-75,142-161`)では合算が取れない。
  - **ただし「両資源のdiffを先に完成させる」ではない(再々査読 Major 1)。** schedule diffは、**template applyの後でなければ決まらない値**を1つ持つ — 新規templateを参照するscheduleの `template_id` である(`roles/semaphore_templates/tasks/schedules_read.yml:2-7,14-17`、`schedules_preflight.yml:17-25`、`filter_plugins/semaphore_schedules.py:519-535`)。**同じ変更でtemplateとそれを参照するscheduleを足す経路はカタログが明記しており**(`defaults/main.yml:719-725`)、これを壊してはならない。
  - **分けるのは「計画」と「payload」である。**

| 段階 | いつ | 決まるもの | 決まらないもの |
|---|---|---|---|
| **計画(write前)** | 両資源の書き込みより前 | **write-setの対象と件数**(作成・更新それぞれ、template + schedule 合算)。**上限判定はここで行う** | 新規templateを参照するscheduleの `template_id`(**pendingとして計画に載せる**) |
| **payload確定(write中)** | template applyの直後 | pendingだった `template_id` を、POSTの応答で得た実idで埋める | — |

  - **計画段階で名前解決できない `template` 参照のうち、「今回作成する予定のtemplate」に無いものは従来どおり失敗させる**(R10の厳格さを落とさない)。
  - 超過時に「templateだけ適用済み」が発生しないことを実装記録とテストで示す。
  - **この上限が守るのは「人が書き間違えたcron」ではない。** 1件の誤りは件数で区別できず、上限をいくつにしても通る。**守るのは、望ましい状態を計算する機械が壊れて、write-setが人の手の大きさを超える形へ膨らむ場合**(カタログの一括置換、描画・比較ロジックの破損で全件が `changed` になる等)である。Phase 1 の作成上限が「読みが壊れて全件newになる」形に置かれたのと対称の位置づけ。
  - **残存リスクとして明記する**: **1件の書き間違いは、commitのレビューだけが防ぐ。** 本機構はそこを守らない。
- **P0-8 成果物を2つに分ける(査読 Finding 3 / 再査読 Major 2)。** 1つのファイルに「毎回の記録」と「最後に成功した印」を兼ねさせない。失敗runはsuccess reportを更新できず、report保存の失敗自身をそのreportへ書けないためである。

| 成果物 | path | 書く条件 | 持つもの |
|---|---|---|---|
| **run report(毎回・不変)** | `<report_dir>/reconcile/runs/<run_id>.json` | **成否によらず毎回**、runの最後に原子的publish | run id / 開始・完了時刻(JST) / mode / 資源ごとのplanned・actual件数 / 部分適用の内訳 / 最終status / 通知試行の結果 |
| **latest-success marker** | `<report_dir>/reconcile/latest-success.json` | **全applyとverifyが成功した回だけ**原子的に差し替え | run id / 完了時刻(JST) / 参照するrun reportのpath |

  - **失敗した回は latest-success を触らない**(前回の成功が残る)。生存確認(P0-13)が見るのは latest-success だけである。
  - **既存の2つの `latest.json` は資源別のdiff / outcomeとして残す**(廃止しない)。**それらは生存確認の正本ではない**ことを、role内のコメントとSystem Contextへ明記する。
  - **`run_id` は `<開始時刻JST、ミリ秒精度>-<Semaphore task id または `manual-<pid>`>`** とし、**手動runが同時刻に重なってもpathが衝突しない**形にする(再々査読 Suggestion 1)。
  - **run report自身の保存に失敗した回**は、下表のとおり rc非ゼロで終える。**保存できなかった事実はSlack通知本文が運ぶ**(代替証跡)。
  - **publishの順序と、markerが指す先(再々査読 Major 2)。** ①run reportをtemp→原子的publish ②markerをtemp→原子的差し替え、の順に行う。**markerは必ず、既にpublish済みのrun reportを指す**(逆順にすると、存在しないreportを指すmarkerが一瞬できる)。
  - **run reportはmarkerの成否を持たない(第4次査読 Major 1)。** run reportは自分より後に起きる事象を記録できない。**「印が更新されたか」の正本はmarkerそのもの**であり、`run_id` がその回のものになっているかで読む。**run reportが持つのは `status`(success / partial / failed)まで。**
  - **したがって「reconcileは全成功したが印を更新できなかった」回は、次の3つで観測する** — 最終rcが非ゼロ、通知が出ている、**markerの `run_id` が最新のrun reportを指していない**。run report側は `status=success` のままで正しい(reconcile自体は成功しているため)。
  - **生存確認(P0-13)が見るのはmarkerだけである。** marker更新に失敗した回は、**古いmarkerのまま残るのが正しい** — 印が更新されていないのは事実だからで、閾値を超えればfindingが出る。

- **P0-8a 失敗時の状態表(再査読 Major 2)。** 7ケースについて、次を固定する。**「通知あり」は配送成功ではなく、`common_slack` のinclude到達を指す。** evidence生成もSlack送信も `common_slack` がbest-effortで吸収する(`roles/common_slack/tasks/notify.yml:44-51`)ため、**配送成功を成否の根拠にしない。**

| ケース | notify include到達 | evidence | Slack送信 | 最終rc | run report | latest-success |
|---|---|---|---|---|---|---|
| 全成功・変更あり | する | 生成 | 試行 | 0 | 保存(status=success) | **更新** |
| 全成功・変更なし | **しない** | なし | なし | 0 | 保存(status=success) | **更新** |
| template途中失敗 | する | 生成 | 試行 | 非ゼロ | 保存(status=partial、適用済み件数を明記) | **据え置き** |
| schedule途中失敗 | する | 生成 | 試行 | 非ゼロ | 保存(status=partial、同上) | **据え置き** |
| run report保存失敗 | する | 生成 | 試行 | 非ゼロ | **無し**(保存できなかった旨を通知本文が運ぶ) | **据え置き**(reportが無いものを指せないため更新しない) |
| **latest-success publish失敗**(applyとverifyは全成功) | する | 生成 | 試行 | **非ゼロ** | 保存(`status=success`) | **据え置き**(旧markerが残る。**最新のrun reportを指していないことが、失敗の証跡である**) |
| evidence生成失敗 / Slack送信失敗 | する | 無し / 生成 | 失敗 | **その回の本来のrc**(送信失敗でrcを変えない) | 保存 | **本来の条件どおり** |
- **P0-9 通知は起きたことだけ。** 通知するのは、**変更を適用した回 / reconcileが失敗した回 / canonical不一致で書き込みを拒否した回 / orphan集合がbaselineから変わった回 / 金曜で停止がある回**。**「変更なし」を「変更・警告条件・失敗のいずれも無い」と定義し、その日は通知しない。**
  - **「通知あり」は配送成功を意味しない(査読 Finding 4)。** `common_slack` は送信失敗をbest-effortで吸収する。**観測可能な定義は「`common_slack` のinclude へ到達したこと」**とする(evidence生成も吸収されうるため、evidenceの有無は必須条件にしない)。
  - ケースごとの対応は **P0-8a の表が正本**である。
- **P0-10 失敗通知に秘密を載せない。** 既存のtoken scrub済み経路だけを使い、生の `ansible_failed_result` や Authorization の値を、Slackにも0644のレポートにも出さない。**通知wrapperはroleが整形済みの情報だけを受け取り、生の失敗値を読み直さない。**
- **P0-11 orphanは集合で比較する(査読 Finding 6 / 再査読 Major 6)。** 件数ではなく、**環境を越えて意味が保てるkey(正規化した name / playbook の組)**で比較する。**Semaphoreの数値idはansy / quoryで異なり復元でも変わるため、baselineに使わない**(診断情報としてのみ出す)。**baselineの更新はreview済みのcommitで行い、日次runが自動学習しない。**
  - **置き場は `roles/semaphore_templates/defaults/main.yml` の `semaphore_templates_orphan_baseline`。** 実値は **1件のみ** — `{ name: "SEMI-SAFE: Semaphore templates setup", playbook: "playbooks/semaphore_templates_setup.yml" }`(2026-09-16にquory API `/project/1/templates/37` で確認。ansyにも同名・同playbookで存在する)。
  - **正規化契約**: `name` は前後の空白を除去し、内部の連続空白を1つへ畳む。**大小文字は変えない**(別のtemplateを同一視しないため)。`playbook` はrepo相対pathとして扱い、先頭の `./` を除去し、区切りは `/` のまま。**いずれも空文字列になったらbaseline不正として失敗**させる。
  - **比較はsorted listで行う**(数学的setにしない)。同じkeyのorphanが1件から2件へ増えた場合も差分として現れる。
  - **baselineが欠落 / 型違い / 要素にキー欠落があるときは、正常扱いにせず失敗**させる。
- **P0-12 ドリフト検査の識別子ごとの処遇(査読 Suggestion 3 / 再査読 Major 4)。** 現行のSemaphore probe(`roles/deployment_drift_check/tasks/semaphore_probe.yml:63-122`)が生成する3つを、次のとおり確定する。

| 識別子 | 処遇 | 理由 |
|---|---|---|
| `semaphore_template` | **撤去(remove)** | 日次reconcileが同じ差分を直す。残すと「直った後に鳴る」か「直す前に鳴る」かのどちらかになり、毎日の通知が判断の要らないもので埋まる |
| `semaphore_probe_error` | **維持(keep)** | API到達・認証・応答形式の観測であり、reconcileが置き換えない。**reconcileが動かない日にこれだけが残る** |
| `checked_counts.semaphore_templates` | **維持(keep)** | 「何件見たか」の可視化で、findingではない |
| `semaphore_reconcile_stale`(新設) | **追加(add)** | P0-13の鮮度finding。categoryの文字列はこの名前で固定する |
- **P0-13 生存確認の範囲を正直に絞る(査読 Finding 2、Yoshinobu決定 2026-09-15)。** 残すドリフト検査に「reconcileの最終success reportが古ければfinding」を持たせる。**ただしこれが検出できるのは「reconcileのscheduleだけが壊れた場合」である。**
  - **Semaphore service停止・quory停止では、監視する側(00:40のドリフト検査)も同じschedulerから起動されるため走らない。** この機構ではそれを検出できない。**これはPhase 2が持ち込む欠陥ではなく、既存の日次ジョブすべてに等しくかかる既存条件である。**
  - **SLOと閾値(再査読 Major 3)。** **04:00の欠測は、次の00:40のドリフト検査で検知する。** 位相差20時間40分から、閾値は次の算数で決まる。

| 時点 | latest-successの経過時間 | 期待 |
|---|---|---|
| 正常時の00:40(前日04:00が最後の成功) | **20時間40分** | findingを出さない |
| 04:00を1回落とした翌日の00:40 | **44時間40分** | **findingを出す** |

| 実物の状態(非canonical) | 振る舞い |

## 6. 受入条件

### Phase 1

- **AC1** Given カタログが非空、When 一覧APIがHTTP 200で空配列を返す、Then **書き込み0件・rc非ゼロ・通知あり**で停止する。
- **AC2** Given 一覧の応答に、idが欠落した行・markerが解釈できない行・identityが重複する行のいずれかがある、When reconcileする、Then **書き込み0件・rc非ゼロ**で停止し、どの行のどの問題かがログに出る。
- **AC3** Given 上限を超える新規作成が算出された(既定値は実装時に決定)、When **無人実行**、Then 書き込み0件・rc非ゼロ・通知あり。When **明示の変数指定あり**、Then 実行できる。
- **AC1a** Given 一覧に**markerを持たない行**(自己参照template `Semaphore templates setup` と同じ形。quoryで `id=37`、ansyで `id=81` として恒久的に存在する)が含まれる、When preflightする、Then **通る**。その行はorphanとして扱われ、書き込みは阻まれない。**markerの不在はread-setの破損ではない。**
- **AC5a** Given 実物の `arguments` が `false` / `null` / `"[]"` / `[]` のいずれか、When preflightと比較を通す、Then **preflightは通り、比較は一致**になる(preflightの型受理範囲が正規化表と一致していること)。
- **AC4** Given カタログが `required: false` / `default_value: ""` を明示したsurvey var、When 実物がそれらを返さない、Then 比較は**一致**(2026-09-15のIncidentの再発防止)。
- **AC5** Given 実物の `arguments` が `false`、カタログが `[]`、Then **一致**。Given 実物が `["--limit","quory"]`、カタログが `[]`、Then **不一致**として変更に現れる。
- **AC6** Given 比較対象が想定外の型(例: `survey_vars` が文字列、schedule detail が非mapping)、When 比較する、Then **一致とみなさず非ゼロで停止**し、**対象名とフィールドパス**がログに出る。
- **AC7** Given 同じカタログと同じ実物、When reconcileを2回続けて実行する、Then 2回目は**変更0件**(冪等性)。
- **AC8** Given 1回目の途中で失敗した、When 再実行する、Then 重複作成が起きない。

### Phase 2

- **AC9** Given カタログが `active: true`・実物が `false` のschedule、When 日次reconcileが走る、Then **`active` は書き換えず**、他のフィールドだけ同期する。rc=0。**diff後からfresh GETまでの間にactiveが変わっても、fresh値を保持する。**
  - **AC9a** Given `active` だけが異なる(他フィールドは一致)、Then **changed=0**。ただし金曜であれば P0-6 の一覧には載る。
  - **AC9b** Given 実物が `active: false` かつ `cron_format` に差がある、When PUTする、Then 書き込み後のverifyでも **`active` は `false` のまま**で、`cron_format` だけが揃う。
- **AC10** Given 金曜(`Asia/Tokyo`)、実物で `active: false` が1件以上、Then **一覧が通知される**。Given 金曜で停止0件、Then 通知しない。**Given 金曜以外、停止が1件以上あっても、一覧は通知しない。**
- **AC11** Given 無人実行で更新件数が **4件**(= `semaphore_reconcile_max_updates` の既定)、Then 適用しrc=0。Given **5件**、Then **template・scheduleとも書き込み0件・rc非ゼロ・通知試行あり**。**5件のケースは3通り試す — template側だけで5件 / schedule側だけで5件 / template 2件 + schedule 3件の混在。** 混在で止まることが、資源ごとの上限で判定する誤実装を落とす。Given 明示の変数指定あり、Then 5件でも適用できる。**上限判定がtemplateのapplyより前に行われることを、「templateだけ適用済み」が発生しないことで示す。**
  - **AC11a** Given 同じ変更で**新規templateと、それを参照する新規schedule**を足す、When 上限内、Then **両方が作られ、scheduleの `template_id` が作成されたtemplateを指す**。When 上限超過、Then **どちらも作られない**。
- **AC12** Given 変更・警告条件・失敗のいずれも無い日、Then **通知なし・rc=0**、**latest-success markerが更新され、その回のrun reportも保存される**。
- **AC13** Given P0-8a の**7ケース**、Then 各行の **notify include到達 / evidence / Slack送信 / 最終rc / run report / latest-success** が表のとおりになる。**Slack送信失敗・evidence生成失敗でも最終rcを変えない。** **失敗した回に latest-success が前回の値のまま残ることを確認する。**
  - **AC13a** Given applyとverifyは全成功したが **latest-success の差し替えに失敗**、Then **rc非ゼロ**、run reportは **`status=success`** で保存され、**markerは前回の値のまま(その回の `run_id` を指していない)**である。**その後にドリフト検査が走ると、閾値を超えていれば `semaphore_reconcile_stale` が出る**(印が更新されていないことは事実であり、隠さない)。
  - **AC13b** Given run reportのpublish、Then **markerが指すpathは常に既に存在するrun report**である(marker先行publishの実装を落とす)。
- **AC14** Given APIへ到達できない / tokenが読めない、Then **rc非ゼロ・通知試行あり**。**token および生のAPI失敗文が、通知本文・run report・latest-success・既存のtemplate / schedule レポート・console log・notification evidence のいずれにも含まれない。**
- **AC15** Given orphan集合がbaselineから変わった(追加 / 除去 / **同数の1対1入替** / **同一keyの重複追加(1件→2件)**)、Then 通知あり。Given 並び順だけの違い、Then 通知しない。Given baselineが**欠落 / 型違い / 要素のキー欠落**、Then 正常扱いにせず失敗させる。
- **AC16** Given latest-success markerの経過時間が **20時間40分(正常時の位相)**、Then findingを出さない。Given **ちょうど24時間**、Then **findingを出す**。Given **44時間40分(1回欠測の翌00:40)**、Then findingを出す。Given 欠落 / 通常ファイルでない / 読めない / JSON不正 / 未来時刻、Then findingを出す。**categoryは `semaphore_reconcile_stale`。**
- **AC17** Given ドリフト検査、Then **`semaphore_template` のfindingは出ない**。**`semaphore_probe_error` はAPI到達失敗時に従来どおり出る**。**`checked_counts.semaphore_templates` は従来どおり出る**。配備物probeのfindingは従来どおり出る。
- **AC18(bootstrap)** Given repoへPhase 2をcommitした状態、When Yoshinobuが既存の手動templateを押す、Then 04:00のscheduleが作成される。**API readbackで、P0-14のカタログ行と `name` / `template_id`(= bootstrap template)/ `cron_format` = `0 4 * * *` / `active` = `true` / `task_params.environment` の2値が一致すること、および `params.dry_run` が存在しないことを確認**し、**初回の04:00実行**のrun report・latest-success・通知(変更なしなら通知なし)を確認する。**実ホストへの適用はYoshinobuの操作とし、Implementer / Reviewer / Testerは行わない。**
- **AC19(P0-15)** 接続先が非canonical(ansy)のとき、次の6ケースを固定する。

| # | Given | Then |
