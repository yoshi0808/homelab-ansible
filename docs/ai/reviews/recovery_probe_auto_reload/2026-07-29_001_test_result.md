## 受入条件ごとの判定

### 1. quoryは `-e` なしで `recovery_probe_service_enabled` が true として解決される。ansyはfalseのまま

**PASS(実測)。**
`ansible-inventory --host quory` → `"recovery_probe_service_enabled": true`。
`ansible-inventory --host ansy` → キー自体が出力されない(=inventory層では未設定、
role defaultの `false` にフォールバックする設計どおり)。
playbook実行ログでも quory では `Enable and start recovery-probe (production only)` が
`ok`(実行された)、ansy では同タスクが `skipping` になっており、実行時の変数解決結果と
一致している。

### 2. `-e` なしで quory に対して完走し、新設2 task(稼働状態取得/新旧比較)が実行されPASSする(skipなら不可)

**PASS(実測)。**
`ansible-playbook playbooks/recovery_probe_setup.yml -l quory` の実行ログ:

```
TASK [recovery_probe : Check whether recovery-probe is already running] ... ok: [quory]
TASK [recovery_probe : Record whether recovery-probe was running before this deploy] ... ok: [quory]
...
TASK [recovery_probe : Flush handlers so the freshness check observes the restarted daemon]
TASK [recovery_probe : Collect daemon start time and deployed file mtimes] ... ok: [quory]
TASK [recovery_probe : Assert the running process is not older than what was deployed] ... ok: [quory]
PLAY RECAP: quory : ok=17 changed=0 unreachable=0 failed=0 skipped=0 rescued=0 ignored=0
```

`skipped=0`。新設2 task(状態取得task、および末尾のfreshness assertブロック)は
どちらもskipされず実行され、assertは `ok`(fail_msgに到達していない)。

### 3. その実行によってrecovery-probeが再起動されないこと(プロセス側の事実で判定)

**PASS(実測)。**
実行前後で `ExecMainStartTimestamp` を比較:

- 実行前: `ExecMainStartTimestamp: Wed 2026-07-29 18:44:33 JST`(`ActiveState: active`)
  — これは一次記録(2026-07-29_002_test_result_deployed.md)にある手動restart時刻と一致。
- quory実行後: `ExecMainStartTimestamp: Wed 2026-07-29 18:44:33 JST`(変化なし)
- ansy実行後(quory側を再確認): 同じく `18:44:33 JST` のまま変化なし

`PLAY RECAP` の `changed=0` とも整合しており、handlerは発火していない
(発火条件 `recovery_probe_service_enabled | bool or recovery_probe_running_before | bool`
のうちrestartトリガーとなる「配備物の変更」自体が今回発生しなかったため、
そもそもnotifyされていない — configはすでに18:44:33の反映で最新)。

### 4. ansyに対して同じplaybookを実行しても、ansyのrecovery-probeが起動していない状態のままであること

**PASS(実測)。**
実行前: `ansible ansy -m systemd -a "name=recovery-probe" -b` → `ActiveState: inactive`, `SubState: dead`
`ansible-playbook ... -l ansy` 実行ログ: `Enable and start recovery-probe (production only)` は `skipping`、
freshness関連3 taskも `skipping`(`recovery_probe_service_enabled=false` かつ
`recovery_probe_running_before=false` のため、freshness blockのwhen条件が成立せず)。
`PLAY RECAP`: `ansy: ok=14 changed=0 ... skipped=3`。
実行後の再確認: `ActiveState: inactive`, `SubState: dead` のまま。

### 5. 実行の前後で、監視がpauseされておらず、通知キューに新規の通知が積まれていないこと

**PASS(通知キューは前後比較で確認、pauseフラグは事後確認のみ)。**

- 通知キュー: `/var/lib/homelab-recovery/probe/notify-queue` は実行前・quory実行後とも
  中身は空(`total 8`, `.`/`..`のみ)で新規ファイルなし。
- monitoring pauseフラグ: `/var/lib/recovery-exec/workspace/monitoring-paused` は
  今回の一連の作業完了後に確認し `exists: false`。**事前値は別途取得していない**が、
  今回実行した全taskの中に当該パスへ書き込むものは存在しない
  (`grep` で `roles/recovery_probe/files/recovery-probe.py` 内の参照箇所を確認した限り、
  読み取り専用の分岐条件としてのみ使われ、playbook側のどのtaskもこのパスへ
  書込・削除を行わない)。よってplaybook実行がpause状態を変化させる経路は無いと判断する。
- mute dir(`/var/lib/homelab-recovery/mute`)も実行前後で比較し、既存の
  `authy.json`(`until: 2026-07-25T12:52:58+09:00`)/`sophos-fw.json`
  (`until: 2026-07-25T12:53:00+09:00`)は既に期限切れの残存ファイル(無関係な過去のpve1
  evacuation起因、mtimeは7/25のまま)で、今回の実行前後を通じて内容・mtimeとも不変。
  新規mute/通知は発生していない。
