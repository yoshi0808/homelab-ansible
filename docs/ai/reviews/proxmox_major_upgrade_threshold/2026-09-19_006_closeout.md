## 4. レビューで見つかったもの

**どちらの回も、実装の誤りではなく「範囲の取り違え」だった。**

- `_003`: 閾値を上げると **51〜100件・重要コンポーネントあり・remove無しの帯が人を通さず当たる**。Policyの2026-08-01決定とは整合しており、**件数50だけが取り残された歯止めだった**という整理でYoshinobuが受け入れた(§6)。
- `_004`: 予告の導入文が node を限定せず「翌朝のapplyは自動適用されません」と書いていた。**ただし査読が挙げた機構は誤っていた** — 「超過していない他nodeは独立に適用される」ではなく、**適用順に依存する**。weekly fullはpve2を先、pve1を後に置くため、先のnodeが超過すれば run 自体が終わり後のnodeは適用されず、後のnodeが超過すれば先のnodeは既に適用済みである。2026-09-19の#1164で、pve2の停止後にpve1のapplyが一度も走っていないことをCoordinatorが実測し、機構を訂正して差し戻した。

**Coordinatorが独立に持っていた懸念2件の扱い。**

- 閾値を`lookup('file')`で読む件 → `_004` Suggestion 2として同じものが挙がった。repo内にoverrideが無いことのgrep確認が付き、申し送りへ(§7)。
- removeがcluster和集合のままである件 → **Coordinatorの誤りだった。** weekly full自身の事前ゲート`_wf_remove_count`(`playbooks/proxmox_patch_weekly_full.yml:378`)が同じcluster和集合を使っており、実際のゲート単位に一致している。node単位へ直す方が誤りになる。

## 5. 残存事項

- **`MAJOR_UPGRADE_DETECTED`が2つの段で別基準である**(requirement §7)。2026-09-19は金曜が「major upgradeや置換は検出されませんでした」、土曜が`MAJOR_UPGRADE_DETECTED`で停止と、正反対の判定になった。閾値を100にして衝突頻度は下がるが、名前の重複は残る。**本案件では扱わない。**
- **予告が読む閾値は実行時に効く値ではなくdefaultsファイルの内容である**(requirement §7)。現時点でoverrideは無いが、入ったときに乖離を検知する機構は無い。
- `BLOCKED` / `NO_UPDATES` では予告taskごとskipされる。これらは既存の専用通知が非自動適用を告知済みであり、欠陥として扱わない(`_005`)。

## 6. 次に観測できること

**2026-09-25(金)の dry-run 通知に、予告の節が出るか出ないか。** 出ない(=翌朝そのまま当たる見込み)が期待値である。2026-09-19時点で 88件・remove 0・閾値100 のため、件数超過の枝には入らない。**この案件が狙ったのは「出るべきときに出る」ことなので、出ないこと自体は失敗ではない。**
