# Proxmox apply段のmajor upgrade閾値を100へ揃える

状態: 要件確定(Yoshinobu決定、2026-09-19)。

## 1. 問題定義

2026-09-19 06:00 JSTの`UN-SAFE: Proxmox patch weekly full`(ジョブ#1164)が、pve2で `MAJOR_UPGRADE_DETECTED: major upgrade suspected (88 packages exceed threshold 50)` として停止した。

**判定は2段あり、今回は食い違った。**

| 段 | 機構 | 今回 |
|---|---|---|
| 週次dry-run(cluster) | `roles/proxmox_patch_dryrun/tasks/main.yml:286` — `codex_output.status_inputs.major_upgrade_suspected`。**数値閾値を持たない** | 通した(通さなければapplyへ進まない) |
| apply直前のre-dry-run(node) | `roles/proxmox_patch_apply_node/tasks/main.yml:282` — `_sim_updates \| length > 50` | 止めた(88件) |

**内容を見る側はmajorと判定しておらず、件数の側だけが止めた。** 88件は積み残しではない — 直前のweekly fullは#1069(2026-09-11)がsuccessで、**1週で88件**である。

上流の既知問題は全件が該当しないことを確認済み(pve-manager 9.2.18 / proxmox-ve 9.2.0、major versionをまたがない。`pve-ha-manager`は両ノード5.2.5で、5.2.4未満が対象のHA stall該当せず。Windowsゲスト無し、MTU 1500、OVHでない、cgroupv1は通過済み)。

同じ`MAJOR_UPGRADE_DETECTED`という名前で、Ubuntu側は`ubuntu_vm_full_upgrade_major_total_threshold: 100`を使っており、**数が揃っていない。**

## 2. ゴール

Proxmox apply段の件数閾値をUbuntu側の総数閾値と同じ100に揃える。あわせて、Policyから閾値の実体へ辿れるようにする。

## 3. 非ゴール

- **remove側の閾値を新設しない。** Ubuntuは`remove > 30`でmajorへ倒すが、Proxmoxは**removeが1件でもあれば確認必須**(`_redryrun_has_removes` → `MAINTENANCE_REQUIRED` + 一致する確認文字列)で既に厳しい。揃えると緩む。
- **dry-run段(`proxmox_patch_dryrun`)を変更しない。** こちらは数値閾値を持たない設計である。
- **Policyへ数値を書かない。** 値の正本は role の default のままとする。

## 4. 要件

### P0 / Must

- `roles/proxmox_patch_apply_node/defaults/main.yml` の `proxmox_patch_apply_major_upgrade_threshold` を `50` から `100` にする。
- `docs/ai/policies/proxmox_operations_policy.md` SB-041 へ、閾値の実体が各roleのdefaultであることを示す1行を置く(数値は書かない)。変更履歴へ追記する。
- **金曜のdry-runが、翌朝のapplyがそれを自動適用するかどうかを先に判定し、しない場合は理由とともに通知へ出す。** dry-runの`_final_status`は変えない(止めない)。
- **その判定に使う件数を、applyが評価するのと同じ単位に揃える。** 現状はdry-runがcluster和集合、applyがnode単位で、別々の量を同じ閾値と比べている(§4.1)。

### 4.1 件数の齟齬

| 段 | 使っている数 | 実体 |
|---|---|---|
| dry-run通知 | `unified_dryrun.cluster_summary.total_unique_updates`(`tasks/main.yml:335`) | **pve1とpve2の和集合**。`files/proxmox-dryrun-merge.py:86`が`updates_list`をパッケージ名で重複排除した長さ |
| apply再dry-run | `_sim_updates \| length`(`roles/proxmox_patch_apply_node/tasks/main.yml:282`) | **その node 1台分** |

ノード間で導入済みパッケージが異なれば和集合の方が大きくなるため、両者は原理的に一致しない。**node別の件数は`unified_dryrun.node_summaries[<node>].update_count`として既に存在する**(`proxmox-dryrun-merge.py:78`)。

`remove_count`も同じくcluster和集合である(`tasks/main.yml:336`)。`_has_removes`も`unified_dryrun.removes | length > 0`(`tasks/main.yml:260`)でcluster和集合から導かれる。node別のremove件数は`node_summaries[<node>].remove_count`として存在する(`proxmox-dryrun-merge.py:79`)。

**2026-09-19の実測で齟齬が出ている。**

| 段 | 通知に出た数 | 単位 |
|---|---|---|
| 金曜17:40 dry-run #1153(`#patches`) | 「**pve1/pve2共通で87件**の更新、削除は0件」 | cluster |
| 土曜06:16 apply #1164(`#alerts`) | 「**更新パッケージ数: 88** / remove 数: 0」 | pve2のnode単位 |

**87と88。** 閾値と比較されるのは後者だけで、人が前夜に見るのは前者である。

## 5. 受入条件

- AC1: Given 変更後のrepo、When `proxmox_patch_apply_major_upgrade_threshold` を検索、Then 値は `100` であり、`50` を持つ箇所は残っていない(過去の案件記録を除く)。
- AC2: Given 変更後のrepo、When `50` をハードコードしたテスト・fixtureを検索、Then 存在しない。
- AC3: Given 89件以上のsimulated updates、When re-dry-run分類、Then `MAJOR_UPGRADE_DETECTED` にならない(100以下のため)。Given 101件、Then `MAJOR_UPGRADE_DETECTED` になる。
- AC4: Given remove 1件以上、When re-dry-run分類、Then 件数によらず確認必須のままである(非ゴールの確認)。
- AC5: Given SB-041、When 読む、Then 閾値の実体の所在へ辿れ、かつ数値は書かれていない(**どのroleのdefaultかを名指しする**)。
- AC6: Given 翌朝のapplyが自動適用しない入力、When 金曜のdry-runが走る、Then 通知に「自動適用されない」ことと**その理由**が出る。Given 自動適用される入力、Then その警告は出ない。
- AC7: Given dry-runの予告判定、When 件数を閾値と比べる、Then 比較しているのは**applyが評価するのと同じnode単位の件数**であり、cluster和集合ではない。
- AC8: Given 予告判定のいずれの分岐、When dry-runが完了、Then `_final_status`と終了コードは予告の有無で変わらない(止めない)。

## 6. 影響(確定)

**51〜100件・重要コンポーネントあり・remove無しの帯は、閾値を100にすると人を通さず自動適用される。** 分類は`major → elif (important or removes) → else PATCH_READY`の順で、確認必須になるのは`MAJOR_UPGRADE_DETECTED`か`MAINTENANCE_REQUIRED かつ remove あり`だけだからである(`roles/proxmox_patch_apply_node/tasks/main.yml:283-315`)。従来この帯は件数だけで止まっていた。

**#1164はこの帯そのものだった。** 金曜#1153の通知が「pve1/pve2共通で87件の更新、**削除は0件**」と述べており、cluster全体でremoveが0である。したがって金曜の`MAINTENANCE_REQUIRED`は**重要コンポーネント由来**であり、通知が名指ししているのは`Proxmox kernel` / `pve-manager` / `qemu-server` / アクセス制御関連である。

apply側が評価したpve2自身の値は**88件 / remove 0**(#1164通知)。閾値100ならmajorにならず、removeが0である以上、確認必須の枝(`MAINTENANCE_REQUIRED かつ remove あり`)には原理的に入らない。**重要コンポーネントの有無によらず、土曜は無人で適用されていた。**

**これはPolicyと矛盾しない。** 2026-08-01に「重要コンポーネント更新を自動適用しない」という目的を撤回し、removeを伴わない`MAINTENANCE_REQUIRED`を自動適用すると決めている(SB-003 / SB-027 / SB-039)。**件数50のゲートだけがその決定から取り残された歯止めだった。** Yoshinobuはこの帯の自動適用を受け入れたうえで、金曜の予告(P0-3)で可視性を確保する判断を採った(2026-09-19)。

## 7. 申し送り(本案件のスコープ外)

**2つの段が`MAJOR_UPGRADE_DETECTED`という同じラベルを別の基準で使っている。** 2026-09-19の実測では正反対の判定になった。

- 金曜 dry-run #1153: 「**major upgradeや置換は検出されませんでした**」(内容ベースの判定)
- 土曜 apply #1164: 「`[ABORT] MAJOR_UPGRADE_DETECTED 検出`」(件数ベースの判定)

閾値を100へ上げると衝突する頻度は下がるが、**同じ名前が2つの意味を持つ状態は残る。** 本案件では扱わない。

**予告が読む閾値は、実行時に効く値ではなく defaults ファイルの内容である。** `lookup('file', ...) | from_yaml` で `proxmox_patch_apply_node/defaults/main.yml` を直接パースしているため、Ansibleの変数優先順位を経由しない。**現時点でこの変数をoverrideする箇所はrepo内に無い**(2026-09-19の査読がgrepで確認)。将来 group_vars・Survey・`-e` でoverrideされると、予告と実際のapplyが食い違い、**それを検知する機構は無い**。値を複製しない要求とは両立しており、本案件では変更しない。
