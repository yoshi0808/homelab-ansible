# requirement: sandbox が自分でパッチを当て、必要なときに再起動する

起案: Coordinator / 2026-09-04 / 依頼者: Yoshinobu

## 1. 問題定義

**`sandbox` はセキュリティ更新しか当たらず、再起動を必要とする状態のまま放置される。**

2026-09-04にansyから実測した現況。

| 観測点 | 値 |
|---|---|
| OS / uptime | Ubuntu 26.04 LTS / **3週6日** |
| `unattended-upgrades` | `enabled` / `active`。毎日走っている |
| `Unattended-Upgrade::Allowed-Origins` | release + `-security` + ESM 2種。**`-updates` を含まない** |
| `Unattended-Upgrade::Automatic-Reboot` | **設定行が存在しない**(既定 `false`) |
| 保留更新 | **57件。すべて `resolute-updates`** |
| `/var/run/reboot-required` | **2026-08-22 から存在**(`linux-image-7.0.0-30-generic` / `linux-base`) |

**設定が壊れているのではない。** `ansy` の `/etc/apt/apt.conf.d/50unattended-upgrades` は sandbox と同じ内容である(同日実測)。本番ホストで `-updates` と再起動を担っているのは月次の `playbooks/ubuntu_vm_full_upgrade.yml`(`dev_nodes:control_nodes:radius_servers:monitoring_servers`)であり、**`sandbox_nodes` はそのレーンに入っていない。** 同日の ansy は保留27件・`reboot-required` 無しであり、差はこの構造から出ている。

**月次レーンへ `sandbox_nodes` を足す解は採れない。** 月次は quory の Semaphore から走るが、**quory は sandbox へ届く鍵を持たない**(`id_sandbox` は ansy 専用、2026-08-19に `id_ann` から分離)。採るには quory→sandbox の経路を新設することになり、承認境界の変更を伴う。

### 1.1 追記(2026-09-05、Tester の実機検証で判明)

**sandbox には `/etc/apt/apt.conf.d/52unattended-upgrades-local`(46バイト)が既にあり、`Unattended-Upgrade::Automatic-Reboot "false";` だけを持つ。** apt.conf.d はファイル名順に読むため、`52sandbox-auto-patch` より後(`s` < `u`)に読まれて勝つ。初回実装はこのファイルを知らずに `52` を選んでおり、**Allowed-Origins は効いたが再起動設定は無効化されていた**(AC1 FAIL)。Implementer と Reviewer のローカル fixture にはこのファイルが無く、**実機でしか出なかった。**

**出自は cloud-init の user-data(`write_files`)である。** ansy / sandbox の双方で `/var/log/cloud-init.log` に書き込みの記録があり、`/var/lib/cloud/instances/*/user-data.txt` に同じ `write_files` エントリがある。VMテンプレート作成時のものであり、手作業ではない(Yoshinobu、2026-09-05)。**`ansy` でも実効値は `Automatic-Reboot "false"` である** — 本番は月次playbookと03:30の条件付きrebootが再起動を担うため、これで正しい。

**sandbox の cloud-init は再実行されない。** `cloud-init status` は `disabled` / `disabled-by-generator`、旧datasourceは `DataSourceNoCloud [seed=/dev/sr0]` だが `lsblk` に `sr0` は無く、seed が外されている(2026-09-05実測)。最後の実行は2026-08-02。

**`docs/ai/context/operations/sandbox-vm.md` §2 は現況と食い違っている。** 「Allowed-Origins に `-security` と `-updates` の両方を含む」「パッケージを追随させるために何かをする必要はない」と書かれているが、`-updates` は含まれていない。

## 2. ゴール

1. **sandbox が自分で `-updates` まで当てる。** 外から何かを流す必要がない。
2. **再起動が必要になったとき、sandbox が自分で再起動する。**
3. **その設定が repo から再現できる。** バックアップから復元しても手作業でやり直さずに済む(`sandbox-vm.md` §6)。

## 3. 非ゴール(やらないと決めたこと)

- **quory から sandbox へ到達する経路を作らない。** 承認境界の変更であり、本案件の目的には要らない。
- **Semaphore に登録しない。** 設定を1回配ったあと、実行を担うのは sandbox 自身の apt timer である。schedule もtemplateも増やさない。
- **`sandbox` を他のグループへ足さない。** `inventories/homelab/hosts.yml` の `sandbox_nodes` の注記が禁じている。監視対象にもしない。
- **`/etc/apt/apt.conf.d/50unattended-upgrades` を書き換えない。** distro が配るファイルであり、パッケージ更新で衝突する。drop-in で足す。
- **本番ホストの unattended-upgrades 設定に触れない。** 本案件の対象は `sandbox_nodes` だけである。
- **保留中の57件とカーネル再起動を、手で先に解消しない。** 機械がそれを解消することが本案件の受入そのものである(§6 AC7)。
- **cloud-init の user-data(VMテンプレート側)を変更しない。** repo の管理外であり、変えると今後作る全VMに効く。本番の「unattended-upgrades に再起動させない」という現行の挙動まで変わってしまう。**sandbox 側で上書きする。**
- **`unattended-upgrades` 以外のパッチ経路を作らない**(snap、Pro の有効化など)。sandbox は Pro 未アタッチだが、本案件では変えない。

## 4. ユーザーストーリー

Yoshinobu が sandbox を使おうとしたとき、そのホストが数週間分の更新を溜め込んでおらず、再起動待ちのカーネルを抱えたままでもない。**そのために誰も何も実行しない。**

## 5. 要件(MoSCoW)

| # | 優先度 | 内容 |
|---|---|---|
| R1 | **P0 (Must)** | `sandbox_nodes` だけを対象に、unattended-upgrades の **drop-in 設定ファイル**を配る role と playbook を作る |
| R2 | **P0 (Must)** | drop-in が `Unattended-Upgrade::Allowed-Origins` へ **`-updates`** を追加する。既存の origin を減らさない |
| R3 | **P0 (Must)** | drop-in が **`Automatic-Reboot` を有効**にし、**再起動時刻を `04:00`** とする |
| R4 | **P0 (Must)** | **ログイン中のセッションがあっても再起動する。** 誰かが SSH を張りっぱなしにしたことで再起動が起きない状態を作らない(本案件が塞ごうとしている症状そのものになるため) |
| R5 | **P0 (Must)** | 値は role の `defaults/` に置き、時刻・origin・有効無効を変数で変えられるようにする |
| R6 | P1 (Should) | `playbooks/README.md` へ登録する |
| R7 | P1 (Should) | `docs/ai/context/operations/sandbox-vm.md` §2 を実測に合わせて書き直す。**「何もしなくてよい」という結論は成り立たない** |
| R8 | **P0 (Must)** | **drop-in が、同じキーを設定する既存ファイルより後に読まれること。** 現物では `52unattended-upgrades-local` がある(§1.1)。**`52unattended-upgrades-local` という名前を使い回さない** — 他ホストでは「cloud-init が書いた `false`」を意味しており、同じ名前に逆の意味を当てると横断して読む者が誤る |
| R9 | **P0 (Must)** | **配ったあと、実効値が意図どおりかを確かめ、違っていれば失敗する。** 書けたことと効いたことは別である(§1.1 がその実例) |
| — | Won't | Semaphore登録、quory経路、他グループへの適用、50番ファイルの改変、cloud-init user-dataの変更 |

**時刻 `04:00` の根拠**: Notion「バッチ処理工程管理表」を2026-09-04に確認した。日次の窓は 01:00(UniFi Console update / Proxmox ローカルバックアップ)、02:00(UniFi AP・スイッチ update)、03:00(UniFi Protect / quory の自動 reboot)、03:30(authy・monnie の条件付き reboot)で埋まっており、**04:00 から 05:30 まで空いている。** なお **quory は既に同じ機構(unattended-upgrades の `Automatic-Reboot`)を 03:00 で使っている** — 本案件はこの環境に前例のある形である。

## 6. 受入条件(Given/When/Then)

**AC1(設定が入る)**
Given playbook を sandbox へ適用した後
When `apt-config dump` を読む
Then `Unattended-Upgrade::Allowed-Origins` に `-updates` が含まれ、`Automatic-Reboot` が有効、`Automatic-Reboot-Time` が `04:00`、ログイン中でも再起動する設定になっている。**既存の `-security` / ESM の origin が消えていない。**

**AC2(検知に効く)**
Given 適用後の sandbox
When unattended-upgrades を dry-run で走らせる
Then **`-updates` 由来のパッケージが「アップグレード対象」として選ばれる**(適用前は0件だった)。

**AC3(冪等)**
Given 1回適用済みの sandbox
When 同じ playbook をもう一度実行する
Then `changed=0`。

**AC4(check mode)**
Given 未適用または適用済みの sandbox
When `--check` を付けて実行する
Then 異常終了せず、実ファイルが変更されない。

**AC5(既存ファイルの不変)**
Given 適用後の sandbox
When `/etc/apt/apt.conf.d/50unattended-upgrades` を見る
Then **内容が適用前と同一**である。

**AC6(索引と文書)**
Given 変更後の作業ツリー
Then `playbooks/README.md` に本 playbook の行があり、`docs/ai/context/operations/sandbox-vm.md` §2 の記述が §1 の実測と一致する。

**AC7(機械が実際に解消する ─ 観測)**
Given 適用後、sandbox をそのまま放置する
When 翌日以降に sandbox を見る
Then **保留していた `-updates` が当たっており、`/var/run/reboot-required` が消えている**(= 04:00 の自動再起動が起きた)。uptime がリセットされていることで確認できる。

**AC9(効いたことを機械が確かめる)**
Given `Automatic-Reboot` を `false` にする別の drop-in が、本 role の drop-in より後に読まれる名前で存在する状態
When playbook を適用する
Then **playbook が失敗する**(黙って成功しない)。意図した実効値になっているときは成功する。

**AC8(構文)**
Given 変更後の作業ツリー
When `ansible-playbook --syntax-check` を対象 playbook に対して実行する
Then 終了コード `0`。

## 7. 実行境界

- **対象ホストは `sandbox` のみ。** 承認境界では `monnie` / `ansy` と同じ「確認不要」側にある(`sandbox-vm.md` §1)。
- **Implementer は実ホストへ到達しない。** コードを書くところまでで、sandbox への適用は行わない。
- **sandbox への適用と AC1〜AC5・AC7 の検証は Tester が行う**(実ホストへ到達してよい唯一のRole、`docs/ai/policies/execution_boundary_policy.md` EXEC-050)。
- **`--forks 1` は本案件では不要**(対象が1ホストのみで、`inventories/sandbox/` の別名多重マッピングを使わないため)。使うのは `inventories/homelab/hosts.yml` の `sandbox_nodes` である。

## 8. オープンクエスチョン

- **sandbox は本番より先へ進む。** `-updates` を随時取り込むため、月次でしか上がらない本番ホストとの間に「進んでいる側」の乖離が生まれる。`sandbox-vm.md` §2 の狙い(乖離しない)に対しては、遅れる方向から進む方向へ変わるだけでゼロにはならない。**リハーサル環境としての価値に影響するかは、実際に使ってみないと分からない。** 本案件では受け入れる。
- **sandbox は Ubuntu Pro に未アタッチである**(`pro status` で `attached: False` を実測)。ESM の origin は Allowed-Origins に書かれているが、実際に効いているかは未確認。本案件では触らない。
- **04:00 の再起動が、長時間走る検証を中断しうる。** 壊してよい箱であり、時間帯も業務時間外だが、**そういう箱になったことは知っておく必要がある。**

## 9. タイムライン

急がない。ただし `reboot-required` は2026-08-22から立っており、放置期間はすでに2週間を超えている。
