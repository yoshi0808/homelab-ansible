## drop-inの内容と根拠

既定値で描画される設定の要点は次のとおり。

```text
Unattended-Upgrade::Allowed-Origins {
  "${distro_id}:${distro_codename}-updates";
};
Unattended-Upgrade::Automatic-Reboot "true";
Unattended-Upgrade::Automatic-Reboot-Time "04:00";
Unattended-Upgrade::Automatic-Reboot-WithUsers "true";
```

ローカルにインストール済みのAPT 3.2.0の公式`apt.conf(5)`は、設定断片を英数字順で読み、匿名要素を持つscopeを再オープンするとlistへ追加し、既存list/scopeの消去は`#clear`でしか行えないと定義している。したがって、99番drop-inでAllowed-Origins scopeを再オープンして匿名のupdates要素だけを書く形は、50番の既存originを複製も上書きもせず追加する。`::`をscope構文内で重ねる誤用はしていない。

一方、`Automatic-Reboot`等のscalarは後勝ちである。初回実機検証ではcloud-init由来の`52unattended-upgrades-local`が初回実装の`52sandbox-auto-patch`より後に読まれ、実効値を`false`へ戻した。修正版は管理名を`99sandbox-auto-patch`へ移して既知の52番より後に読む。`52unattended-upgrades-local`という名前は他VMでもcloud-initが配った`false`設定を意味するため、逆の意味では再利用しない。さらに未知の後続設定にもfail-closedとなるよう、配布後の実効値をassertする。

初回実装では`/tmp/sandbox-auto-patch-apt/parts`のfixtureでlist合成を測った。修正版はさらに`/tmp/sandbox-auto-patch-r9/`へlocalhost inventoryと隔離APT configを作り、repoの`playbooks/sandbox_auto_patch.yml`を実際に実行した。権限昇格は無効化し、dest / owner / group / 旧pathだけをfixtureへ上書きした。

- 50番fixture: release / security / ESM相当の異なるsentinel 3件。
- 既存52番fixture: `52unattended-upgrades-local`に`Automatic-Reboot "false"`。初回版の旧`52sandbox-auto-patch`も配置。
- 正常系: playbookは旧52番を除去して99番を配り、Allowed-Originsは元の3件を保持したままupdatesが4件目に追加された。再起動実効値は`true` / `04:00` / `true`、rc=0。再実行は`changed=0`。
- AC9異常系: 99番より後の`99zz-force-false`へ`Automatic-Reboot "false"`を置いて同じplaybookを実行した。実効値assertが発火し、recapは`failed=1`、rc=2。後続fixtureを除去すると再びrc=0になった。

再起動設定の意味は、ローカルにインストール済みのunattended-upgrades公式READMEで確認した。Automatic-Reboot=trueは`/var/run/reboot-required`検出後の無確認再起動、Automatic-Reboot-WithUsers=trueはユーザーがログイン中でも再起動、Automatic-Reboot-Timeは即時でなく指定時刻の再起動を意味する。
