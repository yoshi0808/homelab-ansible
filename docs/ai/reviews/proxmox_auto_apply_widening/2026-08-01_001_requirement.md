# requirement — weekly full patchの自動適用範囲の拡大と単一node適用

日付: 2026-08-01
状態: 確定(Yoshinobu承認済み)

## 1. 背景

2026-08-01 06:00のSemaphoreジョブ#507(`UN-SAFE:Proxmox Weekly Full Patch`)が `exit 4` で失敗した。調査の結果:

- 原因は **pve1が06:00時点で到達不能**だったこと。開始16秒後にpve1のpreflightで停止している。`MAINTENANCE_REQUIRED` は原因ではない
- 過去3回(07-11 / 07-18 / 07-25)はいずれも `success` で終わっており、**`MAINTENANCE_REQUIRED` によるclean skipは実データで動いている**
- pve1の土曜起動は**Yoshinobuの手作業で時刻が一定しない**ため、06:00の自動適用は「pve1が起きているか」に毎週賭けている状態にある

そしてYoshinobuの実運用は「**結局のところ、毎週、手作業でパッチを適用している**」であった。現行Policyの「重要コンポーネント更新を自動適用しない」は、事故を防ぐのではなく人手を消費しているだけで、人間ゲートが形骸化している。

単一node適用の要求は、**ノード故障で代替機の調達に時間がかかる状況**を想定したものである。生き残ったノードを数週間未パッチで放置するほうが危険である。

## 2. 変更内容

### 2.1 自動適用の可否と、ジョブの終わり方

| dry-run status | 自動適用 | ジョブの終わり方 |
|---|---|---|
| `NO_UPDATES` | しない | **緑** |
| `PATCH_READY` | する(現行どおり) | 緑 |
| `MAINTENANCE_REQUIRED`(removeなし) | **する**(新規) | 緑 |
| `MAINTENANCE_REQUIRED`(**removeあり**) | しない | **緑** + 通知 |
| `MAJOR_UPGRADE_DETECTED` | しない | **緑** + 通知 |
| `BLOCKED` | しない | **赤** |
| 到達可能node **0** | — | **赤**(SB-094の既存規定を維持) |

**`BLOCKED` だけを赤に残す。** あれは「apt / dpkgが壊れている」という実障害だからである。逆に正常系(適用対象外と判定しただけ)で赤を出すと、**本物の赤を見逃す**。これは#507で実際に起きた読み違いである。

**removeを伴う更新を自動適用から外す**のは、SB-025が「removeあり: 置換関係に応じて `MAINTENANCE_REQUIRED` または `BLOCKED`」と定めており、上記の変更をそのまま入れると**無人でのパッケージ削除**が発生するため。判定にはdry-run成果物の `remove_count` を用いる(実物で存在を確認済み)。

### 2.2 単一nodeでの自動適用

**到達可能なnodeが1つ以上あれば、到達できたnodeに適用する。** 両node揃うことを要求しない(fixed-pair gateの撤廃)。

- 通知に**適用対象nodeと、単一node適用である事実**を明示する
- 到達可能nodeが0の場合は従来どおり明確なエラーで停止する(SB-094)

**`pve2`先行の読み替え。** SB-001の「pve2を先行検証nodeとし、pve1を保護する」は、**両nodeが利用可能なときの順序制約**として扱う。pve2が利用不能でpve1だけが生きている場合、pve2の先行実績なしにpve1へ適用する。これを禁じると「pve2が故障したらpve1は永久に未パッチ」となり本要求の主旨に反する。**ただしその場合、通知に「pve2先行実績なしの単一node適用である」ことを明示する。**

#### 単一node時のguest退避(2026-08-01追加。B案)

**片node運用では、guestの退避先が存在しない。** SB-012・SB-088はapply前の退避と「対象node上にrunning guestが残っていないこと」を要求するが、反対nodeが利用不能な状況では行き場がない。当初の設計はこの点を扱っていなかった。

したがって**単一node自動適用は、対象nodeにrunning guestが無い場合に限る**。

| 状況 | 挙動 |
|---|---|
| 両nodeが利用可能 | 従来どおり反対nodeへ退避してから適用 |
| 単一nodeのみ利用可能、対象nodeに**running guestなし** | そのnodeへ適用する |
| 単一nodeのみ利用可能、対象nodeに**running guestあり** | **適用しない。緑で終了し、通知する**(人手へ渡す) |

**guestを停止して適用する案は採らない**(2026-08-01 Yoshinobu判断)。家庭内サービスを無人で停止させないため。結果として、ノード故障で生存node側に全guestが載る状況では自動適用は働かず、手動運用のままとなる。**これは承知のうえでの選択である。**

### 2.3 手動適用の確認文字列

`proxmox_patch_apply_manual_confirm` が `MAJOR_UPGRADE_DETECTED` も受理する。現行は `MAINTENANCE_REQUIRED` のみ。

- `proxmox_patch_apply_mode == 'manual'` かつ `proxmox_patch_apply_manual_confirm == '<検出されたstatus>'` のときに続行する
- 確認文字列が検出されたstatusと一致しない場合は従来どおり停止する

## 4. やらないこと

- **`BLOCKED` を自動適用の対象にしない。** 緑にもしない
- **`MAJOR_UPGRADE_DETECTED` を自動適用の対象にしない**(手動+確認文字列のみ)
- evacuate → apply → restore のguest退避flow、mute枠、reboot処理を変更しない。これらはstatus判定とは独立の保護であり、本作業の対象外である
- **control node分離の「要求」を変更しない** — controllerがProxmox cluster上に無いことの確認は維持する。**ただしこれは、その確認をどのhostへ問い合わせるかの実装まで固定する意味ではない**(2026-08-01明確化)。現行実装は `hosts: "{{ groups['proxmox'][0] }}"` でpve1に固定されており、**pve1が到達不能な回に開始直後で停止する**(Incident #507と同型)。到達できたnodeへ問い合わせれば同じ保証が得られるため、**この固定は変更対象とする**
- SB番号の振り直し

## 6. 実行identityと権限境界

**到達してはいけない状態**として示す。

- **実ホストへパッチが適用された状態で報告が返らないこと。** 本作業は実装のみであり、本番適用は行わない
- **pve1 / pve2 / authy / sophos-fw / UniFi機器へ非冪等操作が行われた状態で報告が返らないこと。** これらは保護対象ホストである
- **`--check` を伴わない `proxmox_patch_apply_node.yml` / `proxmox_patch_weekly_full.yml` の実行が行われた状態で報告が返らないこと**
- **`git add` / `git commit` / `git push` が実行された状態で報告が返らないこと**
- 書込先は `playbooks/`、`roles/proxmox_patch_apply_node/`、`roles/proxmox_patch_dryrun/`(必要な場合)、`docs/ai/policies/proxmox_operations_policy.md`、本案件フォルダに限る。それ以外が変更された状態で報告が返らないこと
- 権限が昇格した状態に到達しないこと

harnessの安全機構にブロックされた場合、別の形で同じ結果へ到達せず、ブロックされた事実を報告に含めて返すこと。

## 8. 未解決事項(実装時に判断が要る可能性があるもの)

- 単一node適用時、**restore(home nodeへの復帰)とguest退避**が両node前提の実装になっていないか。なっている場合は、実装せずに報告すること(§4により本作業の対象外であり、影響があるなら設計判断が要る)
