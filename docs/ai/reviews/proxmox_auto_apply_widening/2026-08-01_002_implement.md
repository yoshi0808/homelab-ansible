## 2. §2.1(自動適用の可否とジョブの終わり方)の実装

### 2.1.1 `proxmox_patch_apply_node`role

既存の`_redryrun_is_mr`(単一boolean、major/important/removeのOR)を、SB-025と同じ順序で明示的に`_redryrun_status`(`MAJOR_UPGRADE_DETECTED` / `MAINTENANCE_REQUIRED` / `PATCH_READY`)へ分類し直した。そのうえで`_redryrun_requires_confirmation`を「`MAJOR_UPGRADE_DETECTED`、または`MAINTENANCE_REQUIRED`かつremoveあり」だけに限定した。これにより:

- `MAINTENANCE_REQUIRED`でremoveなし(important componentのみ) → `_redryrun_requires_confirmation=false` → autoモードでもabortせず継続(新規)。
- `MAINTENANCE_REQUIRED`でremoveあり → 従来どおりabort(autoモード)/確認文字列必須(manualモード)。
- `MAJOR_UPGRADE_DETECTED` → 従来どおりabort/確認文字列必須だが、確認文字列は`MAJOR_UPGRADE_DETECTED`自体を要求する(§2.3、後述)。

`_apply_abort_type`に新値`major_upgrade_detected`を追加し、既存の`maintenance_required`と区別した(通知subject/bodyのPhase3/4除外リストにもこの値を追加)。

### 2.1.2 `proxmox_patch_weekly_full.yml`(Step 2b)

`_wf_proceed`を「`PATCH_READY`、または`MAINTENANCE_REQUIRED`かつ`remove_count==0`」で定義し、それ以外は`NO_UPDATES` / `MAJOR_UPGRADE_DETECTED` / `MAINTENANCE_REQUIRED`(remove_count>0)ならclean skip(exit 0)、それ以外(`BLOCKED`、`UNKNOWN`、dry-runがどのnodeもカバーしなかった場合)はfail(non-zero)とした。`remove_count`は`_final_report.remove_count`(=`unified_dryrun.cluster_summary.total_unique_removes`)をそのまま使う。

## 3. §8 未解決事項1: `remove_count`の粒度

**cluster単位である。node単位ではない。** `roles/proxmox_patch_dryrun/tasks/main.yml`の`_final_report.remove_count`は`unified_dryrun.cluster_summary.total_unique_removes`(`proxmox-dryrun-merge.py`が生成)であり、これは元々到達nodeの数に依存しない設計(2026-07-26のADR-002で単一node対応済み)。したがって「1nodeでもremoveがあれば全体を見送るか、node単位で判断するか」という問いは、**既にcluster単位に決着済みの値をそのまま使うことで解消される**——1node dry-runでも、そのnodeのremoveがあればcluster-level `remove_count`は1以上になり、正しくskip側に落ちる。新規の設計判断は不要だった。

## 4. §8 未解決事項2 → 追補2(B案)で解消: guest退避/restoreの両node前提

初版報告で確認した事実は変わらない: `roles/proxmox_evacuate_node`の呼び出し元playbook(`playbooks/proxmox_evacuate_node.yml`)は、evacuate本体の前にdestination_node(target_nodeの反対側)のhealthcheckを無条件で要求するplayを持ち、destinationが到達不能ならUNREACHABLEで停止する。**このroleへは今回も一切手を入れていない**(Coordinatorの指示どおり)。

Coordinatorの追補2(B案、Yoshinobu判断)を受け、**この制約をevacuate/restore側でなく、オーケストレータ側の自動適用条件で吸収する**実装へ変更した。`playbooks/proxmox_patch_weekly_full.yml`のStep 2bに以下を追加:

1. 単一nodeのみが今回の対象になった場合に限り(両node対象時は従来どおり)、対象nodeへ`delegate_to`して`pvesh get /cluster/resources`を実行し、その node 上に`status=running`の`qemu`/`lxc`が存在するか確認する(`_weekly_full_single_node_has_guests`)。
2. running guestが存在する場合 → 適用せず、Slack通知(理由・dry-run status・remove_countを含む)を送り、`_weekly_full_skip=true`にして`meta: end_play`で緑終了する(AC10前半)。
3. running guestが存在しない場合 → 通常どおり進む。ただし**evacuateはそもそも呼ばない** — Step 3/7の`import_playbook: proxmox_evacuate_node.yml`に新設した`_weekly_full_both_nodes`(両node対象時のみtrue)を`when:`条件へ追加し、単一node運転ではevacuateを完全にスキップして直接apply(Step 4/8)へ進む。これにより「反対nodeが無いのに反対nodeのhealthcheckを要求する」evacuateの入口にそもそも到達しない。
4. restore(Step 6/10)はevacuateと異なり反対nodeを一切参照しない実装(`playbooks/proxmox_restore_vm_placement.yml`は`hosts: localhost`と`hosts: "{{ target_node }}"`のみで構成)ため、既存の`_weekly_full_target_pveN`ゲートのみで変更不要と判断した(単独ノードで呼んでも「移動すべきものが無い」no-opになるだけで害がない)。
5. `roles/proxmox_patch_apply_node`自身が持つ既存の「running guestが残っていればabort」チェック(SB-088、未変更)は、上記1〜3が正しく機能していれば単一node運転では素通りするだけの冗長な二重チェックとして残る(意図的、防御的)。

**guestを無人で停止して適用を強行する設計は採用していない**(Yoshinobu判断、requirement.md §2.2追記)。結果として、ノード故障で生存node側に全guestが載っている状況(HA failover後など)では、自動適用は働かず緑終了+通知に留まり、手動対応が必要なまま残る。これは意図された仕様である。

## 5. §8/§4に追加で発見した問題

### 5.1 `_final_status`/`_final_report`のhost lookupバグ(修正済み)

`proxmox_patch_weekly_full.yml`の旧Step 2bは`hostvars[groups['proxmox'][0]]['_final_status']`(常に`pve1`のhostvarsを見る)という固定lookupだった。`roles/proxmox_patch_dryrun`のPhase 2は`run_once + delegate_to: localhost`(`delegate_facts`なし)で`_final_status`/`_final_report`を設定するため、**そのfactは「run_once を担ったhost」に記録される**。pve1自身がPhase 1で脱落した場合(＝今回の主要シナリオ)、run_once を担うのはpve2になり、factは`hostvars['pve2']`に載る。旧コードの固定lookupは`hostvars['pve1']`を見るため、**単一node(pve1側が脱落)シナリオでは常に`_status`が`UNKNOWN`にフォールバックし、Step 2bがfail扱いになる**——つまり§2.2の実装対象そのもののシナリオで、旧コードのまま新しいgate緩和だけを足しても機能しなかった。

`_status_hosts_with_fact`(`groups['proxmox']`のうち`_final_status`が定義されているhostを動的に探す)へ変更し、decoyで実際にこのシナリオ(down側がgroup先頭、factは生存側に付く)を再現して修正を確認した(§6のtest2 Scenario B)。**Coordinatorから「維持すること」と明示的に指示された修正であり、追補後も変更していない。**

### 5.2 Preflightのcontrol node分離checkが単一固定nodeで実行される問題 → 追補1で解消

初版報告時点: `playbooks/proxmox_patch_weekly_full.yml`のStep 0(`Preflight - Verify control node is not on Proxmox cluster`)は`hosts: "{{ groups['proxmox'][0] }}"`(現在のinventory順で`pve1`)に固定されており、pve1が到達不能な回はこのplayがUNREACHABLEで停止し、incident #507と同型の症状が再現する、と報告した。requirement.md §1の「開始16秒後にpve1のpreflightで停止している」はこのplayを指していると考えられる。

Coordinatorの追補1により、「controllerがcluster上に無いことの確認」という要求と「pve1に問い合わせる」という実装は別物であることが明確化され、実行host選定の変更が許可された(AC9新設)。これを受け、Step 0を2つのplayへ分割した:

- **Step 0a(新設)**: `hosts: proxmox`で`roles/proxmox_exec_node`(ADR-006の既存共通role。5 playbookで実績あり、`playbooks/proxmox_backup_restore_verify.yml`と同じ使い方)を呼び、到達可能な候補から1台を動的group `pwf_preflight_query_node`へ登録する。
- **Step 0b**: 従来の"Preflight - Verify control node is not on Proxmox cluster" playを、`hosts: "{{ groups['proxmox'][0] }}"`から`hosts: pwf_preflight_query_node`へ変更しただけで、中身(`pvesh get /cluster/resources`によるVM名リスト取得、controller自身がcluster上のVMまたはProxmox nodeでないことの確認、許可controller一覧との照合)は一切変更していない。`pvesh`はcluster全体APIのため、問い合わせ入口nodeが変わっても結果は同じ(`proxmox_backup_restore_verify.yml`のPlay 1と同じ理由)。

decoyで、group先頭ホストを閉ポート(down)、2番目を`ansible_connection: local`(up)にした構成で、`roles/proxmox_exec_node`を実際にロードして実行し、preflightクエリが正しく2番目のホストへ委譲されること、かつ`rc=0`で完走することを確認した(§6参照)。

### 5.3 独立レビューfinding 1(2026-08-01差し戻し): Step 0bが空groupで黙ってskipされうる(修正済み)

5.2の対応(Step 0a/0bの分割)自体は妥当と評価されたが、独立レビューで新たな欠陥を指摘された: **`pwf_preflight_query_node`が空の場合、`hosts: pwf_preflight_query_node`のStep 0bは対象0台として黙ってskipされ、後続のplay(healthcheck以降)がそのまま実行され続ける。** 具体的な経路: `roles/proxmox_exec_node`のT1(呼び出し規約assert、`tasks/main.yml:27`)は`ansible_play_hosts_all | sort == (groups[pen_candidate_group] | sort)`という**完全一致**を要求するため、`--limit <単一node>`でStep 0aの`hosts: proxmox`が絞られると必ず破れる。これはAnsibleが「playの対象host数が0件」をエラー扱いしないために起こる、確認そのものが省略されて先へ進む壊れ方であり、requirement.md §4の「control node分離の確認は維持する」という要求に反する。

**`roles/proxmox_exec_node`自体は指示どおり一切変更していない**(`--limit`対応は別案件として`docs/ai/status.md` Nextに起票済み、triaged outとして扱う)。代わりに、Step 0bの末尾に「確認が実際に完了した」ことを示すfact `_preflight_confirmed`を立て、直後に新設した**Step 0c**(`hosts: proxmox`)がそのfactを`assert`で検査し、無ければ停止するようにした。

- **`hosts: localhost`ではなく`hosts: proxmox`を選んだ理由**: decoyで検証した結果、**`hosts: localhost`のplay自体も、`--limit <localhostにマッチしないhost>`が指定されると対象0件として黙ってskipされる**ことを確認した(既存のStep 2b/2c/11もこの性質を持つが、それらは本findingの対象外であり今回は変更していない)。`hosts: proxmox`であれば、`--limit <実在のproxmox node>`はその1台を含むため必ず非空になり、guardが確実に実行される。
- **実装中に発見した副次的な重大バグ**: Step 0bの末尾で`_preflight_confirmed`を`delegate_to: localhost`で設定する際、`delegate_facts: true`を付け忘れると、`delegate_to`は実行先を変えるだけで**factは委譲先ではなく元のinventory_hostname側に記録される**(`_final_status`/`_final_report`のhost lookupバグ、§5.1と同じ種類の罠)。これに気づかず実装した最初のバージョンは、Step 0cのguardが正常時も含めて**常にfail**する状態だった。decoyでの実行結果(`hostvars['localhost']`に何も乗っていない)から発覚し、`delegate_facts: true`を追加して修正、再度decoyで正常時に`rc=0`で完走することを確認した。

自己検証の詳細は§6を参照。

**訂正(2026-08-01再レビュー): 当初の因果モデルは誤りだった。** 上の段落(および前回のCoordinatorによる差し戻し文)は「`--limit <単一node>`で`roles/proxmox_exec_node`のT1 assertが破れると、Step 0bが黙ってskipされたまま**healthcheck以降が実行され続け、適用まで到達しうる**」という経路を根拠にしていた。再レビューでReviewerがdecoyで実測した結果、**この経路は実在しない**ことが判明した: T1 assertは`run_once + delegate_to: localhost`で評価され、そのplayの唯一のhost(`--limit`で1台に絞られている)がここで失敗すると、Ansibleは標準動作としてそのhostを以降の**全play**から除外し、run全体を非0終了(`rc=2`)で止める。healthcheck以降が「`--limit`を許可するから」という理由で実行され続けることはなかった。**Step 0cを外した状態でも同じ`rc=2`停止になることをReviewerが確認済み**であり、当初報告した「Step 0cが無いとhealthcheck以降が走り続ける」という因果は事実と異なる。

**それでもStep 0cは残す。** 理由はT1 assert違反のケースを塞ぐためではなく、**それ以外の理由で`pwf_preflight_query_node`が空になるケース**(assertが破れる以外の経路でStep 0aがgroupを populate し損ねる場合)に対する防御が、Step 0c無しでは存在しないため。この経路の実在性・具体的な発生条件までは今回洗い出せていないが、「確認が行われなかったら理由を問わず進まない」という明示的なfail-closed保証を、特定の1つの原因(T1 assert違反)にしか効かない暗黙の副次効果(host失敗伝播)に委ねるのではなく、コードとして持たせておくことに意味があると判断した。当初の実装動機(T1 assert違反時の防御)は誤りだったが、Step 0c自体を撤去する理由にはならない。

**教訓の一般化**: 今回の一連の修正(§5.1のhost lookup、Step 0cのguard設計、その実装中に踏んだdelegate_factsの罠、そして本節の因果モデルの誤り)はいずれも同じ形の欠陥——「`delegate_to`だけでfactの所在を決め打ちする」「playが対象0件になり得ることを見落とす」「decoyで実測せず動作を類推だけで報告する」——であり、単発の偶然ではなくこのplaybook全体で繰り返し発生している欠陥クラスである。今回はいずれもdecoyでの実行結果(目視でなく`rc`・`hostvars`の中身)を見て発覚・修正した。

### 5.4 独立レビューfinding 4(2026-08-01再レビュー): 「やっていない」と書いてあるのに実際にはやっている(修正済み)

Step 11の通知本文が、単一node適用時に`{{ n }}: パッチ適用 完了(単一node適用のため退避・復帰は実施していません)`と表示していたが、これは事実と異なる。`import_playbook: proxmox_restore_vm_placement.yml`(Step 6/10)のgateは`_weekly_full_target_pveN`のみで、`_weekly_full_both_nodes`は見ていないため、**単一node運転でもrestoreは実際に実行される**。同じ趣旨の記述漏れがPolicy側(SB-032、§5.1標準flow項目5)にも見つかった。

**Coordinatorの判断: コードは変えず、文言を実際の挙動に合わせる。** restoreをskipする方向へ変更しない理由は次の2点(Coordinatorが決定): ①本番パッチchainの制御フローへ手を入れる変更をこの段階で増やしたくない。②何もしていないno-opのrestoreは無害なだけでなく、**何らかの理由でguestがhome nodeから外れていた場合に元へ戻す安全網**として機能する。skipするとこの安全網が失われる。

対応した記述:

- `playbooks/proxmox_patch_weekly_full.yml` Step 11の通知本文: 「退避は行っていません。復帰playbookは実行されますが、何も退避していないため実質no-opです」という、実行はされるが退避対象が無いため実質no-opである旨が伝わる文言へ変更。
- 同ファイルStep 6/10の`import_playbook`直前のコメント、および冒頭Flowコメントの項目6/10: restoreが単一node時も実行され、安全網として意図的に残していることを明記。
- `docs/ai/policies/proxmox_operations_policy.md` SB-032、§5.1標準flow項目5: 「evacuate・restoreを行わず」という記述から「restore」を外し、restoreは両経路で実行される安全網である旨を明記。

コード(`when:`条件、import_playbook呼び出し)は一切変更していない。decoyでJinjaテンプレートの新文言が意図どおりレンダリングされることを確認済み(§6参照)。

## 9. 未解決事項・残存リスク

1. **evacuate/restore roleは未変更のまま。** 単一node運転でrunning guestが残っている場合の扱いは、「guestを無人停止して適用を強行しない」というYoshinobu判断(B案)により、自動適用を見送る形で解決済み。node故障でHA guestが生存node側へfailover済みの状況では、自動適用は働かず手動対応が必要なまま残る——これは§8/§4で報告した制約の**解決**ではなく**受容**である(Yoshinobu既知・承知のうえの選択)。
2. Policy改訂のうち11件を超える8箇所の追加改訂(SB-012、SB-088、および付随6箇所、§7参照)はYoshinobuの承認を要する。
3. **`roles/proxmox_exec_node`自体の`--limit`対応は本案件のスコープ外のまま**(`docs/ai/status.md` Nextの別案件)。Step 0cのfail-closed guardは「確認が行われなかったら進まない」ことだけを保証しており、「`--limit`単体nodeでも確認が行える」ようにはしていない。したがって`--limit <単一node>`での`proxmox_patch_weekly_full.yml`実行は、今回の修正後も(黙って通過するのではなく)明示的に赤で停止する、という結果になる。これは意図した挙動である(fail-closedの要求どおり)が、`--limit`でこの playbook を使いたい実運用ニーズが今後出てきた場合は、別案件(exec_node側の`--limit`対応)の完了を待つ必要がある。
4. `roles/proxmox_patch_apply_node`の通知本文に「MAINTENANCE_REQUIRED(remove無し)を widened policy により自動適用した」旨の`[INFO]`行を追加したが、`roles/proxmox_patch_dryrun`自身のCodex生成通知(`mail_subject`/`mail_body`)は変更していないため、同一の週で「dry-run: 人間判断を推奨」という通知と「apply: 自動適用完了」という通知が両方Slackに流れる可能性がある。Codexのclassify prompt/出力文言は本requirementの対象外と判断し変更していないが、運用上紛らわしい可能性があるため申し送る。
5. 単一node運転時のrunning guest確認(`pvesh get /cluster/resources`)は、対象nodeへ`delegate_to`する形でStep 2bに追加した。両node運転時はこのタスク自体が`when:`でskipされ、既存の動作(evacuate経由)に一切影響しないことをdecoyで確認済みだが、実Proxmox環境での`pvesh`出力形式そのもの(JSON schema)は`roles/proxmox_evacuate_node`が同種の問い合わせで既に使っている前提を流用しており、新規の疎通確認はできていない(実host非依存の制約による。Tester工程での実地検証を推奨)。
6. **Step 0cのguard、および§5.1で修正した`delegate_facts`の罠は、いずれも実Proxmox環境での実地確認ができていない**(decoyのみ)。`roles/proxmox_exec_node`は既に5 playbookで実績があるため選定ロジック自体のリスクは低いと判断しているが、Step 0a/0b/0cを跨いだfactの受け渡し(`_preflight_confirmed`)は今回新規に組んだ配線であり、Tester工程での実地確認(`--check`)を推奨する。
