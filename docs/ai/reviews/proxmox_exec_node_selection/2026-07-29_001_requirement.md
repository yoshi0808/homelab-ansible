# requirement: Proxmox実行ノード選定の共通化(決め打ちの除去)

作成: 2026-07-29 / Coordinator
Tier: 3(軸A = 本番影響のある実ロジック変更 + 複数ホストのorchestration / 軸B = Tier 3はReviewerを工程に含むため`+R`なし)

## 1. 問題定義

Proxmoxクラスタへ入るplaybookの多くが、**実行ノードを`pve1`に決め打ち**している。pve1は夏季平日シャットダウン運用中(`roles/recovery_probe/defaults/main.yml` の`recovery_probe_pve_host`のコメントが正本)のため、これらは平日日中に機能しない。

**現に壊れている箇所は2系統ある。**

### (a) 自律復旧ラダー — 発火時に失敗する(未観測)

```
playbooks/recovery_vm_reboot.yml:40       hosts: pve1
playbooks/recovery_service_restart.yml:37 hosts: pve1
playbooks/recovery_ha_failover.yml:40     hosts: pve1
```

2026-07-21の`e9ac523`は`recovery_probe_pve_host`をpve1→pve2へ向けたが、**そのラダーが起動するplaybook 3本を更新していない**(commitのstatは`roles/recovery_probe/defaults/main.yml`と`playbooks/README.md`の2ファイルのみ)。結果、`recovery-probe.py`は次の非対称な状態にある。

| 経路 | 使うノード | 現状 |
|---|---|---|
| pvesh確証 (`pvesh_vm_status`) | `cfg["pve_host"]` = pve2 | 動作する |
| stopped VMのstart (`pvesh_vm_start`) | `cfg["pve_host"]` = pve2 | 動作する |
| ラダー第2段 (`recovery_vm_reboot.yml`) | **pve1固定** | pve1停止中は失敗 |
| ラダー第3段 (`recovery_ha_failover.yml`) | **pve1固定** | pve1停止中は失敗 |

対象は`recovery_probe_targets`の全3件(sophos-fw / authy / monnie、いずれも`action: ladder`)。縮退は安全側(rc≠0 → critical通知でエスカレーション)であり破壊はしないが、**自動復旧が効かず通知のみになる**。

### (b) proxmox_backup_restore_verify — 2026-07-28に実際に失敗した

Semaphore job #469(2026-07-28 18:30 JST)の実ログ:

```
TASK [Get cluster resources] ***
fatal: [pve1]: UNREACHABLE! => {"changed": false, "msg": "Task failed: Failed to
connect to the host via ssh: ssh: connect to host pve1.internal port 22: No route
to host", "unreachable": true}
[WARNING]: Could not match supplied host pattern, ignoring: brv_restore_targets
PLAY [Verify backup restore on chosen node] ***
skipping: no hosts matched
PLAY RECAP ***
pve1  : ok=1  changed=0  unreachable=1  failed=0  skipped=0  rescued=0  ignored=0
Failed to run task: exit status 4
```

決め打ちは2箇所ある。

1. **Play 1(`playbooks/proxmox_backup_restore_verify.yml:36-38`)** — `hosts: proxmox` + `run_once: true`、`ignore_unreachable`なし。`inventories/homelab/hosts.yml`がproxmoxグループを **pve1 → pve2 の順**で定義しているため`run_once`の担い手がpve1に固定され、`PLAY RECAP`にpve2が一度も現れない。**pve2は健全だったのに一切使われていない。**
2. **restore先ノード決定(同 L104-109)** — VMの`prefer<node>`タグだけで`'pve1'`/`'pve2'`のリテラルへ写像し、到達性を見ていない。(1)を直しても、当月の対象VMが`preferpve1`なら Play 2 が再びpve1を狙って失敗する。

終了コード`4`(`RUN_UNREACHABLE_HOSTS`)は、2026-07-26に`proxmox_patch_dryrun`で解消したのと同一の欠陥クラスである(`docs/ai/reviews/proxmox_patch_dryrun/2026-07-26_005_test_result.md` §13-4)。**同じ問題が別のplaybookに残っていた。**

### 共通する構造

`playbooks/unifi_backup_fetch.yml`(ADR-001、2026-07-25)だけが「pve1優先・pve2フェイルオーバー」のpreflightを持つ。同ADRのConsequencesは「同種の要望が他playbookでも繰り返し出た場合はOperations Context化を再検討する」と記しており、**今回がその条件成立**である。5箇所が同じ1つの問いに帰着する — 「どのノードで実行するか」。

## 2. ゴール

Yoshinobu表明(2026-07-29):

> pveはフェイルオーバーしている可能性があることを前提にしているので、どちらかを決め打ちするのは避けたい。優先はこのノードと決めるのは良いですが、どちらかが生きていれば継続できるという考え方が好ましい。

- Proxmoxクラスタへ入るplaybookから、実行ノードのホスト名リテラルを除去する。
- 「優先ノードを尊重しつつ、到達可能なノードが1つでもあれば継続する」を**1つの共通機構**で実現し、5箇所がそれを使う。
- 上記の結果として、`recovery_probe_pve_host`を将来pve1へ戻すか判断する、という申し送り自体を消滅させる。

## 3. 非ゴール

- **`playbooks/proxmox_patch_weekly_full.yml` の `hosts: pve1` / `hosts: pve2`(L250 / L300)は対象外。** 各ノードを順にパッチする意図的な固定であり、片系だけで適用すると版数driftを作る。`docs/ai/policies/proxmox_patch_policy.md` SB-027/SB-028がこれを要求している。
- クラスタ全体が停止している場合の代替経路(ADR-001 Option (b) = quoryへ直接NFS mount)は扱わない。
- Proxmoxのタグ設計(`verify` / `prefer<node>` / `hacritical` / `ops`)は変更しない。
- Semaphore側のスケジュール設定・環境変数は変更しない(repo外。§7参照)。

## 4. ユーザーストーリー

- Yoshinobuとして、pve1が夏季平日に停止していても、月次のbackup restore-verifyが**pve2で完了**してほしい。バックアップが本当に復元できるかの確認が季節で止まるのは、この検証の存在意義に反するため。
- Yoshinobuとして、pve1停止中にVMがハングしたとき、自律復旧ラダーが**pve2を入口として実行**されてほしい。復旧が要る瞬間に「入口が居ない」で止まるのは、自律復旧を持つ意味を失わせるため。
- Coordinatorとして、pve1の起動・停止に合わせてrepoの変数を書き換える運用を無くしたい。**書き換え忘れが黙って効かない安全装置を作る**ため(2026-07-21の`e9ac523`が現にそうなった)。

## 5. 要件

### P0(初回実装に不可欠)

| # | 要件 |

## 6. 受入条件

### AC1: ラダーがpve1停止中に実行できる

- **Given** pve1が到達不能、pve2が健全
- **When** `recovery_vm_reboot.yml` を `--check` 付きで対象VMに対して実行する
- **Then** Play 0 がpve2を選定し、Phase 1(タグ再検証)がpve2経由で完走する。**終了コードは`0`**。`PLAY RECAP`に`unreachable=0`が出る(`ignored`は出てよい)

### AC2: ラダーが両ノード到達不能なら明示的に停止する

- **Given** pve1・pve2とも到達不能
- **When** 同playbookを実行する
- **Then** 「どのノードも到達不能」と両ノードの到達性を明記したメッセージでfailする。**終了コードは非ゼロ**。Slack通知はplaybook既定の経路に従う

### AC3: restore-verifyがpve1停止中に完走する

- **Given** pve1が到達不能、pve2が健全、当月の対象VMが`preferpve1`
- **When** `proxmox_backup_restore_verify.yml` を実行する
- **Then** Play 1 がpve2で選定を完了し、restore先としてpve2を選ぶ。VMID 999 の restore → 起動 → health判定 → 破棄まで完走する。**終了コードは`0`**。レポートJSONとSlack本文に**「preferred node pve1 が到達不能なため pve2 で実施」に相当する記載**がある

### AC4: restore-verifyの通常経路が変わらない

- **Given** pve1・pve2とも健全
- **When** 同playbookを実行する
- **Then** 対象VMの`prefer<node>`タグどおりのノードでrestoreされる。代替実施の記載は**出ない**。終了コードは`0`

### AC5: unifi_backup_fetchの外部挙動が変わらない

- **Given** R8の置き換え後
- **When** 「両系到達可能」「pve1のみ」「pve2のみ」「両系不能」の4条件で Play 1 を実行する
- **Then** 選定結果は置き換え前と同一(pve1優先 / 到達可能な側 / fail)。fail時のメッセージは両ノードの到達性を含む

### AC6: recovery-probeの候補フォールバックが効く

- **Given** `recovery_probe_pve_hosts` に2候補、先頭が到達不能
- **When** `pvesh_vm_status` 相当の呼び出しを行う
- **Then** 2番目の候補で結果を得る。全候補が到達不能なときだけ `pve-unreachable` を返す

## 7. オープンクエスチョン

| # | 問い | 扱い |
|---|---|---|
| Q1 | Semaphore実行環境で `ANSIBLE_CACHE_PLUGIN` / `ANSIBLE_GATHERING` が設定されていないか | **Yoshinobu実施**。repo外のためAIから確認不可。有効だと`proxmox_patch_dryrun`の到達判定がキャッシュ済みfactsを読み、停止中のノードを到達可能と誤判定する(2026-07-26 Reviewer再現済み)。**本案件のR1はfact依存でなく明示的な`ping` probeで判定するため、本案件の成果物はこの影響を受けない** — 影響を受けるのは既存の`proxmox_patch_dryrun`のみ |
| Q2 | pve2の`local-zfs`に、restore-verify用VMID 999の一時ディスクを収める空き容量があるか | **Testerが実測**。`verify_restore_storage: local-zfs`はノードローカルであり、pve2は現在全VMを収容している。不足するとAC3が成立しない |
| Q3 | 代替ノードでのrestore-verifyのSlack severityを`ok`のままとするか | **Coordinatorが確定済み**: `ok`とする。検証自体は成功しており、代替である事実は本文とレポートJSONで伝える。severityを上げると「毎夏warningが並ぶ」状態を作り、本物の異常を埋もれさせる |

## 8. タイムライン考慮

- **(b) は既に本番で失敗している。** 月次ジョブのため次の発火は約1か月後だが、pve1が停止している限り再発する。
- **(a) は発火していないが armed である。** `homelab-monitoring-pause` は2026-07-29に解除済みで、probeは`recovery_probe_service_enabled: true`(quory host_vars)で稼働している。今日ハングが起きればラダーは失敗する。
- AC3/AC4 の実地検証は **pve1の起動状態に依存する**。AC3(pve1停止中)は平日にそのまま検証できる。**AC4(両系健全)はpve1が起動している時間帯を要する** — 週末のパッチ運用に合わせるのが自然。
- R9の配備は、2026-07-29に入れた`recovery_probe`の自動反映(`handlers/main.yml`)が**実際に内容が変わる配備で発火するかの初観測**になる(`docs/ai/status.md` Watch行)。

## 9. リスク

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| (Operational) 共通roleへの寄せ替えで`unifi_backup_fetch`の実績ある挙動を壊す | 中 | 中 | AC5で4条件の同値性を明示的に検証する。R8はP1に置きP0の後に行う |
| (Operational) ラダーのpreflight Play追加が`check-mode-native`のゲートを跨ぐ | 中 | 高 | preflightは`ping`と`set_fact`と`add_host`のみで副作用を持たない。`--check`での完走をACに含める(AC1)。破壊的フェーズの`ansible_check_mode`ゲートには触れない |
| (Operational) pve2の`local-zfs`容量不足でrestore-verifyが失敗する | 中 | 中 | Q2としてTesterに実測させる。不足が判明した場合はR6の設計判断へ差し戻す(skip+通知へ倒す) |
| (Operational) 代替ノードでのrestoreが本番配置と異なることを運用者が見落とす | 中 | 低 | R6で報告本文とレポートJSONの両方へ明記する |
| (Strategic) 共通機構がProxmox以外へ拡張されると仮定して過剰に一般化する | 低 | 低 | 入力をinventory group名に限定し、Proxmox固有の概念(タグ、pvesh)をroleへ持ち込まない |
| (Operational) 5箇所同時変更で、どれか1つの回帰に気づかない | 中 | 中 | Step 1 / Step 2 に分け、Step 1が通ってからStep 2へ進む。ACを箇所ごとに分離済み |
