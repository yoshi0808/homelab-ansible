## 2. 契約(plan §1)との対応

### 1-1 変数名・タスク構成

`defaults/main.yml`: `pen_candidate_group`(既定`proxmox`)、`pen_prefer`(既定`''`)を定義。`pen_target_group`/`pen_caller`は契約どおり既定値を持たせず、未指定ならT1が落とす。

`tasks/main.yml`: T1(入力assert)→T2(ping probe)→T3(set_fact pen_reachable)→T4(全滅時fail)→T5(add_hostで選定)の5task構成。task数を増やしていない(中間計算はT4/T5それぞれの`vars:`に閉じ込め、新規taskとして数えていない)。

- T1: `pen_target_group`/`pen_caller`非空、`ansible_play_hosts_all | sort == (groups[pen_candidate_group] | sort)`(呼び出し規約)、`pen_prefer == '' or pen_prefer in groups[pen_candidate_group]`(prefer綴り誤り検出)の3種をassert。`run_once` + `delegate_to: localhost`。
- T2: `ansible.builtin.ping` + `ignore_unreachable: true` + `ignore_errors: true` + `register: pen_ping`。
- T3: `pen_reachable: not (pen_ping.unreachable | default(false) | bool) and not (pen_ping is failed)`(plan指定の式そのまま)。
- T4: `run_once` + `delegate_to: localhost`。`when`は`ansible_play_hosts_all | map('extract', hostvars) | selectattr('pen_reachable', 'equalto', true) | list | length == 0`。メッセージは`pen_caller`と全候補の`host=bool`列挙(`zip` + `map('join','=')` + `join(', ')`)。
- T5: `add_host` + `run_once` + `delegate_to: localhost` + `changed_when: false`。選定式は`pen_prefer`が到達可能集合に含まれればそれ、でなければ`ansible_play_hosts_all`順で到達可能な先頭。

`map('extract', hostvars) | selectattr(..., 'equalto', true) | map(attribute='inventory_hostname') | list`という到達可能ホスト名抽出パターンは、`roles/proxmox_patch_dryrun/tasks/main.yml`の`_reached_nodes`(2026-07-26に実機検証済み)と同一手法を再利用した。新規のJinja技法(namespace+for-loopでの文字列組み立てなど)は避け、既に本番実績のあるパターンのみを使っている。

### 1-2 適用表

## 4. 自己検証

### 4-1 `--syntax-check`

3playbookとも`ansible-playbook <file> --syntax-check -e target=authy`で構文エラーなし(`recovery_exec_target`が未解決という`[WARNING]`のみ、dynamic groupが実行前に存在しないため想定どおりで既存の`unifi_backup_fetch.yml`と同種)。

### 4-2 decoy inventoryでの4条件検証

**環境**: scratchディレクトリ(`/tmp/claude-.../scratchpad/decoy_u1/`、リポジトリ外)に、実host名を使わない decoy inventory 4種と decoy playbook を作成。`ANSIBLE_ROLES_PATH=/home/yoshi/homelab-ansible/roles`を設定し、`roles/proxmox_exec_node`をそのまま(コピーせず)実行させた。decoyホスト名は`dnode1`/`dnode2`(candidate group名`proxmox`は流用、group名自体はホスト名ではないため許容と判断)。

- 両候補到達可能: `ansible_connection: local` × 2
- 先頭のみ到達可能: `dnode1`=local、`dnode2`=ループバックの閉ポート(closed port、`Connection refused`実測済み)
- 2番目のみ到達可能: 逆
- 両候補到達不能: 両方closed port(61234/61235)

decoy playbookは、Play 0(role呼び出し)の直後に`post_tasks`で`ansible_play_hosts_all`全件の`pen_reachable`を`host=bool`形式でdumpし(到達不能ホストにも立つことを直接確認)、続くPlay(`hosts: decoy_target`)で`groups['decoy_target'] | length == 1`のassertと`pen_reachable`の値・**型**(`type_debug`)を出力するconsuming taskを置いた。目視だけで終わらせず、`length`フィルタと`selectattr`まで実際に通した。

**実測結果**:

| ケース | dump結果 | 選定結果 | exit code |
|---|---|---|---|
| 両方reachable | `dnode1=True, dnode2=True` | `dnode1`(定義順先頭、prefer未指定) | 0 |
| 先頭のみreachable | `dnode1=True, dnode2=False` | `dnode1` | 0 |
| 2番目のみreachable | `dnode1=False, dnode2=True` | `dnode2`(フォールバック) | 0 |
| 両方unreachable | `dnode1=False, dnode2=False` | T4が発火、`decoy_test: no node in group 'proxmox' is reachable via SSH ping, cannot select an execution host. Candidate reachability: dnode1=False, dnode2=False.` | **2**(非ゼロ) |

`pen_reachable`の型は`selected=dnode1 pen_reachable=True (type=bool)`のように出力され、文字列でなく実際のPython boolであることを確認した(本skillの「control構文のみのJinjaがNoneになる」既知バグと同型の懸念があったため、型まで確認した — 詳細は§5)。

到達不能ホスト(`dnode2`など)にも`pen_reachable`が立っていることは、Play 0の`post_tasks`のdump(全候補を`ansible_play_hosts_all`経由で列挙)で確認した。`PLAY RECAP`側でも該当ホストは`ignored=1`(`ignore_unreachable`によりPlayに残存)として現れ、`unreachable=0`(致命的UNREACHABLEとしては扱われない)ことを確認した。

**追加検証(contractの範囲外だが、共通roleの健全性のため実施)**:
- `pen_prefer: dnode2` + 両方reachable → `dnode2`が選定される(prefer優先)ことを確認。
- `pen_prefer: dnode2` + `dnode2`が到達不能(先頭のみreachableのinventory) → `dnode1`へフォールバックすることを確認。
- `pen_prefer: dnode-typo`(候補groupに存在しない名前) → T1のassertで`"pen_prefer ('dnode-typo') must be either empty or a member of that group"`として即fail することを確認(綴り誤りを黙って無視しない、plan本文の要求どおり)。
- `--limit dnode1`(候補groupの一部だけに制限) → T1の呼び出し規約assertが`play hosts: ['dnode1'], group members: ['dnode1', 'dnode2']`の不一致で正しく落ちることを確認。3本のladder playbookは実運用で`--limit`を使わない(各playbookの「使用方法」コメントは`-e target=...`のみ)ため実害はないが、この制約自体は今回の契約の一部(呼び出し規約のassert)として機能している。

## 5. Jinja設計上の判断根拠(目視で終わらせないための検討過程)

このskill(`ansible-implementation-style`)には「control構文のみのJinjaが空文字列でなく`None`になる」という既知バグの記録があり、当初は到達可能ホスト名リストを`{% for %}`+`namespace`で組み立てる案を検討した。しかしこの手法は「controlブロック+最後の`{{ expr }}`」という構造になり、この構造がAnsible-core 2.20の新テンプレートエンジン(`ansible/_internal/_templating/`)でどう評価されるか(native型で返るか、文字列化されるか)を確信できなかったため、**採用しなかった**。

代わりに、同一リポジトリ内で2026-07-26に実機検証済みの`roles/proxmox_patch_dryrun/tasks/main.yml`の`_reached_nodes`パターン(`map('extract', hostvars) | selectattr(attr, 'defined') | map(attribute='inventory_hostname') | list`、単一の`{{ }}`式のみで完結)を転用した。この方式は「controlブロックなし、単一のフィルタチェーン式のみ」であるため、target-group一致判定・None化バグのいずれの懸念も生じない。実際にdecoy検証で`type_debug`まで確認し、`pen_reachable`・選定結果とも期待どおりのnative型・値であることを実測で確認済み(§4-2)。
