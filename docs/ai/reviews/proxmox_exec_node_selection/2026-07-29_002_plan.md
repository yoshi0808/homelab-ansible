作成: 2026-07-29 / Coordinator

Tier 3。この計画はReviewerの計画査読(層1・層2)を経てからImplementerへ渡す。

## 0. 方針

「どのノードで実行するか」という同一の問いに5箇所が帰着するため、**preflightをコピーせず1つのroleへ括り出す**。`playbooks/unifi_backup_fetch.yml` の既存preflight(ADR-001、実地PASS済み)を原型とし、ホスト名リテラルを inventory group と `ansible_play_hosts_all` の定義順へ一般化する。

**Step 1(欠陥の解消)が通ってからStep 2(負債の整理)へ進む。** 分割の理由は量ではなくリスクの性質 — Step 1は本番で現に壊れているもの、Step 2は動いているものの作り直しであり、回帰したときの切り分けを可能にするため。

## 1. 設計(Implementerに発明させないため、ここで確定させる)

### 1-1. 新role `roles/proxmox_exec_node`

`tasks/main.yml` と `defaults/main.yml` のみ。handlers・templates・filesは持たない。

**呼び出し規約**: このroleは「候補ノード全体を`hosts:`に持つPlay」から呼ぶ。roleが自分でPlayを作ることはできないため、この前提はroleの先頭でassertする(下記T1)。

| 変数 | 既定 | 意味 |
|---|---|---|
| `pen_candidate_group` | `proxmox` | 候補ノードのinventory group名。呼び出し側Playの`hosts:`と一致させる |
| `pen_prefer` | `''` | 優先ノードのinventory名。空なら定義順の先頭を優先とみなす |
| `pen_target_group` | (必須) | 選定結果を登録するdynamic group名 |
| `pen_caller` | (必須) | 失敗メッセージの先頭に付ける呼び出し元識別子 |

**出力**

- dynamic group `{{ pen_target_group }}` に、選定された**1ノードだけ**が登録される。
- 全候補ノードに per-host fact `pen_reachable`(bool)が立つ。到達不能ノードにも立つ(`set_fact`はcontroller側で完結するため、`ignore_unreachable`でPlayに残ったホストにも実行される — 2026-07-26に実機で確認済み: `docs/ai/reviews/proxmox_patch_dryrun/2026-07-26_005_test_result.md` §14-4)。

**タスク構成**

| # | タスク | 要点 |
|---|---|---|
| T1 | 入力assert | `pen_target_group` / `pen_caller` が非空。`ansible_play_hosts_all` が `groups[pen_candidate_group]` と一致すること(呼び出し規約の担保)。`run_once` + `delegate_to: localhost` |
| T2 | `ansible.builtin.ping` | `ignore_unreachable: true` + `ignore_errors: true` + `register`。**fact gatheringではなく明示的なprobeで判定する**(requirement Q1: fact cachingが有効な実行環境でも誤判定しないため) |
| T3 | `set_fact: pen_reachable` | `not (register.unreachable | default(false) | bool) and not (register is failed)`。`unifi_backup_fetch` の実装と同一式 |
| T4 | 全滅時のfail | `run_once` + `delegate_to: localhost`。メッセージに `pen_caller` と**全候補ノードの名前と到達性**を列挙する(R3) |
| T5 | `add_host` で選定 | `run_once` + `delegate_to: localhost` + `changed_when: false` |

**T5の選定式**(確定):

```
到達可能なノード一覧 R = ansible_play_hosts_all のうち hostvars[h].pen_reachable が真のもの
                        (ansible_play_hosts_all は inventory 定義順を保つ)
選定 = pen_prefer が R に含まれれば pen_prefer、含まれなければ R の先頭
```

`pen_prefer` が候補groupに存在しない名前だった場合は T1 のassertで落とす(綴り誤りを黙って無視しない)。

| playbook | `pen_prefer` | `pen_target_group` |
|---|---|---|
| `recovery_vm_reboot.yml` | (空=定義順) | `recovery_exec_target` |
| `recovery_service_restart.yml` | (空=定義順) | `recovery_exec_target` |

**Play構成(変更後)**

|---|---|---|

```
候補   = groups['proxmox']（inventory定義順）
prefer = 候補のうち、対象VMのtagsが 'prefer' ~ <その候補名> を含むもの（0個または1個）

prefer が無い          → 現行どおり fail（「prefer<node>タグが無い」）
prefer が到達可能      → restore_node = prefer,             fallback = false
prefer が到達不能      → restore_node = 到達可能な候補の先頭, fallback = true
到達可能な候補が無い   → Play 1 の T4 で既に fail 済み（ここへ到達しない）
```

`add_host` で `brv_restore_targets` へ渡す変数に `brv_preferred_node` と `brv_restore_fallback` を追加する。

### U5: recovery-probe.py の候補フォールバック

**担い手**: Implementer(subagent)

**触るファイル**
- `roles/recovery_probe/files/recovery-probe.py` — `pvesh_vm_status`(L214-)と`pvesh_vm_start`(L238-)が使う`cfg["pve_host"]`を候補ループへ
- `roles/recovery_probe/templates/recovery-probe.json.j2` L10 — `pve_host` → `pve_hosts`(配列)
- `roles/recovery_probe/defaults/main.yml` L25-28 — `recovery_probe_pve_host: pve2` を `recovery_probe_pve_hosts: [pve1, pve2]` へ。**暫定である旨のコメントを削除する**(暫定でなくなるため)

**要点**(2026-07-29改訂。初版の設計は計画査読 `2026-07-29_003_plan_review.md` で層1・層2の両方から否定されたため差し替えた)

- **操作ごとにフォールバックする方式を採らない。** 代わりに、ラダー発火のたびに**先頭で1度だけ read-only の probe でノードを選び**、以降の pvesh 呼び出しは全てそのノードへ送る。Ansible側(§1-1)と同じ「先に選んでから動く」構造にする。
- 新規 `pick_pve_host(cfg) -> str | None`: `cfg["pve_hosts"]` を定義順に `ansible <host> -m ansible.builtin.ping` で probe し、**rc が 0 の最初のノード**を返す。全滅なら `None`。**stdout/stderr の文字列解析を行わない。**
- `pvesh_vm_status` / `pvesh_vm_start` は選定済みノードを**引数で受け取る**(`cfg["pve_host"]` の参照をやめる)。両者を1つのヘルパへ寄せない。
- `fire_ladder`(L260-)は `record_firing` の直後で `pick_pve_host` を1回呼ぶ。`None` なら**既存の `pve-unreachable` 分岐(L288-295)へそのまま合流**させる(critical通知 + return)。制御フローの変更を最小に保つ。

**この設計が初版の2つの欠陥をどう解消するか**

| 指摘 | 解消 |
|---|---|
| 層1: 冪等な `pvesh_vm_status` と非冪等な `pvesh_vm_start` で判定基準が違うのに、共通ヘルパの仕様が片方しか定めていない | 共通ヘルパを作らない。フォールバックは probe 段階だけで起き、**pvesh 呼び出しは一切リトライしない**ため、冪等性の区別が不要になる |
| 層2: `ansible` の UNREACHABLE は stderr に出ない(`ansible.cfg` が `display_failed_stderr` を設定しておらず既定は `no`。実測で確認済み) | 文字列解析を使わない。`ping` モジュールの rc だけで判定する |

**受け入れる残存リスク**: probe 成功後・pvesh 実行前にそのノードが落ちる競合窓が残る。その場合 pvesh が失敗し、既存のラダー失敗経路(critical通知でエスカレーション)へ落ちる — **現行と同じ挙動**であり、非冪等操作の二重発行は起きない。

- 配備は `playbooks/recovery_probe_setup.yml -l quory`。2026-07-29に入れた自動反映(`handlers/main.yml`)により、内容が変わる配備なので**restartが発火するはず** — これは`docs/ai/status.md` Watch行の初観測になる。Testerは`ExecMainStartTimestamp`が配備物のmtimeより新しいことを確認する(playbook末尾のassertが自動判定する)。

**完了条件**: AC6。ローカルのstub `ansible` で「先頭候補が到達不能→2番目が選ばれる」「全候補到達不能→`None`→critical通知」の2分岐を確認する。
