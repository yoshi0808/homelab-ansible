## 2. 契約(plan §3 U5)との対応

- **操作ごとのフォールバックを廃止**し、`fire_ladder`の`record_firing`直後で新規`pick_pve_host(cfg)`を1回だけ呼ぶ設計にした。共通ヘルパ(`_run_on_any_pve`的なもの)は作らず、`pvesh_vm_status`/`pvesh_vm_start`は選定済み`pve_host`を**引数で受け取る**形にとどめた(層1指摘の「冪等性の異なる2箇所に単一判定基準を強制する」問題を、ヘルパそのものを作らないことで解消)。
- `pick_pve_host`は`cfg["pve_hosts"]`を定義順に`ansible <host> -m ansible.builtin.ping`でprobeし、**rcが0の最初のノード**を返す。全滅なら`None`。**stdout/stderrの文字列解析は一切行わず、`r.returncode`のみで判定する**(層2指摘: 本リポジトリの`ansible.cfg`は`display_failed_stderr`を設定しておらず既定`no`のため、`UNREACHABLE!`はstdoutに出る。plan本文の該当記述をコメントに引用し、なぜ文字列解析をしないかを残した)。
- `fire_ladder`内は次の形にした(制御フロー変更を最小化):
  ```python
  record_firing(fpath, firings)
  pve_host = pick_pve_host(cfg)
  if pve_host is None:
      vm_status, vm_node, vm_id = "pve-unreachable", None, None
  else:
      vm_status, vm_node, vm_id = pvesh_vm_status(cfg, pve_host, target)
  log(f"LADDER {target}: pvesh status = {vm_status}")
  if vm_status == "pve-unreachable":
      queue_notify(cfg, "critical", ... "pve 到達不能" ...)  # 既存の文言そのまま、無変更
      return
  ```
  既存の`pve-unreachable`分岐(通知タイトル・本文)は1文字も変更せず、`pick_pve_host`が`None`を返した場合と`pvesh_vm_status`自体が失敗した場合の両方がこの1箇所へ合流する。`vm_status == "pve-unreachable"`のとき`pvesh_vm_status`は呼ばれない(候補全滅なら無駄なpvesh呼び出しをしない)。
- `pvesh_vm_start`(`vm_status == "stopped"`のときのみ呼ばれる)は選定済み`pve_host`をそのまま使い、`fire_ladder`は`pick_pve_host`を2度呼ばない。非冪等操作(VM start)が同一発火内でリトライされる経路はコード上存在しない(呼び出しは`fire_ladder`本体に1箇所のみ)。
- `recovery_probe_pve_host`(単一)を`recovery_probe_pve_hosts`(リスト、既定`[pve1, pve2]`)へ置き換えた。「暫定」コメントは削除し、pve1が平日シャットダウン中でも自動フォールバックするため書き換え運用が不要になった旨を記載(requirement R9のゴール「申し送り自体を消滅させる」に対応)。
- テンプレートは`"pve_host": "{{ recovery_probe_pve_host }}"` → `"pve_hosts": {{ recovery_probe_pve_hosts | to_nice_json }}`(既存の`targets`キーと同じ`to_nice_json`フィルタを踏襲、新規パターンを持ち込んでいない)。

## 5. 追記(2026-07-29 差し戻し対応): 配備時のinventory妥当性assertを追加

### 5-1. 指摘内容

`ansible <host> -m ansible.builtin.ping` は、`<host>` が inventory のどのホストパターンにもマッチしない場合、実機には一切接続せず**rc=0**(`Could not match supplied host pattern, ignoring`という警告のみ)を返す。`pick_pve_host`はrcのみで到達性を判定するため、`recovery_probe_pve_hosts`に綴りを誤った・inventoryから削除された名前が入っていると、そのホストを「到達可能」と誤選定してしまう。現行の設定値(`[pve1, pve2]`)は実inventoryと一致しているため直ちには顕在化しないが、将来の設定変更時に無言で壊れうる。

### 5-2. 追加した対応(契約どおり)

- **`pick_pve_host`(Python側)は一切変更していない。** 実行時の文字列解析を増やす方向(計画査読で既に否定された方向)には戻していない。`git diff --stat -- roles/recovery_probe/files/recovery-probe.py roles/recovery_probe/templates/recovery-probe.json.j2 roles/recovery_probe/defaults/main.yml` が本追記の前後で変化していないことを確認済み(§1の実装から1バイトも変えていない)。
- 代わりに**配備時(Ansible側)の妥当性検証**を追加した。`roles/recovery_probe/tasks/main.yml` の先頭(既存の最初のタスクより前)に以下のassertを新設。

  ```yaml
  - name: Assert recovery_probe_pve_hosts is non-empty and every host exists in inventory
    ansible.builtin.assert:
      that:
        - recovery_probe_pve_hosts | length > 0
        - recovery_probe_pve_hosts | difference(groups['proxmox']) | length == 0
      fail_msg: >-
        recovery_probe_pve_hosts が空、または inventory の proxmox グループ
        ({{ groups['proxmox'] | join(', ') }}) に存在しないホスト名を含んで
        います: {{ recovery_probe_pve_hosts | difference(groups['proxmox']) }}。
        pick_pve_host はホストパターン不一致時も rc=0 を返すため、この値の
        誤りは実行時には検知できない。recovery_probe_pve_hosts を修正すること。
      quiet: true
  ```

  - リストが空の場合は`length > 0`が偽になりfailする(契約どおり)。
  - `groups['proxmox']`は`inventories/homelab/hosts.yml`が持つ静的group(pve1, pve2)で、動的group登録(`proxmox_exec_node`が使うような`add_host`)を必要としない — このassertはホストへの接続を一切行わず、controller側のJinja評価のみで完結する。
  - `handlers/main.yml`・`playbooks/recovery_probe_setup.yml`は無変更(契約どおり、`git status`/`git diff`で確認済み)。
