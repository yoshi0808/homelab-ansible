# requirement: 月次full-upgradeでauthy / monnieのhealthcheck WARNINGを捨てない

状態: 合意済み(2026-10-10、Yoshinobu)

## 背景

2026-09-26のplaybook一覧・Policy監査で見つかった `_003` F5(`docs/ai/reviews/playbook_catalog_policy_audit/2026-09-26_003_*.md`)。

`roles/ubuntu_vm_full_upgrade/tasks/healthcheck.yml` は、authyでは `radius_healthcheck`、monnieでは `monitoring_healthcheck` の `check.yml` を流用している。両roleは `radius_warnings` / `monitoring_warnings` を出力しているが、集約のtask(「Consolidate healthcheck warnings across all node types」)は ansy/quory の汎用checkの warnings しか集めていない。その直前のコメント「radius / monitoring の各roleは warnings を返さない(criticalsのみ)」は事実と違う(`roles/radius_healthcheck/tasks/check.yml:7`、`roles/monitoring_healthcheck/tasks/check.yml:4` の Exports)。

Policy `docs/ai/policies/ubuntu_vm_patch_policy.md` の UV-056(healthcheckが `WARNING` または `CRITICAL` なら通知対象と判定する)と UV-072(healthcheckが `WARNING` なら通知する)に合わない。

## 求めること

- R1. 集約した warnings に、authy では `radius_warnings`、monnie では `monitoring_warnings` を含める。criticals の集約と同じ形にそろえる。
- R2. 事実と違うコメントを、現状に合う内容へ直す。
- R3. warnings を受け取ったあとの扱い(`tasks/main.yml` の通知と、処理を止めないこと)は変えない。criticals の扱いも変えない。
- R4. ansy / quory の汎用checkの挙動を変えない。

## 受入条件

- AC1. authy で `radius_warnings` が空でないとき、集約後の `ubuntu_vm_full_upgrade_healthcheck_warnings` にその要素が含まれる。monnie と `monitoring_warnings` についても同じ。
- AC2. 3種類の warnings がすべて空のとき、集約結果は空のリストになる(未定義や `None` にならない)。
- AC3. 対象外のホストで、別のホスト種別の変数が未定義でもエラーにならない。
- AC4. `ansible-playbook --syntax-check` が、このroleを使うplaybookで通る。

## 検証の手段

実ホストには触れない。固定の入力を与えて集約のtaskだけを動かす方法(localhost、`ansible_connection: local`)で AC1〜AC3 を確かめる。実ホストでの確認は、次の月次の自動発火の通知を観測して行う。

## 範囲外

- radius / monitoring の各roleが何を `WARNING` と判定するかの見直し。
- 同じ監査の他のfinding。
