## AC1 — pve が1台停止しているときの `recovery_exec_setup`

コマンド(`recovery_exec` roleの `target_setup.yml` を `include_role tasks_from` で直接
実行。`--check`必須、tester-gate: check-mode-native):

```
ansible-playbook test_recovery_exec_pve.yml --check \
  -e '{"recovery_exec_pve_probe_timeout": 3,
       "recovery_exec_pve_targets": [
         {"name":"decoy-pve-up","host":"<LOOPBACK>"},
         {"name":"decoy-pve-down","host":"<TESTNET-A>"}]}'
```

実測(RC=プロセス終了コード、`echo $?`で直接取得):

```
RC=0
TASK [Probe TCP reachability ...]
ok: [localhost] => (item={'name': 'decoy-pve-up', 'host': '<LOOPBACK>'})
failed: [localhost] (item={'name': 'decoy-pve-down', 'host': '<TESTNET-A>'}) => {"msg": "Timeout when waiting for <TESTNET-A>:22", ...}
...ignoring
TASK [Show which pve target nodes are targeted vs excluded this run]
  "対象としたpveホスト: decoy-pve-up",
  "外したpveホスト    : decoy-pve-down"
TASK [Create recovery-exec user on pve target nodes]
skipping: [localhost] => (item={'name': 'decoy-pve-up', ...})   # --check gateにより非適用。ループには1件のみ
（以降5タスクも同様に decoy-pve-up の1件のみがループに現れ、decoy-pve-down は現れない）
PLAY RECAP: ok=4 changed=0 unreachable=0 failed=0 skipped=18 ignored=1
```

判定: 終了コード0、生きている側(decoy-pve-up)が6タスクすべてのループに残り、外した側
(decoy-pve-down)は1件目のprobe以降どのタスクのループにも現れない。出力に両方の名前が
残る。**PASS**。

### 否定対照実験(decoyの妥当性の裏取り)

修正前と同じ形(未フィルタの `recovery_exec_pve_targets` をそのまま `delegate_to` ループ
する、check_mode制約の無い素のplaybook)で同じdecoy対象(<LOOPBACK>=到達可能、
<TESTNET-A>=到達不能)を実行:

```
RC=4
changed: [localhost -> <LOOPBACK>] => (item={'name': 'decoy-up', ...})   # 1件目は成功
failed: [localhost -> <TESTNET-A>] (item={'name': 'decoy-down', ...}) => {"unreachable": true, ...}
fatal: [localhost -> {{ target_item.host }}]: UNREACHABLE! => {"msg": "All items completed", ...}
（"Should this print"のdebugタスクは出力に現れない＝play中断）
PLAY RECAP: unreachable=1
```

requirementが引用する2026-08-11 task 675(`failed=0`のままrc=4、pve2への後続タスクが
実行されない)と同型の失敗を、このdecoy構成が実際に再現することを確認した。これにより
AC1〜AC3の実測がdecoyの都合の良い前提の上に成立しているのではなく、修正前は実際に壊れ、
修正後に直る、という比較になっていることを自分で裏取りした。

(初回の対照実験はplay全体に`connection: local`を付けており、`delegate_to`の宛先に
関わらず全タスクがコントローラ上でローカル実行される既知の罠を踏んで無効だった。
`connection: local`を外して再実行し、上記の結果を得た。)

## AC4 — 到達不能ホストがある日の drift チェック

decoy inventory(`decoy-reachable`=`ansible_connection: local`、`decoy-unreachable`=
`ansible_host=<LOOPBACK> ansible_port=2223`で閉ポート)+ decoy catalog
(`deployment_drift_check_files`を上書き。`decoy-reachable`に「一致するfile」1件+
「distが存在せずfindingになるfile」1件、`decoy-unreachable`に同じく「findingになる
はずのfile」1件を割り当てて、到達不能側でも本来ならfindingが立つ状態を作った)で、実際の
`collect.yml`/`evaluate.yml`/`report.yml`をscratch playbook経由で実行(safe-readonly、
`--check`なし、`skip_notifications: true`明示)。

```
PLAY RECAP: decoy-reachable ok=21 ... / decoy-unreachable ok=12 skipped=16 ignored=2 / localhost ...
TASK [Show the drift summary]
  "drift        : 1 件",
  "checked      : decoy-reachable",
  "unverified   : decoy-unreachable"
report JSON:
  "checked_hosts": ["decoy-reachable"],
  "unverified_hosts": ["decoy-unreachable"],
  "checked_counts": {"decoy-reachable": {...}}   # decoy-unreachableのキーは存在しない
  "findings": [ {host: decoy-reachable, ...} ]   # decoy-unreachable由来のfindingは0件
```

decoy-unreachableの実行ログでは、`Stat deployed files`タスクが実際に
`"unreachable": true`を持つ`fatal: UNREACHABLE!`結果(`ignore_unreachable`により
ignore)を返しており、`collect.yml`の"Downgrade reachability"タスクがこの`unreachable`
キーの有無を正しく読んでいることを実測で確認した(requirement Q2で「未確認」とされていた
`register`の挙動そのもの)。

判定: 終了コード0、`unverified`に到達不能ホスト名が載り`checked`には載らない、到達不能
ホスト由来のfindingが0件、かつ到達可能ホスト(decoy-reachable)のfindingは1件のまま
(到達不能ホストの存在が他のfindingを潰していない)。**PASS**。

なお8本の"Build findings for X"タスクは差分上すべて同一の`when: deployment_drift_check_reachable`
が付いており(diff読み合わせで確認)、今回実測したのは`file`カテゴリのみだが、機構は
カテゴリに依らず共通(同じ変数・同じ`when:`パターン)であるため、`forced_command`等
他カテゴリへも同様に効くと判断する(カテゴリごとの個別実行はしていない)。

## AC6 — 全ホスト到達可能なときの drift チェック

### decoy(単一ホストのみ、reachable)

`decoy-reachable`のみを対象に同じ構成で実行。`unverified: []`、findingは1件のまま生成
される(present.txtは一致、missing.txtはfinding)。

### 実host回帰(到達可能な範囲: ansy / monnie)

```
ansible-playbook playbooks/deployment_drift_check.yml \
  -e deployment_drift_check_hosts=ansy:monnie -e skip_notifications=true
```

```
RC=0
"drift        : 0 件",
"checked      : ansy, monnie",
"unverified   : (なし)"
PLAY RECAP: ansy ok=24 ... / monnie ok=22 ... / localhost changed=2 (レポート保存のみ)
TASK [Notify only when drift was found]  → skipping (drift=0のため)
```

実際の本番カタログ・実host(quory/authy/pve1/pve2は含めず)に対して、新しい
`deployment_drift_check_reachable`ゲートを含む現行コードが正常に完走し、到達可能な
2ホストとも`checked`に載り`unverified`は空、既存のfinding検出(今回は0件=健全な現状)が
機能することを確認した。

判定: **PASS(部分)**。「finding内容が現行と一致する(回帰が無い)」を、diffの適用前
コードとの直接A/B比較では確認していない — 作業ツリーの実装を変更せず退避・復元する
手段が無いため(Tester制約)。代わりに(a) diffの読み合わせで8本の"Build findings"の
本体Jinjaが無変更で`when:`追加のみであること、(b) decoy/実hostの双方でfinding生成が
現に機能していることの2点で判断した。完全なA/B比較が要る場合はCoordinator判断で
別途の手段(例: 別worktreeでの比較)を検討されたい。

## 静的検証で確認した対応関係

- `collect.yml`の"Downgrade reachability"タスクが参照する8つの`register`名
  (`deployment_drift_check_file_stat`/`_unit_show`/`_keys_raw`/`_report_owner`/
  `_hosts_raw`/`_path_stat`/`_sudoers_listing`/`_dispatch_probe_result`)は、同ファイル内の
  実際の`register:`宣言8件と一致している(`grep -n "register:"`で確認)。一致しない場合
  `| default([])`により沈黙して不整合が起きるため個別に裏取りした。
- `target_setup.yml`のpve向け6タスクは、diffにより`loop: recovery_exec_pve_targets`から
  `loop: recovery_exec_pve_targets_reachable`へ機械的に置換されている(6箇所とも確認)。
  authy/monnie向けタスク(`recovery_exec_targets`使用)は無変更。
- `recovery_exec/defaults/main.yml`の`recovery_exec_pve_probe_timeout: 5`はコードコメントで
  設計根拠(同一LAN内のTCP接続、応答は概ね即時)が説明されている。実playbookでの計測は
  未実施(pve到達不能)。

## 未実施(理由つき)

- `recovery_exec_setup.yml`の`-l quory`実host完全E2E: ansyはquoryへの認証情報を持たず
  実行不可能。`inventory_hostname: quory`をdecoyで偽装することも、decoy成立条件1
  (実host名を書かない)に反するため行わなかった。`target_setup.yml`単体実行(本報告の
  AC1〜AC3)で代替した。`roles/recovery_exec/tasks/main.yml`のquory guard自体は本diffの
  対象外であり、今回の変更によって壊れていないことをコード読み合わせでのみ確認した
  (無変更行であることをdiffで確認済み)。
- pve1/pve2実機での障害再現: 認証情報が無く、かつpve1は本日(日曜)起動中で平日停止状態を
  再現できない。
- AC6の完全A/Bバイナリ比較: 対象実装を変更しない制約下でのretreat/restoreの手段が無い。
- R7(所要時間の計測): 実pveへ到達できないため計測対象がない。
- R8(authy/monnie側への同種probe): requirement非対象(P2)につき未実施。
- Semaphore実行時の終了コード反映(rc→Semaphoreジョブ成否表示): Semaphoreを起動していない
  ため未確認。本報告のrcはすべて`ansible-playbook`プロセス自身の終了コード(`$?`)である。

## 残存リスク

- AC6の「回帰なし」は完全なA/B比較ではなく、コード読み合わせと部分実行での確認に留まる。
  finding本体のJinjaは無変更のため技術的リスクは低いと判断するが、確定的な証明ではない。
- `recovery_exec_pve_probe_timeout`(既定5秒)の妥当性は実測していない。pve1が停止して
  いる平日に初めて本番で計測されることになる。
- `roles/recovery_exec/tasks/main.yml`のquory guardと今回のtarget_setup.yml変更の
  組み合わせ(E2E)は、実host環境でしか検証できない。次にquoryから手動起動されたときが
  実質的な初回検証になる。
