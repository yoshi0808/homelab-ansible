# requirement: pve の停止を「到達不能」として扱う(2箇所)

案件: `pve_unreachable_handling`
作成: 2026-08-16 / Coordinator

## 1. 問題定義

`pve1` は夏季平日にシャットダウンする運用にある。2本の playbook が、この**予定された停止**を「異常」として扱っている。どちらも根は同じで、**pve が落ちうることが対象ホストの決め方に反映されていない**。

### ① `recovery_exec_setup.yml` が rc=4 で終わり、生きているノードへの配備も止まる

`roles/recovery_exec/tasks/target_setup.yml` の pve 向け6タスク(181・203・218・234・258・299行)は、いずれも `recovery_exec_pve_targets`(`pve1` / `pve2` 固定)を `loop` し `delegate_to: "{{ target_item.name }}"` で配布する。到達性の判定は1箇所も無い。

`pve1` が停止していると、その item が `unreachable: true` になり、**Ansible は loop 内の1件の unreachable を task 全体の UNREACHABLE へ昇格させる**。host が unreachable になると play はそこで打ち切られる。

観測(task 675、2026-08-11 09:13 JST):

```
TASK [recovery_exec : Create recovery-exec user on pve target nodes]
failed: [quory -> pve1] (item={'name': 'pve1', ...}) =>
  {"msg": "... ssh: connect to host pve1.internal port 22: No route to host",
   "unreachable": true}
ok:     [quory -> pve2(pve2.internal)] => (item={'name': 'pve2', ...})
fatal: [quory -> {{ target_item.name }}]: UNREACHABLE! => {"msg": "All items completed", ...}

PLAY RECAP
quory : ok=45  changed=1  unreachable=1  failed=0
Failed to run task: exit status 4
```

**`failed=0` である。** 実装は失敗していない。打ち切りが pve セクションの**最初の**タスクで起きるため、**生きている `pve2` に対しても後続5タスク(`.ssh` / dispatch script / sudoers / authorized_keys ほか)が実行されない。**

### ② `deployment_drift_check` が到達不能を drift として報告する

`playbooks/deployment_drift_check.yml:30` のヘッダは設計意図をこう書いている。

> 到達できないホストは「未確認」として記録し、赤くしない(pve1の平日停止運用)

実際にはそうなっていない。2つの機構が噛み合っていない。

- `playbooks/deployment_drift_check.yml:39` の `ignore_unreachable: true` は、**ホストを play から脱落させない**。`pve1` は `ok=18 ignored=1` で完走し、`play_hosts_ok` に残る。
- `roles/deployment_drift_check/tasks/report.yml:34-36` の `unverified` は `play_hosts_all` から `play_hosts_ok` を引いた差集合で求める。上記により**空になる**。
- `roles/deployment_drift_check/tasks/evaluate.yml:88-95` は `r.content is not defined` という1条件だけで finding を作り、`detail` に固定文字列 `authorized_keysが読めない(未配備か権限)` を焼き込む。unreachable の結果も `content` を持たないため、この分岐に落ちる。

結果、レポート JSON に**到達不能だったという情報が1つも残らない**。観測(task 676、2026-08-11 09:38 JST、ジョブ自体は `success` / exit 0):

```
drift        : 1 件
checked      : quory, ansy, monnie, authy, pve1, pve2
unverified   : (なし)
```

**2026-08-11、この JSON を読んだ側が「pve1 の recovery-exec 用 authorized_keys 配備または権限に drift が出ている」と誤診断した。** 正しくは `No route to host` であり、同一 task で `pve2` は `ok` を返している。両者は `roles/deployment_drift_check/defaults/main.yml:293` の**同一カタログエントリ**で、`recovery_exec_setup.yml` の**同一ループが同一 run で配布する**。片方だけ配備や権限が壊れることは起こらない。

さらに Slack 通知(`report.yml:100-116`)は、この finding に対する「直し方」として **①で失敗する playbook のボタン**を提示する。誤った警告が、失敗する操作を指している。

## 2. ゴール

1. 到達できるホストへは、他のホストの停止に関わらず**配備が最後まで届く**。
2. 到達できずに対象から外したホストが、**出力に名前で残る**。
3. 到達不能を「異常」と呼ばない。drift レポートで**未確認として区別**される。

## 3. 非ゴール

- **検知能力の向上は含めない。** `template` 配備物(dispatch script / sudoers / unit 本体 / authorized_keys)の内容を repo と突き合わせる Tier 2 は別案件(`roles/deployment_drift_check/defaults/main.yml:8-12`、status.md の該当行)。**本案件を終えても、pve の dispatch script が古いままであることは検知できない。**
- **`proxmox_patch_dryrun` の到達性判定の寄せ替えは含めない**(status.md の別行。据え置き理由が生きている)。
- **`roles/proxmox_reachable_nodes` の再利用・改修は含めない。** 同 role の呼び出し規約は「候補 group の部分集合を `hosts:` に持つ play から呼ぶ」であり判定対象は play のホストだが、本案件の2箇所はいずれも条件を満たさない — ①は pve が `delegate_to` の宛先で play のホストではなく、②は play の `hosts:` が5グループの和で `proxmox` の部分集合にならない。**再利用するのは「fact gathering ではなく明示的な probe で判定する」という考え方だけ。**
- `pve1` の停止運用そのものは変えない。
- `recovery_exec_setup.yml` に schedule を付けない(現在 schedule は無く、手動起動のみ)。

## 4. ユーザーストーリー

- 運用者として、`pve1` が停止している日に `recovery_exec_setup` を流しても、**生きている `pve2` には配備が完了してほしい**。そして**何を飛ばしたのかを名前で知りたい** — 「触っていない」と「触って正常だった」は別物であり、ログを読み解かないと区別できない状態では取り違える。
- 運用者として、drift の警告は**本当のドリフトのときだけ**鳴ってほしい。予定された停止で毎回鳴ると、本物のドリフトが埋もれる。
- 調査する側(人・AI とも)として、**レポート JSON だけを読んで正しい結論に至りたい**。到達不能だった事実が記録に残っていなければ、書かれているとおりに読んで誤診断する。

## 5. 要件

### P0(必須)

| ID | 要件 |
|---|---|
| **R1** | `recovery_exec_setup.yml` は、pve 向けループの**手前で一度だけ**各 `recovery_exec_pve_targets` の到達性を測り、到達できたものだけを以降6タスクの対象にする。判定は fact gathering ではなく**明示的な probe** による(Semaphore 側の fact caching に依存しない)。 |
| **R2** | R1 により、`pve1` 停止時も play は打ち切られず、**`pve2` に対して6タスクすべてが実行される**。 |
| **R3** | 到達できず対象から外したホストが、**playbook の出力に名前で残る**。「対象にしたホスト」と「外したホスト」の双方が読み取れること。 |
| **R4** | `deployment_drift_check` は、到達不能に起因する読み取り失敗を **finding として計上しない**。未配備・権限異常による読み取り失敗との**区別が付く**こと。 |

| **R7** | ①の probe のタイムアウトは、停止ノードがある日に playbook 全体の所要時間を目立って延ばさない値にする。 |

## 6. 受入条件

終了コードは Semaphore が成否判定に用いるため、すべての AC で明示する。

### AC1 — pve が1台停止しているときの `recovery_exec_setup`

- **Given** `recovery_exec_pve_targets` の一方が到達不能、他方が到達可能な状態
- **When** `recovery_exec_setup.yml` を `-l quory` で実行する
- **Then**
  - 終了コードは **`0`**(現行は `4`)
  - 到達可能な側に対して pve 向け6タスクが**すべて実行される**(現行は1タスク目で打ち切り)
  - 出力に、対象としたホスト名と**外したホスト名の双方**が現れる
  - `authy` / `monnie` 向けの既存タスク群の挙動は変わらない

### AC2 — pve が2台とも到達可能なとき

- **Given** `recovery_exec_pve_targets` の両方が到達可能
- **When** `recovery_exec_setup.yml` を `-l quory` で実行する
- **Then**
  - 終了コードは **`0`**
  - 両ノードに対して6タスクが実行される(**現行の挙動から変化しないこと**)
  - 外したホストは無い旨が出力から読み取れる

### AC3 — pve が2台とも到達不能なとき

- **Given** `recovery_exec_pve_targets` の両方が到達不能
- **When** `recovery_exec_setup.yml` を `-l quory` で実行する
- **Then**
  - 終了コードは **`0`**(Yoshinobu 決定、2026-08-16)
  - **サイレント成功にしない。** pve 向け配備が1件も行われなかったことが出力から明確に読み取れる(外したホスト名を両方とも出す)
  - `authy` / `monnie` 向けの配備は従来どおり完了する

決定の理由: `pve` は配布先の一部にすぎず、`authy` / `monnie` への配備は成立している。クラスタ全停止は別の検知経路が拾うべき事象であり、この playbook を赤くしても復旧には寄与しない。

### AC4 — 到達不能ホストがある日の drift チェック

- **Given** 検査対象のうち1ホストが到達不能
- **When** `deployment_drift_check.yml` を実行する
- **Then**
  - 終了コードは **`0`**(現行も 0。変えない)
  - サマリの `unverified` に当該ホスト名が**載る**
  - `checked` に当該ホスト名は**載らない**
  - 到達不能に起因する `forced_command` の finding が **0 件**になる
  - レポート JSON の `unverified_hosts` に当該ホスト名が入る
  - **他ホストの drift 検出は従来どおり働く**(到達不能ホストの存在が他の finding を潰さない)

### AC5 — 本物の読み取り失敗が握り潰されないこと

- **Given** ホストは到達可能だが、対象の `authorized_keys` が存在しない、または読み取り権限が無い
- **When** `deployment_drift_check.yml` を実行する
- **Then**
  - **finding が立つ**(`expected: readable` / `actual: read failed`)
  - 当該ホストは `unverified` に**入らない**(到達はできているため)
  - 終了コードは **`0`**

### AC6 — 全ホスト到達可能なときの drift チェック

- **Given** 検査対象の全ホストが到達可能
- **When** `deployment_drift_check.yml` を実行する
- **Then** 終了コード `0`、`unverified` は空、finding の内容が**現行と一致する**(回帰が無い)

## 8. タイムライン考慮

- **実ホストで失敗経路を再現できない。** `pve1` は本日(2026-08-16、日曜)起動中であり、平日停止の対象外。停止状態の再現は**decoy inventory**(閉じたポート=到達不能 / `ansible_connection: local`=到達可能)で行う。実ホストで確かめられるのは「到達可能な側が従来どおり通ること」(AC2 / AC6)のみ。
- **本番への反映には配備が要らない。** 変更対象はいずれも repo 内の role/playbook であり、`quory` は1分間隔の timer で `origin` から pull する(`docs/ai/context/operations/code-delivery-to-production.md`)。ただし `recovery_exec_setup` は schedule を持たないため、**実際に pve へ配備が届くのは次に手動起動したときである。**
- 次に `pve1` が停止するのは平日であり、②の効果(誤検知が消えること)が本番で観測できるのはその日になる。
