# test_plan: pve_unreachable_handling

> **表記についての注記**: この repo は公開されており、pre-commit が IPv4 リテラルを機械的に弾く(例外は認められない — `docs/ai/memory/` の feedback 参照)。そのため decoy で実際に用いた数値アドレスは `<LOOPBACK>`(ループバック)/ `<TESTNET-A>` `<TESTNET-B>`(RFC 5737 TEST-NET-1 の文書用非割当アドレス2つ)/ `<ANYADDR>`(ワイルドカード束縛アドレス)へ置き換えて記載している。**fixture を再現するときはこれらを実値へ戻すこと。**


作成: 2026-08-16 / Tester

## 対象

未commit差分5ファイル(`roles/recovery_exec/{tasks/target_setup.yml, defaults/main.yml}`、
`roles/deployment_drift_check/tasks/{collect.yml, evaluate.yml, report.yml}`)。
判定対象は requirement §6 の AC1〜AC6。先行のimplement/review記録の主張は判定材料にせず、
現物のコードとplaybook実行結果だけで判定する。

## 到達性の制約(前提)

- `pve1`/`pve2`/`quory`/`authy`/`sophos-fw` に ansy から到達する認証情報は無い。
  `recovery_exec_setup.yml` の `hosts: control_nodes`(実質 `-l quory`)を実ホストへ
  向けて実行することはできない。
- `roles/recovery_exec/tasks/main.yml` の配布guardは `inventory_hostname == 'quory'` を
  リテラルで要求するが、これを満たすためにdecoy inventoryへ実host名`quory`を書くことは
  decoy成立条件1(実host名を書かない)に反するため行わない。main.ymlはこの案件の差分に
  含まれない(guard自体は変更対象外)ため、**判定対象の`target_setup.yml`を
  `include_role: tasks_from: target_setup` で直接実行し、main.ymlのguardを経由しない**
  方式を取る。
- `deployment_drift_check.yml` は safe-readonly。到達できる `ansy`/`monnie` に対しては
  実プレイブックをそのまま実行してよい。ただし既定カタログは実host名(`quory`/`authy`/
  `pve1`/`pve2`)に紐づくため、到達不能ホストが絡むシナリオ(AC4/AC5)はdecoy専用の
  inventory・catalogで検証する。

## 検証方針(層)

1. **静的検証**: diff全文の読み合わせ。`when:`ゲート・register名・変数名の対応関係を
   grep で裏取りする(実装者コメントの引用を信頼せず、実物を確認)。
2. **decoy実行(recovery_exec)**: `roles/recovery_exec/tasks/target_setup.yml` を
   `include_role tasks_from` で単独実行し、`recovery_exec_pve_targets` をdecoy値へ
   差し替える。`check-mode-native` のtester-gateに従い常に `--check` を付与する
   (Tester役は本適用しない)。
3. **decoy実行(deployment_drift_check)**: 実際のplaybook構成を模したscratch playbook
   (2play構成、`hosts:`/カタログをdecoy値へ差し替え)で `collect → evaluate → report` を
   通しで実行する。`safe-readonly` なので `--check` は不要。
4. **実host回帰(到達可能な範囲のみ)**: `deployment_drift_check.yml` を
   `-e deployment_drift_check_hosts=ansy:monnie` で実行し、現行の本番コード経路が
   壊れていないことを確認する(AC6の一部)。
5. **否定対照実験**: decoy構成(reachable=<LOOPBACK>、unreachable=<TESTNET-A>)が
   requirementの記述する不具合(rc=4、task内UNREACHABLE昇格)を実際に再現するかを、
   修正前と同じ形(`delegate_to`ループを未フィルタのまま回す)の使い捨てplaybookで
   確認する。これによりdecoyの妥当性そのものを自分で裏取りする。

## decoyの構成と、strictな条件からの意図的な逸脱

- `deployment_drift_check` 検証: host名は `decoy-reachable`(`ansible_connection: local`)・
  `decoy-unreachable`(`ansible_host=<LOOPBACK> ansible_port=2223`、閉ポート)。
  カタログ(`deployment_drift_check_files`等)もdecoy専用に上書きする。条件1〜3を
  厳密に満たす。
- `recovery_exec` 検証: 到達可能側は `<LOOPBACK>`(このホスト自身のsshd、port 22)。
  到達不能側は本来「loopback宛の閉ポート」が条件だが、**本環境のsshdは`<ANYADDR>:22`で
  全loopbackアドレスを捕捉するため、loopback上でport 22だけを閉じる構成が作れない**
  (target_setup.ymlのprobeはportを22に固定しており、port側での回避もできない)。
  この構造的制約により、`<TESTNET-A>`(RFC 5737 TEST-NET-1、文書用途専用の非割当アドレス
  帯)を代替に使う。理由: (a)実在するいかなるホストにも割り当てられない、
  (b)インターネットへ到達せず本環境のデフォルトゲートウェイでも応答が無くtimeoutする
  ことを`/dev/tcp`および`ssh -o ConnectTimeout`で実測済み、(c)decoy条件2の趣旨
  (実システムに触れない閉じた宛先を作る)を満たす。この逸脱は否定対照実験でdecoyの
  妥当性を自分で裏取りすることで補う。

## 未実施と理由

- `recovery_exec_setup.yml` を `-l quory` で実host(または `inventory_hostname: quory`
  のidentityを含む構成)へ通す完全E2E実行。理由: ansyはquoryへの認証情報を持たず、
  かつidentityを`quory`に偽装するのはdecoy条件1に反するため。`target_setup.yml`単体の
  実行で代替。
- `pve1`/`pve2`実機での障害再現。理由: 認証情報が無く、かつ`pve1`は本日(日曜)起動中
  で平日停止の状態を再現できない(requirement §8に記載のとおり)。
- AC6の「finding内容が現行と一致する(回帰なし)」の完全A/Bバイナリ比較(diff適用前
  コードでの同一条件再実行との突き合わせ)。理由: 対象実装を変更しない制約下では
  作業ツリーの変更を退避しての再実行はできない。diffの読み合わせ(finding生成本体の
  Jinjaは無変更、`when:`追加のみ)+ decoy/実hostでのfinding生成が壊れていないことの
  実行確認で代替する。
- R7(probeタイムアウトが実行時間を目立って延ばさない)の実playbookでの計測。理由:
  実pveへ到達できないため計測対象がない。既定値(5秒、逐次wait_for)の妥当性は
  コードコメントの設計根拠とdecoy実行時の所要時間(概算)から判断する。
- R8(authy/monnie側への同種probe適用、P2/対象外)は要件どおり未実施。
