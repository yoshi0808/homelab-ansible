## 3. オープンクエスチョンへの回答

### 3.1 Q1(①のprobe手段)

**採用: `ansible.builtin.wait_for`(host/portのTCP接続確認、`delegate_to: localhost`)。`ansible.builtin.ping` + `delegate_to` + `ignore_unreachable`は不採用。**

理由: `ping`をprobeに使う場合も、対象ごとに`delegate_to`を変えるloopという同じ形になり、§2.1で再現した「loop内の1件のunreachableがtask全体をUNREACHABLEへ昇格させる」機構をprobe自身が再度踏む可能性がある。`ignore_unreachable: true`がその昇格を実際に抑止するかは実測していない(requirementのQ2はこの逆側 — controller側で完結するtaskの話 — であり、`ping`のように対象へ実際に接続するmoduleの昇格抑止は別の検証項目になる)。

`wait_for`はhost/portを引数に取るだけのTCP接続確認で、実行そのものは`delegate_to: localhost`(=ansible-playbookを起動したcontroller自身)で行われ、**pve1/pve2へのAnsible接続を一切確立しない**。したがって上記の昇格機構に触れようがない。`delegate_to: localhost`を選んだ根拠は、`inventories/homelab/host_vars/quory.yml`の`ansible_connection`条件分岐(quory自身から実行するときは`local`、ansyから`-l quory`で実行するときは`ssh`)が示すとおり、実際に6タスクの`delegate_to`接続が起点とする場所は「play中のquory」ではなく「ansible-playbookを起動したcontroller」であり、これは常に`localhost`と一致するため。

実測(`fix_test.yml`、到達可能1/到達不能1): probe後にloopを`recovery_exec_pve_targets_reachable`へ絞った2つのdummy task(A'/B')が両方とも到達可能側に対して実行され、rc=0。出力に「対象としたホスト」「外したホスト」双方が現れた。全滅ケース(`fix_test_all_down.yml`)でも rc=0、loopは0件で自然にskipし、両方が「外したホスト」に出力された。

**check_modeの落とし穴(実測)**: `wait_for`は`check_mode.support: none`。`check_mode: false`を付けないと`--check`下で自動skipされ、そのskip結果は`failed: false`を持つため、`selectattr('failed', 'equalto', false)`が**skipされたホストを誤って「到達可能」と判定する**(`checkmode_test.yml`で実測)。このため実装では`check_mode: false`を明示した。probe自体は読み取りのみで対象への副作用が無いため、常時実行して問題ない(TS-017と同じ判断)。

タイムアウト値(R7)は`recovery_exec_pve_probe_timeout: 5`(秒)とした。実測ではなく判断根拠のみ: 同一LAN内へのTCP接続であり到達可能時はミリ秒オーダー、到達不能時の実観測("No route to host")も即時失敗する経路のため、5秒は「待たされる」体感が出ない範囲の保守的な上限。

known_hostsのtask(旧299行、`ssh-keyscan`を`lookup('pipe', ...)`で呼ぶ)もrequirementが数える「6タスク」に含まれるため、同じ`recovery_exec_pve_targets_reachable`でloopを絞った。理由: `delegate_to`は使っていないため§2.1の昇格機構は踏まないが、`ssh-keyscan`は`lookup('pipe', ...)`というAnsible outside の subprocess 呼び出しであり、到達不能hostに対しては空/エラー終了になりうる。`lookup('pipe', ...)`が非ゼロ終了で例外を出すかは未実測だが、絞ることで疑義自体を除去した(AC1の「終了コード0」を確実にするための保守的判断)。

### 3.2 Q2(②: registerされるのか、変数が未定義になるのか)

**実測結果: 変数は未定義にならない。`register`は`unreachable: true`を含む辞書としてセットされる。** これはrequirementの2択のうち前者であり、`content`のようなmodule固有のキーだけが欠ける。

実測(`q2_test2.yml`、slurpタスクを`ignore_unreachable: true`のplayでdecoyの到達不能hostに対して実行し`register: ddc_slurp`のフルダンプを取得):

```
ddc_down (unreachable) の register内容:
{"changed": false, "exception": "...", "msg": "...Connection refused", "unreachable": true}
(content キーは存在しない)
```

`ddc_slurp.unreachable is defined` → `True`、`ddc_slurp.content is defined` → `False`。loop化した場合も同様で、`.results`の各itemに`unreachable: true`が個別に付き、`.item`も保持される(`q2_test4.yml`で確認)。

**この実測を踏まえた設計上の追加発見(地の文の訂正)**: 上記が成立するため、`roles/deployment_drift_check/tasks/evaluate.yml`の各finding builderは`r.unreachable | default(false)`を見れば個別に区別できる。しかし別途実測したところ(`q2_test3.yml`)、**`set_fact`はcontroller側で完結するため到達不能hostでも実行され続ける**(`roles/proxmox_reachable_nodes`のヘッダに実機確認済みと記載されている挙動と同一。今回はslurp/stat/command等の実接続を要するmoduleでも同じ前提で良いか改めてdecoyで確認した)。加えて、`when: false`でgateしたloop付きtaskの`.results`は**空リストにはならず、`{'skipped': True, 'item': ..., 'skip_reason': ...}`という中身の薄いstubがloop件数ぶん残る**(`q2_test3.yml`で確認)。この2点から、「collect.yml側のtaskを`when: <reachable>`でgateすれば済む」という単純な設計は成立しない(gateしても`.content`や`.stat`が無いstubがそのまま残り、既存の`r.content is not defined`判定が同じように誤発火する)。

最終的に採用した設計は、**collect.yml側のtask(stat/command/slurp)は変更せず素通しし、evaluate.yml側の"Build findings for X" 8タスクをhost単位の`deployment_drift_check_reachable`(collect.yml先頭に追加した明示的probeが立てるfact)で丸ごとgateする**方式にした(詳細は§4)。

### 3.3 Q4(checked_countsに到達不能hostを含めるか)

**含めない。** `report.yml`の`checked_counts`は、新設した`deployment_drift_check_checked_hosts`(到達可能なhostだけのリスト)に対して`zip` + `map('extract', ...)`する形へ変更した。

理由: 到達不能hostの`deployment_drift_check_checked_counts`(evaluate.ymlの"Combine findings for this host"が計算)は「何件を検査する**予定**だったか」(collect.ymlの"Select the checks..."がhost単位のカタログ件数を数えるだけのtaskで、到達性に関わらず常に実行される)であり、「実際に何件検査**できた**か」ではない。到達不能hostを含めると、実際には1件も採れていないのに`{keys: 1}`のような非0件がchecked_countsへ出て、`checked_hosts`から除外した意図と矛盾する。

実測(`verbatim_report_logic2.yml`、report.ymlの実際のJinja式をfabricated hostvars 6件・うち1件unreachableに対して逐語で実行): `checked_counts`の出力に不到達hostのエントリが含まれないことを確認した。

requirement §9は②の対象に`evaluate.yml`(finding判定に到達不能の区別を入れる)と`collect.yml`(到達不能フラグの収集)を挙げていたが、実装は**`evaluate.yml`内の個々のJinja分岐(`r.content is not defined`等)には手を入れず、host単位の`when: deployment_drift_check_reachable`gateで8タスクを丸ごとskipする**方式にした。理由は§3.2で述べたとおり、`r.unreachable`をfinding builderごとにチェックする案も動作はするが、host単位の1つのfactで判定を一本化するほうが変更点が少なく、かつ「到達不能なら1件も採らない」という意図をより直接に表現できると判断したため。AC5(到達可能だが本当に読めない場合)への影響が無いことは、`deployment_drift_check_reachable`がtrueのときは各finding builderのJinja本体を一切変更していないことから自明であり、追加の実測はしていない。

### 8.1 Finding 1 — probe通過後に到達不能となったホストでR4/R5/AC4が破れる

**再現された問題**: `roles/deployment_drift_check/tasks/collect.yml`冒頭のpingは「その時点で」到達可能だったことしか保証しない。probe後、8本のcollect task(stat/command/slurp)の実行中にhostが到達不能になっても、`deployment_drift_check_reachable`(probe時点の値のまま)は更新されず、`when: deployment_drift_check_reachable`のgateは効かないままfinding builderが走る。到達不能な個々のtask結果は`r.content is not defined`のような既存判定に「読み取り失敗」として拾われ、誤ったforced_command findingが立つ。かつ、このhostは`checked`に残ったまま(`deployment_drift_check_reachable`が依然trueのため)。

これは初回実装(§7で撤回した記述)が「flappingは稀」として明示的に受容していた欠陥であり、その受容判断そのものが誤りだった — R4(到達不能に起因する読み取り失敗をfindingとして計上しない)・R5(unverifiedへ載せる)・AC4を直接破るため、受容できる対象ではなかった。

**修正**: `roles/deployment_drift_check/tasks/collect.yml`の8つのcollect task(既存、無変更)の直後に、新設task「Downgrade reachability if any collect task actually observed unreachable」を追加した。8つのcollect resultをすべて連結し、`unreachable`キーを持つitemが1件でもあれば`deployment_drift_check_reachable`を(probeの時点でtrueだったとしても)falseへ格下げする。この格下げは`evaluate.yml`のfinding builder gateより前(同一ファイル内、`evaluate.yml`実行より前)に完了するため、`evaluate.yml`自体への追加変更は不要だった。

```yaml
- name: Downgrade reachability if any collect task actually observed unreachable (mid-run flap)
  ansible.builtin.set_fact:
    deployment_drift_check_reachable: >-
      {{ deployment_drift_check_reachable
         and not (
           (deployment_drift_check_file_stat.results | default([])
            + deployment_drift_check_unit_show.results | default([])
            + deployment_drift_check_keys_raw.results | default([])
            + deployment_drift_check_report_owner.results | default([])
            + deployment_drift_check_hosts_raw.results | default([])
            + deployment_drift_check_path_stat.results | default([])
            + deployment_drift_check_sudoers_listing.results | default([])
            + deployment_drift_check_dispatch_probe_result.results | default([]))
           | selectattr('unreachable', 'defined') | list | length > 0
         ) }}
```

根拠: Q2(§3.2)で実測済みのとおり、`register`は到達不能でも未定義にならず`unreachable: true`を持つ。この情報はcollectの時点で既に各resultの中に存在しており、握りつぶさず使えば済む(Reviewerの指摘どおり)。「ホストが一度でも到達不能を経験したら、そのhostの全カテゴリのfindingを信用しない」という設計(host単位の1つのfactに格下げを畳み込む)を維持し、finding単位の個別`r.unreachable`分岐は追加していない — 理由は、mid-runで部分的に壊れたhostのデータを一部だけ信用する方が危険(どの時点で壊れたか特定できない)と判断したため。

### 8.2 Finding 2 — `deployment_drift_check_reachable`が未定義のホストでreport.yml全体がクラッシュ、または双方から無言で消える

**再現された問題**: `report.yml`の`checked_hosts`/`unverified`/`checked_counts`は`ansible_play_hosts_all | map('extract', hostvars) | selectattr('deployment_drift_check_reachable', 'equalto', ...)`という形で書いていた。`play_hosts_all`に載っているホストのうち1つでも`deployment_drift_check_reachable`(または`deployment_drift_check_checked_counts`)がhostvarsに一度もset_factされていないと、`selectattr`/`map('extract', hostvars, attr)`は**その属性アクセスで即座に例外を投げ、report.yml全体が失敗する**(decoyで実測、§8.4参照)。これは`hostvars[h].attr | default(...)`のようなJinja2標準のdot記法+`default`filterとは挙動が異なり(dot記法は`Undefined`を返し`default`で安全に処理できる)、`map('extract', ...)`は内部で`getattr`相当を直接使うため`default`フィルタで保護できない。

**修正**: `report.yml`の`checked_hosts`/`unverified`/`checked_counts`を、すべて明示的なJinja for-loop + `hostvars[h].<attr> | default(...)`へ書き換えた。未定義は**明示的にunverified側へ分類する**(fail-closed。「到達性が確認できない以上checkedとは言えない」という判断、Reviewerの「fail-closedかunverifiedか、どちらでもよいので明示的に」という要求への回答)。

```yaml
deployment_drift_check_checked_hosts: >-
  {%- set checked = [] -%}
  {%- for h in hostvars['localhost'].deployment_drift_check_play_hosts_all | default([]) -%}
    {%- if hostvars[h].deployment_drift_check_reachable | default(false) -%}
      {%- set _ = checked.append(h) -%}
    {%- endif -%}
  {%- endfor -%}
  {{ checked }}
deployment_drift_check_unverified: >-
  {%- set unverified = [] -%}
  {%- for h in hostvars['localhost'].deployment_drift_check_play_hosts_all | default([]) -%}
    {%- if not (hostvars[h].deployment_drift_check_reachable | default(false)) -%}
      {%- set _ = unverified.append(h) -%}
    {%- endif -%}
  {%- endfor -%}
  {{ unverified }}
```

`checked_counts`も同型のfor-loopへ変更した(`hostvars[h].deployment_drift_check_checked_counts | default({})`)。`checked_hosts`はreachable==trueと確認できたhostだけなので通常この属性は定義されているはずだが、万一(reachable判定後に別の理由で当該hostの処理が完了しなかった場合等)未定義でもクラッシュせず空dictへfail-safeする。
