## 4. item 9のcheckpoint 4部分 — 取り込み前DLPが実データの往復経路で正しく機能すること

### 4.1 `_014`との違い

`_014` §3.3は、`oprc.dlp.scan()`をansy上で直接importして呼んだだけの**関数レベル**の確認だった(quoryのoutboxを経由していない)。今回はOperatorが実際にquory上で作成した実データ(OPRES・DEVREQ各1件)が存在するため、**`operator-channel-client get`という実コマンドの実行結果**として、checkpoint 4のコードパス全体を通した確認ができる。

### 4.2 `cmd_get`が実際に何を検証するか(静的確認)

配備物と一致する`roles/operator_request_channel/files/bin/operator-channel-client`の`cmd_get`(217〜247行)を読み、`get`が1回の呼び出しで次を順に行うことを確認した。

1. `schema.validate(message, schema_doc)` — ローカルに検証済みのschemaとの整合性
2. `meta["dlp_engine_version"] == dlp.ENGINE_VERSION`(quoryとansyのDLPエンジンバージョン一致)
3. `meta["dlp_ruleset_sha256"] == cfg["expected_dlp_ruleset_sha256"]`(ruleset hash一致)
4. `meta["content_sha256"] == canonical.content_hash(message)`(内容hash照合、改ざん検知)
5. **checkpoint 4本体**: `dlp.scan(message, ruleset, ...)` を実行し、`result.blocked`ならmessageを表示せず拒否

いずれか1つでも失敗すれば`_deny(...)`で処理が止まり、messageは表示されない設計になっている。

### 4.3 実データでの実行結果

§2・§3の`get`呼び出しは両方とも**rc=0でmessage本文が出力された**。上記の設計に従えば、これは次のすべてが実データに対して成立したことを意味する。

- schema検証を通過した(1)
- quoryとansyのDLPエンジンバージョンが一致した(2)
- quoryとansyのruleset hashが一致した(3)
- 内容hashが一致し改ざんが検出されなかった(4)
- **checkpoint 4のDLPスキャンが実データに対して実行され、良性データを正しく通過させた(5、allow方向)**

これは`_014`には無かった確認であり、checkpoint 4が「実データの往復」で機能していること(配線・allow方向の判定)を実測で示す。

### 4.4 依然として実データでは確認できない部分(reject方向)

checkpoint 4がDLP検出対象を実際に**拒否**することは、今回も実データの往復では確認していない。理由は構造的なもので、設計どおりであれば疑似secretを含むOPRES/DEVREQはcheckpoint 3(quory持ち出し前DLP)で作成時点で拒否され、outboxに置かれない。ansyから取得できる対象になり得ない。これを実データで確認するには、Operator local CLIで意図的にDLP検出対象を含むmessageを作ろうとする操作が要るが、それはOperatorの権限であり本試験の到達範囲外である。

このため、reject方向は`_014`と同じ**関数レベル**の確認で補った(deployedのままの`oprc.dlp.scan()`をansy上で直接呼ぶ。§1でこのファイルがrepo srcと一致し前回から不変であることを確認済みなので、`_014`の関数レベル確認は現在の配備物に対しても引き続き有効と判断できる)。

```
$ python3 -c "...oprc.dlp.scan()を疑似PEM鍵・private IPv4で直接呼ぶ..."
pem       blocked=True  [('pem_private_key', 'pem-or-ssh-private-key', '/observed_facts/0')]
privipv4  blocked=True  [('private_ipv4', 'private-ipv4', '/observed_facts/0')]
```
検出値は`findings`に含まれず(`category`/`rule_id`/`pointer`のみ)、今回も非漏洩を確認した。

### 4.5 判定

**PASS。** 実データの往復で、checkpoint 4のコードパス全体(schema/engine version/ruleset hash/content hash/DLPスキャン)が正しく配線され、良性データを正しく通過させることを実測した。DLP検出時のreject方向は、設計上real round tripでは再現不能なため、`_014`と同じ関数レベルの確認(かつ配備物不変の裏取り)で補完している。この関数レベルの限界は解消されていないため、残存リスクとして§6に記載する。

## 6. 残存リスク

1. **quory側`oprc/`ライブラリ・`oprc-receive`・`operator-channel`のバイト単位hash照合は、4回連続で到達可能な手段が無い。** `deployed-hash`カタログに本案件のファイルが1件も登録されていないため。今回の試験でaccept-request(item 3、Operatorの報告と本Tester実行の`status`照会で`answered`への遷移を間接確認済み)・OPRES作成・standalone DEVREQ作成が実データとして機能したことは、quory側コードが少なくとも実処理を通していることの強い間接証拠にはなるが、hash一致そのものの直接証明にはならない。`deployment_drift_check.yml`のカタログへ本案件のファイルを追加すれば解消する(前回までと同じ提案)。
2. **checkpoint 4のreject方向は、実データの往復では今回も再現できていない。** 設計上checkpoint 3が正しく機能していればDLP検出対象はoutboxに置かれないため、原理的にreal round tripでは成立しない。関数レベルの確認(§4.4)で補っているが、これは「checkpoint 4が実際に配線されたコードパスの中で正しくblockedを返すか」までは実データで確認していないという意味で、`_014`から質的に変わっていない。
3. **item 2〜4・7(Operator local CLI操作そのもの)は本試験のスコープ外。** Operatorの報告(accept-request成功、reply-opres成功、new-devreq成功、DLP疑似secret拒否)を、ansy側から観測可能な範囲(request ID・state・内容の一致、DLP拒否の固定文言)で裏取りしたに留まる。Operator local CLIの出力そのもの(`list-pending`/`show-request`の表示形式など)はansyからは見えない。
4. **quoryのspoolに新規request増加は無い。** 今回は既存2件(Operatorが作成したOPRES・DEVREQ)を取得しただけで、submitは行っていない。累計はitem 1系列の2件(前回までの記録)+今回の2件=4件のまま(今回の試験による純増はゼロ)。
