## 指摘

### 1. `docs/ai/status.md`の「全項目を通った」という要約が、自ら引用する記録の適用範囲を超えている — **クローズを妨げる**

`docs/ai/status.md`のNow行は次のように書く。

> 「**Operator Request Channel MVP — 縦方向試験が全項目を通った(2026-08-09)。** submit → accept → OPRES → ansy取得が端から端まで通った。standalone DEVREQ、持ち出し前DLP(checkpoint 3)、取り込み前DLP(checkpoint 4)、既存25操作の非回帰も通っている。…判定は `2026-08-09_016_vertical_test_4.md`(ansy側)と**Operatorの報告(quory側)**。」

しかし引用元の`_016_vertical_test_4.md`自身は、§6「残存リスク」3で「**item 2〜4・7(Operator local CLI操作そのもの)は本試験のスコープ外**」と明記し、まとめの表(§8)にitem 2・3・4・7を一切含めていない。checkpoint 3(quory持ち出し前DLP)についても§4.4で「**今回も実データの往復では確認していない**」と明記している。

つまり「accept」「OPRESの作成」「standalone DEVREQの作成」「checkpoint 3」が実際に成功したという事実は、ansy側のどの記録にも書面として存在しない。唯一の根拠は「Operatorの報告(quory側)」という、案件フォルダ内に対応する文書が無い外部情報である。requirementの設計(§2.2)は「quoryを正式な保管先とするもの」を明示しており、Operatorのセッション記録がGit管理外であること自体は正しい設計だが、**それを理由に、ansy側記録の要約が「通った」と断定してよいことにはならない**。

さらに、`_016`§6の1つ目の残存リスクは「今回の試験でaccept-request(item 3、**Operatorの報告と本Tester実行の`status`照会で`answered`への遷移を間接確認済み**)」と書くが、この`status`照会のコマンドと出力は`_016`本文のどこにも示されていない。同じ文書の他の全ての主張(item 1・5・6後半・9・10)はコマンドと実際の出力のペアで裏付けられており、この1件だけが例外的に「確認した」という記述だけで済まされている。**根拠の実在**(Auditorの検査観点)に照らすと、この1文だけは自己完結していない。

**クローズを妨げる理由**: `docs/ai/status.md`はYoshinobuのクローズ判断が直接読む要約であり、そこに書かれた「全項目を通った」が実際の検証範囲(items 5・6後半・9・10のみ実測PASS、items 2・3・4・7・checkpoint 3は未検証のまま)より広いことは、判断者に実態より進んだ状態を伝える。commitの前に、次のいずれかが要る。

- (a) items 2・3・4・7とcheckpoint 3について、Operatorの実際の出力(コマンドと結果)を案件フォルダへ書面として残し、それに基づいて「通った」と記述する。
- (b) 書面化しないのであれば、「Operatorの口頭報告に基づき、書面記録は無い」ことを明記した上で、Yoshinobuがその報告を受入の根拠として足りるとみなすかどうかを別途確認する。

いずれにせよ、現状の「全項目を通った」という表現のまま次のセッションへ引き継ぐと、根拠の無いまま既決事項として扱われる。

### 2. requirement §19の完了条件のうちitem 22・23・25が、`_010`以降一度も再訪されないまま案件の要約から消えている — **クローズを妨げる**

`_010_deploy_verification.md`は、item 22(`SEMI-SAFE: Semaphore templates setup`によるtemplate登録)・item 23(登録templateの構造確認)・item 25(Yoshinobuによる明示実行)をいずれも「未判定」とし、判定に要るものとして「Semaphore側のtask実行履歴、またはYoshinobu自身の申告」を挙げた。同じ`_010`§6は「quory側のserver setup自体は、このtemplate登録より前に**別経路で**完了している」と観察している——つまり実際の配備は、requirement §12.4/§12.5が定めた「Semaphore template登録 → Yoshinobuが明示実行」という経路を通っていない可能性が高い。

この3項目は`_012`・`_014`・`_016`のいずれにも一度も現れない(`grep`で確認、本文中に"item 22"/"item 23"/"item 25"の文字列自体が無い)。`docs/ai/status.md`は「**残る未判定は quory側 `oprc/` ライブラリのhash直接照合1件だけ**」と述べており、item 22・23・25の存在に触れていない。

**クローズを妨げる理由**: これは「未解決の明示」(Auditorの検査観点)そのものである。黙って落ちている項目がある状態でクローズすると、requirement §19の完了条件28項目のうち3項目(22・23・25)について「判定しないまま忘れられた」のか「別経路での配備で置き換えることをYoshinobuが容認した」のかを、記録からは区別できない。後者であれば、その判断をどこかに一行残す必要がある。前者であれば、`docs/ai/status.md`の要約へ差し戻すべきである。

### 3. `docs/ai/roles/operator.md`に、同名の見出し「## 現在の状態」が2箇所あり、内容が矛盾している — クローズを妨げない

7〜10行目は「Operatorの具体的な責務、権限、利用可能な機能および安全制約は**設計中**である」とし、30〜32行目は「Operator Request Channelを介したOPREQの受領、OPRESの返却およびDEVREQの作成は**実装済み**である」とする。`git log --follow -p`で確認したところ、前者は本案件着手前(`1b071ce`)に作られた記述で、後者は本案件の実装完了時(`92e4e90`)に追記されたものであり、**前者を更新・削除しないまま後者が積み増された**。

3か月後にこの文書を先頭から読む者は、7〜10行目で「まだ設計中」という前提を持ったまま30行目以降の「実装済み」という記述に至り、矛盾に直面する。Yoshinobuの実質的な承認・実装は成立しているため、これはクローズを妨げる指摘ではないが、commit前に前者の節を削除するか「本セクションは初期の状態であり、下記『開発側とのやりとり』節に置き換わった」等へ書き換えることを推奨する。

### 4. 作業ツリーに、案件フォルダのどこにも記録されていない未commit差分(`docs/ai/roles/coordinator.md`)がある — クローズを妨げない

`git status --short`で確認したところ、`docs/ai/roles/coordinator.md`に1段落の追記(「カタログに無い事実が要るとき…Operator Request Channelで quory側Operatorへ調査を依頼する」)が未staged・未commitのまま存在する。この変更は明確に本案件(Operator Request Channel)を前提とした内容だが、`docs/ai/reviews/operator_request_channel/`のどのファイルにもこの変更への言及が無く、**誰が・いつ・なぜ加えたのかを記録から辿れない**(Auditorの検査観点「決定の追跡」に該当)。

`docs/ai/status.md`は既にstage済み(`git status`で`M`表示)であるのに対し、この変更はstageすらされておらず、他の変更と扱いが揃っていない。

**クローズを妨げる指摘にはしない**理由: 内容自体は本案件の設計(requirementが禁じた能力を増やしていない、既存の`operator-channel-client submit`を使うだけ)と矛盾せず、安全側の変更である。ただし、commit前にCoordinatorが「この案件の一部としてstageし経緯を一行残す」か「この案件のスコープ外として別途扱う」かを明確にすることを推奨する。
