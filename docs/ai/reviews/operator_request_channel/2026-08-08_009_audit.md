## 指摘

### 1. plan が明示した安全策(quory Python版の preflight assert)が実装されていない — **クローズを妨げる**

plan §1「未確認事項への対処」は、quoryのPython版が確認できないことへの対処として次を明記している。

> 「server setup playbook の先頭で `python3 -c 'import sys; assert sys.version_info >= (3,9)'` 相当のpreflight assertを置き、前提が崩れていれば配備前に停止させる。」

plan §8「未解決事項」も「quory の Python 版(§1)。server setup の preflight assert で配備前に確定する。」と、この対処が実施される前提のまま案件を終えている。

しかし `roles/operator_request_channel/tasks/{common,server,client}.yml` と `playbooks/operator_request_channel_server_setup.yml` を通読・`grep`したが、`version_info`・`python3 -c`・`assert`(Python版チェック相当のもの)は1つも無い(`common.yml`の`assert`はrepo側schema/rulesetの`stat`可否を見るものであり、quory側のPython版とは無関係)。

- `_004_implement_core.md`・`_005_implement_channel.md`のいずれにも、このpreflightを実装した・見送った・別の形で代替したという記述が無い。
- `_006_review.md`はTS-014ガード(`when: not ansible_check_mode`)の存在は確認しているが、このpreflightの有無には触れていない。
- `_007_test_plan.md`・`_008_test_result.md`にも、このpreflightに対応する検証項目が無い。

つまり、plan本文が「Python 3.9+標準ライブラリのみ」という設計判断(D1、TOMLではなくJSONを採る根拠でもある)の裏付けとして明示した安全策が、後続のどの工程でも実装・検証・意図的な削除のいずれとしても扱われないまま、記録上は「実施される予定のもの」として残っている。記録だけでは「実装されなかった」のか「実装したが記載を忘れた」のかを再構成できない。

**クローズを妨げる理由**: これはimplementの実装漏れそのものというより、**この案件の記録が「plan通り実装された」という前提で完結してしまっている**ことが問題である。§1で明示的に「未確認」とフラグを立てた環境事実への対処が、実際には欠落したまま各工程を素通りしている。commitの前に、(a) preflightを実装してテストへ追加するか、(b) 実装しないと決めるならその理由と代替(例: import失敗時にPythonが素朴にSyntaxError/ImportErrorで落ちるため機能的にはfail closed側になる、という代替担保)をplan §1/§8へ明記するか、いずれかの手当てが要る。

### 2. `.gitignore` の変更が、どの案件記録にも実施者・時点・根拠として残っていない — クローズを妨げない

`git status`は `.gitignore` を変更差分(`M .gitignore`)として示しており、`!scripts/tests/operator_request_channel/` の追加行が入っている。この変更は`_004_implement_core.md` §6-1が「`.gitignore`は自分の成果物パス外であり変更していない — Coordinatorの判断が必要」と明記した論点への対処そのものであり、`_006_review.md`・`_008_test_result.md`はこの行が「意図どおり機能している」ことを確認済みとして扱っている。

しかし、**誰が・いつ・どちらの選択肢(`.gitignore`を直すか、依頼文のpath自体を見直すか)を採ったのかを記す記録が案件フォルダのどこにも無い**。`_005_implement_channel.md`(Implementer Bの対象パス一覧)にも`.gitignore`は挙がっていない。Reviewer・Testerはこの変更が既に存在する前提で確認しているだけで、決定の経緯には触れていない。

Auditorの検査観点「決定の追跡」に該当するが、実質的な選択(狭める方でなく復活させる方を採った)は安全側であり、機能的な誤りは無い。記帳漏れの性質のもの(監査自体が記録を古くする類ではなく、単純な記載漏れ)であるため、クローズは妨げないが、commit前にCoordinatorが一行(plan §8か本diffの説明)へ「`.gitignore`に`!scripts/tests/operator_request_channel/`を追加(Coordinator、理由: 依頼文のpath指定を維持しテスト成果物を追跡対象にするため)」等を残すことを推奨する。

### 3. Phase 3 チェックカタログの不変条件 I-1(「すべてread」)が、この案件によって部分的に成立しなくなっているが、当該文書は無更新のまま — クローズを妨げない

`docs/ai/reviews/dev_prod_boundary/2026-08-03_008_phase3_check_catalog.md`は「このファイルが『何を露出させるか』の正本である」と自称し、`dev-investigate`/`recovery-investigate-dispatch-quory.sh`に対する不変条件I-1として「すべて read。`pvesh create`/`set`/`delete`...を1つも露出しない」を掲げ、「以降、ここに無いチェックを実装へ足す場合は再度承認を要する」と明記している。

本案件は同じidentity(`dev-investigate`)・同じdispatcherファイルへ、`operator-request-submit`という**書き込み系**操作(新規spoolへのmessage作成)を追加した。plan §0のQ1でYoshinobuはこの書き込み能力(新設spoolへの`dev-investigate`ACL追加)を明示的に承認しており、手続き上の「再承認」自体はこの案件の中で行われている。

ただし、**カタログ文書自身(I-1)はこの例外を反映するよう更新も注記もされていない**。plan・review・test_resultのいずれも、`deployed-hash`対応表を拡張しない判断の根拠としてこのカタログへ言及しているが(「足すには再承認が要る」)、I-1という不変条件そのものがこの案件によって部分的に成立しなくなった事実には触れていない。3か月後にこのカタログ単体を読んだ者は、`dev-investigate`が今も「すべてread」だと誤認する。

Yoshinobuの実質的な承認(Q1)は成立しているため、これはクローズを妨げる指摘ではない。ただしカタログ文書への1行の注記(「Q1(operator_request_channel、2026-08-08)によりwrite操作1件を例外として承認済み」等)を推奨する。
