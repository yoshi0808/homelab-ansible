## 4. クローズ判断

**クローズする**(Yoshinobu、2026-08-09)。

**残す残存リスク**(状態の正本は `docs/ai/status.md`、値をここへ二重に持たない):

1. quory側 `oprc/` ライブラリのバイト単位hash照合は4回連続で手段が無い。`deployed-hash` カタログへ本案件のファイルを追加するか、`deployment_drift_check.yml` を quory に対して通常Ansible経路で実行すれば解消する。
2. checkpoint 4 の reject 方向は、実データの往復では原理的に検証できない(checkpoint 3 が正しく機能していれば outbox に検出対象が置かれないため)。関数レベルの確認に留まる。
3. item 23 の schedule 不在は dispatch から観測できない。
4. quory の spool に試験messageが4件残る。削除機能は設計上どこにも無い。

**設計上の申し送り**: この案件は**書き込みの門が POSIX ACL だけだと仮定**しており、mount 層の制約を持っていない。実バグ4件目(EROFS)がそこを突いた。同型の2層(bwrapの `writable_roots` と systemdの `ReadWritePaths` の両方が要る)は `recovery_exec` 経路で既に踏んでいる。後続案件の設計入力とする。
