## 2. §21 の確定事項

### 2.1 実装言語とpackage構成

**Python 3、標準ライブラリのみ。** 共通ロジックは1つのpackageディレクトリに置き、**ansyとquoryへ同一バイト列を配備**する。

```text
roles/operator_request_channel/files/oprc/     ← repo(正本、両ホスト共通)
  __init__.py        バージョン定数のみ
  canonical.py       canonical JSON と内容hash
  config.py          config読込、engine version / ruleset hash 照合、fail closed
  dlp.py             DLP engine(ルールセットを解釈する。検出値を戻り値に含めない)
  ids.py             request_id / conversation_id の生成・検証
  schema.py          JSON Schema サブセット validator
  store.py           spool layout、atomic create、append-only event、上限
  wire.py            payload の読み込み(サイズ・UTF-8・duplicate key・非有限数の検査)

roles/operator_request_channel/files/bin/
  operator-channel-client   ansy側client(§5.1)
  oprc-receive              quory側 forced command 受け口(§5.2)
  operator-channel          quory側 Operator local CLI(§5.3)
```

- 3つのエントリポイントはいずれも薄く、判断ロジックを持たない。DLP・schema・store の呼び出し順だけを持つ。
- 全ファイルを **`copy` で配備する**(`template` を使わない)。`roles/deployment_drift_check/defaults/main.yml` 冒頭の但し書きのとおり、`copy` 配備物だけが日次ドリフト検査Tier 1の対象になるためで、§14 の「配備済みhashを検査する」を満たす唯一の方法である。
- **ルールセットとschemaは JSON とする**(`dlp-rules.json` / `request-schema-v1.json`)。requirement §12.2/§12.3 は `dlp-rules.toml` を「想定する論理配置」として挙げているが、TOMLの標準パーサは Python 3.11 以降にしか無く、quoryの版が未確認である以上「両ホストで同一の解釈」を保証できない。`json` はどの版にもあり、`copy` 配備物としてhash比較もそのまま効く。**§21 が委ねた「configの具体pathと内容」の範囲内の変更**として扱い、能力は1つも増やしていない。

### 2.2 spool の file layout

```text
/var/lib/operator-request-channel/
├── inbox/<request_id>.json              受理したOPREQ(message + meta)
├── outbox/<request_id>.json             Operatorが作成したOPRES／DEVREQ
├── events/<request_id>.jsonl            そのrequestの状態イベント(append-only)
└── quarantine-metadata/<attempt_id>.json 受付失敗の記録(payloadを含まない)
/var/log/operator-request-channel/audit.jsonl
```

- **状態イベントをrequestごとの別ファイルに分ける。** 単一の共有ファイルへの追記にすると、同時submit時のイベント欠落を防ぐためのロックが全requestに効いてしまう。requestごとなら、`O_APPEND` の追記だけで §16「同時submit時にevent欠落や部分書込みが起きない」を満たす。
- **保存ファイルの形**: `{"message": {...}, "meta": {...}}`。`meta` は `content_sha256` / `dlp_engine_version` / `dlp_ruleset_sha256` / `received_at` / `source`。内容hashは `message` の canonical JSON に対して取る(hash自身を含む構造をhashしない)。
- **conversation の索引は持たない。** 保存件数に上限があるため、`show-conversation` は該当ディレクトリを走査して導出する。§7.2 の「indexは再構築可能な派生物」を、indexを作らないことで満たす。

### 2.3 owner / group / mode / ACL

既存の3つのACLと `systemd-journal` グループ所属は**触らない**。新しい領域にだけ、新しいACLを付ける。

| path | owner:group | mode | ACL(新規付与) |
|---|---|---|---|
| `/var/lib/operator-request-channel/` | root:root | `0755` | — |
| `inbox/` | root:root | `1700` (sticky) | `u:dev-investigate:rwx`, `u:yoshi:rx`, default `u:yoshi:r` |
| `outbox/` | root:root | `1700` (sticky) | `u:yoshi:rwx`, `u:dev-investigate:rx`, default `u:yoshi:rw`, default `u:dev-investigate:r` |
| `events/` | root:root | `1700` (sticky) | `u:dev-investigate:rwx`, `u:yoshi:rwx`, default `u:dev-investigate:rw`, default `u:yoshi:rw` |
| `quarantine-metadata/` | root:root | `1700` (sticky) | `u:dev-investigate:wx`, `u:yoshi:rwx`, default `u:dev-investigate:rw`, default `u:yoshi:rw` |
| `/var/log/operator-request-channel/` | root:root | `0755` | — |
| `/var/log/operator-request-channel/audit.jsonl` | root:root | `0660` | `u:dev-investigate:rw`, `u:yoshi:rw` |
| `/usr/local/libexec/operator-request-channel/**` | root:root | `0755` / `0644` | — |
| `/etc/operator-request-channel/**` | root:root | `0644` | — |
| `/usr/local/bin/operator-channel`, `/usr/local/sbin/recovery-investigate-dispatch-quory.sh` | root:root | `0755` | — |

- **`inbox` について、この設計が与える性質は「他のidentityの本文を読めない」であって、「提出側が自分の提出物を読めない」ではない。**
  - `inbox` に入るのは coordinator identity が書いた OPREQ だけである(§4.2 により、他の主体はここへ書けない)。したがって提出側が読み返せても、**自分が書いた内容以外は1バイトも見えない**。
  - **当初この節は「提出側から本文を読めないようにする」と書いていた。それは成り立たない。** message ファイルは `_atomic_create` が呼び出しプロセスの権限で作るため所有者が `dev-investigate` になり、mode `0440` の owner ビットで読める。ACLの与え方によらない(2026-08-08、実装時の指摘)。
  - **Coordinatorが最初に行った実測は root 所有のファイルで測っており、配備の実態と条件が違っていた。** その表は削除した。測るときは、実際に誰がそのファイルを作るのかを条件に含めること。
  - default ACL が付与するのは、`inbox` に作られたファイルに対する `yoshi` の read である(Operatorが読むために要る)。
- **ディレクトリの `r` を `dev-investigate` へ与える(2026-08-08、配備後検証 `_010_deploy_verification.md` で改訂)。** 当初は `wx` だけにしていたが、それでは `inbox` の**エントリ列挙**ができず、上限検査(§2.4 の保存件数・総容量)が `PermissionError` で落ちて **submit が1件も通らなかった**。
- **帰結**: `operator-request-status` は inbox の本文を読まず、`events/` だけから状態を導出する。この性質は上の改訂後も維持する。
- message本文は `0440` 相当(mask後)で作成し、作成後に書き換えない。
- **program・schema・rules・config は root 所有で、channel利用identityから変更できない**(§12.3)。
### 2.3.1 残存リスク R-1(受容済み、2026-08-08 Yoshinobu)

`inbox/<id>.json` の所有者は作成した `dev-investigate` になるため、**このOS identityそのものを掌握した攻撃者は、自分が提出したOPREQを unlink できる**。sudo・setuid・常駐brokerのいずれも使えない(§17 で除外)以上、ファイルの所有者を root にする手段が無い。

**受容の根拠は次の3つであり、「本番状態を変えないから」ではない。**

1. **forced commandから削除・更新操作へ到達できない。** dispatcherが公開する語彙は §4 の4本だけで、そこに削除・更新の入口が1つも無い。`oprc-receive` にも `operator-channel` にも、message本文を書き換える／消すコードパスを実装しない。
2. **任意shellが存在しない。** `authorized_keys` は `no-pty` を含むオプション付きの forced command 1本だけであり(この案件で変更しない)、対話shellが得られない。
3. **sudoが存在しない。** `dev-investigate` は `/etc/sudoers.d/` 配下にエントリを1つも持たず、この案件でも作らない。§14 のドリフト検査が「channel programがsudoersを持たないこと」を日次で見る。

**保証しないこと(明示)**: 上記3つはいずれも「forced command経由の入口」に対する保証である。**OS identity `dev-investigate` そのものが侵害された場合の完全なimmutabilityは保証しない。** stickyビットにより他のidentityが作ったファイルには触れられないが、自分が所有するファイルの unlink は防げない。

**検出側の担保**: §2.9 のとおり、message と event の不整合を検出した時点で fail closed とする。監査(`audit.jsonl`)は root 所有で、両identityへ追記のみを許す。

この制約は plan(本節)・test(§6 の該当項目)・audit(案件クローズ時の受入対象)の3箇所へ記録する。

### 2.4 TTL・保存件数・総容量・retention

| 項目 | 値 | 根拠 |
|---|---|---|
| `expires_at` の最大TTL | 受理時刻 + **14日** | 調査依頼が有効でありうる現実的な上限。超えるpayloadは受理しない |
| `expires_at` 省略時 | 受理時刻 + **7日** | |
| 保存件数 | `inbox` / `outbox` **各500件** | |
| 総容量 | `/var/lib/operator-request-channel/` 全体で **128 MiB** | 1 message ≤ 64 KiB × 上限件数の実効値に余裕を持たせた値 |
| 上限到達時 | **新規submit・新規outbound作成を fail closed で拒否**。古いmessageを暗黙に削除しない | §8 |
| retention | **自動削除は行わない。** TTL超過は `expired` イベントを追記するだけで本文を消さない | §7.2・§11「message本文の編集・削除機能を提供しない」 |
| 正式な削除手順 | Yoshinobuが quory 上で root として、対象 `request_id` の `inbox`/`outbox`/`events` の3ファイルを退避先へ `mv` してから削除する。**CLI・dispatcher・playbookのいずれにも削除機能を持たせない**(持たせた時点で、経路から本文を消せることになる) | §10.2・§11 |

### 2.5 request ID / conversation ID の形式

```text
request_id       req-YYYYMMDDTHHMMSS+0900-<hex16>
conversation_id  cnv-YYYYMMDDTHHMMSS+0900-<hex16>
```

- 正規表現: `^req-[0-9]{8}T[0-9]{6}\+0900-[0-9a-f]{16}$` / `^cnv-...`(同形)。
- 時刻部は `datetime.now(JST).strftime('%Y%m%dT%H%M%S%z')` の**実変換結果**であり、`+0900` を後から貼らない(`skills/ansible-implementation-style/SKILL.md`)。生成後に自分の正規表現で検証し、一致しなければ fail closed。
- 乱数部は `secrets.token_hex(8)`。
- `.` と `/` を構造的に含みえないため、path traversal は綴れない(既存 `FILE_RE` と同じ設計)。ファイル名は `<request_id>.json` / `<request_id>.jsonl` として、**ID以外の文字を連結しない**。

### 2.6 cursor / paging の形式

- `operator-outbound-list [<cursor>]`。`cursor` は**直前ページの最後の `request_id`** そのもの(上記の正規表現に一致しなければ拒否)。検索式・条件式は受け取らない。
- 並び順は `(created_at, request_id)` の昇順で決定的。ページサイズは **50固定**(引数で変えられない)。
- 応答は `{"items":[...], "next_cursor": "<request_id>|null"}`。

### 2.7 evidence ID の形式

```json
{"kind": "semaphore_task|incident_bundle|drift_report|report_file|journal_window", "id": "<opaque>"}
```

- `kind` は固定enum。`id` は `^(?!.*\.\.)[A-Za-z0-9_+.:-]{1,128}$`(`/` を含まず、`..` を綴れない)。
- **`id` からpathを組み立てる処理をどこにも書かない。** quory側は受け取った値を保存・表示するだけで、既存helperへ渡しもしない(渡した瞬間に「任意pathの入口」になる)。Operatorが人としてその証跡を見に行くための参照子である。

### 2.8 config の具体pathと内容

両ホストとも `/etc/operator-request-channel/config.json`(root:root `0644`)。**`template` で配備する**(ホストごとに値が違い、期待hashを配備時に埋めるため)。

ansy:

```json
{
  "config_version": 1,
  "role": "coordinator",
  "channel_enabled": true,
  "ssh_destination": "quory-investigate",
  "ssh_connect_timeout_seconds": 15,
  "libexec_dir": "/usr/local/libexec/operator-request-channel",
  "schema_path": "/etc/operator-request-channel/request-schema-v1.json",
  "dlp_rules_path": "/etc/operator-request-channel/dlp-rules.json",
  "expected_schema_sha256": "<配備時にrepoのファイルから算出して埋める>",
  "expected_dlp_engine_version": "1",
  "expected_dlp_ruleset_sha256": "<同上>",
  "max_payload_bytes": 65536,
  "dlp_timeout_seconds": 20
}
```

quory: 上に加えて `"role": "operator_host"`、`spool_dir` / `audit_log_path`、§2.4 の上限値(`max_ttl_days` / `default_ttl_days` / `max_messages_per_box` / `max_total_bytes`)、`page_size`。

- **期待hashは配備時にAnsibleがrepoのファイルから算出して埋める。** 配備後に誰かがホスト上の `dlp-rules.json` を書き換えると、次回起動時にhash不一致で **fail closed** になる(§9.2)。
- **`channel_enabled: false` が §13 の無効化スイッチ**。root所有のconfigにしか無く、channel操作だけを拒否し、既存 `dev-investigate` の25本のread-onlyチェックには一切触れない(dispatcher側の実装で、channel arm に入ってからconfigを読む)。

### 2.9 message と event の不整合は fail closed

message本文と状態イベントは別ファイルであり(§2.2)、片方だけが存在する／食い違う状態が原理的に起こりうる。**読み出し側は、不整合を検出したらその request について fail closed とする** — 推測で補完せず、部分的な結果も返さない。

| 検出条件 | 扱い |
|---|---|
| message は在るが `events/<id>.jsonl` が無い、または `submitted` イベントを持たない | その request の取得・状態照会を拒否。監査へ `inconsistent` を記録 |
| `events/<id>.jsonl` は在るが message が無い | 同上 |
| message の `content_sha256` が本文の再計算値と一致しない | 同上(§7.1 の「取得時に再照合する」) |
| event列が許可されない遷移を含む(例: `submitted` を経ずに `answered`) | 同上 |
| event行がJSONとして壊れている、または `request_id` が自身と一致しない | 同上 |

- 拒否は `denied:` 相当を stderr へ出して非ゼロ終了し、**stdoutへ部分的なmessageを出さない**(§16「中途半端なmessageを可視化しない」)。
- **一覧(`outbound-list` / `list-pending`)では、不整合な request をエントリごと除外し、除外件数だけを返す。** 一覧全体を落とすと、健全な1件のせいで運用が止まる。
- 不整合は自動修復しない。復旧は §2.4 の削除手順と同じく、Yoshinobuの明示操作に委ねる。

### 2.10 Semaphore template 名

### 2.11 時刻同期が成立していないときは新規submitを止める

requirement §6.1「時刻同期が成立していない場合はfail closedとするか、少なくとも新規submitを停止する」への対応。**当初の計画から欠落しており、計画査読(`_003_plan_review.md` Critical 2)で指摘されて追加した。**

- **対象は quory 側で `created_at` を採番する2経路だけ**である(`oprc-receive` の submit と、Operator local CLI の OPRES／DEVREQ 作成)。ansy側clientは `created_at` を持たない(§6.1 が受入口の時刻を使うと定めているため)ので、この検査を持たない。
- **判定手段は `chronyc tracking`**。quory は chrony で同期しており(`roles/time_sync_check/defaults/main.yml` が quory を chrony ホストとして扱っている)、既存 `roles/time_sync_check/tasks/check_chrony.yml` と同じ一次情報を使う。
- 固定 argv・shellなし・5秒timeoutで起動し、次をすべて満たす場合にだけ「同期している」と判定する。1つでも欠ければ **新規submit／新規outbound作成を拒否する**。

| 条件 |
|---|
| 終了コードが 0 |
| 出力に `Leap status` 行が在る |
| 出力に `Not synchronised` を含まない |
| `System time` のオフセット絶対値が `max_clock_offset_seconds`(既定 **60**)以下 |
| 上記を判定できない(出力が解釈できない／timeout／`chronyc` が起動できない) → **拒否側へ倒す** |

- **取得・状態照会は止めない。** 止めるのは新規採番を伴う操作だけである(§16「channelの障害が既存read-only調査を停止させない」と同じ考え方を、channel内部にも適用する)。
- 拒否時は `denied:` 相当を stderr へ出して非ゼロ終了し、監査へ拒否段階として記録する。**時刻の実測値を検出値として出力しない**(§9.4 の対象ではないが、出力面は同じ規律で揃える)。

## 4. dispatcher へ足す4本

既存の固定arity `read -r check p1 p2 p3 extra` と改行拒否をそのまま通り、`case` に4つのarmを足す。**`eval` も再shell解釈も使わず、固定pathの `oprc-receive` へ `exec` で委譲する。**

| 入口 | operand | 委譲先 |
|---|---|---|
| `operator-request-submit` | 無し(payloadはstdin) | `exec /usr/local/libexec/operator-request-channel/oprc-receive submit` |
| `operator-outbound-list` | `[cursor]`(request_id形式のみ) | `... oprc-receive outbound-list [cursor]` |
| `operator-message-get <request-id>` | request_id形式のみ | `... oprc-receive message-get <id>` |
| `operator-request-status <request-id>` | request_id形式のみ | `... oprc-receive request-status <id>` |

- request_id の検査は dispatcher 側とライブラリ側の**両方**で行う(既存 helper と同じ多層防御)。
- `source` は `oprc-receive` が `coordinator` に固定する。payload に `source` / `request_id` / `created_at` が含まれていれば**拒否**する。
- `oprc-receive` は `OPRES` / `DEVREQ` の作成要求を受け付けない(§4.2)。
- `channel_enabled: false` のときは、この4本だけが `denied:` で非ゼロ終了する。
