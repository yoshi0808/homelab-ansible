# Operator Request Channel MVP 要求仕様

作成日: 2026-08-08  
対象: `docs/ai/reviews/operator_request_channel/`

## 1. 目的

ansy側Coordinatorとquory側Operatorの間で、次のメッセージを手作業のコピー＆ペーストなしに安全に受け渡せる最小経路を作る。

- `OPREQ`: CoordinatorからOperatorへの本番調査依頼
- `OPRES`: OperatorからCoordinatorへの調査結果
- `DEVREQ`: OperatorからCoordinatorへの開発修正依頼

情報交換の経路自体が新しい漏洩経路になり得るため、経路とDLP（機微情報検査）は不可分のものとして同時に導入する。DLPを通過しない経路、DLPを任意に無効化できる経路、検査失敗時に通信を継続する経路は作らない。

本MVPは情報交換だけを対象とする。request本文は、本番操作の承認、実行指示または権限付与として扱わない。

## 2. 正本と保管場所

### 2.1 Gitを正本とするもの

次の実装・設定・文書は、`homelab-ansible` Repoを正本として管理する。

- request schema
- DLP検査プログラムとルールセット
- ansy側client
- quory側channel処理プログラム
- quory側Operator用local CLI
- SSH forced command dispatcherのallowlistと委譲処理
- Ansible role、playbookおよびSemaphore template定義
- permission、配備、検証、drift検査の定義
- テストコード

### 2.2 quoryを正式な保管先とするもの

次のruntimeデータはGit管理せず、quory側の専用領域を正式な保管先とする。

- 受理済みOPREQ
- 作成済みOPRES／DEVREQ
- request間の親子関係とconversation
- requestの内容hash
- 状態イベント
- channel自身の監査イベント

ansyが取得したOPRES／DEVREQはコピーであり、正式な保管先ではない。

Semaphoreのジョブ結果、対象サーバーの状態およびログ原本は、それぞれ元システムが正本である。本channelはそれらを複製せず、必要に応じてopaqueなevidence IDを保持する。

## 3. 対象ホスト

- `ansy`: 開発側。Coordinatorとchannel clientが動作する。
- `quory`: 本番運用側。Operator、forced command receiver、message storeが動作する。

他ホストのユーザー、鍵、ACL、sudoers、サービス、ファイルおよびauthorized_keysは変更しない。

## 4. Trust Boundaryと採用するSSH経路

### 4.1 既存経路の再利用

ansyからquoryへの通信には、既存の`dev-investigate` SSH鍵、quory上の`dev-investigate`ユーザーおよび既存forced commandを再利用する。

```text
ansy
  ↓ 既存dev-investigate鍵
quory: dev-investigate
  ↓ authorized_keysの既存forced command
/usr/local/sbin/recovery-investigate-dispatch-quory.sh
```

本MVPでは次を行わない。

- 新しいSSH鍵の生成・配布・削除・rotation
- 新しいSSH着地ユーザーの作成
- 既存秘密鍵または公開鍵の複製
- `authorized_keys`エントリの追加・削除・変更
- forced commandのpath変更
- quoryからansyへ接続する逆方向SSH鍵の作成

OPRES／DEVREQはansyが既存SSH経路でquoryからpullする。

### 4.2 identityと許可するmessage type

`source`はpayloadの自己申告を信用せず、実行入口からサーバー側で決定する。

| 実行入口 | source | 作成を許可するtype |
|---|---|---|
| ansyからの既存SSH forced command | `coordinator` | `OPREQ`のみ |
| quory上のOperator local CLI | `operator` | `OPRES`、`DEVREQ` |

ansyから`OPRES`または`DEVREQ`をsubmitしようとした場合は拒否する。quoryのOperator local CLIから`OPREQ`を作成しようとした場合も拒否する。

既存鍵がansy側の複数主体から利用可能である場合でも、本MVPが証明するsourceは個人ではなく「ansy側開発identity」である。個人単位の認証が必要になった場合は、別Requirementで専用identityを検討する。

## 5. 初回実装の機能範囲

### 5.1 ansy側

- OPREQ payloadの作成・schema検証
- 送信前DLP
- quoryへのOPREQ submit
- ansy宛OPRES／DEVREQの一覧取得
- request IDによるOPRES／DEVREQ取得
- request状態の取得
- 取得後DLP
- schema version、DLP version、ruleset hash、内容hashの照合

### 5.2 quoryのSSH受入口

既存`recovery-investigate-dispatch-quory.sh`へ、次の固定操作を追加する。名称は実装時にこの意味を維持する範囲で調整してよいが、操作範囲を広げてはならない。

```text
operator-request-submit
operator-outbound-list
operator-message-get <request-id>
operator-request-status <request-id>
```

dispatcherは既存の構文検証方針を維持し、`SSH_ORIGINAL_COMMAND`を`eval`または再shell解釈しない。channel固有処理は固定pathの専用プログラムへ`exec`で委譲する。

### 5.3 quoryのOperator local CLI

Operatorがquory上で次を行えるlocal CLIを提供する。

```text
list-pending
show-request <request-id>
accept-request <request-id>
reject-request <request-id>
reply-opres <request-id>
new-devreq
show-conversation <conversation-id>
show-status <request-id>
```

local CLIは任意path、任意command、SQLまたはshell式を入力として受け付けない。

### 5.4 requestの流れ

```text
CoordinatorがOPREQを作成
  ↓ ansy送信前DLP
既存SSH forced command
  ↓ quory受入前DLP
quoryにimmutable messageとsubmitted eventを保存
  ↓
YoshinobuがquoryでOperatorセッションを起動
  ↓
Operatorがrequestをacceptし、許可された範囲で調査
  ↓
OperatorがOPRESまたはDEVREQを作成
  ↓ quory持ち出し前DLP
quoryのoutboxへ保存
  ↓ ansyがread-onlyでpull
ansy取り込み前DLP
  ↓
Coordinatorが受領
```

request登録だけでOperatorセッション、調査、ジョブまたは本番操作を自動起動しない。

### 5.5 Operator起点のDEVREQ

DEVREQはOPREQへの返信だけでなく、quoryで発見した障害を起点として単独作成できる。

```text
YoshinobuがquoryでOperatorセッションを起動
  ↓
Operatorが障害を調査
  ↓
Operatorがstandalone DEVREQを作成
  ↓ DLP
ansyがpull
  ↓
Coordinatorが原因分析と修正方針を担当
```

Operatorは観測事実と未確認事項を分けて渡す。真因の確定および修正方法の設計は開発側Coordinatorが主体となる。

## 6. request schema

OPREQ／OPRES／DEVREQ共通のschemaをversion付きJSON Schemaとして定義する。YAML表記での論理構造は次のとおりとする。

```yaml
schema_version:
request_id:
conversation_id:
type: OPREQ | OPRES | DEVREQ
source: coordinator | operator
in_reply_to:
created_at:
expires_at:
repo_commit:
purpose:
target_names:
observed_facts:
requested_information:
evidence_references:
expected_result:
unconfirmed:
```

### 6.1 サーバー側で付与するフィールド

次は受入口が付与し、payloadによる上書きを許可しない。

- `request_id`
- `source`
- `created_at`
- 受理時の内容hash
- DLP engine version
- DLP ruleset hash

`created_at`は受入口の時刻を使用する。`expires_at`は固定された最大TTLを超えてはならない。時刻同期が成立していない場合はfail closedとするか、少なくとも新規submitを停止する。

### 6.2 conversationと返信関係

- 新規OPREQでは`in_reply_to`を空とし、`conversation_id`は起点requestに対応させる。
- OPRESは応答対象のOPREQを`in_reply_to`で参照し、そのconversationを引き継ぐ。
- OPREQへの応答として作るDEVREQも`in_reply_to`と`conversation_id`を設定する。
- standalone DEVREQでは`in_reply_to`を空とし、自身を起点とするconversationを作る。
- 存在しないrequest、異なるconversationまたは許可されないtype関係への参照は拒否する。

### 6.3 フィールド制約

- `target_names`はinventory名またはDNS名の配列とし、IPアドレスを許可しない。
- `observed_facts`と`unconfirmed`は明確に分離する。
- `evidence_references`は任意pathではなく、quory側が解釈するopaqueなevidence IDと種別だけを保持する。
- 生ログ本体をrequestへ含めない。
- `additionalProperties`は許可しない。
- 全文字列、配列要素数、JSON階層およびpayload全体に有限の上限を設ける。
- wire上のpayload最大値は64 KiB以下とし、実装がより小さい上限を採用してもよい。
- JSONのduplicate key、非UTF-8、不正なUnicodeおよび非有限数値を拒否する。

## 7. immutable messageと状態イベント

request／response本文と状態を同じファイルの更新で管理しない。

### 7.1 message

- DLPとschema検証に合格したmessageだけを新規保存する。
- 一度受理したmessage本文を更新・置換しない。
- request IDの衝突時に上書きしない。
- canonical JSONに対する内容hashを保存し、取得時に再照合する。
- 同じmessageを複数回取得しても内容を変更しない。

### 7.2 状態イベント

状態遷移はappend-only eventとして記録する。

```text
submitted
accepted
rejected
answered
expired
```

現在状態はevent列から導出する。高速表示用indexを持つ場合、そのindexは再構築可能な派生物とする。

DLPまたはschemaで受入前に拒否されたpayloadにはrequest IDを発行せず、`rejected`状態のrequestとして保存しない。監査には検出値を含まない受付失敗イベントだけを残す。

## 8. quoryの保存領域

正式なruntimeデータはOperator起動ディレクトリやGit worktreeへ置かず、quoryの専用領域へ保存する。

想定配置は次とする。最終pathを変更する場合も、同じ分離と権限を維持する。

```text
/var/lib/operator-request-channel/
├── inbox/
├── outbox/
├── events/
└── quarantine-metadata/

/var/log/operator-request-channel/
└── audit.jsonl
```

- `inbox`: ansyから受理したOPREQ
- `outbox`: Operatorが作成したOPRES／DEVREQ
- `events`: 状態イベント
- `quarantine-metadata`: 受付失敗のカテゴリ、JSON位置、時刻等。payloadは保存しない。
- `audit.jsonl`: request本文を含まない監査イベント

保存は一時ファイルからのatomic renameまたは同等のatomic createを用い、symlink／hardlink、path traversal、既存ファイル上書きを許可しない。作成時umaskと最終owner／group／modeを固定する。

保存件数と総容量に上限を設け、上限到達時は古いmessageを暗黙に削除せず、新規submitをfail closedで拒否する。retentionと正式な削除手順は、実装前のplanで明示する。

## 9. DLP

### 9.1 4つの検査点

同一の検査実装とルールセットを、次の4箇所で必ず使用する。

1. ansyのOPREQ送信前
2. quoryのOPREQ受入前
3. quoryのOPRES／DEVREQ持ち出し前
4. ansyのOPRES／DEVREQ取り込み前

DLPを通信処理から任意に外せるoptionを提供しない。

### 9.2 fail closed

次の場合はmessageを送信、保存または取り込みしない。

- DLP programを起動できない
- schemaを読み込めない
- engine versionまたはruleset hashが期待値と一致しない
- 検査処理がtimeoutまたは異常終了する
- payloadが上限を超える
- 検査結果を判定できない

### 9.3 最低限の検出対象

- PEM形式秘密鍵およびSSH秘密鍵
- Slack tokenおよびwebhook URL
- Semaphore API token
- Bearer tokenおよびJWT
- password、secret、token等のkey-value
- Vault復号済み平文
- credentialを含むURL
- 環境変数の一括dump
- `/proc/*/environ`等を由来とする出力
- private IPv4
- IPv6 ULAおよびlink-local
- field contextを考慮した高entropy文字列

gitleaksを基礎として利用してよいが、private IP、schema上のfield contextおよびchannel固有形式は専用ロジックで補う。commit hash、request ID、conversation ID、内容hash等を高entropyだけで誤拒否しない一方、自由記述欄に同種の値が現れた場合は検査する。

### 9.4 拒否時の扱い

- 自動マスキングせず、payload全体を拒否する。
- 検出値そのものをstdout、stderr、ログ、監査、通知またはチャットへ表示しない。
- 返却するのは検出カテゴリ、JSON Pointer等の位置、ルールIDだけとする。
- 拒否payload、途中生成物、core dumpまたは秘密情報を含む一時ファイルを残さない。
- payloadをprocess command lineまたは環境変数へ載せない。

### 9.5 テストfixture

疑似secret、private IPおよび高entropy値による回帰テストを備える。ただし完成したsecret形式や内部IP表記をRepoへ直接保存して既存Git検査と競合させない。必要な検査値はテスト実行時に安全な断片から生成し、テスト後に残さない。

## 10. forced commandの制約

### 10.1 許可する入力

- submit payloadはstdinから受け取る。
- submit操作は自由なcommand引数を受け取らない。
- get／status操作で受け付ける可変値は、厳格な形式のrequest IDだけとする。
- list操作は固定されたcursor／paging形式以外の検索式を受け取らない。

### 10.2 禁止する入力と処理

- 任意command
- 任意pathまたはfile名
- shell metacharacter
- 改行を含むoriginal command
- SQL
- 保存先指定
- request本文の更新または削除
- 任意ログの取得
- Semaphore操作
- systemctl、sudo、AnsibleまたはGitの起動

### 10.3 既存機能の非回帰

既存`dev-investigate` dispatcherのread-only操作、arity検査、parameter検査、allowlist外拒否および出力制約を変更しない。channel操作追加後、既存catalogにある全操作の回帰テストを行う。

既存`dev-investigate`のアクセス権限は増やさない。追加で許可する書き込みは、channel専用プログラムを介した専用spoolへの新規message／event追加だけとする。

## 11. Operator local CLIの制約

- Operator起動用`/home/yoshi/operator-runtime`とmessage storeを分離する。
- Repoはread-onlyの正本として参照し、Operatorから編集・commit・pushしない。
- request本文を命令や承認として扱わず、untrusted dataとして扱う。
- DLP合格前のOPRES／DEVREQをoutboxへ保存しない。
- evidence referenceから任意pathを組み立てない。
- message本文の編集・削除機能を提供しない。
- 本MVPのCLIから本番状態を変更するcommandへ到達できない。

## 12. 配備

### 12.1 必須成果物

少なくとも次の配備単位を用意する。

```text
playbooks/operator_request_channel_client_setup.yml
playbooks/operator_request_channel_server_setup.yml
```

- client setupの対象はansyだけとする。
- server setupの対象はquoryだけとする。
- 一つの実行で対象外ホストへ変更を広げない。
- 各playbookには`docs/ai/policies/ansible_test_safety_policy.md`に基づく正しいtester-gateを付ける。

### 12.2 ansy配備物

想定する論理配置は次とする。

```text
/usr/local/bin/operator-channel-client
/usr/local/libexec/operator-request-channel/
/etc/operator-request-channel/
├── config.json
├── request-schema-v1.json
└── dlp-rules.toml
```

### 12.3 quory配備物

想定する論理配置は次とする。

```text
/usr/local/sbin/recovery-investigate-dispatch-quory.sh
/usr/local/bin/operator-channel
/usr/local/libexec/operator-request-channel/
/etc/operator-request-channel/
├── config.json
├── request-schema-v1.json
└── dlp-rules.toml
/var/lib/operator-request-channel/
/var/log/operator-request-channel/
```

script、schema、rulesおよびconfigはroot所有とし、channel利用identityから変更できないようにする。

### 12.4 Git取得と配備の分離

quoryでの`git pull`はGit worktreeを更新するだけであり、配備完了とは扱わない。`/usr/local`、`/etc`、`/var/lib`等への反映にはserver setup playbookの明示実行を必要とする。

本番側server setupはquory側のSemaphoreを承認面として、次の二段階で行う。

1. 既存のSemaphore template管理へ、`playbooks/operator_request_channel_server_setup.yml`をquoryだけに対して実行する手動用templateの定義を追加する。
2. quoryが確定済みcommitを取得した後、既存の`SEMI-SAFE: Semaphore templates setup`を実行してそのtemplateをSemaphoreへ登録・更新する。その後、Yoshinobuが登録されたserver setup templateをSemaphore UIから明示的に実行する。

`SEMI-SAFE: Semaphore templates setup`の実行はtemplateの登録・更新であり、Operator Request Channel serverの配備そのものではない。server setup templateの実行が成功し、配備後検証に合格するまでは配備済みと判断しない。

server setup templateにはscheduleを登録しない。git pull、template登録、timerまたは他の定期処理からserver setupを自動起動しない。ansyからquoryのserver setup playbookを直接実行する経路も追加しない。

ansy側client setupはansyだけを対象として実行し、quoryまたは他の本番ホストを対象に含めない。

### 12.5 配備順序

初回配備は次の順序を基本とする。

1. ansyで実装、review、test、commit、pushを完了する。
2. quoryが確定済みcommitを取得する。
3. quory側で既存の`SEMI-SAFE: Semaphore templates setup`を実行し、server setup templateをSemaphoreへ登録・更新する。
4. 登録されたserver setup templateが、期待するplaybook、inventoryおよびquory限定の対象範囲を持ち、scheduleを持たないことを確認する。
5. Yoshinobuがquory側のSemaphore UIからserver setup templateを明示実行する。
6. 配備後のread-only検証を行う。
7. ansy側でclient setupを実行する。
8. DLPとschemaのversion／hash一致を確認する。
9. 疑似payloadによる往復試験を行う。

配備途中のversion不一致時はchannelを利用不能としてfail closedにし、既存`dev-investigate` read-only操作には影響させない。

## 13. channelの無効化

既存鍵と既存forced commandを共有するため、channelを停止する目的で既存鍵やauthorized_keysを削除してはならない。

root所有configにchannel固有のenable／disable制御を持たせる。disable時は追加したchannel操作だけを拒否し、既存`dev-investigate` read-only操作を維持する。

無効化はmessageを削除せず、新規submit、Operatorによる新規outbound作成およびansyへの取得を停止する。保全済みデータの削除は別の明示手順とする。

## 14. drift検査

既存のdeployment drift検査へ、少なくとも次を追加する。

- ansy clientの配備済みhash
- quory channel programの配備済みhash
- dispatcherの配備済みhash
- schemaのhash
- DLP rulesetのhash
- ansyとquoryのengine／ruleset version一致
- spool、event、audit領域のowner／group／mode
- channel programがsudoersを持たないこと
- 既存authorized_keysのforced command構造が変わっていないこと
- channel操作のallowlist外拒否

監視のためにauthorized_keys本文、公開鍵本体、秘密情報またはrequest本文を出力しない。

## 15. 監査

accepted messageについて、次を記録する。

- request ID
- conversation ID
- type
- source identity
- created_at
- 内容hash
- schema version
- DLP engine version
- DLP ruleset hash
- 状態イベントと時刻
- 処理結果

受付前に拒否したpayloadについては、request本文、内容hash、検出値を保存せず、次だけを記録する。

- attempt ID
- 受付時刻
- source identity
- 拒否段階
- 検出カテゴリ
- JSON上の位置
- rule ID
- DLP engine version／ruleset hash

## 16. 非機能要件

- 同じrequest IDに対する取得結果は決定的であること。
- network切断やclient再試行で既存messageを上書きしないこと。
- 中途半端なmessageを可視化しないこと。
- 同時submit時にもrequest ID衝突、event欠落または部分書込みが起きないこと。
- stdoutはprotocol出力だけとし、診断は秘密情報を含めずstderrへ出すこと。
- 正常時・拒否時ともに秘密情報をプロセス一覧、shell historyまたは一時ファイルへ残さないこと。
- channelの障害が既存`dev-investigate` read-only調査を停止させないこと。
- channelの障害がSemaphore、対象ホスト、既存jobまたはscheduleへ影響しないこと。

## 17. 初回実装で除外する範囲

- Semaphore jobの開始・再実行・停止
- Semaphore scheduleの登録・変更・削除
- サービス再起動、停止またはenable／disable
- 対象サーバーへの書き込み
- 任意shell command実行
- Ansible playbookの本番実行
- Git操作またはコード修正
- Operatorからの自動的なCoordinator起動
- request登録によるOperatorセッション自動起動
- Slack通知
- 生ログ転送
- 証跡原本の複製
- Operatorと既存Semaphore Playbookの共通実行ロック
- 新しいSSH鍵、SSHユーザー、sudoersまたは常駐broker serviceの作成

## 18. テスト要件

### 18.1 offline test

- 全message typeのschema正常系・異常系
- originとtypeの許可matrix
- standalone DEVREQと返信DEVREQ
