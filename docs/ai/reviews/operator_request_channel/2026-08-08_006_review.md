## Code Review: Operator Request Channel MVP(初回実装)

### Summary

DLPエンジン・schema検証・spool・request_id/conversation_id生成・fail-closed規律は4検査点すべてで同一実装・同一ルールセットを通っており、既存`dev-investigate`の25操作・鍵・`authorized_keys`・forced command pathへの変更は無い(diffで確認)。検出値の非出力、atomic create、ACLの最小権限化も実装レベルでは要求どおり作り込まれている。一方、**quory側の実際の到達性を成立させる配備手順に構造的な欠落が1件**あり、これを埋めない限り「ansyから既存SSH forced command経由でOPREQを登録できる」(requirement §19)という完了条件そのものが満たせない。加えて、設定値が実装へ配線されていない箇所と、通常運用下で自己誘発しうる整合性エラーが1件ずつ見つかった。

### What Looks Good

- **DLP4検査点の実装一致**(requirement §9.1): `operator-channel-client`(submit前/pull後)、`oprc-receive`(受入時)、`operator-channel`(`_create_response`、持ち出し前)のすべてが`config.load_and_verify_dlp_ruleset(cfg)`→`dlp.scan()`という同一コードパスを通る。`dlp.py`はchannel固有のフィールド名を一切持たず、ルールセットは`copy`配備でTier1ドリフト検査の対象になっている(`roles/deployment_drift_check/defaults/main.yml`の新規追加分で確認)。
- **fail-closed網羅**(§9.2): engine version不一致・ruleset hash不一致・schema hash不一致・timeout(`SIGALRM`ベース、非対応環境でも即fail-closed)・payload超過・DLP判定ブロックのいずれも例外送出→呼び出し側`_deny`/`_error`(非ゼロ終了)で終わり、途中結果を返す経路が無いことをコードで確認した。
- **検出値の非出力**(§9.4): `dlp.py`の`Finding`はcategory/rule_id/pointerのみを保持し、`scan()`の戻り値・例外いずれにもマッチ文字列を含まない設計になっている。`schema.ValidationError`もpointer/ruleのみ。stdout出力はprotocol JSONのみ、diagnosticsは固定文言の`denied:`/`error:`のみで、payload本体やDLP検出値を含む経路が無いことをコードで確認した。
- **immutabilityとatomic create**(§7.1、§8): `store._atomic_create`は`tempfile.mkstemp`+`os.link`(symlink追従なし、EEXISTで`StoreConflict`)で構成されており、requirement§8の「atomic renameまたは同等のatomic create」「symlink/hardlinkを許可しない」の両方を満たす。一時ファイルは成功・失敗いずれの経路でも`finally`で削除される。
- **既存`dev-investigate`の非回帰**(§10.3): `recovery-investigate-dispatch-quory.sh`の既存25 armの本文・arity検査・拒否文言は1文字も変更されておらず(diffで確認)、新規4armは末尾に追記されている。改行拒否・fixed-arity `read`は新旧共通で先に走る。コマンド名の衝突も無い(29本、重複なし)。
- **ACLの最小権限**(§2.3、§8、§12.3): `defaults/main.yml`のコメントが、plan本文の表記(`inbox`へのdefault read付与)と実際のACL定義の食い違いを明記した上で、狭い側(dev-investigateにinbox読み取りを与えない)を採用している。この判断はコードの整合性(`oprc-receive`のrequest-statusがinboxの本文を読まず`read_state_from_events`を使う設計)とも一致している。
- **Git検査**(§18.3): DLP fixtureはすべて`_fixtures.py`が実行時にfragmentから組み立てており、PEM/Slackトークン/JWT/RFC1918 IPv4等の完成形文字列はソース中に存在しない。`__pycache__`は`.gitignore`のグローバルルール(`__pycache__/` / `*.pyc`)で既に除外され、`git status`にも出ていない。`.gitignore`の追加行(`!scripts/tests/operator_request_channel/`)も意図どおり機能している。
- **配備方式とドリフト検査の整合**(§14): 共有ライブラリ・schema・rulesetはすべて`copy`配備(Tier1適格)で、ホストごとに2エントリへ分けた設計・理由がカタログのコメントに明記されており、実装(`hosts: [ansy]`/`hosts: [quory]`各1エントリ、同一src)とも一致することを確認した。新設3クラス(owner/group/mode、sudoers不在、allowlist外拒否probe)は`collect.yml`→`evaluate.yml`→既存`report.yml`(変更不要、汎用集約のため)まで配線されており、`report.yml`のSlack通知が検出値やauthorized_keys本文を含まないことも確認した。
- **tester-gate分類**(Policy TS-026/TS-036): 両playbookとも`check-mode-native`、理由文が実際のguard(`when: not ansible_check_mode`、TS-014)と一致しており、role/task側は分類・理由を複製せず参照に留めている(TS-036)。
