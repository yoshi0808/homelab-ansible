## 3. AC4: `canonical_api_base_url` が残っており、ゲート撤去後も接続先を検査している

**PASS(実API、3通りの実測)。**

### 3.1 素の新規作成ブロック(canonical上書きなし)

ベースライン(20件、全`active:false`、21件目未作成)へ、**canonical上書きなしで**(defaultsのまま=quory URL)適用した。

- 新規作成(id無し→POST)を試みる直前に `Refuse to create this schedule active against a non-canonical connection (R2)` でfail、rc≠0。
- 直後に直接APIで確認: **schedule は20件のまま(21件目は作成されず)、既存20件もすべて `active: false` のまま**(新規作成が最初の処理項目であるため、後続の20件の更新PUTには到達すらしていない)。
- template側(`SAFE: Semaphore update check`)は作成された(templateのreconcileは本ACのgateと無関係な既存機構であり、書き込みブロックの対象ではない)。

### 3.2 既存21件が揃った状態からの再有効化ブロック(接続先を戻す)

AC1/AC2検証後の「21件フル一致」状態から、id=30(`SEMI-SAFE: Semaphore db backup daily`)を直接APIで `active: false` へ戻し、cronだけカタログ値と異なる値にprobeした(activeはfalseなので実際にはcatalog=trueと不一致だが、この節の目的は「fresh GETがfalseを見る」経路の確認)。canonical上書きなしで適用すると、fresh GETで観測した`active: False`を`true`へ動かそうとする書き込みが `Abort all remaining writes if this write would newly activate against a non-canonical connection (R2)` でブロックされ、id=30は`active: false`のまま(書込0件)だった。

### 3.3 レビュー指摘の競合(diff時点スナップショット vs fresh GET)を実APIのタイミングで再現

**これが今回もっとも重要な実測である。** `2026-08-24_004_review.md` High 1が指摘した欠陥(diff計算時点のスナップショットで「有効化対象」を判定すると、diffと実際の書き込みの間の外部変更を見逃す)が、**実際のAPIタイミングで再現しないことを確認した。**

手順:
1. 21件フル一致状態から、id=30のcronだけを直接APIで変更(`0 12 * * *` → `0 11 * * *`)。`active`はcatalog値と同じ`true`のまま — **diff計算時点では`fields=['cron_format']`のみで、'active'は差分に含まれないはず**(旧設計が有効化対象を「diff時点で active が差分に含まれる項目」として静的に列挙していたら、id=30はここで対象外と誤判定される)。
2. `ansible-playbook`を**canonical上書きなしで**バックグラウンド起動すると同時に、別プロセスから0.4秒後にid=30の`active`を直接APIで`false`へ変更する(UIでの操作を模した外部変更)。
3. 結果: **playbookは`id=30`への書き込み直前、fresh GETが観測した`active: False`を検出し、「falseからtrueへ動かします」というR2ブロックメッセージでfail、rc≠0。** 直後に直接APIでid=30を確認し、`active: false`・cronはprobe値のまま(書込0件)だったことを確認した。

**旧設計(diff時点スナップショット判定)であれば、この経路はブロックされず素通りしていたはずの構成**(diffは'active'を差分に含めない、しかし実際のfresh GETは変化後の値を見る)である。**今回、実際のAPIタイミングでこの競合を発生させ、修正後のコードが正しくブロックすることを確認した。** これはレビューが実Ansible(decoy)で再現・Implementerがローカル`hosts: localhost`のJinja評価で確認した内容を、**実Semaphore APIに対する実タイミングで裏付けたもの。**

## 4. レビュー指摘のもう1つの欠陥(非bool `active` のtruthiness fail-open)の実API確認

**実Semaphore APIでは再現できないことを確認した(良い意味で)。**

- 直接APIで、schedule(id=21)の`active`フィールドをJSON文字列`"false"`(非bool)にしてPUTを試みたところ、**Semaphore自身がHTTP 400で拒否し、値は変化しなかった。**
- DBスキーマ(`sqlite3 .schema project__schedule`)を確認したところ、`active`列は`INTEGER NOT NULL DEFAULT 1`であり、Go側の構造体マーシャリングにより、GETのJSON応答は常に真の`bool`型で返る(SQLiteのINTEGER 0/1をGoの`bool`フィールドへデコードする際に型が固定される)。

**結論: 修正済みのtype-safeな判定(`isinstance(value, bool)`)は防御的に正しいコードだが、この実Semaphoreインスタンス・このスキーマでは、`active`が非boolとしてAPIから返る経路は実際には到達できない。** 修正自体は無害な防御であり撤回を勧める理由にはならないが、**「実際に踏める脆弱性だったか」という問いには、この環境では「踏めない」と答えるのが正確**。API/DB双方でbool型が強制されているため、レビューが指摘した経路は理論上の頑健性であり、実観測された不具合ではない。

## 6. この経路では確かめられなかったこと

- **fresh GETからPUTそのものまでのごく短い競合窓**(§3.3で閉じたのは「diff計算からfresh GETまで」の窓のみ)。implement記録・requirementとも、この最後の窓自体はSemaphore APIにETag/トランザクションが無いため閉じられないと明示・受容しており、今回もこれを覆す新しい手段は見つけていない。
- **quory本体での実挙動**(21件の実際の状態、実際の`active`型)。EXEC-052によりquoryには到達できないため未確認。ただしAC2は「カタログと観測値が一致していれば無変更」という設計をansy上の21件で確認しており、quory固有の値に依存しない性質である。
- **`semaphore_templates.py`の`_target_fields()`/`_observed_fields()`の`or []`型畳み込み欠陥**(implement記録§3.6、`docs/ai/status.md`へ引き渡し済み)。本案件のAC1/AC2/AC4の対象範囲外であり、今回のテストでも意図的に触れていない(template側の書き込みは今回いずれも「新規作成」のみで、この欠陥が影響する「型不一致による誤ったunchanged判定」の経路は踏んでいない)。
