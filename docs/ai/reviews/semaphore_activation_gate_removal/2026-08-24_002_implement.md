### 設計の中身: 「2段」をどう畳んだか

`semaphore_schedules_desired(entry, template_id)` は `stage` と `observed_detail` の2引数を失い、`desired['active']` はカタログの `entry['active']` を無条件にそのまま返すだけになった。従来は「新規は常に `active: false` で作成」「既存は観測値を維持(true→falseの即時反映のみ、false→trueは別段階待ち)」という間接化があったが、この間接化自体が有効化ゲートに協調するためだけに存在していた。

`semaphore_schedules_diff()` の戻り値は `new` / `stage1` / `unchanged` / `pending_activation` の4キーから `new` / `changed` / `unchanged` の3キーへ縮小した。`active` 単独の差分(旧 `pending_activation` に相当する状況)は、他のフィールドと同列に `changed` へ入る ―― これが AC1(1回の適用で有効になる)を成立させている核。

`get-then-merge-then-send`(R8)自体、および `closed-world` でのidentity-drift時の「残り全中断」/移行期間での「1件見送り継続」という分岐(R8本文)は、有効化ゲートとは独立した一般的な安全機構なので、そのまま維持した。post-write verify・non-managed diff チェック(AC4/AC17、旧requirement番号)も同様に維持。

## 3. R2(改訂後): `canonical_api_base_url` を復元し、write-time で成立する接続先検査を組み直した

### 3.1 初版(diff時点判定)にあった競合 ―― `2026-08-24_004_review.md` High 1

**復元の最初のバージョンは、diff計算の直後に1回だけ「有効化対象」を静的に列挙し(`semaphore_schedules_activation_targets(diff_result)`)、それが空でなければ非canonical接続先を拒否する、という設計だった。** これは不健全だった。独立レビューが実Ansibleで次を再現した。

1. カタログ`active: true`、diff時のGETも`active: true`、**cronだけ差分** → `fields=['cron_format']` で有効化対象は空と誤判定される
2. 接続先が非canonicalでも、有効化対象が空なのでcanonical検査を通過する
3. **diffとPUTの間にUIで`active: false`へ変更される**
4. PUT直前のfresh identity検査はid/nameしか見ないため、この変化を検出せず通過する
5. **fresh objectへ、diff時点の`item.after.active: true`が上書きされてPUT** ―― 非canonical接続先で再有効化が成立してしまう

**判定はdiff時点のスナップショットではなく、実際に書く値で行う必要があった。**

### 3.5 型を確かめずtruthinessで見ていた欠陥 ―― `2026-08-24_005_review.md` High 1

**`semaphore_schedules_would_newly_activate`が、`before_active`/`desired_active`の両方を`bool()`へそのまま通していた。** Pythonの`bool("false")`は`True`である(空でない文字列は常にtruthy)。したがって、fresh GETの`active`がAPI都合で非bool(たとえば文字列`"false"`)として返ってきた場合、`not bool("false")`が`False`になり、「既に有効なので今回の書き込みは有効化ではない」と誤判定していた。**判定不能が安全側(有効化するかもしれない、として扱う)ではなく、通す側へ倒れていた。** 独立レビューが実Ansibleでこれを再現し(fresh `active: "false"`、desired `true`、非canonical接続先で`would_activate=false`となりPUTを通す)、同日中に別案件(`semaphore_update_check`の`html_url`を`length > 0`だけで見ていた欠陥、`null`/数値での評価例外)でも同型の欠陥が続けて見つかっている、という指摘を受けた。

**修正: 両引数を実`bool`(または`before_active`のみ`None`、「まだ存在しないschedule」というR2自身の規約)だけを正当な入力とし、それ以外はすべて「有効化するかもしれない」側(`True`)へ倒す。**

```python
if not isinstance(desired_active, bool):
    return True   # 分類不能 -- 「有効化ではない」と決めつけない
if desired_active is False:
    return False  # 曖昧さなく有効化ではない(beforeの型を問わない)
if before_active is None:
    before_active = False  # R2の規約: 未作成のschedule = 未有効
if not isinstance(before_active, bool):
    return True   # 分類不能 -- 「既に有効」と決めつけない
return not before_active
```

`isinstance(value, bool)`を使う(`bool(value)`という素朴な真偽変換は使わない)ことで、文字列・数値(`0`/`1`含む。`bool`は`int`のサブクラスだが`1`自身は`bool`のインスタンスではないため`isinstance(1, bool)`は`False`になる)・`dict`・`list`・空文字列のいずれも「分類不能」として`True`側(有効化するかもしれない、なので接続先検査の対象にする)へ倒れる。

### 3.6 同型の欠陥がこのroleの他所に無いか(Coordinator指示の横断確認)ーー訂正

**2026-08-24、この節の当初の結論「他に無かった」は誤りだった。** `2026-08-24_006_review.md` が、独立レビューとして role を見直し、**この監査が見落としていた同型の欠陥を template 側に見つけた**。以下は訂正後の内容。

**見落としの事実**: 監査当初、`semaphore_schedules_desired()`の`bool(entry['active'])`・`semaphore_schedules_url_matches_canonical()`・`semaphore_templates.py`の`_parse_marker`/reconcileロジックの3箇所を確認し、「同型欠陥は無い」と結論した。**このとき`semaphore_templates.py`の`_target_fields()`/`_observed_fields()`にある`entry.get('arguments') or []` / `observed_row.get('survey_vars') or []`という別のtruthiness畳み込みを見ていなかった。** `_parse_marker`のすぐ近く(同じファイル)にあるコードを読みながら、その先の`_target_fields`/`_observed_fields`まで検査範囲を広げられていなかった。**自己申告の監査では出ず、独立レビューが実Ansibleで再現して初めて見つかった。**

**見落とした対象(template側の`or []`)**: `roles/semaphore_templates/filter_plugins/semaphore_templates.py`の`_observed_fields(observed_row)`(127-149行付近)が、`observed_row.get('arguments') or []`・`observed_row.get('survey_vars') or []`で観測値を正規化している。`roles/semaphore_templates/tasks/read.yml`の正規化(58-72行付近)は、API応答の`arguments`/`survey_vars`が文字列ならJSON decodeするが、**文字列でない値(`false`、`0`、`{}`等)は型を保ったまま素通しする**。その素通しされた値が`_observed_fields()`に渡ると、`or []`が`false`や`{}`のようなfalsy値を「正当な空配列」と同一視して`[]`へ畳み込む。**型を確かめずに真偽で見て、判定不能(不正な型)が「同期済み(`unchanged`)」という通す側へ倒れる**、`would_newly_activate`の旧欠陥と同じ形。`_target_fields(entry)`(catalog側)も同じ`or []`を使う。

**本案件では直さない。** 理由は3つ:

1. **既存欠陥であり、本案件(有効化ゲート撤去)の差分が持ち込んだものではない。** `git show HEAD:roles/semaphore_templates/filter_plugins/semaphore_templates.py`でも同じ形が存在する。
2. **本案件は既に独立レビュー5ラウンド目であり、無関係な既存欠陥を混ぜると差分が読みにくくなる。**
3. **`_observed_fields()`/`_target_fields()`はtemplateのreconcile(作成/更新)判定そのものであり、ここを直すとtemplate側の`changed`/`unchanged`判定という実Semaphoreに対する挙動が変わる。** 受入条件の検証が別途要る、本案件(schedule側の有効化ゲート撤去)のscopeとは異なる検証が必要になる。

### 3.7 横断監査の他の指摘(`2026-08-24_006_review.md` Suggestion 1/2への対応)

- **Suggestion 1(URL一致filterの「型が違えば必ず不一致」という説明が字義どおりには誤り)**: `semaphore_schedules_url_matches_canonical()`に、両引数へ非空の**同値**dict(例: 両方とも`{'a': 1}`)を渡すと、`_normalize_api_base_url()`はどちらも型を変えずそのまま返し、`bool(canonical) and used == canonical`は`True`(一致)になる。§3.6の「型が違えば必ず不一致になる」は、この「両方が同じ非文字列型で、たまたま等しい」ケースを排除できていなかった。**ただし現実の書き込み経路では、`api_base_url`は先行する`GET /projects`等のURI taskへ実際に使われるため、文字列でない値(dict等)を渡すとURI taskの時点で失敗し、この関数まで到達しない。** 迂回の実証はReviewerも確認できていない。この記録は「先行URIが型違いのURLを停止させる」という前提込みで正確にする ―― filter単体の性質としては「型が違えば必ず不一致」ではなく「文字列以外の同値ペアは一致し得るが、それが実害を持つ経路は今のところ無い」と記述するのが正しい。**この関数自体を文字列以外なら常にfalseへ限定する変更は、本案件のscope外(activation predicateの型安全化とは別の、URL比較filterの防御強化)として、ここでは行わない。**

## 5. R4(改訂後): 既存21件が撤去後の適用で1件も変化しないこと

**「全フィールドがカタログと一致しているから無変更」という意味であり、「撤去が新規登録の経路にだけ効く」という意味ではない(2026-08-24改訂)。** 撤去後は既存scheduleの`active: false → true`も、他のフィールドと同じ`changed`経路で直接反映される ―― それが撤去の目的そのものである。

**開発側で確かめられる範囲では、既存21件の観測値が変化しない設計であることを filter 単体テストで確認した。** 実際にSemaphore APIへ21件を適用して差分ゼロを確認する作業(AC2)はTesterの領分であり、この案件では行っていない。

確認した理屈: 既存21件はいずれも「カタログの5フィールド(`active`含む)がすでに観測値と一致している」状態(`semaphore_schedules_as_code` 案件で導入された時点でカタログは実測値の転記だった)。新しい `semaphore_schedules_diff()` は各フィールドを `_strict_equal` で単純比較するだけで、5フィールドすべてが一致していれば `unchanged` に入り、`changed`/`new` のいずれにも入らない ―― PUT/POSTは一切発行されない。**21件は全てquoryの実状に合わせて`active: true`が観測値と一致しているため、R2で復元した接続先検査(`schedules_apply_item.yml`の`semaphore_schedules_would_newly_activate`)にも抵触しない** ―― そもそもPUT自体が発行されないので、write-time判定へ到達すること自体がない。
