# Code Review: Semaphore schedule activation gate removal（再レビュー2）

Reviewer: Codex / 2026-08-24  
Verdict: **Request Changes**

## Summary

前回 High 1 の具体的な迂回（diff時点ではcronだけ差分、fresh GETでは`active: false`、desiredは`true`）は閉じた。現物のAnsible式を実行し、現在は`would_activate=true`となることを確認した。canonical接続、既にactive、無効化、新規作成の対照条件もコード上は必要十分であり、内部factの`-e`偽装防止、復旧向けfail文面、requirement §7.1も前回指摘へ正しく対応している。

一方、fresh GETの`active`を真偽値として型検証せずPythonのtruthinessへ通すため、APIが文字列`"false"`を返すと「既に有効」と誤判定する。非canonical接続先でそのままcatalogの`active: true`をPUTできることを実Ansible評価で再現した。R2の接続先境界が判定不能時にfail-openするため、修正が必要である。

## What Looks Good

- race判定をdiff結果から切り離し、既存scheduleではfresh GET後・PUT前、新規ではPOST前に配置した。前回の具体的な古いsnapshot経路は閉じている。
- canonical URLの一致判定は1つのfactへ集約され、既存/新規の双方が同じ結果を消費する。接続先判定の複製は無い。
- identity drift時はcanonical判定より先にclosed-world failまたはmigration skipとなり、未設定の内部factを誤って消費しない。
- fail文面は「恒久的なcanonical変更」と「fixture限定の一時上書き」を区別し、復旧Contextと衝突しない。
- requirement §7.1は、順序保証まで捨てた理由を単なる煩雑さではなく実データと受容判断から復元できる。
- shell/commandの追加、token表示、`no_log`後退、外部から内部判定を偽装できる変数追加は無い。

## Verdict

**Request Changes** — 前回のraceは報告された時間窓では閉じ、文書指摘も解消した。しかしfresh API値の型違いでR2の接続先境界を迂回できる。真偽値型をfail-closedで検証し、task経路のnegative fixtureを追加してから再レビューすること。
