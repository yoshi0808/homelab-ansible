# requirement: schedule の有効化ゲートを撤去する

起案: Coordinator / 2026-08-24 / 決定: Yoshinobu

## 1. なぜ撤去するか

**2026-08-24、Yoshinobu が撤去を決定した。**

> そもそも要らないです。導入時には時間を留意して導入するものです。**この機能自体が人間にとって混乱を招きます。** 問題なのは、今の登録する時間と、設定されたスケジュールとがあまりにも近い場合のみ検討すべき事です。いつ登録するかわからないから登録して良いかフラグを立てるなんてのはナンセンスです。**次回の起動は何月何日の何時です、のチャット上の確認だけで良いのでは。** なぜ実装まで大袈裟にやらないといけないのかが理解できません。

> **後から振り返りをした時に何のために作ったのか絶対に理解できない。**

**この最後の一文が撤去の芯である。** 機構は残るが、それが何を守っているかは残らない。

## 2. 実際に起きたこと(2026-08-24)

`semaphore_update_check` の schedule を1件登録するのに、**押下2回・commit 2回**を要した。

1. `#826` — setup を押す。schedule は作られたが `active: false` で保留
2. Coordinator が `semaphore_schedules_allow_activation: true` の commit
3. `#828` — もう一度押す。有効化される
4. Coordinator が `false` へ戻す commit

**そして Coordinator は、この機構を Yoshinobu へ説明するのに3往復を要し、それでも伝わらなかった。** 説明の巧拙ではなく、**機構が説明を要する形をしている**ことの現れである。

**次回の起動は 2026-09-10 20:00、登録から16日先だった。** 守るべき危険は存在しなかった。

## 3. この機構が守ろうとしていたもの

**「カタログに schedule を書くこと」と「本番で走り出させること」を、別々の人の行為に分けること。**

**ただし人の関与はもともと2箇所ある** — カタログへ書く commit のレビューと、setup ボタンの押下である。**ゲートは、既にある関与の上へもう1段を積んでいた。**

**そして畳み忘れても何も鳴らない。** フラグが立ったままであることを検出する仕組みは無く、**保護は静かに消える。**

## 4. ゴール

- **カタログが宣言した `active` を、そのまま反映する。**
- **押下1回・commit 1回で schedule が登録され、有効になる。**
- **撤去した理由が、次に読む人へ残る。**

## 5. 非ゴール

- **カタログの他の性質を変えない。** cron / template / task_params / 無効化の反映、closed-world フェーズ、timezone の一致検査は現状のまま。
- **「登録と発火が近すぎる」問題を実装で解こうとしない**(§7)。

## 6. 要求

| # | 要求 |

| R1 | **`semaphore_schedules_allow_activation` と、その検証・分岐を撤去する。** 2段適用(`stage1` / `stage2`)、`pending_activation`、`created_pending_activation`、`activation_gate` を含む |
| R2 | **`semaphore_schedules_canonical_api_base_url` は残す**(2026-08-24 改訂)。当初「独立した目的を持つか確かめる」としたが、**実装者が「消費箇所がゲートだけ」を根拠に撤去し、独立レビューがそれを覆した。** 旧R15の目的は**Restore複製のansyへ書かないこと**であり、**ゲートが消えて `active` を直接書くようになった分、その危険はむしろ増えている。** **消費箇所の有無と目的の有無を取り違えない** |
| R3 | **レポートの schema から、撤去したキーを落とす。** 読み手が「昔あったもの」を探さないように |
| R4 | **現在の21件が、撤去後の適用で1件も変化しないこと。** これは「全フィールドがカタログと一致しているから無変更」という意味であり、「撤去が新規登録の経路にだけ効く」という意味ではない(2026-08-24 改訂)。**撤去後は既存 schedule の `active: false → true` も直接反映される** — それが撤去の目的そのものである |

## 7. 代わりに何も置かない

**置かない。**

当初この節には「schedule を追加するとき、Coordinator は押していただく前に次回の起動時刻を必ず伝える」と書いていた。**Yoshinobu が撤回させた(2026-08-24)。**

> **なんとなくリスクがあるから、そのリスクが顕在化する可能性を考えずに仕組みだけは作る。** これは俺が一番嫌いなパターンだ。**守れないのは許す** — そういう時もある。**だけど、到底守れないのに意味なく仕組みを作り込むのは許せない。**

**撤去する機構と、同じ穴から出ていた。** 「登録した直後に発火する」が実際に起きたことは一度も無く、今回も16日先だった。**顕在化の可能性を測らないまま、置き換えを用意しようとした。**

**加えて「Coordinator が毎回言う」は、Coordinator が破ろうと思えば破れる。** 自分で破れる対策は対策ではない。

**実際に「登録直後に発火した」が起きたときに考える。** それまでは何も置かない。

## 7.1 2段構造(順序保証)も撤去した — その実測(2026-08-24)

**独立レビューが「2段構造は明示許可ゲートだけでなく、`task_params` を検証してから有効化する順序保証でもある。その喪失は未承認だ」と指摘した。** 旧 R8-3 の理屈は、**Semaphore API が `task_params` の未知キーを捨てても同じ payload の `active: true` は受理しうるため、同居させると検証が失敗した時点で既に走り出している**、というものである。

**Coordinator が実データで測り、この環境では成立しないと判断した。Yoshinobu が承認した。**

| 測ったもの | 結果 |
|---|---|
| カタログ21件の `task_params` | **18件が空(`{}`)。** 本案件で追加した Semaphore update check も空 |
| `dry_run: "true"` を持つ2件 | **未指定で fail-closed。** `playbooks/prometheus_update_check.yml` 冒頭に「**未指定は意図しない自動upgradeを防ぐため fail-closed**」と明記。落ちても**止まるだけで、勝手に適用されない** |
| `force_renew: "false"` を持つ1件 | role の既定値も `false`。落ちても挙動が変わらない |

**「破壊的な適用が、誤った引数で静かに走り出す」経路が存在しない。** 落ちる値が無いか、落ちれば止まるかのどちらかである。

**旧 R8-3 が観測に基づくかも探した。** `semaphore_schedules_as_code` の案件記録を辿った範囲では、**API が未知キーを捨てたという観測の記録は見つからなかった** — レビュー往復の中で決まった設計判断に見える。**「無い」と断定はしない**(探した範囲の話である)。

**この節が無いと、次に読む人は「なぜ順序保証まで捨てたのか」を再構成できない。** 撤去の理由が「煩雑だったから」だけに見え、**測ったうえで捨てたことが残らない。**

## 8. 過去の決定との関係

**この機構は `semaphore_schedules_as_code` 案件の R12 条件③ / R15 として作られた。** 本案件はそれを取り消す。

**当時の案件記録は履歴として残す**(消さない)。ただし **`docs/ai/memory/decisions/rejected-proposals.md` へ「有効化ゲートを再び作らない」を記録する** — 同じ発想が再び出たときに止めるため。
