# Code Review: Semaphore schedule activation gate removal

Reviewer: Codex / 2026-08-24  
Verdict: **Request Changes**

## Summary

実行コード上の旧gate、2段task、旧report key、旧変数・filterは撤去され、`new / changed / unchanged` の3分類、カタログ`active`の直接反映、`active: false`による既存scheduleの無効化、check-mode境界は成立している。67件のfilter test、6件のtask-flow test、syntax checkもすべて通った。

ただし、撤去した2段構造とcanonical URLには、「実行ごとの明示許可」とは独立した安全目的があった。現requirementはそれらもR1へ一括している一方、決定理由は登録直後の発火と人の追加操作だけを扱い、別の安全保証を失う判断を記録していない。またliveのrestore手順とplaybookコメントに撤去前の境界が残る。したがって、このままTesterへ渡さず、Yoshinobuの判断境界とlive文書を揃える必要がある。

## Removal / Behavior Check

- `semaphore_schedules_allow_activation`、`semaphore_schedules_canonical_api_base_url`、`semaphore_schedules_activation_gate`、`semaphore_schedules_stage2_precheck`と旧outcome factはlive実行コードから消えている。残るrole/test内の旧語は撤去を説明するコメントだけである。
- 旧stage1/stage2の4 taskファイルと`test_activation_gate.py`は削除され、mainのimportは単一の`schedules_apply.yml`へ置換されている。到達しない旧filter entry/import/helperも無い。
- report JSONは`diff.new / changed / unchanged_count`と`outcome.created / updated / update_skipped`だけで、`pending_activation`、`created_pending_activation`、`stage1_*`、`stage2_activated`、`activation_gate`は無い。AC5の実装面はPASS。
- `active`はpreflightでnative boolを要求され、`desired()`がその値を反映する。新規`active:true`、新規`active:false`、既存`true→false`、既存`false→true`、全一致の各filter分岐をunit testが実行している。
- 既存5フィールドが全一致なら`unchanged`へ入り、apply loopは`new`と`changed`だけなので書込みは出ない。これによりAC2の論理は成立するが、実API上の21件が現在も一致することはTester確認が必要である。
- fresh GET、identity drift、get-then-merge、post-write managed/non-managed verify、closed-world、timezone、report失敗の再送出、check-mode外側gateは撤去に巻き込まれていない。
- 追加された警告・承認フラグ・発火時刻確認等の代替機構は無い。System Contextの外部バッチ表更新義務はcron衝突管理の既存一般則であり、今回撤去した有効化gateの代替ではない。

## Canonical URL Judgment

機械的な「唯一のconsumerだったか」は実装記録どおりで、旧worktreeではdiff previewとstage2 authoritative評価の2箇所が同じactivation filterへ渡していただけである。しかしR2が問う「独立した目的」はconsumer graphではなく守る境界で判断すべきである。旧R15は明示許可条件と接続先allowlist条件を別々に定義し、API接続先だけを切り替えられる構造でansyを保護していた。

現コードで`false → true`自体は消えず、特別扱いされなくなっただけである。したがって「独立した目的は無かった」は支持できない。接続先境界も意図して撤去する判断は成立し得るが、現在の「行為そのものが無くなるから目的も消える」という根拠では成立しない。

## What Looks Good

- `active:false`は他の管理項目と同じ`changed`経路でPUTされ、撤去前から必要だった無効化を壊していない。
- diffとreportのschemaは同時に縮み、旧keyを参照する未定義変数経路がない。
- apply前のfresh identity確認と、書込み後のmanaged/non-managed検証は単一段へ正しく移植されている。
- canonical変数に独立した旧consumerが無かったこと、現在21件一致ならwrite 0となることのコード説明は現物と一致する。
- Coordinatorが直したcode-delivery Contextの`active`直接反映と過去実測の過去形化は概ね正しい。Finding 3の別live文書とSuggestion 2を除き、4条件gateと`pending_activation`の現在形は除去されている。

## Verdict

**Request Changes** — 機能残骸の大半は正しく撤去され、直接反映・無効化・report・check-modeも成立する。しかし、接続先allowlistとverify-before-activationという独立した安全目的まで同時に失う判断が正本に記録されておらず、live restore手順も現実と逆である。Yoshinobuの判断境界を明記し、live文書の撤去漏れとrequirementの判定不能な文言を直してから再レビューすること。
