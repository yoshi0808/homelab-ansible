# 記録: 月次の併記行を「上げるべき更新」と読み違えた

日付: 2026-09-03
対象: 本案件が確定した設計(週次=系統内のみ / 月次=全体の最新を併記)
結果: **機構に欠陥は無い。読み手(Coordinator)の誤りである。**

## 何が起きたか

2026-09-03、monnie の月次 full-upgrade の report に次の行があった。

```
non-apt update available: prometheus 3.13.2 → 3.14.0
```

**Coordinator はこれを「未適用の更新」と読み、apply を勧めた。** Yoshinobu は recovery mute を120分張り、`UN-SAFE: Prometheus update (Manual)` を `dry_run=false` で実行した(ジョブ #940)。

**結果は `changed=0` / `status: up_to_date` である。**

```
"track": "3.13",  "track_latest": "3.13.2",  "target": "3.13.2",
"result": "3.13.2",  "overall_latest": "3.14.0"
```

**機構は設計どおりに動いた。** 上げなかったことが正解である。

## なぜ誤りか

**2026-08-22、Yoshinobu は 3.13 LTS に留まると決定している。** `3.14.0` は通常の機能リリースであり、上げることは LTS から降りることを意味する(requirement §1)。

**月次が全体の最新を併記するのは、当初の R4 を撤回して置き換えた安全網である**(requirement §8)。「系統ごと世界に置いていかれた」ことを可視化するための行であって、行動を促す行ではない。**週次が系統内だけを見て静かなことと対になっている。**

Coordinator は**この決定を確認せずに**推奨した。`docs/ai/reviews/prometheus_lts_track/` も `rejected-proposals.md` も読んでいない。

## 費やしたもの

- 監視の停止(recovery mute 120分)
- 何も変えないジョブの実行1回(#940、20秒)

**本番への影響は無い。** トランザクションは `up_to_date` で早期に終わり、バックアップも切り替えも発生していない。

## 設計へのひとこと(提案であって欠陥指摘ではない)

併記行は現在 `non-apt update available: prometheus 3.13.2 → 3.14.0` とだけ出る。**「系統外」であることが行の中に無い。** 決定を知らない読み手には、更新すべき対象と区別が付かない。

**同じ誤読は次の読み手にも起こりうる。** 直すなら、併記行に系統の情報(例: 運用系統は 3.13、これは系統外)を含める形が考えられる。**ただし機構は現状で設計どおりであり、変えるかどうかは運用上の判断である。**
