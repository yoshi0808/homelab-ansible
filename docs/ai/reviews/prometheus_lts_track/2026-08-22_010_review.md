# review: prometheus の運用 track 対応（Tester検出バグ修正）

Reviewer: Codex / 2026-08-23  
対象: `2026-08-22_009_test_result.md`後の修正、根本原因、scope外7箇所、回帰guard  
Verdict: **Request Changes**

## Summary

`roles/prometheus_update_check/tasks/main.yml`の修正2箇所で使う`\g<1>`は妥当であり、実タスクを抽出して実`ansible-playbook`で評価した結果、target/trackのassertとinstalled/trackのmismatch判定はいずれも意図どおりに動いた。

根本原因については、Implementerの「`{{ }}`とbare conditionalでAnsibleのbackslash処理が異なる」という中核判断を支持する。Coordinatorの二重引用符YAMLによる再現不成立はこの判断を反証しない。ただし、実装記録はこの規則をYAML scalarとJinja tagの差を無視して一般化し、正常なscope外7箇所を壊れていると誤判定している。また、追加された回帰guardはbare conditionalしか通らず、今回実際に壊れていた`{{ }}`-templated `set_fact`経路を固定していない。

## Findings

### 1. Medium — 根本原因の一般化により、元assertとscope外7箇所を誤って「壊れている」と記録している

対象:

- `docs/ai/reviews/prometheus_lts_track/2026-08-22_002_implement.md:117-128`
- `docs/ai/reviews/prometheus_lts_track/2026-08-22_002_implement.md:186`

実装記録117行は、旧`'\\1'`が2箇所とも後方参照として機能しなかったと現在形で述べる。しかし実測と同記録128行の訂正どおり、旧assertのbare conditionalでは`'\\1'`が正しく、実際に壊れていたのは`{{ }}`で評価される`track_installed_mismatch`の`set_fact`側だけだった。117行と128行は相互に矛盾する。

さらに186行が壊れているとするscope外7箇所を、元ファイルから`yaml.safe_load`でtask単位に抽出し、fixtureとともに実`ansible.builtin.set_fact`で評価した。結果は全件正常だった。

| 箇所 | 実行結果 |
|---|---|
| `proxmox_hw_check/tasks/main.yml:67-69` | `NIC eno1 is DOWN`、`NIC eno2 error rate exceeds threshold`、`NIC eno3 drop rate exceeds threshold` |
| `proxmox_healthcheck/tasks/main.yml:54,74,77` | `ZFS pool degraded/faulted: tank`、`replication stale (>24h): job-critical`、`replication stale (>2h): job-warning` |
| `proxmox_hw_check/tasks/main.yml:172` | summary中に`nic_state=NG[eno1=DOWN]` |

前半6箇所は外側がYAML二重引用符なので、YAML parserがソース上の`\\1`をJinjaへ渡す前に`\1`へする。その後、Ansibleの`{{ }}`向けpre-escapeを経て正しいbackreferenceになる。172行はブロックスカラーだが、式は`{{ }}`ではなく`{% set %}`内にあり、Ansibleのvariable-tag専用pre-escape対象ではないため、ソース上の`\\1`で正しく動く。

したがって、scope外7箇所を別案件の不具合として起票すべきではない。実装記録は、旧assertが正常だった事実と7箇所の実測結果に合わせて訂正する必要がある。

### 2. Medium — 回帰guardが、今回実際に壊れた`set_fact`評価経路を検査していない

対象: `roles/prometheus_update_check/tasks/main.yml:53-98`

guardの2条件はいずれも`ansible.builtin.assert.that`のbare conditionalとして評価される。コメント自身も79行でbare-conditional経路だけを通すと述べている。今回の旧`'\\1'`はbare assertでは正常で、`{{ }}`-templated `set_fact`だけを壊していたため、このguardは元の故障クラスの肝である評価経路を再現していない。

またguardはproductionの2式とは別のリテラルを複製している。たとえば247行のproduction replacementだけを旧`'\\1'`へ戻しても、guard側の`\g<1>`は変わらずPASSする。2つ目の「3.14.0の結果が3.13ではない」条件も、置換結果がリテラルbackreferenceへ壊れた場合にPASSするため、負例として故障検出力が弱い。

少なくとも`{{ }}`-templated `set_fact`でcanary結果を生成し、後続assertで期待値を検査する経路を含める必要がある。コメント、fail message、実装記録132行の「回帰を固定した」という主張も、実際に監視する範囲へ揃えるべきである。

## Root-cause Judgment

ansible-core 2.20.1の現物では、`ansible/_internal/_templating/_jinja_bits.py`が`{{ }}`の`TOKEN_VARIABLE_BEGIN`〜`TOKEN_VARIABLE_END`内にある文字列tokenだけをpre-escapeする。一方、`ansible/_internal/_templating/_engine.py`はconditional評価時に、後方互換のため明示的に`escape_backslashes=False`としている。よって、同じYAML解析後文字列でも`{{ }}`とbare conditionalの結果が異なるというImplementerの中核診断は正しい。

ただし最終結果は次の3層で決まるため、「set_factなら常に1本、assertなら常に2本」という一般則にはできない。

1. YAML scalarの形式がJinjaへ渡すbackslash本数を変える。
2. Jinja tagが`{{ }}`か`{% %}`かでAnsible pre-escapeの対象が変わる。
3. bare conditionalではpre-escapeが無効になる。

実モジュールで得た最小行列は次のとおり。

| YAML解析後のbackslash数 / 評価経路 | 結果 |
|---|---|
| 2文字 / block scalarの`{{ }}` | リテラル`\1`（不正） |
| 1文字 / block scalarの`{{ }}` | capture展開（正常） |
| 2文字 / bare conditional | capture展開（正常） |
| 2文字 / `{% set %}` | capture展開（正常） |
| `\g<1>` / 今回のbareと`{{ }}` | capture展開（正常） |

Coordinatorが試したYAML二重引用符の`\\1`は、第1層で1本へ縮んだ後に`{{ }}` pre-escapeを受けるため正常になる。これはImplementerの中核診断と両立する。
