## Requested Checks

### M3: recovery path

- defaults の `default('3.13')` は `true` 引数を持たないため、明示した空文字を既定値へ戻さず `prometheus_update_check_track == ''` にする。
- input assert は空 track なら target/track major.minor 一致条件を短絡し、`track_installed_mismatch` も `track | length > 0` が偽なので成立しない。
- 空 track は `track_gate_ok=true`。明示 target は `effective_target_version` となり、current と異なれば `upgrade_wanted=true`。`dry_run=false` かつ native check mode でなければ 352-361 行の destructive include へ到達する。
- `upgrade.yml` の archive 名、checksum URL、download URL、展開元、post-verify はすべて `prometheus_update_check_effective_target_version` を参照し、途中で configured track に戻らない。
- ただし空 track 経路は従来どおり `releases/latest` の取得・parse 成功も要求する。したがって案内は remote collection が正常な run では実行可能だが、mismatch と同時に `releases/latest` 障害が起きている run では target pin があっても `collection_failed` になる。これは今回の M4 が明示した空-track fallback 境界と一致し、mutation を誤って通す問題ではない。

### M4: collection relaxation and fallback

- configured track では `remote_collected = track_collected` となり、`releases/latest` の status / parse は判定を止めない。track が空のときだけ latest の HTTP 200 と semver を追加要求する。
- track found なら comparison basis は常に track latest であり、壊れた overall latest へ落ちない。
- track not found かつ latest 不正時の installed-version fallback は `is version(current, '>')` の例外を避けるための no-op 値である。このとき `track_gate_ok=false`、`upgrade_wanted=false`、Status=`track_not_found`、通知後に final fail となる。
- track collection failureでも `track_found=false` なので同じ gate が閉じ、Status=`collection_failed`。空 track で latest failure の場合も `collected=false` で apply へ進まない。判定不能を `up_to_date` として正常終了させる経路はない。

### UV-088 notification boundary

- `track_installed_mismatch` が出す具体版は current installed version だけであり、GitHub の overall latest / track latest は出さない。configured track と placeholder `X.Y.Z` は診断・操作書式であって、取得した系統外候補ではない。
- `track_not_found` は configured track と current を出す。この Status に到達するには installed の major.minor が configured track と一致しているため、current は系統外版ではない。
- `collection_failed` は mismatch より後順位なので、configured track 時に具体的な系統外 installed versionをこの分岐へ流さない。
- 以上から通知コードは改訂後 UV-088 には一致する。Finding 1 はコードの追加漏れではなく、requirement が同じ承認境界へ更新されていない問題である。
