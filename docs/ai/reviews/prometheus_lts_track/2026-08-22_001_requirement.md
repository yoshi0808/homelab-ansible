# requirement: prometheus の更新検知を、実際に運用している系統に対して行う

起案: Coordinator / 2026-08-22 / 依頼者: Yoshinobu

## 1. 問題定義

**prometheus の更新検知が2つ並存し、どちらも運用していない系統を指している。**

| 機構 | 比較先 | 頻度 | 適用・切り戻し |
|---|---|---|---|
| `roles/prometheus_update_check/` | `releases/latest` | 週次(金 17:05) | **持つ**(apply / rollback テンプレート、バックアップ3世代) |
| `roles/ubuntu_vm_full_upgrade/` の非aptレジストリ | `releases/latest` | 月次 | 持たない。**Status を `REVIEW_REQUIRED` へ上げる**(`UV-032`) |

**2026-08-22、Yoshinobu は 3.13 LTS に留まると決定した**(`docs/ai/memory/decisions/rejected-proposals.md`)。3.13.0 が LTS、現在の 3.13.2 はその最新パッチである。**3.14.0 は通常の機能リリースであり、上げることは「LTS から降りる」ことになる。**

しかし **`releases/latest` に LTS という概念は無い。** その結果、

1. **週次も月次も、当面ずっと「更新あり」と言い続ける。** 3.15、3.16 が出れば、そのたび指す先が変わるだけで状態は同じ
2. **monnie の月次 Status は、apt 側に何もなくても毎月 `REVIEW_REQUIRED` になる。** 「人間が見るべき」という信号が常時点灯し、**本当に効くべきときに効かなくなる**
3. **上げてよい版が来たときに、人が判断材料を集め直さないと押せない。** 「毎月無視する」を選ぶと、次に本当に上げるべき 3.13.3 も同じ扱いで流れる

**同じ判断(更新があるか)を2箇所が別々に実装している**点は `docs/ai/core.md`「値を二重に持たない」に触れる。

## 2. ゴール

- **運用している系統の中でだけ更新を検知する。** 3.13.3 が出たときに鳴り、3.14 系では鳴らない
- **更新の有無を判定する機構を1つにする。** 判定できる側(適用と切り戻しを持つ側)が判定する
- **系統から取り残されたことが見える。** 手で持つ値である以上、EOL を過ぎても静かなままにならないこと

## 3. 非ゴール

- **LTS かどうかを機械に判定させない。** GitHub の release に LTS のフラグは無く、判定材料は本文中の自由文か docs ページだけである。**自由文の解析に依存する検知は作らない**(2026-08-22 の conffile 案件で同じ理由により方式ごと退けている)
- **自動適用を作らない。** 検知までを自動、適用は手動という既存の方針(Yoshinobu、2026-08-10)を変えない
- **非apt レジストリの機構そのものを撤去しない。** prometheus は登録の第1号であり、外すと機構全体が一度も動かなくなる

## 4. 要求

| # | 要求 |
|---|---|
| R1 | `prometheus_update_check` に**系統を指定する値**を設ける。**既定値は repo に `3.13` を置く。** `-e prometheus_track=<系統>` で上書きでき、**空文字なら従来どおり系統を絞らない** |
| R2 | **検知と適用の両方が同じ値を見る。** 系統を指定した状態で apply したとき、系統外の版が入らないこと |
| R3 | **既定値の置き場は1箇所だけにする。** Semaphore の schedule 側に持たせない — 次の LTS が出たときに直す場所が2つになるため |
| R4 | **週次の通知は、指定された系統の中だけを扱う。上流から取得した系統外の版を出さない。****ただし、検知の対象が系統の外にあることを伝えるときは、いま入っている版を示してよい**(2026-08-23、`UV-088` の改訂に合わせて追記)。(2026-08-22 改訂。当初は「全体の最新」の併記を求めていたが、**それは機械が系統の外を見て人へ差し出す形**であり、§8 の軸に反する。系統が古びたことは月次のアップグレードレーンが示す) |
| R5 | **月次の非aptレジストリは、版を出すが Status を上げない。** 判断は週次の専用 role に一本化する。`UV-032` の改訂を伴う(§6) |
| R6 | **系統が見つからないときに黙らない。** 指定した系統に1件も release が無い場合(綴り誤り、EOL 後の削除)を、更新なしと区別できる形にする |

## 6. Policy 改訂(2026-08-23、Yoshinobu 承認のうえ反映済み)

**改訂前の `UV-032`**

> 両方の取得成功と数値比較によりupdateありが確定した場合だけ、Statusを最低`REVIEW_REQUIRED`へ昇格し、reasonを追加する。

**改訂後(現行)**

> 両方の取得成功と数値比較によりupdateありが確定した場合、reasonを追加する。**Statusは昇格させない**(UV-094)。apt以外のプロダクトのアップグレードの採否は人が決めるものであり(UV-087)、monthlyの判定は事実の提示に留める。

**改訂の理由**: 昇格は「人間が見るべき」という信号だが、**非apt側にはそれを判断する専用機構が別にあり、そちらは適用と切り戻しまで持つ**。月次が同じことを毎月言い続けると、信号の意味が失われる。**退けているのは昇格の当否ではなく、判断を2箇所に置くこと**である。

`UV-033`(既存の `BLOCKED` / `MAJOR_UPGRADE_DETECTED` を非apt結果で降格させない)は**変更しない**。

## 7. 手で持つ値であることの帰結

**系統は人が設定する。** 次の LTS が出たら1箇所を書き換える。これは推測を排して「どの系統に乗っているか」を明示された値にするための選択であり、欠落ではない。

**ただし、手動値には固有の壊れ方がある** — 3.13 が EOL を迎えても週次の検知は静かなままで、**「更新なし」と「系統ごと見捨てられた」が同じ見え方になる**。**これは月次のアップグレードレーンが塞ぐ** — monthly の判定が系統外の最新を出し続けるため、そこで乖離が見える。**週次に系統外を持ち込まない**(§8、R4改訂)。


## 8. アップデートとアップグレードの軸(2026-08-22、Yoshinobu)

**本案件の位置づけは、この軸で決まる。**

| | **アップデート(週次)** | **アップグレード(月次)** |
|---|---|---|
| 動くもの | 系統内のリビジョン・シリアル番号 | バージョン(系統を跨ぐ) |
| aptの担い手 | Ubuntu Pro / unattended-upgrades が当てる。**その対象外は monthly full-upgrade へ回る**(`UV-018`) | monthly full-upgrade |
| apt以外の担い手 | 週次に機械が検知する(`UV-035`〜`UV-038`) | monthly の判定で提示する |
| 機械の役割 | 検知する。**適用は、Ubuntu Pro / unattended-upgradesの対象なら機械が当て、それ以外は人が `dry_run=false` を明示する**(`UV-035`〜`UV-038`) | **検知して人へ出すまで。判断と版の指定は人** |

**aptはこの2つのレーンに跨がる**(`UV-085`)。Ubuntu Pro / unattended-upgrades が当てない通常更新は monthly へ回るため、apt側は周期だけでレーンを決められない。

**本案件が触るのは週次(アップデート)のレーンだけである。** 系統を移すこと=アップグレードは人が版を指定して行う。**機械は月次の判定で候補を検知して提示するが、採否を判定せず、版も指定しない**(`UV-087`)。

**この軸により、当初 R4 が塞ごうとしていた穴は塞ぐ必要が無くなった。** 「系統が EOL を迎えても静かなまま」は、**月次のアップグレードレーンが系統外の最新を出し続ける**ことで見える。週次に系統外を持ち込むと、消したかったノイズを別の場所へ作り直すことになる。

**同じ理由で、月次の非apt行は消すべきものではない。** 誤っていたのは Status を昇格させていたこと(人が決めることを機械が判定していた)だけであり、事実の提示そのものはアップグレードレーンの仕事である。
