### 2. Medium — 実装記録冒頭に「旧2箇所とも壊れていた」という撤回済みの原因説明が残る

## Root-cause Verification

ansible-core 2.20.1の実`set_fact` / `assert` / `when`で独立に得た結果:

| YAML / 評価経路 | 結果 |
|---|---|
| 二重引用符scalarにソース2本の`\\1` / `{{ }}` set_fact | YAML後1本、結果`3.13`（正常） |
| folded scalarに2本 / `{{ }}` set_fact | 結果リテラル`\1`（不正） |
| folded scalarに1本 / `{{ }}` set_fact | 結果`3.13`（正常） |
| plain scalarに2本 / bare assert | PASS |
| 二重引用符scalarにソース2本 / bare assert | YAML後1本、FAIL |
| plain scalarに2本 / `when` | task実行 |
| 二重引用符scalarにソース2本 / `when` | YAML後1本、task skip |

これにより、(a) YAML二重引用符がJinja/Ansible templating前の実効backslash数を変えることと、(b) 同じpost-parse内容でも`{{ }}`とbare conditionalで結果が変わることの双方を確認した。Coordinator説・Implementer初期説のどちらか一方だけでは全行列を説明できない、という更新後の結論は正しい。

より厳密には(b)はJinja一般の性質ではなく、ansible-coreのtemplating layerの挙動である。現物の`ansible/_internal/_templating/_jinja_bits.py`は`{{ }}`のstring tokenだけをpre-escapeし、`_engine.py`はconditionalで後方互換のため`escape_backslashes=False`にする。実装記録124行の「Jinja側」という表現は、将来の一般則として残すなら「AnsibleのJinja templating layer」へ寄せると誤解が少ない。
