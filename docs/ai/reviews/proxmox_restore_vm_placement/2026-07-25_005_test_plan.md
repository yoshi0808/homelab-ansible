## 3. カバレッジ戦略

### 3.1 Unit / static

承認後、Actualより先に以下を実行する。

```bash
scripts/check-tester-gate.sh
ansible-playbook -i inventories/homelab/hosts.yml \
  playbooks/proxmox_restore_vm_placement.yml \
  -e target_node=pve2 \
  --syntax-check
git diff --check
```

合格条件:

- tester-gate lintが全playbookを受理する。
- inventoryを明示したsyntax checkが成功する。
- whitespace errorがない。
- markerは`check-mode-native`のままである。
- `target_node` allowlistは`pve1` / `pve2`だけである。
- recovery actionの実行構文は0で、手動案内文字列だけが残る。

静的検査が失敗した場合はActualへ進まず、結果をTech Leadへ返す。

### 3.2 Integration: Actual check

#### Exact command

```bash
scripts/safe-ansible-check.sh \
  playbooks/proxmox_restore_vm_placement.yml \
  -i inventories/homelab/hosts.yml \
  -e target_node=pve2 \
  --check
```

`--limit`は付けない。localhost playの`target_node`検証を実行した後、第二playの
`hosts: "{{ target_node }}"`を`pve2`だけへ解決する。`pve1`は対象にしない。
`--diff`はruntime reportに実行時のguest識別情報が現れる可能性を避けるため付けない。

#### 許容する副作用

- localhostでの入力assertと外部gate設定assert。
- pve2へのAnsible接続、facts収集、`pvesh get /cluster/resources`によるread-onlyな
  VM / CT識別。
- Ansible transportに必要な一時module stagingと通常の自動cleanup。
- controller側の`reports/proxmox-restore/` directory確認・作成と、
  `*_pve2_restore.json` 1件の書込み。reportは`.gitignore`対象である。
- stdout / stderr / Ansible recapの生成。

許容しない副作用を検出した場合は失敗とする。

#### check modeで実行されるべき項目

- localhostの`target_node` validation。
- recovery mute tasksのskip判定。
- pve2のfacts収集。
- 外部gate defaultsのvalidation。
- result facts初期化。
- controller report directoryの確認。
- `Get cluster resources`、parse、non-HA VM / CT識別、restore plan表示。
- plan-only fact設定。
- alwaysのcontroller report保存。

#### 親not-check destructive blockによりskipされるべき項目

- non-HA VM / CT migration。
- migration後のwait、再収集、停止guestのstart。
- maintenance mode解除と待機。
- HA guestのrelocateと復帰待ち。
- 新gateのhelper copy、helper実行、HTTP HEAD、JSON parse / validation、helper remove、
  到達性fail判定。
- post-restore healthcheck。

新gateのhelper removeも親block内なのでcheck modeではskipされる。helper copy自体が
skipされるため、今回実行に由来するhelper artifactは存在せず、target node側の追加cleanupは
不要である。

#### report合格条件

生成されたcontroller reportを、実行時識別情報を転記せずに確認する。

- `result == "PLAN_ONLY"`
- `external_reachability_status == "NOT_RUN"`
- `external_probe_attempts == 0`
- `external_probe_elapsed_seconds == 0`
- `maintenance_disabled == false`
- `vms_migrated_back == []`
- `vms_started == []`
- `post_healthcheck_status == "UNKNOWN"`
- `error_msg == ""`

### 3.3 E2E / apply / post-healthcheck

本Tester工程では実施しない。通常実行はVM移動、maintenance変更、relocate、start、
外部HTTP、healthcheckを伴うcontrolled applyであり、今回の許可範囲外である。

## 4. 通知とrecovery境界

- playbookは第二playで`skip_notifications: "{{ ansible_check_mode }}"`を設定する。
- recovery mute 3件は`when: not ansible_check_mode`によりskipされる。
- post-restore healthcheck自体が親not-check block内でskipされるため、
  `common_slack`通知経路へ到達しない。
- `recovery_vm_reboot.yml`をinclude / import / command実行しない。
- Actual logにrecovery action taskがなく、recovery action実行数0であることを確認する。
- 手動recovery案内は外部到達失敗用message内の文字列であり、check modeではそのfail taskも
  skipされる。

## 5. 停止条件

次のいずれかで即停止し、別host・通常実行・再試行へ進まない。

- Tech Leadのcommand承認がない。
- 静的検査が失敗する、または承認後にdiff / scopeが変わる。
- pve2がUNREACHABLE、SSH / become / setup / `pvesh`で失敗する。
- 実行対象にpve1または想定外hostが含まれる。
- recovery mute、destructive block、新gate、外部HTTP、healthcheck、migration、
  maintenance、relocate、startのいずれかが実行される。
- controller reportが保存されない、またはreport値が合格条件と異なる。
- recovery actionが1件でも実行される。
- 秘密情報または実行時guest識別情報を成果物へ転記する必要が生じる。

pve2到達不能時はpve1へ切り替えず、`NOT RUN / BLOCKED`としてTech Leadへ返す。
