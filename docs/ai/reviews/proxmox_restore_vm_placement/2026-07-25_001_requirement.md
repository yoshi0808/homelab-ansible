# 要求仕様: proxmox_restore_vm_placementへの外部到達性確認ゲート追加

## 1. 問題定義

`roles/proxmox_restore_vm_placement/tasks/main.yml`は、HA VMのrelocate完了を「Wait for HA-managed VMs to return to target node」(230-255行目)で確認しているが、これは`pvesh get /cluster/resources`が返す**Proxmoxの`status`フィールド(running/stopped)だけ**を見ている。VMプロセスが起動すればすぐに`running`になるため、対象VMがSophos Firewallの場合、ゲストOS/firewallソフトウェア自体が起動を終えて実際にルーティングを再開したかどうかは全く確認していない。

この直後(261行目)に`proxmox_healthcheck`(→`common_slack`によるSlack通知)が無条件で実行されるため、Sophos再起動中のネットワーク断とタイミングが重なると、`common_slack`のSlack webhook POSTがDNS解決エラーで失敗する。2026-07-24・2026-07-25の2日連続で観測済み(いずれも約3分11〜12秒の断)。下書き記録: `docs/ai/memory/temporary/2026-07-24_proxmox_restore_slack_notify_network_timing_draft.md`。

対照として`roles/recovery_probe/files/recovery-probe.py`の`external_reachable()`(HTTP HEADによる実際の外部疎通確認)は、この種の断を正しく検知し、疎通回復後まで通知を遅延させるqueue+flush設計を持つ。ただしこれは`recovery-probe.service`という独立監視プロセスの話であり、`proxmox_restore_vm_placement`自体には同種のチェックが存在しない。

## 2. ゴール

`proxmox_restore_vm_placement`のHA VM復帰確認(Proxmox `status`レベル)と、post-restore healthcheck+Slack通知の間に、**実際の外部到達性を確認するゲート**を追加する。疎通が確認できない場合は、healthcheckへ進まず、明確な理由とともに失敗として停止する。

## 3. 非ゴール

- `recovery_vm_reboot.yml`等の自律復旧action呼び出しをこのplaybookから行わない。`docs/ai/policies/autonomous_recovery_policy.md` §5「共通の経路分離」(AR-008)とAR-083「manual layerは人間の判断責任で直接起動できる」により、自動playbookからの無人呼び出しはPull/Push/Manualいずれの経路にも該当せず、現行Policyでは無権限の第4経路になる(2026-07-25、Yoshinobu・claude間で確認・合意済み)。疎通確認が失敗した場合、エラーメッセージで`recovery_vm_reboot.yml -e target=sophos-fw`の手動実行を案内するだけに留める。
- `docs/ai/policies/autonomous_recovery_policy.md`の改訂は行わない。
- Slack通知の仕組み自体(`common_slack`、`recovery-probe.py`)の変更は行わない。
- `proxmox_evacuate_node.yml`等、他のPlaybookへの同種チェック追加は別依頼とする。

## 4. 要件(MoSCoW)

**P0(Must)**:
- `roles/proxmox_restore_vm_placement/tasks/main.yml`の230-255行目(HA VM復帰待ち)と261行目(healthcheck実行)の間に、新しいタスク「外部到達性の確認」を追加する。
  - チェック方法は`roles/recovery_probe/files/recovery-probe.py`の`external_reachable()`と同種(HTTP HEADリクエスト、タイムアウト数秒、HTTPErrorも到達性ありとみなす)。`target_node`上で実行する(そのノード自身がSophos経由でインターネットに出る経路を直接検証するため)。
  - リトライ間隔・タイムアウトはrole defaultsで設定可能にする(既存の`proxmox_restore_ha_timeout`等と同じ形式)。初期値は15秒間隔・5分程度のタイムアウトを目安とする(実測データ: 2日とも約3分11〜12秒の断)。
  - 既存のblock全体(86-88行目、`when: not ansible_check_mode`、`tags: [destructive]`)の中に置き、check-mode時の扱いは周囲のタスクと同じにする(特別扱い不要)。
- 疎通確認が失敗(リトライを使い切る)した場合:
  - `proxmox_healthcheck`(261行目)を実行しない。
  - 失敗理由を「HA復帰は確認できたが、Sophos経由の外部到達性が確認できなかった」ことが明確に分かるメッセージにする(既存の`ansible_failed_result.msg`をそのまま使う汎用メッセージにしない)。
  - メッセージ内で`recovery_vm_reboot.yml -e target=sophos-fw`の手動実行を案内する。
  - 既存の`rescue`/`always`構造(`_restore_failed`、JSON report保存、再raise)はそのまま活用する。

**P1(Should)**:
- 疎通確認成功時は、待機に要した時間を記録・reportへ含める(将来のタイムアウト調整の参考データにする)。

## 6. 受入条件(Given/When/Then)

- Given HA VM復帰確認(Proxmox status)が成功した状態で、When 外部到達性が即座に確認できる場合、Then 通常通りhealthcheckへ進み、これまでと同じ結果になる。
- Given HA VM復帰確認が成功したが外部到達性がまだ回復していない状態で、When リトライ内に疎通が回復した場合、Then healthcheckへ進み成功する(疎通回復まで待った上で継続)。
- Given 外部到達性がリトライを使い切っても回復しない状態で、When タイムアウトしたとき、Then healthcheckへ進まず、Sophos到達性を理由とする明確なメッセージで失敗し、`recovery_vm_reboot.yml`の手動実行案内を含む。
- Given 修正後のコードが存在する状態で、When `git diff`を確認したとき、Then `roles/proxmox_restore_vm_placement/`以外に意図しない変更がない。
