# 委任Tier判定の2軸化: レビュー指摘の修正

- 日付: 2026-07-26
- 担当: Coordinator(実装者)
- 工程: `1+R`(単一〜少数ファイル・runtime影響なし + 複数正本にまたがる責任分界の再配置のためReviewer付加)
- レビュー: `001_review.md`(1巡目)、`002_review.md`(2巡目)。**両巡ともCritical 4件を検出**

## 改訂の目的

`skills/delegation-tier/SKILL.md`の2つの節が正面から矛盾していた。

- 「引き上げ条件」節: 多ファイル横断・安全境界の再定義・Policy本文の再編は**runtime影響の有無に関わらずTier 4**
- 「Role固有Skillの適合」節: Policy / docのみの変更は**工程を上げずCoordinatorが担う**

2026-07-26の旧core.md退役が両方に該当して判定不能になり、しかも**どちらに従っても誤り**だった(前者=subagent 4本が空振り、後者=規範消失1件と機能中のdangling参照2件をcommitしていた)。実際に機能したのは「Coordinator実装 + Reviewer 1回」で、その形がTier表に存在しなかった。

## 採用した設計

判定を2軸へ分離し、「引き上げ条件」概念は軸Bへ統合して廃止した。

- **軸A**: 実装に専門性・実機検証が要るか → Tier番号
- **軸B**: 取りこぼしが起きても自分では気づけない形か → `+R`(Reviewer付加)
- 軸Bの判別要点: **作業に「対象範囲の選定」が含まれるか**(多ファイル一括変換、規範・正本の移設、複数正本にまたがる規範の再配置)
- `1+R` / `2+R`を新設。Tier 3 / 4はReviewerを内包するため`+R`を付けない

## この工程で得られた知見

- **判定ロジックの欠陥は、そのロジックを使う実案件に当たるまで顕在化しない。** このSkillは2026-07-22に3巡のレビューを通っていたが、今回の矛盾は残存していた。露見したのは実際に両方の節に該当する案件(core.md退役)を判定しようとした時である。
- **矛盾を消すと穴ができる**。1巡目・2巡目とも、Coordinatorの修正が矛盾を解消した代わりに到達不能な分岐を作っていた。分類ラダーを直すときは、矛盾の解消と全域性(totality)の維持を別々に確認する。
- **最良の反例は「今やっている作業自体」である**(2巡目Critical #1)。判定基準を書き換えるときは、その基準で自分の今の作業を判定してみる。
