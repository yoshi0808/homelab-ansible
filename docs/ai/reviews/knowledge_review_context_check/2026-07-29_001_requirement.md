# Requirement: 月次Knowledge振り返りへContext陳腐化チェックを追加する

## 背景・経緯

2026-07-29、Coordinatorの自己レビューでSystem/Operations Context(`docs/ai/context/system/`・`docs/ai/context/operations/`)の要否を検討した(`docs/ai/reviews/process_retrospective/2026-07-29_006_ansible_context_map_retirement.md`)。結論はAnsible地図3ファイル(`inventory-map.md`等)とは異なり有用だが、**Context文書が案件を経由せずに陳腐化する経路は残る**と判断した。対応の方向性は次の2本立てで合意済み(`docs/ai/reviews/process_retrospective/2026-07-29_007_context_doc_maintenance_direction.md`)。

1. 案件が触れる範囲は、実装Stepの一部としてContext更新を組み込む(`docs/ai/roles/coordinator.md`へ反映済み)。
2. **案件が触れない範囲(長期間どの案件からも参照されないContext)の陳腐化は、①だけでは拾えない。** 月次Knowledge振り返り(`ansible-knowledge-review.timer`、既に自律稼働中)へチェックを追加する。本requirementは②を対象とする。

## 対象・非対象

- 対象: `docs/ai/context/system/*.md`、`docs/ai/context/operations/*.md`、`docs/ai/context/ansible/repository-overview.md`の記述内容が、対応する`roles/`・`playbooks/`・`inventories/homelab/`の現物と整合しているかの検査。
- 非対象: Policy(`docs/ai/policies/`)の正否判定(Auditor・本チェックとも技術的正否は判定範囲外という既存原則を維持)。`docs/ai/context/ansible/`配下は地図3ファイル廃止により対象自体が縮小済み(repository-overview.mdのみ)。

## 制約・安全境界(最重要)

無人実行(`claude -p`、systemd timer起動、対話相手なし)の**読み取り範囲拡張**を伴う。現状は`docs/`・`skills/`・auto-memoryのみで、`roles/`・`playbooks/`・`inventories/`は読めない(`docs/ai/memory/lessons/claude-code-unattended-session-confinement.md`の意図的な設計)。

- **拡張してよい範囲(Coordinator提案)**: `roles/`、`playbooks/`、`inventories/homelab/`(`hosts.yml`・`group_vars/`・`host_vars/`)。
- **拡張しない範囲**: `inventories/vars/`。`docs/ai/context/ansible/repository-overview.md`自身が「複数入口から参照する実行変数。秘密を含み得る」と唯一名指ししているパスであり、Context記載内容(node役割、依存関係、運用順序)の検証にこのパスの中身は不要。
- **書込範囲は変更しない**(`docs/ai/memory/`・`docs/ai/context/`・`skills/`のみ、現状維持)。
- **commit/pushはしない**(現状維持)。差分は作業ツリーに残し、Yoshinobuが確認してcommitする。
- **中止条件は既存のまま**(作業ツリーが汚れているとき)を維持する。
- **本番ansyの実タイマーへの反映(実際の`job-settings.json`再生成・configure)は本案件の対象外とする。** 本案件はtemplateの変更・decoy検証までとし、実タイマーへの反映はYoshinobuのcommit後、別途の判断で行う。

## Context陳腐化チェックの検出方法(具体化。計画査読Finding 1で追記)

1. 各Context文書から、明示的に名指しされているrole名・playbook名・host名を拾う(例: `proxmox_healthcheck`、`proxmox_patch_weekly_full.yml`、`pve1`)。
2. 拾った名前が実際に`roles/`・`playbooks/`・`inventories/homelab/hosts.yml`に実在するか確認する。存在しなければ、リネーム・削除された可能性が高く指摘対象とする。
3. 実在するrole/playbookについて、Context文書が述べる「処理順序」「依存関係」「安全上の注意」のうち、対象の`tasks/main.yml`または`defaults/main.yml`の内容から**明確に矛盾すると判断できるものだけ**を指摘する(例: Context文書が「pve2が先」と書いているのに、playbookのtask順が逆になっている、等)。解釈が割れる・断定できないものは指摘しない。
4. 全文の逐語照合は求めない。前回の振り返り以降にauto-memoryや案件記録で言及された形跡があるrole/playbookを優先する。時間内に終わらない範囲は「未確認」として報告し、次回へ持ち越す。

## 受入条件

- AC1: 無人実行の読み取り範囲が`roles/`・`playbooks/`・`inventories/homelab/`まで拡張され、`inventories/vars/`は引き続き読めないことを、decoy環境で実測確認できる。
- AC2: 書込範囲・commit/push禁止・中止条件など、拡張対象外の制約が一切緩んでいないことをdecoy環境で実測確認できる(封じ込めの3条件が引き続き成立する)。
- AC3: 月次振り返りのprompt(`roles/knowledge_review/templates/review-prompt.md.j2`等)に、Context陳腐化チェックの指示が追加されている。チェックは「記録どうしの矛盾」に類する**指摘のみ**を行い、Context文書を無人実行が自動で書き換えることは求めない(書込先の許可はあるが、無人実行に技術的正否の自動修正までは求めない。人間の確認前提を維持するため)。
- AC4: 既存の月次Knowledge振り返り・障害評価の動作(スコープ・出力)に回帰が無いことを確認する。
- AC5: `docs/ai/role-routing-index.md`「無人実行されるCoordinator」表、`docs/ai/memory-classification.md`等、関連する規範文書がすべて新しい読み取り範囲を正しく反映している。

## 非ゴール

- Context文書の自動修正(書込はできるが、無人実行に「直す」判断まで求めない。指摘に留める)。
- Policy文書の陳腐化チェック(Policyは人間の判断領域であり、対象外)。
