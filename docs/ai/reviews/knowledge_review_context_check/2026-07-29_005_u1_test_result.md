1. scratchpad配下に repo と同じ相対パス階層(`roles/`・`playbooks/`・`inventories/homelab/`・`inventories/vars/`・`docs/ai/memory/`・`docs/ai/context/`・`skills/`)を持つ decoy ディレクトリを作成し、`git init`した(値は見ないダミーマーカー文字列のみ)。

3. 本番の実起動コマンド(`roles/knowledge_review/tasks/main.yml`の`argv`)を確認し、フラグを実測条件と一致させた:
   `claude -p --output-format text --model <model> --setting-sources '' --settings job-settings.json --add-dir <automemory>`。
   `--permission-mode`は本番でも指定されていない(未指定=default)ため、今回の検証も未指定で揃えた。
4. 各AC項目を個別prompt(全項目まとめた実行1回、疑わしい結果は単一項目に絞った再実行で追試)で確認した。

## 残存リスク・追加で見つかった問題(FAILの原因分析)

**FAIL(項目2・3)の原因は「pathパターンの迂回」ではなく、そもそも`inventories/vars/`が明示的なdenyルールを持たないこと。**

`job-settings.json.j2`の`deny`は`["Bash", "WebFetch", "WebSearch"]`のみで、`Read(inventories/vars/**)`のような明示的拒否は無い。今回の実測で判明したClaude Code(v2.1.220)の挙動は次の通り:

- **作業ディレクトリ(cwd)外**へのReadは、allowに無ければ明示的に拒否される(`/etc/hostname`を単独で読ませる追試で確認: `"Claude requested permissions to read from /etc/hostname, but you haven't granted it yet"`)。これは`claude-code-unattended-session-confinement.md`の記載と整合する。
- しかし**cwd内**でallowにもdenyにも列挙されていないpathは、拒否されず読めてしまう(今回`inventories/vars/secrets.yml`で実測)。

これは今回の変更(`Read(roles/**)`等の追加)が原因ではなく、**既存の`job-settings.json.j2`(今回の変更前から)が持っていた既存のギャップ**である可能性が高い。従来のallowが`Read(docs/**)`・`Read(skills/**)`のみだった時点でも、cwd内であれば`roles/`・`playbooks/`・`inventories/vars/`を含む全ファイルがおそらく読めていたと推測される(本検証では旧設定での追試は行っていないため「推測」に留める。必要なら別途旧job-settings.jsonでの同一追試を推奨)。

**この案件のrequirement/AC1が「`inventories/vars/`は引き続き読めないこと」を明示的な受入条件として置いている以上、この状態はFAILとして扱うべきである。** 対応案(実装判断はCoordinator/Implementerへ差し戻し):

- `deny`配列へ`"Read(inventories/vars/**)"`を明示的に追加する。denyはallowより優先されることは`feedback_permission_ask_beats_allow_and_path_bypass.md`(auto-memory)で既に確認済みの性質であり、今回のFAILの直接の解決策になる可能性が高い(本検証では時間の都合上、deny追加後の再実測までは行っていない。**追加修正後の再検証が必要**)。
- あわせて、他の非allow・非cwd外パス(例: `.git/`、`README.md`、リポジトリ直下の設定ファイル等)についても同様に「cwd内・未列挙は読める」という前提で影響範囲を再点検すべき。
