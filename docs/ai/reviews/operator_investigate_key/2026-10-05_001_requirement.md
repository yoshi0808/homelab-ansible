# Operatorに専用の調査鍵を持たせる — requirement

日付: 2026-10-05 (JST)
状態: 実装・検証済み、配備待ち(方針はYoshinobu了承、2026-10-05「調査なんでopeも君もみんな調べられるようにしておきたい」)。計画査読 `_002` Approve。Suggestion O-1→R4、O-2→AC4/AC5、O-3→AC8b、AC8の注記を反映済み

## 1. 問題定義

**quory側Operatorは、対象ホストの読み取り専用の調査(`homelab-investigate-<host>`)を実行できない。** 2026-10-05、Coordinatorが出したLoki調査の依頼(OPREQ `req-20261005T142944+0900-3f9b0e7f3ef66fb3`)に対し、Operatorは `homelab-investigate-monnie loki-window` を実行したが、Lokiへ問い合わせる前のSSHの段階で失敗した(OPRES `req-20261005T143356+0900-460075717f47108c`)。理由として返ってきたのは2点:

- 専用SSH identityを、Operatorの実行identityから読めない
- monnieのhost keyをstrict checkingで検証できない

現物:

- Operatorはquory上でOSユーザー `yoshi` として動く(`roles/operator_request_channel/defaults/main.yml` の `operator_request_channel_operator_user`)
- quory上のwrapper `/usr/local/bin/homelab-investigate-<host>` は、`recovery-exec` の鍵と known_hosts をパスで決め打ちしている(`roles/recovery_exec/templates/homelab-investigate.sh.j2` の `KEY=` / `KNOWN=`)
- 対象ホスト側の `recovery-exec` の `authorized_keys` は、quoryの `recovery-exec` の鍵2本(調査・action)と、ansyのCoordinatorの調査鍵1本を持つ(`roles/recovery_exec/templates/authorized_keys.j2`、pveは `authorized_keys-pve.j2` の2本)。調査鍵はいずれもforced commandでdispatchだけを許す

**ansy側Coordinatorは自分の鍵で同じdispatchへ届くが、Operatorには相当する鍵が無い。**

## 2. ゴール

**Operator(quoryの `yoshi`)が、自分専用の鍵で、Coordinatorと同じ読み取り専用dispatchへ届く。** 届く先は authy / monnie / pve1 / pve2 で、語彙はdispatchが既に許すものと同じ。

## 3. 非ゴール(今回やらない)

- **`recovery-exec` の鍵を `yoshi` に読ませること。** identityの区別が崩れる。`docs/ai/policies/execution_boundary_policy.md` EXEC-082(実行identityを昇格しない)の趣旨にも反する
- **dispatchの語彙を変えること。** Loki検索の拡張は別案件(`docs/ai/reviews/loki_text_filter/`)
- **action(状態を変える)鍵をOperatorへ与えること。** 調査用だけ
- `sophos-fw` / UniFi機器への経路
- quory自身の調査経路(Operatorはquory上にいる)
- Operatorの起動時指示(quory側の `AGENTS.md`)の変更。repoはOperatorの指示の正本ではない(`docs/ai/roles/operator.md`「この文書の位置づけ」)。必要な手順の変更は申し送りとして記録する

## 4. ユーザーストーリー

Coordinatorとして、開発側の語彙で取れない事実をOperatorへ依頼したとき、Operatorが同じdispatchで調べて返せる状態にしたい。調査の手段が依頼先で詰まると、依頼の経路そのものが機能しない。

## 5. 要件

### P0(Must)

| # | 要件 |
|---|---|
| R1 | **quoryの `yoshi` に、Operator専用の調査鍵を用意する。** 秘密鍵はquoryで生成し、quoryの外へ出さない。repoへ秘密鍵を入れない。既存の鍵生成と同じく、既に存在すれば作り直さない |
| R2 | **その公開鍵を、authy / monnie の `recovery-exec` の `authorized_keys` へ、Coordinatorの調査鍵と同じforced command・同じ制限オプションで加える。** pve1 / pve2 へは、pve用dispatchのforced commandで加える。action鍵と同じ行・同じforced commandにしない |
| R3 | **既存の鍵の登録を崩さない。** `recovery-exec` の調査鍵・action鍵、ansyの調査鍵の行は、内容・forced commandとも変わらない。`authorized_keys` は従来どおり排他で描画する(本数が決まっていることがドリフト防止の仕組みである) |
| R4 | **Operatorが、既存と同じコマンド名 `homelab-investigate-<host> <check> ...` で、自分の鍵を使って届く。利用者向けの入口の名前は変えない**(内部で別の実装へ委譲するのは構わない)。通常ホスト用(`homelab-investigate.sh.j2`)とpve用(`homelab-investigate-pve.sh.j2`)の両方が対象。`recovery-exec` として呼ばれたとき(自律復旧のCodex、`incident_capture` の収集器)の挙動は変えない。**引数から鍵のパスを受け取る形にしない** |
| R5 | **`yoshi` 用の known_hosts を用意し、strict host key checkingのまま検証が通るようにする。** 検証を緩めない(`StrictHostKeyChecking=no` 等を使わない) |
| R6 | **日次のドリフト検査の期待値を新しい本数へ揃える**(`roles/deployment_drift_check/defaults/main.yml` の authorized_keys 行)。揃えないと、配備した翌日にドリフトとして報告される |
| R7 | **`--check` で状態を変えない。** 既存のtarget_setupの規律(鍵の生成・配備は `--check` で実行しない)に揃える |

| # | 要件 |
|---|---|

## 6. 受入条件

| AC | 内容 |
|---|---|
| AC1 | **Given** 描画した `authorized_keys.j2` **Then** authy / monnie 用は4行(調査・action・ansy調査・Operator調査)。Operator行のforced commandと制限オプションはansy調査行と同一 |
| AC2 | **Given** 描画した `authorized_keys-pve.j2` **Then** pve用は3行。Operator行のforced commandはpve用dispatch |
| AC3 | **Given** 既存3行(pveは2行) **Then** 変更前と同一の文字列 |
| AC4 | **Given** 通常用・pve用の両wrapperを `recovery-exec` 相当で呼ぶ **Then** 使う鍵とknown_hostsは従来どおり `recovery-exec` のもの(2 identity × 2 wrapperでsshのargvを捕捉して確かめる) |
| AC5 | **Given** 通常用・pve用の両wrapperを `yoshi` 相当で呼ぶ **Then** Operatorの鍵と `yoshi` 用known_hostsを使い、`StrictHostKeyChecking=yes` のまま。`recovery-exec` の鍵のパスを参照しない |
| AC6 | **Given** wrapperへ鍵やknown_hostsのパスを引数で渡そうとする **Then** 受け付けない(既存のarity/allowlistで拒否される) |
| AC7 | **Given** ドリフト検査の期待値 **Then** authy/monnie=4、pve1/pve2=3 |
| AC8 | **Given** `recovery_exec_setup.yml` を `--check` で decoy inventory に流す **Then** 鍵生成・authorized_keys配備は実行されず、完走する。inventoryの接続先を差し替えただけで安全と判定しない — `target_setup.yml` のTCP probeは `target_item.host` を直接使い `--check` でも動くため、実宛先を持たないfixtureで、対象のgateまで実際に到達した証跡を残す |
| AC8b | **Given** Operator鍵の生成タスク **Then** 初回生成後の再実行で鍵が変わらない。秘密鍵の所有者は `yoshi`・modeは0600、`yoshi` 用known_hostsは `yoshi` が読める(タスク定義とdecoy/ローカル実行で確かめる) |
| AC9 | **Given** 配備後(本番、Yoshinobuが実行) **Then** Operatorが `homelab-investigate-monnie loki-count <since> 5m` を実行して結果が返る。確認はOperatorへのOPREQで行う |
| AC9b | **Given** 配備後 **Then** systemd経由の `recovery-exec` 経路(`incident_capture` の収集器)が従来どおり届く。**Codexのsandbox経由の経路はこのACの対象ではない**(差分レビュー `_004` のCoordinator対応と監査 `_006` 対応を参照)。次に障害捕捉の収集がバンドルを作った周期で、quoryの `homelab-incident-capture.service` のjournalに `denied: investigation wrapper requires` が出ず、収集エラーにwrapper起因のものが無いことを、Coordinatorが `quory-investigate journal-unit` で確かめる(差分レビュー `_004` M-2) |

**配備の申し送り**: `playbooks/recovery_exec_setup.yml` をquoryのSemaphoreで実行する(保護対象の pve1 / pve2 / authy の `authorized_keys` が変わる。実行はYoshinobu)。pve1は平日停止のため、pve1への反映は稼働日に限られる。ドリフト検査の期待値(R6)は同じcommitで入るため、配備まではドリフト検査が「本数不一致」を報告しうる — 配備をcommitの直後に行う。
