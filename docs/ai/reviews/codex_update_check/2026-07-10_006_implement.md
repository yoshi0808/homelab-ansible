# npm 本体のメジャーバージョン更新対応 — 実装報告

対象要求仕様: `2026-07-10_005_requirement.md`（既存実装の経緯: `2026-07-09_001_requirement.md` / `2026-07-09_002_implement.md`）

## 実装概要

既存の `codex_update_check` role（Codex CLI = `@openai/codex` のバージョン確認・更新）に、
npm 本体のバージョン確認・**メジャーバージョンのみ**自動更新するフェーズを追加した。
マイナー/パッチのみの差分は更新せず通知もしない。既存の Codex CLI 更新フローには手を
入れていない（退行なし）。

## 作成・更新したファイル

- `roles/codex_update_check/tasks/main.yml`（更新）
  - Phase 1n: npm 本体の現在バージョン取得（`npm --version`、収集のみ）
  - 付随して、npm バイナリの dpkg 管理有無を情報収集のみで記録
    （`which npm` → `dpkg -S <path>`。判定・更新可否のゲートには使わない。
    test_plan での実ホスト確認に使えるよう debug summary に残すのみ）
  - Phase 2n: npm レジストリの最新バージョン取得（`npm view npm version`、収集のみ）
  - Phase 3n: メジャーバージョン判定（`current.split('.')[0] != latest.split('.')[0]`）。
    判定は Ansible 側（`set_fact`）で行い、shell 側では判定しない（core.md §7）
  - Phase 4n: メジャー差分がある場合のみ `npm install -g npm@latest` を実行
    （`become: true`、既存 Codex CLI 更新と同じ sudo パターン）
  - per-host ステータスを4値で記録: `updated` / `update_failed` /
    `up_to_date`（完全一致）/ `minor_patch_skip`（差分はあるがメジャーは同一）
  - Phase 5（結果集約・通知）を拡張し、npm の結果を Codex CLI の結果と統合した
    1通の Slack 通知にまとめた（実装判断: 別建てにすると週次で最大2通に増え、
    運用上の可読性が下がるため統合を選択）。失敗判定は Codex CLI / npm 両方の
    failed_hosts を合算し、いずれかがあれば `alerts`/`error` チャンネル・fail する
- `roles/codex_update_check/defaults/main.yml`（更新）
  - `codex_update_check_npm_package: "npm"` を追加（既存の `codex_update_check_package`
    と同じ命名パターン）
- `playbooks/codex_update_check.yml`（更新）
  - ヘッダコメント・`tester-gate: risk-accepted` 理由文に npm 本体更新を含む旨を追記
  - 「常に本実行」の判断根拠（npm 本体更新も同じ実行タイミング・同じ sudo 権限で
    行うためリスクの性質は変わらない）を追記

## 設計判断: npm の dpkg 管理と self-update の扱い（要求仕様の追記事項への回答）

claude から追記された情報（npm は NodeSource の `nodejs` deb にバンドルされ dpkg 管理下）
を踏まえて検討した。

**検討した代替案**: apt 経由（`apt-get install --only-upgrade nodejs` 等）で npm を
バンドル更新する方式。

**却下した理由**: NodeSource の `nodejs` パッケージが同梱する npm のバージョンは
Node.js 本体のメジャーバージョンに紐づいており、npm だけを独立して任意のメジャー版へ
進める手段ではない。この方式を採ると事実上 Node.js 本体の更新を伴うことになり、
要求仕様の「初回実装では除外する範囲: Node.js 本体（node）の更新」に反する。
そのため、今回のスコープ内では **npm 自身の self-update
（`npm install -g npm@latest`）以外に採れる方式がない** と判断した。

**採用した設計**: 要求仕様の実施項目2の通り self-update 方式を維持する。ただし以下の
トレードオフが生じることを前提として明記する。

- `npm install -g npm@latest` は dpkg が所有するファイル
  （`/usr/lib/node_modules/npm` 配下）を上書きするため、dpkg のパッケージ状態と
  実ファイルがドリフトする（`dpkg -S` の結果と実際のバージョンが不一致になる）
- 後続の `apt upgrade`（`nodejs` パッケージの更新）で npm がバンドル版に巻き戻る
  可能性がある
- 巻き戻った場合でも、週次実行の Phase 3n が再度メジャー差分を検知して再更新する
  ため、**自己修復（self-heal）**する。ただし「巻き戻り→再更新」のサイクルが
  繰り返される可能性があり、これは意図した仕様として許容する
- この注意喚起は implement ファイルに書くだけでなく、npm 更新を実施した回の
  Slack 通知本文にも自動で追記されるようにした（`codex_update_check_npm_updated_hosts`
  が1件以上ある場合のみ、dpkg ドリフト・自己修復の注意文を付加）

この判断（self-update 方式の採用・ドリフト許容）自体は Yoshinobu の最終判断が必要な
論点だと考えている。claude 経由で提示し、採否を仰いでほしい。

## shell と Ansible tasks の責務分離（確認）

- `npm --version` / `npm view npm version` / `which npm` / `dpkg -S` は command
  モジュールで実行し、収集のみ（`changed_when: false`, `failed_when: false`）
- メジャー判定・更新要否・通知内容・fail 制御はすべて `set_fact` / `when` /
  `ansible.builtin.fail` で Ansible tasks 側が担う

## 未対応事項 / Tester に依頼したい確認項目

1. **dpkg 管理の実機確認**: `dpkg -S $(which npm)` 相当を ansy/quory 実機で実行し、
   `nodejs` パッケージが所有していることを確認する（要求仕様の制約事項）
2. **メジャー判定の実地確認**: 例) 10.9.7→11.0.0 は更新対象、10.9.7→10.10.0 /
   10.9.8 はスキップとなること。2026-07-10 時点でレジストリの npm 最新が
   メジャー先行している場合、初回実行で即発動する点に注意（要求仕様に明記あり）
3. **self-update 実行確認**: メジャー差分があるホストで `npm install -g npm@latest`
   が実行され、`npm --version` で新バージョンが確認できること
4. **dpkg ドリフトの実地観測**: self-update 後に `dpkg -S $(which npm)` を再実行し、
   dpkg のパッケージ状態と実ファイルの不一致（またはdpkgの認識）がどう見えるかを
   記録する（本設計のトレードオフを実地で裏付けるため）
5. **冪等性確認**: 更新直後の再実行で `up_to_date` としてスキップされ、通知が
   飛ばないこと
6. **既存 Codex CLI 更新の非退行確認**: 既存の @openai/codex 更新フローが
   引き続き正しく動作すること
7. **Slack 通知内容の確認**: npm 更新実施時に、統合された1通の通知に
   「Codex CLI 更新実施」「npm本体 メジャー更新実施」の両セクション、および
   dpkg ドリフト注意文が正しく含まれること

## 注意点

- self-update 方式の採否（上記「設計判断」節）は claude を経由して
  Yoshinobu の判断を仰ぐ必要がある未確定事項。test_plan にはこの判断結果と、
  上記確認項目1・4（dpkg 管理・ドリフト観測）を必ず含めてほしい
- 実ホストの調査（npm バイナリパス・dpkg 所有パッケージ名・実際のレジストリ最新版）は
  行っていない。すべて tester による実地確認が必要
