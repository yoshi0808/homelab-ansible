- 起案: claude（要件定義・ハブ役）/ 承認: Yoshinobu（承認欄: 下記）
- 対象実装: `2026-07-10_008_implement.md`（再レビュー合格: `2026-07-10_009_review.md`）

## 前提・重要な注意

- 対象 playbook は `# tester-gate: risk-accepted`（常に本実行）。したがって
  **Phase 1 の実行はレジストリの npm 最新がメジャー先行していた場合、
  ansy / quory の npm 本体を実際にメジャー更新する**（現在 npm 10.9.7。
  npm 11 系が最新なら初回実行で即発動）。この点を承認の前提とする。
- 実行元は quory のみ（playbook 冒頭の assert）。変更ファイルは未コミットのため、
  quory の正式 checkout へ**バックアップを取ってから**変更3ファイルを同期して実行する
  （/tmp 一時コピー方式は前回 slack.yml の権限差分で通知が失敗したため使わない。
  cert_renew_quory テスト時と同じ「backup + 同期」方式を推奨）:
  - `playbooks/codex_update_check.yml`
  - `roles/codex_update_check/tasks/main.yml`
  - `roles/codex_update_check/defaults/main.yml`
- tester は各フェーズで実行コマンド・結果・置き換えた理由・未検証事項を
  test_result に記録する。

## Phase 0: 事前調査（read-only）

1. **dpkg 所有の実機確認**（ansy / quory 両方）:
   - `which npm` → そのパスの `dpkg -S`
   - `npm root -g` で npm 実体ディレクトリを特定し、`/usr/lib/node_modules/npm`
     （想定）の所有パッケージを `dpkg -S` で確認
   - 期待: NodeSource の `nodejs` パッケージが所有（要求仕様の前提の裏付け）
2. **バージョン現況**（ansy / quory 両方）:
   - `npm --version`（現在: 10.9.7 想定）
   - `npm view npm version`（レジストリ最新）
   - メジャー差分の有無を記録し、**Phase 1 で実更新が発動するか否かをこの時点で判定・明記**
3. `@openai/codex` の現在バージョンも記録（非退行確認のベースライン）

## Phase 1: 本実行（risk-accepted・quory から）

4. quory 正式 checkout（同期済み）で `ansible-playbook playbooks/codex_update_check.yml` を実行
5. 確認項目:
   - メジャー差分あり時: 両ホストで npm が更新され、`npm --version` が新メジャーに
     なること（`updated`）
   - メジャー差分なし時: `up_to_date` / `minor_patch_skip` で更新・npm 通知が
     ないこと
   - 既存 @openai/codex 更新フローが正しく動作すること（非退行）
   - Slack 通知が統合された1通で、npm 更新実施時は npm セクション＋
     dpkg ドリフト注意文が含まれること
   - rc=0 で完走すること

## Phase 2: 冪等性

6. Phase 1 直後にもう一度実行
   - npm は `up_to_date`（または直後に新規リリースがあった場合の
     `minor_patch_skip`）となり、更新・通知が発生しないこと
   - rc=0

## Phase 3: dpkg ドリフト観測（Phase 1 で実更新が発動した場合のみ）

7. Phase 0 の dpkg 所有確認を再実行し、self-update 後に dpkg のパッケージ状態と
   実ファイルの見え方がどう変化したかを記録する（採用済み設計のトレードオフの
   実地裏付け。修正は不要、観測のみ）

## Phase 4: 失敗経路の確認（must-fix 指摘2の修正検証・ベストエフォート）

8. tester の判断で安全な方法を選択して、更新失敗時に `update_failed` として記録され、
   集約 → Slack `alerts`/`error` 通知 → 最終 `fail` に到達することを確認する。
   - 例: `-e codex_update_check_npm_package=<存在しないパッケージ名>` の上書きが
     収集フェーズに影響する場合は `collection_failed` 経路の確認に切り替える等、
     実挙動を見て安全な代替を選んでよい
   - 実 Slack error 通知が飛ぶ場合があるが、テストとして許容（実施前に test_result に
     予告を記録すること）
   - 安全に失敗を注入できないと判断した場合は、その理由と「コード検査＋
     implementer のローカル6ケース検証結果を根拠に許容」の旨を test_result に記録
     して未検証事項として残す

## Phase 5: 異常系（ダウングレード拒否・実地は条件付き）

9. レジストリ最新が現在より小さいメジャーになる状況は通常作れないため、
   実地確認は必須としない。Phase 0 の取得値で判定ロジックの入力を記録し、
   ローカル検証済み6ケース（008_implement 参照）を根拠として記録すればよい

## 合否基準

- Phase 0〜2 がすべて期待通り: 合格（Phase 3 は観測のみ、Phase 4-5 はベストエフォート）
- いずれかで想定外の挙動: test_result に記録し claude へ返す（claude が requirement と
  突合して Yoshinobu に提示する）
