## 結論

**要修正（must-fix 2件）**。

メジャー判定を Ansible 側に置く責務分離、既存 Codex CLI と npm の結果集約、
マイナー/パッチ差分を通知対象にしない条件、dpkg ドリフトを許容して週次で
自己修復する設計の文書化は、要求仕様と整合している。一方で、現在の実装は
「最新メジャーが上がった場合のみ」という更新方向を保証せず、npm 更新コマンドの
失敗時には意図した status 集約・Slack error 通知へ到達できない。

## 指摘

### 1. [must-fix] メジャー判定が「上昇」ではなく単なる「不一致」になっている

対象: `roles/codex_update_check/tasks/main.yml:132-142`

`codex_update_check_npm_needs_update` が
`_current_major != _latest_major` であるため、最新タグ側のメジャーが現在値より小さい
場合にも更新対象になる。たとえば current=`12.0.0`、latest=`11.5.0` でも true となり、
`npm@latest` へのダウングレードを実行する。要求仕様は「メジャーバージョンが
上がっている場合のみ」なので、数値として `latest_major > current_major` を判定する
必要がある。

また、現状の `_collected` は stdout が空でないことしか確認せず、メジャー部分を
数値として検証していない。比較修正時は、想定外の出力を更新対象にせず
`collection_failed` として扱えるよう、SemVer形式（少なくとも先頭の数値メジャー）を
検証してから整数比較すること。例示ケース 10.9.7→11.0.0=true、
10.9.7→10.10.0=false、10.9.7→10.9.8=false に加え、12.0.0→11.5.0=false も
確認対象にするとよい。

### 2. [must-fix] npm 更新失敗時に status 集約・Slack error 通知へ到達しない

対象: `roles/codex_update_check/tasks/main.yml:147-162,167-262`

`Update npm itself to the latest major version` は `failed_when` を指定していないため、
`npm install -g npm@latest` が非ゼロ終了すると、そのホストはその場で failed になり、
直後の `Record per-host npm update status` は実行されない。全対象ホストが同様に失敗した
場合は集約 block 自体も実行されず、少なくとも要求仕様の「更新失敗時は fail し、
rescue で Slack error 通知」に到達しない。一部ホストだけ失敗した場合も、集約が
たまたま残存ホストで動くことに依存する脆い制御になる。

更新コマンドの rc を一旦収集できるようにし、全ホストの status を確定した後で
Slack error 通知と最終 `fail` を行う構造にすること。あるいは明示的な block/rescue で
失敗結果を記録し、必ず集約・通知へ到達させること。既存 Codex CLI 更新タスクにも同じ
構造上の問題があるため、この機会に両更新フローを同じ失敗処理へ揃えると、要求された
既存フローの非退行と統合失敗判定を一貫して保証できる。

### 3. [suggestion] dpkg 所有確認は npm 実体ディレクトリも観測した方がよい

対象: `roles/codex_update_check/tasks/main.yml:91-110`

`dpkg -S $(which npm)` は通常 `/usr/bin/npm`（symlink/launcher）の所有確認に留まり、
要求仕様が問題としている `/usr/lib/node_modules/npm` 配下の所有・上書きドリフトを
直接確認しない。今回の fact は更新ゲートではなく情報表示のみなので実装を止める問題
ではないが、test_plan では `npm root -g` 等から npm 実体を特定し、その配下が
`nodejs` パッケージ所有であることを更新前後に確認する方が、設計判断の根拠になる。

## 観点別確認

- メジャー判定: **NG**。不一致判定であり上昇判定になっていない。
- 既存 Codex CLI 更新フロー: 通常成功・取得失敗のロジックに直接の退行は見当たらない。
  ただし更新コマンド非ゼロ時の集約不能は既存問題として残り、npm統合後も保証できない。
- Slack 通知統合: failed_hosts のリスト合算、channel/status/title/最終failの条件自体は整合。
  ただし更新コマンド失敗時に集約地点へ到達できないため、失敗経路としては NG。
- shell/tasks 責務分離: **OK**。command は収集・更新実行、比較・通知・fail制御は
  Ansible tasks に置かれている。
- dpkg管理・ドリフト許容: self-update採用理由、aptによる代替を採らない理由、
  巻き戻り後の週次自己修復、Slack注意文が明記されており概ね整合。最終採否は
  implement 記載どおり Yoshinobu の判断事項。
