# requirement: `--check` 下で障害捕捉が書き込む経路を塞ぐ(案件3)

作成: 2026-09-27 / Coordinator
起点: `docs/ai/reviews/playbook_catalog_policy_audit/2026-09-26_004_findings_cert_safety_boundary.md` 未確認2。範囲はYoshinobu合意済み(2026-09-27)。

## 1. 問題定義

ADR-004(補1)は「`capture.yml` に `check_mode: false` を付けない。`--check` 実行では捕捉も書かない」と定め、`roles/common_slack/tasks/capture.yml` のヘッダも「check_mode … always false in practice … it does not write anything under --check」と書く。

**しかし、呼び出し側が `check_mode: false` のblockの中から `notify.yml` をincludeすると、その `check_mode: false` がinclude先の `capture.yml` の書込タスクまで継承され、`--check` 下でもspoolへ書き込む。**

Coordinatorが2026-09-27にlocalhostで再現した(収集器の配備markerと `capture_spool_dir` を一時ディレクトリへ差し替え、`skip_notifications: true`)。

| 実行 | 普通の `notify.yml` include | `check_mode: false` のblock内からのinclude |
|---|---|---|
| 通常実行 | 書く | 書く |
| `--check` | 書かない | **書く**(レコードの `check_mode` は `True`) |

playの結果(ok / failed 等)はどの組合せでも変わらなかった。

該当しうる呼び出し元(監査 `_004` 未確認2の列挙): `roles/recovery_ha_failover/tasks/main.yml`、`roles/recovery_service_restart/tasks/main.yml`、`roles/recovery_vm_reboot/tasks/main.yml`、`roles/ubuntu_vm_full_upgrade/tasks/main.yml`。

## 2. ゴール

- `--check` 下では、呼び出し側の `check_mode` 指定に関わらず、捕捉は書き込まない(ADR-004 補1の意図どおり)
- 通常実行では、従来どおりすべての通知を捕捉する(IC-008 / IC-009)
- 捕捉は被観測playの終了コード・タスク結果の件数を変えない(IC-010。現行の「捕捉が加える `ok` +5」は受入済みの状態として維持し、増やさない)

## 3. 非ゴール

- 捕捉を通知の抑止判定より前に置く設計(IC-009)は変えない
- `capture.yml` に、通知の属性(status / channel / title / message / skip_notifications 等)を条件にした `when:` を足さない(ADR-004 (c))。**`ansible_check_mode` を条件にした `when:` も足さない**(タスク結果の件数が `skipped` 側で変わりうるため。§5 R1の方式を採る)
- 呼び出し側(上記4 role)の `check_mode: false` は変えない(IC-027「捕捉を成立させるためにcaller側の通知ロジックを書き換えない」)
- Policy TS-005 の `role-guarded` 定義、IC-010 の件数の文言は、Policy改訂の流れで扱う
- `notify.yml` は変えない

## 4. ユーザーストーリー

- Yoshinobuとして、Semaphoreの Dry Run や Tester の `--check` 実行が、本番の障害証拠(spool)にレコードを残さないでほしい

## 5. 要件

| # | 要件 |
|---|---|
| R1 | `capture.yml` の**書き込みを伴うタスク**(spoolディレクトリの作成、レコードの書き込み、「書いた」印の更新など)に、CLIの `--check` の値をそのまま使わせる指定(`check_mode: "{{ ansible_check_mode }}"` 相当)を付け、呼び出し側から継承した `check_mode: false` を打ち消す。値の出どころは `ansible_check_mode`(CLIの `--check` から作られ、taskの `check_mode: false` では変わらない)とする |
| R2 | `capture.yml` のヘッダコメントとADR-004への言及を、R1の実態に合わせて直す(「呼び出し側が `check_mode: false` のblockからincludeしても、書き込みタスクはCLIの値に従う」) |
| R3 | 書き込み以外のタスク(markerの存在確認、文脈の組み立て)は現行のまま。**「書いた」印(`_capture_written_id`、`capture.yml` の `set_fact`)は、`set_fact` がcheck modeでも値を設定するため、R1の指定だけでは止まらない。** `--check` のときは、印に今回のIDを設定せず、それまでの状態(未定義なら未定義、既に値があればその値)を保つ値設計にする。タスクは `when:` でskipさせず、件数を変えない。通常実行で `notify.yml` の末尾の `capture: <id>` 行が出る条件(`_capture_written_id is defined`)と、その値は変えない(計画査読 `_002` M1) |
