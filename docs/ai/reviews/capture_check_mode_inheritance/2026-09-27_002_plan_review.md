## Code Review: capture_check_mode_inheritance requirement

### Summary

`file` / `copy` の各taskへ `check_mode: "{{ ansible_check_mode }}"` 相当を直接置く方式は、callerのblockから継承した `check_mode: false` よりtask側が優先され、CLI `--check` 下の実書込みを止める。ただしR1は `_capture_written_id` を更新する `set_fact` も同じ方式で止まるかのように扱っており、実際にはcheck modeでもfactが設定される。R3 / AC3を満たす値の決め方を要件へ追加するまで実装へ進めない。

なし。

### What Looks Good

- `ansible_check_mode` がCLI `--check`由来のまま真を保つという前提は現物と一致する。localhost最小再現では、外側blockの `check_mode: false` が動的include先へ継承された状態でも、内側taskに直接置いた `check_mode: "{{ ansible_check_mode }}"` が優先され、file/copyは実体を作らなかった。したがってspoolディレクトリ作成とレコード書込みに対するR1の方式自体は成立する。
- 該当callerの列挙は現物と一致する。`recovery_ha_failover`、`recovery_service_restart`、`recovery_vm_reboot` は外側blockが `check_mode: false` で、その `always` 内からnotifyをincludeする。`ubuntu_vm_full_upgrade` もCommon processing block内の3経路が同じ継承下にある。
- 変数名は現物と一致する。配備判定は `capture_collector_marker`、spool差替えは `capture_spool_dir`、通知footer用の印は `_capture_written_id` である。
- R1〜R3とACの骨格は対応している。R1の実書込み抑止はAC1、件数不変はAC2、印はR3 / AC3、配備markerと失敗隔離の回帰はAC4 / AC5、文書と既存検査はR2 / AC6で観測できる。
- 通常実行では `ansible_check_mode == false` のため、taskへ同値を戻す指定は現行の実行経路を変えない。marker無しのgate、通知属性で絞らない条件、notify冒頭でのcapture、block/rescueも変更対象外であり、IC-008 / IC-009 / IC-010 / IC-027およびADR-004 (a-2) / (b-1) / (c-2)を維持できる。
- callerや`notify.yml`を変更せず、既存の `capture.yml` に閉じるため、再利用漏れ・重複実装はない。新しいshell、外部通信、機密変数、権限変更も導入しない計画であり、Ansible固有のセキュリティfindingはない。
