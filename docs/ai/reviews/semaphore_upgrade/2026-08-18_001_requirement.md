# requirement: Semaphore 2.18.4 → 2.19.8 の版上げ(quory)

作成: 2026-08-18 / Coordinator

## 1. 問題定義

`ansy` / `quory` の Semaphore はともに **2.18.4**(2026-05-18公開)で、上流の現行は **2.19.8**(2026-08-17公開)である。

**apt リポジトリが存在せず、新版が出たことを知る経路が無い**(`docs/ai/context/system/semaphore.md`「インストールと版上げ」)。導入は GitHub Releases の `.deb` を `apt install` した形で、供給元は `/var/lib/dpkg/status` だけである。したがって版は放置すると開くだけで、閉じるには人が気づいて手を入れるしかない。

**不可逆なのはプロセスではなく DB である。** `semaphore server` は起動時にマイグレーションを実行するため、restart した時点でスキーマが上がる。バイナリを戻しても旧版が動く保証は無い。

## 2. ゴール

`quory` の Semaphore を 2.19.8 へ上げる。**戻せる状態を作ってから上げ、上げた後に壊れていないことを観測できる形で確かめる。**

## 3. 非ゴール

- **`semaphore_update_check` playbook の新設。** 新版の検知を定期的に回す仕組みは別案件とする(方針は決定済み: 自動適用はしない、`dry_run=true` の検知だけを回す、当てるときは手動)。**本案件を先に済ませる** — 版上げで何が起きるかを知ってから設計する方が、playbook の設計入力として正しい順序である
- **`ansy` の版上げ。** 2026-08-18に完了済み(本文書 §9)
- **Operator に実行させる能力の設計。** Operator の役割は本番調査とトラブル対応であり、routine な変更の実行主体にしない(Yoshinobu、2026-08-18)。`docs/ai/roles/operator.md` も Semaphore 操作を「設計中」側に置いている
- **非同期シェル(`async` / `poll: 0`)による切り離し。** `KillMode=control-group` の下では成立しない(§9で実測)。repo にも実績が無い
- **Semaphore job から起動し `systemd-run` で restart 以降を transient unit へ逃がす2段構え。** 機構としては成立する(§9で実測、実績は `roles/ubuntu_vm_full_upgrade/tasks/reboot_quory.yml`)が、**今回は採らない**(Yoshinobu、2026-08-18)。版上げそのものの未知の上に機構をもう1つ重ねることになり、失敗の切り分けができなくなるため。**成否が job の色に出なくなり、二段目が起動しなかったことを無音と区別する通知まで作り込む必要が出る**。playbook 化する案件を起こすときの設計入力として残す
- **schedule の有効化状態を変えること。** 本案件は版だけを動かす
- **2.19 の新機能(Workflows / Docker・Kubernetes executor / JWT ID token)の採用。** 上がった結果として存在するが、使うかどうかは別の判断

## 4. ユーザーストーリー

Yoshinobu として、Semaphore の版を上げたい。ただし **本番の制御平面であり、DB のマイグレーションが不可逆**なので、①戻せる退避が確実に取れていること ②上げる瞬間を自分が決められること ③上がった後に壊れていないことを機械が示すこと、を満たしたい。

## 5. 要件

**手順そのものの正本は `2026-08-18_002_manual_procedure.md` である。** ここには、手順に落ちる前の「満たすべきこと」だけを置く。

| # | 要件 | 優先 |
|---|---|---|
| R1 | **退避を先に確定させる。** `semaphore.db` / `config.json` / projects export の3点。既存の `roles/semaphore_db_backup` がこの3点セットを NFS へ出す | P0 |
| R2 | **install と restart を分離し、restart の直前にサービスを止めた状態でもう一度スナップショットを取る。** これが唯一の確実なロールバック点になる | P0 |
| R3 | **`.deb` の変種(`semaphore_` / `semaphore_community_`)を毎回照合する。** 取り違えると版と一緒にエディションまで入れ替わる | P0 |
| R4 | **今回は playbook 化せず手動で実行する**(Yoshinobu、2026-08-18)。未知(OQ1 / OQ2)が残る状態で自動化の機構を重ねると、失敗がマイグレーション由来か機構由来か切り分けられない | P0 |
| R5 | **ロールバック手順を成果物に書く。** バイナリを戻すだけでは戻らない(DB が上がっている) | P1 |
| R6 | **`docs/ai/context/system/semaphore.md` の誤りを直す** | P1 |

## 6. 受入条件

すべて `quory` 上での実行を対象とする。

**AC1 — 退避が先に確定している**
> Given `semaphore_db_backup` を1回実行した直後の状態で
> When 版上げ playbook を起動する
> Then 退避3点(`semaphore.db` / `config.json` / projects export)の存在を確認できないときは、**install を1つも実行せず終了コード非ゼロで停止する**。Slack `alerts` へ通知する

**AC2 — install ではサービスが再起動されない**
> Given Semaphore が 2.18.4 で稼働している状態で
> When `.deb` を install するタスクが完了する
> Then `systemctl show semaphore -p MainPID` の値が install 前と**同一**である。`semaphore version`(ディスク上のバイナリ)は 2.19.8 を返し、稼働プロセスは 2.18.4 のままである

**AC3 — マイグレーションが完走する**
> Given install 済みでサービスを停止し、最終スナップショットを取った状態で
> When サービスを起動する
> Then journal に `Executing migration` 7行と `Migrations Finished`、`Semaphore 2.19.8-`、`Server is running` が現れ、`systemctl is-active semaphore` が `active` を返す。**現れないまま落ちたらロールバックへ進む**(AC10)

**AC4 — オブジェクトが失われていない**
> Given 版上げ完了後に
> When API へ `GET /api/project/<id>/templates` と `.../schedules` を発行する
> Then 件数が版上げ前と**同一**である。差があれば終了コード非ゼロで停止する
> (根拠: 2.19 は task history に server-side pagination を入れた。template / schedule 一覧が truncate されないことを ansy で確認済みだが、**quory の件数で確かめ直す**)

**AC5 — 本番が依存している読み取り経路が壊れていない**
> Given 版上げ完了後に
> When `homelab-semaphore-query` の7クエリ(`recent-failed` / `running` / `task-errors` / `task-hosts` / `task-output` / `task-time` / `template-list`)を実行する
> Then すべて SQL エラーなく返る。`task` の時刻が `YYYY-MM-DD HH:MM:SS.nnnnnnnnn +0000 UTC` の形を保っている

**AC6 — reconcile が通る**
> Given 版上げ完了後に
> When `semaphore_templates_setup.yml` を `--check` で実行する
> Then `failed=0` で完走し、カタログとの差分が出ない

**AC7 — schedule が消えても止まってもいない**
> Given 版上げ完了後に
> When `project__schedule` の `active` を読む
> Then 版上げ前に有効だった schedule がすべて有効のままである
> (**ansy では確かめられない** — R15 の allowlist が canonical な quory の URL 以外での有効化を禁じており、ansy の schedule は全件 `active=0` である)

**AC8 — 失敗したときに戻せる**
> Given 版上げが AC3〜AC7 のいずれかで失敗した状態で
> When ロールバック手順を実行する
> Then 2.18.4 のバイナリと退避した `semaphore.db` が復元され、`systemctl is-active semaphore` が `active`、UI が 200 を返す

## 7. 成功指標

- 版上げ後、**次の schedule 実行が緑で終わる**(Semaphore の定期ジョブが従来どおり発火し、成否判定が機能している)
- `homelab-semaphore-query` を使う既存経路(dispatch の `semaphore-query`、incident 調査)が引き続き答えを返す

## 8. オープンクエスチョン

| # | 問い | 現状 |
|---|---|---|
| OQ1 | **quory の `task` テーブルに、新しい FK 制約を満たさない行があるか** | 未確認。2.19 のマイグレーションは `task` を copy-rebuild し、`user_id` / `project_id` の FK を `ON DELETE SET NULL` / `CASCADE` へ変える。**ansy の task は1行、quory は675行以上**(2026-08-11時点、`semaphore-query recent-failed` で実測)。行数自体は些少だが、制約違反の行があれば copy で落ちる。**2.19.7 が壊し 2.19.8 が直したのがこの経路である** |
| OQ2 | **鍵(`access_key`)の移行が quory で問題なく通るか** | **ansy では原理的に確かめられない。** ansy の鍵は `type=none` の1本だけで、これは ansy を無害にしている性質そのものである。2.19 は keyring と key rotation に手を入れている。quory の鍵は本番の認証経路そのものである |
| OQ3 | `needrestart` の設定が quory でも ansy と同じか | 未確認。ansy では設定ファイルに `$nrconf{restart}` の指定が無く既定動作で自動 restart した。quory の設定は測っていない。**R2 は環境設定に依存せず明示的に抑止するため、答えが何であれ手順は変わらない** |
| OQ4 | 2.19.8 の SQLite マイグレーション修正が十分か | 2.19.8 の変更内容は `Fixed SQLite migration` の1点のみで、公開は2026-08-17(本案件の前日)。**修正が新しいこと自体は残存リスクとして受け入れる**か、2.19.9 を待つかは Yoshinobu の判断 |

**正本は `2026-08-18_003_result.md`「ansy と quory の差(実測)」である。** 本案件は ansy を先に 2.19.8 へ上げ、その結果を入力として quory の手順を組んだ。**値をここへ写さない。**

## 10. タイムライン考慮

急がない。**証明書の更新が9月上旬に本番の答え合わせを迎える**(`docs/ai/status.md`)ため、その観測と重ねない方がよい。Semaphore を止めると schedule の起動と結果閲覧が止まるので、**定期実行の窓を外して実施する** — 窓の正本は Notion「バッチ処理工程管理表」であり、カタログだけで判定しない。
