## Major(blocking)

### M1 通知 status の順序入替で、失敗・中止が `warning` に格下げされる(既存挙動の回帰)

- `tasks/main.yml` の `_notify_status` は、`aborted or _post_hc_status != 'OK'` を先頭の `warning` 条件にし、`_apply_abort_type != 'none' or _apply_failed` の `error` を後ろへ回した。
- `_post_hc_status` の初期値は `UNKNOWN`(main.yml 65行)で、再起動前に止まる全ての中止・失敗(`apt_update`、`apply_failed`、`healthcheck` など)では `OK` にならない。**従来 `error` だったこれらがすべて `warning` になる。** チャンネルは従来どおり `alerts` だが、status の色と区別が失われる。requirementは「aborted を warning にする」ことだけを求めており、既存の error を動かす要求は無い。
- 必要な対応: 順序は `abort_type/failed → error`、その次に `aborted or post_hc != OK → warning`、とする。`aborted` は `_apply_failed` が偽のときだけ成り立つので、この順で要求を満たす。
- 検出されなかった理由(M5 に続く): `tests/_eval_notify_case.yml` は main.yml のこの節を複製したもので、複製側は旧順序のまま(128-135行)。試験は main.yml を読まない。

### M2 削除の途中・直後の失敗が `aborted`(warning、適用は SUCCESS)へ倒れ、壊れた状態が見えなくなる

`rescue` は一律で `aborted` を書く(`kernel_cleanup.yml` 末尾)。`aborted` は「何も削除していない」場合の区分(R6)だが、次の失敗は削除が始まった後に起きる。

- `Purge only validated old kernel packages` が rc≠0(dpkg が一部を消した後に失敗、hook 失敗、dpkg ロック、timeout による kill)で失敗 → rescue → `aborted`。`dpkg --audit` も R7 の検証も走らない。半削除・`iF` 状態のまま適用は SUCCESS、weekly full は次の node へ進む。R8 が防ぎたい事態そのもの。
- purge 後の収集・`from_json`・評価で task が失敗(出力の途中切れ等) → 同じく `aborted`。
- これは「rescue での吸収」+「`status` の既定値への倒し」+「適用結果を変えない」が合成された形で、壊れていることが `[WARNING]` の1行に畳まれる。
- 必要な対応: purge の直前に「削除に着手した」印(fact)を立て、rescue はその印があれば `broken`(適用 FAILED)にする。または purge task を `failed_when: false` にして rc と出力を記録し、必ず R7(`dpkg --audit` 等)へ進める。rescue の理由には `ansible_failed_task.name` と purge の stdout/stderr 末尾を入れる(現状は固定文言で、どの task で落ちたか分からない。purge の出力は report にも残らない)。

### M3 purge の timeout が初回の一括削除に対して短く、dpkg を SIGKILL する

- `proxmox_patch_apply_kernel_cleanup_timeout: 120` を collect・simulation・purge に共通で使い、`timeout --kill-after=10s` で包む。初回は pve1 で約26個、pve2 で約30個を1回の `dpkg --purge` で消す。各 purge は postrm hook(initramfs、`proxmox-boot-tool` の ESP 処理)を動かす(計画査読 M5 が指摘した点。実測は無い)ため、120秒で収まる根拠が無い。
- 超えると dpkg が kill され、dpkg の状態が中断のまま残る(M2 により `aborted` として扱われる)。計画査読 M1(c) が「強制終了すると dpkg が中断状態で残り翌週 `apt_check` abort に出る」と指摘したのと同じ経路。
- 必要な対応: purge だけ別の変数にして、実測に基づく十分な値にする(根拠が無ければ、kill しない・または初回は件数で分ける等を Coordinator が決める)。requirement は「timeout を付ける」とだけ書いており、値は未決定のため、Coordinator の判断を要する。

### M4 R7「kernelのメタパッケージが `ii` のまま」が検証されていない

- `_kernel_cleanup_verified` は `^proxmox-kernel-[0-9]+\.[0-9]+$` に一致する `ii` が **1つ以上** あることしか見ない。削除前に `proxmox-kernel-6.17` と `proxmox-kernel-7.0` の2つがあるとき、片方が消えても通る。
- R7 は「R2で残した版、kernelのメタパッケージ、`proxmox-ve` が状態 `ii` のまま」。削除前の収集結果(`_apply_kernel_cleanup.packages`)に同じ一覧があるので、削除前後の meta 名の集合の一致で比較できる。

### M5 試験が実際の削除経路を通っていない

- `test_kernel_cleanup_task.yml` は全ケースで `proxmox_kernel_cleanup_fixture` を渡す。`kernel_cleanup.yml` の fixture 分岐で status が `unevaluated` 以外になるため、**収集・評価・両simulation・purge・R7・rescue の各 task は一度も実行されない**。通っているのは skip 判定、fixture の代入、`broken → _apply_failed` の3点だけ。
  - AC3(running が最新でない・boot-tool 失敗 → skipped)、AC4(simulation 不成立 → aborted)、AC5(task 失敗でも report と通知が出る)、AC7(`--check` で削除されない)は、task を通した試験が無い。`--check` のケースも無い(`ansible_check_mode: false` を play var で固定している)。
  - `_kernel_cleanup_verified` の式、`when` の連鎖、`status` の遷移は、本体のどの試験でも評価されない。式が誤っていても `removed` / `broken` のどちらが出るかは本番の初回まで分からない。
- 通知の試験(`_eval_kernel_cleanup_case.yml` の `notify_status` / `notify_subject`)は、試験の中で再実装した式で、main.yml を読まない。M1 のような回帰を検出できない。requirement R10 は「複製しない・同じファイルを include」を求めており、この部分は満たされていない。
- 必要な対応: fixture を使わない経路を通す。`command` を差し替えられない場合は、収集 task の出力を fact で与える(例: collect/simulation/purge の結果を入力 fact にして task 本体はそのまま通す)など、Coordinator が方式を決める。最低でも、AC4(Inst 行つき)・purge 失敗(M2)・`--check` の3つは task を通すこと。通知の status・subject は、main.yml の式を試験が include できる形(独立ファイル化)にするか、parity 試験に今回の節を足す。
- fixture 分岐自体が本番の task ファイルに入っていて、extra-vars 等で `proxmox_kernel_cleanup_fixture` が定義されれば、収集も検査もせずに任意の `removed` が入る。削除には至らないが、結果の偽装経路が本番コードに残る(Minor 1 も参照)。

## 確認済み(問題なしと判断したもの。静的な読解による)

- 削除対象の決定: boot-tool の manual+automatic と実行中を残し、実行中が最新でなければ評価が例外(skipped)。`ii` / `rc` 以外(`hi`、`iF` 等)は対象にならない。名前は `^proxmox-kernel-<ver>-pve-signed$` のみ。メタ(`proxmox-kernel-6.17`)は対象外。解析不能・空・`None.` の扱いは fail-closed。
- R4: dpkg simulation の rc≠0・空、apt の rc≠0・空・解析不能、`Remv`/`Purg` の集合不一致、`Inst`/`Conf` の存在をすべて止める。実測原文(`Purg` + `Inst`/`Conf`)が止まることを単体試験が原文ファイルから確認している。
- 削除コマンドは `dpkg --purge <名前の列挙>` のみで、`apt autoremove` / `apt-get purge` の実行は無い。argv は list で渡され、シェル展開を通らない。
- `--check` では skip 判定が先に `skipped` にし、purge task にも `not ansible_check_mode` と `tags: [destructive]` がある。None と空文字の取り違えは見当たらない(`default` と `| bool` を使う箇所のみ)。
- report への `kernel_cleanup` 追加、既存の `running_kernel` を流用しない点(R12)、`broken → _apply_failed`(後続の `Re-raise` で play 失敗)、`aborted → alerts` + `warning`(M1 の順序問題を除く)。配備は Phase 2 の copy で毎回行われる。
