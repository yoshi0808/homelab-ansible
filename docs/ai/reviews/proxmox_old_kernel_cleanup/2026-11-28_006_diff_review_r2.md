## Major(blocking)

### M1 試験が追加契約を満たしていない: 本番の失敗経路と `main.yml` の通知式を通す試験が無い

Coordinatorが差し戻し時に決めた契約は「試験は本番のtaskファイルの経路と `main.yml` の通知式を実際に通す」。現状:

- `tests/test_kernel_cleanup_task_flow.yml` は **happy path の1ケース(`removed`)だけ**。`broken`(purge失敗・timeout・purge後の検証不成立)、`aborted`(収集rc非0、simulation不成立、`Inst`/`Conf`)、`skipped` の各分岐、`--check`、`Mark apply failed`(`_apply_failed`/`_apply_abort_type`)は assert されていない。私が stub を変えて手で観測した purge失敗→`broken` と 収集失敗→`aborted` は動いたが、これらは試験として残っていない。
- **`main.yml` の通知式(`_notify_subject` の `broken`/`aborted` 分岐、`_notify_status` の順序、`_notify_channel`、Phase 6 の本文)を通す試験が一つも無い。** `_eval_notify_case.yml` は従来どおり main.yml の複製で、今回の分岐を含まない。`_eval_notify_case_parity.yml` の grep 照合も今回の行を対象にしていない。結果、004 M1 / 005 D3 の回帰(順序入替)は、いま再発しても検出されない。差し戻しの核の1つ(M1)が機械的に守られていない。
- 実装記録は「再検証PASS」としているが、それは上記の1ケースと既存試験の範囲である。

必要な対応: 最低でも次を、本番の `kernel_cleanup.yml` を include する形(現在の stub 方式で足りる)で追加する。
1. purge が rc≠0(一部出力あり)→ `broken`、`purge_output` に出力、`_apply_failed` 真、`_apply_abort_type == kernel_cleanup_broken`。
2. purge後の検証不成立(メタが1つ欠落、audit出力あり等)→ `broken`。
3. 収集 rc≠0 / `Inst` 行つき simulation → `aborted`、purge 未呼び出し。
4. gate 不成立 → `skipped`(`--check` を含む。`--check` は tempfile を使わない作りにする)。
5. 通知: main.yml の subject/status/channel の式を試験が実際に読む形にする(式の切り出しを独立ファイルにして main.yml と試験が同じファイルを include する、または parity 照合へ今回の分岐を追加する)。特に `abort_type != none` かつ `_post_hc_status == UNKNOWN` で `error` になること、`broken` と `aborted` の見出しを確認する。

## Minor(non-blocking)

1. skip 理由の末尾に空白が付く(観測済み: `"post-healthcheck が OK でないため削除しません "`)。003 は「理由文字列は trim」としたが、`trim` が入ったのは rescue の文字列だけで、gate の `_kernel_cleanup_skip_reason` には入っていない。通知本文に末尾空白が出るのみ。
2. `purge_output` は先頭3000文字(`[:3000]`)。dpkg の失敗理由は出力の末尾に出ることが多く、初回の一括削除で出力が長いと失敗箇所が切り捨てられる。末尾側を残す方が診断に役立つ。
3. `broken` を rescue で立てたときも `_apply_failed_task` は固定文字列 `Verify old kernel cleanup`。実際に落ちたtaskは `reason`/`_apply_error_msg` にだけ入る。通知本文の「失敗task:」行は誤誘導になりうる。
4. `version_key` が整数と文字列を混ぜて比較する。版の形が想定外(例: 位置ごとに数字/文字が食い違う)だと `TypeError` で評価が例外になり、fail-closed の `skipped`(見出しは SUCCESS)が毎週続いて見えなくなる。実害は「削除されないまま気づかれない」ことで、安全側。
5. 報告に `packages` 全件と `boot_tool_output` が入る(report JSON が大きくなるのみ)。

## 確認済み(静的な読解と上記の実行による)

- fail-closed: 収集失敗、評価例外、対象なし、simulation 不成立の各分岐が purge の前で止まる。purge の `when` は `status == unevaluated` かつ `not ansible_check_mode`。`purge_started` は purge task の直前に立つ。
- rescue の合成: block 全体が `status == unevaluated` で守られ、purge 前の失敗は `aborted`、purge 着手後はすべて `broken`。`ansible_failed_task` と `_kernel_cleanup_purge` が未定義でも `default` で落ちない。rescue 後も final report と通知は always の後続 task が実行する。
- `broken` → `_apply_failed` 真 → 末尾の `Re-raise` でplay失敗。他に `abort_type` を読む機構は repo 内に無い(`grep` 確認)。
- Jinja の `None`/空文字: `default` は未定義にだけ使われ、`| bool` 付きの比較。収集・評価の空 stdout は `trim | length` で判定している。
- 削除は `dpkg --purge <名前列挙>` のみ。argv は list。`apt-get` は simulation(`-s`)のみ。
- メタパッケージ検証が削除前後の名前集合比較であること、`proxmox-ve` と `proxmox-default-kernel` の `ii` 確認、boot-tool 出力の不変、hook 失敗文字列の検査。
- 本番の task ファイルに試験用の結果注入口は無い(command path の変数化のみ)。
- Policy SB-100 は requirement(post-healthcheck `OK`・実行中が最新・boot-tool と実行中を残す・simulation に他のpackageが出れば削除しない・検証不成立でFAILED)と整合。
