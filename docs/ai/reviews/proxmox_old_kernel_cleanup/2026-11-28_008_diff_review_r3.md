## 非同期purgeの契約の確認

読解と試験の両方で確認した。

- **着手の判定**: `purge_started` は purge task の直前に立つ。起動task自体が失敗・unreachable・job id 無しのときも、後続assertで落ちて rescue に入り、`purge_started` が真なので `broken`。「着手した可能性があれば `broken`」の安全側に倒れる。
- **待機のtimeout**: コマンド自身は `timeout 1800s`(+kill 10秒)、asyncの上限は +30秒、待機は5秒×366回で約1830秒。command timeoutが先に効き rc=124 → assert不成立 → `broken`。待機が尽きた場合も `finished` 偽で assert 不成立 → `broken`。
- **接続断**: 起動応答の断・完了照会の断のどちらも `ignore_unreachable` で受け、assertで通常の失敗に変換する(UNREACHABLEはrescueに入らない点を正しく扱っている)。試験は本物のlocal connection継承のpluginで両方を再現し、`broken`/FAILED/終了2を確認している。pluginは `tests/connection_plugins/` にあり、本番のplaybook・roleの探索経路に入らない(`ANSIBLE_CONNECTION_PLUGINS` で試験だけが指す)。
- **check mode**: gateが先に `skipped` にし、purge taskも `not ansible_check_mode` で二重に守る。試験が collector・dpkg・apt の呼び出しゼロとpackage状態不変を確認。
- **`always` 内の失敗の吸収**: 事後観測は nested block/rescue。block外の task は `set_fact`(local)と `ignore_errors`+`ignore_unreachable` の cleanup のみで、unreachableでalwaysが落ちる経路を見つけなかった。`broken` はどちらのrescueも `failed_task` を立てるため「Mark apply failed」の参照も欠けない。purge失敗後に追加観測も失敗した場合は最初の失敗理由を保持する。
- **ジョブ残留**: 完了したjobだけ `mode: cleanup`。未完了を消さない設計は意図どおり。残留しうる経路は下記 Minor 1。

## Minor(non-blocking)

1. **接続断のあと、host側にpurgeが残っているのに通知から分からない。** 起動応答の断(job idを持たない)と完了照会の断のどちらでも、purgeがhost側で動き続けうる(最長約30分)まま、事後の収集・`dpkg --audit`・report・Slackへ進み、`broken`/FAILEDで終わる。FAILEDで weekly full は次のnodeへ進まないので影響はnode内に閉じ、事後観測が途中状態を拾っても `broken` は変わらない。ただし、reportにjob idが無く、reason/通知にも「dpkgがまだ動いている可能性」が出ない。Yoshinobuが同じ週に再実行すると、前段のdpkg lockと干渉して別の失敗に見える。対応案: `broken` のreasonに接続断の場合は「host側のpurgeが継続している可能性があります」を足し、取れるならjob idをreportへ入れる。契約(接続断は `broken`)は満たしているため blocking にしない。
2. **「完了照会が最後まで終わらない」経路が試験に無い。** `purge_timeout` はコマンドのtimeoutで rc=124 になる経路で、待機ループが尽きる経路やasync上限で打ち切られる経路は通していない(ロジックは単純で、読解では `broken` に倒れる)。
3. **become下のasync・実SSHは試験できていない。** 試験はlocal connectionで、本番のrootへのbecomeとSSH multiplexingは通っていない。初回の本番観測(AC1)の項目に、`async_status` の応答と所要時間を加えてよい。
4. **mutationの検出が文言の緩い正規表現。** `assertRaisesRegex("warning.*error")` は、無関係な失敗(`run_case` が `result.stdout` を AssertionError に入れる経路)の出力に両語が入れば誤って成立しうる。現状は意図どおり `assertEqual` の差で失敗していることを確認した(実害は将来の誤検出のみ)。
