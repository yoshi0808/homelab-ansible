# Requirement: Proxmoxパッチ適用の最後に古いkernelを削除する

日付: 2026-11-28 / 起票: Coordinator / 発案: Yoshinobu
改訂: 2026-11-28 計画査読(`_002_plan_review.md`)のM1〜M6とMinor、およびYoshinobuが両nodeで採った `proxmox-boot-tool` とsimulationの出力(本書7章末)を反映
工程の記録: 計画査読はClaude Codeのsubagent(Reviewer)で行った。規定の起動経路(`scripts/codex-role.sh plan-reviewer`)ではなく、Coordinatorの起動誤りである。指摘はすべて採り入れた。
承認: Q3・Q4・SB-100の文はYoshinobu承認済み(2026-11-28)。

## 1. 問題定義

pve1 / pve2 には、`proxmox-kernel-*-pve-signed` が状態 `ii` で残り続けている(2026-11-28 `pkg-list` で確認。pve1 29個、pve2 33個)。週次パッチは新しいkernelを入れるが、古いものを消す工程が無いため、kernelが更新されるたびに1つずつ増える。

両nodeとも、起動用のESPは `proxmox-boot-tool` が管理しており、ESPに入っているのは同ツールが選んだ3つ(6.17.13-21、7.0.14-28、7.0.14-30)だけである。**それ以外の版は起動メニューに出ず、ルートファイルシステムに残っているだけ**であり、消しても起動できる版は変わらない。

## 2. ゴール

kernelの更新で再起動した週に、新しいkernelで無事に起動したことを確かめた直後、起動に使われていない古いkernelを削除し、何を消したか(または消さなかった理由)を完了通知の本文に載せる。

## 3. 非ゴール

- **`apt autoremove` も `apt-get purge` も使わない。** aptは依存を満たすために別パッケージを消したり入れたりする(7章末の実測では、メタが指す版を消そうとすると無署名版を新規に入れる案を出した)。
- **kernelのメタパッケージ(`proxmox-kernel-<series>`、`proxmox-default-kernel`)は消さない。** 6.17系列を使い続けるかは別の判断である。
- **残す版を自前で計算しない。** 版の並べ替えやメタの依存解析はせず、`proxmox-boot-tool kernel list` に従う(R2)。
- **kernelの更新による再起動をしなかった週は掃除しない。** 更新が無い週(weekly fullが適用roleに入らない)も、更新はあったが再起動しなかった週も含む。
- ESPの同期を独自に行わない。ESPに載っている版は削除対象にならないため、同期の必要が生じない。
- 再起動の要否判定・適用・退避の流れは変えない。既存の再起動検出が `proxmox-kernel-6.17` / `proxmox-kernel-7.0` しか比較しない穴は別案件とする。
- 1回あたりの削除数に上限を置かない。初回の一括削除はCoordinatorが観測する(10章)。

## 4. ユーザーストーリー

- Yoshinobuとして、毎週のパッチの完了通知を見るだけで、古いkernelが片付いたこと、または片付けなかった理由を知りたい。
- Yoshinobuとして、新しいkernelで起動できたと確かめられない週には何も消されず、削除で何かが壊れた週はそれが見出しで分かり、次のnodeへ同じ削除が進まないようにしたい。

## 5. 要件

### P0(Must)

- **R1 実行位置と条件**: 削除処理は `roles/proxmox_patch_apply_node/tasks/main.yml` の `always` 節、post-healthcheckの最終値が確定した後・final report作成の前に置く(`block` 末尾は再起動前で、post-healthcheckもまだ無いため不可)。次がすべて成り立つときだけ削除に進む。
  - 適用が失敗していない(`_apply_failed` が偽)
  - **今回の実行で再起動した**(`_apply_reboot_done` が真)
  - post-healthcheck(再試行後の最終値)が `OK`
  - **この時点で採り直した** `uname -r` のkernelが、インストール済みのkernel本体の中で最新である(`_apply_collect.running_kernel` は再起動前の値なので使わない)
  - `--check` ではない(`tags: [destructive]`、`when: not ansible_check_mode`)
- **R2 残すもの**: `proxmox-boot-tool kernel list` の「Manually selected kernels」と「Automatically selected kernels」の和に、動いているkernelを加えた集合を残す。それ以外の `proxmox-kernel-<ver>-pve-signed`(状態 `ii`)を削除対象とする。`proxmox-boot-tool` が失敗した、出力を解析できない、集合が空、または動いているkernelがインストール済みの一覧に見つからない場合は**何も削除しない**。
- **R3 削除は `dpkg --purge` で名前を指定して行う**: dpkgは名指ししたパッケージしか消さず、他のインストール済みパッケージが依存しているものは「dependency problems - not removing」で拒否する(7章末の実測)。巻き添えの削除は、この仕組みによって起こらない。
- **R4 削除前の検査(fail-closed)**: 削除の直前に、同じ対象で `dpkg --simulate --purge` と `apt-get -s purge` を行い、次をすべて満たすときだけ削除する。満たさなければ何も削除しない。
  - dpkgのsimulationがエラー無しで終わる
  - aptのsimulationの `Remv` / `Purg` 行の集合が削除対象と完全に一致する
  - aptのsimulationに `Inst` / `Conf` 行が1つも無い(依存を満たすための差し替えが要る対象が混ざっていないこと)
  - どちらのsimulationも失敗・空出力・解析できない行が無い
- **R5 失敗の吸収と既定値**: 削除処理は `always` 内のnested `block` / `rescue` に入れ、どこで失敗してもfinal reportとSlack通知が必ず出るようにする。削除の結果を表すfactsは**処理に入る前に「未評価」の既定値で初期化**し、通知本文の組み立てで未定義参照が起きないようにする。dpkg / apt / `proxmox-boot-tool` の呼び出しにはtimeoutを付ける。
- **R6 結果の区分と通知**: 削除の結果を次の4つに区分し、apply reportのJSONと完了通知の本文に載せる。
  - `removed`: 削除し、R7の検証も通った。本文には削除した件数と版の範囲(最古〜最新)、残した版を載せる。全版の一覧はreportに残す(通知の文字数上限で適用パッケージ一覧が削られないように)
  - `skipped`: R1・R2の条件に当たった、または削除対象なし。本文に理由を1行
  - `aborted`: R4の検査で止めた、または削除処理の途中で失敗した。**通知のstatusを `warning` にし、見出しに警告が出るようにする**(`[SUCCESS]` のままにしない)。適用の結果(SUCCESS/FAILED)と終了コードは変えない
  - `broken`: 削除した後、R7の検証に通らなかった。R8に従う
- **R7 削除後の検証**: 削除の直後に次を確かめる。
  - `dpkg --audit` が空
  - R2で残した版、kernelのメタパッケージ、`proxmox-ve` が状態 `ii` のまま
  - `proxmox-boot-tool kernel list` の結果が削除前と同じ
  - 削除の出力にhookの失敗が無い
- **R8 削除で壊れたときの扱い**: R7に通らなかったnodeは、**適用の結果をFAILEDにする**。weekly fullはpve2がFAILEDならpve1へ進まないため、pve2で壊れた削除がpve1で繰り返されない。
- **R9 Policy改訂**: `docs/ai/policies/proxmox_operations_policy.md` のSB-004(無人のremoveを自動適用しない)の例外として、本案件の削除を書き足す(SB-100として新設済み)。改訂文はYoshinobuの承認を得てから入れる。
- **R10 試験できる形**: R1〜R4の判定を `retry_healthcheck_once.yml` と同じく独立したtaskファイルに切り出し、本体と試験の双方が**同じファイルをinclude**する(既存の `_eval_*` のように本体の断片を複製しない)。`proxmox-boot-tool kernel list`・dpkg一覧・両simulationの出力の解析はPythonの純関数とし、fixtureで単体試験する。収集はshell、判定はAnsible / Pythonとする(`skills/ansible-implementation-style/SKILL.md` の責務分離)。

### P1(Should)

- **R11** 状態 `rc` のkernelパッケージも同じ処理でpurgeする。
- **R12** reportの既存キー `running_kernel`(再起動前の値)は流用せず、削除処理で採った値は別のキー名で残す。

## 6. 成功指標

- kernelが更新されて再起動した週の後、各nodeのkernel本体が `proxmox-boot-tool kernel list` の集合(現状では3個)だけになっている。
- `aborted` / `broken` が出た週は、通知の見出しだけでそれが分かる。

## 7. 受入条件

- **AC1** Given 適用成功・再起動あり・post-healthcheck `OK`・動いているkernelが最新、When 週次パッチがそのnodeを終える、Then R2の集合以外のkernel本体が削除され、R7の検証が通り、完了通知(Slack `#patches`、status `ok`)の本文に件数・版の範囲・残した版が載り、apply reportのJSONに全一覧が入り、playの終了コードは0。**削除後に `pkg-list` / `kernel-status` で残った集合がR2と一致する**ことをCoordinatorが確かめる。
- **AC2** Given 再起動していない、post-healthcheckが `OK` でない、または適用が失敗した、When そのnodeを終える、Then 何も削除されず(`skipped`)、通知の本文に理由が載る。終了コードと見出しは従来どおり。
- **AC3** Given 再起動後の動いているkernelがインストール済みの最新ではない、または `proxmox-boot-tool kernel list` が失敗・空・解析不能、When そのnodeを終える、Then 何も削除されず(`skipped`)、通知に理由が載る。
- **AC4** Given dpkgのsimulationがエラー、aptのsimulationに対象外の `Remv` / `Purg`・対象の欠落・`Inst` / `Conf` 行がある、どちらかのsimulationが失敗・空・解析できない、のいずれか、When 削除処理に入る、Then 何も削除されず(`aborted`)、通知のstatusが `warning` で見出しに警告が出て、適用の結果と終了コードは変わらない。
- **AC5** Given 削除処理のどこかでtaskが失敗する、When そのnodeを終える、Then final reportとSlack通知が出る(既定の「結果を取得できませんでした」文に置き換わらない)。
- **AC6** Given R7の検証に通らない、When そのnodeを終える、Then 結果がFAILEDになり、weekly fullは次のnodeへ進まない。
- **AC7** Given `--check`、When 実行する、Then 削除の操作は行われない。
- **AC8** Given 解析関数、When fixture(7章末の実測出力そのもの、現状のpve1/pve2の一覧、pinあり、`rc` 混在、動いているkernelが一覧に無い)を与える、Then 期待どおりの残す集合・削除対象・検査結果を返す。
- **AC9** `proxmox_operations_policy.md` に、R9の例外が承認済みの文で入っている。

**どこで観測するか**:
- AC2〜AC5・AC7はdecoy上で、R10の切り出したtaskファイルを通して検証する。AC8は単体試験で検証する。
- AC6の「次のnodeへ進まない」は既存のweekly fullの分岐をそのまま使うため、FAILEDになることまでを検証する。
- AC1は本番の初回でしか分からない。実際のdpkgとhookの挙動、所要時間、通知の文字数がこれに当たる。実装後にkernelが更新される最初の週に、Coordinatorが削除後の状態と通知を確かめる。

### 実測(2026-11-28、Yoshinobuが両nodeで実行。状態を変えない)

- `proxmox-boot-tool status`: 両nodeとも `System currently booted with uefi`。pve1はESPが2つ(ZFSミラー)、pve2は1つ。いずれも `6.17.13-21-pve, 7.0.14-28-pve, 7.0.14-30-pve` で構成。
- `proxmox-boot-tool kernel list`: 両nodeとも Manually selected `None`、Automatically selected は上の3つ。
- メタが指す版を名指ししたsimulation(`proxmox-kernel-6.17.13-21-pve-signed`):
  - `apt-get -s purge` は、メタを消すのではなく、依存を満たすため **無署名版 `proxmox-kernel-6.17.13-21-pve` を新規に入れる**案を出した(`Purg` 1行 + `Inst` / `Conf`)。`Remv` / `Purg` だけを見る検査では、この差し替えを見逃す。
  - `dpkg --simulate --purge` は `dependency problems - not removing` で拒否した。
- `apt-get -s` の「no longer required」一覧には、`proxmox-boot-tool` が選んだ3つと `6.17.2-1` が載っていない(`6.17.2-1` は手動導入の印が付いていると見られる。印そのものは未確認)。

## 8. オープンクエスチョン

- **Q1(決定済み)** 残す版は数で決めず、`proxmox-boot-tool kernel list` に従う(Yoshinobuの「3つは固定でよいのか」を受けて、2026-11-28)。
- **Q2(決定済み)** 掃除はkernelの更新で再起動した週だけ(Yoshinobu、2026-11-28)。
- **Q3** R8(削除後の検証に通らなければFAILEDにして次のnodeを止める)。推奨: このまま。
- **Q4** 手動導入の印が付いている `6.17.2-1`(インストーラが入れた最初のkernelと見られる)も削除対象に含めるか。推奨: 含める。起動に使われておらず、dpkgが依存を守るため。

## 10. タイムライン

急がない。本番で初めて効くのは、実装後にkernelが更新されて再起動する最初の週である。初回はたまった分(現状からの見込みでpve1が26個、pve2が30個。Q4で `6.17.2-1` を含める場合)がまとめて消えるため、その週はCoordinatorが通知と削除後の状態を確かめる。
