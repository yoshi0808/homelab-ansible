## 1. 計画として成立しているか(構造)

**挿入位置は実在する。ただし `block` の中ではなく `always` の中である。**

- R1 の「post-healthcheck 最終値が OK」は `always` 内の 1003-1032行(`Retry...` と `Re-determine...`)で初めて確定する。削除は 1032 と 1034(`Build and save final report`)の間にしか置けない。requirement §9 の「post-healthcheck の後、report作成の前」は正しい。
- `block`(103-945行)の末尾は再起動前の状態で、post-HC が無いので使えない。`rescue` は `block` の失敗しか受けない。**`always` 内のタスクが失敗しても `rescue` は掛からない。**

## Major(blocking)

### M1 always 内で失敗すると report と Slack が出なくなる。「失敗を吸収する」仕組みが requirement に無い

- always の既存タスクは全て個別に `ignore_errors: true` を持つ(983, 989, 1013, 1067, 1202, 1235...)。素の削除タスクが1つ失敗すると、以降の always(report、Slack、`Re-raise`)が実行されない。R4「適用結果を失敗にしない」はこのままでは成立しない。
- 通知本文を作る set_fact(1075-1202行)は **1つの巨大な set_fact に `ignore_errors: true`**。新しい節で未定義変数を1つ参照するだけで、全体が失敗し、`_notify_body` は初期値 `パッチ適用の結果を取得できませんでした`(69行)のまま送られる(SUCCESS の週でも)。
- 求める変更: (a) 新facts(`_kcleanup_*`)を 39-77行の初期化 task に足し、**既定値は「未評価/結果不明」を表す値**にする(「削除対象なし」を既定にしない)。(b) 削除側は nested `block/rescue` か全taskの `ignore_errors` + `failed_when: false`、いずれにせよ rescue 側が必ず「失敗」を表す状態を書く。(c) apt に `timeout` を付ける。無いと apt が止まったとき Semaphore ジョブも通知も止まる。強制終了すると dpkg が中断状態で残り、翌週の `apt-get check`(`apt_check` abort)に出る。(d) 接続断・`from_json` 失敗・空 stdout も「結果不明」として通知に出す。

### M2 R3 が fail-open になり得る(simulation の読み方が未規定)

- 既存の解析は `^Remv ` だけを見る(275-278行)。R7 の `rc` を purge すると、`apt-get -s purge` は `Purg` 行で出る(一般知識。ここでは実行していない)。`Remv` だけを数える実装だと「対象外の remove は無い」と誤判定して実削除に進む。**simulation と実削除は同じコマンド(remove か purge か)・同じ引数にし、`Remv|Purg` の両方を数えることを要件に書く。**
- R3 は「対象以外が remove されるなら止める」とだけ書いている。**simulation 自体が失敗(rc≠0)・出力が空・解析できない・対象の一部が見つからない** ときも止める、と明記する(`docs/ai/core.md` の「判定できないときは止める」)。判定は「simulation の remove/purge 集合 == 削除対象集合」の集合一致にする。
- 実削除の直前に simulation と同じ一覧を使うこと(間に別の apt 操作が入らない)も書く。

### M3 R4 の「警告として載せる」だけでは壊れていることが見えない

- 通知の channel/status/subject は `_apply_abort_type` / `_apply_failed` / `_post_hc_status` だけで決まる(1191-1199行)。削除の警告が出ても subject は `[SUCCESS]`、channel は `patches`、status は `ok` のままになる。AC4 は「通知に警告が載り」としか書かず、subject・status・channel を決めていない。
- 毎週 `patches` の SUCCESS 本文の末尾に警告が出続けても、気づかれずに放置される(R3 が毎週発動し続ける状況が典型)。
- 求める変更: 削除の警告時の `_notify_status`(`warning`)・subject・channel を AC に書く。今の post-HC 非OK の `[WARNING]` に相当する扱いにするのが筋。「削除しなかった理由」のうち、正常な理由(対象なし)と、異常を示す理由(R3 発動、simulation失敗、削除失敗)を分け、後者だけ警告に上げる。
- 失敗の中身(R3 が掛かったパッケージ名、apt の最後の数行)も本文に載せる。

### M4 削除後の検証が無い。post-HC は削除より前、pve1 へ進む判定も削除前の値

- post-HC は削除の前に採る(R1 の条件)。削除が dpkg を壊しても、メタ/`proxmox-ve` を巻き込んでも、post-HC は OK のままになる。weekly_full は「pve2 の post-HC OK の場合だけ pve1 へ進む」(policy 221行)ので、pve2 の削除に失敗しても pve1 へ進み、同じ削除をもう一度行う。
- 求める変更: 削除直後に、少なくとも (a) `dpkg --audit` が空、(b) 残すべき集合(実行中・1つ前・メタの依存先)が `ii` のまま、(c) `proxmox-ve` / `proxmox-default-kernel` / 各メタが `ii` のまま、(d) 起動構成の整合(M5)を確認し、結果を report と通知に出す。いずれか欠けたら警告(M3)。
- さらに、pve2 の削除が警告で終わったときに pve1 の削除を行わない、という扱いを検討する(Minor 側の判断で足りる。決めてよい)。

### M5 起動まわり(proxmox-boot-tool / ESP / pin)が非ゴール1行でしか扱われていない

- requirement は「ESP の同期は kernelパッケージの postrm hook に任せる」とするが、その hook が実際に何を行うか、2台で何が使われているか(grub と systemd-boot-efi の両パッケージが入っており、どちらで起動しているかは `pkg-list` / `kernel-status` からは判定できない)を確かめていない。**未確認。** 以下は一般知識で、現物では確かめていない: proxmox-kernel-helper は postinst/postrm hook で `proxmox-boot-tool` の refresh を呼ぶ。1パッケージごとに postrm が走るので、26〜30パッケージの削除で hook も同数回走る。ESP が満杯・未マウントなどで hook が失敗すると、dpkg が中途半端な状態で残る。
- `proxmox-boot-tool kernel pin`(次回以降の起動kernelの固定)がある場合、固定された版が削除対象に入ると起動できなくなる。R2 の残す集合に pin が入っていない。
- 求める変更: 実装前に両nodeで `proxmox-boot-tool status`(起動方式)と pin の有無を Coordinator が確認し結果を記録する。pin を読む収集を script に入れ、pin された版を残す集合へ足す(読めない/解釈できないなら削除しない)。初回の所要時間を見積もり、timeout を決める(M1)。
- `kernel-status` の `/boot/vmlinuz-*` と dpkg の突合(ESP と /boot の整合まで見るかは Coordinator の判断。最低限、削除前後の `/boot` 一覧を report に残す)。

### M6 テストの形では R1〜R4 の配線が検証されない

- 既存の `tests/_eval_*.yml` は main.yml の該当 task を「verbatim で複製」し、grep で一致を見る方式(`_eval_notify_case_parity.yml` の冒頭に明記)。`_eval_*` は role 本体を通らない。今回の削除は block 外の `always` 内で、`when` の組み合わせ(R1 の4条件)と配置順(最終 `_post_hc_status` の再判定 1032 より後であること)が本質なので、複製した断片を試験しても、本体の配線は試験されない。
- decoy で role を通しても、`pvesh` が無く Phase 1 の最初で rescue に落ちる。つまり decoy で本体を通せるのは「適用失敗 → 何も削除しない」(AC2 の一部)だけ。
- 求める変更: R1 の判定と R2/R3 の判定を **`tasks/` 下の独立ファイル(例 `retry_healthcheck_once.yml` と同じ include_tasks 方式)に切り出し、role 本体と試験の双方が同じファイルを include する**。複製と grep 一致の方式を新たに増やさない。入力(`_apply_failed`、`_post_hc_status`、running/installed、simulation 出力)をfactで渡せる形にすれば、AC2〜AC4 を本物のコードで通せる。
- 通知節を足すと、`_eval_notify_case*.yml` の複製と grep 一致試験の更新も要る(未確認の漏れが出やすい)。§9「触るもの」に試験側の更新を明記する。

## Minor

1. **R2 の定義の詰め(fixture に必要)**
   - `uname -r` は `<abi>-pve`、パッケージ名は `proxmox-kernel-<abi>-pve-signed`、dpkg の Version は別の文字列(今は一致しているが別物)。running との突合を名前(abi)で行うのか Version で行うのかを決める。running が一覧に無い(別種のkernel、unsigned 等)ときは何も削除しない、を fixture に入れる。
   - 版の順序は dpkg の比較規則を使う(文字列順は不可。今の一覧にも `7.0.2-6` / `7.0.6-2` / `7.0.12-1` / `7.0.14-2` / `7.0.14-30` があり、文字列順だと狂う)。R8 の「Python の純関数」はコントローラ(quory)で動くので、`apt_pkg` が無い前提で dpkg 比較を自前実装するか、host 側の `sort -V` / `dpkg --compare-versions` を収集に含めるかを決める。
   - メタの依存先は `Depends` から取る(`|` による代替、版制約を含む)。このとき選択を誤ると R3 が発動し続けて「何も消えない」になるだけで安全側。**安全の網は R3 であり、R2 のメタ項目は機能のため**、と位置づけを分けて書く。
   - 「インストール済みの kernel 本体のうち最新」の対象は `ii` のみとし、`dpkg --audit` が空でない/`iU`/`hi` などがあるときは削除しない、を R1 に足す。
2. **Q3(kernel更新のない週も走らせる)は前提が成立しない週がある。** weekly_full は `NO_UPDATES` なら apply を skip する(playbook 387-400行)。「今朝の形」(更新なしの週)では apply role に入らず、掃除も走らない。更新はあるが kernel 更新はない週には走る。Q3 は「更新ありの週は走らせる」と読み替え、2026-12-05 に初回が走るかも「更新がある週かどうか」に依存する(requirement §10 の「早ければ」に条件を書く)。
3. **初回の削除が最大かつ最も未検証。** pve2 が30件、pve1 が26件を1回で消す。1回あたりの上限(例: 古い順に N 件まで)を置くと、postrm の所要時間・失敗の影響・通知の長さが小さくなる。置かない場合は、初回だけ Coordinator が立ち会って観測する、と §10 に書く。
4. **通知の長さ。** `notification_body_limit` は 3500。パッケージ一覧の描画は本文全体の長さを測って切り詰める(1220行)。26〜30版の列挙は短い1行に畳む(版をカンマ区切り、または件数+範囲)。そうしないと適用パッケージ一覧が初回に削られる。
5. **report のフィールド。** 既存の `running_kernel`(1061行)は再起動前の値。流用せず、新しい名前(例 `kernel_cleanup` 配下)に再起動後の running と削除結果を入れる。`proxmox_running_versions` は report の `result` / `reboot_done` / `reboot_trigger` / `run_timestamp` だけを読むので、フィールド追加は影響しない(`latest_apply` を確認)。
6. **§9 の「どの setup playbook が要るか」は前提が違う可能性が高い。** 既存の collect script は role の task が毎回 `/usr/local/sbin/` へ copy する(197-229行)。新しい script も同じ形にすれば setup playbook は要らない。要るかどうかを実装記録に書く、でよいが、先に「要らない見込み」を書いておく。copy は `block` 内(Phase 2)にあり、事前チェックで abort した週には配備されないが、その週は削除しない(R1)ので問題ない。
7. **R6 の置き場。** SB-003/SB-004/SB-039 は dist-upgrade の simulation の remove を指す。今回の purge は別の操作で、字面の矛盾ではなく「例外」というより「別の操作の追加」を明記する形が自然。SB-003 の本文以外に、weekly flow を説明する 299行付近と `docs/ai/context/system/proxmox.md` に追記が要るかを実装前に確かめる(未確認)。承認文は requirement のとおり Yoshinobu の承認後に入れる。
8. **既存の再起動検出の穴(今回の範囲外、事実として記録)。** `proxmox-patch-apply-collect.sh` は `proxmox-kernel-6.17` / `proxmox-kernel-7.0` だけを比較する。新系列(例 7.2)のメタが入ると、再起動が要らないと判定され、running ≠ 最新のまま AC3 に入り、掃除が静かに走らなくなる。AC3 の理由を「警告」に上げておけば(M3)この穴が見える。穴自体の修正は別案件。
