## 着手時の契約確認 (2026-09-06)

実装前にCoordinatorへ境界の判断を返した。以下は照会時点の経緯であり、
現在の結論は後段の「改訂契約への実装」が置き換える。

- 現行 `roles/semaphore_upgrade/tasks/upgrade.yml` の
  `Reinstall pinned Semaphore package without needrestart restart` は切り離し予約より
  前に実行され、直後のsha256 assertがtarget binaryへの置換を確認している。
  この順序では、遅延後に走行中jobを検出して停止を中止しても、AC4の
  「版もバイナリも変わらない」は満たせない。前案件P0-2がinstallをAnsibleへ
  割り当てていた点と、新案件P0-3 / AC4 / AC7の境界が両立しない。
- 推奨: Ansibleは取得・照合・退避・遅延予約までを担い、detached側が走行中jobを
  確認した後にinstall・MainPID不変/sha256照合・stopへ進む。job検出時はinstallにも
  stopにも進まず中止する。これは前案件の責務分担を変更するためCoordinatorの
  契約整理を待つ。install後からstopまでの競合窓も残るので、直前再確認でjobが
  見つかった場合の扱いを含め、AC4の「変わらない」の基準時点を確定する必要がある。
- OQ1の暫定提案は予約時点から60秒を既定・下限とする。実測30秒はjob開始から
  stopまでの時間であり、予約後の確定猶予30秒を測ったものではない。既存
  `roles/ubuntu_vm_full_upgrade/tasks/reboot_quory.yml` の30秒下限に対して余裕を
  とる提案で、60秒が確定を保証するという実測根拠は無い。最終job確認で起動元が
  runningのままなら中止する防御と、Testerによるquory実測を必須とする。
- 既存reboot実装のtimer待機中はserviceがinactiveになる落とし穴、予約確認は
  timer/service双方を見ること、通知の既存様式は指定された現物で確認した。

## 待機上限の提案・制限

`semaphore_upgrade_job_wait_timeout`の既定120秒、許容1〜600秒を提案した。
これは猶予ではなく、起動元確定と他job終了の合計待機上限である。短いjobを待てる
2分の運用上の予算とし、超過時は旧binaryへ戻して再試行可能にする。600秒の上限は
設定誤りで新版binaryを載せたまま無期限に滞留しないための安全弁。値に確定保証の
実測根拠は無く、Testerによるquory確認を要する。終端/空きを観測すれば即時進む。

最後のDB読取りからstopまでの極小の競合窓は残る。scheduleの排他ロックを取得する
機構ではないため、完全なjob投入抑止は保証しない。起動元識別は既存のplaybook一致
方式を継承し、明示IDの環境変数に依存しない。別CLIと同playbook jobを同時に起動
しない前提がある（複数該当は拒否）。

AC2には旧契約の「猶予の下限」が残っている。P0-1/§9の改訂に従い固定猶予は
廃止し、待機上限の正の整数・600秒以下をassertした。AC2文言の追随はCoordinatorへ
返す。AC1/AC4のquory実走はTesterへ持ち越す。
