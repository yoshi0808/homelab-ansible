# requirement: 切り離しの境界を直す(起動元ジョブの確定と、通知の中身)

作成: 2026-09-06 / Coordinator
発端: 2026-09-06 の quory 本番実行(ジョブ #986)。版上げ自体は成功したが、2つ壊れていた。
前案件: `docs/ai/reviews/semaphore_upgrade_automation/`(2026-09-05 クローズ)

## 1. 問題定義

**版上げは成功した。** quory は `2.19.12-012ed06-1788086239`(community)で稼働し、Slack へ `status: success` / `reading_path_check: passed` が届いた。ansy と同一のビルドである。**壊れたのは版上げではなく、その周辺2つである。**

### 1.1 起動元のジョブが確定できない

**ジョブ #986 の行は `running` のまま残り、Yoshinobu が手で止めるまで消えなかった。**

| 時刻(JST) | 事実 | 手段 |
|---|---|---|
| 06:22:39 | #986 開始 | `semaphore-query running` |
| 06:23:09 | `Stopping semaphore.service` → `Started` → `Semaphore 2.19.12-...` → `Server is running` | `journal-unit semaphore.service` |
| 06:23頃 | Slack へ `[Semaphore upgrade] SUCCESS (upgrade)` | Yoshinobu 受信 |
| 06:30:01〜06:30:12 | `SAFE: Recovery monitoring check`(#987)が `success` | `semaphore-query task-time 987` |

**#986 の出力は `Start detached Semaphore transaction through PID 1` で切れている。** `systemd-run` が遅延なしでスクリプトを起動するため、Semaphore の停止が、起動元のジョブが終わり切る前に来る。ジョブの cgroup ごと殺され、最終ステータスを書く主体がいなくなる。

**これは前案件の R1 が顕在化したものである。** ansy の Semaphore はジョブを実行できない(EXEC-052)ため、この経路だけ quory が初回だった。**AC3(Ansible 側が rc=0 で終わる)と AC12(ジョブが緑で終わる)は quory では成立していない。**

**放置すると次が止まる。** `roles/semaphore_upgrade/tasks/upgrade.yml` の preflight は `playbooks/semaphore_upgrade.yml` に一致する走行中ジョブを「自分」として数え **`<= 1` を要求する**。停滞した行が残る限り、次の版上げは2件と数えて拒否される。(ロールバック側には同じ判定が無く、止まらない。)

**同型の問題は repo で既に解かれている** — `roles/ubuntu_vm_full_upgrade/tasks/reboot_quory.yml`(quory が自分を reboot する)。**そこにある解と、その解が持つ落とし穴(タイマーとサービスのどちらの状態を見るか)は、当該ファイルのコメントが正本である。**

### 1.2 通知が結果を伝えていない

実際に届いた本文:

```
[Semaphore upgrade] SUCCESS (upgrade)
host=quory result={'status': 'success', 'mode': 'upgrade', 'version': '2.19.12',
'reading_path_check': 'passed'}; the launching Semaphore job only confirmed
detachment, not this result
```

| # | 欠陥 |
|---|---|
| ① | **末尾の但し書きの宛先が違う。** 「起動元のジョブは切り離ししか確認していない」は**ジョブを見ている人**への注意であり、それを結果通知の中へ貼ったため、「これは結果ではない」と読める文が結果の中にある |
| ② | **本文が Python の dict のダンプである。** 報告ではなくデバッグ出力 |
| ③ | **旧版が無い。** repo の既存規約「upgrade 系の通知は old → new のバージョン必須」に違反する。**今回いちばん大きい変更である pro → community のエディション切り替えにも一言も触れていない** |
| ④ | **日本語でない。** この repo の通知は日本語である |

**原因は文体の好みではなく、経路と契約の両方が欠けたことである。** repo の通知はすべて `roles/common_slack/tasks/notify.yml` を通り、様式はその1本が強制していた。切り離しスクリプトは Ansible の外で走る設計上そこへ届かない。**そして前案件の requirement は、通知が飛ぶこと(P1-2)と検証時に抑止すること(P0-14)しか書かず、中身を一度も規定しなかった。** 様式を運ぶ仕組みから外し、外れた先の契約を書かなかった。

### 1.3 停止の窓へ、別のジョブが入りうる

**今回は当たらなかった。** #987 は 06:30 で、停止は 06:23 に終わっていた。**しかし preflight の「他に走行中のジョブが無い」は preflight 時点の判定であり、実際の停止はその後に来る。** 1.1 の遅延を入れると窓はさらに広がる。**窓の中で schedule が発火すれば、そのジョブは cgroup ごと殺される。**

## 2. ゴール

1. **起動元のジョブが、版上げの前に確定する。** Semaphore が最終ステータスを記録し終えてから停止が来る
2. **通知が、それだけ読めば何が起きたか分かるものになる**
3. **停止の直前に、他のジョブが走っていないことを確かめ直す**

## 3. 非ゴール

| やらないこと | 理由 |
|---|---|
| `dry_run` → `apply` の改名 | **別案件(案件B)。** `ubuntu_vm_full_upgrade` / `prometheus_update_check` と**稼働中のスケジュール3件**に及び、転記を誤ると月次の dry-run が月次の本番 full upgrade になる。影響範囲が違う |
| 切り離しを `common_slack` へ戻す | 構造的に不可能。Ansible の外で走ることが設計であり、そこは変えない |
| 停滞したジョブ行を自動で片付ける仕組み | 1.1 を直せば行は停滞しない。**残骸の掃除機構を足すより、残骸を作らないほうが先である** |
| quory の再版上げ | 既に 2.19.12-community で稼働している。本案件は次回以降に効く |

## 4. 要件

### P0

| # | 要件 |
|---|---|
| P0-1 | **起動元の Semaphore ジョブが確定してから停止が来ること。猶予を秒数で決め打ちしない**(2026-09-06 改訂)。**切り離しスクリプトが、起動元ジョブの行が終端状態に達したことを観測してから停止へ進む。** 上限は設け、達しなければ中止する。**固定の遅延にしない理由**: ①何秒で足りるかを誰も知らない(実測では開始から停止まで30秒あっても確定していなかった) ②遅延はそのまま「新版のバイナリが載ったまま旧版が動いている」窓の長さであり、短いほどよい |
| P0-2 | **切り離しが受理されたことの確認が、遅延を入れた形でも成立すること。** 「起動した」と「まだ待っている」を取り違えないこと |
| P0-3 | **停止の直前に、他の走行中ジョブが無いことを確かめ直す。** 在れば**待つ**。上限まで空かなければ中止する。自分自身の起動元ジョブは P0-1 で終端に達しているため、ここで数える対象ではない |
| **P0-8** | **中止するときは、install で置き換えたバイナリを元へ戻してから終わる**(2026-09-06 追加)。**install は Ansible 側に残す**(前案件 P0-2。install の失敗をジョブの失敗として見える形に保つため)ので、中止の時点でディスク上のバイナリは既に新版である。**`Restart=always` があるため、この状態を放置すると、以後クラッシュや再起動が起きたときに検証もロールバックも伴わずに新版が立ち上がる。** 中止は「安全に止まった」でなければならず、次の事故を仕込んだ状態で終わってはならない |
| **P0-9** | **ロールバックがジョブ台帳を巻き戻すことを、実行した人が知る形にする**(2026-09-06 追加、本番で実測)。`semaphore.db` を書き戻す以上、**退避時点より後のジョブ記録は失われ、退避時点で走行中だった行が復活する。** 2026-09-06 08:12 のロールバックで、#987 と #988 が消え、手で止めたはずの #986 が `running` へ戻った。**復活した行は次の版上げを preflight で拒否させる**(同一 playbook の走行中ジョブが2件に数えられる)。**機構としては避けられない** — DB を戻す以上、台帳も戻る。**したがって、隠さずに伝える** |
| P0-4 | **通知は日本語で、それだけ読んで何が起きたか分かること。** 必須要素: ホスト、**旧版 → 新版**、**旧エディション → 新エディション**、結果、ロールバックしたならその事実と復帰先、JST の時刻、退避の場所 |
| P0-5 | **但し書きの宛先を直す。** 「起動元のジョブの緑は切り離ししか意味しない」はジョブを見る人への注意である。**結果通知の本文へ、結果を打ち消す形で置かない** |
| P0-6 | **`result` の生ダンプを本文にしない。** 構造化データが要るなら結果ファイルが持つ |
| P0-7 | **ロールバック後に `dpkg -V` が不一致を示すことの説明は、ロールバックが起きたときだけ出す**(前案件で入れた `dpkg_bookkeeping`)。成功時に混ぜない |

### P1

| # | 要件 |
|---|---|
| P1-1 | 中止・失敗・自身の異常終了のいずれでも通知が出る(前案件 P1-2 を維持) |
| P1-2 | 通知の本文が Slack の表示上限に収まる |

### Won't

- 通知経路の共通化、テンプレート化。**1箇所しか無いものを共通化しない**

## 5. 受入条件

| AC | Given / When / Then |
|---|---|
| **AC1** | Given quory の Semaphore ジョブとして起動する / When 版上げを実走させる / Then **ジョブが `success` で確定して行が残る。** `running` のまま滞留しない。停止はその後に来る |
| **AC2** | Given 猶予の下限を下回る値 / When 流す / Then 明確なメッセージで停止する(rc 非ゼロ) |
| **AC3** | Given 切り離しの予約が入った直後 / When Ansible が受理を確認する / Then 「予約済みで待機中」と「もう起動した」の両方を成功として扱い、「まだ何も起きていない」と誤読しない |
| **AC4** | Given 停止までの窓の中で他のジョブが走っている / When 切り離しスクリプトが停止しようとする / Then **上限まで待ち、空かなければ停止せずに中止する。Semaphore は停止も再起動もされず、稼働中の版は変わらない。** バイナリは P0-8 により元へ戻っている(2026-09-06 訂正 — 初版は「版もバイナリも変わらない」と書いたが、install は切り離しより前に Ansible 側で終わっているため、手を打たなければ成立しない) |
| **AC5** | Given 版上げが成功する / When 通知が届く / Then **日本語で、旧版 → 新版とエディションの変化が本文にある。** dict のダンプが無い。ロールバックの説明も混ざらない |
| **AC6** | Given 版上げが失敗し自動ロールバックする / When 通知が届く / Then **失敗であることと復帰先の版・エディションが分かり、`dpkg -V` の不一致が想定内であることが書かれている** |
| **AC7** | Given 中止(AC4)/ When 通知が届く / Then **Semaphore を止めていないこと、稼働中の版が変わっていないこと、バイナリを戻したことが分かる。** 「何も起きなかった」ではなく「安全に引き返した」として読める文面であること |
| **AC9** | Given 起動元ジョブの行が上限まで終端に達しない / When 切り離しスクリプトが待つ / Then **停止せず中止し、P0-8 と同じ後始末をして通知する** |
| **AC10** | Given 起動元ジョブが在るはずの状況(Semaphore のジョブとして起動された)/ When 起動元の行が見つからない / Then **明確なメッセージで停止する。待機を飛ばして先へ進まない。** 起動元が在るか無いかは**観測して決める**(`ansible-playbook` を手で流した場合は0件が正しい)。「0件でも通す」と「1件を要求する」を実行の形で切り替えること |
| **AC11** | Given 待機が例外(DB が読めない等)で失敗する / When 中止して後始末する / Then **通知に、Semaphore を止めていないこと・バイナリを戻したことが出る。** 中止の理由によって安全宣言が出たり出なかったりしないこと |
| **AC12** | Given ロールバックが成功する / When 通知が届く / Then **台帳が巻き戻ったこと、いつの時点へ戻ったか、それ以降のジョブ記録が失われたことが本文にある。** あわせて、**復活した走行中の行が次の版上げを止めうること**と、その対処(UI で止める)が分かる |
| **AC13** | Given 走行中の版上げジョブが複数あると preflight が判定する / When 拒否する / Then **どの行が該当するかと、ロールバック直後にはこれが起こりうることが `fail_msg` から分かる。** 「同時実行を拒否した」だけで終わらない |
| **AC8** | Given 既存の抑止機構 / When 抑止して実走する / Then 本番 Slack へ POST されず、本文が結果ファイルから読める(前案件 P0-14 / AC14 の維持) |

**観測点**: AC1 は Semaphore のジョブ一覧、AC4〜AC7 は Slack の実文面と結果ファイル。

## 6. リスク

| # | リスク | 対処 |
|---|---|---|
| R1 | **AC1 と AC4 は quory でしか検証できない。** ansy の Semaphore はジョブを実行できない(EXEC-052) | ansy では機構の側(予約が入り、猶予の後に発火すること)まで測る。**ジョブとして走らせたときの確定は quory で初めて分かる。前案件と同じ非対称であり、今回はそこで壊れた** |
| R2 | 猶予を入れる分、停止までの窓が広がり、schedule と当たる確率が上がる | P0-3 / AC4 がその窓を塞ぐ。**猶予はジョブ確定に足りる最小限にする** |
| R3 | quory を再度上げ下げしないと AC1 が踏めない | **ロールバックと再版上げで踏める**(前案件の Tester が ansy で使った手順と同じ)。実施の可否は Yoshinobu の判断 |

## 8. 工程

1. Implementer(codex 側)
2. 独立レビュー(Claude subagent)
3. Tester — ansy で機構、**quory で AC1 / AC4**(ロールバック → 再版上げ)
4. Auditor、`status.md` 更新、commit
