## 2. AC1 / AC4 をどの観測で判定するか

### AC1(起動元ジョブが `running` のまま滞留せず `success` で確定する)

**判定手順**

1. Coordinator の合図でボタンが押される直前・直後に `semaphore-query running 200` を叩き、新規ジョブIDを捕捉する(押下直後は `running` の一覧に載るはずで、ここで「予約済みで待機中」と「もう起動した」を取り違えない — 一覧に出た時点で「起動した」と扱う)。
2. 一定間隔で `semaphore-query running 200` を再実行し、対象IDが一覧から消える時刻を記録する。
3. 消えた直後に `semaphore-query task-time <ID>` を叩き、最終列(終了時刻)と `status` を確認する。

**合格/不合格の区別**

- **合格**: `task-time <ID>` が `success` を返し、かつ終了時刻が入っている。かつ `running` から消えた時点で `success` が確定していた(=`running` に載っている間に手で止める必要がなかった)。
- **不合格**: (a) `running` に対象IDが一定時間(`job_wait_timeout` の上限120秒+停止処理の時間を超えて)残り続ける、または (b) `task-time` が `success` 以外(`error`/`stopped`)を返す、または (c) `journal-unit semaphore.service` 側で `Stopping`→`Started` が `task-time` の終了時刻より前に来ている(=ジョブの行が確定する前に停止が来た、前回 #986 と同型の欠陥の再発)。
- 前回 #986 との対比: 今回は `task-time` が `stopped`(手で止めた)ではなく `success` で自然に確定することを見る。`stopped` が出た場合は前回と同型の再発として扱う。

### AC4(停止までの窓に入ってきた `SAFE: Time sync check` が無傷で完走し、版上げ側はそれを待ってから停止へ進む)

**判定手順**(回1: ロールバック→約30〜40秒後に Time sync check)

1. ロールバック起動直後、`semaphore-query running 200` でロールバックジョブと、その後投入される Time sync check ジョブの両方のIDを捕捉する。
2. `journal-unit semaphore.service 30m 300` で `Stopping semaphore.service` の時刻を確認する。
3. Time sync check の `semaphore-query task-time <ID>` で終了時刻と `status` を確認する。
4. 2と3の時刻を突き合わせる。

**合格/不合格の区別**

- **合格**: Time sync check の終了時刻が `Stopping semaphore.service` の時刻より**前**にあり、かつ `status=success`。まだ Time sync check が走行中の間は `Stopping` が来ていないことを `running` の一覧(ロールバック側のみ残り Time sync check も残っている状態)で確認する。
- **不合格(中止が発動したケースを含む)**: Time sync check が `running` から消える前に `Stopping semaphore.service` が来ている(cgroupごと殺された=無傷でない)、または Time sync check の `status` が `success` 以外。この場合、`job_wait_timeout` の上限まで待って中止(`aborted`)したはずなので、`journal-unit semaphore.service` 側に `Stopping` 行が**一度も現れない**ことも合わせて確認する(P0-8により何も変えずに引き返しているはず)。
- **中止(AC4のThen節が求める側)を正として扱う場合の確認**: Semaphore の稼働版が変わっていないこと(`journal-unit semaphore.service` に新しい `Stopping`/`Started` が無い)、`is-active` が継続して `active`(同一 MainPID)であることを `status` で確認する。バイナリが元に戻っていることの直接確認(sha256)は §3 のとおり観測不能なため、**間接証拠(MainPID不変・版文字列不変)までしか quory-investigate では踏めない**。
