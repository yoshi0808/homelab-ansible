## 2. 受入条件との対応

案件フォルダ内の Tester 記録(`_022`)は SAFE 3件の段階で ansy に対して行ったものであり、上表はその後の本番での観測にあたる。**新たに満たされた AC は無い** — いずれも `--check` の経路(AC1)と、管理外を消さないこと(AC11)、移行期間に `false → true` を発行しないこと(AC12/AC14)の再観測である。

**この案件は、有効化の PUT を一度も発行していない。** quory の19件は全件が既に `active: true` であり、`pending_activation` は5回とも0件だった。closed-world 化の後も同じである。R12 の4条件のうち「明示許可」が既定で不許可であることが、最後に残る歯止めとして働いている。

**requirement が挙げた3つ目の本番事故(closed-world 後に ansy へ apply すると19件が有効化される)は、実物で止まることを確認した。** ansy で closed-world・管理外0件・`-e semaphore_schedules_allow_activation=true` を与えた `--check` を実行し、`pending_activation` が19件並んだ状態で、R15 の allowlist だけが理由として残り `allowed: false` になることを観測している。

## 4. 運用の起点

**新しい playbook を足すときは、template と schedule を同じ変更で決める**(Yoshinobu、2026-08-10)。定期実行させるなら、既存の実行時刻と競合しない cron を選ぶ。19件の実行時刻が `roles/semaphore_templates/defaults/main.yml` で一望できることが、その判断を可能にしている。

**schedule を先に作ってはならない。** R10 により schedule が指す template は適用時点で実在している必要があり、同一変更で両方を足す場合は template を先に適用する2段階になる。この制約は `_017` High 5 として「`--check` と apply で前提が分岐する」と指摘され、Coordinator が `_018` §3 で採らないと判断したものである。**判断は変えていないが、制約が効くのは新規 playbook を足す人であるため、その人が読む場所(カタログ先頭)へ明記した。**
