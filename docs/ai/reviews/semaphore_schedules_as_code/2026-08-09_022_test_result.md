## 1. 環境上の不具合(findings、Coordinatorへ)

**`reports_base_dir` の既定値(`/home/yoshi/homelab-ansible/reports`)へ、ansy 上の SSH 接続ユーザー `ann` が書き込めない。** `reports/` は `yoshi:yoshi` 所有・mode `775` で、`ann` は所属グループ外のため「その他」権限(`r-x`)しか持たず、`reports/semaphore-templates/` や `reports/semaphore-schedules/` の新規作成に失敗する(`Errno 13 Permission denied`)。この失敗は **schedule 側だけでなく template 側の report task でも同一に発生し**、`--check` を含むあらゆる実行が report 保存の手前で停止する。今回は `-e reports_base_dir=/tmp/semtest-reports` で回避して以降のテストを行ったが、この回避なしには ansy 上で本 playbook を一切実行できない状態だった。ansy 側のディレクトリ権限([mkdir -p]して `ann` が書けるようにする、または `ann` を `yoshi` グループへ加える等)の是正が必要。この修正は環境側であり、私はリポジトリ・ansyの権限設定のいずれも変更していない。

## 5. 未実施・未検証と理由(再掲、判断込み)

- **AC16 / AC20 / AC22 / AC23**: playbook 内部の特定タスク間(preflight の GET と後続の PUT の間)に外部から状態変更を割り込ませる、というタイミング精度を要求する。Tester は検証目的で対象実装へフック・sleep を追加する権限を持たず、外部からの精密なタイミング制御手段も無いため、実 API に対して確定的には再現できなかった。Implementer の `roles/semaphore_templates/tests/task_flow/` がこの制御フロー(block/rescue/always とレポート保存の分離)を fixture 上で通しているが、fixture は実 API を経由していない。**残存リスク**: R16(有効化直前の再取得)・R8(stage1 のPUT直前 identity 確認)・R8-3(stage2 直前の再確認)の実装が主張どおりに機能するかは、実 API に対しては未確認のまま Coordinator の判断に委ねる。AC3/AC15 の同一実行で「新規作成によって schedule 集合が変化したため有効化が全件見送られた」という R16 の動作が**意図せず**実地で1回観測できた(§2 AC15 の実行時、レポートの理由に「preflight 時点から schedule 集合が変化しているため有効化しない(R16)」が出現している)。これは AC16 の fixture そのものではないが、R16 の判定ロジックが実 API 上で少なくとも1系統は正しく発火することの傍証にはなる。
- **AC21**: R9⑦(公開可否 allowlist)を通過しつつ Semaphore API 自身が拒否する `task_params` を用意できなかった。allowlist の許可キー(`force_renew`/`dry_run`/`debug_level`)は実測(6.5節)で Semaphore が実際に保持することが確認済みの値であり、この3キー以外を preflight へ通す経路が無い。**残存リスク**: R9⑦のallowlistと実際のSemaphore側の受理範囲がズレた場合(将来 Semaphore がアップグレードされ、現在許可しているキーの扱いが変わった場合など)にAC21が担保する「HTTP成功でも値が保存されなかったことを検出する」経路が正しく動くかは未確認。R16-2の単体テスト(Implementer報告)はこの経路をmockで確認済みだが、実APIでの確認ではない。
- **AC7 の2件以上一致**: 同名 template の複製作成は許可範囲(schedule の作成・変更・削除)を超えるため行っていない。0件一致は実測済み。
- **AC15 の別名URL・未知URL**: requirement が明記するとおり、到達不能URLは接続失敗が先に起きるため gate 判定へ到達しない。ansy の別名(`/etc/hosts` の短縮名)は TLS 証明書の SAN 不一致で同様に先に失敗する。canonical 一致(不許可なら不可)と canonical 不一致(既定、AC15本則、PASS)の2点で判断材料は揃っていると考えるが、requirement が要求する「4通り目」の完全な確認ではない。
