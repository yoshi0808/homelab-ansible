# requirement: Semaphore schedule をカタログの管理下に置く

作成日: 2026-08-09 / 作成: Coordinator
改訂: 2026-08-09(査読 `_002` 〜 `_006` を反映。**5回のパッチで文書が自己矛盾したため全面的に書き直した**。要件IDは通し番号で振り直してある)

## 1. 問題定義

Semaphore の template は 2026-08-04 に `roles/semaphore_templates/` のカタログが正本になったが、**schedule は対象外のまま**である。その結果、**「どの playbook をボタンにするか」は Git にあるが、「いつ押されるか」は Git の外にある。**

現に quory では **19件の schedule が全て `active=true` で稼働している**。この中には `UN-SAFE: Proxmox Weekly Full Patch` が含まれる。**本番の定期実行の一覧と時刻が、リポジトリのどこにも無い。**

## 2. ゴール

- schedule の定義(対象 template、cron、有効/無効、**実行パラメータ**)の正本をリポジトリに置く。
- quory と ansy の双方へ、同じカタログから冪等に反映できる。
- 反映前に差分を読める(`--check`)。

## 3. フェーズ

本件は2つのフェーズを持ち、**要件の効き方がフェーズで変わる**。フェーズは R17 のフラグが表す。

| フェーズ | 状態 | schedule の新規作成 | 管理外 schedule |
|---|---|---|---|
| **移行期間**(フラグ未設定) | カタログが稼働中19件を書き写している途中 | **起こらない**(R6 が preflight で拒否) | 正常。レポートへ列挙し、**有効化だけ見送って処理は続ける** |
| **closed-world**(フラグ設定済み) | 19件すべてがカタログに載り、管理外が0件になった | 可能。ただし常に無効で作る(R13) | **異常。preflight で全書き込みを停止** |

## 4. 非ゴール

- **schedule の削除を行わない。** カタログに無い schedule に DELETE を発行しない。既存19件が本番稼働中である。
- **rename を扱わない。** 移行期間は R6 が拒否し、closed-world は R18 の管理外検出が停止させる。**したがって rename が通るフェーズは存在しない。** 手順の設計は P2(R20)。
- **inventory / environment を対象にしない。**
- **`SEMI-SAFE: Semaphore templates setup` を扱わない。** この template 自体がカタログ外(自己参照を避ける既存判断)であり、**現行19件にこれを指す schedule は0件**(実測)。
- **Semaphore の UI 権限を変更しない。** 手による編集は従来どおり可能である。
- **Semaphore サーバの timezone 設定を変更しない。** 読むだけである。
- 新しい playbook を追加しない。既存の `playbooks/semaphore_templates_setup.yml` を使う。

### 保証しないこと

**UI で人が直接作った二重 active を、この仕組みは取り除けない。** UI の書き込み権限を残すこと(上記)と、schedule を削除しないこと(R5)を両方採る帰結である。**埋めるには削除権限を持たせるか、Semaphore の状態をリポジトリ側の台帳で二重に持つかのどちらかになり、どちらもこの案件が意図的に避けている形である。**

reconcile が保証するのは次に限られる。

1. **reconcile 自身が二重 active を作らない** — 移行期間は新規作成が起こらず(R6)、closed-world では新規が必ず無効で作られる(R13)。
2. **移行期間**: 管理外を検出したら**レポートへ列挙し、有効化だけを見送る。その他の管理項目(cron・対象 template・`true → false`)の更新は継続する。** 終了コードは `0`。
3. **closed-world**: 管理外を検出したら **preflight で全書き込みを停止**する(非ゼロ)。

**Semaphore にトランザクションも ETag も無いため、preflight と書き込みの間の競合を完全には排除できない。** R16 が幅を狭めるだけである。

**`run_at` は cron スケジュールでは使われていない。** DB の read-only 照会で19件すべて NULL であり、`type` も空である(6.5)。**失われる値が存在しないため、API 応答に現れないことは本件では実害にならない。** ただし受入条件が使う「実行前後の GET 応答の完全一致」は API に現れるフィールドの範囲でしか成立しない、という限界そのものは残る。

## 5. ユーザーストーリー

- Yoshinobu として、本番の定期実行の一覧と時刻をリポジトリで読みたい。
- Coordinator として、schedule を変える提案をするとき、差分を `--check` で示してから適用したい。
- Operator として、schedule の現状を尋ねられたとき、リポジトリを正本として答えたい。

## 6. 要件(すべて P0。P2 は末尾)

### 6.1 カタログと同定

| ID | 要件 |
|---|---|
| R1 | schedule の定義を `roles/semaphore_templates/defaults/main.yml` のカタログへ置く。1エントリが持つのは **schedule 名 / 対象 template 名 / cron / active / `task_params`** の5項目である。<br>**`task_params` を管理対象に含める理由は、そこに実行の危険度を変える値が入っているためである** — 実測で `Ubuntu vm full upgrade` の `dry_run=true`、`Cert_renew` の `force_renew=false` がここにあった(6.5)。cron や active と同じく定期実行の内容を決めるため、非管理にすると「UI で `dry_run` を外しても差分に出ず復元もされない」状態が残る。<br>**カタログは API が返した形のまま不透明な塊として持ち、比較は全体一致で行う。** 型の全体像は未確認(OQ7)だが、**受け取った値をそのまま返す限り型を知る必要は無い**(未知キーは API 側が捨てる)。既存19件の値をカタログへ転記する |
| R2 | **同定は schedule の `name` で行う。** schedule object は `description` を持たない(実測)。template の同定方式(`description` のマーカー)と異なることを、実装とカタログのコメントに明記する。**`name` は全フェーズで変更できない**(R6 と R18 が拒否する) |
| R3 | **`template_id` をカタログへ書かない。** 適用先で毎回 template 名から解決する。id は Semaphore が採番し API で指定できず、ansy と quory で一致しない |
| R4 | **project も名前から解決する。** id を前提にしない |

### 6.2 書き込みの安全性

| ID | 要件 |
|---|---|
| R5 | **削除を行わない。** カタログに無い schedule へ DELETE を発行しない |
| R6 | **移行期間は、カタログの `name` がすべて API 側に実在していなければならない。** 実在しない `name` が1件でもあれば preflight で非ゼロ停止し、書き込みを1件も発行しない。この期間のカタログは稼働中19件の**書き写し**であり、新規追加も rename も正当な操作ではない。**この規則により移行期間には新規作成そのものが起こらず、rename 由来の二重 active が原理的に生じない** |
| R7 | **`--check` で差分だけを出す。** 読み取り(token 読取・名前解決・API GET・差分計算・レポート保存)は `--check` の有無にかかわらず実行し、**書き込み(POST/PUT)だけを `ansible_check_mode` でゲートする** |
| R8 | **更新は get-then-merge-then-send で行う。merge 元は単一取得 `GET /api/project/<n>/schedules/<id>` とする。** 取得した raw object へ**管理5項目の effective desired state**(下記 R8-2)を上書きし、全フィールドを送り返す。<br>**この方式は対象版(2.18.4)で実測して確定した**(下記 6.5)。公式リファレンスが例示する6項目だけの PUT は、**実データの `task_params` を消す**。`task_params` には `dry_run` や `force_renew` といった**実行パラメータが入っており、消えると定期実行の内容が変わる**。<br>**一覧取得 `GET /api/project/<n>/schedules` を merge 元にしてはならない** — `task_params` を含まない一方、`tpl_name` という**実体の無い結合列**を含むため、そのまま送り返すと管理外の値を送ることになる。<br>**merge 元は、各 PUT を発行する直前に取得したものでなければならない。** preflight 時点の取得を apply まで持ち回ると、その間に UI で変更された値を古い値で上書きする(lost update)。**直前の取得で `name` または `id` が preflight 時点と変わっていたときの扱いはフェーズで異なる。**<br>**移行期間**: その1件の PUT を見送り、理由をレポートへ出して**他の更新は継続する**(終了コード `0`)。<br>**closed-world**: **残りの POST / PUT をすべて中止し、非ゼロで終了して再 preflight を要求する。** identity が変わったことは、preflight 後に管理外または置換 schedule が生じた証拠であり、R18 の「管理外なら全書き込み停止」と同じ安全側へ倒す。<br>**既に発行済みの PUT は取り消せない。** この残余をレポートへ明記する。ETag が無いため取得と PUT の間の窓も消せないが、最小化する |
| **R8-2** | **「カタログ値」と「その実行が実際に書く値(effective desired state)」を分けて定義する。** 書き込み payload と書き込み後の検証は、カタログ値ではなく **effective desired state** を基準にする。<br>`name` / `cron_format` / `task_params` は**常にカタログ値**。**`template_id` はカタログには無く、カタログの template 名から当該 API で一意に解決した id である**(R3)。R1 の5項目は**論理項目**であり、API 上の比較フィールドとは対応が1対1ではない。<br>**`active` の desired state は段階別に定義する**(R8-3 が二段階に分けるため、一段階の定義では正常系が破綻する)。<br>**第1段階の desired `active`** — 新規作成なら `false`(R13)。既存なら **カタログが `false` のときだけ `false`(即時無効化)、それ以外は観測値のまま**。第1段階では有効化しない。<br>**第2段階の desired `active`** — 第1段階で管理4項目の一致を確認済みで、かつ R12 の4条件を再確認できたときだけ `true`。それ以外は第2段階そのものを行わない。<br>**カタログ値と desired の差は失敗ではない。** 「有効化待ち」または「有効化を見送った理由」としてレポートへ出す。この区別が無いと、安全ゲートを無視して有効化するか、安全に見送った正常系を失敗にするかの二択になる |
| **R8-3** | **管理項目の更新と有効化を同じ PUT に載せない。二段階に分ける。**<br>**第1段階** — 管理項目(`name` / 解決した `template_id` / `cron_format` / `task_params`)と、**第1段階の desired `active`**(R8-2。新規は `false`、既存は**カタログが `false` のときだけ `false`、それ以外は観測値**)を書き、**直後の単一 GET で第1段階の desired と一致することを確認する**。**第1段階で有効化は行わないが、即時無効化(`true → false`)はここで行う。**<br>**第2段階** — 第1段階の一致が確認できた schedule についてのみ、R12 の4条件を**再確認**したうえで**有効化だけを行う PUT** を発行し、**そちらも直後の単一 GET で検証する**。<br>**一つの PUT に同居させると、API が `task_params` のキーを捨てても同じ payload の `active: true` は受理され得る。** その時点で schedule は既に有効であり、R16-2 が不一致を検出しても**取り消せない**。**危険な実行パラメータが保存されなかった schedule を起動しない**ための順序保証であり、実装手段の指定ではない。<br>**第2段階の PUT も R8 に従う** — 単一 GET を取り直して全フィールドを送る。**「有効化だけを行う」とは minimal payload のことではなく、論理差分が `active` だけであるという意味である。**<br>**第2段階の直前の単一 GET で、管理4項目が第1段階で検証済みの値のままであり、かつ `active` が `false` であることを確認する。** **不一致なら、その schedule を有効化せず、残りの有効化 PUT もすべて中止して非ゼロで終了する。**<br>見送り(終了コード `0` で続行)にしない理由は、**第2段階は closed-world フェーズでしか起こらない**(R12 の条件①)ためである。closed-world で管理項目が実行中に変わったことは、R18 と R8 の closed-world 分岐が「全書き込み停止」で扱う事象と同じであり、そちらへ揃える。これにより**第1段階の後に UI で変更された値を、未検証のまま有効化 PUT へ載せない**。<br>新規作成は従来どおり `false` で作り(R13)、有効化は後続の実行で第2段階として行う |
| R9 | **全カタログの preflight を完了するまで、書き込みを1件も発行しない。** 検査するのは ①カタログ内 schedule 名の重複 ②API 側 schedule 名の重複 ③template 名の解決(0件・複数件の双方) ④cron 文字列の妥当性 ⑤型と必須項目 ⑥移行期間なら R6、closed-world なら管理外の不在 ⑦**カタログの `task_params` が公開可能な値だけであること**。<br>⑦は**このリポジトリが公開前提であるため**に要る — `task_params` は API から取得した不透明な塊をそのまま転記するため、秘密情報が紛れ込む経路になり得る。**秘密候補を検出したとき、および判定できないときは停止する**(判定不能を成功側へ倒さない)。**2026-08-09 時点の19件は実測で全て公開可能な内容だった** — 16件が空の `environment`、残る3件が `force_renew` / `dry_run` / `debug_level` のみで、秘密情報も IP も含まない。**決定的エラーが1件でもあれば非ゼロで停止し、部分適用を残さない**。cron の妥当性の判定規約は**対象 Semaphore 版が受理する grammar を実測して確定する** — 既存19件を valid fixture、当該版が拒否する代表値を invalid fixture として test_plan で固定する |
| R10 | **schedule は、適用時点で Semaphore に実在する template だけを参照する。** template と schedule を同一変更で追加する場合は、template を先に適用する2段階とする。`--check` と apply で前提が分岐しないことをこの制約で担保する |
| R11 | **cron を解釈する timezone を、書き込み先と同じ API から照合する。** **書き込みに使うのと同一の API base URL に対する `GET /api/info` の `schedule_timezone`** とカタログの前提値を照合し、不一致なら停止する。**設定ファイルや環境変数を読まない** — 既存 playbook は `hosts:` を固定して API 接続先だけを `-e` で切り替えるため、ホスト上の設定を読むと接続先と観測対象がずれる。同じ応答の `version` も記録する |

### 6.3 有効化(`active`)

| ID | 要件 |
|---|---|
| R12 | `active` をカタログが持つ。**`true → false` はカタログの値へ即座に確定する。`false → true`(有効化)は次の4条件をすべて満たしたときにのみ行う** — ①**closed-world フェーズであること**(移行期間は理由を問わず有効化しない) ②管理外 schedule が0件であること(R14) ③実行ごとの明示的な許可があり、かつ接続先が許可対象であること(R15) ④preflight 時点から schedule 集合が変化していないこと(R16)。有効化は「apply のたびに無条件で確定する」対象ではない |
| R13 | **新規作成は常に `active: false` で行う**(closed-world フェーズでのみ発生する)。カタログの `active: true` は**既存 schedule の更新にのみ**適用する |
| R14 | **管理外 schedule が1件でも存在する間は、`false → true` を行わない。** 停止はせず、有効化だけを見送って理由をレポートへ出す |
| R15 | **有効化は実行ごとの明示的なパラメータで許可する。既定は不許可。** さらに、**書き込みに使う正規化済みの API base URL が、カタログに定めた canonical な本番 URL と完全一致するときだけ許可する(allowlist 型)。一致しないものはすべて不許可とする。**<br>**「ansy でなければ許可」という否定判定(denylist 型)にしない** — 別名・alias・別表記の DNS 名で同じサーバへ到達できてしまい、fail-open になる。正規化は末尾スラッシュ等の表記差を吸収するだけで、別名までは同一化しない。<br>接続先の判定に inventory host を使わない — 既存 playbook は `hosts: quory` を固定したまま API 接続先だけを `-e` で切り替えるため、識別できない。closed-world フラグはカタログ側にあり両ホストへ同じ値が渡るため、フラグでは検証用複製を守れない。**許可・不許可と判定に使った URL をレポートへ必ず記録する** |
| R16-2 | **POST / PUT の直後に単一 GET を行い、管理5項目が「その段階の desired state」(R8-2)と完全一致することを確認する。第1段階は第1段階の desired と、第2段階は第2段階の desired と比較する。** 不一致なら非ゼロで停止し、当該 schedule の有効化を行わない(第1段階で不一致なら第2段階へ進まない)。 API は**未知のキーを黙って捨てる**(6.5)ため、書き込みが成功しても保存された値がカタログと違うことがある。**正規化された値や捨てられた値を成功として扱わない。** これは `task_params` を不透明な塊として持つ設計の代償であり、**書き込み後の検証で閉じる** |
| R16 | **有効化を発行する直前に schedule 集合を再取得し、preflight 時点から変化していたら有効化を見送る。** トランザクションも ETag も無いため完全な排他はできない。この残余をレポートと記録へ明記する |

### 6.4 フェーズと可視化

| ID | 要件 |
|---|---|
| R17 | **closed-world フェーズへの移行を、単調で明示的なフラグで表す。** カタログのエントリ数で判定しない(将来20件目を正規に追加した時点で検査が解除されてしまう)。**フラグは人がコミットで立て、実装は降ろさない** |
| R18 | **カタログ外の schedule を「管理外」としてレポートへ列挙する(削除はしない)。** 判定は R9 の preflight の一部として書き込みの前に行う。**移行期間はレポートのみで終了コード `0`。closed-world では preflight で非ゼロ停止し、POST / PUT / DELETE を1件も発行しない** |
| R19 | **schedule の差分レポートを、template のレポートと同時に読める形で保存する。差分の schema は管理5項目を前提とする。** 既存の `latest.json` を上書きしない。パスと schema を実装時に確定し、記録へ残す |

### 6.5 対象版 API の payload 契約(2026-08-09、ansy の 2.18.4 で実測)

**この節は測定結果であり、設計判断ではない。** 実装とテストはこの契約に従う。

| 観測 | 結果 |
|---|---|
| 6項目のみの PUT(公式リファレンスの例) | **`task_params` が消える。** 実データ(`SAFE: Authy healthcheck daily`)で before/after を比較して確認 |
| 全フィールドの PUT(`task_params` を含む) | **保持される。** 上記で消した値を同じ方法で復元し、before と完全一致することを確認 |
| `task_params` の書き込み可否 | **正しい形なら書ける。** 型付きで `environment` / `params` を持ち、**未知のキーは黙って捨てられる**(`{"probe":"keepme"}` は反映されなかった) |
| 一覧 `GET .../schedules` | **`task_params` を含まない。** 代わりに `tpl_name`(template 名の結合列)を含む |
| 単一 `GET .../schedules/<id>` | `task_params` を含む。`tpl_name` は含まない |
| `run_at` | **POST / PUT / GET のどの応答にも現れない。** API からは観測も送信もできない |
| 実データの `task_params` | **19件すべてが非空。** うち3件が実行パラメータを持つ — `Cert_renew` が `force_renew=false`、`Ubuntu vm full upgrade` が `dry_run=true`、`Prometheus update check` が `dry_run=true` と `debug_level=4` |

| `run_at` / `type` / `delete_after_run` | **単発実行スケジュール用の列であり、cron スケジュールは使っていない。** DB の read-only 照会で、19件すべて `run_at` が NULL、`type` が空であることを確認した |
| `task_params` の格納 | **別テーブル `project__task_params` にあり、schedule 行は `task_params_id` で参照する。** **PUT は既存行を更新せず新しい行を作り、古い行を孤児にする。** 復元実験で参照先が変わり、現在 ansy に未参照の行が3件ある(22行中) |

**測定は ansy(quory の複製)で行い、変更した1件は同じ手段で復元して before と完全一致を確認した。** probe として作成した schedule は削除済み。**API 経由の観測に加え、`run_at` と `task_params` の格納は DB の read-only 照会で確認した。**

## 8. 受入条件

**各 AC の Given に、フェーズ・API 接続先・有効化許可の3つを明記する。** これらの組合せで期待結果が変わるため。

**AC1(差分表示)**
Given 移行期間、接続先は quory、有効化は不許可。カタログの全 `name` が API 側に実在し、うち1件の管理項目の値が API と異なる
When `--check` 付きで実行する
Then **終了コードは `0`**。差分がレポートへ出力され、**Semaphore 側は1件も変更されていない**(実行前後で GET 応答が一致する)。Slack 通知は飛ばない

**AC2(移行期間は未実在の name を弾く)**

When 実行する(`--check` の有無を問わない)
Then **preflight で非ゼロ停止**し、その `name` がメッセージに出る。**POST / PUT / DELETE がいずれも0件**で、実行前後の API 状態が完全に一致する

**AC3(新規作成は常に無効で作られる)**

**AC4(更新で非管理フィールドを壊さない)**

When `--check` なしで実行する
Then **終了コードは `0`**。`cron_format` がカタログ値になり、**`id` は変わらない**。**書き込み直後の単一 GET で、管理5項目以外の非管理フィールドが実行前と一致する**。fixture には `task_params` が非空の schedule を使う

**AC5(冪等 — カタログが `active: false`、または有効化が絡まない場合)**

**AC6(有効化は別の apply で行われ、その後に冪等になる)**

When ①有効化を**不許可**で再実行する ②有効化を**許可**して再実行する ③さらに再実行する

**AC7(名前解決の失敗で停止)**

When 実行する(`--check` の有無を問わない)
Then **非ゼロで停止**し、どの schedule のどの template 名が何件一致したかがメッセージに出る。**書き込みが1件も発生していない**

**AC8(schedule 名の重複を通さない)**
Given いずれのフェーズでも(移行期間・接続先 quory・有効化不許可を既定の fixture とする)。カタログ内、または API 側に同名の schedule が2件以上ある
When 実行する(`--check` の有無を問わない)

**AC9(preflight で部分適用を作らない)**

When `--check` なしで実行する

**AC10(timezone 不一致で停止)**

When 実行する(`--check` の有無を問わない)
Then **非ゼロで停止**し、期待値と実測値の双方がメッセージに出る。**書き込みが1件も発生していない**。照合に使った値が**当該 API 応答から得たもの**であることがレポートから分かる

**AC11(管理外を消さない)**

**AC12(移行期間は管理外があっても他の更新を続ける)**

When `--check` なしで実行する
Then **終了コードは `0`**。**cron の更新は適用される**。管理外がレポートへ列挙される。**`false → true` は1件も発行されない**

**AC13(closed-world では管理外を書き込み前に弾く)**
Given closed-world、接続先は quory。API 側にカタログに無い `name` の schedule が1件ある
When 実行する(`--check` の有無を問わない)
Then **preflight で非ゼロ終了**し、その `name` がメッセージに出る。**POST / PUT / DELETE がいずれも0件**で、実行前後の API 状態が完全に一致する

**AC14(フラグが立っていなければ、管理外0件でも有効化しない)**
Given 移行期間(フラグ未設定)、管理外0件、接続先は quory、**有効化は許可**。カタログが `active: true` を持つ既存 schedule が API 側で `false`
When `--check` なしで実行する
Then **終了コードは `0`**。`active` は **`false` のまま**で、理由がレポートに出る。**フラグを立てた次の apply で初めて `true` になる**

**AC15(canonical な本番 URL 以外では、明示許可があっても有効化しない)**

**AC23(第2段階の直前に管理項目が変わっていたら有効化せず中止する)**
Given closed-world、管理外0件、接続先は quory、有効化は許可。有効化対象の schedule が2件あり、**第1段階の検証まで正常に完了**している。**第2段階の1件目の PUT の前**に、そのうち1件の `cron_format` が UI で変更される

## 11. タイムライン考慮

**段階適用とする。カタログを一度に19件へ広げない。** reconcile が削除を行わない(R5)ため、カタログに載っている分だけが管理対象になる。

1. SAFE 分類の数件をカタログへ入れ、ansy で `--check` → 適用 → 現物確認
2. quory で `--check` → 適用 → 現物確認
3. 確認できたら次のバッチを足す。SEMI-SAFE、UN-SAFE の順で後ろへ回す
4. 19件すべてが載り、管理外が0件になったら、**closed-world フラグを人が立てる**(R17)

**移行期間中は管理外 schedule が常に存在する。** R14 により、その間 `false → true` は行われない。ansy は Restore 直後に19件すべてが `active: false` であり、これが無ければ検証 apply が定期実行を始めてしまう。closed-world 後は R15(接続先が ansy なら常に不許可)が引き継ぐ。
