## 環境と到達性

- このセッションは ansy 自身の上で動作しており(`hostname` = ansy)、`ansible-playbook` は `ansible_user: ann` で ansy.internal へ SSH する(loopback)。token は `/etc/homelab-recovery/semaphore-templates-api-token`(root:root 0600)、`sudo -n cat` で読める。

## 前提となる制約(依頼文どおり)

- ansy の schedule の作成・変更・削除、probe 用エントリの追加・削除は行ってよい。**変更したものは同じ手段で戻し、実測で確認する**。
- リポジトリ内で変更してよいのはこの2ファイルのみ。`semaphore_schedules_catalog` のような repo 側の値を変えたい場合は、**`-e` extra-vars(JSON)でカタログ全体を上書きする**(Ansible 標準の変数優先順位内であり、repo ファイルは一切変更しない)。
- `git add` / `commit` / `push` は行わない。

## 設計方針

1. **読み取り専用の直接 API 確認を先に行う**(`curl` 相当、`-v`/`-i`/`--trace` は使わない。token はヘッダにのみ載せ、出力・ログへは出さない)。ベースライン(19件、全 `active: false`、id 集合、各 `task_params`)を記録し、全テスト終了後の突合対象にする。
2. **カタログを `-e @<json>` で差し替えて fixture を作る。** 既定の3件カタログ(migration phase、SAFE 3件)をベースに、AC ごとに以下を変える。
   - 移行期間 vs closed-world: `-e semaphore_schedules_closed_world=true`
   - 有効化許可: `-e semaphore_schedules_allow_activation=true`
   - timezone 前提: `-e semaphore_schedules_expected_timezone=<val>`
   - canonical URL: `-e semaphore_schedules_canonical_api_base_url=<val>`(AC6 のみ。理由は §3)
   - カタログ全体: `-e @<json>`(1エントリの migration-phase fixture、重複名、不正 cron、存在しない template 等)
3. **管理フィールドに実差分を作るため、対象 schedule を直接 API で probe(PUT)してから `--check`→apply の順で検証する。** これにより「カタログと API が異なる」という AC の Given を、repo を変えずに再現する。
4. 各テスト後、影響を受けた schedule だけを都度 API で元の値へ戻し、**最終的に19件全件を実測で原状回復確認する**(4節)。

## §3 AC6/AC15 で canonical URL を一時的に上書きする理由

R15 の canonical URL は quory のリテラルであり、ansy からは常に不一致になる(意図どおり — OQ2参照)。これは AC15 の主張(「ansy では有効化されない」)そのものであり、既定値のままの実行で十分に確認できる。

一方 AC6 は「有効化の機構(二段階・冪等性)が正しく動くこと」を確認する AC であり、R15 の URL 判定はその前提条件の1つに過ぎない。ansy 上で AC6 を独立に検証するため、**この1テストに限り** `-e semaphore_schedules_canonical_api_base_url=https://ansy.internal:3000/api` を渡し、URL 条件だけを満たした状態を作る。これは role の実装や `defaults/main.yml` の既定値を変えるものではなく、実行時の `-e` 上書きに留まる。この上書きを使うのは AC6 のみで、AC15 の主張(既定値のままでは有効化されないこと)は別途確認する。

## §4 原状回復の確認方法

全テスト終了後、19件すべてを `GET /project/3/schedules/<id>` で取得し、最初に記録したベースライン(`id`/`project_id`/`template_id`/`cron_format`/`name`/`active`/`type`/`delete_after_run`/`repository_id`/`task_params`)と辞書として完全一致することを確認する。加えて `GET /project/3/schedules` の id 集合が19件のまま変わっていないことを確認する。probe 用に一時作成した schedule(AC3/AC19用)は `DELETE` で削除し、削除後の一覧件数が19件に戻ることを確認する。

## §5 観測できなかった項目(設計時点で判明)

- **AC16 / AC20 / AC22 / AC23**: いずれも「playbook 内部のある1呼び出しと次の呼び出しの間」(preflight の GET と、その後の PUT の間)に UI 側で状態を変える、というタイミング精度を要求する。Tester は実装コードにフックや sleep を挿し込む権限を持たず(検証目的で対象実装を変更しない — Role文書の禁止事項)、外部から実行時間を制御する手段もないため、実 API に対して確定的に再現できない。Implementer の task-flow 自動テスト(`roles/semaphore_templates/tests/task_flow/`)がこの制御フロー自体を通しているが、これは fixture 上の再現であり、実 API 経由の確認ではない。
- **AC21**: 「preflight の R9⑦(公開可否 allowlist)を通過するが、Semaphore API 自体は受理しないキー」という payload を作る必要がある。実測された `task_params` の4形(6.5節)はすべて実際に Semaphore が保持する値であり、allowlist に載っている3キー(`force_renew`/`dry_run`/`debug_level`)以外を preflight へ通す経路が無いため、この2条件を同時に満たす実値を用意できない。同様に、preflight を経由しない外部注入(API を直接叩いて schedule を先に汚す)は「apply がそれを書き込む」という AC の前提と矛盾する。
- **AC7 の複数一致(2件以上)分岐**: ansy 上に同名 template を複製作成する行為は「schedule の作成・変更・削除」の許可範囲外(template の作成は許可されていない)。0件一致は実 API で確認済みだが、2件以上一致の分岐は実 API では確認しない。
- **AC15 の「別名・別表記URL」「未知URL」の2サブケース**: requirement 自身が「到達不能URLでは接続失敗が先に起きるため allowlist 判定そのものを観測できない」と明記している。ansy 向けの別名(例: `/etc/hosts` の `ansy` 短縮名)は TLS 証明書の SAN 不一致で接続段階から失敗するため、gate の判定ロジックまで到達しない。canonical 一致(許可されない)と canonical 不一致(既定 URL、AC15 本則)の2点は確認するが、別名・未知URLの2枝は接続失敗が先行する制約により確認しない。
