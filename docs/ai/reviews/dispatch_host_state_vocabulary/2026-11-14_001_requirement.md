# Requirement: dispatchへホスト状態のread-only語彙を足す(kernel-status / kmod-list / ports / stale-libs)

作成日: 2026-11-14
起案: Yoshinobu(2026-11-14、「いちいちコマンド叩くのは面倒。ライブラリなども含めて確認できるように語彙を追加してはどうか」)

## 1. 問題定義

**脆弱性エントリ(Notion「Proxmox Watch」)を閉じる判定に要る事実のうち、開発側から読めないものが3種類ある。** 2026-11-10〜14の実例:

- ksmbd(ZDI-CAN-33774/33549)の「非該当」判定には、モジュールのロード有無と TCP 445 の待ち受け有無が要った。pve の dispatch には `ports` も `dmesg` も無く(`denied: unknown command`)、Yoshinobuが両ノードのコンソールで `lsmod` / `ss -ltnp` を叩いた。
- CVE-2026-98432 の Ubuntu 側は、修正カーネル 7.0.0-43.43 の**導入**までは `pkg-list` で読めたが、**稼働中のカーネル**を authy / monnie / quory で読む語彙が無く「未確認」で止まった(`load` も pve では denied)。
- パッケージ更新後に、置き換えられた旧ライブラリを掴んだまま動いているプロセス(=サービス再起動が要るか)は、どのホストでも読めない。

いずれも状態を変えない問いであり、答えを得るために人がコマンドを叩く工程を挟んでいる。今後も脆弱性対応のたびに同じ形で発生する。

## 2. ゴール

上の3種類の問いを、ansy から `ssh <host>-investigate <check>` だけで閉じられるようにする。

## 3. 非ゴール(やらないと決めたこと)

- **quory の `dev-investigate` へ sudo を持たせない。** `roles/dev_investigate/tasks/main.yml` 冒頭が「sudo を1つも持たない」ことを契約として明記している。`stale-libs` は quory へ足さない(Yoshinobu了承、2026-11-14)。
- **needrestart を使わない・pve へ導入しない。** pve には未導入(`pkg-list needrestart` 0件、2026-11-14)。導入すると週次パッチの apt 実行へ再起動判定の動作が加わる。Ubuntu 側にある needrestart も dispatch からは呼ばない(実装を1本に揃えるため)。
- **quory 上の Codex 経路(`homelab-investigate*.sh.j2` の wrapper)へは足さない。** 本案件は開発側(ansy)の調査語彙であり、`pkg-list` 追加時(`docs/ai/reviews/dispatch_pkg_and_schedule_vocabulary/`)と同じ扱いにする。
- サービスの再起動・リブートの**実行**は扱わない。dispatch に書込語彙を持たせない(`docs/ai/core.md`「開発と本番の境界」)。
- 既存語彙(`ports` を含む)の rename・挙動変更は行わない。
- Proxmox Watch の日次処理(稼働バージョンページ)への組み込みは本案件に含めない。

## 4. ユーザーストーリー

- Coordinatorとして、修正カーネルが**動いているか**(導入済みかではなく)を、Yoshinobuにコマンドを頼まずに確かめたい。
- Coordinatorとして、特定のカーネル機能(ksmbd 等)が有効か、特定ポートで待ち受けているかを確かめて「非該当」を判定したい。
- Coordinatorとして、ライブラリ更新後に再起動が要るプロセスが残っているかを確かめたい。

## 5. 要件

対象 dispatch は3本である。

| class | ホスト | dispatch | 調査ユーザー |
|---|---|---|---|
| Q | quory | `roles/dev_investigate/files/recovery-investigate-dispatch-quory.sh` | `dev-investigate`(sudo なし) |
| G | authy / monnie | `roles/recovery_exec/templates/recovery-investigate-dispatch.sh.j2` | `recovery-exec` |
| P | pve1 / pve2 | `roles/recovery_exec/templates/recovery-investigate-dispatch-pve.sh.j2` | `recovery-exec` |

### P0(必須)

- **P0-1 `kernel-status`**(Q / G / P、引数なし)。sudo を使わない。出力は次の3点。
  - 稼働中のカーネル(`uname -r`)
  - 導入済みのカーネルイメージ(`/boot/vmlinuz-*` のファイル名一覧)。**0件または読めない場合は、glob 文字列や空出力を正常として返さず、非ゼロで終了する**(判定不能を成功に見せない)。
  - 再起動要求(`/run/reboot-required` の有無と、存在すれば `/run/reboot-required.pkgs` の中身)。無ければ無いことを明示する行を出す。
- **P0-2 `kmod-list`**(Q / G / P、引数なし)。`/proc/modules` の第1列(モジュール名)を出す。sudo を使わない。
- **P0-3 `ports`** を class P へ追加する。class Q / G の既存 `ports`(`ss -ltnup`)と**同じ実行内容**にする。sudo は使わない(他ユーザーのプロセス名が出ないことは許容する)。
- **P0-4 `stale-libs`**(G / P のみ、引数なし)。削除済み(`(deleted)`)の共有ライブラリ・実行ファイルを mapping したまま動いているプロセスについて、PID・プロセス名・該当パスを出す。
  - 実体は**引数を取らない専用スクリプト1本**(例 `/usr/local/sbin/homelab-stale-libs`)。`/proc/*/maps` を読んで表示するだけで、書込・プロセス操作・外部コマンドへの引数受け渡しを一切しない。
  - **判定の契約**(2026-11-14 計画査読 M1 を受けて確定):
    - 対象は、maps の行のうち**パス欄が ` (deleted)` で終わり、かつパスが `/` で始まる通常ファイル**のもの。共有ライブラリと実行ファイル本体の両方を含む。
    - 次は**除外する**(正常に deleted となるもの): `/memfd:` で始まるもの、`/dev/shm/`・`/tmp/`・`/var/tmp/`・`/run/` 配下、`[` で始まる疑似領域、無名 mapping。
    - パスは maps の第6欄以降を1つの文字列として扱う(空白を含むパスを途中で切らない)。
    - 走査中に終了した・読めなくなった PID は黙って飛ばし、全体を失敗にしない。
    - 1プロセスにつき、PID・プロセス名・該当パス(重複を除く)を出す。
  - **スクリプト自身も引数を拒否する。** 引数が1つでも付いたら何も読まずに終了値 **64** で終了する(sudo 層の拒否と区別できる値にする)。
  - 配備先は root 所有・`0755`(調査ユーザーから書き換えられない)。
  - sudoers は**そのスクリプトの絶対パスを引数なしで**許可する1行だけを足す(sudoers の空引数指定 `""` で引数付き実行を拒否する)。class P は `sudoers-recovery-exec-pve-target.j2`、class G は `sudoers-recovery-exec-target.j2`。
  - **sudo 層の拒否を配備時に検査する**(2026-11-14 計画査読 M2 を受けて追加)。setup playbook の配備後に、target 上で `recovery-exec` として**引数付きで** `sudo -n <絶対パス> x` を試み、sudo が拒否した(スクリプトの 64 ではない)ことを assert する task を置く。期待と違えば play を失敗させる。check mode の扱いは既存 task の慣行に合わせる。
  - dispatch は `sudo -n <絶対パス>` で呼ぶ。
  - 該当プロセスが0件のときは rc=0 で、0件であることを示す行を出す。
- **P0-5 arity**。4語彙とも引数を取らない。引数が付いたら既存語彙と同じく `denied:` で非ゼロ終了し、実行しない。
- **P0-6 語彙カタログの更新。** `docs/ai/reviews/dev_prod_boundary/2026-08-03_008_phase3_check_catalog.md` へ §10 と同じ形式で §11 を足し、総数を更新する。sudo を伴う `stale-libs` は、許可の範囲(スクリプト1本・引数なし)をカタログに明記する。

### P1(あるとよい)

- 各 dispatch の usage / 一覧表示に新語彙が載ること(既存の一覧表示があればそれに倣う)。

## 6. 受入条件

- **AC1** Given pve1(pve2 も同じ)、When ansy から `ssh pve1-investigate kernel-status`、Then rc=0 で、空でない稼働カーネル名、導入済みカーネル一覧(1件以上)、再起動要求の有無が出る。値は期待値ではなく観測値として記録する(参考: 2026-11-14 の稼働カーネルは Notion「稼働バージョン」上 `7.0.14-28-pve`)。
- **AC2** Given authy / monnie / quory、When `kernel-status`、Then rc=0 で同じ3点が出る(稼働カーネルの値は観測値をそのまま記録する)。
- **AC3** Given 全5ホスト、When `kmod-list`、Then rc=0 でモジュール名が1行1件で出る。
- **AC4** Given pve1 / pve2、When `ports`、Then rc=0 で待ち受けソケットが出る。
- **AC5** Given pve1 / pve2 / authy / monnie、When `stale-libs`、Then rc=0 で該当プロセス一覧、または0件である旨が出る。
- **AC5a(判定の正しさ、実ホスト外)** Given 実ホストではない環境(ansy のローカル等)、When 削除済みのファイルを mapping し続けるテスト用プロセス(除外対象外のパス)と、除外対象(`/memfd:` 等)を mapping するテスト用プロセスを立ててスクリプトを実行する、Then 前者は一覧に出て、後者は出ない。**常に0件を返す実装はここで失敗する。** 走査中にテスト用プロセスが終了しても rc=0 で完走する。スクリプトに引数を付けたら終了値 64 で、何も出力しない。
- **AC6** Given quory、When `stale-libs`、Then 非ゼロ終了で拒否される(quory には無い語彙)。
- **AC7** Given 全5ホスト、When 各新語彙に引数を1つ付ける(例 `kernel-status x`)、Then 非ゼロ終了で拒否され、実行されない。
- **AC8** Given 本案件で足す sudoers の行、When repo のテンプレートを読む、Then 許可は**スクリプト1本の絶対パス・引数なし(`""`)**に限られ、ワイルドカードを含まない(Reviewer が差分で確かめる)。
- **AC8a** Given `recovery_exec_setup.yml` の配備実行(quory の Semaphore)、When P0-4 の sudo 層拒否の assert task が pve1 / pve2 / authy / monnie で走る、Then 4台とも成功している(=引数付き sudo が sudo 層で拒否された)。確認手段は quory の `semaphore-query task-output` でそのジョブのログを読むこと。
- **AC9** Given 日次ドリフト検査、When 配備翌日の実行、Then 本案件の配備物について finding を出さず、**かつ対象ホストがすべて `checked`(`unverified` でない)**である。`copy` 配備のもの(quory dispatch、`stale-libs` スクリプト)は `deployment_drift_check` の対象へ加える。
- **AC10** Given 既存の dispatch probe(`deployment_drift_check_dispatch_probes`)、When 実行、Then これまでどおり非ゼロで拒否される。
- **AC11** Given 本案件の commit、When カタログを読む、Then 4語彙が class・引数・実行内容・sudo の範囲つきで載り、総数が更新されている。

## 7. オープンクエスチョン

- **【2026-11-14 解決】`stale-libs` の判定方法は P0-4「判定の契約」で確定した(計画査読 M1)。** 契約に無い細部(除外パスの追加など)を Implementer が決めた場合は、根拠を実装記録へ残す。
- **sudoers の空引数指定が対象ホストの sudo で期待どおり効くかは未確認。** pve・Ubuntu とも classic sudo(ansy は sudo-rs で挙動が違う。`sudoers-recovery-exec-pve-target.j2` 冒頭の注記)。**配備時の assert task(P0-4、AC8a)で確かめる**(計画査読 M2)。

## 8. タイムライン考慮

- **commit と配備を離さない。** 配備の入口は class Q が `playbooks/dev_investigate_setup.yml`、class P / G が `playbooks/recovery_exec_setup.yml`。いずれも quory の Semaphore から実行する(Yoshinobuの操作)。**どの task がどのファイルを配るかは Implementer が現物で確かめ直す** — 本 requirement の記述を根拠にしない。
- **pve の配備は到達不能ノードを除外して進む**(`roles/recovery_exec/tasks/target_setup.yml` の到達性判定)。配備ジョブの出力で**外した pve ホストが無い**ことを配備完了の条件にする。外れたノードがあれば、復帰後に再実行するまで配備完了としない(計画査読 M3)。
- 配備後、翌日のドリフト検査で finding が無く、対象ホストがすべて `checked` であることまでを本案件の範囲とする。
