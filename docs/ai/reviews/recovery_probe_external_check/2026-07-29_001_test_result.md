# recovery-probe.py `external_reachable()` 差分検証 — 2026-07-29(配備前・Tier 2)

## AC ごとの判定

### AC1: 戻り値のタプル化がすべての呼び出し側で正しく受けられている — **PASS**

静的確認(grep で呼び出し箇所を全数把握):

- `external_reachable` の呼び出しは1箇所のみ(386行台の `main()` 内)。
- `ext_ok, ext_reason = external_reachable(cfg)` で正しくアンパックしている。
- `flush_notify_queue(cfg, ext_ok)` には `ext_ok`(bool)のみを渡しており、タプルを
  渡していない。`flush_notify_queue` 内部の `if not ext_ok:` は bool を期待する実装のまま
  変更されておらず、意味は変更前と同じ。

根拠: `grep -n "external_reachable\|ext_ok\|flush_notify_queue" recovery-probe.py` の出力
(107, 151, 158, 466, 467, 493行)。呼び出し・アンパック・受け渡しが1箇所ずつしかなく、
型の取り違えは静的に確認できる範囲で存在しない。

### AC2: 失敗の層(名前解決 / TCP / TLS / timeout)が理由文字列から区別できる — **PASS**

`external_reachable()` を4種類の実失敗で直接呼び出し、実測:

| 層 | 手段(実ホスト不使用) | 実測 `reason` |
|---|---|---|
| 名前解決 | `http://host.invalid/`(RFC 2606予約TLD、NXDOMAIN) | `URLError: <urlopen error [Errno -2] Name or service not known>` |
| TCP | loopback の閉ポート宛 URL | `URLError: <urlopen error [Errno 111] Connection refused>` |
| TLS | loopback上の平文HTTPサーバへ `https://` でアクセス | `URLError: <urlopen error [SSL: RECORD_LAYER_FAILURE] record layer failure (_ssl.c:1081)>` |
| timeout | loopback上でacceptのみして無応答のソケット(8秒スリープ) | `TimeoutError: timed out`(実測 elapsed 5.01秒、`urlopen(timeout=5)` どおり) |

4層とも文字列の内容(エラーメッセージ本文)およびtimeoutのみ型そのもの
(`TimeoutError`)で判別可能。DNS/TCP/TLSはいずれも `URLError` 型だが、ラップされた
`errno`/`SSL` 詳細がメッセージ本文に含まれ、文字列上で区別できることを確認した。

副次確認: `HTTPError`(404応答)は従来どおり `ok=True, reason=None` を返す
(`flush_notify_queue` 判定への影響なし)。

### AC3: 連続失敗数のカウントとリセット — **PASS**

`main()` を `load_config` / `external_reachable` / `queue_notify` / `flush_notify_queue` /
`time.sleep` monkeypatch 済みで直接実行し、`targets: {}` としてターゲット probe 部分を
無効化した上で外部到達性チェック部分のみを検証。シナリオごとの実測:

- 単発失敗→回復: 1回連続で通知、本文に「1 回連続」「最初の失敗理由: reasonA」。
- 3回連続失敗→回復: 通知本文「3 回連続」「最初の失敗理由: reasonA」(最初の理由が
  保持されている。2回目・3回目の reasonB/reasonC は本文に出ない設計どおり)。
- 回復後の再発(エピソード1: 2回失敗→回復、エピソード2: 1回失敗→回復): 2件の通知が
  独立に生成され、エピソード2の通知は「1 回連続」「理由: ep2-a」— エピソード1の
  カウント(2)を引き継いでいないことを確認(`ext_fail_count = 0` / `ext_first_reason = None`
  のリセットが機能している)。

### AC4: 常に正常なとき通知が1件も生成されない — **PASS**

上記と同じ harness で `external_reachable` が6サイクル連続 `(True, None)` を返すシナリオを
実行し、`queue_notify` 呼び出し回数 0 を確認。

### AC5: デーモンが落ちない — **PASS(主要経路)/ FAIL(1つの境界ケースを実際に再現)**

- 主要経路(実際に発生しうる例外: `socket.gaierror` 経由の名前解決失敗、
  `ConnectionRefusedError`、`ssl.SSLError`、`TimeoutError` をそれぞれ `urlopen` に発生させた
  AC2 の4テスト、および AC3/AC4 のループ全シナリオ)では例外はすべて `external_reachable()`
  内で捕捉され、`main()` のループは次サイクルへ正常に継続した。クラッシュなし。
- **境界ケースを実際に再現し、FAIL を確認した**: `except Exception as exc:` の中で行っている
  `f"{type(exc).__name__}: {exc}"` は `str(exc)` を呼ぶ。捕捉した例外自身の `__str__` が
  例外を送出する場合(`__str__` をオーバーライドして意図的に `RuntimeError` を送出する
  テスト用例外クラスを用意し、`urlopen` からそれを送出させた)、この文字列化コードが
  未捕捉のまま `external_reachable()` を抜け、`main()` の `while True` ループ全体にも
  それを捕まえる `try/except` が存在しないため、**プロセスが終了する**ことを実測で確認した
  (`main()` 呼び出しがそのまま `RuntimeError: boom in __str__` を送出して終了)。
  - 実際に urllib/socket/ssl が送出する標準ライブラリの例外(`URLError`,
    `socket.gaierror`, `ConnectionRefusedError`, `ssl.SSLError`, `TimeoutError`)は
    いずれも正常な `__str__` を持ち、AC2 の実測4件で問題なく文字列化できている。
    そのため、この境界ケースが実運用で踏まれる可能性は低いと考えられる。
  - しかし AC5 が明示的に要求している「例外の文字列化が失敗しうる場合を含め」に対し、
    実際にそのケースを再現した結果は FAIL である。変更前のコード
    (`except Exception: return False`)はこの経路に触れていなかったため、この脆弱性は
    今回の差分で新規に持ち込まれたものである。
  - 修正案(Tester からの提案。実装はしていない): `external_reachable()` の except節を
    `try: reason = f"{type(exc).__name__}: {exc}" except Exception: reason = type(exc).__name__`
    のように、文字列化自体を保護する。あるいは main() 側で外部到達性チェックの呼び出しを
    ループ単位の `try/except` で包み、失敗時はログのみ出して次サイクルへ進める(後者は
    デーモン全体の堅牢性向上になるがスコープが広がる)。

再現手順・実測ログはこのファイルの検証方法節にあるスクリプト群(3本目のインライン
検証、ファイル化せずコマンドとして実行)に対応する。生ログ全文はここに貼らず、要点の
み上表・上記文へ転記した。

### AC6: 通知本文への内部IP混入なし — **PASS(範囲内で確認)**

- 本番設定 `roles/recovery_probe/defaults/main.yml` の
  `recovery_probe_external_check_url: https://one.one.one.one` はドメイン名であり、
  IPアドレスではない(内部IPが構成に現れる余地がそもそもない)。
- AC2 で実測した4層の失敗理由文字列(名前解決/TCP/TLS/timeout)はいずれも、接続先が
  loopback アドレスであったにもかかわらず、`reason` 文字列中に **IPアドレスを
  含んでいなかった**(`urllib`/`socket`/`ssl` の例外メッセージは errno 名や TLS エラー種別
  を含むが、対象アドレスそのものは含まない実装であることを実測で確認)。
- 追加確認として RFC 5737 の TEST-NET-1 予約アドレス(実ホスト不使用)を直接
  `external_check_url` に指定した場合も `reason` は `"URLError: <urlopen error timed out>"`
  のみで、指定したアドレス自体は文字列中に現れなかった。
- 以上より、通知本文(`ext_first_reason` をそのまま埋め込む設計)に内部IPが混入する
  経路は、今回検証した範囲では確認できなかった。ただし「例外メッセージが将来的に
  アドレスを含む可能性が完全にゼロである」ことまでは証明していない
  (Python標準ライブラリの現行実装に基づく実測であり、将来のPythonバージョンや
  他の例外型までは保証しない)。
