# requirement(ROOT CA に KeyUsage を足す)

2026-08-05 / Coordinator。`docs/ai/status.md` Next の「root CA が KeyUsage 拡張を持たず、Python の `ssl` が CA として受け付けない」に対する案件である。

**着手前の調査で、想定より大幅に小さい案件だと分かった。** 直すのは**ROOT証明書1枚**で、leaf も中間 CA も再発行せず、Ansible 管理外の機器(Wi-Fi クライアント等)の再信頼も要らない。

## 1. 調査で確定した事実(2026-08-05、Coordinator が ansy 上で実測)

| 対象 | KeyUsage | 備考 |
|---|---|---|
| **ROOT `Home-RADIUS-CA`**(自己署名、`notAfter=2056-04-12`) | **無い** | **これが原因。** SKI = `1E:4D:3C:23:B5:43:0C:77:70:65:49:A5:22:0C:E6:8B:6E:61:88:57`、EC P-384、`ecdsa-with-SHA256` |
| 中間 `Home-TLS-CA`(ROOTが署名、`notAfter=2036-06-09`) | **有る**(`Certificate Sign, CRL Sign`、critical) | 問題なし。AKI が上記 SKI を指す |
| leaf(`ansy.internal` 等) | — | 中間が署名。問題なし |

**再現と、直ることの証明**(使い捨ての鍵で作った同型の鎖に対して実施。本物の鍵には触れていない):

| 検証 | 結果 |
|---|---|
| 旧ROOTを anchor に `openssl verify -x509_strict` | **`error 92: CA cert does not include key usage extension`** — 本番で観測されたのと同一 |
| **新ROOT(同じ鍵・KeyUsage付き)を anchor に、中間と leaf はそのまま** | **OK** |
| 旧ROOTを anchor に通常検証 | OK(`curl` が通る理由) |

**ROOT証明書の消費者は2箇所で、フィンガープリント固定は無い**(`git grep` で確認)。

- `roles/homelab_cert_renew/tasks/deploy_ca_trust.yml` — quory の `/home/yoshi/.cert/ca/radius_ca.crt` を slurp し、全ホストの `/usr/local/share/ca-certificates/home-tls-root-ca.crt` へ配る
- `roles/cloudkey_cert_deploy` — CloudKey へのバンドルに含める

## 2. ゴール

- Python の `ssl`(および `-x509_strict` 相当の厳格な検証)が、この PKI を受け付ける
- **回避で入れている `validate_certs=false` を全部外す**

## 3. 非ゴール

- **leaf / 中間 CA の再発行。** 不要であることを実測で確認済み
- **ROOT の鍵の更新。** 鍵を変えると SKI が変わり、中間の AKI と繋がらなくなる。**さらに Ansible 管理外の機器すべてで再信頼が要る**(ROOT は `Home-RADIUS-CA` の名のとおり EAP でも使われている可能性が高い)
- 古い ROOT 証明書の失効・回収。**古いものを持ったままの機器は、そのまま動き続けてよい** — 同じ subject・同じ鍵なので、どちらを anchor にしても鎖は検証できる

## 4. 手順

### Step B(Yoshinobu、鍵を扱う唯一の工程)

**AIはこの工程に一切関与しない。** 能力の問題ではなく、`docs/ai/core.md`「公開情報と秘密情報」が秘密鍵の保存・表示・生成・複製を禁じているためである。

1. Bitwarden から ROOT の秘密鍵を取り出す(鍵は**この工程の外へ出さない**)
2. **同じ鍵・同じ subject** で、KeyUsage を足した自己署名証明書を作る

```
openssl req -x509 -new -key <ROOT秘密鍵> -sha256 -days 10950 \
  -subj "/CN=Home-RADIUS-CA/O=home/C=JP" \
  -addext "basicConstraints=critical,CA:TRUE" \
  -addext "keyUsage=critical,keyCertSign,cRLSign" \
  -addext "subjectKeyIdentifier=hash" \
  -addext "authorityKeyIdentifier=keyid:always" \
  -out radius_ca_new.crt
```

**`-subj` の並び順を変えないこと。** この環境の ROOT は `CN → O → C` の順で作られており、素直に `/C=JP/O=home/CN=...` と書くと **DN が別物になり、中間 CA の発行者名と繋がらなくなる**(2026-08-05に実測。誤った順で作ると `unable to get local issuer certificate` になる)。**Step C の検査はこの誤りを検出する。**

3. できた `radius_ca_new.crt`(**公開物**)を ansy から読める場所へ置く
4. 鍵をオフライン管理へ戻す

### Step C(検証 → 配布)

1. **配る前に検査する。** `scripts/verify-root-ca.sh <新しい証明書>` を実行し、`RESULT: PASS` であること。**FAIL なら配らない**
2. quory の `/home/yoshi/.cert/ca/radius_ca.crt` を差し替える。**差し替え前に必ず退避する**(切り戻しはこのファイルを戻して再配布するだけ)
3. Semaphore の `ca_trust_deploy` のボタンを押す

### Step D(仕上げ)

厳格な検証が通ることを確認したうえで、**回避を3箇所とも外す**。

| # | 場所 | 現在の回避 |
|---|---|---|
| 1 | `roles/deployment_drift_check/defaults/main.yml` | 接続先 `localhost` + `validate_certs: false` |
| 2 | `roles/semaphore_templates/defaults/main.yml` | ansy 向け上書き例のコメント |
| 3 | **quory の ブートストラップ template の survey 既定値** | **repo の外。Yoshinobu の手が要る** |

## 5. 受入条件

| # | 条件 |
|---|---|
| **AC1** | **Given** 新ROOT、**When** `scripts/verify-root-ca.sh` を実行、**Then** `RESULT: PASS`(subject が現行と一致、SKI が一致、KeyUsage critical、実チェーンが `-x509_strict` を通る) |
| **AC2** | **Given** 配布後、**When** ansy / quory から内部HTTPSへ `validate_certs: true` かつ**ホスト名で**接続、**Then** 成功する |
| **AC3** | **Given** 配布後、**When** 既存の `cert_renew` 系が動く、**Then** 従来どおり成功する(中間・leaf を作り直していないため、挙動が変わらないこと) |
| **AC4** | **Given** 回避を外した状態、**When** 日次ドリフト検査が走る、**Then** `semaphore_probe_error` の finding が立たない |
| **AC5** | **Given** 古い ROOT を持つ機器(Ansible管理外)、**When** 従来どおり接続する、**Then** **影響が無い**(検証手段は §7 のとおり限定的) |

## 6. 切り戻し

`/home/yoshi/.cert/ca/radius_ca.crt` を退避したものへ戻し、`ca_trust_deploy` を再実行する。**leaf も中間も触っていないので、戻す対象はこの1ファイルだけである。**
