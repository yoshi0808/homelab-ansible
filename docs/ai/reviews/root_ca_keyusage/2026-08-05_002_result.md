## この案件で分かった、手順側の罠(記録)

`scripts/verify-root-ca.sh` を作る過程で、**私が用意した手順の欠陥を2つ、スクリプト自身が検出した。**

1. **DN の構成要素の順序。** この環境の ROOT は `CN → O → C` の順で作られており、素直に `/C=JP/O=home/CN=...` と書くと DN が別物になり、中間 CA の発行者名と繋がらない(`unable to get local issuer certificate`)
2. **`openssl verify` は `-CAfile` を渡しても既定の信頼ストアを参照する。** `-no-CApath -no-CAstore` を付けないと、「システムに旧 ROOT がある」だけで通ってしまい、検査が何も検査していない状態になる

**どちらも本番で踏めば事故になり、どちらも「検証手段を先に作る」ことで、実物に触れる前に見つかった。**

## 副産物 — ansy にあった中間CA秘密鍵を撤去した(2026-08-05)

配布の確認中に、**ansy に中間CAの秘密鍵(`~/.cert/ca/home_tls_ca.key`)がある**ことに気づいた。**中身は読んでいない。**

**経緯**: 中間CAを ansy で生成し、テストが通ってから quory へ証明書を配った当時の名残(Yoshinobu)。**運用上の役割は無い。**

**消してよいと判断した根拠**(いずれも実測):

- repo内でこの鍵を参照するのは `cert_renew_ca_host` 上のパスだけ。`cert_renew.yml` / `cert_renew_quory.yml` とも同ホストは `localhost`(= quory 上での実行)であり、**ansy を前提にした参照は1つも無い**
- **quory が鍵を持っていることの証拠**: quory の leaf 証明書の `notBefore` が `2026-08-01 00:35:11 JST` — 月次 timer(`*-*-01 00:35:00`)の発火時刻と一致し、`issuer` が `Home-TLS-CA`。**8月1日に中間鍵で発行している**

**なぜ気にするか**: この鍵があれば、内部のどんな名前に対しても全ホストが信頼する証明書を発行できる。**Phase 4 で捨てた SSH 鍵より強い権限**であり、しかも ansy は AI エージェントがシェルを持つホストである。開発側に本番の認証情報を置かないという設計が、ここだけ抜けていた。

**削除は Yoshinobu が実施**(復元不能な操作のため)。Coordinator は削除後に `.key` が存在しないことだけ確認した。同じことが起きないよう、**鍵を参照している場所**(`roles/homelab_cert_renew/defaults/main.yml`)に理由つきで書いた。

**残る注意**: 中間鍵は **quory の1コピー**になった。失っても ROOT から中間を作り直せるため復旧不能ではない(leaf は45日周期で入れ替わる)が、単一コピーであることは意識しておく。

## AC5 の確認と、その範囲(2026-08-05)

**旧ROOTを持つ端末(Ansible管理外のスマートフォン)から、ブラウザでエラーなく開けた**(Yoshinobu)。これで本案件の受入条件はすべて埋まった。

**この確認が覆う範囲**: ブラウザ = OSの信頼ストアによるTLS検証。**旧ROOTしか持たない端末が、新しく配られた鎖を検証できる**ことの実証である。

**覆っていない範囲**: EAP(802.1X)による無線認証の経路は、別途測っていない。**ただし今回の変更はそこへ影響しない** — `authy` の RADIUS サーバ証明書は `cert_renew_hosts_config`(ansy / quory / pve1 / pve2 / monnie)に含まれておらず、**今回1ミリも触っていない**。クライアント側の検証も、上と同じアンカーの関係で成立する。

**RADIUS 本体の証明書について(2026-08-05 Yoshinobu)**: **RADIUS サービス本体が使っているのは ROOT CA であり、Ansible 作業の対象外である。** これは穴ではなく**意図的な線引き**である。`cert_renew_hosts_config` に `authy` が無いのも、repo 内に発行経路が見当たらないのも、そのためである(`ca_trust_deploy` は `radius_servers` を対象に含むので、信頼ストアには新ROOTが入っている)。

**今回の変更はこの経路に影響しない。** ROOT は同じ鍵・同じ subject のまま再発行しており、クライアント側が持つ旧 ROOT でも検証が成立することは AC5 で実測した。**次にここを「管理外の穴」として起票しないこと。**
