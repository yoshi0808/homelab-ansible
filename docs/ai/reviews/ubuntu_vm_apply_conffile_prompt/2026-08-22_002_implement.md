## 案件を分割した理由(R2/R3を外した理由)

3回目のレビュー `2026-08-22_005_review.md` の High 3件は、いずれも「apply**前後**の`${Conffiles}`スナップショット差分」という方式そのものの限界に起因する偽陰性だった。中心は **Finding 2**:

> `recorded_changed and kept_local and not unchanged_local` を非該当として捨てるのは偽陰性になる。この観測は「dpkgが新既定値を置いた後にpostinstが第三の値を書いた」場合だけでなく、「dpkgが`--force-confold`で旧局所版を保持した後にpostinstがそのファイルを変更した」場合にも成立する。pre/postの最終snapshotだけでは両者を区別できない。

つまり、**apply完了時点の2枚のスナップショット(pre/post)だけを比較する設計では、「保持後にpostinstが触った」と「適用後にpostinstが触った」を原理的に区別できない。** これを`indeterminate`(判定不能)として扱えば、postinstが触るconffileを持つ月次applyが日常的に失敗するようになり、Finding 1(fresh installの見落とし)・Finding 3(`newconffile` markerの見落とし)を塞ぐために候補範囲を広げるほど、この偽陰性/判定不能化の頻度も上がる。**方式が天井に当たっている**と判断し、Coordinatorが要件を分割した。R2/R3(保持したconffileの検出・報告)は別案件として持ち越し、次に取り組む際は「apply中の`dpkg`自身の決定をリアルタイムに観測する」等、pre/post比較とは異なる方式を検討する必要がある。

**本ファイルはR2/R3を「未実装のまま放置した」ものではない** — 実際には2回の実装(`2026-08-22_003_review.md`前後の単発post-apply比較、`2026-08-22_004_review.md`前後のpre/post差分+G1〜G3+S1〜S3の強化)を経て、3回目のレビューで方式そのものの限界に到達したことを確認した上での意図的な切り出しである。次にR2/R3へ着手する担当者は、この2つの実装(git履歴、または本レビューフォルダの`2026-08-22_003_review.md`/`004_review.md`/`005_review.md`)を「試して天井に当たった記録」として参照できる。

## 差分の要点(残したもの: R1・R4・R5・G4)

### R1 — `--force-confold`(`tasks/apply.yml`)

`apt-get -y full-upgrade` に `-o Dpkg::Options::=--force-confold` を渡す。ローカル変更のある conffile は既存を保持し、プロンプトを出さない(判定ロジックは持たない — 非ゴール§3どおり)。

### R4/F1/S1 — timeout(`tasks/apply.yml` + `defaults/main.yml`)

`apt-get` 呼び出しを `timeout --kill-after={{ kill_after }} {{ timeout }} apt-get -y full-upgrade -o Dpkg::Options::=--force-confold`(`argv:` 形式)へ。直前に `Assert apply timeout values are positive` を置き、両方の秒数が正であることを fail-closed で検証(duration `0` は `timeout` 自身を無効化するため)。`command` は `failed_when: false` とし、`rc in [124, 137]` を1つの `fail` タスクへ統合、通常失敗は `rc not in [0, 124, 137]`。

**rc=137のメッセージ(S1)**: 「kill-after escalation」と断定せず、「SIGKILLで終了(rc=137)。kill-after escalationと整合するが、`timeout`自身は自分が送ったKILLと外部由来のSIGKILL(OOM killer、operatorの`kill -9`等)を区別できないためrcだけでは原因を確定できない。dmesg/journalctlでOOM killの有無を確認すること」という、確定できる範囲だけを述べる文面。

**上限値を今回変更した: `ubuntu_vm_full_upgrade_apply_timeout_seconds` を 1800→**`3600`**(60分)、Coordinator判断**。`ubuntu_vm_full_upgrade_apply_kill_after_seconds` は`60`のまま変更なし。根拠(`defaults/main.yml` にコメントとして記録済み):

- **リスクは非対称**。短すぎる上限は「健全に進行中のapt-getをkillする」という**自傷**(2026-08-22の実インシデントと同じ壊れたdpkg状態を自分で作る)を引き起こす。長すぎる上限は「本当にハングしたときに気づくのが遅れる」だけで、それ自体は何も壊さない。
- この環境には**ダウンロードが極端に遅くなる実績**がある(Proxmox CDNがこの環境の通信をシンガポール経由へ回した、という別件の観測)。300MB級の月次full-upgradeが同種の経路劣化に当たれば、30分経過時点でもダウンロードが継続中というのは十分あり得る。
- `BLOCKED`/`MAJOR_UPGRADE_DETECTED`はapplyへ到達できずパッケージ数は常に閾値未満 — ここで budget しているのはパッケージ数の多さではなく転送の遅さ。
- `recovery_mute`は120分。60分+kill-after60秒でも、mute失効・自律復旧発火までまだ約60分の余裕が残る。1800秒版より余裕は薄くなるが、上記の非対称性を踏まえてCoordinatorが意図的に長い側へ倒した。

### R4/F4 — timeout失敗時のメッセージ(`tasks/apply.yml`)

①部分適用の可能性、②確認すべき対象(apt-get/dpkgプロセス残存、lock、`dpkg --audit`/`dpkg -C`)、③reboot/post-checkへ進んでいないこと、を明記。具体的な復旧操作は断定しない。

### R5 — needrestart(`tasks/apply.yml`)

`environment:` へ `NEEDRESTART_MODE: l`(一覧のみ、再起動しない)。reboot 判定は UV-051/UV-052 のまま。

### G4 — quoryのreboot不要時に通知が届かない問題(`tasks/reboot_quory.yml`)

**R2/R3とは独立した実バグとして残した。** apply summary 通知が `when: ubuntu_vm_full_upgrade_reboot_required` でゲートされたblock内にあり、reboot不要のapplyでは一度も送信されなかった。通知タスクをblock外へ出し、reboot要否にかかわらず送信、本文中のreboot関連行だけを条件描画する形にした。

## 開発側で確かめられなかったこと

- **実際の conffile プロンプトが `--force-confold` で本当に出なくなるか、`--kill-after`のKILL escalationが実dpkg/aptプロセスに対しても機構どおり働くか**は、ansy から実ホストへ届かないため確認できない(requirement §6のとおり)。timeoutの汎用機構自体(TERM/KILL/rc)はGNU coreutilsの標準動作であり、任意の子プロセスに対しては過去の自己検証で実測済み。
- **timeout 3600秒・kill-after 60秒が実運用で適切か**(特にmuteとの残り約60分の余裕が実際に十分か)は、実際の apply 所要時間・ダウンロード遅延の観測例が乏しいため未検証。
- `NEEDRESTART_MODE=l` が実際に needrestart のプロンプトを塞ぐかは、ansy 上に needrestart が入っていないため未確認。
- **保持したconffileの検出・報告(R2/R3)は本案件では未実装のまま**(意図的な範囲外 — 上記「案件を分割した理由」参照)。当面、apply summary通知は「--force-confoldで適用した」という事実のみを伝え、実際に何が保持されたかは運用者が手動で確認する必要がある。
