# Code Review: ubuntu_vm_full_upgrade conffile prompt対策 3回目再レビュー

Reviewer: Codex / 2026-08-22

## Summary

G1のalert→reboot handling→deferred failという制御順序と、G4のquory apply summary経路は意図どおりになった。reboot側が失敗した場合は各include内のrescueが再raiseし、成功した場合だけconffile側のdeferred failへ到達するため、判定不能が黙って消える経路も対象コード内にはない。

しかし、R2の検出にはなお正常な`held: []`へ落ちる偽陰性がある。特に、G3で追加した第3条件を満たさない一部の状態は「保持されなかった」とは証明できず、fresh installと`newconffile`も観測対象外または非致命として捨てられている。現状は「この実行で保持したconffile」を網羅した通知として受入不可。

## What Looks Good

- `ubuntu_vm_full_upgrade_sim.simulation.inst_detail`はapply前に定義され、既存package候補の取得元として成立している。
- `failed_when: false`後のapt rcは0、124/137、その他で全域が処理され、timeout/部分適用のメッセージも運用確認点を明示する。
- conffile diffの非0はfactとして保持され、即時critical alert後もreboot lifecycleを進め、最後に必ず非0へ戻す構造になった。
- local側はreboot要なら同一sessionで復帰を待ち、healthcheck・summary後にdeferred failへ戻る。quory側は予約成功・summary後に戻る。reboot側の失敗はconffile側で上書きされない。
- G4後もreboot要の場合のsummary順序は予約block成功後のままで、title・予約状態・post-check案内の条件描画も維持されている。reboot不要の場合だけ明示的な`reboot: 不要`が追加される。
- held/判定失敗のimpact blockはlocal/quoryともSlack本文先頭にあり、折り畳み位置より前というR2の配置要件を満たす。
- check-mode境界は`tasks/main.yml`の`ubuntu_vm_full_upgrade_is_apply_target and not ansible_check_mode`外側ゲートのままで、新規変更は`apply.yml`内に閉じる。
- security観点では固定script、`argv`、0600 snapshotを使い、shell展開、秘密値露出、危険なdelegate/lookupの追加はない。既存simulation factと共通Slack通知も再利用されている。
