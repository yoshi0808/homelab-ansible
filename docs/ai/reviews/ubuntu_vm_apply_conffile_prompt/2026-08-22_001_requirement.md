# requirement: 手動applyが conffile プロンプトで無期限に止まらないようにする

起案: Coordinator / 2026-08-22 / 依頼者: Yoshinobu(当日中の修正を指示)

## 1. 問題定義

**`roles/ubuntu_vm_full_upgrade/tasks/apply.yml` の `apt-get -y full-upgrade` は conffile の扱いを指定していない。** そのため、**ローカルで変更された conffile が更新対象に入ると dpkg が Y/N を尋ね、playbook は無期限に停止する。**

2026-08-22 のジョブ **#802** で実際に起きた(経過は `docs/ai/reviews/monnie_unpoller_major_upgrade/2026-08-22_002_result.md`)。壊れ方には3つの層がある。

1. **答えられない。** プロンプトの stdin は Ansible の SSH セッションが握っており、**別のシェルからは答える手段が無い**。人が monnie にログインしていても打ち込む先が無い
2. **止まっていることが分からない。** `command` モジュールは stdout を流さないため、Semaphore の出力は `TASK [... Run apt full-upgrade]` の行で止まったまま。**「時間がかかっている」と「止まっている」が区別できない。** 当日は10分間気づかれなかった
3. **タイムアウトが無い。** 誰も止めなければ永久に待つ。**mute は120分で切れる**ため、放置すると自律復旧が動き出す条件に入る

**`DEBIAN_FRONTEND=noninteractive` はこれを防がない。** 抑止するのは debconf であって、dpkg の conffile プロンプトではない。当日この誤解が事前調査にも入っていた。

**今月たまたま `up.conf` が該当しただけで、構造としては role の実装当初から在った。** 対象4ホストのいずれでも、手動管理されている設定ファイルが更新対象に入れば同じ形で止まる。

## 2. ゴール

- **conffile の扱いを明示し、プロンプトで止まらないようにする。**
- **conffile を保持する設定で適用したことを通知に出す。** 黙って古い設定を残さない。**どのファイルを保持したかは主張しない**(§7 のとおり R2 / R3 は別案件へ移した)。
- **無期限に待たない。** 想定外の停止を、観測可能な失敗にする。

## 3. 非ゴール

- **判定ロジックを変えない。** important パターン、Status 昇格、non-apt レジストリ、reboot 判定のいずれにも触らない。
- **conffile を配布元版へ更新する経路を作らない。** この環境の conffile は手動管理が前提であり(`/etc/unpoller/up.conf` が実例)、保持が正しい既定である。
- **dry_run 側の事前警告は今回作らない。** 「ローカル変更のある conffile が更新候補に含まれる」と月次の判定通知で予告できれば当日の停止は防げたが、判定側へ手を入れることになるため別案件とする(§7)。
- **孤児プロセスの後始末を自動化しない。** 今回止まった `apt-get` は Semaphore がジョブを停止しても残った。これは対処の話であり、本案件は発生させないことを扱う。

## 4. 要求

| # | 要求 |
|---|---|
| R1 | `apt-get ... full-upgrade` に **`-o Dpkg::Options::=--force-confold`** を渡し、ローカル変更のある conffile は**既存を保持**する。プロンプトを出さない |
| R2 | **本案件から外した(2026-08-22)。** `docs/ai/reviews/ubuntu_vm_conffile_held_report/` へ移した。代わりに、**conffile を保持する設定で適用した事実**を通知へ静的に1行出す。**どのファイルを保持したかは主張しない**
| R3 | **同上。** R2 の実現手段だったため一緒に移した
| R4 | **上限時間を設け、超過したら非0で終わる。** メッセージから **timeout で中断したこと**が分かること。上限値は実装時に提案する(当日の apply は停止前の時点で1分未満) |
| R5 | **needrestart のプロンプトも塞ぐ。** `NEEDRESTART_MODE` を明示する。**`l`(一覧のみ、再起動しない)を推奨** — reboot 判定は UV-051 / UV-052 で role 側が持っており、needrestart に勝手にサービスを再起動させると、その設計と二重になる |

## 6. 制約と、開発側で閉じないこと

- **ansy から実ホストへ届かない**(`EXEC-003`)。**実際の conffile プロンプトを再現できるのは本番だけである。** R1 が効いたことの最終確認は、次に「ローカル変更のある conffile が更新対象に入る月」まで確定しない
- 開発側で閉じるのは、①渡している引数の現物 ②通知の描画 ③`--syntax-check` ④decoy で経路が通ること、の4つである
- **decoy で `apt-get` を実行させない。** decoy が偽装するのは接続先だけで、`ansible_connection: local` を使うと **ansy 自身が full-upgrade される**(`docs/ai/core.md`)

## 7. 範囲を縮めた経緯(2026-08-22)

**R2 / R3(どの conffile を保持したかの特定)を本案件から外し、`docs/ai/reviews/ubuntu_vm_conffile_held_report/` へ移した。** Yoshinobu の承認済み。

実装は3ラウンド回し、レビューは 003 / 004 / 005 の3本。**指摘が減らなかった(4件 → 4件 → 3件)うえ、残ったものはすべて同じ原因から出ていた** — 005 の finding 2 が示したとおり、**apply 前後のスナップショットだけでは「旧版を保持した後に postinst が変更した」と「新既定値を適用した後に postinst が変更した」を原理的に区別できない**。fail-closed 契約を守ろうとすると postinst が触る conffile がすべて判定不能になり、apply が日常的に失敗する。

**証明できない「該当なし」を通知に出すのは、何も言わないより悪い。** 保持されたのに「保持なし」と積極的に述べる経路が残るためである。静的な一文へ落としたのはこの判断による。

**R1 / R4 / R5 は影響を受けない。** 今日の無期限停止を止めるのはこの3つであり、いずれもレビューで指摘なしまで到達している。

## 8. 別案件にしたもの

**保持した conffile の特定**(旧 R2 / R3)。`docs/ai/reviews/ubuntu_vm_conffile_held_report/` へ移した。経緯は §7。

**dry_run 側での事前警告。** 月次の判定通知で「ローカル変更のある conffile が更新候補に含まれる」と出せれば、当日の停止は押す前に避けられた。判定側(`classify.yml`)へ手を入れるため本案件からは外す。**この案件は上の移設先と設計を共有する** — どちらも「どの conffile が問題になるか」を知る必要があり、`dpkg-query` による状態比較でそれを得る方式は 005 finding 2 で否定されている。**先に移設先で方式を決めること。**
