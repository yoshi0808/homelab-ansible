## AC4: timeout の非0終了とメッセージ

**PASS**

### 検証方法

`playbooks/zzz_scratch_ac4_test.yml`(実行後削除)で、`apply.yml` の「timeout値の正数assert」「Fail clearly if apt full-upgrade timed out」「Fail if apt full-upgrade failed for a non-timeout reason」の3タスクを `sed` で抽出しそのまま複製し、**「Run apt full-upgrade」タスクだけ** `argv` の `apt-get -y full-upgrade -o Dpkg::Options::=--force-confold` を安全なdecoyコマンドへ差し替えた(`timeout --kill-after=... N` のラッパー部分は現物のまま)。

- rc=124再現: `sleep 100`(TERMで即終了する既定動作)
- rc=137再現: `bash -c "trap '' TERM; sleep 100"`(TERMを無視し、kill-afterでのKILLへ強制的にエスカレートさせる)
- 両ケースとも `ubuntu_vm_full_upgrade_apply_timeout_seconds=2` / `..._kill_after_seconds=2`

コマンド(2回、`-e decoy_variant=rc124` と `rc137` を切り替え):
```
ANSIBLE_LOCAL_TEMP=/tmp/ansible-local ANSIBLE_REMOTE_TEMP='/tmp/ansible-remote-$USER' \
timeout 30 ansible-playbook -i localhost, playbooks/zzz_scratch_ac4_test.yml -e decoy_variant=rc124
# / rc137
```

### 観測結果

| ケース | observed rc | playbook終了コード | メッセージの要旨 |
|---|---|---|---|
| rc124 | 124 | 2(非0) | `apt-get full-upgrade TIMED OUT or was SIGKILLed`、括弧内 `TERM took effect after 2s (rc=124)` |
| rc137 | 137 | 2(非0) | `apt-get full-upgrade TIMED OUT or was SIGKILLed`、括弧内 `process ended via SIGKILL (rc=137). Consistent with ... kill-after escalation ... but GNU timeout(1) cannot distinguish a KILL it sent itself from an externally delivered SIGKILL ... rc alone does not confirm which occurred; check dmesg/journalctl for an OOM kill before assuming this was the timeout` |

- 両ケースとも `ansible.builtin.fail` で停止し、Ansible全体の終了コードは2(非0)。メッセージから "TIMED OUT" であることが明示され、要求どおり非0終了かつ timeout と判別可能。
- **rc=137のメッセージは原因を断定していない**ことを文面で確認した — 「kill-afterのエスカレーションと整合する」とは述べるが、続けて「GNU timeout(1)は自ら送ったKILLと外部からのSIGKILLを区別できない」「rcだけでは確定しない、dmesg/journalctlを見てから判断すること」と明記しており、S1指摘どおり断定を避けている。
- 実行後、decoyプロセス(`sleep 100` / `trap '' TERM; sleep 100`)の残存がないことを `ps aux | grep` で確認した(該当プロセスなし)。

## この経路では確かめられなかったこと

- **実dpkgでの `--force-confold`・needrestart・実 `apt-get` プロセスに対する `timeout`/`--kill-after` の最終挙動**は未確認。ansyから実ホストへ届かないため(`EXEC-003`)、本番でローカル変更のある conffile が更新対象に入る回まで確定しない(requirement §6 に明記済みの制約どおり)。
- **quory の `reboot_required: true` 分岐**は本検証で実行していない。`connection: local` で実行するとタイムアウトwrapperと同様に `systemd-run --on-active=...s ... /sbin/reboot` がansy自身に対して実際に発火してしまうため(decoyが偽装するのは接続先だけで、実行主体自身への副作用は防がない — `docs/ai/core.md`)、意図的に対象外とした。AC2 が要求する「quoryはreboot不要のときにも通知本文へ到達する」点(G4)はreboot_required=falseの経路そのものであり、これは検証済み。
- **`reboot_local.yml` の `reboot_required: true` 分岐**(実際の `ansible.builtin.reboot` 呼び出し)も同じ理由で対象外。AC2はnotice位置の確認が目的であり、reboot要否どちらの分岐でも本文冒頭のnotice行自体の位置は変わらない(テンプレート上、`ubuntu_vm_full_upgrade_conffile_notice` の行は `reboot:` 行より前に固定されておりreboot要否の条件分岐の外にある)ことをコードで確認しているが、reboot=trueでの実行そのものは行っていない。
- authy(`radius_healthcheck`)/monnie(`monitoring_healthcheck`)分岐のnotice位置は個別に実行検証していない。`inventory_hostname` に応じたhealthcheck関連ロールのincludeより後に「Consolidate post-reboot criticals」→通知タスクが続く構造で、通知本文のテンプレート自体は共通のため、位置確認の観点では localhost(いずれの分岐にも該当しない)での実行で代表性があると判断したが、hostname分岐そのものは通していない。
