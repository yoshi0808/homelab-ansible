# Code Review: ubuntu_vm_full_upgrade conffile prompt対策

Reviewer: Codex / 2026-08-22

## Summary

R1・R5の引数、simulation factの到達性、通知位置、check-mode境界は現物上成立している。一方、R4の上限時間を保証しない`timeout`呼出しと、R2の「今回保持したconffile」を保証できず判定不能も0件へ落とす検出経路があるため、現状は受入不可。

## Critical Issues

| # | File | Line | Issue | Severity |
|---|---|---:|---|---|
| 1 | `roles/ubuntu_vm_full_upgrade/tasks/apply.yml` | 54 | `timeout 1800 apt-get ...`には`--kill-after`がない。GNU `timeout`は期限時に既定でTERMを送るだけで、対象がTERMを無視・捕捉した場合は対象が終了するまで待ち続ける。したがって、未知のprompt/maintainer script停止に対してR4の「上限時間」を保証せず、今回の無期限停止クラスを閉じていない。さらにduration `0`はtimeoutを無効化するが、override値を正の値へ制約するassertもない。GNU Coreutils manual: <https://www.gnu.org/software/coreutils/manual/html_node/timeout-invocation.html>。正のdurationをfail-closedで検証し、TERM後の短いgraceを経てKILLする`--kill-after`を追加すること。KILLまで到達した場合のrc=137もtimeout由来として明示的に扱い、通常失敗と区別すること。 | Critical |
| 2 | `roles/ubuntu_vm_full_upgrade/files/ubuntu-full-upgrade-conffile-check.sh` | 7 | post-apply時点の「現物md5 != dpkg記録md5」だけでは、今回`--force-confold`で保持したものと、以前から局所変更されていたが今回のpackage updateではconffile内容が変わらなかったものを区別できない。候補packageへscopeしても、そのpackage内の各conffileが今回競合した証拠にはならない。現状の通知文は後者も「今回保持した」と断定するためR2を満たさず、既知の限界として残せない。少なくともapply前後の`${Conffiles}`記録値と現物digestを比較し、package側conffileの記録値が今回変化し、かつ局所版が保持された組だけを出すなど、今回の遷移を観測すること。厳密化できない場合はR2の要件変更をCoordinatorへ戻し、断定表示をしないこと。 | High |
| 3 | `roles/ubuntu_vm_full_upgrade/files/ubuntu-full-upgrade-conffile-check.sh` | 29 | `dpkg-query`失敗を`continue`し、形式不正、非regular/missing conffile、読取失敗もすべてskipするため、1件も判定できなくても正常な`[]`を返す。Ansible側はそれを「該当なし」と通知し、R2が求める該当なしと未実施/判定不能の区別、およびcoreのfail-closed原則に反する。候補packageごとのquery/parse/read結果を検証し、判定不能はscript非0または明示的なerror schemaとしてapplyを失敗させること。意図的に削除されたconffileと`obsolete` entryの意味も、無言skipではなく仕様として分類すること。 | High |
| 4 | `roles/ubuntu_vm_full_upgrade/tasks/apply.yml` | 63 | timeoutメッセージは孤児`apt-get`の可能性だけを案内し、SIGTERM/KILL時点では既に一部packageがunpack/configure済みでdpkgが中途半端な状態にあり得ることを伝えていない。また、ジョブ手動停止時の「Ansible停止では子が残った」という実測を、process groupへTERMを送るGNU `timeout`経路にもそのまま当てはめている。運用者がaptだけを探して終了し、package databaseの要復旧状態を見落とす。メッセージに「部分適用の可能性」「apt/dpkg process・lockとpackage状態を確認すること」「自動reboot/post-checkへ進んでいないこと」を明記し、具体的な復旧操作は状態確認後に判断させること。 | High |

## What Looks Good

- AC1: `apt-get`へ`-o Dpkg::Options::=--force-confold`が渡る。
- AC3: conffile検出はapt/dpkgの自由文を解析せず、`${Conffiles}`とdigestを使うためlocale依存はない。`LC_ALL=C`もscript実行環境に入る。ただし検出意味論とfail-closed性はfinding 2・3のとおり未達。
- AC5: `NEEDRESTART_MODE: l`がapt taskのenvironmentへ入る。
- 指摘1の前提確認: `ubuntu_vm_full_upgrade_sim`は同一hostのCommon processing内で`set_fact`され、その後にapply includeへ到達する。apply targetなら`ubuntu_vm_full_upgrade_participates`も必ずtrueであり、`simulation.inst`はapply時点で定義済み。
- AC7: destructive includeは引き続き`ubuntu_vm_full_upgrade_is_apply_target and not ansible_check_mode`で囲まれ、新規copy/check/notification factも`apply.yml`内なので`--check`では到達しない。playbookの`check-mode-native`分類と整合する。
- 保持conffile blockは`reboot_local.yml`と`reboot_quory.yml`のapply-summary本文先頭にあり、`common_slack`へ渡すattachment text内で候補一覧より前に描画される。
- timeout taskのrc領域は現状、0=続行、124=timeout fail、その他=generic failで網羅され、`failed_when: false`による非0の握りつぶしはない。
- `ansible-playbook playbooks/ubuntu_vm_full_upgrade.yml --syntax-check`はrc=0。新規shellは`bash -n` rc=0。`shellcheck`はansyに未導入のため未実施。
- 対象差分で秘密値のログ露出、shell injection、危険な`delegate_to`/lookup追加は見つからなかった。

## Test Gaps / Recommended Tests

1. AC4は、短いdurationで単純な`sleep`を止めるだけでなく、TERMを無視する使い捨てprocessを対象にし、grace後に必ず終了すること、rc=137側もtimeoutとして明示されることを確認する。aptは実行しない。
2. AC2/R2は、少なくとも次をfixture化してassertする: (a) 0件、(b) 今回package側conffile digestが変わり局所版を保持、(c) 以前から局所変更済みだが今回package側digestは不変、(d) `dpkg-query`失敗、(e) conffile読取失敗/削除、(f) `obsolete` entry。(c)を通知してはならず、(d)〜(f)を正常な「該当なし」にしてはならない。
3. timeout後の通知/fail文面について、部分適用とpackage database要確認が運用者に見えることを描画で確認する。
4. requirement記載どおり、実際のdpkg conffile競合に対するR1の最終確認は本番で該当更新が発生する月まで未確認として残る。Reviewerは実ホスト検証を行っていない。

## Unverified / Residual Risk

- `--force-confold`と`NEEDRESTART_MODE=l`の実ホスト上の最終挙動は未確認。
- 1800秒が運用上適切かは実績不足。値の妥当性とは別に、まず機械的な上限保証が必要。
- レビュー着手時と返却前の対象差分に変化はなかった。対象外の既存/並行差分には触れていない。

## Verdict

**Request Changes** — findings 1〜4を解消し、修正後diffと対応テスト結果を受け取って再レビューする。
