### P0-5(差し戻しで追加) — timeoutの値の選定根拠

`community.general.slack` の `do_notify_slack()` は `fetch_url(module=module, url=slack_uri, headers=headers, method="POST", data=data)` を **`timeout=` を渡さずに**呼んでいた。`ansible/module_utils/urls.py` の `fetch_url()` シグネチャは `timeout=10` を既定値に持つため、**旧経路の実効timeoutは10秒**だった(requirementの記述と一致、コードで確認済み)。

`ansible.builtin.uri` は自身の既定が30秒であり、かつ `incident_investigate_notify.yml` は `incident-investigate.py` から `subprocess.run(..., timeout=cfg["notify_timeout_s"])`(既定30秒、`roles/incident_investigate/defaults/main.yml:178`)で起動される。既定のまま(30秒 = 30秒)だと、無応答endpointで親のsubprocess timeoutと`uri`自身のtimeoutが同時に競合し、どちらが先に発火するかが保証されない — 親が先に子プロセスを殺せば`rescue`は一度も走らない。

**両taskへ `timeout: 10` を明示した。** 選定根拠:
1. **旧経路の実効値(10秒)とちょうど一致させる** — 「旧経路の実効値を保つ」というP0-5の要求を、値の近似ではなく厳密な一致で満たせる。
2. `incident_investigate_notify.yml` 側の親timeout(30秒)に対して**3倍の余裕**を残す(10秒 vs 30秒)。ネットワーク的な揺らぎ(DNS再試行、TCPの再送)を考慮しても十分な差。
3. `common_slack/tasks/notify.yml` 側には対応する「親」timeoutは無いが、両経路を同じ値に揃えることで「明示的なtimeoutが必要」という判断基準を1つに保ち、値のドリフト(片方だけ変更されて再び競合する)を避けた。
