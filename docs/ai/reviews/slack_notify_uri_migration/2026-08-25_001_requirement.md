# Requirement: Slack送信を `community.general.slack` から `ansible.builtin.uri` へ移す

作成: 2026-08-25 / Coordinator

## 1. 問題定義

**`community.general.slack` は宛先を差し替えられない。** 送信先は `slack.com` / `slack-gov.com` にモジュール内でハードコードされており、`domain` 引数も無視される。`token` に何を渡しても、組み立てられるURLは `hooks.slack.com` である。

**その上に、宛先を差し替える形のdecoyを4回組み、4回とも実Slackへ出た。**

| 日付 | Incident |
|---|---|
| 2026-07-26 | 起動主体未確認(初回) |
| 2026-08-01 | `2026-08-01_tester-slack-decoy-did-not-contain-request.md` |
| 2026-08-02 | `2026-08-02_tester-slack-decoy-domain-quirk-recurrence.md`(自ら「同一欠陥クラスの3回目」と記録) |
| 2026-08-07 | `2026-08-07_decoy-webhook-reached-real-slack-endpoint.md` |

`docs/ai/core.md` は「本番Slackへ通知が送られた状態で報告を返さない」と既に定めている。**書いてあって4回起きている。** 規律ではなく、decoyが成立しない作りが原因である。

**送信は2箇所ある。片方だけ直すと、decoyが成立する経路としない経路が混在する** — 効く前例ができると、効かない側でも効くと思い込むため、いまより危険になる。

## 2. ゴール

**webhook URL を閉じたループバックポートへ向けたとき、`hooks.slack.com` へ一切出ない状態にする。** 宛先の決定をURLの側へ戻す。

## 3. 非ゴール

- **通知の見た目を変えない。** color / icon / attachments の構造も、プレーンテキスト経路の本文も、現行と同一の出力にする。
- **抑止の3トリガ(`skip_notifications` / `ansible_check_mode` / AIエージェントセッション検出)に触れない。** 判定ロジックも `slack_force_send` の効き方も現行のまま。
- **decoyの作り方をSkillやPolicyへ規定しない。** 本案件は作りを直すものであり、手順を足すものではない。
- **`incident-investigate.py` の `WEBHOOK_URL_RE` を消さない。** 多層防御として残す(§5 P0-4)。
- retry / backoff を入れない。現行も best-effort で `rescue` が吸収する設計であり、変えない。

## 4. ユーザーストーリー

Testerとして、通知経路を検証するとき、**vars の webhook URL を閉じたポートへ向けるだけで送信が外へ出ないことを確信したい。** 現在はモジュールの実装を読まない限りそれが成り立たず、実際に4回失敗している。

## 5. 要件

### P0(初回実装に不可欠)

**P0-1. `roles/common_slack/tasks/notify.yml` の送信を `ansible.builtin.uri` へ替える。**
- `url` に `_slack_webhook`(完全なURL)を渡す。
- `body_format: json`、`body` に `{"attachments": [ ... ]}` を現行の5フィールド(`title` / `text` / `color` / `fallback` / `footer`)そのままで組む。
- `status_code: 200` を明示する(Slackのincoming webhookは成功時に本文 `ok` と200を返す)。
- **`no_log: true` を維持する。** URLが秘密である。
- **payload に `link_names: 1` を含める。** `community.general.slack` は `link_names` の既定値が `1` で、**両経路の payload へ常に入れていた**(`slack.py:472`)。省略すると `@here` やchannel/user-group参照の自動解析が無効になり、§3「通知の見た目を変えない」に反する。
- **「Extract token from webhook URL」タスク(現115行付近)を削除する。** URLをtokenへ削る処理が、宛先を指定する手段を捨てていた当の箇所である。

**P0-2. `playbooks/incident_investigate_notify.yml` の送信を `ansible.builtin.uri` へ替える。**
- `body` は `{"text": "{{ _iv_body }}" }`。**N2(ステータス・重要度・色分けを持たない)を維持する** — `attachments` を使わない。
- 同playbook内の `_iv_slack_token` 抽出も削除する。
- `when: not ansible_check_mode` と `tags: [destructive]` と `block`/`rescue` の構造は現行のまま残す。

**P0-3. 両経路とも `rescue` が現行どおり働くこと。接続失敗・非200のいずれでも `rescue` に落ちる。** ただし**その先の挙動は経路ごとに違い、どちらも現行を変えない。**

- `roles/common_slack/tasks/notify.yml` — `rescue` は debug を出して**吸収する**。playは失敗しない(best-effort通知)。
- `playbooks/incident_investigate_notify.yml` — `rescue` は `ansible.builtin.fail` で**再送出する**。**playは失敗する。** 2026-08-07 の Incident(通知が落ちても理由が残らなかった)への対応として意図的にそうしてあり、`incident-investigate.py` がその失敗を受け取る前提になっている。

**訂正(2026-08-25)**: 本項は当初「両経路とも…playが失敗しない」と書いていた。`common_slack` 側の挙動を両経路へ一般化したCoordinatorの誤りである。Implementerが実装中に現物と食い違うことを検出し、勝手に整合させず報告した。経緯は `docs/ai/memory/incidents/2026-08-25_decoy-slack-reached-real-endpoint-during-its-own-fix.md`。

**P0-4. 失敗時の出力にwebhook URLが出ないこと。** `community.general.slack` は失敗msg内のURLを `[obscured]` へ伏せていた(slack.py:449-452)。**`uri` はこれをしない。** `no_log: true` が抑えることを実測で確かめる。`incident-investigate.py` の `WEBHOOK_URL_RE` は残すが、**それに依存せずに漏れないこと**を要件とする。

**P0-5(追加、2026-08-25). 両 `uri` タスクへ明示的な `timeout` を置き、旧経路の実効値を保つ。**

`community.general.slack` は `fetch_url()` へ timeout を渡さず ansible-core の既定(10秒)で動いていた。**`ansible.builtin.uri` の既定は30秒である。** そして `incident-investigate.py` は通知playbookを `subprocess.run(..., timeout=cfg["notify_timeout_s"])` で起動し、**その既定も30秒**(`roles/incident_investigate/defaults/main.yml:178`)。

**同値であるため、応答を返さないendpointでは親が子を殺すのと `uri` が諦めるのが競合し、`rescue` が走らない。** `rescue` は 2026-08-07 の Incident(通知が落ちても理由が残らない)への対応そのものであり、**それを迂回する。** `common_slack` 側も待ち時間が最大3倍になる。

**親の timeout より十分短い値を明示する。** 値の選定は実装者が決めてよいが、根拠を実装記録に残すこと。

### P1(入れたいが、無くても初回は成立する)

**P1-1. `playbooks/README.md` に変更が要るか確認し、要るなら更新する。** 新規playbookは増えないため不要の見込みだが、確認そのものは成果物に含める。

### P2

**P2-1. `docs/ai/context/operations/` に、Slack送信の宛先がURLで決まる旨を1行残すか検討する。** 本案件では判断のみ行い、実施は別。

### Won't

- `common_slack` と `incident_investigate_notify` の送信を1箇所へ統合すること。**後者が前者を経由しないのは N2 を満たすための意図的な設計**であり(playbookヘッダに明記)、本案件で覆さない。

## 6. 受入条件

**AC1 — decoyが成立する(本案件の核心)**
> **Given** `vars/slack.yml` の3つのwebhook URLをすべてループバックの閉ポートへ向けたdecoyを用意し、
> **When** `common_slack/tasks/notify.yml` を経由する通知と `incident_investigate_notify.yml` の通知をそれぞれ実行したとき、
> **Then** どちらも `hooks.slack.com` へ接続を試みない。**確認手段は実行中の接続先の観測**(`ss` / `tcpdump` / strace 等、Testerが選ぶ)であり、**「Slackに出ていないこと」の目視を根拠にしない。** 終了コードは経路で異なる — `common_slack` 経由は `0`(`rescue` が吸収し debug が出る)、`incident_investigate_notify.yml` は**非ゼロ**(`rescue` が `fail` で再送出する。P0-3)。**どちらも現行と同じ終了コードであること。**

**AC2 — 本番へ出る経路が生きている**
> **Given** 実の webhook URL(`#info` チャンネル)を使い、
> **When** 通知を1本送ったとき、
> **Then** `#info` に**現行と同じ見た目**(icon + title、本文、色)で1本届く。終了コード `0`。
> **この検証は本番通知であるため、実行前にYoshinobuの承認を得る。**
>
> **`link_names` の描画効果は、実チャンネルで確かめない**(Coordinator判断、2026-08-25)。効果を出すには本文へ `@here` やchannel参照を含める必要があり、**それは実チャンネルの全員へ通知を飛ばす**。`link_names: 1` は旧経路の既定値を戻したものであり、**検証は payload に当該キーが含まれることの構造的な確認で足りる**(decoyで捕捉したJSON bodyを見る)。Testerはこれを実webhookで試さないこと。

**AC3 — プレーンテキスト経路の形が変わらない**
> **Given** `incident_investigate_notify.yml` を実 webhook で1本送り、
> **Then** `#alerts` に**attachmentsではないプレーンテキスト**で届く(色・ステータス表示が付かない)。N2充足。

**AC4 — 抑止が現行どおり効く**
> **Given** ①`skip_notifications=true` ②`--check` ③`CLAUDECODE` が設定された環境、の3条件をそれぞれ与え、
> **When** 通知タスクを実行したとき、
> **Then** 3条件とも送信タスクへ到達せず `[suppressed]` の debug が出る。**`slack_force_send=true` はトリガ3のみ上書きし、①②は上書きできない**(TS-031)。終了コード `0`。

**AC5 — 失敗してもURLが出ない**
> **Given** 到達できない webhook URL を与え、
> **When** 送信が失敗したとき、
> **Then** playの標準出力・標準エラー・`incident-investigate.py` が捕捉する出力のいずれにも `https://hooks.slack.com/services/` で始まる文字列が現れない。**`WEBHOOK_URL_RE` を無効化した状態でも現れないこと**を確かめる(多層防御が1層でも成立していることの確認)。

**AC7 — 無応答のendpointでも `rescue` が完走する(P0-5)**
> **Given** 接続は受け付けるが応答を返さないローカルのHTTP fixtureへ webhook を向け、
> **When** 両経路をそれぞれ実行したとき、
> **Then** **親の timeout(`incident_investigate_notify_timeout_s`、既定30秒)が満了する前に `uri` が失敗し、`rescue` が完走する。** `incident_investigate_notify.yml` 経路では、`incident-investigate.py` から起動した場合に `TimeoutExpired` ではなく playbook の非ゼロ終了として観測される。
> **接続拒否のfixtureでは検出できない** — 即座に失敗するため競合が起きない。**accept後に無応答となるfixtureを使うこと。**

**AC6 — 配備物側**
> `common_slack` はrepoから読まれるroleであり配備物を持たないが、**`incident-investigate.py` は `/usr/local/sbin/` へ配備されている。** 本案件が同ファイルへ変更を加えた場合は、`deployed-hash incident-investigate` がrepoと一致することを配備後に確認する。**加えなかった場合はその旨を記録する。**

## 7. オープンクエスチョン

- **`ansible.builtin.uri` の check_mode は論点にならない。** 当初Coordinatorは「`uri` は `check_mode: support: none` でauto-skipされるため register の値が変わる」と挙げたが、**両経路とも送信タスクは `ansible_check_mode` を含む `when:` で既にゲートされており、`--check` では送信タスクへ到達しない。** 差は生じない。この項は解消済みとして残す。
- Slack incoming webhook が `attachments` を今も受理するか(legacy扱いだが現行の通知は実際に届いている)。**現行が届いている以上、形を変えなければ受理される**という前提で進める。変える必要が出たら止めて報告する。
- ~~decoyでの接続先観測にTesterがどの手段を使えるか~~ **解消済み(2026-08-25、Coordinatorがansyで実測)。** `ss` / `tcpdump` / `strace` / `lsof` は4つとも存在し、`ss` は非rootでpeer addressまで出る。`tcpdump` はバイナリがあるがキャプチャの権限は未確認。
  **推奨する観測手段は `strace -f -e trace=network` を `ansible-playbook` に掛けること** — 自分の子プロセスが対象なので非rootで動き、`connect()` の宛先が直接見える。`no_log: true` がタスク出力を伏せるため、**モジュールの出力からは宛先を確認できない**ことに注意する(伏せるのは正しい挙動であり、観測はプロセス側から行う)。
  **補助的な指標**: decoyがループバック宛なら `hooks.slack.com` の名前解決自体が発生しない。ansyはこの名前を解決できる状態にあるため(実測)、**解決が起きないことは宛先が差し替わった証拠になる。**

## 8. タイムライン考慮

- 工程は requirement → Implementer → Reviewer(codex側、独立)→ Tester の直列。
- **AC2 / AC3 は本番通知を伴うため、Yoshinobuの承認が要る。** それ以外はdecoyで完結する。
- `incident-investigate.py` へ変更が及ぶ場合、配備はquoryのSemaphore(Yoshinobu起動)であり本案件のscope外。**要ることを成果物に残す。**
