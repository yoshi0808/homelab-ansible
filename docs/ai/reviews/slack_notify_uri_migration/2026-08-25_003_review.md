# Code Review: Slack notify URI migration

Reviewer: Codex / 2026-08-25  
対象: `5cdaf7f..3315c62`  
Verdict: **Request Changes**

## Summary

宛先決定を完全なwebhook URLへ戻す核心の変更は成立している。Reviewerの独立decoyでも、両経路は数値ループバックの閉ポートだけへ接続し、`common_slack`は失敗を吸収してrc=0、incident経路はrescueから再送出してrc=2となり、標準出力へURLを出さなかった。抑止条件、check-mode境界、`no_log`、N2のプレーンテキスト構造も後退していない。

ただし、移行前のHTTP timeout 10秒が`uri`既定の30秒へ暗黙に変わり、incident通知playbook全体を起動する親プロセスの30秒timeoutと競合している。応答しない接続ではplaybookのrescueへ到達する前に親が子プロセスを終了させる。また、旧モジュールが両payloadへ常に入れていた`link_names: 1`が脱落し、本文中の自動的なchannel/user-group参照の解決挙動が変わる。いずれも「現行を変えない」という契約に対する具体的な差である。

## What Looks Good

- 旧token抽出taskは2経路とも削除され、完全なURLが`uri.url`の唯一の宛先入力になった。`community.general.slack`の実行箇所は、`docs/ai/memory/`と案件記録を除く実装内でゼロである。
- 独立decoyで`common_slack`は`rescued=1`, rc=0、incident経路は`rescued=1`, rc=2となり、訂正後P0-3/AC1の経路別契約と一致した。
- 失敗したuri taskは`no_log: true`によりcensorされ、incident rescueは`_iv_send.msg`だけを再送出し、完全URLを保持する`_iv_send.url`を参照しない。Reviewerの接続拒否decoyでもURL、decoy token、ループバックURLは出力されなかった。
- `WEBHOOK_URL_RE`とredaction処理は残り、redaction後にtailを切る順序も不変である。
- `incident-investigate.py`はdocstring/commentのみの変更で、docstringを除いた親commitとのASTは一致した。実行ロジックは変わっていない。
- `incident_investigate_notify.yml`は`when: not ansible_check_mode`と`tags: [destructive]`を維持し、N2どおり`{"text": ...}`だけを送る。`common_slack`の3抑止条件も差分上不変である。
- 2経路を統合しない判断はrequirementのN2境界と一致し、指定された既存資産を無理に再利用する欠陥はない。
- shell/command追加、変数のshell展開、delegate先変更、`no_log`後退はない。
