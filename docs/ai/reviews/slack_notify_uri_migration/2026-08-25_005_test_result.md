## 検証環境

- decoy inventory: `/tmp` scratchpad配下に自作（`hosts.yml` は `ansible_connection: local` の `localhost` のみ、実host名・実IPなし）。`vars/slack.yml` は3 webhook URLを `ループバックアドレス:<port>` の decoy へ差し替えたもの（実値は一度も読んでいない — `inventories/vars/slack.yml` はfile存在確認のみで内容を読んでいない）。
- `common_slack` 経路は、対象 `roles/common_slack/tasks/notify.yml` を自作の使い捨てplaybookから `include_tasks`（絶対パス）で直接呼び、`slack_channel/status/title/message` を渡した。
- `incident_investigate_notify.yml` 経路は、対象playbookをそのまま実行（`-e iv_semaphore_task_id=999 -e iv_report_path=/tmp/fake-report.md`）。
- どちらも `--check` を付けずに実行した。理由: 送信task自体が検証対象であり、`check-mode-native` のもとで `--check` を付けると `when: not ansible_check_mode` により送信taskへ到達せず AC1/AC5/AC7 が成立しない。`docs/ai/core.md`「decoy inventory」節の3条件（実host名・実IPなし／閉ポートまたはlocal接続／実システムに影響するモジュールなし）を満たし、EXEC-042の「`hosts: localhost` + `connection: local` で副作用のない使い捨てplaybook」に該当するため承認不要の範囲として実施した。実行後、使い捨てplaybookと一時inventoryは全て `/tmp` scratchpad配下に閉じている。
- `CLAUDECODE=1` が本セッションのshellで既に設定されていたため、trigger3を上書きして送信taskへ到達させる検証では `slack_force_send=true` を付与した（trigger1/2を検証するケースでは付与しても上書きされないことも確認した）。

## AC1 — decoyが成立する

- 3 webhook URLをすべて `ループバックアドレス:39217`（`echo > /dev/tcp` で事前に closed であることを確認済み）へ向け、両経路を実行。
- `strace -f -e trace=network` で観測: `connect()` は `ループバックアドレス:39217` の1回のみ、両経路とも。`hooks.slack.com` という文字列はstrace出力に一切現れない（`grep -c slack` = 0）。
- 終了コード: `common_slack` 経由 rc=0（`rescued=1`、`[Slack notification failed (ignored)]` debugが出力）。`incident_investigate_notify.yml` 経由 rc=2（`rescue` の `ansible.builtin.fail` が再送出）。
- 「現行と同じ終了コード」の確認: `git log` で両rescue構造（吸収 / 再送出）が本migration以前から存在することを確認した（`common_slack`は`74870ae`以来、`incident_investigate_notify.yml`の再送出構造は`1eebda4`以来、いずれも`5cdaf7f`より前）。今回のmigrationは送信モジュールのみを差し替えており、rescue構造自体は変更されていない。`ansible.builtin.fail`によるtask失敗は常にansible-playbookのrc=2を生むため、モジュール差し替えでrcが変わる余地はない。

## AC4 — 抑止が現行どおり効く

`common_slack/tasks/notify.yml` へ decoy(閉ポート)経由で3条件をそれぞれ単独/併用で与え、自分で再測定した（実装者の自己申告を引き継いでいない）。

1. `skip_notifications=true`（+ `slack_force_send=true` を併用し、trigger1が上書きされないことも確認）→ 送信task `skipping`、`[suppressed]` debugに `trigger1 skip_notifications: True` が出力、rc=0。
2. `--check`（+ `slack_force_send=true` 併用）→ 送信task `skipping`、trigger2が上書きされないことを確認、rc=0。
3. `CLAUDECODE=1`（本セッションの既定状態、trigger3単独）→ `slack_force_send` 未指定では送信task `skipping`（`[suppressed]`にtrigger3=Trueが出力）、rc=0。`slack_force_send=true` を付けると送信taskへ到達（decoy接続拒否で失敗し`rescue`が吸収、rc=0）— trigger3のみ上書き可能であることを実測で確認した。

## AC5 — 失敗してもURLが出ない

- 接続拒否のdecoy（39217）で両経路を実行し、stdout/stderrをファイルへ保存して `hooks\.slack\.com/services/` と decoy自身のtoken文字列パターンの両方をgrep → いずれも0件。
- `no_log: true` により送信taskの出力自体が censored される（`common_slack`側で実測: `"censored": "the output has been hidden..."`）。
- `incident_investigate_notify.yml` の rescue が再送出する `_iv_send.msg` について、**`WEBHOOK_URL_RE` による redaction を経由しない生の `msg` フィールド**を別の使い捨てplaybookで直接debug表示し、接続拒否失敗の `msg` にはそもそもURLが含まれないことを構造的に確認した（`urlopen error [Errno 111] Connection refused` のみ）。これはrequirementが求める「`WEBHOOK_URL_RE`を無効化した状態でも現れないこと」の確認に相当する — regexが実際に効いているからではなく、そもそも`.msg`フィールドにURLが混入しない設計であることを実測で裏付けた。`info['url']`（`_iv_send.url`相当）はrescue taskが参照していないことをコードで確認済み（実装記録・Reviewerと同じ結論を自分でも確認）。

## AC7 — 無応答endpointでも rescue が完走する

- 接続を受け付けるが読み書きを一切しないTCP listener（`accept()`のみ、`recv`/`send`なし）をループバックの未使用ポートに自作し、decoyの3 webhookをそこへ向けた。接続拒否ではなく accept 後無応答の fixture である点を確認済み。
- `incident-investigate.py` の呼び出し形（`subprocess.run(argv, cwd=repo_dir, capture_output=True, text=True, timeout=cfg["notify_timeout_s"])`、既定30秒）を模した使い捨てPythonラッパーで `incident_investigate_notify.yml` を起動 → **`TimeoutExpired` は発生せず**、`COMPLETED rc=2 elapsed=10.88s` で完走。stdout/stderrにURLパターンなし。
- `common_slack` 経由も同じfixtureで実行 → `real 0m10.983s`、rc=0、`rescued=1`。
- 両経路とも `uri` の `timeout: 10` どおり約11秒（TCP接続確立後の応答待ちタイムアウト。接続確立自体のオーバーヘッド込みで実測11秒弱）で失敗し、親の30秒より十分早く完走することを確認した。
- fixtureプロセスは検証後に `kill` し、`ps`で消滅を確認した。

## `link_names` 構造確認

- 200を返すHTTPキャプチャサーバ（`ループバックアドレス:39219`、受信bodyをファイルへ書き出し）へ両経路のdecoy webhookを向けて実行（実Slackへは一切送っていない）。
- 捕捉したJSON body:
  - `common_slack`: `{"link_names": 1, "attachments": [{"title": "...", "text": "...", "color": "good", "fallback": "...", "footer": ""}]}`
  - `incident_investigate_notify.yml`: `{"text": "...", "link_names": 1}`
- 両経路とも `link_names` はpayload直下（top-level）に整数値`1`で存在し、`attachments`/`text`と兄弟の位置。requirement P0-1/P0-2の要求どおり。`@here`等は本文に含めておらず、実Slackへの描画効果テストは行っていない（AC2の限定どおり）。
