## D6 の判断(Yoshinobu、2026-08-06)

`serial_getty_mask` は **allow-list ではなく保護対象の拒否**とした。塞ぐべきリスクは
「保護対象へ届くこと」であり既知の有限集合である。allow-listにすると新しいVMのたびに
inventoryとallow-listの2箇所を直してからでないとボタンが効かず、D2の用途
(cloud-initで作ったら1回押す)と噛み合わない。

**`authy` はこの拒否リストから外してある。** `docs/ai/roles/coordinator.md` の保護対象は
pve1 / pve2 / authy / sophos-fw / UniFi機器だが、**authyはこのplaybookの既定4ホストの
一員であり**、拒否すると既定実行(R1 / AC1)が壊れる。**変更前もCLIで `-l authy` と
指定すればauthyへ適用できたので、新たな露出は増えていない。**

保護対象の一覧は `coordinator.md` が散文で持ち、playbook側は literal のコピーになる。
これは規律4の「値を二重に持たない」に反するが、**規範文書とそれを強制するコードは
原理的に同じ値を2箇所へ持つ**(実装記録 §2.6 に代案と却下理由)。

## 残っているもの

- **`target_hosts` に空文字を与えたときのメッセージが用を成さない。** `serial_getty_mask` は
  保護対象assertが捕まえて rc=2(空文字は全ホストへ解決するため)、`time_sync_ntp_reference` /

- **実ホストでの実行は一度も行っていない。** 検証はすべて decoy と `--check`、および
  `--list-hosts` による対象集合の確認である。ansyから quory / authy / pve1 / pve2 へは
  到達手段が無い。
- **role側assertが既定ホストに対して新たな失敗を生まないことは、静的読解と `--list-hosts` の
  範囲で確かめた。** 実際に既定セットへ流したわけではない。

## decoy条件1について(判断の記録)

独立Reviewer(`..._004`)が、自分のdecoy inventoryで **実ホスト名(`pve1` / `sophos-fw` 等)を
使ったことを自己申告した**。`docs/ai/core.md` のdecoy条件1(実host名・実IPを書かない)を
満たしていない。

**この逸脱は必要だった。** 検査対象が「`pve1` という文字列を拒否するか」である以上、その
文字列なしには検証できない。`ansible_host` を閉じたループバックポートへ固定して条件2・3は
満たしており、`/tmp` に閉じている。**隠さず申告した点を含めて妥当な処置と判断した。**

これは `core.md` の条件1が想定していなかったクラス — **ホスト名のリテラルそのものが検査
対象になる場合** — である。条件1を書き換えるかは Next の「`docs/ai/roles/` 5本のプロンプト
最適化」で扱う(この案件では変更しない)。
