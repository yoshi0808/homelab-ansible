## 2. 変更内容

### 2.1 R1/R2: `target_hosts` による対象ホスト選択(3本共通の形)

3本とも同じ形にした。

1. **`hosts:` 行**を `hosts: "{{ target_hosts | default('<元の値>') }}"` へ変更。`<元の値>` は変更前の `hosts:` の文字列そのまま(serial_getty_mask: `ansy:monnie:quory:authy`、rsyslog_forward_to_monnie: `ansy:quory:authy`、time_sync_ntp_reference: `pve1:pve2:ansy:monnie:authy`)。`target_hosts` 未指定時はJinjaの `default()` がこの文字列を返すので、R1(既存対象と完全に同じ)を満たす。
2. その手前に **`hosts: localhost` の検証play**を新設。`target_hosts is defined` のときだけ、`query('ansible.builtin.inventory_hostnames', target_hosts)` でinventoryへ実際に解決させ、0件なら `assert` で `fail_msg` を出して停止する(`quiet: true`)。`target_hosts` 未指定時はこのplay自体が2 taskとも `skipping` になり、既存の対象(3.のいずれかの元の値)への到達に一切影響しない。

この2点セットにした理由:

- **`hosts:` 行だけでは R2 を満たせない。** Ansibleは host pattern が0件に解決しても標準では `[WARNING]: Could not match supplied host pattern, ignoring: ...` を出すだけで、そのplayを0ホストとしてスキップし後続へ進む(rc=0)。これがrequirement §2の実測(`-e target_hosts=ansyy` → rc=0)そのものであり、`hosts:` の書き方だけでは変わらない。
- **`run_once` 系のpre_tasksガードでは0件を捕まえられない。** `skills/ansible-implementation-style/SKILL.md`「ガードtaskが発火しない条件」のとおり、`run_once` は「生存ホストのうち1台で実行する」という意味であり、対象ホストが0件ならガードtask自体が実行されない。同じ理由で、対象play自身のpre_tasksへ0件チェックを置いても発火しない。
- そのため、**対象ホストの決定とは別のplay(`hosts: localhost`)**で、Ansible自身のhost pattern解決ロジック(`inventory_hostnames` lookup。`hosts:` キーワードや `--limit` と同じ構文・同じ解決規則)を使って検証する設計にした。これは本リポジトリに既存の前例がある——`playbooks/proxmox_patch_apply_node.yml` が `hosts: localhost` の検証playを主playの前に置き、主playの `hosts:` を `"{{ target_node | default('__invalid_target__') }}"` とテンプレート化している(この既存例は固定enumに対するassertで、今回のような任意ホスト名の存在確認ではないため `inventory_hostnames` lookupを追加で使う必要があった)。
- `set_fact` と `assert` はいずれも `ansible-doc` で `check_mode.support: full` であることを確認済み(自己検証3.1)。`--check` 下でも通常どおり実行され、`when: not ansible_check_mode` 等の追加ゲートは不要。

3本とも `target_hosts` という同じ変数名にした。requirement R2 の実測コマンド例(`-e target_hosts=ansyy`)が既にこの名前を使っている。

### 2.5 AC7: role側のホストリストへ含まれないホストの明示的な失敗(差し戻し対応)

**観測された欠陥**: R1/R2の検証play(§2.1)は「`target_hosts` がinventoryへ解決するか」しか見ない。その先で実際に処理を行うのは `roles/time_sync_ntp_reference` と `roles/rsyslog_forward_to_monnie` であり、両roleとも**別の、より狭いホストリスト**を内部に持つ(`time_sync_ntp_reference_chrony_hosts` / `rsyslog_forward_allowed_hosts`、いずれも `defaults/main.yml`)。inventoryには存在するがこのリストに無いホストを与えると、

- `time_sync_ntp_reference`: 唯一のtaskが `when: inventory_hostname in time_sync_ntp_reference_chrony_hosts` でskipされるだけで、**何も変更されないままrc=0で成功する**(§2.1の検証playを通り抜けたあと、もう一段の「何もしない緑」が残っていた)。
- `rsyslog_forward_to_monnie`: 先頭の `assert` の `that:` リストの1条件として `inventory_hostname in rsyslog_forward_allowed_hosts` が既に含まれていたため止まりはする(rc≠0)が、`fail_msg` は「numbered filename and stop policy」という無関係の文言で、**allow-listが原因だとは分からない**。

`serial_getty_mask` はroleを持たずplaybook本体にtaskを直書きしているため、この種の第2のリストが存在しない(requirement §5「AC7の背景」の表のとおり「該当なし」)。したがって対応対象は2 role。

**採った案**: 各roleの `tasks/main.yml` 先頭に、**既存の変数をそのまま参照する** `assert` を1つ追加した。

- `time_sync_ntp_reference`: 新規 `assert`(`that: inventory_hostname in time_sync_ntp_reference_chrony_hosts`)を、既存の `when:` と同じ条件式のまま、既存taskの直前に追加。
- `rsyslog_forward_to_monnie`: 既存の結合 `assert` の `that:` リストから `inventory_hostname in rsyslog_forward_allowed_hosts` の1行を抜き出し、単独の新規 `assert` へ移した(条件式は変更していない。結合assertからは同じ行を削除しただけで、残りの条件は元のまま)。

いずれも `fail_msg` に「どのホストがどの変数のどの一覧に無いか」と、その変数を持つ`defaults/main.yml`のパスを明記した。

**却下した案**:

1. **§2.1の `hosts: localhost` 検証playへ、role側リストの判定も足す。** 却下理由: そのplayは `target_hosts` が実行対象ホストへ解決する*前*に走るplayであり、`inventory_hostname` はまだ「検証対象の1台」を指していない(localhost自身を指す)。role側のリストとの突合をそこで行うには、対象ホスト名を検証playの内部でもう一度手動で取り出す必要があり、かつ判定に使うホストリストの値をどこかから持ってこなければならない——`include_vars: roles/<role>/defaults/main.yml` で読む案も検討したが、これは「同じ値を2箇所に持たない」という規律4の精神には反しない(ファイルは1つ)ものの、playbook側がrole内部の`defaults/main.yml`というファイルパスへ直接依存する新しい結合を生み、role側の実装詳細(変数名・ファイル配置)にplaybookが依存する構造になる。加えて`inventory_hostname`のコンテキストが本来の対象ホストと一致しない検証playの中でこの判定を行うこと自体が不自然。
2. **役割リストの値を検証playへ複製する(例: `-e`のデフォルト値やplaybook側のvarsとして再掲)。** 却下理由: これはrequirement §5末尾が明示的に禁じる「同じ値を2箇所へ持たせない」(`docs/ai/status.md` 規律4)そのものであり、defaults側を変更してもplaybook側が古いまま残るドリフトの温床になる。
3. **role側の `when:`/既存assertをそのまま維持し、`fail_msg` だけ書き換える。** rsyslogには適用可能(既存の結合assertの`fail_msg`を条件別に出し分けることは通常の`assert`モジュールでは不可——1つの`that:`リストに対して1つの`fail_msg`しか持てない)だが、time_syncの方は「skipするだけで何も失敗しない」問題そのものが解決しないため不採用。

**採った案(単独`assert`を1つ追加/分離)を選んだ理由**: 参照している変数はいずれも各roleが既に単一の正本として持っている(`defaults/main.yml`)ため、**値の複製が一切発生しない**。`inventory_hostname` は対象ホストを処理しているplay内で自然に正しい値を持つ。diffも最小(time_syncは純粋に1task追加、rsyslogは既存条件の1行を移動しただけ)。

### 2.6 AC9〜AC11: 独立レビューのCritical/High採用と、却下されたLow2件(2回目の差し戻し対応)

独立レビュー`2026-08-06_003_review.md`のCritical #1・High #2をYoshinobuが現物確認のうえ採用し、requirement D6/D7・AC9〜AC11として追加された。Low #1(命名)・Low #2(重複)はCoordinatorが却下した(Implementerの判断ではない、依頼文どおりに記録する)。

**Critical #1(`serial_getty_mask.yml`のホストスコープ矛盾、D6/AC9/AC10)**: ヘッダは「pve1/pve2はスコープ外」と明言するが、`target_hosts`は自由入力かつguardが無く、pve1等を技術的に到達させられた。

**採った案**: `hosts: localhost` の検証play(§2.1で新設済み)へ、`serial_getty_mask_protected_hosts: [pve1, pve2, sophos-fw, cloudkey]` という**保護対象拒否リスト**を`vars:`として追加し、`(resolved | intersect(protected)) | length == 0` を`assert`する第3のtaskを追加した。`target_hosts is defined` のときだけ動く(既定4ホストは無条件に安全なため、既存の2 taskと同じ条件)。この保護対象リストの値は`docs/ai/roles/coordinator.md`「実ホストへの非冪等操作の承認」の保護対象ホスト行(pve1/pve2/authy/sophos-fw/UniFi機器)から、**authyを除いたもの**——authyはこのplaybook自身の既定4ホストの正規メンバーであり、拒否すると R1/AC1 と矛盾する——を採り、「UniFi機器」はこのrepoが唯一Ansible対象として名指しするUniFi機器である `cloudkey` に対応させた。

**保護対象リストの置き場所(依頼文が明示的に設計判断を求めた点)**:

| 案 | 内容 | 判定 |
|---|---|---|
| **採用**: `serial_getty_mask.yml`本体の検証playに`vars:`として直書き | 新規ファイルを作らない。値の由来(`docs/ai/roles/coordinator.md`)をコメントで明記し、その文書の記述が変わったら手で追随する必要がある旨も明記 | 採用 |

結論として**値の完全な非重複**は達成できない(`docs/ai/roles/coordinator.md`の散文と、playbookの`vars:`の2箇所に同じホスト名が存在する)。これは「同じ機械可読データを2箇所に持つ」というAC7/規律4が禁じた形とは性質が異なる——**一方は人間向けの方針文書、他方はその方針を強制するコード**であり、方針をコードで強制する限り、この種の「複製」は不可避である(ドキュメントを実行時にparseする方が実質的に危険)。コメントで由来と追随義務を明記することで対処した。

**High #2(rsyslog/time_syncの「新規VM」説明とAC7 guardの不一致、D7/AC11)**: ヘッダ・カタログのコメント・survey descriptionから「新規VMを指定する」という記述をすべて除去し、「ansyから直接届かない、既に構成済みのホストへ1台ずつ再適用する」という実際の用途(D7)へ書き換えた。あわせて、R2のinventory解決失敗時の`fail_msg`(「add the host there first if this is a newly created VM」)も、この2本については「新規VMは想定していない」という実態に合わせて書き換えた(serial_getty_maskの同フレーズはD2がそのまま有効なため変更していない)。

**却下されたLow2件(Coordinatorの判断、Implementerはこれに沿って何も変更していない)**:

- **命名(`target_hosts`が`playbooks/systemd_timers.yml`と意味が違う)**: 却下。`systemd_timers.yml`は`groups[target_hosts]`でグループ名としてしか使えないため意味が狭いだけで、グループ名はhost patternとしても妥当(包含関係であり衝突ではない)。「対象を選ぶために何を打つか」の名前を揃える方が読み手に有利、とCoordinatorが判断した。
- **重複(検証playが3本でほぼ逐語的に複製)**: 却下。主playの前に走る必要がある性質上、共通roleへ括り出しても各ファイルにplayの外枠は残るため節約は小さく、**安全のためのguardを間接参照にすると読み手が追う手間の方が増える**とCoordinatorが判断した。
