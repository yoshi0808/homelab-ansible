# spike: agmsg remote機能の探索(段0)

案件: `agmsg_remote_ops_channel`
実施: 2026-08-16 / Implementer(sandbox VM上での使い捨て検証)

対象は §8 Q1(到達範囲の絞り方)と Q4(更新手順と巻き戻し)。実装(role/playbook)はrepoへ残していない。sandbox上の構築物は使い捨てのまま残置した(末尾「sandboxに残した状態」)。

## 段1以降の設計を変える発見(最重要・先出し)

1. **`AGMSG_STORAGE_PATH` は分離を保証しない。** `team.sh`(team configの読み書きの起点)は環境変数を一切見ず、`$SCRIPT_DIR/../teams/$TEAM/config.json` というインストールディレクトリ相対パスで解決する(grep・実行で確認)。段1で「1つのインストールを設定だけ変えて使い回す」設計は取れない。**別インストール(`install.sh --cmd <name>`)を機体ごとに分ける**のが唯一の分離手段。
2. **`docker compose up -d --build` の既定は `0.0.0.0:8787`(全interface、IPv4/IPv6双方)で待ち受ける。** ドキュメントの「to a network you control」という注意書きに反し、**上流のCompose既定値そのものが到達範囲を絞っていない**。段1では`ports:`を明示的にloopback限定へ書き換える必要がある(実証済み、後述)。
3. **Dockerが公開したポートは、ホストのufw(INPUT chain)を素通りする。** Dockerは`DOCKER-USER`/`DOCKER`chainを`iptables`へ直接インストールし、`FORWARD`chainで処理する。ansyの現行ufwは`INPUT`chainだけを管理しており(`ufw status`で22/tcp・3000/tcpのみallow、実測)、**素朴に`ufw allow from quory to any port 8787`と書いても効かない**。到達範囲を絞る層は「Dockerが直接公開するポート」ではなく「ホスト常駐のnginx(非container)」に置く必要がある。
4. **`server/compose.yaml` に `restart:` ポリシーが無い。** ansy再起動後にDockerデーモンが上がっても、このcompose定義のままではコンテナは自動起動しない(R15に抵触)。段1で`restart: unless-stopped`相当を足す必要がある。
5. **既存の証明書ファイルは既にfullchain(leaf+中間CA)である。** `/etc/semaphore/tls/ansy.internal.crt` は2枚(`CN=ansy.internal` → `CN=Home-TLS-CA`)を連結済み(`roles/homelab_cert_renew/tasks/issue.yml`が`<host>.fullchain.crt`を配布している)。**R11(中間CA提示)のために新しい証明書材料を作る必要はなく、reverse proxyの`ssl_certificate`に同じファイルを指すだけでよい。**

## 1. `AGMSG_STORAGE_PATH` による分離

**試したこと**: sandbox上の実インストール(`~/.agents/skills/agmsg-a/`)に対し、`AGMSG_STORAGE_PATH=/tmp/fake-machine-two` を付けて `team.sh` を実行。あわせて `grep -rln AGMSG_STORAGE_PATH scripts/` と `team.sh` のソースを確認。

**分かったこと**: `AGMSG_STORAGE_PATH` を実際に読むのは `lib/storage.sh` / `rename-team.sh` / `check-inbox.sh` の3本のみで、team configの起点である `team.sh`(および `send.sh` / `history.sh` / `inbox.sh` が依存する経路)はこの変数を参照せず、`SCRIPT_DIR` 相対で解決する。上流の `docs/remote-setup.md` 末尾の注記が言う「二台目を環境変数だけで偽装すると、送信は自分のstoreに書けるがteam configは1台目のものを共有し続け、静かに壊れる」という症状は、コード側の参照有無としても裏が取れた。

**結論**: **分離できない。** 段1の安全設計は「別インストール(別 `--cmd`)を機体ごとに用意する」を前提に組む。

## 2. agmsg更新時のteam登録・message DBの扱いと巻き戻し(Q4)

**試したこと**: production版に近い状態(タグ `v1.1.13` — 実機は `v1.1.13-8-g4d3202d` で8 commit分だけ新しいが、`remote.sh`が無い点は実機と一致)からインストールし、team `oldteam` を作って2往復メッセージを送信。`SKILL_DIR`全体をtarでbackupしてから、最新チェックアウト(`v1.2.0`、`remote.sh`/`key.sh`あり)から `install.sh --update --cmd agmsg-old` を実行。

**分かったこと**:
- `install.sh --update` は `scripts/`・`SKILL.md`・`VERSION` 等だけを上書きし、**`db/`・`teams/` には一切触れない**(ソースコード上も `cp -R "$SCRIPT_DIR/scripts/."` のみで `db`/`teams` はコピー元にすら含めていない)。
- 実測: 更新前後で `db/messages.db` と `teams/oldteam/config.json` の SHA-256 は**完全一致**。`db/config.yaml` のMD5も一致。
- 更新後、`remote.sh` / `key.sh` が新規に出現し、`VERSION` は `v1.2.0` に更新。既存メッセージは `history.sh` でそのまま読め、新規送信も正常に機能した。
- **巻き戻し**: 更新前に取った `SKILL_DIR` 全体のtarを `rm -rf` 後に展開して復元。`VERSION` が旧版に戻り、`remote.sh` が再び消え、`history.sh` は更新前の2件に戻った(更新後に送った3件目は正しく消えた=バックアップ時点への復元として機能)。
- 付随確認: `remote.sh disconnect <team>` は接続前のローカル状態へ戻す動線として別に用意されており(ドキュメントの "Back up before connecting" 節)、実際に `spiketeam` で `disconnect` を実行してもローカル履歴は無傷だった。

**Q4への回答**: 更新手順は `install.sh --update --cmd <name>`(スクリプトだけを上書き、db/teamsは不可侵)。巻き戻しは**更新前に `SKILL_DIR` 全体を1回tarするだけ**で十分——db/teamsを個別に退避する必要はなく、更新自体がそこへ触れないため。段1では「更新直前に `~/.agents/skills/agmsg/` 全体をタイムスタンプ付きでバックアップしてから `--update` する」を定型手順にできる。

## 3. E2EE teamの作成と鍵束の受け渡し、サーバ側の暗号文確認

**試したこと**: `remote.sh connect --endpoint http://127.0.0.1:8787 --e2ee spiketeam` でteamを作成・接続、`key.sh handoff` でbundleを書き出し、別インストール(`agmsg-b`、同一sandbox上だが独立ディレクトリ)で `remote.sh pull` → `remote.sh unlock --bundle ... --confirm-digest ...` → `join.sh`。双方向送信後、Postgresコンテナへ `docker compose exec postgres psql` で直接クエリ。

**分かったこと**:
- 双方向配送を確認(A→B、B→Aとも受信側の `history.sh` に着弾)。
- `messages` テーブルのスキーマに `from`/`to`/`body` の列は**そもそも存在しない**(`team_id, id, team_seq, envelope_v, cipher, key_id, blob, envelope_digest` のみ)。
- 全行 `cipher = 'age-v1'`。`blob` をbase64デコードすると `age-encryption.org/v1` ヘッダを持つ本物のage暗号文で、5行全体に対し `alice`/`bob`/送信文言でgrepして**0件**(平文の混入なし)。

**結論**: ドキュメントの主張どおりで、DB現物で確認済み。段1の設計はこのままでよい。

## 4. サーバのTLSチェーン提示(中間CAを含むか)

**試したこと**: agmsgのreference server自体はTLSを終端しない(`server/README.md`「terminate TLS in front of the service」)ため、nginxで代替のreverse proxyを構成。**実鍵は複製できない**(秘密鍵の複製は理由を問わず禁止、`docs/ai/core.md`)ため、sandbox上でroot→intermediate→leafの3段構成を自前生成し、`leaf.crt + intermediate.crt` を連結した `fullchain.pem` をnginxの `ssl_certificate` に指定。`openssl s_client -CAfile root.crt` で検証。

**分かったこと**: nginxはleaf+intermediateの2枚チェーンを正しく提示し、root-onlyのCAfileで `Verify return code: 0` が成立(実測)。**既存の `/etc/semaphore/tls/ansy.internal.crt` を直接読んで確認したところ、これ自体が既にleaf+intermediateの2枚構成**(`CN=ansy.internal` が発行元 `CN=Home-TLS-CA` を含む)。したがって段1では新規に証明書材料を作らず、reverse proxyの証明書パスを既存の `cert_host_config.cert_path`(Semaphoreが使っているのと同じファイル)に向けるだけで成立する見込みが高い。

**結論**: 機構としては成立する。実際のansy証明書を使った終端確認はTester段で行う(自前チェーンでの検証は「連結すれば提示される」ことの証明であり、実鍵を使わない以上これ以上は進められない)。

## 5. 到達範囲の絞り方(Q1)

**試したこと**: `compose.yaml` の `ports: "8787:8787"` を `"127.0.0.1:8787:8787"` に書き換えて再作成し、`ss -ltnp` で待受アドレスを確認。あわせてansy自身の `ufw status` / `iptables -L` を確認し、Docker公開ポートとufwの関係を調べた。

**分かったこと**:
- 既定の `"8787:8787"` は `0.0.0.0:8787` と `[::]:8787` の両方で待ち受ける(実測)。
- `"127.0.0.1:8787:8787"` に変えると `127.0.0.1:8787` のみに変わり、外部interfaceからは到達不能になる(実測)。
- ansyの `iptables -L FORWARD` には `DOCKER-USER` / `DOCKER` chainがあり、公開ポートへの転送はここを通る。ansyの現行ufwはINPUT chainのみ管理しており(22/tcp・3000/tcpのみallow)、**DOCKER-USER chainには何も入っていない** — Docker公開ポートに対する到達制限をufwの通常構文で書いても効かない、という既知の落とし穴が実機でも再現する構造だった。

**Q1への回答(候補、根拠つき)**: 二層で絞る。
   (a) Docker側は `127.0.0.1` のみに公開し、生のHTTPをネットワークへ晒さない。
   (b) TLS終端はnginx(host常駐、非container)が担い、ufwの通常のINPUT chainルール(`ufw allow from <quory> to any port <https-port>`)で発信元を絞る——nginxはDockerの管轄外なので、ufwのINPUT chainがそのまま効く。
   「認証で弾く」は機構が無いため選べない、という要件どおりの制約下で、実機で効くことを確認した組み合わせはこの二層のみ。DOCKER-USER chainへ直接ルールを書く案も理論上はあるが、ufwの管理外に手書きのiptablesルールを持つことになり保守が割れるため、(a)(b)の方が既存のufw運用と一貫する。

## 6. Docker/PostgreSQLの資源消費

**試したこと**: sandboxへdocker.io・docker-compose-v2・nodejs 22・sqlite3・nginx・ageをaptで導入し、`docker compose up -d --build` 後に `docker stats --no-stream` と `docker system df`、`df -h` を実測。

**分かったこと**:
- 稼働中コンテナのRAM: `server` ≈ 33MiB、`postgres` ≈ 31MiB(合計 ≈ 64MiB、軽負荷時)。
- ディスク: イメージ計906MB、ビルドキャッシュ454MB(うち194MBは`docker builder prune`で回収可能)、volume 49MB。**プルーン後の実質フットプリントは概ね1GB弱。**
- sandbox自体は1.9GB RAM/8.1GB diskの小型VMで、apt導入(docker.io等)だけで空き disk が5.0GB→3.7GBへ、build後にさらに3.7GB→2.7GBへ減少した。ansyの実際の空きディスクは未確認(この spike の対象外)。

**掴めなかったこと**: ansy自身の現在の空きディスク・空きRAM。段1着手前にTesterまたはCoordinatorが確認する必要がある。

## 7. 証明書ファイル置き換え時の読み直し手段の候補

**試したこと**: nginxのTLS証明書ファイル(`fullchain.pem`/`leaf.key`)を新しいleaf証明書に差し替えたうえで `nginx -s reload` を実行し、置き換え前後で `openssl s_client` が返すleaf証明書のシリアル番号を比較。

**分かったこと**: `nginx -s reload` はworkerを無停止で再起動し、直後の接続から新しい証明書ファイルを提示する(実測、リロード前後でシリアル番号が切り替わることを確認)。ダウンタイムなしで読み直しが成立する。

**結論(候補どまり、実装はしていない)**: `cert_renew`側を変更しない制約の下では、ansy側に独立した検知手段が要る。実測で成立を確認したのは「ファイルの置き換え→`nginx -s reload`」という後半だけで、**前半(いつ置き換わったかの検知)は試していない**。候補としては systemd `.path` unit(証明書ファイルの変更を検知して reload をキックする)、または短周期タイマーでmtime/hashを比較する方式が考えられるが、どちらも段1での実装・検証が必要。

## 掴めなかったこと(まとめ)

- ansy自身の空きディスク・空きRAM(この spike は sandbox 上でのみ計測した)。
- 証明書ファイルの「置き換わったこと」自体を検知する具体的な実装(reloadが効くことは確認したが、検知の実装は候補止まり)。
- `homelab` team が実際に(実インストールで)remote化と無関係に無傷であることの直接確認。ドキュメント記載の設計(`connect`はteam単位で、未接続teamは共有storeに残る)とコード構造(`migrate-team-store.sh`がteam名をキーに動く)からは支持されるが、2つのteamを並存させて「触っていない方が本当に無傷か」を目視した二者比較は行っていない(実installを操作対象にしないため、production teamでは検証不可)。
- quoryから実際にsandboxのHTTPS経路へ到達できるかの実地確認(AC1-bと同種の残存確認で、この spike は ansy/sandbox側の機構確認に閉じている)。
- Node.js 22 / PostgreSQL 17 という上流の前提バージョンが、ansy自体のapt候補と一致するか(sandboxはUbuntu 26.04で両方aptから直接22系/17系が取れたが、ansyのOSバージョンとpackage候補は未確認)。
