# requirement: 開発↔運用の合図を agmsg で運ぶ(伝書鳩の置き換え)

案件: `agmsg_remote_ops_channel`
作成: 2026-08-16 / Coordinator

## 1. 問題定義

ansy 側 Coordinator と quory 側 Operator のあいだには、既に情報交換の経路がある(`docs/ai/context/operations/operator-request-channel.md`)。調査依頼・調査結果・開発修正依頼の**本文**は、Python + SSH forced command + DLP + spool を通って行き来する。

**それでも Yoshinobu が両方のチャットを手で往復している。** 運んでいるのは request の本文ではなく、その周りにあるもの — 「これを見てほしい」「その前提は違う」「結果が出た」といった**すり合わせの会話**である。既存経路は schema で縛られており、これを意図的に運ばない。

この往復は退屈で、自動化する価値がある。**ただし伝書鳩は3つの仕事を兼ねている。**

1. **運ぶ** — 退屈。自動化してよいのはここだけ
2. **選ぶ** — 相手へ渡す価値があるかを Yoshinobu が判断している
3. **決める** — **渡したという行為そのものが「これをやる」という決定**になっている

3つとも自動化すると、**片側のエージェントがもう片側の作業予定を直接決められる**ようになる。これは仮定ではなく**既に1回起きている**。`docs/ai/status.md`「載せていないもの」に記録がある。

> **quory の Codex 向け Semaphore read-only MCP の配備を案件化すること** — 2026-08-09、Yoshinobu が保留と決定(「レビューアーと会話していたら依頼されてしまった」)。codex 側 Reviewer からの依頼であり、**Reviewer の職掌の外**である

チャネルが違うだけで同じ形である。**本案件は 1 だけを自動化し、2 と 3 を人に残す。**

## 2. ゴール

1. Yoshinobu が両チャットを手でコピーしなくても、開発側と運用側が**すり合わせの会話**をできる。
2. **既存の Request Channel を1文字も変えない。** 本文・DLP・spool・forced command・鍵・identity のいずれにも手を入れない。
3. **agmsg のメッセージが権限を運ばないこと**を、運用習慣ではなく設計上の不変条件として持つ。
4. quory 側に常駐物を1つも増やさない。

## 3. 非ゴール

- **Request Channel の置き換え。** 調査依頼・調査結果・開発修正依頼の本文は、従来どおり forced command と DLP を通る。agmsg はこれを運ばない。
- **agmsg の到達をきっかけとした自動実行。** メッセージが届いても、どちらの側でも何も起動しない。
- **quory への常駐サービス・systemd unit・sudoers の追加。**
- **quory 側の規範の制定**(承認を求める前の提示義務など)。quory 側の管轄であり、**必要であることだけを §9 に申し送りとして書く**。
- `homelab` team(Coordinator + codex Reviewer)の remote 化。**local-only のまま据え置く。**
- 監視・アラートの追加。

## 4. ユーザーストーリー

- Yoshinobu として、片方のチャットで話した内容を**もう片方へ手で貼り直したくない**。ただし、**何を相手に渡すか**と**それを作業にするか**は自分で決めたい。
- Coordinator として、Operator から届いた内容は**報告するが、着手の前に必ず尋ねたい**。届いたことが着手の理由になってしまうと、優先順位付けが Yoshinobu の手を離れる。
- Operator(quory 側)として、届いたテキストを**判断材料として読む**。実行は Yoshinobu の承認を経る。

## 6. 受入条件

### AC1 — サーバが立ち、証明書チェーンが成立する

- **Given** ansy に agmsg サーバを配備した状態
- **When** ansy 側からサーバの TLS ハンドシェイクを観測する
- **Then**
  - **サーバが中間 CA(`Home-TLS-CA`)を含むチェーンを提示する**。リーフ証明書だけを返さない
  - **ルート CA だけを信頼アンカーとした検証が成立する**(`Verify return code: 0`)。既存6エンドポイントと同じ条件
  - ansy 側の既存 Semaphore(同ホスト、別ポート)に影響が無い

**この AC は ansy 側だけで判定できる。** quory へ到達せずに、検証成立の条件の大半をここで潰す。

### AC1-b — quory から実際に到達できる(**残存確認**)

- **Given** AC1 が成立した状態
- **When** quory 側から HTTPS でヘルスチェック相当のエンドポイントへ到達する
- **Then** 正常応答が返り、**検証を無効化していない**

**この AC は ansy から実施できない**(quory への到達手段が無い)。**Yoshinobu が quory 側で確認する区間として残す**(Q3、致命的ではないと合意済み)。

### AC2 — 到達範囲が絞られている

- **Given** サーバが稼働している状態
- **When** 運用上想定していない発信元から到達を試みる
- **Then** 到達できない。**「認証で弾かれる」ではなく「到達しない」で成立させる**(サーバに認証機構が無いため)

### AC3 — 新 team で双方向に届く

- **Given** 新 team が E2EE で作られ、両マシンが接続済み
- **When** Coordinator から Operator へ、および Operator から Coordinator へメッセージを送る
- **Then**
  - 双方向とも受信側のセッションへ届く
  - **サーバ側に保持される行が暗号文である**(`from` / `to` / `body` が平文で読めない)

### AC4 — `homelab` team が local-only のままである

- **Given** 新 team が remote 化された状態
- **When** `homelab` team でメッセージを送受信する
- **Then**
  - 従来どおり届く(codex Reviewer との疎通が壊れていない)
  - **`homelab` team の内容がサーバ側に一切存在しない**

### AC5 — Monitor が両 team を覆う

- **Given** Coordinator が `homelab/claude` と `homelab-ops/coordinator` の両方に登録されている
- **When** どちらの team 宛にメッセージが届いても
- **Then**
  - **1つの Monitor で受信できる**。プロセスもエージェントも増えない
  - **`actas` を使っていない状態で成立すること**(R13)。`actas` は受信を1つの識別子へ限定するため、使うと他方が無音になる

### AC6 — quory に常駐物が無い

- **Given** quory 側の Operator セッションを終了した状態
- **When** quory 上で待ち受けているプロセス・有効な systemd unit を確認する
- **Then**
  - agmsg 由来の常駐プロセスも unit も**存在しない**
  - この状態で Coordinator が送信しても、quory 側では**何も起動しない**(メッセージはサーバに残り、次にセッションが立ったときに読まれる)

### AC7 — 既存 Request Channel が無傷である

- **Given** 本案件の変更をすべて適用した状態
- **When** `git diff` と配備物を確認する
- **Then**
  - `roles/operator_request_channel/` / `roles/dev_investigate/` に差分が無い
  - forced command の語彙が1つも増えていない
  - 日次 `deployment_drift_check` が **exit 0** で、この案件に起因する finding を出さない

### AC8 — 証明書更新後も繋がる

- **Given** `homelab_cert_renew` が ansy の証明書を更新した後の状態
- **When** quory 側から到達する
- **Then** 正常応答が返り、**証明書の検証に失敗しない**。手動の再起動を要しない

## 9. 申し送り(この repo の外)

- **quory 側の規範**: Operator は承認を求める前に「何を、どのホストへ、どういう結果を意図して打つか」を提示すること。**承認プロンプト自体には何が起きるかが載らない**ため、提示が無ければ承認は形式になる。この repo には同型の実例がある(`git commit` の承認で、stage 内容とメッセージ案の提示を義務化した)。
- **決定記録を1本起こす。** `ansy-must-not-trigger-production-changes` の判定軸(本番の状態が変わるか)では本案件は通る。状態を変えないため。ただし同文書が D案を却下した理由は「ansy に能力を与えること」「安く見えることが、この案の危険な点である」だった。agmsg が ansy に与えるのは「**本番側 AI の文脈へ任意のテキストを差し込む能力**」であり、実行ではないが無でもない。**線がどこにあるかを説明できる形で残す。**
- `docs/ai/context/operations/operator-request-channel.md` §2 の「常駐 broker service を作っていない」は**書き換えない**。あれは Request Channel の性質を述べたものであり、今も正しい。正しい形は「**性質の異なる第2の経路が並走することを併記する**」である。
