# quory月次ヘルスチェックレポート

状態: 要件確定。Yoshinobuの「ProxmoxのDiskレポートと同様に、普段見ていないquoryのDisk・メモリを月次で確認したい」に基づく。2026-09-13、quory専用NotionページとNVMe health取得ツールの配備を今回の計画に含める方針を確認。現在地は`docs/ai/status.md`を参照。

## 1. 問題定義

quoryは`control_nodes`に属し、既存`monitoring_healthcheck.yml`の対象`monitoring_servers`には含まれない。容量とメモリに余裕があっても、定期的に読める記録がない。OPRES `req-20260913T103425+0900-66100285a5cf808c`のrestricted sessionで、ext4ルート約467.3GiB中使用約26.2GiB(6%)、メモリ約14.96GiB中available約13.66GiB、swap約4GiB中使用0Bを観測した。一方、同sessionではSMART/NVMe health取得ツールがなく、物理デバイスの健康状態は未確認。systemd bus拒否により既存timerの稼働状態も未確認であり、unit定義の存在を定期実行の証明にしない。

## 2. ゴール

quoryの容量・メモリ・swap・取得可能なディスク健康指標を月次で記録し、人が結論と前回差分を読めるようにする。取得不能は正常値と混同しない。短報はSlack、機械比較の正本はquory上のJSONとする。

## 3. 非ゴール

死活監視、SMART/NVMe self-test、ディスク修復・交換、trim、reboot、既存timerの変更、容量の自動整理は行わない。既存`monitoring_healthcheck`のmonnie対象をquoryへ拡張しない。ツール導入は月次の観測playbookへ混ぜず、配備工程に分ける。

## 4. ユーザーストーリー

管理者はSlack短報で対応要否を知り、人向け正式レポートで容量・メモリ・ディスク健康状態と前回差分、取得不能の理由を確認する。AIはJSONで同じ観測値と比較元を再検証できる。

## 5. 要件

### P0 / Must

- 収集対象はinventory上の`quory`だけとし、実行コンテキストが本当にquoryホストを見ていることを配備前に実測する。Operatorのrestricted sessionの値をAnsible実行時の値と同一と仮定しない。
- ルートとEFIのファイルシステム種別・総量・使用量・空き・使用率、メモリ総量・available、swap総量・使用量を収集する。`df`の使用率を別の分母から再計算しない。
- NVMe transportのディスクが観測された事実と、SMART/NVMe healthが取得できたかを別項目にする。指標を取得できない場合は`UNKNOWN`と理由を記録し、容量が正常でも「ディスク健全」と結論しない。実ホストの実行コンテキストでもツール不在なら、NVMe health取得ツールの導入を配備工程に含める。観測playbook自身はパッケージを導入しない。
- 観測時刻・対象host・収集成否・健康判定・未確認事項をJSONと人向けMarkdownへ保存する。健康判定とジョブ処理結果を分ける。保存先・保持・比較基準は既存のProxmox月次レポート契約を参照し、実装計画で確定する。
- Notionは既存「ストレージ月次点検」と別のquory専用ページを投稿先とし、人向け正式レポートの参照コピーを置く。親ページ・Integration権限・ページ作成または更新の経路は配備前にreadbackで確定する。ローカルJSONの保存はNotion成功に依存させない。
- 通常実行はSlackに短い日本語の結論と正式レポート参照先を通知する。`--check`と通知抑止では本番Slack・Notionへ送信しない。
- 収集・解析・ローカル保存・外部公開の失敗を全体`OK`に畳まず、理由と対象を残してジョブを非0で終了する。健康上の異常だけで処理が完了した場合は判定を可視化し、ジョブ終了コードとは別軸で扱う。
- 月次の自動実行は初回手動検証と実スケジュールreadbackが済むまで有効化しない。日付・時刻は既存ジョブとの重複を照合して決める。

### P1 / Should

- 同じ値の単なる再掲で終わらないよう、前回の成功観測との比較元ID・日時と差分を残す。初回・比較元破損・デバイス交換・カウンタ減少を明示する。
- Notion投稿失敗はローカルJSONを失わせず、同月の二重ページ作成を避ける。再送時に再収集せず保存済みreportを使えるようにする。
- 新しいplaybookを作る場合は`playbooks/README.md`とOperations Contextを更新する。既存の収集・通知・公開実装を利用できるか計画時に照合する。

## 6. 成功指標・受入条件

- AC1: Given quoryから全指標を取得可能、When 月次収集を実行、Then quory上の日時付きJSONと人向けMarkdownに同じreport ID・対象host・各値・比較元が残り、quory専用Notionページの参照コピーとSlack短報が同じreport IDで照合でき、Semaphoreジョブはrc=0となる。
- AC2: Given SMART/NVMe指標が取得不能、When 月次収集を実行、Then JSON・本文・短報は取得不能理由を`UNKNOWN`として示し、「ディスク健全」と表示せず、Semaphoreジョブはrc非0となる。
- AC3: Given 容量・メモリ・swapの異常または前回比悪化、When 比較、Then対象・現在値・比較元・差分・対応要否が人向け本文と短報に表示される。重大度順で重要項目が短報の件数制限から脱落せず、処理が完了していれば健康上の異常だけを理由にジョブを失敗させない(rc=0)。
- AC4: Given quory収集失敗または保存失敗、When 実行、Then成功した部分を可能な限り記録しつつ最終rc非0となり、全体`OK`を出さない。
- AC5: Given native `--check`または通知抑止、When 検証、Then本番Slack・Notionへの送信がなく、`--check`では保存・保持削除・host変更も起きない。
- AC6: Given 配備前後、When 実行先とscheduleを確認、Then実際の収集先がquoryであること、初回手動ジョブのrc・保存ファイル・通知とscheduleのactive/時刻をそれぞれreadbackで確認できる。

## 7. オープンクエスチョン

- quory専用Notionページの親、Integrationの実効権限、月次ページ更新方法は配備前に確定する。既存「ストレージ月次点検」ページへ混在させない。
- NVMe health取得用ツールは現在のOperator restricted sessionに無い。quory実ホストのAnsible実行コンテキストでの有無、対象NVMeの取得可否、必要なら導入するパッケージと実行権限は計画・配備前検証で確定する。
- 月次実行日・時刻、保持期間・比較項目の詳細は計画とレビューで確定する。

## 8. タイムライン考慮

初回は手動・通知抑止で実ホスト観測を確認し、ツールとNotion権限の配備、正式レポートの保存・通知を検証してからscheduleを有効化する。既存のProxmox月次点検やhealthcheckの実行時刻と重複しないことを配備時に確認する。
