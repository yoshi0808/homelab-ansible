# requirement: incident-capture の exit 2 を、ログから読み取れるようにする

日付: 2026-09-02
状態: 起案(Yoshinobu合意済み、2026-09-02)

## 1. 背景

2026-09-01、`quory` の `homelab-incident-capture.service` が2回 exit 2 で終了した。**Coordinatorはこれを既知Incidentの再発と誤認し**、Incidentを起票し、quory側OperatorへOPREQを投げ、原因調査を行った。

**結論は「正常動作」だった。** 経緯は `docs/ai/memory/incidents/2026-09-01_incident-capture-exit2-recurrence.md` にある。要約すると:

1. `pve1` を計画停止していた日だった(Yoshinobu、意図的)
2. `Time sync check` が `pve1` へ到達できず `warning` でSlack通知した(**ジョブは正常終了**。TIME-019〜022の設計どおり、個別ホストの到達失敗では非0終了しない)
3. 通知が出たので `common_slack/capture.yml` が spool へレコードを書いた(`ok`と空以外は全てnotable)
4. collector が「notableな通知があるのに相関する**失敗**ジョブが無い」と判定し、spool単独バンドルを作った(**設計どおり**)
5. そのバンドルの `play_host` が `quory` / `localhost` で、named investigate operation が存在しない(**ADR-003 constraint 4 の設計どおり**)
6. これらが `collection_errors` に入り、exit 2 になった

**どの段階にも誤動作は無い。** 実測でも、`pve1` に到達できた日(8/25〜8/28、8/31)には一度も発生していない。

## 2. 本当の欠陥 — 説明が読めない場所にしか無い

| 何が起きたかの説明 | 行き先 | 開発側から読めるか |
|---|---|---|
| `collection_errors` の詳細 | `_runs/<run_id>.json` | **読めない**(`incident-bundle-helper` のID正規表現が `semaphore-` 接頭辞を要求する。意図的な設計) |
| 同じ内容 | spool単独バンドル | **読めない**(バンドルIDが `semaphore-` で始まらないため同じ理由で指定できない) |
| **`Failed with result 'exit-code'` / `status=2/INVALIDARGUMENT`** | **journal → Loki** | **これだけが読める** |

**説明はすべて到達不能な場所へ行き、到達可能な場所には「失敗した」としか出ない。**

さらに `2/INVALIDARGUMENT` は systemd が exit 2 に付ける一般名であり、**引数の問題は何も起きていないのにそう読める文字列**が残る。

collector が journal へ書くのは現状 `EXIT_INTERNAL_ERROR`(内部例外)の1行だけで(`incident-capture-collector.py:868`)、**exit 2 の経路は何も出力しない。**

**この欠陥の実害は既に発生している** — Coordinatorが誤認し、Incident起票とOPREQ1件を消費した。1行のログがあれば発生しなかった。

## 3. 目的

**`collection_errors` を伴って終了した周期について、何があったかを journal から読めるようにする。**

## 4. 受入条件

- **AC1**: `collection_errors` が1件以上あって exit 2 で終わる周期で、collector が journal へ**要約を出力する**。Lokiに取り込まれ、`Failed with result 'exit-code'` の隣で読める
- **AC2**: 出力に、**各 `collection_errors` の `what` が含まれる**。何件あったかも分かる
- **AC3**: 出力量に上限を設ける。`collection_errors` が多数あるとき、**全件を出さずに切り詰め、切り詰めた事実を明示する**(黙って切らない)
- **AC4**: **`EXIT_OK` の周期では何も出力しない。** 5分ごとに走るため、正常時に journal を汚さない
- **AC5**: 既存の `EXIT_INTERNAL_ERROR` の出力を変えない
- **AC6**: **終了コードの意味を変えない。** exit 2 は従来どおり `collection_errors` があったことを示す
- **AC7**: 出力に IPアドレス・認証情報・秘密情報が混入しない。`collection_errors` の `what` / `why` は spool レコード由来の文字列(play名など)を含みうるため、**そのまま出す前に検討した結果を実装記録へ書く**
- **AC8**: `--check` 相当の副作用が無いこと(このスクリプトはAnsibleではないため、**dry-run経路が無いこと自体を実装記録に明示する**)

## 5. 制約

- **ADR-003 の設計を変更しない。** named operation を足さない、`collection_errors` への記録をやめない、通知条件を変えない、終了コードの体系を変えない
- **`_runs/` と バンドルへの記録は現状のまま維持する。** journal出力はそれらの代替ではなく、**読める場所への要約の追加**である
- 変更は `roles/incident_capture/files/incident-capture-collector.py` に閉じることを想定する。unit template の変更が要ると判断した場合は、理由を実装記録へ書く
- 5分ごとに実行されるため、**正常時のログ量を増やさない**

## 6. 検証の制約

- **ansyからquoryへAnsibleは到達できない。** 実装者は実機で検証できない
- 検証はローカルで、`collection_errors` を含む/含まない両方の入力に対する出力で行う
- 実機での確認は配備後にCoordinatorが行う(`journal-unit` またはLoki)

## 7. やらないと決めたこと(記録)

- **exit 0 化**: 検討したが**採らない**。緑にすると「notableなアラートが出た」事実まで見えなくなる。2026-09-01の事例では、その裏に `pve1` 到達不能という本物の観測があった
- **`_runs/` やspool単独バンドルを読む語彙の追加**: 今回は追加しない。journal に要約が出れば、通常の判断には足りる。詳細が要る場合はOPREQで取れる(2026-09-01に実証済み)
- **計画停止を系に通知する機構**: 年に数回・1日あたり1〜2周期の事象に対して機構を足すのは割に合わない
