### B3の是正の検証

採用されたのは提示案①(`<4>` prefix)で、②(`SyslogLevel=warning`)を退けた理由(scope外の `EXIT_INTERNAL_ERROR` まで昇格してしまう)は妥当である。経路を1段ずつ確認した。

1. `_journal_write()` が `sys.stderr.write(f"<4>{line}\n")` で**1行ごとに**先頭へ付ける。手元実行で、ヘッダ・各項目・省略通知のすべてが `<4>` で始まることを確認した(行の途中に付く経路は無い)。
2. unit(`incident-capture.service.j2`)は `StandardOutput=` / `StandardError=` を指定せず既定(journal)。journaldのストリームパーサは既定 `SyslogLevelPrefix=yes` で行頭の `<N>` を優先度として解釈する。
3. quory側 `rsyslog_forward_to_monnie`: journald drop-inが `ForwardToSyslog=yes` / `MaxLevelSyslog=debug`、`49-monnie-forward.conf` の `omfwd` にseverityフィルタが無い。severity 4 はそのまま monnie へ届く。
4. monnie側 `roles/alloy/templates/observability-sources.rsyslog.j2`: `$syslogseverity == 4` → `AlloyRemoteWarning`(行頭に `warning `)で `/var/log/ubuntu-nodes.log` へ。**`<4>` は「4だけ」を条件にするこの分岐へ正確に乗る**(`<3>` でも `<= 3` の分岐に乗るが、warning が妥当)。
5. alloyの `ubuntu_nodes` file source は `extract_normalized_level_at_start: true` / `strip_normalized_prefix: true` で `level="warning"` を付けてLokiへ。
6. `infra-syslog-all-nodes.json` の既定 `level=["warning","error"]` に入る。**`Failed with result 'exit-code'` と同じ画面・同じフィルタで並ぶ。**

副作用も確認した: `roles/grafana_provisioning/files/alerting/` にあるルールは `unifi-switch-port-errors.yaml` の1本だけで、ubuntu-nodesのログ件数やlevelを見るアラートは無い。**severityを上げたことによるSlack通知の増加は起きない。**

### AC2の再判定(B2のredactionによる情報損失)

Coordinatorの最大の懸念点。**AC2は substantively 満たしていると判断する。**

2026-09-01の実ケースを現物の関数へ与えた出力は次のとおり(手元実行、実機ではない):

```
<4>incident-capture-collector: exiting with 2 collection_errors this cycle (run: 0, bundles: 2; _runs/<run_id>.json only records the 'run' ones):
<4>  [1] (spool-<epoch>-<hex>) no correlated Semaphore job found for a spool record (play name omitted — untrusted, IC-016)
<4>  [2] (spool-<epoch>-<hex>) no named investigate operations available for a spool-correlated host (host name omitted — untrusted, IC-016)
```

- 誤認の中身は「原因不明の失敗 → 既知Incidentの再発だろう」だった。上の3行は**設計どおりの経路の名前を積極的に述べている** — spool単独バンドル(source labelの `spool-` 接頭辞で判る)/ 相関するSemaphore失敗ジョブが無い / そのホストにnamed investigate operationが無い。ADR-003 constraint 4 の設計そのものであり、既知Incidentの症状とは別物だと判別できる。**1行のログがあれば起票もOPREQも要らなかった**というrequirement §2の主張は満たされる。
- 失われたのは「どのホスト・どのplayか」だけで、requirement §7が「詳細が要る場合はOPREQで取れる」と既に決めている範囲に収まる。しかも source label がバンドルIDそのものなので、**OPREQで引く先を journal から一意に指定できる**(初版より辿りやすくなっている)。
- **ホスト名を条件付きで出す妥協案は成立しない。** `no named investigate operations` はそもそも `cfg["failure_snapshot_ops"]` にキーが無い場合の分岐であり、「設定済みホストなら出す」というallowlist方式では**この経路では常に何も出せない**。文字種チェックで通す案は、非信頼な自由記述をLLMが読む場所へ通す点でIC-016/IC-040の趣旨に反する。**現在の固定カテゴリ方式が、この制約下で取れる最良の形である。**

B2の前提(spool由来値が非信頼)は `docs/ai/policies/incident_capture_policy.md` IC-016 と一致しており、過剰な是正ではない。
