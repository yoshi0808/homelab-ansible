## 2. 出力先とseverityの選択(stdout/stderr、warning/info)

**出力先はstderr。severityは各行の先頭に `<4>`(syslog priority: warning)を付けて明示する。**

**出力先**: `incident-capture.service.j2` は `StandardOutput=` / `StandardError=` のいずれも指定していないため、systemdの既定(`StandardOutput=journal` / `StandardError=inherit`)に従う。既定ではstdout/stderrのどちらに書いてもjournalへ届き、journalはユニットのcgroupで行を紐付けるため、`ExecStart=flock -n -E75 ... python3 ...`(`flock`がforkして`python3`を子として実行する構成)でも両プロセスの出力は同じ `_SYSTEMD_UNIT=homelab-incident-capture.service` として記録される。既存の `EXIT_INTERNAL_ERROR` 経路(本ファイル末尾の `except Exception`)が既にstderrへ書いており、同じ経路に揃えることで単一のフィルタ(`journalctl -u ...`)で両方拾える。

**severity(B3是正)**: 初版は既定のsyslog level(info)のまま出力しており、Claude Reviewerが**この案件が防ごうとした状況をそのまま再現させる欠陥**として検出した — systemdは既定 `SyslogLevel=info` で行をjournalへ入れ、quory→monnie(`rsyslog_forward_to_monnie`)→Loki(`roles/alloy/templates/observability-sources.rsyslog.j2`)の転送経路では `$syslogseverity == 4` の行だけが `"warning"` ラベルへ分類される(severity 5/6は `"info"`)。一方、既に本番配備されている `roles/grafana_provisioning/files/dashboards/infra-syslog-all-nodes.json`(≒`roles/alloy/dashboards/infra_syslog_all_nodes.json`)の `level` 変数の既定値は `["warning","error"]` である。**つまり要約はseverity=infoでLokiへは入るが、`Failed with result 'exit-code'`(systemd自身のwarning)が見えている既定の画面には出ない** — AC1の「隣で読める」が実質不成立になっていた。

対応案は3つ検討し(実装記録の元版・両Reviewerが挙げたもの):

1. **各行の先頭へ `<4>` を付ける**(採用)。journald の `SyslogLevelPrefix=`(既定 `yes`)が、実行プロセスの出力行先頭の `<N>`(0〜7)をそのプロセスのkernel-printk風の優先度指定として解釈する仕組みで、`<4>` は syslog優先度4=warningを個々の行にだけ明示的に固定できる。monnie側rsyslogの条件(`$syslogseverity == 4` → `"warning"`)と正確に一致する。
2. unitへ `SyslogLevel=warning` を設定する(不採用)。この設定は「`<N>` prefixを持たない行」全体の既定severityを底上げする。**`<4>` prefixを持たない既存の `EXIT_INTERNAL_ERROR` の1行もこの底上げの対象になってしまい**、Coordinatorが明示した「既存の `EXIT_INTERNAL_ERROR` は今回touchしない、直すなら別案件」に反する副作用を生む。unit template変更にもなる。
3. 読む側の前提として「既定フィルタを外す/`journalctl -u` を使う」とrequirement/実装記録へ明記するだけ(不採用)。両Reviewerとも「問題を読み手へ転嫁するだけで誤認は消えない」として推奨しなかった。

①を採ったため、**unit templateの変更は不要**になった(requirement §5)。`EXIT_INTERNAL_ERROR` の1行は `<4>` を付けず、既定のまま(severity=info)据え置いている — 今回のscopeには含めていない。

## 3. AC7(`what`/`why` の混入検討)の結果 — B2是正後の最終形

**初版の判断は誤っていた。** 初版は「`what` はホスト名・play名・件数・固定文言の組み合わせで、このスクリプト自身がIP/認証情報を組み立てる経路を持たないため混入経路は無い」としていたが、これはcodex Reviewerが指摘したとおり**現物と一致していなかった**。実際には次の5箇所が、spoolレコード由来の非信頼値(IC-016: 書き手は `recovery-exec` またはAnsible controller identityで、いずれも人のレビューを経ていない)を `what` へそのまま連結していた。

| 箇所 | 連結される非信頼値 |
|---|---|
| `reject_spool_file()`(移動失敗時) | spoolファイルの絶対パス |
| `reject_spool_file()`(スキーマ不正時) | spoolファイルのbasename |
| `consume_spool_file()`(削除失敗時) | spoolファイルの絶対パス |
| `collect_host_snapshot()` が呼ばれない経路(host未登録) | `play_host`(spoolレコードのフィールド、値の検証なし) |

**是正**: journalへ出す `what` を、**このスクリプト自身が書いた固定プレフィックス(`WHAT_PREFIX_*`)だけで分類し、非信頼な連結部分は一切出さない**設計に直した(`_redact_untrusted_what()`、§1)。5箇所のいずれかのプレフィックスに一致すれば、固定の要約文(例: `"no named investigate operations available for a spool-correlated host (host name omitted — untrusted, IC-016)"`)へ置き換える。一致しない `what`(Semaphoreのtask id・件数・このファイル自身が書いた固定文言のみで構成されるもの)はそのまま表示する — これらは非信頼な自由記述を連結していないため、redactionの対象にしていない。

- 是正前(初版)は、codexの報告どおり `malformed spool record <試験文字列>...` がstderrへそのまま出ることを別途確認済み(codex側review本文に実測記録あり、本実装記録では再現していない — 是正後の状態で同じ入力を流し、漏れないことを確認する形で検証した)。
