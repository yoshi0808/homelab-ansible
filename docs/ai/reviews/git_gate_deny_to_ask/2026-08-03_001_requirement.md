# requirement: `git commit` / `git push` を deny から ask へ

作成日: 2026-08-03 / 起案: Coordinator / 依頼者: Yoshinobu

## 1. 問題定義

`git commit` / `git push` は3層で全面禁止されている。

| # | 場所 | 内容 |
|---|---|---|
| 1 | `~/.claude/settings.json` `permissions.deny` | `Bash(git commit*)` / `Bash(git push*)` |
| 2 | `<repo>/.claude/settings.json` `permissions.deny` | 同じ2件 |
| 3 | `<repo>/.claude/settings.json` `autoMode.hard_deny` | 絶対パス呼び出しを含む全repoでのcommit/push |

この設計(2026-07-26、`docs/ai/memory/decisions/approval-authority-for-real-host-operations.md`)は、実ホスト操作の承認権限をCoordinatorへ移す代わりに、**リポジトリへの確定操作だけは必ずYoshinobuの手を通す**ことで全体の均衡を取っていた。

前提が変わった。2026-08-03の「開発と運用の境界を能力の不在で作る」案件(commit `73dd527`)で、ansyは `pve1` / `pve2` / `authy` / `quory` / `sophos-fw` への認証情報を1つも持たなくなり、届くのは read 専用の forced command dispatch だけになった。**ansyが本番へ影響を及ぼす経路はGitだけになり、そのGitがYoshinobuの手打ちに固定されている。** 開発の完了と確定のあいだに、Yoshinobuが端末の前にいる必要があるという待ちが常に入る。

## 2. ゴール

- `git commit` / `git push` を、**Yoshinobuが都度確認プロンプトで承認する(ask)**形へ移す。
- 承認の主体と最終責任はYoshinobuのまま変えない。変えるのは「誰がコマンドを打つか」だけである。
- 設定(`.claude/settings.json`)と規範文書のあいだにドリフトを残さない。

## 3. 非ゴール

- **無確認(allow)にはしない。** 今回入れるのは ask であって自動化ではない。
- **subagentへは広げない。** Implementer / Reviewer / Tester / Auditor は従来どおり commit / push を行わない(2026-08-03 Yoshinobu選択)。
- quoryの作業ツリー同期(`git pull --ff-only`)の効率化は本案件に含めない。前提(ansy→quoryの到達手段が消えた)が変わったため再検討の対象だが、要件から起こす別案件とする。
- `git add` / `git diff` の扱いは変えない(従来から許可)。

## 4. ユーザーストーリー

Yoshinobuとして、移動中や端末の前にいない時間帯でも、Coordinatorが整えたcommitを**内容を見たうえで**確定させたい。ただし、内容を見ずに y を押す形にはしたくない。

## 5. 要件

| 優先度 | 要件 |
|---|---|
| P0 | 上表の3層すべてを ask 側へ移す。1つでも `deny` が残れば従来どおりブロックされ、`hard_deny` が残れば ask プロンプトすら出ない(スキーマ上 `soft_deny` は "destructive/irreversible actions that **user intent can clear**"、`hard_deny` は "security boundaries that user intent does **NOT** clear") |
| P0 | 絶対パス形(`/usr/bin/git commit`)でも同じく確認を経ること。旧 `deny` はパターン一致で迂回可能だった(2026-07-25実測)ため、この層は `autoMode` の自然言語ルールが担う |
| P0 | 規範文書(`docs/ai/core.md`、`docs/ai/roles/coordinator.md`、`docs/ai/policies/incident_capture_policy.md`)を設定に追随させる |
| P0 | **確認プロンプトを出す前に、stageした内容の分類とcommitメッセージ案を提示する。** ask の実効性はここに依存する — プロンプト単体には diff が載らないため、提示が無ければ承認は形式になる |
| P1 | subagentが commit / push を行わないことを `docs/ai/core.md` の subagent 節で明示する(設定ではRoleを区別できないため、この層は文書でしか引けない) |
| P2 | 過去の決定記録(`docs/ai/memory/decisions/`、`docs/ai/adr/`)は書き換えず、後継を指す1行だけ足す |

## 6. 成功指標

- Coordinatorセッションから `git commit` を発行すると確認プロンプトが出る(ブロックされない、無確認で通らない、のいずれでもない)。
- `docs/ai/core.md` / `docs/ai/roles/coordinator.md` を読んだだけで、誰が何を承認し誰が実行するかが一意に読める。

## 7. 受入条件

- **AC-1**: Given 変更後の設定、When Coordinatorセッションで `git commit` を含むコマンドを発行する、Then ブロックされず確認プロンプトが表示される。拒否を選べばコマンドは実行されない。
- **AC-2**: Given 変更後の設定、When `/usr/bin/git commit` の形で発行する、Then AC-1と同じく確認プロンプトが表示される(パターン一致の迂回が成立しない)。
- **AC-3**: Given 変更後の規範文書、When `grep -rn "git commit\|git push" docs/ --include="*.md"`(reviews / adr / memory を除く)、Then 「AIは行わない」と読める記述が残っていない。
- **AC-4**: Given 変更後の `.claude/settings.json`、When `jq . ` で読む、Then 妥当なJSONであり `permissions.deny` から2件が消え `permissions.ask` に入っており、`autoMode.hard_deny` から該当節が消え `soft_deny` に入っている。

AC-1 / AC-2 は本セッションのCoordinator自身が承認プロンプトの受け手であり、Tester subagentへは渡せない(プロンプトはセッションの外へ出せない)。**この2件はYoshinobuの目の前で1回実施し、結果を記録する。**

## 8. 引き受けたリスク

| ID | リスク | 影響 | 受容理由 |
|---|---|---|---|
| R-1 | 承認疲れ。y を押すことが習慣化し、内容を見ないまま確定する | 意図しない変更がGitへ入り、quoryのpullを経て本番へ届く | Yoshinobuが明示的に受容(2026-08-03「最終責任はaskにyを押すユーザーにある」)。緩和として P0 の「提示してからプロンプトを出す」を要件に含める |
| R-2 | `73dd527` で確定した開発/運用の非対称な牽制が弱まる。Claude Code側の牽制は「打てないこと」から「y を押す前に見ること」へ変わる | 牽制の強度が構造から手続きへ落ちる | 同上。ただし `.git/hooks/pre-commit`(`scripts/git-pre-commit-check.sh`)と `pre-push` は実行者を問わず走るため、IPアドレス混入等の機械的検査は構造の側に残る |
| R-3 | push先は公開GitHub(`git@github.com:yoshi0808/homelab-ansible.git`)であり、y を押した時点で外部公開される。取り消せない | 秘密情報の公開 | R-2 と同じくフック側に残る検査で緩和。push前の内容提示を要件に含める |

## 9. オープンクエスチョン

なし(subagentの扱いとgit pullの扱いは2026-08-03に確定済み)。
