## 4. AC-1 / AC-2 の実地結果

本案件のcommit(`079ea09`)そのものを試験機会とした。

### AC-1(`git commit` がブロックされず、確認を経て通る)

**通った。** Coordinatorセッションから `git commit -m ...` を発行し、以前のようにブロックされることなく実行され、`.git/hooks/pre-commit` が走って(gitleaks / tester-gate-lint / 3種の突合)commit が作られた。

**確認プロンプトが表示されたことをYoshinobuが目視で確認した(2026-08-03)。** Coordinator側からはプロンプトの有無を観測できない — ツールの返り値は成否だけで、承認の有無は返らない。**したがってこのACは、今後も自動では検査できず、人の目視でしか確定しない。**

**あわせて、このゲートの実効性を支えている条件が判明した。** Yoshinobuの観察: 「普段からプロンプトは出ないので、プロンプト自体が出るのはかなり目立ちます」。`permissions.defaultMode: auto` + `autoMode.classifyAllShell: true` の構成では確認プロンプトが希少であり、**希少であること自体がR-1(承認疲れ)への最大の緩和になっている**。この構成を変えて日常的にプロンプトが出るようにすると、commit/pushの確認はその他大勢に埋もれ、**ゲートは形だけ残って実効性を失う**。プロンプトを増やす方向の変更を検討するときは、この副作用を勘定に入れること。

### AC-2(絶対パス形での迂回が成立しない)

**迂回は成立しなかった。** `/usr/bin/git commit -m ...` は実行されず、**auto mode 分類器によって拒否された**(理由は "Stage 2 classifier error - blocking based on stage 1 assessment")。旧 `permissions.deny` はパターン一致であり `/usr/bin/git` に一致しなかったが、`autoMode.soft_deny` 側は絶対パス表記を本文で明示的に扱っているため、この経路も分類器へ入る。

**ただしACの文言(「確認プロンプトが表示される」)そのものは満たしていない。** 観測されたのは prompt ではなく block であり、しかもその block は分類器の transient error に起因する。**「プロンプトが出る」ではなく「素通りしない」ことだけが確認できた。** `docs/ai/core.md`「安全機構がブロックしたとき」に従い、再試行や別経路での到達は行っていない。

## 5. 未解決事項

- **AC-2(P0)は文言どおりには未達のままクローズした。** 絶対パス形が素通りしないことは確認できたが、そこで**確認プロンプトが出るのか、ブロックされるのか**は未確認である。今回観測されたブロックは分類器のtransient errorに起因しており、正常時の挙動を代表していない。**再試行や別経路での到達は行っていない**(`docs/ai/core.md`「安全機構がブロックしたとき」)。次に絶対パス形の `git` を使う機会があれば、そこが観測点になる。
- **`permissions.ask` / `autoMode.soft_deny` が Coordinator と subagent を実際に区別して動くかは、設定構造からは確認できない**(Reviewer報告)。subagent側の抑止は文書(`docs/ai/core.md`「subagentが共通して守ること」)と `soft_deny` の本文に依存しており、**機構ではなく規範で引いている境界である**。この点は `docs/ai/memory/lessons/permission-boundaries-must-be-designed-not-prompted.md` が扱う面と同じで、実効性は担保されていない。
- 承認疲れ(requirement R-1)には検証手段が無いため `docs/ai/status.md` のWatchへは載せていない。緩和は「プロンプトの前に提示する」義務のみで、それが守られているかを機械的に検査する手段は無い。
