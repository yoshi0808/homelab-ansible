## 2. Policyに固有の事情

**Policyの本文は許可・禁止・停止条件そのものである。** 分類文書や索引と違い、1文落とすと運用の可否が変わりうる。したがって前2案件より判定を厳しくする。

判断軸そのものは同じ — **「読み手が前提となるベースラインを特定できるか」**。特定できない履歴は誤った前提で読まれる分だけ無いより悪い。

## 3. ゴール

Policy本文を、**いま従うべき許可・禁止・停止条件だけ**にする。履歴は「変更履歴」節と `git log` が持つ。

## 4. 非ゴール

- **許可・禁止・停止条件を変えない。** 落とすのは経緯・根拠であって規則ではない。**規則の意味が変わる編集はYoshinobuの領域**であり、必要と判断したら実施せず報告する。
- **Policy ID(`SB-nnn` / `LOG-nnn` / `TS-nnn` 等)を落とさない。** 日付ではなく識別子であり、他文書から参照される。
- 「変更履歴」節を書き換えない(**追記はする。R3参照**)。
- `docs/ai/reviews/` や `docs/ai/memory/` の既存記録を書き換えない。
- `skills/` へ広げない。次の案件とする。

## 5. 落とすもの / 残すもの

前2案件の表に、Policy固有の3行を足したものを判定基準とする。

| 落とす | 残す |
|---|---|
| 規則に埋め込まれた改訂注記(「(2026-08-01改訂、SB-003/SB-027)」) | **規則本文と、括弧内のPolicy ID** |
| 実測の日付注記(「(2026-07-30実測)」「2026-07-26の実測で」) | その実測から確定した**事実と規則** |
| 改訂の経緯(「2026-07-30の改訂で〜という限定を外した」「旧内容は〜だった」) | 改訂**後**の規則 |
| **判断の引用**(「Yoshinobu判断(2026-07-30): 「…」」) | その判断が**既に本文の規則として具現化していること**を確認したうえで、引用は落とす |
| **特定の過去時点を名指しする条項**(「2026-07-16のPhase 1完了は…」「2026-07-17時点の…状態は…」) | それらが instantiate している**一般規則**(「時点履歴を現行契約に昇格させない」)を1つ残す |
| 根拠への参照(`docs/ai/memory/lessons/<file>` を「なぜそうするかはここ」として引くもの) | **行き先・保存先・正本**の指定(「過去の実機PASSは〜に保持する」「形式は〜が正本」) |

## 7. 受入条件

| AC | Given / When / Then |
|---|---|
| AC1 | **Given** 改訂後の対象9本 **When** 「変更履歴」節を除いた本文で日付を数える **Then** 0件。**これは「経緯としての日付」の代理指標である** — 実在ファイル名やID等、経緯でない日付に当たった場合は書き換えず報告する(前案件で代理指標が実装を歪めた実例がある) |
| AC2 | **Given** 改訂前後 **When** 逐行で突合する **Then** **落ちているのは経緯・根拠・判断の引用だけで、許可・禁止・停止条件が1つも変わっていない。** Policy IDも失われていない |
| AC3 | **Given** 改訂後 **When** 「変更履歴」節を読む **Then** 本文から移した退番の記録がすべて含まれている |
| AC4 | **Given** 改訂後 **When** §5「残す」の項目を確認する **Then** 行き先・保存先・正本の指定がすべて残っている |
| AC5 | **Given** リポジトリ全体 **When** `scripts/check-doc-consistency.py` と `scripts/git-pre-commit-check.sh` を実行する **Then** OK。宙ぶらりんの参照が無い |

## 8. リスク

| # | リスク | 対応 |
|---|---|---|
| 1 | **経緯と一緒に許可・禁止・停止条件を落とす。** Policyでは即座に運用の可否が変わる | AC2で逐行突合。**独立レビューを必須とする**。規則の意味が変わる編集は実施せず報告(非ゴール) |

## 9. 工程

先行2案件と同じく**Testerを立てない**。実行される経路が無く、主要リスク(規則を落とす)に効くのは逐行突合による独立レビューである。

**Batch 1(重い2本)→ Batch 2(軽い7本)の順に別々のImplementerで行い、Reviewerは全体の差分を1回で見る。** Batch 1で受け皿・退番・判断の引用の扱いが確定し、Batch 2はそれを適用するだけになる。
