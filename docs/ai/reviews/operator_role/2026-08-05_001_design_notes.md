# Operator役 — 設計の議論メモ

2026-08-04〜05 / Yoshinobu と Coordinator の対話。**着手時期は未定。** requirement ではなく、**繰り返し同じ議論を最初からやらないための集約先**である。決まったことと、まだ決まっていないことを分けて書く。

`docs/ai/status.md` の Next はこのファイルを指すだけにする(値を二重に持たない)。

## なぜこの役を考えているか

現行のRole(Coordinator / Implementer / Reviewer / Tester / Auditor)は**開発工程しか持たず、運用工程が空白**である。実害が出ている形は2つ。

- Semaphore の schedule / environment が repo の外にしかなく、AIから見えない。`recovery_monitoring_check.yml` の Watch 行が「**未登録と正常が区別できない**」という形でこれを踏んでいる。2026-08-04 に template について閉じたのと根は同じ穴である(Yoshinobu指摘)
- 「**リスクは無いが人の手が要る**」操作が残る。2026-08-04 の実例は API キーの作成とブートストラップtemplateの手作りで、判断は明らか(リスクなし)なのに Yoshinobu が何度も操作し、**打ち間違いも起きる**。承認ゲートが守っているのは取り返しのつかない本番影響であって、これらはそこに当たらない

## Yoshinobu が示した方針(2026-08-04)

1. 運用の立場で、秘密になるファイルを渡してよいか評価し、進言する。判断は Yoshinobu
2. リスクはあるが実行しないと目標が達成できないものについて確認を取る。**別の方法があっても Operator は自分でコマンドを組み立てない**
3. playbook はもちろん、コマンド1つでも Operator の任意で実行しない。実行するときは**開発側が組み立てたもの**を使い、承認が要る
4. ジョブのスケジューリングは、承認のもとで Operator が設定できる

**これは現場で実際に行われている運用である**(Yoshinobu)。このリポジトリで役立つかは別途検討する、という位置づけで出された。

## 決まったこと

### D1. 権限は3分類

| 区分 | 承認 | 理由 |
|---|---|---|
| **照会**(状態を変えない) | **不要** | `docs/ai/core.md`「状態を変えない確認は、どのホストに対しても確認不要」 |
| **立ち上げの書き込み**(テンプレート定義、設定の雛形など、**押されるまで何も起きないもの**) | **要** | 頻度は「新しい仕組み1つにつき数回」まで |
| **schedule** | **要**(上より重い) | 以後の**すべての実行から人が外れる**ため。単発の実行より影響が大きい |

**常時の運用書き込みは要らない。** Operator に要るのは「運用する権限」ではなく「**立ち上げる権限**」である。

**「押されるまで何も起きないなら承認不要」という例外は作らない**(2026-08-05に不採用)。Yoshinobu の「私が許可しない限り本番では何も変更が発生しない」を保ち、**例外が無いぶん境界の判定を誰も間違えない**ことを優先する。inert かどうかは**承認を省く根拠ではなく、Operator が説明に添える内容**になる(承認を軽くする側で効かせる)。

### D2. 書き込みの経路を新設しない

**承認つきの書き込み経路はすでに存在する — Yoshinobu が Semaphore のボタンを押すことである。**

Operator の仕事は実行ではなく、**押すべきテンプレートと survey 値を用意し、リスクを説明すること**になる。新しい権限も新しい経路も要らない。

**却下した案**: ansy 側に Operator を置き、書き込み経路を dispatch へ新設する形。**開発側のホストから本番へ書ける経路ができ、Phase 4 で捨てたものが戻る。**「形を変えて昔に戻るだけ」(Yoshinobu、2026-08-05)。

**quory 上にエージェントを置く案は保留**。本番を直接見られる利点はあるが、**シェルを持つエージェントはその時点でホスト全体を持つ**ため、権限は方針ではなく identity で縛る必要がある(`recovery-exec` / `dev-investigate` と同型にはできる)。判断は下記 OQ1 に依存する。

### D3. 照会は一般 read でなく forced command の枚挙で拡充する

一般的な read を渡すより、**何が読まれたかがログに残る**。代わりに払うコストは往復(語彙を1つ足すたびに repo 変更 + quory への配備)であり、**語彙は溜めてから一括で足す** — 1件ずつ足すと配備自体が人手を何度も要求する。

**read は無害ではない。** `/etc/homelab-recovery/` の API token も鍵も `semaphore.db` も、一般 read を渡せば読める。現在の dispatch がそれらを読めないのは枚挙してあるからである。

### D4. 依頼は「コマンド」でなく「目的と受入条件」で出す

一次評価は、**評価する側が代案を出せる立場でないと成立しない**。コマンドまで渡すと Operator は○×を押すだけの中継になる。目的が分かっていれば「その目的なら、そこまで触る必要はない」と**要求の側を小さくできる** — これは代案の提示ではなく拒否の一形態なので、方針3(自分で組み立てない)に抵触しない。

### D5. 中継にならない条件は2つ

- **本番を自分で観測していること**(開発側の説明でなく現物に基づいて評価する)
- **目的を知っていること**(手段の妥当性まで問える)

どちらも無いと、できるのは危険度のラベル貼りだけになる。

**「開発の説明の受け売りで事故る」は現場でも実際に起きている**(Yoshinobu)。一方で**自分でコマンドを組んで実行するのは最も悪い**とされる。この2つの間に立つのがこの役である。

### D6. 承認を支援する仕組みは3層

**「AIが説明する」は支援ではない** — 説明の出所が、間違える当人と同じであるため。git の承認が機能しているのは、gitleaks / IPv4検査 / doc-consistency が**AIの理解と無関係に走って止める**からである。

| 層 | 中身 |
|---|---|
| **① 押す前** | **実行系自身の dry-run** が「何が変わるか」を出す。AIの要約ではなく、そのコードの出力そのもの。**実例がある** — 2026-08-04 のテンプレート初回適用で、`--check` が「新規9・更新34・削除しない1」を先に出し、Yoshinobu がそれを読んでから適用を押した(task #561 → #563) |
| **② 押した後** | **別の仕組みが独立に確かめる。** 日次ドリフト検査がこれにあたる |
| **③ 押せる範囲** | **①も②も無い操作は、そもそも承認を求めない。** これが無いと、③の形は「AIの失敗を Yoshinobu が単独で引き受けるだけ」になる |

**限界も併記する。** dry-run は「AIの理解」からは独立だが、「**コードの正しさ」からは独立ではない** — playbook が間違っていれば、dry-run は間違ったことを自信満々に出す。そこから独立なのは②だけであり、**①だけでは支援にならない。**

### D7. 承認を求めるときに添える4項目

1. **何が変わるか**(dry-run の出力そのもの。要約ではなく)
2. 失敗したら何が起きるか
3. 戻し方
4. **事後に何を見れば結果が分かるか**

**4つが埋まらないなら、承認を求めさせない。** 埋められないのは分析ができていない証拠である。

> 「経営判断が必要と言われるケースは、大体は説明が不足していて物事の分析ができていない。面倒だから経営判断として丸投げされる」(Yoshinobu、2026-08-05)

**依頼の型が、分析を強制する装置になる。** そして「**開発は実現したいことが主眼、運用は引き起こされることを主眼に点検する**」という非対称は、この4項目のうち **2 と 4 が運用側の視点**であることに対応する。開発側は放っておくと 1 と 3 しか書かない。**この役の存在意義は、2 と 4 を必ず埋めさせることである。**

### D8. 評価は「めったに大声を出さない」ことで価値が保たれる

人間の risk 部門がコマンド粒度で評価しないのはコストの制約であり、原理ではない。**その制約だけが外れるのがAIに担わせる場合である。** ただし安くなったぶん、**全件に同じ体裁の所見が付くと定型文になって誰も読まなくなる。** `docs/ai/core.md`「このゲートは確認プロンプトが希少であることで機能している」と同じ壊れ方。**全件に所見が付く設計になったら、その時点で中継に戻っている。**
