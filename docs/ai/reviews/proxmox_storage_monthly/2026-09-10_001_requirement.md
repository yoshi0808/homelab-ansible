# Proxmoxストレージ月次点検

状態: 要件整理済み、詳細設計・実装前。Yoshinobuとの2026-09-09〜10の対話を反映。

## 1. 問題定義

既存のhardware checkはpool情報とscan文字列を保存するが、NVMe healthの前回比較と人が読める月次正式レポートがない。

調査証拠:
- OPRES `req-20260909T191220+0900-d971d04dd9edef38`: 両nodeのrpoolはONLINE、最終scrubは2026-08-09、修復0B・エラー0。pve1はNVMe mirror、pve2は単一NVMe。全3台でNVMe health取得可。
- OPRES `req-20260909T194408+0900-a04510554c9ae89a`: pve2のerror-log累積239、保持された非空ログ1件。media_errorsとcritical_warningは0。発生時期・原因は未確定。
- **Operatorのcron探索結果はユーザーの直接確認で訂正された。** pve1/pve2の `/etc/cron.d/zfsutils-linux` に、第2日曜00:24に `/usr/lib/zfs-linux/scrub` を呼ぶ定義が存在する。systemd timerが無効でも定期scrub経路が無いとは言えない。定義の存在と毎回の完走は別に観測する。

## 2. ゴール

既存scrubの実行結果とNVMe healthを月次で確認し、quoryのファイルで前回比較でき、人とAIはNotionの正式レポートから内容を読めること。Slackは短報と参照リンクを担う。

## 3. 非ゴール

scrub/trimの開始・停止やtimer/cron変更、self-test、修復、デバイス交換、エラーカウンタのクリアは行わない。DB、Notionデータベース、AIによる毎回の判定は導入しない。239の原因を推測で確定しない。

## 4. ユーザーストーリー

管理者はSlackで対応要否を知り、Notionで理由と前月差分を読む。定期ジョブは過去のJSONから同一デバイスを比較し、取得不能や比較不能を正常と混同しない。

## 5. 要件

### P0 / Must

- quoryのSemaphoreから毎月15日朝に起動する。時刻はバッチ処理工程管理表と照合して確定する。第2日曜指定の可否には依存しない。
- ZFS: pool/vdev状態、READ/WRITE/CKSUM、scrub完了日時・修復量・エラー数、実行中/未実行/古い結果を保存する。
- NVMe: 安定したデバイス識別、critical_warning、温度、予備領域、消耗率、media_errors、error-log累積数を保存する。実vdevから物理デバイスを対応付ける。
- 同一デバイスの直近取得成功値と比較する。初回、交換、識別不能、カウンタ減少、過去ファイル破損を明示する。同月再実行でも自己比較によって変化を消さない。差分の比較元ID/日時を残す。
- 239など初回のerror-log非ゼロだけで故障判定しない。以後の増加は要確認とし、critical_warning/media_errorsと別に扱う。
- quoryに日時付きJSONと人向け本文を保存する。ローカル保存が正式な観測記録であり、Notion投稿成功を保存の前提にしない。
- Notionの「ストレージ月次点検」配下に1か月1ページ、両nodeをまとめる。全体結果、host/device別値、比較元と差分、対応事項、未確認事項、レポートID/観測日時を含める。
- 同月再実行で同じページを更新する。投稿結果不明のtimeout後に無条件でページ新規作成を繰り返さない。ローカルJSONを使った再送は再収集と分離できること。
- Integration tokenをquoryで保管し、git、Notion本文、Slack、実行ログに出さない。投稿先への権限設定とトークン配置は配備前提とする。
- 片node/全nodeの取得失敗も対象を明記したレポートに残す。ホストの健康状態と収集/保存/投稿処理の成功を別フィールドにする。
- 通常実行ではSlack短報を送る。検証時の通知抑止とnative check modeでNotion書込を抑止する。

### P1 / Should

- JSON/本文履歴は13か月保持する。削除対象を当該レポートの確定済み履歴に限定し、比較基準と未送信レポートは保全する。Notion側の過去月は自動削除しない。
- NotionページIDとレポートIDの対応、投稿状態、再送に必要な情報はファイルで保持する。並行実行で月次ページや比較基準が競合しない。
- 新playbookを `playbooks/README.md` に登録し、配備・手動再送・確認の手順を記録する。

## 6. 成功指標・受入条件

- AC1: Given 両node正常、When 月次実行、Then JSON/本文/Notion月次ページ/Slack短報が対応するIDで生成され、ジョブrc=0。
- AC2: Given 239から239または240、When 比較、Then 差分0または+1と比較元がJSONと正式レポートに一致する。初回239はbaselineと記録する。
- AC3: Given デバイス交換・カウンタ減少・比較元破損、When 比較、Then 比較不可/リセット疑いを表示し、改善や差分0にしない。
- AC4: Given scrub実行中・完了履歴なし・期限超過・ZFS/NVMe異常、When 点検、Then 個別の理由をJSON/Notion/Slackへ載せる。収集/保存/投稿が完了したhealth異常はrc=0、健康判定はWARNING/CRITICALとして可視化する。
- AC5: Given 片nodeまたは全node到達不能/収集不正、When 実行、Then 未確認hostを含むレポートと短報を可能な範囲で保存・送信し、最終rc非0。片nodeだけのOKを全体OKにしない。
- AC6: Given Notion認証失敗/429/timeout、When 投稿、Then ローカル記録が残り、投稿未完了を短報に表示し、最終rc非0。再送後に同月ページが重複しない。応答不明は自動重複作成より明示停止を優先する。
- AC7: Given 同月再実行、When 収集/投稿、Then 過去観測は保存され、月次ページは1件、同じ月の差分が自己比較で消えない。
- AC8: Given native check/通知抑止、When 検証、Then 本番Notion/Slackへ送信しない。scrub/self-testや既存cron変更は全経路で起きない。
- AC9: Given 保存失敗、When 実行、Then 成功扱いせずrc非0。tokenはfixtureによる失敗経路検証でも出力されない。
- AC10: Given 配備後、When 手動初回実行、Then quory上の保存内容、Notionページ、Slackリンク、Semaphore schedule readbackを照合できる。

## 7. オープンクエスチョン

人の機能判断待ちはない。工程管理表との時刻照合、Integration準備は配備前に必要。scrub鮮度・NVMe閾値、API版、投稿更新・timeout回復契約は詳細設計で確定する。API仕様は公式資料を根拠にする。
