# Closeout: dispatchへread-only語彙を2つ追加する

日付: 2026-09-14

## 到達点

`pkg-list [pattern]`(class Q / P / G)と `semaphore-query schedule-list <n>`(class Q + helper)を追加した。どちらも状態を変えない。工程は requirement(`_001`)→ 実装(`_002`)→ 差分レビュー(`_003`)→ テスト(`_004`)→ 差し戻し1回 → 再実測。

- 差分Reviewer: Major 1件(blocking)+ Minor 3件 → **全て是正済み**。
- Tester: AC1〜AC6 PASS。**差し戻しで class P の実行経路が変わったため、そこは旧実装のPASSを引き継がず再実測した。**

## 判断したこと

**総数の母集団を分けたまま、対応を明示する形を採った**(Major 1の是正)。語彙カタログのD番号系列(27)と、dispatchが実際に受け付ける数(31 = D系列27 + Operator Request Channelの4)は数える対象が違う。カタログ全体の番号を振り直す変更を本案件へ抱き合わせない判断であり、§9.1が同種のズレへ注記を付けて据え置いた先例に倣った。**「総数」という同じ語が2つの母集団を指したまま残らないこと**を満たすべき結果として指示した。

**空白を含むpatternがpattern検証ではなくarity経路で拒否される件は直さない**(Testerの残存リスク指摘)。拒否という結果(非ゼロ終了)は同じである。**エラーメッセージは異なる**(無効な記号は`invalid pattern`、空白入りは`invalid parameter count`。`_004` AC3の観測)ため、区別が付かないから直さないのではなく、**どちらも拒否で終わり、利用者が次に取る行動が変わらないから直さない。**

## 分かったこと(この案件の外でも効く)

**Semaphoreのschedule一覧APIは次回実行時刻を返さない。** `schedule-list` で読めるのは `active` と `cron_format` までである。**scheduleを書いた結果を読み返す**という当初の動機のうち、「入ったか・有効か・cronは何か」は満たされ、「次はいつ走るか」は満たされない。これはこの語彙の限界であり、欠陥ではない — 返らないものを合成しないことをrequirementで先に決めていた。
