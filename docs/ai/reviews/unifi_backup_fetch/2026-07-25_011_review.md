## techlead依頼5項目の確認結果

### 1. run_once + delegate_to: localhost が pve1 unreachable でも後続task(fail判定・add_host)を実行できるか

**結論: 問題なし。**

`ansible/plugins/strategy/__init__.py:599-602`を確認した:

```python
elif task_result.is_unreachable():
    ignore_unreachable = original_task.ignore_unreachable
    if not ignore_unreachable:
        self._tqm._unreachable_hosts[original_host.name] = True
```

`ignore_unreachable: true`が付与されたタスクでhostが実際にunreachableになった場合、そのhostは`_tqm._unreachable_hosts`へ**追加されない**。この集合が同ファイル416行目・1096行目で後続taskの対象host絞り込みに使われるため、`_unreachable_hosts`に入らない = 以後のPlay 1タスクからも除外されない、という意味になる。

新実装は`ignore_unreachable: true`を「Probe SSH reachability」タスク**1つだけ**に付与している。このタスクでpve1が実際にunreachableになっても、上記ロジックによりpve1はPlay 1の残りのタスク(`set_fact`/`fail`/`add_host`)から除外されない。かつこれら3タスクは`set_fact`/`fail`/`add_host`という「controller側で完結し、対象hostへの生きた接続を必要としないaction」であるため、pve1がSSH的に到達不能でも実行できる。

`unifi_backup_fetch_ping.unreachable`が正しく`true`として登録されることも`ansible/executor/task_executor.py:125-128`で確認した(`res['unreachable'] = True`がresult dictへ明示的にマージされるため、`ignore_unreachable`を付けても`.unreachable`キー自体は握り潰されない)。

この設計は`roles/time_sync_check/tasks/check_chrony.yml`の実運用パターン(probeタスクだけに`ignore_unreachable: true`、次の`set_fact`には付けない)と構造的に同一であり、実装報告の説明は正確である。

### 2. 両ホスト到達可能時にpve1のみが選ばれ、pve2への二重実行が起きないか

**結論: 問題なし。**

`add_host`タスクは`run_once: true` + `delegate_to: localhost`。`name:`の値は`hostvars['pve1']`/`hostvars['pve2']`を明示的にインデックス参照するJinja2式であり、run_once実行時に「代表として選ばれるhost」がpve1かpve2かに関わらず同じ値へ評価される(暗黙の`inventory_hostname`やcurrent-host varに依存していない)。したがって`unifi_backup_fetch_target`グループには常に1 host、かつpve1優先ロジックどおりに登録される。

`--list-tasks`実行結果でもPlay 2は`hosts: unifi_backup_fetch_target`(単一動的group)のみを対象にしており、Play 2側の実処理(バックアップ取得・保存・世代削除)が複数hostへ分岐する余地はない。

### 3. 両方到達不能時のfailメッセージが機能する経路か(unreachable状態でのhostvars参照)

**結論: 問題なし。** 項目1と同じ機構により、pve1・pve2の両方が実際にunreachableでも両hostとも`_unreachable_hosts`に入らないため、`fail`タスクの`when:`条件が参照する`hostvars['pve1'].unifi_backup_fetch_host_reachable` / `hostvars['pve2'].unifi_backup_fetch_host_reachable`は両方とも(直前の`set_fact`により)`false`として定義済みの状態で評価できる。`fail`タスクも`run_once: true`のためメッセージは1回だけ出力される。

### 4. roles/unifi_backup_fetch配下のpve1/pve2依存が本当にコメントのみか

**結論: 実装報告のgrep結果と一致。** 独立に`grep -rn "pve1\|pve2\|inventory_hostname" roles/unifi_backup_fetch/`を実行し、ヒットは2件のみで確認した:

- `roles/unifi_backup_fetch/defaults/main.yml:14`(保存先パスの説明コメント)
- `roles/unifi_backup_fetch/tasks/main.yml:11`(root実行理由の説明コメント)

いずれもコードとしてのhost分岐・ハードコードではない。Phase 3の鮮度ガードも`date +%s%3N`を対象host上で実行しており(`roles/unifi_backup_fetch/tasks/main.yml:170-173`)、host非依存のまま動作する。roleへの変更不要という判断は妥当。

### 5. playbook冒頭コメントの正確性・ADRとの整合

**結論: 正確。** 更新後のコメント(pve1優先・pve2フェイルオーバー・preflight・二重実行防止・ADR参照)はADR-001のOption (a)採用内容と一致しており、Play 1/Play 2の実際の構造とも矛盾しない。

## What Looks Good

- `ignore_unreachable`をprobeタスク1つに絞る設計はansible-core本体の実装(`_unreachable_hosts`管理)と整合しており、過不足なく機能する。
- `run_once` + `delegate_to: localhost`のadd_host/failで、`inventory_hostname`等の暗黙per-host変数に依存せず明示的に`hostvars[...]`をインデックスしている点は、run_once特有の「どのhostが代表に選ばれるか不定」という典型的な落とし穴を回避した堅実な書き方。
- Play 2のSlack通知(`Executed on: {{ ansible_facts['hostname'] }}`)は選定されたhost名をそのまま出すため、pve1/pve2どちらで実行されたかが通知本文から自然に分かる。今回の変更に伴う追加修正は不要だった。
- 両方到達不能時のfailメッセージがpve1/pve2それぞれの到達性を明記しており、無言のUNREACHABLEを避けている。
- tester-gate: risk-accepted(--checkの有無に関わらず常に本実行)という既存の不変条件は、Play 1(ping自体が`supports_check_mode=True`で--check下でも実probeする)とPlay 2(`check_mode: false`)の両方で保たれており、今回の2-play化によって崩れていない。
