## 概要

pve1が夏季平日シャットダウン運用で日中停止するため、`unifi_backup_fetch.yml` は
`hosts: pve1` 固定のままだと実行できない。ADR-001の決定(Option a: pve1優先・
pve2フェイルオーバー)に従い、playbookを2 playに分割した。

- Play 1: `hosts: pve1:pve2` でSSH到達性をprobeし、pve1優先・pve2フェイルオーバーで
  実行対象を **1ホストだけ** `unifi_backup_fetch_target` という動的groupへ登録する。
  両方到達不能なら、どちらが不可だったか分かる理由で `fail` する。
- Play 2: `hosts: unifi_backup_fetch_target` で既存のfetch処理(旧単一playの中身)を
  そのまま実行する。

`roles/unifi_backup_fetch` (tasks/main.yml、defaults/main.yml) は grep確認の結果
host固有の依存(pve1/pve2やinventory_hostnameへの参照)は無く、host非依存のまま
変更不要だった(詳細は下記「roleへの依存確認」参照)。

## 実装内容

### host選定ロジック(新規 Play 1)

```yaml
- name: Select unifi_backup_fetch execution host (pve1 preferred, pve2 fallback)
  hosts: pve1:pve2
  gather_facts: false
  become: false
  tasks:
    - name: Probe SSH reachability
      ansible.builtin.ping:
      register: unifi_backup_fetch_ping
      ignore_unreachable: true
      ignore_errors: true

    - name: Record per-host reachability
      ansible.builtin.set_fact:
        unifi_backup_fetch_host_reachable: >-
          {{ not (unifi_backup_fetch_ping.unreachable | default(false) | bool)
             and not (unifi_backup_fetch_ping is failed) }}

    - name: Fail if neither pve1 nor pve2 is reachable
      ansible.builtin.fail:
        msg: "..."
      run_once: true
      delegate_to: localhost
      when: >-
        not (hostvars['pve1'].unifi_backup_fetch_host_reachable | default(false) | bool)
        and not (hostvars['pve2'].unifi_backup_fetch_host_reachable | default(false) | bool)

    - name: Select execution host (pve1 preferred, pve2 fallback)
      ansible.builtin.add_host:
        name: >-
          {{ 'pve1' if (hostvars['pve1'].unifi_backup_fetch_host_reachable | default(false) | bool)
             else 'pve2' }}
        groups: unifi_backup_fetch_target
      run_once: true
      delegate_to: localhost
      changed_when: false
```

設計判断:

- **到達性probeの方式**: `ansible.builtin.ping` + `ignore_unreachable: true` +
  `ignore_errors: true`。`ignore_unreachable` を付けないと、その1タスクで
  playが即fatalになりPlay全体が止まる(通常のAnsible挙動)。このリポジトリでは
  `roles/time_sync_check/tasks/check_chrony.yml` が同じ
  `ignore_unreachable: true` → 次タスクで `.unreachable` 属性を読む、というパターンを
  既に採用しており(複数ホストへの巡回probeで既に実運用・レビュー済み)、それに揃えた。
  `ignore_errors: true` を追加したのは、`ping` module自体が(到達不能以外の理由で)
  失敗した場合でもplay全体を止めず「到達不可とみなしpve2側にフォールバックする」
  安全側の挙動にするため。
- **`set_fact`/`fail`/`add_host` がunreachableホストでも動く理由**: これらは
  controller側で完結するaction(実際のリモート接続を必要としない)ため、
  直前のタスクで対象ホストが到達不能と分かっていても後続タスクは実行できる。
  この前提は `check_chrony.yml` の既存パターンと同一で、実運用実績がある。
- **1ホストだけを選ぶ理由(二重実行・二重ローテーション防止)**: `add_host` を
  `run_once: true` + `delegate_to: localhost` にすることで、pve1・pve2の両方が
  到達可能な場合でも `unifi_backup_fetch_target` グループには常に1ホストのみが
  登録される(pve1が到達可能なら常にpve1を選び、pve2は登録しない)。Play 2は
  そのグループにしか実行されないため、保存先NFS(共有パス)への同時書込・
  同時ローテーションは構造的に発生しない。
- **失敗メッセージ**: 両方到達不能な場合、`fail` の `msg` に pve1/pve2
  それぞれの到達性(true/false)を明記し、「原因が分かる明確なメッセージ」という
  要求を満たす(無言のUNREACHABLEにしない)。
- **2-play構成の採用理由**: `playbooks/proxmox_backup_restore_verify.yml` が既に
  「Play 1で対象を決定し `add_host` で動的groupへ登録 → Play 2でそのgroupに対して
  実処理」という同型パターンをこのリポジトリで採用・レビュー済みのため、新規の
  設計パターンを持ち込まず、それに揃えた。

フェイルオーバー・preflight選定・二重実行防止・ADR参照へ更新した(要求どおり)。

### `roles/unifi_backup_fetch` への依存確認

`grep -rn "pve1\|pve2\|inventory_hostname" roles/unifi_backup_fetch/` を実行し、
2件のみヒット。いずれも**コメント**であり、コードとしてのhost依存(条件分岐・
ハードコードされたhost名など)は無かった:

- `defaults/main.yml:14`: `# 保存先(pve1 上の既存 Synology NFS マウント)。`
- `tasks/main.yml:11`: `# pve1 上で become: true(root)で実行する(...)。`

いずれも「pve1という特定ホストが前提」ではなく「(選ばれた)実行ホスト上で」という
実態を説明するコメントで、pve2で実行された場合も記述の趣旨(NFSマウント経由・
rootで実行する理由)自体は誤りではない。ただし文言としては pve1 決め打ちに読める。
今回のscopeは「playbook冒頭のコメント」の更新に限定されていたため、この2件は
**意図的に変更していない**(scope外の変更を独断で広げないため)。要修正であれば
別途指示をお願いします。

`tasks/main.yml` / `defaults/main.yml` のコード自体(host名の分岐やinventory_hostname
参照)には変更不要だった。

## 未検証事項(実機でしか確認できない — tester委譲)

- **pve1到達可能時にpve1が選ばれること**、**pve1停止・pve2稼働時にpve2へ
  フェイルオーバーすること**、**両方停止時に明確な理由でfailすること**の3パターン
  実機確認。特に「pve1は現在停止中」とのことなので、pve1停止状態でのpve2
  フェイルオーバー実行は実地検証の好機。
- ADR記載のとおり、`/mnt/pve/Synology-nfs/user-backup/unifi` が **pve2上にも
  同一パスで実在するか**(Proxmox cluster storageとして自動適用されている
  はず、との推測はADRに記載済みだがコードからは断定できない)。pve2で
  `mountpoint /mnt/pve/Synology-nfs` の実機確認が必要。これが外れている場合、
  pve2フェイルオーバー実行時にPhase 2(保存先ディレクトリ作成)以降で
  想定外の挙動になる可能性がある。
- 両ホストが同時に到達可能な状況での「pve1が優先されること」の実機確認
  (dry-runでは到達性判定ロジックの単体挙動しか確認できていない)。
- `ansible.builtin.ping` によるSSH到達性probeが、実際のpve1シャットダウン時に
  期待どおり `unreachable: true` を返すこと(理論上は標準的なAnsible挙動だが、
  このplaybook固有の実行環境(quory/ansyからの接続)での確認はしていない)。
