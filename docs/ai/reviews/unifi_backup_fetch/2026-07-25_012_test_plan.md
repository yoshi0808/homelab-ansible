# テスト計画: unifi_backup_fetch pve1→pve2 動的host選定(ADR-001)

対象:

- `docs/ai/adr/001-unifi_backup_fetch-pve1-shutdown-target.md`
- `docs/ai/reviews/unifi_backup_fetch/2026-07-25_010_implement.md`
- `docs/ai/reviews/unifi_backup_fetch/2026-07-25_011_review.md`(Approve、blocking指摘なし)
- `playbooks/unifi_backup_fetch.yml`

## 背景

pve1は夏季平日シャットダウン運用中で停止しており、今がpve2フェイルオーバーの実地検証の
好機であるとtechleadから依頼された(Tier3、tester-gate: risk-accepted、`--check`の有無に
かかわらず常に本実行)。techlead依頼は4項目:

1. 現在の状態(pve1停止・pve2稼働)で実行し、pve2へのE2Eフェイルオーバー成功を確認する。
2. `/mnt/pve/Synology-nfs/user-backup/unifi`がpve2上にも実在することを事前確認する。
3. 両方到達不能時のfailメッセージを、コード読解+可能な範囲のfixtureで検証する。
4. pve1が稼働している場合にpve1が優先されることも、状況次第で確認する。

## 前提確認(実行前)

- 項目2: `roles/unifi_backup_fetch/tasks/main.yml`の「Phase 2 - Ensure backup destination
  directory exists」は`ansible.builtin.file: state: directory`であり、NFSが未マウントでも
  ローカルディスクへ静かにディレクトリを作成し得る(mount実在確認がコード上にない)。
  このためpve2側のマウント実在は本実行前の必須precondition。
- Claude Code製品固有の禁止事項(`docs/ai/core-migration-map.md` C17-01: 実host
  ad-hocを行わない)により、testerが自らpve2へad-hoc確認コマンドを実行することはしない。
  Yoshinobuに確認済み: pve2側のマウントは既存のProxmox cluster storageとして既に実在
  すると確認済み(2026-07-25、agmsgセッション内でのYoshinobu回答)。この結果を前提として
  実行に進む。

## テスト項目

tester(Claude Code)はansy上で動作する。以下はすべてansy上から実行する。

### 1. Fixture: 両方到達不能時のfail経路(techlead依頼#3)

対象ホストの実際の停止は不要という依頼どおり、実pve1/pve2に一切触れないfixtureで検証する。

- `playbooks/unifi_backup_fetch.yml`のPlay 1をそのまま複製したscratch-only playbook
  (`play1_only.yml`、Play 2は含まない)を使い、pve1/pve2という名前のdecoy hostを
  `127.0.0.1:1`(closed port、即座にconnection refused = unreachable)へ向けたfixture
  inventoryに対して実行する。
- 期待結果: `fail`タスクが発火し、メッセージに`pve1 reachable: False; pve2 reachable: False`
  が含まれること。

### 2. Fixture: 両方到達可能時のpve1優先(techlead依頼#4)

pve1が現在停止中のため実pve1では確認できない。同じscratch playbookで、pve1/pve2という
名前のdecoy hostを両方`ansible_connection: local`(controller上で完結、実ホスト無し)に
した別fixture inventoryに対して実行する。

- 期待結果: `unifi_backup_fetch_target`グループにpve1のみが登録されること(add_hostの
  Jinja2式が`hostvars['pve1']`を優先評価することの実地確認。review 2026-07-25_011で
  ansible-core本体のソースからも独立に裏付け済み)。
- 実pve1が到達可能な状態に戻った際の実機確認(実pve1/pve2両方が本当に到達可能な状態)は
  対象外とし、pve1復帰後の別イテレーションに委ねる(下記「対象外」参照)。

### 3. 実行(apply): pve1停止・pve2稼働での実E2E(techlead依頼#1・#2)

`playbooks/unifi_backup_fetch.yml`を実inventoryに対して本実行する(risk-accepted、
`--check`なし)。実行前にYoshinobuの確認を得る(ask-gate)。

- 期待結果:
  - Play 1でpve1がunreachable、pve2がreachableと判定され、`unifi_backup_fetch_target`に
    pve2のみが登録されること。
  - Play 2がpve2上で実行され、ログイン→バックアップ生成・DL→鮮度ガード→Synology保存→
    世代ローテーション→Slack通知(#info/ok)まで`failed=0 rescued=0`で完了すること。
  - 保存先ファイルがpve2上の`/mnt/pve/Synology-nfs/user-backup/unifi`に実在すること
    (前提確認セクションのとおりNFSマウント上への保存であることが担保されている)。
  - Slack通知本文の`Executed on:`がpve2のhostnameであること。

## 対象外(今回スコープ外)

- `roles/unifi_backup_fetch`本体の変更確認(reviewerが独立確認済み、コード変更なし)。
- pve1が実際に稼働している状態での実機確認(techlead依頼#4の実ホスト版)。pve1は
  夏季平日シャットダウン運用中のため本セッションでは確認不可。pve1復帰時に別途確認する。
- 両ノードを実際に同時停止させての実機fail確認(techlead依頼が明示的にfixtureで
  代替可としている)。
