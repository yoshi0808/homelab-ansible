# テスト結果: unifi_backup_fetch pve1→pve2 動的host選定(ADR-001)

対象: `docs/ai/reviews/unifi_backup_fetch/2026-07-25_012_test_plan.md`
実行環境: ansy、`ansible-playbook`(Claude Code、tester)
実行日時: 2026-07-25

## 前提確認

pve2の`/mnt/pve/Synology-nfs`マウント実在は、Claude Code製品固有の禁止事項(実host
ad-hoc不可)によりtester自身では確認せず、Yoshinobuに確認済み(既存のProxmox cluster
storageとして実在)。これを前提に以下を実行した。

## 結果サマリ

| # | 項目 | 対応するtechlead依頼 | 結果 |
|---|---|---|---|
| 1 | Fixture: 両方到達不能→fail | #3 | **PASS** |
| 2 | Fixture: 両方到達可能→pve1優先 | #4(fixture版) | **PASS** |
| 3 | 実行: pve1停止・pve2稼働でのE2E | #1・#2 | **PASS** |

## 1. Fixture: 両方到達不能時のfail経路

`play1_only.yml`(Play 1のみのscratch複製)を、pve1/pve2という名前のdecoy host
(`127.0.0.1:1`、closed port)へ向けたfixture inventoryに対して実行した。

```
fatal: [pve1 -> localhost]: FAILED! => {"changed": false, "msg": "unifi_backup_fetch:
neither pve1 nor pve2 is reachable via SSH, cannot select an execution host.
pve1 reachable: False; pve2 reachable: False."}

PLAY RECAP
pve1  : ok=2 unreachable=0 failed=1 ignored=1
pve2  : ok=2 unreachable=0 failed=0 ignored=1
```

期待どおり、両host到達不能を検知しそれぞれの到達性を明記した理由でfailした。
review 2026-07-25_011の項目3の結論と一致する。

## 2. Fixture: 両方到達可能時のpve1優先

同じscratch playbookを、pve1/pve2両方を`ansible_connection: local`にしたfixture
inventoryに対して実行した。

```
TASK [[test fixture only] Report selected execution host]
ok: [pve1 -> localhost] => {"msg": "selected unifi_backup_fetch_target = ['pve1']"}

PLAY RECAP
pve1  : ok=4 failed=0 skipped=1
pve2  : ok=2 failed=0
```

両方到達可能でも`unifi_backup_fetch_target`にpve1のみが登録され、pve2への二重実行は
発生しなかった。review 2026-07-25_011の項目2の結論と一致する。

実pve1が稼働している状態での同項目の実機確認は、pve1が夏季平日シャットダウン運用中の
ため本セッションでは実施できない(test_planの「対象外」記載どおり)。pve1復帰時に
別途確認する。

## 3. 実行: pve1停止・pve2稼働での実E2E

`ansible-playbook -i inventories/homelab/hosts.yml playbooks/unifi_backup_fetch.yml`
を実inventoryに対して本実行した(risk-accepted、`--check`なし)。

```
TASK [Probe SSH reachability]
ok: [pve2]
fatal: [pve1]: UNREACHABLE! => {"msg": "...ssh: connect to host pve1.internal port 22:
No route to host", "unreachable": true}
...ignoring

TASK [Select execution host (pve1 preferred, pve2 fallback)]
ok: [pve1 -> localhost]   # (add_hostタスク自体はpve1へdelegate_to: localhostされて
                            # 実行されるが、選定結果はpve2。下記Gathering Facts以降が
                            # pve2のみに対して実行されていることで確認できる)

PLAY [unifi_backup_fetch] (hosts: unifi_backup_fetch_target = pve2)
...
TASK [Phase 2 - Ensure backup destination directory exists] ok: [pve2]   # 既存(changedでない)
TASK [Phase 2 - Generate and download the UniFi OS backup] changed: [pve2]
TASK [Phase 3 - Freshness guard (filename timestamp vs now)] ok: [pve2]
TASK [Phase 4 - Place backup file at final path] changed: [pve2]
TASK [Phase 4 - Normalize backup file permissions] changed: [pve2]
TASK [Phase 5 - Remove old backups beyond retention] changed: [pve2] =>
  (item=/mnt/pve/Synology-nfs/user-backup/unifi/unifi_os_backup_1781526993574_...unifi)
TASK [Send Slack notification] ok: [pve2 -> localhost]

PLAY RECAP
pve1  : ok=3  changed=0  unreachable=0  failed=0  skipped=1  ignored=1
pve2  : ok=36 changed=4  unreachable=0  failed=0  skipped=5
```

確認できた点:

- pve1は`No route to host`でunreachableと判定され(夏季平日シャットダウン運用の
  想定どおり)、pve2へのフェイルオーバーが実際に発生した。
- `unifi_backup_fetch_target`に登録されたのはpve2のみ(Play 2の全タスクがpve2に
  対してのみ実行され、pve1に対する二重実行は発生していない)。
- Play 2は`failed=0 rescued=0`で完了(ログイン→生成・DL→鮮度ガード通過→Synology
  保存→世代ローテーション→Slack通知の全phaseが成功)。
- 「Phase 2 - Ensure backup destination directory exists」が`changed`でなく`ok`
  だったことから、ディレクトリは実行前から既に存在していた(このタスクによって
  ローカルディスク上へ新規作成されたのではない)。前提確認セクションのYoshinobu
  確認(pve2側マウント実在)と合わせて、保存先が実際のNFSマウントであったことの
  補強的な確認材料とする。
- 「Phase 5 - Remove old backups beyond retention」が実際に1件削除しており(8世代
  保持ロジックの実削除)、2026-06-15時点の実機検証時に残っていた最初期のバックアップ
  ファイルが今回のローテーションで正しく削除された。
- Slack通知(#info/ok)が送信された(通知タスクが`ok`で完了)。

## 未実施・残存事項

- techlead依頼#4のうち、実pve1が稼働している状態での「pve1優先」実機確認は、pve1が
  現在停止中のため未実施。fixtureでの代替確認(上記2.)はPASS。pve1復帰時に別途
  実機確認を推奨する。
- 両ノードを実際に同時停止させての実機fail確認は、techlead依頼どおりfixtureで代替し
  実施していない(実host destructive操作を避けるため)。

## 総合判定

**techlead依頼4項目のうち3項目(#1・#2・#3)は実機/fixtureでPASS。残る#4(実pve1稼働時
の実機確認)はpve1停止中のため未実施 — blockingではなく、pve1復帰後のフォローアップ
として扱うことを推奨する。** blocking issueなし。
