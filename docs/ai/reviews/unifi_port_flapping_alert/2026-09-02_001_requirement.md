# requirement: UniFiスイッチのポートflappingをsyslogから検知する

日付: 2026-09-02
状態: 起案(Yoshinobu合意済み — requirement作成まで、2026-09-02)

## 1. 背景

Yoshinobu提起(2026-09-02)「syslogの使い道を検討しないといけない。ネットワークのflappingくらいは見るようにしようか」。

`docs/ai/policies/log_observability_policy.md` は**この対象を最初から想定している** — LOG-066が「portのflappingと接続断の繰り返し」をsyslog系統の検知対象として挙げ、LOG-067が未実装の理由を「閾値の時期尚早な設定を避け実データの蓄積を待つため。実装時期は蓄積状況を見て判断する」としている。本案件はその判断を行うものである。

**syslog系統の検知は現在1本も無い**(LOG-047)。Grafanaのalert rule 4本はすべてPrometheus参照で、Lokiを参照するruleもLoki rulerもAlertmanagerも配備されていない。

## 2. 前提の実測

| 事実 | 出所 |
|---|---|
| `usw-core` の `TRAPMGR: Link Up: 0/11` / `Link Down: 0/11` がLokiまで到達している(遷移ごとに1行、秒精度) | 実機で発生させて確認(`docs/ai/reviews/promtail_to_alloy/2026-07-26_030_investigation_unifi_linkup_level_match.md`) |
| 受信時にrsyslogが行を書き換えるため、**severityトークンが消えて `level` が付かない** | 同上、LOG-075 |
| **`level` を含むLogQLセレクタは、この系統の行を一切返さない。** 検知は `job` / `host` / message本文で特定する | LOG-076 |
| `network-devices` は最大のログ源(7,457行/日)で、全行が `level` 無し | 2026-09-01実測(`docs/ai/reviews/syslog_weekly_digest/2026-09-01_001_requirement.md` §2) |

**metrics側は採らない。** unpollerのmetricはスクレイプ間隔のサンプリングであり、**間隔内に落ちて戻った遷移は値が動かず消える**。flappingは遷移の頻度そのものが対象なので、遷移ごとに1行あるsyslogの方が原理的に適している(LOG-066が「metricsの閾値では表れにくい」と述べているのと同じ理由)。**unpollerがポートのlink状態をmetricとして出しているかは未確認**であり、開発側からPrometheusへ問い合わせる語彙が無い。ただし有無は本判断を変えない。

## 3. 目的

**同一ポートが短時間に繰り返しlinkを落とす状態を、発生時にSlackへ通知する。**

## 4. 受入条件

- **AC1**: Lokiを参照するGrafana alert ruleが1本配備され、`job` / `host` / message本文で `Link Down`(および必要なら `Link Up`)を特定する。**`level` でフィルタしない**
- **AC2**: 発火条件(LogQL・比較値・評価間隔・`for`)がrepoのprovisioning YAMLに存在し、そこが正本である。Policy本文へ値を書かない
- **AC3**: **発火条件の根拠が記録に残る** — 算出クエリ、観測期間、**その条件なら直近N日で何回発火していたか**(LOG-081)
- **AC4**: 通知が `slack-homelab` へ届く。alerting YAMLのtop-levelキーは `apiVersion` と `groups` だけであり、`policies` / `contactPoints` 等を含まない(LOG-084)
- **AC5**: 通知本文から、**どのホストのどのポートか**が分かる
- **AC6**: 配備が複製に限られる(`copy` であって `template` でない)。gitとホストのSHA256が一致する(LOG-082)
- **AC7**: `--check` で副作用なく完走する
- **AC8**: 既存4ルールの発火条件・UID・folder・`notification_settings` が変化しない。`alert_configuration.configuration_hash` が不変であることで非回帰を示す(LOG-084)
- **AC9**: Policyの「syslog系統の検知は未実装」という記述(§1の表、LOG-047、LOG-067)が実態と一致する状態で終わる

## 5. 制約

- **発火条件の値をPolicyへ書かない**(LOG-078〜LOG-080)。Policyが持つのは管理の作法だけである
- **nameベースのdatasource参照を使わない。** UID参照が唯一の正しい形であり、preflightが機械的に拒否する(LOG-083)
- **alerting YAMLの反映はGrafanaのrestartが要る**(dashboardと違いpollされない)。restart前に `roles/recovery_mute` でmonnieのmute窓を張る。実行時刻を `ubuntu_nightly` のmonnie処理時間帯と重ねない(LOG-086)
- **手作業のUI編集・UI importを経路にしない**(LOG-078)
- 実行は quory の Semaphore。入口は `playbooks/grafana_provisioning.yml`、`--tags alerting`
- IPアドレス・秘密情報を出力しない

## 6. 未決(着手前にCoordinatorが決める、またはYoshinobuへ上げる)

- **AC3の根拠をどう取るか。** **開発側からは取れない** — `loki-window` は最長1時間・300行が上限、`loki-count` は本文でフィルタできない。`network-devices` は310行/時なので1時間窓でも上限に当たる。**Operator Request Channelで、直近N日の `Link Up` / `Link Down` の host×port別件数を依頼するのが設計どおりの経路である**(EXEC-043)。本日整備した `scripts/oprc-submit.sh` で発行済み — `req-20260902T170856+0900-607a7b449ed2830b`(2026-09-02、登録と通知が1操作で成立)。**回答待ち**
- **`roles/grafana_provisioning` は alerting YAML を1ファイルしか配備できない**(`grafana_provisioning_alert_rule_file` がスカラ)。2本目を足すにはroleを複数ファイル対応へ変える必要がある。既存ファイルへ相乗りさせない(名前と folder が metrics 系統のものである)
- **`alert_rules_predecessor_confirmed` の扱い。** 現在のroleは配備のたびにこのフラグを要求する(2026-07-30の移行で旧4ルールがUIで削除済みであることの人間確認)。新規ファイルの配備でも同じゲートを通ることになる。**既存の安全ゲートに触れる判断なので、変えるならYoshinobuへ上げる**
- **Policy改訂が要る。** §1の表の「未実装」、LOG-047、LOG-067は本案件の完了時点で偽になる。**Policy本文の改訂はYoshinobu必須**(EXEC-030)
- 対象ホストの範囲(`usw-core` 以外のスイッチが同じ行形式で送っているか未確認)

## 7. 範囲外

- **接続断の繰り返し(AP / クライアント側)。** LOG-066はflappingと並べて挙げているが、**Loki(LogQL)でのalertはこの環境で初物**であり、まず1本通してから広げる
- **週次ダイジェスト**(`docs/ai/reviews/syslog_weekly_digest/`)。別案件のまま残す。本案件はダイジェストの完了を待たない — ダイジェストが待っていたのは「levelノイズの中で閾値をどう置くか」であり、flappingは本文パターンで定義できるため前提が異なる
