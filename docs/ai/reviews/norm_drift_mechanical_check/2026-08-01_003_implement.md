## 2. 実装方針

### 2.1 3つの検査を1スクリプトにまとめた構成

`check_playbook_tester_gate` / `check_agent_model_effort` / `check_internal_links` の3関数。各関数は `CheckResult(name, findings, compared)` を返すか、入力集合が空のとき `AnalysisError` を送出する。`main()` は3関数を順に呼び、`AnalysisError` または `RuntimeError` を「エラー(exit 2)」、`findings` が1件でもあれば「不一致(exit 1)」、すべて空なら「OK(exit 0)」に落とす。requirement §3「解析結果が空のときにPASSを返さないこと」に対応する構造そのものを型で強制している(`CheckResult.ok`は`findings`が空かどうかだけを見るので、`compared=0`のまま`ok=True`を返す経路が構造的に存在しない — 各checkが自分で0件を検出して`AnalysisError`を送出しない限りその関数自体が呼び出し元に返ってこない)。

### 2.2 git indexから読む(working treeから読まない)

`read_index_content()`は`git show :<path>`で内容を取得し、`open()`で直接読まない。`git ls-files`も同様にindexを列挙する。これは思いつきではなく、**同じpre-commitチェーンに既にある規約を踏襲した**: `scripts/check-staged-yaml.py`のdocstringと`scripts/git-pre-commit-check.sh`のvault-headerチェックのコメントが、どちらも「commitされるのはindexであってworking treeではない」ことを理由に`git show :<path>`を使うと明記している。

この検査はstaged file一覧に基づく検査ではなく**リポジトリ全体を横断する検査**(48本のplaybook全部、4つのagent定義全部、reviews以外の全Markdown)なので、「今回のcommitでstageされたファイルだけ読む」という形は取れない。かわりに、**全対象パスをindexから列挙し、各内容もindexから読む**ことで、「このcommit後に成立する木の状態」を評価する。working treeにだけ存在する未staged編集(例: README.mdを直そうとして保存したがgit addし忘れた)を「直った」と誤判定しない。

実地での確認: 現在のrepoは`git status`がclean(自分の新規ファイルを除く)なので、index読みとworking tree読みで結果に差は出ない。差が出る経路(staged編集とworking tree編集が食い違うケース)は今回のself-verificationでは作っていない — 3.4節で明示する未検証事項。

### 2.3 Markdownテーブル解析は「連続する`|`始まりの行」を1テーブルとして塊取り

`extract_pipe_tables()`は空行・非`|`行でテーブルの塊を区切り、塊ごとにheader行を独立して解釈する(`find_table`/検査#1のcatalog探索も同じ関数を使う)。ファイル全体を1状態機械で舐めて「今のtester-gate列番号」を引きずる実装にしなかった理由は、`playbooks/README.md`の「安全区分の見方」にある2列の凡例テーブル(`| `tester-gate` | カタログ上の意味 |`)がcatalogテーブルと同じ`tester-gate`という語を含み、状態を引きずる実装だと誤ってheader行と誤認識しかねないため。実際にこの凡例テーブルは「1列目が`playbook`を含む」という追加条件で弾かれることを確認済み(3.1節)。

### 2.4 インラインコードスパンとfenced code blockを除外してからリンク正規表現を掛ける

requirement §4が名指しした2件の偽陽性 —
`docs/ai/memory/lessons/verification-referent-and-path-mismatch.md` と
`skills/document-norm-review/SKILL.md` の `` `[Repository Context](...)` `` — は、どちらも**単一バッククォートで囲われたコードスパンの中の説明文字列**であり、実際のMarkdownリンクではない。`_strip_code_regions()`でfenced code block(` ``` `/`~~~`)を空行化し、続けて残りの行から `` `...` `` の区間を正規表現で除去してからリンク抽出の正規表現を掛けることで、この2件は最初からリンク候補として抽出されない(「除外リストで名指しして弾く」のではなく、「コードスパンの中身はそもそもリンクとして解釈しない」という一般則で自然に解決している)。

副次的に見つけた事実: 同じ理由で、`docs/ai/memory/lessons/`配下のいくつかのファイルにある `[[wiki-link-slug]](説明文)` という独自のZettelkasten風記法(例: `distinguish-nothing-found-from-not-run.md`の`[[verify-the-outside-of-a-claimed-boundary]](境界の外側を検証する...)`)も、正規表現`\[[^\]\n]*\]\(`が二重角括弧`]]`の直後の`(`にマッチしないため、コードスパン除去とは無関係に最初から誤検出しない。実地確認済み(3.3節)。

### 2.5 リンク解決対象は「全git tracked pathの集合」

検査#3の存在判定は、リンク先を`playbooks/README.md`のような特定パターンに絞らず、`git ls-files`(パターン無し = 全tracked path)の集合に対する所属判定にした。リンクは`.yml`・`.md`・`.sh`など何にでも張られうるため。

### 2.6 fixtureは「保存はプレーンなファイルツリー、実行時だけ使い捨てgit repoにする」

`check-doc-consistency.py`は`git ls-files`/`git show :<path>`でindexを読む設計(2.2節)であり、これは変更していない。差し戻し前は、この設計にfixtureを合わせるために**fixtureそのものを`git init`済みの小さなrepoとして保存**していた。しかし「保存された状態が入れ子repoになる」「`.git`の中身がfixture本体よりずっと大きい」「保存場所の`.gitignore`と衝突してリポジトリに残らない」という3つの問題を生んだ(いずれも差し戻しの指摘どおり)。

差し戻し後は逆にした: **fixtureはプレーンなファイルツリーとして保存し、`.git`は一切持たせない**。かわりに`scripts/tests/fixtures/run-fixture-checks.sh`が、実行のたびに各fixtureを`mktemp -d`の一時ディレクトリへコピーし、そこで`git init -q && git add -A .`してから`check-doc-consistency.py --repo-root <一時ディレクトリ>`を呼び、終わったら一時ディレクトリを削除する。「fixtureが保存されている形」と「checkerが読む形」を分離したことで、

- checker側の設計(index読み)は変更不要。
- fixtureはリポジトリに残る通常のファイル(`.git`が無いので入れ子repoにならず、サイズもデータ本体だけ。5 fixture合計25ファイル・224KB→さらに`.gitignore`修正後は純粋にfixtureの中身のみ)。
- 再現手順は`run-fixture-checks.sh`を実行するだけ(3.3節)。

`check-doc-consistency.py`本体には、プレーンディレクトリを直接`--repo-root`に渡したときに分かりやすく失敗させるためのガード(`.git`が無ければ`ERROR: ... not a git working tree` / `exit 2`)を3.7節の頑健化としてすでに入れていたため、「fixtureへ直接向けて実行すると意味のあるエラーで止まる」「`run-fixture-checks.sh`経由なら通る」という区別が自然に付く。

### 2.7 検査#3(改訂2): 除外リストを廃止し、対象を明示列挙する。加えて一般的な欠陥1件を修正

改訂2で判明した2件のblocking findingのうち、1件は**requirement自体の設計欠陥**(除外リスト方式)、もう1件は**実装側の一般的な欠陥**(コードスパン除去の正規表現)だった。両方とも直した。

**(a) 対象決定を除外リストから許可リストへ(requirement改訂に追従)**

改訂前は「全`*.md` − `docs/ai/reviews/`」という除外リスト方式だった。Coordinatorがリポジトリ全体を`git add -A`した状態で実行したところ、`scripts/tests/fixtures/`(検査自身のfixtureデータ。意図的に壊れたリンクを含む)がこの除外リストに入っておらず、**この差分自身のcommitで検査が落ちる**ことが判明した。除外リストは「新しい種類のファイルが増えるたびに書き足す」形であり、書き漏らしが直しようのない指摘に直結する — 今回がまさにその実例である。

requirement §2 検査#3が「対象を明示列挙する方式」に改訂されたため、実装もそれに合わせた。`_is_normative_markdown(path)`が以下を判定する:

- 完全一致: `CLAUDE.md`、`AGENTS.md`、`playbooks/README.md`
- 直下のみ: `posixpath.dirname(path) == "docs/ai"`
- 配下(再帰): `docs/ai/policies/`、`docs/ai/context/`、`docs/ai/roles/`、`docs/ai/memory/`、`docs/ai/adr/`、`docs/ai/prompts/`、`skills/`、`roles/`、`.claude/agents/`(いずれも文字列prefix一致 + `.md`拡張子)

**改訂3(2026-08-01)で `docs/ai/prompts/` と `.claude/agents/` を追加。** 独立レビューはblocking findingなしでApproveだったが、requirement自体の列挙漏れを検出した — 根拠は`skills/document-norm-review/SKILL.md`が規範文書のクラスとして「Policy / Context / Role文書 / SKILL.md / **prompt** / CLAUDE.md」を挙げていること(`.claude/agents/`はRole定義の実行機構であり、role-routing-index.mdが明記する規範の一部)。`_NORMATIVE_PREFIXES`に2エントリを追加しただけで、`_is_normative_markdown`のロジック自体は変更していない。追加後に実測したところ、`docs/ai/prompts/`(追跡ファイル1本: `autonomous_recovery_deploy_runbook.md`)・`.claude/agents/*.md`(4本)とも内部リンクを0本しか持たず、`check3`の比較件数は88のまま変化しなかった(3.2節)。

**(b) `git ls-files`のglobパターンは`*`が`/`を跨ぐ、という見落としを発見・回避**

上記(a)を実装する過程で、当初`git_ls_files(repo_root, ["docs/ai/*.md"])`のようにgit側のパターンマッチに任せる案を検討したが、実測すると**この呼び方は「直下のみ」にならない**ことが分かった:

```
$ git ls-files 'docs/ai/*.md' | wc -l
1025
$ git ls-files 'docs/ai' | grep -c '\.md$'
1025
```

`docs/ai/*.md`は`docs/ai`配下の**全階層**のMarkdown(`docs/ai/reviews/`配下947件を含む)を返した — bashのglobや`fnmatch.fnmatch(..., FNM_PATHNAME)`が持つ「`*`は`/`を跨がない」という直感は、git pathspecの既定matcherには**当てはまらない**(Pythonの`fnmatch.fnmatch`も同様に`/`を跨ぐことを別途確認した)。

これは検査#1で使っている`git_ls_files(repo_root, ["playbooks/*.yml"])`も同じ仕組みで動いている、ということでもある。**現状のplaybooks/には`.yml`を持つサブディレクトリが無いため直下48件と全階層48件が一致し、バグとして顕在化していないだけ**である。検査#1はCoordinatorの指示により今回変更していないため、この潜在的な非頑健性は直さず未解決事項(7節)として残す。検査#3では初めから正しい実装(`posixpath`による文字列比較、git pathspecに依存しない)にした。

**(c) `_strip_code_regions`のコードスパン除去が「開き幅と同じ幅の閉じ」を見ていなかった一般的な欠陥**

`scripts/tests/fixtures/README.md:41`の実際の内容は `` `` `[example](...)` `` `` — **2連続バッククォートで開き、中に単一バッククォートで囲われた文字列を含む**というMarkdownの正式な記法(CommonMarkでは、コードスパンの中に生のバッククォートを入れたいとき、開始・終了を長いバッククォート列にする)。

改訂1時点の実装 `re.sub(r"`+[^`\n]*?`+", " ", line)` は「何個でもいいバッククォート列→バッククォートを含まない文字→何個でもいいバッククォート列」というだけの正規表現で、**開きと閉じの個数を対応させていなかった**。そのため`` `` `[example](...)` `` ``に対して、非貪欲マッチが最短一致(2連続バッククォート + スペース1文字 + バッククォート1個)で打ち切ってしまい、`[example](...)`本体がコードスパンの外に取り残されてリンクとして誤検出されていた。

Coordinatorはこれを「fixture由来の事情ではなく一般の欠陥として直すこと」と指摘した — 妥当な指摘である。**同じ記法(内側に生バッククォートを持つ二重バッククォートのコードスパン)が規範層のどこかに書かれれば、fixtureの除外・非除外に関わらず同じ誤検出が起きる。** 修正は、開き括弧をキャプチャして`\1`で同じ幅の閉じを要求する正規表現に置き換えた:

```python
_CODE_SPAN_RE = re.compile(r"(`+)(.+?)\1(?!`)")
```

`(?!`)`は「閉じの直後にさらにバッククォートが続かない」ことを要求し、閉じ列の途中で早期に一致してしまう事故を防ぐ。単体テストで単一バッククォート・二重バッククォートの両方が正しく1つのコードスパンとして丸ごと除去されることを確認した(3.1節)。

## 6. fixtureの保存形態(解決済み)

**初回提出時の状態(差し戻し理由):** fixtureをそれぞれ`git init`済みの独立したgit repoとして`scripts/tests/fixtures/<name>/`に保存していた。これは3つの問題を生んでいた。

1. `scripts/tests/fixtures/`配下の5 fixtureそれぞれに`.git`ディレクトリがあり、このままリポジトリへ追加すると入れ子repoになる。
2. fixture全体で144ファイル・1016KB、大半が`.git`の中身(実データはごく小さいテキストファイルのみ)。
3. `.gitignore`44行目(当時: `scripts/tests`)が`scripts/tests/`配下を丸ごと無視しており(`git check-ignore -v`で確認済み)、`git status`にも`git add -A`にも現れない — fixtureがリポジトリに残らず、AC3の再現手順を他の人が辿れない状態だった。

**対応:**

- **fixtureをプレーンなファイルツリーに作り直した**(各fixtureの`.git`を削除)。`check-doc-consistency.py`のindex読みの設計自体は変更していない — 実行時にだけ使い捨てのgit repoを作る役目を`scripts/tests/fixtures/run-fixture-checks.sh`(新規)に持たせた。設計の詳細は2.6節。
- **`.gitignore`44行目を変更した**(差し戻しで許可された権限境界)。`scripts/tests`(ディレクトリ丸ごと無視)を`scripts/tests/*` + `!scripts/tests/fixtures/`に変え、「`scripts/tests/`配下は既定で無視するが、`scripts/tests/fixtures/`だけは例外的に追跡する」という形にした。`new-session.sh`等、同じ「ヘルパーシェル」セクションにある他の無視パターンは変更していない。

**確認:**

```
$ git check-ignore -v scripts/tests/fixtures/README.md
(何も出力されない = 無視されていない)

$ git add --dry-run -A scripts/tests
add 'scripts/tests/fixtures/README.md'
add 'scripts/tests/fixtures/check1_tester_gate_mismatch/.claude/agents/sample.md'
... (26ファイル、.gitは1件も含まれない)
```

`.git`ディレクトリは存在しないので入れ子repo化は構造的に起こらず、`git add --dry-run -A`が返す26ファイル(fixture本体25 + `run-fixture-checks.sh`)がそのまま「次にcommitへ入る集合」になる。実際の`git add`は実行していない(§6の権限境界どおり、dry-runのみ)。

AC3の再現手順は`scripts/tests/fixtures/README.md`と本implement 2.6節/3.3節に明記した: `scripts/tests/fixtures/run-fixture-checks.sh`を実行するだけで、リポジトリを取得した別の人が5 fixture全部の期待exit codeとの一致を確認できる。
