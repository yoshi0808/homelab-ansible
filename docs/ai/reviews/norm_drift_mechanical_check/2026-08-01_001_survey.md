# 転記関係の棚卸し — どのドリフトが機械検査になるか

日付: 2026-08-01
作成: Coordinator(read-only調査のため直接実施。subagentは起動していない)
状態: 調査完了。実装対象の確定待ち

## 1. 背景と問い

`docs/ai/status.md` Next に「`playbooks/README.md` と現物の突合を機械的検査にする」がある。着手直前に「それならPolicyなど他にもドリフトする要素はある。READMEを優先したいのか」という問いを受けた。

**優先順位の根拠は無かった。** READMEを選んだのは status.md に書き起こしがあったからで、転記先の中で最も重要だと判断した結果ではない。そこで、実装に入る前に「値の正本が別にあるのに転記している箇所」を洗い出し、各件が機械検査になるかを判定する。

判定の目的は、作るものを決めることと同じだけ、**作ってはいけないものを決めること**にある。根拠は `docs/ai/status.md`「載せていないもの」に既にある判断 — ACL付きパスへのchmod検査を見送った理由は「**効かない検査は『掃引済み』という誤った安心を生む**」であった。同じ基準を本件にも適用する。

## 2. 判定基準

**①機械比較できる**: 両側が**同一語彙の構造化された値**であること。片方が散文なら不可。語彙が違えば、対応表が別途正本として存在しない限り不可。

**②存在だけ検査できる**: 集合の包含は比較できるが、値の一致は比較できないもの。**PASS/FAILにはできず、候補の提示に留まる。**

**③検査不能**: 上記いずれも成立しないもの。ここに無理に検査を書くと偽陽性を生み、「検査があるから見なくていい」という誤った安心だけが残る。

## 3. 調査結果

| # | 転記関係 | 判定 | 現状のドリフト |
|---|---|---|---|
| 1 | playbook `# tester-gate:` ↔ `playbooks/README.md` 表の4列目 | **①** | **0件**(48/48一致) |
| 2 | `.claude/agents/<role>.md` frontmatter の `model:` / `effort:` ↔ `docs/ai/role-routing-index.md`「モデル・effort配分」表 | **①** | **0件**(4/4一致) |
| 3 | Markdown内部リンク ↔ リンク先ファイルの実在 | **①**(規範層に限る) | 規範層 **0件**。`docs/ai/reviews/` 配下に13件 |
| 4 | `playbooks/proxmox_*.yml` の集合 ↔ `proxmox_patch_policy.md` SB-020 安全度表 | **②** | **3件未掲載** |

### 3.1 ①と判定したもの

**#1 playbook ↔ README。** README側は tester-gate の5値をそのまま転記しており、語彙が同一である。48本すべてでヘッダと一致し、README側に実在しないplaybookの行も無い。**2026-08-01に12本の区分不一致を修正した直後なので、現在クリーンであること自体は再発防止の根拠にならない** — 根拠は「12本が実際にドリフトし、案件クローズにもAuditorにも捕まらなかった」ことの側にある。

**#2 agent定義 ↔ routing index。** `role-routing-index.md`「Agent定義との関係」が「役割の規範を agent定義へ複製しない。**正本が二重化するとドリフトする**」と明記している当の箇所であり、model/effort だけは意図的に二重化されている。frontmatter(YAML)と表(Markdown)の両方が構造化された値なので比較できる。現状は auditor=sonnet/medium、implementer=sonnet/high、reviewer=sonnet/medium、tester=sonnet/medium で表と完全一致。

**#3 内部リンク。** リポジトリ内の全Markdownを走査し、**内部リンク103本**(ファイル数ではなくリンクの本数。`docs/ai/reviews/` を含む)を解決した。規範層(`docs/ai/` の policies / context / roles / memory、`skills/`、`CLAUDE.md`、`core.md`)には**壊れたリンクが1件も無い**。検出13件の内訳は、`docs/ai/reviews/` 配下の過去記録が11件、残る2件は本文中の `...` や `file.yml` という説明用プレースホルダ(偽陽性)。

> **`docs/ai/reviews/` を検査対象に含めてはならない。** あそこは案件当時の記録であり、その後ファイルが移動・削除されても記録の側は正しい。含めると11件が恒久的な偽陽性になり、検査そのものが無視されるようになる。

### 3.2 ②と判定したもの

**#4 SB-020 安全度表。** SB-020 は playbook を **safe / semi-safe / controlled apply / unsafe** の4値で分類するが、これは tester-gate の5値とは**語彙も軸も違う**(SB-020は「自動実行を許すか」、tester-gateは「検証時にどう実行するか」)。対応表はどこにも定義されていないため、**値の一致は比較できない**。

比較できるのは掲載の有無だけである。表に無い proxmox playbook は次の3本:

- `proxmox_hw_check.yml` — **SB-095 が read-only点検として名指ししている**ので、このPolicyのscope内であることは確定。掲載漏れ。
- `proxmox_backup_restore_verify.yml` — 専用の `proxmox_backup_restore_verify_policy.md` を持つ。patch policy のscopeに入るべきかは不明。
- `proxmox_snapshot_check.yml` — 同じくscope不明。

**`docs/ai/status.md` の該当行は `proxmox_hw_check.yml` 1本しか挙げていないが、実際は3本である。**

scopeの判定はPolicy本文の解釈を要し、機械には決められない。したがってこれを検査(PASS/FAIL)にはしない。

### 3.3 ③と判定したもの — 作らないと決めたもの

**#5 Policy ID の参照 ↔ 定義。これは作ってはならない。**

Policy群には `<!-- SB-020 -->` 形式の定義が616個ある。素朴に「本文中の `SB-nnn` で定義が無いもの」を検出すると、規範層で8件が挙がる(`SB-023` / `SB-049` / `SB-083` / `SB-084` / `SB-086` / `LOG-002` / `UV-083` / `BRV-070`)。

**8件すべてが偽陽性である。** いずれも各Policyの**変更履歴の行**にのみ現れ、しかも「退番: SB-049 / SB-083 / SB-084 / SB-086(**再利用しない**)」という形で、**廃止した事実を意図的に記録している**。定義が無いのが正しい状態であり、検査が「直せ」と促す先は何も無い。

さらに、この罠は既に明文化されていた — `skills/document-norm-review/SKILL.md` L98:

> **構造化マーカーはマーカー形式で数える**。`grep -c "SB-049"`ではなく`<!-- SB-049 -->`。変更履歴での「言及」と規範としての「実体」を数の上で混同しない。

偽陽性を消すには「変更履歴の節を除外する」ことになるが、それは節の構造への依存を増やしたうえで、**現に検出すべきドリフトが1件も無い**検査を残すことになる。得るものが無い。

なお、`ADR-nnn` は `docs/ai/adr/<nnn>-*.md` というファイル名が定義であり、`<!-- -->` マーカーとは別の名前空間である。`SHA-256` に至っては正規表現の誤爆であった。**素朴な実装の偽陽性率は、この対象では実質100%である。**

**#6 保護対象ホストの二重記載。** `.claude/settings.json` の `autoMode` は保護対象(pve1 / pve2 / authy / sophos-fw / UniFi機器)を**英語の散文の中**で述べ、`docs/ai/roles/coordinator.md` は同じ集合を日本語の表と箇条書きで述べる。`core.md` と `coordinator.md` の双方が「片方だけ変えるとドリフトする」と警告している既知の二重化だが、**両側とも散文であり集合を機械抽出できない**。

これは検査で塞ぐ対象ではなく、**構造で直す対象**である(どちらか一方を機械可読な値のリストにし、他方はそれを参照する)。ただし `settings.json` は harness が解釈する形式に縛られ、自由なキーを足せるかは未確認である。**本調査では方向の指摘に留め、案件化しない。**

## 4. 結論

**作るのは①の3件のみ。1本のスクリプトにまとめる。**

- 対象: #1 playbook↔README、#2 agent定義↔routing index、#3 内部リンク(規範層限定)
- 形式: Python3、標準ライブラリのみ。`scripts/git-pre-commit-check.sh` から呼ぶ
- **偽陽性ゼロで運用できることが前提**。#3 は `docs/ai/reviews/` を除外して初めて成立する

**作らないもの: #5、#6。** 理由は本文の通りで、再提案されたときのために `docs/ai/status.md`「載せていないもの」へ1行残す。

**検査にしないが対処が要るもの: #4。** SB-020の3本の掲載可否はPolicy本文の解釈でありYoshinobuの領域。status.md の該当行を「1本」から「3本」へ改める。

## 5. この結論の限界(未解決事項)

- **①の3件はすべて現在ドリフトが0である。** つまりこの実装は**今あるバグを1件も直さない**。価値は再発防止に限られる。それでも作る根拠は、#1が実際に12本ドリフトした実績を持ち、それが案件クローズでもAuditorでも捕まらなかったことにある。#2 と #3 は「同じ形をしていて安いから同居させる」以上の根拠は無い。
- **転記関係の洗い出しが網羅である保証は無い。** 内部リンク・Policy ID・安全区分・model/effort・保護対象ホストという、機械的に列挙できる形をしたものから当たった。散文の中だけに存在する二重化(例: 手順の説明が2箇所にある)は本調査では見つけられない。
- **#4 のscope判定を先送りしている。** `proxmox_backup_restore_verify.yml` と `proxmox_snapshot_check.yml` が patch policy のscopeに入るかは未判断のままである。
