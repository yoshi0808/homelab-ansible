## `git ls-files`グロブがスラッシュを跨ぐ性質 — check1/check2への実害の判断

Coordinatorの観測(`docs/ai/*.md`が1025件、`playbooks/*.yml`も理論上同じ性質)を実行して裏取りした:

```
$ git ls-files 'playbooks/*.yml' | wc -l   # 48
$ find playbooks -name '*.yml' | wc -l     # 48
$ find playbooks -mindepth 1 -maxdepth 1 -type d   # (該当ディレクトリ0件)
$ git ls-files '.claude/agents/*.md' | wc -l   # 4、.claude/agentsにサブディレクトリ無し
```

さらに、git pathspecの`*`が`/`を跨いでマッチすることを最小構成で再現した(`git ls-files 'a/*.yml'`が`a/x.yml`と`a/b/y.yml`の両方を返すことを確認)。

**判断: check1・check2には現時点で実害が無く、将来的にも実害の質がcheck3とは異なる。**

- `playbooks/`・`.claude/agents/`のいずれも現在サブディレクトリを持たないため、今この瞬間の`compared`件数(96/8)には影響していない。
- 将来サブディレクトリが追加された場合、`git ls-files`のグロブはそのネストしたファイルも拾う。しかしcheck1側の判定ロジックは「拾われた全playbookが`playbooks/README.md`のカタログに載っているか」を見るため、ネストした新規playbookがカタログ未掲載であれば**「catalogに載っていない」という正しい指摘**が出るだけである。check2も同様に「対応する行が無い」という正しい指摘になる。どちらも**構造的に「直しようがない指摘」にはならない**(カタログに追記すれば解消する)。
- これはcheck3の欠陥(finding #1、解消済み)とは非対称である。check3の問題は「対象そのものに含めるべきでないファイル(fixtureの意図的に壊れたリンク)を含めてしまい、直す手段が無い」という構造だったが、check1/check2のグロブが広がっても「対象に含めるべきファイルが増えて、それに対する正しい指摘が増える」だけであり、偽陽性ではなく真陽性が増える方向にしか作用しない。
- 結論として、Coordinatorの「現時点で実害無し」という見立てに同意する。ただし可読性の観点では、`_is_normative_markdown`がスラッシュ跨ぎ問題を明示的に回避した設計になっているのに対し、check1/check2は素朴な`git ls-files`パターンのままという非対称は残る。指摘としてはinformationalに留める。
