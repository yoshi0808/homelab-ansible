前回の must-fix 3件と suggestion 2件は反映されている。quoryの予約処理は初回、

## 前回指摘の確認

### 1. 初回unit不在

**解消。** timer/service両方の `systemctl show` が `failed_when: false` となり、
non-zeroまたは空stdoutはinactiveとして扱う。初回はcleanupをbest-effortで通過し、flag作成、
systemd-run、reservation confirmed更新へ進む。

### 2. timer/service判定

**解消。** 待機中予約の主信号である `.timer` と、発火中のfallbackとなる `.service` の
両ActiveStateを取得する。いずれかが active/activating/reloadingなら既存予約を維持し、
systemd-runを再実行しないため、60秒のカウントダウンを後ろへずらさない。

### 3. flag cleanup分岐

**解消。** reservation confirmedは既存有効予約検出時、または新規systemd-run成功後だけ
trueになる。rescueではfalseの場合だけflagを削除し、後日の無関係なrebootによる誤発火を
防ぐ。trueの場合は実在する予約に対応するflagを維持する。

### 4. QDevice再評価

**解消。** chronyの最大待機後にQDevice、続いてSemaphoreをbounded retryで確認する。
boot初期のQDevice値をchrony待機中ずっと保持する問題はなくなった。

### 5. 集約anchor

**解消。** 実行hostは静的な `ansible_play_hosts_all | first` ではなく、この時点の生存host
集合 `ansible_play_hosts | first` から選ぶ。一方、集約ループはallを維持するので、脱落hostも
HEALTHCHECK_FAILEDとしてrollupへ含める。

## quory予約シナリオ確認

| シナリオ | 判定・処理 | flag最終状態 |
| --- | --- | --- |
| 初回（両unit未存在） | inactive扱い、cleanup no-op、新規systemd-run | 成功時あり。失敗時rescueで削除 |
| 予約後60秒以内の再実行 | timer activeを検出、既存予約を維持、新規予約なし | refreshして維持 |
| timer発火後/service実行中 | service activeを検出、既存実行を維持 | 維持 |
| failed/inactive残骸 | stop/reset-failed後、固定名で新規予約 | 成功時あり。失敗時削除 |
| flag作成後systemd-run失敗 | confirmed=falseのままrescue | 削除 |
| 新規予約成功後の後続失敗 | confirmed=trueでrescue | 維持 |
| 既存予約検出後の後続失敗 | confirmed=trueでrescue | 維持 |

固定名を維持し、active予約を停止せず、非active残骸だけをcleanupするため、並列timerや
無期限の延期を作らない。

## timeout予算

post-reboot scriptの順序は chrony → QDevice → Semaphore → Slack。

- chronyc waitsync: 最大約50秒
- QDevice: 3回試行、5秒のsleepは試行間2回なので最大約10秒
- Semaphore: 同じく最大約10秒
- curl: 最大10秒

実質worst caseは約80秒+軽微な処理時間で、`TimeoutStartSec=120` に約40秒弱の余裕がある。
コメントの「3 tries × 5s = 15s」は安全側の概算であり、unit timeout超過を招く誤差ではない。
