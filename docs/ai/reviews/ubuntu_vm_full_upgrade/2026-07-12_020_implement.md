## 実装概要

019 の実施項目4点をすべて実装した。

1. **phasing 保留の構造化と表示**: simulate.sh が sim_out 中の
   「The following upgrades have been deferred due to phasing:」セクションを
   awk で収集し（追加 apt コマンドなし）、`phased_detail`（name のみの dict
   配列）としてJSONに追加。レポートJSONと全通知の詳細ブロックに
   `(phasing保留)` 行として表示され、件数行も
   `候補: install=N remove=M / 保留(phasing)=K` 形式に変更。
   **適用候補(install の upgrade 分) + 保留(phasing) = `apt list --upgradable`**
   の整合が取れる（受け入れ条件。下記「注意点」の新規インストールの扱い参照）。
2. **通知チャネル**: proxmox_patch_dryrun と同じ方針
   （`'alerts' if BLOCKED else 'patches'`）を採用。正常系レポート
   （NO_UPDATES / UPGRADE_READY / REVIEW_REQUIRED / MAJOR_UPGRADE_DETECTED）
   は #patches、BLOCKED のみ #alerts。既存の異常系 per-host アラート
   （healthcheck 失敗・post-reboot critical・reboot/予約失敗 rescue）は
   従来どおり #alerts で無変更。
3. **ノード単位通知**: 4ノード集約通知（anchor-host 方式の Phase 8）を廃止し、
   共通処理ブロック末尾の「Send per-node report notification」に置き換え。
   各ノードが自分の Status / status_reason / 件数 / バージョン一覧
   （適用候補 + phasing保留）を1通で送る。
4. **表示上限**: 既定 20 → **100** に引き上げ。

表示例（検証プレイブックの実出力より。per-node 通知本文）:

```text
重要コンポーネント更新あり(テスト用)
候補: install=3 remove=1 / 保留(phasing)=2
```
```text
libgcrypt20                   1.10.3-2build1 → 1.10.3-3
linux-image-6.8.0-64-generic  (新規) → 6.8.0-64.67
tzdata                        2025a-0ubuntu0.24.04 → 2025b-0ubuntu0.24.04
oldpkg                        1.0-1 (remove)
python3-software-properties   (phasing保留)
software-properties-common    (phasing保留)
```

## 変更内容の要約と設計判断

### 1. phasing 保留の収集（simulate.sh、core.md §7 維持）

- `LC_ALL=C`（既存設定）前提で deferred セクションのヘッダ行を検出し、
  後続の2スペースインデント行（折り返し・スペース区切りのパッケージ名列）を
  展開して収集。セクションは次の非インデント行で終端（fixture で複数行
  折り返し・セクション無しの両方を検証済み）。
- **バージョンは収集していない**: apt -s のこのセクションは名前のみで、
  phased パッケージには Inst 行も出ないため、sim_out 内にバージョン情報が
  存在しない。019 制約「追加の apt コマンド実行はしない」を優先し、
  保留行は名前 + `(phasing保留)` マーカーのみとした（019 除外範囲の
  「保留である事実と件数・バージョン」のうちバージョンだけ満たせない。
  必要なら別途 requirement 判断。詳細は「未対応事項」）。
- 既存の `inst`/`remv`/`inst_detail`/`remv_detail` は構造・抽出とも無変更。

### 2. phased は判定に含めない（019 制約）

classify.yml は `phased_detail` を一切参照しない（important 分類・remove
後継判定・MAJOR 件数閾値のいずれの入力にもならない）。full-upgrade が
今回適用しないものは判定対象外、という設計判断をヘッダコメントに明文化した。

### 3. per-node 通知と集約廃止（§実施3）

- 旧 Phase 8（anchor-host 方式の集約 + HEALTHCHECK_FAILED rollup +
  全体チャネル判定）を削除し、共通処理ブロック末尾で各ノードが自分の
  レポートを送る方式へ。hostvars 越しの集約複雑性（2026-07-11 review で
  anchor バグ修正まで要した部分）ごと消える。
- healthcheck 失敗ノードは従来どおり個別 #alerts アラートを送って fail する
  （無変更）。per-node レポートには到達しないため、「月次実行後に #patches に
  ないノード = #alerts か Semaphore ジョブ結果を見る」という運用になる
  （per-node 通知タスクのコメントに記載）。
- **全ノード横断サマリは残さなかった**（019 §実施3 は実装者判断)。理由:
  サマリを残すと廃止対象の hostvars 集約機構がそのまま残り簡素化にならない、
  失敗の可視性は per-host アラート + Semaphore ジョブ結果で担保済み。
- タイトルは `[ubuntu_vm_full_upgrade] dry-run (monthly) - <host>: <STATUS>`
  形式（Slack 一覧で状態が判別できる）。apply モード時は
  `apply target - <host>: <STATUS>`。

### 4. チャネル/レベルのマッピング（§実施2、proxmox_patch_dryrun 踏襲）

| Status | channel | slack_status |
| --- | --- | --- |
| BLOCKED | alerts | critical |
| MAJOR_UPGRADE_DETECTED | patches | warning |
| REVIEW_REQUIRED | patches | warning |
| NO_UPDATES | patches | info |
| UPGRADE_READY | patches | ok |

- MAJOR_UPGRADE_DETECTED を #patches にしたのは proxmox_patch_dryrun の
  実装（alerts は BLOCKED のみ）をそのまま踏襲したもの。apply 拒否
  （BLOCKED/MAJOR とも apply 不可の assert）は従来どおり有効。
- check-mode の would-apply 通知（--check + dry_run=false 時）も info →
  patches へ変更（applyサマリの --check 時の代替であり patch サイクルの
  正常系レポートのため）。
- 旧集約の「REVIEW_REQUIRED でも #alerts」挙動は廃止（019 の発端どおり、
  正常運用の月次レポートが #alerts に来ること自体が問題だった）。

### 5. 上限 100 の根拠（§実施4）

`ubuntu_vm_full_upgrade_major_total_threshold`（既定100）と揃えた。
MAJOR 閾値未満の月＝正常な月次は必ず全件が Slack 本文に載り、レポートJSONは
障害切り分け専用になる（019 の要望どおり）。100 を超えるのは
MAJOR_UPGRADE_DETECTED（apply 禁止の異常系）の領域で、そこでの切り詰めは
安全弁として妥当。閾値を調整する場合は両者を揃えることを defaults の
コメントに記した。

## 注意点

- **新規インストール（Inst 行で旧バージョン無し）は `apt list --upgradable`
  に現れない**ため、新規を含む月は install 件数 > upgradable 側になり得る。
  受け入れ条件の厳密な等式は「install のうち upgrade 分 + phased =
  upgradable」であり、詳細ブロックでは新規が `(新規)` と明示されるので
  照合時に区別できる。018 T-4 の monnie ケース（新規0件）では
  install 23 + phased 2 = 25 で一致する想定。
- 集約通知の廃止により、`ubuntu_vm_full_upgrade_results` /
  `..._notify_channel` / `..._notify_status` の各 fact と anchor-host 方式は
  コードから消えた（経緯コメントも含め削除。履歴は git と本シリーズの
  implement/review に残る）。
- per-node 通知は共通処理ブロック内（`check_mode: false` 継承）のため、
  従来の集約通知と同じく --check でも実送信される（check-mode-native 設計
  どおり。tester は従来どおり skip_notifications で抑止可能）。
- tester-gate 分類（check-mode-native）・Semaphore テンプレート・実行経路・
  IP/秘密情報の扱いに変更なし。
