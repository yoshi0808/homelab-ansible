## 結論

**再レビュー合格。must-fix / suggestion / nit の指摘なし。**

絶対パス `include_tasks` から `include_role` + `tasks_from: check` への変更4箇所は
適切である。元roleのfiles lookup contextを復元しながら、check.ymlだけを実行し、
main.yml側のreport保存・Slack通知・critical failは実行しない。取り込まれるdefaultsにも
呼出し元roleとの衝突は見当たらない。

## 確認結果

### 1. 変更4箇所

以下はすべて正しい形になっている。

- pre-upgrade authy: `include_role: radius_healthcheck`, `tasks_from: check`
- pre-upgrade monnie: `include_role: monitoring_healthcheck`, `tasks_from: check`
- post-upgrade authy: 同上
- post-upgrade monnie: 同上

各includeには従来と同じinventory_hostname条件があり、authyでradius、monnieでmonitoring
だけが実行される。post-reboot側もreboot block内にあり、既存のrescue境界を維持する。

`include_role` は対象roleのcontextでtaskを処理するため、check.yml内のbare sourceは次へ
正しく解決される。

- `radius-healthcheck.sh` → `roles/radius_healthcheck/files/`
- `monitoring-healthcheck.sh` → `roles/monitoring_healthcheck/files/`

testerが観測したcaller role側files検索によるlookup failureを解消する方式として妥当である。

### 2. check.yml限定とmain.yml副作用

`tasks_from: check` はroleのtask入口を `tasks/check.yml` に変更する。したがって
`tasks/main.yml` は暗黙実行されない。

両check.ymlが行う処理:

- healthcheck script配置
- script実行とJSON parse
- critical/warning分類
- report fact構築
- debug summary

両main.ymlだけが行う処理:

- localhost report directory/file保存
- Slack通知
- critical時の最終fail

新しいinclude_role経路ではmain.yml側の3副作用は走らない。ubuntu_vm_full_upgrade側が
critical集約・通知・failを担当する既存の責務分離を維持する。

なおcheck.yml内には「空出力ならfail」が残る。これは収集自体が成立しない場合のtask errorで
あり、main.ymlのhealth判定に基づく最終failとは別物で、従来設計どおりである。

### 3. defaultsと変数scope

include_roleにより対象roleのdefaultsもrole実行中に利用可能になる。

- radius: `radius_healthcheck_report_dir`
- monitoring: `monitoring_healthcheck_report_dir`

どちらもrole固有prefixを持ち、ubuntu_vm_full_upgradeの変数と衝突しない。またcheck.ymlは
これらreport directory defaultsを参照しないため、今回の限定呼出しに実質的な影響はない。

check.ymlがexportするfacts/register値（`radius_*`, `monitoring_*`, `healthcheck_raw`）は
後続の呼出し元taskが参照できる。authy/monnieは相互排他的に片方のroleだけを実行するため、
共通名 `healthcheck_raw` のhost内衝突もない。post-reboot時の再実行は同じ種類の最新結果へ
意図的に更新される。

`include_role` のdefault `public: false` によりrole vars/defaultsを後続へ公開することには
依存しておらず、必要な出力はcheck.ymlの `set_fact` / `register` でhost factsとして残る。
