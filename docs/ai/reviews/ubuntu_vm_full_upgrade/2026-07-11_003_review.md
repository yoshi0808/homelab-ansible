## 結論

**要修正（must-fix 5件、suggestion 2件）。**

5区分の大枠、重要removeのBLOCKED優先、主力プロダクトのノード別表示、quoryの3分類、
確認文字列、check-modeの破壊的include境界、radius healthcheck抽出は概ね要求に沿う。
一方、更新計画の信頼性、recovery mute対象、quory再起動予約の再実行性、boot直後確認の
待機、Ansibleのapt/pip管理明示に不足がある。

## 指摘

### 1. [must-fix] `apt-get update` 失敗を Status が無視し、古いindexで applyを許可し得る

対象:

- `roles/ubuntu_vm_full_upgrade/files/ubuntu-full-upgrade-simulate.sh:11-18`
- `roles/ubuntu_vm_full_upgrade/tasks/classify.yml` の `Determine Status`

収集JSONには `apt_update.rc` があるが、BLOCKED判定は `apt_check.rc` と
`simulation.rc` しか見ていない。updateが失敗しても既存cacheに対するcheck/simulationが
成功すれば、`UPGRADE_READY` / `REVIEW_REQUIRED` となり、手動applyまで進める。
この場合、月次通知もapply直前再判定も最新repository状態を保証しない。

共通処理§5.1の先頭にapt updateを置く目的と、Proxmox policyの「計画を信用できない場合は
BLOCKED」に照らし、`apt_update.rc != 0` もBLOCKED条件・reasonに含めること。

### 2. [must-fix] recovery muteをansy/quoryにも作成している

対象: `roles/ubuntu_vm_full_upgrade/tasks/apply.yml:14-19`

apply.ymlは4ノード共通で無条件に `recovery_mute_target: inventory_hostname` を設定する。
しかし autonomous recoveryのmute対象は authy / monnie / sophos-fw であり、ansy/quoryは
復旧対象ではない。現状は `/var/lib/homelab-recovery/mute/ansy.json` と
`quory.json` という消費者のない状態を書き込み、将来対象が増えた際にも誤った運用前提を
残す。

requirement外の追加自体は、full-upgrade中のmaintainer scriptによるサービスrestartを
考えると authy/monnieには妥当である。includeを `inventory_hostname in ['authy','monnie']`
に限定すること。sophos-fwは本playbook対象外なので設定しない。

### 3. [must-fix] quoryの固定 `systemd-run --unit` が既存unitとの衝突で再実行不能になる

対象: `roles/ubuntu_vm_full_upgrade/tasks/reboot_quory.yml:41-49`

`--unit=ubuntu-vm-full-upgrade-reboot` を固定しているため、同名transient timer/serviceが
active、waiting、failed、またはまだsystemdに残っている状態で再実行すると
`systemd-run` が「unit already exists」で失敗する。典型例はreboot予約後60秒以内の
Semaphore再実行、予約後の手動キャンセル、予約コマンドの部分失敗である。

既存unitの状態を事前収集し、すでに有効な同一予約なら冪等に扱うか、安全に停止・reset
して再作成するかを明示すること。単純にランダム名へ変えるだけでは複数reboot予約を
並存させるので不可。flag作成・予約・通知の部分失敗時に残る状態も含め、再実行時の
一意性を保証する必要がある。

### 4. [must-fix] post-reboot checkがSemaphore/QDeviceの起動完了を待たず誤検知する

対象:

- `scripts/quory_post_upgrade_check/quory-post-upgrade-check.service:1-12`
- `scripts/quory_post_upgrade_check/quory-post-upgrade-check.sh:50-68`

unitは `network-online.target` の後に起動するだけで、corosync-qdeviceとSemaphoreの
起動順序・ready状態を待たない。scriptも両サービスに対して `systemctl is-active` を
1回実行するだけなので、通常のboot競合で一時的なinactive/activatingをCRITICALと判定し、
flagを削除して再試行しない。chronyだけは `waitsync` により最大約100秒待つが、chrony
待機より前に取得したqdevice_statusは後から再評価されない。

サービスunitへの `After=` だけではアプリケーションreadyまで保証しないため、少なくとも
Semaphore/QDeviceも期限付きリトライでactiveを待つこと。最終判定は各待機後の最新値で
行い、全体が `TimeoutStartSec=120` に収まるようtimeout予算を設計すること。

### 5. [must-fix] ansy/quoryのAnsible管理方式（apt/pip）の明示要件を満たしていない

対象:

- `roles/ubuntu_vm_full_upgrade/defaults/main.yml:68-83`
- `roles/ubuntu_vm_full_upgrade/tasks/classify.yml` の product impact
- `roles/ubuntu_vm_full_upgrade/tasks/main.yml` の Slack message

requirement §5.2は ansy/quoryについて、ansibleがpip管理ならapt判定対象外である旨を
レポートへ明記するよう求めている。現在は `ansible.*` をapt候補とmatchするだけで、
該当なしの場合も単に「該当なし」と表示する。これは「apt候補を確認したが影響なし」と
「Ansible自体がpip管理なので対象外」を区別できない。

実ホストでapt管理かを収集するか、少なくとも管理方式をhost_vars等の明示設定として持ち、
ansy/quoryそれぞれのレポートとSlackに「apt管理: 判定対象」または
「pip管理: apt full-upgrade判定対象外」を表示すること。未確認なら「管理方式未確認」と
し、該当なしへ丸めないこと。

## suggestion

### 6. [suggestion] quoryの通知→正常終了→reboot発火の時間保証を明文化・強化する

対象: `roles/ubuntu_vm_full_upgrade/tasks/reboot_quory.yml:41-67`

実装順はflag作成→予約→Slack通知でrequirement §7.2に沿うが、60秒は
common_slackの応答時間とAnsible recap/Semaphore job確定時間より必ず長いという機械的な
保証ではない。Slack処理が長引けばplaybook終了前に発火し得る。

予約タスクをquory処理の最後に置く、遅延値へ十分な下限assertを設ける、Semaphore側での
実測をtest planに含める等で保証を強めること。少なくとも「通知送信後に予約」なら、
通知の遅延がrebootまでの猶予を消費しない。予約失敗時に「reboot scheduled」と通知済みに
なる逆順問題は、通知文を「upgrade完了、これから予約」へ分ける等の設計が必要になるため、
指摘3の再実行設計と合わせて決めるとよい。

### 7. [suggestion] healthcheck失敗時の集約タスクを未定義hostvarsに耐えるようにする

対象: `roles/ubuntu_vm_full_upgrade/tasks/main.yml:156-173`

参加ホストがhealthcheckでfailするとstatus/simulationが設定されない一方、
`ubuntu_vm_full_upgrade_participates` はtrueのままである。別ホスト（通常は先頭ansy）が
aggregationへ到達すると、その失敗ホストの未定義
`ubuntu_vm_full_upgrade_status` 等を参照して二次エラーになり得る。個別healthcheck alertは
先に送るため安全停止自体はするが、月次4ノード集約の診断性が悪化する。

未収集ホストを明示的な `HEALTHCHECK_FAILED` 相当の通知項目として組み込むか、集約対象を
status定義済みに限定し、欠落ホストを別一覧で示すこと。

## 指定観点別の確認

### check-mode-nativeのゲート

- `apply.yml` のdynamic include全体が
  `ubuntu_vm_full_upgrade_is_apply_target and not ansible_check_mode` でゲートされる。
- apt full-upgrade、recovery_mute書込み、reboot、quory flag作成、systemd-run予約はすべて
  apply.yml配下なので、通常の `--check` 経路からは到達しない。
- 確認文字列、healthcheck、simulation、Status拒否はcheck modeでも実行される。
- common blockは `check_mode: false` のためscript配置、apt index更新、report保存、Slack通知
  は実変更される。これはヘッダのsemi-safe説明とは整合するが、requirement §13の
  「dry_run=trueは状態変更一切なし」という字義とは差がある。apt updateを要求する以上
  package index更新は避けられないため、policy/requirement側で「パッケージ・サービス状態を
  変更しないsemi-safe」の意味へ明確化する余地がある。

### Status/remove

- NO_UPDATES / UPGRADE_READY / REVIEW_REQUIRED / BLOCKED /
  MAJOR_UPGRADE_DETECTED の優先順と主要条件は§5.3/§5.4に概ね一致する。
- simulation失敗と重要remove+後継不明はBLOCKED。
- removeありでblockingでなければREVIEW_REQUIRED。
- successor判定は末尾version除去によるheuristicで、誤判定可能性はimplementに明記済み。
- apt update失敗漏れは指摘1。

### Slack/Vault

- 各hostの全product labelを常に出し、空の場合は「該当なし」とする。
- quoryはAnsible実行基盤/QDevice/NTP基準を個別表示する。
- main notificationは既存common_slackを使い、Vault済み
  `inventories/vars/slack.yml` を参照するため既存方針と整合する。
- post-reboot scriptのsecretはrepositoryへ含まれず、root:root 0600のlocal fileを手動配置する
  指示で、requirement §12が明示的に許す案の範囲内。リポジトリ内に実webhook値はない。
- ansy/quoryのapt/pip明示だけ不足（指摘5）。

### recovery_mute

authy/monnieへの追加はmaintainer scriptのrestartによる誤復旧を避ける点で妥当。
ansy/quoryへの設定は対象外（指摘2）。sophos-fwには本playbookから設定されない。

### quory delayed reboot

- monotonic delayの採用、flag mode 0644（非secret）、予約後のsummary、Ansible内で復帰を
  待たない構造は要求に沿う。
- 固定unit再実行衝突は指摘3、終了順序の厳密保証は指摘6。

### radius_healthcheck抽出

旧main.ymlの収集・parse・classify・report・debug・notify・critical failは、新check.ymlと
薄いmain.ymlの合成で維持されている。既存radius_healthcheck role呼出しの機能退行は
静的には見当たらない。新roleからcheck.ymlだけを呼ぶことで通知/report/failの重複も避ける。

### 確認文字列

apply対象hostで、未指定は空文字、不一致もassert failとなり、共通処理前に停止する。
Statusの事前申告には使っておらずrequirement §4/§6と一致する。

### post-reboot script

- `chronyc waitsync 20 0.5 0 5` は固定sleepではなく内部retry+timeoutを持つ。
- unit全体のTimeoutStartSecは120秒、curlは10秒timeout。
- secret配置指示はroot:root 0600、実secretは未収録。
- Semaphore/QDevice待機不足は指摘4。
