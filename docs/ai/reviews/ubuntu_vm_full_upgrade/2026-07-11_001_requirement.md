# ubuntu_vm_full_upgrade 要求仕様

作成日: 2026-07-11
版: v1.0
対象: Ubuntu VM/ノード(ansy / monnie / authy / quory)の月次full-upgrade判定・通知・手動適用

参照:

- docs/ai/prompts/core.md
- docs/ai/prompts/ubuntu_vm_patch_policy.md（既存のsecurity/ESM自動適用・reboot方針との関係）
- docs/ai/prompts/proxmox_patch_policy.md（Status/重要コンポーネント判定の設計を踏襲）
- docs/ai/prompts/cert_renew_policy.md（quory上でのSemaphore/quory固有処理の分離前例）

---

## 1. 目的

Ubuntu Pro + unattended-upgradesはsecurity/ESM/ESM Appsパッチのみを自動適用しており、
main/updates/universe等の非securityパッケージは対象外のまま溜まっていく。

本仕組みは、この非security領域を含む`apt full-upgrade`の対象パッケージを月次で
洗い出し、重要コンポーネントの有無やremoveの有無から適用可否をStatus判定して通知する。
実際の適用(apply)は自動化せず、常に手動判断・手動実行とする。

---

## 2. 対象ホスト・実行元

| ホスト   | 役割                        | 実行元(月次dry-run)              | 実行元(手動apply)           |
| -------- | --------------------------- | -------------------------------- | --------------------------- |
| `ansy`   | Ansible開発環境             | Semaphore(quory)                 | Semaphore（本番）           |
| `monnie` | 監視基盤                    | Semaphore(quory)                 | Semaphore（本番）           |
| `authy`  | RADIUS/FreeRADIUS           | Semaphore(quory)                 | Semaphore（本番）           |
| `quory`  | 本番Ansible実行基盤/QDevice | Semaphore(quory、自己対象を含む) | Semaphore（本番。§7.2参照） |

本番の手動applyは原則としてSemaphore経由のみとする。ansyからの`ansible-playbook`
CLI直接実行は開発・動作確認用途に限定し、本番ノードへの実適用には使わない。

月次dry-runはSemaphore(quory上で稼働)から4ノード一括実行する。dry-runは状態変更・
rebootを一切伴わないため、quory自身が対象に含まれてもSemaphoreプロセスは中断されない。

---

## 3. 作成・更新対象ファイル

- `playbooks/ubuntu_vm_full_upgrade.yml`（新規。ansy/monnie/authy/quory共通の入口）
- `roles/ubuntu_vm_full_upgrade/`（新規role。Phase構成はimplement時にCCが設計）
- quory専用のpost-reboot healthcheck一式（新規、Ansible管理外。§7参照）
  - 配置場所・ファイル名はimplement時にCCが提案し、requirementでは固定しない
- 既存`roles/ubuntu_nightly`等にあるauthy/monnieのpost-reboot service確認ロジックが
  流用できる場合は共通化を検討する（新規roleに重複実装しない）

## 4. 引数と実行モード

playbookは以下2つの引数を取る。

- `dry_run`（true/false）
- `node`（対象ノード名。dry_run=falseの場合は単一ノード指定必須）

| モード       | dry_run | node                                 | 実行契機                                   |
| ------------ | ------- | ------------------------------------ | ------------------------------------------ |
| 月次自動判定 | true    | 全ノード(ansy, monnie, authy, quory) | Semaphore月次スケジュール                  |
| 手動apply    | false   | 単一ノード指定                       | ユーザーが都度手動実行。スケジュールしない |

playbookの引数はこの2つのみとする。手動apply時に別途要求する確認文字列
（§6参照）は、Status（`UPGRADE_READY`/`REVIEW_REQUIRED`等）をユーザーが
事前申告するための引数ではなく、誤実行防止のための安全装置である。
Statusはapply実行時にplaybookがsimulationを再実行して都度自動判定するため、
「どのStatusを想定してapplyするか」をユーザー側の引数として持たせる設計は
採らない（Proxmoxの`MAINTENANCE_REQUIRED`手動applyのような対象Status指定は
本仕組みでは行わない）。

## 5. 確認項目・実施項目

### 5.1 共通処理(dry_run true/false 両方)

1. 対象ノードのhealthcheck（既存healthcheck roleがあれば流用）
2. `apt-get update`
3. `apt-get check`
4. `apt-get -s full-upgrade`によるsimulation
5. 重要コンポーネント判定（§5.2）
6. remove判定（§5.3）
7. Status確定（§5.4）
8. Slack通知（ノード別の重要モジュールへの言及を含む）

### 5.2 重要コンポーネント判定

共通リスト（全ノード対象）:

```
kernel(linux-image-*, linux-generic)
systemd
udev
netplan.io / network-manager
openssh-server / openssh-client
sudo
libc6
```

ノード別追加リスト（そのノードの主力プロダクトに対する依存パッケージ）:

| ノード | 主力プロダクト                          | 追加対象                                                     |
| ------ | --------------------------------------- | ------------------------------------------------------------ |
| authy  | FreeRADIUS/WPA3認証基盤                 | freeradius*, libssl*, openssl, sssd*, wpa*関連               |
| monnie | Prometheus/Grafana/Loki監視基盤         | prometheus*, grafana*, loki*, docker*(使用時)                |
| ansy   | Ansible開発環境                         | python3*, ansible*(apt管理の場合。pip管理ならこの判定対象外である旨をレポートに明記) |
| quory  | 本番Ansible実行基盤 / QDevice / NTP基準 | python3*, ansible*(同上), chrony, ntp関連, corosync-qdevice, corosync |

具体的なパッケージ名リストの最終確定・拡張はimplement時にCCが対象ホストの
実インストール状況を確認して行ってよい。

### 5.2.1 レポートでの主力プロダクト依存の明示（重要）

Status判定に使うだけでなく、Slack通知（dry_run=true/false問わず）には
**ノードごとの主力プロダクトへの影響有無を明示的に記載する**。

- 該当パッケージが更新候補に含まれる場合: 対象パッケージ名と、それが
  どの主力プロダクトに関連するか（例:「freeradius-common → FreeRADIUS」）を
  一覧で示す
- 該当パッケージが更新候補に含まれない場合でも「該当なし」と明記する
  （「何も書かれていない」と「確認したが影響なし」を区別できるようにする）
- quoryは主力プロダクトが複数（Ansible実行基盤 / QDevice / NTP基準）ある
  ため、この3つを個別に分けて記載する（ひとつにまとめない）

これにより、通知を見た時点で「今回のupgradeでこのノードの主力サービスに
触るパッケージが含まれているか」が一目でわかる状態にする。

### 5.3 remove判定

Proxmox patch policyの考え方を踏襲する。

- simulation成功 + remove対象に後継/置換と見えるinstallが同時にある → `REVIEW_REQUIRED`
- simulation失敗、または重要コンポーネントがremoveされ後継が確認できない → `BLOCKED`

### 5.4 Status区分

| Status                   | 条件                                                         | 意味                                                  |
| ------------------------ | ------------------------------------------------------------ | ----------------------------------------------------- |
| `NO_UPDATES`             | 更新候補なし                                                 | 何もしない                                            |
| `UPGRADE_READY`          | 重要コンポーネント該当なし、removeなし、simulation成功       | 手動apply可（自動適用はしない）                       |
| `REVIEW_REQUIRED`        | 重要コンポーネント更新あり、またはremoveあり(後継確認できる) | 人間判断のうえ手動apply                               |
| `BLOCKED`                | simulation失敗、重要コンポーネントremoveで後継不明           | apply禁止（dry_run=falseでも拒否）                    |
| `MAJOR_UPGRADE_DETECTED` | codename変化疑い、大量install/remove(閾値はimplement時にCCが提案) | 通常運用から除外。release upgrade検討は別プロジェクト |

Statusに関わらず、dry_run=trueは常にread-onlyで通知のみ。実適用はdry_run=falseのみ。

## 6. 手動apply(dry_run=false)のフロー

1. 確認文字列チェック（未指定/不一致なら即停止。Proxmoxの`MAINTENANCE_REQUIRED`手動apply
   と同じパターン）
2. §5.1の共通処理を実行し、Statusを再確定
3. `BLOCKED` / `MAJOR_UPGRADE_DETECTED`の場合はここで停止（apply拒否）
4. `apt full-upgrade`を実行
5. reboot要否判定
6. reboot要否に応じてノード種別ごとに分岐（§7参照）
7. summary通知（apply結果 + reboot有無 + healthcheck結果）

`--check`(dry_run=true)では確認文字列は不要（状態変更を伴わないため）。

---

## 7. reboot処理（ノード種別で分岐）

### 7.1 ansy / monnie / authy

同一Ansibleセッション内でreboot〜post-healthcheckまで完結させる。

- reboot実行
- SSH/API復帰待ち
- post-healthcheck
  - authy: freeradius状態 + 1812/udp・1813/udp Listen確認
  - monnie: prometheus(9090)・grafana(3000)・loki(3100) Listen確認
  - ansy: SSH復帰 + uptime確認のみ

既存`ubuntu_nightly.yml`のservice確認ロジックがあれば共通role化して流用する。

### 7.2 quory（特殊対応）

quoryはSemaphore自身が稼働するノードだが、今回の設計では
「playbookが完全に正常終了した後にrebootを発火させる」ことで、Semaphore
job自体の中断を回避する。したがってquory対象のapplyもSemaphore経由で実行してよい
（cert_renew_quory.ymlのような実行経路分離は不要）。

処理内容:

1. `apt full-upgrade`完了後、reboot-required判定
2. reboot-required trueの場合、`systemd-run`等でワンショットのreboot予約を
   60秒後に仕込む（コマンド詳細はimplement時にCCが実装）
3. full-upgrade起因のrebootであることを示すフラグファイルを作成する
4. playbookはここで（reboot発火前に）summary通知を送り、正常終了する
5. playbook自体はreboot発火後の状態を待たない・確認しない

**post-reboot確認（Ansible管理外）**

quoryはSemaphore/Ansibleセッションが再起動でリセットされるため、reboot後の
確認はAnsible経由ではなくquoryローカルのsystemd unitで完結させる。

- boot時に起動するsystemd unit（`network-online.target`依存）
- フラグファイルが存在する場合のみ実行（full-upgrade起因のrebootのみ対象。
  他要因でのrebootでは発火しない）
- 確認項目:
  - corosync-qdevice（QDevice、Proxmoxクラスタから見たquoryの健全性）
  - chrony同期状態（`chronyc waitsync`等でリトライ+タイムアウト。固定sleep待機は
    使わない。quoryはNTP基準ノードのため必須項目）
  - Semaphore稼働状態
- 確認完了後、Slack webhookへ直接通知（Ansible/Ansible変数ではなくVault等から
  webhook URLを読む。実装方式はCCに委ねる）
- 確認完了後、フラグファイルを削除する

このpost-reboot check一式はAnsible playbookの管理対象外（Ansibleでデプロイする
かどうかも含め、初回実装の範囲外とする。§9参照）。

## 8. 制約

- IPリテラルをファイルに書かない（core.md §3。名前解決方針に従う）
- Ansible playbook内でgit pullしない（自己更新問題を避ける。core.md §11）
- 部分適用はしない（重要コンポーネント以外だけ先に当てる、等の運用はしない）
- 確認文字列は手動apply(dry_run=false)時のみ要求する
- `BLOCKED` / `MAJOR_UPGRADE_DETECTED`はdry_run=falseでも問答無用でapply拒否
- quoryのreboot予約〜playbook終了までの間にreboot が発火してはならない
  （60秒等、余裕を持った遅延にする。厳密な秒数はimplement時にCCが調整してよい）
- quory post-reboot checkはchrony確認にリトライ+タイムアウトを持たせる。
  固定sleep待機のみで済ませない
- 秘密情報（Slack webhook URL等）はVault管理とし、平文でファイルに書かない

## 9. 初回実装で含める範囲

- `ubuntu_vm_full_upgrade.yml`（dry_run/node引数、4ノード共通）
- Status判定ロジック（5区分）
- 重要コンポーネント判定（共通リスト+ノード別リスト）
- remove判定
- Slack通知（dry-run結果、ノード別の重要モジュール言及）
- 手動apply時の確認文字列チェック
- ansy/monnie/authyの同一セッションreboot+post-healthcheck
- quoryのreboot予約（systemd-run等での遅延reboot）+ フラグファイル作成
- quory post-reboot checkスクリプト + systemd unit一式の作成
  （Ansibleでのデプロイ自動化は範囲外。ファイル一式の作成・配置手順の提示まで）

## 10. 初回実装では除外する範囲

- `MAJOR_UPGRADE_DETECTED`時のrelease upgrade自体の実施（別プロジェクト）
- Codex CLIによるchangelog分類・urgency自動判定との連携（Proxmox側にある仕組みの
  横展開は次イテレーション以降で検討）
- quory post-reboot checkスクリプトのAnsible経由デプロイ自動化
- 複数ノードへの同時手動apply（1回の手動apply実行は単一ノードのみ）
- 月次dry-run結果の履歴管理・トレンド分析

---

## 11. shellとAnsible tasksの責務分離

- apt simulation実行、パッケージ一覧・changelog等の収集はshell/command
- 重要コンポーネント該当性判定、remove判定、Status確定はAnsible tasks側で行う
  （shell側で最終判定しない）
- quory post-reboot checkスクリプトはAnsible外の独立したbashスクリプトとし、
  判定〜Slack通知までスクリプト内で完結させる（Ansibleとは連携しない）

---

## 12. 秘密情報

- Slack webhook URLはAnsible Vault管理とする
- quory post-reboot checkスクリプトが読むwebhook URL等の秘密情報の格納場所は
  implement時にCCが提案する（Ansible Vault経由で配置するか、quoryのroot専用
  ファイルとして直接配置するかを含めて検討）

---

## 13. read-only / 変更系の区別

| 処理                              | 区別                                               |
| --------------------------------- | -------------------------------------------------- |
| dry_run=true（月次自動判定）      | read-only。パッケージ・サービス状態の変更・reboot一切なし（§5.1が要求する`apt-get update`によるaptインデックス更新のみ発生する。2026-07-11レビュー指摘を受けた字義の明確化） |
| dry_run=false（手動apply）        | 変更系。確認文字列必須、単一ノード指定必須         |
| quory post-reboot checkスクリプト | read-only（確認とSlack通知のみ。設定変更はしない） |
