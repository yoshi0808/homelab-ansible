## 実装概要

月次dry-run通知・applyサマリ通知・レポートJSONに、パッケージごとの
「旧 → 新」バージョン差分（npm outdated 風）を追加した。データは既存の
`apt-get -s full-upgrade` 出力（sim_out）からの抽出のみで、追加のaptコマンド
実行はない。表示フォーマットと表示上限の定義は tasks/main.yml の1箇所
（事前レンダリングした per-host fact）に集約し、3つの通知（dry-run集約・
ansy/monnie/authy applyサマリ・quory applyサマリ）が同じブロックを埋め込む。

表示例（検証プレイブックの実出力より）:

```text
libgcrypt20                   1.10.3-2build1 → 1.10.3-3
linux-image-6.8.0-64-generic  (新規) → 6.8.0-64.67
tzdata                        2025a-0ubuntu0.24.04 → 2025b-0ubuntu0.24.04
linux-image-6.8.0-60-generic  6.8.0-60.63 (remove)
oldpkg                        ? (remove)
```

## 変更内容の要約

### 1. simulate.sh（収集とJSON整形のみ、core.md §7 維持）

- 既存の `inst_names`/`remv_names`（grep -oP、名前のみ）は**一切変更していない**
  → `simulation.inst` / `simulation.remv` は従来と同一で、classify.yml の
  Status判定・important分類・remove後継判定の入力は変わらない（§制約）。
- 追加: `grep '^Inst ' | sort -u` / `grep '^Remv ' | sort -u` で生の行を
  Pythonへ渡し、正規表現で構造化。
  - `Inst <pkg> [<old>] (<new> <source> ...)` → `{"name", "old", "new"}`。
    新規インストール（`[<old>]` 無し）は `old: ""`。
  - `Remv <pkg> [<ver>]` → `{"name", "version"}`。バージョン無しは `""`。
- grep がマッチ0件でも `set -uo pipefail`（-e なし）のため従来同様に
  空文字となり、パイプライン全体は失敗しない（検証済み）。

### 2. レポートJSON（§実施2）

per-host レポートに `inst_detail` / `remv_detail` を追加。既存フィールドは
名称・内容とも不変（後方互換）。通知の「…他N件(レポートJSON参照)」の参照先。

### 3. 表示ブロックの一元化（§実施3・4・5）

`tasks/main.yml` の共通処理ブロック末尾（classify後、レポート保存前）で
per-host fact `ubuntu_vm_full_upgrade_notify_detail_block` を1回だけ組み立てる。

- 形式: Slack等幅表示のための ``` コードフェンス内に、Inst → Remv の順で
  1行ずつ。パッケージ名は表示対象内の最長名に `ljust` で揃える
  （npm outdated 風の桁揃え）。
- 上限: `ubuntu_vm_full_upgrade_notify_detail_max_lines`（既定20）。超過分は
  「…他N件(レポートJSON参照)」に切り詰め。既定20の根拠: 通常の月次は
  数十パッケージ規模（defaults の MAJOR閾値の根拠と同じ観測前提）で、
  4ノード合計でもメッセージが読める長さに収まり、それを超える月は
  レポートJSONを開いて精査すべき状況そのものであるため。
- inst エントリ（old/new キー保持）と remv エントリ（version キー保持）は
  `'new' in d` で判別。表示は `<pkg> <old> → <new>` / `<pkg> <ver> (remove)`、
  新規は `(新規) → <new>`、バージョン欠落は `?`。
- 消費側は3通知とも `{{ ...detail_block }}` の埋め込みのみで、フォーマット・
  上限のロジック重複はない。

各通知の変更:

- **dry-run集約通知**: 各ホストの「候補: install=N remove=N」行の直後に
  block を挿入。件数行・Status行・product_impact 行は不変（§制約の
  「通知の全体構造は変えない」）。NO_UPDATES / HEALTHCHECK_FAILED ホストは
  block が空のため従来と同一表示。
- **applyサマリ（reboot_local.yml / reboot_quory.yml）**: 
  「適用: install=N remove=N (直前のsimulation結果)」行 + block を追加。
  データは同一実行セッションの Phase 1-8 で必ず先行して作られる
  `ubuntu_vm_full_upgrade_sim` と上記 fact の再利用のみで、apply後の
  追加収集はない（§実施5の指定どおり）。

### 4. 実装中に発見した check_mode/templating 系の落とし穴（新規知見）

`set_fact` の値 `"{{ _block | trim }}"` で、`_block` テンプレートの出力が
空（候補0件）のとき、native templating が空出力を `None` に解決し、
`trim` がそれを文字列化して **リテラル `"None"` が通知に出る**不具合が
検証プレイブックで検出された。`| default('', true) | trim` で修正済み
（`default(..., true)` は falsy な `None` を空文字に置換）。
core.md §18.3 の落とし穴リストに将来追記する価値がある挙動
（「空レンダリング → None → フィルタが 'None' 文字列化」）。

## 実行した確認コマンドと結果

実ホストへの接続・ssh直接実行・実ホスト向けansible実行・git commit/pushは
行っていない（core.md §17）。

1. **Python抽出ロジックの単体検証**: simulate.sh のヒアドキュメント部分を
   sed でそのまま抽出し、捏造した apt -s 行（通常更新・新規インストール・
   バージョン無しRemv・カンマ付きsource）を環境変数で投入
   → `inst_detail`/`remv_detail` とも期待どおり構造化された。
2. **shell構文/抽出**: `bash -n` OK。grep マッチ0件時の挙動（rc=0扱い・空値）
   も単体で確認。
3. **テンプレートレンダリング検証（core.md §17 例外の使い捨てプレイブック）**:
   `hosts: localhost` + `connection: local` + set_fact/debug/assert のみの
   検証プレイブックを scratchpad（リポジトリ外）に生成して実行。
   builder タスクと3通知の slack_message は**実ファイルから yaml.safe_load で
   逐語抽出**したものを使用（コピペ複製ではなく実装そのものを検証）。
   - シナリオ1（既定上限・5候補・3通知全部）: 桁揃え・(新規)・(remove)・
     `?`・NO_UPDATES/HEALTHCHECK_FAILED の block 非表示、
     いずれも期待どおり（冒頭の表示例は本シナリオの実出力）。
   - シナリオ2（上限5・9候補）: 5行 + 「…他4件(レポートJSON参照)」。
   - シナリオ3（候補0件）: 当初 `"None"` 混入を検出（上記4章）→ 修正後、
     空文字 assert 合格。
   検証プレイブックは検証後に削除済み。
4. **静的チェック**: `ansible-playbook playbooks/ubuntu_vm_full_upgrade.yml
   --syntax-check` OK / `bash scripts/check-tester-gate.sh` OK（33 playbooks）/
   `git diff --check` OK。

## 注意点

- **reboot_quory.yml も §実施5 の対象に含めた（判断）**: requirement の
  文面が引用する現状メッセージは reboot_local.yml のものだが、quory の
  applyサマリ（`quory - send summary notification`）も「何が適用されたか
  分からない」点は同一のため、同じ1行+blockを追加した。スコープ外と
  判断される場合、reboot_quory.yml の該当4行を外すだけで戻せる
  （他の変更から独立）。
- 集約通知の per-host エントリには構造化データではなく事前レンダリング済み
  `detail_block` 文字列を載せた。フォーマット定義を1箇所に保つためで、
  構造化データ自体はレポートJSON側に残る。
- apt -s が同名パッケージのInst行を複数出す異常ケースでは、名前リスト
  （sort -u）は1件に畳まれ、detail は生の行数どおり並ぶ（収集は生データを
  尊重）。実運用のaptでは発生しない想定。
- playbook の tester-gate 分類（check-mode-native）・Semaphoreテンプレート・
  実行経路・IP/秘密情報の扱いに変更なし。set_fact/通知はいずれも既存の
  `check_mode: false` ブロック内で従来どおり動作する。
