## 反映した指摘

### 指摘1 [must-fix] 初回実行(unit未存在)で`systemctl show`が失敗しblockに入れない

対象: `roles/ubuntu_vm_full_upgrade/tasks/reboot_quory.yml`

`systemctl show`タスクに`failed_when: false`を追加した。未存在unitの
`stdout`が空、またはrcが非ゼロでも例外を投げず、`(stdout | trim) or 'inactive'`
というJinjaパターンで「不明時はinactiveとして扱う」ように統一した。これにより
**reboot-requiredなquoryの初回applyで確実に予約できる**ようになった
(修正前は初回実行が必ずrescueに落ちていた)。

### 指摘2 [must-fix] `.service`ではなく`.timer`のActiveStateで予約有効性を判定

対象: `roles/ubuntu_vm_full_upgrade/tasks/reboot_quory.yml`

`systemd-run --on-active --unit=...`は待機中`.timer`がactive、対応する
`.service`は発火前はinactiveのまま、という実際の状態遷移を踏まえ、
`.timer`と`.service`両方のActiveStateを取得し、**いずれかが**
`active`/`activating`/`reloading`なら「予約は有効」と判定するよう修正した
(timerの通常状態を主判定、firing直後にserviceがactiveになるエッジケースを
fallbackで拾う)。これにより、60秒以内の再実行で「待機中の正規予約」を
誤って「予約なし」と判定し、reboot時刻を無期限に後ろへずらし続けるバグを解消した。

### 指摘3 [must-fix] 予約部分失敗時のflag整合性(reservation_confirmed factで分岐)

対象: `roles/ubuntu_vm_full_upgrade/tasks/reboot_quory.yml`

`ubuntu_vm_full_upgrade_quory_reservation_confirmed`という明示的なfactを導入した。

- 初期値: 既存の有効な予約(指摘2の判定)を検出した時点でtrueにする
- 新規予約の場合: `systemd-run`成功後にtrueへ更新する(失敗した場合、この
  set_factには到達しないため値はfalseのまま)
- `rescue`ブロックはこのfactを見て分岐する:
  - `reservation_confirmed`が**false**(予約が一度も確立していない) →
    pending flagファイルを削除してからalert通知(「reboot未予約、
    今後別理由でrebootしてもpost-upgrade checkは誤発火しない」)
  - `reservation_confirmed`が**true**(予約自体は有効。flag更新や通知等
    その後の処理だけが失敗) → flagは**削除しない**まま alert通知
    (「reboot予約は有効。post-upgrade checkは予定通り発火する」)

これにより、予約が実際には確立していないのにflagだけが残って将来の無関係な
rebootでpost-upgrade checkが誤発火する、という事故経路を塞いだ。

### 指摘4 [suggestion] QDeviceをchrony待機後に再評価

対象: `scripts/quory_post_upgrade_check/quory-post-upgrade-check.sh`

corosync-qdeviceのチェック順序を、chrony待機(最大50秒)の**後**へ移動した
(以前は最初に約10秒だけpollして値を固定していた)。これによりSemaphoreと
同様、boot後により多くの経過時間を確保した状態で最終判定できるようになった。
タイムアウト予算(chrony 50秒+qdevice 15秒+semaphore 15秒+curl 10秒
=約90秒、`TimeoutStartSec=120`に対し十分な余裕)はレビューの再計算結果と
一致することを確認した。

### 指摘5 [suggestion] 集約実行hostが失敗しても他ホストのrollupを送れるように

対象: `roles/ubuntu_vm_full_upgrade/tasks/main.yml`

集約タスクのアンカー選定を`ansible_play_hosts_all | first`(静的な全ホスト
リストの先頭。healthcheck失敗で脱落したホストでも変わらない)から
`ansible_play_hosts | first`(この時点で**まだ生存している**ホストのみを
含む動的リスト)へ変更した。先頭ホスト(通常ansy)自身がhealthcheckで
failしても、生存している他のホストのいずれかが確実に集約タスクへ到達する
ようになった。集約対象を列挙するループ(`Build per-host status summary`)は
引き続き`ansible_play_hosts_all`を使う(healthcheck失敗ホストの
HEALTHCHECK_FAILEDエントリも表示に含めるため)。

## 検証(ローカル、実ホスト非依存)

実ホストへの接続・`ansible-playbook`の実実行・`ansible` ad-hocコマンド・
ssh直接実行・git commit/push・秘密情報の参照はいずれも行っていない
(core.md §17)。localhostでの実`systemd-run`実行は、ユーザー環境にtransient
unitを残してしまうため行っていない(レビューの指示通り、状態遷移を模した
合成データで判定ロジックのみを検証した)。

```
$ ansible-playbook playbooks/ubuntu_vm_full_upgrade.yml --syntax-check
$ bash scripts/check-tester-gate.sh
[tester-gate-lint] OK (33 playbooks)
$ bash -n scripts/quory_post_upgrade_check/quory-post-upgrade-check.sh
$ bash -n roles/ubuntu_vm_full_upgrade/files/ubuntu-full-upgrade-simulate.sh
$ git diff --check
```

`hosts: localhost, connection: local`の使い捨てplaybookに、`reboot_quory.yml`と
**全く同じJinja式**を実際のsystemd-run状態の組合せに見立てた合成
`timer_stdout`/`service_stdout`ペアを注入して`reservation_active`判定を検証した
(確認後削除)。

| ケース | timer | service | reservation_active | 期待 |
| --- | --- | --- | --- | --- |
| A. 初回実行(unit未存在、show失敗で空stdout) | inactive | inactive | False | 新規予約を作成 |
| B. 60秒以内の再実行(timer待機中、serviceは未発火) | active | inactive | **True** | 既存予約を維持(これが今回のバグ) |
| C. timer発火直後、serviceがreboot実行中 | inactive | active | True | serviceフォールバックで捕捉 |
| D. 前回異常終了の残骸(failed) | failed | failed | False | cleanupして新規作成 |
| E. 既存/新規いずれも「予約なし」相当 | inactive | inactive | False | 新規予約を作成 |

5パターンすべて期待通りの結果を確認した。特にケースBは今回のmust-fix2が
修正した具体的なバグ(待機中の正規予約を誤って「予約なし」と判定していた)を
直接再現・検証したものである。
