## B. 非apt管理プロダクト更新チェック

### 1. 汎用registry

`roles/ubuntu_vm_full_upgrade/defaults/main.yml`:9-28へ`ubuntu_vm_full_upgrade_nonapt_per_node`を追加した。各entryは次をデータとして持つ。

- product名
- current / latestのJSON endpoint
- JMESPath version query
- latest tagのstrip prefix
- timeout
- local endpointのproxy使用有無
- 人間向けnote

第1弾はmonnieのprometheusのみ。currentは`localhost:9090/api/v1/status/buildinfo`、latestはGitHub Releases APIの`prometheus/prometheus/releases/latest`を登録した。

current取得にはbuildinfo HTTP endpointを選んだ。実際に稼働中のPrometheus自身が返す版を確認でき、バイナリの配置pathやsystemd `ExecStart`のパースに依存しないため。localhost endpointは環境proxyの影響を避けるため`current_use_proxy: false`とした。

### 2. read-only / best-effort収集

新設ファイル:

- `roles/ubuntu_vm_full_upgrade/tasks/collect_nonapt_product.yml`
  - `ansible.builtin.uri`のGETだけを使う。
  - current / latestとも`changed_when: false`、`failed_when: false`。
  - timeout既定10秒。GitHub側はJSON Accept headerを送る。
- `roles/ubuntu_vm_full_upgrade/tasks/evaluate_nonapt_product.yml`
  - HTTPレスポンスからregistryのJMESPathでversionを抽出する。
  - latestの`v` prefixを除去する。
  - 先頭ゼロなしの厳密3要素`^(0|[1-9][0-9]*)[.](0|[1-9][0-9]*)[.](0|[1-9][0-9]*)$`を満たす両versionだけをAnsibleのsemver `version` testで比較する。
  - response評価をGETから分離し、外部接続なしで決定3状態を回帰テスト可能にした。

result state:

- `update_available`: 両取得・抽出成功、数値比較成立、current < latest
- `up_to_date`: 両取得・抽出成功、数値比較成立、current >= latest
- `failed`: endpoint失敗、JSON field欠落、または数値比較不能

resultの`current_rc` / `latest_rc`はcollector共通の合成rcとして定義した。

- `0`: HTTP 200かつversion抽出成功
- `1`: HTTP 200だがJSON field欠落
- HTTP status（例: 404）: HTTP応答エラー
- `-1`: 接続・timeout等でHTTP statusなし

実HTTP statusも`current_http_status` / `latest_http_status`へ別保存する。これにより通知の簡潔なrcとreportの診断情報を両立する。

### 3. dry-run限定ガード

`roles/ubuntu_vm_full_upgrade/tasks/main.yml`:122-132で、参加hostごとに結果を空listで初期化し、registry loopは`when: dry_run | bool`の場合だけ実行する。

- 月次`dry_run=true`: 登録productを確認する。
- `dry_run=false`: 結果は空listのままで、外部GETを実行しない。apt apply経路は従来どおり。
- registryなしhost: 空listのまま。

### 4. Status昇格とapt判定回帰防止

`roles/ubuntu_vm_full_upgrade/tasks/classify.yml`:118-164で、従来のStatus式とreason式を内容変更なしで`ubuntu_vm_full_upgrade_apt_status` / `_apt_status_reason`として先に評価し、その後に非apt結果を重ねる2段構成へ変更した。

- confirmed `update_available`なし: Status / reasonはapt基礎判定のまま。
- updateあり + apt `NO_UPDATES` / `UPGRADE_READY`: `REVIEW_REQUIRED`へ昇格。
- updateあり + apt `REVIEW_REQUIRED`: Status維持。
- updateあり + apt `BLOCKED` / `MAJOR_UPGRADE_DETECTED`: 上位Status維持。
- updateありの場合は、いずれのStatusでも`status_reason`へ`non-apt update available: NAME CURRENT → LATEST`を追記する。
- `failed`は選択対象外でStatus / reasonを一切変えない（fail-quiet）。

この構成により、MAJOR閾値・important判定・remove後継判定・apt失敗BLOCKEDの既存ロジック自体には手を加えていない。

### 5. 通知とreport JSON

`roles/ubuntu_vm_full_upgrade/tasks/main.yml`:217でper-host reportへ`nonapt` listを追加した。各entryにはname / current / latest / state / rc / HTTP status / note / reasonを保存する。

同ファイル:272-280でノード単位通知へ次の行を追加した。

- 更新あり: `apt外: prometheus CURRENT → LATEST (更新あり・手動更新が必要)`

- 失敗: `apt外: prometheus 取得/比較失敗(current rc=X / latest rc=Y)`

既存のapt件数、phasing、hold、package detail、product impact表示は削除・変更していない。registry結果が空なら非apt行も出ない。

## review 037 must-fix修正

初版036の比較可能ガード`^[0-9]+(?:[.][0-9]+)+$`は、`1.2` / `1.2.3` + `.4`（連結した4要素版）/ `01.2.3`も通す一方、後段の`version_type='semver'`がそれらを拒否し得た。このため比較不能を`failed`へ落とす前にversion testが例外となり、fail-quietに反してplaybookを中断する経路があった。

`roles/ubuntu_vm_full_upgrade/tasks/evaluate_nonapt_product.yml`のcurrent/latest両ガードを、SemVer parserが確実に受理する先頭ゼロなしの厳密3要素へ変更した。

```text
^(0|[1-9][0-9]*)[.](0|[1-9][0-9]*)[.](0|[1-9][0-9]*)$
```

ガード外ではconditional expressionのsemver `version` testを評価せず、必ず`state: failed`を記録する。state計算を独立factへ分離し、`reason`も`update_available`の場合だけ保存するよう整理したため、失敗result自身にも誤った更新理由は残らない。追加mock結果:

| current mock | 評価task | state | apt候補なし時のStatus / reason |
|---|---|---|---|
| `1.2` | 中断なし | `failed` | `NO_UPDATES` / non-apt reasonなし |
| `1.2.3` + `.4`（連結した4要素版） | 中断なし | `failed` | `NO_UPDATES` / non-apt reasonなし |
| `01.2.3` | 中断なし | `failed` | `NO_UPDATES` / non-apt reasonなし |

既存のvalid `2.53.0 → 3.5.1`は引き続き`update_available`、`3.5.1 → 3.5.1`は`up_to_date`となることも同時に再確認した。
