## Findings

### must-fix: cert_renew の global pause 説明に失敗時の残留条件がない

- `docs/ai/prompts/autonomous_recovery_policy.md:249`
- 対応実装: `playbooks/cert_renew.yml:113-130`

追加文は「grafana-server再起動の前後をTTLなしのグローバルpause / resumeで挟む」と
記載している。正常経路のtask順としては一致するが、`deploy_grafana`が失敗した場合、
後続のresume taskは実行されない。resumeは`always` / `rescue`に無く、global pauseは
TTLなしなので、人間が明示resumeするまで全targetの監視が停止したままになる。

今回のrequirementはmute一覧を実装と突合し、補足も実態に合わせることを要求し、コードは
変更しない方針である。したがってpolicy側に、pause→deploy→正常時resumeという実装であること、
deploy失敗時はpauseが残り手動resumeが必要であることを明記する必要がある。これは単なる
文体差ではなく、障害時の監視停止を運用者が見落とさないための正本情報である。

## 重点確認結果

### hold収集とエラー防御

- `apt-mark showhold`はdpkg selectionのread-only参照で、package状態を変更しない。
- scriptは`set -uo pipefail`で`-e`を使っていないため、command substitution失敗後も
  `hold_rc=$?`を正しく保持してJSON生成まで継続する。
- `hold_names`はrc=0の場合だけstdout/stderr統合結果から生成される。rc!=0では必ず空のままなので、
  `E: ...`等の診断文字列がpackage名として通知・reportへ入る経路はない。
- script JSONは`apt_mark_showhold.rc` / `tail`と`simulation.hold`を分離する。
- reviewerのrc=42 mockでも、script exit=0、`hold=[]`、`rc=42`、診断tail保持を確認した。

### 通知表示と既存表示の回帰

- hold行は`simulation.hold | length > 0`のJinja条件内だけにあり、0件時は行を生成しない。
- 挿入位置は既存の候補/phasing件数行の直後で、Inst / Remv / phased detailを作る
  `_details`、表示cap、monospaced blockには変更がない。
- report JSONへの`hold` / `hold_collection_rc`追加は既存fieldを削除・変更しない。
- hold名はsort済み・重複排除済みで、表示件数とjoin対象が同じlistに基づく。

### classify / Status / applyへの非関与

- `roles/ubuntu_vm_full_upgrade/tasks/classify.yml`は未変更で、holdを参照しない。
- MAJOR件数、important判定、remove後継判定、Status、status_reasonはいずれも従来どおり
  Inst / Remv（phasingは既存の表示専用例外）だけに基づく。
- `tasks/apply.yml`、reboot経路、manual apply gate、tester-gate markerは未変更。
- holdはnotificationとper-host reportへの追加だけであり、要求の表示専用境界を守る。

### mute一覧の突合

対象別muteの列挙とTTLは実装に一致する。

- evacuate: authy / monnie / sophos-fw、120分
- patch apply: 同3target、60分
- restore placement: 同3target、90分
- ubuntu nightly: reboot対象のauthy / monnie、30分
- weekly full: 同3target、360分（短いsub-playbook muteで短縮されない）
- ubuntu_vm_full_upgrade apply: authy / monnie、45分

`cert_renew.yml`が対象別muteではなくTTLなしglobal pauseを使うという分類も正しい。
ただし上記findingのとおり、失敗時resumeの非保証をpolicyへ反映する必要がある。

### unpoller対応(b)

コードで同一version文字列を除外せず、playbook headerとpolicyへ既知事象として記録する
対応(b)は妥当。表示文字列一致だけで除外するとepoch / Debian revision / architectureや
repository metadata差を隠す可能性があり、生のapt planを保持する方が安全である。
Statusへの例外追加もなく、「機能本体を変更しない」という制約に適合する。
