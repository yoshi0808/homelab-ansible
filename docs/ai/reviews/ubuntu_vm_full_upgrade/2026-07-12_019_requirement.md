# ubuntu_vm_full_upgrade 通知改修第2弾: ノード単位化・#patches化・phasing保留表示・上限引き上げ（requirement）

- 日付: 2026-07-12
- 起案: claude（要件定義・ハブ役）
- 発端: 通知バージョン差分表示（requirement 014 / implement 015 / review 016）の
  テスト（test_plan 017 / test_result 018）に対する Yoshinobu の判定と追加要望

## 背景

test_result 018 の T-4 で、monnie の `apt list --upgradable` 25件に対し
通知/JSONの候補が23件となる不一致が出た。原因は Ubuntu の phased updates
（段階的ロールアウト）: 差分2件（python3-software-properties /
software-properties-common 0.120→0.120.1）は候補バージョンが `(phased 10%)`
で、`apt-get full-upgrade` は保留する一方 `apt list --upgradable` には表示
される（ansy 上の `apt-cache policy` で確認済み。monnie 実機での裏取りは
次回テストで行う）。

表示された23件のバージョン値自体は全件正確だが、Yoshinobu の判定は
**「件数不一致は NG」で不合格**。あわせて通知の届き方について以下の
追加要望があった（2026-07-12）:

- 通知は proxmox パッチ系と同様 #patches チャネルへ（現状は #alerts に届く）
- 4ノードを1通にまとめる集約通知は分量的に無理がある。ノード単位で通知する
- 「…他N件(レポートJSON参照)」は、外出中は SSH できず実質確認不能。
  レポートJSONは障害切り分け専用の位置付けとし、通常運用は Slack 本文で
  完結させる。表示上限をもっと引き上げる（完璧は求めないが）

## 実施項目

1. **phasing 保留分の表示（件数整合）**: `apt-get -s full-upgrade` 出力に
   含まれる phasing 保留パッケージ（"deferred due to phasing" 相当）を
   shell で収集・構造化し（収集と整形のみ）、レポートJSONと通知に追加する。
   通知では適用候補と明確に区別して表示する（例: 保留行に `(phasing保留)`
   を付す、または「保留(phasing): N件」のセクションを分ける）。
   **適用候補 + phasing保留 の合計が `apt list --upgradable` の件数と
   整合する**ことが受け入れ条件。
2. **通知チャネルの変更**: 月次dry-run通知・applyサマリ通知を #patches へ。
   `roles/proxmox_patch_dryrun/tasks/main.yml` の
   `'alerts' if BLOCKED else 'patches'` と同じ考え方で、異常
   （BLOCKED / healthcheck FAILED / post-reboot critical 等）は従来どおり
   #alerts、正常系レポートは #patches とする。
3. **ノード単位通知への分割**: 月次dry-runの4ノード集約通知（1通）を廃止し、
   ノードごとに1通のレポート通知にする。各通知にそのノードの Status /
   status_reason / 件数 / バージョン一覧（適用候補 + phasing保留）を含める。
   全ノード横断の短いサマリ通知を残すかは実装者判断（必須ではない）。
4. **表示上限の引き上げ**: ノード単位通知を前提に、通常月の全件が Slack
   本文に収まる水準へ既定値を引き上げる（現行20行。目安50以上、実装者が
   根拠を添えて選ぶ）。超過時の切り詰め機構自体は安全弁として残してよいが、
   通常運用で「レポートJSON参照」に依存しない状態にする。

## 制約

- requirement 014 の制約を引き継ぐ: shell は収集とJSON整形のみ（core.md §7）、
  tester-gate 分類・Semaphore実行経路の変更なし、秘密情報・IPリテラルなし
- 追加コマンドの扱い（2026-07-12 改訂）: 当初は「追加の apt コマンド実行は
  しない（既存 sim_out からの抽出のみ）」としていたが、apt の計画出力には
  phasing 保留分のバージョンが含まれず、実施項目1の「バージョン一覧」と
  両立しないことが review 021 の must-fix で確定した。Yoshinobu の判断
  （2026-07-12）により、**read-only の補助収集（`apt-cache policy` 等、
  ローカルキャッシュ読取のみでシステム状態を変更しないもの）に限り許可**に
  緩和する。パッケージ状態を変更しうるコマンド、ネットワークへ再取得しに
  いくコマンド（apt-get update の再実行等）の追加は引き続き不可
- 既存の `inst_detail` / `remv_detail` の構造は維持し、phasing 保留は
  別フィールドとして追加する
- **phasing 保留分は classify の Status 判定・important 分類・件数閾値判定に
  含めない**（full-upgrade が適用しないものは判定対象外。表示のみ）。
  この設計判断は実装コメントに残す
- healthcheck FAILED 等の既存の異常系 per-host アラート（#alerts）の挙動は
  変えない

## 初回実装で除外する範囲

- changelog・更新理由の取得・表示（従来どおり）
- phasing の進捗率そのものの表示や追跡（保留である事実と件数・バージョン
  が分かれば足りる。バージョンは上記改訂どおり read-only 補助収集で取得する）
