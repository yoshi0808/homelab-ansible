# ubuntu_vm_full_upgrade への非 apt 管理プロダクト更新チェック追加（第1弾: prometheus）— 要求仕様

- 日付: 2026-07-17
- 起案: claude（要件定義・ハブ役）/ 承認: Yoshinobu（方向は 2026-07-16 に決定済み: 「別 playbook ではなく ubuntu_vm_full_upgrade 内に apt 以外の対象サービスとして登録し通知経路を一本化する」）
- 優先度: 中（monnie の prometheus は apt 管理外のため、現状どの自動チェックにも乗っていない = silent gap）

## 背景

- monnie の prometheus は**手動インストール（apt 管理外）**。月次 full-upgrade では永久に更新候補に
  出ず、更新の見逃しが構造的に発生する（[[project_monnie_monitoring_stack]] 2026-07-12 起票）。
- 方向性（Yoshinobu 2026-07-16）: 別 playbook を新設せず、**月次 dry-run（毎月2日）の中で
  非 apt プロダクトも一緒にチェックし、通知を一本化**する。
- 将来の「ホスト別プロダクト目録」（apt / 非apt / GUI管理の3クラス管理）の非apt枠の実装先例となるため、
  **prometheus 固有ではなく汎用の登録構造**にする。

## 実施項目

### ① defaults に非 apt プロダクトの登録構造を新設

`roles/ubuntu_vm_full_upgrade/defaults/main.yml` に per-node の非 apt プロダクトリストを追加する。
構造は実装判断だが、次を表現できること（名称は例）:

```yaml
ubuntu_vm_full_upgrade_nonapt_per_node:
  monnie:
    - name: prometheus
      # 現在バージョンの取得（ノード上で read-only 実行）
      current_version_cmd: "curl -fsS --max-time 10 http://localhost:9090/api/v1/status/buildinfo"
      current_version_jq: ".data.version"   # 取得方式は実装判断（下記 NOTE）
      # 最新バージョンの取得（GitHub Releases API、月1回なので rate limit 問題なし）
      latest_url: "https://api.github.com/repos/prometheus/prometheus/releases/latest"
      latest_tag_strip_prefix: "v"
      note: "手動インストール。更新は人間作業（Notion『Prometheus / Grafana / unifi-poller セットアップ手順』参照）"
```

- **現在バージョン**: prometheus は `localhost:9090/api/v1/status/buildinfo` が version を返す
  （read-only HTTP、recovery_exec の prometheus-targets チェックと同系）。バイナリ
  `prometheus --version` のパースでもよい。取得方式は実装判断とし、選定理由を implement に記載。
- **最新バージョン**: GitHub Releases API の latest（= 最新 stable）。`v` プレフィックスを剥がして比較。

### ② 月次 dry-run 通知への表示

- ノード単位の #patches 通知に、非 apt プロダクトの行を追加する。表示例（形式は実装判断）:
  - 更新あり: `apt外: prometheus 2.53.0 → 3.5.1 (更新あり・手動更新が必要)`
  - 最新: `apt外: prometheus 3.5.1 (最新)`
  - 取得失敗: `apt外: prometheus 取得失敗(current rc=X / latest rc=Y)` — **best-effort。取得失敗で
    playbook を fail させない**（Slack 通知と同じ流儀）。
- report JSON にも `nonapt` セクションとして current/latest/判定/rc を保存する。

### ③ Status 判定への関与（Yoshinobu 決定 2026-07-17: 関与させる）

- 非 apt プロダクトに**「更新あり」が確定した場合、そのノードの Status を最低 `REVIEW_REQUIRED` に
  昇格**させる（既存 Status がそれ以上＝MAJOR 系ならそのまま上位を維持。降格はしない）。
  `status_reason` に `non-apt update available: prometheus X → Y` 相当の理由を追加し、
  人間が通知だけで昇格理由を判別できるようにする。
- **取得失敗（current/latest いずれかの収集 rc≠0）は Status に関与させない**。外部 API の一時不調で
  毎月誤 REVIEW になる事故を避けるため、失敗は表示行と report JSON の rc のみで伝える（fail-quiet）。
  「更新あり」の判定は両方の取得成功 + バージョン数値比較が成立した場合に限る。
- classify.yml（Status 判定）に手が入るため、レビューでは既存の apt 系判定
  （MAJOR 閾値・important・remove 後継）への回帰がないことを重点確認する。

## 制約・NOTE

- **自動更新は絶対にしない**。チェックと通知のみ（prometheus の更新は人間の手動作業）。
- 収集はすべて read-only（ローカル HTTP GET / GitHub API GET）。
- **monnie から api.github.com への HTTPS 到達**が前提 → pre-deploy 確認項目（tester）。
  月1回×1プロダクトなので未認証 rate limit（60/h）は問題にならない。
- dry_run=false（apply 経路）ではこのチェックを**実行しない**（apply は apt 世界の操作。
  非 apt はあくまで月次レポートの情報）。実装判断で dry-run 限定のガードを置く。
- バージョン比較は `version` テストフィルタ等の数値比較とし、単純文字列比較の罠
  （2.53.0 vs 3.5.1 等）を避ける。プレリリースは latest API が返さない前提でよい。
- **実装着手は 033（小改修バンドル）のレビュー収束後**。同一ファイル
  （defaults / tasks/main.yml / policy / playbook ヘッダ）を触るため、順序実行で衝突を避ける。
  同じ implementer が続けて担当するのが望ましい。
- 秘密・IP をリポジトリに書かない。

## 確認項目（tester 工程）

- 月次 dry-run（--check ではなく dry_run=true の通常実行。tester-gate 分類の現状に従う）で
  monnie の通知に prometheus 行が出ること（更新あり/最新のどちらかが実データで出る）。
- 取得失敗系: latest_url を一時的に無効な値にした dry-run（またはモック）で「取得失敗」表示になり、
  playbook が fail しないこと。
- report JSON の `nonapt` セクション。
- 既存通知（apt 候補・phasing・hold 表示）への回帰なし。
- Status 昇格の3ケース: (a)更新あり→REVIEW_REQUIRED へ昇格＋status_reason に理由、
  (b)最新→Status 不変、(c)取得失敗→Status 不変（誤 REVIEW にならない）。
  apt 系判定（MAJOR/important/remove）への回帰なし。
