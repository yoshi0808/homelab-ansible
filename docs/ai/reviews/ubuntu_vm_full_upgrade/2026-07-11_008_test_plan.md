## 前提・重要な注意

- 変更ファイル一式（playbook / roles/ubuntu_vm_full_upgrade / roles/radius_healthcheck /
  scripts/quory_post_upgrade_check）は未コミットのため、quory 正式 checkout へ
  **バックアップを取ってから**同期して実行する（backup + 同期方式）。
- **Phase A は実変更なし**（apt インデックス更新と Slack 通知のみ。requirement §13 の
  明確化どおり）。**Phase B・C は実際の apt full-upgrade + reboot を伴う**。
- ansy への apply（Phase B）は、エージェント群が稼働する ansy 自身を再起動するため
  tester では実行できない。quory への apply（Phase C）も Semaphore 自身が対象。
  いずれも **Semaphore 経由で Yoshinobu が実行**する（requirement §2 の本番経路の
  実証を兼ねる）。tester は事前検証・事後検証を担当する。
- Phase B・C の実施可否・タイミングは **Phase A の実データ（各ノードの Status と
  更新候補の内容）を見てから別途判断**する（本計画では枠のみ定義）。

## Phase A: 実変更なしの全ロジック検証（tester、今回実施分）

### A-0: 準備

1. quory 正式 checkout へ変更ファイル一式を backup + 同期
2. 4ノードの現在の稼働状態を記録（uptime、主要サービス active）

### A-1: 月次 dry-run（本番モードの実行）

3. quory から `ansible-playbook playbooks/ubuntu_vm_full_upgrade.yml -e dry_run=true` を実行
   - 期待: 4ノードすべてで healthcheck→simulate→classify→Slack 通知が完走、rc=0
   - 各ノードの Status と更新候補数を記録（Phase B/C の判断材料）
   - Slack 通知に §5.2.1 の要件（主力プロダクト影響の明示、「該当なし」明記、
     quory の3プロダクト個別表示、ansy/quory の ansible 管理方式表示）が
     含まれることを確認
   - 実変更がないこと: パッケージ・サービス・reboot なし

### A-2: --check での apply 経路検証（実変更なし）

4. `--check -e dry_run=false -e node=ansy -e ubuntu_vm_full_upgrade_confirm=ansy`
   - 期待: 引数検証・confirm・healthcheck・Status再判定・拒否判定まで走り、
     「would apply」通知で正常終了。apt full-upgrade / reboot / mute / flag は不発火

### A-3: 確認文字列の安全装置検証

5. `-e dry_run=false -e node=ansy`（confirm 未指定）→ 即 fail
6. `-e dry_run=false -e node=ansy -e ubuntu_vm_full_upgrade_confirm=wrong` → 即 fail
   （どちらも --check なしでよい: confirm 検証は共通処理より前に停止するため実変更なし。
   不安なら --check を付けてもよい — 検証価値は同等）

### A-4: 重要コンポーネントリストの実地突合（read-only）

7. 4ノードで `dpkg -l` を取得し、`defaults/main.yml` のパターンリストと突合。
   抜け漏れ（インストール済みなのにリストにない重要パッケージ）・過剰マッチを報告
8. ansy/quory の ansible 管理方式（apt or pip）を実地確認し、host_vars に設定すべき
   値を報告（現在は「管理方式未確認」がデフォルト）

### A-5: quory post-reboot check スクリプトの静的検証（配置はしない）

9. スクリプトの shellcheck / bash -n、および chronyc waitsync・リトライ・timeout 予算
   （120秒内）の机上確認。**quory への配置・unit 有効化は Phase C の事前準備で行う**

## Phase B: ansy への実適用（Yoshinobu 実行、Phase A 結果を見て別途判断）

- 事前: Semaphore にテンプレート登録（Yoshinobu）。tester が A-4 の結果を反映した
  host_vars 更新を確認
- 実行: Semaphore から `dry_run=false, node=ansy`（+confirm）
- 注意: **ansy の tmux セッション（エージェント群）は reboot で消滅**する。
  実行前にエージェント作業を区切り、reboot 後に `./new-session.sh` で再構築
- 事後（tester）: apply 結果・reboot・post-healthcheck の Semaphore ログ確認、
  ansy のパッケージ/uptime/サービス実地確認

## Phase C: quory への実適用（Yoshinobu 実行、Phase B 完了後に別途判断）

- 事前準備（tester または Yoshinobu、要承認）:
  - `scripts/quory_post_upgrade_check/` 一式を quory へ手動配置（配置手順は
    スクリプト冒頭コメント）、`/etc/ubuntu-vm-full-upgrade/slack-webhook-quory.conf`
    作成（root:root 0600）
  - フラグファイルなしでの unit 不発火確認（`ConditionPathExists` の検証）
- 実行: Semaphore から `dry_run=false, node=quory`（+confirm）
- 期待: playbook が通知送信→正常終了→約60秒後に reboot 発火。reboot 後、
  post-reboot check が QDevice/chrony/Semaphore を検証して Slack 通知、フラグ削除
- 事後（tester）: Semaphore 稼働・QDevice 健全性・chrony 同期・フラグ削除済みの確認、
  transient unit の残骸なし確認
- 補足: quory reboot 中は Proxmox クラスタの QDevice 投票が一時不在になる
  （pve1/pve2 両方 online なら quorum は維持される）
