# ubuntu_vm_full_upgrade — 修正報告(テスト不合格による差し戻し対応)

対象:

- `docs/ai/reviews/ubuntu_vm_full_upgrade/2026-07-11_009_test_result.md`(Phase A 不合格・A-1 blocker)
- `docs/ai/reviews/ubuntu_vm_full_upgrade/2026-07-11_008_test_plan.md`

tester が実ホスト(authy/monnie)で発見した実バグを修正した。

## 原因

`roles/ubuntu_vm_full_upgrade/tasks/healthcheck.yml` および
`roles/ubuntu_vm_full_upgrade/tasks/reboot_local.yml` が、`radius_healthcheck`/
`monitoring_healthcheck`ロールの`tasks/check.yml`を絶対パスの
`ansible.builtin.include_tasks`で再利用していたが、**`include_tasks`はAnsibleの
role文脈(ファイル検索コンテキスト)を切り替えない**ため、`check.yml`内の
`copy: src: radius-healthcheck.sh`(bare filename)が呼び出し元
(`ubuntu_vm_full_upgrade`)の`files/`で検索されてしまい、実際に存在する
`roles/radius_healthcheck/files/`が検索対象に入らず解決に失敗していた。

tester実行時のエラー:

```text
authy : Could not find or access 'radius-healthcheck.sh'
searched:
  roles/ubuntu_vm_full_upgrade/files/radius-healthcheck.sh
  roles/radius_healthcheck/tasks/files/radius-healthcheck.sh
  ...
```

## 修正内容

対象2ファイルの計4箇所を、`ansible.builtin.include_tasks`(絶対パス)から
`ansible.builtin.include_role`(`tasks_from: check`)へ変更した。

- `roles/ubuntu_vm_full_upgrade/tasks/healthcheck.yml`
  - authy: `include_role: {name: radius_healthcheck, tasks_from: check}`
  - monnie: `include_role: {name: monitoring_healthcheck, tasks_from: check}`
- `roles/ubuntu_vm_full_upgrade/tasks/reboot_local.yml`(post-reboot検証、
  同型の再利用箇所)
  - authy: 同上
  - monnie: 同上

`include_role`はAnsibleが実際にターゲットroleのcontextへ入るため、
`copy`/`template`の`src:`がそのroleの`files/`/`templates/`に対して正しく
解決される。`tasks_from: check`は引き続き`check.yml`のみを実行し、
`main.yml`(通知・report保存・fail)は実行しない — 前回レビューで確認済みの
「通知/report/failの重複を避ける」性質は`include_role`経由でも維持される
(`tasks_from`は実行対象タスクファイルを限定するだけで、role文脈の切り替え
という`include_role`の本質的な挙動には影響しない)。

## 他の再利用箇所への同型バグの有無(確認)

同ロール内の他の`include_tasks`呼び出し(`common_slack/tasks/notify.yml`、
`recovery_mute/tasks/set.yml`)についても同型の脆弱性がないか確認した。

- `common_slack/tasks/notify.yml`: `include_vars: file:
  "{{ inventory_dir }}/../vars/slack.yml"`という明示パスを使っており、
  bare filenameのrole-context依存lookupは行っていない。安全
- `recovery_mute/tasks/set.yml`: `slurp`/`copy`とも明示的な絶対パスまたは
  `content:`(ファイル名lookupを伴わない)を使っており、安全

該当する脆弱性箇所はhealthcheck.yml/reboot_local.ymlの計4箇所のみだった。

## 検証(ローカル、実ホスト非依存)

実ホストへの接続・`ansible-playbook`の実実行・ssh直接実行・git commit/pushは
行っていない(core.md §17)。

```
$ ansible-playbook playbooks/ubuntu_vm_full_upgrade.yml --syntax-check
$ ansible-playbook playbooks/radius_healthcheck.yml --syntax-check      # 回帰確認
$ ansible-playbook playbooks/monitoring_healthcheck.yml --syntax-check  # 回帰確認
$ bash scripts/check-tester-gate.sh
[tester-gate-lint] OK (33 playbooks)
$ git diff --check
```

さらに、tester が報告した現象そのものを**実際のAnsible実行で再現し、修正が
機能することを実証**した。`/tmp`配下(実ホスト・実productionコードに一切
触れない使い捨てディレクトリ)に最小構成の2 role(`role_a`が
`tasks/check.yml`+`files/marker.txt`を持ち、呼び出し元がそれを再利用する
構造)を作り、同一パターンで検証した(確認後削除)。

| 方式 | 結果 |
| --- | --- |
| `include_tasks`(絶対パス、修正前と同じ構造) | **失敗**。`Could not find or access 'marker.txt'` — tester報告のエラーと完全に同じ現象を再現 |
| `include_role`(`tasks_from: check`、修正後と同じ構造) | **成功**。`role_a`のcontextへ切り替わり、`role_a/files/marker.txt`を正しく解決してcopyが実行された(`changed: 1`) |

この再現実験により、(a)報告されたバグの原因特定が正しいこと、(b)採用した
修正方式が実際に問題を解消することの両方を、実ホストに触れずに実証した。
