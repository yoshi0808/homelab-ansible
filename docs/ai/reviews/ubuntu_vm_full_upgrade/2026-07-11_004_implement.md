## 反映した指摘

### 指摘1 [must-fix] `apt_update.rc != 0` をBLOCKED条件・reasonに追加

対象: `roles/ubuntu_vm_full_upgrade/tasks/classify.yml`

`Determine Status`のBLOCKED条件に`ubuntu_vm_full_upgrade_sim.apt_update.rc != 0`を
追加し、reasonメッセージにもupdate/check/simの3つのrcすべてを含めるよう修正した。
これにより、`apt-get update`が失敗して古いindexのままcheck/simulationが「たまたま」
成功しても、その結果を信用せずBLOCKEDとして扱う。

### 指摘2 [must-fix] recovery muteをauthy/monnieのみに限定

対象: `roles/ubuntu_vm_full_upgrade/tasks/apply.yml`

`Set recovery mute before full-upgrade`タスクに
`when: inventory_hostname in ['authy', 'monnie']`を追加した。autonomous recoveryの
mute消費者はauthy/monnie/sophos-fwのみであり、ansy/quoryへの書き込みは消費者のない
ファイルを残すだけだった。sophos-fwは本playbookの対象外のため設定しない。

### 指摘3 [must-fix] quoryのsystemd-run固定unit名の衝突対策(冪等化)

対象: `roles/ubuntu_vm_full_upgrade/tasks/reboot_quory.yml`(全面書き直し)

`--unit=ubuntu-vm-full-upgrade-reboot`を固定名のまま維持しつつ、以下を追加した。

1. `systemctl show ubuntu-vm-full-upgrade-reboot.service --property=ActiveState --value`
   で既存unitの状態を事前収集する
2. `active`/`activating`/`reloading`なら「既存の予約が有効」と判定し、新規の
   `systemd-run`実行を**スキップ**する(冪等な既存予約維持)
3. それ以外(failed/inactive等の残骸)の場合のみ、`systemctl stop`+
   `systemctl reset-failed`(both best-effort、`failed_when: false`)で
   クリーンアップしてから新規予約を作成する
4. フラグファイルの内容は「既存予約を維持」/「新規に予約」のどちらかを反映するよう
   更新(冪等な再実行でも内容が事実に即すように)

ランダムユニット名での並存は行わない(指摘の通り、複数reboot予約の並存を防ぐため)。

### 指摘6 [suggestion] quoryの通知→終了→reboot発火の時間保証を強化(指摘3と合わせて設計)

対象: `roles/ubuntu_vm_full_upgrade/tasks/reboot_quory.yml`

- `ubuntu_vm_full_upgrade_quory_reboot_delay_seconds >= 30`を要求するassertを追加した
  (デフォルト60のままなら通過。極端に短い値へのオーバーライドで安全マージンが
  消える事故を防ぐ)
- flag作成→unit状態確認→cleanup→**systemd-run予約**→Slack通知、という順序自体は
  維持した(予約完了 **後** に通知するため、「予約前に通知」による逆順の混乱は
  発生しない)。順序を「通知→予約」へ入れ替える案は**採らなかった**:
  入れ替えると予約に失敗した場合に「予約した」という虚偽の通知が既に飛んで
  しまう問題を新たに作り込むため
- 代わりに、flag作成〜unit確認〜cleanup〜予約〜通知の一連を1つの`block`+`rescue`に
  まとめた。どこで失敗しても`rescue`が`alerts`チャンネルへ
  「reboot **未予約**の可能性があります」という明示的な失敗通知を送ってから
  `fail`する。これにより「成功通知は予約が実際に成功した(または既存予約が有効
  だった)場合にしか送られない」という不変条件を保証した(指摘6が懸念した
  「予約失敗時に成功通知が飛ぶ逆順問題」への対処)
- Semaphore実測によるさらなる保証強化(実際のSlack応答時間・Ansible/Semaphore
  ジョブ確定時間の実測)はtester工程に委ねる(未対応事項)

### 指摘4 [must-fix] post-reboot checkでcorosync-qdevice/Semaphoreの起動待ちリトライを追加

対象:

- `scripts/quory_post_upgrade_check/quory-post-upgrade-check.sh`
- `scripts/quory_post_upgrade_check/quory-post-upgrade-check.service`(TimeoutStartSecは
  120のまま、予算の再設計のみ)

`wait_for_active <unit> <max_tries> <interval>` という再利用可能なリトライ関数を追加し、
corosync-qdeviceとSemaphoreの両方に適用した(以前は`systemctl is-active`を1回実行
するだけだった)。

タイムアウト予算(`TimeoutStartSec=120`に収まるよう再設計):

| チェック | 方式 | 最大所要時間 |
| --- | --- | --- |
| corosync-qdevice | `wait_for_active` 3回×5秒間隔 | 15秒 |
| chrony | `chronyc waitsync 10 0.5 0 5`(既存の内部retry) | 50秒(20→10回に削減) |
| semaphore | `wait_for_active` 3回×5秒間隔 | 15秒 |
| curl(Slack通知) | `--max-time 10` | 10秒 |
| **合計(worst case)** | | **90秒**(120秒予算に対し約30秒の余裕) |

最終判定は各待機シーケンスの**最新値**(`wait_for_active`が返した最後の観測値)で
行うため、qdeviceの初期値がchrony待機中に変化しても古い値のままにはならない
(指摘4が具体的に指摘した問題)。

### 指摘5 [must-fix] ansy/quoryのAnsible管理方式(apt/pip)明示

対象:

- `roles/ubuntu_vm_full_upgrade/defaults/main.yml`
- `roles/ubuntu_vm_full_upgrade/tasks/classify.yml`
- `roles/ubuntu_vm_full_upgrade/tasks/main.yml`

新規default変数`ubuntu_vm_full_upgrade_ansible_managed_by`(デフォルト`unknown`、
host_varsで`apt`/`pip`に上書き可能)を追加した。`ubuntu_vm_full_upgrade_products`の
ansy「Ansible開発環境」とquory「本番Ansible実行基盤」エントリにのみ
`managed_by_note: true`フラグを付け、`classify.yml`がこのフラグを見て
`note`フィールド(`apt管理: 判定対象` / `pip管理: apt full-upgrade判定対象外` /
`管理方式未確認`)を計算するようにした。QDevice/NTP基準など他のproductエントリには
このnoteは付かない(空文字列)。

`main.yml`のSlackメッセージテンプレートを`{{ p.label }}{{ '(' + p.note + ')' if
p.note else '' }}: ...`に更新し、noteがある場合のみラベルに括弧書きで併記する。
これにより「該当なし」と「pip管理のため元々判定対象外」を区別できるようになった。

実ホストでのAnsible管理方式確認はtester工程に委ねる(未対応事項)。

### 指摘7 [suggestion] healthcheck失敗ホストに対する集約の耐性

対象: `roles/ubuntu_vm_full_upgrade/tasks/main.yml`

`Build per-host status summary`を書き直し、`hostvars[item].ubuntu_vm_full_upgrade_status
is defined`を明示的にチェックするようにした。`participates=true`だが
healthcheck失敗で`status`が未設定のホストは、`HEALTHCHECK_FAILED`という明示的な
Statusエントリとして集約結果に含める(reason欄には個別healthcheckのcriticals内容、
取得できなければ「詳細不明」の旨を表示)。`Determine overall notification
channel/status`のchannel/status判定にも`HEALTHCHECK_FAILED`をalerts/critical扱いで
追加した。これにより、1ホストのhealthcheck失敗が集約タスク自体を(未定義hostvars参照で)
壊し、他の全ホストの通知まで巻き込んで失われる事態を防いだ。

## §13 の字義明確化について

要求仕様§13に「(§5.1が要求するapt-get updateによるaptインデックス更新のみ発生する。
2026-07-11レビュー指摘を受けた字義の明確化)」が追記された。これは前回実装時点で
すでに採用していた設計(`apt-get update/check/-s full-upgrade`はパッケージ本体を
変更しないためsemi-safe/read-onlyとして扱う、`proxmox_patch_dryrun.yml`と同じ考え方)
と完全に一致するため、コード変更は不要だった。

## 検証(ローカル、実ホスト非依存)

実ホストへの接続・`ansible-playbook`の実実行・`ansible` ad-hocコマンド・
ssh直接実行・git commit/push・秘密情報の参照はいずれも行っていない(core.md §17)。

```

$ git diff --check
```

`hosts: localhost, connection: local`(実SSH接続なし)の使い捨てplaybookで
以下を個別検証(確認後削除)。

1. **指摘1(apt_update失敗)**: `apt_update.rc=1`のみ(check/sim rc=0)を注入し、
   `BLOCKED`かつreasonに3つのrcすべてが含まれることを確認
2. **指摘5(managed_byノート)**: ansyで`managed_by=unknown`(既定)→
   `管理方式未確認`、`managed_by=pip`→`pip管理: apt full-upgrade判定対象外`、
   quoryで`managed_by=apt`→`本番Ansible実行基盤`のみ`apt管理: 判定対象`が付き
   QDevice/NTP基準にはnoteが付かないことを確認
3. **指摘3(systemd-run冪等性)**: `wait_for_active`関数を`systemctl`を
   モックした純粋なbash関数として切り出し、(a)途中でactiveになるケース、
   (b)max_triesまでactiveにならないケース、(c)即座にactiveなケースの
   3パターンで期待通りのreturn code/出力を確認
4. **指摘7(集約の耐性)**: `participates`/`has_status`の3状態
   (両方true / participatesのみtrue / 両方false)に対する分岐ロジックを
   同じ入れ子三項演算子パターンで直接検証し、期待通りHEALTHCHECK_FAILED/
   NORMAL/除外が選択されることを確認
