## 前提

- 対象playbookは `# tester-gate: check-mode-native`。tester の実行は
  `scripts/safe-ansible-check.sh` + `--check` 必須
- tester sandbox の一時パスは 018 で確立した分離方式を必ず使う:

```bash
ANSIBLE_LOCAL_TEMP=/tmp/ansible-local \
ANSIBLE_REMOTE_TEMP='/tmp/ansible-remote-$USER' \
scripts/safe-ansible-check.sh playbooks/ubuntu_vm_full_upgrade.yml \
  -e dry_run=true --check
```

（`$USER` はシングルクォートでターゲット側展開。固定パス /tmp/ansible-remote
は使わない）

- phasing の保留状況は日々変動するため、期待件数は固定せず**テスト時点の
  実測同士**で突合する

## T-1: 月次 dry-run 経路の実データ実行（tester）

期待:

- 4ノード完走（failed / unreachable = 0）、当日レポートJSON 4件保存
- **ノード単位の通知が4通**送信される（旧集約1通は存在しない）
- タイトルは `[ubuntu_vm_full_upgrade] dry-run (monthly) - <host>: <STATUS>`
- 件数行は `候補: install=N remove=M / 保留(phasing)=K` 形式
- BLOCKED / healthcheck 失敗がない限り、#alerts への送信はゼロ
  （すべて #patches）

## T-2: Slack 受信側 UI の目視（Yoshinobu）

- **#patches チャネル**にノード単位で4通届いていること（#alerts に来ない）
- 保留行が `<pkg> <installed> → <candidate> (phasing保留)` で表示されること
- コードフェンスの等幅描画・桁揃え（015 からの継続確認）
- 上限100行のため、通常月は「…他N件」が出ないこと

## T-3: レポートJSONの突合（tester）

- `phased_detail` が `name` / `installed` / `candidate` を持つ
- `inst_detail` / `remv_detail` の構造は第1弾から不変、既存フィールドも互換
- 通知本文の件数（install / remove / 保留）とJSON側の件数が一致

## T-4: 件数整合の実機裏取り（tester、monnie。前回 018 T-4 の再挑戦）

- `apt list --upgradable`（read-only）と突合し、受け入れ条件を確認:
  **inst_detail の upgrade 分（old ありの行）+ phased_detail =
  `apt list --upgradable` の件数・名前集合**
  （新規インストール分は `(新規)` 行で区別されるため除外して数える）
- phased_detail の各パッケージについて `apt-cache policy` で
  `(phased N%)` 注記を裏取りし、installed/candidate 値が JSON と一致すること
  （= deferred 検出と apt-cache パースが monnie の apt でも機能する証跡）
- 差分が出た場合: 即中断の前に、まず当該パッケージの `apt-cache policy` を
  確認して原因を記録する（018 の教訓: apt list は full-upgrade 計画の正では
  ない）。phasing 等で説明がつけば記録のうえ判定を続け、説明がつかなければ
  中断して claude へ返す

## T-5: NO_UPDATES 理由文言（tester、ansy。該当時のみ）

- テスト時点で ansy が適用候補0件かつ保留>0件なら（2026-07-12 朝時点は
  該当: inst=0 / phased 2件）、ansy の通知とJSONの status_reason が
  「今回のfull-upgrade適用候補なし(phasing保留あり)」になること
- 該当状況でなければ N/A と記録（不合格にはしない）
