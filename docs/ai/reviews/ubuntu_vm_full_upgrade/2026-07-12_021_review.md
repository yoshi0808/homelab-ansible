## 指摘

### must-fix: phasing 保留分のバージョン一覧が欠落している

requirement 019 は、ノード単位通知に「件数 / バージョン一覧（適用候補 + phasing保留）」を含めることを明記している（requirement 019:43-45）。しかし `phased_detail()` は `{"name": ...}` だけを保存し（`ubuntu-full-upgrade-simulate.sh`:104-108）、通知にも名前と `(phasing保留)` しか表示しない。implement 自身もこの未対応を記録している。

ただし、実装の説明どおり、`apt-get -s full-upgrade` の deferred セクションが名前しか出力しない場合、requirement 019:53-55 の「既存 `sim_out` からの抽出のみ、追加 apt コマンド禁止」とバージョン取得は両立しない。そのため解決策は次のどちらかを人間が選ぶ必要がある。

- phasing 保留は名前と件数のみで受け入れ、requirement のバージョン一覧対象から明示的に除外する。
- 追加収集を許可する要件に改め、phased パッケージの旧/候補バージョンを構造化する。

### suggestion: phasing 保留のみの場合は status_reason を「適用候補なし」にする

`classify.yml`:122,131-132 では Inst/Remv が0件なら、phased が存在しても Status=`NO_UPDATES`、理由=`更新候補なし` となる。phased を Status 判定に含めない設計は requirement どおりだが、同じ通知の直後に「保留(phasing)=N」が並ぶため、「更新候補なし」は読み手に矛盾して見える。Status は維持したまま、phased がある場合の理由を「今回の full-upgrade 適用候補なし（phasing保留あり）」等にすると意味が正確になる。

## 指定された重点確認

### 1. simulate.sh の awk 抽出

`LC_ALL=C` の出力例としてコード内に明示された「固定ヘッダ、後続の空白開始行、次の非空白開始行で終了」という形に対し、awk の状態遷移は妥当。折り返し行は `NF` 個の名前へ展開され、`sort -u` で重複も除かれる。実ホストの apt バージョンでヘッダ文言が同一かは tester による受け入れ確認が必要。

### 2. 集約通知廃止後の参照

`rg` で role 配下を確認し、削除対象の `ubuntu_vm_full_upgrade_results` / `ubuntu_vm_full_upgrade_notify_channel` / `ubuntu_vm_full_upgrade_notify_status`、および集約用 `ansible_play_hosts` / `hostvars[...]` 参照は残っていない。per-node 通知は参加ホストの common-processing block 内で実行されるため、必要な status/simulation/detail/product facts はすべてその前に定義される。

### 3. channel/status マッピング

`classify.yml` が生成する Status は `BLOCKED` / `MAJOR_UPGRADE_DETECTED` / `NO_UPDATES` / `REVIEW_REQUIRED` / `UPGRADE_READY` の5種であり、現在の分岐は requirement/implement の表どおりにマップする。

| Status | channel | slack_status |
| --- | --- | --- |
| `BLOCKED` | `alerts` | `critical` |
| `MAJOR_UPGRADE_DETECTED` | `patches` | `warning` |
| `REVIEW_REQUIRED` | `patches` | `warning` |
| `NO_UPDATES` | `patches` | `info` |
| `UPGRADE_READY` | `patches` | `ok` |

healthcheck failure、post-reboot critical、reboot/予約失敗の既存異常経路は `alerts` / `critical` のままである。
