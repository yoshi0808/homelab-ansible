# requirement: AIエージェントセッション発の実行では Slack 実送信を既定で抑止する

案件: `slack_send_optin`
作成: 2026-08-02 / Coordinator
状態: **クローズ**(2026-08-02)。TS-031 と `docs/ai/core.md` の改訂はYoshinobu承認済み

## 1. 問題定義

`roles/common_slack/tasks/notify.yml` の抑止条件は `skip_notifications` と `ansible_check_mode` の2つだけで、**どちらも既定は偽である**。したがって抑止手段を1つ誤ると本番Slackへ出る。

**この構造が原因の事象は8日間に4回発生している。**

| # | 日付 | 起動主体 | 抑止に使おうとしたもの | 結果 |
|---|---|---|---|---|
| 1 | 2026-07-26 | **未確認**(専用Incidentファイルが無い) | — | 実送信 |
| 2 | 2026-07-29 | Tester | 実行時に渡す `skip_notifications` | 付与忘れ → 実送信 |
| 3 | 2026-08-01 | Tester | decoyの `vars/slack.yml` | 宛先差し替えが効かず `hooks.slack.com` へ到達 |
| 4 | 2026-08-02 | Tester | decoyの `vars/slack.yml` | 同上(メッセージ配信なし、実HTTP 1件) |

一次記録: `docs/ai/memory/incidents/2026-07-29_tester-slack-notify-misfire.md`、`.../2026-08-01_tester-slack-decoy-did-not-contain-request.md`、`docs/ai/reviews/tester_mode_full_removal/2026-08-02_006_test_result.md` §残存リスク1。

**#4はIncident化されていない**(`2026-08-02_007_audit.md` 指摘2が「前日の同型Incidentと紐付けられていない」と指摘済み)。本案件で起票する。

#3・#4 は `--check` なしで送信経路そのものを走らせるのが目的だったため、**TS-031(check mode下では送らない)では原理的に防げない**。#2 は変数の付与忘れである。**3件に共通するのは「起動したのがAIエージェントのセッションだった」ことだけ**であり、そこが唯一の共通の抑止点になる。

### 誤った前提を1つ棄却した記録

当初は「コントローラが `ansy` なら開発実行なので送らない」を検討したが、**ansyは開発専用ではない**。現物で確認したとおり、ansyをコントローラとする本番通知経路が2本稼働している。

| 本番経路 | timer | 通知の出方 |
|---|---|---|
| 月次Knowledge振り返り | `ansible-knowledge-review.timer`(次回 2026-08-26) | `playbooks/knowledge_review.yml`(`hosts: localhost`)から送信 |
| 障害バンドル同期 | `ansible-incident-sync.timer` | `roles/incident_sync` から送信 |

ホスト名で判別すると**この2本が黙って止まる**。採らない。

## 2. ゴール

- **AIエージェントのセッションが起動した ansible 実行では、Slack への実送信を既定で行わない。**
- 本番の通知経路(quory/Semaphore、ansyのsystemd timer)の挙動を**一切変えない**。
- 判別が失敗したときは**送信側に倒れる**(本番が沈黙する側に倒さない)。
- decoyが成立しない欠陥クラスを、Testerが実際に読む場所へ残す。

## 3. 非ゴール

- callerごとの opt-in 化(`notify.yml` の include は **48箇所 / 28ファイル**。2026-08-02に `grep -rn "common_slack/tasks/notify.yml" --include='*.yml'` で実測)は行わない。1箇所で完結させる。
- `skip_notifications` / `ansible_check_mode` の既存2条件の意味は変えない。TS-031は削らず、条件を1つ足す改訂に留める。
- 通知の本文・チャンネル・色・capture連携には手を触れない。
- Semaphore側の設定変更を要求しない(repo外でありAIから検証できないため、変更を前提にした設計にしない)。

## 4. ユーザーストーリー

- **Tester として**、通知経路を含む playbook を `--check` なしで回すとき、変数の付与を忘れても本番Slackへ出ないでほしい。decoyの成否をモジュール実装まで読んで判断しなくても安全側であってほしい。
- **Yoshinobu として**、本番のアラート・レポート通知は今までどおり届いてほしい。抑止機構を足したせいで通知が消えることがあってはならない。
- **Coordinator として**、抑止が効いた事実と理由が実行出力に出ていてほしい(効いたのか、そもそも通知タスクに到達しなかったのかを区別したい)。

## 6. 受入条件(Given/When/Then)

**AC1 — エージェントセッション発では送らない**
Given `CLAUDECODE` が設定された環境(=Claude CodeのBashツール経由)
When 通知経路を含む playbook を `--check` なし・`skip_notifications` なしで実行する
Then Slack へのHTTPリクエストが**1件も発生しない**(送信taskがskipされたことを task 結果で確認)、`debug` に第3条件が効いた旨が出力される、playbookは **rc=0** で完走する

**AC2 — 本番相当の環境では従来どおり送る**
Given `CLAUDECODE` が未設定で `INVOCATION_ID` が設定された環境(systemd起動の再現)
When 同じ playbook を実行する
Then 送信taskが**実行される**(decoy webhook宛。実 `hooks.slack.com` へ到達させないこと)、`debug` の抑止メッセージは出ない、rc=0

**AC3 — 判別失敗は送信側へ倒れる**
Given `CLAUDECODE` も `INVOCATION_ID` も未設定の環境
When 同じ playbook を実行する
Then 送信taskが**実行される**(=沈黙しない)、rc=0

**AC4 — 既存2条件の意味が変わっていない**
Given エージェントセッション外の環境
When `--check` 付きで実行する / `skip_notifications=true` を付けて実行する
Then いずれも従来どおり抑止され、`debug` に該当条件が名指しで出る、rc=0

**AC5 — 明示的送信の逃げ道と、上書きできない2条件**
Given `CLAUDECODE` が設定された環境
When 次の3通りで実行する — ① `slack_force_send=true` のみ ② `slack_force_send=true` + `skip_notifications=true` ③ `slack_force_send=true` + `--check`
Then ①は送信taskが実行される。**②と③はいずれも抑止される**(`slack_force_send` が上書きできるのは第3条件だけであり、`skip_notifications` と `ansible_check_mode` は覆せない)。いずれも rc=0。③が送信されるならTS-031違反であり**実装差し戻し**とする

**AC6 — 本番の通知経路に挙動差分が出ていない**
Given 変更後の作業ツリー
When `git diff` を確認する
Then `roles/common_slack` 以外に**挙動を変える差分が無い**。`playbooks/` 配下の差分は**コメント行のみ**であり(R12)、task・`when:`・`vars:` に差分が無い

**AC7 — 宣言と実装が一致している**
Given 変更後の作業ツリー
When R6の3ファイル・R11のヘッダコメント・TS-031本文を、`notify.yml` の実 `when:` 式と1つずつ突き合わせる
Then 4箇所すべてが実装と一致し、2条件だけを名指しする記述が**リポジトリ内に1つも残っていない**(`docs/ai/reviews/` 配下の過去の案件記録は当時の事実なので対象外)

**この照合は人手で行う。** `scripts/check-doc-consistency.py` は①playbookの `tester-gate` ヘッダ↔`playbooks/README.md` ②agent定義の `model`/`effort`↔`role-routing-index.md` ③規範層markdownのリンク解決、の3関係しか検査せず、**notify.yml の guard式と文書の対応は検査対象外である**(2026-08-02にスクリプトのdocstringと実装で確認)。同スクリプトの通過を本ACの根拠にしない

**検証の制約**: 本案件の検証は**本番Slackへ1件も到達させずに行うこと**。#3・#4 の再来を避けるため、`community.general.slack` を経由する経路を実ネットワークで走らせない。環境変数の有無による `when:` の評価結果を観測する方法(Jinja評価、task の skip/ok 判定)で組む。
