## OQ2(`lookup('env', ...)`をinclude_tasksされたtask fileのwhen:で評価する挙動)の確認

**確認手段**: 実ホストに触れないdecoy(スクラッチ領域、`ansible_connection: local`のlocalhost 1台 + 閉ポートの疑似リモートホスト1台。実host名・実IP・実システムに影響するモジュールはいずれも使っていない)で、`notify.yml`と同型の`set_fact` + `lookup('env', 'CLAUDECODE')`を`include_tasks`経由で読み込むタスクファイルを作り、環境変数の有無・プレイの対象ホスト・`--check`の有無を変えて実行した。

**確認した事実**:

1. `lookup('env', 'CLAUDECODE')`は、それを呼ぶタスクの`delegate_to`やプレイの対象ホストに関係なく、**常にansible-playbookプロセス自身(コントローラ)の環境変数**を読む。プレイの対象ホストを「到達不能な疑似リモートホスト」にしても(`delegate_to: localhost`より前に当該ホストへの接続を要求しない構成のため実際には到達を試みない)、結果は`CLAUDECODE`の有無だけで決まった。
2. `include_tasks`(動的include)経由でも、静的includeとの評価タイミングの違いは観測されなかった — 該当taskに実行が到達した時点で、その時点のコントローラ環境変数を素直に読む。
3. `set_fact`タスク自体は`--check`下でもスキップされず正常に実行される(`ansible.builtin.set_fact`はcheck_mode対応のためtrigger3の判定自体はcheck mode下でも壊れない)。

**結論**: notify.ymlの実装(`_slack_agent_session_detected`をset_factで一度確定させてからwhen:で参照する構成)は、include_tasksであることによる評価タイミングのズレやdelegate_toとの相互作用による誤判定の心配がないことを確認した。
