## 検証項目と結果

### 1. `--check` 実行で play が完走すること — PASS

実行コマンド:
```
ANSIBLE_LOCAL_TEMP=/tmp/ansible-local ANSIBLE_REMOTE_TEMP='/tmp/ansible-remote-$USER' \
ansible-playbook playbooks/ubuntu_nightly.yml --check -e skip_notifications=true \
-l monitoring_servers,radius_servers
```
- 終了コード: `0`
- PLAY RECAP:
  - `authy`: ok=9 changed=1 unreachable=0 failed=0 skipped=0 rescued=0 ignored=0
  - `monnie`: ok=9 changed=1 unreachable=0 failed=0 skipped=0 rescued=0 ignored=0
- `changed=1` は `Save skipped report`(`check_mode: false` でレポートJSONを書く既存タスク、変更対象外)。この結果ファイルは `reports/` 配下で `.gitignore` により追跡外(`git check-ignore` で確認済み)であり、リポジトリの状態には影響しない。
- `-e skip_notifications=true` を必ず付ける指示どおり付与済み。今回両ホストとも `reboot_required=false`(実機の実際の状態)だったため `meta: end_host` で play がホストごとに終了し、Slack通知タスク自体に到達しなかった。よって「通知が実際にスキップされたこと」はこの実行では確認できていない(下記「未実施」参照)。

### 2. `--check` 時に reboot 系タスクが skip されていること — 部分PASS(実機では未到達、decoyで意味論を確認)

- 実機の2ホストは今回とも `reboot_required=false` であり、`meta: end_host` が reboot ブロックより先に効くため、実機の `--check` 実行では reboot ブロック自体に到達しなかった(到達すれば `not ansible_check_mode` で丸ごとskipされる設計)。これは実装のバグではなく、今日この時点でのホストの実際の状態(reboot_required=false)による。Coordinatorの依頼にあった「reboot系タスクがskipされていること」を実機のみで直接観測することはできなかった。
- 代替として、該当ブロックの `when: not ansible_check_mode` ゲート構造だけを切り出したdecoy playbook(`ansible_connection: local`、実system非干渉)を作成し `--check` で実行:
  - `TASK [Reboot host (decoy)]` → `skipping`
  - `TASK [Wait for monitoring services (decoy)]` → 3ポートすべて `skipping`
  - RECAP: `ok=0 changed=0 skipped=2 rescued=0`
  - これは実playbookと同一の `when: not ansible_check_mode` ブロックゲート構造であり、Ansibleの意味論として `--check` 時にこのブロックが確実にskipされることを裏付ける。ただし実playbook本体そのものをこの経路で通したわけではない点は限定条件として明記する。

### 3. rescue文面がループ失敗・スカラー失敗の両方で正しく展開されること — PASS

decoy(`ansible_connection: local`、`command: true/false` のみ使用、実system非干渉)で、実装と同一のJinja式をそのまま3パターンに適用して確認:

| パターン | `_nightly_failed_task` | `_nightly_fail_reason` | `type_debug` | 備考 |
|---|---|---|---|---|
| ループタスク(3項目中item=2のみ失敗) | `Loop task that fails on one item` | `non-zero return code` | `str` | `ansible_failed_result.results` から `selectattr('failed')` で正しく抽出 |
| スカラータスク(単純失敗、`msg`あり) | `Scalar task that fails` | `non-zero return code` | `str` | `results` 未定義の分岐(`else`側)が機能 |
| スカラータスク(`failed_when: true`で`msg`が空文字列の縁エッジケース) | `Scalar task that fails via failed_when without msg` | `(理由が取得できなかった)` | `str` | **重要**: 空文字列 `msg: ""` を `default(..., true)` で正しく拾い、フォールバック文言になった。indicated incident(Noneや空文字列を見逃してlengthでクラッシュ)は再現しなかった |

3パターンとも `rescued=1` としてrescueへ正しく入り、後続の `debug` タスクまで到達、`type_debug` は一貫して `str`(NoneTypeではない)。クラッシュや空値の混入は観測されなかった。

## 未実施・観測できなかった項目

1. **実機での「reboot_required=true時の--check挙動」** — 今日時点で両ホストとも `reboot_required=false` だったため、実機では到達しなかった。次に `reboot_required=true` になる夜の実行時に、Slack「check-mode: reboot required」通知の内容と `reboot`/`wait_for` ブロックのskip表示を実機で確認することを推奨(この点はincidentファイルの残存リスクとも一致)。
2. **`skip_notifications=true` が実際にSlack送信を止めることの実行内での直接確認** — 今回の`--check`実行では通知タスク自体に到達しなかったため、フラグの実効性はコード読解(`roles/common_slack/tasks/notify.yml`の `when` 条件)による確認に留まる。decoyでの再現は行っていない(範囲外と判断)。
3. **monnie実機でのループバックへの`wait_for`到達性そのもの**(修正の中心的な狙い)は、reboot経路の実機検証がCoordinatorの指示で明示的に範囲外とされているため、今回検証していない。decoyの`when: not ansible_check_mode`ゲート確認とJinja式の安全性確認で代替した。
