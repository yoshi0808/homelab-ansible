## 確認結果

### 1. ROOT CAは独立した単一certificate fileとして配布される

- defaultsに追加されたsourceは `cert_renew_root_ca_src_crt: /home/yoshi/.cert/ca/radius_ca.crt` である。
- ROOT専用slurpは `cert_renew_ca_host`、現在のplayではquoryへdelegateされ、`run_once: true` で取得する。
- 配布先は `/usr/local/share/ca-certificates/home-tls-root-ca.crt`、owner/groupはroot、modeは `0644` である。
- 既存中間CAの `/usr/local/share/ca-certificates/home-tls-ca.crt` とは別ファイルであり、contentを連結する処理はない。
- 両destinationは `.crt` 拡張子を持ち、`update-ca-certificates` の1 file / 1 certificate前提を崩していない。
- 根拠調査ではsourceの `radius_ca.crt` が自己署名ROOT 1枚であること、中間 `home_tls_ca.crt` が別の1枚であることが確認済みである。

### 2. 秘密鍵を読まず、配らない

- 新規差分が追加するsourceは `.crt` だけである。
- `deploy_ca_trust.yml` に `.key`、`cert_renew_ca_src_key`、private key contentの参照はない。
- defaultsに以前から存在する中間CA署名用 `cert_renew_ca_src_key` は本task fileから参照されず、今回の差分でも変更されていない。
- `radius_ca.key` の変数、slurp、copy、destinationは追加されていない。

### 3. 既存中間CA処理は非回帰

`git diff`上、既存の次の処理には変更がない。

- `cert_renew_ca_src_crt` の値
- `Slurp CA certificate from source host` のsrc/register/delegate/run_once
- `Deploy CA certificate to system trust store` のcontent/destination/owner/group/mode
- 既存copyの `notify: update-ca-certificates`

ROOT処理は既存taskの後ろに追加されており、中間CAの配布先や変数を上書きしない。

### 4. handler集約と冪等性

- 中間copyとROOT copyは同じ `notify: update-ca-certificates` を使用する。
- handler定義は既存の単一 `update-ca-certificates` のままである。
- Ansibleのhandler queueでは同一handlerへの複数notifyはhostごとにdeduplicateされるため、両copyがchangedでも各hostでhandlerは1回実行される。
- ROOTだけ、または中間だけがchangedの場合も同じhandlerが1回実行される。
- 両copyは `content` とdestinationの既存内容を比較するため、内容・metadataが同一ならchanged=falseとなる。2回目no-op時はnotifyされず、handlerも発火しない。
- handlerの `check_mode: false` は既存のrisk-accepted方針を維持している。

### 5. risk-acceptedとcheck mode

動作上の回帰はない。

- `ca_trust_deploy.yml` のrisk-accepted headerは不変である。
- 唯一の呼び出し元は `import_role tasks_from: deploy_ca_trust` に `check_mode: false` を指定している。
- static importへ付いたtask keywordはimport対象taskへ適用されるため、既存中間copyと新規ROOT copyはどちらも `--check` 中に実実行される。
- よってROOT copyだけに追加されたtask-level `check_mode: false` は、現在の入口では挙動を変えない冗長指定である。

非対称性への判断は下記Suggestionのとおりであり、Must-fixではない。

### 6. host式は要求どおり全6hostへ展開される

playのhost式は変更されていない。

```text
control_nodes:dev_nodes:monitoring_servers:radius_servers:proxmox
```

`ansible-playbook --list-hosts` の展開結果は次の6hostだった。

```text
ansy
quory
monnie
authy
pve1
pve2
```

各groupは現在それぞれ意図した対象を含み、重複hostはAnsible inventory上で重複実行されない。このPKIを利用する管理・監視・認証・Proxmox nodeへsystem trust anchorを配る対象として妥当である。

## Suggestion

### ROOT copy固有の `check_mode: false` は外し、play入口をpolicyの単一管理点にする

該当箇所:

- `roles/homelab_cert_renew/tasks/deploy_ca_trust.yml:33`
- `playbooks/ca_trust_deploy.yml:33`
- `playbooks/ca_trust_deploy.yml:37`

現在の唯一の入口ではimport_role全体に `check_mode: false` があるため、ROOT copy固有の指定は不要であり、中間copyとの実動作差もない。

一方、将来このtask fileを別playから呼んだ場合は、ROOTだけ実変更し、中間はcheck-mode simulationになる非対称性が生じる。risk-acceptedはplaybook入口で明示された運用判断なので、既存中間copyへ指定を追加するより、新規ROOT copyから冗長な `check_mode: false` を外して既存taskと揃え、入口のimport_roleを単一のpolicy適用点にする方が明瞭である。

この整理を行わなくても、現行 `ca_trust_deploy.yml` の動作・安全性・冪等性は要求を満たすため、承認を妨げない。
