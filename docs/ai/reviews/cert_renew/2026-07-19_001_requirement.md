# 要求仕様: deploy_ca_trust に ROOT CA 配布を追加(信頼チェーン完結)

作成日: 2026-07-19
起票: claude(要件定義)
種別: 変更系(roles/homelab_cert_renew)

## 目的

各ノードのシステム信頼ストアに **自己署名 ROOT CA(`radius_ca.crt`)** を配布し、内部 TLS の
信頼チェーンを完結させる。現状は中間 CA しか配布しておらず、ROOT が無いため OpenSSL 系
クライアント(unpoller の verify_ssl=true 等)が `depth=1 中間CA / error 2 unable to get
issuer certificate` で検証失敗する。

## 背景 / 根拠(調査で確定済み)

- 調査記録: `docs/ai/reviews/misc/2026-07-19_ca_root_trust_investigation.md`(tester read-only)
- 確定事実:
  - PKI 構成は 2 階層。quory に **ROOT `radius_ca.crt`(自己署名, SKI=AKI)** と
    **中間 `home_tls_ca.crt`(issuer=ROOT, `CA:TRUE pathlen:0`)** が実在し、署名関係は正しい
    (中間 AKI = ROOT SKI、`openssl verify -CAfile radius_ca.crt home_tls_ca.crt` 成功)。
  - cloudkey は `leaf → 中間 → ROOT` の 3 枚を正しい順序で提示(サーバ側も正しい)。
  - しかし `roles/homelab_cert_renew/tasks/deploy_ca_trust.yml` は
    **中間 `home_tls_ca.crt` 1 枚だけ**を `/usr/local/share/ca-certificates/home-tls-ca.crt`
    に配布し、**ROOT を配る定義が無い**。
  - monnie の `/etc/ssl/certs/ca-certificates.crt`(122 枚)に 中間=1 / ROOT=0。
    中間の取り込み(update-ca-certificates の link)は正常 = **ドリフトではない**。
  - **ansy でも同じ depth1/error2 を再現** = monnie 固有ではなく **全ホスト共通の定義漏れ**。
- 分類: **主因=definition omission(ROOT 未配布)/ 併発=single-certificate 構成 /
  host drift は否定**。
- 既存の前例: `roles/cloudkey_cert_deploy/defaults/main.yml:23` が
  `cloudkey_root_ca_crt: "{{ cloudkey_ca_dir }}/radius_ca.crt"` として ROOT を認識済み
  (命名・役割の裏付け)。

## 対象

- ロール: `homelab_cert_renew`(`tasks/deploy_ca_trust.yml`, `defaults/main.yml`)
- 配布先ホスト: `ca_trust_deploy.yml` の対象 6 ホスト(ansy/quory/monnie/authy/pve1/pve2)。
  = `control_nodes:dev_nodes:monitoring_servers:radius_servers:proxmox`。play 側は変更不要。
- ソース: quory の `/home/yoshi/.cert/ca/radius_ca.crt`(公開証明書のみ。**秘密鍵は扱わない**)。

## 作成・更新ファイル

- `roles/homelab_cert_renew/tasks/deploy_ca_trust.yml`
- `roles/homelab_cert_renew/defaults/main.yml`

## 実施内容

### 1. ROOT CA ソースパスを defaults に追加

```yaml
# 既存
cert_renew_ca_src_crt: /home/yoshi/.cert/ca/home_tls_ca.crt   # 中間CA(据え置き)
# 追加
cert_renew_root_ca_src_crt: /home/yoshi/.cert/ca/radius_ca.crt # 自己署名ROOT CA
```

### 2. deploy_ca_trust.yml に ROOT の slurp + copy を追加

- 既存の中間 CA の slurp/copy は**そのまま維持**(dest `/usr/local/share/ca-certificates/home-tls-ca.crt`)。
- ROOT を **別ファイル**として追加配布する:
  - quory から `cert_renew_root_ca_src_crt` を slurp(`delegate_to: {{ cert_renew_ca_host }}`, `run_once: true`)。
  - `copy` で dest **`/usr/local/share/ca-certificates/home-tls-root-ca.crt`**(0644 root:root)、
    `notify: update-ca-certificates`。
- **重要(single-certificate gotcha 回避)**: ROOT を中間と同じ 1 ファイルに連結(bundle 化)
  してはならない。`/usr/local/share/ca-certificates/` は「1 ファイル 1 証明書」で
  `update-ca-certificates` が処理するため、**ROOT は独立した .crt** にする。ファイル名は
  `.crt` 拡張子必須。
- 両 copy が `update-ca-certificates` を notify するが、handler は 1 回に集約されればよい
  (既存 handler `update-ca-certificates` を流用、冪等)。

### 3. 冪等・no-op 挙動の維持

- CA 証明書は長期不変のため、通常は両 copy とも `changed=false` の no-op。
- ROOT 追加後の初回のみ changed → `update-ca-certificates` が走り、以後 no-op。

## 制約

- 既存の中間 CA 配布・変数名・play(`ca_trust_deploy.yml`)の host 式・通知/handler を壊さない。
- **risk-accepted 継続**: この playbook は `--check` を含め常に本実行する既存方針
  (`ca_trust_deploy.yml` ヘッダ, core.md §18)。ROOT 配布も同分類(サービス再起動なし・
  `update-ca-certificates` はバンドル再構築のみ)なので方針変更なし。`check_mode: false` を
  既存 copy に合わせて付与。
- **秘密鍵(`radius_ca.key` / `home_tls_ca.key`)は読まない・配らない**。公開証明書のみ。
- IP・秘密情報をリポに書かない([[feedback_no_ip_in_repo]])。
- 時刻表記 JST([[reference_repo_timestamp_jst_convention]])。

## 初回実装スコープ

- defaults に `cert_renew_root_ca_src_crt` 追加
- deploy_ca_trust.yml に ROOT の slurp + copy(独立ファイル)追加、既存中間はそのまま
- 既存 `update-ca-certificates` handler 流用

## 初回除外スコープ

- unpoller の `verify_ssl=true` 再適用(= 本修正 APPLY 後の**別ステップ**。
  monnie で `openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt <leaf>` が
  `0 (ok)` になったのを確認してから。[[project_unpoller_source_ip_and_verify_ssl]])
- ROOT ローテーション/世代管理・古い CA の削除(prune)。今回は追加のみ。
- 「Go(unpoller)は verify_ssl=true で通ったのに openssl は落ちた」差異の解明(別途)。

## テスト観点(tester 向け・APPLY 後)

- 全 6 ホストで `/usr/local/share/ca-certificates/home-tls-root-ca.crt` が存在(1 枚・ROOT subject)。
- 各ホストの `/etc/ssl/certs/ca-certificates.crt` に ROOT subject が **1 枚**含まれ、
  ROOT の subject hash に対応する `/etc/ssl/certs/<hash>.0` symlink が生成される。
- monnie で `openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt <cloudkey-leaf>` が
  **`OK` / return 0**。`openssl s_client -connect cloudkey.internal:443 -servername
  cloudkey.internal` の `Verify return code: 0 (ok)`。ansy でも同様に 0。
- 中間 CA(既存)の取り込みが非回帰(中間 subject も引き続き 1 枚)。
- 冪等: 2 回目の APPLY で両 copy が changed=false(update-ca-certificates 非発火)。
- **estate 全体の健全性確認(追加)**: cloudkey だけでなく、内部 TLS を張る別サービス
  (例 grafana HTTPS もしくは semaphore HTTPS)に対しても、いずれかのホストから
  `openssl s_client -connect <svc-host>:<port> -servername <svc-host>` の
  `Verify return code: 0 (ok)` を確認する。これは「semaphore/grafana/proxmox は中間だけで
  検証成功していた」という前提が実は未検証(verify_ssl=true でクライアント検証を踏んだ実績が
  cloudkey/unpoller が初)のため、ROOT 配布後に同種の穴が残っていないことを実証する目的。
  ROOT を anchor にすれば、サーバが leaf+中間 でも leaf+中間+ROOT でも chain が閉じる。

## shell / Ansible 責務分離

- shell: なし(`update-ca-certificates` は既存 handler の command のみ)。
- Ansible tasks: ROOT の slurp/copy 追加、handler 流用。
