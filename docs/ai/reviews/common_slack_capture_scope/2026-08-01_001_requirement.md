# requirement: 収集器のいないcontrollerでspoolレコードを書かない

日付: 2026-08-01
状態: **確定**(2026-08-01 Yoshinobu指示。選択肢を3つ示し「1でお願いします」)
関連: `docs/ai/adr/004-notify-capture-insertion.md`、`docs/ai/policies/incident_capture_policy.md` IC-004

## 1. 問題定義

`roles/common_slack/tasks/capture.yml` は通知1件につきspoolレコードを1件書く。書き先は `delegate_to: localhost` すなわち **`ansible-playbook` を実行しているcontroller側**である。

**捕捉はquoryでのみ行う(IC-004)。ansyに収集器は存在しない。** それにもかかわらず、ansyから流した実行(手動実行、Testerの `--check` 検証など)のレコードもansyの `reports/incidents/_spool/` へ書かれ、**消費する主体が無いまま蓄積していた。**

2026-08-01時点の実測:

| host | `_spool/` 件数 | 収集器 |
|---|---|---|
| ansy | **15**(最古は2026-07-27頃) | **無し** |
| quory | 2 | 有り(5分周期で消費) |

**性質としては「読み手のいない場所へ書き続けている」状態**であり、無限に増える。実害は小さいが、同じ欠陥クラス(キューへ書くが誰も読まない)を直前のIncidentで踏んでいる。

## 2. ゴール

**収集器が配備されていないcontrollerでは、spoolレコードを書かない。**

## 3. 非ゴール

- **どの通知を捕捉するかを内容で絞ること。** ADR-004 (c) / D7 のとおり、捕捉可能なcontrollerでは**すべての通知を無条件に捕捉する**。
- ansy側に収集器を配備すること(IC-004により捕捉はquoryのみ)。
- 保持期間の新設。
- `notify.yml`(送信側)の変更。

## 4. 要件

| # | 要件 |
|---|---|
| C1 | 収集器が配備されていないcontrollerでは、spoolディレクトリの作成もレコードの書き込みも**行わない** |
| C2 | 判定は**収集器の配備状態**で行う。**通知の属性(status / channel / title / message / tester_mode / skip_notifications)を条件にしない** |
| C3 | **判定に `capture_spool_dir` の存在を使わない。** 同ファイルの不変条件が「`capture_spool_dir` を存在しない/書けないパスへ差し替えてAC4を検証する」と定めており、AC4は**書き込みが試みられて失敗すること**に依存している。spoolの存在で門を作ると、その検証が「黙ってskip」に化けて成立しなくなる |
| C4 | 捕捉するcontrollerでの挙動を変えない(記録の内容・ファイル名・`_capture_written_id` の意味・footerの出方) |
| C5 | 捕捉しないcontrollerで、**通知そのものは従来どおり送られる**。captureの不在が送信に影響しない |
| C6 | `--check` での挙動を変えない(このファイルは従来から `--check` で何も書かない) |
| C7 | 既存の不変条件を壊さない — ACLへのchmod相当を持ち込まない、`assert`/`fail`/`ignore_errors` を使わない、`rescue:` は `debug` 1つのまま、外部I/Oを増やさない |

## 5. 受入条件

### AC1 — 収集器のいないcontrollerで書かれない

- **Given** ansy(収集器の設定ファイルが存在しない)
- **When** 通知を伴うplaybookをansyから実行する
- **Then** `reports/incidents/_spool/` に**新しいレコードが増えない**。ディレクトリが無い場合は**作られない**。playbookの終了コードは従来どおり

### AC2 — 収集器のいるcontrollerでは従来どおり

- **Given** quory(収集器の設定ファイルが存在する)
- **When** 同上
- **Then** レコードが**1件書かれる**。内容・ファイル名・footerのidが従来と同じ意味を持つ

### AC3 — 通知は止まらない

- **Given** 収集器のいないcontroller
- **When** 通知を伴うplaybookを実行する
- **Then** **Slack通知は従来どおり送信される**(captureの不在が送信経路に影響しない)。footerのcapture idは出ない

### AC4 — 内容による絞り込みが入っていない

- **Given** 収集器のいるcontroller
- **When** `slack_status` が `ok` / `warning` / `critical` のいずれの通知でも
- **Then** **すべて捕捉される**(ADR-004 (c) / D7 が変わっていないこと)

### AC5 — 既存のAC4検証手段が生きている

- **Given** 収集器のいるcontrollerで `capture_spool_dir` を存在しない/書けないパスへ差し替える
- **When** 通知を伴うplaybookを実行する
- **Then** 書き込みが**試みられて失敗し**、`rescue` が拾ってplayは継続する(黙ってskipされない)

### AC6 — 構文

- **Given** このファイル
- **When** `ansible-playbook --syntax-check` と `ansible-lint`
- **Then** 新規の指摘が出ない。**このファイルのYAML構文エラーはblock/rescueでは捕捉できずplayを殺す**(ファイル冒頭に明記)ため、構文の妥当性は必ず確かめる

## 6. この変更が覆している過去の判断

同ファイルのTASK-COUNT節は次を記録していた。

> NOT done: the spool-directory *creation* task was deliberately kept (not moved to deploy-time-only), per Coordinator decision — moving it to the incident_capture role's deploy-time setup would break capture on ansy (Tester's dev box), which never runs that role.

**この理由は成立していない。** ansyには収集器が無く、書かれたレコードを読む主体が最初から存在しない。「ansyでcaptureが壊れる」の「capture」に実体が無かった。**ただし当時の判断を誤りと断ずるのではなく、前提(ansy側にも消費者が現れる想定だったか)が今と違った可能性を残す** — `controller` フィールドが「quory in production, ansy under Tester」を区別するために置かれていることは、ansy側の記録にも用途を想定していた形跡である。**その用途は現時点で実装されていない。**

## 7. オープンクエスチョン

| # | 内容 | 扱い |
|---|---|---|
| Q1 | ansyに既にある15件をどうするか | **作業ツリー外へ退避する**(削除ではなく移動)。読み手が存在しないため保持する理由が無い一方、退避なら取り戻せる |
| Q2 | ansy側の捕捉に将来用途が生まれたら | そのときは**収集器をansyへ配備する**か、`capture_collector_marker` を指す先を変える。**この変更は「書くなら読み手を用意する」という不変条件を作るものであり、ansy側の捕捉を永久に禁じるものではない** |

## 8. 一次の制御は運用側にある(2026-08-01 Yoshinobu)

**「基本はansyから通知を実行しないこと」** — これがこの問題に対する一次の制御である。

**この変更はその代わりではなく、後ろの守りである。** ansyから通知を伴うplaybookを流す運用が無ければ、そもそもレコードは生まれない。今回の15件は、手動実行とTesterの `--check` 検証がansyから走ったことで積まれたものであり、**運用の線を引けば発生源が消える**。

したがってこの変更が担うのは、「線を越えた実行が起きたときに、読み手のいない場所へ書き続けない」ことに限られる。**この機構が入ったことをもって、ansyから通知系playbookを流してよいと読み替えない。**

## 9. 実装の変遷(記録)

初版は `ansible.builtin.stat` + `register` で配備状態を判定した。**独立レビューF1により差し替えた** — `register` が `ansible-lint` の `var-naming[no-role-prefix]` を1件増やし(実測: HEAD版4件 → stat版5件)、AC6「新規の指摘が出ない」を満たさなかった。

差し替え後は Jinja の `is exists` テストを `when:` に直接書く形とし、**タスクも変数も1つも増えていない**(実測: HEAD版4件 → 現行4件)。`when:` はもともとcontroller側で評価され、このblockは `delegate_to: localhost` であるため、**判定するファイルシステムと書き込む先が一致する**。

**あわせてCoordinatorの誤りを記録する**: 差し替え前、Coordinatorは「lintの指摘はHEAD版と同一(新規なし)」と報告していたが誤りだった。HEAD側の出力に `sort -u` を、作業ツリー側に `tail -6` をかけ、**加工の異なる出力どうしを突き合わせていた**。件数を数えるときは同じ加工を通すこと。

## 10. Q1(既存15件)の実施結果

**退避を実施した(2026-08-01、Coordinator)。** ansyの `reports/incidents/_spool/` にあった15件を、削除せずセッションのscratchpad配下へ移動した。移動後のansy側は0件。

**退避先は非永続領域である。** セッションが終われば失われ、後から同じ確認はできない。**そのことを承知のうえで、repo内へは戻さない** — `reports/` は `.gitignore` 済みであり、内部IPを含みうる生ログ相当の内容をcommit対象へ持ち込まないため(ADR-005 R-3)。**失われて困る内容は無い**: 各レコードは過去のSlack通知の写しであり、通知自体は送信済み、かつ読み手(収集器)がansyには存在しない。
