状態: **確定**(2026-07-31 Coordinator作成 → Policy改訂の承認を経て実装・配備・検証まで完了。**P0は全件実装済み、P1のR13は本ラウンドでは未実施**(§5参照)。以後この文書は当時の要求の記録として読む)

関連: `docs/ai/policies/incident_capture_policy.md`(要改訂。提案は `2026-07-31_003_policy_amendment_proposal.md`)、`docs/ai/adr/009-*`(実装方式)、既存の3段パイプライン(`docs/ai/reviews/incident_auto_capture/`、`.../incident_auto_capture_step2/`)

## 1. 問題定義

Semaphoreがスケジュール実行したplaybookが異常終了すると、現在は次までしか自動で起きない。

1. Semaphore自身のSlackアラート(ジョブ番号つき)が飛ぶ。
2. `homelab-incident-capture.timer`(5分毎)が証拠バンドル `reports/incidents/semaphore-<jobid>/` を作る。
3. `ansible-incident-sync.timer`(毎時)がansyへ複製する。
4. 月次の評価が、溜まったバンドルをまとめて読む。

バンドルは**起きたこと**を持つが、**なぜ落ちたか**は誰も書かない。Yoshinobuはジョブ番号を見るたびに、Semaphore UIを開くか、Slack経由でCodexへ都度依頼して原因を突き止めている。判断材料は揃っているのに、解釈だけが毎回人手にかかっている。

観測された事実を2つ挙げる。

- **playbook側の通知経路は、失敗時にはほとんど到達しない。** 捕捉が本番稼働していた2026-07-28〜30の失敗ジョブ9件のうち、`common_slack/notify.yml` の通知が記録されたのは1件(`ubuntu_nightly`)のみで、残り8件は `spool_records: 0` だった。Ansibleはタスク失敗時点でそのplayを止めるため、post_tasksの通知まで進まない。
- **月次評価まで待つと、その時点のホスト状態は失われている。** バンドルは収集時のスナップショットを持つが、解釈されないまま最長1か月滞留する。

## 2. ゴール

| # | ゴール |
|---|---|
| G1 | Semaphoreジョブが `error` / `stopped` で終わったとき、**人手を介さずに**推定原因がquory上のincident report群へ残る |
| G2 | 一次調査結果がansyへ複製され、Yoshinobuが修正依頼を起こす入力になる |
| G3 | 調査に使うLLMセッションが、復旧アクション・監視停止・muteを**構造的に**呼べない |
| G4 | 一次調査が壊れても、被観測playbookの終了コード・タスク結果の件数・所要時間が変わらない |

## 3. 非ゴール

- **自動修正・自動commit。** 将来やる意思はあるが今回は作らない。承認境界は「Yoshinobuのgit commit」のまま動かさない(`docs/ai/core.md`)。
- **Slack #alert への報告。** 当初の依頼に含まれていたが、2026-07-31にYoshinobuが「まだ安定していないので人が間に入る」と判断し今回の範囲から外した。**設計は後から足せる形にする**(P2 R14)。
- **`原因分類` タグの記入と `解決済み` への遷移。** 人の領域(IC-020)。
- **Semaphore以外(systemd timer等)で起きた失敗の調査。**
- **既知条件の自動除外判定**(IC-022の実装)。今回は記録する枠だけを持つ。
- **ansy側での調査。** 月次評価は現行のまま変えない。

## 4. ユーザーストーリー

- **Yoshinobuとして**、朝Slackで赤いジョブ番号を見たとき、ansyのミラーに既に推定原因が書かれていて、Semaphore UIを開かずに修正依頼を起こせる。
- **Coordinatorとして**、修正依頼を受けたとき、散文を読み解かずに機械可読な調査結果から着手できる。
- **月次評価として**、バンドルだけでなく一次調査の結論も読めるので、滞留や再発の判断が付く。

## 6. 受入条件

終了コードと観測点まで書く。スケジューラから起動される経路が2つ(Semaphore / systemd)あるため、どちらの成否判定に載るかを明示する。

### AC1 — 被観測への非干渉(正常時)

- **Given** quoryでSemaphoreがplaybookを実行する
- **When** そのplaybookが成功する
- **Then** 調査要求は生成されず、ジョブの終了コードは `0` のまま、PLAY RECAPの ok/changed/failed/skipped/rescued/ignored が導入前と一致する

### AC2 — 被観測への非干渉(失敗時)

- **Given** 同上
- **When** playbookがタスク失敗またはunreachableで終わる
- **Then** 調査要求が1件生成され、かつ**ジョブの終了コードは導入前と同じ値**(`2` / `4` など、失敗の種類に応じた既存の値)であること。調査要求の生成が終了コードを変えないこと

### AC3 — 未配備環境での無害性

- **Given** ansy(調査機構を配備していない)で任意のplaybookを実行する
- **When** 成功・失敗のいずれでも
- **Then** 何も生成されず、終了コードと標準出力が導入前と一致すること

### AC4 — 調査の成果物

- **Given** 未処理の調査要求がある
- **When** 調査が実行される
- **Then** `reports/incidents/_investigations/semaphore-<id>.json` と同名 `.md` が生成され、jsonが §7 のフィールドを持ち、調査unitの終了コードが `0` で `systemctl is-failed` が `failed` を返さないこと

### AC5 — LLMセッションの封じ込め

**2026-07-31改訂。** U0の実測により、当初想定していた「execpolicyで拒否させる」は成立しない(`2026-07-31_002_u0_test_result.md`、`docs/ai/memory/incidents/2026-07-31_codex-execpolicy-allowlist-not-enforcing.md`)。境界は**鍵とトークンの所有**で作る(ADR-009 (c) c-3)。

- **Given** 調査専用ユーザーで動くLLMセッション
- **When** `homelab-recover-*` / `homelab-investigate-*` に相当するコマンドを実行する
- **Then** SSH鍵を読めずに失敗すること。**この確認は、対象ホストへ到達しない形(鍵ファイルへのアクセス可否)で行い、復旧コマンドを実際に完走させない**
- **かつ** `homelab-semaphore-query` / `homelab-reports` に相当する読み取りは成功すること(**拒否と通過の両方を観測しない限り、境界が効いた証明にならない**)
- **かつ** promptから該当の禁止文言を削っても、この失敗と成功の関係が変わらないこと

### AC6 — 失敗の可視化

- **Given** LLM呼び出しがタイムアウトまたは非ゼロ終了する
- **When** 調査が実行される
- **Then** jsonに失敗した事実と理由が残り、調査unitが**非ゼロ終了**して `systemctl is-failed` が `failed` を返すこと。成果物が一切作られないまま静かに終わらないこと

### AC7 — 重複排除

- **Given** 同一ジョブ番号の調査要求が複数ある、または調査が多重に起動される
- **When** 実行される
- **Then** そのジョブに対する成果物が1組だけ存在し、LLM呼び出しが1回だけ行われること

### AC8 — 複製と保存

- **Given** `_investigations/` に成果物がある
- **When** 毎時の `ansible-incident-sync.timer` が走る
- **Then** ansyの `reports/incidents/quory/_investigations/` に現れること。**quory側で元が消えてもansy側は消えない**こと(同期は削除操作を持たない)

### AC9 — 公開情報と秘密情報

- **Given** 生成された成果物とunitのログ
- **When** 内容を確認する
- **Then** 内部IPアドレス・token・vault平文・webhook URLが現れないこと

## 7. 成果物のフィールド(`.json` が正)

確定はImplementerではなくここで行う。**将来の自動連携(R15)が散文を再パースせずに済むこと**が目的。

**この成果物は一次情報であって原因の確定ではない**(2026-07-31 Yoshinobu表明。開発=Claude Code と運用=Codex の分離と牽制)。真因の特定と修正の著述は開発側が行い、一次情報を修正へ渡すかはYoshinobuが判断する。**スキーマはこの線を反映する** — 観測された事実を先に置き、リポジトリ内のパス特定や修正差分の欄は持たない。

| フィールド | 内容 |
|---|---|
| `schema_version` | 1 |
| `semaphore_task_id` | ジョブ番号(特定できなければ `null` と、その事実を `notes` へ) |
| `template` / `playbook` | Semaphoreのテンプレート名 / playbookパス |
| `job_status` | Semaphoreが記録した最終ステータス |
| `investigated_at` | RFC3339・JST(+09:00)。裸のZ/UTCを書かない |
| `observations` | **観測された事実。** 失敗したタスク、返ってきたメッセージ、バンドルのスナップショットから読み取れる状態。生ログの転記はしない |
| `verdict` | 観測から読み取れる**一次的な所見**(1行)。**原因の確定ではない** |
| `confidence` | `high` / `medium` / `low` |
| `evidence_refs` | 参照したバンドル等のパス(内容は複製しない) |
| `known_condition` | 既知条件由来と見られるか(真偽 + 理由。判定基準はP1で決めない) |
| `status` | `new` / `failed`(人が拾ったかどうかは**書かない** — 判断の正本は `docs/ai/memory/incidents/`) |
| `llm_rc` | LLM呼び出しの終了コード |
| `notes` | 上に収まらない事実 |

**持たない欄**(意図的):

- `suspect_paths`(リポジトリ内の被疑パス) — **削除した。** 当初は将来の自動修正の入力として置いたが、コードのどこが原因かを特定するのは開発側の仕事であり、運用側にそこまで書かせると分離が崩れる。
- 修正差分・パッチに相当する欄 — 同じ理由(改訂案 IC-042)。

## 9. タイムライン考慮

- **Policy改訂の承認が実装の前提。** `incident_capture_policy.md` は事象ごとのLLM起動を明示的に禁じており(IC-003 / IC-005 / IC-006 / IC-007)、改訂なしにこの要求は実装できない。
- **quoryへの配備にはYoshinobuの手作業(`git pull --ff-only`)が要る。** quory作業ツリーの自動同期は2026-07-29に意図的に見送られている(`docs/ai/status.md`「載せていないもの」)。
- **実発火の観測は自然発生の失敗を待つ。** 検証は意図的に失敗するdecoyで行い、Semaphore経由の本番経路は次の実失敗をWatchに載せる。
