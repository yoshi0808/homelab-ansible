## 4. 境界が「鍵の不在」で成立していることの説明

`homelab-recover-authy`(`roles/recovery_exec/files/homelab-recover-authy`)は次のようにハードコードされている。

```
KEY=/home/recovery-exec/.ssh/id_recovery_action
...
exec ssh -T -F /dev/null -i "$KEY" ... "recovery-exec@authy.internal"
```

このキーファイルは`roles/recovery_exec/tasks/main.yml`「Lock down SSH key permissions」タスクで`owner: recovery-exec, group: recovery-exec, mode: "0600"`に固定されている。`incident-inspect`は`recovery-exec`のメンバーではなく(本roleは`recovery_exec_group_members`のような相互グループ追加を一切行わない)、`other`権限は0なので、`incident-inspect`のUIDで`homelab-recover-authy`(world-executable, mode 0755)を実行しても、`ssh -i $KEY`が鍵ファイルを開けず`Permission denied`相当で失敗し、`BatchMode=yes`によりパスワード等へのフォールバックも起きない。`homelab-recover-monnie`・`homelab-investigate-*`(投資対象外だが同型)も同じ`recovery-exec`所有の鍵(`id_recovery_investigate`/`id_recovery_investigate_pve`)を参照しており、同じ理由で失敗する。

同様に`homelab-monitoring-pause`(`/var/lib/recovery-exec/workspace/monitoring-paused`へ`touch`、workspaceはmode 0770 owner/group recovery-exec)や`homelab-mute-set`(`/var/lib/homelab-recovery/mute`はcreate-only 0755 + `recovery-exec`宛named ACL rwx、`other`はr-x)も、`incident-inspect`から実行すると書込み権限が無く失敗する — こちらは「鍵」ではなく「ACL/グループ非該当」が境界になっているが、根は同じ「能力の不在」である。AC5が要求する検証方法(鍵ファイルへのアクセス可否)はSSH系コマンドに対して直接該当し、非SSH系の2コマンドについては同型の権限境界として付記した。

`/home/yoshi`(§0の事故で実測: mode 0750, owner yoshi:yoshi)・`/var/lib/semaphore`(実測: mode 0710)・`/var/lib/semaphore/semaphore.db`(実測: mode 0640)はいずれも`incident-inspect`にACLを追加しない限り到達不能であり、本roleが追加するのはこの3箇所へのtraverse/readのみである。これにより「読み取りは通る・復旧は鍵が無くて失敗する」という、AC5が要求する両方向の観測が机上で説明できる状態になっている(実機での`sudo -u incident-inspect homelab-recover-authy`実行による直接確認はTesterの領域であり本記録では行っていない)。

## 5. 冪等性についての判断

`ansible.builtin.user`(既存なら無変更)・`ansible.builtin.file`/`template`(内容/属性が同じなら無変更)・`ansible.posix.acl`with`state: present`(既存エントリと同じなら無変更)・sudoersの`template`(内容が同じなら無変更)は、いずれも`roles/recovery_exec`が本番で採用し2回目実行でchanged=0になることが実証済みのモジュール使用パターンと同型である(`roles/recovery_exec/tasks/main.yml`のコメント「2回目以降のchanged=0」を参照)。**本roleについては実機での2回目実行を意図的に行っていない**(§0の事故を踏まえ、これ以上`ansible-playbook`を実行する行為そのものを避けたため)。したがって「配備playbookは繰り返し実行して結果が変わらない」は設計上の類推であり、実測ではないことを明記する。

冪等性を壊しうる箇所として自己点検した点:
- `mkdir`等の`creates:`を使うcommandタスクは本roleに存在しない(全て`file`/`template`/`user`/`acl`モジュールのみ)。
- `.codex`ディレクトリのmode 0700・workspaceのmode 0750は初回作成時から固定値であり、`reports/incidents/`のような「既存ACLを持つ共有ディレクトリへの`mode:`付きfileタスク」には該当しない(このユーザー専用ディレクトリであり、ACL mask書き換えのリスク自体が構造的に存在しない)。

## 6. 選ばなかった選択肢とその理由

- **`--sandbox workspace-write` + `writable_roots`制限で書込みを絞る案**: ADR-009 (c) c-3の表は`network_access = false`という`recovery_exec`と同じキーの言及に留まり、sandbox modeそのものの選択(`read-only`か`workspace-write`か)を明示していない。要件R6/IC-035「LLMにファイル書込権を与えないこと」を字義どおり満たすには、workspace-writeで書込先を制限するより`--sandbox read-only`で書込機構自体を無くす方が構造的に確実と判断した。デメリットは`[sandbox_workspace_write]`セクションが実質的に不使用になる点だが、ADRの文言との対応が取れるようコメントで明記して残した。
- **`execpolicy`テーブルを配備しない案**: U0で無効と判明済み(効いていない)ため、いっそ設定自体を書かない案も検討したが、`recovery_exec`が同じ状況で「意図の記録として残す」判断をしている(`codex-config.toml.j2`のコメント参照)ため、本roleも同じ扱いに揃えた。将来`.rules`ファイル機構等で有効化される可能性に備え、削除より保持を選んだ。
- **ACL付与数**: ADRのConsequences節は「ACL 2件」と書いているが、本実装は`/home/yoshi`traverse・`/var/lib/semaphore`traverse・`semaphore.db`read の3タスクになっている。これは`recovery_exec`自身が同じ目的のために既に3タスク(traverse×2 + read×1)を使っている実装と完全に同型であり、ADRの「2件」はおそらく「semaphore.dbアクセス」と「reports/traverse」を2つの論理単位として数えた大まかな表現だと解釈した。件数の食い違いは実装判断であり、必要なら次工程で確認してほしい。
- **incident-inspectをrecovery-execグループへ追加する案**: 検討していない(そもそも境界を壊す方向の変更であり、要件と正反対)。
- **ワークスペースdirのmode**: `recovery_exec_workspace`は0770(グループ書込み、`recovery_exec_group_members`にyoshiを追加して相互読み書きさせるため)だが、`incident-inspect`のワークスペースは`sudo -u incident-inspect`経由でのみ触られる想定であり、グループ経由の共有アクセスが要件に無いため0750(グループはread-onlyにすらしていない実質的な意味は無いが、`incident-inspect`の主グループがそのまま設定されるため実害なし)とした。
