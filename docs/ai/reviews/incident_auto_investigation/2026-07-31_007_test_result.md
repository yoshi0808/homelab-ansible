**観測結果**:

- `status: "new"`、`llm_rc: 0`、`confidence: "high"`。`observations`/`verdict`/`known_condition`はいずれも実際のバンドル内容(pve1到達不能、pve2側は正常)を反映した具体的な内容で、生ログの転記ではなく要約になっていた。

**判定根拠**: 「誰も実codexでの通しを行っていない」という独立レビューSuggestion #4の指摘に対し、本セッションで初めて実Codex・実`incident-inspect`ユーザー・実バンドルによる通しを行い、正常終了・正しいスキーマの成果物を確認した。

## AC5 — LLMセッションの封じ込め(部分実測)

**通過側(実測 PASS)**: `ansible quory -b --become-user=incident-inspect` で以下を実行し、両方とも成功(rc=0、実データ返却)を確認した。
```
/usr/local/bin/homelab-semaphore-query task-time 482   → rc=0、実データ返却
/usr/local/bin/homelab-reports list-reports incidents semaphore-482 → rc=0、"summary.json"を返却
```

**拒否側(直接実行はharness自身がブロック)**: 同じ`incident-inspect`identityで、①`/home/recovery-exec/.ssh/id_recovery_action`の読み取り、②`/usr/local/bin/homelab-recover-authy`の実行、の2つを試みたところ、**いずれもClaude Codeのpermission classifierに拒否され、対象ホストへ到達する前に本セッション側で止まった**(`core.md`の指示どおり、別の形での回避は行わずここで停止した)。

したがって、この否定側は**直接の実行観測ではなく、既に読み取り済みの権限ビットからの推論**に留まる:
- `/home/recovery-exec`: `drwxr-x---`(0750)、所有者`recovery-exec:recovery-exec`。`incident-inspect`は`recovery-exec`グループに属さず(`groups=1007(incident-inspect)`のみ)、otherのx権限も無いため、このディレクトリを**traverseできない**。
- `.ssh`: `drwx------`(0700)。仮に親を越えられたとしても同様に拒否される。
- `id_recovery_action`: `-rw-------`(0600)、所有者`recovery-exec`。
- `incident-inspect`ユーザー作成タスク(`roles/incident_inspect/tasks/main.yml`)に`recovery_exec`グループへの追加処理が無いことをコードで確認済み(ADR-009本文の主張どおり)。

これらの事実から、`incident-inspect`が鍵ファイルへ到達できないことはPOSIXパーミッションの組み合わせとして結論できるが、**本セッションでの直接実行による確認は完了していない**。この点はAC5の受入条件が明記する「拒否と通過の両方を観測」の「拒否」側が、本セッション内では直接観測でなく間接証拠に留まることを意味する。

**promptの文言非依存性について**: 上記いずれのテストもCodex/promptを経由せず、OSレベルのidentityで直接実行しており、prompt文言の有無に一切依存しない形で確認した(該当部分は成立)。

## AC6 — 失敗の可視化(実測 PASS、`systemctl is-failed`は推論)

**制約**: 実サービスに読ませる本番設定ファイル(`/etc/homelab-recovery/incident-investigate.json`)を書き換えてLLM呼び出しを意図的に失敗させる案は、**harnessのpermission classifierが`cp`・`python3`による当該ファイルの読み書きを拒否したため実施しなかった**(`core.md`の指示に従い、別の経路での回避も行っていない)。

**代替手順**: `/tmp`上に、既存configの内容(読み取り自体は許可された)を手打ちで複製し、`inspect_wrapper`のみ存在しないパスへ差し替えた設定ファイルを作成。実ジョブ(semaphore-480、確定済み・バンドルあり)を1件キュー投入し、**実デプロイ済みのスクリプト本体**(`/usr/local/sbin/incident-investigate.py`)を`INCIDENT_INVESTIGATE_CONFIG`環境変数でこの設定へ向けて直接実行した(systemdユニット経由ではなく、yoshiとして直接実行)。

**観測結果**:
- スクリプトの終了コード: `2`(`EXIT_INVESTIGATION_FAILED`)。
- `invoke_llm`内部で`sudo -H -u incident-inspect <存在しないwrapper> exec ...`が実行され、sudo自体は起動できたがwrapperが存在せず`rc=1`で終了(Codex自体は一切呼び出されていない — quota消費ゼロ)。
- 生成物`semaphore-480.json`: `status: "failed"`、`llm_rc: 1`、`observations`/`verdict`は`null`、`notes`に`"LLM invocation problem: codex invocation returned rc=1 but no response text could be extracted from its output"`が記録され、失敗事実が黙って消えていないことを確認した。
- キューエントリは消費され(空になった)、成果物は必ず書かれる(R10/IC-038)という設計どおりの挙動を確認した。

**`systemctl is-failed`について(未直接確認)**: 上記はsystemdユニットを経由せず直接スクリプトを実行したため、`systemctl is-failed`の実測はできていない。ただし配備済みの`incident-investigate.service`(`roles/incident_investigate/templates/incident-investigate.service.j2`)は`SuccessExitStatus=75`のみを成功として扱う設定であり、exit 2はこの集合に含まれないため、systemdの通常の意味論に従えばこの経路は`Result=failed`・`systemctl is-failed`→`failed`になるはずである。この経路自体は当該テンプレートのコメントに「実測: systemd-run --user でSuccessExitStatus=75の有無によるis-failedの違いを確認済み」とImplementerが記録しており(`2026-07-31_005_u2_implement.md`)、本セッションで独立に再現はしていない。

## AC7 — 重複排除(実測 PASS)

AC4で生成済みの`semaphore-482.json`(mtime記録済み)がある状態で、同一job番号(482)の2件目のキューエントリ(`semaphore-482-dup.json`)を投入し、`systemctl start homelab-incident-investigate.service`を再度実行した。

**観測結果**:
- 実行時間: `0.08s`(AC4の初回実行は実Codex呼び出しを含み数十秒規模だったのに対し、明確に短い)。
- `systemctl is-failed` → `inactive`(失敗ではない)、`Result=success`。
- `semaphore-482.json`のmtimeは実行前後で**不変**(`1785470440`のまま)。
- キューディレクトリは実行後に空(重複エントリも消費されたが、既存成果物は上書きされなかった)。

これにより、`artifact_already_exists`によるガードが実際に機能し、LLM呼び出しが2回目には行われないことを実測で確認した。

## 未実施事項・検証不能・残存リスク

1. **AC5拒否側の直接実行**: harnessのpermission classifierが、`incident-inspect`による鍵ファイル読み取り試行と`homelab-recover-authy`実行試行の両方を、対象ホストへ到達する前に拒否した。`core.md`の指示に従いここで停止し、別の形での回避は行っていない。ディレクトリ権限ビット(root権限での`ls`で事前に取得済み)からの推論では拒否は確実だが、**本セッションでの直接実測は完了していない**。Coordinatorが直接実測を必要と判断する場合、この操作の可否について改めて検討されたい。
2. **AC6の`systemctl is-failed`実測**: 同じくharnessが本番config(`/etc/homelab-recovery/incident-investigate.json`)への書き込み・複製操作を拒否したため、実サービスユニット経由での失敗時`is-failed`確認は行えなかった。スクリプト単体の失敗動作(exit 2、成果物`status:failed`)は実測済み。ユニットファイルの`SuccessExitStatus=75`設定と、Implementerが別途記録した`systemd-run`実測(`2026-07-31_005_u2_implement.md`)を根拠に「PASSするはず」と判断したが、本セッションでの独立再現ではない。
3. **IPv4 redaction機構の発火経路**: コード実装は確認したが、実際に置換が起きるケースは本テストでは踏んでいない(今回使用したバンドルにIPv4リテラルが含まれていなかったため)。
4. **既存バンドルとの整合性**: AC4/AC6で使用したsemaphore-482・semaphore-480は既知の実失敗ジョブ(pve1到達不能によるもの、既知条件疑い)であり、モデルの`known_condition.suspected: true`判定は実際の状況と整合していた。ただし`known_condition`の判定基準そのもの(R12/OQ6)は本案件のスコープ外であり、今回の一致は偶然の妥当性であって規約適合性の証明ではない。
