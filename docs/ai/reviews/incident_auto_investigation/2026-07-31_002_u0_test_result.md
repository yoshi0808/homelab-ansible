## M1(主目的): 基底設定が許可しているコマンドを、追加の設定層で拒否させられるか

**結論: できなかった。試した3つの機構(`--profile`層、`-c`によるexecpolicy上書き、専用`CODEX_HOME`への書き直し)のいずれでも、基底で許可されているコマンドを拒否させることはできなかった。**

### 検証環境

quory上、`recovery-exec`ユーザーの実`~/.codex/config.toml`・`auth.json`を**コピー**した独立ディレクトリ(`/tmp/tester_m1_codexhome`、本番ディレクトリとは別物)を作り、そこへ`CODEX_HOME`を向けて`codex exec`を直接起動した(本番wrapperは経由していない)。codex-cli 0.145.0。

### 実施した4回のcodex exec呼び出し(すべて実モデル呼び出し、課金対象)

1. **profile層でexecpolicyを絞る**: `readonly.config.toml`という名前のprofileファイル(`default_policy="deny"`、allowは`homelab-reports`/`homelab-semaphore-query`のみ)を`CODEX_HOME`に置き、`--profile readonly`を付けて`homelab-mute-status`を実行させた → **成功**(拒否されなかった)。
2. **ベースライン(絞りなし)で execpolicy allow-list に無い任意コマンド**: 本番と同一内容のconfig.toml(`default_policy="deny"`、allowは`homelab-*`のみ)のまま、allow-listに一切無い`id`を実行させた → **成功**(`uid=1004(recovery-exec)...`が返った)。default_policy="deny"であっても、allow-listに無い任意コマンドがそもそも通ることを確認した。
3. **`-c`によるexecpolicy + approval_policy上書き**(初回、シェルクォート起因の疑いで再実施): `-c 'execpolicy.default_policy="deny"'` `-c 'execpolicy.rules=[...]'` `-c 'approval_policy="untrusted"'`を付けて`homelab-mute-status`→`homelab-semaphore-query recent-failed 3`の順に実行させた → **両方成功**。banner上の`approval:`表示は`never`のまま変化しなかった。
4. **専用`CODEX_HOME`のconfig.tomlに直接`approval_policy = "untrusted"`と絞ったexecpolicyを書き込み**(`-c`を一切使わず、CLIオーバーライドの疑いを排除): 同じく`homelab-mute-status`→`homelab-semaphore-query recent-failed 3`の順で実行 → **両方成功**。banner上の`approval:`は依然`never`。

### 一般的な`-c`上書き機構自体は機能することの確認(sanity check、5回目の呼び出し)

`-c 'model="gpt-5.5-mini"'`を付けたところ、banner上の`model:`表示が実際に`gpt-5.5-mini`に変わり、さらにOpenAI側から「'gpt-5.5-mini' model is not supported...」という具体的なエラーが返った(オーバーライドがリクエストまで伝播した確たる証拠)。**つまり`-c`によるオーバーライド機構そのものは機能している**。にもかかわらず`approval_policy`だけは`-c`でも、専用CODEX_HOME直書きでも、`never`から動かなかった。

### 解釈(推測を含む)

- `codex exec`(非対話モード)は`approval_policy`の設定値によらず内部的に`never`相当で動作している可能性が高い(非対話実行では承認者が存在しないため)。**これは推測であり、codex-cliのソースやドキュメントで直接確認したわけではない。**
- `[execpolicy]`のルール(`default_policy`/`rules`)は、少なくとも`codex exec`+`approval_policy=never`の組み合わせでは、コマンド実行そのものをブロックするハードゲートとして機能していない。`--strict-config`検証では`execpolicy`キーは「認識されないフィールド」としては弾かれなかった(スキーマ自体は認識されている)ため、キー名のtypoではない。
- 実行できるコマンド自体が、本番の`sandbox_workspace_write.writable_roots`(ファイルシステム書き込み制限)やSSH鍵・sudoers等の**別レイヤ**で制約されている可能性はあるが、これは本測定の範囲外であり未確認。

## M2: リポジトリの`ansible.cfg`がSemaphore実行に効いているか

**結論: 確定はできなかったが、「効いている」と推定できる状況証拠が複数得られた。**

- Semaphoreはテンプレートごとにリポジトリ全体をチェックアウトしており(`/opt/semaphore/project_1/repository_1_template_<N>/`)、そのチェックアウト直下にリポジトリの`ansible.cfg`がそのまま存在する(内容を比較し、リポジトリ側と完全一致を確認)。ansible-playbookは通常この位置(カレントディレクトリ)の`ansible.cfg`を自動検出するため、Semaphoreが何も上書きしなければ効くはずの配置になっている。
- `/etc/semaphore/config.json`、`systemctl cat semaphore.service`(`Environment=`行)、稼働中semaphoreプロセスの`/proc/<pid>/environ`のいずれにも`ANSIBLE_CONFIG`環境変数は見つからなかった(=明示的な上書きの形跡なし)。
- `ansible.cfg`の`vault_password_file = ~/.ansible/vault/homelab_vault_pass`について、Semaphoreサービスは`User=yoshi`(`HOME=/home/yoshi`)で動いており、`/home/yoshi/.ansible/vault/homelab_vault_pass`は実在する。チェックアウト内には`ANSIBLE_VAULT`形式の暗号化ファイル(`inventories/vars/cloudkey.yml`等)も存在する。これらのplaybookがSemaphore経由で定期実行されていること自体は既知(cronによるscheduled task)であり、`ansible.cfg`のvault設定が効いていなければ復号に失敗するはずの構成である。
- **未確定の理由**: Semaphore自身が独自のVault機能(Key Store経由でvaultパスワードをSemaphore側管理にする機能)を使っている可能性を排除できていない。これを確認しようとしてSemaphoreのsqlite DB(`/var/lib/semaphore/semaphore.db`の`project__template_vault`テーブル)へSELECTを1件投げたところ、**harnessのpermission classifierにブロックされた**。ブロックの妥当性は判定せず、別経路での回避も行わず、そこで停止した。
- 確定するには、実際に稼働中のSemaphoreタスクプロセスの`/proc/<pid>/cwd`と`/proc/<pid>/environ`をタスク実行中にリアルタイムで観測するか、Coordinator/Yoshinobuの判断でDBの`project__template_vault`テーブル(vault方式の列だけ、実値は見ない)を確認する必要がある。

## M3(best-effort): `SEMAPHORE_TASK_DETAILS_`に続くフィールド名

**結論: 確定できた。ジョブ番号は`SEMAPHORE_TASK_DETAILS_ID`。**

- quory上のquoryバイナリ(`/usr/bin/semaphore`)の`strings`出力ではフォーマット文字列`SEMAPHORE_TASK_DETAILS_%s`のみが見え、`%s`部分(実行時に決まる変数名)は静的文字列としては見えなかった。
- 公開されている`semaphoreui/semaphore`のGitHub上のソースを読み取り専用で確認した(quoryへの操作は伴わない)。インストール版と同じ`v2.18.4`タグのtarballを取得し、`services/tasks/LocalJob.go`内の`getTaskDetails`関数と、それを`fmt.Sprintf("SEMAPHORE_TASK_DETAILS_%s", strings.ToUpper(taskDetail))`で環境変数化する箇所(184-185行相当)を確認した。
- `v2.18.4`のtaskDetailsマップのキー(大文字化されて環境変数名の末尾になる)は以下の通り:
  - `id` → `SEMAPHORE_TASK_DETAILS_ID`(ジョブ番号)
  - `message`(Task.Messageが空でない時のみ)→ `SEMAPHORE_TASK_DETAILS_MESSAGE`
  - `username` → `SEMAPHORE_TASK_DETAILS_USERNAME`
  - `url` → `SEMAPHORE_TASK_DETAILS_URL`
  - `commit_hash` → `SEMAPHORE_TASK_DETAILS_COMMIT_HASH`
  - `commit_message` → `SEMAPHORE_TASK_DETAILS_COMMIT_MESSAGE`
  - `inventory_name` / `inventory_id` → `SEMAPHORE_TASK_DETAILS_INVENTORY_NAME` / `_INVENTORY_ID`
  - `repository_name` / `repository_id` → `SEMAPHORE_TASK_DETAILS_REPOSITORY_NAME` / `_REPOSITORY_ID`
  - Task型テンプレート以外(`type`, `incoming_version`, `target_version`)は今回のスケジュール実行(通常Taskテンプレート)には該当しない。
- インストールされているのが本当に`v2.18.4`のビルドかは`semaphore --version`相当の表示(バックグラウンドで既に共有された情報)に基づく前提であり、quory上でバイナリのビルド情報から直接ソースと突き合わせたわけではない(ソース側の確認はGitHub上の公開tarballのみ)。
