# Proxmox weekly full: 件数超過を退避の前で止める — requirement

日付: 2026-09-20 (JST)
状態: 着手前(Yoshinobu承認、2026-09-20)

## 1. 問題定義

**weekly full chainの適用ゲートと、apply roleの停止条件は、別の基準で判定している。**

| 段 | `MAJOR_UPGRADE_DETECTED` の根拠 | 実装 |
|---|---|---|
| dry-run段(chainの2bゲートが読む) | Codexの分類結果 `major_upgrade_suspected` | `roles/proxmox_patch_dryrun/tasks/main.yml:286` |
| apply段(再dry-run) | **更新候補の件数 > `proxmox_patch_apply_major_upgrade_threshold`** | `roles/proxmox_patch_apply_node/tasks/main.yml:282` |

そのため、**2bゲート(`playbooks/proxmox_patch_weekly_full.yml:370-378`)を通過したうえでapplyだけが落ちる組合せが構造的に存在する。** このときchainは既にmuteと退避を済ませている。

- **最初の副作用は退避ではなくmuteである。** chain自身のStep 2c(`playbooks/proxmox_patch_weekly_full.yml:495-532`)が、2bゲートを通過した直後にauthy / monnie / sophos-fwへ**360分**のmuteを張る。`proxmox_evacuate_node.yml:35-57`の120分muteはその後で、`recovery_mute`の`max()`規則により実効の残りは360分側が支配する。
- 退避は`proxmox_evacuate_node.yml`本体。
- chainは`import_playbook`の直列であり、apply playがfailした時点でrunが終わるため、**`proxmox_patch_weekly_full.yml:702`の`proxmox_restore_vm_placement.yml`へ到達しない。**

**実測(一次記録の参照)**: 2026-09-19のジョブ#1164で、走ったplayは`Set recovery mute`→`Evacuate target_node`→`Proxmox patch apply (single node)`(中止)であり、復帰は走っていない。この日は後続の#1167が完走して結果的に片付いた。出典は`docs/ai/reviews/proxmox_major_upgrade_threshold/2026-09-19_006_closeout.md` §4および`docs/ai/status.md`。**Coordinatorが本案件で自ら再観測したものではない。**

**あわせて確認した事実(2026-09-20、`ssh quory-investigate "semaphore-query template-list 30"`)**: 本番のtemplate #7 `UN-SAFE: Proxmox patch weekly full` は `arguments: "[]"` で `survey_vars` キーを持たない。repo側カタログ`roles/semaphore_templates/defaults/main.yml:145-147`と一致しており、**ドリフトではなく設計どおりである。** 手動確認の口は#8 `UN-SAFE: Proxmox patch apply node`(survey 3つ)にある。

## 2. ゴール

1. **翌朝のapplyが件数で止まる見込みの週は、chainが退避とmuteの前にclean-skipで終わる。**
2. 閾値の出所を増やさない。

## 3. 非ゴール(今回やらない)

- **applyが実処理(download / apt / reboot)で失敗したときに復帰を通すこと。** 本案件のゲートはpre-changeの停止だけを扱う。実処理の失敗は人の対応が要る本物の失敗であり、直すなら`_apply_abort_type`でpre-changeのabortだけを選別する別案件になる。
- **超過したnodeだけを除外して他nodeを適用すること(per-node除外)。** 現行の2bゲートはcluster単位でclean-skipする設計であり、そこへ別の粒度を混ぜない。
- **template #7へのsurvey_vars追加。** 週次chainは無人実行前提で、手動確認の口は#8に既にある。承認の入口を増やさない(EXEC-060)。
- **2段の`MAJOR_UPGRADE_DETECTED`が同名で別基準であることの統合。** `proxmox_major_upgrade_threshold`案件の closeout §5 が申し送り済み。
- **閾値の値(100)の見直し。**

## 4. ユーザーストーリー

運用者として、件数超過の週に土曜朝のジョブが止まったとき、**VMが退避先に残ったまま・muteが張られたままにならないでほしい。** 止まる理由が通知で分かり、必要なら#8と#10を自分の判断で回したい。

### 5.1 判定factの契約(P0)

**2bゲートとforecastの間の受け渡しは、人向けの警告文字列を再利用せず、専用の構造化factで行う。** 現行の`_apply_forecast_node_warnings`は表示用の文字列listで、超過なしの正常週は空listになる。これをそのまま判定材料にすると「正常」と「判定不能」が同じ形になる。

| 項目 | 契約 |
|---|---|
| fact名 | `_apply_forecast_apply_gate` |
| 型 | dict |
| `evaluated` | bool。判定を実施したこと自体を表す。**この値が`true`でなければ判定不能である** |
| `threshold` | int。apply roleのdefaultsから読んだ値 |
| `blocking_nodes` | listで、要素は`node`(str)と`update_count`(int)を必ず持つdict。**空listは「超過nodeなし」という有効な値であり、判定不能ではない** |
| host scope | 既存の予告factと同じく`run_once` + `delegate_to: localhost`(`delegate_facts`無し)で置かれるため、`_final_status`と同じhostに載る。2bは既存の`_status_host`探索(`playbooks/proxmox_patch_weekly_full.yml:365-370`)と同じ方法で参照する |
| 判定不能とするもの | factが未定義 / factがdictでない / `evaluated`が`true`でない / `threshold`がintでない / `blocking_nodes`がlistでない / `blocking_nodes`の要素に`node`または`update_count`が無い |
| **判定不能に含めないもの** | `node`が文字列でない、`update_count`が整数でない、という**要素の値の型**。2bゲートは`blocking_nodes`が空かどうかしか見ず、これらの値は通知文にしか使われないため、consumer側の停止条件にしない。**producerが正しい型で入れることはAC10が担保する** |

**表示用の`_apply_forecast_node_warnings`は残す。** 通知文はそのまま使い、判定だけを本factへ移す。
