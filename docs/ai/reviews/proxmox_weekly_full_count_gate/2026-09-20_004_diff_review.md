## 観点別所見

### 要求外の実装

見当たらない。変更対象は要求§9が想定する2ファイルのみ。新規defaultsファイルや閾値の複製は無い(AC8)。

### §5.1 fact契約の成立

- producer(`apply_forecast.yml` L13-26): `_apply_forecast_apply_gate`は`_pre_status == 'NEEDS_CLASSIFICATION'`のときのみ`run_once`+`delegate_to: localhost`(delegate_facts無し)で生成され、`evaluated: true`固定・`threshold`は`| int`・`blocking_nodes`は`node`/`update_count`を持つdictのlist。producerが空listを返す入力(閾値以下のnodeのみ)では`blocking_nodes: []`となり、これは契約どおり正常値。
- consumer(playbook L406-420): `evaluated is sameas true`・`threshold`の`type_debug == 'int'`・`blocking_nodes`の`type_debug == 'list'`をassertし、いずれか欠落/型不正でfail。空listはこのassertを通過し(assert 2の`select('mapping')|length == blocking_nodes|length`は`0==0`で自明に真)、後続の`length > 0`判定でproceedへ倒れる。**正常週の空listと判定不能が構造的に別経路になっている。**
- §5.1の「判定不能に含めないもの」(`node`/`update_count`の値の型)は、consumer側のassert 2が`selectattr(..., 'defined')`のみでキーの存在だけを見ており、値の型を検査していないため、要件どおり除外されている。

### 閾値以下の週が止まらないこと(最大リスク)

- L406-420のassertは`blocking_nodes`の長さに関わらず必ず実行されるが、正常週(空list・型正しい)ではすべて真になり通過する。
- L432-457の新規skip blockは`when: _wf_apply_gate.blocking_nodes | length > 0`でガードされており、空listのときは実行されず、L461「Set per-node targets...」以降の既存proceed経路へそのまま流れる。
- 新規taskは既存の`when: not (_wf_proceed | bool)`block(L383-404)の**後**に位置し、かつその既存blockは`meta: end_play`で終わるため、新規assert/skip blockは`_wf_proceed`がtrueの経路(PATCH_READY/MAINTENANCE_REQUIRED無removeでdry-runがnode covered)でしか到達しない。既存のclean-skip/fail判定を横取りしていない。
- 結論: 閾値以下の週を誤って止める経路は無い。

### 既存のclean-skip/failとexit code

- `NO_UPDATES`/`MAJOR_UPGRADE_DETECTED`/removeあり`MAINTENANCE_REQUIRED`は、旧来どおりL383-404のblock内で`meta: end_play`により新規task群へ到達する前に終わる。`BLOCKED`/`UNKNOWN`も同blockの`fail`タスクで新規task群に到達しない。AC6が要求する既存分岐・exit codeへの影響は無い。
- 新規skip blockの`_weekly_full_skip: true`は既存の単一node guest-blocked skip(L520-547)と同じ変数・同じ`meta: end_play`パターンを再利用しており、後続の全play(Step 2c mute L563, evacuate L602/696, apply L619/711, healthcheck L643/731, restore L676/757, 完了通知 L773)が既存の`hostvars['localhost']['_weekly_full_skip']`ガードでそのまま抑止される(AC3)。完了通知playはL773で`_weekly_full_skip`がtrueなら`meta: end_play`し、"Weekly Full Patch Complete"のtitleを生成しない(AC2後半)。

### 新factが生成されない週(`_pre_status != NEEDS_CLASSIFICATION`)での2bの挙動

- `main.yml`のL283-292(`_final_status`算出)を見ると、`_final_status`が`PATCH_READY`または`MAINTENANCE_REQUIRED`になるのは`_pre_status == 'NEEDS_CLASSIFICATION'`の分岐(elif/else)経由のみで、`_pre_status != 'NEEDS_CLASSIFICATION'`のときは`_final_status`が`_pre_status`(`BLOCKED`または`NO_UPDATES`)にそのままコピーされる。
- したがって、weekly full chain内(Step 2aが同一runで`proxmox_patch_dryrun.yml`をimportしてからStep 2bが読む構成、L328/L351)では、「`_wf_proceed`がtrueかつ`_apply_forecast_apply_gate`が未生成」という組合せは到達不能。新規assertが実務上fail-closedとして発火するのは、facts自体が壊れた/欠落した異常系(hostvars探索ミス等)のみであり、AC9が想定する金曜dry-run単独実行(`proxmox_patch_dryrun.yml`単体)はこのassertを経由しない producer 側のみの経路。

### check mode(`# tester-gate: check-mode-native`)

- 新規assert/set_fact/`meta: end_play`はいずれもstate変更を伴わず、check mode下でも通常どおり実行される。
- 新規Slack通知はheader既存の`slack_status: "{{ 'info' if ansible_check_mode else 'warning' }}"`パターンを踏襲し、実送信は`common_slack/tasks/notify.yml`側の`ansible_check_mode`無条件抑止(2026-07-31 R3)に委ねている。呼び出し側で`check_mode: false`を付けていないため、二重抑止にも二重送信にもなっていない。

### 閾値の複製

`grep`で`proxmox_patch_apply_major_upgrade_threshold`のrepo全体の出現箇所を確認し、値を持つのは`roles/proxmox_patch_apply_node/defaults/main.yml`のみ。2bゲート(playbook側)はdefaultsを読まず、producerが計算済みの`_wf_apply_gate.threshold`だけを参照している(AC8)。
