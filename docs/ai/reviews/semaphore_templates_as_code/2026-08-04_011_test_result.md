## 6. 残存リスク

1. **root所有0600の実tokenファイルをtoken.ymlが正しく読める、という組み合わせが、quoryでの本番初回実行まで誰にも実地確認されていない。** fixtureはダミー文字列、Testerの実API検証は非root所有ファイルの迂回。技術的リスクは低いと判断するが未確認である事実は残る。
2. **quoryのproject/inventory/repository名、TLS/CA状態、`become`可否はすべて未確認の仮定のまま。** 誤っていてもR9-b(fail-closed)により日次検査は赤くならないが、`semaphore_probe_error`findingが毎朝出続ける状態になりうる。
3. **`roles/semaphore_templates/defaults/main.yml` L351-354のコメント例(`validate_certs`既定のまま`ansy.internal`へ向ける)は、CAのKeyUsage問題により実際には動かないことを実測した。** 次にこの例をそのまま使おうとする作業者を誤らせる。この差分の対象外ファイルなので本検証では修正していない
4. **probe.ymlのrescue(独立レビューCritical #1対応)がTLS/API失敗の実際の例外形状を捕まえられるかは、閉ポートfixtureでのみ確認されており、ansyで実測したCERTIFICATE_VERIFY_FAILEDという具体的な例外形状そのものでは確認できていない**(token.ymlのroot要求のため到達できなかった)。例外の捕まえ方(`block`/`rescue`)自体はAnsibleの一般的機構であり、例外の種類(Jinja式のAttributeErrorか、uriモジュールのFailedError系か)によって振る舞いが変わる余地は低いと判断するが、完全な一致ではない。
