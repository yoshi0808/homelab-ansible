## 2. 判断の根拠

### 2.1 R9-c: 選んだ接続の形

**probe.ymlはSemaphore role自体の既定値(`quory.internal` / `validate_certs: true`)を変えず、呼び出しsite(`roles/deployment_drift_check/tasks/semaphore_probe.yml`のinclude_role `vars:`)だけで上書きする形にした。** role既定値そのものを`localhost`/`validate_certs: false`へ変更する選択肢もあったが、それだと「role自体の恒久の望ましい値」と「CA問題が解消するまでの回避」が同じ変数の中で区別できなくなる(`docs/ai/status.md`のWatch行が指す独立案件が終わったとき、defaults/main.ymlの値をそのまま正しい値として使えなくなる)。呼び出しsideでの上書きなら、独立案件が終わったときに`deployment_drift_check/defaults/main.yml`の2行を削除するだけで恒久値(role既定)へ自動的に戻る — 「戻せる形」の実装そのものをこの2行に持たせた。

具体的な値(`https://localhost:3000/api` + `validate_certs: false`)は、requirement本文が明示する「P0のブートストラップtemplateと同じ形を踏襲する」の指示をそのまま採用した。ブートストラップtemplateのsurvey既定値自体はrepo外(Semaphore UI上)にあり参照できないが、`docs/ai/status.md`のWatch行(「root CA が KeyUsage 拡張を持たず」の項)がその値を記述しており、そこから転記した。

**seamの置き場**: token→resolve→read→reconcileの4段を`roles/semaphore_templates/tasks/probe.yml`という新規タスクファイルへまとめ、`deployment_drift_check`側は`include_role: tasks_from: probe`を1回呼ぶだけにした。代替案として「`deployment_drift_check`側でblock/rescueを持ち、`semaphore_templates`の各taskを直接importする」形も検討したが、却下した — token scrubの正規表現やno_logの扱いは`semaphore_templates_token`という`semaphore_templates`role内部の変数に依存しており、role境界をまたいでこのロジックを複製すると、tokenの変数名が将来variantすればdeployment_drift_check側の複製が気づかれずに古いまま残るリスクがある。**「失敗を外へ出さない」責務は、tokenを扱うroleの内部に置く方が安全**という判断。

`probe.yml`のrescueは`tasks/main.yml`のrescue(token scrub → TLS原因の切り分け → `fail`で再送出)とほぼ同じscrubロジックを重複して持つ。共有(例えば`import_tasks`でscrub部分だけ切り出す)も検討したが、**両者は「例外を握り潰さない」(main.yml)と「例外を外へ出さない」(probe.yml)という正反対の目的を持つ**ため、間接化すると呼び出し側を読むたびに「今回はどちらの意味か」を確認する負荷が生まれると判断し、重複(約10行)を許容した。

### 2.2 R10-a: `-l` が落ちることの扱い

requirement本文は「ボタンには引数が無く、押すと play の `hosts:` 全体へ流れる。復元という目的には上位集合で足りるため許容し、判断をコード側のコメントへ残す(通知本文へは書かない)」と既に決めている。実装はこれをそのまま採用し、**通知本文には`-l`相当の情報を一切出さない**(`直し方: Semaphoreで「{{ name }}」を押す`のみ)。コード側のコメントは`roles/semaphore_templates/defaults/main.yml`のR7セクション(既存、P0で書かれた「引数は空、対象は各playbookの`hosts:`に委ねる」という決定)がそのまま該当し、R10-aのために新しいコメントを追加する必要は無いと判断した — 同じ設計決定を指しているため、二重に理由を書くと将来どちらかだけが更新されて食い違う。

複数候補(AC3)のときも同様に、`run_host`情報は一切出さない(`Semaphoreで次のいずれかを押す — A / B`)。個々の候補がどのホストへ向くかはSemaphore側のsurvey定義(`target`パラメータ等)が持っており、`-l`と同じ理由でrepo側の通知が代弁する情報ではないと判断した。

### 2.3 OQ3: orphansの期待値を「件数」で持つ判断

requirement は「実装判断に委ねる」とした上で「件数で持つ場合、1件消えて1件増えた状態を見逃すことを記録へ残すこと」を要求している。**件数を選んだ**。

理由:
- 識別子集合(既知orphanの`id`集合)で持つ案は、実運用で最初にreconcileが走ったときの実際の`id`(quory側でSemaphoreが採番する、実行時にしか分からない値)を`deployment_drift_check`側のdefaults/main.ymlへ手で転記する必要があり、**その転記自体がYoshinobuの実行を待たないと埋められない**(このセッションはquoryへ到達できない)。件数(`1`)は、requirement文中に既に確定した事実として書かれている(「現在1件(ブートストラップtemplate)が正常な状態」)ため、実装時点で埋められる。
- 名前集合で持つ案(idより安定に見える)も検討したが、ブートストラップtemplateの名前はUI手作業の対象であり、他の34本と異なりこのrole自身が`description`マーカーを書き込まない(自己参照を避けるためカタログに含まれない、OQ3(P0側)参照)。**名前の一致検査に頼ると、Yoshinobuがブートストラップtemplateを改名しただけで誤検知する**。

盲点(既知のまま許容): `_orphans | length`が`deployment_drift_check_semaphore_expected_orphans`(既定1)と一致している限りfindingを出さない。したがって「ブートストラップtemplateのマーカーが消えて`orphans`から外れ(orphan扱いされなくなる)、かつ別の1件が新たにorphanになる」ケースは、件数(1)が変わらないため検出できない。この盲点はTester/運用の観測(`report-show semaphore-templates latest.json`のorphans一覧を月次等で目視する)で補うほかなく、本実装のスコープには含めていない。

2. **OQ2(このrequirement文書の未解決事項)**: quoryの実行identityが`become`できるか。できなければAC6の失敗系(fail closed)に落ちるが、それ自体が正しく動くかは(a)を通して確認できる。
3. **AC7の実inventory版**: `ansible-playbook playbooks/deployment_drift_check.yml --check`を実inventoryに対して実行し、書き込み系APIコールが1件も発行されないことをquory側のSemaphoreアクセスログ等で裏付けられるなら追加確認する(コード上は構造的に保証済みなので必須ではない)。
4. **`deployment_drift_check_semaphore_api_base_url`/`validate_certs`の値が実際にquoryのCA問題を回避できるか** — §2.1の値はrequirement文中の記述からの転記であり、quoryで実行するまで正しさを確認できない。誤っていればAC6の失敗finding(rc=0のまま)に落ちるだけなので安全側だが、**「毎朝failed findingが出続ける」状態になる可能性がある**ことは運用上把握しておく価値がある。
5. **OQ3の盲点(§2.3)**: 「1件消えて1件増えて orphans の件数が変わらない」ケースを、実運用で定期的に`orphans`一覧を目視するような形で補うかどうかは、Coordinator/Yoshinobuの運用判断に委ねる。
