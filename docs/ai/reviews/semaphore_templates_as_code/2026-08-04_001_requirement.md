# requirement: Semaphoreテンプレートをrepoの正本にする(Step 1)

作成日: 2026-08-04
Coordinator: claude

## 1. 問題定義

**Semaphoreのテンプレートは「本番で人が押せるボタン」そのものであり、その定義がリポジトリの外にある。**

2026-08-04 に `semaphore-query template-list` を追加して初めて全量を読んだ(34本。id は 36 まであるが 13 と 18 が欠番で、実在は34)。分かったこと:

1. **定義がUIの手作業でしか作られていない。** Semaphoreを構成するroleはこのリポジトリに存在せず(`homelab_cert_renew` が証明書を配る箇所のみ)、テンプレートの名前・引数・survey varsはGitのどこにも無い。
2. **手で命名した結果、表記が揺れている。** `UN-SAFE` と `UNSAFE`、コロン後の空白の有無、`Cert_renew` のようにアンダースコアが残るもの。Yoshinobu表明(2026-08-04)「私が命名するとドリフトの元になる。何らかの定義を元に命名してほしい」。
3. **setup系playbook 12本のうち、テンプレートがあるのは3本だけ。** 残り9本は、ドリフトが検出されても**押すボタンが存在しない**。2026-08-04に導入した「直し方」の案内は12本すべてに対してコマンドを出すが、その4分の3は人の操作面から実行できない。
4. **人の役割との不一致。** Yoshinobu表明(2026-08-04)「リスクを理解して判断するのが私の役目であって、コマンドを流すのが私の仕事ではない」。判断に必要な情報はAIが揃えられるが、**押すボタンの定義が人の手作業に残っている**。

## 2. ゴール

1. **テンプレート定義をリポジトリの正本にする。** 名前・playbook・引数・survey varsをrepoが持つ。
2. **名前を定義からレンダリングする。** 人は分類とラベルを選ぶだけで、文字列を打たない。
3. **quory上で冪等にreconcileする。** ansyへ新しい能力を一切増やさない。
4. **ボタンが無いsetup playbook 9本にボタンを与える。**

## 3. 非ゴール

- **Semaphore本体(アプリ・DB・設定)の導入や更新のAnsible化。** 今回の対象はテンプレート定義だけである。
- **inventory / repository / environment / schedule の管理。** これらもrepo外だが、今回は触らない。scheduleを触ると定期実行の停止を招きうる。
- **ansyからSemaphoreを操作する経路。** APIの呼び出しはquory上でのみ行う。2026-08-04にC案(Semaphore schedule化)・D案(forced commandによる配備起動)を却下した判断と同じ線を維持する。
- **テンプレートの削除。** §5 R5 を参照。定義に無いものを消さない。
- **`tester-gate` と CLASS の一致検査。** §5 R8 の理由により、作らない。

## 4. ユーザーストーリー

- Yoshinobuとして、押すボタンの一覧と意味を**Gitの差分として**レビューしたい。UIを開いて目視で確認したくない。
- Yoshinobuとして、ボタンの名前を自分で考えたくない。**分類を選べば名前が決まる**形にしたい。
- Coordinatorとして、ドリフトの「直し方」を**実際に押せるボタンの名前**で案内したい。いま案内しているCLIコマンドは、Yoshinobuの操作面と一致していない。

## 5. 要件

### P0(必須)

**R1. 定義スキーマ**

新規role `semaphore_templates` の `defaults/main.yml` にテンプレート定義のカタログを置く(`deployment_drift_check` のカタログと同じ流儀)。1エントリが1テンプレートに対応し、次を持つ。

| フィールド | 必須 | 内容 |
|---|---|---|
| `playbook` | ○ | `playbooks/*.yml` の相対パス |
| `class` | ○ | 固定enum `SAFE` / `SEMI-SAFE` / `UN-SAFE` / `SANDBOX` |
| `variant` | — | 同じplaybookに複数テンプレートがあるときのラベル(`dry-run` / `apply` / `check` など) |
| `title` | — | 表題の上書き。省略時は `playbook` から機械変換 |
| `arguments` | — | CLI引数の配列。既定は空 |
| `survey_vars` | — | Semaphoreのsurvey定義(現在の値をそのまま持つ) |
| `class_reason` | — | R8参照 |

**実スキーマに存在する列だけを扱う。** `project__template` の列は2026-08-04に実測済み(`docs/ai/context/system/semaphore.md`)。存在しない列を定義に持たせない。

**R2. 名前のレンダリング**

```
name = "{class}: {title}{ (variant)}"
```

- `title` 省略時は `playbook` のbasenameから機械変換する(`.yml` を除去、`_` を空白へ、先頭を大文字)。
- `title` の上書きを許すのは、**ファイル名が対象を正しく表していない場合**があるためである(実例: `playbooks/radius_healthcheck.yml` の現在の表題は `SAFE: Authy healthcheck` で、対象ホスト名の方が人には分かりやすい)。上書きもrepo内でレビューされるため、UI手編集とは別物として扱う。
- **`class` と `variant` は人が選ぶが、名前の文字列は人が打たない。**

**R3. reconcile role**

quory上で実行し、Semaphore REST API 経由で定義を反映する。

- **冪等であること。** 同じ定義に対して2回目以降は変更を出さない。
- **既存テンプレートの同定は `playbook` + `variant` で行い、`name` では行わない。** 名前はレンダリング結果であり変わりうるため、名前で同定すると改名のたびに新規作成になる。
- `--check` で**適用せず差分だけを出す**こと(R6)。

**R4. API tokenの置き場**

- **tokenはリポジトリに置かない。** quory上のファイル(root所有・0600)から読む。
- **ansy側にtokenを置かない。** ansyからSemaphoreを操作できる状態を作らない。
- tokenが読めない場合は、**推測や代替経路へ回らず停止する**(終了コード非ゼロ)。

**R5. 削除しない**

**定義に無いテンプレートをAPIで削除しない。** 削除は「人が押せるボタンが黙って消える」ことであり、取り違えたときの被害が作成・更新と非対称である。定義に無いものは**報告する**に留め、消すかどうかはYoshinobuが判断する。

**R6. 適用前に差分を出す**

初回適用は34本の既存テンプレートに触れる。**何がどう変わるかをYoshinobuが読んでから適用できること。**

- `--check` 実行で、①新規作成されるもの ②名前・引数・surveyが変わるもの(変更前後) ③定義に無い既存テンプレート、の3つを出す。
- この出力は**判断の材料**であり、`docs/ai/roles/coordinator.md` の「一次情報 → 検証意見 → 判断」の一次情報にあたる。

**R7. ボタンの無いsetup playbook 9本を定義に含める**

現在テンプレートがあるのは `incident_investigate_setup` / `recovery_exec_setup` / `dev_investigate_setup` の3本のみ。残りをすべて定義へ入れる。**引数は空**とし、対象は各playbookの `hosts:` に委ねる(2026-08-04に `-l` を巡って実際に混乱が起きたため、引数を持たせない形を既定とする)。

**R8. `class` と `tester-gate` の食い違いには理由を1行持たせる。検査はしない**

両者は**別の軸**である。`tester-gate` は「Testerがどう実行してよいか」、`class` は「押すと本番に何が起きるか」を表す。実測(2026-08-04):

- `safe-readonly` の playbook が `SAFE` にも `SEMI-SAFE` にもなっている
- `risk-accepted` の playbook が `SAFE` になっている
- `check-mode-native` の playbook が `SEMI-SAFE` / `UN-SAFE` / `SANDBOX` の3つに散る(同じplaybookでも変数で本番影響が変わるため)

**一致検査を作ってはならない。** 正しい状態に対して警告が出続け、いずれ誰かが「揃える」方向へ壊す。代わりに、食い違うエントリにだけ `class_reason` を1行持たせる。既知の2件は次のとおりで、いずれもYoshinobuが2026-08-04に判断済みである。

| playbook | class / tester-gate | 理由 |
|---|---|---|
| `proxmox_backup_restore_verify` | `SAFE` / `risk-accepted` | 復元先VMIDは999に固定(assertで他の値を拒否)、NIC切断で起動し判定後に破棄する。既存VMには影響しない |
| `proxmox_patch_dryrun` | `SAFE` / `safe-readonly` | `apt-get update` でパッケージリストを更新するため厳密にはread-onlyではないが、パッケージ状態は変わらない。Policy §7 が「分類名から副作用ゼロを推定しない」と明示している範囲内 |

### P1(すべき)

**R9. 定義と実物の一致をドリフト検査で見る**

`deployment_drift_check` の枠組みへ、テンプレート定義とSemaphore実物の突合を加える。**Step 0で `template-list` が読めるようになったため、初めて可能になった。**

**R10. 「直し方」をテンプレート名で言えるようにする**

2026-08-04に導入した `直し方: ansible-playbook <playbook> -l <host>` は、Yoshinobuの操作面(Semaphore)と一致していない。定義がrepoに来れば、`playbook` からテンプレート名を**導出ではなく参照で**引ける。

### Won't

- テンプレートの削除(R5)
- schedule / inventory / environment の管理(§3)
- `tester-gate` との一致検査(R8)

## 6. 受入条件

**AC1(R3): 冪等である**

- **Given** 定義と実物が一致している状態
- **When** playbookを通常実行する
- **Then** `changed=0` で終わり、終了コードは **0**。APIへの書き込みリクエストが1件も発行されない

**AC2(R6): 適用前に差分が読める**

- **Given** 定義と実物が食い違う状態
- **When** `--check` 付きで実行する
- **Then** 新規・変更(前後つき)・定義に無い既存、の3分類が出力され、**APIへの書き込みは発行されず**、終了コードは **0**

**AC3(R2): 名前がレンダリングされる**

- **Given** `class: UN-SAFE` / `playbook: playbooks/prometheus_update_check.yml` / `variant: rollback` の定義
- **When** 適用する
- **Then** 実物の名前が `UN-SAFE: Prometheus update check (rollback)` になる(現在の `UNSAFE:Prometheus rollback(Manual)` の表記ゆれが解消する)

**AC4(R3): 改名しても新規作成されない**

- **Given** 既存テンプレートに対し、レンダリング結果が現在の名前と異なる定義
- **When** 適用する
- **Then** **同じ `id` のまま名前が更新される**(新しいidのテンプレートが増えない)。ジョブ履歴とscheduleは `template_id` を参照しているため、これが崩れると過去の履歴が切り離される

**AC5(R5): 削除しない**

- **Given** 定義に存在しないテンプレートがSemaphoreにある状態
- **When** 適用する
- **Then** そのテンプレートは**残っており**、報告にだけ現れる

**AC6(R4): tokenが無ければ止まる**

- **Given** tokenファイルが存在しない、または読めない状態
- **When** 実行する
- **Then** 明確なメッセージで停止し、終了コードは**非ゼロ**。APIへのリクエストは発行されない

**AC7(R7): 9本にボタンができる**

- **Given** 適用後のSemaphore
- **When** `ssh quory-investigate "semaphore-query template-list 200"` を実行する
- **Then** setup系playbook 12本すべてに対応するテンプレートが存在し、いずれも `arguments` が空である

**注(2026-08-04)**: この文言は当初、新設9本だけを想定して書かれており、既存3本のうち `incident_investigate_setup` が観測時点で `["-l quory"]` を持つことと衝突していた(Testerが機械確認で検出)。**Coordinatorの判断で、この1件は転記せず空へ揃える** — `-l quory` は無効果(playが `hosts: quory` 単独であることを `--list-hosts` で実測)であり、2026-08-04にCoordinatorの誤った助言で当日設定されたもので、他の全テンプレートは `arguments` を空にしてsurvey側にパラメータを持つ既存の流儀に反するため。**転記原則の例外はこの1件のみ。**

**AC8: 秘密が残らない**

- **Given** 適用の実行ログとレポート
- **When** 読む
- **Then** API tokenが平文で現れない(`no_log` 等で抑止されている)

## 7. オープンクエスチョン

- **OQ1: Semaphore APIのバージョンとエンドポイントの形。** `project__template` のDBスキーマは実測済みだが、**APIは未確認**である。実装はまず**読み取り系だけで到達性と応答形式を確かめてから**書き込みへ進むこと。
- **OQ2: tokenの発行方法と置き場の具体。** UIから発行する必要がある可能性が高く、その場合はYoshinobuの手が1回要る。
- **OQ3: ブートストラップ。** このplaybookを流すためのテンプレート自体は手作りになる。**そのテンプレートを定義に含めるか、除外するか。** 含めるなら、自分を更新する経路が生まれることを踏まえた扱いが要る。
- **OQ4: `project_id` / `inventory_id` / `repository_id` の扱い。** 実測ではすべて `1` だが、定義に固定値として持たせるか、実行時に解決するか。

## 8. タイムライン考慮

- **AIからquoryへは到達できない。** Implementer / Reviewer は実ホストに触れず、Testerも認証情報を持たない。**APIの実挙動を確かめられるのはYoshinobuがSemaphoreから流したときだけである。**
- したがって工程は「ローカルで確かめられるところまでを固め、`--check` の差分をYoshinobuが読み、適用はYoshinobuが押す」形になる。**これはこの案件の主題そのもの**(判断は人、実行はSemaphore、確認はAI)であり、制約であると同時に最初の実演でもある。
- 初回適用は既存34本に触れる。**R6の差分出力をYoshinobuが読むまで、適用は行わない。**

## 検証方針

- レンダリング規則・定義の妥当性・冪等判定のロジックは、**ローカルで検証する**(実データを転記した定義に対し、レンダリング結果が期待どおりか)。
- API呼び出しは、**到達できないため実地検証をACの一部として残す**。`--check` の差分出力が最初の実地観測点になる。
- `ansible-lint` と `--syntax-check` を通す。

## 工程

Implementer 1体 → Reviewer 1体(独立)。**Testerは起動しない**(実ホストへ到達できないため、起動しても検証できない)。実地の観測はYoshinobuの実行によって得る。

## 追補(2026-08-04): ansy の Semaphore で実測できるようになった

Yoshinobu表明(2026-08-04)「ansyのsemaphoreは使い放題」。API token を ansy 上のファイルへ置いてもらい、**本番へ触れずに API の実挙動を確かめられるようになった**。§8 の「APIの実挙動を確かめられるのはYoshinobuがSemaphoreから流したときだけ」という前提は、**テンプレート定義のAPI操作に関しては解消した**(ジョブを起動しないため、鍵も本番も関与しない)。

### 実測で崩れた仮定(2026-08-04、`https://ansy.internal:3000`)

| 仮定 | 実測 |
|---|---|
| `project_id` / `inventory_id` / `repository_id` は `1` 固定 | **ansy では全て `2`**、quory は `1`。**固定値で持たせてはならない** |
| `arguments` は配列 | APIは**文字列**で返す(`"arguments":"[]"`) |
| `project__template` のDBスキーマが扱うべき列の正本 | APIは `environment_id` / `environment_ids` を返すが、**この列はDBスキーマに無い**。**APIの形が正本**である |

R1 の「実スキーマに存在する列だけを扱う」は、**DBスキーマではなくAPIの応答形式**を指すものとして読むこと。

### 追加の要件

**R11(P0). 同定情報を Semaphore のオブジェクト自身に持たせる**

`legacy_name` + ローカル state ファイルによる2段構えの同定を廃止する。レビューが再現した failure(初回適用で名前が書き換わった後に state ファイルを失うと、`legacy_name` はもう一致せず、34本が重複作成され本物は永久に更新されなくなる)は、**正本が2箇所にある構造そのものに由来する**。

- 同定キーは Semaphore 側のオブジェクトが持つこと。`description` 列は現在34本すべてで空であり、管理キーの置き場として使える。
- **`description` が API で往復するかを実測してから採用すること。** 往復しないなら別の置き場を選び、理由を記録する。
- 採用した場合、`description` は管理対象フィールドになる。

**R12(P0). `project_id` / `inventory_id` / `repository_id` は名前で解決する**

固定値を定義に持たせない。実行時に API から名前で引く。ansy と quory で値が異なることが実測で確定している。

**R13(P0). PUT の意味論を実測する**

全置換か部分更新かを ansy で確かめ、**全置換であれば管理外フィールドを読み出してから書き戻す**(取得→マージ→送信)。レビュー指摘のとおり、全置換なら UI で設定された `autorun` 等が次の reconcile で無言で消える。

### 実測の境界

- **ansy の Semaphore(`https://ansy.internal:3000`、project id=2)のみ**を対象とする。
- **ジョブを1つも起動しない。** テンプレートの作成・更新はジョブ実行ではない。
- ansy の Semaphore には既存テンプレート(`id=4` ほか)と実行履歴がある。**既存を変更・削除しない。**
- quory の Semaphore へは到達しない(手段も無い)。
