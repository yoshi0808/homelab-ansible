## 2. 設計判断とその根拠

### 2.1 git操作とAnsibleの分離(契約どおり)

`worktree-sync.sh`(systemd timerがflock越しに起動)が git fetch / status / merge --ff-only を行い、それ以外は一切しない。通知が必要になったときだけ、`cd $REPO_DIR && ansible-playbook playbooks/worktree_sync_notify.yml -e @<json>` を呼ぶ。playbook側(`worktree_sync_setup.yml`・`worktree_sync_notify.yml`)はgitコマンドを一切実行しない。`docs/ai/core.md`「playbook自身にGit更新を行わせない」を満たす。

### 2.2 `git pull --ff-only` ではなく `git fetch` + `git merge --ff-only`

「既に最新か」を判定してから初めて通知要否・Semaphore確認要否を決める設計のため、fetchを先に独立させた(`git pull --ff-only`だと内部でfetchとmergeが一体化し、「今回は変更なしだった」の判定に出力パースが要る)。動作としては`git pull --ff-only`と等価。

### 2.3 Semaphore実行中判定

requirement §6.1のSQLをそのまま使用(`SELECT count(*) FROM task WHERE status NOT IN ('success','error','stopped')`)。`yoshi`はsemaphore.dbの所有者としてACL無しに読める(F-11)ため新規権限なし。**sqlite3コマンド自体が失敗した場合も「実行中」側に倒す**(判定不能なら安全側)。DBパス・sqlite3バイナリパスはrole defaultsとしてテンプレート変数化した(`worktree_sync_semaphore_db` / `worktree_sync_sqlite_bin`) — `homelab-semaphore-query`のような複数呼び出し元を持つ共有CLIと違い、この値を使うのはこのroleだけなので、Testerがsandbox dbに差し替えてdecoy検証できるようにする狙い。

### 2.4 見送り(defer)の観測性

`STATE_DIR/defer_count`に連続見送り回数を書く。**Semaphore起因の見送りでのみ**カウントし、「既に最新」「dirty tree停止」「pull成功」「pull失敗(non-ff)」の各終端では0にリセットする(dirty tree停止時はカウンタに触れない — このカウンタの意味を「Semaphore見送りの連続」に限定するため。dirty tree自体は毎回必ず通知するので別途無音になる心配がない)。閾値`worktree_sync_defer_notify_threshold: 3`の倍数ごとに通知する(1回目では鳴らない=AC-B-2充足、以後も鳴り続けるので「1回だけ鳴って以後沈黙」という別の無音化を作らない)。スケジュールは`incident_capture`と同じ5分間隔を踏襲。**3・5分という数値はImplementerの設計判断であり、Yoshinobu/Reviewerの確認候補。**

### 2.5 通知チャネルの割り当て

`worktree_sync_notify.yml`は`sync_status`が`error`/`warning`なら`alerts`、`ok`なら`info`へ振り分ける(`cert_renew_quory.yml`と同じ流儀)。既存の`recovery_probe_notify.yml`を再利用しなかった理由: そのplaybookは常に`alerts`固定、かつメッセージ本文が「検知時刻/送信時刻の差はインターネット断中のキュー保留」という recovery-probe 固有の文脈を前提にしており、そのまま使うと意味的に誤った説明文が本番Slackに出る。専用の小さいplaybookを新設した。

### 2.6 本番有効化は host_vars 経由(`-e`の渡し忘れ対策)

`worktree_sync_service_enabled`の既定値は`false`(配備のみ、timerは起動しない)。本番quoryでは`inventories/homelab/host_vars/quory.yml`から`true`を供給する。`incident_capture_setup.yml`(ヘッダコメントで`-e`渡しを案内)ではなく`recovery_probe_setup.yml`(host_varsに真実を置く)の流儀を採った — 後者は「`-e`の渡し忘れがsha256sumやgit diffでも見えない」という実際のインシデント(2026-07-29)を踏まえた設計であり、同種の問題形状(quory専用・timer駆動)にはこちらが安全だと判断した。

### 2.7 `hosts: quory`固定

requirement「配備先はquoryのみ」のとおり、`incident_capture_setup.yml`/`recovery_push_setup.yml`/`dev_investigate_setup.yml`と同じく`hosts: quory`を直接指定した(`recovery_probe_setup.yml`のような`dev_nodes:control_nodes`+ansy inert配備は採らない)。

### 2.8 AC-3(recovery-execへの新規権限ゼロ)

本実装は`ansible.posix.acl`タスクを一切持たず、recovery-execという識別子への言及もない(コメント中の「ACL不要」という説明のみ)。`grep -rn "recovery-exec\|recovery_exec\|acl"`で確認済み(該当なし)。

## 4. 未検証・残存事項

- **実quoryでの動作は未検証**(Implementerの権限外、Testerへ委ねる)。特に: `yoshi`が実際に`/usr/local/sbin`・`/etc/systemd/system`・`/var/lib`・`/run/lock`へ`become`経由で書き込めること(他roleの既存実績に基づく前提であり、本実装で新規に確認したものではない)、実semaphore.dbのスキーマ(`task.status`の値域)が`docs/ai/context/system/semaphore.md`の記述と現在も一致していること、quoryのorigin remoteへの実際のfetch到達性。
- **確認とpullの間の競合窓(R-5/AC-B-3)は自己検証の対象外。** requirement自身が「消せない」と明記しており、確認するとすれば競合を意図的に発生させる必要がありテスト側の作為が入るため、Testerでも再現性のある検証は難しい可能性がある。受容事項として扱った。
- `git fetch`自体の失敗(ネットワーク断)は分岐をコードレビューで確認したのみで、実行によるテストはしていない(サンドボックス環境でネットワーク到達性を人工的に落とす手段を持たなかったため)。
- 見送り閾値3・schedule 5分は設計判断であり、Yoshinobuの意図(「見送りが連続していることを後から観測できる」の許容時間)と一致するかは未確認。
- `worktree_sync_service_enabled`は状態ディレクトリ・スクリプト・unit配備そのものはゲートしない(`ansible_check_mode`のみでゲート)。ゲートするのはtimerのenable/startだけ。既存の`incident_capture`と同型であり、意図した設計だが明示しておく。
