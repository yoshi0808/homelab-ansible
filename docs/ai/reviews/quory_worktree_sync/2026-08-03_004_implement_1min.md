# 追加変更: timerを1分間隔にし、通知の抑止を設計し直す

実施日: 2026-08-03 / 実施: Coordinator
契機: Yoshinobuが timer 間隔を **5分 → 1分** と決めたこと(push直後に手でSemaphoreジョブを回す使い方があり、5分は長い)

## 1. なぜ間隔だけの変更で済まなかったか

**閾値が「回数」で持たれており、その意味がtimer間隔に依存していた。**

`worktree_sync_defer_notify_threshold: 3`(見送り3回ごとに通知)は5分間隔を前提に「15分見送ったら通知」を意図していた。**1分間隔へ移すと同じ設定が「3分で通知」になる。** healthcheck系のSemaphoreジョブは数分かかるのが普通なので、**毎朝の正常運転で警告が出る**状態になっていた。誤報を生む設定変更が、設定値を1つ書き換えるだけで静かに成立してしまう形だった。

あわせて、**異常系の通知が毎回無条件だった**。

- 汚れた作業ツリー: 人が直すまで続く状態。**1分間隔だと直すまで毎分Slackへ出る**(1時間で60通)。
- `git fetch` 失敗: 取得先はGitHubであり、一時的な不調でも復旧まで鳴り続ける。

いずれも5分間隔でも同じ性質を持っていたが、1分化で実害の水準に達する。

## 2. 変更内容

| 対象 | 変更 |
|---|---|
| `defaults/main.yml` | `worktree_sync_defer_notify_threshold: 3`(回数)を **`worktree_sync_defer_notify_after_seconds: 1800`(経過時間)へ置換**。`worktree_sync_error_renotify_seconds: 3600` を新設。`worktree_sync_schedule` を `*:0/5` → `*:*:00`。`worktree_sync_timer_accuracy: 5s` を新設 |
| `worktree-sync.timer.j2` | `AccuracySec` を固定値 `30s` から変数へ。1分周期に対して30秒のばらつきは大きすぎる。`Persistent=false` の理由をコメントで明示 |
| `worktree-sync.sh.j2` | `should_notify <signature>` / `clear_suppression_state` を追加。異常系4経路すべてを `should_notify` 経由にした。見送りは `defer_count`(回数)から `defer_since`(起点時刻)へ |

### `should_notify` の設計

**判定と記録を1つの関数にまとめてある。** 分けると「判定したが記録し忘れる」が起きうるため、呼び出し側は戻り値だけを見る。

- signature が前回と違えば**即通知**する。初回と、別の異常へ変わったときは遅れない。
- 同じ signature が続くあいだは `ERROR_RENOTIFY_SECONDS`(1時間)ごとにのみ再通知する。**鳴り止んで忘れられることを防ぐ。**
- 汚れの signature には `git status --porcelain` のハッシュを混ぜてある。**別のものが汚れ始めたら抑止中でも即通知される**(「同じ状態が続いている」と「新しい問題が増えた」は別)。
- 健全な結果(追随済み / pull成功)に到達したら `clear_suppression_state` で状態を捨てる。次の異常は必ず即通知される。

**閾値を時間で持つことは、この案件に限った話ではない。** 回数で持つと、周期を変えたときに閾値の意味が黙って変わる。**壊れても「たまに余計な通知が出る」形でしか現れないため、気づかれにくい。**

## 3. 検証(Coordinator実施、実ホストへは触れていない)

`/tmp` 配下に使い捨てのgitリポジトリ2つ(origin役・作業ツリー役)、SQLiteの偽 `semaphore.db`、`ansible-playbook` のmockを置き、**role defaults を実際に読ませてrenderしたスクリプト**を7シナリオで動かした。

| # | 条件 | 期待 | 結果 |
|---|---|---|---|
| S1 | clean + 遅れ + ジョブなし | pull し `ok` 通知、抑止状態は消える | PASS(rc=0、状態ファイル消滅を確認) |
| S2 | 汚れたまま3回実行 | 通知は**1回だけ** | PASS(3回実行で1通) |
| S3 | 汚れの中身が変わる | 抑止中でも**即再通知** | PASS |
| S4 | ジョブ実行中 | 30分までは無通知、超えたら1回、以後は抑止 | PASS(11回実行で0通 → 31分に偽装して3回実行で1通) |
| S5 | 既に最新 | 完全に無通知、rc=0 | PASS |
| S6 | `semaphore.db` が読めない(`chmod 000`) | **pullせず見送る**(安全側) | PASS(HEAD不変、`defer_since` 記録) |
| S7 | quory側に独自commit(履歴分岐) | 専用の通知文面 | PASS |

あわせて `bash -n`、`systemd-analyze verify`(このunitへの指摘なし)、`systemd-analyze calendar "*:*:00"`(毎分に正規化されること)を確認した。render は `jinja2.StrictUndefined` で行っており、**未定義変数があればrender時に失敗する**状態で通っている。

## 4. 未解決事項

- **quory実機での挙動は依然として未検証。** GitHubへの `git fetch` の実所要時間、systemd配下でのvault解決、`semaphore.db` のスキーマが現行のままか、配備そのものが通るか。すべて初回実行で分かる。
- **1分間隔のfetchは1日1440回GitHubへ出る。** レート制限に触れる水準ではないと判断したが、実測はしていない。触れた場合の出方は `git fetch` 失敗 → エッジ検出つきのerror通知である。
- `ERROR_RENOTIFY_SECONDS`(1時間)と `DEFER_NOTIFY_AFTER`(30分)はYoshinobuが選んだ値。**運用してみて変える前提**で、どちらも `defaults/main.yml` の変数である。
