## 4. ゴール

Yoshinobuが端末の前にいなくても、**承認を伴って**quoryのcheckoutを `origin/main` へ追随させられるようにする。

## 5. 非ゴール

- **無承認の自動配備にはしない**(承認をどこで取るかは §7 の未決事項)。
- checkoutが古いことの**検知だけ**を作って同期を作らない、という中途半端な決着にはしない。ただし検知が先行して価値を出すなら段階分けは可。
- Semaphoreのschedule・template・repository設定の変更は含めない(repo外の状態でありAIから確認も変更もできない)。
- `git pull` 以外のデプロイ動作(setup playbookの実行等)は含めない。**「repoを直しても配備物は古いまま」は別クラスの問題であり**(`docs/ai/status.md` Next)、pullでは解決しない。

## 6. 設計案

**この案件の実質は「承認と実行をどこに置くか」であり、実装量ではない。**

### 案A: timerが検知してSlackへ通知、pullはYoshinobuが手打ち

quoryのtimer(F-2の既存機構、`yoshi` 実行)が `git fetch` して `origin/main` との差分を見て、遅れていればSlackへ通知する。pull自体は従来どおり手打ち。

- **足す能力: ゼロ。** `git fetch` は作業ツリーを変えない。
- 解決するのは「古いことに気づけない」だけで、**端末の前にいる必要は消えない。**

### 案B: timerが `git pull --ff-only` まで行う(承認はpush時点で済みとみなす)

- **足す能力: ゼロ。** timerは既に `yoshi` としてそのディレクトリで動いている(F-2)。新しい鍵も権限も要らない。
- **論点は権限ではなく承認の意味。** `git push` が今日から都度承認になった(F-8)ため、「Yoshinobuが承認した内容だけがoriginに存在する」状態は既に成立している。**この案は「pushの承認をもって配備の承認とする」という統合であり、承認を削るのではなく1回に畳む。**
- 引き受けるもの: 「コードを確定してよい」と「いま本番へ入れてよい」を**分けられなくなる**。push直後にラダーが発火すれば新コードで走る。

### 案C: Codexにpullさせる(Slackで依頼=承認)

- **足す能力: 大きい。** F-3〜F-5より、Codexにpullさせるには `/home/yoshi/homelab-ansible` を `recovery-exec` から書ける状態にする必要がある。**そしてF-4のとおりCodexにはコマンド許可リストが無い。** checkoutを書けるようにした時点で、Codexは `git pull` だけでなくそのツリー内の任意の書き換えができる。
- **これは `docs/ai/core.md`「開発と運用の分離」の「Codexは修正を書かない」を構造的に破る。** 規範で禁じても、能力の側が開く。**Phase 4 が「境界は能力の不在で作る」と結論した直後に、その結論に逆行する。**
- **推奨しない。**

### 案D: Codexは要求だけを立て、pullは別の主体が行う

Codexが書けるのは**狭いトリガ用ディレクトリ1つだけ**(`mute` ディレクトリと同じ扱いで `writable_roots` と `ReadWritePaths` に足す)。そこにマーカーが置かれたら、`yoshi` 所有のsystemd path unitが `git pull --ff-only` を実行する。

- **Codexの能力は「pullを要求する」ちょうど1つに限定される。** checkoutへの書込権は渡らないため、案Cの問題は生じない。
- 承認は**SlackでYoshinobuがCodexへ依頼した事実**(F-6により送信者は限定済み)。スマホから行える。
- 足す機構: トリガ用ディレクトリ、path unit、service unit、Codex側の作法(AGENTS.md)。**案Bより明確に重い。**

### 決定: 案B(2026-08-03 Yoshinobu)

**案Bを採る。** 足す能力がゼロで、承認は `git push` のプロンプトへ既に存在する。OQ-2(確定と配備を分けたいか)は「分けない」で決着した。

**あわせてYoshinobuが追加した要求: pullするとき、Semaphoreのジョブが動いていないことを確認できるとよい。** これを R-5 / AC-B-2 として §6.1 に展開する。

## 6.1 Semaphoreジョブとの排他(案Bの追加要求)

### なぜ要るか

OQ-1のとおりSemaphoreは同じcheckoutを使う。**`git pull` は作業ツリーをその場で書き換えるため、ジョブの実行中に走ると、ansible-playbookが「一部は旧版、一部は新版」のツリーを読む状態が起こりうる。** roleのtasks・templates・varsは実行の途中で必要になった時点で読まれるため、pullがその途中に挟まると整合しない組み合わせで走る。**これは「古いまま走る」より悪い** — 古いだけならその版として一貫しているが、混ざったものはどの版としても正しくない。

### 確認手段(F-9〜F-11の裏取り後に確定)

**`semaphore.db` を直接読む。** F-11のとおり `yoshi` は所有者として元から読めるため、**新しい権限も秘密も要らない。** 当初「timerでは読めない可能性が高い」としたのは誤りだった。

判定は**status語彙の完全な列挙に依存させない**形にする。

```sql
SELECT count(*) FROM task WHERE status NOT IN ('success','error','stopped');
```

- 終端の語彙3つは実測済み(`docs/ai/context/system/semaphore.md`)。**「終端でないものは実行中とみなす」**方向に倒すことで、未知のstatus値(`waiting` / `starting` / `running` 等)が出ても**安全側(見送る側)へ倒れる**。
- 逆に、終端に到達しないまま残ったタスクがあると**永久に見送り続ける**。これはAC-B-2(見送りが続いた状態を無通知にしない)が拾う。**塞ぐのではなく、気づける形にする。**

**採らなかった手段**: `pgrep -f ansible-playbook`(ジョブ起動からプロセスが生えるまでの隙間を取りこぼし、Semaphoreの実行形態も未確認)、SemaphoreのAPI(tokenという秘密が1つ増え、「足す能力ゼロ」を損なう)。

### 排他のイディオムは既存に合わせる

F-10のとおり、既存の `ansible-cert-renew-quory.service` は `ExecStart` を `/usr/bin/flock -n /run/lock/<name>.lock` で包んでいる。**同期unitも同じ形を採る。** ただしこれが防ぐのは**同期unit自身の多重起動**だけであり、Semaphoreジョブとの排他にはならない(Semaphoreはこのlockを取らない)。**2つを混同しない。**

### 塞ぎきれないもの(先に明示する)

**どの手段を採っても、確認とpullのあいだにジョブが始まる余地は残る。** 確認は「同時実行の確率を下げる」ものであって、排他ではない。**本当の排他はSemaphore側もロックを尊重して初めて成立するが、Semaphoreは我々の管理下にない。**

したがって設計方針は次のとおりとする。

1. **確認して、動いていれば今回は諦める(defer)。** 待たない、殺さない、強行しない。timerは繰り返し来るので、見送りの費用はほぼゼロである。
2. **見送ったことを黙って捨てない。** 何周期も連続で見送っている状態は、同期が止まっているのと同じである(R-2)。
3. **残る競合窓は受容する。** 消せないものを消したことにしない。

## 7. オープンクエスチョン

### 回答済み(2026-08-03 Yoshinobu)

- **OQ-1: Semaphoreは `/home/yoshi/homelab-ansible` を使うのか、自前のcloneを持つのか** → **同じcheckoutを使う。** したがってcheckoutが古いことの影響は、ラダー系・reports・incident capture・`dev_investigate` だけでなく**Semaphoreの定期ジョブ全体に及ぶ**。影響範囲は最大であり、同期を作る価値はその分大きい。
- **OQ-3: Yoshinobu自身は今もquoryへsshできるか** → **できる。** 「物理的にアクセス不能」になったのはansyであってYoshinobu本人ではない。したがって案A(通知のみ)は成立するが、**端末の前にいる必要は消えないため、目的(スマホから完結する)を満たさない。**
- **OQ-4: pullが失敗したときどうするか** → **手作業でリカバリする。** あわせてYoshinobuが明示した規範: **「quoryではリポの内容は直接修正しない。必ずansyで修正したものをquoryへ配布する。」** したがって作業ツリーが汚れている状態は**そもそも起きてはならない異常**であり、自動で解消しにいくのは誤り。検知して止め、人へ上げるのが正しい。この規範は本案件の実装より広く効くため、**採用案が決まった時点で `docs/ai/context/ansible/repository-overview.md` へ1行として反映することを提案する**(現行は「quoryでは原則としてコードを直接編集・commitしない」で、`git pull` 失敗時の扱いまでは言っていない)。

- **OQ-2: 確定(push)と配備(pull)を別々の判断として持ちたいか** → **分けない。案Bを採る。** pushした内容は次のtimer周期で自動的にquoryへ入り、判断は `git push` のプロンプト1回になる。

- **OQ-5: Semaphoreジョブの実行中をどの手段で判定するか** → **`semaphore.db` を直接読む。** F-11で権限の懸念が消えたため確定(§6.1)。

## 8. 受入条件

OQ-5(実行中の判定手段)が決まるまでAC-B-2の観測手段は確定できない。**それ以外は確定させる。**

- **AC-1**: Given quoryのcheckoutが `origin/main` より遅れている、When timerが動く、Then checkoutが `origin/main` と一致し、**その事実が本番の外から観測できる**(Slack通知またはreport)。「静かに成功する」形にしない。
- **AC-2**: Given 作業ツリーが汚れている、When timerが動く、Then **`--ff-only` が失敗して停止し、その事実がSlackへ届く。** 汚れを消して成功させにいかない(Yoshinobu明示: quoryではリポの内容を直接修正しない)。
- **AC-3**: When 実装後に `recovery-exec` の到達範囲を数える、Then `/home/yoshi/homelab-ansible` 配下への書込権が**付いていない**こと。
- **AC-B-1**: Given Semaphoreのジョブが実行中、When timerが動く、Then **pullを実行せずに見送り、終了コードは正常**(赤くしない)。次の周期で再試行する。
- **AC-B-2**: Given 見送りが連続している、When その状態が続く、Then **見送り続けていることが観測できる。** 1回の見送りは通知しなくてよいが、**見送りが続いた状態を無通知にしない**(R-2の再来を防ぐ)。**閾値は回数でなく経過時間で持つ**(2026-08-03、30分)— 回数で持つとtimer間隔を変えたときに閾値の意味が黙って変わり、正常運転で鳴るようになる(`2026-08-03_004_implement_1min.md`)。異常系の通知はエッジ検出とし、同じ状態が続くあいだは1時間ごとにのみ再通知する。
- **AC-B-3**: Given timerがpullを実行した、When その最中にSemaphoreジョブが開始された、Then **この競合は防げない。** ACとして検査せず、R-5として受容する。
