## 2. 設計判断とその根拠

### 2.1 main.ymlへの挿入(§2.4固定位置)

`Save report`(既存175-192行)の直後、`Collect resulting diff` の直前に、`incident_metrics.yml → incident_evaluation.yml → incident_index_write.yml` の3タスクを `ansible.builtin.include_tasks`(**動的include**)で追加した。`git diff` は純粋な追加のみで、既存行への変更はゼロ(自己検証2.6参照)。

`incident_metrics.yml` と `incident_index_write.yml` はU4の担当でまだ存在しないが、`include_tasks`(動的include)は解決を実行時まで遅延するため、`ansible-playbook --syntax-check` は対象ファイルの不在をエラーにしない。これは自分でscratch環境を作って実測確認済み(存在しない`.yml`を`include_tasks`で参照しても`--syntax-check`はrc=0)。一方 `ansible-lint` は静的にファイルを読もうとして `load-failure[filenotfounderror]` を2件報告する(§4「自己検証」参照)。これはU4が着手すれば自然に解消する、実装順序に起因した既知のギャップであり、本ファイルの欠陥ではない。

3つのincludeそれぞれの `when` は次の理由で使い分けた。

- `Compute incident evaluation metrics` / `Run incident evaluation`: `not (knowledge_review_aborted | bool) and knowledge_review_incident_eval_enabled | bool` のみ(`ansible_check_mode` を見ない)。既存の「Render review prompt」「Render job permission profile」と同じ考え方で、読み取り・テンプレート描画は `--check` でも実行してよい(副作用はansyローカルの `~/.local/state` 配下、または後述のとおりincident_evaluation.yml内部の各タスクが自分で `check_mode: false` / `when: not ansible_check_mode` を個別に持つ)。
- `Write incident evaluation index`: `not ansible_check_mode` を追加。この3本目はU4が「評価が失敗しても必ずindexを書く」ファイルであり、ファイル書込そのものが目的のため、既存の「Save report」「Update next review date」と同じ扱いで `--check` では丸ごとskipする。

### 2.2 evaluationタスクの内部(incident_evaluation.yml)

I-8で固定されたargvをそのまま実装した。`--setting-sources ""`(空)、`--permission-mode` は付けない(封じ込めのCLI側2条件)。`--add-dir` も付けない(§2.4「着地点がcwd内なので不要」)。`timeout: knowledge_review_incident_timeout`(900)、`failed_when: false` + `ignore_errors: true` を両方付けた(理由は既存 `main.yml:140-145` と同一の実測結果 — `failed_when: false` だけではタスクタイムアウトが `TaskTimeoutError` として `failed_when` の評価経路の外で捕捉され致命的失敗になる)。

テンプレート描画2つ(`incident-review-prompt.md.j2` / `incident-job-settings.json.j2`)は `check_mode: false` で常に実描画し(既存「Render review prompt」と同じ扱い)、claude起動と成果物保存の2タスクだけを `not ansible_check_mode` でゲートした(check-mode-native)。

`incident_eval_rc` / `incident_eval_artifact` / `incident_eval_summary` の3 factは、I-5が指定した名前をそのまま使った(`knowledge_review_` prefixを付けていない)。理由: これらはU3→U4間の**固定インターフェース**(I-5「U3が生成するfact」)であり、名前を変えるとU4が読む名前と一致しなくなる。`ansible-lint` の `var-naming[no-role-prefix]` がこの3変数を指摘するが、契約で固定された名前を実装判断で変えるべきではないと判断し、そのまま残した(§4「自己検証」に明記)。同じ扱いは `incident_eval_index`(U4が生成するfact)にも及ぶはずで、U4着手時に同じ指摘が出ることが見込まれる。**この点はU6(評価側レビュー)へ申し送る。**

### 2.3 None/Undefined の扱い(自己検証で最も時間を割いた点)

`incident_eval_artifact` は成功時はパス文字列、失敗時は**Python の `None`**(Jinja `else None` を1つの `{{ }}` 式全体として評価させることでAnsibleのnative type変換を働かせる)。空文字列にしなかったのは、下流(U4の `incident_index_write.yml`)が `to_json` でindexへ書き出す際に `null` になる必要があるため。scratchで検証: 成功時 `type=str`、失敗時 `type=NoneType`・`is_none=True`・`to_json` で `null` になることを実測した。空文字列だと`""`になり、"データが無い"と"空文字列が返った"の区別がJSON上で失われるため、意図的に区別した。

`incident_eval_index`(U4が生成、まだ存在しない)への参照は**ドット表記を使わず `.get('key') | default(fallback, true)` で統一した**。理由は自己検証中に実際に踏んだ罠 — Jinja/Ansibleのdict型に対してドット表記で存在しないキーへアクセスすると、`Undefined` に落ちずに `object of type 'dict' has no attribute 'X'` という**即時例外**になることをscratchで実測した(値がNoneになって後段でクラッシュする既知の罠とは別の、より即効性のある同種の罠)。`.get()` + `default(fallback, true)`(第2引数`true`でNoneも含めてfallbackさせる)の組で、①キー自体が無い ②キーはあるが値が `null` の2パターンともクラッシュしないことを、`incident-review-prompt.md.j2` を実際にrenderして3パターン(index未定義・null値入り・実データ入り)すべてで確認した(出力は本記録に転記せず、確認した事実だけを記す)。

`incident_eval_summary` の判定順(`FAILED → STALE → NO_DATA → OK`)も、rc / mirror_stale / mirror_bundle_total の3系統で分岐が正しく出ることをscratchで実測した。I-8がRun incident evaluationタスクの `when` を3条件に固定しているため、「新規バンドルが0件なら起動そのものをskipする」という追加条件は入れていない — `NO_DATA` はAnsible側の事後分類であり、起動可否の条件には使っていない。

### 2.4 時間予算(§2.4・査読F-1)

`TimeoutStartSec` の式を `knowledge_review_timeout + 600` から `knowledge_review_timeout + knowledge_review_incident_timeout + 900` へ変更した。

初回実装では直前の説明コメント2行を元のまま残した(契約が「時間予算の1行のみ」と明示していたため、いったんコメントも書き換えたあと自分で巻き戻した)。**その結果、コメントが「claude -pは1本」の前提のまま(式は2本ぶんを足しているのに)食い違う状態になり、Coordinatorから差し戻された。** 原因はCoordinator自身が課した「1行のみ」という許可範囲の側にあったため、逸脱としては扱われず、許可範囲が「`TimeoutStartSec` の行と、それを説明する直上のコメント」へ広げられた。

コメントを次の内容へ更新した(`ExecStart` / `User` / `WorkingDirectory` は変更していない)。

- claude -pが2本(振り返り本体→評価の順)であること、および順序が「予算が尽きたら新しい工程(評価)の側が犠牲になる」という意味を持つこと
- 式の内訳(2本の上限の合計+preflight等の余裕)
- 具体的な数値(1800/900/2400/3600等)はコメントへ書かず、`{{ knowledge_review_timeout }}` / `{{ knowledge_review_incident_timeout }}` という既存コメントと同じ変数参照の流儀に統一した(変数を変えたときにコメントが腐らないため)。「2本」「既定90秒」はrepo既存コメントも使っていた構造的な事実・systemdの既定値であり、対象の変数値ではないため残した。

実際にJinjaを描画して確認した実値: `knowledge_review_timeout=1800` / `knowledge_review_incident_timeout=900` のとき `TimeoutStartSec=3600`。2本の `claude -p` の最悪ケース合計(1800+900=2700)に対し、余裕900を残す形になっており、計画の数値(3600)と一致する。

### 2.5 playbooks/incident_evaluation.yml(§2.8、手動専用)

**設計判断としてもっとも時間を使った点。** 契約は「main.yml の既存タスクの行を書き換えない」「`knowledge_review_incident_only=true` で評価工程だけを回せるようにする」の両方を要求するが、この2つを素朴に組み合わせると矛盾が生じる。

main.yml の既存タスク(振り返り本体・auto-memoryスナップショット・`claude -p` 本体・`MEMORY.md` 更新・Save report)は、既存の `when: not (knowledge_review_aborted | bool)` または `not ansible_check_mode` にしか反応しない。この2変数以外を既存タスクに追加で見させることは「既存行を書き換えない」に反するため不可能。したがって `knowledge_review_incident_only=true` を渡しても、`roles: - role: knowledge_review` で素朴に全体を起動すれば main.yml は最初から最後まで走り、**評価だけを回す**という目的を達成できない。

このため、**`playbooks/incident_evaluation.yml` は `roles/knowledge_review/tasks/main.yml` を経由しない**設計にした。評価工程3ファイル(`incident_metrics` / `incident_evaluation` / `incident_index_write`)だけを `ansible.builtin.include_role`(`tasks_from`)で個別に呼ぶ(`playbooks/knowledge_review_timer.yml` が `install_timer` を呼ぶのと同じ既存パターン)。main.yml を経由しないため、その既存タスクの `when` を一切変更する必要が無い — 経路の分離を**構造**(main.ymlを通らない)で担保し、変数の分岐では担保していない。

これに伴い2つの追加課題が生じ、両方とも解決した。

1. **role defaultsの読み込みタイミング。** `roles:` play-keywordの各要素に `tasks_from` を付ければ役割defaultsを早期ロードしつつ特定ファイルだけ実行できると想定していたが、**この版のansible-core(2.20.1)では実際には機能せず、常に `main.yml` が実行されてしまうことをscratchで実測して確認した**(想定と異なったため、実装を差し替えた)。かわりに `pre_tasks` の先頭で `ansible.builtin.include_vars` を使い `roles/knowledge_review/defaults/main.yml` を直接読み込む形にした。`{{ playbook_dir }}/../roles/...` という相対path表記は本リポジトリの既存playbook群(`proxmox_patch_weekly_full.yml` 等)で使われている慣用形であり、新規の書き方ではない。
2. **中止判定(IC-025)の重複。** main.ymlを経由しないため、`knowledge_review_aborted` を決める「Check working tree is clean」「Decide whether to abort」「Report abort reason」のロジックを本playbook内に再掲した(main.ymlの当該タスクは変更していない。ロジックは同一のものを複製しただけ)。手動専用playbookであってもIC-025と同じ安全弁(汚れていれば評価も走らせない)を保つ設計判断は§2.7がすでに下しており、本ファイルでもそれを踏襲した。

**`knowledge_review_incident_only` は削除した(2026-07-28、Coordinator決定)。** 初版ではこの構造的分離のもとで評価工程3ファイルのいずれからも実際に参照されない(main.ymlの `when` も参照しない)変数として `defaults/main.yml` に定義し、本playbookで `true` を明示していた — 挙動を左右するのは変数ではなく「main.ymlを経由しない」という構造そのものだったためである。この不一致(契約I-5の文言と、実装が変数を消費していない事実)は自分で気づいて未解決事項として申告したが、Coordinatorの扱いは「契約と違うので記録に残す」ではなく**除去**だった。理由: 定義されているのに条件式・`when:`・テンプレートのいずれからも参照されない変数は、将来 `-e knowledge_review_incident_only=true` を月次playbookへ付けて「評価だけ走る」と期待する経路を作ってしまう(実際には月次が丸ごと走る)。このリポジトリは死んだ分岐・宙ぶらりん参照で繰り返し損をしており(直近では `job-settings.json.j2` が実在しないLessonファイルを指していた事例がある)、その再発を避ける判断である。`main.yml` に条件分岐を足して変数を生かす形も不採用とされた — `main.yml` を経由しない構造にしたこと自体が正しい解であり、そこへ分岐を戻すと既存行に触れることになりAC9の面積が増えるため。削除に伴い、`playbooks/incident_evaluation.yml` の「記録用のマーカーとして残す」というコメントも落とした(無いものの不在を説明し始めると際限が無いため)。`grep -rn "incident_only" roles/ playbooks/` が無結果(exit 1)になることを確認済み。
