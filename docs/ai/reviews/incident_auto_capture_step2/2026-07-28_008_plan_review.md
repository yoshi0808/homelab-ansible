**F-1【Critical】2回目の `claude -p` が systemd の `TimeoutStartSec` の予算に入っていない。最悪ケースで月次ジョブごとSIGKILLされ、Slack通知まで消える**

現物:

- `defaults/main.yml:20` → `knowledge_review_timeout: 1800` ⇒ **unit の実効値は 2400 秒**
- `tasks/main.yml:146` → 既存の `claude -p` タスクは `timeout: "{{ knowledge_review_timeout }}"`(=1800)

したがって **claude -p 2本で最悪 3600 秒 + preflight・snapshot・git status の分**が要り、**unit の 2400 秒を確実に超える**。`Type=oneshot` の `TimeoutStartSec` 超過は SIGTERM→SIGKILL であり、`ansible-playbook` が途中で殺される。

**その結果、`playbooks/knowledge_review.yml` の `post_tasks` にある Slack 通知が一度も走らない。** これはこのroleが `tasks/main.yml:35-37` で「素の fail はホストを失敗扱いにし post_tasks の Slack 通知がスキップされて『中止したこと自体』が誰にも伝わらない」として明示的に避けた失敗の形そのものであり、AC9(既存動作を変えない)違反である。R-8 の対処①②③はいずれもこれを検出しない(差分は追加のみ、プロファイルは無変更、`--check` では claude タスクが skip される)。

さらに波及がある:

- **unit の変更が必要になる** → `install_timer.yml` は `become: true` でユニットを配る。計画には **knowledge_review 側の再配備単位が存在しない**(U2 は `incident_sync` 専用、U7 は転送のみ)。unit を変える以上 W1(Yoshinobu の commit)への依存も1本増える。

**F-3【Major】転送機構の未決定(U0-1)が U1 と U4 へ漏れている。`fetch` 経路では §2.6 の3指標の意味が変わる**

現物で確認したこと:

- `ansible.posix.synchronize` は既定 `archive: true`(モジュール引数定義 418行)で `--archive` を渡す ⇒ **mtime を保存する**
- `ansible.builtin.fetch` の action plugin(`/usr/lib/python3/dist-packages/ansible/plugins/action/fetch.py`)には **`utime` / `copystat` / `copy2` の呼び出しが1つも無い** ⇒ **mtime を保存しない**(checksum 比較による冪等性は持つ)

計画 §2.6 の3指標(`bundles_new_since_last_eval`、`oldest_unreviewed_bundle_age_days`、およびそれらを載せる I-3)は**すべてミラーのディレクトリ mtime を尺度にしている**。計画自身が「rsyncがmtimeを保存するため、quory側の保持判定と同じ尺度になる」と根拠を書いている。**`fetch` ループを採った瞬間、この根拠は消える** — mtime は「事象の発生時刻」ではなく「取得時刻」になり、ミラーを作り直せば全件が「新着」に化ける。滞留検知(P0-5②・AC8)の意味が変わる。

U0 は「判定規則は固定済み・案を新たに考えない」としているが、**固定されているのは機構の選び方だけで、選ばれた機構ごとの下流の定義は固定されていない。** その結果 U1(同期の実装形)と U4(指標の算出)がそれぞれ未申告の未決定を抱える。

**差し戻し要求**: ①`fetch` 経路を採ったときの指標定義(例: 到着時刻を `_sync/` 側に記帳して mtime に依存しない)を計画で先に決める、または ②`fetch` 経路を捨て、rsync が両端に無い場合は「配備してから進む」を分岐にする — のどちらかを選ぶ。**U4 の「未決定 0」はこのままでは成立しない。**

**F-4【Major】§2.3「現行の `.gitignore` のままでも P0-3 は成立する」は無条件には成立しない。転送中の一時ファイルを検査していない**

計画 F6 が `git check-ignore` で確認した5パスは、**すべて転送が完了したあとの着地物**である。転送機構が転送中に作るファイルは1つも検査されていない。自分で確認した結果:

```
reports/incidents/quory/semaphore-1/.summary.json.Ab3xQ1   → NOT-IGNORED
```

rsync が既定で使う `.<basename>.<ランダム6文字>` 形式の一時ファイルは、**現行の `.gitignore` のどの行にも一致しない。** この形のファイルが残ると **unscoped の `git status --porcelain` が非空**になり、月次が `ABORTED_DIRTY` で止まる — 本案件が最も避けたい形である(計画のスコープ付き検査は同期側でこれを検出できるが、それは検出であって予防ではない)。

**確かめられた範囲を正確に書く**: `ansible.posix.synchronize` は既定 `delay_updates: true`(引数定義438行)で `--delay-updates -F` を渡す(モジュール496-498行を現物で確認)。`--delay-updates` を使うと一時ファイルは保持ディレクトリへ入るため、上の形にならない可能性が高い。**ただし rsync が `--delay-updates` 下で実際に付ける一時ファイル名までは確かめていない**(rsyncのソースを読んでおらず、実測もしていない)。したがって「現行 `.gitignore` で成立しない」とは断定しない。

断定できるのは次である:

1. **計画が「成立する」と断定していることが誤りである。** 根拠にした検査は着地物5パスだけで、この経路を見ていない。
