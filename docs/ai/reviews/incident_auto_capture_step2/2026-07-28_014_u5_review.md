## 確認した事実(再現手順の要約)

decoy環境(スクラッチディレクトリに`roles/incident_sync`・`roles/common_slack`・`playbooks/incident_sync.yml`をコピーし、独自の`ansible.cfg`/inventoryを用意。inventory の`control_nodes`ホスト名は実装のデフォルト値`incident_sync_source_host: quory`と一致させる必要がある — 最初`decoy-quory`という名前で試したところ`hostvars['quory']`参照が静かに空扱いになり誤った失敗経路を検出しかけた。これはテスト側の設定ミスであり実装のバグではない、と自己訂正した)。

1. **正常系2周**: `ansible_connection: local`のquory、実バンドル1件・妥当な`_heartbeat.json`→ 1周目`transferred_files:2`/`result:ok`、2周目`transferred_files:0`/`result:ok`、`git status --porcelain -- reports/incidents`は両周とも空。
2. **速い失敗**: quoryを`127.0.0.1:1`(接続拒否)へ向ける → `rc=255`のrsyncエラーが`incident_sync_transfer_msg`として伝播し、`_sync/last-sync.json`に`result:failed`・`errors`配列付きで書かれ、Slack通知(層1)が正しい内容で発火し、最終的に`fail`でexit=2。
3. **ハートビート破損(日付として不正な文字列)**: `_heartbeat.json`の`generated_at`を`"not-a-real-date"`にして正常な転送を実行 → `finalize.yml`が`Compute heartbeat epoch`タスクで`AnsibleError`により未捕捉のままクラッシュ。`exit=2`だが`_sync/last-sync.json`は**存在しない**(ディレクトリごと未作成)。Slack通知も発火しない。
4. **ハートビート破損(不正JSON)**: `_heartbeat.json`の中身を`not json at all {{{`にして再実行 → より早い`Read mirror heartbeat content`タスクで同様にクラッシュ、`exit=2`、`_sync/last-sync.json`は書かれない。

いずれも実ホストへは接続せず、破壊的操作(削除等)は行っていない。使用後、スクラッチディレクトリは削除済み。

## Verdict

**Request Changes**(Critical Issue #1がblocking)。

Tech Leadへの返却時の主な論点:
1. Critical #1は、`_sync/last-sync.json`書き出し・Slack通知よりも前に「ハートビート解析」を置いた**タスク順序**そのものに起因する。ハートビート解析を`block/rescue`で囲む、または解析失敗時に`mirror_stale: true`・`mirror_heartbeat_generated_at: null`へ安全側フォールバックしてクラッシュさせない形にする、のいずれかで解消可能と考えられるが、対処方法の選定はTech Lead/Implementerの判断に委ねる(自分では実装ファイルを変更していない)。
2. Major #2は実装よりも運用パラメータ(rsync/ssh側のconnect timeout値)の追加が対処になると考えられ、`TimeoutStartSec`の再計算(評価側で行ったF16/R-9と同種の予算計算)を転送側にも及ぼす必要があるかの判断をCoordinatorへ上げる。
3. Suggestions #3・#4は blocking ではないが、#4は`roles/knowledge_review`側(U6のスコープ)にも影響するため、U6のReviewerと突き合わせることを推奨する。
