### 1.3 `roles/incident_sync/tasks/transfer.yml`(新規、play1相当)

`ansible.posix.synchronize`(`mode: pull`)で quory → ansy をpullする。`delegate_to` は付けない(action pluginが `delegate_to`無し・remote_transport有りを検知して自動的にローカル実行へ切り替える設計であり、公式のpull例も`delegate_to`なし)。`delete`/`--remove-source-files` は一切使わない。

**自己検証で発見し、設計を変更した点(重要)**:

1. **role defaultはhostvars越しにクロスホスト参照できない。** `incident_sync_mirror_dir`(role default)を play1 の中から `hostvars['localhost'].incident_sync_mirror_dir` で読もうとすると `object of type 'HostVarsVars' has no attribute ...` で失敗する(角括弧表記でも同じ)。原因はrole defaultがそのroleを一度importされたホストにしかmergeされないためで、play2(finalizeをimportする側)がまだ実行されていないplay1の時点では localhost 側にこのキーが存在しない。**対処**: role defaultではなくgroup_vars由来の `reports_base_dir`(全ホストから常時参照可能)を使い、`incident_sync_ansy_mirror_dir` という**task-scoped fact**を play1 の先頭で組み立てる。defaults/main.yml のコメントに「接尾辞を変えたら両方揃える」注記を残した。
2. **`ansible.posix.synchronize` は rsync出力(`--stats`含む)を `.stdout` ではなく `.msg` に入れて返す。** `.stdout` は常に空文字列だった。統計抽出(`transferred_files`)の入力を `.msg` に修正。
3. **`failed_when: false` は `is failed` を無条件でFalseに固定する。** 転送taskへ `failed_when: false` を付けているため、直後のfact計算で `incident_sync_transfer_raw is failed` を使うと**存在しないsource_dirを与えてrc=23を発生させても偽のまま**だった(`skills/ansible-implementation-style/SKILL.md` の既知の落とし穴と同型)。`.rc | int != 0` を直接見る形へ修正し、`--check`でtask自体がskipされた場合(rc未定義→既定-1)だけは「未実施」として除外するよう `not ansible_check_mode` を明示的に足した。

いずれも机上の設計段階では気づかず、decoy環境での実行によって初めて発見した(詳細は §2)。

### 1.4 `roles/incident_sync/tasks/finalize.yml`(新規、play2相当)

I-7の①〜⑤をこの順で実装した。

1. `hostvars[incident_sync_source_host]` の facts有無で到達可否を判定(facts無し=到達不能として扱う。short-circuitで未定義属性アクセスを回避)
2. ミラーの `_heartbeat.json` を読み、`generated_at` から経過秒数・staleness(既定3時間)を算出。heartbeatが無い場合は age=-1(番兵値)・stale=trueに倒す
3. `git status --porcelain -- {{ incident_sync_git_status_scope }}` でスコープを絞った検査(P0-3・AC1・OQ-C)
4. `_sync/last-sync.json`(I-2 schema_version 1)を**必ず**書く。`errors` は空配列でも必ず出す
5. 失敗(層1・alerts/error)/heartbeat stale(層2・alerts/warning)をSlack通知。**成功時は通知しない**(I-6)。両方とも `not ansible_check_mode` でも絞り、`--check` では実送信を試みない
6. `result == 'failed'` のときのみ非ゼロで `fail`(stale単独ではfailさせない — 転送機構自体は健全なため)

ミラーへの削除操作は1つも実装していない(`--delete` はもちろん、ローカルファイルの `state: absent` 系タスクも無い)。

### 6.1 Critical #1(非信頼データによる無条件クラッシュ)— 修正済み

**根本原因**: `finalize.yml` の心拍解析(`lookup('pipe', 'date -d ...')` と `from_json`)が `block/rescue` で囲われておらず、`_heartbeat.json`(非信頼identity `recovery-exec` が書く、IC-016)の内容が壊れていると `AnsibleError` が未捕捉のまま伝播し、`_sync/last-sync.json` の書き出し・Slack通知・`fail` を含む残りタスクが一切実行されなかった。

**対処**: 心拍の読取・解析一式(旧: 「Check mirror heartbeat file presence」〜「Compute heartbeat age and staleness」の8タスク)を `block:` で包み、`rescue:` で安全側(`mirror_stale: true`・`mirror_heartbeat_generated_at: null`・`mirror_heartbeat_age_seconds: -1`)へフォールバックするようにした。解析失敗の事実自体は `incident_sync_heartbeat_parse_error` に記録し、「Build errors list」で `errors` 配列へ追加し(黙らせない — IC-011)、layer2のstale通知本文にも解析エラー行を追加した。`result` は `failed` にしない(転送自体は健全なため。既存の「stale」の扱いと同じ側に倒した)。

**自己検証**: 査読が使った2つの発火条件を両方decoy環境で再現した。
- `generated_at: "not-a-real-date"` → `rescued=1`(play recap)を確認、`_sync/last-sync.json` が書かれ(`mirror_stale: true`・`mirror_heartbeat_generated_at: null`・型は`json.load()`で確認)、layer2 Slack通知(warning)が解析エラー文言込みで発火した。
- `_heartbeat.json` の中身を `not json at all {{{` にした場合も同様に `rescued=1`・状態ファイル書き出し・通知発火を確認した。
- 正常系(有効な`generated_at`)・冪等性(2周目 `transferred_files:0`)・完全到達不能(facts不在)の既存シナリオも退行なく通ることを再確認した。

### 6.2 Major #2(SSH/rsyncの接続timeout未設定)— 修正済み

**対処**: `transfer.yml` の `synchronize` taskへ2つのタイムアウトを追加した。
- `rsync_timeout: "{{ incident_sync_rsync_timeout_s }}"`(既定60秒) — module パラメータで rsync 自身に `--timeout=N` を付与させる(接続確立後、データが流れなくなった場合の上限)。
- `use_ssh_args: true` + task `vars: ansible_ssh_common_args: "-o ConnectTimeout={{ incident_sync_ssh_connect_timeout_s }}"`(既定10秒、`roles/recovery_exec` の既存テンプレートと同じ慣例値) — action pluginの `is_rsh_needed()` ロジックにより、モジュールが自動生成する `--rsh=ssh -i <private_key> ...` へ `ConnectTimeout` を追記させる(自分で `--rsh` を丸ごと上書きすると private_key 等の自動設定が失われるため、この経路を選んだ)。SSHのTCP接続確立自体が固まった場合(blackhole)の上限。

**数値の根拠**: `incident_sync_timeout_start_sec`(unit の `TimeoutStartSec`、既定300秒)に対し、ConnectTimeout(10) + rsync_timeout(60) + 実転送時間(U0実測 41件・2.0MBなら数秒) + play2の所要時間(heartbeat判定・git status・状態書出し・Slack通知、数秒)は十分余裕を持って収まる。300秒という既存の予算値自体は変更していない。

**自己検証**: decoy技法の制約(`ansible.posix.synchronize` のaction pluginが `127.0.0.1`/`localhost`/`::1`(`ansible.constants.LOCALHOST`)を特別扱いしてローカル実行に倒すため、この3つそのものの閉ポートでは実際のssh接続コマンドを検証できない)を回避するため、**ループバック用アドレス範囲内にあり、かつ`ansible.constants.LOCALHOST`の3つのいずれにも該当しない値(`127.0.0.1`の最後のオクテットだけを`1`から`2`に変えたもの)を宛先にした閉ポートdecoy**を新たに用意した。`-v` 出力で実際に構築されたrsyncコマンドラインを確認し、`--timeout=60` と `--rsh='... -o ConnectTimeout=10'` の両方が実際に含まれていることを確認した(査読が「実行で再現できなかった」としていた経路の静的配線を、実行結果の文字列として直接確認した形)。真の「blackhole」(TCP SYNへの無応答)そのものの再現はdecoy環境の性質上できない(査読も同じ限界を記録している)。`connection=local` の正常系では `--rsh` 自体が付かない(ConnectTimeoutは無関係)ことも確認し、既存の高速失敗経路(接続拒否)・正常系・冪等性に退行が無いことを再確認した。

### 6.3 Suggestion #3(ミラーパス接尾辞の重複)— 実行時検出を追加

完全な変数統合はできない(role defaultはそのroleを一度importされたホストにしかhostvars越しに見えないため、play1からplay2のrole defaultを読むことはできない — U1本体の自己検証で確認済みの制約)。代わりに、`finalize.yml` へ **`incident_sync_mirror_path_mismatch` 検出task** を追加した — play1が実際に書き込んだ先(`hostvars[incident_sync_source_host].incident_sync_ansy_mirror_dir`、set_factで持ち越されるためクロスホスト参照可能)と、play2自身のrole default `incident_sync_mirror_dir` を突き合わせ、**不一致なら `result: failed` にして `errors` へ具体的な差分を出す**。「片方だけ変えると黙って壊れる」を「片方だけ変えると次の実行で見える形で失敗する」へ変えた。
