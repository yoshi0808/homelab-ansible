## 2. 設計(Tech Leadが決めたこと)

### 2.1 全体像

```
[quory] 収集器(5分毎・既存・無改修)
          reports/incidents/{<bundle>/, _runs/, _heartbeat.json, _spool/}
                    │  ansy起点のpull(毎時・読み取りのみ)
                    ▼
[ansy]  reports/incidents/quory/          ← ミラー。同期だけが書く(IC-031)
        reports/incidents/_sync/          ← 同期の実行状態。同期だけが書く
        reports/incidents/_evaluations/   ← 評価成果物。Ansibleだけが書く
        reports/incidents/_spool/         ← ansy自身の通知spool(既存・F8)
                    │  月次(既存timer、新しい器は作らない)
                    ▼
        claude -p(Edit許可ゼロ・Bash deny)→ 標準出力 → Ansibleがファイル化
                    │
                    ▼
        人 / 対話セッションが docs/ai/memory/incidents/ へ昇格(IC-020・IC-032)
```

**書き手が交差しない。** ミラーは同期だけが書き、評価成果物は評価だけが書き、判断の正本はgit管理下にある。これがIC-031(ミラーは上書きされる)とIC-032(証拠と判断を別の場所に置く)の実装形である。

### 2.3 D-2 着地点と `.gitignore`(Q2)

**初版は「現行の `.gitignore` のままでもP0-3は成立する」と断定していた。この断定は誤りだったので撤回する。** 根拠にした検査(F6)は**転送が終わったあとの着地物5パスだけ**を見ており、**転送中の一時ファイルを1つも見ていなかった**。自分で確認し直した結果がF18で、rsyncの一時ファイルは**既定形(`.<basename>.<乱数6文字>`)も `--delay-updates` の保持ディレクトリ形(`.~tmp~/`)も、現行の `.gitignore` のどの行にも一致しない**。IC-033が「汚れている = `git status --porcelain` 非空。未追跡を含む」と定義した以上、これが1つ残れば月次は中止する — **本案件が最も避けたい形である。**

したがって次の2点を**両方**、**必須として**採る。

1. **`.gitignore` へ `reports/incidents/` のディレクトリ単位除外を1行足す。これは「推奨」ではなく、rsync系機構を採る場合の前提条件である**(2026-07-28 Coordinator承認。査読F-4)。ディレクトリ単位にすれば一時ファイルの命名規則に依存しなくなり、この論点そのものが消える。副次的に、収集器が将来1つ拡張子を増やしても無言で破れない(Step 1がRSK-13として記録した形)。追跡ファイルへの影響が無いことはF7で確認済み。**機構を切り替える判断(R-2)が起きたときは、除外設定の前提も必ず一緒に見直す**(Coordinator決定1)。
2. **同期の最後に、スコープを絞った `git status --porcelain -- reports/incidents/` が空であることを検査し、空でなければ失敗させる。** 除外設定が壊れた瞬間に**同期側が**失敗する。月次ジョブが `ABORTED_DIRTY` で沈黙するより1か月早く、原因の近くで気づける。

**スコープを絞るのは必須である。** ansyの作業ツリーは人の作業で日常的に汚れている(requirement O7)。全体の `git status` が空であることを同期の受入条件にはできない(2026-07-28 Coordinator承認、§7 OQ-C)。

**1と2は役割が違う。** 1は**予防**(一時ファイルが最初から追跡対象に見えない)、2は**検出**(除外が壊れたことに同期自身が気づく)。**検出だけでは足りない** — 検出したときには既に月次を止めうる状態が作られている。U7・U8は「転送の**最中**にスコープを絞らない `git status --porcelain` が非空にならないこと」も観測する(査読F-4)。

### 2.4 D-3 評価の入り方(Q3)

**新しいtimerもplaybookも作らない。** 既存の `ansible-knowledge-review.timer` → `playbooks/knowledge_review.yml` → `roles/knowledge_review` の中へタスクを足す。

| 選択肢 | 採否 | 理由 |
|---|---|---|
| 既存の `claude -p` 呼び出しへ入力と出力を足す | **不採用** | 既存セッションのallowlistへ `Read(reports/incidents/**)` を足すことになり、`Edit(docs/ai/memory/**)` を持つセッションが非信頼バンドルを読む形になる。AC9(既存動作を変えない)の面積も最大になる |
| **同roleの中で2回目の `claude -p` を、専用の権限プロファイルで起動する** | **採用** | 評価セッションの許可が**Edit ゼロ**になる(ADR-005 Decision (2)がそのまま生きる)。既存セッションのプロファイルは1文字も変わらないためAC9の面積が最小。失敗も互いに波及しない |
| 別roleに切る | 不採用 | 中止判定・vault preflight・Slack集約を二重に持つことになる。器を増やさないというD-3の趣旨からも遠い |

**評価セッションの権限プロファイル**(新規テンプレート。すべて相対path、`--add-dir` を使わない):

```
allow: ["Read(docs/**)", "Read(skills/**)", "Read(reports/incidents/**)"]
deny:  ["Bash", "WebFetch", "WebSearch"]
```

- **`Edit` エントリを1つも置かない。** 「バンドルへ書かせない」を禁止の列挙ではなく**許可の不在**で達成する(AC5、IC-018、F12の「実効は `Edit()`」)。
- 承認済みの拡大は `Read(reports/incidents/**)` の**この1エントリだけ**である。`Read(docs/**)` / `Read(skills/**)` は既存プロファイル(F11)と同一で、拡大ではない。
- **着地点をrepo作業ツリー内にしたことで `--add-dir` が不要になった。** これは副次効果ではなく重要な帰結で、計画査読R-1が指摘した「repo外を読ませようとして絶対path表記の `Read()` を書き、ルールが照合されず全拒否になる」経路が**構造的に発生しない**(F12の成立条件1)。
- 実行時の作業ディレクトリは既存と同じ `knowledge_review_repo_dir` であり、相対path表記がそのまま照合される。
- **JSONに書けるのは3条件のうち1つだけである。**「`acceptEdits` を付けない」「`--setting-sources` を空にする」はCLI引数であり、権限プロファイルには書けない(査読F-5)。**したがって起動時のargvもインターフェースとして固定する — I-8。**

#### 挿入位置(査読F-14。実装者に委ねない)

`roles/knowledge_review/tasks/main.yml` の **`Save report`(175-192行)の直後、`Collect resulting diff`(194行)の直前**に、次の順で挿入する。

```
[既存: 中止判定 → prompt描画 → vault preflight → auto-memoryスナップショット →
       job-settings描画 → 振り返り本体(119) → 期日更新(158) → Save report(175)]
  ↓  ここから追加
incident_metrics.yml      … I-3の素材を算出(評価より前でなければならない。promptが使う)
incident_evaluation.yml   … 2本目の claude -p → stdout を Ansible がファイル化
incident_index_write.yml  … 評価のrc/成果物パスを合わせてindexを書き出す
  ↓  ここまで
[既存: Collect resulting diff(194) → Build summary(208)]
```

**この位置を選んだ理由**:

1. **既存の系列が丸ごと完了してから新しい工程が始まる。** 振り返り本体・期日更新・report保存はすべて手前で終わる。**新工程が失敗しても、既存動作は1つも欠けない**(AC9)。逆順にすると、評価が長引いた場合に既存側が実行されない事態が起こりうる(査読F-1後段)。
2. **`Collect resulting diff` と `Build summary` より前**に置くことで、最終的な `git status` と summary が評価の結果まで含む。`Build summary` は `incident_eval_summary` を読む必要がある。
3. 3ファイルに割るのは所有者を分けるためである(§4のU3/U4)。

#### 時間予算(査読F-1。**放置すると月次ジョブごとSIGKILLされる**)

F16のとおり、現行のunitの予算は **2400秒**、既存の `claude -p` 単体の上限が **1800秒**である。2本目を足せば予算を確実に超え、`Type=oneshot` の超過は SIGTERM→SIGKILL となり、**`post_tasks` のSlack通知ごと消える**。これは同roleが `tasks/main.yml:35-37` で「素の fail は…post_tasks の Slack 通知がスキップされて『中止したこと自体』が誰にも伝わらない」として明示的に避けた失敗の形そのものであり、**AC9違反である。**

**決めた実値**:

| 項目 | 値 | 根拠 |
|---|---|---|
| `knowledge_review_timeout`(既存・振り返り本体) | **1800(据え置き)** | 既存動作を変えない |
| `knowledge_review_incident_timeout`(新設・評価) | **900** | 評価は `summary.json` を起点に窓を区切って読む(§2.5・R-6)ため、全repoを仕分ける振り返り本体より軽い。半分を割り当てる |
| `TimeoutStartSec`(unit) | **`knowledge_review_timeout + knowledge_review_incident_timeout + 900` = 3600** | 2本の上限の和(2700)に、preflight・auto-memoryスナップショット(`cp -a`)・`git status` 2回・prompt描画・Slack送信のための余裕900を足す。**既存の余裕600から300増やしたのは、工程が1本増えた分である** |
| 実行順 | **振り返り本体が先、評価が後** | 上記「挿入位置を選んだ理由」1 |

**これはunitテンプレートの変更を伴う** → `roles/knowledge_review/templates/knowledge-review.service.j2` を書き換え、**`playbooks/knowledge_review_timer.yml` で再配備する必要がある**(`install_timer.yml` は `become: true`)。**配備は独立した工程単位(U10)であり、W1(Yoshinobuのcommit)に依存する。**§4・§5に入れた。

### 2.5 D-4 評価の出力(Q4)

- LLMは**標準出力に評価本文を返すだけ**。ファイル化・配置・命名はAnsibleが行う(F10と同じ形)。
- 成果物: `reports/incidents/_evaluations/<YYYY-MM-DD>-incident-evaluation.md`(gitignore済み。AC5・AC6)。
- 併せてAnsibleが**決定論的なindex** `reports/incidents/_evaluations/<YYYY-MM-DD>-index.json` を書く(§2.6の検知の入力かつ出力)。
- **`_evaluations/` は同期の書込対象外**であるため、ミラーの上書きで消えない(IC-031)。
- promptには、月次promptと同じ**注入対策の段落**(F13)と、**生ログを転記せずバンドルへの参照だけ書く**指示(IC-017)を入れる。後者は文章による規律であり境界ではない — 構造側の担保は「成果物はgitignore済みで、人のレビューを経ないと公開repoへ入らない」ことである。
- **規律である以上、遵守を測る観測を置く**(査読F-8)。U9が評価成果物を読み、**生ログの転記が無くバンドルへの参照だけであること**を確認する。守られているかを誰も見ない状態にしない。

### 2.6 検知(Q5、P0-5、AC7、AC8)— 決めたこと

**① 転送が止まったこと**

| 層 | 観測点 | 検知までの時間 |
|---|---|---|
| 1 | 同期プロセスが**非ゼロ終了**し、systemdが `failed` を報告。あわせて `alerts` チャンネルへSlack通知 | 1周期(1時間) |
| 2 | 同期は成功したが**ミラーの `_heartbeat.json` が古い**(既定 3時間 = 収集器の5分周期の36倍)→ Slack warning。収集器の死とネットワーク片側断の両方をこの1点で拾える(F2の設計意図の利用) | 1周期(1時間) |
| 3 | 月次評価が `_sync/last-sync.json` とミラーの心拍年齢を読み、古ければ通知のseverityを上げ、評価成果物にも書く | 最大1か月 |

**数値の関係(P0-2)**: quory側の保持は30日(F3)。同期は毎時なので保持窓の中に約720回の再試行機会がある。1回でも失敗すれば層1で即座に可視化されるため、**転送の停止が保持期間の満了に到達するには、失敗が可視化された状態で30日放置される必要がある**。

**残る死角(受け入れる。§6 R-4)**: timerが `disable`/`mask` されるか、ansyが長期停止すると層1・層2は発火せず、層3(最大1か月)だけが残る。これは保持期間30日と拮抗する。**閉じるなら既存の日次healthcheckへ1行足すのが筋**だが、v1では器を増やさず、残存リスクとして記録する。

**② 評価結果が昇格されないまま滞留していること**

`docs/ai/memory/incidents/` のIncidentの型(`skills/incident-recording/SKILL.md`)には**相関IDの欄が無い**。したがって「このバンドルは昇格済みか」をIDで機械照合する設計は、人が毎回IDを書く新しい約束を必要とし、書き忘れると滞留カウンタが永久に減らない。**採らない。**

代わりに、**人の記帳を一切必要としない指標**をAnsibleが数える。

**尺度は「ミラーのファイルmtime」ではなく「`summary.json` の `generated_at`」とする**(査読F-3、Coordinator決定6)。初版はmtimeを使い「rsyncがmtimeを保存するため」を根拠にしていたが、**F17のとおり `fetch` 経路はmtimeを保存しない。**転送機構の選択で指標の意味が変わる設計は採らない。`generated_at` は収集器が書き出し直前に全バンドルへ無条件で入れる値であり(F19)、**どの機構で運んでも、何度運び直しても変わらない。**心拍と run report も同じフィールドを持つため、心拍の年齢判定も同じ尺度で統一できる。

- `bundles_new_since_last_eval`: `summary.json` の `generated_at` が前回評価日以降であるバンドルの数
- `incidents_added_since_last_eval`: `docs/ai/memory/incidents/` のうち、**ファイル名の日付**が前回評価日以降のもの(SKILLが `<YYYY-MM-DD>_<slug>.md` を規定。mtimeはcheckoutで壊れるので使わない)
- `oldest_unreviewed_bundle_age_days`: 前回評価以降に現れたバンドルのうち `generated_at` が最も古いものの経過日数

**IC-033の前提条件2との関係**: 「評価は前回評価時点からの差分を数え、遅れて実行しても取りこぼさない」を満たす形になっている。`previous_evaluation_date` は `_evaluations/` に実在するindexのうち最新の日付であり、**評価が何か月止まっても、次に走ったときの窓はその分だけ広がる**。中止は喪失ではなく遅延に留まる。

**滞留の判定**: 前者が正で後者が0のまま次の月次を迎えたら、「N件の新しい証拠が届いたが、その間にIncident記録は1件も増えていない。最古はD日前」と**件数と経過日数**で報告する(AC8)。粗いが決定論的で、誰も記帳しなくても自己回復する。

**既知条件のノイズ(P1-1)**: 実測で約半数がpve1の平日運用由来である以上、この件数は初期から大きく出る。v1では**除外せず、件数を分けもしない**(requirementはP1で「除外しない形でもよい」を許容している)。信号として意味を持つのは絶対値ではなく「Incidentが1件も増えていない」という側である。判定基準の設計は後続へ回す。

### 2.7 IC-025(月次評価は作業ツリーが汚れているとき実行しない)との関係 — **重要**

**評価工程は既存の中止判定の後ろに置き、汚れていれば評価も走らせない(安全側)。**

- 評価セッションは書込許可をゼロで走るため、安全弁の理由(「進行中の変更へ書き込みを混ぜない」`roles/knowledge_review/tasks/main.yml:6`、`:48`)は評価段には当たらない。**それでも走らせる設計は採らない** — IC-025は「月次評価は…実行しない」と書いており、その一部だけを例外にするのは**Policyを緩める判断**にあたる。requirement §7が禁じている。
- **代償**: 8/26に作業ツリーが汚れていれば、評価も一緒に中止する。requirement O7のとおり汚れは日常的に発生する。
- **Policy改訂なしで目的は達成できる**: 既存の `ABORTED_DIRTY` 通知が「commit後に `systemctl start ansible-knowledge-review.service` で再実行」と案内しており(`playbooks/knowledge_review.yml:52-55`)、運用として既に成立している。8/26のゴールは「commit済みの状態で発火させる」ことで満たせる。
- **IC-033(2026-07-28追加)がこの運用を規範として確定させた** — 再実行はYoshinobuが行い、自動化は再実行しない。**本計画の設計はその枠内にある。**あわせてIC-033は成立条件を2つ課した。①転送されたミラーを削除しない → §2.2「削除しない」と一致 ②評価はcatch-up型である → §2.6・I-3の `previous_evaluation_date` と一致。**どちらも本計画が既に満たしており、崩す変更を入れない**(§7 OQ-Eに申し送り)。
- **Coordinatorへ**: 「Edit許可ゼロの評価段だけは汚れていても走らせる」という選択肢は**存在するが、Policy(IC-025)の解釈変更にあたるためYoshinobuの領域**である。本計画は提案しない。§7 OQ-Aとして記録する。

### 2.8 対話セッションからの可読性(P0-7)と、評価の単独実行

- P0-7は着地点をrepo内にしたことで自動的に満たされる(`Read` / `Grep` が届く)。
- あわせて **`playbooks/incident_evaluation.yml`(手動専用、timerに載せない)** を作り、`knowledge_review_incident_only=true` で評価工程だけを回せるようにする。理由は2つ。
  1. **検証のため。** 月次playbook全体を素で起動すると、auto-memoryのスナップショット・`MEMORY.md` の**次回期日行の書き換え**(`roles/knowledge_review/tasks/main.yml:154-173`)・Knowledge振り返り本体まで走ってしまい、**本番の月次を前倒しで消費する**。評価だけを安全に試す口が要る。**なお、実経路(2本の `claude -p` が同じ実行の中で走ること)の確認はこの口では代替できない**ため、U11が `knowledge_review_automemory_dir` を複製へ差し替えたうえで**1回だけ**全体を通す(査読F-7。手順は§4 U11に固定)。
  2. 対話セッションから任意のタイミングで評価を回せる(開発への還元というゴールに直結)。
- **新しい器ではない**(timerもscheduleも増えない)。既定値 `false` により月次の既存経路は一切変わらない(AC9)。

### I-6 Slack通知の契約

- **同期**: 成功時は**通知しない**。失敗(層1)は `alerts` / `error`、心拍staleは `alerts` / `warning`。理由 — 毎時の `ok` 通知はSlackを汚すだけでなく、`notify.yml` 経由で**ansy側の `_spool/` に毎時レコードを積む**(F8)。
- **評価**: 既存 `[knowledge_review]` 通知の本文へ**1ブロック追加**するに留める。通知そのものを増やさない。追加内容は `incident_eval_summary`、新規バンドル数、`incidents_added_since_last_eval`、最古の経過日数、心拍の年齢。
- **AC9の担保**: 既存の `slack_title` / `slack_channel` / `slack_status` の決定ロジックには触れない。severityの引き上げは、`FAILED`/`STALE` のときに限り `warning` 側へ倒す1条件の追加として行う(Coordinatorが差分で確認できる形)。

## 9. タイムラインと、間に合わない場合の切り方

- 次回の月次発火まで約4週間あり、**全体(P0-1〜P0-7)を間に合わせる前提で組んでいる。** 第2版で単位が2つ増え合計440になったが(初版380)、期間に対する余裕は変わらない。期日の正本はauto-memoryであり、ここへ写さない。
- **切るならこの線**: U0・U1・U2・U5・U7・U8(=転送だけ)を先に通す。**落ちるのはP0-4・P0-5②・AC5・AC6・AC8**であり、8/26は「対話セッションがミラーを読んで評価する」形になる(P0-7は満たされているので実行可能)。**転送を落とす選択肢は無い** — quory側の保持30日が動き続けるため、転送が無い期間は証拠が失われ続ける。
- **この線で切る場合、`knowledge_review` 側には一切手を入れない**(U3・U4・U10・U11がまとめて落ちる)。したがって**F-1の時間予算の問題も発生しない** — 評価工程を足さない限り `claude -p` は1本のままである。切り方として自己完結している。
- 逆順(評価だけ先)は成立しない。評価する対象がansyに無い。
