## 2. 設計判断とその根拠

### 2.1 中間factの命名

`incident_eval_index` はI-5が定める契約上のfact名であり変更していない(U4→評価段が読む形。実際には評価前の部分集合を渡し、`incident_index_write.yml` が評価後に完成させる — I-3「このファイルは2段階で作られる」)。

一方、算出過程の中間fact(前回評価日候補リスト、バンドル一覧、心拍生データ等)はすべて `knowledge_review_incident_metrics_` を接頭辞にした。契約に無い名前まで `incident_eval_` を名乗ると、契約上のfact名(`incident_eval_index`・U3の3fact)と紛れて将来の変更で衝突・誤読を招くと判断したため。`ansible-lint` の `var-naming[no-role-prefix]` は `incident_eval_index` の1件だけが残る(U3が `incident_eval_rc`/`artifact`/`summary` について行ったのと同じ理由 — 契約で固定された名前を実装判断で変えない。§4「自己検証」参照)。

### 2.2 3指標の実装(§2.6)

- **`bundles_new_since_last_eval`**: ミラー配下の `semaphore-*`/`spool-*` ディレクトリを `find` で列挙し、各 `summary.json` を `slurp`+`from_json` で読み、`generated_at`(収集器が書き出し直前に無条件で入れる値。`incident-capture-collector.py:788`)を尺度に「前回評価日**以降**(当日を含む)」で数えた。**「以降」を包含的(`>=`)に解釈した** — previous_evaluation_dateは日付粒度(`YYYY-MM-DD`)しか持たず、同日内の重複評価(手動再実行等)でごく僅かな二重カウントが起こり得るが、IC-033が明示的に「取りこぼさない」側を優先する設計(中止は喪失でなく遅延)であるため、厳密な排他(`>`)より包摂側(`>=`)を選んだ。
- **`incidents_added_since_last_eval`**: `docs/ai/memory/incidents/` を `find` の `patterns: "????-??-??_*.md"` で列挙し(命名規約に合わない`README.md`等は find の時点で除外される)、**ファイル名の先頭10文字(日付)**で同じ「以降」判定をした。mtimeは一切参照していない(要求どおり)。
- **`oldest_unreviewed_bundle`**: 「新着」集合の中で `generated_at` が最小のものを`sort(attribute='generated_at')|first`で選び、`age_days` は `to_datetime('%Y-%m-%dT%H:%M:%S%z')` で両者をdatetime化した差分の `.days`(floor)。**bundle_idはディレクトリ名を再構成せず、`summary.json` 自身が持つ `bundle_id` フィールドをそのまま使った**(収集器がバンドル生成時に必ず入れる。`incident-capture-collector.py:592`・`:740-742`)。
- **mtimeを使わない、ということの徹底**: `find` の結果(`item.mtime`等)は一切読んでいない。日付比較はすべて `summary.json`/ファイル名由来の文字列・値のみで行った。

### 2.3 `mirror_heartbeat_age_seconds` / `mirror_stale`(検知②③・§2.6層3)

心拍ファイル(`_heartbeat.json`)が読めない(同期が一度も成功していない/ファイルが壊れている)場合、`mirror_heartbeat_age_seconds` は `null`、`mirror_stale` は **無条件で `true`** にした。「未知」を「新鮮」側へ倒すと検知漏れ(IC-021違反)になるため、安全側(stale扱い)へ倒す判断をした。

**しきい値 `knowledge_review_incident_heartbeat_max_age_s`(既定10800秒=3時間)は `roles/knowledge_review/defaults/main.yml` に置いた(2026-07-28、Coordinator差し戻しにより改訂)。** 初回提出では `incident_metrics.yml` のJinja式に `| default(10800)` としてインラインの即値を埋めていたが、これは「設定できない(defaultsに無いので実質の既定値がコード中に隠れる)」「見えない(他の調整可能な値はすべてdefaultsに並ぶのに、この閾値だけ気づけない)」の2点で問題があるとCoordinatorから差し戻された。設計(ミラーの `_heartbeat.json` から評価時点で再計算する。同期timer停止時の検出手段になる)自体は妥当と判定されたため変更していない。

修正後は `incident_metrics.yml:212-224`(「Compute mirror_stale」タスク)が変数を直接参照するだけになり、`| default(...)` は付けていない。`defaults/main.yml` 側のコメントに、`roles/incident_sync/defaults/main.yml` の `incident_sync_heartbeat_max_age_s`(同じ3時間・同じ10800)と**値を揃える意図だが変数としては独立しており、片方だけ変えるとstale判定の基準がroleごとにずれる**ことを明記した(統合はしない、というCoordinatorの指示どおり)。`grep -rn "10800" roles/` で両roleの1箇所ずつにしか現れないことを確認済み(§3)。

### 2.4 I-3の2段階書き出し(`incident_eval_index` → `incident_eval_index_final`)

`incident_index_write.yml` は `incident_eval_index`(metrics.ymlが作った部分集合)と、U3が生成する `incident_eval_rc`/`incident_eval_artifact` を `combine()` フィルタで合成し、schema上のキー名 `evaluation_rc`/`evaluation_artifact` へ変換して書き出す。

- `incident_eval_rc`/`incident_eval_artifact` の欠落に対する `default()` は**第2引数(true)を付けていない**。理由: 第2引数trueを付けると、Jinjaの `default` フィルタは「偽値全般」(0、空文字列、false等)も未定義と同じ扱いにしてしまうため、`incident_eval_rc=0`(評価成功)という正当な値まで `-1` に上書きされる危険がある(自己検証で確認 — 第2引数無しの `default(-1)` なら rc=0 が保持されることを実測)。
- `incident_eval_index` 自体への `| default({})` は、metrics.ymlと本ファイルのwhen条件が現状完全に一致しているため理論上は常に定義済みだが、将来どちらかのwhenだけが変更された場合の防御として残した(自己検証でこの縮退経路もクラッシュしないことを確認済み)。

### 2.5 Slack通知(I-6)

`playbooks/knowledge_review.yml` の `post_tasks` の中に、**既存のif/elifチェーンの外側**へ新規ブロックを1つ追加した(`{% if incident_eval_index is defined %}`)。`incident_eval_index` はfindなど読み取り処理が成功しさえすれば必ず作られるfactで、評価工程が無効化されている(`knowledge_review_incident_eval_eval_enabled=false`)場合は未定義のままになるため、これをブロック全体のガードにした。ブロック内部の個々の値も `.get()`(ドット記法ではない)で読み、`oldest_unreviewed_bundle` が `null` の場合は `(x or {}).get(...)` で `'n/a'` へ安全に倒す。

`slack_status` は既存の三項式に**1つのOR条件を追加しただけ**(`incident_eval_summary` が `FAILED`/`STALE` のとき、base が `info` であれば `warning` へ引き上げる。base が既に `error`/`warning` ならそのまま)。`slack_title` は1文字も変更していない。`slack_channel` は初回提出時点では無変更だったが、これがU6のBlockingを生んだ(§2.6)。

### 2.6 U6独立レビュー対応(2026-07-28)

**Blocking: `slack_channel`が障害評価を反映しない(U6 Critical #1)。** 初回提出の`slack_channel`は`knowledge_review_summary in ['CHANGES','NO_CHANGES']`のみで決まっており、`incident_eval_summary`を一切見ていなかった。その結果、月次振り返り本体が健全(`NO_CHANGES`)でも障害評価が`FAILED`/`STALE`なら、`slack_status`は`warning`へ上がるのに通知は`info`チャンネルへ流れるという不整合があった。

Coordinatorの判断: **これは実装の逸脱ではなく契約(I-6)側の穴であり、契約をCoordinatorが改めた** — I-6は「`slack_channel`の決定ロジックには触れない」としていたが、計画R-4が「同期timer停止時は月次評価(層3)が最後の砦」と受容している以上、その最後の警告が`info`へ落ちるのは受容した残存リスクの見積もりより実際の検知力が弱いことになる。`slack_status`と同じ条件を`slack_channel`にも追加してよい、とCoordinatorが契約を修正した。

実装は`slack_status`で確立した形と対称にした。

```yaml
slack_channel: >-
  {{ 'info' if (knowledge_review_summary in ['CHANGES', 'NO_CHANGES']
                and (incident_eval_summary | default('OK')) not in ['FAILED', 'STALE'])
     else 'alerts' }}
```

「healthy(`info`側)になるのは、振り返り本体がhealthyで**かつ**障害評価もhealthyなときだけ」という条件へ変えた。振り返り本体が既に`alerts`側(`FAILED`/`ABORTED_DIRTY`)ならこの追加条件を評価するまでもなく`alerts`のままであり、既存の分岐は壊れていない。

**Suggestion: `TimeoutStartSec`の`+900`の余裕分と`knowledge_review_incident_timeout`(既定900)が数値として一致している(U6 Suggestion #2)。** `roles/knowledge_review/templates/knowledge-review.service.j2`のコメントへ、この2つが独立な値であり片方を変えてももう片方は追随しないことを明記した(式そのものは変更していない)。
