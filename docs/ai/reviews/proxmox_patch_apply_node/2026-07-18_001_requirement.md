# 要求仕様: patch apply の DL/適用分離 + NAS deb キャッシュ + ログ永続化

作成日: 2026-07-18
起票: claude（要件定義）
種別: 変更系（tasks/main.yml, defaults/main.yml ほか）

## 目的

`proxmox_patch_apply_node` の適用を、いまの `command: apt-get -y dist-upgrade`
一発から改善する。狙いは3つ。

1. **可視化・切り分け**: download と apply(展開/設定) を別タスクに分離し、
   失敗を `download_failed` / `apply_failed` に区別する。`command` モジュールは
   stdout を完了まで返さないため、現状は DL 中ずっと無応答に見える
   （2026-07-18 に pve2 で約30分の「無応答」が実は正常 DL 中だった）。
2. **DL 遅延の根治**: パッケージ deb を NAS 共有に prefetch し、各ノードは
   ローカルキャッシュに seed してから apply する。海外 CDN からの遅い DL を
   「1回だけ」にする（方式①・サーバ無し）。
3. **ログ永続化**: download / apply 各フェーズの出力を対象ノードに保存する
   （現状は `_apply_stdout` を report 内で3000字 truncate するのみ）。

## 背景 / 根拠

- 2026-07-11_001（tester 調査）: 所要時間差の主因は download 速度差。同一 257MB を
  pve2=`4分43秒/909 kB/s`、pve1=`31秒/8,190 kB/s`。install/initramfs 性能差ではない。
  当時「なぜ pve2 が 909 kB/s だったか」は apt report だけでは未分解のまま。
- 2026-07-18（本セッション）で真因確定:
  - Proxmox CDN の GeoDNS がこの日本網を **シンガポール**へ向ける
    （`dig` CNAME: download.proxmox.com→download.cdn→**jp.as.cdn→sg.cdn**、
    traceroute hop12=`sg3.cdn.proxmox.com`）。
  - ping 実測: 近い SG ノード=RTT73ms→単一フロー30MB/s、遠経路の sg3 ノード=
    RTT179ms→6.5MB/s。**apt は少コネクションの単一フロー → スループットが RTT に反比例**。
    パッチ時 ~1MB/s は悪い SG ノード＋DL 負荷ロス。どのノードを引くかで速い/遅いが決まる。
  - ハード/WAN 経路/sophos の配置/IPv6/MTU(1500) は全てシロ（両 pve とも 10GbE FD、
    client speedtest は sophos 位置に依らず 6.8Gbps）。
- 対処方針: 海外 CDN への距離は消せないので、**SG からの取得を1回に集約**する
  ローカル deb キャッシュ（NAS）を導入する。apt-cacher-ng(常駐proxy)/POM(150GBフルミラー)
  は今回不採用（将来トラブル時のエスカレーション）。

## 対象

- グループ: proxmox
- ホスト: pve1, pve2
- 実行前提: **既存の PVE ストレージ `Synology-nfs`（NFS）を流用**。両ノードに

  → **ロール側で mount タスクは不要**。参照はこの PVE マウントパス（IP は書かない）。
- deb キャッシュ用ディレクトリ（案・調整可）: `/mnt/pve/Synology-nfs/proxmox-patch-cache/<YYYYMMDD>/`

## 実施内容

### 1. Phase 2 を download / apply に分割

現行の単一タスク「Apply patches (apt-get dist-upgrade)」(main.yml:293) を分割する。
各ノードの実行順は次のとおり（NAS キャッシュ有効時）:

1. **seed（2a 前）**: NAS の当日ディレクトリが在れば
   `cp -n <nas_dir>/<YYYYMMDD>/*.deb /var/cache/apt/archives/`
2. **2a download**: `apt-get -y -d dist-upgrade`（DEBIAN_FRONTEND=noninteractive）
   → ローカル archives の不足分だけ取得。2ノード目は seed 済みなので取得ゼロ。
3. **publish（2a 後）**: `cp -n /var/cache/apt/archives/*.deb <nas_dir>/<YYYYMMDD>/`
   → 後続ノード用に NAS へ公開。1ノード目がここで全 deb を載せる。
4. **2b apply**: `apt-get -y dist-upgrade` → この時点で `Need to get 0 B`、ローカル速度で適用。

- 各ノードが seed→download(不足のみ)→publish→apply で対称。SG からの実 DL は
  「新 deb につき1回・最初のノードだけ」に集約される。
- `apt-get update` は前段 predryrun で実施済のため、seed した deb は実リポ索引の
  ハッシュで検証されて使われる（署名/自前 Packages 索引は**不要**）。

### 1.5 異なるスタートラインでの正当性（重要）

pve1 と pve2 のインストール済み版・保留・カーネル世代が**食い違っていても壊れない**。
NAS deb キャッシュは**正当性の前提ではなく最適化**であり、安全弁は apt 自身にある。

- `apt-get -d` / `dist-upgrade` は、`/var/cache/apt/archives/` に置かれた deb を、その
  **ノード自身の索引（`apt-get update` で取得した Packages/Release のhash・version）**
  と照合してからしか使わない。一致しない deb は**使われず、SG から取り直される**だけ。
  → **キャッシュ起因で誤った版をインストールすることは構造上あり得ない。**
- スタートラインが違うと、キャッシュは**交差分（両ノードが同版で必要とする deb）だけ**
  効き、**差分は各ノードが SG から落とす**。`Need to get 0 B` が `Need to get <小>` に
  劣化するだけで、失敗はしない。1ノードだけが必要とする deb（例: 片方だけの追加
  パッケージや別カーネル）は、そのノードで普通に取得される。
- 日付キー（`<YYYYMMDD>`）により、**別日パッチは別 dir = 相互流用しない**（陳腐化を回避、
  安全側）。相互流用の恩恵が出るのは **同一 run/同日に両ノードを回す時**（＝weekly_full の
  通常フロー）。別日なら各ノードが自分の SG DL を払うが、分割・ログ・report 改善は効く。
- seed したが使われなかった deb は archives に残るだけ（無害）。必要なら apply 後に
  `apt-get autoclean` で索引から消えた分を掃除。

### 1.6 ミラー選択（probe-and-pin）— 遅い SG ノードの回避

prefetch(2a) で実 DL が発生する時、掴む SG ノードのくじ（1〜30MB/s）を「速い1台に
決め打ち」して均す。**生 IP をリポに焼く固定はしない**（`download.proxmox.com` は GeoDNS
で回る CDN ノード群＝IP は ephemeral。焼くと陳腐化・障害耐性ゼロ）。代わりに**毎 run その場で
測って固定**する。

手順（2a の直前、実 DL がある時。RTT probe は軽いので cache-hit 時も常時実行で可）:

1. 候補 IP を収集: `download.proxmox.com` を複数回解決／既知の per-node 名
   (`sgN.cdn.proxmox.com` 等) を引く等で数個集める。
2. **RTT で選抜(ping)**。本件では RTT が単一フロー速度のよい代理（実測: 73ms→30MB/s,
   179ms→6.5MB/s, ロス0%）。最小 RTT を採用。速度直接測定でもよいが RTT が安く十分。
3. 採用 IP を**その run だけ固定**: `/etc/hosts` に `<ip> download.proxmox.com` を一時追記
   → `apt-get -d`(prefetch)→ **必ず削除**。追記/削除は block/always で**原子的に戻す**
   （残置した hosts 行が死んだ CDN IP を指すと将来 apt が壊れるため、復元を最優先で保証）。
4. ②(speed-floor リトライ)方式は**不採用**（走行中の速度監視＋kill/resume 状態機械が重い）。
   ③はDL前に測って固定するだけで途中killが無く、単純・決定論的。

天井の明示: 最速ノードでも ~73ms/30MB/s（SG 距離は消えない）。本機能は「外れくじ(1MB/s)を
消し **安定 ~30MB/s** に均す」もの。ギガビット化はキャッシュ側の役割。257MB を 30MB/s ≈ 9秒。

代替実装メモ: `/etc/hosts` 改変を避けるなら、`apt-get --print-uris` で URL を得て大物 deb を
`curl --resolve download.proxmox.com:80:<ip>` で archives へ直接 prefetch → 残りを
`apt-get -d`、でもよい。どちらでも可、レビューで確定。

### 2. abort_type / 通知の分離

- `_apply_abort_type` に `download_failed`(2a 失敗) / `apply_failed`(2b 失敗) を追加。
  通知 subject・body、rescue、report の `abort_type` 分岐に反映する。
- NAS の mount / seed / publish 失敗は**致命にしない**（下記フォールバック）。

### 3. NAS キャッシュのフォールバック（非クリティカル依存）

- NAS 未到達・mount 失敗・seed/publish 失敗のときは、**警告を出しつつ通常経路
  （SG から直 DL）で apply を続行**できること。NAS をパッチの必須依存にしない。
- 有効/無効フラグで丸ごと切れること。

### 4. ログ永続化

- 2a / 2b の stdout+stderr を対象ノードの
  `/var/log/proxmox-patch/<run_ts>-download.log` / `-apply.log` に保存。
- ディレクトリ作成・パーミッション。世代掃除は最小（当日 dir 方式＋古い NAS dir の
  保持世代数で簡易 prune）。logrotate は今回スコープ外。

### 5. report 拡張（観測性）

- 保存 report JSON に download 統計を追加: `download_bytes` / `download_seconds` /
  `cache_hit`(= Need to get 0 B か) を最低限記録。可能なら解決したミラー(remote host)も。
  → 次回また遅い時に「どのミラーを引いたか / キャッシュが効いたか」が後追いできる。

### 6.（検討・初回スコープ外可）長尺 apply の async

- 2b は initramfs 再生成等で長引く。`async`+`poll` で SSH タイムアウト回避＋定期的な
  生存表示を検討。実装複雑度を見て初回は見送ってよい。

## defaults/main.yml に追加する変数（案）

- `proxmox_patch_apply_nas_cache_enabled: true`
- `proxmox_patch_apply_nas_cache_dir: /mnt/pve/Synology-nfs/proxmox-patch-cache`
  （既存 PVE ストレージ流用。マウントはしない・存在確認のみ）
- `proxmox_patch_apply_nas_cache_keep`: 保持する日付世代数（古い dir の prune 用）
- `proxmox_patch_apply_log_dir: /var/log/proxmox-patch`
- `proxmox_patch_apply_mirror_probe_enabled: true`（ミラー選択 probe-and-pin の ON/OFF）
- `proxmox_patch_apply_mirror_probe_count`: RTT 測定する候補 IP 数（例 3〜5）
- `proxmox_patch_apply_mirror_host: download.proxmox.com`（probe/pin 対象ホスト）

## 制約

- 既存の処理フロー・変数名・通知/レポート構造を壊さない。
- `--check`(ansible_check_mode) ネイティブ gating を維持: read-only 前段は
  `check_mode: false` で実走、DL/apply/reboot は `ansible_check_mode` でガード
  （2a/2b とも `not ansible_check_mode`。--check を安く保つ。core.md §18）。
- destructive 分類は [[feedback_destructive_classification_criteria]] の2基準
  （本番影響・本体省略でも検証価値が残るか）で判断。2a(download のみ)は本番影響なしだが、
  本番 apply の一部として 2a/2b とも `tags: [destructive]` を継続するのが無難。
  最終判断はレビューで確定。
- 秘密情報を扱わない。**IP をリポに書かない**（NAS はホスト名/内部 DNS。[[feedback_no_ip_in_repo]]）。
- **quory を使わない・常駐サーバを立てない**（方式①の前提）。
- リポの時刻表記は JST（[[reference_repo_timestamp_jst_convention]]）。ログ/report の ts に注意。

## 初回実装スコープ

- Phase 2 の seed→2a→publish→2b 分割
- `download_failed` / `apply_failed` の abort_type 分離＋通知反映
- NAS キャッシュ（enabled フラグ・フォールバック付き）
- **ミラー選択 probe-and-pin（RTT 選抜＋一時 hosts pin／原子的復元、enabled フラグ）**
- `/var/log/proxmox-patch` ログ永続化
- report への download 統計（bytes / seconds / cache_hit／可能なら採用ミラー IP・RTT）

## 初回除外スコープ

- async+poll（必要性を見て次段）
- logrotate（当日 dir 世代掃除の最小 prune のみ）
- ミラー選択の speed-floor リトライ案（走行中の速度監視＋kill/resume）— probe-and-pin で
  代替するため不採用
- キャッシュ代替案 apt-cacher-ng（常駐 proxy）/ POM（フルミラー150GB）。今回不採用、将来
  トラブル時に PBS 導入と併せ格上げ。

## shell / Ansible 責務分離

- shell: seed/publish の deb コピー、ログ tee。deb 検証は apt に委譲。
- Ansible tasks: 分割・分岐・NAS mount 確認・prefetch/seed/publish の orchestration、
  abort_type/通知/report 反映、フォールバック制御。

## テスト観点（tester 向け）

- `--check`: read-only 前段が実走、DL/apply/reboot がガードされる。
- 2ノード実機（weekly_full 経路含む）: 1ノード目 publish で NAS に deb が載り、
  2ノード目は seed で取得ゼロ → `Need to get 0 B` で SG DL 無し apply 完了。
- NAS 未到達時: 警告のうえ SG 直 DL で apply 続行（致命化しない）。
- 擬似失敗: 2a 失敗→`download_failed`、2b 失敗→`apply_failed` の subject 確認。
- ログが `/var/log/proxmox-patch` に download/apply 別で残る。report に download 統計。
