## 結論

**要修正。Must-fix 4件。**

download/apply の分離、`download_failed` / `apply_failed` の伝播、apt による node ごとの transaction 決定、永続ログと統計、NAS 失敗時の warn-and-continue、既存 apply/reboot/healthcheck フローとの接続は概ね要求どおりである。

一方、残置した `/etc/hosts` marker を見逃す経路、NAS command の待機上限、root 実行の prune 境界、check mode 中の新規 helper 配備は、安全要件を満たしていない。

## Must-fix

### 1. mirror を選択できなかった download では、SIGKILL 後の残置 marker を検出しない

該当箇所:

- `roles/proxmox_patch_apply_node/files/proxmox-patch-apt-phase.sh:68`
- `roles/proxmox_patch_apply_node/files/proxmox-patch-apt-phase.sh:69`
- `roles/proxmox_patch_apply_node/files/proxmox-patch-apt-phase.sh:73`
- `roles/proxmox_patch_apply_node/tasks/main.yml:561`

`/etc/hosts` の regular-file / symlink 検査と retained marker 検査が、次の条件内にまとめられている。

```bash
if [[ "$phase" == "download" && -n "$mirror_address" ]]; then
```

このため、以前の実行が SIGKILL されて temporary marker が残った後、次回実行で probe disabled、名前解決失敗、または全 ping 失敗により `_mirror_selected_address` が空になると、helper は marker を検査せず `apt-get -d` を開始する。Ansible の download 前後比較も、開始時点から同じ stale file なら SHA-256 / mode / uid / gid が一致して通過する。

結果として、死んだ CDN address への stale pin を「通常 DNS selection」と誤認したまま apt を実行し、残置も黙認する。これは「marker stacking reject」「no silent stale pin」の要求に反する。

修正案:

- `download` phase では `mirror_address` の有無に関係なく、apt 実行前に `/etc/hosts` が regular non-symlink であることと retained marker がないことを必ず検査する。
- backup/candidate 作成と pin の atomic replace だけを `mirror_address` 非空時に限定する。
- retained marker は自動削除せず `download_failed` で停止し、manual recovery を要求する。

### 2. NAS 操作の「bounded timeout」が保証されていない

該当箇所:

- `roles/proxmox_patch_apply_node/tasks/main.yml:365`
- `roles/proxmox_patch_apply_node/tasks/main.yml:368`
- `roles/proxmox_patch_apply_node/tasks/main.yml:379`
- `roles/proxmox_patch_apply_node/tasks/main.yml:398`
- `roles/proxmox_patch_apply_node/tasks/main.yml:442`
- `roles/proxmox_patch_apply_node/tasks/main.yml:622`
- `roles/proxmox_patch_apply_node/tasks/main.yml:654`

`findmnt` は `timeout` の外で実行されている。また、path probe / mkdir / seed / publish / prune は `timeout DURATION command` だが、`--kill-after` がない。

GNU `timeout` は duration 到達時に既定で TERM を送るだけで、対象 command が TERM で終了しなければ待ち続け得る。NFS stall を non-critical dependency として隔離する目的では、現在の形は hard bound にならない。GNU coreutils manual も、initial signal で終了しない command を KILL するには `--kill-after` が必要としている。

修正案:

- `findmnt` を含む全 NAS 関連 command を `timeout --kill-after=<短い猶予> <上限> ...` で包む。
- path probe の固定15秒も同様にする。
- kernel の uninterruptible sleep は userspace timeout だけでは解消できないという限界は残るが、少なくとも TERM 無視による無期限待機を防ぐ。
- 現在どおり `failed_when: false` と warning/report 記録は維持する。

参考: <https://www.gnu.org/software/coreutils/manual/html_node/timeout-invocation.html>

### 3. root で実行する prune の許可境界が広すぎる

該当箇所:

- `roles/proxmox_patch_apply_node/tasks/main.yml:18`
- `roles/proxmox_patch_apply_node/tasks/main.yml:20`
- `roles/proxmox_patch_apply_node/tasks/main.yml:22`
- `roles/proxmox_patch_apply_node/files/proxmox-patch-cache.sh:11`
- `roles/proxmox_patch_apply_node/files/proxmox-patch-cache.sh:15`
- `roles/proxmox_patch_apply_node/files/proxmox-patch-cache.sh:68`

Ansible assert と `require_safe_directory` は `/`、`/mnt`、`/var` だけを直接拒否する。したがって、設定ミスで mount path を `/etc`、`/usr`、`/home`、`/root`、`/boot`、`/var/log` などにし、その配下を cache dir に指定しても検査を通る。

prune は root で `rm -rf --one-file-system` を実行するため、「cache dir は mount path の文字列上の子」というだけでは destructive command の境界として不十分である。要件の前提は既存 PVE storage の `/mnt/pve/<storage>` であり、それより広い system path を許可する必要はない。

修正案:

- mount path を `/mnt/pve/<単一の安全な storage 名>` に制限する。
- cache dir はその mount path の直下または明示した subtree に厳密に制限する。
- helper 側でも operation ごとの期待境界を検査する。少なくとも seed destination / publish source は `/var/cache/apt/archives` に固定し、prune source は検証済み cache root と一致させる。
- copy 対象の `.deb` は regular non-symlink file に限定する。`cp` は既定で source symlink を辿るため、cache 内の symlink を archive として読ませない。

参考: <https://www.gnu.org/software/coreutils/manual/html_node/cp-invocation.html>

### 4. check mode が新規 helper を実際に対象 node へ書き込む

該当箇所:

- `roles/proxmox_patch_apply_node/tasks/main.yml:204`
- `roles/proxmox_patch_apply_node/tasks/main.yml:211`
- `roles/proxmox_patch_apply_node/tasks/main.yml:213`
- `roles/proxmox_patch_apply_node/tasks/main.yml:220`

`Copy apt phase runner` と `Copy optional NAS cache helper` に `check_mode: false` が付いているため、`--check` でも `/usr/local/sbin` を実際に作成・更新する。

この2 helper は `when: not ansible_check_mode` の destructive block 内でしか呼ばれず、check mode の read-only precheck には不要である。要求仕様が `check_mode: false` の実走を求めているのは検証価値のある read-only 前段であり、未使用 helper の配備は read-only ではない。

修正案:

- この2 copy から `check_mode: false` を外し、native check-mode simulation にする。
- または `when: not ansible_check_mode` で配備自体を skip する。
- 既存 collect helper は check mode の read-only collection に必要なので、今回の2 helper と分けて扱う。

## Suggestion

### pre-apt safety failure を persistent log と通知へ残す

該当箇所:

- `roles/proxmox_patch_apply_node/files/proxmox-patch-apt-phase.sh:70`
- `roles/proxmox_patch_apply_node/files/proxmox-patch-apt-phase.sh:74`
- `roles/proxmox_patch_apply_node/tasks/main.yml:607`

regular-file / marker 拒否は stderr のみに出て、既に作成した persistent log には残らない。Ansible の `_apply_error_msg` も rc と log path のみなので、後追い時に marker 残置が原因だと分かりにくい。

安全検査エラーを `tee -a "$log_path"` し、download failure の通知/reportにも `_download_raw.stderr` の短い抜粋を入れると、manual recovery の判断が速い。

## 確認できた点

- `/etc/hosts` pin は同一 directory の candidate から atomic renameし、backup は metadata-preserving copy、通常の EXIT/HUP/INT/TERM では atomic restoreする。
- Ansible は download failure を直ちに task failure にせず、download 後にも `/etc/hosts` の SHA-256 / mode / uid / gid を比較してから停止する。
- seed は `.deb` を archives に置くだけで、transaction の選択と取得物の検証は各 node の `apt-get -d dist-upgrade` / `apt-get dist-upgrade` に委譲されている。異なる package starting line を直接 `dpkg` で上書きする経路はない。
- NAS の availability / seed / publish / prune failure は `failed_when: false` と warning fact で direct download/apply を継続する構造である。
- download 前に `download_failed`、apply 前に `apply_failed` を設定し、rescue、通知、report の分岐へ伝播する。
- apt command は `DEBIAN_FRONTEND=noninteractive LC_ALL=C` で実行され、pipeline の apt rc は `PIPESTATUS[0]` で保持する。
- `Fetched` の単位変換、`Need to get 0 B` の cache-hit marker、apply elapsed marker は shell output から report factへ接続されている。
- target が Trixie である前提では `cp --update=none` の利用は成立する。
- destructive block の seed/download/publish/prune/apply と reboot は `ansible_check_mode` で gate され、既存の前後 dry-run / healthcheck / notify / report の大枠は維持されている。
