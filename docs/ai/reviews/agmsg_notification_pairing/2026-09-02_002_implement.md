## 2. `scripts/oprc-submit.sh` の設計

**登録は取り消せない。** したがって「通知できない状態では登録しない」を、登録より前の停止で作る。

1. 要旨が空(空白のみを含む)なら停止 — submitしない
2. payloadがJSONとして読めなければ停止 — submitしない
3. `send.sh` / `team.sh` が存在しなければ停止 — **通知経路が無い状態で登録しない**
3-2. **teamが存在し、`coordinator` と `operator` の両方がrosterに居ることを確かめる。** これらは `send.sh` が送信時にしか検査しないため、確かめずに進むと不可逆なsubmitの後で初めて「送れない」が分かる
3-3. **`oprc.ids` を読めることを確かめる。** 返ってきた `request_id` を検証できない状態で登録しない
4. submit失敗 → 通知は送らず非0(登録されていない)
5. 応答から**契約に適合する** `request_id` を読めない → **登録された可能性を明示**して非0。通知は送らない。応答がobjectであること、`request_id` が文字列でありID形式に適合することまで見る(truthy判定だとdictや改行入り文字列をそのままIDとして通知してしまう)。形式契約は `roles/operator_request_channel/files/oprc/ids.py` を読み込んで使い、正規表現をここへ写さない
6. 通知の送信失敗 → **「登録済みで取り消せない、通知だけが未送」**と、手で送り直すコマンドを示して非0
7. 正常 → `登録: <request_id>` と `通知: 送信済み` の2行

通知の本文は `request_id` + 要旨 + 「本文はspoolのrequestをshow-requestで読んでください」。**本文そのものは載せない**(agmsgはDLPを通らない)。

**負のコントロールを3本取った。** ①rosterのidentity検査を潰すと**4と5だけがFAIL**、②`request_id` の型・形式検査をtruthy判定へ弱めると**dictと形式不正だけがFAIL**、③`value != value.strip()` を外すと**末尾LFの1件だけがFAIL**する。テストが素通りしていないことの確認である。

**末尾LFのfixtureはJSON escapeのまま渡す。** 生LFを本文へ埋めるとJSON自体が壊れ、`json.load` の失敗経路へ落ちて `strip` 検査を一度も通らない(Pythonの `$` は末尾LFの手前で一致するため、この検査が無いと素通りする)。生LF版は「応答がJSONとして読めない」経路として別に置いた。

**回帰テストが `.gitignore` の `scripts/tests/*` に一致していた。** 打消しを足すまで `git status --untracked-files=all` にも現れず、commitすれば消える状態だった。修正後に未追跡として現れることを確認した。

## 4. 残っているもの

- **wrapperを使わず `operator-channel-client submit` を直接叩けば、この担保は外れる。** 機械では捕まえられない — ansy側に「自分が何を登録したか」の記録が無く、`list` が返すのはquory発のoutboundだけである。捕まえるには client へ台帳を持たせる必要があり、requirement §6 で範囲外とした
- **remote teamでは、通知が相手の文脈に入ったことを確かめられない。** 既読が戻らないため、確かめられるのは送信までである。その先はOperatorセッションの起動(Yoshinobu)に委ねられる
- **要旨に何を書くかはwrapperが検査しない。** agmsgにDLPは無く、載せてよいものの判断は書き手に残る
