# requirement: 依頼の登録と、相手へのagmsg通知をセットで成立させる

日付: 2026-09-02
状態: 起案(Yoshinobu合意済み、2026-09-02)

## 1. 背景

**Coordinatorがagmsgを通知として正しく使えておらず、quory側Operatorとcodex側Reviewerが、OPREQやレビュー依頼の内容に気づかないまま放置になりうる**(Yoshinobu、2026-09-02)。

`docs/ai/roles/coordinator.md` は「OPREQを登録したら、続けてagmsgでOperatorへ通知する。登録は通知ではない」と定めていた。**規範はあるが、成立したかを誰も確かめていない。** 登録(`operator-channel-client submit`)と通知(`send.sh`)は別々のコマンドであり、片方だけを実行しても何も咎めない。

codex Reviewerについては、**初回依頼を `spawn.sh --boot-prompt` で渡すと、依頼がメッセージとして1通も存在しない状態になる**。2026-09-01の `loki_investigate_vocabulary` の初回依頼がこれに当たり、agmsgの履歴に無い。存在しないものは配送も既読も確かめられない。

## 2. 誤っていた前提(記録として残す)

本案件の検討で、Coordinatorは次の2つを誤って前提に置き、Yoshinobuに2回訂正された。

1. **「返りに気づけないこと」が課題だと読んだ。** 課題は送りの側である。
2. **「Operatorセッションは自動起動しないので、通知の宛先には誰も居ない」と書いた。** 誤りである。**起動するのはYoshinobuであり、起動されるまではYoshinobuが責任を持つ。相手は常に存在する前提で送る。**

**気づかせるのはメッセージの送り手であるCoordinatorであり、その手段はagmsgしかない。**

## 3. 測った事実

| 事実 | 手段 |
|---|---|
| 既読マークは recipient 側のセッションが取り込んだときにしか付かない | `check-inbox.sh` / `inbox.sh` の `storage_mark_read_batch` |
| local team `homelab` では両方向とも `○` になる — 送り手から受け取りを確かめられる | `history.sh homelab` |
| **remote team `homelab-ops` では使えない。`coordinator → operator` の全メッセージが `●` のままである** — 4分後にOPRESが返った 2026-08-17 の通知も `●` | `history.sh homelab-ops` |
| ansy側に「自分が何を登録したか」の記録は無い。clientの語彙は submit / list / get / status で、`list` が返すのは quory 発の outbound だけ | `roles/operator_request_channel/files/bin/operator-channel-client` |

**remote側で送信後に確かめられるのは「送ったこと」までである。** その先はOperatorセッションの起動に委ねられる。

## 4. 目的

**登録(または依頼)と、相手への通知が、片方だけ起きた状態を作れないようにする。**

## 5. 受入条件

- **AC1**: OPREQの登録と通知が1操作で行われる。**要旨が無い、通知経路が無いときは、登録より前に止まる**(登録は取り消せないため)
- **AC2**: 登録後に通知の送信が失敗したら、**「登録済みであり取り消せない、通知だけが未送である」と明示して非0で終わる。** 黙って成功にしない
- **AC3**: 応答から `request_id` を読めなかったときも、登録された可能性を明示して非0で終わる
- **AC4**: 正常時は、登録した `request_id` と通知の送信の**両方**を報告する。これがセット成立の確認になる
- **AC5**: codex Reviewerへの依頼が、**メッセージとして存在する形**で送られる。`--boot-prompt` へ依頼文を載せない
- **AC6**: 規範に「Operatorを起動するのはYoshinobu、気づかせるのはCoordinator、手段はagmsg」が明記されている。**セッションが立っていないことを通知しない理由にしない**

## 6. 範囲外

- **未応答OPREQの検出**(ansy側の台帳、セッション開始時の表示、返りの監視)。いずれも「返りに気づけない」という誤った理解の上に積んだもので、取り下げた
- **`operator-channel-client` 本体の改修。** wrapperを使わず直接叩けば担保は外れるが、それを機械で捕まえるには client へ台帳を持たせる必要があり、ansy自身への配備という別の障害物を伴う(`docs/ai/status.md` 計上済み)。今回は入れない

## 7. 制約

- **試験用のOPREQを登録しない。** spoolはappend-onlyで削除手段がCLIにもdispatcherにもplaybookにも無く(`docs/ai/context/operations/operator-request-channel.md` §5)、試験1件が永久に残る。検証はスタブで行う
- agmsgはDLPを通らない。通知に載せるのは `request_id` と要旨だけとし、本文はspoolのrequestを読ませる
