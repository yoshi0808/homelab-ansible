## 0. 方針

**ロールは1つ、`roles/grafana_provisioning` に統合する。** dashboard(R2/R3)とalerting(R4)は別種の資源だが、対象ホスト(monnie)・配備哲学(複製のみ、preflightで名前ベース参照を拒否)・restart対象(`grafana-server`)を共有する。分けても再利用は生まれず、restartの一本化(R5)がむしろ跨ぎにくくなる。

**配備単位を3段に分ける。理由はリスクの性質が異なるため(本番影響の有無・restartの有無)。**

1. **Step 1**: dashboard JSON 7枚の複製のみ。restart無し・mute不要・**本番無風**(AC1: 初回は changed=0)。
2. **Step 2**: provider yaml明示化 + alerting YAML配備 + **案件で唯一のrestart**。R8(旧4件削除)がこの直前に必須。
3. **Step 3**(P2、R10): syslogダッシュボードの追加。**Step 1/2のどちらにも依存されない**(requirement R10「詰まってもStep1・Step2は止まらない」)。並行して進めてよいが、Yoshinobuからのclassic export入手が前提のため別Implementer単位にする。

**Reviewer/Testerの検証もStep単位で分ける。** Step 1は本番無風なので検証コストが低く先に確定できる。Step 2は破壊性を持つため、Step 1が確定してからのほうが変更点を切り分けやすい。

#### 1-5b. repo↔ホストのSHA256比較(2026-07-30追加、U1実装の指摘を受けて)

**`copy` の `--diff` に依存して差分を読む設計は成立しない。** Policy TS-014が破壊的taskへ `when: not ansible_check_mode` を要求するため、Policy準拠の実装では `--check` 下で `copy` がskipされ `--diff` が何も出さない(U1実装のImplementerが指摘。requirement R7に訂正を記録済み)。

代わりに**read-onlyの比較タスクを`preflight_dashboards.yml`へ追加する**。

- ホスト側: `ansible.builtin.stat` に `checksum_algorithm: sha256` を付けて各ファイルのchecksumを取得する(ファイルが存在しない場合も扱う)。
- repo側: `lookup('file', role_path ~ '/files/dashboards/' ~ item, rstrip=False) | hash('sha256')`。

  **`rstrip=False` は必須。** 初版の計画はこれを欠いており、そのまま実装すると**ホストとrepoがバイト一致していても全7枚が`match: false`になる**(2026-07-30、U1実装のImplementerがdecoy検証で発見、Coordinatorが独立に再現確認)。Ansibleの`file` lookupは既定で`rstrip: true`のため末尾改行を落とすが、`ansible.builtin.stat`のchecksumは生バイトに対する値である。7枚全てが末尾LFを持つため、差は必ず出る。

  ```
  default (rstrip暗黙true) = 0bf33649...   ← 常に不一致になる
  rstrip=False             = 9d0ba20c...   ← statおよびsha256sumと一致
  ```

  **目視では検出できない誤り**であり、`docs/ai/memory/lessons/verify-through-the-consuming-filter.md`(フィルタまで通して検証する)が扱う欠陥クラスに該当する。式を書いた側(Coordinator)が見落とし、既知一致のdecoyで実際の出力を確認した側(Implementer)が捕らえた。
- 一致/不一致/ホスト側不在を、ファイル名つきで**1つのdebugまたはassertで一覧表示する**。
- **`check_mode: false` を付けて `--check` でも常時実行する**(read-onlyな診断であり、Policy TS-014が `check_mode: false` を指定している対象そのもの)。
- **不一致があっても停止しない。** これは「どちらが新しいか」を人に見せる診断であり、不一致は正当な状態(repo側を意図的に変更した直後)でもありうる。停止すべきなのはR3のnameベース参照だけである。

これによりAC6の「配備前に差が読める」は`copy`の`--diff`ではなくこのタスクの出力で満たす。**AC1(初回はchanged=0)の裏付けにもなる** — 比較で全7枚一致と出れば、`copy`がchanged=0になることが配備前に予測できる。

### Step 2を「1回のrestart」で通す起動(2026-07-30、配備前の読み直しで追記)

初版は「同じ1回のrestartにまとめる」と意図だけ書き、**起動方法を書いていなかった。** 実測(`--list-tasks`)で次が判明した。

| 起動 | provider配備 | alerting配備 | restartタスク |
|---|---|---|---|
| `--tags dashboards` | なし | なし | **0件**(Step 1が本番無風だった裏付け) |
| タグ無し(フル実行) | あり | **なし**(`never`) | 2件 |
| `--tags provider` | あり | なし | 2件 |
| `--tags alerting` | **なし** | あり | 2件 |
| **`--tags provider,alerting`** | あり | あり | 2件 |

**したがってStep 2の正しい起動は次の1コマンドである。**

```
ansible-playbook playbooks/grafana_provisioning.yml \
  --tags provider,alerting -e alert_rules_predecessor_confirmed=true
```

- **`--tags provider` と `--tags alerting` を別々に流すとrestartが2回発生し、R5「案件全体で1回に集約する」に反する。**
- **`--tags alerting` 単独ではprovider yamlが配備されない。**
- **タグ無しのフル実行はrestartしうる**(provider yamlに差分があれば`changed=true`)。これは仕様である — provider設定の変更は反映にrestartを要する。ただし**Step 2の前にフル実行すると、providerだけ明示化してrestartを1回消費し、Step 2で2回目が必要になる。**
- Step 2を上記1コマンドで通した後は、どの起動でも全て`changed=false`になりrestartは発生しない(**冪等**)。**途中で失敗したら同じコマンドを再実行するのが正しい復旧手順である。**

同じ起動をplaybookヘッダとrequirement AC3にも明記した。

restart手順(`grafana_provisioning_restart_needed`かつ`not ansible_check_mode`のときだけ):

1. `roles/recovery_mute/tasks/set.yml`をinclude(`recovery_mute_target: monnie`、`recovery_mute_minutes: {{ grafana_provisioning_mute_minutes }}`、`recovery_mute_reason: "grafana_provisioning: grafana-server restart for provider/alerting deploy"`)。
2. `ansible.builtin.systemd`で`grafana-server`を`restarted`。
3. `ansible.builtin.wait_for`でport 3000を待つ(`homelab_cert_renew`と同じ timeout 30)。
4. **`alert_configuration.configuration_hash`のread-only確認**(`become: true` + `sqlite3 ... mode=ro`、Tester・Step0で実証済みの手段)。現在値`c6c0ff263e3ebf225d478e187c42cd99`から不変であることをassertする。
5. 4ルールが`alert_rule`テーブルに存在することを同じ手段で確認する。**不在ならfailする**(1-4のQ3が想定する失敗をここで検出する)。
6. **`grafana-server`のログにprovisioningエラーが出ていないことを確認する**(`journalctl -u grafana-server --since` をrestart時刻以降で、`become: true`のread-only)。1-4のQ3(folder参照)が失敗した場合、ルール不在とログの両方に現れる。**Step 0でjournalctlは`ann`単体では読めず特権が要ると判明している**(`002_investigation.md`)ため、`become`前提で実装する。

**手順の適用条件(2026-07-30追加。初版がこれを書いておらず、U3実装で誤検出経路が生じた)**

| 手順 | 実行条件 |
|---|---|
| 1〜4(mute / restart / port待ち / `configuration_hash`不変) | **restartが起きたとき**。provider単独のrestartでも意味を持つ検査である |
| **5・6(4ルール存在 / ログのprovisioningエラー)** | **このrunでalerting YAMLを配ったときのみ** |

**5・6を「restartが起きたとき」に紐づけてはいけない。** `alerting`タグは既定実行から外れているため(1-7)、タグ無しのフル実行では provider だけがchangedになりrestartが走る。R8手順1で旧4ルールを削除済みの状態でこの経路を踏むと、**restartした上で「4ルールが無い」とfailする** — provider配備は成功しているのに失敗と報告され、かつアラート空白が続いている、という紛らわしい状態になる。

**条件が偽のときは「検査を省略した」ことが実行ログから読めるようにする。** 黙ってskipすると「4ルールを確認した」のか「確認していない」のかが後から区別できない(`docs/ai/memory/lessons/distinguish-nothing-found-from-not-run.md`)。

**手順5(DB上のルール存在確認)が主、手順6(ログ確認)が従**という位置づけを実装コメントに明記する。ログのパターン(「provisioning」と「error」を同一行に含む)は実際の失敗文言で検証できていない — 実際の失敗ログが存在しないため。ログ側が空振りしてもDB側で捕まる構造にしておけば、この未検証は許容できる。

**パネル描画の目視確認(AC3)とSlack本文の確認(AC4)はここに含めない。** admin資格情報を新設しない設計(requirement非ゴール)のため、Testerが認証付きAPIで機械化できる範囲を超える。AC3のパネル描画はYoshinobuの目視確認、AC4は次回実発火時のWatch項目とする(requirement§11で確定済み)。
