## 1. 問題定義

Grafanaの可視化とアラートが、repoの内容とホストの現物のどちらを正本とするか定まっていない。3クラスが別々の方式で管理されている。

| 対象 | 現在の管理方式 | Ansible管理か | 手作業の所在 |
|---|---|---|---|
| UniFi 7枚(Techno Tim製) | **file provisioning済み**。provider名 `unifi`、JSONは `/var/lib/grafana/dashboards/unifi-*.json` | **いいえ** | ホストへのJSON配置とprovider yamlの作成・更新 |
| `infra_syslog_all_nodes.json` | UI import → **DB管理** | いいえ | 変更のたびにUIからimport(手順書 = `docs/ai/reviews/promtail_to_alloy/2026-07-17_grafana_infra_syslog_all_dashboard_import.md`) |
| packet error / drop のアラート4件 | **UI/DB管理**(folder `UniFi`、Prometheus datasource、rule-local `notification_settings.receiver: slack-homelab`) | いいえ | 全部。閾値・PromQL・`for`・通知先がrepoのどこにも無い |

repoには `roles/unpoller/dashboads/`(7枚、tasks無し。ディレクトリ名もtypo)と `roles/alloy/dashboards/`(1枚)があるが、**いずれも配備経路を持たないスナップショット**である。「repoに置いてある」と「ホストに配備されている」が独立に動くため、どちらが新しいかを機械的に判定できない。

### 属人性の本体は2つある

1. **アラート4件がUIにしか存在しない。** 誰がいつ何を根拠に閾値を決めたかがrepoに無く、Yoshinobu以外は再現できない。ルールUID・folder・receiverは `docs/ai/reviews/promtail_to_alloy/2026-07-19_grafana_alerting_grounding.md` §5 に調査時点の値が残っているが、これは調査記録であって正本ではない。
2. **ホスト上のJSONは上流と同一でない。** 2026-07-12のGrafana 13.0.2→13.1.0で全パネルが `Data source prometheus not found` になった事故の恒久対応として、`jq walk` でdatasource参照をnameベース(`Prometheus` / `${DS_PROMETHEUS}`)からUID(`ffn83gysyghs0c`)へ機械置換している。**この変換手順はNotionの手順書にしか無い。** repoの7枚はUID参照になっており変換後の版と推測できるが、突合していない。

### 上流追跡が空白

`docs/ai/reviews/product_inventory/2026-07-17_002_manifest_v1.md` 残ギャップ2が「Techno Timダッシュボードの上流追跡手段が無く、13.1破損のような事故を事前に拾えない」を既に起票している。本案件はこのギャップに隣接するが、**同一ではない**(§3参照)。

## 2. ゴール

Yoshinobu表明(2026-07-30):

> 現行のtechno timダッシュボードのfireについては直接の私が試行錯誤して登録したので属人的になってるのが嫌なのです。

> syslogダッシュボードは自作だから更新周期は自分で決められる、techno timダッシュボードは彼のrepoが更新されたタイミングおよび別のplaybookで取り込む事を前提で考えれば良い。

- **repoを正本とし、配備をAnsibleの冪等な操作にする。** 手作業のUI importとホストへのファイル配置を経路として廃止する。
- **アラート4件をprovisioning YAMLとしてrepoへ移し、UI編集不可(provisioned)にする。** 閾値変更がgit diffに現れる状態にする。
- **配備は「repoの複製」だけを行い、変換や生成を含めない。** gitにあるものがホストにあるものと一致する状態を保つ(§5 R3)。
- 上流取り込み(upstream → repo)は配備と分離し、後続増分として独立させる。

## 3. 非ゴール

- **contact point と notification policy tree を一切変更しない。** root receiver は `empty`、child route なしのまま維持し、Slackへの到達は各ruleの `notification_settings.receiver: slack-homelab` で行う(根拠と唯一性は 2026-07-19 grounding §4)。provisioning YAMLに `policies` / `resetPolicies` / `contactPoints` / `deleteContactPoints` を書かない。
- **datasourceのprovisioning化はしない。** Loki / Prometheus はDB/UI管理のまま(grounding §2)。
- **上流追跡(`timothystewart6/unpoller-unifi` の更新検知)は本案件の範囲外。** 後続の独立増分とし、`prometheus_update_check` と同型(週次check → Slack通知 → 人間ゲート → 適用)で設計する。UID置換変換のコード化もそちらへ含める。
- **`ubuntu_vm_full_upgrade` への相乗りはしない。** ダッシュボードはapt管理外で月次適用の対象外であり、同じ判断は2026-07-16にprometheus更新チェックで既に出ている(独立playbookを採用)。
- **アラートの閾値・条件そのものの調整は本案件では行わない。** 移行で値を変えると、Slackが静かになったときに「移行の欠陥」と「新しい閾値」を切り分けられない。調整は移行完了後の別サイクルとし、その所有と手順をR13で定める。
- legacy panel型(`graph` / `table-old`)のmodern化は行わない。将来Grafanaが自動移行を廃止したら再発するが、本案件では扱わない。
- **Grafana admin資格情報 / service account token を新設しない。** reloadはサービスrestartで行う(§5 R5)。
- **旧アラート4件の削除をAnsibleに実装しない。** DB/UI管理リソースの削除であり、Yoshinobuが手動で行う(§5 R8)。
- Grafana本体・unpoller・Lokiのバージョン管理、`apt-mark hold` の方針変更は扱わない。

## 4. ユーザーストーリー

- Yoshinobuとして、packet error / dropの閾値を**git logで辿れる**ようにしたい。UIで試行錯誤した結果が自分の記憶にしか無い状態は、自分が忘れた時点で誰にも保守できないため。
- Yoshinobuとして、自作のsyslogダッシュボードを変更したら、**UIを開かずplaybookを1本回すだけ**で反映させたい。更新周期は自分で決めるので、定期実行は要らない。
- Yoshinobuとして、Techno Tim上流が更新されたときに**取り込むかどうかを自分で判断**したい。自動追従は13.1破損の再発経路になるため。
- Coordinatorとして、ホストのJSONとrepoのJSONの差を`--check --diff`で見えるようにしたい。**どちらが新しいか判定できない状態そのもの**が、07-12の事故を「配備の副作用」として再発させる余地を残すため。

## 5. 要件

### P0(初回実装に不可欠)

**R1. 調査(Step 0、read-only)。** 実装内容を確定させるため、Testerが次を観測して記録する。**変更・reload・restartは一切行わない。**

1. `/etc/grafana/provisioning/dashboards/` 配下の全ファイルを逐語取得する。provider名、`folder`、`path`、`allowUiUpdates`、`updateIntervalSeconds`、`foldersFromFilesStructure` の実値。
2. `/var/lib/grafana/dashboards/` の7枚と repo `roles/unpoller/dashboads/` の7枚を**SHA256とJSON意味の両方**で突合する。差異があれば箇所を列挙する。
3. `infra_syslog_all_nodes.json`(`dashboard.grafana.app/v2` / `kind: Dashboard` 形式)がclassic file provisionerで読めるかを、**本番へ配置せずに**判定する。判定できない場合は「不明」と返し、推測で埋めない。
4. アラート4件をGrafanaの**Export(provisioning YAML形式)で取得**する。UID・folder・group・`interval`・PromQL・比較値・`for`・`notification_settings`、および **`annotations` / `labels`(通知本文に何が入るか)** を落とさない。Slack webhook値は取得しない。
5. 上記4の`annotations`から、**発火時のSlack本文が「どの機器のどのportが、いくつだったか」を含むか**を判定する。含まないなら、その事実を明記する(R14の入力になる)。

**受入はCoordinatorが行う。** R2以降の実装はこの受入後に着手する。

**R2. dashboard provisioningをAnsibleが所有する。** provider yamlとJSONの配布をroleで冪等に行う。

現行 `unifi.yaml` は provider名 `unifi` / `folder: 'UniFi'` / `type: file` / `path: /var/lib/grafana/dashboards` / `orgId: 1` の5項目だけを持ち、**`allowUiUpdates`・`updateIntervalSeconds`・`foldersFromFilesStructure` は記述が無く Grafana の既定値に依存している**(2026-07-30調査 R1-1)。

- **既定値依存をやめ、`allowUiUpdates: false` と `updateIntervalSeconds` を明示的に書く。** 既定値は現状の意図と一致している(`allowUiUpdates` の既定は `false` なので、UniFi 7枚は**既にUI編集不可**)が、**このリポジトリはGrafana更新で既定挙動が黙って変わる事故を既に経験している**(13.1でnameベースdatasource fallback解決が廃止され全パネルが描画不能になった)。意図を値として書けば、次の更新で既定が変わっても差分として現れる。
- provider名とJSON配置パスは現行のまま維持する(下記)。

- **provider名とJSON配置パスは現行のまま(`unifi` / `/var/lib/grafana/dashboards/`)を維持する。** provider名を変えるとGrafanaが旧providerのダッシュボードを孤児として扱う経路が生じ、UID保存・folder所属・既存アラートのdashboard参照に影響しうる。**Grafanaから見て無変化、Ansibleから見て所有権移転**という形にする。
- repoのJSON正本を1箇所へ統合する(`roles/unpoller/dashboads/` の typo と配備経路の無さを同時に解消する)。移設後に旧パスへの参照が残らないことを確認する。

**R3. 配備は複製に限る。変換・生成を配備時に行わない。** テンプレート展開でJSONを組み立てず、repoのファイルをそのまま配る。加えて**nameベースのdatasource参照が1つでも含まれていたらpreflightで停止する。** これは07-12と同一クラスの破損(13.1でnameベースfallback解決が廃止された)を、誰がJSONを編集しても機械的に止めるための不変条件である。

**判定条件は精密に書く必要がある**(2026-07-30、repo 7枚の実測で確定)。「`prometheus` という文字列を探す」ような雑な検査は全ファイルを誤って弾く。

| 判定 | 対象 | 実測(7枚) | 理由 |
|---|---|---|---|
| **止める** | `${DS_...}` 形式のプレースホルダ(文字列中のどこでも) | 0件 | 名前解決に依存する。13.1で解決不能 |
| **止める** | `.datasource` の値が**文字列**であるもの(`"datasource": "Prometheus"`) | 0件 | 同上 |
| **通す** | `.datasource.type` の値が `"prometheus"` | 18〜283件/枚 | **プラグイン種別であり必須。** `{type: prometheus, uid: <UID>}` のtype側 |
| **通す** | `__inputs[].label` / `pluginId` / `pluginName`、`__requires[]` | 各1件 | 名残の宣言。解決経路に使われない |
| **通す** | `.datasource.uid` が `"grafana"` | 1件/枚 | 組み込みの `-- Grafana --` datasource(annotations用) |
| **通す** | `description` / `tags` / `links[].title` 中の `unifi-poller` 等 | 4件/枚 | 表示テキスト |

**この環境ではdatasourceの登録名を変更できない**(2026-07-30 Yoshinobu明示: 「実データを送っているのはunpollerであり、登録されるのはprometheus。ここは私が改変できません」)。上流は `__inputs: DS_PROMETHEUS`(label `Prometheus`、大文字P)を宣言し実datasource名は `prometheus`(小文字)であるため、**13.0.2まではname fallbackの大小無視で解決できていたものが13.1で解決不能になった** — これが07-12の因果である。したがってUID書き換えは偶発的な対処ではなく**上流取り込みのたびに必要な恒久的工程**であり、R11の増分に変換のコード化を含める根拠になる。

**R4. アラート4件をrule-only provisioning YAMLとしてrepoへ置く。**

**正本は `003_ui_export_alert_rules.yaml`**(2026-07-30、YoshinobuがGrafana UIの「Export rule」で出力した実物)。Grafana自身が出した形なので、これを**無編集で配備する**(2026-07-30、Yoshinobu承認)。

- **UIDもfolderも書き換えない。** exportは既存UID(`dfoih9pbfckxsf` / `bfoii89j7l88wf` / `dfoiihloh6hogd` / `dfoiiku15evi8e`)と `folder: UniFi` をそのまま持つ。UID衝突は**旧4件の削除を配備の前に置くこと**で回避する(R8)。**新UIDの割り当ては行わない** — 編集はこの案件で最も壊れやすい工程であり、Grafanaの出力を1文字も触らないことが最良の防御である。
- 配置先は `/etc/grafana/provisioning/alerting/` 配下のAnsible管理ファイル。既存 `sample.yaml` は編集しない。
- exportのtop-levelキーは `apiVersion` と `groups` のみであることを確認済み(`policies` / `contactPoints` 等を含まない)。**preflightで機械的に再検査する**(将来の編集で壊れないため)。
- 全ruleが `notification_settings: {receiver: slack-homelab}` を持つことを確認済み(単一オブジェクト形式。Q7決着)。
- 発火条件(PromQL・比較値 `0.5 gt`・`for: 1m`・`interval: 1m`)は**exportのまま**。改善案があっても本案件では適用せず、R13のサイクルへ回す。

**exportはDBの完全なダンプではなく、Grafanaが正規形と見なす形である。** DB生値にあった `relativeTimeRange`(refId C)、`labels`(空文字列)、`keep_firing_for`、`dashboard_uid`、`panel_id`、`rule_group_idx` はexportに現れない(既定値・内部表現のため省略される)。**これらを「欠落」と見て補わないこと。** rule順序はリスト順で表現される(TX Drop / RX Drop / TX Error / RX Error = DBの `rule_group_idx` 1〜4と一致)。

**R5. reloadの要否を対象ごとに分け、restartは案件全体で1回に集約する。** 3種類のファイルは反映機構が違う(2026-07-30調査 R1-1により判明)。

| 配る物 | 反映機構 | restart |
|---|---|---|
| dashboard JSON(`/var/lib/grafana/dashboards/`) | dashboard providerが `updateIntervalSeconds` 間隔でpollする | **不要** |
| provider yaml(`/etc/grafana/provisioning/dashboards/`) | 起動時読み込み | 必要 |
| alerting YAML(`/etc/grafana/provisioning/alerting/`) | 起動時読み込み(2026-07-19 grounding §7) | 必要 |

- **JSONの配布だけならrestartもmuteも要らない。** これはStep 1を本番無風で通せることを意味する。
- provider yamlの明示化(R2)とalerting YAMLの配置(R4)は**同じ1回のrestartにまとめる**。restart前に `roles/recovery_mute/tasks/set.yml` でmonnieのmute窓を張る(`recovery_push_targets` のmonnieは `grafana-server` を復旧対象に含む)。実行時刻は `ubuntu_nightly` のmonnie処理時間帯と重ねない。
- **`updateIntervalSeconds` の既定値(10秒)はGrafana公式ドキュメントの記述であり、monnie上の実挙動を観測したものではない**(調査R1-1が明示)。Step 1でJSONを配ったとき、restartなしで反映されるかどうかがそのまま実地確認になる。反映されなければprovider yamlの明示化とrestartをStep 1へ繰り上げる。

**R6. 事後検証は「サービスactive」で終わらせず、全パネルの描画とアラートのload状態まで確認する。** 07-12の教訓(`grafana-server` はactiveなのに全パネルがdatasource未解決だった)を検査項目に反映する。加えて既存4ruleとpolicy treeの非回帰をread-onlyに突合する。

**R7. tester-gateは `check-mode-native`。** read-onlyなpreflight(UID確認、top-levelキー検査、JSON参照形式検査、UID衝突検査)は `--check` でも本実行し、ファイル配置とrestartだけを `ansible_check_mode` でゲートする。`dry_run` extra-varによるfail-closedゲートは採らない — この入口はスケジューラへ登録せず人が起動するため、fail-closedが守る対象(放置された定期ジョブの自動適用)が存在しない。

**訂正(2026-07-30、U1実装のImplementer指摘により判明)**: 初版は「`--check --diff` でホストとrepoの差分が読めることが主要な安全機構になる」と書いていたが、**これはPolicyと両立しない。** `docs/ai/policies/ansible_test_safety_policy.md` TS-014 が「破壊的taskには `when: not ansible_check_mode` と `tags: [destructive]` を付ける」と定めており、Policy準拠の実装では `copy` タスクが `--check` 下でskipされるため `--diff` は何も出さない。**Policyが正本であり、requirement側の記述が誤っていた。**

**「配る前に差を読む」手段は、Policyに沿った別のタスクで実現する。** `--check` でもskipされない read-only の比較タスク(ホスト側ファイルのSHA256を `stat` で取得し、repo側の `lookup('file') | hash('sha256')` と突合して差異を報告する)を preflight 側に置く。`copy` の `--diff` に依存しない。これは診断であり `check_mode: false` を付けて常時実行してよい。

| LOG-073 | 「metrics系統の検知ルールと通知経路の規範は本書で定義せず、**将来別Policyで扱う**」「alert ruleの実体はGrafana UI側にありGit管理外であるため、リポジトリ内の記述をもって現在有効な検知内容と判断しない」 | 後半は本案件が完了した時点で**事実として偽になる**。前半は方針変更にあたる |

一方、**dashboardの規範は既に一部が本Policyに存在する**(LOG-030 / LOG-031 / LOG-077、および§2末尾「dashboard JSONの実体はcodeを正本とする」)。ただし対象はsyslog統合dashboardに限られ、UniFi metrics dashboard 7枚はどのPolicyにも現れない。ファイル名は `log_observability_policy` であり **Observability を名乗りながら本文がsyslog収集に限定されている**状態であるため、scope を観測プレーン全体へ広げる改訂は名称との整合を回復する方向である。

改訂の線引き(Coordinator案):

- **配備方式は本Policyが持つ** — repoを正本とする、provisioningで配る、UI編集不可、notification policy treeを改変しない、rule-local routingを使う、配備は複製に限る、nameベースdatasource参照を禁じる。
- **「発火条件」と「障害判断の基準」を別の概念として扱う**(Yoshinobu 2026-07-30)。**用語は下表で固定し、以後どちらも単に「閾値」と呼ばない** — 1つの語が2つの世界を指していたことが、この論点が曖昧になっていた原因である。

  | 用語 | 何を決めるか | 正本 | 属する世界 |
  |---|---|---|---|
  | **発火条件** | PromQL、比較値、評価間隔、`for` | provisioning YAML | **仕様**。根拠つきでrepoに残す |
  | **障害判断の基準** | 発火の頻度を見て障害扱いにするか | 人間の判断(LOG-065が既に明文化) | **運用**。Policyにも仕様にも書かない |

- **発火条件は仕様として管理するが、値をPolicy文書へは書かない。** 「Policyに書かない」は「管理しない」ではない — **provisioning YAML そのものが仕様書**であり、git管理・レビュー・diffの対象になる。Policyが規定するのは管理の作法(どこが正本か、根拠を併記せよ、UI編集を認めない)だけで、値は持たない。値をPolicyとYAMLの二重持ちにしない(`docs/ai/core.md`「値を二重に持たない」)。
- **境界は固定ではない。** `for` や rate 窓をルール側へ移すと、それまで運用だった解釈が仕様へ移る(§7 Q5)。移した分だけ根拠を書く義務が増える、という対称性をPolicyに明記する。
- LOG-073後半の「Git管理外」記述は、本案件のクローズをもって削除する。

**規範文書の変更であるため、Reviewerには `skills/document-norm-review` の観点で照合させる。** 特に「LOG-063 / 073 / 074 を書き換えた結果、他条項(LOG-004 / 047 / 065)と矛盾していないか」を明示的に問う。

**R13. 発火条件の試行錯誤サイクルを定義し、文書化する(Yoshinobu提起 2026-07-30)。**

「どうなったら発火するか」は単純でなく調整が要る、という前提を受ける。**移行(本案件)と調整(このサイクル)を分離**したうえで、調整の既定手段を次のとおりとする。

1. **AIが反実仮想で根拠を作る。** Prometheusのrange queryをread-onlyで引き、候補となる比較値・評価窓ごとに「直近N日で何回発火していたか」を機器/port別に算出する。今この根拠がどこにも無いことが属人性の本体であり、ここはAIが担う。
2. **Yoshinobuが意味を決める。** どのportが既知のノイズか、1時間あたり何回のdropならSlackを鳴らす価値があるか、1回のflapを事象と見るか。データから導けないため人間が担う。
3. **確定値をrepoへ置き、根拠を併記する。** 値だけでなく算出クエリ・観測期間・反実仮想の発火回数を残す(R12の規範と対応)。
4. **配備はplaybook。** 現実が想定と違えば、その観測を新しいデータとして1へ戻る。

**Grafana UIでのalert rule作成を禁止はしないが、正本にはしない。** 探索(Explore・alert preview)はread-onlyなので推奨する。試行のために非provisionedの複製ruleを作る場合は、専用folderに置き、確定後に削除する。**UIの複製から手作業で値を書き写す経路を既定にしない** — R4の「意味を変えずに移す」が最も壊れやすいのはこの転記である。

なお現行Policy LOG-065は「metrics系統では通知の発生頻度そのものを運用者が判断材料に使う。少数の発火は様子見とし、同一portのdropが頻発する場合に問題ありと判断する。**この解釈規約は閾値では表現されず人間の判断に属する**」と記録している(引用中の「閾値」はR12の用語では**発火条件**を指す)。つまり**現行の4ルールは「素朴な発火条件 + 人間側の障害判断」という意図的な設計**であり、調整不足ではない。障害判断の一部をルール側(`for`、rate、port別)へ移すならLOG-065も改訂対象になる。移すか否かはR13サイクルの中でYoshinobuが決める(§7 Q5)。

**R14. 発火の説明可能性を確保する(Yoshinobu指摘 2026-07-30)。** 「なぜ発火したのか」には2つの読みがあり、正本の置き場だけでは①しか満たさない。

| | 問い | 満たす手段 |
|---|---|---|
| ① | なぜ**この条件で**発火する設計なのか | 発火条件の根拠(算出クエリ・観測期間・反実仮想の発火回数)をYAMLに併記する(R13-3) |
| ② | なぜ**今回**発火したのか | 通知本文に「どの機器のどのportが、いくつだったか」が含まれること。ruleの`annotations` / `labels`の設計に属する |

②について、**2026-07-30の調査(R1-5)で分岐が確定した — 「含んでいない」側である。**

現行4ルールの `annotations` は機器(`{{ $labels.name }}`)とport(`{{ $labels.port_id }}` / `{{ $labels.port_name }}`)を含むが、**発火時の実測値を埋め込むプレースホルダが無い**。したがって:

- **`annotations` への実測値の追加を本案件の要件に含める。** 発火条件(PromQL・比較値・`for`・評価間隔)は一切変えないため、R4の「意味を変えずに移す」とは衝突しない。変えるのは通知本文だけである。
- **既存の `annotations` キー名は変えない。** 現行は `{"TX Drop": "TX Drop検知: ..."}` のように `summary` / `description` ではない独自キーを使っている。キー名を変えると通知本文の体裁が変わるため、追加は既存キーの文字列内に留める。
- **これは `003_ui_export_alert_rules.yaml` に加える唯一の意図的な変更である**(R4は無編集配備)。**git上では「無編集のexportをcommit」→「annotationsに実測値を追加」の2commitに分け**、忠実な移行と意図的な改善を混ぜない。配備は1回のrestartで両方を反映してよい(commitを分ける目的はdiffの可読性であって、適用の分離ではない)。
- **テンプレート式が無効だと、Grafanaは通知本文へエラー文字列を描画する**(静かに失敗せず、しかし人間が読むまで気づかない)。どの式で実測値を出すかは計画時に確定し、**実際に発火させた通知本文で確認できるまで「完了」としない**。既存4ルールが `refId: A`(Prometheusクエリ)と `refId: C`(閾値expression)の2段構成である点が式の選択に影響する。

移行後に「発火した通知を見て、どの機器のどのportが、いくつだったのか読み取れる」ことを検査項目に入れる(R6と同じ検証工程)。

### P2(後続でよい。R10は2026-07-30にP0相当へ格上げ済み)

**R10. `infra_syslog_all_nodes.json`(syslogダッシュボード)をclassic形式で入手する経路を1つ確かめる。**

**問題はダッシュボードの側ではなくファイル形式の側にある。** UniFi 7枚はclassic形式で、**今日この瞬間もfile provisioningで動いている** — このGrafanaでclassic provisioningが機能することは実証済みである。詰まっているのは「新しいUIのexportがv2形式を出す」ことだけで(公式issue `#123607`)、能力の限界ではない。

repo側で確認したこと(2026-07-30): `roles/alloy/dashboards/`、`docs/ai/reviews/promtail_to_alloy/` の2ファイル、および `git log --follow` の全リビジョン(`6e0b53e` / `5280322`)が**すべてv2形式**。**classic形式の版はrepoに存在しない。**

**経路が確定した(2026-07-30、Yoshinobu提供のUIスクリーンショットで確認)。** Grafana 13.1の **Export dashboard → Advanced options** に `Model: [Classic] [V2 Resource]` と `Format: [JSON] [YAML]` の切替がある。**`Model: Classic` を選べばclassic形式で出力できる。** DBを掘る必要はなくなった。

したがって syslogダッシュボードも**本案件の対象に含める。** 実施時の条件:

- **`Model: Classic` / `Format: JSON` を選び、「Share dashboard with another instance」トグルは OFF のままにする。** ONにするとGrafanaは共有用の形(`__inputs` と `${DS_...}` プレースホルダ)を出力し、**これは2026-07-12に全パネルを描画不能にしたnameベース参照そのものである。** OFFならdatasource UIDがリテラルで入る。
- 万一ONで出力されたものが混入しても、**R3のpreflight検査が配置前に止める。** この経路は今回の設計で既に塞がれている(ガードが実際に効く場面がここで具体化した)。
- classic exportが `uid: infra-syslog-all-nodes-v1` を保つことを確認する。uidが変わるとブックマークや既存リンクが切れる。現行のv2ファイルは `metadata.name` = `metadata.uid` = `infra-syslog-all-nodes-v1`、`spec.title` = `Infra Syslog (All Nodes)`。
- **配置先は既存 `unifi` providerのpathではなく、別providerを新設する。** `unifi` providerは `folder: 'UniFi'` を指すため、同じpathへ置くとsyslogダッシュボードがUniFi folderに入ってしまう。**新規providerの追加は、既存providerの改名とは違って孤児化リスクを持たない**(R2の警告は改名についてのもの)。folder名は現在このダッシュボードが置かれているfolderに合わせる(実施時に確認する)。
- **現在この1枚はUI import由来のDB管理**であり、同一uidをfile provisioningで引き取る形になる。dashboardはalert ruleと違って provenance衝突ではなく「provisionedとして引き取られる」挙動が期待されるが、**これは未確認なので配置前に確かめる。** 引き取れない場合の代替はalert ruleと同じ形 — Yoshinobuが先にUIから削除する。

**この1枚の結果はUniFi 7枚とアラート4件に影響しない。** 詰まってもStep 1・Step 2は止まらない。

### UniFi 7枚をClassic exportで作り直さない(2026-07-30、Yoshinobu提起により明文化・実測で確定)

**Classic export経路はsyslogダッシュボード専用である。UniFi 7枚に適用してはいけない。**

7枚はディスク上に**classic形式の原本が既に存在し、それがrepoとバイト一致している**(R1-2)。一方でGrafanaはロード時にschemaを移行して描画しており、`Model: Classic` でexportすると**移行後の内容**が出てくる。

**実測で確定した(2026-07-30、Yoshinobu提供の `unifi-switches.json` Classic export と repo版の機械diff)。**

| 項目 | 結果 |
|---|---|
| PromQLクエリ(`targets.expr`) | **18/18完全一致**。データ取得式そのものは壊れない |
| datasource参照 | **全panel一致**(UID形式のまま) |
| panel型 | **18枚中15枚が書き換わった**(`graph`→`timeseries`、`table-old`→`table`、`autoMigrateFrom`に旧型を記録) |
| `schemaVersion` | export=`42` / repo=`39`(exportの方が新しい) |
| panel個別のキー | `links`(パネル間リンク)・`timeFrom`/`timeShift`(個別時刻範囲)・`cacheTimeout`・`isNew`・`pageSize` 等が消え、`autoMigrateFrom` に置き換わる |

**クエリは壊れないが、体裁設定の一部が気づかれにくい形で失われる。** 07-12は「全パネル描画不能」という派手な破壊だったが、これは**見た目だけでは検出できない劣化**であり、「機能を使っていないから安全」という確認では防げない(消えたキー自体が「元は使われていたかどうか」の証拠であり、事前のgrep検査では判定できない)。

exportで置き換えると、**クエリは同じでもファイル内容が大きく変わる**(移行が実体化する)。これは「配備は複製に限る」(R3)に反する。**7枚の正本はディスク上の原本(= repoの現物)であり、Grafanaの出力ではない。**

なお7枚は `allowUiUpdates` 既定 `false` によりUI編集が不可能なため、**Grafana内部の版がディスクの原本から人手で乖離した可能性はない。** 乖離しうるのはGrafana自身の移行処理の分だけであり、それが上表で実測された。

**R11. 上流取り込み増分の起票。** `product_inventory` 残ギャップ2と統合して1件にする。

Step 2'' はStep 2の実装が確定した後に行う(Yoshinobu指摘: 「実装に目処がついてからの更新で良い」)。**先にPolicyを書くと、実装で判明した事実と食い違ったまま規範が残る。** 閾値の調整サイクル(R13)の初回はクローズ後に回す。

## 11. 受入条件

Step 0の観測値(`002_investigation.md`)を前提に確定した。**「エラーにならない」で終わらせず、終了コード・通知の有無・観測点を明示する**(`skills/requirements-analysis`「成功の観測方法まで書く」)。対象は単一ホストなので、**monnieが到達不能な場合は継続に意味がなく、終了コード非0のfailとする**(複数ホストの部分成功を許す設計は取らない)。

**AC1(所有権移転の忠実性 — Step 1)**
Given repo 7枚とホスト7枚のSHA256が一致している(R1-2)、When dashboard配布を`--check`なしで実行する、Then **JSON配布タスクは changed=0**、終了コードは`0`、Slack通知は送られない、`grafana-server`のrestartもreloadも発生しない、7枚の描画は変化しない。
**changed≠0 なら停止する** — 配る内容がホストの現物と違うことを意味し、07-12と同一クラスの破損に踏み込む手前だからである。

**AC2(JSONの反映がrestart不要か — R5の実地確認)**
Given AC1が通っている、When repo側のJSONに可視で無害な1箇所の変更(panel titleやdescription等)を入れて配布し、`updateIntervalSeconds`(既定10秒)を超える時間待つ、Then UI上の当該dashboardへ反映される。**続けて変更を戻して再配布し、終了時のホスト側SHA256が開始時と一致すること**を確認する(この検証は可逆である)。反映されない場合はR5の分岐に従い、provider明示化とrestartをStep 1へ繰り上げる。

**AC3(restartの非回帰 — Step 2)**
Given R8の手順1〜3(削除→配備→確認)がこの順で完了している、When provider yamlとalerting YAMLを配置して`grafana-server`をrestartする、Then 終了コードは`0`、serviceがactive、**`alert_configuration.configuration_hash` が `c6c0ff263e3ebf225d478e187c42cd99` から変化していない**(policy treeとcontact pointを触っていない機械的証拠)、4件の新ルールがDB上に存在しUI上でProvisioned表示になっている(旧ルールはR8手順1で既に削除済みのため「既存ルールが残る」ことは期待しない)。
**パネル描画の確認(7枚)はYoshinobuが目視で行う** — admin資格情報を新設しない設計(§3非ゴール)のため、Testerはこの確認を認証付きAPIで機械化できない。`configuration_hash`とDB上のrule存在確認はTesterが行い、パネル描画のみYoshinobuの確認に委ねる。

**AC4(発火の説明可能性 — R14、Step 2完了の必須条件にはしない)**
Given 新ルールがloadされている、When 実際にpacket error/dropが発生する(またはYoshinobuが意図的に発火させる)、Then Slackへ通知が届き、本文に**機器名・port・発火時の実測値**が含まれる。**テンプレート式のエラー文字列が本文に描画されていないこと**を目視で確認する。

**この確認は健全なネットワーク状態では発生しない**(発火条件そのものがdrop/errorの実測を要求するため)。人為的に発火させるには実機ネットワークへの操作が要り本案件のscope外である。したがって**AC4は案件クローズの必須条件にせず、次に実際に発火した時点の確認としてWatchへ回す**(`docs/ai/status.md`の既存様式)。旧4ルール削除後は同一事象で1通のみになることも、この初回発火時に併せて確認する。

**AC5(preflightのfail-closed — R3)**
Given nameベースのdatasource参照を含む細工したJSON(decoy、本番へは配置しない)、When playbookを実行する、Then **ファイル配置に到達する前に**failで停止し、終了コードは非0、ホスト側のファイルは一切変化しない。

**AC6(`--check`の挙動 — R7)**
Given ホストとrepoが一致している、When `--check --diff`で実行する、Then preflight(JSON参照形式検査、**repo↔ホストのSHA256比較**、alerting YAMLのtop-levelキー検査)は**本実行され**、ファイル配置とrestartは実行されず(Policy TS-014に従い `when: not ansible_check_mode` でskipされる)、終了コードは`0`、Slack通知は送られない。
**`copy` の `--diff` 出力には依存しない**(R7の訂正を参照)。「repoとホストのどちらが新しいか」はSHA256比較タスクの出力で読む。
