## 対象1: U6実装

### 現物で確認した項目

1. **`deploy_provider.yml`のループ化でunifi.yaml配備結果が変わらないこと(観点1)** — **確認した。** 独立decoy(`reviewer_decoy/test_provider_loop.yml`、`ansible_connection: local`、fakeroot配下)で、Step 2既配備済みを模したunifi.yamlへ実際の`deploy_provider.yml`タスクファイルを`import_role`経由で実行し、(a) 実行前後でSHA256チェックサムが不変、(b) 2回目の実行で`grafana_provisioning_provider_result.changed`(トップレベル)が`false`になることを実測した。Implementerの申告と一致する。

2. **`grafana_provisioning_dashboard_files`と`grafana_provisioning_dashboard_destinations`の対応漏れ検出の仕組み(観点2)** — **確認した。片方だけの要素は「サイレントな誤配備」ではなく、preflight段階でfatalに落ちる。** 独立decoy(`test_missing_dest.yml`)で、`dashboard_files`にのみ存在し`dashboard_destinations`に無いファイル名を注入したところ、`Preflight | collect host-side SHA256 for managed dashboard JSON`タスクで`Error while resolving value for 'path': object of type 'dict' has no attribute '...'`という**Jinja2の未定義キーエラーで即fatal**になった。これは`deploy_dashboards.yml`のcopyタスクより**前**(`tasks/main.yml`の実行順でpreflightが先)で発生するため、実際に配置が行われる前に停止する。**fail-closedではあるがfail-clearではない** — エラーメッセージは「destinationsに追加し忘れている」ことを直接示さない汎用的なJinjaエラーであり、原因特定には`preflight_dashboards.yml`のコードを読む必要がある。Implementerも二重管理を「避けられていない」と自己申告済み(未解決事項3)であり、新規の欠陥ではないが、Suggestionとして記載する(下記)。

3. **restart判定のループ化後の正当性(観点3)** — **確認した。** 同じdecoyの`register`出力を検査し、2 item中1 itemだけ変更された場合にトップレベル`.changed`が`true`、両方無変更なら`false`になることを実測した(Implementerの実測と一致)。`restart_and_verify.yml`の`grafana_provisioning_provider_result.changed | default(false)`は無変更のままで正しく機能する。

4. **uid assertの対象範囲(観点4)** — **確認した。1枚(`infra-syslog-all-nodes.json`)のみを対象とし、8枚全部には掛からない。** `preflight_dashboards.yml`の該当タスクにloopが無く、`role_path ~ '/files/dashboards/infra-syslog-all-nodes.json'`とハードコードされている。requirement R10が「uidが変わるとブックマークが切れる」と述べる対象はこの1枚だけであり、他7枚(UniFi)には同種の懸念がrequirement上存在しない。**仕様として妥当**と判断する。誤検出は無い — 独立decoy(`test_preflight_real.yml`、実repoの8ファイルに対して`import_role`で直接実行)でR3スキャン8/8 `ok`、uid assert `ok`を確認済み。

5. **タグ経路(観点5)** — **確認した。** `ansible-playbook playbooks/grafana_provisioning.yml --list-tasks`をタグ無し/`dashboards`/`provider`/`alerting`/`provider,alerting`の5通りで実行し、計画§1-6の表(6組み合わせ)と完全に一致することを確認した。`--tags alerting`単独ではprovider配備が現れず(alerting配備はNoneの `never`タグでdefault実行から除外)、`--tags provider,alerting`でのみ両方が1回のrestartパスへ合流する。

6. **新ディレクトリのowner/mode(観点6)** — **確認した。** `deploy_dashboards.yml`の`grafana:grafana 0755`は、`002_investigation.md` R1-2bの実測値(`stat -c '%U:%G %a %n' /var/lib/grafana/dashboards` → `grafana:grafana 755`)と一致する。Implementer記録は「実測値ではなく類推」と書いているが、**R1-2bはU6実装より後に追補された実測記録であり、Implementerの実装時点ではまだ存在しなかった**(実装記録のタイムスタンプと計画§1-8の記述を突合)。Coordinatorの追補で「実測と一致した」ことが確定しているため、**現時点でこの値は実測値によって裏付けられている**。Implementerの実装コメントが「類推、実測ではない」と書いたままなのは古い状態を引きずった記述であり、Coordinatorが確定した以上コメントの更新漏れ(Suggestion、下記)。
