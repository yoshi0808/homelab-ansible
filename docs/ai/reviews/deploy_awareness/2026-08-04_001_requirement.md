# requirement: 配備が要ることに気づける仕組み(A: 検出後の案内 / B: commit時の予告)

作成日: 2026-08-04
Coordinator: claude

## 1. 問題定義

**repoを直しても配備物は古いまま**という構造(`docs/ai/context/operations/code-delivery-to-production.md` §2)は、これまでに5回起きている。5件目(2026-08-04、`incident-investigate.py`)は日次ドリフト検査が自動で拾った最初の事例だが、そこで分かったのは検出だけでは足りないということである。

- **変更する人が「この変更は配備が要る」と知る手段がrepoに1つも無い。** 昨夜の版ずれを作ったcommit(`7904ba2`)の時点で、それに気づける手がかりは存在しなかった。
- **検出しても直し方が分からない。** ドリフト通知は「食い違っている」と「レポートのパス」しか伝えず、**どのplaybookを流せば直るのか**を書いていない。受け取った人は自分でroleとplaybookの対応を辿り直すことになる。

これは人の理解不足ではなく、理解を助ける仕組みの不在である。

## 2. ゴール

1. **ドリフト通知を受け取った人が、そのまま流せるコマンドを得る。**
2. **配備が要る変更をcommitする人が、その時点で気づく。**
3. **この2つが同じ1枚の地図(ドリフト検査のカタログ)を読む。** 対応表を二重に持たない。

## 3. 非ゴール

- **配備の自動化・遠隔起動は含めない。** ansy側へ新しい能力(sudo、配備を発火するforced command)を一切増やさない。実行は従来どおりquoryのSemaphoreから人が流す。
- **`template` 配備物の内容ドリフト検査(Tier 2)そのものは作らない。** B の粗い予告でのみ触れる。
- ドリフト検査の対象カタログそのものの拡張(新しい検査対象を増やすこと)は含めない。

## 4. ユーザーストーリー

- Yoshinobuとして、ドリフト通知を受け取ったとき、**Semaphoreに何を流せばよいかを通知本文から直接知りたい**。roleとplaybookの対応を毎回辿り直したくない。
- 変更する人(Implementer / Coordinator)として、`roles/*/files/` を触ってcommitするとき、**その場で「配備が要る」と知りたい**。翌朝のドリフト通知で知るのでは、その間ずっとrepoと本番が食い違う。

## 5. 要件

### P0(必須)

**R1. カタログへ `playbook:` を持たせる**

`roles/deployment_drift_check/defaults/main.yml` の各エントリへ、**その状態を復元するplaybookの相対パス**を追加する。

- 対応は**推測で書かない。** 各 `playbooks/*_setup.yml` が実際にimportしているroleを現物で確認して決める。
- **R1-a(最重要): 実際にその状態を復元しないエントリには書かない。** 「直し方」として書かれたものが直さないなら、案内が無いときより悪い。具体的に確認を要するもの:
  - `deployment_drift_check_units` のうち **期待が `disabled` / `inactive` のもの**(ansyの `recovery-probe.service` / `recovery-io.service`)。setup playbookを流しても**無効化はされない**(roleに無効化taskが無い)。したがって `playbook:` を持たせてはならない。
  - `deployment_drift_check_forced_command_keys` — 期待エントリ数との食い違いを、該当roleのauthorized_keys配備が**排他的に上書きして直すのか**を確認する。追記型なら直さないので持たせない。
  - `deployment_drift_check_report_dirs` / `deployment_drift_check_hosts_file` — 対応するplaybookが存在しない(`/etc/hosts` はAnsible管理外)。持たせない。
- 持たないエントリでは、通知に「直し方」行を**出さない**(空文字や `-` を出さない)。

**R2. `incident_investigate_service_enabled` の期待状態をrepoへ書き出す**

R1-a の前提として必要。現状この変数は default `false` で、`inventories/homelab/host_vars/quory.yml` にも無く、**本番のtimerが有効なのは過去に一度 `-e` で渡された結果でしかない**。このままでは「timerがdisabledになっている」というドリフトに対し、`playbook:` が案内するコマンドを流しても直らない。

`recovery_probe_service_enabled` / `worktree_sync_service_enabled` が既に同ファイルにある形に揃えて、`incident_investigate_service_enabled: true` を quory の host_vars へ置く。

**R3. finding に `playbook` を載せ、通知に「直し方」を出す**

- `roles/deployment_drift_check/tasks/evaluate.yml` — finding の型へ `playbook` を追加する(L5 の型コメントも更新)。持たないエントリでは空。
- `roles/deployment_drift_check/tasks/report.yml` — Slack本文の各 finding へ次の1行を追加する。`playbook` が空なら行ごと出さない。

  ```
  直し方: ansible-playbook <playbook> -l <host>
  ```
- JSONレポートは finding をそのまま載せているため追加の変更を要さない(要さないことを確認すること)。

**R4. commit時に「配備が要る」と予告する**

新規 `scripts/check-deploy-needed.py` を作り、`scripts/git-pre-commit-check.sh` へ check4 として追加する。

- staged された差分のパス一覧を取り、カタログの `src` と一致したら、**そのエントリの `playbook` と `hosts`** を添えて「配備が要る」と出す。
- **commitをブロックしない**(終了コード0)。配備はcommitの後の工程であり、ここで止めると成立しない順序を要求することになる。

**R5. カタログの `playbook:` の実在をassertする**

同じ `check-deploy-needed.py` の中で、カタログの全 `playbook:` についてファイルの実在を確認する。1つでも欠けたら**非ゼロで終了しcommitをブロックする**。

- R4(警告のみ)とR5(ブロック)は判定の性質が異なる。**スクリプト内で明示的に分けて書く**(出力の見出しも分ける)。
- ブロックする理由: repo内で完結した矛盾であり、playbookを改名した本人がその場で1行直せる。放置すると、次にドリフトが出た日に「書いてあるのに動かないコマンド」を人へ渡すことになる。

### P1(すべき)

**R6. `template` 配備物(Tier 2)を粗く予告する**

staged差分に `roles/<role>/templates/` が含まれ、かつその `<role>` をimportする `playbooks/*_setup.yml` が存在するとき、「配備が要る可能性(内容検査の対象外)」と出す。

- **カタログ由来の予告(R4)とは区別して出す。** こちらは正確な対応ではなく推定である。
- 対象がTier 2 — 日次ドリフト検査も拾えない穴 — であるため、commit時の予告が唯一の気づく機会になる。

**R7. fixtureテスト**

`scripts/tests/` へ、R4 / R5 / R6 の判定を確認するテストを置く。既存のテストの流儀に合わせる。

### P2(できれば)

**R8(2026-08-04、実装中の発見により撤回)。** 当初「フィールドは今回追加しない」と決めたが、これは **`-l` の対象が常に finding のホストと一致する**という誤った前提の上に立っていた。実装が `--list-hosts` で反証した。R9 が置き換える。

### P0(2026-08-04 追補 — 実装が発見した事実に基づく)

**R9. `-l` の対象をカタログが持てるようにする**

`playbook:` を持つべきエントリのうち、**配備を実行すべきホストが finding のホストと異なるもの**がある。`roles/recovery_push` / `roles/recovery_exec` の一部は `hosts: quory` の play から `delegate_to` で authy / monnie へ配備しており、`ansible-playbook <playbook> -l authy` は play の hosts パターンと交わらず**何も配備しない**(実装が `--list-hosts` で実測済み)。

- カタログのエントリへ、`-l` に渡すホストを表す任意フィールドを追加する。省略時は従来どおり finding のホストを使う。
- **finding・Slack通知・R4 の commit 時予告のすべてが同じ値を使う**こと。片方だけが正しい案内を出す状態にしない。
- これにより案内が出せるようになる5エントリ(`recovery-push.sh` / `recovery-trigger@.service` / `recovery-loki-helper` と、authy・monnie / pve1・pve2 の `forced_command_keys`)へ **`playbook:` を持たせること。** 現状これらは commit 時にも通知時にも案内が1つも出ない。

**R10. R2 と同型の2件を閉じる**

`recovery_io_service_enabled` / `incident_capture_service_enabled` も、quory の host_vars に真実が無い。R2 と同じ理由・同じ流儀で `true` を置き、対応する2つの unit エントリ(`recovery-io.service` / `homelab-incident-capture.timer`、いずれも quory)へ `playbook:` を持たせる。

**期待状態が `true` であることの根拠**: 2026-08-04 00:40 の日次ドリフト検査で quory の unit 5件すべてが期待どおりに揃っており、`drift_count` は 1(該当は file カテゴリの1件のみ)だった。すなわち両 unit は現に `enabled` / `active` である。**host_vars へ書く値は観測された現実と一致する。**

ansy の `recovery-io.service`(期待 `disabled` / `inactive`)はこの追補の対象外とする。`state` が管理されておらず playbook を流しても `active` へのドリフトは直らないため、R1-a により `playbook:` を持たせない。

### Won't

- 配備の自動実行(Semaphore schedule化)。別途判断する。
- `check-doc-consistency.py` への統合。カタログをパースするコードが `check-deploy-needed.py` にしか無いため、パースを二重に持たない判断で同居させる。

## 6. 受入条件

**AC1(R1/R3): 通知に直し方が出る**

- **Given** カタログの `files` エントリに対応する配備物が repo と食い違う状態
- **When** `playbooks/deployment_drift_check.yml` を実行する
- **Then** Slack本文の当該 finding に `直し方: ansible-playbook playbooks/<name>_setup.yml -l <host>` の行が含まれ、**そのplaybookが実在する**。playbook実行の終了コードは従来どおり **0**(ドリフト検出は赤にしない既存仕様、AC7 を壊さないこと)

**AC2(R1-a): 直さないものには書かない**

- **Given** ansy の `recovery-probe.service` が期待(`disabled`/`inactive`)と食い違う状態
- **When** 同上
- **Then** その finding に「直し方」行が**含まれない**。JSONレポートの当該 finding の `playbook` も空である

**AC3(R3): 正常時は従来どおり無通知**

- **Given** ドリフトが1件も無い状態
- **When** 同上
- **Then** 通知は飛ばず、終了コードは **0**、`reports/drift/latest.json` の `drift_count` は 0

**AC4(R4): commit時に予告が出る**

- **Given** `roles/incident_investigate/files/incident-investigate.py` を変更して stage した状態
- **When** `git commit` する
- **Then** 「配備が要る: `playbooks/incident_investigate_setup.yml`(quory)」が標準出力に出て、**commitは成功する**(終了コード0)

**AC5(R4): 無関係な変更では出ない**

- **Given** `docs/` 配下だけを変更して stage した状態
- **When** 同上
- **Then** 配備に関する出力が1行も出ず、commitは成功する

**AC6(R5): 実在しないplaybookはブロックする**

- **Given** カタログの `playbook:` の1つを実在しない名前へ書き換えて stage した状態
- **When** 同上
- **Then** どの行が壊れているかを名指しするメッセージが出て、**commitが失敗する**(非ゼロ終了)

**AC7(R2): 期待状態がrepoに書かれている**

- **Given** `inventories/homelab/host_vars/quory.yml`
- **When** 読む
- **Then** `incident_investigate_service_enabled: true` があり、既存2件と同じ流儀のコメントが添えられている

**AC8(R6): Tier 2 の予告が区別して出る**

- **Given** `roles/incident_investigate/templates/` 配下を変更して stage した状態
- **When** `git commit` する
- **Then** カタログ由来の予告とは**別の見出し**で「配備が要る可能性」が出て、commitは成功する

## 7. オープンクエスチョン

- **OQ1**: `deployment_drift_check_forced_command_keys` のエントリ数ドリフトを、該当roleの配備が実際に直すか。**Implementerが現物で確認し、直さないなら `playbook:` を持たせない**(R1-a)。確認結果を implement 成果物へ書くこと。
- **OQ2**: ansy の `ansible-knowledge-review.timer` を配備するplaybookの特定。`playbooks/systemd_timers.yml` が候補だが未確認。

## 8. タイムライン考慮

- 本番への影響は、次にドリフトが検出された日の通知本文にしか出ない。**効き目の確認は `status.md` の Watch へ置く。**
- 検証は decoy(`/tmp` のカタログと fixture)で完結する。**実ホストへの到達は一切不要**であり、Tester は起動しない。

## 検証方針

- **A側**: `/tmp` に decoy カタログ(存在しない `dest` を1件含む)を作り、`skip_notifications` で Slack へ出さずに通知本文を `debug` で表示して文面を確認する。**本番ホストへは触れない。**
- **B側**: `scripts/tests/` の fixture で AC4 / AC5 / AC6 / AC8 を確認する。
- `ansible-lint` と `--syntax-check` を通す。

## 工程

Implementer 1体 → Reviewer 1体(独立)。**Testerは起動しない** — 実ホストへの到達が不要で、ACがすべて decoy と fixture で観測できるため(`docs/ai/roles/coordinator.md`「ACの実機検証はTesterへ渡す」が対象とする実機検証が発生しない)。この判断はCoordinatorが下した。
