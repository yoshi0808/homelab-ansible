### 3.1 delegate_to による `-l <host>` の不一致(5エントリ)

対象: `recovery-push.sh` / `recovery-trigger@.service`(authy, monnie)、`recovery-loki-helper`(monnie)、forced_command_keys の authy/monnie 分・pve1/pve2 分。

これらは全て `hosts: quory` の play(`recovery_push_setup.yml`)または `hosts: dev_nodes:control_nodes` の play(`recovery_exec_setup.yml`、ただし対象ノードは含まれない)から `delegate_to: "{{ target_item.name }}"` で配布されている。R3 の「直し方」テンプレートは `-l <host>` の `<host>` に finding 自身のホスト(= 実際にドリフトが起きたホスト、例: authy)を使うしかないが、`ansible-playbook playbooks/recovery_push_setup.yml -l authy` を実測すると **hosts(0)** で何もしない:

```
$ ansible-playbook playbooks/recovery_push_setup.yml -l authy --list-hosts
  play #1 (quory): ...
    pattern: ['quory']
    hosts (0):
```

正しい直し方は `-l quory` だが、finding のホストからは quory という値を導けない(finding が持つのは drift の起きた側のホスト)。「直し方」を書けば誤り、書かなければ情報が無い、のどちらかしか選べず、R1-a「実際にその状態を復元しないエントリには書かない」を文字どおり適用して**書かない**側を選んだ。

副作用として、`scripts/check-deploy-needed.py` の R4(commit時予告)もこの5エントリの `src` が変更された場合に何も警告しない(playbook: フィールドが空のため)。R4の出力は `-l` を含まないため本来は警告できたはずだが、`playbook:` フィールドを「R3のSlack行とR4の予告の両方が同じ意味で読む単一のフラグ」として設計したため、同じ判断がR4側にも及んでいる。**この5件は commit時にも配備後の通知にも何のヒントも出ない状態**であり、Coordinatorへの申し送り事項とする(§6)。

### 3.2 quory の unit で `-e` が渡し忘れられている(2エントリ、R2に隣接して発見)

対象: `recovery-io.service`(quory)、`homelab-incident-capture.timer`(quory)。

R2 が塞いだのは `incident_investigate_service_enabled` だけだったが、同型の問題が他に2つ残っていた:

- `recovery_io_service_enabled`(既定 `false`)は `inventories/homelab/host_vars/quory.yml` に無く、`playbooks/recovery_io_setup.yml` のコメントは quory 本番有効化に `-e recovery_io_service_enabled=true` を明記している。
- `incident_capture_service_enabled`(既定 `false`)も同様に quory の host_vars に無い。

`roles/recovery_io/tasks/main.yml` L169-176 の「Enable recovery-io service」taskは `enabled: "{{ recovery_io_service_enabled }}"` を**無条件**に適用する(quory限定のwhenは無い)。ここが `recovery_probe`/`incident_capture`/`incident_investigate` と違う点で、**`enabled` はfalseへ明示的に戻す(=無効化を「直してしまう」ことがある)が、`state` は `enabled|bool` が false のとき `omit` になり active/inactive を管理しない**。つまり `-l quory` だけを流しても、enabled 不一致は直る場合と直らない場合が両方ありえ、active 不一致は直らない。挙動が一貫しないため、こちらもR1-aの対象として `playbook:` を持たせなかった。

`homelab-incident-capture.timer` の enable/start task(`roles/incident_capture/tasks/main.yml`)は `incident_investigate` と同じ形で `when: incident_capture_service_enabled | bool` によって丸ごとスキップされる(タスク自体が実行されない)。`-e` 無しでは enabled/active どちらの不一致も直らない。

**注記**: `deployment_drift_check_files` の該当ファイル配備タスク(`incident-capture-collector.py` 本体のcopy)自体は上記の変数に依存しないため、file側のカタログエントリ(`playbook: playbooks/incident_capture_setup.yml`)は問題なく機能する。影響を受けるのは unit(timer/service の enable/active)側のみ。

**この2件をR2と同じ形でhost_varsへ真実を出すかどうかは、今回のrequirementが明示的にスコープへ含めていない(R2はincident_investigate_service_enabledのみを名指ししている)。独断でscopeを広げず、host_varsへの追加は行わなかった。** §6で申し送る。
