# 要求仕様: prometheus_update_check に実適用(upgrade)を追加 — --check ゲート方式

作成日: 2026-07-19
起票: claude(要件定義)
種別: 変更系(既存 role/playbook 拡張)。**destructive な upgrade ブロックを追加**

## 目的

既存 `prometheus_update_check`(チェック+通知のみ、commit `3593e4c`)を拡張し、
**同一 playbook を `--check` の有無でモード分岐**する。`proxmox_patch_apply_node` と同じ
「read-only は常時実行 / destructive は `not ansible_check_mode` でゲート」パターン。

- **`--check`(金曜 18:05 スケジュール)** = バージョン確認 + Slack 通知のみ。**upgrade しない(dry-run)**。
- **`--check` 無し(週末に手動実行)** = 確認 + **実際に新バイナリを適用** + 通知。
- **backup を取得し、適用失敗時は自動 rollback** できること。

Prometheus は手動バイナリ管理で更新頻度が高く、毎回の手作業(wget→展開→cp→restart)を
playbook 化して安全化・再現性確保するのが狙い。

## 背景 / 根拠

- ベース: `roles/prometheus_update_check` + `playbooks/prometheus_update_check.yml`
  (現在は check-only。監査 001..005、[[project_monnie_monitoring_stack]])。
- 現況(2026-07-19 実測): monnie 実機 = **3.12.0**、GitHub latest = **3.13.1**。
  金曜スケジュール(Semaphore 登録済)で `3.12.0 → 3.13.1 update_available` 通知が着弾済。
- 手動インストール手順(Yoshinobu 提供): バイナリ `/opt/prometheus/{prometheus,promtool}`、
  config `/opt/prometheus/prometheus.yml`(**更新時は維持・上書きしない**)、systemd
  `prometheus.service`、`--web.enable-lifecycle`、storage `/var/lib/prometheus`、retention 60d。
- 適用対象アーキ: linux-amd64(monnie)。

## 確定した設計判断(Yoshinobu 2026-07-19)

1. **`--check` でも通知する**(現コミットの `when: not ansible_check_mode` 抑止を変更)。
   - `--check` + 更新あり → 「current → target 更新あり(未適用)」通知。
   - `--check` 無し + 適用実施 → 「適用完了 current → target」/「適用失敗・rollback 済」通知。
   - `up_to_date` → 両モード無通知。`collection_failed` → 両モード alerts。
2. **適用バージョン = 検知した最新を自動適用 + 任意でピン**。
   - 既定: 適用対象 = GitHub latest(検知した版)。
   - `-e prometheus_target_version=X.Y.Z` 指定時: その版を適用(明示ピン。緊急時の
     既知良好版への切替=ダウングレードも許容)。形式 `^\d+\.\d+\.\d+$` を検証。

## 判明した前提(調査で確定)

- **notify.yml は `community.general.slack` を使い `ansible_check_mode` を尊重** →
  `--check` で実際に POST するには notify include に **`check_mode: false`** が必要。
  これは [[feedback_check_mode_slack_notify]] の「--check で Slack を抑止」原則への
  **意図的な例外**(このツールでは通知が成果物のため)。**明示的にそう設計する**。
  テスト/誤爆回避の逃げ道として `-e skip_notifications=true` は従来どおり有効に保つ
  (notify.yml が尊重)。
- **monnie の recovery probe は `icmp` + `tcp:3000`(Grafana)を監視、prometheus:9090 は
  見ていない**(`roles/recovery_probe/defaults/main.yml`)→ prometheus 再起動で復旧プローブ
  誤発火なし = **mute 不要**。ただし `monitoring_healthcheck`(9090 を見る別スケジュール)が
  restart 秒窓に重なる低確率はある(実害は瞬間的、許容)。

## 対象

- 拡張 role: `prometheus_update_check`(defaults + tasks)
- 拡張 playbook: `playbooks/prometheus_update_check.yml`
- 対象ホスト: monnie。実行元 quory。GitHub egress(API + release binary DL)必要。
- スケジュール: 金曜のものは **`--check` 付き**へ変更(Semaphore UI 側作業。playbook 外)。

## 実施内容

### Phase 1-3(既存・collect + judge): 変更最小

- current(`prometheus --version`)/ latest(GitHub `/releases/latest`)収集・semver 判定は
  現状維持(`check_mode: false` で --check でも実走)。

### Phase 3.5: 適用対象バージョンの決定

- `_target_version` = `prometheus_target_version`(指定時、`^\d+\.\d+\.\d+$` 検証)
  else latest(検知版)。
- `_upgrade_wanted` = collected かつ:
  - ピン無し: `latest is version(current, '>')`(上位のみ)
  - ピン有り: `_target_version != current`(ダウングレード含む・明示的意図)

### Phase M: モード選択(排他)

- `prometheus_update_check_rollback`(= CLI `-e rollback=true` を map)が true → **手動
  rollback モード**(Phase R)。この時、通常の upgrade(Phase U)は実行しない。
- false(既定)→ 通常フロー(Phase 3.5 target 決定 + Phase U upgrade)。
- Phase 1-3(collect current/latest)はどちらのモードでも実走してよい(current 把握のため)。
  ただし rollback モードでは latest 取得失敗を致命にしない(GitHub 不通でも rollback 可能に)。

### Phase R: 手動 rollback(destructive・`when: prometheus_update_check_rollback and not ansible_check_mode`, tags:[destructive])

事後に人間が障害を検知した場合の、backup からの復帰(自動 rollback とは別経路)。

1. **backup 探索**: `prometheus_update_check_backup_dir` 配下の世代を列挙。
   - `prometheus_update_check_rollback_to`(= CLI `-e rollback_to=X.Y.Z`、`^\d+\.\d+\.\d+$`)
     指定時: 該当版の backup を選択。無ければ fail-closed。
   - 未指定時: **直近(mtime 最新)の backup** を選択。
   - backup が1つも無ければ **fail-closed**(status=`rollback_failed`, 明確なメッセージ)。
2. **現バイナリを退避**: 戻す前に、現行(疑わしい)`prometheus`/`promtool` も backup dir へ退避
   → rollback 自体を可逆にする(誤検知時に前進復帰可能)。
3. **restore**: 選択した backup の `prometheus`/`promtool` を `/opt/prometheus/` へ復元。
4. **restart** → **health 検証**(active + `--version`==restore 版 + `/-/healthy` 200)。
5. **失敗時**: 停止し status=`rollback_failed`・alerts 通知(config/storage は不変なので手当て可能)。
6. 成功 → status=`rolled_back`。
- `--check` + rollback = **どの backup(版)へ戻すかを表示のみ**で実行しない(dry-run)。

### Phase U: upgrade(destructive・`when: (not prometheus_update_check_rollback) and not ansible_check_mode and _upgrade_wanted`, tags:[destructive])

順序と各ステップの安全条件:

1. **backup**: 現 `/opt/prometheus/prometheus` と `promtool` を
   `{{ prometheus_update_check_backup_dir }}/{{ current }}-{{ ts }}/` へ退避(mode 保持)。
   保持世代 `prometheus_update_check_backup_keep`(既定 3)を超える古い backup を prune。
2. **download + checksum 検証**: GitHub releases から
   `prometheus-{{ target }}.linux-amd64.tar.gz` と `sha256sums.txt` を取得し **SHA-256 照合**
   (`get_url` の checksum、または DL 後に検証)。timeout 付き・失敗は upgrade_failed。
3. **展開**(temp)→ 新 `prometheus`/`promtool` を取り出す。
4. **promtool による config 事前検証**: **新** promtool で既存 `prometheus.yml` を
   `promtool check config` → **失敗ならバイナリ差し替え前に中断**(現構成のまま無傷)。
5. **swap**: 新 `prometheus`/`promtool` を `/opt/prometheus/` へ配置(owner/mode 維持)。
   config・storage・unit は触らない。
6. **restart**: `systemctl restart prometheus`。
7. **health 検証**: service active かつ `--version` == target かつ HTTP `/-/healthy`
   (localhost:9090)が 200、を確認。
8. **失敗時 rollback**: 6/7 のいずれか失敗で backup バイナリを復元 → restart →
   復旧(active + 旧 version)を確認。status = `upgrade_failed`。
9. **cleanup**: temp 削除。

### Phase 4: 通知(両モード・include に check_mode:false)

- notify include を `check_mode: false` で常時実行(--check でも POST)。
  `when` から `not ansible_check_mode` を除去し、status に応じて出す/出さないを制御。
- status → 本文/channel:
  - `update_available`(--check 時): info。「current → target 更新あり(未適用・--check)」+ release URL。
  - `upgraded`(apply 成功): info。「適用完了 current → target」+ health OK。
  - `upgrade_failed`(apply 失敗): alerts/error。失敗ステップ + 「backup へ rollback 済(現 version)」。
  - `rolled_back`(手動 rollback 成功): info。「rolled_back: from → to」。
  - `rollback_available`(`--check` + rollback の dry-run で対象 backup あり): info。
    「rollback 対象(未実行・--check): 現 version → 戻し先 version(backup パス)」。
    ※ 2026-07-19 追記(implementer2 実装前 Q への回答): rollback の `--check` も通常 `--check`
    と対称に対象を通知する(up_to_date 流用は不可=「何もすることが無い」と衝突)。
  - `rollback_failed`(手動 rollback 失敗/backup 無し): alerts/error。理由(backup 不在等)。
    `--check` でも backup 不在なら rollback_failed で通知(「戻せない」ことは dry-run でも知らせる)。
  - `up_to_date`: 無通知。
  - `collection_failed`: alerts/error(既存の diagnostic 抜粋維持)。
- `-e skip_notifications=true` で全通知抑止(テスト用)。

## defaults 追加(案)

- `prometheus_update_check_target_version: ""`(空=latest 自動、`-e` で上書き)
- `prometheus_update_check_arch: linux-amd64`
- `prometheus_update_check_download_base: https://github.com/prometheus/prometheus/releases/download`
- `prometheus_update_check_backup_dir: /opt/prometheus/backups`
- `prometheus_update_check_backup_keep: 3`
- `prometheus_update_check_service: prometheus`
- `prometheus_update_check_install_dir: /opt/prometheus`
- `prometheus_update_check_health_url: http://localhost:9090/-/healthy`
- `prometheus_update_check_rollback: "{{ rollback | default(false) | bool }}"`
  (**CLI はシンプルに `-e rollback=true`**。内部は namespaced 変数で参照=衝突回避)
- `prometheus_update_check_rollback_to: "{{ rollback_to | default('') }}"`
  (**CLI は `-e rollback_to=3.12.0`**。空=直近 backup)

### 共通引数規約(将来の unpoller / dashboard 等でも再利用)

手動適用/ロールバック系 playbook で共通に使う CLI 引数規約として確立する:
- CLI 表面: **`rollback`(bool)** / **`rollback_to`(版・任意)**。シンプルに保つ。
- role 内部: 必ず **`<role>_rollback` / `<role>_rollback_to` へ map** して参照(グローバル
  `rollback` を role ロジックに直接撒かない=複数 role 読み込み時の衝突回避)。
- 意味論(全 playbook 共通): `rollback=true` → 直近 backup へ復帰。`rollback_to=X` → 特定
  backup を選択、無ければ fail-closed。`--check` 併用 → 対象表示のみ(dry-run)。
  戻す前に現物も退避=rollback 自体も可逆。backup 不在は fail-closed。
- 構文注意: `-e` はコンマ区切り不可。`-e rollback=true -e rollback_to=3.12.0`
  または `-e "rollback=true rollback_to=3.12.0"`。

## 制約

- **config(prometheus.yml)・storage・unit・retention は変更しない**。バイナリ2本のみ。
- **destructive ブロックは `not ansible_check_mode` + `tags:[destructive]` でゲート**。
  read-only collect と通知は常時実行(check_mode:false)。tester-gate 分類は
  `check-mode-native`(patch_apply と同型)。
- **秘密鍵・IP をリポに書かない**。GitHub は公開・認証なし。時刻 JST。
- shell でバージョン判定しない(collect/DL は module、判定は set_fact)。core.md §7。
- mute は不要(monnie probe が prometheus を見ないため。上記前提参照)。

## 初回実装スコープ

- Phase 3.5(target 決定・ピン)、Phase U(backup/DL+checksum/promtool 検証/swap/restart/
  health/rollback/cleanup)、Phase 4 の両モード通知(check_mode:false)+ status 拡張。
- defaults 追加。金曜スケジュールへの `--check` 付与は UI 作業(スコープ外・手順を final に明記)。

## 初回除外スコープ

- prometheus.yml / unit / retention の変更、他コンポーネント(grafana/loki/promtool 単独)の適用。
- 複数アーキ対応(amd64 のみ)。Semaphore 側の設定変更。

## shell / Ansible 責務分離

- module: `prometheus --version`(get)、`uri`(GitHub API get)、`get_url`(DL+checksum)、
  `unarchive`/`copy`(swap)、`systemd`(restart)、`uri`(health get)。
- Ansible tasks: target 決定・semver 判定・backup/prune・rollback 制御・status 確定・通知本文。
- shell 判定は行わない。

## テスト観点(tester 向け)

- **--check(dry-run)**: collect 実走・**upgrade ブロック skip**・通知は「update_available
  (未適用)」が出る(誤爆回避で tester は `-e skip_notifications=true` を使う)。バイナリ
  mtime/inode 不変・service 無風。
- **apply 成功パス**(実機 or ステージ): backup 生成・checksum 照合・promtool 検証通過・
  swap・restart・`/-/healthy` 200・`--version`==target・status=upgraded。
  ※ 実機適用は Yoshinobu の明示 GO 下で(3.13.1 を初回ケースにできる)。
- **rollback パス**(擬似失敗注入): health 失敗時に backup 復元→restart→旧 version 復帰・
  status=upgrade_failed・alerts 通知。
- **checksum 不一致**: DL 改竄/破損を模擬 → swap 前に中断・現構成無傷。
- **promtool config 失敗**: 新 promtool で不正 config → swap 前中断。
- **ピン**: `-e prometheus_target_version=3.13.1` で対象固定、範囲外/不正形式は中断。
- **up_to_date**: current==target で無通知・無変更。
- **手動 rollback**(`-e rollback=true`): 直近 backup を選び、現バイナリ退避 →
  restore → restart → health → `rolled_back: from → to` 通知。`--check` 併用で対象表示のみ。
- **rollback 版指定**(`-e rollback=true -e rollback_to=3.12.0`): 該当 backup を選択。
  存在しない版は fail-closed(rollback_failed)。
- **backup 不在時 rollback**: fail-closed・alerts・現バイナリ無変更。

## モード早見(3モード)

| 起動 | 挙動 |
|---|---|
| 無印 + `--check`(金曜スケジュール) | 確認 + 通知のみ(未適用) |
| 無印 + `--check` 無し(週末手動) | 適用 + 失敗時 自動 rollback + 通知 |
| `-e rollback=true`(手動) | backup へ復帰(任意で `-e rollback_to=版`)+ 通知 |
