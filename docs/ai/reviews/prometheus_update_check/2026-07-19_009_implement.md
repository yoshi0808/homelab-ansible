## 1. 復旧成功判定の厳格化

`upgrade.yml`の自動rollbackと`manual_rollback.yml`の失敗後復旧から、restore `copy`と`systemd restart`の`failed_when: false`を除去した。復旧処理を継続する箇所は`ignore_errors: true`を使い、moduleが返す`failed`を保持する。

復旧状態を`succeeded`にする条件を次の全項目一致へ変更した。

- `prometheus`と`promtool`のrestore taskが実際に成功
- `systemd restart`が実際に成功
- `systemctl is-active`をretry付きで確認し、rc=0かつ`active`
- 復旧後の実`prometheus --version`を再収集し、復元対象版と一致
- `/-/healthy`をretry付きで再確認し、HTTP 200
- 復旧後の`prometheus`と`promtool`がregular non-symlink file
- 退避時と復旧後の両バイナリSHA-256が一致

いずれかが不成立なら復旧状態は`failed`とし、statusはそれぞれ`upgrade_failed` / `rollback_failed`のままにする。手動rollback失敗時の`result_version`は推測値ではなく、復旧後に実収集できたversionだけを記録する。

## 2. トランザクション排他と世代衝突防止

upgradeとmanual rollbackの破壊的transaction全体を、`/run/lock/prometheus_update_check.lock` directoryの原子的`mkdir`で排他した。既存lockがある場合は待機・上書きせずfail-closedとする。取得したlockはtransactionの`always`で空directory専用の`rmdir`により解放する。

異常終了で`always`が実行されなかった場合はlockが残り、次回も安全側へ停止する。再実行前に人間が稼働transaction不在を確認してlockを除去する運用となる。

upgrade backupとmanual rollback pre-imageの世代作成は次の順に変更した。

1. 対象pathが存在しないことを`stat follow:false`で確認
2. `mkdir`で排他的に作成（既存なら失敗）
3. canonical pathが期待値と一致し、backup rootの直接の子で、directoryかつnon-symlinkであることを再確認
4. 検証後に2バイナリをcopy

manual restoreでは、discovery後・lock取得後・restore直前に選択世代directoryのcanonical境界と、世代内`prometheus`/`promtool`がregular non-symlink fileであることを再検証する。

## 3. current version不明時のmanual rollbackをfail-closed化

rollback modeでも、現行`prometheus --version`のrcが0で、versionが`X.Y.Z`としてparseできる場合だけbackup discoveryと破壊的rollbackへ進むようにした。

current収集失敗時は次を設定してrestoreを実行しない。

- status: `rollback_failed`
- failure step: `current_version_collection`
- error: unreadable current binaryからのrecoveryは本roleのscope外

GitHub latest収集失敗はmanual rollbackの可否に使用していないため、currentが有効なら従来どおりrollback可能。

## 4. release page URLの分離

asset download用`prometheus_update_check_download_base`とは別に、`prometheus_update_check_release_page_base`を追加した。

`update_available`通知は次のrelease詳細ページを表示する。

`https://github.com/prometheus/prometheus/releases/tag/v<version>`

## 5. manual rollback backup retention

manual rollback成功後にも`backup_keep` retentionを適用した。次の2世代は常に保護し、それ以外をmtime降順で保持枠へ入れて古い世代をpruneする。

- rollbackで選択した復元元世代
- rollback直前に作成した現行pre-image世代

`backup_keep`が2未満でも復旧可能性を優先してこの2世代は削除しないため、その場合の実保持数は設定値を上回り得る。retention失敗は成功したrollbackを巻き戻さないようbest-effortとした。
