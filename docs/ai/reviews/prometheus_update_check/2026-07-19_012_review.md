## 確認結果

### 1. backup generation cleanup の所有権限定

- `roles/prometheus_update_check/tasks/upgrade.yml:5-17,130-141,433-442`
- `roles/prometheus_update_check/tasks/manual_rollback.yml:5-15,158-169,362-371`

upgrade/manual rollback の双方で `generation_created` は false で初期化され、排他的 `mkdir` の正常終了後にだけ true になります。未完成世代の削除条件は次の全ANDです。

- 自トランザクションが lock を取得済み
- 自トランザクションが generation を作成済み
- backup complete 前

したがって、lock競合、既存path衝突、generation作成前の失敗では計算済みpathへ触れません。assert と `mkdir` の間に別pathが作られて `mkdir` が失敗する競合でもフラグは false のままであり、他トランザクションの使用中／既存世代を削除する経路は塞がれています。

### 2. lock解放失敗の通知と失敗化

- `roles/prometheus_update_check/tasks/upgrade.yml:567-599`
- `roles/prometheus_update_check/tasks/manual_rollback.yml:510-535`
- `roles/prometheus_update_check/tasks/main.yml:192-208`
- `roles/prometheus_update_check/tasks/notify.yml:5-12,51-57`

`rmdir` は rc/stderr を登録し、`failed_when: false` で共通通知まで処理を継続します。rc非0時は、上書き前の operation status/error を別factへ保存し、実処理で観測済みの `result_version` を保持したまま status を `lock_release_failed` へ遷移させます。

`lock_release_failed` は次のすべてに整合して追加されています。

- 通知対象 status
- Slack `alerts` / `error` 分類
- 元 operation status、観測 version、元 error、lock path、`rmdir` 診断を含む専用本文
- 通知後の最終 fail 条件

このため、upgrade/rollback 自体の成否を `lock_release_failed` と混同せず伝えつつ、lock解放不能を成功終了にはしません。同一 `set_fact` 内の参照が変更前 status を保持することも localhost fixture で確認しました。

### 3. stale lock の解除手順

`docs/ai/reviews/prometheus_update_check/2026-07-19_011_implement.md` に、Semaphore job、実行元 process、対象ホストの swap/restore/restart、directory の非symlink性と空状態を確認してから、空directory専用の `rmdir -- /run/lock/prometheus_update_check.lock` だけを実行する手順があります。`rm -rf` の禁止と、判断不能／`rmdir` 失敗時は解除せず調査する条件も明記されています。

異常終了時に stale lock を残して次回を fail-closed にする方針と整合しています。

### 4. 未使用 defaults の削除

旧 `prometheus_update_check_release_url` と `prometheus_update_check_manual_reference` は削除済みで、レビュー対象外を含むリポジトリ内に実コード参照は残っていません。release page と asset download はそれぞれ `release_page_base` / `download_base` に分離されたままです。
