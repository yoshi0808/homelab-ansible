## 確認結果

### 1. managed hostを変更しない

- managed host上で実行するcommandは、変数化されたPrometheus binaryへの単一argument `--version` だけである。
- GitHub取得は `ansible.builtin.uri` のGETであり、responseを収集するだけである。
- その他は `set_fact` と `debug`、条件付きSlack includeだけである。
- `get_url`、download、unarchive、copy、template、file、package管理、binary差し替え、config変更、systemd/service、restart/reloadのtaskはない。
- Prometheus本体、storage、retention、service unit、Semaphore scheduleを操作する処理はない。
- Slack送信だけはcontroller側の外部副作用だが、要求どおりupdate available / collection failureの通知目的に限定される。

### 2. collectと判定が分離され、上位版だけを検出する

- installed version収集は `ansible.builtin.command` の `argv` で、shell expressionや比較を含まない。
- latest release収集は `ansible.builtin.uri` のGETで、公開 `/releases/latest` endpointを使用する。
- current/latestのparse、collection status、version比較、最終statusはすべて `set_fact` で行う。
- update判定は `latest is version(current, '>')` であり、単純な `!=` は使っていない。
- current/latestが同版ならfalse、latestが下位でもfalse、latestが上位の場合だけtrueになることをローカルJinja評価で確認した。

### 3. check-mode-nativeと通知条件

- read-only commandとuriには `check_mode: false` があり、`--check` でも収集を実走する。
- Slack includeには `not ansible_check_mode` があり、check modeでは通知task自体をincludeしない。
- 通知条件は `update_available` / `collection_failed` の2状態だけで、`up_to_date` は静音である。
- playbook headerの `tester-gate: check-mode-native` と実装が一致する。
- localhostの実行元確認とmonnie向けrole実行の2 play構成であり、対象はinventory上monnie 1hostに展開される。

### 4. collection failureを握ってstatusへ落とす

- binary commandとGitHub uriはともに `failed_when: false` で、moduleが結果を返す通常の実行失敗をplay failureにしない。
- binary不在、実行失敗、nonzero rcはregistered resultのrcでcollection failureになる。
- GitHubのDNS/connection timeout等はuri resultのfailed/status absentまたは `-1` 相当となり、`status | default(-1) | int` が200でないためcollection failureになる。
- rate limitやserver errorもnon-200 statusでcollection failureになる。
- responseにJSONがない場合、`json | default({})` と `tag_name | default('')` でlatestは空になる。JSONがnullの場合もローカルJinja評価でfatalにならず空へ落ちることを確認した。
- HTTP 200でもJSON/tagが欠落・不正ならversion format検査がfalseとなりcollection failureになる。
- current/latest parse taskは失敗時にも必ず空文字factを作るため、後続statusやSlack templateに未定義参照はない。
- managed host自体のSSH unreachableやtask引数のtemplate errorはmodule resultを返せないため、このrole内の `failed_when: false` では握れないが、これは今回対象のbinary/API収集失敗とは別のAnsible実行基盤障害である。

### 5. version抽出と比較

- current regexはmultiline anchor `(?m)^` を使い、`prometheus, version X.Y.Z` 行から3つの数値componentだけを抽出する。
- 行末またはversion直後のspaceを要求するため、周辺の別の数値を誤って拾いにくい。
- 複数行fixtureから `3.4.0` を抽出できることをローカルJinja評価で確認した。
- latestはGitHub `tag_name` の先頭小文字 `v` だけを除去する。
- collection成立条件はcurrent/latestとも `^[0-9]+[.][0-9]+[.][0-9]+$` の完全一致である。
- 比較入力が数値3 componentに限定されるため、上位・同版・下位の判定は要求どおりになる。
- malformed tagやpre-release suffixは誤通知せずcollection failureになる。`/releases/latest` を使うため、通常はstable tagだけが対象になる。

### 6. Slack内容

- update available時は `info` channel / `info` status、collection failure時は `alerts` / `error` である。
- 本文には `current → latest` のversion行、status、release URLがある。
- 「自動更新は行いません」「適用は人間が判断」「手動更新手順を参照」が明記される。
- collection failure時はinstalled側をrcまたはparse failure、GitHub側をHTTP statusまたはtag parse failureとして分けて表示する。
- up-to-date時はSlack include条件を満たさない。

### 7. 非回帰

- 実装は新規playbook、新規role、新規review文書だけで、既存role/playbookやPrometheus本体管理fileに差分はない。
- 別件のuntracked review文書はユーザー作業として触れていない。
- `prometheus_update_check.yml` はsyntax-checkを通過した。
- tester-gateは新規playbookを含む全37 playbookでPASSした。
- `git diff --check` はPASSした。

## Suggestion

### collection failure通知へmodule messageの短い抜粋を加える

該当箇所:

- `roles/prometheus_update_check/tasks/main.yml:95`
- `roles/prometheus_update_check/tasks/main.yml:96`

現在もbinary側/API側のどちらが失敗したかは判別でき、要件は満たす。ただしDNS failure、connection timeoutなどのuri失敗はSlack上では主に `HTTP status=-1` またはunknownと見えるため、原因文字列は分かりにくい。

collection failure時に、次を短くtruncateして追加すると運用時の切り分けが速い。

- binary: `stderr` または `msg`
- GitHub uri: `msg`

公開version/APIのdiagnosticだけを対象とし、将来認証headerを追加する場合にもresponse全体やinvocationを通知しない形が安全である。この改善はstatus分類や承認を妨げない。
