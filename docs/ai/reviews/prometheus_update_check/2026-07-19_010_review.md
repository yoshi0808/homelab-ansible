## Must-fix

### 1. ロックを取得／世代を作成していないトランザクションが backup generation を削除できる

- `roles/prometheus_update_check/tasks/upgrade.yml:5-14,18-40,117-183,428-435`
- `roles/prometheus_update_check/tasks/manual_rollback.yml:5-14,16-38,145-211,357-364`

両 transaction の rescue は、世代 path が定義済みで `*_backup_ready == false` なら `file: state=absent` を実行します。`lock_acquired` や「自分が generation の `mkdir` に成功した」という条件がありません。

このため、例えば同一秒に同じ現行版で A/B が起動した場合、次の競合が成立します。

1. A が lock を取得し、`<version>-<timestamp>` を作成する。
2. B は同じ path を計算するが lock の `mkdir` に失敗する。
3. B の lock assert が rescue に入り、A が作成・使用中の同名 generation を再帰削除する。

また、lock を取得した実行でも、同名の正常な generation が既に存在して freshness assert が失敗すると、その実行自身は generation を作っていないのに既存 generation を削除します。これは collision を fail-closed にする設計と逆で、排他導入前より危険です。

upgrade/manual rollback の初期化時に `*_generation_created: false` を持たせ、排他的 `mkdir` の成功後だけ true にしてください。未完成世代の cleanup は少なくとも次の全条件で限定する必要があります。

- transaction lock を自分が取得済み
- generation を自分が新規作成済み
- backup complete 前

既存 path の検出や lock 競合では、対象世代に一切触れず fail-closed にしてください。

## Suggestions

### 1. lock 解放失敗も status/通知経路へ載せる

- `roles/prometheus_update_check/tasks/upgrade.yml:568-575`
- `roles/prometheus_update_check/tasks/manual_rollback.yml:503-511`

通常の異常終了で空 lock directory が残り、次回が fail-closed になる方針は安全側として妥当です。人間が稼働 transaction 不在を確認してから `rmdir` する運用も合理的です。

一方、`always` 内の通常解放 `rmdir` は未捕捉の fatal failure です。directory が非空、既に消失、filesystem error 等で失敗すると、後続の共通 Slack 通知まで到達せず、実際の適用結果と lock 残留状態を報告できません。`rmdir` の rc を保持して処理を継続し、失敗時は実バイナリの結果を偽らない診断を status/error と alerts 通知へ載せたうえで play を失敗化することを推奨します。

### 2. stale lock の解除手順を運用文書へ残す

lock directory は意図的に空で owner PID/job metadata を持たないため、残留 lock が active か stale かは path だけでは判断できません。Semaphore job、Ansible process、対象ホスト上の swap/restart が動作していないことを確認し、空 directory に対してだけ `rmdir` する手順を運用文書へ明記すると安全です。

## 008 指摘事項の確認結果

### 1. 復旧成功判定の厳格化: 解消

- 自動 rollback と manual rollback 失敗後復旧の restore copy / restart は `ignore_errors: true` で実失敗を保持している。
- `succeeded` は restore 2本、restart、retry付き active、実収集 version、retry付き HTTP 200、regular non-symlink、退避時と復旧後の2本の SHA-256 一致の全ANDになっている。
- 条件不成立時も status はそれぞれ `upgrade_failed` / `rollback_failed` である。
- manual recovery の `result_version` は復旧後に実際に parse した値だけを使用している。automatic rollback の pre-swap failure は、実行開始時に正常収集済みの current version を使用している。

### 2. 排他・世代衝突・restore直前検証: 一部未解消

- `/run/lock/prometheus_update_check.lock` の原子的 `mkdir` は全 destructive transaction を覆い、既存 lock では待機せず fail-closed になる。
- lock は自分が取得した場合だけ、`always` で空 directory 専用の `rmdir` により解放する。
- generation は不在確認、排他的 `mkdir`、canonical/direct-child/non-symlink 再確認、copy の順になっている。
- manual restore は discovery 後、lock 取得後に、選択世代と世代内2バイナリを再検証している。
- ただし上記 Must-fix のとおり、rescue cleanup の generation 所有権が不足している。

### 3. current version 不明時の manual rollback: 解消

current command の rc=0 かつ `X.Y.Z` parse 成功時だけ discovery/restore に進み、それ以外は `rollback_failed` となる。latest release の成否は rollback 可否に使用していない。

### 4. release URL: 解消

asset download base と release page base が分離され、通知は `releases/tag/v<version>` を使用している。

### 5. manual rollback retention: 解消

rollback 成功後に、選択した復元元と直前 pre-image の2世代を常に保護し、残りの保持枠だけを unprotected generations に割り当てている。find/prune failure は best-effort で、成功した restore を巻き戻さない。

### 6. 前回確認済み事項の回帰: なし

モード排他、`not ansible_check_mode` と `destructive` tag、swap前の checksum/promtool検証、swap後の active/version/health retry、check mode の通知例外に回帰は見つかりませんでした。
