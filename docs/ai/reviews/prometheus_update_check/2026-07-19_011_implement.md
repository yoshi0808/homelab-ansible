## 1. backup generation cleanupの所有権限定

upgrade transactionに`prometheus_update_check_upgrade_generation_created`、manual rollback transactionに`prometheus_update_check_manual_generation_created`を追加した。いずれも初期値は`false`で、世代directoryの排他的`mkdir`が成功した直後だけ`true`にする。

rescueで未完成世代を削除する条件を次の全ANDへ変更した。

- 当該transactionがlockを取得済み
- 当該transactionがgenerationを新規作成済み
- backup 2本のcopyが完了する前

これにより、lock競合したtransaction、既存pathのfreshness assertで停止したtransaction、generation作成前に失敗したtransactionは、計算済みpathに同名世代が存在しても一切削除しない。自分がlock配下で新規作成した未完成世代だけがcleanup対象になる。

## 2. lock解放失敗の通知と失敗化

upgrade/manual rollbackの`always`にある`rmdir`は、`failed_when: false`でrc/stderrを保持して後続処理を継続するようにした。解放失敗時は、適用結果を上書きして成功・失敗を偽らないよう次を別factへ退避する。

- lock解放前のoperation status
- 実際に観測したresult version
- lock解放前のoperation error

その後statusを`lock_release_failed`、failure stepを`lock_release`に設定する。共通Slackはalerts/errorとして元のoperation結果、観測version、lock path、`rmdir`診断を通知する。通知後の最終fail条件にも`lock_release_failed`を追加したため、lock解放不能を成功終了にはしない。

## 3. stale lockの安全な解除手順

`/run/lock/prometheus_update_check.lock`はPID/job metadataを持たない空directory lockである。pathの存在だけではactive transactionかstale lockかを判別できないため、解除は次の順で行う。

1. Semaphoreで対象playbookのrunning jobと再実行jobが無いことを確認する。
2. Ansible実行元で`prometheus_update_check`を実行中の`ansible-playbook` processが無いことを確認する。
3. 対象ホストでbinary swap、backup/restore、Prometheus restartが進行していないことを確認する。serviceが安定しており、`prometheus`/`promtool`とbackup世代が観測中に変化していないことも確認する。
4. lock directoryがdirectoryかつsymlinkでなく、完全に空であることを確認する。空でない場合や判断できない場合は解除せず調査する。
5. 上記をすべて満たした場合だけ、対象ホストで次を実行する。

   ```bash
   sudo rmdir -- /run/lock/prometheus_update_check.lock
   ```

`rm -rf`は使用しない。`rmdir`が失敗した場合は内容を削除して再試行せず、active transactionまたはfilesystem異常として調査する。
