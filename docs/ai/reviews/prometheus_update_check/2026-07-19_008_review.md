# prometheus_update_check 3モード拡張レビュー

## 結論

**要修正**です。

3モードの分岐、check mode の破壊的処理抑止、更新前の checksum/config 検証、更新後の active/version/HTTP 200 検証、失敗通知後の play 失敗化は概ね要件どおりです。一方、復旧成功の誤判定とバックアップ世代の競合により、障害時に「復旧成功」と通知しながら不整合なバイナリが残る経路があります。

## Must-fix

### 1. `failed_when: false` により復旧失敗が成功扱いになる

- `roles/prometheus_update_check/tasks/upgrade.yml:356-427`
- `roles/prometheus_update_check/tasks/manual_rollback.yml:241-289`

自動ロールバックと手動ロールバック失敗後の復旧で、`copy` / `systemd` に `failed_when: false` を指定した結果を、後続処理が `registered_result.failed` で判定しています。Ansible は `failed_when: false` のタスク結果を `failed: false` として登録するため、copy や restart 自体が失敗しても、この条件では検出できません。

自動ロールバック側は Prometheus の active/version も確認していますが、promtool の復元失敗は検出できません。restart が失敗しても旧プロセスが active のままなら、これも成功扱いになり得ます。手動ロールバック側は active/version/health の再収集すらなく、3つのモジュール結果だけで `succeeded` を設定し、`result_version` も復旧確認なしで元バージョンにしています。

`ignore_errors: true` など、失敗情報を保持したまま rescue を継続できる方法へ変更してください。そのうえで、少なくとも次を満たした場合だけ復旧成功にしてください。

- Prometheus と promtool の復元タスクが成功
- service restart が成功し、retry 付きで active を確認
- 実バイナリから再収集した version が復元対象と一致
- promtool も復元前バックアップと checksum 等で一致

手動ロールバック失敗後の復旧にも同等の事後検証が必要です。

### 2. 秒単位の世代名と非排他的な directory 作成ではバックアップが衝突する

- `roles/prometheus_update_check/tasks/upgrade.yml:11-13,92-116`
- `roles/prometheus_update_check/tasks/manual_rollback.yml:10-15,107-125`

世代名が `<version>-<YYYYMMDDTHHMMSS>` であり、`file: state=directory` は既存ディレクトリを正常として受け入れます。同一秒の再実行や並行実行では同じ世代へ上書き／混在し、復旧元が壊れます。また、並行する2トランザクションは別名になっても binary swap と restart を相互に割り込ませられます。

破壊的トランザクション全体にホスト単位の排他ロックを設け、取得できない場合は fail closed にしてください。世代ディレクトリも「存在しないこと」を確認したうえで排他的に作成し、直接の子・canonical path・非 symlink をコピー前に再確認してください。手動復元では discovery 後に時間差があるため、選択済み世代内の `prometheus` / `promtool` が regular non-symlink file であることも、実際の restore 直前に再検証してください。

### 3. 現行バージョン収集失敗時の手動ロールバックが可逆にならない

- `roles/prometheus_update_check/tasks/main.yml:39-113,119-121`
- `roles/prometheus_update_check/tasks/manual_rollback.yml:10-15`
- `roles/prometheus_update_check/tasks/discover_backups.yml` の世代名フィルタ

rollback mode では現行バージョン収集失敗を discovery の status が上書きし、破壊的ロールバックまで進めます。その際の pre-rollback backup は `unknown-<timestamp>` になりますが、discovery は数値バージョンで始まる世代だけを候補にします。したがってロールバック自体が成功すると、直前状態へ戻すために作ったバックアップを、この role の manual rollback では選択できません。

要件上、rollback mode で非致命扱いにするのは latest release 取得失敗であり、現行バージョン収集失敗ではありません。通常は現行 version/rc が有効でなければ破壊的 rollback を fail closed にしてください。壊れた現行バイナリからの救済も要件に含めるなら、`unknown` ディレクトリではなく、検証可能な metadata を持ち discovery で再選択できる pre-image として明示的に設計する必要があります。

### 4. update_available 通知の release URL がリリースページを指さない

- `roles/prometheus_update_check/tasks/notify.yml:23-25`

現在の URL は download asset 用 prefix の `.../releases/download/v<version>` で、asset filename がなく、GitHub のリリース詳細ページでもありません。要件の release URL としては `https://github.com/<owner>/<repo>/releases/tag/v<version>` を生成してください。download base とは別の変数に分けると用途を混同しにくくなります。

## 確認できた点

- `--check` は inspect/notify のみで、upgrade/manual rollback の include に `not ansible_check_mode` がある。
- normal と `rollback=true` は相互排他的で、破壊的 include に `destructive` tag がある。
- checksum は対象 archive 名の行を完全一致で抽出し、展開前に照合している。
- 新しい promtool による config check が binary swap より前にある。
- swap 開始後の失敗だけ自動ロールバック対象とし、失敗通知後に play を失敗化している。
- upgrade/manual rollback の成功判定は active/version/HTTP 200 を retry 付きで確認している。
- Slack の status/channel 分岐と既存 collection diagnostics は維持されている。
