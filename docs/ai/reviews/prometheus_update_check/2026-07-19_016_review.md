# prometheus_update_check dry_run主ゲート移行レビュー

## 結論

**要修正**です。

`dry_run` 未指定時の二重 fail-closed、native check modeとの二段ゲート、rollback status再分類、既存安全機構の不変性は概ね要件どおりです。ただし、destructive gate が検証済みのraw `dry_run`ではなく、extra-varで独立に上書き可能な`prometheus_update_check_dry_run`を参照しているため、`dry_run=true`を指定しても適用経路へ入れる安全ゲート迂回があります。

## Must-fix

### 1. namespaced alias のextra-var上書きで `dry_run=true` を迂回できる

- `roles/prometheus_update_check/defaults/main.yml:17`
- `roles/prometheus_update_check/tasks/main.yml:6-20,138-144,159-176,188-203`

role defaultは次のmappingです。

```yaml
prometheus_update_check_dry_run: "{{ dry_run }}"
```

しかしAnsibleではextra-varsがrole defaultsより高優先です。preflightとrole先頭が検証するのはraw `dry_run`だけで、両者の一致は検証していません。一方、upgrade/manual rollbackのdestructive gateとrollback dry-run再分類はnamespaced側を参照します。

したがって、例えば次の競合extra-varsではassertをすべて通過します。

```text
-e dry_run=true -e prometheus_update_check_dry_run=false
```

このとき通常modeでは`not prometheus_update_check_dry_run`がtrueになり、`not ansible_check_mode`かつ`upgrade_wanted`ならupgrade includeが実行されます。rollback modeでも同じ理由でrestore includeが実行され得ます。主ゲートとして表示・検証した値と実際の破壊的境界が分離しており、fail-closed要件を満たしません。

雛形の`ubuntu_vm_full_upgrade`と同様に、検証後のraw `dry_run | bool`をdestructive gate、rollback再分類、表示の唯一のsource of truthとして直接使用し、不要なnamespaced defaultを削除してください。namespaced aliasを残す必要がある場合でも、少なくともrawとの一致をassertしたうえで、破壊的境界そのものはraw `dry_run`で判定してください。

localhost fixtureで対象defaultsを読み込み、上記2つのextra-varsを与えると、rawはtrue、namespaced側はfalse、かつ現在のapply条件`not namespaced and not ansible_check_mode`がtrueになることを確認しました。

## 確認できた点

### 1. 未指定／不正値のfail-closed

- playbook preflightとrole先頭の双方に`dry_run is defined` assertがある。
- playbook preflightはmonnie向けplayより前にあり、未指定なら対象hostのcollectへ進まない。
- roleを直接呼ぶ場合も、最初のtaskで未指定を停止する。
- 値は大文字小文字を正規化した`true`/`false`だけを許可し、それ以外を拒否する。

このため、既存の金曜Semaphore taskが`dry_run`未指定のままでも自動upgradeせずjob failureとなり、従来のハザードは解消しています。ただし上記Must-fixの競合aliasは別経路です。

### 2. 二段destructive gate

namespaced aliasがraw `dry_run`と同値である通常入力では、条件は要件どおりです。

- upgrade: `not rollback && not dry_run && not ansible_check_mode && upgrade_wanted`
- manual rollback: `rollback && not dry_run && not ansible_check_mode && selected backupあり`

したがって、`dry_run=true`またはnative `--check`のどちらでもdestructive includeはskipされ、`--check -e dry_run=false`は適用条件の判定経路を維持したままswap/restore/restartをskipします。

### 3. rollback dry-run再分類

選択backupがある場合だけ、explicit dry-runで`rollback_available`へ再分類します。backup不在ではselected pathが空のため`rollback_failed`を上書きせず、current収集失敗時は後続のreject taskが`rollback_failed`を確定します。native `--check`時の既存`rollback_available`も維持されています。

### 4. 変更禁止4ファイルと既存安全機構

ベースcommit `0d8f2e4`との`git diff --exit-code`は差分なしで、実物のSHA-256は実装記録と一致しました。

### 5. status／通知／playbook header

- status名とchannel/error分類、通知対象、通知後fail条件は不変。
- 通知blockの`check_mode: false`とcommon Slackの`skip_notifications`経路は維持。
