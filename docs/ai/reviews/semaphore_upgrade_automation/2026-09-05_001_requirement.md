# requirement: Semaphore 版上げの自動化(手動手順書 → playbook + 切り離しスクリプト)

作成: 2026-09-05 / Coordinator
決定: Yoshinobu(2026-09-05)「自動化を作って ansy で検証し、同じ自動化で quory にも適用する」

## 1. 問題定義

Semaphore の版上げは現在 **`docs/ai/reviews/semaphore_upgrade/2026-08-18_002_manual_procedure.md` の手打ち手順**でしか行えない。2026-08-18 に一度通しており手順そのものは成立しているが、8段・20コマンド超をYoshinobuが quory 上で順に打つ形であり、`docs/ai/core.md`「人の手に残すのは判断だけになるよう設計する」に反している。

**自動化を阻んでいたのは1点だけである** — 版上げは Semaphore 自身の再起動を含み、**その版上げを Semaphore のジョブとして走らせると、再起動が自分自身を殺す。**

この制約は実測で確定している(`docs/ai/context/system/semaphore.md`)。

- `semaphore.service` は `KillMode` を明示しておらず、systemd の既定 `control-group` が効く。**再起動は cgroup ごと殺すため、そのジョブとして走っている `ansible-playbook` も死ぬ**
- **`setsid` / `nohup` では逃げられない**(2026-08-18 実測)。cgroup の所属は fork で継承される
- **逃げる唯一の方法は `systemd-run` で PID1 に別 unit を作らせること**

2026-08-18 に playbook 化を見送った理由は「未知が残る状態で `systemd-run` の2段構えを重ねると、失敗したときにマイグレーション由来か機構由来かを切り分けられない」だった。**この前提は今回失効している** — 2.19.8 → 2.19.12 には**マイグレーションが1本も無い**(§6 実測)。マイグレーション由来の失敗が原理的に起きないため、切り分けの懸念そのものが消えている。

## 2. ゴール

1. **Semaphore の版上げを、Yoshinobu がボタンを1回押すだけで完了する形にする。** 手打ちのコマンドを残さない
2. **再起動をまたいで検証し、失敗したら自動でロールバックする。** ジョブが死ぬことを前提に、判定と復旧を切り離した実行主体へ持たせる
3. **結果が必ず観測できる。** ジョブの成否は「切り離しに成功したか」までしか語れないため、版上げ自体の合否は別経路(Slack)で届く
4. **同じ実装を ansy と quory の両方で使う。** ansy で先に実行して検証し、同じものを quory へ当てる
5. **今回の対象は 2.19.8(非community)→ 2.19.12(community)である。** 版上げとエディション切替を同時に行う(`semaphore_upgrade/2026-08-18_002_manual_procedure.md` §3 の持ち越し)

## 3. 非ゴール(やらないと決めたこと)

| やらないこと | 理由 |
|---|---|
| **schedule への登録(定期自動適用)** | Yoshinobu決定(2026-08-10)「自動適用はしない。当てるときは手動」。**自動化するのは手順であって判断ではない。** テンプレートとして登録するが schedule には載せない |
| **新版検知の側の変更** | `roles/semaphore_update_check/` は 2026-09-05 に初の陽性を返しており(ジョブ #974)、機構として成立している。本案件は検知の下流だけを扱う |
| **`homelab-semaphore-query` の変更** | 2026-08-19 に REST API へ移行済み。本案件では**検証対象**として使うだけで、手を入れない |
| **`inventories/` の変更(`host_vars/ansy.yml` への `ansible_connection` 追加を含む)** | quory の Semaphore も同じ inventory を読むため、2026-08-24 に quory が自分自身を見て drift を誤報した事故がある(`9e9daf5`)。ansy でのリハーサルは **CLI の `-e ansible_connection=local`** で通す(§5 P0-9) |
| **手動手順書の廃止** | ロールバック経路と、自動化そのものが壊れたときの退避路として残す。位置づけを「fallback」へ降格する記述だけを足す |
| **`config.json` の変更・移行** | dpkg 管理外で版上げでは変化しない(実測済み)。触らない |
| **Semaphore の Pro 機能の代替検討** | `executor_image` 空 / `runner` 0件であり、使っていない(2026-08-19 quory 実測。適用直前に再測する) |

## 4. ユーザーストーリー

- Yoshinobu として、月次の新版検知が陽性を返したら、**窓を選んでテンプレートを1回実行するだけ**で版上げを終えたい。手順書を開いてコマンドを写経したくない
- Yoshinobu として、版上げが失敗したときに**自分が気づく前に元へ戻っていて**ほしい。そのうえで何が起きたかを Slack で知りたい
- Coordinator として、版上げの合否を**ジョブの終了コードではなく明示の通知**で知りたい。ジョブは切り離しの成功しか語れないため

## 6. 実測した前提(2026-09-05、Coordinator が確認)

**版差の実体** — 手段: GitHub API(`compare` / `contents` / `releases`)。

| 事実 | 値 |
|---|---|
| 2.19.9 / 2.19.10 | **存在しない**(Releases に無し。2.19.8 の次は 2.19.11、その次が 2.19.12) |
| `v2.19.8...v2.19.12` | 9 commits / 6ファイル(CI 2、`db/sql/SqlDb.go` はテスト用ヘルパ追加のみ、`db_lib/TerraformApp.go` はログ1行、`services/runners/job_pool.go` と `util/config.go` は runner/executor 登録まわり) |
| **マイグレーション** | `db/sql/migrations/` は**両タグとも129ファイルで同一 = 新規0本** |
| 機能変更の影響 | すべて runner / executor 系。**この環境は `runner` 0件**(2026-08-19 quory 実測、適用直前に再測) |

**community `.deb`(2.19.12)** — 手段: `.deb` を取得して `dpkg-deb -I` / `-x`。

| 項目 | 値 |
|---|---|
| Package名 | `semaphore`(非community と同一。**置換になり衝突しない**) |
| `.deb` sha256 | `3858f6bc6eaef3a6223e55fc03eebf69fec89bcf802afb48449321de2964d170` |
| バイナリ sha256 / サイズ | `9a54577383992d79458cc6d4714a26b9aa6e14b3eb0bc51ea221e17ada97e6f0` / 49,643,682 B |
| `guest` role | community ソース(`db/ProjectUser.go` @ v2.19.12)に存在。**読み取り経路はエディション切替で壊れない** |

**unit の現物** — 手段: ansy は `systemctl cat`、quory は `ssh quory-investigate "unit-cat semaphore.service"`。

- **ansy と quory の `semaphore.service` は同一内容である。** `User=yoshi` / `Group=yoshi`、`Restart=always`、`RestartSec=10s`、`ConditionPathExists` 2件、`KillMode` の明示は**無い**(systemd 既定 `control-group`)
- これにより、**kill の意味論に関する ansy での検証は quory に対して忠実である**

**マイグレーション0本のときの起動ログ** — 手段: ansy の `journalctl -u semaphore`(restart は不要だった。ansy は 2.19.8 のまま 8/19 と 9/3 に再起動しており、その2回が**そのまま「新規マイグレーション0本での起動」の実例**である)。

```text
Started semaphore.service - Semaphore UI.
semaphore[...]: SQLite @/var/lib/semaphore/semaphore.db semaphore
semaphore[...]: Tmp Path (projects home) /opt/semaphore
semaphore[...]: Semaphore 2.19.8-3449a04-1786894505
semaphore[...]: Interface
semaphore[...]: Port :3000
semaphore[...]: Server is running
```

**マイグレーションに関する行は1行も出ない。`Migrations Finished` も出ない**(8/18 の版上げ時は `Executing migration v2.18.6` 〜 `v2.19.14` の7本と `Migrations Finished` が出ていた)。

**したがって現行の手動手順書 §5 の合否条件は、今回の版上げでは誤って発火する** — 「`Migrations Finished` が出ないまま落ちたら 8. のロールバックへ」は、**成功した 2.19.8 → 2.19.12 でもそのまま成立してしまう。** 使える成功マーカーは **`Server is running` と直前の版の行**である(P0-7 / AC7)。

**読み取り経路の版上げ前の基準値** — 手段: `ssh quory-investigate`。

- `semaphore-query recent-failed 3` → 3行(ジョブ 938 / 802 / 675)
- `semaphore-query template-list 1` → JSON 1件
- `semaphore-query running 5` → 0行(走行中ジョブ無し)

**この経路は SQLite 直読みではなく REST API である**(`roles/recovery_exec/files/homelab-semaphore-query`、2026-08-19 に移行済み)。2026-08-18 に AC5 を落とした WAL / ACL の問題は**構造的に消えている**が、消費側で測るという教訓だけが残る(P0-8)。

| **AC15** | Given `dry_run` を渡さない / When playbook を流す / Then **明確なメッセージで停止する**(rc 非ゼロ)。既定値で dry-run として続行しない |

| **AC17** | Given ロールバックを実施した直後のホスト / When 同じ目標版へもう一度版上げを流す / Then **人手の介入なしに成功する。** 「apt が already installed と判定して no-op → 検証が版・sha256 の不一致を検出 → 自動ロールバック」のループに入らない。**ロールバックが復旧手段として成立するには、そのあと同じ修正をもう一度当てられることまでが要る** |
| **AC13** | Given 本案件で新設した playbook / When `playbooks/README.md` を見る / Then 記載がある |

**部分成功の扱い**: `serial: 1` で1台ずつ処理し、**あるホストが失敗しても他ホストは続行しない**(`any_errors_fatal`)。版上げは1台ずつ人が窓を選んで行うものであり、まとめて流す運用を作らない。

## 8. リスク

| # | リスク | 影響 | 対処 |
|---|---|---|---|
| R1 | **`systemd-run` による切り離しが、Semaphore ジョブとして走らせたときに実際に効くかを ansy で確かめられない** | 本番で初めて確かめることになる | **ansy の Semaphore はジョブを実行できない**(鍵を持たず clone もできない、EXEC-052)ため、テンプレート経由の経路は原理的に踏めない。**代替として ansy で「`semaphore.service` の cgroup へ入れた子プロセスが restart で死に、`systemd-run` で作った unit は生き残る」ことを直接測る。** これは機構そのものの検査であり、ジョブ実行の有無に依存しない |
| R2 | **`Restart=always` が失敗を隠す** | 落ちても10秒後に起きるため、1点観測では健全に見える | P0-6。一定時間の安定を見る |
| R3 | **`ConditionPathExists` により、壊れたバイナリでの `start` が「成功」に見える** | ロールバックが失敗しても成功と報告されうる | P0-5。rc ではなく `is-active` と HTTP で見る |
| R4 | **切り離しスクリプトの通知が失われると、結果が誰にも届かない** | 版上げの成否が不明のまま放置される | P1-2(`trap`)と P1-3(結果ファイル)。加えて月次の `semaphore_update_check` が独立の後追い確認になる(ただし最大1か月遅れる) |
| R5 | **pro → community で、pro 側だけが当てたマイグレーションがあった場合の挙動が未確認** | community バイナリが未知のスキーマを見る | **推論では「余分な行やテーブルが残っても無害」だが測っていない。** ansy が同じ pro 版であり、リハーサルがそのまま答えになる |
| R6 | 版上げの窓が他の定期実行と衝突する | ジョブが巻き添えで死ぬ | 窓の正本は Notion「バッチ処理工程管理表」。preflight で走行中ジョブ無しも確認する(P0-2) |
| R7 | **手動手順書と自動化が二重に正本を持つ** | 片方だけが直る | 手順書を fallback へ降格し、版・sha256 等の値は自動化側(role の defaults)を正本にする |

## 10. タイムライン考慮

- **急がない。** 2.19.12 は機能的にこの環境へ何ももたらさない(§6)。期限は無い
- ただし**上げるまで毎月10日の検知が鳴り続ける**。異常ではないが、鳴り続けると異常との区別が鈍る
- **今回が最も安全な投入窓である** — マイグレーション0本・機能差ゼロという条件は次の版では手に入らない。機構の初回投入をこれ以上安い状況で行うことはできない
