## Code Review: semaphore_upgrade_automation

### Summary

不可逆点の手前(preflight・退避・edition判定・DB統計)をAnsibleが担い、`systemd-run`で
切り離したPythonスクリプトが再起動以降を担う構造は、requirement §1の制約(自分自身の
cgroupを殺す)に沿って正しく組まれている。rollbackの世代選択、`transaction.json`/
`rollback.json`の受け渡し、`MainPID`によるinstall-restart分離、edition判定のfail-closed
設計は正当性上の欠陥を見つけられなかった。一方、**切り離しスクリプトのSlack通知に
`common_slack`のTS-031抑止機構(`ansible_check_mode`/`skip_notifications`/`CLAUDECODE`)
が一切効かない**ため、AC3/AC4/AC8/AC9の実地検証はそのままでは本番`#patches`へ実通知を
送ることになる。また**AC1のdry-run報告`main_pid_unchanged: true`は測定していない
リテラル**であり、requirementが求める観測点を実際には満たさない。この2点をBlockingとする。

なし。

### What Looks Good

- `roles/semaphore_upgrade/tasks/upgrade.yml:268-297`: `NEEDRESTART_MODE=l`でのinstallの前後で`MainPID`を実測・assertしており、requirement §6の実測(`needrestart`がinstall直後にrestartする)への対処が正しく機能する設計になっている。
- edition判定(`upgrade.yml:99-112`)は「わからなければ`unknown`でfail-closed」になっており、`docs/ai/core.md`の判定不能原則に沿う。Pro→community切替時の`runner`/`executor_image`残存チェック(132-152)も要求にない安全側の追加。
- rollbackの世代選択(`tasks/rollback.yml`)は`transaction.json`のみを対象にし(`rollback.json`は別名のため誤って再帰しない)、`combine()`で`backup_dir`等の元transaction値を保持したまま`mode`/`pre_rollback_dir`等だけ上書きする設計により、`restore()`が常に正しい旧版ファイルを指す。ロールバック中の失敗に対する二段目の退避(`pre_rollback_dir`)と復元(`semaphore-upgrade-detached.py:209-226`)も筋が通っている。
- `start_and_verify()`(`files/semaphore-upgrade-detached.py:93-122`)は`is-active`とHTTPの両方を、`Restart=always`の10秒間隔を跨ぐ連続安定窓で見ており、P0-5/P0-6の要求を字義通り満たす。判定基準(`Server is running`+版行、`Migrations Finished`を使わない)もrequirement §6の実測と整合する。
- Slack webhookの扱い(root:root 0600のファイル経由、`finally`での`unlink`)はP0-10のトークン流出教訓を踏まえた設計になっている(通知そのものの抑止機構が無い点はM1で別途指摘)。
- `playbooks/README.md`・`roles/semaphore_templates/defaults/main.yml`への追記は既存の記法・分類軸(`class`とtester-gateは別軸)を踏襲しており、既存カタログとの矛盾は無い。
