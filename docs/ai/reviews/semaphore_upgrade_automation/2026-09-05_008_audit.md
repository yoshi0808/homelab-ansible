## 指摘

### 1. 記録どうしの矛盾(クローズを妨げない)

`2026-09-05_002_implement.md`「独立レビュー差し戻し対応」の見出し「Blocking 5件」は、
`003_review.md` の Major 3件(M1〜M3)に加えて `004_review.md` の **M2**(「consumer
identityがroot判定だけ」に対応)と **S1**(「dry_runが暗黙既定」に対応)を含めている。
しかし `004_review.md` は M2 を明示的に **Minor** と格付けし(「Blockingとはしない」)、
S1 を **Suggestion** とし(「実装の欠陥ではなくrequirement解釈の確認事項」)、Verdictは
「Approve(blocking findingなし)」「承認を妨げない」と述べている。implement.md の
「Blocking 5件」という記述は、004 の実際の verdict と食い違う。

実害は無い(過剰に直した側であり、必要な修正が欠落したわけではない)。しかし
`004_review.md` を読んだ者と `002_implement.md` だけを読んだ者とで、004 の結論について
異なる理解を持つ。記録としては implement.md 側の見出しが不正確である。

### 2. 根拠の実在は確認できるが、記録内に検証の裏付けが無い(クローズを妨げる)

`002_implement.md` の最終節「最終レビュー差し戻し対応(2026-09-05、007)」は、
`007_review.md` の Major M1(ロールバック後の dpkg 台帳不整合が観測できる形で
どこにも記録されていない)への対応として、`semaphore-upgrade-detached.py` の
result へ `dpkg_bookkeeping` フィールドを追加し、`playbooks/README.md` へ運用注記を
足したと述べる。

この2点はコード上に実在することを確認した(`files/semaphore-upgrade-detached.py`
242〜261行付近の `DPKG_BOOKKEEPING_NOTE` / `result["dpkg_bookkeeping"]`、
`playbooks/README.md` 51〜52行の注記)。ここまでは「根拠の実在」として問題ない。

**しかし、この節だけが他のすべての差し戻し対応節(002・005・006の各追記)と違い、
自己検証の記録を一切持たない。** 002初版・003/004対応・005対応・006(D1/D3/D4)対応の
どの節にも `ansible-lint` / syntax-check / `ast.parse` / `/tmp` fixture 実行などの
検証手段と結果が明記されているが、007対応の節にはそれが無い。この diff は
`semaphore-upgrade-detached.py` の `main()` 内、Tester が繰り返し実行し AC8/AC9/AC17 で
使った `result` 構築ロジックの直後に手を入れており、構文・キー名の誤りが混入しても
記録上は検出されない構造になっている(このAuditorが `ast.parse` で構文だけは
確認できたが、それはこの記録の外で行った確認であり、記録それ自体は「検証した」を
主張していない)。

`007_review.md` の Verdict は「M1解消後はBlocking findingが無くなるため、再確認は
差分の該当箇所のみで足りる(full re-reviewは不要)」としているが、その「再確認」自体が
どの成果物にも記録されていない。次に本案件を読む者(quory 適用を判断する Coordinator を
含む)は、record だけからは「007の修正が最低限の構文確認すら経ていない」ことに
気づけない。

**これはクローズを妨げる。** 反映は軽い — 007対応節へ、最低限
`ansible-lint`/syntax-check/`ast.parse` のいずれかの実行結果を1行加えるか、Tester による
再確認を1回挟めばよい。再監査は前提にしない。

### 3. 未解決の明示が一部欠けている(クローズを妨げない)

`007_review.md` の Suggestion S2(`systemd-run` 起動が拒否された極端系での webhook
ファイルの取り残し)と S3(ロールバック時に読み取り経路が再出現した場合の
`query_user` 空文字列による例外)について、`002_implement.md` は採否のいずれも
記録していない。003/004/005 の Suggestion はすべて「採用済み非Blocking」または
「却下・既知の制限」のいずれかに分類されているのに対し、007のS2/S3だけは
implement.md 上で一度も言及されない。Reviewer 自身が non-blocking と明言しているため
クローズは妨げないが、「やらなかったことと理由」が記録されていない点は他の回との
扱いが不揃いである。

### 4. 状態の正本(`docs/ai/status.md`)との突合

該当行(62行目、「着手候補: Semaphore を 2.19.12 へ上げる」)は、まだ
`docs/ai/reviews/semaphore_upgrade/2026-08-18_002_manual_procedure.md` の手動手順だけを
適用手段として記述しており、本案件で新設・レビュー・ansy実地検証まで完了した
`playbooks/semaphore_upgrade.yml` の存在に触れていない。本案件の requirement §11 は
この記録追随を明示的に**step 6(step 5のquory適用より後)**として計画しており、
Coordinatorがまだ着手していないだけであるため、「黙って落ちている」わけではない
(requirementに書かれた予定どおりの未着手)。該当行が残っていること自体は指摘にしない
規律に従い、指摘としては扱わないが、次にこの行を更新する際は「手動手順が唯一の手段」
という現在の記述を、本案件の状態(自動化実装済み・ansyで実地検証済み・quory適用は
Yoshinobu待ち)へ差し替える必要がある。

`docs/ai/context/system/semaphore.md`「インストールと版上げ」節も同様に、
「版上げの playbook は、この抑止を明示しない限り install と restart を分けられない」
という仮定形の記述のままで、実装済みの `roles/semaphore_upgrade` の存在を反映していない。
これも requirement §11 step 6 の範囲であり、現時点では想定どおりの未着手として扱う。

  4回の追記で実測され、D1/D3/D4 の3 defect と修正・再検証のループが記録上追跡できる。

  (cgroup切り離し実験、pro→community DB open)。

  5(quory適用)・6(記録追随)は未着手であり、そのこと自体は requirement に明記された

## 判定

**条件付き受入。**

クローズを妨げる指摘は上記2のみ — `007_review.md` の Major M1 に対する最終修正
(`dpkg_bookkeeping` フィールドとREADME注記)について、実装差分は現物で確認できるが、
その差分に対する検証記録(自己検証・レビュー・テストのいずれか)が案件記録のどこにも
無い。これを反映(検証結果を implement.md の該当節、または新規の軽量な確認記録へ
1件追記)すればクローズしてよい。再監査は前提にしない。

指摘1・3は記録の正確性・一貫性の問題であり、クローズを妨げない。反映するかどうかは
Coordinatorの裁量とする。指摘4は現時点では欠落ではなく、requirementが計画した
step 6(quory適用後)の実施事項として扱う。
