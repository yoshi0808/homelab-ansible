## 変更内容

`acl-status` arm の固定 name→path 表(既存4件: `yoshi-home` / `semaphore-dir` / `semaphore-db` / `reports-root`)へ、2件を追記した。

```
incident-inspect-root)    target_path=/var/lib/incident-inspect ;;
incident-inspect-context) target_path=/var/lib/incident-inspect/semaphore-context ;;
```

既存の `case` パターンに沿った純追記で、他の行は1行も変更・削除していない(`git diff` で `+` のみ27行、`-` は0行)。

あわせてヘッダのコメントブロック(冒頭、既存の「Total is now 29」の段落の直後)へ、`acl-status` の表が4→6へ増えたが check(arm)の総数は29のままである旨を追記した。`acl-status` arm 自身のコメントには、2項目それぞれが何を観測するか(requirement §1・AC2の理由づけ)を書いた。

## 自己検証で実際に観測したこと

- `bash -n roles/dev_investigate/files/recovery-investigate-dispatch-quory.sh` → 構文エラーなし。
- `shellcheck` はこの環境に無かった(`command -v shellcheck` が rc=1)。新規指摘の有無は確認できていない。
- arm(case ラベル)の総数を `awk` で数え上げ → **29**(変更前と同数。ラベル一覧を出力し、`acl-status` を含む既存全arm名が保たれていることを目視確認)。
- `git diff --stat` → `1 file changed, 27 insertions(+)`、削除行は0。**既存arm(25本 + Operator Request Channelの4本)の arity 検査・拒否文言は1文字も触れていない**ことを、変更が純追記であることそのもので確認した(行を書き換える形では実装していない)。
- `SSH_ORIGINAL_COMMAND` を与えてスクリプトをローカルで直接実行し、実ホストへは触れずに以下を確認した。
  - `acl-status etc-passwd`(表に無い名前)→ `denied: invalid path for acl-status` / rc=1。
  - `acl-status /etc/shadow`(パスそのもの)→ 同上、同じ拒否文言・rc=1。
  - `acl-status incident-inspect-root` / `acl-status incident-inspect-context` → いずれも `deny_invalid` を通らず `getfacl` へ到達(ローカルに当該パスが存在しないため `getfacl: ...: No such file or directory` / rc=1 で終わるが、これは「未知パスとして拒否された」のではなく「表に一致し `getfacl` を試みた」ことの証拠 — 拒否メッセージと文言・経路が異なることで区別できる)。
  - `acl-status yoshi-home`(既存項目)→ 変更前と同じ `getfacl -p` 出力(owner/group/ACLエントリ)、rc=0。既存経路が壊れていないことのサニティ確認。
  - `rm-everything`(未知の最上位 check)→ `denied: unknown command 'rm-everything'`、rc=1。変更前と同一文言。
  - `acl-status yoshi-home extra`(4引数)/`acl-status`(引数無し)→ いずれも既存の arity guard(`denied: invalid parameter count for 'acl-status'`)で拒否。

これらは AC3(語彙が増えていない・既存arity検査と拒否文言が不変)と AC4(表に無い名前・パスそのものが `deny_invalid path` で拒否される)を、配備前にローカルで裏付けたもの。
