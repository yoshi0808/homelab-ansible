# Requirement: 一次調査の先読みディレクトリを、開発側から観測できるようにする

作成: 2026-08-25 / Coordinator

## 1. 問題定義

**repo が所有者と mode を設定しているパスについて、本番の現物を開発側から見る手段が無い。** そのため runtime の失敗を前にして、推測するか止まるかの二択になる。

**2026-08-22、一次調査(ジョブ #802)が先読みファイルを書けずに失敗した。**

```
failed to write pre-fetched Semaphore context file for the LLM:
[Errno 13] Permission denied:
'/var/lib/incident-inspect/semaphore-context/semaphore-context-802.txt'
```

LLM は Semaphore のジョブ出力・ホスト結果・エラー本文を一切読めず、所見は「特定不能」で終わった。**先読み機構は 2026-08-19 の導入以来1度も動いていない。**

**2026-08-25、配備(ジョブ #838)の出力から1段絞れた。** ディレクトリを作るタスクが `changed` ではなく **`ok`** を返している。

- **「作られていなかった」ではない。** 意図した所有者(`yoshi`)と mode(`0750`)で既に存在する。
- **ただしこの `ok` は root から見た正しさでしかない。** role は `become: true` で走り、runtime の書き手は `User=yoshi`(`homelab-incident-investigate.service`)である。
- **配備は何も変えていないため、`EACCES` を出した状態がそのまま残っている。**

**ここから先は観測できない。** `acl-status` の対象は `yoshi-home` / `semaphore-dir` / `semaphore-db` / `reports-root` の固定4件で、`/var/lib/incident-inspect/` 配下の arm が無い。

**同じ形が2回目である。** `semaphore-db` の ACL も、`dev-investigate` が traverse を失って以降、開発側から恒久的に観測できない(`docs/ai/status.md` に既載)。

## 2. ゴール

**先読みディレクトリと、そこへ至る親ディレクトリの所有者・mode・ACL を、開発側から read-only で観測できるようにする。**

**原因の特定と修正は本案件の範囲外である**(観測できるようになってから別案件で行う)。

## 3. 非ゴール

- **`EACCES` を直すこと。** 本案件は観測手段だけを足す。**直す前に見えるようにする**(順序を逆にすると、直ったかどうかを測れない)。
- **dispatch スクリプトを template 化して表を生成すること。** **取れない** — 同スクリプトは `copy` 配備物であることが**ドリフト検査 Tier 1 の適格条件**であり(`roles/deployment_drift_check/defaults/main.yml` 冒頭、カタログ77-78行)、template にすると `deployed-hash` による突合が成立しなくなる。**観測手段を足すために別の観測手段を壊す。**
- **将来「観測の穴が開いたこと」を検知する検査を作ること。** **取れない** — repo が `owner:` / `acl` を設定しているパスは Jinja 変数であり機械的に列挙できない。**同じ理由で既に退けられた提案がある**(`docs/ai/memory/decisions/rejected-proposals.md`「ACL付きパスへのchmodをpre-commitで検査すること」)。
- **新しい check(arm)を足すこと。** 本案件が足すのは**既存 arm `acl-status` の固定 enum の項目**であり、check の総数(29)は変わらない。
- 書込・実行の語彙を足すこと。**read のみ**(`docs/ai/core.md`「読み取りは持たせてよい。状態を変えるものは持たせない」)。

## 4. ユーザーストーリー

Coordinator として、本番で `EACCES` を見たとき、**そのパスの所有者と mode を推測せずに読みたい。** いまは読めないため、原因を断定できないまま止まるか、推測して誤るかのどちらかになる。

## 5. 要件

### P0

**P0-1. `acl-status` の固定 name→path 表へ2項目を足す。**

| 名前 | パス | 何が分かるか |
|---|---|---|
| `incident-inspect-root` | `/var/lib/incident-inspect` | **こちらが決定的。** `getfacl` に要るのは親(`/var/lib`)への traverse だけで、そこは誰でも通れる。**確実に読める。** この mode / 所有者が、`yoshi` がその下へ入れるかを決める |
| `incident-inspect-context` | `/var/lib/incident-inspect/semaphore-context` | 上を通れなければ `Permission denied` になる。**それも情報である**(通れないことの直接の証拠) |

**P0-2. operand からパスを組み立てない。** 既存の `case` と同じく、名前から固定パスへ引く形を保つ(スクリプト冒頭 I-3)。

**P0-3. ヘッダの check 総数の記述を正しく保つ。** 足すのは arm ではなく enum の項目なので、**総数は 29 のまま**である。誤って増やさない。ヘッダに「`acl-status` の対象は 4 → 6 へ増えたが check は増えていない」ことが読み取れる形にする。

### P1

**P1-1. 増やした2項目が、何を観測するために在るのかをスクリプトのコメントに残す。** 後から読んだ人が「何を守っているか分かるか」(`docs/ai/memory/lessons/measure-whether-the-risk-has-ever-materialized.md` の判断の順序3)。

### Won't

- `/var/lib/incident-inspect/workspace`(`incident-inspect` の作業領域)を表へ足すこと。**本案件の問いに関係しない。** 必要になったときに別途判断する。

## 6. 受入条件

**AC1 — 親ディレクトリが読める**
> **Given** dispatch を quory へ配備した後、
> **When** ansy から `ssh quory-investigate "acl-status incident-inspect-root"` を実行したとき、
> **Then** `/var/lib/incident-inspect` の `getfacl` 出力(owner / group / mode / ACLエントリ)が返る。終了コード `0`。

**AC2 — 葉の結果がどちらであっても観測になる**
> **Given** 同上、
> **When** `acl-status incident-inspect-context` を実行したとき、
> **Then** `getfacl` の出力が返るか、`Permission denied` で終わるかのいずれかである。**どちらでも AC は充足する** — 前者は葉の権限が読めたこと、後者は `dev-investigate` が親を通れないことの直接の証拠である。**「読めなかった」を失敗として扱わない。**

**AC3 — 語彙が増えていない**
> **Given** 変更後のスクリプト、
> **Then** arm(check)の総数は **29 のまま**である。書込・実行の語彙は1つも増えていない。既存 25 arms の arity 検査と拒否文言は1文字も変わっていない。

**AC4 — 表に無い名前は拒否される**
> **Given** 変更後のスクリプト、
> **When** 表に無い名前(例: `etc-passwd`)や、パスそのもの(例: `/etc/shadow`)を operand として渡したとき、
> **Then** `deny_invalid path` で拒否される。終了コードは既存の拒否経路と同じ。

**AC5 — 配備物と repo が一致する**
> **Given** quory へ配備した後、
> **When** `deployed-hash investigate-dispatch-quory` を実行したとき、
> **Then** repo の `roles/dev_investigate/files/recovery-investigate-dispatch-quory.sh` の `sha256sum` と一致する。**`copy` 配備物であることが保たれている**(template 化していないことの確認を兼ねる)。

## 7. オープンクエスチョン

- **`dev-investigate` が `/var/lib/incident-inspect` を traverse できるかは未知である。** できなければ AC2 は `Permission denied` になる。**それは失敗ではない**(AC2 に明記)。
- **観測した結果が原因を確定させるかは分からない。** 親が `0700` で `incident-inspect` 所有なら説明が付くが、そうでなければ別の軸を探すことになる。**本案件は観測手段を足すところまでで、原因の断定は含まない。**

## 8. タイムライン考慮

- 工程は requirement → Implementer → Reviewer(codex側、独立)→ Tester の直列。
- **配備は quory の Semaphore(Yoshinobu起動)であり、押下が1回要る。** テンプレート名は `roles/semaphore_templates/defaults/main.yml` で確認する。
- **AC1 / AC2 は配備後にしか測れない。** 配備前に確かめられるのは AC3 / AC4(スクリプトの静的な性質)だけである。
