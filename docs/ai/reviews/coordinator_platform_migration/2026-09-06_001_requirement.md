# Coordinator を別CLIへ移せるようにする — requirement

作成: 2026-09-06 / Coordinator

## 1. 背景

Yoshinobu が Coordinator を Claude Code から Codex へ移すことを決めた。あわせて次が示された。

- **このリポジトリは公開されており、特定ベンダーのAIを前提にしないと謳っている。**
- **Coordinator を Claude Code へ戻すことも今後ありうる。どちらでも動く構成が望ましい。**

したがって本案件のゴールは「Codex へ移すこと」ではなく、**どちらのCLIが Coordinator でも成立する形にすること**である。

## 2. 決めたこと

### 2.1 役の割り当て(Yoshinobu承認、2026-09-06)

当初案は Coordinator=Codex / Implementer=Claude Code / Reviewer=Codex だったが、**検める対4つのうち2つが同一CLIになる**ため採らなかった(Reviewerが Coordinator の計画を査読する対、Tester が Implementer を検証する対)。

採ったのは **作る側 / 検める側でCLIを分ける**形である。CLIが2つのとき、検める対4つすべてを別CLIにできる唯一の解。

| 側 | Role | CLI | モデル | 段 |
|---|---|---|---|---|
| 作る側 | Coordinator | Codex | `gpt-6-astra` | medium |
| 作る側 | Implementer | Codex | `gpt-5.6-sol` | low |
| 検める側 | Reviewer / Tester / Auditor | Claude Code | `sonnet` | medium |

Coordinator の段を `low` にしない理由は ADR-011 に記録した。

### 2.2 起動手段

**Codex から Claude Code は起動できない**(`collaboration.spawn_agent` の `model` は codex 系のみ。2026-09-06 実測)。したがって検める側は **agmsg 一択**である。Yoshinobu の指示により、ペインは畳まない運用とする。

## 3. 制約

- **playbook / role のコードに触れない**(Yoshinobu、2026-09-06)。
- **auto-memory 110件の仕分けは保留**(Yoshinobu、2026-09-06)。Coordinator が Claude Code へ戻る機会があれば再開する。
- 既存の牽制の対を1つも壊さない。
- 規範の本体(承認境界、独立性、報告、status維持、Gitの扱い)は変えない。**変えるのは実現方式の層だけ。**

## 4. 観測した事実(変更の根拠)

1. **agmsg 経路と Agent tool 経路では、役に渡る文脈が違う。** agmsg で spawn した Claude Code セッションには `MEMORY.md`(Coordinator の auto-memory 索引)と `session-context.py` の出力が**フルで入り**、`CLAUDE.md` は「この対話セッションはCoordinatorなので `coordinator.md` を読む」と**役を誤らせていた**。実測で、立てた Reviewer は自分の役を `.claude/agents/reviewer.md` の description から理解していた。
2. **repo の `skills/` 14本は codex から見えていなかった。** `.codex/skills/` にsymlinkを置くと見えるようになる(同一モデル・同一段での対照付き)。Claude Code 側は `.claude/skills/` の追跡済みsymlinkで同じことをしていた。
3. **2つの安全機構は種類が違う。** `.claude/settings.json` の `autoMode` は散文で意図を判定する分類器、`~/.codex/rules/default.rules` は argv の前方一致。**ホスト別の非冪等判定は後者では表現できない。**
4. codex 側には `git restore` / `checkout` / `switch` / `stash` / `reset` / `clean` の規則が1つも無かった。
5. **codex の設定は repo の外にあり、Claude Code の設定は repo の中にあった。** 非対称。
6. `~/.codex/rules/default.rules` に退役識別子 `techlead2` の規則が残っていた。

## 5. 受入条件

- **AC1** 規範の原則層(`core.md`、`coordinator.md`、`execution_boundary_policy.md`)から、特定AI製品への依存が消えていること。製品名が残ってよいのは①入口ファイル名②「現在の割り当て」の明示③その製品固有の機構の説明、の3つだけ。
- **AC2** `CLAUDE.md` と `AGENTS.md` が対称で、Coordinator がどちらへ移っても**入口文書を書き換えなくてよい**こと。
- **AC3** 検める対4つ(Reviewer↔Coordinator計画 / Reviewer↔Implementer差分 / Tester↔Implementer / Auditor↔Coordinator記録)が、いずれも別CLIになる割り当てが規範として書かれていること。
- **AC4** 安全境界のうち **前方一致で表現できるもの**が codex 側へ移っており、**表現できないもの**は受け入れた事実と根拠が記録されていること。
- **AC5** codex 側の承認ルールが repo で追跡され、`git log` で変更を追えること。
- **AC6** `scripts/check-doc-consistency.py` の3検査が通ること。
- **AC7** 変更した記述が現物と食い違っていないこと(特に `agent-messaging.md` §5 の「repo に現れない」系の記述)。

## 6. 受け入れた残存リスク

- **`ansible-playbook` は codex 側で無条件 `allow`。** ホスト別の非冪等判定を前方一致で書けないため。根拠は EXEC-002(実効的な境界は能力の不在で作られている)であり、ansy は保護対象ホストへの鍵を1本も持たない。
- **Slack抑止の3層目が効かなくなる。** `roles/common_slack/tasks/notify.yml` の AI セッション検出は `CLAUDECODE` 環境変数だけを見ており、Codex Coordinator では発火しない。**残る2層(`skip_notifications`、`ansible_check_mode`)は上書き不可で効く。** 本案件では playbook / role に触れないため直さない。
- **未一致コマンドの codex 既定(allow/prompt/deny)は未確認。** 追加した6規則はどちらでも正しいため、確認を待たずに適用した。
- **`default.rules` の `tmux capture-pane -p -t %5` を許可する2規則が死んでいる**(ペインIDは再作成のたびに変わり、`%5` は現存しない)。壊れてはいないため触っていない。**行番号で指さない** — 規則の追加でずれる。

## 7. 持ち越し

- auto-memory 110件(feedback 47 / project 39 / reference 21)の仕分け。**Codex は auto-memory を読まないため、移行後この知識は使われない。**
- Reviewer の別体性。ペインを畳まない運用では `send.sh` が同じ文脈へ届くため、`reviewer-plan` / `reviewer-diff` の2識別子に分けるかは未決。
- `rename.sh homelab claude coordinator`。走行中の自分自身は rename できないため、切り替え時点で行う。
