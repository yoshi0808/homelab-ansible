# requirement: Proxmoxパッチの停止が通知に出ない経路を塞ぐ(案件2b)

作成: 2026-09-27 / Coordinator
起点: `docs/ai/reviews/playbook_catalog_policy_audit/2026-09-26_005_summary.md` 仕分けB の `_002` F08。範囲と方針はYoshinobu合意済み(2026-09-27)。

## 1. 問題定義

1. **退避・復帰が失敗しても、Slackに何も出ない。** `roles/proxmox_evacuate_node/tasks/main.yml` と `roles/proxmox_restore_vm_placement/tasks/main.yml` は、失敗すると `rescue` で理由を記録し、`always` でreportを保存して再raiseするだけで、通知のincludeが無い。weekly fullでは、途中のplayで対象hostが失敗すると最後の完了通知(`playbooks/proxmox_patch_weekly_full.yml` の「Send weekly full patch complete notification」)に到達しないため、**止まったこと自体が通知されない**。Policy SB-056「停止時はsummary通知に停止理由を含め」、SB-070「pve2停止通知: 停止理由、pve1へ進んでいないこと、対応要否、失敗taskまたはhealthcheck、report path」に反する
2. **applyの通知(node単位)の中身が足りない。** `roles/proxmox_patch_apply_node/tasks/main.yml` の通知は、更新packageを件数でしか載せず、停止時に「以降のnodeへ進んでいない」ことを書かない。SB-070の成功通知(更新package)・停止通知(pve1へ進んでいないこと)に届いていない
3. **weekly fullの完了通知に、nodeごとの再起動の有無が無い。** SB-070の成功通知「reboot要否」に届いていない

## 2. ゴール

- 退避・復帰・適用のどこで止まっても、止まった段と理由がSlackに出る
- 通知の本文だけで判断できる。**reportのファイルを開かないと分からない書き方をしない**(Slackからreportは開けない。reportを読めるのはCoordinatorのread-only経路かquoryのターミナルだけ)

## 3. 非ゴール

- `BLOCKED` 通知の「timer停止・contingency route・復帰条件」(SB-070)は扱わない。scheduleを止める仕組みを持たない判断(2026-09-27)に合わせ、Policy改訂の流れで扱う
- `MAINTENANCE_REQUIRED` 通知の中身(dry-runのAIが作る文面)は変えない
- 金曜のdry-runの予告と土曜の適用の差(予告に無かったpackage)を通知で区別しない(Yoshinobu、2026-09-27)
- changelogの要約をAIで作らない(機械的に抜き出す)
- reportの置き場所(ディレクトリのパス)を通知に載せない(§5 R4)
- weekly fullの制御の流れ(どこで止まるか、次の段へ進むか)は変えない。変えるのは通知だけ
- 通知先の設計(`common_slack`)は変えない。check modeやAIセッションでの抑止は既存のguardに任せる

## 4. ユーザーストーリー

- Yoshinobuとして、土曜朝のパッチが途中で止まったら、スマホのSlackだけで「どのnodeの、どの段で、何が理由で止まったか」「pve1には進んでいないか」を知りたい
- Yoshinobuとして、詳しく調べてほしいときは、通知に載った目印をCoordinatorに伝えればreportを読んでもらえるようにしたい

## 5. 要件

### P0

| # | 要件 |
|---|---|
| R1 | `proxmox_evacuate_node` が失敗したら、`#alerts` へ `error` で通知する。本文: 対象node、**失敗したtaskの名前**(`ansible_failed_task.name` 等から保存する)と停止理由(`_evac_error_msg`)、**実際に**退避できたVM・強制停止したVMの一覧、**以降の段(このnodeへの適用、次のnode)へは進んでいないこと**、reportの目印(R4)。<br>**実際に成功した分だけを数える**: 現行は全loop完了後に予定対象全件を `_evac_vms_migrated` / `_evac_vms_force_stopped` へ代入するため、途中のitemで失敗すると一覧が空になり、後段の失敗では未確認の予定全件が成功扱いになる。loopの各itemの結果から成功分を確定する形に改める(計画査読 `_002` Major 3) |
| R2 | `proxmox_restore_vm_placement` が失敗したら、`#alerts` へ `error` で通知する。本文: 対象node、**失敗したtaskの名前**と停止理由(`_restore_error_msg`)、**実際に**戻せたVM・起動したVMの一覧、**VMが退避先に残っている可能性があること**、reportの目印(R4)。一覧はR1と同じく各itemの結果から成功分だけを確定する |
| R3 | `proxmox_patch_apply_node` の成功通知に、**実際に適用したpackageごとのパッチ内容**を端的に載せる(SB-070「更新package、必要最小限のchangelog要約」)。形: `<package> <installed> → <candidate>: <changelogの最新項目の1行目>`、changelogにCVE番号があれば列挙する。新規installは `(新規) → <candidate>` と表示する。changelogは適用の直前に機械的に取り出す(dry-runの収集スクリプトにある取り出し処理を再利用してよい)。取り出せなかったpackageは「changelog取得不可」と書き、通知と適用は止めない。件数が多いときは先頭の一定数と「ほかN件」にしてよい(上限は実装の既定値)。<br>停止(abort / 失敗)の通知には「このnodeで停止した。weekly full から実行されている場合、以降のnodeへは進まない」旨と、失敗したtaskの名前を載せる |
| R4 | **reportの目印**: R1〜R3の通知の末尾に、そのreportの**ファイル名だけ**(例: `20260926T061832_pve1_apply.json`)を1行載せる。ディレクトリのパスは載せない。Coordinatorが `report-show` で読むときの目印であり、SB-070の「report path」をこの形で満たす。**reportを保存してから通知する**(applyは現行、通知の後で保存しているので順序を改める)。保存に失敗したときは、ファイル名の代わりに「report保存失敗」と書く |
| R5 | weekly fullの完了通知に、nodeごとの再起動の有無(実施した / しなかった、理由)を載せる。**完了通知の文面以外は変えない** |

## 6. 受入条件

**実ホストには触れない。** 検証はfixtureとlocalhost実行、`scripts/safe-ansible-check.sh`(`--check`)の範囲で行う(ansyからpveへは到達手段が無い、EXEC-010)。通知は実送信せず、`notify.yml` に渡る変数(channel / status / title / message)で確かめる。

| AC | Given / When / Then |
|---|---|
| AC1 | **Given** 退避が失敗する入力(migration失敗、healthcheck失敗のそれぞれ) **Then** `notify.yml` が channel `alerts`・status `error` で呼ばれ、本文に対象node・失敗したtaskの名前・停止理由・「以降の段へは進んでいない」・reportのファイル名(ディレクトリを含まない)がある。**その後も失敗は再raiseされる** |

| AC1c | **Given** 退避の失敗に加えて、通知の本文組み立て、またはnotify.ymlのincludeを意図的に失敗させる **Then** 元の失敗メッセージで非0終了する |
| AC2 | **Given** 復帰が失敗する入力(AC1・AC1b・AC1cと同じ3系統) **Then** AC1と同様に通知され、本文に「VMが退避先に残っている可能性」がある。一覧は成功分だけ。失敗は再raiseされる |
| AC3 | **Given** 退避・復帰が成功する入力 **Then** R1・R2の通知は呼ばれない(既存の成功経路に通知が増えない) |
| AC4 | **Given** applyの成功入力(更新packageが数件、上限を超える件数、新規install、changelogにCVEがあるもの・無いもの・取得できないもの) **Then** 通知本文に、packageごとの `<package> <installed> → <candidate>: <changelogの1行目>` とCVE番号がある。新規installは `(新規)`、取得できないものは「changelog取得不可」。上限を超える場合は「ほかN件」 |
| AC5 | **Given** applyの停止入力(`MAINTENANCE_REQUIRED` のabort、`BLOCKED` のabort、apply失敗のそれぞれ) **Then** 通知本文に「このnodeで停止」と以降のnodeへ進まない旨、reportのファイル名がある |
| AC6 | **Given** weekly fullの完了通知(pve2 / pve1とも再起動あり、片方なし、単一node適用) **Then** 本文にnodeごとの再起動の有無がある。完了通知以外のタスクに差分が無いこと(`git diff` で確認) |
| AC7 | **Given** check mode **Then** R1・R2の通知は送信されない(既存のguardで抑止)。退避・復帰のreport保存など既存の挙動も変わらない |

| AC9 | **Given** 既存の検証(`roles/proxmox_patch_apply_node/tests/`、`roles/proxmox_patch_dryrun/tests/`、`roles/proxmox_healthcheck/tests/`、`scripts/tests/`)と `scripts/check-doc-consistency.py` **Then** 通ること。stageした状態で `scripts/git-pre-commit-check.sh` が通ること |
