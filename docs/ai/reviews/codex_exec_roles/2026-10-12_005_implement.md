# Implement: `codex exec` のRole入口

## 実装結果

- `scripts/codex-role.sh`を新設した。`implementer`、`plan-reviewer`、`auditor`ごとにmodel / effort / sandbox / Role文書を一箇所のreadonly配列で定義し、Role起動指示を依頼文の先頭へ付ける。
  - 新規起動は `-m`、`-c model_reasoning_effort=...`、`-s` を渡す。
  - resumeは `-m`、`-c model_reasoning_effort=...`、`-c sandbox_mode="..."` を毎回渡す。
  - 新規起動出力の `session id:` を抽出し、既定の `~/.local/state/codex-role/<session-id>` にRoleを記録する。resumeはこの記録を照合してからCodexを呼ぶ。
  - `CODEX_ROLE_CODEX_BINARY` と `CODEX_ROLE_STATE_DIR` はテスト用overrideとして使える。ただしbinaryはoverride後もcanonical pathが `~/.agents/` 配下なら呼ぶ前に拒否する。既定binaryはスクリプト内一箇所の `/usr/bin/codex`。
  - Auditorは自由文・resumeを受けず、`--case-dir` とその配下の既存ファイルである `--start-at` だけから依頼文を組み立てる。
- `scripts/check-doc-consistency.py`にcheck4を追加した。git indexから `scripts/codex-role.sh` の実行用配列とcoordinator.mdの `Role / 工程 | 現在のCLI | 起動時指定 | 既定段` 表を読み、3役のmodel / effortを照合する。`現在のCLI`列は読まない。
- `scripts/session-context.py`から`AGMSG_SPAWNED`による早期returnを削除した。
- `scripts/tests/codex_role/run-tests.sh`を追加した。実行時に `/tmp` 下の偽Codexを作り、実CLIを一切起動しない。

## Coordinator向け使用例

```bash
# Implementer新規起動。標準入力または --prompt FILE のどちらかで依頼を渡す。
scripts/codex-role.sh implementer --output docs/ai/reviews/<target>/implementer-final.md <<'EOF'
<Coordinatorの依頼文>
EOF

# 高effortが必要なImplementerだけは明示して引き上げる。
scripts/codex-role.sh implementer --effort high \
  --prompt /tmp/implementer-request.md \
  --output docs/ai/reviews/<target>/implementer-final.md

# plan-reviewer新規起動と継続。新規起動のstdout末尾に出る
# "codex-role session id: <id>" のidをresumeへ渡す。
scripts/codex-role.sh plan-reviewer --prompt /tmp/review-request.md \
  --output docs/ai/reviews/<target>/plan-review.md
scripts/codex-role.sh plan-reviewer --resume <session-id> \
  --prompt /tmp/review-followup.md \
  --output docs/ai/reviews/<target>/plan-review-round2.md

# Auditorは案件フォルダと同フォルダ内の読み始める成果物だけを渡す。
scripts/codex-role.sh auditor \
  --case-dir docs/ai/reviews/<target> \
  --start-at docs/ai/reviews/<target>/001_requirement.md \
  --output docs/ai/reviews/<target>/audit.md
```

## 未完・残存リスク

`.codex/rules/default.rules`のR3変更は未完である。このファイルを`apply_patch`で更新しようとしたところ、sandboxが次を返して拒否した。

```text
patch rejected: writing outside of the project; rejected by user approval settings
```

実体はrepo内として読めるが、安全機構が拒否した操作を別手段で迂回していない。そのため現時点では同ファイルに `git add` / `git commit` / `git push` のallow、tmux許可、agmsgのsend/remote許可が残っている。Coordinatorが許可された経路でR3のこの部分を反映し、AC4およびAC3bを確認する必要がある。

また、session記録は新規Codex成功後の出力から採取するため、実CLI出力形式が要件の `session id:` 行と異なる場合は明示的に失敗する。このfail-closed動作自体はテスト済みだが、実CLIでの互換性は未確認である。

## 差し戻し対応: prompt stdinと作業ディレクトリ

- 新規・resumeのどちらも、Codexへ渡すpromptの末尾引数を明示的な `-` にした。resumeは引数を省略しても標準入力を読まないため、これでwrapperが組み立てた依頼文を確実に渡す。
- 呼出元のcwdに依存しないよう、promptファイルの読み込み・生成が終わった後、Codex実行直前にwrapperが `REPO_ROOT` へ移動する。新規・resumeは同じ共通実行経路を通る。
- 偽Codexは末尾のprompt引数が `-` 以外なら非0で失敗し、起動時cwdを記録するよう拡張した。テストは `/tmp` 下のrepo外ディレクトリからwrapperを呼び、新規とresumeの両方でcwdがrepo root、かつ明示的なstdin promptがあることを確認した。

## 差し戻し対応(2回目): session状態と実行境界

- Role記録を `role<TAB>effort` 形式へ拡張した。Implementerを `--effort high` で新規起動したsessionはhighを記録し、resumeは呼出側の既定値でなく記録値を採用する。旧形式のroleだけの記録は、そのroleの既定mediumとして後方互換で読む。
- 新規Codexが非0で終わっても、出力にsession idがあれば先に記録してから、Codex自身の終了コードをそのまま返す。出力に複数の `session id:` 行がある場合は最初の行だけを採用する。
- wrapper自身による入力・状態・設定の拒否は終了コード64に統一した。Codexが返す終了コードとはテストで73を使い、区別して確認した。
- 空および空白だけの依頼文を、ファイル入力・標準入力ともに拒否する。
- `--output` はrepo rootへ移動する前、すなわち呼出元cwdを基準にabsolute pathへ正規化する。相対指定でもCodexにはabsolute pathだけを渡す。
- 新規・resumeのいずれにも `-c sandbox_workspace_write.network_access=false` を明示する。
- Auditorの依頼文へは、`realpath`で存在と案件フォルダ内であることを検証した後のrepo相対pathだけを入れる。呼出側の未正規化文字列は入れない。

自己検証は `bash scripts/tests/codex_role/run-tests.sh` で行った。偽Codexの引数、stdin、cwd、出力、終了コード、session state fileを確認し、上記の8項目をそれぞれPASSとした。本物のCodexは起動していない。
