## Phase 7 process観察

### 不要なContext

各Roleはsetupで指定したcore、routing、対象role、限定した旧core節、今回成果物だけを使った。他healthcheck role、inventory詳細、過去の中間review全文は読まず、不要Contextを抑制できた。

### 必要情報の不足

初回受入条件の「memoryと対称」だけでは、disk `used_percent` が `used / total` なのか、予約領域と切り上げを含む`df` Use%なのか一意でなかった。Implementerはmemory式を選び、Reviewerが80/90%見逃しを発見した。setupを`df` Use%へ更新後は実装・レビュー・テストが一意になった。

また、Coordinator原依頼をtrio memberが直接参照できない場合がある。setupへ送信元・時刻を追加し、ownerが正規化した要件とのtraceabilityを残した。将来はagmsg message IDまたは監査ファイルへの引用が望ましい。

### Tech Lead指定の過不足

Context / Policyの量と対象ファイル、Role別読込順序は適切だった。一方、Tech Leadは初回にdisk Use%の意味論を明記できず、Coordinator依頼の`tasks/main.yml`という旧構造上の指定も現行`tasks/check.yml`へ補正する必要があった。現行コードを先に確認して要件の語を具体化するゲートが必要である。

### Role責務

Implementerは実装と自己検証、Reviewerは意味論と回帰、Testerは独立証拠と副作用判断に集中し、不適切な責務重複はなかった。同じ境界fixtureの再実行は独立QAとして必要な重複だった。通常の2付きtrio routingも一貫して機能した。

### 公開Skill

汎用code review Skillとplaybook新規作成Skillは、この既存roleの2ファイル差分には広すぎた。限定Contextと現行Role手順を暫定Skillとして使う方が精度とContext効率が高く、不採用は妥当だった。

### Knowledge候補

次は根拠が得られたが、Knowledge基盤が未実装で単一pilotのため、直ちに共通Knowledgeへ昇格しない。

1. disk使用率はmemoryの`used / total`を流用せず、予約領域と切り上げを含む`df` Use%の意味論を要件へ固定する。
2. tester-gate markerだけを信頼せず、copy / report / notificationと実際のguard名をコードで再評価する。
