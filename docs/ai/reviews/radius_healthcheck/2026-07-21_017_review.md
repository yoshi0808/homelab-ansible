## Findings

### 1. [must-fix][resolved] ディスク使用率が `df` の運用上の使用率より低くなり、閾値を見逃す

- Initial path:
  - `roles/radius_healthcheck/files/radius-healthcheck.sh:57-64`
  - `roles/radius_healthcheck/files/radius-healthcheck.sh:104-108`
  - Consumer: `roles/radius_healthcheck/tasks/check.yml:45-56`
- Evidence:
  - 初回実装は `round(disk_used / disk_total * 100)` を `used_percent` としていた。
  - `df` の Use% は、予約領域を含む total ではなく通常利用可能な領域を基準にした `used / (used + available)` を切り上げた値に相当する。したがって、予約領域があるファイルシステムでは分母が異なり、予約領域がない場合でも Python の最近接丸め（ties-to-even）と `df` の切り上げで結果が異なる。
  - このホストの `/` でも `df` は `46%` だが、取得値に現行式を適用すると `44.99%`、Python の `round` 後は `45%` となった。
  - 例として、`total=100, used=76, available=19` なら現行式は `76%`（OK）だが、`df` 相当は `80%`（WARNING）。同様に critical 境界も下回って判定され得る。
- Impact:
  - `check.yml` の比較自体は整数入力に対して 79=OK、80/89=WARNING、90=CRITICAL と正しいが、入力値が過小になるため WARNING/CRITICAL を通知しない安全上の見逃しが発生する。
- Required change:
  - `df` の第5フィールド（Use%）を取得して `%` を除去し、整数として検証して JSON に渡すことを推奨する。独自算出する場合は、`used + available > 0` を検証した上で `used * 100 / (used + available)` を切り上げ、`df` の意味論と一致させる。
  - `collection_ok`、total/used/available の既存検証は維持する。
  - 79/80/89/90 の整数値だけでなく、切り上げで 80/90 に到達する小数境界と、`total != used + available` の予約領域ケースを確認する。
