# radius_healthcheck disk使用率チェック 実装

日付: 2026-07-21
担当: `implementer2`
案件owner: `techlead2`

## 実装概要

`roles/radius_healthcheck` に、ルートファイルシステムのdisk使用率収集と判定を追加した。既存memory実装と同じデータ形・責務分割を使い、shellは `df` の収集とJSON整形だけ、Ansibleはcollection失敗・warning・criticalの判定とreport/debug生成を担当する。

## 変更ファイル

- `roles/radius_healthcheck/files/radius-healthcheck.sh`
  - `LC_ALL=C df -B1 -P /` からsize / used / availableをバイト単位で、第5フィールドのUse%を運用上の使用率として収集する。
  - size / used / availableが数値、totalが正、Use%が `%` 付き整数の場合だけ `collection_ok: true` とし、失敗時はfalseとゼロ値をJSONへ出力する。
  - Use%から `%` を除いた整数を `used_percent` としてJSONへ渡す。予約領域とdfの切り上げを保持し、`used / total` から独自算出しない。
- `roles/radius_healthcheck/tasks/check.yml`
  - disk収集失敗をcriticalとする。
  - `used_percent` 80–89をwarning、90以上をcriticalとする。
  - `radius_report.disk` とdebug summaryへ `collection_ok` / `total_mb` / `used_mb` / `available_mb` / `used_percent` を追加する。
  - disk debugは表示内容を変えずfolded scalarで折り返し、新規のline-length違反を避ける。

次は変更していない。

- `roles/radius_healthcheck/tasks/main.yml`: 保存・通知・failだけを担う既存分割を維持した。
- `playbooks/radius_healthcheck.yml`: `# tester-gate: safe-readonly` を維持した。
- 既存service / port / journal / memoryの収集・判定・report項目。

## 自己検証

### 成功

1. Shell構文

   ```bash
   bash -n roles/radius_healthcheck/files/radius-healthcheck.sh
   ```

   結果: 成功。

2. ローカルの正常収集JSON

   ```bash
   bash roles/radius_healthcheck/files/radius-healthcheck.sh |
     jq -e '.disk.collection_ok == true
       and (.disk.total_mb | type == "number")
       and (.disk.used_mb | type == "number")
       and (.disk.available_mb | type == "number")
       and (.disk.used_percent | type == "number")
       and .disk.total_mb > 0'
   ```

   結果: `true`。diskの全項目が出力され、型と正のtotalを確認した。

3. `df` 失敗時のJSON

   ```bash
   df() { return 1; }
   export -f df
   bash roles/radius_healthcheck/files/radius-healthcheck.sh |
     jq -e '.disk == {
       "collection_ok": false,
       "total_mb": 0,
       "used_mb": 0,
       "available_mb": 0,
       "used_percent": 0
     }'
   ```

   結果: `true`。collection失敗を判定可能なJSONへ整形することを確認した。

4. 実df Use%とfixture境界

   - ローカル `/` で `df -B1 -P /` のUse%とJSONの `disk.used_percent` を比較し、expected=46 / actual=46で一致した。
   - df fixtureの第5フィールドを79 / 80 / 89 / 90%として実行し、JSONがそれぞれ79 / 80 / 89 / 90を保持することを確認した。Ansible判定は79→OK、80/89→WARNING、90→CRITICALとなる。
   - 予約領域と切り上げ境界のfixture `total=105, used=79, available=20, Use%=80%` で、`total != used + available` でもJSONがdf値80を保持した。
   - critical切り上げ境界のfixture `total=105, used=89, available=10, Use%=90%` でJSONがdf値90を保持した。
   - Use%が整数percent形式でないfixtureは `collection_ok=false`、全disk値ゼロになった。

## pilot読込プロセスの所感

### 指定外Context

指定外のSystem Context、他healthcheck role、過去の中間reviewは読んでいない。自己検証に必要な対象コード、tester-gate script、setupメモの公開Skill軽評価だけを追加確認した。

### 情報の不足

初回依頼ではdisk `used_percent` の意味論が明示されず、memory対称から `used / total` を選んだため、予約領域とdfの切り上げを反映できなかった。reviewer2の指摘後、setupメモがdf第5フィールドUse%を正本とする受入条件へ更新され、曖昧さは解消した。diskとmemoryで同名の値でも意味論が異なる点は、最初から受入条件へ明記する必要があった。

### 指定の過不足

参照範囲は適切だった。旧core §4は対象group、§6–7はshell / Ansible責務、現行roleは対称パターン、requirements/finalはread-onlyと確定状態の確認にそれぞれ使えた。finalは内容が短いため、現在のコードを優先する指定が有効だった。

### 責務重複

重複は生じていない。diskの収集・JSON整形はshell、判定・report・debugは `tasks/check.yml`、保存・通知・failは既存 `tasks/main.yml` に維持した。

### Skill不採用

setupメモで評価済みの汎用review Skillとplaybook新規作成Skillは、この既存roleへの小差分には範囲が広すぎる。現行の対称実装と限定Contextを暫定Role Skillとして使う方が、追加Contextを抑えながら要件へ正確に適合できたため、不採用は妥当だった。外部Skillのinstall・コピーは行っていない。

### Knowledge候補

Lesson候補として「disk使用率はmemoryの `used / total` を流用せず、予約領域と切り上げを反映するdf Use%の意味論を固定する」が生じた。fixtureで差を確認済みだが、現時点では単一pilotのため、本成果物とreviewへ記録し、共通Knowledgeへの昇格はTech Leadの判断に委ねる。
