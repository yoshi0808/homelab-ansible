# 自律復旧の無効状態を日次で検知する(requirement)

作成: 2026-08-01 / Coordinator
起点: Yoshinobuの提案「毎日朝にチェックして監視がMuteであればSlack通知(警告)というのはどうかしらね」(2026-08-01)。`docs/ai/status.md` Next「global pauseの解除忘れを構造で防ぐ(TTL付与、または未解除の定期通知)」の後者を採る決定。

## 1. 問題定義

2026-07-21から2026-07-29まで**8日間**、自律復旧のglobal pauseが解除されないまま残り、全targetのpull probeがskipされ続けた。誰も気づかなかった構造的な理由は2つある(`docs/ai/memory/incidents/2026-07-29_global-monitoring-pause-left-on-8-days.md`)。

1. global pauseにTTLが無い(target別muteは1〜240分のTTLで自動失効するが、global pauseは明示的なresumeまで無期限)
2. **pause中であることを知らせる経路が無い**。`homelab-monitoring-status` を誰かが能動的に叩かない限り分からない

加えて、同じ「自律復旧が効いていない状態が続く」失敗クラスの穴がもう1つある。`recovery-probe.service` は `Restart=on-failure` だけを持ち、`OnFailure=` による通知経路を持たない(`roles/recovery_probe/templates/recovery-probe.service.j2` の現物で確認)。**`systemctl stop` / `disable` で止めた場合、pauseと同じく誰も気づかない。**

## 2. ゴール

- global pauseが継続している状態を、遅くとも翌朝には人間へ届ける。
- `recovery-probe` が動いていない状態も同じ入口で検知する。
- 正常時は無通知とし、通知が来たこと自体が異常の信号になる状態を保つ。

## 3. 非ゴール

- **global pauseへのTTL付与は採らない。** TTLで自動resumeすると、意図的に停止しているホスト(夏季のpve1など)に対して復旧ラダーが誤発火し得る。人間の判断を挟む通知の方が安全である(2026-08-01、Yoshinobu選択)。
- **target別mute(TTL付き)は検査対象に含めない。** 自動失効するため解除忘れが構造的に起こらず、かつ土曜06:00のweekly full patchがevacuate muteを立てるため、朝の検査に含めると毎週偽警報になる(2026-08-01、Yoshinobu選択)。
- pauseを立てた主体・理由を記録する仕組み(pause flagは空ファイルで理由を持たない)は本件では作らない。
- Semaphoreのschedule登録そのものはrepo外の手作業であり、本件の成果物に含まれない(§7 OQ1)。

## 4. ユーザーストーリー

運用者として、自律復旧を止めたまま作業を終えてしまっても、翌朝のSlackで「まだ止まっている」と知らせてほしい。**いつから止まっているか**が本文にあれば、うっかり1日なのか放置8日なのかをその場で判断できる。

## 6. 成功指標(受入条件)

| AC | Given / When / Then |
|---|---|
| AC1 | **Given** global pauseが無く `recovery-probe` が active **When** playbookを実行する **Then** Slack通知は送られず、終了コードは `0` |
| AC2 | **Given** global pauseが有効 **When** 同上 **Then** `alerts` へ `warning` が1本送られ、本文にpause開始時刻と経過が含まれ、終了コードは `0`(通知が信号であり、ジョブは緑) |
| AC3 | **Given** `recovery_probe_service_enabled` が真のhostで `recovery-probe` が active でない **When** 同上 **Then** `alerts` へ `warning` が1本送られ、本文に `systemctl is-active` の生の値が含まれ、終了コードは `0` |
| AC4 | **Given** `homelab-monitoring-status` が `ACTIVE` / `PAUSED` のいずれでもない出力を返す **When** 同上 **Then** playbookは**非ゼロで停止**し、判定不能である旨のメッセージを出す。Slackへ「正常」を意味する通知を送らない |
| AC5 | **Given** `--check` 付き実行 **When** 同上 **Then** read-onlyの確認タスクは実行され、通知は `roles/common_slack` の `ansible_check_mode` 抑止によりdebug表示に留まり、**Slackへは送信されない** |
| AC6 | **Given** 修正後のリポジトリ **When** `--syntax-check` / `ansible-lint` / `scripts/git-pre-commit-check.sh`(tester-gate lint と check-doc-consistency を含む)を実行する **Then** いずれも新規のエラーを出さない |

### 検証の制約(重要)

- **AC2・AC3・AC4はdecoyで検証する。** 実quoryにpause flagを立てる、あるいは `recovery-probe` を停止することは、まさに本件が防ごうとしている状態を自ら作る操作であり行わない。
- **実quoryに対して実行してよいのはAC1(正常時=無通知)の経路のみ**である。read-onlyコマンド2本(`homelab-monitoring-status`、`systemctl is-active`)と設定ファイル1つの読み取りに限られる。
- **Slackへの実送信は行わない。** Testerの検証が本番Slackへ到達した事象が3回起きている(`docs/ai/memory/incidents/2026-07-29_tester-slack-notify-misfire.md`、`.../2026-08-01_tester-slack-decoy-did-not-contain-request.md`)。通知本文の確認は抑止経路のdebug出力で行う。

## 7. オープンクエスチョン

- **OQ1(Yoshinobuの手作業)**: Semaphoreの日次schedule登録(**06:30 JST**、2026-08-01 Yoshinobu指定)はrepo外のUI作業であり、AIから実施も確認もできない。登録されるまでこの仕組みは動かない。`docs/ai/status.md` Watchへ残す。
- **OQ2(残存リスク)**: global pauseを使う定期処理と06:30が重なると、作業中のpauseに対して警告が出る。現在global pauseを使うplaybookは `cert_renew.yml`(月次)のみだが、Semaphoreのschedule時刻はrepo外のため重複の有無を事前に確認できない。偽警報が出た場合の対処はP2-1の猶予導入。
- **OQ3(検知の空白)**: 本playbook自身がSemaphoreで失敗し続けた場合、それを知らせるのはSemaphoreのジョブ履歴だけである。監視の監視は作らない。

## 8. タイムライン考慮

急ぎではない。ただしschedule登録までは効果ゼロであるため、実装完了時にYoshinobuへ手作業の依頼を明示する。
