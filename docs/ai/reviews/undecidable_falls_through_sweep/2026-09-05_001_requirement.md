# requirement: 「判定不能が通る側へ倒れる」箇所の掃き出し(第2家族: `| length`)

日付: 2026-09-05(2026-09-05 改訂 — 走査単位と成果物の出し方を変更)
依頼: Coordinator → codex側 Implementer
性質: **実装ではない。読んで一覧にする(事実収集)。直さない。**

## 探すもの

`docs/ai/core.md`「作るものが満たすこと」は次を要求している。

> **判定できないときは止める。** 前提が満たせない、対象が見つからない、状態をどちらとも解釈できない — これらを正常扱いにしない。**空の成功、無言の完走、既定値へのフォールバックで先へ進めない。** 壊れているときほど「問題なし」に見える設計を作らない。

この要求に反している箇所を挙げる。**このリポジトリで実際に複数件発生しており、いずれも読解では出ず、実行して初めて出た。**

## 走査の起点と範囲

**起点は grep のヒット行である。ファイル全体を読まない。**

```
git grep -nE '\| *length' -- playbooks roles scripts
```

現在383ヒット。**このヒット行だけが対象である。**

- `or []` / `or {}` / `or 0` の家族は Coordinator が別途処理済みのため**対象外**。
- 各ヒットについて、その式が評価する対象が何になりうるかを、**そのヒットを含む task / 関数 / play の範囲内**で判断する。呼び出し元を1段たどるのは可、そこから先は追わない。
- **範囲内で判断できないものは深追いせず「未確定」節へ回す。**

## 対象を「判定している箇所」に限る

値を表示・記録するだけの箇所は対象外。**次のいずれかを決めている分岐だけ**を見る。

- changed / unchanged、一致 / 不一致
- ok / ng、正常 / 異常、通知する / しない
- 有効 / 無効、実行する / skipする、要 / 不要
- 存在する / しない、到達できる / できない

## 各件に書くもの(分量の上限つき)

1. `file:line`
2. **どの入力でどちら側へ落ちるか** — 1〜2行
3. **その入力が現在の経路で到達しうる根拠** — 1〜2行

**合計で1件あたり4行を超えない。** コードの引用は式そのもの(1行)までとする。

## 足切り

- **現在の入力で到達する経路を示せないものは findings に入れない。** 「理論上 `None` になりうる」だけのもの、将来の改名や将来の拡張を前提にするものは入れない。それらは「未確定」節へ1行で置く。

## 進め方 — ここが今回の変更点

**成果物へ逐次追記しながら進める。まとめて最後に書かない。**

- 走査した範囲(どのファイルまで、何ヒットまで見たか)を成果物の冒頭に書き、**進むたびに更新する。**
- **途中で止まっても、どこまで走査したかと、そこまでの findings が成果物に残っている状態を保つ。**
- 前景の実行上限や利用枠に達しそうだと判断したら、**そこまでを書き切ってから終える。** 全件終わらないまま終わってよい。**「終わらなかった」は失敗ではない。何も残らないことが失敗である。**

## 受入条件

- **AC1**: 成果物の冒頭に、走査済み範囲と未走査範囲が書かれていること。全件終わっていなくてよい。
- **AC2**: findings の各件が上記1〜3を満たし、1件4行を超えないこと。
- **AC3**: 深刻度を「判定を誤らせる(壊れていても問題なしに見える)」と「例外で落ちる(気づける)」の2つに分けること。**前者が本題である。**
- **AC4**: 意図的にその挙動を選んでいると読める箇所は、その根拠(コメント・requirement)を1行添えて外す。外した判断も残す。

## 到達してはいけない状態

- 成果物1本以外に、自分が変更したファイルがある状態で報告が返ること。**実装は直さない。**
- 実ホストへ触れた状態、実行identityを昇格した状態に到達すること。
- stage / commit が行われた状態。
- **走査を続けたまま自分のターンを終えること。** 途中で終えるときは、成果物を書き切ってから終える。
