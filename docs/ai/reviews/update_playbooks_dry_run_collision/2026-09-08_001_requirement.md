# requirement: 稼働中update playbookの`dry_run`衝突を解消する

作成: 2026-09-08 / Coordinator
先行案件: `docs/ai/reviews/semaphore_upgrade_native_check_mode/`

## 1. 問題定義

`ubuntu_vm_full_upgrade.yml`と`prometheus_update_check.yml`は、playbook独自の
extra-var `dry_run`を実行モードの選択に使う。一方、Semaphore自身も
`task_params.params.dry_run`をAnsibleの`--check`として使う。同じtemplate / scheduleに
同名で別の意味を持つ値が並び、実際の変更可否を一意に読めない。

先行した`semaphore_upgrade`はscheduleを持たないため、独自`dry_run`を廃止して
Semaphore UI Dry Runへ統一できた。残る2本は、通常実行のinspectionがSlack通知を
送る稼働scheduleを持つ。scheduleを単純に`--check`へ変えると
`common_slack`が通知を抑止し、更新検知という運用目的を失う。

したがって、今回は「何をするか」をnamespacedな`operation`で表し、
Semaphore UI Dry Run / `ansible_check_mode`は「選んだoperationを変更なしで検査するか」
という別軸にする。旧`dry_run`を名前だけ変えたbooleanとして残さず、許される操作を
列挙したenumにする。

## 2. ゴール

1. playbook独自の`dry_run`とSemaphore native Dry Runの名前衝突をなくす。
2. 稼働中の月次・週次inspectionとSlack通知を維持する。
3. manual apply / update / rollbackの明示性と既存の安全条件を維持する。
4. `--check`を全operationに直交する、変更・通知なしの検証経路にする。
5. 旧template / scheduleと新コードが一時的に混在しても、変更側へ倒れない。

## 3. 非ゴール

| やらないこと | 理由 |
|---|---|
| apt以外のupdateを無人で自動適用する | `docs/ai/status.md`の別案件であり、現行Policyと衝突する |
| Ubuntu full-upgradeの対象host、Status判定、確認文字列、reboot方式を変える | mode名の整理と独立した本番挙動である |
| Prometheusのtrack、artifact検証、backup世代、自動rollback、healthcheckを変える | 成立済みの更新transactionを維持する |
| 通知channel・本文・best-effort契約を再設計する | scheduleの既存観測点を維持する |
| `common_slack`のcheck mode抑止を緩める | 全playbook共通の安全契約を変えない |
| template / scheduleをrename・増減する | reconcileのrename非対応と既存schedule identityを維持する |
| 本案件の検証目的で実update / rollback / rebootを行う | destructive経路は静的照合と`--check`で検査する |

## 4. ユーザーストーリー

- Semaphore利用者として、画面のDry RunとSurveyの`dry_run`を見分ける必要なく、
  templateが行う操作を一意に理解したい。
- 運用者として、月次Ubuntu判定と週次Prometheus確認の通知を従来どおり受け取りたい。
- manual apply利用者として、対象operationと既存の確認入力を明示しない限り、
  package・binary・serviceが変更されてほしくない。
- Testerとして、同じoperationを`--check`で通し、通常実行の入力検証と予定動作を
  副作用・Slack送信なしに確認したい。

## 5. 要件

### P0 (Must)

| # | 要件 |
|---|---|
| P0-1 | `ubuntu_vm_full_upgrade.yml`はnamespaced enum `ubuntu_vm_full_upgrade_operation`だけで`inspect` / `apply`を選ぶ。独自`dry_run`を有効入力として使わない |
| P0-2 | `prometheus_update_check.yml`はnamespaced enum `prometheus_update_check_operation`だけで`inspect` / `update` / `rollback`を選ぶ。独自`dry_run`と旧`rollback` booleanを有効入力として使わない |
| P0-3 | 旧`dry_run`は値にかかわらず、Prometheusの旧`rollback`も定義されていれば、healthcheck・version収集・download・変更より前にrc非ゼロで停止し、新しいoperationと`--check`の使い方を示す。無視して通常実行へ進めない |
| P0-4 | Ubuntuの`inspect`は全対象hostで既存の判定・per-node通知を行う。`apply`は既存どおり`node`と一致する単一hostだけが参加し、`ubuntu_vm_full_upgrade_confirm`の一致を必須とする |
| P0-5 | Prometheusの`inspect`は既存のversion / track判定と通知だけを行う。`update`は既存のguarded update、`rollback`は既存のbackup選択とmanual rollbackへ接続する。未知operationは変更前に拒否する |
| P0-6 | `ansible_check_mode`はoperationと直交させる。いずれのoperationでも`--check`中はpackage / binary / backup / lock / service / reboot / detached unit / result fileを変更せず、Slackを送らず、診断と予定動作を表示する。状態を変えない収集だけに必要最小限の`check_mode: false`を許す |
| P0-7 | 5つのSemaphore templateから独自`dry_run` Surveyを除去し、各variantに対応するnamespaced operationを渡す。Ubuntu applyの`node` / confirmation、Prometheus rollbackの`rollback_to`等、operation以外の既存入力は維持する |
| P0-8 | 月次Ubuntu scheduleは`operation=inspect`、週次Prometheus scheduleは`operation=inspect`をenvironmentから渡す。両scheduleのSemaphore native `params.dry_run`はfalseのまま維持し、通常inspectionとSlack通知を継続する |
| P0-9 | 新コードが先にquoryへ届き、旧template / scheduleが一時的に旧変数を渡す期間はP0-3でfail-closedする。template catalog reconcile後、実template 5件とschedule 2件をread-only APIで観測してから移行完了とする |
| P0-10 | `ubuntu_vm_patch_policy.md`、`docs/ai/context/operations/ubuntu-vm-patch.md`、playbook header、`playbooks/README.md`、template catalogコメント、`docs/ai/status.md`を新しいoperationとnative Dry Runの意味へ揃え、旧`dry_run`を有効な呼出しとして残さない |
| P0-11 | `# tester-gate: check-mode-native`を維持し、既存の通常inspection / apply transactionと、`--check`時の副作用・通知抑止を回帰検証する |

### P1 (Should)

| # | 要件 |
|---|---|
| P1-1 | 最終debug / notificationはoperationを表示し、独自dry-runとnative check modeを混同する語を出さない |
| P1-2 | 旧変数の拒否guardは`tags: [always]`とし、tag限定実行でも回避されない |
| P1-3 | operation判定をrole内の単一factへ正規化し、個々の変更taskへ文字列比較を重複させない |

### P2 (Could)

- なし。

### Won't

- `dry_run`を`apply: true/false`のような反転booleanへ機械的にrenameしない。
- scheduled inspectionをSemaphore native Dry Runへ変えない。native Dry RunではSlackが
  抑止され、scheduleの目的が変わるためである。

## 7. オープンクエスチョン

なし。operation名は`ubuntu_vm_full_upgrade_operation`と
`prometheus_update_check_operation`、値は上記enumを採用する。schedule通知を維持するため、
先行`semaphore_upgrade`と異なりscheduled inspectionの通常実行は維持する。

Policy本文の変更を含むため、実装着手前に本requirementのscopeとしてYoshinobuの承認を得る。

## 8. タイムライン考慮

- Step 1: requirementと詳細計画を作成し、別CLIのReviewerが計画査読する。
- Step 2: Policy・playbook・role・catalog・fixtureを同じ差分で実装する。
- Step 3: localhost / decoyでoperation行列、旧入力拒否、`--check`副作用ゼロを検証し、
  別体ReviewerとTesterを通す。実update / rollback / rebootは行わない。
- Step 4: commit / push後、新コードと旧templateの混在期間は旧入力拒否で停止する。この間に
  scheduleが発火した場合、その回のinspectionとSlack通知が行われない可能性があるが、
  変更側へfallbackさせないための意図したfail-closedとして扱い、reconcileを連続して行う。
- Step 5: YoshinobuがquoryのSemaphoreからtemplate catalogをreconcileし、template 5件と
  schedule 2件をreadbackする。初回scheduled inspectionまたは同条件の手動実行で
  rcとSlack通知を観測する。
- Step 6: `docs/ai/status.md`から残存案件を除き、Auditorを1回起動してクローズする。
