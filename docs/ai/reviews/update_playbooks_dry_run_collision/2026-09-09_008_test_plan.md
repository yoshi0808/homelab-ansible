## 1. 安全境界

- 実host（`pve1`/`pve2`/`authy`/`sophos-fw`/UniFi）、quory、production Slackへは触れない。
- 通常のupdate/apply/rollback/reboot、Semaphore template/schedule catalog reconcileは実行しない（EXEC-052、requirement非ゴール）。
- commit/pushは行わない。
- 使い捨てplaybookは`playbooks/`直下に一時作成し、検証後に削除して`git status --porcelain playbooks/`で残存なしを確認する。実host名・実IPは書かない。
- `hosts: localhost` + `connection: local`の副作用のない使い捨てplaybook、および対象playbook自身が持つ`hosts: localhost, connection: local`のplay（`prometheus_update_check.yml`の第1 play）はEXEC-042により提示不要の状態を変えない確認として扱う。
- `--check`実行時は`skip_notifications=true`を明示し、`CLAUDECODE`環境変数によるnotify.yml側抑止も働くことを前提にするが、二重に確認する。

## 2. 検証範囲とNot Runの判断基準

対象2playbookの入力guard（legacy拒否・operation enum検証・順序）、check mode下の副作用ゼロ、Semaphore catalogのexact shapeを検証する。次の経路は環境制約でNot Runとする（推測しない）。

| 経路 | Not Run理由 |
|---|---|
| Ubuntu playbook-level `pre_tasks`をhosts groupごと通す実行（`dev_nodes:control_nodes:radius_servers:monitoring_servers`） | 該当groupに属するhostがdecoy inventoryへ実host名なしで作れない（`node`のenum値が`ansy`/`monnie`/`authy`/`quory`という実host名そのものであり、decoy条件1「実host名を書かない」と両立しない）。代わりに、playbook本文の`pre_tasks`と完全一致する文字列をsed抽出したlocalhost限定fixtureで同じassertの合否を確認する。 |
| Prometheus第2 play（`hosts: monnie`）を実inventory経由で実行 | `hosts: monnie`が実host名を直接指定しており、decoy化すると実host名を書くことになる。代わりに`ansible.builtin.import_role`をlocalhost限定fixtureで直接呼び出し、role本体（`tasks/main.yml`のguard、update/rollback blockのwhen条件）を検証する。 |
| `node`のenum値と`inventory_hostname`の一致によるUbuntu apply単一host参加（AC2/AC3の一部） | 同上の理由でinventory_hostnameを実host名にできない。コード読解（`ubuntu_vm_full_upgrade_is_apply_target`の定義とP0-4の記述一致）と、enum外の値でのnode拒否実測で代替する。 |
| 実Semaphore 5 template・2 scheduleのreconcile/readback（AC9） | catalog reconcileはrequirement非ゴール（Step5、Yoshinobu実施）。本検証はcatalogのYAML定義をshapeとして静的照合するに留める。 |
| 通常inspection（apply/update/rollback含む本番相当実行）のSlack通知観測（AC1/AC4） | 実host・productionSlackへ触れないため。既存notify.yml/common_slackの契約（check mode抑止、`CLAUDECODE`抑止）はコードレベルで確認する。 |

## 3. 検証項目

### 3.1 静的検証

1. `ansible-playbook --syntax-check` を両playbookに対して実行。
2. `ansible-lint` を両playbookに対して実行。
3. `scripts/check-tester-gate.sh` で全playbookのマーカー検査。
4. `scripts/check-doc-consistency.py` でdoc整合検査。
5. `git diff --check` でwhitespaceエラー確認。

### 3.2 入力guardとfail-closed（AC7、P0-3）

Prometheus第1 play（`hosts: localhost, connection: local`、対象playbook本体）を直接実行し、次を確認する。

- 未指定 → operation-requiredでrc非ゼロ、facts収集(setup)未到達。
- `dry_run=true` / `dry_run=false` → legacy guardでrc非ゼロ、facts収集未到達。
- `rollback=true` / `rollback=false` → 同上。
- `operation=bogus`（未知値）→ operation-requiredでrc非ゼロ。
- `operation=inspect|update|rollback` → guard通過、後続の`ansible_facts['hostname'] == 'quory'`assertまで到達（ansy上のためここで意図的に失敗するが、guard通過の証跡として扱う）。

Ubuntuは`pre_tasks`をsed抽出したlocalhost限定fixtureで同じ経路（未指定 / legacy / 未知値 / 正常値）を確認する。

### 3.3 role本体のoperation分岐とcheck mode副作用ゼロ（P0-6、AC5/AC6）

`ansible.builtin.import_role: name: prometheus_update_check`をlocalhost限定fixtureで直接呼び出し、対象variableを外部から注入して次を確認する。

- `operation=update`かつ`--check` → update blockの`when`条件（`operation=='update' and not ansible_check_mode`）がfalseになり到達しないことをタスク一覧で確認（実download/binary swap/serviceを起こさない）。
- `operation=rollback`かつ`--check` → rollback discoveryは到達するが、restore blockの`when`（`operation=='rollback' and not ansible_check_mode`）はfalseで到達しない。
- 変更taskの`when`文字列を静的grepし、`not ansible_check_mode`が全destructive blockに掛かっていることを確認する（P0-6横断照合）。

Ubuntu applyの`not ansible_check_mode`境界は`roles/ubuntu_vm_full_upgrade/tasks/main.yml`のinclude条件を静的照合する（apply.ymlの起動が`ubuntu_vm_full_upgrade_is_apply_target and not ansible_check_mode`であること）。

### 3.4 Semaphore catalog exact shape（AC9の静的部分）

`roles/semaphore_templates/defaults/main.yml`をPythonでYAML読込し、5 templateのsurvey_vars（name/type/values/default）と2 scheduleのenvironment/`params.dry_run`/cron/active/debug_levelをrequirement記載値と突合する。

### 3.5 旧語掃引（AC8）

対象ファイル（playbook 2本、role 2本、Policy、Operations Context、README、status.md、catalog）に対し、有効な入力として読める`dry_run`/`rollback`の残存が無いことをgrepで確認する（reject-only guard文字列とSemaphore native `params.dry_run`、identity保持文字列は除外）。
