# 実装計画: 稼働中update playbookの`dry_run`衝突解消

作成: 2026-09-08 / Coordinator
契約: `2026-09-08_001_requirement.md`

## 1. 変更単位

### 1.1 Ubuntu VM full upgradeのoperation契約

対象:

- `playbooks/ubuntu_vm_full_upgrade.yml`
- `roles/ubuntu_vm_full_upgrade/defaults/main.yml`
- `roles/ubuntu_vm_full_upgrade/tasks/`

変更:

1. `ubuntu_vm_full_upgrade_operation`を`inspect` / `apply`のenumとして入口で検証する。
2. `dry_run is defined`を値にかかわらず最初に拒否する移行guardへ置き換え、
   `tags: [always]`でtag限定時にも先行させる。
3. 現行の`dry_run | bool`参照を、正規化したoperation factへ置き換える。
4. `inspect`は全host参加、`apply`は`node`一致hostだけ参加とする現在の分岐を維持する。
5. `apply`のknown-node検査、confirmation一致、Status拒否、単一host変更を維持する。
6. `ansible_check_mode`はoperationと直交させ、`apply --check`では共通判定と
   would-applyを表示するが`apply.yml`へ到達させない。
7. header、通知title、debug等の`dry-run (monthly)`表記を`inspect`へ揃える。

### 1.2 Prometheus update checkのoperation契約

対象:

- `playbooks/prometheus_update_check.yml`
- `roles/prometheus_update_check/defaults/main.yml`
- `roles/prometheus_update_check/tasks/`

変更:

1. `prometheus_update_check_operation`を`inspect` / `update` / `rollback`のenumとして
   localhost playの最初とrole入口で検証する。
2. `dry_run is defined`と旧`rollback is defined`を値にかかわらず最初に拒否する
   `tags: [always]`移行guardにする。
3. defaultsの`rollback`から作るmode factを廃止し、正規化したoperationから
   inspect/update/rollback判定を1回だけ作る。
4. version / track収集、Status判定、backup discoveryを必要なoperationへ接続し直す。
   現在のstatus語彙と優先順位は変えない。
5. update blockは`operation=update and not ansible_check_mode`、rollback blockは
   `operation=rollback and not ansible_check_mode`を必須にし、既存の追加guardを維持する。
6. `update --check`はtargetと予定動作、`rollback --check`は選択backupと予定動作を
   表示する。いずれもdownload / restore / service / Slackへ到達させない。
7. summaryと通知文から独自dry-run表現を除き、operationとnative check modeを
   別フィールドとして表示する。

### 1.3 Semaphore template / schedule移行

対象:

- `roles/semaphore_templates/defaults/main.yml`
- 同roleのtemplate / schedule reconcile検査

変更:

1. Ubuntu 2 templateの`dry_run` Surveyを、`name: ubuntu_vm_full_upgrade_operation`の
   operation Surveyへ置換する。
   dry-run variantは`inspect`、apply variantは`apply`を渡し、applyのnode / confirmationを
   維持する。
2. Prometheus 3 templateの`dry_run` Surveyとrollback variantの旧`rollback` Surveyを、
   `name: prometheus_update_check_operation`のoperation Surveyへ置換し、それぞれ
   `update` / `inspect` / `rollback`を渡す。
   target / rollback_to等の既存入力を維持する。
3. Ubuntu月次scheduleのenvironment keyを`ubuntu_vm_full_upgrade_operation`、
   Prometheus週次scheduleのenvironment keyを`prometheus_update_check_operation`とし、
   いずれも値`inspect`を渡す。
4. 両scheduleの`params.dry_run: false`を維持する。Prometheusの`debug_level`、cron、
   active、template参照も変更しない。
5. catalogの第2バッチコメントを、environmentのoperationとSemaphore native
   `params.dry_run`が別軸である説明へ更新する。
6. desired / observedのtemplate Surveyとschedule task_paramsを比較する既存テストへ、
   5 template・2 scheduleのexact shape検査を追加する。

## 3. 検証順序

1. 旧入力guard、operation enum、全参照の静的検査。
2. syntax、ansible-lint、tester-gate lint、doc consistency、catalog unit test。
3. localhost / decoyで5経路と異常入力を実行し、task到達性と出力を確認する。
4. Testerが安全wrapper経由で許可された`--check`を実測し、副作用・通知の前後差分を取る。
5. 通常inspectionの通知経路はfixtureで確認する。本案件の検証として実update / rollback /
   rebootを行わない。
6. commit / push後、Yoshinobuがquoryでtemplate catalogをreconcileする。実template 5件と
   schedule 2件をread-only APIで照合後、scheduled inspectionと同条件の通常実行で
   rcとSlack通知を観測する。

## 4. 移行順序と停止条件

1. 新コードが先にquoryへ届き、旧template / scheduleが旧変数を渡す期間は、
   reject-only guardによる明示失敗を許容する。旧変数を無視して継続してはならない。
   この期間にscheduleが発火すると、その回のinspectionとSlack通知が行われない可能性がある。
   これは変更側へfallbackさせないための意図したfail-closedであり、push後はreconcileを
   連続して行って移行窓を短くする。
2. reconcileのdry-run差分で5 template・2 schedule以外の変更が出たら適用しない。
3. scheduleの`params.dry_run`、cron、active、Prometheus `debug_level`が現行値から変わる
   差分が出たら適用しない。
4. operation未指定・未知値がinspectまたは変更側へfallbackするなら実装を止める。
5. `--check`で変更taskまたはSlackへ到達するなら実装を止める。
6. Ubuntu applyの単一host / confirmation、Prometheusのtrack / backup / rollback安全条件を
   維持できない変更が必要なら、要件を広げずCoordinatorへ戻す。
7. quory readbackがcatalogと一致しない、または通常inspectionの通知が観測できない場合、
   statusを未完了のままにしてクローズしない。
