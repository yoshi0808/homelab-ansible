# requirement: Proxmoxの稼働中の版をNotionの固定ページへ書く

状態: 確定 r3(2026-10-16、Coordinator。計画査読 `_002`〜`_004` と読み手のClaudeの要望を反映。`_004` の残1件はユーザーストーリーの文言修正のみで、再査読は省いた)

## 1. 問題定義

Notionの「Proxmox Watch」DBは、Proxmox関連の脆弱性・新リリースを記録し、定期タスク(別のClaudeセッション)が「うちの環境に該当するか」を判定する。判定には pve1 / pve2 の**稼働中の**版が要るが、いまは定期タスクのプロンプトに版を直書きしており、週次パッチのたびに古くなる。2026-10-16には、10/10の週次パッチで修正済みになっていたCVE-2026-74580が「未対応」のまま残っていた。

週次パッチ(`playbooks/proxmox_patch_weekly_full.yml`)の末尾へ書き込みを足す案は採らない。NO_UPDATESの週は最終Playの先頭(`meta: end_play`)で抜け、異常検出の週は途中で止まるため、ページが更新されないまま古い版を最新として読ませることになる。

## 2. ゴール

- pve1 / pve2 の稼働中の版を、毎日、Notionの固定ページ「Proxmox Watch: 稼働バージョン」へ上書きする。
- 定期タスクが機械的に読める書式にする。
- 取れなかった値を、取れなかったと読める形で書く(古い値を残さない、空欄にしない)。

## 3. 非ゴール

- 週次パッチ(`proxmox_patch_weekly_full.yml` と import先)への変更。触らない。
- 版の比較・該当判定。定期タスク側の仕事であり、このplaybookは事実を書くだけ。
- 履歴の保持。ページは毎回上書きする。
- Proxmox Watch DBの行の作成・更新。
- Slackへの定常通知。正常時は通知しない(R7)。
- Notion連携・トークンの新設。既存のものを使う(R5)。

## 4. ユーザーストーリー

- Proxmox Watchの定期タスクとして、ページを読めば pve1 / pve2 が今どの版で動いているかと、その値がいつ取られたかが分かり、CVEの修正版と比較できる。
- Yoshinobuとして、ページを開けば、直近のapply試行(週次・手動を区別しない)の時刻・成否・再起動の有無と、各ノードの版が一目で分かる。

## 5. 要件

### P0

- **R1 新しいplaybook** `playbooks/proxmox_running_versions.yml` を作る。対象は `proxmox` グループ。ホストの状態を変えない(読み取りのみ)。到達不能ノードの扱いは既存のread-only点検と同じ方式(`ignore_unreachable` と到達ノードの選別。`docs/ai/adr/008-proxmox-readonly-check-unreachable-node.md`)に従い、片系が到達不能なだけでAnsibleのrcが4にならないようにする。
- **R2 集める値(ノードごと)**
  - `kernel`: `uname -r`(稼働中カーネルのABI表記)
  - `kernel_pkg`: 稼働中カーネル(`/boot/vmlinuz-<uname -r>`)を所有するパッケージのdpkg上の版(例: `7.0.14-23`)
  - `kernel_installed`: 起動可能なカーネルの実体パッケージのうち最新の版。候補は、dpkgの状態が installed(`ii`)で、名前が `proxmox-kernel-<ABI>-pve-signed` または `proxmox-kernel-<ABI>-pve` のもの。メタパッケージ(`proxmox-kernel-7.0` 等)と `proxmox-kernel-helper` は含めない。版の比較はDebianの版比較(`dpkg --compare-versions` と同じ規則)で行い、文字列順で比べない。`kernel_pkg` と同じ版体系なので、両者が異なれば「インストール済みだが再起動待ち」と読める。候補が1件も無いときは `status: error`
  - `pve_manager`: `pveversion` の出力から pve-manager の版
  - `pve_qemu_kvm_installed`: `pve-qemu-kvm` パッケージのdpkg上のinstalled版。**稼働中のVMが使っているQEMUの版ではない**
  - `collected_at`: 収集時刻(JST、ISO 8601)
  - いずれかの値が取得できない・期待した形式に解析できないとき、そのノードは `status: error` とする(値を推測で埋めない)。
- **R3 直近のapply結果(補助情報)**: quory上のapplyレポート(`proxmox_patch_apply_report_dir`、ファイル名 `<JST timestamp>_<node>_apply.json`)から、ノードごとにファイル名の時刻が最新の1件を読み、`last_apply_at`(`run_timestamp`)、`last_apply_result`(`result`: `SUCCESS` / `FAILED`)、`reboot_done` を書く。**これは「直近のapply試行」であり、週次・手動の区別も成否の選別もしない**(レポートに週次/手動の識別子が無いため)。レポートが無い・読めない・期待したキーが無いときは3キーとも `unknown` とし、それだけではジョブを失敗させない。
- **R4 ページの書式と更新手順**
  - 本文は、先頭のヘッダ用コードブロック1つと、ノードごとのコードブロック(pve1、pve2の順)からなる。各行は `key: value` 形式。キーの集合と順序は固定し、値が無くても行を省かない。
  - ヘッダのキー: `state` / `updated_at` / `status` / `note`。
    - `state`: `complete` または `updating`。**読み手は `state: complete` のときだけ本文を有効とみなす。**
    - `status`(全体): 全ノード `ok` なら `ok`、一部が `ok` 以外なら `partial`、全ノードが `ok` 以外なら `error`。
    - `note`: 固定文「pve_qemu_kvm_installed はパッケージのインストール版であり、稼働中VMのQEMUの版ではない」。
  - ノードのキー: `node` / `status` / `kernel` / `kernel_pkg` / `kernel_installed` / `pve_manager` / `pve_qemu_kvm_installed` / `collected_at` / `last_apply_at` / `last_apply_result` / `reboot_done`。ノードの `status` は `ok` / `unreachable` / `error`。`ok` 以外のノードでは版のキーをすべて `unknown` とし、前回の値を残さない。
  - 更新手順: ①ヘッダを `state: updating` に書き換える → ②ノードのブロックを書き換える → ③最後にヘッダを `state: complete` と新しい `updated_at` / `status` に書き換える。途中で失敗すればヘッダは `updating` のまま残り、読み手は無効と判定できる。次回の実行は①から通しでやり直し、それで回復する。①自体が失敗した場合はページが前回の `complete` のまま残るが、`updated_at` が古くなるので読み手の鮮度判定(下記)で検出される。
  - 鮮度の閾値は読み手(Proxmox Watchの定期タスク)が持つ(`updated_at` が26時間より古ければ書き込み停止とみなす)。このplaybookは閾値を持たない。
- **R5 認証情報**: 既存のNotion連携のトークンファイル(`roles/proxmox_storage_monthly` / `roles/quory_health_monthly` と同じもの)を同じ扱い(通常ファイル・mode 0600・symlink拒否を検査し、Git・引数・ログ・通知へ出さない)で使う。書き込み先ページIDはroleのdefaultsに置く(既存2roleの親ページIDと同じ扱い)。
- **R6 抑止**: `--check`、`skip_notifications=true`、AIセッション検出(`roles/common_slack/tasks/notify.yml` と同じ3条件)のいずれかで、Notionへの送信もトークンファイルの読み込みも行わず、書く予定の本文を表示する。
- **R7 終了コードと通知**
  - 全体 `ok` かつNotion更新完了: rc 0、Slack通知なし。
  - 全体 `partial` で、`ok` 以外のノードがすべて `unreachable`: ページへ書き、rc 0、Slack通知なし(pve1の夏季平日停止など、片系の到達不能は運用上ありうる。到達不能の検知はhealthcheckの役目)。
  - いずれかのノードが `error`(コマンド失敗・解析不能): ページへ書いたうえで rc 非0、Slack `#alerts` へ1通。収集処理そのものが壊れている状態を緑にしない。
  - 全体 `error`(全ノード `unreachable` を含む): ページへ書いたうえで rc 非0、Slack `#alerts` へ1通(SB-095の「全node到達不能は明確なエラーで停止」と同じ扱い)。
  - Notion更新失敗(認証・権限・API異常・ページ不在、R4の途中失敗を含む): rc 非0、Slack `#alerts` へ1通(理由は静的なエラーコードのみ)。
  - 上記の通知が重なるときも1回の実行につき `#alerts` は1通にまとめる。
- **R8 定期実行**: `roles/semaphore_templates/defaults/main.yml` のtemplateカタログと `semaphore_schedules_catalog` へ**同じ変更で**エントリを足す(カタログの「templateとscheduleを同時に決める」契約に従う)。scheduleは毎日 07:00 JST、**`active: false` で足す**。既存scheduleの `active` はreconcileが観測値を保持する(operator-owned。`roles/semaphore_templates/filter_plugins/semaphore_schedules.py`)ため、**有効化はYoshinobuがquoryのSemaphore UIで行う**。手順: reconcileでtemplateとinactiveのscheduleが作られる → templateを手動実行してAC1を確かめる → UIでscheduleを有効にする → カタログの値も `active: true` に揃える変更を別にcommitする(reconcileへの効果は無く、カタログを読む者のため)。時刻の根拠: 土曜の週次パッチ 06:00 の後で、Notion「バッチ処理工程管理表」で06:30〜12:00の窓は quory の軽い確認1本のみ。読み手の定期タスクは07:55に実行される。**scheduleをカタログへ足す変更と同時に、同表へも行を足す**(有効化待ちである旨を併記)。
- **R9 索引と分類**: `playbooks/README.md` に追加する。`# tester-gate: check-mode-native` とする(Notionページの更新は破壊的操作に当たり、`role-guarded` の「副作用がSlack通知のみ」に当てはまらない。同じくNotionへ書く `proxmox_storage_monthly.yml` / `quory_health_monthly.yml` と同じ分類。収集は `--check` でも本実行し、Notion更新だけを `ansible_check_mode` でゲートする)。

## 受入条件

- **AC1** Given 両ノードに到達でき連携が共有済み、When 通常実行、Then rc 0、Slack通知なし。Notionの読み戻しで、ヘッダが `state: complete` / `status: ok`、両ノードが `status: ok`、`kernel` が各ノードの `uname -r` と、`kernel_pkg` が稼働中カーネルの所有パッケージのdpkgの版と、`kernel_installed` がR2の候補集合でDebian版比較した最新と、`pve_qemu_kvm_installed` がdpkgのinstalled版と一致する。
- **AC2** Given 片方のノードが到達不能(decoyで再現)、When 実行、Then rc 0、Slack通知なし。ヘッダは `status: partial`、そのノードは `status: unreachable` で版のキーがすべて `unknown`、もう片方は `ok`。
- **AC2b** Given 両ノードが到達不能(decoyで再現)、When 実行、Then rc 非0、`#alerts` へ1通(本番Slackへは送らず通知captureで観測)、ヘッダは `status: error`。
- **AC2c** Given 片方のノードで版の取得コマンドが失敗する、または出力が解析できない(fixtureで再現)、When 実行、Then そのノードは `status: error`、rc 非0、`#alerts` へ1通。
- **AC1b** Given 複数系列(6.x と 7.x)、メタパッケージ、`-signed` と非signed、`ii` 以外の状態のパッケージが混在するdpkg一覧(fixture)、When `kernel_installed` を選ぶ、Then Debian版比較での最新の実体パッケージの版が選ばれる。`kernel_pkg` と一致するケースと異なるケースの両方で、値がそのまま書かれる。
- **AC3** Given `--check`、`skip_notifications=true`、AIセッションのそれぞれ、When 実行、Then Notionへの送信・トークンファイルの読み込み・Slack送信のいずれも行わず、書く予定の本文全体が出力に表示される。
- **AC4** Given トークンが無効、または書き込み先ページが連携へ共有されていない、When 実行、Then rc 非0、`#alerts` へ1通、通知とログにトークンが出ない。
- **AC4b** Given R4の②または③でNotion APIが失敗する(fakeで再現)、When 実行、Then rc 非0、ヘッダは `state: updating` のまま残る。続けて正常な実行をすると `state: complete` に戻る。
- **AC5** Given applyレポートが無い、または最新のレポートが `result: FAILED` のノード(fixtureで再現)、When 実行、Then 前者は `last_apply_at` / `last_apply_result` / `reboot_done` が `unknown`、後者は `last_apply_result: FAILED` と書かれ、どちらもそれだけではrc 0。
- **AC6** 週次パッチの関連ファイル(`playbooks/proxmox_patch_weekly_full.yml` と import先・`roles/proxmox_patch_apply_node`)に差分が無い。
- **AC7** `playbooks/README.md`、templateカタログ、`semaphore_schedules_catalog`(`active: false`)に追加されている。scheduleの有効化(UI)とカタログを `true` に揃える変更は本案件のcommit後に行う。
