## 検証環境(すべて/tmp配下のscratch。repoへは書いていない)

- decoy inventory 3種。(a) pve1/pve2とも `ansible_connection: local`・`ansible_become: false`。ホストごとにwrapper interpreterで `FAKE_NODE` を切り替え、PATH先頭のfake `uname` / `pveversion` / `dpkg-query` が、モードファイル(ok / cmdfail / badparse)に応じた出力を返す。`dpkg --compare-versions` は実物を使用。(b) pve1=local、pve2=閉ポート(127.0.0.1:1)へのssh。(c) 両方とも閉ポートssh。
- 実行時の環境は `CLAUDECODE` 設定済み(AI抑止が常時効く)。そのためSlackは `[suppressed]` 表示として観測した。トークンパスは存在しないファイルを指定し、読まれれば失敗として現れる構成にした。
- 実行コマンド: `ansible-playbook -i <decoy> playbooks/proxmox_running_versions.yml [--check] [-e skip_notifications=true] -e ..._apply_report_dir=<scratch> -e ..._notion_token_file=<存在しないパス>`、`python3 roles/proxmox_running_versions/tests/test_logic.py`、`--syntax-check`、`scripts/check-tester-gate.sh`、Notion module を差し替えたPython fixture(`t2.py`)。

## 未実施(理由)

- AC1の実値照合、AC4の実トークン・実共有: ansyは実Notion・実pveへの手段を持たないため。
- 通知captureによるSlack送信の観測: 本番Slackへ送らない方針。`common_slack`の抑止表示で件数と本文のみ確認した。
- `become: true`(sudo)での収集、実pveのdpkg出力形式(`dpkg-query -S`が複数パッケージ所有を返すケースなど)、Notion APIの実ページ構造(blocks/children、複数ページ分のページネーション)。fakeでは再現していない。
- Semaphore reconcileの実反映(UI有効化手順を含む)。R8のうちバッチ処理工程管理表への行追加(repo外)。
- R10(Policy表への1行追加)は本工程の対象外で、差分にも無い。

## 初回手動実行(quory)で合否を決める観測点

1. `ansible-playbook playbooks/proxmox_running_versions.yml --check` を先に実行し、本文が出てNotionが変わらないこと。
2. 通常実行でrc 0、Slack通知なし、Notionの固定ページが3つのcode block(ヘッダ、pve1、pve2)で、ヘッダが `state: complete` / `status: ok`。
3. 各ノードで `uname -r` と `kernel`、`dpkg-query -W -f='${Version}' <所有パッケージ>` と `kernel_pkg`、`dpkg-query -W -f='${db:Status-Abbrev} ${Package} ${Version}\n' 'proxmox-kernel-*'` から選んだ最新と `kernel_installed`、`pve-qemu-kvm` のdpkg版と `pve_qemu_kvm_installed`、`pveversion` と `pve_manager` が一致すること。
4. ページが空または管理対象のcode blockだけで始まること(段落等が混在すると `managed_blocks_invalid` でrc 非0になる)。連携未共有のときは `http_404` 相当の静的コードのalertが1通で、トークン文字列を含まないこと。
5. 直近のapplyレポートがある場合に `last_apply_*` がファイル名時刻最新の1件の値と一致すること。
