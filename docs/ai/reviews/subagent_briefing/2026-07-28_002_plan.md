### requirement D2(未symlink 2件)の裏付け — 本Tech Lead自身による一次観測

requirement D2 は「両Skillはharnessのskill一覧に現れない(2026-07-28 Coordinator実測)」としている。**本Tech Lead役subagentの起動時に配られたskill一覧でも、同じ状態を独立に観測した。**

- `.claude/skills/` の相対symlinkは **10件**(`ls -la`。すべて `../../skills/<name>` 形式、git上は mode `120000` で追跡されている)

**ただし欠陥の性質は「到達不能」ではなく「自動検出されない」である。** 両Skillは正本パスで明示参照されており(`docs/ai/roles/reviewer.md` は `document-norm-review` を規範文書レビュー時の必須併用と定め、`docs/ai/role-context-matrix.md` はReviewer列で「着手時必須」としている。`incident-recording` は `docs/ai/roles/techlead.md` の必須Skillと `docs/ai/memory-classification.md` から参照されている)、依頼文でパスを渡せば読める。**壊れているのは `docs/ai/context-classification.md`「Skillの配置とCodex/Claude Codeへの公開方法」が定める公開経路の片方だけ**である。U2の重大度をこの範囲で見積もる。

### requirementが書かなかった因果(Tech Leadの判断)

型の欠落が引き起こしているのは**量の不足ではなく、配分の誤り**である。ゼロから書くたびに、**書かねばならない項目が落ち、書いてはならない項目が増える**。方向が逆の2つの欠陥が同時に出ている。

| 方向 | 何が起きるか | 根拠 |
|---|---|---|
| **書き落とし** | 実行identityと権限境界を書かなかった依頼文で、subagentが承認範囲外へ踏み込んだ。lesson 教訓2 は「**書かれていない境界は、判断の余地として扱われる**」と明示している。2件目の再発 | O3 |
| **書きすぎ(方法)** | 方法を指定した4件すべてで往復が発生。指定しなかった1件では発生しなかった | O4 |
| **書きすぎ(因果)** | 原因を完成形で渡した依頼文があり、Tech Leadが実測で反証した。「未検証・反証可」の断り書きがあっても、完成した因果は検証の出発点を固定する | O5 |

この2方向は独立ではなく、**互いを強化する**。retrospective §4-3 は「失敗するたび指示を細かくしたため、後半の依頼文は1本1,500語規模になり、反響がさらに増えた」と記録している。すなわち**書きすぎは、書き落としに起因する失敗への反応として増える**。

**この因果は、型の設計に直接ひとつの制約を課す。** 章立てだけを定める型では、書きすぎ方向を一切抑えられない。**各章が「書くもの」と「書かないもの」を対で持たなければ、型は片方向にしか効かない。** requirement §4「型の粒度」の決定は、この因果から独立に裏付けられた。

### 型が塞がないもの(残存リスク。Skill本文にも1行書かせる)

lesson 教訓3 と「それでも残る設計則」表は、境界の実効性を3段のラダーで整理している — ①能力の不在(最も強い)②判断を要する制御(classifier / ASK)③文章による依頼。**このSkillが作るのは③である。** 文章はsubagentに解釈される(lesson 本文「存在したのは文章による依頼だけである。文章はsubagentに解釈される」)。

したがってAC1が「型の構造として塞がれる」と言うとき、塞がれるのは**書き落とし**までであり、**解釈による逸脱ではない**。この限界を型の中に書かないと、Skillの存在自体が「境界は担保された」という誤った安心を生む。**AC1の合格をもって権限境界の問題が解決したと読めない形にすること**を、U1の必須要素に入れる。

## 1. オープンクエスチョンへの回答(requirement §9)

### Q2(Tech Leadが決める)— Role別の差分の持ち方

**決定: 独立した1節に、Role×差分の表を1つだけ置く。章立て側はRole非依存にする。**

根拠は2つ。

1. **保守コストが行数でなく箇所数で効く。** 章ごとにRole分岐を書くと、同じ差分が章数だけ分散する。Roleを1つ足したとき(`docs/ai/status.md` Next にOperator役の新設が着手候補として実在する)、全章を掃く必要が出る。これは `skills/document-norm-review/SKILL.md` が欠陥クラスとして持つ「新概念の部分反映」そのものであり、既知の反復欠陥を自分で作り込むことになる。
2. **分量制約と乗算になる。** requirement §4 は既存Skillと同水準(実測 23〜139行)を求めている。章×Roleの二重展開は行数が乗算で増え、水増しを禁じる `docs/ai/core.md` 最終段に抵触する。

### Q1(Tech Leadが提案し、Coordinatorが承認)— 差し戻し時の再起動を型に含めるか

**提案: 含める。ただし章を増やさず、初回用の型に対する「差し替え・追加する項目」を1節(目安5〜10行)で足す形にする。**

根拠は3つ。

1. **規範は既にあるが、形が無い。** `docs/ai/roles/coordinator.md`「入出力と差戻し」は「差戻しは理由と再確認条件を明示したうえで、該当フェーズのsubagentを再起動する」と定めている。何を書くかは決まっているのに、どう書くかの型が無い局面である。
2. **最も劣化しやすい局面が、型の外に残る。** retrospective §4-3 の悪循環(失敗のたび指示を細かくする)は**まさに再起動時に発生する**。初回起動だけを型にすると、書きすぎ方向が最も強く出る場面を型が見ていないことになる。
3. **コストが小さい。** 初回の型を再掲せず差分だけを書けば、追加は1節で済む。

**この項目は計画時点では未決定(U1の未決定1件)であり、Coordinatorがゲートで決める。** 承認されなければU1はこの節を書かない。U1の他の要素はこの決定に依存しないため、単位の分割は不要である。

### W1 — Yoshinobuのcommit(工程上の待ち)

requirement §6 が明示的に計画へ入れるよう求めている。**位置は U3 の Approve 後、クローズ前**。

**性質が前回案件と違う点を明記する。** `docs/ai/roles/coordinator.md`「計画受領時のゲート」#5 の文言は「実ホストへの適用を含む案件のみ」を対象としており、**本案件は文言上その条件に当たらない**(実ホスト適用が無いため、commit前に検証がブロックされる依存が存在しない)。それでもW1を工程へ置く理由は2つ。

1. `docs/ai/core.md`「Git管理されたリポジトリ内容をコードと文書の正本とする」— **commitされるまで、新Skillは正本になっていない。** 作業ツリーだけの状態で「新設完了」と扱うと、次のセッションやquoryから見えない。
2. AC3の検出確認(W2)は作業ツリーのsymlinkでも成立するが、**他のセッション・他のホストで再現するにはcommitが要る**。

**AIはcommit / pushを行わない。** U1〜U3のいずれのsubagentも `git add` までに留める。

### W2 — AC3の検出確認(Coordinator、セッションをまたぎうる)

requirement AC3 が「確認はCoordinatorが行う」と定め、その理由に harness の登録タイミングが版依存であることを挙げている。**この記述は現物で裏付けられる** — `docs/ai/role-routing-index.md`「Agent定義との関係」に「セッション途中に作成した定義が登録されるかは、harnessの版に依存する。2026-07-26には登録されず、2026-07-28の`pmo`追加では同一セッション中に登録された。したがって『次のセッションまで使えない』とも『すぐ使える』とも決め打ちしないこと」とある(対象はagent定義だが、同じ harness の検出機構である)。

**同一セッションで現れない場合、これはクローズのブロッカーにしない。** 未確認のまま次セッションへ持ち越し、確認して記録する。ただし**持ち越すこと自体を `progress.md` へ書く** — 黙って落とすと、Auditorの検査項目「未解決の明示(『やらなかったこと』と理由が書かれているか)」に引っかかる。

## 7. requirementに対する疑義(Coordinatorへ返す)

いずれも実施せず、判断を返す。

### 疑義#1(**要判断・クローズ手続きをブロックする**)— 書込先3パスとクローズ手続きの衝突

requirement §6 は書込先を `skills/`、`.claude/skills/`、`docs/ai/reviews/subagent_briefing/` の**3つのみ**と定め、それ以外を変更した状態で完了報告しないとしている。

一方 AC5 は Auditor の受入を要求し、`docs/ai/roles/auditor.md`「責任・権限」は Auditor の検査項目として次の2つを持つ。

- **2. 状態の正本との突合** — `docs/ai/status.md` の該当行が案件の現況と一致しているか(本案件は status.md Now #1 の「次にやること②」に実在する)
- **3. 実績の記帳の確認** — `docs/ai/effort-baseline.md` へ当該案件が記帳されているか

**この2ファイルはどちらも3パスの外にある。** 記帳しなければ Auditor は不合格を返し、記帳すれば §6 の書込境界に触れる。

**Tech Leadの読み**: §6 の3パスは**実装の書込境界**(U1〜U3のsubagentに課すもの)であって、**Coordinatorのクローズ手続きを縛る意図ではない**と解する。根拠は §6 の続きの文が「§3の非ゴールに当たる変更が必要と判断したら、実施せずCoordinatorへ返す」となっており、非ゴール(既存正本の**規範本文**の改訂)を参照していること — status.md も effort-baseline.md も規範本文ではなく状態・実績の記録である。

**それでも文言はそう書かれていないため、Coordinatorが明示的に判断すること。** 実施はしない。

### 疑義#2(軽微・記録のみ)— `docs/ai/context-classification.md` に §6 が2つある

requirement §4・AC3 が配置規約の正本として「`docs/ai/context-classification.md` §6」を指しているが、**同ファイルには `## 6.` で始まる節が2つ存在する** — 「6. 完了条件の確認」と「6. Skillの配置とCodex/Claude Codeへの公開方法」。意図されているのは後者である。

**本案件の非ゴール(既存正本の規範本文の改訂)に当たるため、修正しない。** ただし U1/U2 のImplementerが「§6」だけを頼りに読むと誤った節に着地しうるため、**依頼文では節番号でなく節タイトル(「Skillの配置とCodex/Claude Codeへの公開方法」)で指すこと**。番号の重複自体は別案件として起票するかをCoordinatorが判断する。

### 疑義#3(軽微・記録のみ)— Auditorの単位の大きさの基準が正本に無い

`docs/ai/effort-baseline.md`「採用する単位」は実行単位を「Implementer / Reviewer / Tester」と定義し、計画・査読単位を基準の対象外としている。**2026-07-28に新設されたAuditorはどちらにも分類されていない。** 本計画では参考値25を置き、層1の基準(80)の適用対象外として扱った。分類の確定は本案件の範囲外。

### 疑義#4(軽微・記録のみ)— 既存Skillの行数レンジ

requirement §4 は既存Skillを「50〜130行」としているが、実測は **23行(`duplication-reuse-check`)〜139行(`delegation-tier`)**。下限も上限も外れている。**運用上の影響は無い**(§4の趣旨は「水増ししない」であり、U1の目標は上限側の130行以内で足りる)。requirementの訂正は求めない。

## 8. 各単位の依頼文に必ず入れる境界

本案件の主題そのものであるため、依頼文自身が §0 の因果に従う。**Coordinatorが依頼文を書く際の必須項目**として申告する。

| 項目 | 全単位共通の内容 |
|---|---|
| **実行identity** | ansy上のリポジトリ作業ツリーのみ。**identityを昇格させない**(`sudo`、`--become-user` を含む) |
| **書込先(結果で書く)** | requirement §6 の3パス**以外のファイルが変更された状態で報告が返ることは受け入れられない**。手段の禁止ではなく到達してはいけない状態として書く(lesson 教訓1) |
| **実ホスト** | doc-only。**実ホストへ触れた状態・Ansibleを実行した状態(`--check` を含む)で報告が返ることは受け入れられない** |
| **git** | `git commit` / `git push` を行わない。`git add` はU3のAC4検証時のみ |
| **安全機構** | ブロックされたら別の形で同じ結果へ到達せず、その事実を報告に含めて返す(`docs/ai/core.md`「安全機構がブロックしたとき」) |
| **方法** | §2 の構造要素(S1〜S9)は契約なので指定する。**それ以外の書き方・章名・順序・語調は指定しない**(O4) |
| **因果** | §0 の因果はTech Leadが現物で確かめた判断として渡してよいが、**反証してよい**旨を添える。U3(Reviewer)には §0 の結論を渡さず、requirement §1 の観測とS1〜S9の契約だけを渡す — 独立照合の出発点を固定しないため(O5) |
| **並行** | U1・U2を同時に立てる場合、§5 の「並行させる場合の必須の依頼文条件」を両方へ書く |
