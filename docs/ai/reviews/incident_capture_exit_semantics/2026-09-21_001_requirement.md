# incident-capture: 成功ジョブの通知を収集エラーにしない — requirement

日付: 2026-09-21 (JST)
状態: 着手前(Yoshinobu承認、2026-09-21)。**初版から方針を変更した。§11を参照。**

## 1. 問題定義

**週に1回、`homelab-incident-capture.service` が `Failed to start` を出す。原因は特定済みである。**

```
09:00:13  SAFE: Syslog weekly digest(月曜 09:00 のschedule)が成功し、
          slack_status = "info" で通知した (roles/syslog_weekly_digest/tasks/main.yml:80)
09:05:05  収集器: "info" は notable (:193) → 失敗したSemaphoreジョブが無く相関先なし
          → collection_errors 1件 (:931-957) → exit 2 (:159) → systemd が Failed to start
```

**実測(2026-09-21、Coordinatorが確認)**: spool記録のIDに埋まった時刻が `2026-09-21 09:00:13 JST`、当日は月曜、`semaphore-query recent-failed` に当日の失敗ジョブは無い(=相関先が存在しない)。直近24時間で288周期中1件が失敗していた。

**収集器は失敗したSemaphoreジョブとしか相関を取らない**(ADR-003 (c)、新しい問い合わせ能力を足さないため)。**したがって、成功したジョブから出た `info` / `warning` 通知には原理的に相関先が無い。** これは収集の失敗ではない。証拠バンドルは作られており、取りこぼしでもない。

**同じクラスに、見るべきものが同居している。** `roles/systemd_timers/files/ansible-timer-failure-capture.sh` は、systemd timerで走ったansibleが失敗したとき `slack_status: "error"` のspool記録を書き、意図的にこの経路へ流す。**この経路はSlackを送らない**(同スクリプト57-59行)。**したがって `Failed to start` は、timer経由の失敗にとって数少ない可視の痕跡である。**

## 2. ゴール

**成功したジョブの `info` / `warning` 通知を、収集エラーとして扱わない。** それ以外の挙動は変えない。

## 3. 非ゴール(今回やらない)

- **終了コードの意味を増やすこと。** 初版はこれを狙ったが、`incident_capture_policy.md` IC-024(収集エラーのある周期は非ゼロ終了しsystemdが `failed` を報告する)と衝突する。**本案では収集エラーを記録しないため、IC-024の文面も終了コードも触らない。**
- **`flock -n -E 75`(多重起動抑止)の扱い。** 24時間で1件も観測していない。
- **相関の仕組み**(失敗ジョブとしか相関しない設計、ADR-003 (c))を変えること。
- **notable判定**(`NON_NOTABLE_SLACK_STATUS`)を変えること。
- **単独バンドルを作らないようにすること。** 証拠は残す。
- 通知経路の追加。**特に、timer失敗経路へSlackを足さない。**

## 4. ユーザーストーリー

運用者として、syslogの `Failed to start homelab-incident-capture.service` を見たときに、**人の対応が要るものだと信じたい。** 毎週決まって出るなら、その行は読まれなくなる。

## 5. 要件

### P0(Must)

| # | 要件 |
|---|---|
| R1 | **相関先が無いspool記録のうち、`slack_status` が `info` または `warning` の2値ちょうどのものだけ、`collection_errors` へ積まない。** 判定は記録を生成する箇所(`incident-capture-collector.py:948`)で行い、後段の文字列prefix照合に依存しない |
| R1b | **免除は明示した2値に限る。** 未知の値、想定外の型、欠落のいずれも**従来どおり `collection_errors` へ積む**(`docs/ai/core.md`「判定できないときは止める」)。「`error` / `critical` 以外を免除する」形にしない |
| R2 | **`error` / `critical` は従来どおり `collection_errors` へ積む。** timer失敗経路(`ansible-timer-failure-capture.sh`)の痕跡を消さない |
| R2b | **免除されたspool記録のバンドルに、後段で別クラスの収集失敗が付いたときは、その周期は従来どおり `2` で終わる。** 免除は相関不一致1件についてだけ働き、バンドル全体を免除しない |
| R3 | **R1の場合も単独バンドルは作り、相関が取れなかった事実と理由(tolerance値を含む)をsummaryへ残す。** 収集エラーではない位置へ置く |
| R4 | **本物の収集失敗は分類に吸われない。** 壊れたspool記録の退避失敗、消費済み記録の削除失敗、snapshot取得時の記録など、`collection_errors` へ積まれる他のクラスは対象外である |
| R5 | **終了コードの定数(0 / 2 / 3)とunit templateを変更しない。** R1に当たる周期は、積むものが無い結果として自然に `0` で終わる |
| R6 | **repo内に自動テストを置く。** `scripts/tests/<case>/` の既存様式に従い、オフラインfixtureだけで完結させる |

## 6. 受入条件

**すべてオフラインfixtureで検証する。実ホスト・Semaphore・本番Slackに触れない。**

| AC | 内容 |
|---|---|
| AC1 | **Given** `slack_status="info"` のnotableなspool記録があり相関先が無い **Then** `collection_errors` は0件、終了コードは`0`、journalへ何も出ない |
| AC2 | **Given** AC1と同じ入力 **Then** 単独バンドルは作られ、summaryに相関が取れなかった事実と理由(tolerance値を含む)が**収集エラーではない位置に**残る |
| AC3 | **Given** `slack_status="error"` で相関先が無い(timer失敗経路の形) **Then** 従来どおり `collection_errors` へ1件積まれ、終了コードは`2` |
| AC4 | **Given** `slack_status="critical"` で相関先が無い **Then** AC3と同じ |
| AC5 | **Given** `info` と `error` の両方が同一周期にある **Then** 終了コードは`2`で、`collection_errors` は `error` の1件だけ |
| AC6 | **Given** 本物の収集失敗(壊れたspool記録の退避失敗など) **Then** 従来どおり `collection_errors` へ積まれ、終了コードは`2` |
| AC7 | **Given** 内部例外 **Then** 終了コードは`3`のまま |
| AC8 | **Given** 変更後のrepo **Then** `EXIT_OK` / `EXIT_COLLECTION_ERRORS` / `EXIT_INTERNAL_ERROR` の値と `incident-capture.service.j2` は変更されていない |
| AC9 | **Given** `semaphore-<id>` 形式のバンドル **Then** 生成内容が変更前と同じ(一次調査 `incident-investigate.py` が走査するのはこの形式のみで、`spool-*` を見ない) |
| AC10 | **Given** `slack_status` が未知の値(例 `"unknown"`)、キー欠落、**および非文字列 — 整数だけでなくJSONのlistとobjectを含む** — のそれぞれで相関先が無い **Then** 従来どおり `collection_errors` へ積まれ、終了コードは`2`(R1b)。**`3`(内部例外)にしない** — 素の集合メンバシップ判定はunhashableな値で `TypeError` を投げるため、そこを通さない形にする必要がある(計画査読 S3) |
| AC11 | **Given** `info` の単独バンドルに、後段でbundle levelの収集失敗(wrapperバイナリ不在、名前付き操作が無い等)が付く **Then** その収集失敗は `collection_errors` に記録され、終了コードは`2`(R2b) |

**配備の申し送り**: 収集器のscriptを変えるため、**repoへ入れただけでは本番に効かない。** `playbooks/incident_capture_setup.yml`(Semaphore template `SEMI-SAFE`)の実行が要る。実行そのものは本案件のscope外だが、要ることを成果物へ残す。

## 11. 初版からの変更(2026-09-21)

初版は「終了コードの意味を分け、unit側で成功扱いにする」案だった。計画査読(`_002`)が **IC-024との衝突をCriticalで指摘**し、あわせて①成功コードに`75`を使うとflock競合まで成功になる②SSH到達不能の分類に関する記述が現行コードと合っていない③文字列prefixだけでは分類を限定しきれない、の3件を挙げた。

**Yoshinobuの判断で、Policyを触らない方向へ切り替えた**(2026-09-21)。相関先が無いこと自体を収集エラーと呼ばないため、IC-024も終了コードもunitも触らない。①②③はいずれも初版の構成に由来する指摘であり、本版では発生しない(①②は該当箇所が無くなり、③は生成箇所での判定に変えた)。

**あわせて、初版に無かった事実を2つ足した** — 発端が月曜09:00の `SAFE: Syslog weekly digest` の `info` 通知であること(§1)と、timer失敗経路がSlackを送らないため `Failed to start` がその痕跡になっていること(§1、RR-1)。
