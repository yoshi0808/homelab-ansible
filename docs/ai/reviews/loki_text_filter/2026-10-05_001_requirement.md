# Loki横断ログ調査に固定文字列の絞り込みを足す — requirement

日付: 2026-10-05 (JST)
状態: 実装・検証済み、配備待ち(方針とAR-096の改訂はYoshinobu了承、2026-10-05)。計画査読 `_002` のMajor L-1→R10/AC8、Minor L-2→RR-3、L-3→R8、推奨→AC9/RR-5を反映済み

## 1. 問題定義

**2026-10-05、Wi-Fiテレビ(`00:16:f5:22:da:86`)の過去の切断を、Lokiから遡って数えられなかった。** 使えるのは `loki-window <job> <since> <window> <level>` だけで、1回に1時間・300行まで、本文で絞れない。同日07:16までは別端末のACL拒否ログが約70行/分あり、300行は4分ほどで尽きた。30日を遡るには1万回近い問い合わせが要る。

あわせて、1行300文字の切り詰めにより、次の2つが読めなかった:

- UniFiのCEFイベント(`job=unifi`)のクライアント名・MACアドレス(行の後半にある)
- u7-1f の `stahtd` が出した `soft failure` の詳細

**本文の絞り込みは、2026-07-29の導入時に「初版に含めない。実運用で必要性が見えたら、正規表現ではなく固定文字列 + 厳格な文字種で検討する」と先送りされていた**(`docs/ai/reviews/slack_loki_investigation/2026-07-29_002_requirement.md` §3・§11、同 `progress.md`)。その後Policy AR-096へは「自由文字列によるlog本文filterを許可しない」という禁止として写された。必要性は今回観測された。

## 2. ゴール

**固定文字列(英数字と `:` `.` `_` `-`、1〜64文字)でLokiのログ本文を絞り込み、1時間より長い範囲を遡れる。** 注入の経路は増やさない。

## 3. 非ゴール(今回やらない)

- **正規表現による絞り込み**(LogQL `|~`)。処理量が入力で爆発しうる
- 既存3語彙(`loki-count` / `loki-window` / `loki-errors`)の引数と挙動の変更(R6のMAX_LINE_LENGTHを除く)
- 出力量の上限(`QUERY_LIMIT` / `MAX_LINES`)の引き上げ
- Operatorの鍵(別案件 `docs/ai/reviews/operator_investigate_key/`)

## 4. ユーザーストーリー

Coordinator・Operatorとして、「この端末・このホスト・このエラーコードが、この期間に何回どこで出たか」をLokiから直接引きたい。

## 5. 要件

### P0(Must)

| # | 要件 |
|---|---|
| R1 | **固定文字列で絞り込む検索語彙を1つ足す**(名前と引数の順はImplementerの判断でよい)。引数は job(既存のjob列挙に、全jobを対象にする値を1つ加える)、since(既存と同じ分精度・JST固定)、window(R3)、絞り込み文字列(R2) |
| R2 | **絞り込み文字列は `^[A-Za-z0-9:._-]{1,64}$` に一致するものだけを受け付ける。** quory側wrapperと対象ホスト側dispatchの双方で独立に検証し(AR-097)、helperもLokiへ問い合わせる前に同じ検証をする。LogQLでは固定文字列一致(`\|=`)だけに使い、正規表現(`\|~`)にしない |
| R3 | **windowは列挙allowlistで、最大7日**(例: `1h` / `6h` / `24h` / `3d` / `7d`)。既存のjob・since・windowの検証の規律に揃える |
| R4 | **出力量の上限は既存のloki-window / loki-errorsと共有する**(`QUERY_LIMIT` / `MAX_LINES`、AR-098)。上限で切り詰めたときの通知形式も既存と同じにする(要求した範囲のどこまで読めたかが分かる) |
| R5 | **`eval` やshellの再解釈を経由しない**(AR-097と既存dispatchの規律)。シェルのメタ文字・改行・空白・クォートを含む値は、どの層でもLokiへ到達する前に `denied:` で拒否される |
| R6 | **`MAX_LINE_LENGTH` を300から1000へ上げる**(既存語彙にも効く)。§1の2件は300文字で読めなかった。行数の上限は変えないため、1回の応答の上限は最大で約3.3倍になる |
| R10 | **配備されるCodex向けの説明 `roles/recovery_exec/templates/AGENTS.md.j2` を同期する。** 新語彙(許可文字・window・全job指定・切り詰め時の扱い)と、既存語彙の1行文字数の上限(1000)を書き、「自由文字列によるlog本文grepには対応しない」等の旧説明を残さない(AR-028の説明同期) |
| R7 | **repo内に自動テストを置く**(dispatch・wrapperの検証、helperのクエリ組立てと検証)。オフラインで完結させる。Lokiへは問い合わせない |

## 6. 受入条件

**すべてオフラインで検証する。実ホスト・Lokiへ問い合わせない。**

| AC | 内容 |
|---|---|
| AC1 | **Given** 絞り込み文字列 `00:16:f5:22:da:86`、`kicked`、`EVENT_STA_LEAVE`、`u7-2f` **Then** wrapper・dispatch・helperの全層で受け付けられ、helperが組み立てるLogQLは `\|= "<値>"` を含み `\|~` を含まない |
| AC2 | **Given** 空文字、65文字、空白、`"`、`'`、`\`、`$(id)`、`;`、`\|`、改行、`*`、`/` を含む値 **Then** 各層が独立に `denied:` で拒否し、helper(またはLokiへの問い合わせ)へ到達しない。wrapperを経由しない直接のdispatch呼び出しでも同じ |
| AC3 | **Given** 許可外のwindow(例 `8d`、`30d`) **Then** `denied:` |
| AC4 | **Given** 全jobを対象にする値 **Then** selectorが全jobに一致し、levelでの絞り込みを含まない(AR-099) |
| AC5 | **Given** 結果がMAX_LINESを超える **Then** 既存と同じ形式の切り詰め通知が出る |
| AC6 | **Given** 既存3語彙 **Then** 引数の検証と出力は変更前と同じ(MAX_LINE_LENGTHの値だけが1000になる) |
| AC7 | **Given** 変更後のAR-096 **Then** R9の文面どおりで、変更履歴に1行ある |
| AC8 | **Given** 変更後の `AGENTS.md.j2` とカタログ§9 **Then** 新語彙が載り、本文grep非対応・300文字上限・`any` だけが唯一の経路といった旧説明が残っていない |
| AC9 | **Given** 新語彙で新たに許す長いwindow(`3d` / `7d`) **Then** 既存の `loki-window` / `loki-errors` のwindow allowlistには入らない |

**配備の申し送り**: `playbooks/recovery_exec_setup.yml` をquoryのSemaphoreで実行する(quoryのwrapperと、authy / monnieのdispatch、monnieのhelper(Lokiを持つtargetだけに配備される)が入れ替わる。実行はYoshinobu)。案件 `operator_investigate_key` と同じplaybookのため、配備は1回にまとめる。配備後、Coordinatorがansyから新語彙でテレビのMACアドレスを7日分検索できることを確かめる。(2026-10-05監査 `_006` A-1を受けCoordinatorが訂正。当初は全4ホストのhelperが変わると読める記述だった)
