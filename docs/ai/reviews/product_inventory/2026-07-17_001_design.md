# ホスト別プロダクト目録（product inventory）— 設計メモ v0

- 日付: 2026-07-17
- 起案: claude（要件定義・ハブ役。本メモは requirement 前の設計たたき台。Codex 未使用＝Claude 直筆）
- 動機: 2026-07-17 の会話「サーバー毎の利用プロダクトを漏れなく（構成ドリフトなく）常に安定最新版で把握する。それが Ansible 構成管理の本来の使い道では」。
- 位置づけ: 小さく刻んで着手する将来タスク（Codex 枠温存のため設計は Claude 主体・実装は最小）。

## 1. 問題設定（守る不変条件）

**すべてのホストの全プロダクトが、〈Ansible が正本を持つ（git 正本＋ドリフト検知）〉か〈policy に既知の管理外として明記〉のどちらかに落ちていて、"誰も追っていない silent gap がゼロ"であること。**

敵は「手動運用そのもの」ではなく「**記録されていない**手動運用」。目録は "何が・どのホストに・どの方式で管理され・現在版は何か" を1枚に束ね、gap を可視化する。

## 2. 管理3クラス（本 homelab の現実。log_observability の議論で確立）

| クラス | 例 | 版追跡の既存手段 | ドリフト/更新の扱い |
|---|---|---|---|
| **A. apt 管理** | alloy / loki / grafana / freeradius / rsyslog / python3 / chrony 等 | 月次 `ubuntu_vm_full_upgrade` + important パターン（REVIEW_REQUIRED） | 月次で候補検知→人間レビュー→手動 apply |
| **B. 非 apt / 手動** | prometheus（手動インストール）等 | 2026-07-17 新設の非apt registry（buildinfo↔GitHub Releases 比較、Status 昇格） | 検知→通知→**更新は人間作業** |
| **C. GUI / アプライアンス** | CloudKey NTP(rsyslogd setting) / Sophos DNS・syslog / UniFi rsyslog 宛先 / pve の手動 rsyslog | policy 文書に管理境界として明記 | Ansible 非対象。設定正本は policy/implement 文書 |

## 3. 現状の部品は散在している（ギャップ）

版・管理方式の情報が repo/memory/policy に分散:

- **A**: `roles/ubuntu_vm_full_upgrade/defaults/main.yml` の `ubuntu_vm_full_upgrade_important_per_node` / `_products` / `_ansible_managed_by`
- **B**: 同 defaults の `ubuntu_vm_full_upgrade_nonapt_per_node`（現状 monnie/prometheus のみ）
- **C**: `docs/ai/prompts/log_observability_policy.md`（rsyslogd/pve 手動）、`reference_proxmox_cli_paths_and_units`、`reference_unifi_ntp_use_ip_not_hostname` 等の policy/memory
- **サービス稼働**: `roles/monitoring_healthcheck`、`roles/recovery_exec` の investigate（版でなく生死）

→ **「このホストに何が載っていて、それぞれどう管理され、今どの版か」を1目で見る統合ビューが無い。** 新プロダクト導入時に「どのクラスにも登録し忘れる」= silent gap の温床。

## 4. 設計案

### 案A: 生成レポート型（read-only インベントリ）
各ホストを走査し「導入プロダクト＋版＋管理クラス」を JSON/通知に出す healthcheck 的 playbook。
- ○ 実態を機械的に採取（宣言と実体のズレが出にくい）／既存 reports/ 基盤に乗る
- × "あるべき姿" の宣言が無いので「本来あるべきものが消えた」ドリフトは検知しにくい

### 案B: 宣言的マニフェスト＋差分チェック型（推奨の核）
repo に「各ホストにあるべきプロダクトと管理クラスの宣言（manifest）」を正本として置き、チェッカが**実体 vs 宣言**を突合してドリフト通知する。
- ○ silent gap を構造的に潰せる（宣言に無い＝未登録を検出、宣言にあるのに実体に無い＝消失を検出）
- ○ 3クラスを1つの manifest スキーマで表現でき、A/B/C の既存部品を**参照統合**できる（重複定義でなく単一正本へ寄せる）
- × 初期の宣言作成コスト（ただし既存 defaults/policy から機械的に集約可能）

### 案C: 既存 nonapt registry の拡張
#3 で作った `nonapt_per_node` の構造を「全クラスのプロダクト manifest」へ一般化し、`ubuntu_vm_full_upgrade` の月次に相乗り。
- ○ 通知経路が一本化済み（prometheus 方針＝月次相乗りと整合）／新規 playbook 不要
- × ubuntu_vm_full_upgrade は Ubuntu VM 対象。pve/appliance(C) までカバーするとスコープが肥大。目録は「観測範囲が全ホスト」なので置き場所として最適ではない可能性

## 5. 推奨と増分（小さく刻む）

**方向: 案B の思想（宣言的 manifest＋ドリフト差分）を、案C の通知一本化に乗せる。** ただし一括構築せず増分で:

1. **増分1（Claude 主体・Codex ほぼ不要）**: 現状の散在情報を集めて **静的な "product manifest" ドキュメント1枚**を作る（ホスト×プロダクト×クラス×管理場所×版追跡手段の表）。これだけで人間の "把握" は達成でき、silent gap の棚卸しにもなる。実装ゼロ。
2. **増分2**: manifest を機械可読な `defaults` 変数（`homelab_product_manifest`）へ移し、A/B の既存 registry をそこへ**参照統合**（重複を単一正本へ）。
3. **増分3**: 実体採取チェッカ（read-only）で "宣言 vs 実体" を突合し、未登録/消失/版差を月次通知に出す。C（GUI/appliance）は "宣言のみ・実体採取は best-effort or 手動確認" として扱う。

## 6. 未確定の論点（Yoshinobu 判断）

- 目録の**置き場所**: `ubuntu_vm_full_upgrade` 相乗り（通知一本化）か、独立 role/playbook（全ホスト＝pve/appliance も自然にカバー）か。
- **C の実体採取をどこまで自動化するか**（GUI 設定は Ansible で読めない。宣言＋手動確認に留めるのが現実的か）。
- 「安定最新版」の定義: 案B の版追跡を **latest そのまま**でなく **"レビュー付きで意図的に上げる"**（important パターン→REVIEW の思想）に揃える点は log_observability の教訓どおり。
