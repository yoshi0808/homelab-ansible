# requirement: quory の Semaphore を定期的に退避する

案件: `semaphore_db_backup`
作成: 2026-08-17 / Coordinator

## 1. 問題定義

**quory は VM ではないため、Proxmox のバックアップに乗らない。** 他の管理対象(monnie / ansy / sandbox)が VM として日次・週次で保護されているのに対し、本番の制御平面である quory だけがその外にある。

**Git が持っているものと、持っていないものを取り違えない。** **template と schedule は Git にある** — `roles/semaphore_templates/defaults/main.yml` のカタログが正本で、schedule は `semaphore_schedules_as_code` 案件(2026-08-10 クローズ)で入った。実行パラメータ(`task_params`)も同じエントリが持つ。**したがって「いつ何が押されるか」は reconcile で戻せる。**

**Git に無いのは次である。**

| 失うもの | 戻せるか |
|---|---|
| users(アカウント、API token) | 戻せない。作り直し |
| task の実行履歴 | 戻せない |
| access key の実体(暗号化されて DB 内) | 戻せない。`config.json` の鍵とセットでのみ復号できる |
| inventory / repository / environment のオブジェクト定義 | 戻せない。**カタログはこれらを名前で参照するだけ**で、定義そのものを持たない |
| project 自体 | 戻せない。**これが無いと template も schedule も適用先が無い** |

**最後の行が効く。** カタログは既存の project に対して reconcile するものであり、project ごと失われた状態から自力では立ち上がらない。

**そして現在の退避は手作業1回きりである。** 2026-08-04 に ansy の Semaphore を「quory のバックアップからの復元」で立てた実績があり、それが唯一の記録である。定期的に取る手段は無い。

## 2. ゴール

1. **quory の Semaphore の状態を、定期的に quory の外へ退避する。**
2. **退避物だけで、Semaphore が起動する状態まで戻せる。**
3. **新しい仕組みを1つも増やさない。** 実行経路・保存先とも、既に動いている `unifi_backup_fetch`(quory の Semaphore から起動 → pve が Synology NFS へ書く)の形へ揃える。

## 3. 非ゴール

- **自動リストア。** 戻す操作は人が行う。本案件が用意するのは退避物と手順だけである。
- **quory 全体のバックアップ。** 対象は Semaphore に限る。
- **退避物の暗号化。** NAS の当該フォルダは pve のみがアクセスできる(Yoshinobu、2026-08-17)。
- **SSH 鍵そのものの退避。** Semaphore の backup 対象外であることが quory → ansy の取り込みで確認済みで、鍵は Bitwarden と外部媒体にある(Yoshinobu、2026-08-17)。
- **schedule / template の Git 管理。** `semaphore_schedules_as_code` で既に済んでいる。本案件はそこへ手を入れない。
- **退避が止まったことを検知する仕組み。** §7 Q3 に論点として残す。

## 4. ユーザーストーリー

- Yoshinobu として、quory が失われたときに **Semaphore を作り直すのではなく戻したい**。どの template がどの schedule で動いていたかを思い出す作業をしたくない。
- Yoshinobu として、**バックアップの取得そのものに手をかけたくない**。押すのは復元のときだけでよい。
- Coordinator として、**退避物に何が入っていて何が入っていないかを記録から読めるようにしたい**。復元の場面で「これで足りるのか」を推測したくない。

## 5. 要件

### P0(初回実装に不可欠)

| # | 要件 |
|---|---|
| **R1** | 退避対象は3つとする — `/var/lib/semaphore/semaphore.db`、`semaphore projects export` の JSON、`/etc/semaphore/config.json`。**3つが揃って1世代**である |
| **R2** | **DB は一貫スナップショットとして取る。** `semaphore.db` は `journal_mode=delete`(WAL でない)ため、稼働中の `cp` は中途状態を掴みうる。`sqlite3 ".backup"` を使う |
| **R3** | 保存先は Synology NFS とし、**書き込みは pve ノードが行う**。実行ノードの選定は `roles/proxmox_exec_node`(pve1 優先、pve2 フォールバック)に委ね、本案件で選定ロジックを持たない |
| **R4** | 保存先への確定は**原子的 rename** で行い、世代ローテーションを持つ。既定は日次・30世代 |
| **R5** | **`config.json` の内容を、ジョブ出力・Slack 通知・レポート・変数へ出さない。** Slack Webhook URL を含む。運ぶのは不透明なファイルとしてのみで、保存先でのモードは `0600`・所有は root とする |
| **R6** | 結果を Slack へ通知する。成功 = info/ok、失敗 = alerts/error(`common_slack` の既存規約に従う) |
| **R7** | **終了コードは、3点すべての退避と確定が成功したときだけ `0`**。1つでも欠けたら非ゼロで終わる。Semaphore は終了コードで成否を判定するため、部分的な成功を成功として返さない |
| **R8** | **quory に `sqlite3` が無い場合、理由の分かるメッセージで停止する**(§7 Q1)。存在を仮定して失敗させない |

## 6. 成功指標

- 定期実行が緑で続き、保存先の世代が日ごとに増えている。
- **復元が1回成功する。** 退避物だけを使って、別インスタンス(ansy)で Semaphore が起動し、template と schedule が読めること。これが実質的な唯一の指標である。

## 7. オープンクエスチョン

- **Q1: quory の `sqlite3`(2026-08-17 クローズ)。** **入っている。版は 3.46.1、64-bit で ansy と同じ。** Operator への照会で確認した(OPRES `req-20260817T192701+0900-c2f0209b146bc183`)。**パッケージを足す分岐も、`projects export` だけへ縮退する分岐も消えた。** R8 は要件として残す — 実行時の前提確認であり、確認済みであることは前提が将来も成り立つことを意味しない。
- **Q2: 頻度と世代数。** **quory の `semaphore.db` は 51,474,432 bytes(約 49.1 MiB)**(同 OPRES)。ansy 側の 648KB に対して約80倍で、ほぼ task の実行履歴とその出力である。**日次・30世代で保存先の消費は約 1.5GB。** 圧縮は入れない(復元の手数が増えるのに対し、この規模では見合わない)。変えるなら role の変数1つ。
- **Q3: 退避が止まったことに気づく手段が無い。** schedule が UI で無効化されれば何も起きず、失敗通知も出ない(そもそも走らないため)。カタログは `active: true` を持つので **`--check` の reconcile なら差分として見える**が、**reconcile 自体は schedule カタログの19件に入っておらず、人が押したときにしか走らない**(2026-08-17 確認)。これは本案件に固有の穴ではなく、19件すべてに同じ形でかかっている。**今回は作らない** — 検知を1つ足すより先に、この種の「乱立」をどう整理するかの判断が要る(`docs/ai/status.md`「載せていないもの」、2026-08-07)。**必要と判断されたときの起点としてここに残す。**

## 8. タイムライン考慮

- **本 playbook の template と schedule は、どちらもカタログへ書いて reconcile で入る**(R10)。UI での手作業は要らない。
- 配備 playbook の実行は quory の Semaphore から行う。ansy から quory へは到達手段が無い。

## 9. 受入条件

**AC1(正常系・退避)**
Given quory の Semaphore が稼働しており、pve1 が到達可能である
When `playbooks/semaphore_db_backup.yml` を quory から実行する
Then 保存先に**新しい世代が1つ増え、その中に3ファイル(`semaphore.db` / export JSON / `config.json`)が揃っている**。playbook の**終了コードは `0`**。Slack の info/ok へ1通届く。**`config.json` の内容はジョブ出力のどこにも現れない**

**AC2(実行ノードのフォールバック)**
Given pve1 が到達不能で pve2 が到達可能である
When 同上
Then **pve2 へ書かれ、終了コードは `0`**。「pve1 が到達不能だったこと」が summary から読める。Slack は info/ok

**AC3(世代ローテーション)**
Given 保存先に既定世代数の世代が存在する
When 同上
Then **最も古い世代が削除され、総数が既定値を超えない**。削除された世代名が summary に出る

**AC4(DB の一貫性)**
Given Semaphore がジョブを実行中である(DB への書き込みが発生している)
When 同上
Then 退避された `semaphore.db` が**単体で開けて `PRAGMA integrity_check` が `ok` を返す**。終了コードは `0`

**AC5(異常系・`sqlite3` 不在)**
Given 対象ホストに `sqlite3` が存在しない
When 同上
Then **退避を1つも作らずに停止し、終了コードは非ゼロ**。停止メッセージに「`sqlite3` が無いこと」と「それが必要な理由」が出る。Slack は alerts/error

**AC6(異常系・保存先へ到達できない)**
Given pve1 / pve2 のいずれも到達不能である、または NFS マウントが無い
When 同上
Then **中途半端な世代を保存先へ残さず**(確定は原子的 rename のため)、**終了コードは非ゼロ**。Slack は alerts/error

**AC7(復元)**
Given AC1 で作られた世代がある
When 3ファイルを ansy の Semaphore へ戻し、サービスを起動する
Then **Semaphore が起動し、template と schedule が UI / API から読める**。この検証は ansy 上で行い、quory へは触れない
