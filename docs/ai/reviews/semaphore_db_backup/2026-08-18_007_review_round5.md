# Code Review: semaphore_db_backup round5

## Summary

round4 High #1とSuggestions #1/#2、全quory delegate、UNREACHABLE matrix、残存リスクを再照合した。通常のPhase 1、Phase 2後半、Phase 3、cleanup自身のUNREACHABLEは明示assertで通常failureへ戻り、role `always`・外側`rescue`・rc非ゼロへ到達する。旧fixtureのdecoy用語もcore.mdへ整合した。

ただしPhase 2先頭tempfileの検査位置に1件の漏れがあり、集約assertより前にunreachable結果の`.path`を参照する。またpve実行ノードの途中喪失は「task属性では扱えない」障害ではなく、Ansible controllerであるquoryは生存しているため同じ方式で扱える。R6通知と機密cache cleanupを欠く既知経路としてTesterへ渡すだけでは受け入れられず、Request Changesとする。

## What Looks Good

- Phase 1 statは`ignore_unreachable`直後に専用assertがあり、`.stat.exists`参照前に判定不能を通常failureへ戻す。
- Phase 2の5 registerとPhase 3の3 registerはすべて予約変数リストに入り、extra-varsによる結果偽装を拒否する。Phase 2先頭tempfileを除けば、各UNREACHABLEは既存assert/通常failureまたは集約assertへ収束する。
- Phase 3は3 fetchすべてを実行後にaggregateし、いずれかの`is unreachable`を検出するとrole `always`へ進む。`ignore_unreachable`が示す`is success=True`を成功根拠に使う箇所はない。
- cleanupのquory taskは`ignore_errors`と`ignore_unreachable`を分けて持ち、最終assertも`is failed` / `is unreachable`の双方を見る。通常failure・connection failureのどちらも後続controller/staging cleanupを妨げず、最後にrun failureへ戻る。
- 閉loopback matrixはcleanup自身、本体途中、Phase 1初回接触を分け、後続task、role `always`、外側`rescue`、rc=2を観測している。fixtureはcore.mdのdecoy 3条件に整合する。
- round4 Suggestions #1/#2はclosed。round2の旧runを「実接続しなかった非適格fixture」、round3以降をcompliant decoyとして区別し、`-i /dev/null`が第2条件の根拠ではないことも明記した。
- 多層エスケープ、command rcのno-match吸収、`--check`でのみ未評価になる新規分岐は今回差分にない。既存`argv`、機密の`no_log`、`roles/proxmox_exec_node` / `roles/common_slack`再利用も維持される。
- Semaphore/cert_renewの規範訂正に、意味変化・条件緩和・撤回した旧規範の再導入はない。
- `scripts/check-tester-gate.sh`は`OK (56 playbooks)`、`git diff --check`はrc 0。
