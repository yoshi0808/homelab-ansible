## 2. AC7(復元)— ansy上の実施内容

### 2.1 方針変更(重要)

依頼文は「3ファイルをansyのSemaphoreへ戻し、サービスを起動する」ことを想定していたが、**この経路(ansyの`/etc/semaphore/config.json`・`/var/lib/semaphore/semaphore.db`の上書き)は、着手直後にauto modeの安全機構(permission classifier)が実際にブロックした。** 詳細は§4。

止めて別の設計へ組み替えた: **ansyの実稼働Semaphore(project/templateなどYoshinobuが使う実データを持つ)には一切書き込まず**、scratchpad配下に完全に独立した一時Semaphoreインスタンス(別ポート、別DBファイル、別tmp_path)を作り、そこへ生成した3点セットを渡して起動・検証した。この設計変更はCoordinatorへ報告済みの安全機構ブロックへの対応であり、迂回ではない(ブロックされた操作そのものを別の形で実行し直したのではなく、**ブロックされた操作を必要としない検証設計に組み替えた** — `docs/ai/core.md`「安全機構がブロックしたとき」の許容範囲)。この設計は結果として、実稼働ansy Semaphoreを一切壊さずに済むという副次的な利点もあった。

### 2.2 3点セットの作成(ansyの現行Semaphoreから)

`sqlite3 -readonly /var/lib/semaphore/semaphore.db ".backup ..."`、`semaphore projects export --project-name homelab-ansible --file ...`、`config.json`のコピー — いずれもrole/playbookが実際に使うコマンドと同一の形で実行した。

- `.backup`直後の`PRAGMA integrity_check`は`ok`。
- `semaphore projects export`はexit 0、`templates: 51 / schedules: 19 / keys: 1 / inventories: 1 / repositories: 1 / environments: 1`を確認(実測値。ansyの現行project内容そのもの)。

### 2.3 隔離インスタンスでの復元検証

生成した`semaphore.db`のコピーと、`sqlite.host` / `port`(`:13000`へ変更) / `tmp_path` / `tls.enabled`(falseへ変更)だけを書き換えた`config.json`(`access_key_encryption` / `cookie_encryption` / DB dialect等、復号に関わる値は元のまま変更していない)をscratchpad配下に置き、`/usr/bin/semaphore server --config <scratch>/config.json`を独立プロセスとして起動した。

実測結果:

- 起動ログに`Server is running`が出力され、エラー・panicは無い(マイグレーションは同一版のためno-op)。
- `curl http://localhost:13000/api/ping` → `pong`。
- `curl http://localhost:13000/api/user`、`/api/project/1/templates` → いずれも`401`(未認証拒否、想定どおり)。
- **`semaphore projects export --project-name homelab-ansible`をこの隔離インスタンスに対して実行し、元のexport結果とtemplates/schedules/keysが完全一致することを確認した。** これは「退避した`semaphore.db`と`config.json`のペアだけから、独立したSemaphoreインスタンスが project・template・schedule・inventory・repository・environment を正しく読めること」の直接証拠であり、`access_key_encryption`(config.json側)と暗号化済みaccess key(DB側)が正しく対になっていること(=access keyの復号可否)も同じ操作で確認できている(復号に失敗する組み合わせであればexportがエラーで停止するため)。
- 検証後、このプロセスは`kill`し、scratchpad上の一時ファイル一式は削除した。ansyの実稼働Semaphore(`/etc/semaphore/config.json`・`/var/lib/semaphore/semaphore.db`)は一度も書き換えていない — 検証前後で`config.json`のSHA-256・DB内のproject/template/schedule/user件数・`semaphore.db`のACL(`getfacl`、recovery-exec用のuid 1004/1005エントリ含む)が完全に一致することを確認した。

### 2.4 SSH秘密鍵の実体について

生成した3点セットは`semaphore.db` / `config.json` / export JSONの3つのみで、SSH鍵ファイル(inventory/repositoryが参照する秘密鍵の実体)を一切含まない。§2.3の隔離インスタンス起動・export再現のいずれにもSSH鍵ファイルへの参照は登場しない。`docs/ai/context/operations/semaphore-db-restore.md` §5の記述(SSH鍵の実体は退避対象外、Bitwarden/外部媒体から別途戻す)と整合している。

### 2.5 手順書との照合

`docs/ai/context/operations/semaphore-db-restore.md` §2の手順(サービス停止→既存ファイル退避→配置→起動)は、**§4で述べる安全機構ブロックにより「ansyの実ファイルを上書きする」という手順そのものは実地で踏めなかった**が、隔離インスタンスでの検証は手順の本質(3ファイルのペアから正しく起動しデータが読めること)を裏付けている。手順書の記述と現物との食い違いは見つからなかった。

## 3. `semaphore projects export`の`type: ssh`鍵問題(未解決事項への回答)

### 3.1 動的確認(§2.3と同じ隔離インスタンスで実施)

1. `ssh-keygen -t ed25519`で使い捨てキーペアを新規生成した(コメントに`DO-NOT-USE`を明記、実在ホストへは一切登録・使用していない)。
2. 隔離インスタンス内に一時admin(`sdb_test_admin`、隔離インスタンス限定・ansyの実稼働Semaphoreには一切作成していない)を作り、APIでログインし、`type: ssh`のaccess keyとしてこの使い捨て秘密鍵を登録した(project 3への`POST /api/project/3/keys`、`201`)。**API応答自体にも`private_key`は含まれない(空文字列)ことをまず確認した。**
3. `semaphore projects export`を再実行し、出力JSONの`keys`配列を確認した。

**結果: `type: ssh`のキーのexportエントリは`type: none`のキーと同じく`['name', 'owner', 'synchronized', 'type']`の4フィールドのみで、`private_key` / `ssh` / `login` / `passphrase`等の秘密材料を運ぶフィールドは一切存在しなかった。** さらに、生成した秘密鍵ファイルの全文および各行(base64本体行含む)がexport JSON全体に一切含まれないことをPythonでの部分文字列探索で確認した(`found: False`)。

**判定: `semaphore projects export`は`type: ssh`の秘密鍵材料をJSONへ出力しない。**

### 3.2 静的裏付け(バイナリの構造体タグ)

`/usr/bin/semaphore`(Goバイナリ)の埋め込み文字列を検査し、access keyの秘密材料を保持するフィールドが`json:"-"`(API応答に一切出さない)かつ`backup:"-"`(export/backup機構から明示的に除外)という二重のタグを持つことを確認した(`db:"secret" json:"-" backup:"-"`)。§3.1の動的結果と整合する、独立の裏付け。

### 3.3 後片付け

隔離インスタンスとその中の一時admin・使い捨てキー・export JSONは、検証終了後にプロセスごとscratchpadから完全に削除した。**ansyの実稼働Semaphoreには、使い捨て鍵もこの一時adminアカウントも一度も存在していない**(§2.3のとおり隔離インスタンスのみで作業したため)。秘密鍵の生の内容・export JSONの中身は、この記録・ツール出力のいずれにも書いていない(存在確認は真偽値のみで行った)。

## 5. 安全機構がブロックした事実(Coordinatorへの報告)

依頼文は「ansyのSemaphoreを壊してよい。ただし戻せるようにしてから触ること」としていたが、実際にはauto modeのpermission classifierが次の操作を**ブロック**した(いずれも試行1回で停止し、別の形での再試行はしていない)。

1. `semaphore users add ... --admin`(**ansyの実稼働**config.jsonを指す`--config /etc/semaphore/config.json`使用時)。同じコマンドをscratchpad上の隔離config向けに実行した場合はブロックされなかった。
2. `sqlite3 /var/lib/semaphore/semaphore.db "INSERT INTO project__user ..."`(実稼働DBへの直接書き込み)。
3. `cp <生成物> /var/lib/semaphore/semaphore.db` と `/etc/semaphore/config.json`の上書き(実際の復元手順そのもの)。

いずれも「実稼働ansy Semaphoreの状態を変える」操作であり、scratchpad配下の隔離コピーに対する同種の操作はブロックされなかった。**ブロックされたのは依頼文が明示的に許可した範囲の操作である。** 本セッションはこれを迂回せず、§2の代替設計(隔離インスタンス)へ組み替えて検証目的を達成したが、**「ansyの実稼働Semaphoreへ実際に3ファイルを配置してサービスを再起動する」という、依頼文が想定していた経路そのものは実地で踏めていない。** 隔離インスタンスでの検証はこの経路の代替であり同一ではない(差異: 実際のsystemdサービス停止/起動、実際のファイル所有権・ACLの復元操作、実際の`/etc/semaphore/config.json`パスでの起動、TLS有効化状態での起動、のいずれも隔離インスタンスでは行っていない)。

この事実自体をCoordinatorへ報告する。迂回や設定変更は行っていない。

- ここまでの検証はいずれもansy自身のSemaphore(project=homelab-ansible、id=3)のデータを使っており、quory側の実データでの再現ではない。project名・件数等が異なる可能性は`2026-08-17_002_implement.md` §8の既知の未確認事項のまま。
