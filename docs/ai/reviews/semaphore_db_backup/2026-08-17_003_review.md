# Code Review: semaphore_db_backup

## Summary

R1〜R11 / AC1〜AC7、実装記録、対象8ファイルの未commit差分、接続先の既存role、Semaphore System / Operations Context、Ansible Test Safety Policyを照合した。3点セットの通常経路、`proxmox_exec_node`再利用、NFS mount判定、原子的rename、カタログ追加の基本構造は要件に沿うが、外部変数からroot権限の削除先を差し替えられる経路と、実失敗をrc 0へ吸収できる経路があるため、この状態では受入不可である。

## What Looks Good

- R3の実行ノード選定は`roles/proxmox_exec_node`を再利用し、独自の到達性・優先順位ロジックを重複実装していない。pve1/pve2の結果もsummaryへ残る。
- `findmnt`は`failed_when: false`の後でrcとstdoutの両方をassertしており、「mountなし」と「判定不能」を成功へ落としていない。rc規約上、no-match/nonzeroはいずれもfail-closedになる。
- DBは`sqlite3 .backup`後に`PRAGMA integrity_check == ok`を確認し、3ファイル配置後に同一filesystem内の`mv -T`へ進む。通常経路では確定前のstagingと確定済み世代が区別される。
- shell moduleを使わず、外部値を渡すcommandは`argv`形式である。Jinja→shell→regex等の危険な多層エスケープは対象差分に見当たらない。`lookup('pipe')`のcommandは静的文字列だけで、外部変数を補間していない。
- `config.json`を扱う明示taskには`no_log: true`があり、Slack summaryへ内容を入れていない。最終保存modeも`0600`である。ただしcontroller中継の保護はCritical #3が未解決。
- Play 2には変更前の`ansible_check_mode`停止assertがあり、role blockは`check_mode: false`である。`scripts/check-tester-gate.sh`は`OK (56 playbooks)`。ただしCritical #1によりrisk-accepted条件1の最悪ケース説明が現実と一致しないため、修正後に分類理由を再照合する必要がある。
- templateとscheduleは同じ差分で追加され、render後template名とschedule参照名が一致する。新cronは既存カタログ内で重複せず、closed-world flagを降ろしていない。
- `docs/ai/context/system/semaphore.md`と`docs/ai/policies/cert_renew_policy.md`の訂正は、現行`semaphore_schedules_catalog`（cert_renewのcronと`task_params.environment.force_renew`を含む）と一致する。liveなContext/Policy/Role/Skill/実装コメントを撤回文言で機械検索し、「scheduleがrepo外」とする旧境界の残存は検出しなかった。規範本体の安全境界・責任主体の消失や緩和も見当たらない。
