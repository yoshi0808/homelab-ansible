# Test: Semaphore upgrade native check mode(ansy実機、native --check診断)

作成: 2026-09-07 / Tester
契約: `2026-09-06_001_requirement.md` / 計画: `2026-09-06_002_plan.md` / 実装: `2026-09-06_004_implement.md` / レビュー: `2026-09-06_005_review.md`、`2026-09-06_006_review.md`(いずれもRe-review Approve)

## 承認scope

Coordinatorから明示された範囲のみ実施した。

- 対象: `ansy` 1hostに対する `playbooks/semaphore_upgrade.yml` のnative `--check` 診断(upgrade check / rollback check)。
- 使用wrapper: `scripts/safe-ansible-check.sh`(`--check` 付け忘れを機械的に防ぐ、TS-024)。
- 対象外: 通常upgrade/rollback(`--check`なし実行)、`quory`その他の実ホスト、package取得/download/backup作成、production Slack到達。
- consumer reading path(`homelab-semaphore-query` / token)はansyに意図的に存在しない環境であるため、`-e skip_reading_path_check=true` による明示skip経路を検証した。reading path「有り」側の分岐はansyでは構造的に検証不能であり、既存レビュー(`2026-09-06_006_review.md` Re-review)がstub fixtureで確認済み。

## 実測と推測の区別

- **実測**: T1〜T6のrc、diagnostic出力、backup/work root不変、result file/semaphore.db不変、service再起動なし、consumer reading path不在の事実。すべて上表のコマンドをansy上で自分で実行して得た。
- **推測を含まない**: 「reading path無し環境で確実にskip経路へ入る」という主張は、コード条件(`length == 2`必須)とバイナリ不在の実測を根拠にしており、憶測ではない。
- **推測(コードの読解に依拠、非実測)**: T5/T6で「診断・変更経路のいずれにも到達しない」という説明は、`main.yml`のtask順序を読んだ判断であり、`--tags destructive`等の組み合わせまでは本Testerは再実行していない(Reviewerが`006_review.md`で実測済み)。

## 未実施事項・残存リスク

1. **consumer reading path「有り」側の実機検証は本Testerでも未実施。** ansyは意図的にこの経路を持たないため構造的に検証不能。Reviewerがstub fixtureで消費側ロジックの成立を確認済みだが、実物の`homelab-semaphore-query`出力形式との一致は示されていない(`006_review.md`未確認事項に既出)。**quoryでの初回`--check`実行が、この分岐の実データに対する最初の検証になる。**
2. **AC3/AC4(通常実行)、AC6(複数host拒否)、AC7〜AC10は本案件のTester工程では未実施。** 承認scopeの範囲外であり、それぞれRe-review Approve済みのReviewer記録(静的照合・decoy実測・lint)を根拠として引き継ぐ。
3. **AC8(実template観測)は本Testerの実行手段の外。** requirement §8 Step 5どおり、quory側でのtemplate catalog reconcile後にCoordinator/Yoshinobuが観測する。
4. rollback候補として実データ `2.19.8-pro` が選択された。これはansy上の過去の実運用/検証活動(2026-09-05の版上げ操作)が残した実transactionであり、本Testerが作成したものではない。値の意味(edition `pro`)は本案件のscope外であり、本Testerは追加調査していない。
5. 実行環境固有の制約: このシェルの標準入出力がnon-blockingに設定されており、`ansible-playbook`が起動直後に`ERROR: Ansible requires blocking IO`で失敗する事象があった。`| cat`で標準出力をパイプすることで回避した(fdがblockingになる)。実行結果・rcには影響しない技術的回避であり、diagnostic自体の内容を変えていない。

## 結論

Coordinatorが承認したscope(ansy 1hostのnative `--check`診断、explicit skip経路)について、upgrade check・rollback checkの双方でrc=0、P0-4が禁止する副作用(backup/work directory作成、`.deb`保存、DB/config/binary退避、transaction/result/marker書込み、package/service操作、detached起動、Slack送信)が実測でゼロ件であることを確認した。旧`dry_run`引数は`--check`下でも実機で確実に拒否される(rc=2)。承認scope外のAC(AC3/AC4/AC6/AC7〜10)はReviewer記録を引き継ぎ、本Testerでは再実行していない。reading path「有り」側の実データ検証はquoryでの初回実行まで残存リスクとして持ち越す。

対象実装ファイルは1つも変更していない。本ファイルおよびこのテストコマンドの実行以外にrepo状態を変えていない(着手前後の`git status --short`は本ファイル追加以外差分なし)。
