# requirement: Semaphore upgrade の Dry Run を Semaphore UI 標準へ統一する

作成: 2026-09-06 / Coordinator
前案件: `docs/ai/reviews/semaphore_upgrade_automation/`、`docs/ai/reviews/semaphore_upgrade_detach_reporting/`

改訂: 2026-09-06 / 計画査読Suggestion #1を受け、P0-7とAC6へ単一host guardを
通常実行・`--check`の双方に適用することを明記した。

## 1. 問題定義

`UN-SAFE: Semaphore upgrade (apply)` と `UN-SAFE: Semaphore rollback` は、
Semaphore 自身の Dry Run (`ansible-playbook --check`)とは別に Survey Variable
`dry_run` を持つ。同じ画面に同名・別意味の入力があり、2026-09-06 のジョブ
#984 では Semaphore 側の Dry Run を選んだ結果、role が preparation 全体を
短絡して、実質的な検査をしないまま緑で完了した。

独自 `dry_run=true` は DB・config・binary の退避、`.deb` の取得、transaction
metadata の書込みを行うため、「状態を変えない」という Semaphore 側 Dry Run
の意味とも一致しない。

さらに `roles/semaphore_upgrade/tasks/main.yml` の rollback include は
`ansible_check_mode` と `rollback` だけで判定し、独自 `dry_run` を参照しない。
そのため Survey で `dry_run=true` を指定しても、Semaphore 側 Dry Run がオフなら
実 rollback へ進む。実際にこの組合せで本番 rollback を行った事実は未確認である。

リポジトリ全体では独自 `dry_run` を持つ playbook が3本あるが、本案件は schedule
を持たず手動実行だけの `semaphore_upgrade.yml` に限定する。

## 2. ゴール

1. Semaphore upgrade / rollback の dry-run 操作を Semaphore UI 標準の Dry Run
   だけに統一する
2. UI Dry Run で状態を変えず、実行可否の判断に使える診断結果を得る
3. 通常実行の upgrade / rollback と、UI Dry Run の境界を1つの
   `ansible_check_mode` で決める
4. 旧 `dry_run` を渡す呼出しを黙って apply として扱わない

## 3. 非ゴール

| やらないこと | 理由 |
|---|---|
| `prometheus_update_check.yml` の `dry_run` 整理 | 稼働中の週次 schedule と update Policy に影響するため別案件 |
| `ubuntu_vm_full_upgrade.yml` の `dry_run` 整理 | 稼働中の月次 schedule と複数hostの参加条件に影響するため別案件 |
| Semaphore upgrade の版・edition・checksum更新 | Dry Run入口の統一とは独立した変更 |
| detached transaction、再起動後検証、自動rollback、通知文面の再設計 | 前2案件で確立した本実行経路を維持する |
| Semaphore upgrade のschedule追加 | 本playbookは引き続き手動実行に限定する |
| Policy本文の変更 | `check-mode-native` の既存規範で要求を表現できる |

## 4. ユーザーストーリー

- Semaphore UI利用者として、Dry Runをオンにすれば標準どおり状態を変えずに
  upgrade / rollback の事前診断ができ、同名のSurvey入力に迷いたくない。
- CLI利用者として、dry-runは `--check` だけで選び、通常実行との境界を
  他の `check-mode-native` playbookと同じ形で理解したい。
- 運用者として、古い `-e dry_run=...` が残っていた場合、それが無視されて
  意図しないapplyへ進むより、明示的に停止してほしい。

## 5. 要件

### P0 (Must)

| # | 要件 |
|---|---|
| P0-1 | `semaphore_upgrade.yml` と `roles/semaphore_upgrade/` は、実行モードの選択に独自 `dry_run` を使用しない。通常実行はupgradeまたは明示rollback、`--check`はそれぞれの診断とする |
| P0-2 | apply / rollback のSemaphore templateから `dry_run` Survey Variableを削除する。apply templateの `--limit quory` と、rollback templateの `rollback=true` / optional `rollback_to` は維持する |
| P0-3 | `--check`では、installed version、target、稼働job、service/consumer reading path、および選択モードに必要な既存状態を実データから診断する。rollbackでは候補の有無と選択対象まで示す |
| P0-4 | `--check`では、backup directory/work directoryの作成、`.deb`保存、DB/config/binary退避、transaction/result/marker書込み、package操作、service操作、detached unit起動、Slack送信を行わない |
| P0-5 | 通常実行のupgrade、already-current、明示rollback、detached transaction、再起動後検証、自動rollback、通知、結果ファイルの契約を維持する |
| P0-6 | `dry_run` が値にかかわらず定義されていたら、旧引数であることと `--check` の使用方法を示して、変更前にrc非ゼロで停止する。旧呼出しを無視して通常実行へ進めない |
| P0-7 | 通常実行・`--check`のどちらも、1回の実行対象はちょうど1hostでなければ処理開始前に停止する。templateの `--limit quory` だけに安全性を依存せず、診断とapplyで対象hostの選び方を変えない。複数hostの一括診断は本playbookの用途に含めない |
| P0-8 | playbookヘッダ、`playbooks/README.md`、template catalogの説明を新しい意味論に揃える。旧 `dry_run` を有効な使い方として案内しない |
| P0-9 | `# tester-gate: check-mode-native` と実経路を一致させる。診断のためcheck mode非対応moduleを実行する場合は、状態を変えないtaskだけを `check_mode: false` とする |

### P1 (Should)

| # | 要件 |
|---|---|
| P1-1 | `--check`の最終出力は、host、mode、current、targetまたはrollback candidate、`would_apply` / `would_rollback` / `already_current` の判断を人が読める形で示す |
| P1-2 | 既存のtarget packageが取得可能かを状態変更なしに確認できる範囲で確認する。package内容の完全なhash/edition照合がdownloadなしには成立しない場合、それを実施済みと主張せず、本実行preflightに残る検査として明示する |

### P2 (Could)

- なし。

### Won't

- 独自モードを `apply` など別名のSurvey Variableへ置き換えない。UI上の実行モードは
  Semaphore標準Dry Runの1つだけにする。

### リスクレジスタ

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| 旧templateが `dry_run=false` を渡したまま新コードを実行する | Medium | High: 無視すると意図せぬapplyになりうる | P0-6でfail-closedし、template reconcile後に通常実行を解禁する |
| 独自 `dry_run` 削除によりCLI無指定が2host applyになる | Medium | High | P0-7で単一hostを実行時検証する |
| `--check`診断のために `check_mode: false` を広く付け、書込みtaskまで実行する | Medium | High | P0-4/P0-9をtask単位で照合し、decoyとansy実測で副作用を確認する |
| check経路を分割した結果、本実行preflightの検査が抜ける | Medium | High | 通常upgrade/rollbackの既存ACを回帰テストし、共通診断を二重実装しない |
| template catalog更新だけで配備済みUIが変わったと誤認する | Medium | Medium | `semaphore_templates_setup.yml`適用後の実template観測を完了条件に含める |
| 同名変数を持つ他2playbookまで機械的に変更する | Low | High: scheduleの実行意味が変わる | 非ゴールを守り、対象pathとdiffをレビューで確認する |

## 7. オープンクエスチョン

なし。旧 `dry_run=true` が行っていたbackup/download/transaction作成はUI Dry Runへ
引き継がない。完全hash/edition照合はP1-2のとおり、本実行直前のpreflightに残す。

## 8. タイムライン考慮

- 緊急対応ではない。実装速度より、通常実行とcheck modeの4経路
  (upgrade/rollback × apply/check)の独立検証を優先する。
- Step 1: requirementと詳細計画、別CLIによる計画査読。
- Step 2: 実装とローカル/decoy自己検証。
- Step 3: 別体Reviewerによる差分レビュー。
- Step 4: Testerがansyでcheck modeと回帰を検証する。本番quoryへのupgrade/
  rollbackは本案件の検証目的では再実行しない。
- Step 5: commit/push後、YoshinobuがquoryのSemaphoreからtemplate catalogを
  reconcileし、AC8を観測する。それまでは旧templateと新コードの組合せを
  P0-6がfail-closedさせる。
- Step 6: Incidentを解決済みに更新し、Auditor、status更新、案件クローズ。
