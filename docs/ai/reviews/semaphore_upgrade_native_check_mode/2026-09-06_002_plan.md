# 実装計画: Semaphore upgrade native check mode

作成: 2026-09-06 / Coordinator
契約: `2026-09-06_001_requirement.md`

## 1. 変更単位

### 1.1 実行入口と変数契約

対象:

- `playbooks/semaphore_upgrade.yml`
- `roles/semaphore_upgrade/defaults/main.yml`
- `roles/semaphore_upgrade/tasks/main.yml`

変更:

1. `dry_run` をmode selectorから除去する。
2. `dry_run is defined` の場合は値にかかわらず最初にfail-closedする移行guardへ
   置き換える。
3. 通常実行・check modeとも実行対象が1hostであることを、roleの診断・変更task
   より前に検査する。複数hostの一括診断は許可しない。
4. modeは `rollback` と `ansible_check_mode` の直交する2軸だけで決める。
5. check modeでupgrade/rollbackの診断部分を実行し、通常実行だけが変更部分へ
   到達する構造にする。
6. 現行 `main.yml` の固定文言だけを出す `check_mode_no_changes` debugは削除し、
   実データを読んだ診断結果へ置き換える。

### 1.2 upgrade経路の分離

対象:

- `roles/semaphore_upgrade/tasks/upgrade.yml`
- 必要に応じて同role `tasks/` 配下に追加する診断用task file

変更:

1. installed version、binary stat、running job、reading path、service owner、baseline
   等の状態変更を伴わない観測・assertを、check/通常の共通診断として1回だけ定義する。
2. check mode非対応のcommand/shellは、状態変更を伴わないものに限って
   `check_mode: false` で実行する。
3. directory作成、download/extract、backup、transaction書込み、install、detached
   起動を通常実行側へ隔離する。
4. check modeでは取得していないpackage内容やedition/hashを検証済みと主張せず、
   本実行preflightに残る検査として出力する。
5. 通常実行では既存のedition/hash照合、already-current、backup、detach契約を維持する。
6. `defaults/main.yml` の `semaphore_upgrade_dry_run` 定義と、現行
   `upgrade.yml` のdry-run報告gate・already-current gate・apply block gateを
   すべて移行対象とする。reject-only guard以外の参照を残さない。

### 1.3 rollback経路の分離

対象:

- `roles/semaphore_upgrade/tasks/rollback.yml`
- `roles/semaphore_upgrade/tasks/select_rollback_candidate.yml`
- 必要に応じて同role `tasks/` 配下に追加する診断用task file

変更:

1. reading pathとrollback-ready candidateの発見・選択をcheck/通常の共通診断にする。
2. check modeでは選択候補と予定動作を報告して終了する。
3. pre-rollback backup作成、rollback metadata書込み、detached起動は通常実行へ隔離する。
4. 独自 `dry_run` がrollbackへ効いていなかった経路を、単一の
   `ansible_check_mode` gateに置き換える。
5. upgrade/rollbackの診断出力は共通キー(`host`、`mode`、`current`、
   `target`または`rollback_candidate`、`action`、未実施検査)を使い、経路で
   意味と粒度を変えない。

### 1.4 Semaphore templateと利用者向け文書

対象:

- `roles/semaphore_templates/defaults/main.yml`
- `playbooks/README.md`
- `playbooks/semaphore_upgrade.yml` ヘッダ

変更:

1. apply/rollback templateのSurveyから `dry_run` を削除する。
2. applyの `--limit quory`、rollbackの `rollback=true` と `rollback_to` は維持する。
3. dry-run手順をSemaphore UI Dry Run / CLI `--check`へ一本化する。
4. scheduleは追加・変更しない。

### 1.5 テストと記録

対象:

- `roles/semaphore_upgrade/files/test_*.yml` / `test_*.py` のうち影響するもの
- 必要な新規fixture
- `docs/ai/reviews/semaphore_upgrade_native_check_mode/`
- `docs/ai/memory/incidents/2026-09-06_semaphore-upgrade-dry-run-does-not-gate-rollback.md`
- `docs/ai/status.md`

検証対象:

1. upgrade normal / upgrade check / rollback normal / rollback checkの4経路。
2. `dry_run=true` / `dry_run=false` の拒否。
3. 複数host通常実行の変更前拒否。
4. check経路で永続ファイル・package・service・detached unit・Slackが変化しないこと。
5. 既存のcapture-origin、rollback candidate、detached Python testsの回帰。

## 3. 検証順序

1. YAML/syntax、tester-gate、対象lint、Python既存unit/fixture。
2. localhost/decoyで旧引数拒否、複数host拒否、4経路のtask到達性を確認。
3. Testerがansyを単一hostに限定し、`scripts/safe-ansible-check.sh`経由で
   upgrade/rollback checkを実測する。通知はcheck modeの既存抑止を確認する。
4. 通常実行の破壊部分はfixtureで境界まで確認する。本案件のためにquoryの
   upgrade/rollbackを再実行しない。
5. commit/push後、quoryでtemplate catalogをreconcileし、実templateのSurveyを
   読み取ってAC8を確認する。これはYoshinobuがSemaphoreから起動する。

## 4. 失敗時の停止条件

- check modeでP0-4の書込みtaskへ到達するなら実装を止める。
- 旧 `dry_run` が無視され通常実行へ進むなら実装を止める。
- 単一host guardがroleの変更taskより後に来るなら実装を止める。
- 他2playbookまたはscheduleへ差分が及ぶなら本案件へ混ぜず停止する。
- 既存upgrade/rollback本実行契約を維持できない変更が必要なら、要件を勝手に
  広げずCoordinatorへ戻す。

## 5. 工程

1. 別CLI Reviewerによる本計画の査読。
2. Implementerがrequirementを正本として実装・自己検証し、implement記録を作る。

4. Testerがtest planとtest resultを作り、許可されたansy checkを実測する。
5. Auditorが案件フォルダからクローズ可否を再構成する。
6. CoordinatorがIncident/statusを更新し、Yoshinobuへcommit/pushの承認を求める。
