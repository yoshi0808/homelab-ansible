## 所見(Coordinatorへ)

対象実装は一切変更していない。以下は報告のみで、修正は行っていない。

**F1(低・fixtureの衛生 / 本案件の判定には影響なし)**
`test_native_check_mode.yml`のunavailable variantは、意図された「reading path 2ファイルとも不在」ではなく**「2ファイル中1ファイルが実在」**を検証している。
`Create consumer query token fixture`がテンプレート化されたpath(unavailable時は`missing-token`)へtokenを作るのに対し、`Remove consumer reading path for the unavailable fixture variant`は固定名`bin/query` / `query-token`を消すため、`missing-token`が残る。実測で`missing-token`が存在し`missing-query`が存在しないことを確認した。
判定式が`length == 2`のため結果は`false`で正しく、M3/M4の判定は有効である。ただし**「両方不在」という状態はこのfixtureでは一度も通っていない**。
なお偶然ながら、この「binaryは不在・tokenは存在」という形は`2026-09-06_007_test_ansy.md`が記録した実`ansy`の状態と一致する。

**F2(観察・本変更による退行ではない)**
upgrade側は`Require no other running job and at most this one upgrade job`で稼働jobを**assertで止める**が、rollback側は稼働jobを数えて診断へ表示するだけで**止めるassertが無い**。`git diff`で確認したところ、この非対称は変更前の`rollback.yml`にも同様に存在し、本案件が持ち込んだものではない。ただし分割によって2つのdiagnoseファイルが並んだことで差が見えやすくなっており、意図的なら理由を、そうでなければ別案件を検討する余地がある。

**F3(観察・本変更による退行ではない)**
`upgrade_diagnose.yml:111,222` と `rollback_diagnose.yml:77` は`systemctl show semaphore.service`を**リテラルで**書いており、`semaphore_upgrade_service`変数を使っていない(同変数の実質的な利用は`upgrade.yml:143`のmetadata記録のみ)。そのためfixtureの`semaphore_upgrade_service: semaphore-upgrade-native-check.service`という上書きは**効いておらず**、fixtureは`PATH`で`systemctl`自体を差し替えることで成立している。これも変更前から同じ記述であり、退行ではない。ただし「fixtureがservice名を上書きしている」という見かけを安全の根拠にはできない。

**F4(手続き・今回実際に発生)**
fixture rootが固定path`/tmp/semaphore-upgrade-native-check`で、pre_tasksが毎回rootごと削除・再作成するため、**同一ホスト上の並行実行は互いを破壊する**。今回まさに他agentとの衝突懸念で全結果を破棄・再実行した。実行ユーザやPIDでrootを分離すれば同型の再発を防げる(`skills/test-strategy/SKILL.md`のtemp path分離と同じ論点)。本Testerは対象実装に手を入れないため変更していない。

## 結論

承認scope(localhost `/tmp` fixture、decoy inventory、静的検査、repo内既存テスト)において、

- **native check modeの4経路(upgrade / rollback × reading path available / unavailable)は3周連続で全12回rc=0**、診断出力は要求されたshape(host / mode / current / target または rollback_candidate / action / running_jobs / reading_path_check)を満たし、P0-4が禁じる副作用は内蔵assertと独立観測の双方で**0件**だった。
- **旧`dry_run`は値によらず、`--tags destructive`併用時も`ok=0`でfail-closedする。**
- **2host一括は`serial: 1`下でも診断・変更より前に停止する。**
- **`--check`なしのfixture起動はwrapperが拒否する(G1a、実測)。** fixture自身の先頭assertによる二重の拒否は、実行ではなく`test_detach_boundary.py`の静的検査を根拠とする(下記「訂正」節)。
- **静的検査・既存テスト8本はすべてrc=0。**

AC3 / AC4 / AC6通常実行側 / AC8はいずれも承認scopeまたはPolicy(TS-023)の外であり、本Testerは実施していない。reading path「有り」側の実データ検証はquoryでの初回`--check`まで残存リスクとして持ち越す。

対象実装ファイルは1つも変更していない。repo内で本Testerが作成したのは本ファイルのみで、着手前後の`git status --short`は本ファイルの追加以外に差分がない。decoy inventoryと実行ログはscratchpad配下(`/tmp`)に置き、repoへ持ち込んでいない。
