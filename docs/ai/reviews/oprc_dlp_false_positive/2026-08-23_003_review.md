# Code / Security Review: Operator Request Channel DLP 誤検知修正

Reviewer: Codex / 2026-08-23

## Summary

実装差分そのものは、entropy の候補文字クラスだけを狭め、閾値・engine・13件のパターン規則を維持している。パターン規則は entropy 候補抽出より先に全文字列へ独立適用されるため、本変更で検出力は落ちない。拒否メッセージも `rule_id` と schema 検証済み payload の `pointer` だけを出し、検出値を保持・出力しない。

一方、安全性判断の根拠と配備手順には blocking finding がある。実装記録の「平均間隔」は delimiter 間隔ではなく有限トークン両端を含む分割片長で、固定 seed も再現手順も存在しない。さらに message に保存された旧 ruleset hash は配備後も更新されないため、未取得の既存 message が新 client から取得不能になる。安全機構の緩和量と移行時の可用性を正しく判断できる状態へ直す必要があり、Request Changes とする。

## Security Assessment

- 非ゴールは守られている。`min_length=20`、`min_bits_per_char=3.8`、`engine_version="1"` は不変で、`oprc/dlp.py` に差分はない。変更は ruleset version と candidate pattern、client denial表示だけである。
- JSONには13件のパターン規則が残る。`_scan_impl` は全文字列へのpattern scanを先に行い、entropyはその後に対象pointerだけへ行うため、candidate pattern変更はpattern ruleへ波及しない。全13 rule IDの独立fixtureで発火を確認した。
- `Finding` が持つのは category / rule_id / pointerだけで、client summaryは後二者だけを出す。submit前にはschema検証済みであり、get側も表示前にschema検証する。schemaの `additionalProperties` 境界上、pointerは既知field名とarray indexで構成され、payload値を含めない。新しい漏えい経路は見つからなかった。
- relaxation は要求どおりunknown delimiter-bearing secretだけへ効くが、残存穴は「小さい」とは評価できない。均等に混ぜた20〜48-byte乱数では標準約7%、URL-safe約16%を見逃し、20-byte URL-safeでは約34%を見逃す。既知形式はpattern ruleが補完するため、受容可否は「未知形式の短いURL-safe秘密にこの率を許すか」で判断すべきである。
- Reviewer見解は、上記率を明示してYoshinobuが受容するなら候補パターン変更自体はrequirementの意図内で受容可能。ただし Findings 1〜3の測定・移行計画を直さずに本番適用することは推奨しない。

## What Looks Good

- §1のAnsible変数名、apt path、repo相対pathは新rulesetで通り、旧rulesetではblockされることを再確認した。
- `rule_id at pointer` は複数findingを落とさず、検出値を出力しない。local submitとlocal intakeの両deny経路に適用される。
- ruleset hashは各hostの配備時にrepo-side fileから再計算されるため、「rulesetは一切変更してはいけない」という旧説明は確かに誤りである。問題は変更そのものではなく、同一hostの更新窓・host間の過渡期・既存message metadataを含む移行管理である。
- known secretのpattern規則、entropy閾値、scan対象pointer、engine code、権限境界、外部command実行には変更がない。
