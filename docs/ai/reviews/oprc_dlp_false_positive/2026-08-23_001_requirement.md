# requirement: Operator Request Channel の DLP がパスと識別子で誤検知する

起案: Coordinator / 2026-08-23 / 依頼者: Yoshinobu(優先度高と判断)

## 1. 問題定義

**この経路の本来の使い方をすると、送信前 DLP に止められる。**

2026-08-22、monnie の `unattended-upgrades` 設定を Operator へ問い合わせる OPREQ が `denied: dlp blocked this payload before it was sent` で拒否された。原因は `dlp-rules.json` の `entropy` 節(`high-entropy-string`)で、次の2箇所が閾値を超えていた。

- `observed_facts[3]` — Ansible の変数名 `ubuntu_vm_full_upgrade_important_per_node.monnie`
- `requested_information` — apt の設定ファイルパス

**実測(`min_length: 20` / `min_bits_per_char: 3.8` / `candidate_pattern: [A-Za-z0-9+/_=.-]{20,}`)**

| 種別 | bits/char | **変更前**の判定 |
|---|---|---|
| Ansible変数名 `ubuntu_vm_full_upgrade_important_per_node.monnie` | 3.95 | BLOCK |
| apt設定パス `/etc/apt/apt.conf.d/50unattended-upgrades` | 3.92 | BLOCK |
| **repo相対パス `roles/prometheus_update_check/tasks/notify.yml`** | **4.24** | **BLOCK** |
| commit hash(40hex) | 3.84 | BLOCK |
| base64風トークン | 4.84 | BLOCK |
| Slack風トークン | 5.14 | BLOCK |

**本物の秘密(4.8〜5.1)と日常語彙(3.8〜4.2)の差が 0.6 bits しかない。** とくに **repo 相対パスが最も高い 4.24 を出す**。この経路は調査依頼のためにあり、ファイルパスを載せるのが本来の使い方であるため、**設計目的と DLP が正面から衝突している。**

**原因は閾値ではなく指標の性質である。** Shannon エントロピーは辞書を持たないため、意味のある語の連結(`prometheus_update_check`)とランダム文字列を区別できない。閾値を上げるだけでは、少し長いパスで再発する。

## 2. ゴール

- **AC1 が挙げる3種(Ansible変数名 / apt設定パス / repo相対パス)が通る。** **この環境の語彙すべてが通ることは求めない** — 区切りを含まない16文字以上の断片は今も候補になり、`UNREACHABLE+report` は承知のうえで BLOCK のままである(§8)。
- **形の分かっている秘密は引き続き止まる。**
- **止まったとき、どこが引っかかったかが送り手に分かる。**

## 3. 非ゴール

- **`min_bits_per_char` を上げない。** 鈍くするのは原因に触れない対処である(Yoshinobu、2026-08-23 に A 案を不採用)。
- **`min_length` は下げてよい**(2026-08-23 追記)。**検出を戻す方向であり、原因を覆い隠さない。** ただし**誤検知が増えないわけではない** — 追跡ファイル1,760本の走査で **61種 → 66種**(§8)。増分5種は承知のうえで採る。
- **エントロピー判定そのものを外さない**(E 案不採用)。形の分かっていない秘密を拾う経路を消さない。
- **パターン規則(PEM鍵 / Slack / JWT / Bearer / Semaphoreトークン / URL埋め込み資格情報ほか)を1つも減らさない。**
- **DLP エンジン(`oprc/dlp.py`)を変更しない。** `engine_version` を上げない。

## 6. 確かめること(実装時に判断し、記録へ残す)

- **base64 の標準アルファベットは `+` と `/` を含む。** `/` を候補の文字クラスから外すと、`/` を含む base64 は分割されうる。**ランダムな base64 で `/` が現れる間隔と、分割後も 20 文字以上が残るかを実測すること。** 「平均64文字に1回だから問題ない」を計算せずに前提にしない
- **URL-safe base64 は `-` と `_` を使う。** 同じ検証を行うこと
- **commit hash(40hex)は本変更後も止まる**(区切りを持たないため)。これを変えるかどうかは本案件のスコープ外とし、**止まる事実を記録に残す**

## 7. 残存リスク

**区切り文字を含む未知形式の秘密は見逃す。** これは C 案が構造で切ることの裏返しであり、承知のうえで採る。**事故で貼り付けた秘密は元の形を保つ**ため、実害は小さいと見ているが、**測って確かめたわけではない。**


## 8. 採用した形と、その根拠(2026-08-23)

**最終形は `candidate_pattern` = `[A-Za-z0-9+]{16,}`**(区切り `/` `_` `-` `.` と `=` を除外、`min_length` 16、`min_bits_per_char` 3.8)。

### 検出率(最終形での測定)

| 入力 | 変更前(`min_length` 20 / `=` あり) | **最終形** |
|---|---|---|
| URL-safe 20バイト | 63.9% | **74.8〜75.0%** |
| 標準 20バイト | 80.4% | **87.7〜88.3%** |

(2つの値は Coordinator と Implementer が独立の seed・別スクリプトで測ったもの。同方向・近似で一致した)

**下限を 16 にした理由**: 20 のままだと URL-safe 20バイトが 63.9% に落ちる。16 まで下げると戻り、14 以下は頭打ちになる。

**`=` を外した理由**: `=` は base64 の末尾paddingにしか現れないため**秘密の検出では末尾数文字を失うだけ**である一方、残すと `Description=Reload` のような `key=value` がひと続きの断片になる。**独立レビューが systemd の unit 行3件で反例を出した。**

### 誤検知はゼロではない(承知のうえで採る)

**当初「この環境の語彙8種で誤検知0」を根拠にしていたが、これは自分で選んだ標本だった。** 独立レビューが全追跡ファイルから反例を出した。

**`UNREACHABLE+report` は、`min_length` 20 では通り、16 では BLOCK される。** `+` が候補クラスに残っているためである。**`+` を外せばこれは消えるが、下表のとおり減るのは2種だけで、代わりに標準 base64 が `/` に加えて `+` でも割れる。割に合わないため採らない**(Yoshinobu 決定、2026-08-23)。

**追跡ファイル1,760本(`docs/ai/memory/` を除いた `git ls-files`、400KB超は除外)を走査し、`min_length` と閾値 3.8 の両方を満たして BLOCK される文字列の種類数**(真陽性を含むため誤検知の数ではない。方向を示す値):

| 候補クラス | `min_length` 20 | 16 |
|---|---|---|
| `+` `=` あり | 79種 | 90種 |
| **`=` を外す(採用)** | 61種 | **66種** |
| `+` も外す | 60種 | 64種 |

**下限を 16 にしたことの増分は 5種である。** `+` を外しても2種しか減らない。

**`docs/ai/memory/` を除いたのは、独立レビューが `docs/ai/core.md` の規定によりそこを読めず、含めると数字を検算できないためである。** 当初の走査は除外しておらず、母集団が1,809本だった。

**実装記録 §3(8b) の走査とは母集団が違う。** あちらは拡張子で絞って1,737本、本表は絞らず400KB超だけ除いて1,760本である。**測っているものも違う** — あちらは「16〜19文字の新規候補と BLOCK 件数」、本表は「候補クラスごとに BLOCK される種類数」。**どちらも独立レビューが再現できる母集団であり、数字を突き合わせるときはこの違いを踏まえること。**

**文字クラスの調整では衝突ゼロに到達しない。** 4ラウンド削るたびに別の衝突が出た。**ゼロを追うのをやめ、止まったときに場所が分かる形**(拒否メッセージの `rule_id at pointer`)で運用する。既存の14件(PascalCase / hex)は本変更の前から BLOCK されており、`docs/ai/status.md` の着手候補とした。

## 9. 配備で取り残されるもの(承知のうえで受け入れる)

**受理時の ruleset hash が message の metadata に不変で保存され、取得時に現在の hash と照合される。** そのため **旧 ruleset で作られた未取得 message は、配備後に取得できなくなる。**

**「配備前に drain する」は現在のCLIでは実行できない。** この経路に「読んだ」を記録する操作が無く、ライフサイクルは `submitted` → `expired`(TTL)だけである。`get` を実行しても state は変わらない。

**2026-08-23 時点で `submitted` の7件は、配備前にすべて内容を読んだ。** いずれも当時の案件への回答で、3案件ともクローズ済み。**取りこぼしていた判断は無い。**

| 08-16 | OPRES ×3 | agmsg remote の前提条件 / 到達確認 / quory側 sync engine の状態 | 同上 |
| 08-17 | OPRES | Semaphore 退避設計に必要な読み取り調査 | `semaphore_db_backup` |

**構造の問題は残る。** 次に ruleset を変えるときも同じ判断が要り、「読んだ」を記録する手段が無い以上、毎回内容を読んでから配備することになる。**別案件の候補とする。**
