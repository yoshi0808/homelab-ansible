## 0. 検証方法の要旨

`operator-channel-client submit` / `get` / `list` / `status` はいずれも実行していない(安全境界どおり)。かわりに `oprc/dlp.py`(AC4でReviewer確認済み・無変更)を実際にimportし、`oprc.dlp.scan(payload: dict, ruleset, timeout)` を**直接評価**して確認した。「読解で済ませない」の指示に沿い、すべて実行結果であり推測・書き写しではない。

- `dlp.load_ruleset()` で **`roles/operator_request_channel/files/dlp-rules.json`(repo)** と **`/etc/operator-request-channel/dlp-rules.json`(配備済み、ansy)** の両方を実ファイルからロードし、両方に対して同一payloadを走査して比較した(値の書き写しはしていない — ファイルは自分でparseしてPythonオブジェクトとして使っただけ)。
- AC3(拒否メッセージの文面)は、`operator-channel-client` の実コード(`_findings_summary()`)を `importlib` でモジュールとしてロードし、**その関数を直接呼んで**確認した。`submit`/`get` などのコマンド分岐(`cmd_submit`等)は一切呼んでいない。`if __name__ == "__main__":` はモジュールロードでは実行されないため、ssh呼び出しには到達しない。
- 補助として、repoの自動テスト `python3 scripts/tests/operator_request_channel/run-tests.py` を実行した(338件 OK)。これはリポジトリ内のローカルテスト実行であり安全境界内。

**新たに検出値を成果物へ書かない**という指示に従い、AC2で使ったbase64風・Slack風トークンは `secrets` モジュールでその場生成した値であり、本ファイルには実際の文字列を記載していない(生成方法のみ記載)。

### 3.2 パターン規則13件がすべて個別に発火する

`dlp-rules.json` の `rules` 配列は13件(`pem-or-ssh-private-key` / `slack-token` / `slack-webhook-url` / `semaphore-api-token` / `bearer-token` / `jwt` / `generic-secret-keyvalue` / `vault-decrypted-plaintext` / `credential-in-url` / `env-dump` / `proc-environ` / `private-ipv4` / `ipv6-ula-or-link-local`)。各ruleにつき、その規則だけが狙って発火する合成文字列を1つずつ用意し(秘密値ではなく規則の形だけを満たす合成テキスト。IPv4はRFC1918範囲内の合成アドレス、IPv6はリンクローカル範囲の合成アドレスで、実ホストの値ではない)、13件全部で対応する `rule_id` がfindingsに含まれることを確認した。13件全件が該当する `rule_id` を出し、「未発火」は0件だった。

(`jwt`のテスト文字列は `high-entropy-string` も同時に発火したが、これはentropy側の候補抽出とパターン規則が独立ロジックであるためであり(`oprc/dlp.py:249-251` と `:261-267` の別ループ)、`jwt` 自体が発火していない証拠にはならない — `jwt` は期待どおりfindingsに含まれていた。)

**PEM鍵 / JWT / Bearer / Semaphoreトークン / URL埋め込み資格情報を含む13件すべてが従来どおり発火することを実測した。**

## 4. AC3 — 判定: PASS

`operator-channel-client` の `_findings_summary()` を `importlib.machinery.SourceFileLoader` でモジュールとしてロードし(`__main__` ガードは実行されないため、ssh呼び出し・submit/get分岐には到達しない)、関数を直接呼び出して確認した。

- `Bearer` 形式の文字列と `credential-in-url` 形式のURLを含むpayloadを `dlp.scan()` に通すと、`bearer-token`(pointer `/observed_facts/0`)と `credential-in-url`(pointer `/requested_information`)の2件がfindingsに入った。
- `_findings_summary(result)` の出力は `"bearer-token at /observed_facts/0; credential-in-url at /requested_information"` — **`rule_id` と `pointer` のみ**。
- `category`(`bearer_or_jwt` / `credential_url`)の文字列が出力中に含まれていないことを実測(`in` 演算子でチェック、両方とも不在)。
- マッチした値そのもの(`Bearer `の後続文字列、URL中のuser:passの部分)が出力中に含まれていないことも実測(不在)。

`cmd_submit` / `cmd_get` の実コードはどちらもこの `_findings_summary()` を `_deny()` の引数に直接渡しているだけであり(`operator-channel-client:186` `:249`)、関数を直接呼んだ結果はコマンド経路を実行した場合の出力と同一になる。

## 6. 未実施項目とその理由

- **ansy実機への配備・実配備後の`operator-channel-client submit`によるend-to-end確認は行っていない。** 依頼文の安全境界で明示的に禁止されているため(submit/get/list/statusいずれも不可)。§1のとおり、ansyはまだ旧rulesetのまま稼働している。
- **quory側の配備状態は確認していない。** quoryへのAnsible実行・SSH到達も本依頼のscope外。
- **`config.json`のhash突合の実機確認(`sha256sum`と`expected_dlp_ruleset_sha256`の一致)は、配備後の状態についてはまだ行っていない。** 今回確認したのはあくまで「配備前の現状は自ホスト内で整合している」ことのみ(§1)。
- **実際に`operator-channel-client`をCLIとして起動しての引数解析・stdin読込経路の確認は行っていない。** `_findings_summary()`のみを関数として直接呼んだ。ただし当該関数はコマンド分岐から渡される引数と同一の`ScanResult`を渡しているため、出力文面自体はコマンド実行時と同一になるはずである(実測はしていない前提の推論であることを明記する)。
- **AC4は依頼どおり再検証していない**(Reviewer確認済みのため)。
