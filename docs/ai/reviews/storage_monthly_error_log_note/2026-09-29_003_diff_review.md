2. **`references`追加が既存のreport読み取り処理を壊していないか。旧形式でも動くか**:
   - `storage_archive.py`の`archive()`内の履歴読み込み(`history.append`前のスキーマ検証)は`schema_version` / `report_id` / `collected_at` / `hosts` / `collection` / 各deviceの`id`・`values`のみを見ており、`references`の有無を検査しない。旧形式(`references`キー無し)でも例外なく読める。
   - `freeze_devices`・`prune`は`hosts`配下のdevice情報のみを参照し、`references`に触れない。
   - replay分岐(`storage_archive.py:113-116`)は`read_json`で読んだreportをそのまま`markdown`/`short_summary`へ渡す。両関数は`report.get("references", [])`で旧形式でも空リスト扱いになり、例外もキー欠落表示も起きない。
   - `storage_notion.py`の`publish`は`markdown(report)`経由でのみreportへ触れ、`references`を直接読まない。旧形式でも新形式でも同じ経路で動く。
   - `storage_files.py`の`read_json`はJSONをそのまま返すだけで、鍵の集合を検査しない。
   - `test_legacy_report_without_references_remains_usable`(`tests/test_storage_monthly.py`)が、`references`キーを取り除いたreport dictへ直接`markdown()`/`short_summary()`を呼び、例外なく動くこと・「## 参考」や「参考:」が出ないことを確認しており、AC6を実測でカバーしている。
   - 結論: 破壊なし。旧形式でも動く。

3. **判定条件(media_errors==0 かつ critical_warning==0)が既存CRITICAL判定(媒体エラー・重大警告・spare)と矛盾・重複しないか。型で誤判定しないか**:
   - `values`は`integer()`関数を通した後の値(str/intどちらの入力でも`int`型に正規化済み)なので、`== 0`比較で型起因の誤判定は起きない(既存の`integer()`が文字列digitのみ許容し、負値・bool・非数値を拒否する既存ロジックをそのまま利用している)。
   - 参考行に分類してissueを作らない分岐(131-136行目)と、media_errors/critical_warning/spareによる既存CRITICAL判定(142行目)は独立したコードパスであり、削除・置換はしていない。media_errors>0またはcritical_warning!=0のときは従来どおり`entry["issues"].append(["WARNING", ...])`が実行され(137-138行目)、かつ142行目のCRITICAL判定も従来どおり評価される。二重にissueが立つ組み合わせ(WARNING「error log count increased」+ CRITICAL「NVMe health warning/media errors/spare」)は本差分導入前から存在する挙動であり、本差分で新たに生じたものではない。
   - S2で述べたspareのみのケースを除き、矛盾は無い。

4. **Slack短報の「先頭3件+ほかN件」の並びで、参考の行が重要な行を押し出さないか**:
   - `short_summary`(`storage_monthly.py:242-250`)は`details = sorted_issues(report)の変換結果` の後に `references` を `extend` で**末尾に追加**してから先頭3件を切り出す。`sorted_issues`はUNKNOWN→CRITICAL→WARNINGの優先順で並べるため、実issueが3件以上あるときは参考行がその手前に割り込むことはなく、「ほかN件」のカウントにのみ算入される形で後ろへ回る。
   - 実issue数が3件未満のときに限り参考行が表示枠に入るが、これはissueを押しのけていない(空いている枠を埋めているだけ)。
   - 結論: 重要な行を押し出す経路は無い。
