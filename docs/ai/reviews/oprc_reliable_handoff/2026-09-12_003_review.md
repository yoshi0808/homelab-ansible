# Code Review: OPREQ送信と回答受領の安定化(scripts/oprc-*、Coordinator Role、agent-messaging.md、operator-request-channel.md)

### Summary
実装は001の3点(受信の確実化、sync状態の区別、OPREQ作成/検証の共通化)を機能面では満たしており、`run-tests.sh`(19件)・`test_helpers.py`(6件、要下記)・`check-doc-consistency.py`(3件)・`git diff --check`は自分で再実行してすべてPASSした。ただし、新設したCoordinator Role文書の文言が既存のPolicy(EXEC-082「実行identityを昇格しない」)と衝突しかねない表現になっている点、および新規Pythonロジックの単体テストがこのディレクトリの標準実行経路(`run-tests.sh`)から呼ばれず回帰検知を素通りする点の2つがblockingとして残る。

### What Looks Good
- `scripts/oprc-prepare.py`のvalidate経路は`schema.reject_server_assigned_fields`を生payload(candidate生成前)に対して呼んでおり、AC3「違うtypeやserver-assigned fieldsを上書きして受け入れない」を満たす。`--output`時のみ`type`/`schema_version`を補い、検証専用モード(`oprc-submit.sh`が呼ぶ経路)では補わないため、手作成OPREQのtype欠落を正しく拒否する(`test_invalid_or_secret_request_never_creates_output`で確認、かつ自分でも同テストを再実行しPASS)。
- `scripts/oprc-sync-check.py`の分類(`engine stopped`→2、`engine running`が無い/タイムスタンプ不明→4、期限超過→2)を、自作したスタブ`remote.sh`で`stale`/`old`/`nosync`/`fail`の4モードそれぞれについて`scripts/oprc-submit.sh`を直接実行し、意図通りexit 4/2/4/4になることを実測した(Suggestion #1の指摘対象はテストの配線であって、分類ロジック自体の正しさは確認済み)。
- `scripts/oprc-replies.py`は両team(`homelab`/`homelab-ops`)のinbox確認を独立したtry/exceptで行い、片方が失敗してももう片方を試み、`excluded_count != 0`のページを検知したら例外化して「未回答」の断定を止める。`operator-channel-client`の実装(`cmd_list`/`cmd_get`のcursor形式・レスポンス形状)および`oprc-receive`の`cmd_outbound_list`(`items`/`next_cursor`/`excluded_count`のキー)を実物で突き合わせ、想定と一致することを確認した。AC1「既読・submittedをフィルタしない」も`test_read_already_submitted_reply_across_pages`で担保されている。
- `scripts/oprc-submit.sh`の`set -euo pipefail`により、`oprc-sync-check.py`の`sys.exit(2|4)`がラッパーの終了コードへそのまま伝播することを実測で確認した。
- スコープ(対象ファイル一覧)は依頼文・requirementの範囲と完全に一致しており、範囲外ファイルへの変更は無い。`check-doc-consistency.py`・`git diff --check`もPASS。実ホスト・外部サービスへは一切接続していない。
