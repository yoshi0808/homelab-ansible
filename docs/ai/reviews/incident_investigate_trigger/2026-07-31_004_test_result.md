## R2(バンドル単位のOSError、実測)

**fixture作成上の訂正が1点ある**: 実装記録`2026-07-31_002_implement.md`§0/§3は「`summary.json`自体を`chmod 000`すればstatで`PermissionError`になる」と記述しているが、これは技術的に不正確である。POSIXの`stat(2)`はファイル自身のパーミッションビットを見ない(必要なのは経路上の各ディレクトリへのsearch(x)権限のみ)。実際に`chmod 000`したファイルに対して所有者が`os.stat()`を試すと、下記のとおり**成功する**ことを確認した。

```
$ touch f.txt && chmod 000 f.txt && python3 -c "import os; print(os.stat('f.txt'))"
os.stat_result(st_mode=32768, ...)   # 成功する。PermissionErrorにならない
```

正しくPermissionErrorを起こすには、**バンドルディレクトリ自体**(`summary.json`の親)を`chmod 000`し、そのディレクトリへのtraverseを塞ぐ必要がある。この訂正を踏まえてfixtureを組み直し、以下を確認した。

fixture: `semaphore-901`(ディレクトリごと`chmod 000`)・`semaphore-902`(健全、未調査、8分前)を同居させて1回実行。

**観測結果**:
```
incident-investigate: could not stat bundle 'semaphore-901': PermissionError: [Errno 13] Permission denied: '.../semaphore-901/summary.json'
EXIT=3
```
生成された成果物: `semaphore-902.json`/`.md`のみ(**健全なバンドルは異常バンドルに道連れにされず正常処理された**)。同時に**最終的な終了コードは3**であり、異常の発生自体は隠されない(`main()`が`scan_errors`を最終exit codeへ反映する設計どおり)。

**この訂正の位置づけ**: コード自体の挙動(実装が意図した「バンドル単位で隔離しつつ、終了コードで異常を可視化する」)は正しく機能していることを、正しい再現手順で独立に確認した。指摘は実装記録の自己検証手順の記述(fixtureの作り方)が技術的に不正確だった点についてであり、実装コード自体の欠陥ではない。

## AC6(通常のansible実行がcallbackを読み込まない、対照実験で実測)

**制約**: 本番のquoryキューディレクトリ(`/var/lib/homelab-recovery/incident-investigate/queue`)は`ls`が`Permission denied`(下記「quoryでの読み取り専用確認」参照)であり、かつ現在のquoryのリポジトリ作業ツリーはこの差分の配備前(旧`ansible.cfg`のまま)である。したがって「本番quoryで実際にキューファイルが新規に作られないこと」の直接観測は配備後にしか行えない(契約§9どおり)。

**代替として、次の対照実験をscratchで行った**(実host非依存、`/tmp`完結):

1. `roles/incident_investigate/callback_plugins/incident_investigate_trigger.py`(未commitの現物、ロジック無変更)をscratchへコピーし、`QUEUE_DIR`定数だけを`/tmp`上の実在するダミーキューディレクトリへ書き換えた(このファイル自体の判定ロジック・`CALLBACK_NEEDS_ENABLED`は無変更)。
2. decoy inventory(`localhost ansible_connection=local`)に対し、常に失敗するタスク1つを持つplaybookを用意。
3. **Variant A**(現在のリポジトリの`ansible.cfg`をそのまま`ANSIBLE_CONFIG`に指定 — この差分がそのまま反映された状態): `SEMAPHORE_TASK_DETAILS_ID=999999`を設定して実行 → PLAY RECAPは`failed=1`(正しく失敗を検出)、**ダミーキューディレクトリにファイルは生成されなかった**。
4. **Variant B**(`callback_plugins`/`callbacks_enabled`の2行を、scratchコピーのcallbackを指すよう追加しただけの別`ansible.cfg`。それ以外は同一): 同じplaybook・同じ環境変数で実行 → `failed=1`は同じだが、**`semaphore-999999.json`がダミーキューディレクトリへ生成された**(`failed_hosts: ["localhost"]`を含む正しい内容)。

同一のcallbackコード・同一の失敗play・同一のSemaphore env varで、**`ansible.cfg`の2行の有無だけ**が結果を分けることを直接観測した。これは「`ansible.cfg`の変更がcallbackの無効化の唯一の原因である」ことの直接証拠であり、間接証拠(`ansible-config dump`のキー不在)より強い。

**補強**: `ANSIBLE_CONFIG=/home/yoshi/homelab-ansible/ansible.cfg ansible-config dump --only-changed`で`callback_plugins`/`callbacks_enabled`いずれも現れないことを再確認。`--syntax-check`を対象5 playbook(`incident_investigate_setup.yml`・`incident_inspect_setup.yml`・`incident_sync.yml`・`cert_renew.yml`・`systemd_timers.yml`)全てに対して実行し、いずれも正常終了。`--check`モードでも同じdecoy playbookが例外なく完走すること(`command`モジュールが既定で`--check`下ではskipされる挙動込み)を確認した。
