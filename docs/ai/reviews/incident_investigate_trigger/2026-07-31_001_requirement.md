# requirement: 一次調査の起動契機をcallbackから証拠バンドルの走査へ切り替える

日付: 2026-07-31
状態: **確定**(方針Cは2026-07-31にYoshinobuが暫定決定済み。本書はその実装契約)
親記録: `docs/ai/memory/incidents/2026-07-31_incident-investigate-callback-did-not-enqueue.md`(Incidentが正本。本書はそこで合意された「修正内容」を実装契約へ落としたもの)
関連: `docs/ai/adr/009-per-incident-investigation-runtime.md` (a) a-4、`docs/ai/policies/incident_capture_policy.md` §3.5

## 1. 問題定義

一次調査の起動契機(ADR-009 (a) a-4)は、ansible callback plugin が失敗時にキューファイルを書き、quoryの毎分timerがそれを拾う形だった。**この経路は本番のSemaphore実行で発火しない。**

原因は確定している — Semaphoreが起動する `ansible-playbook` プロセスに `SEMAPHORE_TASK_DETAILS_*` 環境変数が1つも渡っておらず、callbackが「Semaphore以外の起動経路(非ゴール)」とみなして黙って `return` していた(2026-07-31、quory実機で実測)。切り分け済みの事項・実測値・訂正はIncidentが正本であり、ここへ複製しない。

2026-07-31時点で、タスク#495(`cert_renew`)の証拠バンドルは生成されているが調査は起動しておらず、`reports/incidents/_investigations/` は空である。

**この問題の構造**: 捕捉はSemaphoreのDBを5分毎にポーリングする独立経路を持つのに対し、調査はplaybook実行内の経路1つだけに依存していた。冗長性の非対称がそのまま出た。

## 2. ゴール

- **Semaphoreジョブが失敗したとき、一次調査が実際に起動して成果物を残す状態に戻す。**
- 起動契機を、既に動いている捕捉の成果物(証拠バンドル)の出現へ移す。
- **可逆にする。** 方針Cは暫定であり、callback経路へ戻す判断が将来ありうる。

## 3. 非ゴール

- **callback plugin の削除**。ファイルは残す(`ansible.cfg` の2行を外すことで無効化する)。
- **Semaphore側の設定変更**(案A: `SEMAPHORE_TASK_DETAILS_*` を注入させる)。repo外の操作であり、注入手段の有無も未確認。
- **Semaphore以外の実行経路の捕捉**(requirement R8「Semaphore外ジョブの保険」)。従前どおり未実装のまま。
- **成果物のスキーマ変更**。`docs/ai/reviews/incident_auto_investigation/2026-07-31_001_requirement.md` §7 が引き続き正本。
- **LLM封じ込め(c-3)・実行identity(d-2変形)・成果物置き場(e-2)の変更**。ADR-009のこれらの決定は動かさない。
- 一次調査のSlack通知(P2 R14)。

## 4. ユーザーストーリー

Yoshinobuとして、Semaphoreのジョブが失敗したとき、翌朝に `reports/incidents/_investigations/` を見れば一次情報が揃っていてほしい。**「バンドルはあるのに調査だけ無い」という、今回気づくまで誰も気づかなかった状態を作らないでほしい。**

## 6. 受入条件

### AC1 — 未調査バンドルが拾われる(通過側)

- **Given** `reports/incidents/` に `semaphore-<id>/summary.json` があり、`_investigations/semaphore-<id>.json` が存在しない
- **When** `incident-investigate.py` を1回実行する
- **Then** そのバンドルが調査対象として選ばれ、`_investigations/semaphore-<id>.json` と `.md` が生成される。**選定されたこと自体は、生成された成果物のファイル名(`semaphore_task_id`)で観測する**(LLM呼び出しが成功したかどうかとは独立に観測できる)

### AC2 — 調査済みバンドルが再投入されない(非通過側)

- **Given** `semaphore-<id>/` と `_investigations/semaphore-<id>.json` の**両方**が存在する
- **When** `incident-investigate.py` を1回実行する
- **Then** そのバンドルに対してLLMを呼ばない。**成果物の内容(`investigated_at`)が変化しない**こと、かつ終了コードが `0` であることで観測する
- **観測点**: AC1とAC2は**両方**観測しなければ機構が効いた証明にならない(Incident「修正内容」4)

### AC3 — 古いバンドルが対象外になる

- **Given** `semaphore-<id>/summary.json` の mtime が閾値より古く、`_investigations/` に対応する成果物が無い
- **When** `incident-investigate.py` を1回実行する
- **Then** そのバンドルは選ばれず、成果物も作られない。終了コードは `0`
- **根拠**: 2026-07-31時点でquoryには `semaphore-*` バンドルが**48件**あり(ansy側mirrorで実測)、閾値が無いと初回の切り替えで48件すべてがLLMへ投げられる

### AC4 — 1周期1件

- **Given** 未調査のバンドルが2件以上ある
- **When** `incident-investigate.py` を1回実行する
- **Then** 生成される成果物は**1件だけ**である

### AC5 — 選定順序

- **Given** 未調査のバンドルが2件以上あり、mtimeが異なる
- **When** `incident-investigate.py` を1回実行する
- **Then** **古い方**が選ばれる(積み残しが飢餓状態にならないこと。新しい方を優先すると、古い未調査バンドルが永久に処理されない経路ができる)

### AC6 — 通常のansible実行がcallbackを読み込まない

- **Given** `ansible.cfg` から2行を外した状態
- **When** 任意のplaybookを `--check` または `--syntax-check` で実行する
- **Then** callback pluginがロードされない。**キューディレクトリが存在する環境(quory)でも、キューファイルが新規に作られないことで観測する**
- **注**: plugin側の `CALLBACK_NEEDS_ENABLED = True` により `callbacks_enabled` から外れれば発火しない(2026-07-31に実測済み。`docs/ai/reviews/incident_auto_investigation/2026-07-31_005_u2_implement.md`)

### AC7 — 既存の失敗系の挙動が変わらない

- **Given** バンドルは存在するが `task-time` がジョブの終了を返さない、またはLLM呼び出しが失敗する
- **When** `incident-investigate.py` を1回実行する
- **Then** 何を試みて何が取れなかったかを書いた成果物が `status: failed` で残り、終了コードは `2` になる(IC-038、既存AC6と同じ)

## 7. 成功指標

- **本番で、Semaphoreジョブの失敗から30分以内に `_investigations/semaphore-<id>.json` が出る。** 内訳は捕捉の周期(最大5分)+ 調査timerの周期(1分)+ LLM呼び出し(最大300秒)。
- `semaphore-495`(この問題で滞留している1件)が、切り替え後の最初の対象として拾われる。

## 9. タイムライン考慮

- **この修正が入るまで、Semaphoreジョブが失敗してもバンドルは作られるが調査は起動しない。** 証拠の保全には影響しない(捕捉と転送は正常)。
- 本番反映には**Yoshinobuの `git commit` / `push` と、quoryでの `git pull --ff-only`、および `playbooks/incident_investigate_setup.yml` の再実行**が要る。quory作業ツリーの自動同期は2026-07-29に意図的に見送られている。
- **AC1の本番での観測(`semaphore-495` が実際に拾われること)は配備後にしか行えない。** 配備前の検証はscratch環境での選定ロジックの確認までであり、両者を混同しない。

## 10. 受け入れる代償(この設計が引き受けるもの)

1. **調査が捕捉に依存する。** 捕捉が止まればバンドルが作られず、調査も起動しない。callback経路は捕捉と独立していたため、この点では冗長性が下がる。引き受ける理由は、**その独立した経路が現に発火しなかった**ことにある(冗長性は動いて初めて冗長性である)。
2. **即時性が下がる。** 検出が最大5分遅れる(捕捉の周期)。ADR-009 (a) a-3 のConsに挙げた「最大5分の遅延」をここで受け入れる。
3. **playが始まる前の失敗を拾えない点は変わらない**(YAML syntax error等)。ただし**捕捉側はSemaphoreのDBを見るため、playbookが1タスクも走らずに失敗したジョブでもバンドルを作る** — この点はむしろcallback方式より広い。
4. **a-3(収集器から起動する)そのものではない。** 収集器(`recovery-exec`)にLLM起動を持たせるとIC-006(捕捉の段でLLMを使わない)に触れる。**走査するのは別unit・別identity(`yoshi`)であり、捕捉の段は決定論的なまま**である。この区別を実装で崩さない。
