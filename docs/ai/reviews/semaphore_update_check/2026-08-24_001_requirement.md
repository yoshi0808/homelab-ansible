# requirement: Semaphore の新版が出たことを検知する

起案: Coordinator / 2026-08-24 / 依頼者: Yoshinobu

## 1. 問題定義

**Semaphore の新版が出ても、誰も気づかない。**

`apt` リポジトリが存在せず、`.deb` は GitHub Releases からしか取れない(`docs/ai/context/system/semaphore.md`)。したがって **apt の月次判定にも週次のアップデート経路にも乗らない。** 2026-08-18 の 2.18.4 → 2.19.8 は、Yoshinobu が新版の存在に気づいて手で当てた。

**適用そのものは既に手順化されている**(`docs/ai/reviews/semaphore_upgrade/2026-08-18_002_manual_procedure.md`、8節)。**残っているのは検知だけである。**

## 2. ゴール

- **新版が出たことを、人が気づかなくても分かる状態にする。**
- **prerelease を追わない。** メインストリームだけを見る。
- **判定できないときに黙らない。**

## 3. 非ゴール

- **適用しない**(Yoshinobu 決定、2026-08-10)。当てるのは人で、手順は既存の手順書に従う。**本案件は `dry_run` に相当する検知だけを持つ。**
- **系統(track)を固定しない。** Semaphore に LTS の区分は無く、`releases/latest` が prerelease を除外するため、**追う対象は「Latest」1つで足りる**(§6)。prometheus の `track` に当たる機構は作らない。
- **community 版への切り替えを扱わない。** 別の申し送り(`status.md`)であり、版上げと同時に行う判断である。
- **`.deb` を取得しない。** 検知は版の比較までとし、成果物をダウンロードしない。

## 4. 要求

| # | 要求 |
|---|---|
| R1 | **現在版は `semaphore version` の出力の先頭 `X.Y.Z` を使う。** 実測値は `2.19.8-3449a04-1786894505` の形で、コミットとビルド番号が続く。**この2つを版の比較に使わない** |
| R2 | **上流は GitHub Releases の `releases/latest`。** **prerelease を除外するロジックを自前で書かない** — `releases/latest` が構造的に除外する(§6)。**tag 一覧を引いて自分で選り分けない** |
| R3 | **対象は `ansy` と `quory` の2台。** 両方が Semaphore を持つ |
| R4 | **通知に `現在版 → 新版` と release ページの URL を載せる。** 版を落とした通知にしない |
| R5 | **検知だけを行う。** 適用・ダウンロード・サービス操作を一切含めない |
| R6 | **次の3つを「更新なし」と区別する** — ①取得・parse・比較の失敗 ②`releases/latest` の版が**現在版より古い**(リポジトリ側で Latest を手で固定した場合に起こりうる) ③現在版が読めない |

## 5. 受入条件

| # | AC | 検証者 |
|---|---|---|
| AC1 | 現在版と `releases/latest` が一致するとき、**更新なしとして静かに終わる** | Tester |
| AC2 | 新版がある状況で、**`現在版 → 新版` と release ページ URL を含む通知が出る** | Tester(fixture) |
| AC3 | **`v2.20.0-alpha1` のような prerelease を更新候補として出さない** | Tester |
| AC4 | R6 の3つが、**更新なしと区別できる形で観測できる**(通知とジョブの終了コードの両方) | Tester(fixture) |
| AC5 | 適用・ダウンロード・サービス操作のタスクが1つも無い | Reviewer |
| AC6 | `--syntax-check` rc=0 | Implementer |

## 6. `releases/latest` を使う根拠(2026-08-24 実測)

| tag | prerelease | |
|---|---|---|
| `v2.20.0-alpha1` | **True** | 2026-08-21 |
| **`v2.19.8`** | False | **`releases/latest` が返す** |
| `v2.19.6-rc1` / `v2.19.5-beta12` ほか | True | |
| `v2.18.29` / `v2.18.28` | False | |

**alpha / beta / rc がすべて `prerelease=True` で運用されている。** したがって `releases/latest` を引けばメインストリームだけが得られ、**除外ロジックを自分で持つ必要が無い。**

**ただし GitHub の「Latest」はリポジトリ側で手動固定できる。** 既定は「最新の非prerelease」だが、そうでない状態を作れる。**R6 ② はこれへの手当てである。**

## 7. 周期

**月次を採る。** `docs/ai/policies/ubuntu_vm_patch_policy.md` `UV-085` の軸で、**版が上がるものはアップグレード側(月次)**である。prometheus の週次は系統内のパッチを見るもので性格が違う。

**Semaphore の schedule に載せてよい** — 検知は Semaphore 自身を再起動しないため(2026-08-10 の決定に明記)。

## 8. 参考にする実装

`roles/prometheus_update_check/` を雛形とする。**ただし `track` の機構は持ち込まない**(§3)。流用するのは、GitHub Releases API を read-only で引く形、版の比較、判定不能を fail-closed にする構造である。

**`dry_run` は持たない**(2026-08-24 訂正)。当初この一覧へ「`dry_run` の明示必須」を含めていたが、**それは適用の経路があって初めて意味を持つ**。本 role は検知だけで適用が存在しないため、`dry_run` は何もゲートしない。**何も守らない必須引数を置かない。**
