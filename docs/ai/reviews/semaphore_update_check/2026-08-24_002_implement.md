### 0.1 Coordinatorからの指摘への回答: AC3(prerelease除外)は実装の欠陥ではない

Coordinatorから「`2.20.0`は`v2.20.0-alpha1`から`-alpha1`を落とした結果ではないか
(実装がtag一覧を引いて選別しているか、`releases/latest`の結果へ正規化を掛けて
いるのではないか)」という指摘を受けた。**調べた結果、これは実装のバグではなく、
このセッションが自分で用意したfixtureの値がそのまま本番へ出た**ことが原因である。

**根拠1: シナリオ2で使ったmock応答の中身**(`releases/latest`の代わりに参照させた
ローカルの静的JSON、実GitHubへは一切問い合わせていない)。

```
$ cat .../www/v2200.json
{"tag_name":"v2.20.0","html_url":"https://github.com/semaphoreui/semaphore/releases/tag/v2.20.0","prerelease":false}
```

`v2.20.0`という値そのものを、実在するバージョンかどうか確認せずにこのセッションが
手で書いた(「currentより大きい版」を作るために選んだ数値であり、GitHubの実データ
から導出したものではない)。`html_url`も同様に自分で組み立てた文字列で、実在しない
tagを指す。**通知に出た`2.19.8 → 2.20.0`とrelease URLは、このJSONの内容をそのまま
転記した結果であり、コードが`v2.20.0-alpha1`のようなものを加工して作った値ではない。**

**根拠2: 実装が上流のtagへ適用する正規表現は`regex_replace('^v', '')`(先頭の`v`を
落とすだけ)の1つだけであり、これ以外の加工を一切行わない**
(`roles/semaphore_update_check/tasks/main.yml`「Parse latest Semaphore release」)。
現在版側の正規化(`semaphore version`出力からcommit/build番号を落とす
`regex_findall`)は`semaphore_update_check_current_raw.stdout`だけを入力にしており、
`semaphore_update_check_latest_raw.json.tag_name`(上流のtag)には一切触れない —
2つの変数は完全に独立した別のtaskで計算され、共有される処理は無い。したがって
「現在版の正規化を上流のtagにも当てている」という経路自体がコード上に存在しない。

**根拠3(実測): 本物のprerelease形状のtagを与えて再現実験した**(§4.2シナリオ6、
このセッション内で実施済み)。`tag_name: "v2.20.0-alpha1"`(実在するalpha1タグと
同じ形)をmock応答に与えたところ、`regex_replace('^v', '')`の結果は
`"2.20.0-alpha1"`のままであり、これは`is match('^[0-9]+[.][0-9]+[.][0-9]+$')`
(厳密なX.Y.Z一致)を満たさないため`semaphore_update_check_latest_collected`が
`false`になり、statusは`collection_failed`になった(`update_available`にはならない、
rc=2)。**`-alpha1`を落として`2.20.0`という偽の候補を作る経路があるなら、この
シナリオでこそ再現するはずだが、再現しなかった。**

**tag一覧を取得する経路も存在しない** — `roles/prometheus_update_check`が持つ
`releases?per_page=...`相当のtask(track内の全リリースを列挙して選別する)は
このroleに実装していない(§3非ゴール、`roles/semaphore_update_check/tasks/
main.yml`はGitHubへ`releases/latest`を1回GETするtaskしか持たない)。

**結論: AC3(prerelease除外)はrequirement R2が意図するとおり成立している** —
`releases/latest`自体がprereleaseを返さない構造(§6実測)に依存しており、実装側は
それを裏切るような加工(サフィックスの切り捨て・tag一覧からの選別)を一切行って
いない。今回本番へ出た`2.20.0`は、**このセッションが検証用に手で書いた架空の値**
であり、実際の`releases/latest`(現在も`v2.19.8`)からは一度も来ていない。

**2026-08-24_003_review.md(独立レビュー)もこの説明を現物評価で再現し、確認した**
(「Coordinatorの当初推測は再現しない」「実装記録の訂正が正しい」)。

## 2. R6の3つをどう区別したか

`tasks/main.yml`の「Judge Semaphore update-check status」task(Phase 3)で、
比較を試みる**前**に3つの異常を独立した条件として先頭から順に判定する
(該当したものを採用、以降は評価しない)。

| 優先順 | requirement上の番号 | status | 条件 |
|---|---|---|---|
| 1 | ③ 現在版が読めない | `current_unreadable` | `semaphore version`のrc≠0、またはstdoutが`X.Y.Z`形式にmatchしない |
| 2 | ① 取得・parse・比較の失敗 | `collection_failed` | GitHub応答のHTTP status≠200、`tag_name`が`X.Y.Z`形式にmatchしない、または`html_url`が文字列でない・trim後に空(Finding 2 — R4が通知へ必須とするfieldの欠落・不正型・空白のみも取得成功の一部を欠いた状態として扱う) |
| 3 | ② releases/latestが現在版より古い | `latest_older_than_current` | 両方読めた上で`latest is version(current, '<')` |
| (通常) | — | `update_available` / `up_to_date` | 両方読めた上で`latest > current` / `latest == current` |

3異常はいずれも**両辺がsemver形式であると確認済みのときにしか`is version(...)`へ
到達しない**構造になっている(①と③のガードが先に通せんぼする)ため、「比較そのものが
失敗する」というR6①の後半("...比較の失敗")に対応する専用分岐は別途持たない —
比較に到達する時点で入力の正当性は既に保証されているため、比較自体が失敗する余地が
構造的に無い。

AC4(「通知とジョブの終了コードの両方」で区別)は、`current_unreadable` /
`collection_failed` / `latest_older_than_current`の3つで`ansible.builtin.fail`
(rc非ゼロ)を発生させ、`update_available` / `up_to_date`はrc 0のまま完走させることで
満たした。

## 3. 選んだcronとその根拠

`roles/semaphore_templates/defaults/main.yml`の`semaphore_schedules_catalog`へ
次のエントリを追加した。

```yaml
- name: "SAFE: Semaphore update check monthly"
  template: "SAFE: Semaphore update check"
  cron: "0 20 10 * *"
  active: true
  task_params:
    environment: "{}"
```

**毎月10日 20:00 JST。** 選定理由はカタログ内コメントとして同じ差分に書いた
(`roles/semaphore_templates/defaults/main.yml`のエントリ直前コメント)。要点:

- requirement §7「月次を採る」(`docs/ai/policies/ubuntu_vm_patch_policy.md`
  UV-085: バージョンを跨ぐ変化はアップグレード側=月次)に従い月次を選んだ。
- **このカタログに載っている他の20エントリの実行時刻と20時台は重ならない**
  (00:10=1日Cloudkey、00:40=毎日drift check、03:30=毎日nightly、
  05:30-05:50=毎日healthcheck群、06:00=土曜Weekly Full Patch/日曜Cert renew、
  06:30=毎日recovery monitoring check、12:00=毎日db backup、
  17:00-18:30=金曜週次群、18:00=木曜Proxmox snapshot check、
  18:15=2日Ubuntu vm full upgrade dry-run、18:30=28日Proxmox backup restore
  verify)。**当初この列挙からThu 18:00のProxmox snapshot checkが抜けており、
  レビュー(2026-08-24_003_review.md Suggestion #1)で指摘を受けて補った** —
  非衝突という結論自体は変わらない。
- 日にち(10日)も既存の月次3件(1日・2日・28日)と重ならない。

**この判断は当初カタログだけを根拠にしており、`docs/ai/context/system/
semaphore.md`が明記するとおり「このカタログだけでは全体の衝突を判定できない」**
(UniFi Console/AP・スイッチ/Protectの自動update、Proxmoxのローカル/NASバックアップ、
ZFS TRIM・scrub、systemd timer、unattended-upgrades等はカタログの外にある)。
それらを横断して持つのはYoshinobuが別途管理するNotionの「バッチ処理工程管理表」
(このリポジトリの外)であり、Implementerはこの表を読める立場に無い。**この選定は
Coordinatorの確認待ちとして本節に書き、確認を依頼した。**

**2026-08-24、Yoshinobuがこの表を実際に確認し、20時台にこの表側の予定が無いことを
確かめた上でこの時刻を選んだ。これによりカタログだけでは埋まらなかった部分が確定し、
`cron: "0 20 10 * *"`は確定である。** カタログ内コメントも、この確認が「選定時点で
確認した事実」であり「20時台は空いている」という恒久の性質の記述ではないこと、
**この行自身が毎月10日20:00の枠を占有すること**、Notionの表が横断の正本であり
カタログだけでは判定できないことの3点が伝わる形へ書き直した — 2026-08-23に
`semaphore_schedules_catalog`の別エントリで「コメントを書いた変更自身がその枠を
埋めていた」誤り(commit `7676c78`で是正済み)を再現しないための書き方である。

## 6. 判断メモ

- **`dry_run`変数を持たせていない。** このroleには適用の分岐そのものが無い
  (§3非ゴール、R5)ため、ゲートする対象を持たない`dry_run`は意味の無い飾りになる。
  requirement §8は当初「流用するのはdry_runの明示必須」と書いていたが、
  Coordinatorがこれをrequirement側の誤りと判断し§8を訂正した(レビューFinding 3、
  2026-08-24)。実装はこの訂正の前後で変更していない — 最初から`dry_run`を持たせて
  いなかった判断がそのまま正本と一致した。流用したのは「明示必須・fail-closedに
  する」という設計原則であり、`dry_run`という変数名ではない(defaults/main.ymlと
  tasks/main.ymlのヘッダにこの判断を明記した)。
- **`tester-gate`は`role-guarded`(Finding 1、レビューで訂正)。** 当初
  `safe-readonly`としていたが、このplaybookの唯一の外部状態変更はSlack通知であり、
  TS-005の定義(「副作用がSlack通知のみで、common_slackの抑止guardで止まる」)は
  `role-guarded`そのものを指す。`playbooks/semaphore_update_check.yml`のヘッダを
  修正した。Semaphore template UI上の`class: SAFE`(`roles/semaphore_templates/
  defaults/main.yml`)とは別軸であり、そちらは変更していない。
- **`html_url`の成功条件を「非空」から「文字列であり、trim後も非空」へ強化した
  (Finding 2、レビューで2回発見)。** 1周目: 修正前は`tag_name`さえ有効なら
  HTTP status 200・`html_url`欠落でも`update_available`かつrc 0になり、
  R4(release URL必須)とR6①(取得失敗を更新なしと区別)の両方に反していた
  (§4.2シナリオ7で発火確認)。2周目: `length > 0`だけの判定では、非空の
  object/listが「URLとして成功」扱いになる、空白だけの文字列も同様、`null`や
  数値は`length`評価自体が失敗して通知の前でtask failureになりうる、という
  3つの取りこぼしが指摘された。`semaphore_update_check_latest_url_valid`という
  単一のfactへ「`type_debug == 'str'` かつ `trim`後の`length > 0`」を集約し、
  `semaphore_update_check_latest_collected`(main.yml)と診断分岐(notify.yml)の
  両方がこのfactだけを参照する形にした(判定ロジックの二重定義を避ける、
  `docs/ai/core.md`「値を二重に持たない」)。`and`の短絡評価により、文字列でない
  値へ`trim`を通す前に判定が確定するため、型に起因する評価例外は起きない。
  8種類の型(正常文字列/空文字列/空白のみ/object/list/null/数値/フィールド欠落)
  すべてで使い捨てfixture実評価により発火を確認した(§4.2シナリオ8a〜8g、7)。
  **URLの形式(スキーム・ホスト名)までは検査していない** — Coordinatorの指示
  どおり、型と非空はR4/R6を満たすために必要な最小限であり、狭い正規表現で
  GitHub側の形式変化に対して脆くする判断は採らなかった。
- **release URLは`html_url`をAPI応答からそのまま使い、自前のURL組み立てテンプレート
  を持たない。** prometheus_update_checkの`_release_page_base`相当の変数を追加
  しなかった(値を二重に持たない、`docs/ai/core.md`)。
- **`Validate Semaphore update-check configuration`のassertを
  `semaphore_update_check_api_timeout`のみに絞った。** binary/repo/api_urlの
  相互一貫性検査(prometheus_update_check流)は、このroleには保護すべき
  backup/restoreのpath構築が無いため安全上の価値が薄く、かつTester(fixture)が
  AC2〜AC4を再現するために必要な`-e`上書きを妨げる(tasks/main.ymlのコメントに
  詳細)。
