# Code Review: Semaphore update check

Reviewer: Codex / 2026-08-24  
Verdict: **Request Changes**

## Summary

`releases/latest`だけを1回GETする構造、prerelease tagを候補へ変換しないこと、現在版と上流tagの独立処理、後方参照を使わない`regex_findall`、R6の主要3状態、適用task不在、カタログ内cron非衝突は確認できた。Coordinatorの「通知の2.20.0はalpha suffixを落とした値」という当初推測は現物と一致せず、実装記録の訂正が正しい。

一方、playbookの`tester-gate`分類がSlack副作用を持つ実装と矛盾し、必須のrelease URLが欠落しても検知成功になる。またrequirement §8が明示する`dry_run`必須と実装の省略が未合意のまま競合する。前2件はコード/安全分類の欠陥、3件目は正本の解釈をCoordinatorが閉じる必要があるためRequest Changesとする。

## Prerelease / Normalization Evaluation

GitHub公式REST API文書の[`Get the latest release`](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)は、latestをnon-prereleaseかつnon-draftの最新releaseとして定義する。実装のendpointはdefaultsの`.../releases/latest` 1本だけで、`releases?per_page=`やtag一覧を取得するtaskは無い。requirement §6の観測だけでなく、上流の公式契約とも一致する。

現物のparse/status taskを`yaml.safe_load`で名前指定抽出し、localhostの実`ansible-playbook`で評価した。

| 入力 | current parse | latest parse | status |
|---|---|---|---|
| current=`2.19.8-3449a04-1786894505`, latest=`v2.19.8` | `2.19.8` | `2.19.8` | `up_to_date` |
| 同current, latest=`v2.20.0` | `2.19.8` | `2.20.0` | `update_available` |
| 同current, latest=`v2.20.0-alpha1` | `2.19.8` | **`2.20.0-alpha1`（suffix維持）** | `collection_failed` |

- 上流tagへ行う加工は`regex_replace('^v', '')`だけで、alpha/beta/rc suffixを落とさない。strict `X.Y.Z` matchがprerelease形状を拒否する二重の安全も実評価できた。
- 現在版は`current_raw.stdout`だけを`regex_findall`へ渡し、上流版は`latest_raw.json.tag_name`だけを別taskで処理する。変数・task・regexに共有処理は無く、現在版のsuffix除去が上流tagへ流れる経路はない。
- `regex_findall`はcapture groupを直接返し、replacement引数を持たない。実評価でcurrent=`2.19.8-3449a04-1786894505`から`2.19.8`を得た。Prometheus案件の`\1`/`\g<1>`問題が起きる後方参照面は存在しない。
- 本番Slackへ出た架空`2.20.0`はコードから導出された値ではなく、実装記録§0.1が示すmock JSONのtagを先頭`v`だけ除いて転記した結果、という説明が現物と一致する。

## R6 / Failure-path Check

抽出した現物taskの評価結果:

| ケース | status | 通知分岐 | 最終fail |
|---|---|---|---|
| current rc≠0またはparse不能 | `current_unreadable` | `#alerts` / error | 対象 |
| HTTP失敗またはtag parse不能 | `collection_failed` | `#alerts` / error | 対象 |
| latest < current | `latest_older_than_current` | `#alerts` / error | 対象 |
| latest = current | `up_to_date` | skip | 非対象 |
| latest > current | `update_available` | `#patches` / info | 非対象 |

`set_fact`のternaryはcurrent→latest取得→older→newer→equalの順で全域を覆い、入力がstrict digit 3成分へ限定された後にだけ`version`比較へ到達する。3異常は通知includeの後に`ansible.builtin.fail`対象となるため、best-effort通知の成否と独立した非0 job signalを持つ。Finding 2のURL欠落だけが、現在このラダーをすり抜けるrequired-field parse failureである。

## AC5 / Security / Reuse Check

- Role/playbookで使うmoduleは`assert`、`set_fact`、`command`、`uri`、`debug`、`include_tasks`、`fail`、`import_role`だけである。
- 唯一の`command`はargv形式の`/usr/bin/semaphore version`で、shellを介さない。ダウンロード、`apt`/`dpkg`、`get_url`、`copy`、`file`、`unarchive`、`systemd`/`service`、reboot、backup/rollback、handlerは存在しない。**AC5はPASS**。
- APIはGETだけで、`return_content`を読む。tag一覧・asset取得・`.deb` URL取得はない。
- Slackは既存`common_slack`を再利用し、独自Webhook処理やsecret出力を追加していない。diagnosticは200文字で切る。ただし、この再利用こそplaybook分類を`role-guarded`にする根拠である（Finding 1）。
- API URL/binaryはrole prefix付きdefaultsで、commandはargv形式。新しいshell injection面や`delegate_to`/lookupによる信頼境界越えはない。

## Schedule Check

- rendered template名の重複は0、scheduleが参照する未定義templateは0。

- System Contextが警告するとおり、カタログ外の横断表はReviewerから読めない。外部の「バッチ処理工程管理表」との非衝突は未確認で、Coordinator/Yoshinobuの照合がschedule確定前に必要である。これは実装記録も正しく未確認事項としている。

## Test Gap Review

- Implementer fixtureはequal/newer/older/current parse/HTTP/JSON/prereleaseを実行しており、主要statusと通知/rcを覆う。
- **不足**: status=200・valid tag・`html_url`欠落/不正のfixtureが無く、R4/R6のFinding 2を逃した。修正後はこのnegative fixtureを追加し、`collection_failed`、alerts本文、非0終了を確認すること。
- Testerは実ホスト上の2台のversion出力、2 host到達、実scheduleの登録/起動を別工程で確認する必要がある。本レビューでは実ホストへ触れていない。
- 本番Slackの到達は既に誤送信で観測されたが、これをテスト成功として再利用しない。今後のfixtureは`skip_notifications=true`またはAI抑止を明示し、rendered本文だけを確認すること。

## What Looks Good

- track機構を持ち込まず、GitHub release一覧を自前で選別していない。
- prerelease suffixをstable候補へ変換する処理はなく、Coordinatorの当初懸念は再現しない。
- current/latestの処理は入力変数もtaskも独立し、後方参照を避けた選択は有効。
- `latest_older_than_current`を専用status・alerts・非0終了にし、手動Latest固定が永久に黙る経路を塞いだ。
- `up_to_date`だけを通知skipし、update_availableは現在版→新版とAPI由来URLを描画する構造である（URL field検証はFinding 2）。
- template/scheduleを同じcatalog変更に含め、scheduleのtemplate名がrender結果と一致する。
- 実装者は本番Slack誤送信を1回で止め、隠さず§0に記録した。以後の送信抑止も記録されている。本レビューでは通知経路を一度も呼んでいない。
