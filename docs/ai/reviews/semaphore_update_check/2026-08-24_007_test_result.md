## 3. AC3 — `v2.20.0-alpha1`のようなprereleaseを更新候補として出さない

**PASS。二重の根拠で確認した。**

**根拠1(実データ、2026-08-24実測、Coordinator依頼分)**:

| tag | prerelease | |
|---|---|---|
| `v2.20.0-alpha1` | **True** | 2026-08-21公開 |
| `v2.19.8` | False | **`releases/latest`が実際に返す値** |
| `v2.19.6-rc1` / `v2.19.5-beta12` | True | |
| `v2.18.29` / `v2.18.28` | False | |

`releases/latest`を素で叩くと`v2.19.8`が返り、`v2.20.0-alpha1`は候補にすら現れない。**AC1の実データ実行(§1)がそのままこの状態でのAC3裏付けになる** — roleは実際に`up_to_date`(現在版2.19.8と一致)を報告し、alphaを候補として一切示さなかった。

**根拠2(fixture、コードの防御そのものを実行で確認)**: 「releases/latestが構造的にprereleaseを除外する」という前提が将来崩れた場合に備え、`tag_name`にprerelease形状の値(`v2.99.9-alpha1`)を直接与えるfixtureを実行した。結果: `status: collection_failed`(`update_available`にはならない)、rc=2。roleの`Parse latest Semaphore release`は`v`を落とすだけで`-alpha1`のようなsuffixを一切加工しないため、`X.Y.Z`厳密一致(`is match('^[0-9]+[.][0-9]+[.][0-9]+$')`)に失敗し、`semaphore_update_check_latest_collected`が`false`になる経路を実測で確認した。

**根拠1だけで足りるか**: 足りない。根拠1は「今のGitHubの運用がこうなっている」という外部事実の確認であり、`releases/latest`の除外はGitHub側の仕様であって本実装の担保ではない(requirement §6も「GitHubの"Latest"はリポジトリ側で手動固定できる」と明記— R6②はまさにこれへの手当て)。**根拠2を合わせて初めて「万一prerelease形状の値がAPI応答に混ざっても、このroleのコード自身が候補として通さない」という主張が成立する。** 両方を確認したのでPASSとした。
