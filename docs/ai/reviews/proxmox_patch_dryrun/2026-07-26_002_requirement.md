# Requirement: Proxmox Patch Dry-run 単一ノード対応

**日付**: 2026-07-26
**Role**: Tech Lead(`techlead`)
**Owner**: `techlead`(無印trio)
**関連**: `2026-07-26_001_single_node_dryrun_investigation.md`、`docs/ai/adr/002-proxmox-patch-dryrun-single-node.md`

## Tier判定

**Tier 4**。

`skills/delegation-tier/SKILL.md`の判定手順に従うと、本案件は「引き上げ条件」に複数該当する。

- **Policy本文の再編**: `docs/ai/policies/proxmox_patch_policy.md`のSB-023を、単一ノード実行を明示禁止する現行文から条件付き許可へ書き換える。あわせて§4.1のStatus解釈注記、§7の制約追加、変更履歴への追記が必要で、Policy本文の複数箇所にまたがる改訂になる。
- **安全境界の再定義**: 「dry-runは単一ノードでも実行可、ただしapply側は引き続き両ノード必須」という新しい境界線を導入する。これはPolicy上の許可範囲そのものの変更である。
- **多ファイル横断**: `playbooks/proxmox_patch_dryrun.yml`、`roles/proxmox_patch_dryrun/tasks/main.yml`(複数箇所)、`docs/ai/policies/proxmox_patch_policy.md`、`docs/ai/context/operations/proxmox-patch.md`にまたがる。

これらはruntime影響の有無に関わらずTier 4への引き上げ条件に該当するため、Coordinatorからの引き渡し時点でTier 4として扱う。Implementer固有Skill(`skills/ansible-implementation-style`)、Reviewer固有Skill(`skills/code-review`、`skills/duplication-reuse-check`、`skills/ansible-security-review`)、Tester固有Skill(`skills/test-strategy`)がいずれも適用対象であり(role/playbook/Policyの実コード変更を伴うため)、Tier 3以上への昇格自体は妥当。そのうえで上記引き上げ条件によりTier 3ではなくTier 4とする。Tier 4の運用に従い、調査(`2026-07-26_001_...md`)→Coordinator受入→実装の2段階とし、Reviewerは逐行照合を行う。

## 1. 問題定義

homelabでは夏季の室温対策として`pve1`を平日日中シャットダウンする運用にしている(`pve2`は常時稼働)。毎日実行される`playbooks/proxmox_patch_dryrun.yml`(パッチのdry-run検出、実適用はしない)は、pve1停止時に構造的に機能しなくなっている。原因は3層にわたる。

1. playレベルの`any_errors_fatal: true`により、pve1がUNREACHABLEになるとpve2の処理まで中断される。
2. `roles/proxmox_patch_dryrun/tasks/main.yml`が複数箇所で`hostvars['pve1']`/`hostvars['pve2']`を固定参照しており、`--limit pve2`で回避しようとしても未定義変数エラーで失敗する。
3. `docs/ai/policies/proxmox_patch_policy.md`のSB-023が単一ノードdry-run実行を明示的に禁止しており、実装を直しても現状はPolicy違反になる。

2026-07-26、Yoshinobuより「SB-023の制約対象が誤っていた。dry-runは版数差分(drift)を発生させないため単一ノードでも許可すべきで、drift回避が必要なのはapply側」という方針確定があった(詳細は`2026-07-26_001_single_node_dryrun_investigation.md`§4)。

## 2. ゴール

- pve1停止中でも、到達可能な側のノード(通常はpve2)のpatch候補情報(dry-run結果)を日次で取得できるようにする。
- 「`--limit`による意図的な単一ノード実行」と「意図しない通信断(UNREACHABLE)」を通知文面レベルで区別する。
- apply側(実パッチ適用、SB-027/SB-028/SB-032)の「両ノード揃った状態を要求する」というdrift回避の安全境界は変更せず維持する。
- SB-023を新しい意図に合わせて改訂する(新規SB番号を採番、廃止番号は再利用しない)。
- 両ノードが揃っている通常週は、既存のfixed-pair dry-run結果(Status/Urgency/report/通知)が変更前と同一であることを保証する(回帰なし)。

## 3. 非ゴール

- apply/evacuate/weekly full側のPolicy・実装変更(SB-027/SB-028/SB-032等の条件そのものは対象外)。
- pve1・pve2が両方到達不能な場合の新しい代替経路の設計(現行同様、明確な失敗メッセージで停止する。サイレント成功にしないことのみが要件)。
- `scripts/codex-classify.sh`のプロンプト全文書き換え(全文精読して問題が見つかった場合のみ、必要最小限の修正に留める)。
- 週次スケジュール自体の変更(Semaphore UI側の設定はscheduler正本であり本リポジトリの変更対象外)。
- SB-023以外のPolicy節の全面書き直し(該当箇所への追記・条件分岐化に限定する)。

## 4. ユーザーストーリー

Yoshinobuとして、夏季にpve1が日中停止していても、pve2側のパッチ候補情報を毎日欠かさず把握したい。なぜなら、パッチ情報の欠測が続くと、pve1復帰後にまとめて対応すべき更新の全体像が見えにくくなるからである。同時に、apply(実際のパッチ適用)については、pve1/pve2間で版数差分が生じないという既存の安全性を一切妥協したくない。

## 5. 要件(MoSCoW)

### P0(Must)

- `roles/proxmox_patch_dryrun/tasks/main.yml`のPhase 2以降を、`hostvars['pve1']`/`hostvars['pve2']`固定参照ではなく、実際に到達・処理できたノードの動的集合(`ansible_play_hosts`相当)に基づく処理へ変更する。
- `playbooks/proxmox_patch_dryrun.yml`の`any_errors_fatal: true`を除去する。あわせて、到達・処理できたノードが0件の場合に明示的に失敗する(サイレントな空処理にしない)ガードを追加する。
- 通知文面(件名・本文)から`groups['proxmox']`による「pve1/pve2 ともに」等の両ノード決め打ち表現を除去し、実際に処理したノード集合を動的に表示する。
- `docs/ai/policies/proxmox_patch_policy.md`のSB-023を、dry-runは片方ノードでも実行可とする条件分岐へ改訂する。apply側の両ノード要求(SB-027/SB-028/SB-032)は変更しない。

### P1(Should)

- `_final_report`の`reboot_required_pve1`/`reboot_required_pve2`固定キーを、ノード数に依存しない動的な形式へ再設計する。
- 「意図しない通信断」と「`--limit`による意図的単一ノード実行」を、通知文面上で異なる表現に区別する。

### P2(Could)

- `scripts/codex-classify.sh`のプロンプトテンプレート全文を精読し、暗黙のクラスタ前提文言(パラフレーズ)がないか確認する。
- `docs/ai/policies/proxmox_patch_policy.md`§4.1(Status表)および§7(制約・禁止事項)に、単一ノード実行時のStatus解釈(相手ノード未検証であること、`PATCH_READY`が「このノードだけは」の意味になること)を追記する。
- `docs/ai/context/operations/proxmox-patch.md:30`の「dry-runまたはre-dry-run」という一文を、Policy改訂後の内容に合わせて更新する。

## 6. 成功指標

- pve1停止中の日次dry-run実行がエラー終了せず、pve2の候補情報を含むreportとSlack通知が生成される。
- 生成された通知・reportに「pve1/pve2 ともに」等の事実と異なる文言が出力されない。
- 両ノードが揃っている通常週のfixed-pair dry-run結果(Status/Urgency/report内容)が、本変更の前後で同一である。
- apply/weekly full側のgate条件(両ノードhealthcheck OK、dry-run `PATCH_READY`)が本変更の影響を受けない。

## 7. オープンクエスチョン

- `reboot_required`の動的dict化に伴うreport JSON schema変更について、repo内消費者は0件と確認済み(`2026-07-26_001_...md`§5)だが、repo外(Semaphore dashboard等)での参照有無は未確認。実装着手前にYoshinobuへ確認する。
- 単一ノード実行時に`classification.common`/`{node}_only`(比較対象がいないため単一ノードでは自明値になる)をreportから省略するか、そのまま出力し通知文言だけで補足するかは、Implementer実装時の軽微な設計判断としてTech Leadへ相談してよい。
- SB-023改訂で新設するSB番号の具体的な採番と正確な文面は、ADR-002の方向性に沿ってImplementerが起案し、Reviewerが既存Policy全文との整合を逐行照合する。

## 8. タイムライン考慮

- pve1の夏季シャットダウンは季節運用であり、実装完了が遅れるほど日次dry-runの欠測日数が積み上がる。P0範囲を優先して実装・検証まで通す。
- P1/P2は同一サイクルで続けてよいが、P0のみを先行してReviewer/Tester検証まで通し、P1/P2を後続の別サイクルに分けることも許容する(Implementerへの指示でTech Leadが明示する)。

## 受入条件(Given/When/Then)

**AC1**: Given pve1が夏季シャットダウン運用により到達不能で、pve2が到達可能かつhealthcheck OKである。When 日次スケジュールが`playbooks/proxmox_patch_dryrun.yml`(`--limit`なし、`hosts: proxmox`のまま)を実行する。Then playbookはエラー終了せず、pve2のみを対象とするdry-run結果(Status/Urgency/report/Slack通知)を生成し、通知文面はpve1が未到達であった旨を明示する。

**AC2**: Given pve1・pve2の両方が到達可能でhealthcheckが共にOKである。When 従来どおり`playbooks/proxmox_patch_dryrun.yml`を実行する。Then 結果のStatus/Urgency/report内容は本変更前と同一のfixed-pair dry-run結果になる(回帰なし)。

**AC3**: Given オペレータが明示的に`--limit pve2`を指定して実行する。When playbookが完走する。Then 通知文面はこれが`--limit`による意図的な単一ノード実行であることを、通信断ケース(AC1)と異なる文言で示す。

**AC4**: Given pve1・pve2の両方が到達不能である。When playbookが実行される。Then playbookはmerge処理へ進まず、到達ノードが0件である旨の明確なメッセージで停止する(空reportやサイレント成功にしない)。

**AC5**: Given 単一ノードdry-runの結果が`PATCH_READY`である。When `proxmox_patch_weekly_full.yml`等のapply系flowがgate条件を評価する。Then 単一ノードdry-runの`PATCH_READY`は、apply系が要求する「両ノードのdry-run PATCH_READY」条件を満たしたとはみなされない(SB-032の要求は変更しない)。
