## 3. AC4(両node到達不能時の明示fail)の既知の制約 — Coordinator/Tech Leadへの確認事項

> **2026-07-26 追記(本節の制約は§9で解消済み)**: 本節が記録する「両node到達不能時にAC4ガードが発火しないdead code」という制約は、§9の`ignore_unreachable`対応により**解消した**。到達不能nodeがplayから即座に落ちなくなったことで、全node到達不能でも生存メンバーとしてrun_onceを担げるhostが残り、明示メッセージ付きのfailが実際に発火する(decoy実測、§9-4)。ガードtaskの設置場所はroleのPhase 2冒頭から`playbooks/proxmox_patch_dryrun.yml`のplay冒頭へ移した(roleのPhase 2は「到達nodeが1つ以上ある」ことが前提で、そこへ辿り着けない以上roleの中では原理的に捕まえられないため)。以下§3-1〜§3-4は当時の判断根拠として保存する。§3-2で却下した案A/案Bの評価自体は今も有効(今回採った方法はそのどちらでもない)。

### 3-1. 経緯

初回実装では`run_once: true` + `delegate_to: localhost`の単純なガードtaskを追加したが、decoy inventory(127.0.0.1閉ポート/`ansible_connection: local`、実host名・実IPなし)による実地検証で、**同一play内の全hostが失敗/到達不能になった時点でAnsibleのlinear strategyがそのplayの残りtaskを一切スケジュールしなくなり、delegate先がlocalhostであってもこのガードtask自体が発火しないdead codeになる**ことが判明した(`ansible.builtin.ping`/`ansible.builtin.fail`のいずれで全host失敗させても同じ、`meta: clear_host_errors`を挟んでも同じ)。一方、pve1/pve2の片方だけが失敗する場合(AC1/AC3の実際の想定シナリオ)はこの問題が起きず、ガードtaskも通知文言区別も正しく動作することを確認済み(§4参照)。

Coordinatorの指示を受け、この制約を解消する設計を2案検討・実地検証したが、いずれも本caseの4ファイル限定scopeでは実装できないことが判明したため、単純なガードtask設計(dead codeの制約を残す)へ戻した。

### 3-2. 検討・却下した案

**案A: `hosts: proxmox:localhost`(単一play内にlocalhostを追加)**

localhostを常に生存するplay memberとして加えれば、pve1/pve2が両方失敗してもrun_onceタスクを引き継ぐhostが残るはずだった。両node健全時はrun_onceが引き続き`groups['proxmox'][0]`(通常pve1)を選ぶことも確認済み。しかし実地検証の結果、**`roles/proxmox_healthcheck`(本caseのscope外)の`Build Semaphore health summary` task(`run_once`、delegate_toなし、`{% for host in ansible_play_hosts %}`で`hostvars[host].proxmox_report`を参照)が、localhostがhealthcheck role自体をskip(`when`で除外)しているだけで`ansible_play_hosts`には残り続けるため、`hostvars['localhost'].proxmox_report`未定義でJinja renderingが失敗する**ことが判明した。これは異常系だけでなく**両node健全時の通常運行でも毎回発生する**致命的な回帰であり、`roles/proxmox_healthcheck`はscope外かつ他playbook(`proxmox_healthcheck.yml`、`proxmox_patch_weekly_full.yml`)共有roleのため修正できない。案Aは却下。

**案B: play分離(collect playとmerge playを分ける)**

`hosts: proxmox`のままplay 1(healthcheck + Phase 0/1)を無変更で残し、play 2(Phase 2-6)を独立したplayとして追加する案。play 2で`gather_facts: false` + 全task `delegate_to: localhost`にすれば、pve1/pve2へ実際に接続する task が皆無になるため、play 2単体では両nodeとも「失敗していない」扱いのまま run_once が機能する、という仮説を実地検証した。

しかし検証の結果、**Ansibleは host の失敗/到達不能状態を playbook 実行全体を通じて(play境界をまたいで)保持しており**、play 1で両node が失敗すると、同じ `hosts: proxmox` を対象とする play 2 は(play 2自身が一度もpve1/pve2へ接続を試みていなくても)**開始すらされない**(`PLAY [...]`のbannerすら出力されない)ことを確認した。`meta: clear_host_errors`をplay 2の最初のtaskに置いても同じ結果だった。

play 2の`hosts:`を`localhost`単体にすれば play 1 の失敗と無関係に必ず開始されるが、その場合 `_final_status` 等の `run_once` factの格納先が `hostvars[groups['proxmox'][0]]`(通常pve1)から`hostvars['localhost']`へ変わる。`playbooks/proxmox_patch_weekly_full.yml:130-132`のコメントが明記するとおり、同playbookの`_status`変数は`hostvars[groups['proxmox'][0]]['_final_status']`を直接参照しており、この変更は同ファイル(scope外、4ファイル限定の対象外)の修正なしに壊れる。案Bも却下。

### 3-3. 現在の挙動(採用した設計)

- pve1/pve2の**片方**が失敗/到達不能な場合(AC1)、または`--limit`で片方のみを対象にした場合(AC3): ガードtaskは正しく機能し(`_reached_nodes | length == 0`は偽)、生き残った側のnodeだけでdry-runが完走し、通知文言も正しく区別される。**これが本feature本来の主目的(夏季pve1平日シャットダウン運用時の日次dry-run欠測解消)であり、正しく動作する。**
- pve1/pve2が**両方**失敗/到達不能な場合(AC4): 本ガードtask自体は発火しない(dead code)。**←この記述は§9で解消済み。現在は両node到達不能時に`playbooks/proxmox_patch_dryrun.yml`の`Fail if no proxmox node could be reached`が明示メッセージ付きで発火する(rc=2)。ただし「両nodeとも到達はできたがhealthcheck等でin-play失敗した」ケースは引き続き本ガードもplaybook側ガードも発火せず、下記のAnsible標準報告に委ねる**。しかし、Ansible自身が両hostを`UNREACHABLE`または`FAILED`として明示的に報告し(host別のfatalメッセージ、`PLAY RECAP`)、playbook全体が非ゼロ終了する(decoy検証実測: UNREACHABLEはrc=4、FAILEDはrc=2)。merge処理へは進まず、reportファイルも生成されない。AC4が求める「空reportやサイレント成功にしない」という安全性の実質は、本ガードtask自身のメッセージではなく、この**Ansible標準の失敗報告**によって満たされる。

上記のとおり、AC4を**独自メッセージ付きで**確実に発火させるには、本case外(`roles/proxmox_healthcheck`または`playbooks/proxmox_patch_weekly_full.yml`)への波及を伴う設計変更が必要である。以下いずれかの判断をCoordinator/Tech Leadに仰ぎたい。

### 7-2. 修正2: weekly_full.ymlのapply安全ゲート非対称性(Critical Issues #2、scope 4→5ファイルへ拡張、Yoshinobu承認済み)

### 8-1. バグの内容

`_node_reachability_note`(`roles/proxmox_patch_dryrun/tasks/main.yml`の`Build node reachability note text`task)は、`_unreachable_nodes`・`_limit_excluded_nodes`が両方空(=fixed-pairで両ノードとも正常参加、AC2が想定する通常時であり、日次実行で毎回通る経路)の場合、`{%- else -%}{%- endif -%}`という「静的文字列を一切含まないJinja制御構造のみ」のテンプレートになる。Ansibleの Templar はこの場合、レンダリング結果を空文字列`""`ではなく**Python の `None`** として`set_fact`する(Ansibleの既知の仕様: テンプレート全体がJinjaマークアップのみで構成され結果が空文字列になる場合の`None`変換)。この`_node_reachability_note`(値`None`)に対し`| length`フィルタを適用していた3箇所すべてで`object of type 'NoneType' has no len()`により例外終了していた。Tester実測での実際のクラッシュ地点は`Save minimal MD report for NO_UPDATES or BLOCKED`task(`content:`内の`{% if _node_reachability_note | length == 0 %}`)。

### 8-2. 修正内容

Coordinator指示に従い、原因側の是正と使用側の防御の両方を実施した。

1. **原因側**: `Build node reachability note text`task直後に、`_node_reachability_note`を`| default('', true)`で明示的に空文字列へ再coerceする新task(`Coerce None (from an empty pure-Jinja template) back to a real empty string`)を追加した。`default(default_value, boolean=true)`の第2引数`true`は「`None`もdefault適用対象に含める」ためのAnsible/Jinja既定filterの仕様であり必須。
2. **使用側(防御)**: `| length`を適用する3箇所すべてを`| default('', true) | length`へ統一した。
   - `roles/proxmox_patch_dryrun/tasks/main.yml`の`Save minimal MD report for NO_UPDATES or BLOCKED`(content内の`{% if %}`)
   - 同ファイルの`Set notification content for NO_UPDATES`(`_notify_body`内の`{% if %}`)

## 9. 終了コード4の解消(`ignore_unreachable`対応、2026-07-26、`2026-07-26_005_test_result.md`§13-4)

### 9-1. 背景と方針

Testerの実ホストAC1検証(pve1を実際にシャットダウンした状態)で、機能要件はすべて充足しているにもかかわらず**playbookプロセスの終了コードが`4`(`RUN_UNREACHABLE_HOSTS`)になる**ことが判明した(`2026-07-26_005_test_result.md`§13-4、§8項目6)。`failed=0`でpve2は完走し通知文面も正しいが、日次スケジューラ(Semaphore)は非ゼロ終了をタスク失敗として表示するため、夏季pve1シャットダウン期間中は毎営業日「赤い成功」が並び本物の障害と区別できない。すなわち本caseの目的である「pve1停止中も日次dry-runを継続する」が実質的に未達だった。

Coordinator(Yoshinobu承認済み)より、Testerが挙げた4案のうち**`ignore_unreachable`案を採用**する方針と、Testerが警告した副作用((a)除外文言が消える、(b)`_reached_nodes`にpve1が残りmerge段が壊れる、(c)AC4の停止挙動が変わる)を自分で潰すこと、およびAC4ガードが発火するようになるかをdecoyで実測することの指示を受けた。変更対象は`playbooks/proxmox_patch_dryrun.yml`と`roles/proxmox_patch_dryrun/tasks/main.yml`の2ファイル限定。

### 9-2. `ignore_unreachable: true`を1行足すだけでは直らない(実測)

先に結論を書くと、**1行追加では終了コードは`0`にならず`4`が`2`(`RUN_FAILED_HOSTS`)に変わるだけ**だった。Testerが予測した(a)(b)(c)とは別の、より手前の理由による。

`ignore_unreachable`は到達不能hostをplayから落とさない。落ちないhostには以降の全taskが配られ続けるが、`roles/proxmox_healthcheck`(本caseのscope外、他playbookと共有)は`when: healthcheck_raw.stdout | length == 0`のように**前段のregister結果を参照する`when`**を持つ。到達不能hostのregisterには`{"unreachable": true, ...}`が入り`stdout`が無いため、この`when`評価が例外になりhostは**FAILED**になる。decoy実測(下記harness、片node到達不能):

```
TASK [decoy_healthcheck : Fail if healthcheck returned no output]
fatal: [decoy_node1]: FAILED! => {"msg": "Task failed: Error while evaluating conditional:
object of type 'dict' has no attribute 'stdout'"}
PLAY RECAP: decoy_node1 ok=4 failed=1 ignored=3 / decoy_node2 ok=38 failed=0   → 終了コード 2
```

report・通知の内容自体は正しく生成される(この時点で(a)(b)は顕在化しない。到達不能hostがFAILEDとしてplayから落ちるため、結果的に`ansible_play_hosts`から消えるため)。しかし終了コードは非ゼロのままで目的を達成せず、しかも表示されるのは素直な`UNREACHABLE`ではなく「dict object has no attribute 'stdout'」という原因を誤解させるFAILEDになる。**Testerの(b)の懸念は正しかったが、それが顕在化しなかったのは「scope外のroleの`when`がたまたま例外を出してhostを落としてくれている」という副作用に依存していたからで、設計として安全ではない**(§9-3で実証)。

### 9-3. 実装内容(2ファイル)

**(1) `playbooks/proxmox_patch_dryrun.yml`**

- playレベルに`ignore_unreachable: true`を追加(指示どおり)。

  1. `Record whether this node answered fact gathering`(`_node_reachable: "{{ ansible_facts | length > 0 }}"`)。`set_fact`は接続を必要としないため到達不能hostでも`ok`で実行される(実測)。

### 9-4. AC4ガードの実測結果 — **発火するようになった(既知の制約は解消)**

Coordinatorから明示的に確認を求められた点。**両node到達不能でガードtaskが発火する**(decoy実測、両host=127.0.0.1閉ポート):

TASK [Fail if no proxmox node could be reached]

### 9-6. `proxmox_patch_weekly_full.yml`への影響(対象外ファイル、変更なし)

本playbookを`import_playbook`する側への波及を確認した。**同ファイルの修正は不要と判断した**(Coordinatorの制約どおり触っていない)。

- **pve1が最初から停止している場合**: weekly_fullのStep 0 preflightは`hosts: "{{ groups['proxmox'][0] }}"`(=pve1)を単独で対象とするため、そのplayの全hostが到達不能となりplaybook実行自体がそこで終了する(decoyの2 play構成で実測、HEAD・新版とも`rc=4`で同一、Step 2aのplayは開始すらしない)。**この経路に変化はない**。
- **pve1がStep 0/1bを通過した後に落ちた場合**: `run_once`のfact格納先に差が出る。HEADでは到達不能hostは`_unreachable_hosts`へ入るため`hostvars['pve1']['_final_status']`が**未定義**となり、Step 2bは`_status = UNKNOWN`でblockしていた。新版では`ignore_unreachable`によりpve1が`_unreachable_hosts`へ入らないため、`_final_status`がpve1側にも格納される(decoy実測: HEAD=`<UNDEFINED>`、新版=`NO_UPDATES`)。つまり**Step 2bのblock根拠が「`_status`がUNKNOWN」から「`_dryrun_missing_nodes`が非空」へ移る**。後者はまさに本caseのCritical Issue #2対応(§7-2)で追加したゲートであり、実測したfact形状(`node_summaries`は生存node分のみ)を同ゲート式へ与えると`missing=['pve1'] GATE_BLOCKS=True`となることを確認した。**安全側の結論は変わらないが、依存する防御が入れ替わる**点は記録しておく。

### 9-7. 残存リスク・未検証事項

- **(実測)play開始後に落ちたnodeは、依然として非ゼロ終了になる**。`ignore_unreachable`がplay全体に効くため、gather_facts成功後に落ちたnodeはplayに残り続け、`roles/proxmox_healthcheck`のregister参照`when`で例外化してFAILED(rc=2)になる(§9-2で観測した機構そのもの。gather後に落とすdecoyは作れていないため、この経路の端から端までの実測ではなく、機構の実測+コード読解による帰結)。report・通知は生存node分が正しく生成される。**「実行前から停止している」という夏季シャットダウン運用の本題は`0`になり、「途中で落ちた」という異常事態は赤いまま**という切り分けになるので運用上は妥当と判断したが、より厳密にやるなら`ignore_unreachable`をplayレベルではなくgather_facts task(明示`ansible.builtin.setup` + `register`)だけに限定する案がある。Coordinator指示が「playレベルに追加」と明示していたため、独断でそちらへは倒していない。
- 到達判定に`ansible_facts | length > 0`を使っているため、将来この playに`gather_facts: false`を入れると全nodeが「到達不能」と判定される。その場合はAC4ガードが発火して明示的に落ちる(サイレント成功にはならない)方向へ倒れるが、`gather_facts`を変える際は本判定もセットで見直す必要がある。
- AC4発火時にSlack通知は飛ばない(通知task手前で停止するため)。これは変更前と同じで、検知はSemaphoreの失敗表示に依存する。requirement.md AC4は「明確なメッセージで停止」までしか要求していないため要件内と判断したが、通知が要るなら別案件。
- decoy harnessは`proxmox_healthcheck`の**構造**を写したstubであり実物ではない。実物固有の`when`/factが別の壊れ方をする可能性は排除できない(ただし§9-2で観測したFAILEDは実物と同じ「registerの`stdout`参照」構造に由来する)。実ホストでの最終確認はTester担当。
- 実データがNEEDS_CLASSIFICATION(Codex分類経路)のケースはdecoyでは通していない(`scripts/codex-classify.sh`を起動しないため)。ただし今回の変更は`_reached_nodes`の求め方とplay冒頭3 taskだけで、Codex経路との接点は`_reached_nodes`の値のみ。
- 実ホストへのansibleコマンド実行、`git commit`/`git push`は行っていない。decoy一式はscratchpad配下のみ(`127.0.0.1`と閉ポート、実host名・実IPなし)で作成し、検証後に削除済み。`/tmp/proxmox_dryrun_nodes_*.json`の残留は今回の実行由来では発生していない(別セッション由来の`...T143102.json`1件は本セッション開始前から存在しており、削除・変更していない)。
