## 2. 実行1: AC1相当コマンド(`ansible-playbook playbooks/proxmox_patch_dryrun.yml -e tester_mode=true`)

### 2-1. 実測: 前提不成立

`proxmox_healthcheck`のSemaphoreサマリ出力で両ノードとも`OK`、healthcheck上pve1・pve2ともに到達・healthy(quorum/ZFS/services/systemd/reboot/replicationすべて健全)であることを実測した。`date` / `date +%A`をこのホストで確認し、2026-07-26は日曜日であることを確認した(`docs/ai/context/operations/`等が定める夏季シャットダウンは平日のみ)。つまり本タスク指示にあった「AC1の実地検証機会」の前提(pve1停止中)は、本セッションの実行時刻には成立していなかった。これは実装・Policyの不具合ではなく、単に検証タイミングの巡り合わせの問題である。

### 2-2. 実測: 実行時クラッシュ(Critical、blocking)

前提不成立のまま指示どおりコマンドを実行したところ、両ノード健全・`_final_status = NO_UPDATES`という平常時の結果に対して、以下のタスクで例外終了した。

```
TASK [proxmox_patch_dryrun : Save minimal MD report for NO_UPDATES or BLOCKED]
[ERROR]: Task failed: Finalization of task args for 'ansible.builtin.copy' failed:
Error while resolving value for 'content': The filter plugin 'ansible.builtin.length'
failed: object of type 'NoneType' has no len()
Origin: roles/proxmox_patch_dryrun/tasks/main.yml:339 (content: | ... {% if _node_reachability_note | length == 0 %} ...)
```

`PLAY RECAP`: `pve1 ok=32 changed=4 unreachable=0 failed=1 skipped=11`。playbook全体は非ゼロ終了。

### 2-3. 根本原因の特定(実ホストに触れないdecoyで再現・確認)

`roles/proxmox_patch_dryrun/tasks/main.yml:101-109`の`Build node reachability note text`タスクは、`_unreachable_nodes`・`_limit_excluded_nodes`が両方空(=fixed-pairが両ノードとも正常参加、AC2が想定する通常時)の場合、`{%- else -%}{%- endif -%}`という「テンプレート全体がJinja制御構造のみで静的文字列を一切含まない」構成になる。

`/tmp/.../scratchpad/bug_repro/repro.yml`という最小構成(localhost限定、pve1/pve2非接続、実ホストへの影響なし)で、`main.yml`の該当ロジックをそのまま複製して単体検証したところ、この場合`set_fact`の結果は空文字列`""`ではなく**`None`**になることを確認した(`type_debug` → `NoneType`、`is none` → `True`)。これはAnsibleのTemplarにおける既知の仕様(スカラー全体がJinjaマークアップのみで構成され、レンダリング結果が空文字列になる場合に`None`へ変換される)に起因する。

この`_node_reachability_note`(値`None`)に対し、以下3箇所すべてが`| length`フィルタを無条件または準無条件で適用しており、`None`が渡ると同じ例外で落ちる。

- `roles/proxmox_patch_dryrun/tasks/main.yml:346`(`Save minimal MD report for NO_UPDATES or BLOCKED`、`when: _pre_status != 'NEEDS_CLASSIFICATION'` = NO_UPDATES/BLOCKEDの場合に必ず通る)← 今回実測でヒットした箇所
- `roles/proxmox_patch_dryrun/tasks/main.yml:388`(`Set notification content for NO_UPDATES`、`when: _final_status == 'NO_UPDATES'`)
- `roles/proxmox_patch_dryrun/tasks/main.yml:432`(`Append node reachability note to notification body`、`when: _node_reachability_note | length > 0` — **Status分岐に関係なく常に評価される**ため、NEEDS_CLASSIFICATION(Codexが分類した、更新候補ありのケース)でも同じ理由で落ちる)

すなわちこのバグは、`_unreachable_nodes`と`_limit_excluded_nodes`が両方空になる**あらゆる通常のfixed-pair実行**(Status がNO_UPDATES / BLOCKED / NEEDS_CLASSIFICATIONのいずれであっても)で発生する。これはAC1固有の話ではなく、AC2が保証すべき「両ノード揃っている通常週の回帰なし」を実測レベルで破っている。日々のスケジュール実行は、パッチ候補の有無に関わらず、両ノードが健全である限り原則として毎回この経路を通るため、本番影響は大きいと判断する。

**推定原因**: `_node_reachability_note`のJinja式が「静的文字列を全く含まない、制御構造のみのテンプレート」であることが直接の引き金。Implementer/Reviewerのdecoy検証は「`_node_reachability_note`が空文字列になる経路を辿ること」をコード読解およびdebug出力の目視で確認したにとどまり(`2026-07-26_004_review.md`のAC2回帰確認節、`2026-07-26_003_implement.md`のdecoy検証4パターン)、その値に対して実際に`| length`フィルタを適用する後続タスクまで実行して型を検証してはいなかった。今回の実ホスト実行で初めて顕在化した。

## 5. AC2について(指示§4への対応)

指示では「pve1が現在停止しているため実地検証はできない」との前提でImplementer/Reviewerのdecoy検証結果を根拠として受け入れる想定だったが、実際にはpve1が稼働していたため、§2の実行で意図せず実地確認の機会が得られた。その結果、decoy検証(コード読解・debug出力の目視確認)では検出されなかった実行時クラッシュを発見した。この時点ではAC2は「decoy検証を根拠に受け入れる」のではなく実測でFAILと判定していたが、**§9の再検証によりPASSへ更新済み**(Implementerの修正、Reviewerの独立decoy end-to-end検証、Testerによる実ホスト再実行のいずれもクラッシュ解消・文言完全一致を確認)。

## 6. AC4について(指示§5への対応、実施せず)

指示および`2026-07-26_003_implement.md`末尾のCoordinator判断(選択肢1採用)により、両ノード同時到達不能の意図的な再現は行っていない。Ansible標準のUNREACHABLE/FAILED報告+非ゼロ終了で「サイレント成功にしない」という安全性の実質を満たすという判断は、Implementer/Reviewer双方がdecoy inventoryで検証済み(`2026-07-26_003_implement.md`§3-3、`2026-07-26_004_review.md`のCritical Issues #1行のAC4欄)であり、本セッションでもこれを追加検証する必要はないと判断した。

## 7. AC5について

`playbooks/proxmox_patch_weekly_full.yml`の実行が§4のpreflightで止まったため、この時点ではStep 2bの新ゲート(`_dryrun_missing_nodes`)を実ホストで検証できなかった。Reviewerが独立decoy(2-play構成、`ansible_connection: local`)で3パターン(fixed-pair PATCH_READY→通過、非対称欠落→block、逆方向欠落→block)を検証しCritical Issue #2の解消を確認済みであり(`2026-07-26_004_review.md`追記部分)、本セッションではこれを覆す情報は得ていない。

**§11更新**: quoryから実行した結果、当日の実データがNO_UPDATES(PATCH_READY非該当)だったため、`_dryrun_missing_nodes`を`when`条件に含む`Fail if dry-run status is a genuine error, unexpected, or did not cover both nodes`タスク自体が、その手前の「クリーンスキップ+`meta: end_play`」ブロックにより到達前に短絡され、実行されなかった(詳細は§11)。したがって実データによる直接検証は今回も完了しておらず、引き続きReviewerのdecoy検証を根拠として受け入れる。PATCH_READYが実際に出る週(通常、更新候補がある週)にquoryから再実行することで直接検証できる。

**§13-4で提起した終了コード問題は解消した(rc=`4` → `0`、実ホスト実測)。** 機能面は§13のPASS内容から一切劣化しておらず、正規化diffで「終了コードと新規3タスクの分だけが差」であることを機械的に確認した。追加された3タスクはいずれも実ホストで期待どおり動作し、特に「到達不能ノードでも`set_fact`が実行される」という設計の前提と「`meta: end_host`によるpve1の除外」を実機で確認した。**AC1は留保なしでPASSへ更新する。**

残るのは§14-5のa(Semaphore側のfact caching設定の実査)・b(AC4のTester実地検証)・c(AC5のStep 2b実データ検証)であり、いずれも本修正の品質ではなくTesterの許可範囲およびデータ発生タイミングの制約による。
