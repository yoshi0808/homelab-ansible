# proxmox_patch_dryrun: pve1停止時の安全な検証計画

## 依頼

- 対象: `playbooks/proxmox_patch_dryrun.yml`
- 状況: `pve1`停止中を想定する。
- 確認事項: `--limit pve2`で安全に成立するか。
- 境界: 許可のない実ホスト実行は行わない。APPLYは行わない。

## 結論

現行実装では、`--limit pve2`によるplaybook完走は成立しない。

Ansibleのhost pattern上は実行対象を`pve2`だけへ絞れるが、
`roles/proxmox_patch_dryrun/tasks/main.yml`のmerge・status・report処理は
`hostvars['pve1'].node_dryrun`と`hostvars['pve2'].node_dryrun`を固定で要求する。
関連Policyも本playbookを`pve1` / `pve2`固定ペア、単一ノード非対応と定義している。
したがって、`pve1`停止中の実ホストE2Eは実施せず、静的検証までで停止する。

## 安全性判定

- playbook header: `# tester-gate: safe-readonly`
- Policy上の分類: semi-safe (`apt update`、simulation、changelog収集、分類)
- 実装上の副作用:
  - 対象ノードへ収集scriptを配置する。
  - `apt-get update`によりpackage metadataを更新する。
  - controller上へ一時ファイルとreportを作成・削除する。
  - 通知抑止変数がなければSlack通知経路へ入る。
- `tasks` blockに`check_mode: false`があるため、`--check`を加えても上記処理を
  単純なread-onlyへ変換できない。

headerの通知抑止説明は現行実装と一致する。healthcheck通知はcaller側の
`when: not skip_notifications`でguardされ、`common_slack`へ到達する通知は
`tester_mode`または`skip_notifications`で抑止される。playbookが抑止変数を
自動設定するという意味ではないため、検証実行時は現行の運用入力である
`skip_notifications=true`を明示する。

## Unit / static

### 静的に確定できた事項

1. inventoryの`proxmox` groupは`pve1`と`pve2`の2ホストである。
2. playbookの対象は`hosts: proxmox`であり、無制限実行は両ホストを対象にする。
3. `--limit pve2`というhost pattern自体は対象選択を`pve2`へ絞る意図に合う。
4. healthcheckの集約は`ansible_play_hosts`を使うため、選択されたhostだけを集約する。
5. patch dry-run roleの統合処理は両hostの`node_dryrun`を固定参照する。
6. Policy §6.3は`pve1` / `pve2`固定ペア、単一ノード非対応と明記する。

### host-freeで実行可能な追加確認

以下はinventoryと構文だけを読む。実ホストへ接続しない。

```bash
scripts/check-tester-gate.sh
ansible-playbook -i inventories/homelab/hosts.yml \
  playbooks/proxmox_patch_dryrun.yml --syntax-check --limit pve2
ansible-playbook -i inventories/homelab/hosts.yml \
  playbooks/proxmox_patch_dryrun.yml --list-hosts --limit pve2
ansible-playbook -i inventories/homelab/hosts.yml \
  playbooks/proxmox_patch_dryrun.yml --list-tasks --limit pve2
```

期待結果:

- tester-gate lintがmarkerを受理する。
- syntax checkが成功する。
- list-hostsが`pve2`だけを表示する。
- list-tasksがrole呼出しを展開する。

これらはhost選択と構文だけを確認するものであり、固定`hostvars['pve1']`参照の
runtime失敗や実ホスト上の処理成功を証明しない。

## Integration

実ホストを使わず、次をfixtureまたはlocalhost専用の使い捨て検証で確認する。

1. `pve2.node_dryrun`だけが存在するhostvarsを入力する。
2. 両ノード固定のmerge式が`pve1.node_dryrun`未定義でfail-closedになることを確認する。
3. 両ノードのfixtureを与えた場合だけmerge・status・report生成が進むことを確認する。

使い捨て検証を行う場合も、対象実装は変更せず、秘密情報・内部識別子をfixtureへ
入れない。生成物は一時ディレクトリ内に限定する。

## E2E

### pve1停止中

実施しない。`--limit pve2`は接続範囲を絞ってもplaybookの固定ペア契約を満たさず、
完走不能である。さらに本playbookは厳密な無変更read-onlyではない。

### 将来の実行確認条件

次のいずれかを満たし、担当Tech LeadとYoshinobuが明示承認した後に別計画で行う。

- `pve1`が復旧し、Policyどおり固定ペアで実行できる。
- 単一ノードmodeが要件・Policy・実装へ明示的に追加され、両ノード固定参照が解消される。

実行時は通知抑止の現行契約を再確認し、少なくとも`skip_notifications=true`を
明示する。`tester_mode`は検証実行の運用入力としては廃止済みだが、
`common_slack`内の互換guardは現存する。
