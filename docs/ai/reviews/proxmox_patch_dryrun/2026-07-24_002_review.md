# Code Review: pve1停止中の `proxmox_patch_dryrun.yml` 運用リスク

## Summary

通常の全ホスト実行は、`gather_facts: true` によるpve1への接続失敗を `any_errors_fatal: true` が全対象ホストの致命的失敗として扱うため、明示taskへ進む前にfail closedとなる。一方、`--limit pve2` はpve1の到達性確認を対象集合から外すが、dry-run roleはpve1/pve2固定ペアを直接参照するため、pve2で`apt-get update`等を実行した後、集約時に失敗する。単一ノードdry-runの代替にはならない。

## Critical Issues

| # | File | Line | Issue | Severity |
|---|---|---:|---|---|
| 1 | `playbooks/proxmox_patch_dryrun.yml` | 10-13 | pve1停止中の通常実行では、play対象が`proxmox`全体、fact収集あり、かつ任意hostのunreachable/errorを全hostへ波及させる設定である。このためpve1のfact収集失敗後、pve2のhealthcheck/dry-run taskへは進まない。これは固定ペア運用としてfail closedだが、pve2だけの更新候補を得られる挙動ではない。 | must-fix（運用） |

## What Looks Good

- `proxmox_healthcheck`自体は`ansible_play_hosts`を集約対象に使うためlimit-awareであり（`roles/proxmox_healthcheck/tasks/main.yml:138-219`）、Policy上も単一ノードhealthcheckは許可されている（`docs/ai/policies/proxmox_patch_policy.md:363-370`）。ただしdry-run roleは別で、固定ペア依存である。
- healthcheckはquorum、主要service、apt/dpkg等をCRITICAL判定し（`roles/proxmox_healthcheck/tasks/main.yml:47-75`）、dry-run roleも各対象hostのhealthcheckが`OK`以外なら停止する（`roles/proxmox_patch_dryrun/tasks/main.yml:6-9`）。
- dry-run roleは集約後もpve1/pve2双方のapt/simulation結果を明示確認し（`roles/proxmox_patch_dryrun/tasks/main.yml:89-103`）、最終reportにも双方のreboot要否を要求する（同:216-227）。不完全な単一ノード結果をcluster結果として正常完了させない点はfail closedである。
- `gather_facts: true`は単なる疎通確認だけではなく、healthcheck roleの時刻閾値・report名に使う`ansible_facts['date_time']`を供給する（`roles/proxmox_healthcheck/tasks/main.yml:27-30,130-136`）。
- shell変数注入の新規差分はなく、対象収集は固定commandを使っている。今回の依頼は実装diffレビューではないため、duplication/reuseの追加findingはなし。

## Recommended Operation While pve1 Is Down

1. `proxmox_patch_dryrun.yml --limit pve2`を実行しない。
2. Semaphore等の定期dry-run / weekly full scheduleが有効なら一時停止し、現在実行中の同系jobがないことを確認する。
3. pve2単体の状態確認が必要なら、Policyが許可する`proxmox_healthcheck.yml --limit pve2`までに留める。ただしこれはcluster fixed-pair dry-run Statusの代替ではない。
4. pve1復旧後、両ノード到達可能な状態で通常のfixed-pair dry-runを実行する。
5. pve1停止中にもpve2の更新候補評価が必須なら、単一ノード用の要件・Status・通知・排他を別案件として定義する。

## Verdict

**Request Changes（運用計画）** — 現行コードは固定ペアPolicyに対してfail closedだが、pve1停止中の`--limit pve2`手動運用は非対応であり、定期実行との重複防止も共通には保証されない。コード変更は行っていない。
