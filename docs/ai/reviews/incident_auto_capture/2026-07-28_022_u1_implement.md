## 4. 自己検証

### 4.1 構文検証(ansy上)

```
$ ansible-playbook --syntax-check playbooks/recovery_probe_notify.yml
playbook: playbooks/recovery_probe_notify.yml
```

`recovery_probe_notify.yml` は `common_slack/tasks/notify.yml` を経由して `capture.yml` を無条件includeする実プレイブックであり、実際の呼び出し経路を通した構文検証になっている(rc=0、エラーなし)。

### 4.2 decoy検証(scratchpad、実行後に削除済み)

目視だけで終えず、実際に `ansible.builtin.file` モジュールを動かして下流の挙動(ACL maskの実測)まで確認した。`hosts: localhost` / `connection: local` の使い捨てplaybookを3本、scratchpad配下にのみ作成・実行し、検証後に削除した(実host名・実IPなし、副作用は全てscratchpad内に閉じている)。

**検証1(修正後のタスクの再現)**: 事前に `chmod 0775` + `setfacl -m u:nobody:rwx` でACL付きディレクトリ(mask::rwx, stat=775)を用意し、`mode:` を削除した版のタスクを1回実行。

結果:
```
file module changed: False
mode after (octal): 0775
getfacl before: [... 'user:nobody:rwx', 'group::rwx', 'mask::rwx', ...]
getfacl after:  [... 'user:nobody:rwx', 'group::rwx', 'mask::rwx', ...]  (完全一致、#effective: 注記なし)
```
→ **修正後のタスクは既存ACLディレクトリに一切触れない**ことを実測で確認した。

**検証2(対照: 修正前=`mode: "0755"` 残存のタスク)**: 同じ手順でACL付きディレクトリ(mask::rwx, stat=775)を用意し、`mode: "0755"` を残した版のタスクを1回実行。

結果:
```
getfacl after: [... 'user:nobody:rwx\t#effective:r-x', 'group::rwx\t#effective:r-x', 'mask::r-x', ...]
```
→ **修正前のタスクは実際にmaskをrwxからr-xへ書き換える**ことを実測で再現した(`changed_when: false` により報告上は `changed: False` のまま静かに発生する点も含め、本番事故の記述と一致)。この対照実験により、削除した1行が実際に因果メカニズムの一部であったことを自分の手で裏付けた(他人の記録の追認ではなく再現)。

**検証3(新規ディレクトリ作成、ansy相当のケース)**: 対象パスが存在しない状態から修正後のタスクを実行(ansyのようにroleが流れず、ディレクトリがまだ無いホストを模擬)。

結果:
```
exists: True
is_dir: True
mode after (octal): 0775  (このsandboxのumask依存)
```
→ **新規作成は引き続き成功する**ことを確認した。umask依存で0775になった点はRSK-B(計画§9)が既に指摘済みの既知の露出であり、U1のスコープ外(U3のR2で確認予定)。

以上3本のplaybookと生成したディレクトリはすべてscratchpad配下(`/tmp/claude-1000/.../scratchpad/u1_decoy/`)に作成し、検証完了後に `rm -rf` で削除済み。リポジトリ・実ホストへの影響はゼロ。
