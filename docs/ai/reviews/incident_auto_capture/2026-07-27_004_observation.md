## T-OQ1a(ansy): `task`テーブルの列定義・生値・status語彙

安全分類: 読み取りのみ、ansyは開発ホスト。承認不要。

### 実行コマンド・実測結果

```
sqlite3 -readonly /var/lib/semaphore/semaphore.db "PRAGMA table_info(task);"
```
→ `end`列は**実在する**(6番目のカラム: `end|DATETIME`)。列一覧(抜粋): `id, template_id, status, playbook, environment, created, start, end, user_id, project_id, message, version, commit_hash, ...`

```
sqlite3 -readonly /var/lib/semaphore/semaphore.db "SELECT id,status,start,end FROM task ORDER BY id DESC LIMIT 3;"
```
→
```
18|success|2026-07-24 10:34:02.346004434 +0000 UTC|2026-07-24 10:37:26.881921251 +0000 UTC
17|success|2026-06-21 11:39:07.037413497 +0000 UTC|2026-06-21 11:39:14.924717783 +0000 UTC
16|success|2026-06-21 11:38:08.874039043 +0000 UTC|2026-06-21 11:38:18.649920857 +0000 UTC
```

```
sqlite3 -readonly /var/lib/semaphore/semaphore.db "SELECT DISTINCT status FROM task;"
```
→ `stopped` / `success` / `error`(ansyのDBには`success`が多く、`recent-failed`が対象とする`error`/`stopped`以外に`success`が実在することを確認)

### そこから決まること — **OQ1の答え**

生値は `YYYY-MM-DD HH:MM:SS.nnnnnnnnn +0000 UTC` という形式であり、**RFC3339でもZ表記でもない**。これはGoの`time.Time`のデフォルト`String()`出力そのもの(区切りは空白、ナノ秒精度、末尾が`+0000 UTC`というリテラル文字列)。

- 末尾は `Z` でも裸の `+09:00` でもなく、**` +0000 UTC` という固定サフィックス**。オフセットは常に`+0000`(UTC固定)。
- Yoshinobuが`recovery.io`経由で見た`2026-07-26 20:45:01 UTC`(区切りが空白、末尾`UTC`、ナノ秒とオフセット数値が無い)は、この生値からナノ秒とオフセット数値部分を落として整形した表示層の値である可能性が高いという投資調査書§3 OQ1の推測と整合する。
- 収集器実装への帰結: `occurred_at`(RFC3339)を作るには、この`YYYY-MM-DD HH:MM:SS[.nnnnnnnnn] +0000 UTC`形式を明示的にパースし、`T`区切り・`Z`または`+00:00`表記へ変換する必要がある。`substr(...,1,19)`ではこの変換ロジックへ渡す情報(オフセット)がそもそも失われるため、`task-time`(non-substr)クエリの追加は正しい前提だった。
- `status`語彙は `success` / `error` / `stopped` の3つを確認した(ansy側)。`recent-failed`が対象とする`('error','stopped')`は`success`を除外する設計であることが裏付けられた。

## T-BASE: AC1のベースライン

### 対象playbookの選定

**選定: `playbooks/recovery_probe_notify.yml`**

選定理由(投資調査書の選定条件に照らして):
1. `roles/common_slack/tasks/notify.yml`のinclude(`playbooks/recovery_probe_notify.yml`の該当行)に**caller側`when:`が付いていない**(無条件include)。投資調査書§1-2が指摘した「include自体が`skip_notifications`/`ansible_check_mode`でゲートされている」経路(radius_healthcheck等)には当たらない。
2. `# tester-gate: role-guarded`であり、実行の副作用はSlack通知のみで、`tester_mode: true`で完全に抑止できる(`assert: not tester_mode`のような即failも持たない — 投資調査書§1-3の5 playbookには含まれない)。
3. ansyで繰り返し安全に実行できる(`hosts: localhost`、外部ホストへの接続なし)。
4. 必須extra vars(`nt_status`, `nt_title`, `nt_message`)を渡すだけで完結し、副作用のない繰り返し実行が可能。

### 実行コマンド

```
ansible-playbook playbooks/recovery_probe_notify.yml \
  -e tester_mode=true \
  --extra-vars '{"nt_status":"ok","nt_title":"W0 baseline test","nt_message":"Tester W0 baseline observation no real send","nt_queued_at":"2026-07-27T12:00:00+09:00"}'
```

(補足: 最初`-e key="value with spaces"`形式を複数回使ったところ、Ansibleが空白区切りをkey=valueの区切りと解釈し値が途中で切れる事故に遭遇した — `title: W0`のみになった。原因は分かっているため実害はないが、**単一の`--extra-vars`にJSONでまとめる**方式へ切替えて再実行し、正しい値が渡っていることを確認した。)

### 実測結果(生のPLAY RECAP)

```
PLAY RECAP
localhost : ok=3 changed=0 unreachable=0 failed=0 skipped=5 rescued=0 ignored=0
```
終了コード: `0`

`tester_mode: true`により`notify.yml`の`[tester_mode] Show notification instead of sending`タスクが実行され(実Slack送信はskip)、実際のSlack送信ブロック(webhook読込等)は`skipping`となった。想定どおりの経路。

### そこから決まること — AC1ベースライン

現行コード(T1導入前)での`recovery_probe_notify.yml`(`tester_mode=true`)実行結果は **`ok=3, changed=0, unreachable=0, failed=0, skipped=5, rescued=0, ignored=0`、終了コード0**。T1導入後(W5 T-AC1)は同一条件で同一playbookを再実行し、この5指標(ok/changed/failed/ignored、および終了コード)が一致することを確認する。
