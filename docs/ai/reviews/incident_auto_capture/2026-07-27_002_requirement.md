# requirement: 障害の証拠バンドル生成(Step 1)

日付: 2026-07-27(JST)
状態: **requirement。実装未着手。**
Tier: **4**(軸A=本番影響のある実ロジック変更かつ実装前に調査と受入を分ける価値がある / 軸B=Tier 4はReviewerを工程内に含むため`+R`は付けない)
前提: `docs/ai/reviews/incident_auto_capture/2026-07-27_001_design_agreement.md` の決定D1〜D7。本requirementはそれを覆さない。

## 1. 問題定義

Ansibleジョブの失敗はSlackへ通知され、YoshinobuがSlack経由でCodex→`recovery.io`のallowlistコマンドで調査している。**調査の道具としては機能している**が、次の3つが失われている。

1. **捕捉されない失敗がある。** 気づかなかった事象・後回しにした事象が記録に残らない。2026-07-27の月次Knowledge振り返りが「種別:未遂の該当2件が未起票、母数不足でタグ集計が働かない」と報告済みで、Incident→Policy/Skill昇格のループが入口の枯渇で回っていない。
2. **調査結果が蒸発する。** `recovery.io` が返す良質な調査結果はSlackの散文であり、機械可読でもリポジトリ内でもない。同じ障害を再度調べても、前回何を確かめたかが残っていない。
3. **3者に共通の識別子が無い。** Slack通知 / `recovery.io` の調査結果 / `docs/ai/memory/incidents/` が互いに紐づかない。

さらに、既存の2つの観測面はそれぞれ**系統的な死角**を持つ。

| 観測面 | 拾えるもの | 落とすもの |
|---|---|---|
| Semaphoreのジョブ結果 | 中断・crash・rc≠0、生ログ全文、ジョブID | **rc=0の意味的WARNING**(Semaphoreは緑のまま) |
| `common_slack/notify.yml` | `slack_status`(warning/critical/error) | **notifyへ到達しない失敗**(UNREACHABLE中断、`any_errors_fatal`、テンプレート/構文エラー、timeout、kill) |

`proxmox_patch_dryrun` の単一ノード問題は後者の実例で、`hosts: proxmox` + `any_errors_fatal: true` により pve1 UNREACHABLE時にplayが即中断し、notifyは発火していない。一方 `proxmox_patch_dryrun` は後に意図的に rc=4→rc=0 へ変更しており、前者の死角も現実に開いている。

## 2. ゴール

**quory上で、ジョブ失敗の証拠を決定論的に(LLMなしで)バンドルとして保全する。**

- 失敗時点の事実(要約ログ・生ログ・rc・時刻)と、収集時点の現況スナップショットを1つのIDの下にまとめる。
- 通知が抑止されている局面でも証拠は残す。
- **観測が被観測(本番ジョブ)の挙動を変えない。**

Step 1単独でも価値がある。人がSlackからバンドルIDを`recovery.io`へ渡せば、調査の初動が速くなる。あわせてStep 2(ansy側の`claude -p`による第一報起票)の入力仕様がこれで確定する。

## 3. 非ゴール

このStepでは次を**実装しない**。

- LLMによる叙述、原因推定、対応提案(Step 2)
- ansy側での取り込みと `docs/ai/memory/incidents/` への起票(Step 2)
- 名前付き操作カタログの拡張(D1/D2。実際の障害が必要性を証明してから)
- あらゆる復旧・是正の実行(`recovery_probe`ラダーと人の領分)
- `recovery.io` allowlistの拡張、新しい常時接続チャネル
- Semaphore UI設定・スケジュールの変更

## 4. ユーザーストーリー

- **Yoshinobu(障害対応時)**: Slack通知にバンドルIDが載っているので、それを`recovery.io`へ渡すだけで、失敗時点の生ログと現況が揃った状態から調査を始められる。何が起きたかを組み立て直す手間が要らない。
- **Yoshinobu(事後)**: 週末や翌朝に、その週に起きた失敗の一覧を証拠つきで見返せる。Slackを遡らなくてよい。
- **Coordinator(対話セッション)**: `/clear` 後でも、バンドルを読めば過去の障害の一次情報に到達できる。Slackの散文でなく構造化された事実から判断できる。
- **月次Knowledge振り返り**: 捕捉漏れが減り、`原因分類`タグの母数が確保される。

## 5. 要件

### P0(初回実装に不可欠)

**R1. 通知経路での捕捉(T1)**
`roles/common_slack/tasks/notify.yml` の**冒頭**、`tester_mode` / `skip_notifications` の抑止ゲート**より前**に捕捉を挿入する。通知の抑止は人間の注意管理、証拠の保全は開発ループであり、別の要件である。`tester_mode` 中はスキップせず**フラグとしてバンドルへ記録**し、仕分けは叙述側(Step 2)へ委ねる。

**T1は安価かつローカル完結でなければならない。** メタデータ(`slack_status` / `slack_channel` / `slack_title` / `slack_message` / playbook名 / 時刻)のファイル書き込みのみを行い、**SSHもHTTPも行わない**。33箇所から呼ばれるため、ここに時間のかかる処理を置くと全通知が遅くなり、ハングの経路にもなる。

**R2. 収集器(quory上、周期実行)**
T1が残したレコードと、Semaphoreのジョブ結果を突き合わせてバンドルを完成させる。

- Semaphoreのジョブ結果(SQLite)から、失敗ジョブのジョブID・テンプレート名・開始/終了時刻・終了ステータス・**生ログ全文**を取得する。
- 既存 `recovery.io` allowlist を機械的に一巡して**現況スナップショット**を取得する(`status` / `failed` / `journal-*-err` / `disk` / `memory` / `load` / `network` / `ports`)。**コマンドは組み立てず、既存の名前を呼ぶだけ**(D1)。
- `/usr/bin/flock -n` で多重起動を防ぐ(`knowledge-review.service` に前例あり)。

**R3. 観測が被観測の挙動を変えない**
最重要。T1の追加によって、**呼び出し元playbookの終了コード・タスク結果・所要時間の有意な増加のいずれも発生させない**。捕捉自体の失敗はplayを失敗させず、失敗した事実をレコードへ残す。

**R4. 成果物は作業ツリーを汚さない**
バンドルは `reports/incidents/<id>/` 配下へ置く。`.gitignore` は `reports/**/*.json` / `*.log` / `*.md` **のみ**を除外するため、**バンドルの全ファイルをこの3拡張子のいずれかにする**(`.txt` は追跡対象になってしまう)。`.gitignore` を変更しない方針とする。

**R5. 収集の失敗を可視化する**
最悪の壊れ方は**静かに空のバンドルを作り続ける**ことである。Semaphoreのスキーマ不一致、SQLiteロック、SSH到達不能、allowlistに無いコマンド指定などは、握りつぶさずバンドル内へ「何を試みて何が取れなかったか」として記録する。この記録はStep 2で §5「未確認事項」の材料になり、カタログ拡張の根拠になる。

### P1(Step 1のうちに入れたいが、無くても成立する)

**R6. 相関IDをSlack本文へ載せる**
IDはSemaphoreジョブ由来ならジョブ番号を使う(**発明しない**)。Semaphore外は `timer-<unit>-<timestamp>`。これにより通知が終点でなく入口になる。

**R7. バンドルのローテーション**
quory上に無限に溜めない。保持世代または保持日数で削除する。

**R8. Semaphore外ジョブの保険**
Semaphoreを経由しない本番ジョブは実質 `cert-renew-quory` のみ。終了コードからの薄い捕捉経路を用意する。

### P2(将来)

**R9. 秘密情報のredaction**
Step 1のバンドルは**quory内に閉じており、`.gitignore` 済みで公開repoへ出ない**ため緊急度は低い。redactionが本当に要るのは、バンドルを公開repoの `docs/ai/memory/incidents/` へ叙述するStep 2の境界である。そこでは「生ログを本文へ転記させず、バンドルへの参照だけ書かせる」規律を仕様に含める。

### Won't

`docs/ai/status.md` に載せない項目、`recovery.io` の対話的調査の置き換え、Notionの時刻管理表の参照(D5により明示的に不採用)。

## 6. 受入条件

すべて `Given / When / Then` で書き、**成否をどこで観測するか**を `Then` に含める。

**AC1(通知経路の捕捉)**
- Given: 本番quoryで、`common_slack`経由の通知を行うplaybookが `slack_status: error` で通知する
- When: 当該playbookを通常どおり実行する
- Then: `reports/incidents/<id>/` が生成され、`slack_status` / `slack_channel` / `slack_title` / playbook名 / 時刻(タイムゾーン明示)を含むメタデータが記録されている。**playbookの終了コードは捕捉導入前と同一**であり、タスクの failed 数も増えていない

**AC2(notifyを逃す失敗クラスの捕捉)**
- Given: pve1が到達不能な状態(夏季平日シャットダウン運用中に再現可能)
- When: `hosts: proxmox` かつ `any_errors_fatal: true` のplaybookをSemaphoreから実行し、notifyへ到達せずplayが中断する
- Then: notify由来のレコードは存在しないが、**収集器がSemaphoreのジョブ結果からバンドルを生成している**。バンドルにはジョブID、`UNREACHABLE` を含む生ログ、終了ステータスが含まれる

**AC3(抑止下でも捕捉される)**
- Given: `tester_mode: true` または `skip_notifications: true` を指定する
- When: 通知を行うplaybookを実行する
- Then: **Slack通知は送信されない**(既存挙動を変えない)が、バンドルは生成され、抑止フラグが記録されている

**AC4(観測が本番を壊さない)**
- Given: 捕捉の書き込み先が存在しない/権限がない/ディスクフルなど、捕捉が失敗する条件
- When: 通知を行うplaybookを実行する
- Then: **playbookは捕捉導入前と同じ終了コードで完了する**。捕捉の失敗はplayを失敗させず、Semaphoreのジョブ結果にも失敗として現れない。捕捉が失敗した事実は収集器側で「取得失敗」として記録される

**AC5(収集器の異常が可視)**
- Given: Semaphoreのスキーマが想定と異なる(カラム名変更等)状況を模擬する
- When: 収集器を実行する
- Then: **空のバンドルを黙って作らない**。「Semaphoreからの取得に失敗した」ことが明示的にバンドルへ記録され、収集器の終了コードは非ゼロ、その値と意味が定義されている

**AC6(作業ツリーを汚さない)**
- Given: バンドルが1件以上生成された状態
- When: quoryの当該リポジトリで `git status --short` を実行する
- Then: **出力が空である**(バンドル由来の untracked ファイルが1件も現れない)

**AC7(多重起動の抑止)**
- Given: 収集器が実行中である
- When: 同じ収集器がもう1つ起動される
- Then: 後発は `flock -n` により即座に終了し、終了コードは「多重起動により実行せず」を意味する定義済みの値になる。**本番ジョブへの影響は発生しない**

## 7. オープンクエスチョン

**OQ1. Semaphoreのタイムスタンプの実体(要・実測)**
Yoshinobuの確認では `/etc/semaphore/config.json` は ansy / quory とも `Asia/Tokyo`。一方 `recovery.io` から取得したジョブ #461 の出力は `2026-07-26 20:45:01 UTC` と表示されていた。**両者は矛盾しうる**(多くの実装はDBにUTCで保存し表示時にローカルへ変換する。逆に、ローカル時刻へリテラルで `UTC` を付けている可能性もあり、その場合は表示自体が誤り)。

**設定ファイルの記述で結論を出さない。** 解決方法を先に決めておく: 既知の壁時計時刻に実行されたジョブを1件選び、SQLiteの当該カラムの生値と突き合わせて保存形式を実測する。バンドルは**タイムゾーンを明示したフィールド**で保持し、ローカル時刻に裸の `UTC` / `Z` を付けない。

**OQ2. 収集器の起動間隔。** 短いほど現況スナップショットが失敗時点に近いが、負荷とノイズが増える。

**OQ3. 現況スナップショットの対象ホスト。** 失敗したホストのみか、同じinventory groupの全ホストか。pve1の障害でpve2の状態が要るように、**隣のホストの正常性が判断材料になる**ため単純に「失敗したホストだけ」ではない可能性が高い。

**OQ4. バンドルの保持期間・世代数(R7の具体値)。**

**OQ5. Step 2で顕在化する「作業ツリー汚れ vs 月次振り返り」。** 無人実行はcommitできないため、Step 2でIncidentを自動起票すると作業ツリーが汚れたまま残り、月次Knowledge振り返りの「作業ツリーが汚れているときは中止」と衝突する。**Step 1では発生しない**(バンドルは`.gitignore`済みでrepo管理外、AC6で担保)。したがってこの判断はStep 2のrequirementへ持ち越す。

**OQ6. 対象ジョブ範囲。** 現時点の想定は「Semaphoreで失敗した全ジョブ(スケジュール実行・手動実行を問わない)」+「notify経由で `warning` / `critical` / `error` を出した全ケース」。playbookを列挙せず、観測面で定義する。これで良いかを調査フェーズで確認する。
