対象の`scripts/git-pre-commit-check.sh`・`scripts/check-staged-yaml.py`・`scripts/check-tester-gate.sh`を使い捨てリポジトリへコピーし、`playbooks/dummy.yml`に有効な`# tester-gate:`マーカーを置いて、vault検査以外の既存チェックが正常系で通ることを確認した上で、以下を実際に実行して確かめた。

1. 依頼が指摘した本来のバグの両方向(stage=平文/worktree=暗号化 → 検出できるか、stage=暗号化/worktree=平文 → 誤検知しないか)

## Suggestions

### 1. `git ls-files -s -- "$file"`がpathspecのglobマッチングを行うため、ファイル名にgit pathspec特殊文字(`*` `?` `[...]`)を含むsymlinkが、同名glob一致する別ファイルと共存すると誤検知でcommitを止める

- File: `scripts/git-pre-commit-check.sh:68`
- 再現条件と実測: `git ls-files -s -- "$file"`は`--`の後がpathspecとして解釈されるため、`$file`に`*` `?` `[...]`が含まれると文字通りのglob展開になる。以下を実測した。
  - vault命名一致のsymlink `group_vars/all/vault[s].yml`(実体は`vault.yml`へのリンク、mode 120000)を1件だけstageすると、`git ls-files -s -- 'group_vars/all/vault[s].yml'`はそのsymlink自身だけを正しく返し(`120000`)、スクリプトはsymlinkとして正しくスキップする。
  - ここへ、無関係な通常ファイル`group_vars/all/vaults.yml`(`vault[s].yml`のブラケット部分`[s]`が文字クラスとして`s`にglob一致する)を**追加でstageする**と、`git ls-files -s -- 'group_vars/all/vault[s].yml'`は2行返す(`120000 ... vault[s].yml` と `100644 ... vaults.yml`)。`file_mode`変数はこの2行を結合した複数行文字列になり、`[[ "$file_mode" == "120000" ]]`が**完全一致しないため成立せず**、symlinkスキップに入らない。結果、`git show ":$file"`でsymlinkの中身(リンク先パス文字列)を読み、それは`$ANSIBLE_VAULT;`で始まらないため、**正当なsymlinkが「暗号化されていません」として誤検知でcommitを止める**(実測: `ERROR: vault/secret-like YAML is not Ansible Vault encrypted... group_vars/all/vault[s].yml` / RC=1)。
  - 逆方向(平文ファイルがglob汚染によりsymlink判定されて検査をすり抜け、秘密情報が漏れる方向)は**再現しなかった**。理由は、$fileが実際にstage済みである限り`git ls-files -s -- "$file"`の出力には$file自身のエントリが(文字クラス上は本来一致しなくても)必ずリテラル一致で含まれることを複数パターンで確認したため。self行のmodeが symlinkでない限り、複数行結合文字列が`"120000"`と完全一致することはなく、`git show`によるfail-closed側の読み取りへ必ず落ちる。つまりこの欠陥は**「機密情報が漏れる」方向ではなく「正当なcommitを誤って止める」方向のみ**に働く。
- 影響: 現在リポジトリ内に`*` `?` `[` `]`を含むファイル名は存在せず、命名規約(snake_case、日本語ディレクトリはあるがglob特殊文字は無い)から見て発生確率は低い。ただし本チェックはYoshinobuのcommitゲートそのものであり、依頼の優先順位1位が「誤検知でcommitを止める経路が無いか」である以上、実測で再現した経路として報告する。
- 推奨対応: `git ls-files -s -- "$file"`をpathspecのglobマッチングから外す。具体的には`git ls-files -s -- ":(literal)$file"`(literal pathspec magic)を使うか、`check-staged-yaml.py`の`staged_modes()`と同様に**全staged対象ファイルを1回のバッチ呼び出しでmode取得し、パスをキーにした連想配列で正確一致lookupする**方式へ揃える。後者はこのSuggestion（globの誤動作）と次項（性能）を同時に解消でき、実装済みのPython版と方針が揃うため保守性も上がる。

### 2. vault検査ループが1ファイルにつき`git ls-files -s`を毎回spawnしている(バッチ化していない)

- File: `scripts/git-pre-commit-check.sh:60-91`
- `check-staged-yaml.py`の`staged_modes()`は「1回のバッチ呼び出しで全パスのmodeを取得する」ことをdocstringで明記し、その理由も「every commitで走り、ファイル数が多くなりうるため」と書いている。シェル側の新設ロジックは同じ目的(symlink判定)にも関わらず、vault/secret命名に一致するファイルごとに`git ls-files -s`を個別spawnしており、同じ方針が踏襲されていない。
- 実測: vault/secret命名に一致する300ファイルをstageして計測したところ約1.9秒(gitleaksのオーバーヘッド込み)。現状のリポジトリ規模・実運用のcommit粒度では実害になる水準ではないが、Suggestion 1の修正(バッチ化)を採用すれば副次的にここも解消される。

### 3. (重複/再利用確認)同一目的のsymlink判定ロジックがshellとPythonで別々に実装されている

- File: `scripts/git-pre-commit-check.sh:64-71` と `scripts/check-staged-yaml.py:46-67,108-109`
- どちらも「vault/secret系ファイルのsymlink(mode 120000)はcontentチェック対象外」という同じ判断を、別々の実装(shellは`git ls-files -s`を都度呼ぶ1行、Pythonはバッチ関数)で行っている。既存のPython側が既にバッチ化・辞書lookupという安全な形で実装済みであるにも関わらず、shell側が模倣していない。Suggestion 1・2の対応と合わせて、shell側をPython側と同じ設計に揃えることを推奨する（新規スクリプトを増やす提案ではない）。

## What Looks Good

- **依頼の核心である「stage≠worktree」不一致は両方向とも修正されている。** 実測: (a) stage=平文/worktree=暗号化 → 修正前は素通りしていたはずのケースが、修正後は`ERROR: vault/secret-like YAML is not Ansible Vault encrypted`でRC=1になり正しく検出する。(b) stage=暗号化/worktree=平文 → 誤検知せずRC=0で通過する。
- **`set -euo pipefail`下での安全性。** `staged_content="$(git show ":$file" 2>/dev/null)"`は`if !`の条件式内に置かれており、依頼が警告した「裸の`var=$(failing_cmd)`即死」パターンを踏んでいない。唯一のもう1箇所の`git ls-files -s`代入(`file_mode=...`)は裸の代入だが、実測した限り`git ls-files -s -- "$file"`自体が非ゼロ終了するケースは作れず(該当なし・複数マッチいずれもrc=0)、`set -e`による即死は再現しなかった。
- **`git rm`によるstaged削除は`--diff-filter=ACMR`により`staged_files`へそもそも現れない**ため、削除操作がvaultループに到達すること自体がなく、誤検知・見逃しどちらの経路にもならないことを実測確認した。
- **renameは新パスのみが対象になり、`git show ":$file"`で新パスのstaged contentを正しく読む。** rename+同時に平文へ改変したケース(`git mv`後に内容を書き換えてre-add)でも正しく検出することを実測確認した(fail-closedではなく通常の`ERROR: ... not Ansible Vault encrypted`経路)。
- **空ファイル・非UTF-8バイナリ内容のvault命名ファイルは、いずれもfail-closedではなく「暗号化されていない」として正しくブロックされる。** 空ファイルの`head -n 1`相当の`<<<`処理、NULバイトを含むバイナリ内容(bashが`ignored null byte`警告を出すのみで処理自体は継続)いずれも実測し、判定ミス(誤って通す)は起きなかった。
- **非ASCIIディレクトリ名の平文vaultファイルも正しく検出される。** 先行修正(`core.quotepath=false`)とこの変更が組み合わさり、`日本語dir/secret.yml`への平文コミットが正しくブロックされることを実測確認した。
- **ファイル名の空白・ハイフン・コロン・先頭ハイフンはいずれも問題なし。** `git show ":$file"`は`:path`構文でpathspecのglob/オプション解釈を経由しないため、`-vault-weird.yml`（先頭ハイフン）や`vault:weird.yml`（コロン含み）でも正しく内容を読み、正しく判定した。
- **symlinkスキップは通常のファイル名では正しく機能する。** vault命名に一致する単独のsymlink（他ファイルとのglob衝突が無い場合）は正しくスキップされ、`check-staged-yaml.py`側のsymlink扱いと一貫している。
- **既存チェック(gitleaks/dangerous-file/IPv4/YAML構文/tester-gate-lint)の出力・順序・終了コードに回帰は無い。** 全ての検証シナリオで、新設ロジックの前後にあるチェック群が期待どおりの順序・メッセージで動作することを確認した。今日追加された`core.quotepath=false`と引用符付きパスのfail-closedガード(1-25行目)はこの変更で触られておらず、機能に影響していない。
- **性能は現状問題ない水準。** vault/secret命名一致ファイル300件でgitleaks込み約1.9秒。実運用のcommit粒度(数ファイル)では体感できる遅延にならない。

## 未確認事項

- ファイル名に`*` `?` `[...]`のようなgit pathspec特殊文字を含む実ファイルは本リポジトリに現存しないため、Suggestion 1は理論上の再現に基づく報告であり、実運用での踏み間違いの実績はない。
- merge conflict中(unmergedなstage 1/2/3が同時に存在する状態)での`git ls-files -s`の複数行出力は個別に試していない。通常のcommit前フックはconflict解消後に実行される前提のため、優先度は低いと判断し検証範囲から外した。

## Verdict

**Approve** — 依頼が指摘した本来のバグ(stage/worktree不一致による誤検知/見逃しの両方向)は解消されており、機密情報が漏れる方向のfail-closed原則も一貫して守られていることを実測で確認した。Suggestion 1(pathspecのglob誤動作によるsymlinkの誤検知)は実在ファイル名では発生条件が満たされず、かつ発生しても機密漏洩ではなく誤ブロック方向にのみ働くため、blockingとはしない。次回このゲートへ手を入れる際にSuggestion 1-3(バッチ化・literal pathspec化)をまとめて解消することを推奨する。
