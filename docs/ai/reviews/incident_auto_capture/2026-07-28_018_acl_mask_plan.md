## 0. 結論(先に言う)

1. **Coordinatorの仮説は反証された。** 「後続の `acl` タスクがno-opになりmaskを戻さない」は誤り。`ansible.posix.acl` は maskの差分を検出して `setfacl` を実行し、**maskをrwxへ復旧する**。実測で確認した(§1.2)。W6の `group:` 追加も引き金ではない(§1.4)。
2. **真の根本原因は「`_spool/` のパーミッションビットに所有者が2人いること」。** `incident_capture` role と T1(`roles/common_slack/tasks/capture.yml`)の両方が `mode: "0755"` を持つ `file` タスクで同じディレクトリをchmodする。ACLを持つディレクトリではchmodがACL maskを書き換えるため、**roleが直したmaskを、次の通知でT1が壊す**。
3. **同じ欠陥クラスの正しい対処法は、このリポジトリに既に存在していた。** `roles/recovery_exec/tasks/main.yml:263-284` と `roles/recovery_mute/tasks/{deploy_cli,set}.yml` が「create-only(`mkdir -m 0755 -p` + `creates:`)、再chmodしない」という不変条件を、2026-07-14の独立レビュー(`review 2026-07-14_008 F1`)の結論として明文化している。`incident_capture` はこの先例を適用していない。**新しい発明は要らない。既存パターンへ寄せるだけ。**
4. 分解は **7単位**(U0〜U6)。最長35分、合計の想定subagent実働 約160分、subagent起動 7体。未決定の設計判断は全体で **3件**(単位あたり最大1件)。

## 1. 現物による裏付け(仮説の検証)

**他人の記録のfile:line参照は使わず、すべて現物を読み直して確認した。**

### 1.1 chmodはACL maskを書き換える(仮説のうち正しい部分)

scratchpadのテンポラリディレクトリで実測(実ホストには触れていない。ローカルの `chmod`/`setfacl` のみ)。

```
初期: user:nobody:rwx / mask::rwx  → stat = 775
chmod 0755 を実行
結果: user:nobody:rwx #effective:r-x / mask::r-x → stat = 755
```

ACLを持つディレクトリでは `stat` のgroupビットは**group entryではなくmask**を映す。したがって「maskがrwxの正常状態」では `stat` が **0775** を返す。role/T1が要求する `mode: "0755"` とは**常に不一致**になり、`file` モジュールは**毎回必ずchmodする**。仮説のこの部分は正しい。

### 1.2 しかし `acl` タスクはno-opにならない(仮説の誤り)

`ansible.posix.acl` の変更検出は `/usr/lib/python3/dist-packages/ansible_collections/ansible/posix/plugins/modules/acl.py` の `acl_changed()`(235-258行)。実装は **`setfacl --test -m <entry> <path>` を実行し、出力行が `*,*` で終わるときだけ「変更なし」と判定する**。エントリ文字列の一致比較ではない。

mask::r-x の状態で `--test` を実行した実測:

```
<path>: u::rwx,u:nobody:rwx,g::r-x,m::rwx,o::r-x,*
```

末尾は `*,*` ではなく `*` 単独(= access ACLは変わる / default ACLは変わらない)。よって **`changed = True` となり `setfacl -m` が実行され、maskはrwxへ復旧する**。`setfacl` は `-m` 指定時に既定でmaskを再計算するため(`--no-mask` を渡していない)、この復旧は副作用ではなく仕様どおりの動作である。

role のタスク列(`file` → access acl → default acl)を通しで再現した実測:

| 段階 | mask | stat |
|---|---|---|
| 前回実行後の定常状態 | `mask::rwx` | 775 |
| `file` の chmod 0755 | `mask::r-x`(`#effective:r-x`) | 755 |
| access aclタスク適用後 | `mask::rwx` | 775 |
| default aclタスク(`--test` は `*,*` = 真のno-op) | `mask::rwx` | 775 |

**role実行の終了時点では必ず `mask::rwx` になる。** default ACL側のmaskはchmodの影響を受けない(`default:mask::rwx` は全段階で保持された)ため、default ACLはこの問題に無関係である。

### 1.3 では誰が壊したのか — T1(`capture.yml`)

`roles/common_slack/tasks/capture.yml` の block 内2番目のタスク:

```yaml
- name: Ensure capture spool directory exists
  ansible.builtin.file:
    path: "{{ _capture_ctx.spool_dir }}"
    state: directory
    mode: "0755"
  delegate_to: localhost
  become: false
  changed_when: false
```

- このタスクは **通知1回ごとに実行される**(`capture.yml` は `notify.yml` 先頭から**無条件に**includeされる。`tester_mode` ゲートより前)。
- `changed_when: false` は報告を抑えるだけで、chmod自体は実行される。
- 実行identityは `become: false` の実行ユーザ(quory本番では `yoshi`)。`_spool/` のownerは `yoshi`(Q5実測)なのでchmodは成功する。
- maskがrwx(stat 775)の状態で `mode: "0755"` を要求 → chmod発火 → **mask::r-x**。role側にはこれを検知する経路がない。
- 一度落ちるとstatは755になり要求と一致するため、以降の通知ではchmodが発火しない。**壊れるのは「role実行後の最初の1回の通知」だけで、あとは壊れたまま固定される。**

### 1.4 観測された時系列との整合(W6起因説の否定)

| 時刻(JST) | 事象 | maskの状態 |
|---|---|---|
| 07-27 夜 W6 role実行 | roleのacl タスクがmaskを復旧 | rwx |
| 07-27 19:42 初回backfill | `reports/incidents/` 配下に38バンドル生成成功 | rwx(生成成功が傍証) |
| 07-28 05:45 / 05:50 の収集器 | spool空(R5b発火)。**削除対象が無いので失敗も出ない** | rwx |
| **07-28 05:50:20 T1が初のspoolレコードを書く** | **同時にchmod 0755が発火** | **r-x へ転落** |
| 07-28 05:55以降 11回 | `os.remove()` が Permission denied | r-x |

`git show cfcd1d3`(w6 implement)で確認したところ、W6が `roles/incident_capture/tasks/main.yml` へ加えたのは **`group: homelab-ansible` の1行とコメント6行だけ**。`capture.yml` の `mode: "0755"` は初出commit `68dd409` の時点から存在しており、W6での追加ではない。

**W6は原因ではない。** ただし「roleを流すとmaskがrwxに戻り、罠が再装填される」という意味では、W6のrole再実行が**罠を再装填した最後の操作**ではある。罠が今回初めて作動したのは、**quory本番でT1に到達する通知が2026-07-28 05:50が史上初だったから**(まさに `2026-07-28_016` がクローズしたWatch項目そのもの)。W6以前も同じ構造で壊れる状態にあり、単に発火条件が揃っていなかっただけである。

### 1.5 なぜ兄の `reports/incidents/` は壊れていないのか

仮説は「`group:` が無いので `file` が無変更だったから」と説明していたが、これも誤り。`reports/incidents/` も `mode: "0755"` を持つので毎回chmodされる。壊れていない理由は **`reports/incidents/` をchmodする書き手がrole以外に居ないから**である。roleは同一実行内で自分でmaskを直すので、実行終了時には常に正常。一方 `_spool/` だけは**role外の書き手(T1)を持つ**。

### 1.6 副次的に判明した既存欠陥(今回の修正対象に含める)

- **roleは恒久的に非冪等である。** `file` が毎回chmodし、access aclタスクが毎回それを直すため、`incident_capture` roleを何度流しても2つのaclタスク(`reports/incidents/` と `_spool/`)が**永久に `changed` を報告し続ける**。これは無害なノイズではなく、§1.1の構造がまだ生きている**観測可能な信号**である。→ AC3の検証述語として使う(§4 U5)。
- **role実行中にmaskがr-xになる窓がある。** `file` タスクから access aclタスクまでの数百ミリ秒〜数秒、maskはr-xである。収集器のtimerは5分間隔で常時稼働しているため、**この窓に収集器が起動すると1周期分だけ削除に失敗しうる**。確率は低いが実在する競合であり、create-only化で同時に消える。

### 1.7 `docs/ai/adr/003-incident-capture-collector-runtime.md` との関係

ADR-003 の Decision (b) b-1 とその「補正(Coordinator、2026-07-27)」(64-65行)は、`reports/incidents/` と `_spool/` へ named-user ACL を付与する**ところまで**を決めている。「その権限を誰が維持し、誰が壊してはならないか」は書かれていない。今回の欠陥はまさにその空白に落ちた。→ 新規ADRは作らず、**ADR-003へ「補正2」として追記する**(§3 D8)。

### C1 — `reports/incidents/` および `_spool/` のパーミッションビットの所有者は `incident_capture` role 単独とする

| 主体 | 許されること | 禁止されること |
|---|---|---|
| `incident_capture` role | ディレクトリの**新規作成時のみ** mode を決める。owner/group はいつでも強制してよい。ACL(access/default)を付与・維持する | 既存ディレクトリへの再chmod |
| T1 `capture.yml` | ディレクトリが無ければ**作る**(ansy等、roleが流れないホストのため) | **modeの指定。既存ディレクトリのパーミッション変更全般** |

**不変条件(この案件で確立する規範): 名前付きACLを持つパスを再chmodしない。** 先例は `roles/recovery_exec/tasks/main.yml:263-284`(2026-07-14 review 008 F1)。

### C2 — 正常状態の定義(検証述語)

`_spool/` と `reports/incidents/` の両方について:

```
user:recovery-exec:rwx      ← "#effective:" の注記が付かないこと
mask::rwx
group::r-x
other::r-x
stat = 0775
```

**判定は `getfacl` の出力に `#effective:` が現れないことをもって行う。** `stat` の値だけで判定しない(0755/0775の見分けは分かりにくく、実際にW6の受入で見落とされた)。

### C3 — AC5掃引の起点は「ACL付与タスク」であり、パス文字列ではない

掃引は次の順で行う。逆順(パス文字列から探す)は**やってはいけない**ことが実証済み(§5)。

1. リポジトリ全体から ACL を作る箇所を列挙する(`ansible.posix.acl` タスク、および `setfacl` を直接呼ぶscript/template)。
2. 各エントリの `path:` に使われている**変数を解決**し、別名(別の変数名で同じ実体を指すもの)を洗い出す。
3. その実体を書くすべてのコード(`file`/`copy`/`template`/`command`/`shell`/Python `os.chmod`)を、**変数名でも**検索する。
4. 「named-userまたはnamed-group ACLを持つパスに対するchmod相当」が1件でもあれば該当。

### C4 — AC4の後始末の選択述語

- 削除対象: `reports/incidents/` 直下の `spool-1785185420-*` バンドルディレクトリのうち、**mtimeが最も古い1件を残した残り全部**。

## 5. AC5の掃引範囲の決定と、その根拠(Tech Leadの判断)

### 決めた範囲

**「named-user または named-group の POSIX ACL を持つ(または将来持ちうる)パスに対する、chmod相当の操作」だけを見る。**

### なぜこの境界で「他に無い」と言えるのか

POSIX ACLのmaskエントリは、**named entry(named-user / named-group)またはgroup entryが存在する拡張ACLにのみ作られる**。maskが存在しなければ、chmodは通常のパーミッションビットしか書き換えず、実効権限が切り詰められる余地は無い。したがって **ACLを持たないパスへのchmodは、この欠陥クラスを原理的に発生させられない。** 「たぶん問題ない」ではなく、機構として閉じている。これがリポジトリ全体のchmodを掃引しないことの正当化である。

### なぜパス文字列からの検索では不十分か(実証済み)

Tech Lead自身が最初にこう検索した:

```
grep -rn "_spool" roles/ playbooks/ scripts/ | grep -iE "chmod|mode:|mkdir -m"
```

**結果はゼロ件。今まさに壊れている当該箇所を1つも拾えなかった。** 理由は、書き手が実パスではなく変数(`incident_capture_spool_dir`、`capture_spool_dir`、`_capture_ctx.spool_dir`)を経由しているため。同じ検索は `reports/incidents` でもゼロ件だった。

**この失敗そのものが、C3(ACL付与箇所を起点に、変数を解決してから書き手を追う)を義務づける根拠である。** U4のReviewerは、この失敗例を再現して掃引記録に載せること(方法の妥当性の証明になる)。
