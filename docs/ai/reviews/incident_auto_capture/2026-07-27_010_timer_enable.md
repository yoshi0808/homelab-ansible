## 1. timer有効化

W5(009_test_result.md)の申し送りどおり、W5では`incident_capture_service_enabled`未指定(既定`false`)でtimerは`disabled`/`inactive`のまま配備されていた。本作業は依頼文に記載のCoordinator承認(全AC PASS、実データreplayで動作確認済みのため`docs/ai/core.md`「未確認のコードをquoryの定期実行へ載せない」に抵触しないとの判断)に基づき、timerを有効化した。

playbook対象(`playbooks/incident_capture_setup.yml`)の`# tester-gate: risk-accepted`マーカーを実行前に確認した。理由文は「quory以外のホストへの破壊操作なし、既存稼働中サービスの再起動なし。変更はディレクトリ作成(冪等)、`reports/incidents/`限定のACL付与(RSK-06どおり`reports/`直下へは付与しない)、script/config/unit配備、および`incident_capture_service_enabled=true`時のみ新規oneshot timerの有効化+起動」であり、実装(`tasks/main.yml`)の内容と照合し乖離なし。`risk-accepted`は`--check`なしの通常実行が前提。

実行コマンド(playbookヘッダに明記された「Production enable」手順そのまま):

```
ansible-playbook playbooks/incident_capture_setup.yml -l quory -e incident_capture_service_enabled=true
```

実測PLAY RECAP: `quory: ok=15 changed=5 unreachable=0 failed=0 skipped=0 rescued=0 ignored=0`

`changed=5`の内訳: `reports/incidents/`ディレクトリ作成、`_spool/`ディレクトリ作成、ACL付与(access, `reports/incidents/`)、ACL付与(access, `_spool/`)、timer enable+start。W5で`skipped`だった「Enable and start incident-capture timer」タスクが、今回は`changed`として実行された(`incident_capture_service_enabled=true`により条件成立)。他の10タスクは`ok`(既に冪等に満たされていた既存配備分、W5配備時点から変更なし)。

`-l quory`のみを指定し、targetsへ波及する引数(`-l`の追加拡張やlimit変更)は付けていない。

## 4. flockの実地確認(quory本番、意図的な多重起動)

W5はfixtureでの検証に留まっていたため、本番配備済みunitに対して実地確認した。

手順:
1. `systemd-run --unit=flock-hold-test --uid=recovery-exec --gid=recovery-exec /usr/bin/flock -x /run/lock/homelab-incident-capture.lock /bin/sleep 12` で、ロックファイルを一時的に排他保持するtransient unitを起動(SSHセッションのライフサイクルから独立させるため`systemd-run`を使用。当初`nohup ... &`で試みたがSSH切断時にプロセスが失われ`Permission denied`という別の誤読を招いたため`systemd-run`に切替)。
2. 保持中に `systemctl start homelab-incident-capture.service` を実行。

結果:

```
Job for homelab-incident-capture.service failed because the control process exited with error code.
systemctl show ... → Result=exit-code, ExecMainStatus=75
journalctl: Main process exited, code=exited, status=75/TEMPFAIL
             Failed with result 'exit-code'.
```

`ExecStart=/usr/bin/flock -n -E 75 /run/lock/homelab-incident-capture.lock ...`(unit定義どおり)の**exit 75が本番環境で実際に再現された**。通常の失敗(exit 1)と区別できる値であることも実測で確認した。

保持プロセス(`sleep 12`)終了後、timerの次回自然発火(20:20:01)で自動的に`Result=success`/`ExecMainStatus=0`へ復帰したことを§5で確認した。`systemctl is-failed homelab-incident-capture.service`も最終的に`inactive`(失敗記録が残っていない)。

透明性のため記載: この確認は「読み取り専用の確認」の範囲を超え、収集器を意図的に1回追加起動させる操作を伴う。ただし対象はTester自身が今回有効化したばかりの新規timer/serviceであり、他の本番サービスへの影響はない(oneshot、状態を持たない、実害が生じてもmax severityはexit 75で正常に収束する設計)。依頼文の「flockの実地確認を可能な範囲で確認してください」という明示指示の範囲内と判断し実施した。Proxmox/Sophos/UniFiへの操作ではないためCoordinatorへの事前提示は不要な区分(tester.md該当箇所)に当たると判断したが、範囲判断の記録として明記する。

副次片付け: 検証用に一時作成した`/tmp/flock-hold.log`(最初の`nohup`試行の残骸)を`rm -f`で削除した。`flock-hold-test.service`はtransient unitのため自動的に消滅済み(`systemctl status`で`could not be found`を確認)。

## 残存リスク

- 本作業で観測できたのは「新規失敗イベントが無い周期」(exit 0、SSHなし)と「flock衝突」(exit 75)の2パターンのみ。実際に新規のSemaphore失敗ジョブが発生し、`incident_capture_failure_snapshot_ops`経由でSSH名前付き操作まで到達する一連の経路は、W5のAC2(過去データreplay)では確認済みだが、**timer有効化後の"リアルタイムの新規失敗"での一次観測はまだ無い**(009_test_result.mdの残存リスクを引き継ぐ)。次に実際の失敗ジョブが発生した際、そのバンドルとハートビートを確認することを推奨する。
