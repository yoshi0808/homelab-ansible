## 詳細: R5(check mode挙動の変化)— 計画の前提を実行検証で反証した

計画は「`command` モジュールは check mode で自動skipされるため、role側のcreate-onlyタスクが `--check` でskipされる影響を評価してください」と指示していた。**この前提は `creates:` を指定した `command` タスクには当てはまらない。**

### ソースの確認

`/usr/lib/python3/dist-packages/ansible/modules/command.py`:
- 266行目: `AnsibleModule(..., supports_check_mode=True, ...)` — `command` モジュールは check mode 対応を自己申告しており、`--check` 下でもモジュール本体のPythonコードは実行される(実行自体がskipされる、というのは `supports_check_mode` を宣言していないモジュールの挙動であり、`command` はこれに該当しない)。
- 306-328行目: `creates`/`removes` の判定(`glob.glob()`)は `module.check_mode` の分岐より**前**に行われる。`creates` パスが既に存在する場合、check/非check問わず同じ結果(`changed: False`、`msg`)を返して即 `exit_json` する。
- 330-346行目: `creates` パスが存在しない場合のみ `changed = True` を立てたあと、`module.check_mode` なら実コマンドを実行せず `msg: "Command would have run if not in check mode"` を返す。`skipped` は `creates is None and removes is None` のときだけ立つため、**`creates:` を指定している今回のタスクでは `skipped` にはならない**(`ok`/`changed` として扱われる)。

### 実行検証(scratchpad decoy、`ansible_connection: local`)

対象タスク相当(`command: mkdir -m 0755 -p <dir>` + `creates: <dir>`)を実際に `--check` と通常実行の両方で流した。

**target不在の場合、`--check`**:
```
changed: [localtest]
"changed": true, "rc": 0, "msg": "Command would have run if not in check mode"
```
→ ディレクトリは実際には作られない(`ls: cannot access 'work': No such file or directory` で確認)。**skipped ではなく「changed=trueの予測」。**

**target存在の場合、`--check` / 通常実行 双方**:
```
changed: False, "msg": "Would not run command since '...' exists" / "Did not run command since '...' exists"
```
→ 両モードで同一の `changed: False` no-op。

### 評価

- **旧 `file` タスク**(mode/owner付き、対象不在)も `--check` では `module.check_mode` 分岐で `changed: True` を即返し実際には作らない(`file.py:636-637`)。**「不在時に `--check` が changed=True を予測する」という挙動は旧・新で同じ。**
- 差は「target**存在**時」に出る: 旧 `file` タスクは mode/owner の diff を毎回評価し、drift があれば `--check` でも `changed: True` を報告できた(ただし本欠陥の根本原因はまさにこの「毎回評価する」性質自体だった)。新 `command` タスクは存在有無しか見ないため、既存ディレクトリの mode がどうなっていようと `--check` は常に `changed: False` を返す。これは**意図した設計(D3: 既存ディレクトリのmodeに二度と触れない)の直接の帰結**であり、欠陥ではない。ただし「`--check` でmode driftを検知できなくなる」という観測可能な副作用ではあるので Suggestion #2 として記録した。
- `playbooks/incident_capture_setup.yml` の tester-gate は `risk-accepted` であり `--check` を正規の実行経路として要求していない(1-27行目で確認済み)。したがって本件は blocking ではない。

**結論: R5は実害なし。ただし計画の技術的前提(自動skip)は誤りであり、Suggestion #1として訂正を推奨する。**
