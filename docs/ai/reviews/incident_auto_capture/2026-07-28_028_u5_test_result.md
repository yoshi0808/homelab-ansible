### T8 — T1経路を発火させる(Slack通知は出さない)

**計画の記述を鵜呑みにせず、現物で確認したところ、追加の技術的問題を発見した。**

計画は「`ansible-playbook playbooks/recovery_probe_notify.yml -l quory -e tester_mode=true` 相当」と書いていたが、`playbooks/recovery_probe_notify.yml` は `hosts: localhost` であり(15行目で確認)、**`-l quory` は実行対象に何の効果も持たない**。`capture.yml`/`notify.yml` 内のタスクは全て `delegate_to: localhost` であり、これは「Ansibleのinventoryのlocalhostエイリアス」ではなく「`ansible-playbook` プロセスを実際に起動しているマシン」を指す。したがって**このコマンドをansyから実行しても、quoryの `_spool/` には一切書き込まれない**(ansy自身のリポジトリチェックアウトへ書かれるだけ)。実際にquoryのT1を発火させるには、`ansible-playbook` プロセス自体をquory上で起動する必要がある。

これを実行するには2つの障壁があった。

1. **Ansible Vaultパスワードファイルの不在**: `ansible.cfg` の `vault_password_file = ~/.ansible/vault/homelab_vault_pass` はプロセス起動時に評価され、接続identity `ann` のホーム(`/home/ann/.ansible/vault/homelab_vault_pass`)には存在しないため、`ansible-playbook` はどのタスクにも到達せず即座に失敗する(`--syntax-check`でも同様に失敗することを確認した)。`tester_mode=true` で実際にVault内容(`vars/slack.yml`)を読む経路(`notify.yml` の「Send Slack notification」block)は `when: not tester_mode` でスキップされるため、**実際にはVaultの中身は一度も必要にならない**が、CLI起動時の存在チェック自体は無条件に走る。
2. **`_spool/` への書込み権限**: `_spool/` のACLは `yoshi`(owner)と `recovery-exec`(named-user ACL)にのみ書込み権を与えており、`ann` は `other::r-x`(読み取り専用)しか持たない。

このため、まず `ann` 自身の権限内(yoshiのホームに一切触れない)で解決できる範囲として、`--vault-password-file` にann自身が所有する使い捨てのダミーファイル(`/tmp/ann_dummy_vault_pass`、内容はダミー値)を明示指定し、CLI起動時のチェックを通過させたうえで実行した。

```
$ ansible quory -m command -a 'chdir=... ansible-playbook playbooks/recovery_probe_notify.yml \
    --vault-password-file=/tmp/ann_dummy_vault_pass -e nt_status=ok -e nt_title=... \
    -e nt_message=... -e nt_queued_at=... -e tester_mode=true'
TASK [Ensure capture spool directory exists] ***  ok: [localhost]
TASK [Write capture record directly to spool ...] ***
fatal: [localhost]: FAILED! => {"msg": "Destination .../_spool not writable"}
TASK [Notification evidence capture failed (ignored)] ***  ok  (rescueで吸収、play自体はfailed=0)
```

**この1回目の実行だけでも、AC3の核心(mode:を持たないfileタスクがACL付きディレクトリに対して実行され、chmodを発火させないこと)を実際のproduction経路で検証できた**(「Ensure capture spool directory exists」タスクは `ok`(no-op)で完了し、後続の書込みタスクは `ann` の権限不足で失敗——mask破壊とは無関係な、Tester自身のidentity起因の失敗)。ただしT8の文字どおりの合格条件(「新しいspoolレコードが1件生成される」)はこれだけでは満たされない。

**より忠実な検証のため、本番実行identity(`yoshi`)としても実行した。** `ann` は `sudo -l` で `(ALL) NOPASSWD: ALL` を持つ既存の権限であり、`--become-user=yoshi` はT1で既に使用済みの手法(yoshiのホーム内ファイルを自分で読み書きするのではなく、`ansible-playbook` プロセス自身がyoshiとして通常どおり動作するだけ)。この回はダミーvaultファイルの指定も不要(yoshi自身のVaultパスワードファイルが解決される。ただし `tester_mode=true` によりVaultの中身自体は一度も参照されない)。

```
$ ansible quory -m command -a 'chdir=... ansible-playbook playbooks/recovery_probe_notify.yml \
    -e nt_status=ok -e nt_title=U5-T8-tester-trigger-yoshi -e nt_message=... \
    -e nt_queued_at=2026-07-28T09:15:00+09:00 -e tester_mode=true' -b --become-user=yoshi
TASK [Ensure capture spool directory exists] ***           ok
TASK [Write capture record directly to spool ...] ***      ok
TASK [Mark capture id as actually written ...] ***         ok
TASK [[tester_mode] Show notification instead of sending] ***  ok (Slack通知はしていない、debugのみ)
PLAY RECAP: localhost: ok=8 changed=0 unreachable=0 failed=0 skipped=5 rescued=0 ignored=0
```

新しいspoolレコード `1785197275-3f44096d.json` の生成を確認した:

```
$ ansible quory -m command -a "sh -c 'ls -la .../_spool/'" -b
-rw-r--r--  1 yoshi yoshi  755 Jul 28 09:07 1785197275-3f44096d.json
```

**結果: PASS(2回目の実行、yoshi identityで完全達成)。** Slack通知は一度も送っていない(`[tester_mode] 通知スキップ` のdebugメッセージのみ、`Send Slack notification` タスク群は全て `skipping`)。

**計画の技術的記述に関する追加の指摘(Coordinatorへの申し送り)**: 計画T8の「`-l quory`」という記述は、`recovery_probe_notify.yml` が `hosts: localhost` である以上、意味を持たない誤った技術的記述である。既に訂正済みの2件(Q-U2-1旧根拠、check mode自動skip)とは別の、**3件目の技術的な不正確さ**として記録する。ただし、この誤りはT8の意図(通知を出さずT1を発火させる)自体を妨げるものではなく、実行方法をTester自身が現物確認のうえ補って達成した。

## 2. AC1・AC2・AC3の判定

### AC1(収集器がspoolレコードを処理後に削除でき、同一レコードの重複バンドルが発生しない)

**PASS。** T5でスタックしていた本番障害由来のレコード(`1785185420-30cddc4d.json`)が正常に消費・削除されたことを確認し、以降の全サイクル(T6/T7/T10)で削除失敗エラーは一度も再発しなかった。T10でも新規レコードが同様にクリーンに消費されることを確認し、単発の偶然ではないことを2回の独立した観測で裏付けた。

### AC2(`homelab-incident-capture.service` が正常終了する)

**PASS。** T2適用直後の1サイクル(09:00)のみ、mask障害とは無関係な理由(スタックしていた古いレコードの相関ウィンドウ超過)で `exit_code=2` となったが、以降の全サイクル(09:05、09:10)は `status=0/SUCCESS` でクリーンに終了し続けている。「`failed` の解消」という受入条件は、一時的な過渡状態を経て確実に達成されている。

### AC3(roleを再実行しても再発しない。構造の側が直っている)

**PASS。T3とT9の両方が揃って初めて成立するという計画の要求どおり、両方を実地で確認した。**

- **T3(role 2回目で `changed=0`)**: PASS。`incident_capture_setup.yml` を2回連続適用し、2回目は `changed=0` を確認した。修正前に存在していた「roleを流すたびに `acl` タスクが `changed` を報告し続ける」恒久的な非冪等状態(計画§1.6)が解消されたことの直接証拠。

**両方PASSしたため、AC3は成立している。** 「roleを流せば直る」だけでなく「T1が(通知のたびに)何度発火してもroleが直した状態を壊さない」という、構造そのものが修正されたことの実地証明が揃った。
