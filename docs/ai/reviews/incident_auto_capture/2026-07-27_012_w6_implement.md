### footerが指すIDの信頼性(2026-07-27、独立レビュー013指摘 → Coordinator決定で修正済み)

初版では footer の値を `_capture_ctx.id` から直接組んでいたが、これには欠陥が
あった。`_capture_ctx` は capture.yml の最初のtask(`set_fact`単体、I/Oなし)で
確定するため、**それより後段**(スプールディレクトリ作成または書き込み)で
失敗した場合、`_capture_ctx.id` は既に定義済みのまま残り、**footerには表示
されるがディスク上には対応するレコードが存在しないID**が出た。実測で確認
した(`capture_spool_dir` を書込不可パスに向けて実行、`capture.yml` 自身の
rescueが発火し `rescued=1`、`_capture_ctx.id` は定義済みのままfooterに出た)。
これは自分で見つけて直さずCoordinatorへ報告し、独立レビュー(013)が同じ
欠陥を再現、Coordinatorが「+1タスクのコストで書き込み成功済みIDのみを
footerへ出す」設計に決定した。

**対応**: block内の最後(書き込みtaskの直後)に `_capture_written_id:
"{{ _capture_ctx.id }}"` を設定する専用taskを追加した(`rescue:` は
`debug` 1つのみのままで、ADR-004の不変条件は変えていない)。`notify.yml` の
`footer:` は `_capture_ctx.id` ではなく **`_capture_written_id`** を参照する
よう変更した:
`{{ 'capture: ' ~ _capture_written_id if _capture_written_id is defined else '' }}`。

これにより block内の1〜3番目のいずれかで `rescue` が発火すると、4番目の
`set_fact` は実行されず `_capture_written_id` は未定義のまま残り、footerは
自動的に空文字へ縮退する。`_capture_ctx is defined` の短絡評価と同じ仕組みで
`_capture_written_id is defined` も未定義時にエラーなく空文字へフォールバック
することを実測で確認済み(下記「自己検証」参照)。

コストは block内のtaskが3→4に増え、正常完了経路の合計taskは
4→5(`ok`の増分は+4→+5)。実装2の削減目標より「通じないIDは無いIDより悪い」
というR6の目的を優先する、というCoordinatorの明示判断による。

## 実装2: タスク数削減(7→4、のち独立レビュー対応で7→5に修正)

W0(この案件のベースライン、`004_observation.md`)時点の値は `ok=3`。
T1導入直後(本セッション開始時点の現状)を実測すると `ok=10`(すなわちT1が
+7)。削減直後の実測は `ok=7`(T1が+4、目標どおり)。**ただしこの後、上記
「実装1」節のfooter信頼性修正で `_capture_written_id` 用のtaskを1つ追加した
ため、最終的な実測値は `ok=8`(T1が+5)。** 削減そのものの効果(6 block
taskを3へ、2taskの `mv` 除去+3つの `set_fact` を1つへ統合)は変わっていない
— 純粋な削減の成果は「7→4」であり、そこへ信頼性のための+1が乗って
最終形が「7→5」になった、という順序で理解すること。

実施した2つの削減:

1. **`.json.tmp` + `mv` の2taskを、`copy` で最終 `.json` へ直接書く1taskへ
   統合。** requirement AC8節の主張(`copy` は `atomic_move()` を呼び、
   主経路は素の `os.rename()`)をソースで確認した上で、**実測でも検証した**:
   このリポジトリの実 `reports/incidents/_spool/`(gitignore対象、同一
   ファイルシステム)へ `copy` で500,000バイトのcontentを直接書き込み、
   書き込み前後で `ls -la` を比較 — 中間ファイル・隠しファイルは一切現れず、
   最終ファイルのサイズも即座に完全なサイズと一致した(部分書き込みが
   観測される窓は無かった)。書き込み後に `git status --short` を確認し、
   対象ファイルは(gitignore済みのため)一切現れないことも確認した
   (実測は本ファイル末尾の一時ファイルではなく、対象を削除する前の生ログを
   本記録作成中に直接確認したもの)。
2. **`set_fact` 3つ(spool先解決/時刻確定/レコード構築)を1つ `_capture_ctx`
   へ統合。** ただし単純な統合はしていない — **同一 `set_fact` task内の
   兄弟キーは互いの値を参照できない**ことを先に実測で確認した(1つの
   `set_fact`に `_now` と、それを参照する `_derived` を並べたところ、
   `_derived` は `_now` を "undefined" として扱った。同一task内の各キーは
   task開始時点の変数スナップショットに対して独立にテンプレート化される)。
   そのため素朴な統合は「時刻を1回だけ確定させる」性質を壊すか、`lookup`
   を複数回呼ぶ形になり、**今日の教訓(`vars:` のlookup複数回評価)と同じ
   クラスの不具合を作る**ため採らなかった。
   代わりに、Jinjaの `{%- set x = ... -%}` を1フィールドの**単一の
   Jinja評価**の中だけで使うテクニックを実測で検証した: `lookup('pipe', ...)`
   を `{% set %}` でローカル変数へ束縛し、同じフィールドの `{{ {...} }}`
   辞書リテラル内で複数回参照させる。カウンタファイルへ副作用ログを仕込んで
   実行したところ **lookup呼び出しは1回のみ**であり、かつ結果の fact は
   `is mapping == True`(文字列化されていないネイティブdict)で、後続task
   から `_capture_ctx.spool_dir` / `.id` / `.record` の属性アクセスが
   正常に機能することを確認した。この技法により、日付の lookup を1回に
   保ったまま spool先パス・id・レコード全体を1つの `set_fact` task内で
   組み立てられた。
   結果、block内のtask数は6→3(コンテキスト構築/ディレクトリ作成/書き込み)。
   `notify.yml` 側の `include_tasks` 1taskと合わせて、正常完了経路の合計
   taskは 7 → **4**。

**削らなかったもの**: スプールディレクトリ作成task(`Ensure capture spool
directory exists`)。計画書・依頼文双方が明示的に温存を指示しており、
削除すると配備playbookが実行されていないansy(Tester環境)で捕捉が
機能しなくなるため。

## 実装3: `_spool/` のグループ所有の是正

`roles/incident_capture/tasks/main.yml` の `Ensure reports/incidents/_spool/
exists` task へ `group: homelab-ansible` を追加した(`owner: yoshi` の隣)。
兄タスク `Ensure reports/incidents/ exists` は `group:` を指定していないが、
これは親 `reports/`(setgid, group=homelab-ansible)からの継承で
group=homelab-ansible になることが `2026-07-27_004_observation.md` で
既に確認済みのため。`_spool/` は `reports/incidents/`(setgidではない、
mode 0755)のさらに下に作られるため継承が一段で途切れ、`become: true`
実行時のプロセス実効グループ(root)がそのまま採用されていた
(`2026-07-27_009_test_result.md` の副次観測どおり)。今回は明示的に
`group:` を指定することで揃えた。

**確認できなかったこと**: ansy(この開発機)には `homelab-ansible` という
Unixグループ自体が存在しない(`getent group homelab-ansible` は空)ため、
このrole自体をローカルで実行して実際にgroupが揃うことを確認する手段がない
(実ホストquoryへの配備playbook実行は禁止されている)。YAML構文と
`ansible-lint` は通したが、実機での反映確認はTesterの領分として残る。
