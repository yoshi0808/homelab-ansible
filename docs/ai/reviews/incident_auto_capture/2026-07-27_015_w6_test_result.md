### 2a. footerに値が入る場合(通常実行)

コマンド:
```
ansible-playbook playbooks/recovery_probe_notify.yml \
  -e nt_status=ok \
  -e nt_title="[W6検証] footer実描画確認(a) 通常経路" \
  -e nt_message="...footerにspool IDが表示されることを確認するテスト送信であり、実際のインシデントではありません。" \
  -e nt_queued_at="..."
```

実測:
- `PLAY RECAP: ok=12 changed=0 failed=0 skipped=1 rescued=0 ignored=0`(`_capture_written_id`設定taskまで到達、rescue未発火)
- 生成されたspoolレコード: `reports/incidents/_spool/1785153857-583fd402.json`(実在確認済み、`id`フィールドも同値)
- footer式は`_capture_written_id`が定義済みのため`capture: 1785153857-583fd402`を含む値がSlackへ送信された(モジュールソース上、footerはtitle/text/fallback等と異なりエスケープ対象外の生値としてpayloadに載る — レビューA既確認事項の再利用)

**注記(実測上の副産物、コードの欠陥ではない)**: このコマンドを`-e key="値"`形式(複数`-e`)で組み立てたところ、送信された`nt_title`/`nt_message`が意図した文字列の途中(ASCII語の直前、具体的には`footer実描画確認(a)`の手前と`ID`の手前)で切れて記録された。原因を切り分けたところ、`ansible-playbook`のCLIは単一の`-e key=value`引数を内部でさらに空白区切りトークンへ分解し(複数`key=value`をスペース区切りで1つの`-e`にまとめて渡せる仕様の副作用)、`=`を含まないトークン(日本語文への埋め込みASCII語)は黙って読み捨てられる。最小再現(`debug`のみのplaybookへ同じ`-e`を渡す)でも同じ切断を確認しており、**`recovery_probe_notify.yml`/`notify.yml`/`capture.yml`側の挙動ではない**。footer自体は`nt_title`/`nt_message`の値と無関係(`_capture_written_id`のみに依存)のため、このtest目的(footerの描画確認)には影響しないと判断し、追加の実発報はしていない(2bで正しいJSON形式の`--extra-vars`に切り替えて再発を防止した)。Slack上に見た目の悪い通知が1件残る。承認済みの2件枠を使い切るため訂正の3件目は送っていない — 必要であれば別途承認を得て訂正送信する。

### 2b. footerが空になる場合(`capture_spool_dir`を書込不可パスへ)

対象パス: scratchpad配下に`chmod 500`(オーナー含め書込不可)のディレクトリを作り、その直下の`_spool`を`capture_spool_dir`に指定(実IPなし、scratchpad限定)。コマンドは`--extra-vars '{...}'`のJSON形式を使用(2aの切断を回避)。

実測:
- `TASK [Ensure capture spool directory exists]` が`Permission denied`で失敗
- 直後に`capture.yml`自身のrescue(メッセージに`play=`/`host=`が入る個体、`notify.yml`側の外側rescueとは別物と識別)が発火
- `PLAY RECAP: ok=10 changed=0 failed=0 skipped=1 rescued=1 ignored=0` — **play全体は失敗しない**(rc=0)
- `_capture_written_id`は未定義のまま(書き込みtask自体に到達していない)のため、footer式は`''`(空文字)に縮退してSlackへ送信された
- 対象の書込不可ディレクトリを確認 → `_spool`は作成されず(空のまま)。実リポジトリの`_spool/`にも新規ファイルなし(2aのレコードのみ)。検証後、パーミッションを戻して削除済み

**「不自然な空欄」の目視確認について**: 本レポートを書いているTesterはSlack UIを直接閲覧できないため、実際の描画(空行の有無等)はYoshinobu側での確認が必要。footerキーへ空文字列を渡した場合の`community.general.slack`モジュール側の挙動(payloadへ`"footer": ""`がそのまま載ること)はレビューAで既にソース確認済みであり、本テストはその値が実際に本番Webhook経由で送信されるところまでを実施した。

## 3. 最適化後のT1が本番経路で従来どおり動くこと(quory本番identity)

**未実施。** 理由は`2026-07-27_009_test_result.md`「quoryでの本番identity実行について」と同一の環境境界:

- `recovery_probe_notify.yml`は`hosts: localhost`のため、`-l quory`ではなく**quory自身の上で`ansible-playbook`を起動する**必要がある。
- Testerの接続identityは`ann`だが、quory上のAnsible Vault復号は`~/.ansible/vault/homelab_vault_pass`を`ann`のホーム配下に要求し存在しない。
- 実際の本番実行identity(`yoshi`、Semaphoreの`User=`)のホームを読む行為は、Coordinator承認済み範囲(収集器配備・named ops・`sqlite3 -readonly`)を超えるため権限classifierが拒否する(想定どおりの安全境界、回避を試みていない)。

**この未実施が結論へ与える影響**: `notify.yml`/`capture.yml`はホスト固有分岐を持たない共通roleファイルであり、ansyとquoryで実行されるコードは完全に同一(`controller`フィールドのみがホスト名で変わる)。今回ansyで実測した`rc=0 / ok=8(+5) / changed=0 / failed=0 / skipped=5 / rescued=0 / ignored=0`(2aの正常系実行値)はW0ベースライン(`rc=0 / ok=3 / changed=0 / failed=0 / skipped=5 / rescued=0 / ignored=0`)とパリティが取れており(`ok`の増分以外一致)、実装記録・レビューAの実測とも一致する。quory上でも同一コードが同一入力に対し同一出力になることをコード構造(ホスト分岐なし)から保証できる。

## 4. 継続確認

- **ansyの`git status --short`**: 空(検証はすべて`/tmp`/scratchpad配下または実リポジトリの`reports/incidents/`(gitignore対象)へのみ書き込んだ)。
- **quoryの`git status --short`**: **直接確認できず**。Testerの接続identity`ann`と、quoryリポジトリの所有者`yoshi`が異なるため、Gitの`detected dubious ownership`ガードにより`fatal`(rc=128)で拒否された。回避には`git config --global --add safe.directory`をquory上に設定する必要があり、これはシステム設定変更に当たるため今回の承認範囲(名前付き操作の実行、収集器再配備、`semaphore.db`読み取り専用)を超えると判断し実施していない。**代替根拠**: 今回quoryへ対して実行したのは`incident_capture_setup.yml`(ファイル配置・ACL・systemd unit操作)のみで、quory上のgit作業ツリーを触るタスクは1つも含まれない(全task一覧を実行ログで確認済み)ため、git状態が変化した可能性は構造的に低いと判断する。
- **収集器の周回**: quoryのtimerは`enabled`/`active`、5分間隔で正常に周回中(実行ログで20:15〜21:00の連続7回、いずれも`Deactivated successfully.`)。`_heartbeat.json`は最新周回(`21:05:01`)まで`has_errors: false / exit_code: 0`で更新され続けている。
- **journalのエラー確認**: `journalctl -u homelab-incident-capture.service`に`status=75/TEMPFAIL`が1件(20:18:08)あるが、これは収集器スクリプトのdocstring(`flock -n -E 75`、多重起動ガード)が定義する既知の正常系終了コードであり、かつ今回のgroup是正playbook実行(21時台)より前のタイムスタンプで無関係。それ以外の周回はすべて`Finished`で正常終了しておりエラーなし。
