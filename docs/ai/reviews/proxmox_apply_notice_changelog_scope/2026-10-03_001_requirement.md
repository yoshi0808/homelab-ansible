# requirement: apply通知のCVEを今回の更新分に絞り、本文が切れないようにする

作成: 2026-10-03 / Coordinator
起点: 案件 `proxmox_patch_notifications_2b`(commit `65d6074`)の本番初回観測(2026-10-03の自動適用)。範囲はYoshinobu合意済み(2026-10-03)。

## 1. 問題定義

2026-10-03の自動適用(pve2 06:14、pve1 06:23、いずれもSUCCESS)のapply通知で、次の2つが起きた。

1. **CVEが過去の履歴まで載った。** `openssl-provider-legacy 3.5.7-1~deb13u2 → 3.5.7-1~deb13u3` の行に、CVE-2006-2937 から始まる数百件のCVEが並んだ。`roles/proxmox_patch_apply_node/files/proxmox-patch-changelog-collect.py` の `changelog_note()` が、`apt changelog <package>` の**出力全体**(新しい版のchangelogの過去の履歴すべて)から `CVE-\d{4}-\d{4,7}` を拾っている(同ファイル50行目)
2. **本文がSlackで途中で切れ、適用後のhealthcheck(Phase 5)とreportのファイル名が届かなかった。** 本文は「CVE-20…」で終わっていた。`roles/common_slack/tasks/notify.yml` は本文を切り詰めない(`attachments[].text` にそのまま渡す)ため、Slack側の上限で切られたと見ている。**判断に最も要る適用後のhealthcheckの結果が見えなくなった**

案件2bの検証ですり抜けた理由: テストの偽の `apt changelog` が最新の項目だけを返しており、本物が過去の履歴まで返すことを再現していなかった。本文の長さの上限も受入条件に無かった。

## 2. ゴール

- packageごとのCVEは、**今回の更新で入る項目(入っている版より新しい項目)**だけになる
- apply通知は、packageやCVEがどれだけ多くても、**適用後のhealthcheck(Phase 5)とreportのファイル名の行が必ず届く**

## 3. 非ゴール

- packageごとの表示の形(`<package> <旧版> → <新版>: <changelogの最新項目の1行目>`)は変えない
- dry-runの通知・収集は変えない
- `roles/common_slack` は変えない(本文の長さは呼び出し側のapply roleで抑える)
- weekly fullの完了通知、退避・復帰の失敗通知は変えない(今回の問題が出ていない)

## 4. 要件

| # | 要件 |
|---|---|
| R1 | `changelog_note()` がCVEを拾う範囲を、**入っている版より新しいchangelogの項目だけ**にする。範囲の決め方は `roles/proxmox_patch_dryrun/files/proxmox-dryrun-collect.sh` の `get_changelog_diff()`(入っている版より新しい項目を取り出す処理。ソース由来の版の空間の違いへの対処を含む)と同じ規則にする。新規install(入っている版が無い)は最新の項目だけとする(dry-runと同じ) |
| R2 | 範囲を決められない(入っている版がchangelogに見つからない等)ときは、**最新の項目だけ**からCVEを拾い、その旨が分かる表示にする(全履歴へは広げない) |
| R3 | 1つのpackageにつき、表示するCVEは**先頭の5件**までとし、残りは「ほかN件」にする(上限は実装の既定値で、変数にする) |
| R4 | apply通知の本文全体に**長さの上限**を設ける(既定値は、Slackのattachmentの本文で切れない安全な値として実装が決め、変数にする。根拠を実装記録に書く)。上限を超えるときは**package一覧の方を短くし**(「ほかN件」)、Phase 5(適用後のhealthcheck)・停止理由・reportのファイル名など、package一覧以外の節は削らない |
| R5 | R4の切り詰めは成功・停止のどちらの通知にも効く |

## 5. 受入条件

**実ホストには触れない。** `apt changelog` は偽のコマンドで置き換え、**過去の履歴を含む本物に近い出力**(複数の項目、古い項目にCVEが多数)を返すfixtureで確かめる。

| AC | Given / When / Then |
|---|---|
| AC1 | **Given** 入っている版 `3.5.7-1~deb13u2`、候補 `3.5.7-1~deb13u3`、changelogに `deb13u3` の項目(CVE 1件)と、それより古い多数の項目(CVE多数) **Then** 拾うCVEは `deb13u3` の項目の1件だけ |
| AC2 | **Given** 入っている版と候補の間に複数の項目がある **Then** その間の項目のCVEをすべて拾い、入っている版の項目とそれより古い項目のCVEは拾わない |
| AC3 | **Given** 新規install **Then** 最新の項目のCVEだけ |
| AC4 | **Given** 入っている版がchangelogに見つからない **Then** 最新の項目のCVEだけを拾い、範囲を決められなかったことが分かる表示がある |
| AC5 | **Given** 範囲内のCVEが6件以上 **Then** 先頭5件と「ほかN件」 |
| AC6 | **Given** packageが多く(例: 60件)、各packageにCVEがある入力で通知本文を組み立てる **Then** 本文の長さが上限以下で、Phase 5の節(適用後のhealthcheckの結果)・reportのファイル名の行が本文に含まれる。package一覧は「ほかN件」で短くなっている |
| AC7 | **Given** 停止(abort)の通知で同様に長い入力 **Then** 停止理由とreportのファイル名の行が本文に含まれ、長さが上限以下 |
| AC8 | **Given** 既存のapply roleのテスト(`roles/proxmox_patch_apply_node/tests/` ほか前の案件の検証)と `scripts/check-doc-consistency.py` **Then** 通ること。stageした状態で `scripts/git-pre-commit-check.sh` が通ること |

## 6. タイムライン・配備

- repoへのpushで、quoryの作業ツリー自動同期により反映される(changelogの取り出しスクリプトはapply roleが実行時にnodeへ配る)。setup playbookの実行は要らない
- 本番での観測: 2026-10-10(土)の自動適用のapply通知で、CVEが今回の更新分だけになり、Phase 5とreportのファイル名が見えること
