## Findings

### Major-1: abort通知の本文長が、上限を超えるケースを再現した(R4/R5、AC6/AC7未充足)

`_notify_abort_package_notes`(`tasks/main.yml` 1251-1291行、`_eval_notify_case.yml`に同一のverbatimコピーあり)の予算配分は、
- `new`側を `_notify_abort_package_budget // 2` 以内に収め、
- `unchanged`側を `_notify_abort_package_budget - (new_linesの実測長) - 40` 以内に収める

という2段の按分だが、**2つの見出し行(「最新 dry-run から追加された更新候補:」「…変わらない更新候補:」)と、見出し間の空行、new側とunchanged側それぞれの「ほかN件」行の長さが、どこの予算計算にも含まれていない**。固定の `-40`(と各アイテムの `+20`)がこれらの実際のオーバーヘッドを吸収できないケースがある。

**実測(scratchpadの独立playbookで確認、repoへは書き込んでいない)**:
- `_new_vs_dryrun`/`_unchanged_vs_dryrun` を各300件(1件あたり短い名前、例 `n123`)にした abort通知で、`_notify_body | length` = **3514**(`proxmox_patch_apply_notification_body_limit` = 3500 を **14文字超過**)。
- 同様に各2000件では3516(16文字超過)、各80件(1件180文字の長い名前)では3402(超過なし)。
- 一方、成功通知側(`_notify_package_notes`、単一リストの予算配分)は、同条件のstressで600件・2000件・10000件のいずれでも上限内(最大3481)。**超過を再現できたのはabort側(2リスト按分)だけ**。
- 実装記録・既存テスト(`test_notify_body_limit.yml`のAC7フィクスチャ: 各30件・1件160文字)では3339(上限まで161文字の余裕)で、この余裕の大きさが原因でこの不備を検出できていなかった。

この不具合は、今回の要求の発端そのもの(「本文が途中で切れ、Phase 5とreportが届かなかった」)と同じ種類の障害を、小さいながら再発させる可能性がある。abort通知は`_apply_abort_type`が`maintenance_required`/`major_upgrade_detected`/`blocked_important_remove`のときに出るが、`_new_vs_dryrun`/`_unchanged_vs_dryrun`の件数は実運用のpackage規模に依存するため、再現した条件(多数の短いpackage名)は非現実的ではない。

**対応が必要**(blocking、Major): 固定オーバーヘッド(2見出し・空行・2本の「ほかN件」)を予算計算へ正しく算入するか、またはJinjaで実際にレンダリングした最終文字列の長さを測ってから収まるまで縮める方式へ変更すること。「成功時は単一リストで安全、abort時は2リストの按分で不足する」という非対称性があるため、success側だけを基準に「十分なマージンがある」と判断しない。

### Minor-1: fixtureの偽changelogに複数項目はあるが、trailer行(` -- Maintainer <...>  日付`)が全エントリに無い

要求の明示観点「各項目の見出し行・trailer行を含む本物に近い形」に対し、`test_changelog_scope.py`の`CHANGELOGS`で trailer行があるのは `openssl` の2エントリのみで、`multi`/`newpkg`/`missing`/`many` には無い。パース対象は見出し行(`^\S+ \(version\) ...`)と `  * ` 始まりの箇条書き行だけなので実害は無いが、「過去の履歴を含む本物の形」の再現度としては一部省略されている。

### Minor-2: `apt_pkg` が import できない場合の扱いが、参照元(dry-run)と異なる

`entries_newer_than_installed()` は `apt_pkg` の `ImportError` を `None`(境界不明→最新項目のみ)として扱う。参照元 `proxmox-dryrun-collect.sh` の `get_changelog_diff()` は同じ例外時 `full[:3000]`(全履歴の先頭3000文字)を返す点で異なる。Proxmox/Debian系ノードで `python3-apt` が欠けることは実運用上まず無く、かつapply側の挙動の方がCVE範囲を広げない安全側(fail-closed)なので実害は小さいが、「同じ規則にする」(R1)という要求文言には厳密には一致しない分岐であり、記録として残す。

### Suggestion-1: CVE一覧の並び順が文字列ソート

`changelog_note()` の `cves = sorted(set(CVE_RE.findall(relevant)))` はdiff対象ではなく既存行(`sorted(...)`自体は今回新規ではなく、対象を「出力全体」→「関連entryのみ」に絞っただけ)。文字列ソートのため例えば `CVE-2024-10` と `CVE-2024-9` の順序が数値的な直感と異なりうるが、今回のスコープ外の既存挙動であり指摘に留める。

### Suggestion-2: `+20`マージンの根拠がコード上に残っていない

`Render package notes...`/`Render bounded abort package notes` 中の各 `+ 20`、abortの `- 40` は、末尾の「ほかN件」行や見出しのための予約だと推測できるが、コメントが無い。Major-1の修正と合わせて、予算配分の設計意図をコードコメントとして残すことを勧める。
