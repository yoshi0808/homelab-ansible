# requirement: codename drift検知を起動する

状態: 着手(段階1のみ)
Coordinator記録 / 2026-09-19

## 1. 問題定義

`roles/ubuntu_vm_full_upgrade` の `MAJOR_UPGRADE_DETECTED` は3信号を持つが、**codename driftは全ホストで休眠している**。`ubuntu_vm_full_upgrade_expected_codename` の既定は空(=検査skip)で、`inventories/homelab/host_vars/` のどこにも設定が無い。生きているのは「合計100超」「remove 30超」の2つで、**いずれもreleaseの変化を件数で推し量る代理指標**である。

**この変数はrelease upgradeを行う機構ではない。** repoにrelease upgradeを実行する経路は無く(`do-release-upgrade` の出現箇所は `roles/ubuntu_vm_full_upgrade/defaults/main.yml:135` のコメント1件のみ)、本案件が足すのは検知だけである。

## 2. ゴール

月次inspectionが、repoの知らないうちに起きたrelease変化を**codenameという直接の証拠**で検知する。

## 3. 非ゴール

- **release upgradeの自動化・半自動化は行わない。** 実施はYoshinobuの手による判断と操作のままとする。
- **4ホストへ一度に入れない**(§5 P0の理由)。
- 新しい検査機構・通知経路を作らない。既存変数を埋めるだけとする。

## 4. ユーザーストーリー

運用者として、あるホストのUbuntu releaseがrepoの想定と違う状態になったとき、次の月次inspectionでそれを知り、**そのホストへのapplyが自動的に拒否される**ようにしたい。

## 5. 要件

| 優先 | 内容 |
|---|---|
| P0 | `ansy` の `host_vars` へ `ubuntu_vm_full_upgrade_expected_codename: resolute` を置く。**実測値のみを置く**(2026-09-19、ansy自身で `/etc/os-release` を確認。`VERSION_CODENAME=resolute`、`Ubuntu 26.04.1 LTS`) |
| P0 | 残り3ホスト(`quory` / `authy` / `monnie`)は**測ってから**埋める。推測値を置かない — 外すとそのホストの月次applyが止まる |
| P1 | 測定はOperator Request Channelで依頼する。**dispatchのチェックカタログにOS releaseを返す動詞は無い**(`docs/ai/reviews/dev_prod_boundary/2026-08-03_008_phase3_check_catalog.md` を確認済み)ため、EXEC-043に従い自分で別手段を組み立てない |

## 6. 成功指標

段階1の完了は、**ansyの月次inspectionが `MAJOR_UPGRADE_DETECTED` を出さないこと**で測る(偽陽性を作っていないことの確認)。

## 7. 受入条件

- **AC1** Given `ansy` の host_vars に `expected_codename: resolute` がある / When 月次inspection(`operation=inspect`)が `ansy` を対象に走る / Then Status は `MAJOR_UPGRADE_DETECTED` にならず、`#patches` へ warning が出ない。playbookの終了コードは従来どおり `0`
- **AC2** Given 同上 / When 将来 `ansy` のreleaseが `resolute` 以外へ変わる / Then Status が `MAJOR_UPGRADE_DETECTED` になり、reasonに `codename drift: expected resolute, actual <新codename>` が入り、手動applyは確認文字列を渡しても `main.yml:374` で拒否される

**AC1の検証はansy自身からは行えない。** `id_ann` 削除以降、`dev_nodes` の group_vars が存在しない鍵を指すため、ansyから ansy を対象にしたplaybookは流せない(`docs/ai/status.md` 記載。本案件では再測していない)。**検証はquoryのSemaphoreの次回定期実行の観測をもって行う。**
