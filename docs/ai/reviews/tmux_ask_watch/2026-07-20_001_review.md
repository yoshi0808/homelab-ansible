# tmux-ask-watch レビュー

## 結論

現状は **commit 不可**。`must-fix` 2件、`suggestion` 3件がある。

tmux に対して実行するサブコマンドは `list-panes` と `capture-pane` だけで、
`send-keys` や承認操作はない。既定の実行経路では tmux ペインに対する読み取り専用性は
保たれている。一方、通知への秘密情報混入防止と承認 UI の識別精度は、現実に再現する
問題が残っている。

## 指摘

### must-fix: 質問行を通知へ転載するため、秘密情報を送信し得る

- 対象: `scripts/tmux-ask-watch.sh:188-201`
- 関連: `scripts/tmux-ask-watch.sh:113-116`

コメントは「コマンド本文や引数」を避けるとしているが、実装は質問と判定した行を
最大300文字そのまま `agmsg` メッセージへ入れる。承認 UI がコマンドや URL、token、
header を質問と同じ行に表示した場合、その値も通知される。

以下の入力が `extract_ask` で抽出されることを確認した。

```text
Do you want to run curl -H Authorization_Bearer_EXAMPLE_SECRET?
1. Yes, proceed
```

また `sanitize_capture` が除去するのは CSI と行末 CR だけで、OSC やその他の制御文字は
残る。質問行を通知する現行方式では、秘密情報だけでなく通知先端末への制御文字混入も
防止できない。

通知は `pane_id` とローカルで計算した fingerprint 程度の固定文に限定し、capture 由来の
文字列を一切含めないことを推奨する。`SESSION` も任意入力なので、通知へ含めるなら安全な
文字種へ制限する。詳細確認は既にメッセージが案内しているとおり対象ペインで行えばよい。

### must-fix: 通常会話の質問を承認 UI として誤検出する

- 対象: `scripts/tmux-ask-watch.sh:125-142`

選択肢などの `indicator` がなくても、質問らしい文が最終非空行から3行以内にあれば承認と
判定する。このため、Claude/Codex の通常回答の末尾にある質問も通知対象になる。

次の通常会話が `extract_ask` からそのまま出力されることを確認した。

```text
Here is a normal assistant response.
Would you like to see another example?
```

少なくとも既知の承認 UI を示す選択肢・キー案内との組み合わせを必須にするなど、単なる
自然言語質問だけでは発火しない条件にする必要がある。Codex/Claude の実際の承認 UI と
通常会話を fixture 化し、positive/negative の回帰テストを追加するのが安全である。

### suggestion: state の read-modify-write に排他がなく、複数 watcher が競合する

- 対象: `scripts/tmux-ask-watch.sh:147-170`, `scripts/tmux-ask-watch.sh:219-253`

状態ファイルは `umask 077`、一時ファイル `0600`、同一ディレクトリ内の `mv` で更新され、
単一プロセス時の権限と原子性は妥当である。しかし scan 全体を守る lock がない。

同じ state file を使う watcher が同時に起動すると、両方が同じ旧 state を読み、同じ通知を
送れる。別 `--session` の watcher が state file を共有した場合は、それぞれが自分の
`CURRENT_HASH` だけでファイルを置換し、相手のエントリを消すため、重複通知が継続し得る。

単一起動を運用前提にするだけでなく、state file ごとの lock を取得し、少なくとも
read / notify / write の競合を防ぐべきである。複数 session watcher を許すなら state file を
分離するか、lock 下で既存エントリを安全に merge する必要がある。

### suggestion: `list-panes` の全エラーを「tmux 不在」として成功扱いし、state を消去する

- 対象: `scripts/tmux-ask-watch.sh:223-227`, `scripts/tmux-ask-watch.sh:251-257`

存在しない `--session`、権限・socket 問題、tmux の予期しない失敗も区別せず、空 state を
書いて終了コード0にする。監視設定ミスが外部監視から見えず、一時障害の復旧後には既存の
承認 UI を新規扱いして再通知する。

「tmux server が存在しない」という期待可能な状態と、それ以外のエラーを分離することを
推奨する。少なくとも予期しないエラー時は旧 state を保持して非0終了または明示的な警告を
返すべきである。

### suggestion: fingerprint が可変な周辺文脈を含み、同じ UI を再通知し得る

- 対象: `scripts/tmux-ask-watch.sh:138-142`, `scripts/tmux-ask-watch.sh:241-248`

質問より前8行から最終行までを丸ごと hash 化するため、選択カーソル、進捗表示、周辺の
ステータス行などが変わる UI では、承認要求自体が同じでも hash が変化して再通知される。
反対に、同じ pane で同一内容の承認要求が解消・再出現し、その間の非表示状態を poll が
観測できなければ見逃す。後者は polling の限界だが、前者は承認要求の安定部分を正規化して
fingerprint にすることで軽減できる。

## 読み取り専用保証の確認

- tmux 呼び出しは `list-panes` と `capture-pane -p` のみ。
- `send-keys`、`run-shell`、キー入力、承認選択はない。
- capture を shell code として評価する処理はない。
- 書き込みは一時作業ディレクトリ、state file、agmsg 通知に限定される。
- `TMUX_ASK_TMUX_BIN` / `TMUX_ASK_SEND_SCRIPT` は任意実行ファイルへ差し替え可能なため、
  hostile な環境変数まで含めた security boundary ではない。テスト用 injection として許容する
  場合、この前提は運用文書へ明記するとよい。
