## 実装概要

Loki への書き込みを monnie ローカル Alloy のみに限定したまま、pve1/pve2 と Sophos を
既存 UDP514 rsyslog ファネルへ追加した。既存 `/etc/rsyslog.d/10-unifi.conf` は変更せず、
別 config で名前解決済み source-IP allowlist と専用2ファイルを管理する。

monnie rsyslog は受信 severity を `error|warning|info|debug` の4値へ正規化して行頭へ書く。
Alloy は新規2ファイルから確実に `level` を抽出し、pve は2番目トークンを `host` にする。
既存 UniFi 2系統は行頭付近の明示 severity だけを best-effort で分類し、不明行には
`level` を付けない。journal は `__journal_priority` を4値へ確実に relabel する。

pve 側は Ansible 化していない。本書後半に Yoshinobu が手動適用する完全な参照設定、
適用手順、検証、可逆手順を記載する。Loki と UFW は変更していない。

## monnie 実装

### rsyslog 受信振り分け

- 既存 `/etc/rsyslog.d/10-unifi.conf` の存在を preflight で要求し、role の出力先が同じで
  ないことを assertする。内容を slurp して既存 `$fromhost-ip` 集合を抽出し、新規の名前解決
  結果との積集合が空であることも assertする。既存 listener、allowlist、2ファイルは変更しない。
- 新規 `/etc/rsyslog.d/15-observability-sources.conf` を管理する。pve1/pve2 と Sophos の
  DNS名を monnie 上の `getent ahostsv4` で実行時解決し、解決結果だけを target config の
  `$fromhost-ip` allowlist に書く。IP address literal は Git に保存しない。
- 全送信名の解決成功、新規 source-IP 間の重複不存在、既存 UniFi source-IP との非重複を
  assertし、不完全・曖昧な allowlist を fail-closed にする。
- pve1/pve2 は `/var/log/pve-nodes.log`、Sophos は `/var/log/sophos-fw.log` へ出力し、
  match 後 `stop` するため既定ローカル出力への重複を抑止する。
- severity 0--3/4/5--6/7 を順に `error/warning/info/debug` へ分岐する rsyslog template を
  使用する。行形式は `<level> <sender-host> <RFC3339 timestamp> <tag/message>`。
- 新規ファイルは `syslog:syslog 0644` で生成し、Alloy が追加 group なしで読める。
- candidate は `/etc/rsyslog.d/15-observability-sources.conf.staging` (`root:root 0640`) へ
  renderし、`rsyslogd -N1 -f <staging>` がPASSした場合だけ同一directory内から正規 `.conf` へ
  promoteする。配備後・restart 前には `rsyslogd -N1` で include 済み全体構成も検証する。
  全体検証/restart/active 確認の失敗時は旧 snippet（初回なら不存在）へ戻し、復元構成を検証して
  rsyslog restart を試みてから failする。staging file は成功・失敗の両方で必ず削除する。

既存 `10-unifi.conf` が送信元 match 後に `stop` する構成は Phase 1 調査で確認済みであり、
後続の `15-observability-sources.conf` は UniFi ログを再処理しない。

### logrotate

新規2ファイルだけを `/etc/logrotate.d/observability-remote-syslog` で管理する。repository と
既存調査資料には UniFi 専用 logrotate の正本が無かったため、Debian の一般的な syslog
運用に合わせて `weekly`, `rotate 4`, `compress`, `delaycompress`, `missingok`, `notifempty`,
`su syslog syslog` を採用した。rotate 後は rsyslog に HUP を送り file descriptor を開き直す。
候補は `/etc/logrotate.d/observability-remote-syslog.staging.disabled` (`root:root 0640`) へrenderし、
`logrotate --debug <staging>` でparseできた場合だけ正規pathへpromoteする。staging fileは
成功・失敗の両方で削除する。tester は APPLY 前に monnie の既存 UniFi
rotation 実態と比較し、保持期間を揃える必要が判明した場合は人間判断へ戻す。

### Alloy file sources と入力契約

- `job=pve-nodes`: `/var/log/pve-nodes.log`、行の2番目から動的 `host`、行頭から `level`。
- `job=sophos-fw`, `host=sophos-fw`: `/var/log/sophos-fw.log`、行頭から `level`。
- 新規2ファイルは sender 有効化前に存在しなくても preflight を通す。既存 UniFi 2ファイルは
  引き続き存在・regular file・world-readable を必須とする。
- `extract_second_token_as_host=true` と静的 `labels.host` の同時指定を assert で禁止した。
- 確実抽出と best-effort 抽出の同時指定も禁止した。
- 全 file source は従来どおり `tail_from_end=true`。Sophos/pve 送信開始前ならファイルは
  未生成であり、Alloy source は空の glob として待機する。

### `level` 標準化

- journal: Alloy が生成する `__journal_priority` を relabel し、0--3=`error`, 4=`warning`,
  5--6=`info`, 7=`debug` とする。既存 `unit` relabel と `job=system,host=monnie` は維持。
- pve/Sophos file: rsyslog が確定4値を行頭に書き、Alloy regex が `level` に昇格する。
- UniFi file: 異種 format のため、先頭から最大3 token 内の明示 severity token のみを
  `stage.match` で分類する。認識できない行は `level` 無しとし、本文中の一般語による
  誤ラベルを避ける。
- UniFi の既存 `job`/静的 `host`/動的 `host` 契約は変更しない。

## pve1/pve2 手動参照設定（Ansible 管理外）

以下は **両ノードへ同じ内容を Yoshinobu が手動適用する**。Debian 13 trixie の標準
repository にある rsyslog を使い、repository は追加しない。

### 選定方式

`ForwardToSyslog=yes` の journald drop-in と rsyslog の systemd syslog socket 連携を採用する。
Debian package の既定 rsyslog 構成と整合し、`imjournal` の state file・再読位置・重複読取を
新たに設計せずに済むためである。`journald.conf` 本体は編集しない。

### `/etc/systemd/journald.conf.d/forward-to-syslog.conf` の完全な内容

```ini
[Journal]
ForwardToSyslog=yes
MaxLevelSyslog=debug
```

`MaxLevelSyslog=debug` を明示し、priority 0--7 の全範囲を渡す。

### `/etc/rsyslog.d/49-monnie-forward.conf` の完全な内容

```rsyslog
# Manually managed for Alloy Phase 2. Canonical copy:
# docs/ai/reviews/promtail_to_alloy/2026-07-17_009_implement.md

action(
    type="omfwd"
    target="monnie.internal"
    port="514"
    protocol="udp"
    template="RSYSLOG_SyslogProtocol23Format"
)

# For messages that reach this rule, forwarding is the only rsyslog output.
# Stop before Debian default file rules to avoid duplicate local syslog files.
stop
```

ファイル名を `49-` とし、既存 `45-frr.conf` より後、`/etc/rsyslog.conf` 本体の Debian default
rules より前に評価する。

- `45-frr.conf` は FRR daemon 名を `/var/log/frr/frr.log` へ書いて `stop` する出力ルール。
  この package 契約を優先し、FRR message は monnie へ転送しない。調査時点で FRR は両ノード
  inactive のため Phase 2 では許容する。将来 Proxmox SDN/FRR を有効化する場合は、専用ログの
  Loki 収集または remote 転送を再検討する。
- `postfix.conf` は `/var/spool/postfix/dev/log` の chroot socket input 宣言だけで、出力/stop
  ruleではない。Postfix message は `45-frr.conf` を素通りして `49-` で monnie へ転送される。
  rsyslog 未導入時は chroot listener が無く失われていた可能性があり、この経路は改善になる。
- その他の全 facility/priority は `49-` で monnie へ UDP forwarding し、直後の `stop` により
  本体 default rules（`/var/log/syslog` 等）の重複生成を抑止する。journald 保持は継続する。

### 手動適用手順

以下は参照手順であり、この実装工程では実行していない。

1. package と repository を事前確認する。

   ```bash
   apt-cache policy rsyslog
   ```

2. Debian 標準 repository から rsyslog を導入する。

   ```bash
   sudo apt install rsyslog
   ```

   package install により service が一時的に auto-start した場合でも、次の設定検証前には
   外部送信設定がまだ無いため monnie への転送は始まらない。

3. drop-in directory と上記2ファイルを、記載どおりの内容・owner/mode で配置する。

   ```bash
   sudo install -d -o root -g root -m 0755 /etc/systemd/journald.conf.d
   sudo chown root:root /etc/systemd/journald.conf.d/forward-to-syslog.conf /etc/rsyslog.d/49-monnie-forward.conf
   sudo chmod 0644 /etc/systemd/journald.conf.d/forward-to-syslog.conf /etc/rsyslog.d/49-monnie-forward.conf
   ```

   内容の投入は editor または here-document で行い、投入後に `sed -n` 等で本書との一致を
   目視確認する。IP address を書かず `monnie.internal` を使う。

4. service start 前に rsyslog 全体構文を検証する。非zeroなら開始せず修正する。

   ```bash
   sudo rsyslogd -N1
   ```

5. rsyslog を enable + start し、active/enabled を確認する。

   ```bash
   sudo systemctl enable --now rsyslog
   systemctl is-active rsyslog
   systemctl is-enabled rsyslog
   ```

6. journald drop-in を反映するため journald を restart する。短時間の handoff が起こり得るため、
   pve の人間ゲート下で1ノードずつ実施する。

   ```bash
   sudo systemctl restart systemd-journald
   systemctl is-active systemd-journald
   ```

7. read-only 確認を行う。

   ```bash
   systemd-analyze cat-config systemd/journald.conf
   systemctl status rsyslog --no-pager
   journalctl -u rsyslog --since=-10min --no-pager
   ```

   テストメッセージ送信や monnie 側実データ確認は承認済み tester 工程で行う。両ノードの
   `/var/log/pve-nodes.log` 着信、2番目tokenの host 判別、`level` 4値を確認する。

### 可逆手順

以下で Phase 2 前（rsyslog package なし、ForwardToSyslog 既定 no）へ戻せる。実際の rollback
は本工程では行わない。

1. rsyslog を停止・disableする。

   ```bash
   sudo systemctl disable --now rsyslog
   ```

2. 手動管理の転送設定と journald drop-in を削除する。

   ```bash
   sudo rm /etc/rsyslog.d/49-monnie-forward.conf
   sudo rm /etc/systemd/journald.conf.d/forward-to-syslog.conf
   ```

3. journald を restart し、`ForwardToSyslog` を既定 no に戻す。

   ```bash
   sudo systemctl restart systemd-journald
   systemctl is-active systemd-journald
   ```

4. rsyslog package を purge する。導入前から存在した `/etc/rsyslog.d/45-frr.conf` と
   `/etc/rsyslog.d/postfix.conf` は削除しない。

   ```bash
   sudo apt purge rsyslog
   ```

5. package/service/drop-in が元の状態であることを read-only 確認する。

   ```bash
   dpkg-query -W rsyslog
   systemctl is-enabled rsyslog
   systemd-analyze cat-config systemd/journald.conf
   ```

### 全体validate・restart・rescueの再構成

- block全体から `when` を除去した。全体 `rsyslogd -N1` task自身は
  `when: not ansible_check_mode` だけを持ち、正規pathへのpromoteがchangedか否かに関係なく

  `alloy_rsyslog_remote_config_result is changed` で限定した。check modeでpromotion taskがskip

  rsyslog active stateを採取してfailする。promoteがchangedなら旧版または不存在へ戻してから

## 2026-07-17 014 production APPLY 3回目後の修正5

014 test_result 追記4で、`alloy validate` がexit 0でも起動時のcomponent graph評価に失敗し、
Alloyがstart limitへ到達したmust-fixを反映した。monnie/pve/Sophosへの操作は行っていない。

### `stage.match` selector の二重escape

UniFi 2 pipelineのselectorは、通常のRiver regex引数ではなく、Riverのquoted stringの中に
さらにLogQLのquoted regexを含む。従来のrender結果は次の形だった。

```river
selector = "{job=\"unifi\"} |~ \"(?i)^(?:\\S+\\s+)...\""
```

River parserが `\\S` を `\S` に戻した後、LogQL parserはその単一backslashをquoted stringの
escapeとして解釈し、`\S` を未定義escapeとして拒否した。修正後のrender結果は次の形である。

```river
selector = "{job=\"unifi\"} |~ \"(?i)^(?:\\\\S+\\\\s+)...\""
```

Jinja string内ではregex metacharacterごとにbackslashを2文字保持し、`to_json` がRiver外側の
quoted string用に各backslashをもう一度escapeする。River parse後にLogQL selectorへ `\\S` /
`\\s` が渡り、LogQL quoted string parse後にRE2へ `\S` / `\s` が渡る。error/warning/info/debug
4本と、unifi/network-devicesの両pipelineを同じ生成式へ集約した。

### `config.alloy.j2` 文字列escape全面掃引

Jinja source、render済みRiver、各component内parserの境界を次の一覧で点検した。

| 箇所 | parse段数 | source/render契約 | 結果 |
|---|---:|---|---|
| `stage.regex.expression` 2本 | River→RE2 | templateの `\\s` / `\\S` がrender後も `\\s` / `\\S`、River後にRE2へ単一backslash | 維持 |
| `stage.match.selector` 4分類×2 source | River→LogQL→RE2 | Jinjaでbackslash 2文字、`to_json`後のRiverで4文字 | 修正 |
| selectorのstream label `job` | River→LogQL | 手組みquoteを廃止し、job値を内側でも `to_json` | 修正 |
| URL、file path、source/journal label値、`max_age`、relabel label名 | River | 全て `to_json` | PASS |
| component宣言label | River | source名からのsuffix連結後に `to_json` | 統一 |
| component参照identifier | River identifier | role input assertの `^[A-Za-z_][A-Za-z0-9_]*$` が保証 | PASS |
| journal relabel regex 4本 | River→RE2 | 数字とcharacter classのみでbackslash/quote無し | PASS |
| 固定 `level` key/value、HTTP sync duration | River | repository固定ASCII quoted string、埋込値無し | PASS |

local Jinja renderで両selectorが `\\\\S` / `\\\\s` を保持し、通常の`stage.regex`は
`\\S` / `\\s` のままであることを別々に確認した。前者を通常regexと同じ本数へ戻すと今回の
runtime failureが再発する。

### 不存在optional fileのdiscovery化

Alloy `1.17.1-1` の実挙動では、exact pathをstatic `targets`へ渡すとreaderを即時生成し、
不存在のpve/Sophos pathが `failed to create source, skipping` となってinitial loadを失敗させた。
007/本書の「空globとして待機」という従来想定は誤りだった。

公式 `loki.source.file` 仕様どおり全file sourceに組み込み `file_match` blockを追加し、
`enabled=true`, `sync_period="10s"` とした。組み込みfile discoveryはpath patternに一致するfileが
現れた時だけtarget readerを増やし、削除時にも更新する。別 `local.file_match` componentより
簡潔でoverheadが小さい公式推奨方式を採用した。

- 既存UniFi 2 fileはpreflightで存在を必須とするため、従来どおり直ちにdiscoveryされる。
- pve/Sophosはfile不存在ならtarget 0件でhealthyのまま待機し、10秒以内のsyncで追加される。
- pve/Sophosは未生成fileなので `tail_from_end=false` へ変更した。最初のsyslog行でfileが生成され、
  次のdiscoveryまでにその行が既存内容となっても、初回行を捨てない。既存UniFiは
  `tail_from_end=true` とpositions契約を維持する。

参照した公式仕様:

- https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.file/
- https://grafana.com/docs/alloy/latest/reference/components/local/local.file_match/
- https://grafana.com/docs/alloy/latest/reference/components/loki/loki.process/

### 起動後runtime gateと可逆化

`alloy validate` はRiverの構文/静的config検証には使えるが、今回の
`stage.match` selector parseやstatic file reader生成を含むruntime component graph評価のerrorを
検出しなかった。この制約を前提に、roleの成功条件を「start直後のactive」から次へ強化した。

1. template配備に `backup: true` を付け、変更前configをremote backupとして保持する。
2. 既存のstart-limit状態を `systemctl reset-failed` し、起動直前のjournal基準時刻を記録する。
   初版では `date --iso-8601=ns` を使ったがlocale依存が判明し、修正6でepoch秒へ訂正した。
3. Alloy start/restart後15秒settleする。
4. `systemctl is-active alloy.service == active`、`http://localhost:12345/-/ready == 200`、
   verification windowのjournalにinitial-load/component fatal patternが無いことを同時assertする。
   Phase 1で確認済みのremotecfg `noop client` 1行はcomponent graph fatalではないため対象外とする。
5. runtime gate失敗時、template backupがあれば旧configを戻してnative validateし、start-limitを
   resetしてrestartする。旧configにも同じ15秒/active/ready/journal gateを適用する。
6. 旧configがhealthyならその状態を維持してrole自体はfailし、新config失敗を隠さない。
7. backupが無いfresh cutover、または旧configのruntime再確認も失敗した場合は、Alloyを
   stopped/disabledへ収束させ、Promtailをstarted/enabledへ戻してからfailする。
8. 成功時または旧config復旧成功時は一時backupを削除する。

この構造により、APPLYが成功扱いのままAlloyが数秒後にfailedとなる経路を塞ぎ、失敗したroleが
`Alloy failed + Promtail inactive` を残さない。現在のmonnieは3回目APPLY由来のAlloy failed状態だが、
次回の人間承認済みAPPLY以外では触らない。次回はmain path先頭の `reset-failed` からfix-forwardし、
新configも失敗した場合だけ旧config再確認、さらに失敗ならPromtailへfallbackする。

## 2026-07-17 014 production APPLY 4回目後の修正6

014 test_resultの4回目APPLY追記で、新Alloy config自体はactive/ready、component graph、実Loki
dataの全てが健全だった一方、runtime journal gateだけが誤FAILした原因を反映した。monnieの
localeではGNU dateがnanosecondの小数点をカンマで出力し、`journalctl --since` が拒否した。
monnie/pve/Sophosへの操作は行っていない。

### locale非依存のjournal verification window

main pathと旧config recovery pathの両方を同じcontractへ変更した。

```text
/usr/bin/date +%s
/usr/bin/journalctl --unit alloy.service --since @<epoch> --no-pager --output=cat
```

- `date +%s` は表示用日時ではなくUNIX epoch秒のASCII数字だけを返す。
- Ansible command moduleが末尾newlineを除いた `stdout` に `@` をrole側で付け、
  `journalctl`のUNIX timestamp入力として渡す。
- timezone、月/曜日名、小数点記号、fraction桁数、UTC offsetのlocale表現に依存しない。
- register名も `_started_at` から `_started_epoch` へ変更し、値のcontractを名前で明示した。
- active/ready/journal rc/fatal patternのassert、15秒settle、backup recovery/fallback構造は変更しない。

### `roles/alloy` のdate・時刻format全面掃引

`date`, `journalctl --since`, `strftime`, `to_datetime`, `iso-8601`, `epoch` と、template内の時刻指定を
全数検索した。

| 箇所 | 用途 | parser境界 | 判定 |
|---|---|---|---|
| main path `date +%s` | journal window始点 | `stdout`→`journalctl --since @...` | epochへ修正 |
| recovery path `date +%s` | 復旧journal window始点 | `stdout`→`journalctl --since @...` | epochへ修正 |
| rsyslog template 4本の `%timereported:::date-rfc3339%` | 保存するlog本文 | rsyslog固定property format。別command入力ではなく、Alloyはそのtimestamp自体をparseしない | 維持 |
| `strftime` / `to_datetime` / その他ISO日時生成 | 該当無し | — | PASS |

`alloy_runtime_settle_seconds`, journal `max_age="12h"`, file discovery `sync_period="10s"` は
duration literalであり、日時文字列やlocale変換ではない。

### 外部command出力formatの同クラス全面掃引

`roles/alloy/tasks/main.yml` の全 `ansible.builtin.command`、register、その後の `stdout`,
`stdout_lines`, `stderr`, `rc` consumerを点検した。

| producer | consumer | 前提と処置 |
|---|---|---|
| `date +%s` 2件 | `journalctl --since @<epoch>` | command間の直接受け渡し。今回修正 |
| `getent ahostsv4` | IPv4 regex→rsyslog allowlist template | 行頭のASCII IPv4と後続whitespaceだけを抽出し、STREAM等の語や列数は消費しない。sender別非空assertも維持 |
| `apt-cache policy alloy` | candidate存在assert | `Candidate:` tokenをparseするため `LC_ALL=C` をcommandへ明示して固定 |
| `systemctl show` | service property assert | `KEY=VALUE` のmachine-readable property名/値だけを比較。人間向けstatus文は不使用 |
| `systemctl cat` | unit contract assert | unit本文中のpath/flagだけを検索し、表示用日時やlocale文言は不使用 |
| `systemctl is-active` | active assert / rollback message | systemdの固定state token `active` を使用。人間向けstatus文は不使用 |
| `alloy validate`, `rsyslogd -N1`, `logrotate --debug` | cutover/rollback制御 | 成否はexit codeのみ。表示文を別commandへ渡さない |

moduleの構造化戻り値も併せて確認した。templateの `backup_file` はcopy/file moduleのpathへ、slurpの
