## 実装概要

ansy / quory / authy の journald を、各nodeのrsyslogから既存monnie UDP/514集約点へ転送する
Ansible role/playbookを追加した。monnie側は既存data-driven route/file source loopへ3 senderと
`ubuntu_nodes` destination/sourceを追加し、Lokiでは `job=ubuntu-nodes`、動的 `host`、4値
`level` として扱う。

monnie自身のjournal sourceは収集componentやpriority mappingを変えず、静的labelだけを
`job=system` から `job=ubuntu-nodes` へ変更した。これにより新規データではmonnie / ansy /
quory / authyが同じjob意味論へ揃う。過去の `job=system` dataはLoki側でそのまま残る。

Loki、UFW、pve1/pve2の手動管理設定、Sophos/UniFiのGUI設定には変更を加えていない。IP address
literalやsecretもrepositoryへ保存していない。

## pre-deploy reconの反映

testerのread-only reconから次を実装contractとして固定した。

| node | rsyslog導入前状態 | managed rule | forward後 `stop` | local logging contract |
|---|---|---|---|---|
| ansy | 導入済み、active/enabled | `49-monnie-forward.conf` | 無し | 既存 `/var/log/syslog` 等を維持 |
| quory | 導入済み、active/enabled | `49-monnie-forward.conf` | 無し | 既存 `/var/log/syslog` 等を維持 |
| authy | 未導入 | `49-monnie-forward.conf` | 有り | fresh installでdefault local fileを新規生成しない |

3台とも既存 `21-cloudinit.conf` はCloud-init専用fileへ出して `stop` する。その後の49番で一般
messageをmonnieへ送り、Ubuntu default `50-default.conf` より先に評価する。ansy/quoryは49番で
止めず既存local outputも継続し、authyだけ49番で止める。

roleはrecon driftをfail-closedにする。管理する49番を除いた `*.conf` basenameを取得し、node別の
required/allowed集合と比較する。ansy/quoryは20-ufw/21-cloudinit/50-defaultを要求し、authyは
導入前の20/21を要求したうえで、package導入後に生成される50-defaultだけを追加許容する。未知の
snippet追加・既知snippet削除があれば、番号/`stop`/output内容の再調査前には変更しない。
既存49番にrole ownership markerが無い場合も上書きを拒否する。

## monnie受信側

### sender allowlistと出力

`alloy_remote_syslog_sources`へ次を追加した。

- `ansy.internal` → `ubuntu_nodes`
- `quory.internal` → `ubuntu_nodes`
- `authy.internal` → `ubuntu_nodes`

既存roleがmonnie上で `getent ahostsv4` を実行し、senderごとの非空IPv4集合、全remote sender間の
一意性、既存UniFi allowlistとの非重複をassertする。新3台もpve/Sophosと同じ集合へ入るため、
既存5 senderやUniFiと重複するsource identityはpromotion前にfailする。解決済み結果だけがtarget
configへ入り、IP literalはGitに入らない。

新destinationは `/var/log/ubuntu-nodes.log`。既存template loopによりseverity 0--3/4/5--6/7を
`error|warning|info|debug`へ正規化し、`<level> <sender-host> <RFC3339 timestamp> ...` 形式で
`syslog:syslog 0644` fileへ出す。route後はmonnie側で `stop` し、受信messageの別local output重複を
防ぐ。既存AppArmor対応どおり、candidateは `/etc/rsyslog.d/*.conf.staging` へrenderし、同pathで
`rsyslogd -N1 -f` がPASSした時だけ正規configへpromoteされる。inline `template.validate` は使わない。

logrotate templateはdestination valuesを列挙する既存構造のため、新pathも同じweekly/rotate 4/
compress/delaycompress/missingok/notifempty/su/sharedscripts契約へ自動追加される。

### Alloy sourceとmonnie journal label

`alloy_file_sources`へ次を追加した。

```yaml
name: ubuntu_nodes
path: /var/log/ubuntu-nodes.log
tail_from_end: false
labels:
  job: ubuntu-nodes
extract_second_token_as_host: true
extract_normalized_level_at_start: true
extract_level_best_effort: false
require_existing_file: false
```

これはpve_nodesと同一pipeline契約で、静的hostを持たないため相互排他assertにも適合する。組み込み
`file_match` がsender有効化前の不存在fileをtarget 0件で待ち、生成時はBOFから読んで最初の1行を
保持する。

monnie journal entryはname=`system`をcomponent identifierとして維持し、labelsだけを
`job=ubuntu-nodes, host=monnie`へ変更した。`loki.source.journal`、`unit` relabel、priorityから4値
`level`へのmapping、max_ageは不変。candidate contract assertへubuntu_nodes source/processと
monnieの新job/hostを追加した。

`config.alloy.j2` 自体は変更していない。したがってJinja→River→LogQLの新しいescape境界は無い。
念のため全renderを再確認し、既存UniFi selector 8本はRiver上 `\\\\S` / `\\\\s`、通常
`stage.regex`は `\\S` / `\\s` の既存contractを維持することを確認した。

## 送信側role

### 設定内容

`roles/rsyslog_forward_to_monnie` は対象をansy/quory/authyだけにassertで限定する。

journald drop-in:

```ini
[Journal]
ForwardToSyslog=yes
MaxLevelSyslog=debug
```

rsyslog action:

```rsyslog
action(
    type="omfwd"
    target="monnie.internal"
    port="514"
    protocol="udp"
    template="RSYSLOG_SyslogProtocol23Format"
)
```

`stop` は `rsyslog_forward_stop_after_forward_by_host` からnode別にrenderする。ansy/quory=false、
authy=true。targetはDNS名だけで、送信側configにもIPを保存しない。

### package、staging、service順序

1. mutation前にrole input、既存snippet集合、49番ownership collisionをassertする。
2. template lookupでcandidateをlocal renderし、target/port/protocol/template/stop有無をassertする。
3. rsyslog binaryをstatし、未導入時だけapt state=presentを実行する。したがってansy/quoryのapt taskは
   skip、authyだけfresh installとなる。
4. journald drop-in directoryとdrop-inを配置する。本体journald.confは編集しない。
5. `/etc/rsyslog.d/49-monnie-forward.conf.staging` (`root:root 0640`)へcandidateをrenderする。
6. AppArmor許可pathで `rsyslogd -N1 -f <staging>` を実行し、PASS時だけ`remote_src` copyで
   正規49番 (`root:root 0644`)へpromoteする。`always`でstagingを削除する。
7. 正規include済み全体を `rsyslogd -N1` で毎APPLY検証する。
8. package installまたは正規config promotionがchangedならrsyslogを必ずrestartする。authyでaptが
   config配置前にauto-startしても、最終runtimeは49番をloadしたprocessへ収束する。
9. drop-inがchangedならsystemd-journaldを必ずrestartする。
10. change時はrestart直前に `date +%s` を取り、10秒settle後に両serviceのactive stateと
    `journalctl --since @<epoch> --output=cat` を確認する。ISO日時やlocale依存formatは使わない。
11. activation失敗時は、変更前にslurpした49番/drop-in（初回は不存在）へ戻し、復元後の全体
    rsyslog validateと両service restart/state採取を試行してからroleをfailする。

`when`は全てYAML stringで、change判定は `is changed` を使う。rollback native validationは
`failed_when: false` のためtask stateではなく、resultの `['rc'] == 0` を明示判定する。stat結果を
参照する場合もbracket notation + `bool` filterを使い、conditionalでdict属性や `.changed`を
直参照しない。

### check mode

playbookは `tester-gate: check-mode-native`。file/apt/templateはnative check modeを使い、staging
native validation、promotion、full validation、service restartは `not ansible_check_mode` の時だけ
実行する。rsyslog未導入のfresh authy checkではremote directory/binaryがまだ存在しないためremote
candidate placementはskipするが、template lookupとcontract assertは必ず実行する。導入後checkでは
remote file差分もnativeに評価される。

## playbookと段階ロールアウト

`playbooks/rsyslog_forward_to_monnie.yml` はhostsを `ansy:quory:authy` に明示限定し、`serial: 1`。
加えてpre_tasksのrun_once assertが `ansible_play_hosts_all | length == 1` を要求するため、明示limitを
省いた3台連続実行はrole開始前にfailする。実行順はplaybook内コメントと運用gateで次へ固定する。
実装工程ではいずれも実行していない。

1. monnieへ `playbooks/alloy_setup.yml` を承認済みAPPLYし、ubuntu-nodes受信file/sourceとmonnieの
   journal job変更を先にactive/ready確認する。
2. `-l ansy` をAPPLYし、sender→file→Loki E2Eと既存local syslog継続を確認する。
3. `-l quory` をAPPLYし、同じE2Eに加えてrestart直後のAnsible疎通を確認する。
4. authy APPLY前にquory経由でmuteする。ansy/quoryは監視対象外なのでmute不要。

   ```bash
   ansible quory -b -m ansible.builtin.command \
     -a 'homelab-mute set authy 60 alloy phase2 ubuntu sender apply'
   ```

5. `-l authy` をAPPLYし、E2E、AppArmor、`/var/log/syslog`非生成を確認する。全gate PASS後だけ
   authy muteをclearする。

各APPLYはYoshinobuの明示判断が必要。testerはsyntax-check/checkを先に行い、各nodeのE2E PASS前に
次nodeへ進まない。

## 2026-07-17 018 review後の修正

`2026-07-17_018_review.md` のmust-fix 3件と軽微3件を反映した。

### check mode service state gate

`systemctl is-active rsyslog` と `systemctl is-active systemd-journald` の2 command taskに
`check_mode: false` を追加した。これはread-only state収集であり、check modeでも実行する。
既導入ansy/quoryでは後続active assertも評価されるため、command moduleのcheck-mode skipにより
空stdoutを比較して誤FAILする経路を除いた。fresh authy checkではrsyslog binary preexistence条件に
よりrsyslog state task/assertは引き続きskipし、存在するjournaldだけをread-only確認する。

### rollback validationのrc判定

復元後 `rsyslogd -N1` はrollback継続のため `failed_when: false` を維持する。この場合
`result is succeeded` はnative command rcではなくAnsible task failed flagの反転であり、rc非zeroでも
trueになり得る。restart条件を次へ変更した。

```yaml
when: rsyslog_forward_restore_validation['rc'] == 0
```

復元構成がnative validationを通らなければrsyslog restartを実行しない。最終failure messageには
validation rcとstderr、rollback後service stateを含める。

### 単一host rolloutの強制

sender playbookのpre_tasksにrun_once assertを追加し、`ansible_play_hosts_all | length == 1` を要求する。
`serial: 1` はbatch sizeだけを制御して3台連続実行を防がないため、今後は `-l ansy` / `-l quory` /
`-l authy` のいずれか1台を明示しないとroleへ進めない。これによりnode間E2E gateとauthy mute手順を
limit付け忘れで迂回する経路をfail-closedにした。

### ownershipとauthy rescue範囲

- journald drop-inにも49番と同じownership marker gateを追加した。recon時点では不存在でも、別管理系が
  同pathを作った後にroleが上書きすることを拒否する。
- activation rescueは管理した49番/drop-inを旧内容または不存在へ戻すが、authyへfresh installした
  rsyslog package自体は自動purgeしない。package removalは破壊範囲が大きいため、人間承認下の本書
  authy手動rollbackで行う。最終failure messageもこの残存状態と手順を明示する。
- monnie側UniFi overlap assertのfail messageを `pve/Sophos sender` から全remote syslog senderへ
  一般化し、ansy/quory/authyを含む実際の検査範囲と一致させた。
