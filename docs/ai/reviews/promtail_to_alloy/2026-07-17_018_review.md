# Alloy Phase 2 拡張（Ubuntu nodes journald 集約）レビュー

## 結論

**要修正（must-fix 3件）**。設計の主要部分は要求を満たしているが、check mode、rollback、段階ロールアウトの安全ゲートに適用前の修正が必要。

## Findings

### must-fix 1: 既導入ノードの `--check` が service state assert で誤失敗する

対象: `roles/rsyslog_forward_to_monnie/tasks/main.yml:272-326`

`Read rsyslog active state` と `Read systemd-journald active state` は `ansible.builtin.command` だが、`check_mode: false` がない。command module は `creates` / `removes` がない場合、check mode では実行せず skipped となる。この結果、ansy / quory では後続 assert の条件が真である一方、登録結果の `stdout` は空になり、`stdout == 'active'` が失敗する。journald 側も同じ問題を持つ。

ローカルの最小再現でも、check mode で command が skipped、空の `stdout` を使う assert が failure となることを確認した。

修正案: 状態参照だけを行う2つの `systemctl is-active` task に `check_mode: false` を付け、check mode でも実状態を収集する。代わりに assert 自体を check mode で省略すると、既存サービス状態を確認する gate が弱くなるため前者を推奨する。

根拠: [Ansible command module の check mode 動作](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/command_module.html)

### must-fix 2: rollback validation が非ゼロ終了でも「成功」と判定される

対象: `roles/rsyslog_forward_to_monnie/tasks/main.yml:387-402`

復元後の `rsyslogd -N1` は `failed_when: false` で登録され、その後の restart 条件が次になっている。

```yaml
when: rsyslog_forward_restore_validation is succeeded
```

`failed_when: false` により task の failed 状態は常に false になるため、`rsyslogd -N1` の `rc` が非ゼロでも `is succeeded` は真になる。つまり、復元後の全体設定が不正でも rsyslog をその設定で restart し得る。ローカルの最小再現でも、`/usr/bin/false` + `failed_when: false` の登録値について `rc != 0` と `result is succeeded` が同時に真になることを確認した。

修正案: string conditional を `when: rsyslog_forward_restore_validation.rc == 0` とし、非ゼロ時は restart を明示的に抑止する。必要なら rescue 最終メッセージに validation の rc / stderr を含める。

根拠: [Ansible failed test](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/failed_test.html)（`succeeded` は failed test の逆）

### must-fix 3: 1ノードごとの E2E gate と authy mute が playbook 上で強制されない

対象: `playbooks/rsyslog_forward_to_monnie.yml:7-26`

コメントでは `-l ansy` → `-l quory` → `-l authy` と各 E2E gate、authy APPLY 前の mute を要求しているが、playbook 自体は `hosts: ansy:quory:authy` と `serial: 1` のみである。`serial: 1` は各 batch を1台にするだけで、batch 間に人手の E2E 承認待ちを設けない。そのため `--limit` を付け忘れた APPLY は3台を連続適用し、authy の mute 前確認も迂回できる。

要求仕様は「1ノードずつ適用し、都度 tester が E2E 確認してから次へ進む」、authy は APPLY 前に quory 経由で mute と明記しているため、コメントだけでなく fail-closed にする必要がある。

修正案: `pre_tasks` の `run_once: true` assert で `ansible_play_hosts_all | length == 1` を要求し、必ず単一ホストの明示 limit で実行させる。authy の mute 状態を安全に read-only 検証できる既存インターフェースがあるなら、authy 選択時はその preflight も追加する。自動検証手段がなければ、少なくとも単一ホスト強制により手順上の mute gate を飛ばした3台連続適用を防ぐ。

## Suggestions

### suggestion: journald drop-in にも既存ファイルの所有権 gate を追加する

`49-monnie-forward.conf` は ownership marker がない既存ファイルを上書きしない一方、journald drop-in は既存内容を退避したうえでそのまま上書きする。recon 時点では対象パスがなくても、recon 後の drift や別管理系との衝突に備え、同じ fail-closed 方針を drop-in にも適用すると安全性が揃う。

### suggestion: authy fresh install 後の rescue 範囲を明文化する

authy で package install 後に activation failure となった場合、管理ファイルは rollback されるが、導入前の「rsyslog package 不在」までは自動復元されない。意図的に package removal を自動化しないのであれば、rescue の保証範囲と手動 rollback 手順への誘導を failure message に明記すると運用時の判断が速い。

### nit: UniFi overlap の fail message を sender 全体に合わせる

`roles/alloy/tasks/main.yml` の fail message は `A pve/Sophos sender ...` のままだが、判定対象は ansy / quory / authy を含む。`A remote syslog sender ...` などへ更新すると実際の検査範囲と一致する。

- recon drift / ownership: required/allowed snippet 集合による未知ファイル拒否と、既存49番の ownership marker 検証を確認。

- 非対象: Loki、UFW、pve 管理方式、Sophos、UniFi routing の意図しない変更は確認されず。receiver allowlist 拡張と Ubuntu source 追加の範囲に限定。
- staged rollout / mute: 手順書には ansy → quory → authy と authy mute command が記載されているが、上記 must-fix 3のとおり playbook 側の単一ホスト gate が不足。
