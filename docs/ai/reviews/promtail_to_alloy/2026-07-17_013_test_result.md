## 4. must-fix: UniFi allowlist extraction regexの過剰escape

対象: `roles/alloy/tasks/main.yml` の `alloy_existing_unifi_allowed_ipv4s` 設定。

production式は Jinja string内で regex metacharacterのbackslashを二重化している。

```text
regex_findall('(?m)\\$fromhost-ip\\s*==\\s*[^\\r\\n0-9]*([0-9]{1,3}(?:\\.[0-9]{1,3}){3})')
```

実際の Ansible/Jinja評価ではこの二重backslashがregex engineへ過剰escapeとして渡り、
想定書式にもmatchしなかった。

外部接続なしの localhost mock結果:

| expression | extraction result |
|---|---|
| production（二重backslash） | `[]` |
| 同一pattern（単一backslash） | 1件抽出 |

一時mock playbookは検証後に削除した。

修正案: Jinja string内のregexを単一backslashへ修正し、実taskと同じ
`slurp → b64decode → regex_findall` 経路で single quote / double quote / 複数conditionを
assertする。修正後は本書 §3 の safe check-modeを再実行し、DNS解決、積集合、candidate validate、
destructive skip、`failed=0` まで確認する必要がある。

対象: `roles/alloy/tasks/main.yml` の `Build the runtime source-IP allowlist`。

production式には前回と同型の二重backslashが残っている。

item.stdout | regex_findall('(?m)^([0-9]{1,3}(?:\\.[0-9]{1,3}){3})\\s')

| pve2 | 0 | 1 |
| Sophos | 0 | 1 |

さらに production roleには各senderの
`alloy_remote_syslog_allowed_ipv4s[name] | length > 0` assertが無い。そのため次が同時に起きる。

1. DNS commandのstdoutはIPv4形式を含むため、resolution assertはPASS。
2. runtime regexは空listを生成。
3. 全sourceのflatten結果は空で、重複assertは `0 == 0` としてPASS。
4. 既存UniFi集合とのintersectionも空でPASS。
5. rsyslog candidateはsource-IP route無しでも構文上validとなり得る。

修正には少なくとも次の両方が必要。

- runtime extraction regexをAnsible/Jinjaで機能する単一backslashへ修正する。
- build直後に全senderの抽出listが非空であることをassertし、今後のescape regressionを
  fail-closedにする。

修正後は safe checkを再実行し、件数非空assert、重複、UniFi積集合、candidate validate、
destructive skip、`failed=0`、事後非変更まで再確認する。
