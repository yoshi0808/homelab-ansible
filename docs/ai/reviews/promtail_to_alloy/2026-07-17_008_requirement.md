- 前提: Phase 1（monnie promtail→Alloy、2026-07-16 実機PASS）完了。正本 `docs/ai/prompts/log_observability_policy.md`。

## 目的

収集平面を pve1/pve2 と Sophos へ拡張し、全ソースに severity（`level`）ラベルを載せて
Phase 3（アラート→Slack）の土台を作る。**Loki への書き込みは monnie ローカルのみ**を維持し、
リモートノードからの Loki 直接 push・新規ポート開放は行わない。

## アーキテクチャ（v2 確定形）

```
pve1/pve2: journald → (ForwardToSyslog) → rsyslog(新規導入・omfwd) → UDP514 → ┐
Sophos:    GUI設定で syslog 送信                                    → UDP514 → ┤ monnie rsyslog(既存listener)
UniFi:     既存(変更なし)                                           → UDP514 → ┘
  → source-IP allowlist で振り分け → /var/log/{unifi,unifi-devices,pve-nodes,sophos-fw}.log
  → monnie ローカル Alloy(file sources) + Alloy(journal source) → Loki(localhost:3100)
```

- **不採用の代替案（記録）**: pve ローカル Alloy + リモート push（UFW 3100 開放・未認証 Loki 露出・
  Grafana サードパーティリポをハイパーバイザへ追加、が難点で不採用。将来 pve ログの unit 精度や
  配送保証が必要になったら再検討）。systemd-journal-remote（monnie に新 listener/ポートが必要で不採用）。
- 010 調査の確定事実: pve に rsyslog 未導入（Debian trixie main から 8.2504.0-1 導入可・リポ追加不要）、
  ForwardToSyslog は既定 no、syslog.socket は inactive、流量 13〜19行/分（warning+ は約1行/時）。
  Yoshinobu 判断（2026-07-17）: rsyslog 程度の導入はサーバー挙動への影響リスク低で許容。

## スコープ

### A. pve1/pve2: rsyslog 導入 + monnie への転送（**Yoshinobu の手動作業**・Ansible 化しない）

（Yoshinobu 決定 2026-07-17: pve 側の rsyslog 導入・設定は手動で行う。Ansible 対応は不要。）

1. **repo 側の成果物は「参照設定」のみ**: implementer は pve に配置すべき設定ファイルの**完全な内容**を
   implement 文書内に記載する（コピペで適用できる形）。対象:
   - `/etc/systemd/journald.conf.d/forward-to-syslog.conf`（`ForwardToSyslog=yes` の drop-in。
     本体 conf は編集しない）または rsyslog `imjournal` 方式 — **方式は実装判断**とし、
     Debian 13 trixie の rsyslog 既定（imuxsock/imjournal）との整合と選定理由を記載。
   - `/etc/rsyslog.d/` に置く転送設定（`omfwd` で monnie:514/UDP、全 priority。宛先はホスト名。
     ローカルファイル出力の重複生成を抑止する設定も含める）。
2. **手順**: `apt install rsyslog`（Debian 標準リポ、リポ追加なし）→ 設定配置 → `rsyslogd -N1` 検証 →
   enable+start、の順を implement に手順として記載（実行は Yoshinobu）。
3. **可逆性**: rsyslog stop+disable + purge + drop-in 削除で原状復帰できることを手順に明記。
4. **管理境界の記録**: pve の rsyslog は「手動管理（設定の正本は implement 文書/policy 参照）」として
   `log_observability_policy.md` に明記する（silent gap を残さない。目録の管理境界原則）。

### B. monnie: 受信振り分け + Alloy ソース追加（pve + Sophos）

6. **rsyslog 振り分け**: 既存 UDP514 listener に source allowlist を追加 —
   pve1/pve2 → `/var/log/pve-nodes.log`（1ファイル・host はログ行から抽出）、
   Sophos → `/var/log/sophos-fw.log`。**UniFi の既存振り分けの非回帰必須**。
   受信テンプレートで severity を行頭に書き出す形式（例: `%syslogseverity-text%`）を**検討**し、
   採用すれば Alloy の level 抽出が確実になる（実装判断・UniFi 経路には適用しない）。
7. **logrotate**: 新規2ファイルのローテーションを既存 unifi ログと同じ扱いに揃える
   （既存の rotate 設定を調査し、無ければ新設。実装判断・implement に記載）。
8. **Alloy file sources 追加**: `job=pve-nodes`（host 抽出=2番目トークン regex、network-devices と同型）、
   `job=sophos-fw`（host 固定）。ファイル不存在でも Alloy が fail しないこと（Sophos 送信設定前の状態）。
9. **Sophos 送信側は Yoshinobu の GUI 作業**（SFOS Log settings で syslog サーバ = monnie:514/UDP）。
   repo 側は受信準備まで。UFW は 514/udp 開放済みで変更不要。

### C. `level` ラベル標準化

10. **journal 系**（monnie の `loki.source.journal`）: journald `PRIORITY` を `level` へマップ
    （`error|warning|info|debug` の4値へ正規化。0-3→error、4→warning、5-6→info、7→debug）。
11. **file 系**: 新規2ファイル（pve-nodes / sophos-fw）は受信テンプレート採用時は確実抽出、
    非採用時は best-effort regex。既存 unifi / network-devices は best-effort regex
    （取れなければ `level` 無し。誤ラベルより無ラベル優先）。
12. **reviewer suggestion（2026-07-16_004）の消化**: `alloy_file_sources` の入力 assert に
    「`extract_second_token_as_host=true` と静的 `labels.host` の同時指定禁止」の相互排他を追加。

### D. 文書同期

13. `docs/ai/prompts/log_observability_policy.md` を v2 実態へ更新: §2.1 の「Linux ホスト=ローカル
    Alloy」を「**monnie=ローカル Alloy / リモート Linux ホスト=rsyslog 転送でアプライアンスと同じ
    ファネルに合流**（Loki 書き込みは monnie ローカルのみ、という設計原則を明文化）」へ改訂、
    §3 構成図・§5 ロードマップ消化、不採用代替案の記録。

## 制約

- **Loki・UFW は一切変更しない**（新規ポート開放なし。514/udp は開放済み）。
- UniFi 経路（振り分け・2ファイル・既存3系統ラベル）の非回帰。
- pve への変更は rsyslog 導入 + journald drop-in のみ。他のサービス・設定に触れない。
- APPLY は人間ゲート（pve への新規パッケージ導入・monnie の rsyslog/Alloy 変更）。
- 秘密・IP をリポジトリに書かない。実機検証は tester 工程。

## 確認項目（tester 工程）

- dry-run: `--syntax-check` + `--check` + 設定ファイルの構文検証（rsyslogd -N1 相当があれば使用）。
- APPLY 後（monnie 側は人間ゲート通過後に Ansible、pve 側は Yoshinobu 手動適用後）:
  - pve1/pve2: rsyslog active/enabled（手動適用の結果確認・read-only）、
    journald→rsyslog→monnie の転送実データが `/var/log/pve-nodes.log` に着信
    （両ノード分・host 判別可）、pve ローカルの副作用なし（重複ログ生成が想定内）。
  - monnie: `{job="pve-nodes"}` の実データ + `host` + `level` ラベル、`{job="sophos-fw"}` は
    Sophos 送信設定後に確認（設定前はファイル不存在で Alloy が fail しないこと）。
  - journal 系の `level` ラベル（`{job="system"} | level="error"` 等が機能）。
  - UniFi 経路の非回帰（rsyslog 514 受信・既存2ファイル増加・既存3系統ラベル不変）。
  - 可逆性の確認は手順の文書化まで（実際の巻き戻しはしない）。
