# promtail → Grafana Alloy 移行 Phase 1（monnie・現行UniFi経路の1:1移植）— 要求仕様

- 日付: 2026-07-16
- 起案: claude（要件定義・ハブ役）/ 承認: Yoshinobu（claude→impl-codex 送付前に最終確認）
- 前提調査: `docs/ai/reviews/promtail_to_alloy/2026-07-16_001_current_state.md`（tester read-only、実機採取済み）
- 上位方針（Yoshinobu 決定・2026-07-16）: 観測基盤は「収集平面（全ソース→Loki）＋監視/フック平面（Loki/Grafana アラート→Slack）」の2平面。エージェントは Alloy に統一。syslog 集約は **D1=(a) rsyslog を集約役に残し Alloy がファイル tail**。本 requirement は **Phase 1 = EOL の promtail を Alloy へ 1:1 置換**（rsyslog 据え置き）に限定。ソース拡張（pve/Sophos）と severity ラベル標準化は Phase 2、エラーフック（アラート）は Phase 3。

## 目的

monnie の promtail（v3.6.11、apt、EOL）を Grafana Alloy へ置換する。**現行の UniFi ログ収集経路の振る舞いを変えず**、EOL エージェントから離脱する。rsyslog（UDP514 受信・source-IP allowlist・2ファイル振り分け）は一切変更しない。Loki / Grafana も変更しない。

## 移植元＝保持すべき現状契約（001 調査より。移行後も不変にする）

promtail `/etc/promtail/config.yml` の以下を Alloy で等価に再現する:

1. **UniFi controller ログ**: ファイル `/var/log/unifi.log` を tail → ラベル `job=unifi`, `host=uckg2`
2. **switch/AP ログ**: ファイル `/var/log/unifi-devices.log` を tail → ラベル `job=network-devices`、さらに **log 行の2番目のトークンを `host` ラベルに抽出**（promtail の `regex: '^\S+ (?P<host>\S+) '` + `labels: host`）
3. **monnie journal**: systemd journal（`max_age: 12h`）→ ラベル `job=system`, `host=monnie`、`__journal__systemd_unit` を `unit` ラベルへ relabel
4. **出荷先**: `loki.write` で `http://localhost:3100/loki/api/v1/push`（認証なし）
5. rsyslog が書く2ファイルは `syslog:syslog 0644`（world-readable）。宛先・振り分けは rsyslog 側のまま

## 設計方針

- **repo 管理化**: promtail は repo 管理外（手動運用）だった。Alloy 化を機に **Ansible role（`roles/alloy` 想定）+ playbook（`playbooks/alloy_setup.yml`、対象 monnie=`monitoring_servers`）** として repo 管理にする。Phase 2 で pve/Sophos へ広げやすいよう、収集ソースは変数化して monnie 既定を defaults に置く（ただし Phase 1 の実配備は monnie のみ）。
- **導入方式**: apt。既に monnie に Grafana Labs リポ（`/etc/apt/sources.list.d/grafana.list`, `apt.grafana.com stable main`）があり、`alloy` パッケージを同リポが提供する。**新規リポ追加は不要**。loki/promtail と同じ apt 管理方針に揃える（月次 full-upgrade で更新される）。
- **config 形式**: Alloy の River/`.alloy` 構文で、`loki.source.file`×2・`loki.source.journal`・`loki.process`（host 抽出）・`loki.relabel`（journal unit）・`loki.write` を上記契約どおり構成し、`/etc/alloy/config.alloy` に配置。
- **cutover（二重取り込み防止が肝）**: 手順は「Alloy 導入→config 配置→**config 検証（`alloy validate`/`alloy fmt` 相当）**→ promtail を stop + disable → alloy を enable + start」。promtail と alloy が**同時に同じファイルを tail して Loki へ二重投入する状態を残さない**。失敗時は promtail を再 enable で戻せる（可逆）。
- **positions/state 継続**: Alloy はファイル位置を自身のデータディレクトリ（`--storage.path`、既定 `/var/lib/alloy/data`）で管理する。promtail の `positions.yaml` は移植しない。cutover 時に軽微な取りこぼし or 少量重複が生じ得るが homelab では許容（implement に明記）。既定の tail 開始位置（末尾からか先頭からか）を明示的に決め、大量再取り込みを避ける。
- **service/ポート**: apt 版の `alloy.service`（実行ユーザー `alloy`、env `/etc/default/alloy`）を使う。Alloy の HTTP listen（既定 `127.0.0.1:12345`）は明示設定し、promtail の 9080 とは別ポート（promtail 停止で 9080 は解放）。UI/HTTP endpoint を有効にするかは実装判断（既定 localhost バインドで可）。

## 対象ファイル（想定）

- `roles/alloy/`（新規: tasks/defaults/templates/handlers。config テンプレート `config.alloy.j2`）
- `playbooks/alloy_setup.yml`（新規、`-l monnie` で配備。tester-gate マーカー付与）
- （promtail 停止・disable は role 内 task で。promtail のパッケージ削除は Phase 1 では**しない**＝可逆性のため保留し、後日別途）

## 実施項目

1. `roles/alloy` を作成し、apt で `alloy` を導入、`/etc/alloy/config.alloy` を上記4契約どおりに生成、`alloy.service` を管理。
2. Alloy の config を配備前/配備時に **構文検証**する（`alloy validate` 相当。visudo と同様の fail-safe を意図）。
3. **cutover**: 検証後に promtail stop+disable → alloy enable+start。二重 tail を残さない順序で。
4. Alloy 実行ユーザーの**読み取り権限**を担保: `/var/log/unifi*.log` は 0644 で可。**journald 読み取りには `alloy` ユーザーが `systemd-journal` グループ等に属する必要**があるため、apt 版が付与済みか確認し、無ければ role で付与。
5. `playbooks/alloy_setup.yml` にヘッダの `# tester-gate:` マーカーを付ける（分類は下記）。

## pre-deploy 確認（implement/NOTE に明記、tester 工程で実機確認）

- monnie の既存 Grafana リポで `apt-cache policy alloy` が候補を返すこと（`alloy` パッケージ名・バージョン）。
- apt 版 `alloy.service` の実行ユーザー・既定 config パス・env ファイル・`--storage.path`・HTTP listen の既定値。
- `alloy` ユーザーが journald を読めるか（`systemd-journal` グループ所属の有無）。
- `alloy validate`（または `alloy fmt`）の正確なサブコマンド名と exit 挙動。
- `/var/log/unifi.log` / `/var/log/unifi-devices.log` の実ラベル（`uckg2` 等）が現行と一致。

## 検証項目（tester 工程・dry-run 優先、APPLY は Yoshinobu 判断）

- config `alloy validate` が通ること。
- **cutover 後、Loki に3系統が届くこと**（read-only で Loki クエリ: 直近数分の `{job="unifi"}` / `{job="network-devices"}`（`host` ラベル付き）/ `{job="system", host="monnie"}`（`unit` ラベル付き）にエントリがある）。
- promtail が停止・disable、alloy が active・enabled、**両者が同時にファイルを tail していない**こと（Loki 側で重複が出ていないこと）。
- rsyslog が無変更で active・UDP514 受信継続、`/var/log/unifi*.log` が増加継続。
- ラベル・host 抽出・unit relabel が現行と等価（既存 Grafana ダッシュボード/クエリが壊れない）。

## tester-gate 分類

- `playbooks/alloy_setup.yml` は **APPLY で実サービスの cutover を伴う**（promtail 停止・alloy 起動）。read-only ではない。既存の分類基準（[[feedback_destructive_classification_criteria]] 相当: 本番影響で判断）に照らし、**check-mode / dry-run を必ず通し、本番 APPLY は Yoshinobu の人間ゲート**（core.md §14）。tester は `--syntax-check` + `--check`（`scripts/safe-ansible-check.sh` 準拠）+ `alloy validate` までを実施し、APPLY はしない。分類マーカーの最終値は実装判断（`dry-run-aware` 等）だが、「無条件 APPLY 可」の分類にはしないこと。

## 制約

- rsyslog（UDP514 受信・allowlist・2ファイル振り分け）、Loki、Grafana は一切変更しない。
- ソース拡張（pve/Sophos）、severity/`level` ラベル標準化、アラート（エラーフック）は Phase 1 に含めない（Phase 2/3）。
- promtail パッケージの削除は Phase 1 では行わない（可逆性のため stop+disable に留める）。
- 秘密・IP をリポジトリに書かない。実ホスト検証は tester 工程。

## 除外（→ Phase 2 / 3）

- Phase 2: pve1/pve2 へローカル Alloy（journald→Loki）、Sophos を rsyslog 集約へ追加、全ソースの `level`（severity）ラベル正規化。
- Phase 3: Grafana 管理アラート（または Loki ruler）でエラーフック → Slack。既存 recovery/Slack 経路との統合。
