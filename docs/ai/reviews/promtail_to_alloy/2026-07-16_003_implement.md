## 実装概要

monnie の EOL Promtail を Grafana Alloy へ置換する role と playbook を新規作成した。
rsyslog、Loki、Grafanaの設定には触れず、現行Promtailの3収集系統とラベル契約を
Alloy River configへ1:1移植する。

APPLY時はAlloyパッケージのauto-startを抑止し、repo/config/path/権限/CLIを確認して
候補configを`alloy validate`した後にだけ、Promtail停止・disable → Alloy
enable・startの順でcutoverする。Alloyの起動・active確認に失敗した場合はAlloyを
停止・disableし、Promtailをstarted・enabledへ自動復元してfailする。

## positions 方針

Promtailの`/var/lib/promtail/positions.yaml`は移植しない。Alloy自身のstorage pathで
位置を管理し、file sourceは`tail_from_end=true`として初回起動時の全履歴再送を防ぐ。
cutover境界では少量の取りこぼし、またはjournalの`max_age=12h`再読による少量重複が
起こり得るが、requirementどおりhomelab Phase 1では許容する。

Promtailパッケージ、config、positionsは削除しない。rollback可能な状態を維持する。

## role の処理フロー

1. file/journal source変数と固定Phase 1 endpointをassert。
2. River候補をメモリ上でrenderし、3 source・process・relabel・write・tail設定をassert。
3. 既存`/etc/apt/sources.list.d/grafana.list`が`apt.grafana.com`を参照することを確認。
   repo追加・鍵追加は行わない。
4. `apt-cache policy alloy`にcandidateがあることを確認。
5. rsyslog所有の2 log fileが存在し、world-readableであることを確認。modeは変更しない。
6. apt moduleの`policy_rc_d: 101`でpackage scriptによるAlloy auto-startを抑止してinstall。
7. apt版unitのUser、EnvironmentFile、binary/config引数、storage pathを確認。
8. `alloy validate --help` / `alloy run --help`でCLIとHTTP listen flagを確認。
9. package作成済み`alloy` userと`systemd-journal` groupの実在を確認し、userを
   `systemd-journal`へappend。既存supplementary groupは維持する。
10. `/etc/alloy`、storage directory、`/etc/default/alloy`、configを管理。
11. template moduleの`validate: /usr/bin/alloy validate %s`と、配備後の明示validateを実施。
12. destructive blockでPromtail stop+disable → Alloy enable+start → active確認。
13. block失敗時はAlloy stop+disable → Promtail start+enable → fail。

## service / permission 方針

- apt版`alloy.service`を使い、独自unitは作成しない。
- `/etc/default/alloy`で`CONFIG_FILE=/etc/alloy/config.alloy`を固定する。
- HTTP/UIは名前ベースのloopback `localhost:12345`へ明示bindする。IP literalは書かない。
- config: `root:alloy 0640`、config directory: `root:alloy 0750`。
- storage: `alloy:alloy 0750`。
- journald: `alloy`を`systemd-journal` supplementary groupへappend。
- rsyslog出力file: 現行`syslog:syslog 0644`をread-only preflightし、roleでは変更しない。

## tester-gate / check mode

`playbooks/alloy_setup.yml`は`check-mode-native`とした。

- aptはnative check mode。
- candidate River configは全runでメモリ上render・契約assertする。
- read-only package/repo/service診断は`check_mode: false`で実状態を読む。
- fresh hostの`--check`はpackage user/binary/unitを作らないため、それらに依存する
  config file配置・Alloy native validateは実施できない。この制約をplaybook headerと
  task NOTEに明記した。
- Promtail stop+disable / Alloy enable+startは`when: not ansible_check_mode`かつ
  `tags: [destructive]`のblockに隔離した。
- APPLYは本番log agent cutoverなのでYoshinobuの明示判断が必要。

## pre-deploy / tester 必須確認

- `apt-cache policy alloy`のpackage名、candidate version、origin。
- apt版`alloy.service`の`User=alloy`、`/etc/default/alloy`、CONFIG_FILE、ExecStart、
  `--storage.path`、HTTP listen flag。
- requirementはstorage既定を`/var/lib/alloy/data`とし、本roleもfail-closedでunit内の
  同pathを要求する。一方、2026-07-16時点のGrafana最新Linux文書には
  `/var/lib/alloy`と記載があるため、**monnieの実candidate unitを正本として必ず確認**する。
  不一致時は自動推測せず、cutover前にrequirement / defaultを再判断する。
- `/usr/bin/alloy validate <path>`の正確なCLI、valid/invalid時のexit code。
- `alloy` userの実在、`systemd-journal`加入後のjournal read可否。
- `/var/log/unifi.log` / `/var/log/unifi-devices.log`のowner/mode/増加継続。
- `localhost:12345` bindと`/var/lib/alloy`配下の実positions/data生成先。
- APPLY前後にPromtail/Alloyのactive/enabled状態と同時tailが無いこと。
- Lokiで3系統と既存label契約、network deviceのhost抽出、journal unit labelを確認。
