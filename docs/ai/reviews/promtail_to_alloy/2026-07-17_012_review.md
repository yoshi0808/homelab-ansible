## 確認結果

### pveローカルruleとの順序

- 手動参照設定は`49-monnie-forward.conf`へ変更され、既存`45-frr.conf`より後、Debian
  default file ruleより前に評価される。
- 010 §6の実採取内容どおり、`45-frr.conf`は列挙したFRR daemon messageを
  `/var/log/frr/frr.log`へ出力して`stop`する。したがってFRR専用ローカル契約は49より先に
  保持される。
- FRRは両pveでpackage導入済みだがservice inactive、journal entryと専用fileは無しという
  実事実に基づき、Phase 2ではFRRをremote転送しない判断が明記された。将来SDN/FRR有効化時に
  専用file収集または転送を再検討する条件も残る。
- `postfix.conf`は`/var/spool/postfix/dev/log`を追加するinput宣言だけで、出力/stop ruleではない。
  そのsocketから入るPostfix messageは45を通過して49で転送される。既存fileを無効化する
  副作用はなく、rsyslog未導入時に失われていた可能性のあるchroot messageを収集できる。
- その他のmessageだけが49の転送後`stop`し、journald保持を維持しながらDebian default fileへの
  重複を抑止する。011で指摘した無条件10先行によるFRR/Postfix rule到達不能は解消した。

### UniFi allowlistとの重複fail-closed

- 既存`10-unifi.conf`を`slurp`し、`$fromhost-ip == '<IPv4>'` / double quote / 空白差を許容する
  regexで既存identity集合を抽出する。
- Phase 1実調査の10-unifi構造はIPv4 literalとの`$fromhost-ip` equalityを使うため、実書式と
  extraction contractは一致する。reviewer mockでもsingle quote、double quote、同一行の複数条件
  から3 addressを正しく抽出した。
- 抽出結果0件なら新規route配備前にassert failureとなる。新規pve/Sophos内の重複検査に加え、
  既存UniFi集合と新規集合の`intersect`が非空でもassert failureとなる。
- reviewer mockで非重複intersection=0、1 address重複intersection=1を確認した。既存10が先に
  `stop`するfirst-match routingに対し、曖昧identityをfail-closedにする構造である。

### 全体rsyslog検証とrollback

- 新規snippetはtemplate moduleで単体`rsyslogd -N1 -f %s`を通した後、変更時だけ配備済みの
  全体構成を`rsyslogd -N1`で検証し、成功後にrestart、`is-active`確認する。
- 配備前に旧snippetの存在と内容を保存する。全体検証・restart・active確認のいずれかが失敗すると
  rescueへ入り、旧版ありなら内容を復元、初回配備なら新規snippetを削除する。
- 復元後は全体`rsyslogd -N1`を再実行し、成功した場合だけrestartする。その後active状態を
  fail-quietで採取し、validation rcとservice状態を含む明示failureでroleを停止する。
- 復元validation失敗時に不正構成でrestartしない点も安全側であり、初回/更新の両経路をカバーする。
  011 suggestionの全体検証・受信点復旧は満たされた。
