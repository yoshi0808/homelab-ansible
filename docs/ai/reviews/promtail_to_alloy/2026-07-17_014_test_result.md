## 追記: AppArmor原因切り分け

- 実施日: 2026-07-17
- 対象: `monnie`
- 方法: read-only (`aa-status`, kernel journal, directory listing)
- service/config/mute操作: なし

### 結論

**014停止原因は rsyslogd AppArmor profileによるcandidate fileのread拒否。**

通常のUnix modeだけの問題ではない。APPLY時の `rsyslogd -N1 -f <candidate>` processはroot
(`fsuid=0`) だったが、enforce中の `rsyslogd` profileが
`/home/ann/.ansible/tmp/.../.source.conf` のreadを拒否した。

### 1. aa-status

見出し付き抽出結果:

```text
112 profiles are in enforce mode.
   rsyslogd
4 processes are in enforce mode.
   /usr/sbin/rsyslogd (...) rsyslogd
```

- `rsyslogd` profile: enforce
- 稼働中 `/usr/sbin/rsyslogd`: enforce profile適用中
- complain / unconfinedではない

### 2. kernel AppArmor audit

指定時刻以降のkernel journalに、APPLY失敗と同時刻の1件を確認した。

```text
apparmor="DENIED"
operation="open"
class="file"
profile="rsyslogd"
name="/home/ann/.ansible/tmp/.../.source.conf"
comm="rsyslogd"
requested_mask="r"
denied_mask="r"
fsuid=0
ouid=0
```

拒否対象はroleがtemplate validateへ渡した一時candidateそのもの。014のmodule stderrにある
path・時刻と一致するため、因果関係は確定できる。

### 3. directory mode

```text
drwxr-xr-x 0755 ann:ann /home/ann
drwx------ 0700 ann:ann /home/ann/.ansible
```

`.ansible` はowner-onlyだが、auditではrootのopenがAppArmor policyで明示拒否されている。
directory modeを緩めるだけの対応は原因に対する適切な修正ではなく、remote tmp全体の露出も招くため
採用すべきでない。

### 修正・再試行条件

template validateのcandidateを、rsyslogd AppArmor profileがreadを許可する限定的な一時pathへ
安全に置く方式に変更するか、同等にscopeを限定したvalidator方式を実装する。home配下remote tmpの
権限緩和やprofile全体のdisable/complain化は避ける。

修正後は次の順で再確認が必要。

1. syntax-check
2. safe `--check`
3. 人間の再承認
4. production APPLY
5. rsyslog/Alloy/UniFi/Lokiのpost-APPLY gate
6. 全gate PASS時だけmute clear
