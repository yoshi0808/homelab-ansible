# Alloy Phase 2 拡張: ansy / quory / authy の journald 集約（job=ubuntu-nodes）— 要求仕様

- 日付: 2026-07-17
- 起案: claude（要件定義・ハブ役。Claude 直筆・Codex 未使用）/ 承認: Yoshinobu（本文承認は claude→implementer 送付前）
- 前提: Phase 2（pve1/pve2 + Sophos）2026-07-17 完了・commit `d21d39b`。本件はその直接の拡張。
- 位置づけ: `docs/ai/prompts/log_observability_policy.md` の収集平面をさらに拡張。pve と違い **ansy/quory/authy はフル Ansible 管理ノード**なので、送信側も Ansible で自動化する（pve は Yoshinobu の方針で手動管理のまま・本件は変更しない）。

## 目的

ansy（開発）・quory（本番 Ansible 実行基盤）・authy（FreeRADIUS）の journald を、pve1/pve2 と同じ経路（journald → rsyslog → monnie:514/UDP）で monnie に集約し、Loki で検索・将来のアラート（Phase 3）対象にする。

**あわせて、monnie 自身の journald（Phase 1 で `job=system, host=monnie` としてローカル Alloy 収集済み）を `job=ubuntu-nodes` へ統合する**（Yoshinobu 承認・2026-07-17）。収集方式は変えない（monnie はローカル `loki.source.journal` のまま、他3台は rsyslog 転送のまま）。ラベルの意味論を「収集方式」でなく「ログの種類（Proxmox 以外の汎用 Ubuntu VM のシステムログ）」で揃えるための**ラベル値の変更のみ**。これにより最終的に `job=ubuntu-nodes` の `host` は `monnie` / `ansy` / `quory` / `authy` の4値になる。過去データは旧 `job=system` のまま残り、新規分のみ新ラベルで記録される（データ消失なし）。

## ⚠️ 今日（2026-07-17）の Phase 2 実装で確定した「再発見禁止」の教訓（必読・そのまま再利用すること）

実装者は以下を**独自に再調査・再設計しない**。該当コード（`roles/alloy/tasks/main.yml`、`roles/alloy/templates/observability-sources.rsyslog.j2`）を読み、**同じパターンをコピーして適用**すること。

1. **AppArmor**: `rsyslogd` 自身の AppArmor プロファイルが、Ansible の remote tmp（`/home/<user>/.ansible/tmp/...`）上の candidate ファイルの読み取りを **root プロセスにも拒否**する（enforce mode、Debian/Ubuntu の rsyslog パッケージ同梱プロファイル）。したがって `ansible.builtin.template` の `validate:` オプションで直接 `rsyslogd -N1 -f %s` を呼ぶ実装は**必ず失敗する**。
   - **対処（実証済み・そのままコピー）**: candidate を `/etc/rsyslog.d/<name>.conf.staging`（`*.conf` の include glob に拾われない拡張子）へ render → その場所で `rsyslogd -N1 -f <staging>` 検証 → PASS 時のみ同ディレクトリ内 `remote_src` copy で正規 `.conf` へ promote → `always` で staging を必ず削除。
   - Ubuntu（ansy/quory/authy）でも AppArmor が有効な可能性が高いため、**最初から staging 方式を採用**する（pve と同じ苦労を繰り返さない）。
2. **非文字列 conditional**: `when:` は必ず文字列の filter test（`is changed` / `is defined` 等）で書く。`(x | default({...})).changed` のような dict 属性直参照は `Conditional expressions must be strings` で失敗し、しかも `--check` では該当 task 自体が skip されるため **check-mode では検出できない**（今日発生・rescue も同じ理由で不発火した）。
3. **locale 依存の時刻文字列**: `date --iso-8601=ns` 等は locale によりカンマ小数点を出力し、`journalctl --since` がパース拒否（rc=1）する。**必ず `date +%s` で epoch 秒を取得し、`journalctl --since @<epoch>` の形式で渡す**（今日この1点で APPLY が2回落ちた）。
4. **rsyslog は設定配置前から動いている**: `apt install rsyslog` は即座にサービスを自動起動する。**設定ファイル配置後に `rsyslog` サービスの再起動が必須**（`policy_rc_d` での auto-start 抑止 → 全設定確定後に明示 start、または configure 後に確実に restart する設計にする）。今日 pve1 の手動適用でこの見落としにより2回 FAIL した。
5. **journald の転送有効化**: `ForwardToSyslog=yes` は `journald.conf.d/` の drop-in で行い、本体 `journald.conf` は編集しない。**変更後は `systemd-journald` の再起動も必須**（drop-in 配置だけでは反映されない）。
6. **多層エスケープの一般則**: Jinja→YAML→regex、Jinja→River→LogQL のような多段変換を書く場合、点修正でなく**該当ファイル全体の同クラス regex/conditional を一括点検**する。今回は新規 River テンプレート追記が不要な設計（既存 job を増やすだけ）なのでリスクは低いが、念のため `config.alloy.j2` に変更が入る場合は全面点検を行うこと。

## スコープ

### A. 受信側（monnie、`roles/alloy` 拡張）

1. `roles/alloy/templates/observability-sources.rsyslog.j2` に ansy/quory/authy を新規 sender として追加。**実行時 DNS 解決**（既存の pve/Sophos と同じ方式。IP をリポジトリに書かない）。
2. 出力は新規ファイル `/var/log/ubuntu-nodes.log`（`job=ubuntu-nodes` として `pve-nodes` とは分離。意味的に Proxmox ハイパーバイザと汎用 Ubuntu VM は別種のため）。行フォーマットは pve-nodes と同一（severity 4値を行頭・2番目トークンが host）。
3. **既存 allowlist との重複 fail-closed assert を拡張**: 新規3送信元の解決 IP が、既存 UniFi・pve・Sophos の allowlist と重複しないことを確認（既存の `intersect` assert のロジックを流用・対象リストに追加するだけ）。
4. `roles/alloy/templates/config.alloy.j2` に `loki.source.file "ubuntu_nodes"` を追加。**pve-nodes と全く同じ契約**（`extract_second_token_as_host=true`、確実 level 抽出、`job=ubuntu-nodes`）。`alloy_file_sources` の defaults 追加で足りるはずで、テンプレートの構造変更は不要（既存の `{% for source in alloy_file_sources %}` ループに乗る設計になっているはず。乗らない場合のみテンプレート修正し、その際は上記5番の全面点検を行う）。
5. logrotate: 新規ファイルを既存 `observability-remote-syslog.logrotate.j2` の対象パス一覧に追加するだけ（構造変更不要）。
6. **`alloy_file_sources` の相互排他 assert**（2026-07-16_004 由来）にも新規 source が正しく適合すること（動的 host 抽出 + 確実 level、静的 host ラベル無し）。
7. **monnie 自身の journal source のラベル変更**: `roles/alloy/defaults/main.yml` の `alloy_journal_sources`（monnie 用エントリ）の `labels.job` を `system` から `ubuntu-nodes` へ変更する（`labels.host` は `monnie` のまま静的維持）。収集ロジック（`loki.source.journal`、`__journal_priority` → `level` の4値マップ、`unit` relabel）は変更しない。この変更は monnie の Alloy config 再配備（validate → restart）を伴うため、既存6系統（unifi/network-devices/pve-nodes×2/sophos-fw/旧system）の非回帰確認に含める。

### B. 送信側（ansy / quory / authy、新規 Ansible 管理）

7. **新規 role**（例: `roles/rsyslog_forward_to_monnie`）を作成し、次を管理する:
   - `apt install rsyslog`（**authy のみ**。ansy/quory は既導入のため設定追加のみ。recon 2026-07-17_ubuntu_predeploy_recon.md 確定）。
   - `/etc/systemd/journald.conf.d/forward-to-syslog.conf`（3ノードとも新規: `ForwardToSyslog=yes` / `MaxLevelSyslog=debug`）。
   - `/etc/rsyslog.d/49-monnie-forward.conf`（`omfwd` で monnie:514/UDP、`RSYSLOG_SyslogProtocol23Format`）。**`stop` はノード別**（role 変数 or host_vars で制御）: **ansy/quory=stop なし**（rsyslog 既導入・`/var/log/syslog` 稼働中→既存ローカルログを保持しつつ転送を足す、`50-default.conf` の前に位置し stop しない）、**authy=stop あり**（rsyslog 未導入・fresh install→pve と同型で新規ローカルファイル生成を抑止）。3ノードとも既存 `21-cloudinit.conf` の stop ルールは維持（49番はその後・50-default の前）。**staging-validate 方式**（上記教訓1）で配置。AppArmor は ansy/quory が rsyslogd profile enforce 済、authy は install 後に生成されるため、いずれも staging 前提。
   - 配置後、rsyslog 全体 `-N1` 検証 → **rsyslog restart（上記教訓4を厳守）** → journald restart（上記教訓5を厳守、epoch ベースの settle 確認を推奨）。
   - 可逆性: rsyslog stop+disable + drop-in 削除 + purge で完全復帰できる手順を implement に記載（pve と同じ水準）。
8. **既存ファイル名との衝突回避**: 各ノードの `/etc/rsyslog.d/` に既存の番号付き conf があれば（pve の `45-frr.conf` のような先行ルールに相当するもの）、**必ず read-only で内容を確認してから**新規ファイルの番号順序を決める（pve で FRR/Postfix の扱いを誤った教訓。今回は事前確認を pre-deploy に明記）。

## Pre-deploy 確認（tester、read-only。実装着手前に実施し、requirement/implement の前提を検証する）

- ansy / quory / authy それぞれで: `dpkg -l rsyslog`（導入済みか）、`/etc/rsyslog.d/` の既存ファイル一覧と中身、`/etc/systemd/journald.conf` の `ForwardToSyslog` 現状値、AppArmor の rsyslogd profile 有無（`aa-status | grep rsyslog`）。
- 3ノードの直近 journal 流量目安（`journalctl --since -1hour | wc -l`）。
- monnie 側の `10-unifi.conf` / `49-pve-sophos...` 相当の既存 allowlist 内容（新規3ノードの IP との非重複を事前に見積もる）。

## 安全設計・実行順序

- **mute**: `authy` は自律復旧の監視対象（`homelab-mute` の ALLOWED_TARGETS に含まれる）。authy への APPLY 前に `homelab-mute set authy <N>` を quory 経由で実行する（今日と同じ、ローカル sudo ではなく `ansible quory -b` 経由）。**ansy/quory は監視対象外のため mute 不要**。
- **段階ロールアウト**: ansy（開発・最低リスク）→ quory（本番 Ansible 基盤・自分自身への変更なので特に丁寧に）→ authy（本番 FreeRADIUS）の順で1ノードずつ適用し、都度 tester が E2E 確認してから次へ進む（今日の pve2→pve1 と同じ思想）。
- **quory への注意**: quory 自身が実行元でもあるため、rsyslog/journald restart 中に ansible 接続断が起きないか確認する（restart は通常 SSH セッションに影響しないはずだが、念のため tester は restart 直後に別の read-only コマンドで疎通確認する）。
- **APPLY は人間ゲート**（Yoshinobu の明示判断）。tester は既定で APPLY しない。dry-run（`--syntax-check` + `--check`）を先に通す。
- 受信側（monnie）の設定変更を伴う場合は、Phase 2 と同様に monnie を先に確認（既存5系統の非回帰）。

## 確認項目（tester 工程）

- dry-run: 3ノード分の sender role + monnie 受信側拡張、いずれも `--syntax-check` + `--check` PASS。
- APPLY 後（ノードごと、人間ゲート通過後）:
  - 送信側: rsyslog/journald active、新設定ファイルの内容一致、AppArmor 由来のエラーが journal に無い、ローカル副作用（`/var/log/syslog` 等の増加）が `stop` により止まっていること。
  - 受信側: `/var/log/ubuntu-nodes.log` に該当ノードの行が着信（level 4値 + host 一致）。
  - Loki: `{job="ubuntu-nodes", host="<node>"}` に level 付き実データ。
  - **monnie ラベル変更後**: `{job="ubuntu-nodes", host="monnie"}` に新規 timestamp の実データが出て、`{job="system", host="monnie"}` は新規増加が止まる（過去データは残存）ことを確認。
  - 既存5系統（unifi / network-devices / pve-nodes×2 / sophos-fw）の非回帰。
  - quory: restart 前後で ansible 接続が維持されていること。

## 制約

- Loki・UFW は変更しない（既存 514/udp 受信に乗るだけ）。
- pve1/pve2 の管理方式（手動）は変更しない。本件は ansy/quory/authy のみ。
- 秘密・IP をリポジトリに書かない。
- 平文 UDP・allowlist は認証でない、という既存の policy 記載（§6）の制約はそのまま適用される（新規ノードもこのリスクを共有する）。
