## tester-gate と安全方針

- marker: `check-mode-native`
- syntax-check / dry-run の local temp は sandbox 内で書ける `/tmp` 配下を使用した。
- dry-run は `scripts/safe-ansible-check.sh` を使い、必ず `--check` を付けた。
- `--check` なしの playbook 実行（APPLY）は実施していない。
- package 操作、service stop/start/restart、設定 file 配備、user/group 変更は実施していない。

## APPLY 前に未確認の package-owned contract

Alloy 未導入の fresh host なので、次は pre-deploy / `--check` では確認不能だった。

- candidate `alloy.service` の実 `User=`
- `/etc/default/alloy` の package contract
- unit の `CONFIG_FILE` / `ExecStart` / HTTP listen flag
- storage path が `/var/lib/alloy/data` か `/var/lib/alloy` か
- `/usr/bin/alloy validate` / `run` CLI の実引数・exit behavior
- package-created `alloy` user / group
- `alloy` user の `systemd-journal` membership
- journald file の実読可否
- candidate config の Alloy-native validate

role は package install の auto-start を `policy_rc_d: 101` で抑止した後、上記 unit / CLI /
account / storage contract を assert し、不一致なら config deploy / Promtail stop 前に fail する。
そのため、unknown は残るが現時点の dry-run blocker ではない。ただし fail-safe assert を
迂回して APPLY を継続してはならない。

## APPLY 判断材料

### GO 材料

- package candidate と existing repository が確認済み
- source file の read 前提が確認済み
- candidate River config の3 pipeline contract が dry-run で PASS
- rollback 用 Promtail unit が loaded
- destructive block は check mode で完全 skip
- fresh-package contract は cutover 前の fail-closed assert で保護される
- dry-run 後の現行収集 service は unchanged

### residual risk / 人間判断事項

- package unit の実 storage path が role の `/var/lib/alloy/data` 想定と異なる場合、APPLY は
  Promtail 停止前に fail する。正本は install 後の実 unit とする。
- Promtail positions は移植せず `tail_from_end=true`。cutover 境界の小さな gap / overlap は
  requirement 上の許容事項だが、Yoshinobu の判断対象。
- Alloy process が active でも journald 読取成功や Loki label 等価性は保証されない。
- service cutover 自体は `--check` で実証できず、APPLY 後の実データ gate が必須。

## post-APPLY 必須 gate

APPLY 後は、service active だけで完了判定しない。最低限、次を read-only で検証する。

1. 実 package contract
   - `systemctl cat/show alloy.service` から `User`, EnvironmentFile, ExecStart,
     `--storage.path`, HTTP listen address を正本確認。
   - storage path の実 directory / ownership / data生成を確認。
   - `/usr/bin/alloy validate /etc/alloy/config.alloy` が成功。
2. service exclusivity / duplicate 防止
   - Alloy が active / enabled。
   - Promtail が inactive / disabled。
   - Promtail と Alloy が同時に同じ file を tail していない。
3. Loki 実データ3系統
   - `job=unifi`, expected static `host` label。
   - `job=network-devices`, regex 由来の `host` label付き実データ。
   - `job=system`, `host=monnie`, `unit` label付き実データ。
4. journald 実読可否
   - Alloy active のみを成功条件にしない。
   - `{job="system", host="monnie"}` の新規実 log と `unit` label を確認する。
   - 欠落時は package group / `adm` / `systemd-journal` と journal permission を再調査。
5. rsyslog / Loki 非回帰
   - rsyslog UDP 514 listener と2 output file の増加継続。
   - Loki endpoint と既存 query が正常。
