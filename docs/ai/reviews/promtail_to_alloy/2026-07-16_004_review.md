## Findings

### suggestion: 動的 host 抽出 source に静的 host を禁止する input assert を追加する

- `roles/alloy/tasks/main.yml:12`
- `roles/alloy/defaults/main.yml:33`

現行 defaults の `network_devices` は `labels.job=network-devices` のみで、静的 `host` は
混入していない。`loki.process.network_devices_host` が2番目のtokenを抽出し、
`stage.labels`で `host` へ昇格するため、現在の出力契約は正しい。

一方、`alloy_file_sources` は将来拡張用の変数であり、入力 assert は
`extract_second_token_as_host=true` と `labels.host` の同時指定を禁止していない。
将来の override で静的 host が加わると、regex match時の上書きとnon-match時の静的値残留が
混在し、誤ったhost labelを作り得る。動的抽出sourceでは `item.labels.host is not defined`、
非動的な `unifi` では期待する静的hostがある、という相互排他をassertすると安全である。

### suggestion: tester で journal の実読可否を明示確認する

- `roles/alloy/tasks/main.yml:221`
- `roles/alloy/defaults/main.yml:8`

roleは `alloy` を `systemd-journal` supplementary groupへappendし、サービス起動はその後なので、
通常のjournal file permissionには適合する。公式 Alloy 文書はLinux package利用時に
`adm` と `systemd-journal` の両方への所属を案内し、権限不足でもcomponentがエラー無しで
起動してjournalを収集しない場合があると明記している。

packageが既に `adm` を付ける可能性やtarget側permission差があるため、role側で無条件にgroupを
増やすことをmust-fixとはしない。ただし、`alloy` activeだけではjournal収集成功を証明できない。
testerはgroup一覧だけでなく、cutover後の `{job="system", host="monnie"}` と `unit` labelの
実データを必須gateとして確認すること。必要なら実機結果に基づき `adm` 追加をroleへ反映する。

参考: [Grafana Alloy: loki.source.journal](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.journal/)

## 重点確認結果

### River config と Promtail 契約

- `/var/log/unifi.log`: `job=unifi`, `host=uckg2` のstatic targetで
  `loki.write.local.receiver`へ直送している。
- `/var/log/unifi-devices.log`: static labelは `job=network-devices`のみ。regex
  `^\\S+ (?P<host>\\S+) ` はPromtailと等価で、named captureを `stage.labels` が
  `host`へ昇格し、その後にwriteへ送る。
- journal: `max_age="12h"`、`job=system`, `host=monnie`、
  `__journal__systemd_unit` → `unit` のrelabel ruleが一致する。
- write endpointは `http://localhost:3100/loki/api/v1/push`、認証追加無し。
- 両file sourceは `tail_from_end=true`。Promtail positionsを移植しない方針と整合し、
  初回の全履歴再送を避ける。
- `loki.source.syslog` はなく、UDP514受信とsource-IP routingはrsyslogに残る。

公式component schemaでも、`loki.source.file`のstatic targets / `tail_from_end`、
`loki.process`のnamed-capture regex / `stage.labels`、`loki.source.journal`の
`max_age` / `labels` / `relabel_rules`は使用可能な形である。

参考:

- [Grafana Alloy: loki.source.file](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.file/)
- [Grafana Alloy: loki.process](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.process/)
- [Grafana Alloy: loki.source.journal](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.journal/)

### cutover / rollback

- `apt policy_rc_d: 101`でpackage install時のauto-startを抑止する。
- package unit / CLI / source permissionを確認し、configをnative validateした後にだけ
  destructive blockへ入る。
- block内はPromtail stop+disable → Alloy enable+start → active確認の順で、roleが
  新たに両tailerを同時起動する順序はない。
- startまたはactive確認が失敗すると、rescueがAlloy stop+disable → Promtail
  start+enableの順で復元し、最後に明示failする。
- config deploy/validateまでの失敗はPromtail停止前なので、既存収集経路を維持する。
- Promtail package/config/positionsを削除しておらず、rollback可能性を保持する。

storage pathはdefaultsの `/var/lib/alloy/data` と最新Linux文書の `/var/lib/alloy` に差がある。
roleはinstalled unit内に期待pathが存在しなければconfig/cutover前にassertで停止し、推測して
Promtailを止めないためfail-safeである。testerはmonnieのcandidate unitを正本として確認し、
不一致ならrequirement/defaultを再判断する必要がある。

参考: [Grafana Alloy: Linux configuration](https://grafana.com/docs/alloy/latest/configure/linux/)

### tester-gate / check mode

- `check-mode-native` は妥当。read-only repo/package/service診断は `check_mode: false` で
  実状態を読み、apt/file/template/userはnative check modeを使う。
- service cutoverとそのrescueは1つのblockにまとまり、block全体が
  `when: not ansible_check_mode` + `tags: [destructive]` で隔離される。
- fresh hostの`--check`ではpackage-owned binary/user/unitが作られずnative validate不能、
  という限界をheaderとimplementに明記している。
- APPLYはPromtail停止を伴うためtesterは実行せず、Yoshinobuの明示判断が必要。

### scope

新規role/playbookはrsyslog config/service、Loki config/service、Grafana config/service、
CloudKey設定を変更しない。Promtailもstop+disableのみでpackage削除はない。
pve/Sophos、severity label、alert/Slack hookは追加されていない。
