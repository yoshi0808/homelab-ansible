# Role文書6本の歪み棚卸し(2026-08-18 第1回)

対象: `docs/ai/roles/*.md` 6本、`docs/ai/core.md`、`docs/ai/role-context-matrix.md`、`docs/ai/context-classification.md`、`docs/ai/memory-classification.md`。

分類はYoshinobuが定めた3クラス(`docs/ai/status.md` Next「プロンプト最適化」)。**①やること・やらないことの衝突 / ②読み取れない箇所 / ③細かく指示するよりAIに任せた方が良い箇所。**

## ① やること・やらないことの衝突

### 1-1. 実ホスト実行の禁止が2本に同文で置かれ、例外リストまで重複している

`docs/ai/roles/implementer.md`「禁止・エスカレーション」と `docs/ai/roles/reviewer.md`「禁止・エスカレーション」が、**同じ禁止と同じ例外リスト**(`--syntax-check`等のローカル検証 / decoy inventory / ansy作業ツリーと`/tmp`)を持つ。

`docs/ai/core.md`「subagentが共通して守ること」は既に「**実ホストへ触れてよい範囲は自分のRole文書が定める**」と書いており、禁止そのものがRole側にあるのは正しい。**重複しているのは例外リストの方**であり、片方だけ直せば黙ってドリフトする。

### 1-2. 安全機構にブロックされたときの指示が2つあり、優先関係が書かれていない

| 場所 | 指示 |
|---|---|
| `docs/ai/core.md`「安全機構がブロックしたとき」 | **止めて**、ブロックされた事実をCoordinatorへ**報告する** |
| `docs/ai/roles/reviewer.md`「禁止・エスカレーション」 | 一件ごとの承認を求めず、**静的レビューを継続**し、判定できない場合に限って保留する |

Reviewer側は「ブロックされた事実を報告する」に触れていない。両立するとも読めるが、**どちらが優先かは書かれていない。**

## ② 読み取れない箇所

### 2-1. 定義の無い機構を前提にしている(`READY報告`)

`docs/ai/role-context-matrix.md:9`

> | 起動時 | セッション開始時に必ず読む。**READY報告**の前提。 |

**`READY報告` は repo のどこにも定義が無い**(全文検索のヒットは Proxmox の `PATCH_READY` だけで無関係)。読み手は存在しない手順を探すことになる。

### 2-2. 「必須Skill」欄に、Skillとして実在しない名前が並ぶ

| Role | 「必須Skill」に並ぶ名前 | `skills/` に実在するか |
|---|---|---|
| Implementer | `skills/ansible-implementation-style/SKILL.md` | ある |
| Implementer | repository exploration / 最小差分編集 / 自己検証 / 成果物記録 | **無い**(4件とも) |
| Tester | `skills/test-strategy/SKILL.md` | ある |
| Tester | 静的検証 / 限定実行 / 再実行・異常系検証 / Ansible安全ゲート判定 / 証跡記録 | **無い**(5件とも) |

これらは能力の名前であってSkillではない。**同じ欄にパス付きの実在Skillと混在している**ため、読み手は該当する `SKILL.md` を探しに行く。しかもいずれも各Roleの「責任・権限」節で既に定めており、欄としても重複している。

### 2-3. `auditor.md` の見出しが「必須ContextとSkill」だが、Skillの記載がゼロ

Auditorは実装Skillを読まない設計(同節が明示)なので**内容が正しく、見出しだけが合っていない**。

### 2-4. `operator.md` の「設計中」がどこまでを指すか読めない

「現在の状態」節は、Request Channel 実装済み → agmsg 開通済み → **「それ以外の責務、権限、利用可能な機能および安全制約は設計中である」**と続く。3段落目が2段落目までを含むのか除くのかが読み取れない。

### 2-5. Operator だけ構造が違う理由が書かれていない

他5本にある「必須ContextとSkill」節が Operator に無く、`docs/ai/role-context-matrix.md` にも Operator 列が無い。**Operatorがquory側で動きこの表(開発工程)の対象外だからだが、そう書かれていない。** Auditorは列が無い理由を明記している(同ファイル「Auditorの参照範囲」)ので、扱いが非対称である。

## ③ 細かく指示するよりAIに任せた方が良い箇所

### 3-1. Skillへ切り出した査読観点が、Role文書に残っている

`docs/ai/roles/reviewer.md`「差分レビュー」末尾2項が、`skills/ansible-correctness-review/SKILL.md` の手順と同じ範囲を扱う。

| reviewer.md | ansible-correctness-review/SKILL.md |
|---|---|
| 多層エスケープ・rc規約・`--check`で評価されない条件分岐を毎回列挙する | 「評価文脈」= 変数の未定義・空・型違い、変数優先順位、host scope、lookupの再評価、**多層エスケープ** |
| 無音化・例外吸収で「該当なし」と「判定できなかった」が同じ出力に落ちていないか | 「結果判定」= rc、`changed_when`、`failed_when`、`rescue`、**例外吸収が、成功・該当なし・判定不能を区別しているか** |

Skill側は「正本との関係」で**重大度・返却先・独立性だけをreviewer.mdへ委ねる**と宣言しており、観点は自分が持つ形になっている。commit `860f635`(2026-08-10)でSkillへ切り出したときに、Role側を消し忘れたものである。

**Coordinator側の類似記述(`coordinator.md`「委任するときの独立性」の無音化の項)は重複ではない** — あちらは個々の判断ではなく**合成した結果を全体を見る立場から問う**という別の観点で、Skillが扱っていない。
