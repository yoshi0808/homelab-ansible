## AC別の合否

**AC6(静的な網羅)— PASS**
`scripts/check-tester-gate.sh`はexit 0(46 playbook)。これとは独立に、`grep -n "^# tester-gate:" playbooks/*.yml`で17件の母集団を自分で数え直し、17本それぞれについて実際に状態変更を行うplayの`pre_tasks:`に`that: not (ansible_check_mode | bool)`が存在することを目視確認した(Implementer/Reviewerの列挙を鵜呑みにせず、自分のgrep/Readで再現)。`proxmox_backup_restore_verify.yml`と`unifi_backup_fetch.yml`は選定用play(read-only、副作用なし)にはassertが無く、実際に変更するplayにのみ存在することも確認した。

**AC1(risk-acceptedの停止)— PASS(15/17は直接確認、2/17は間接確認)**
17本全てに`--check`を付けて実行し、全て終了コード**2**、`changed=0`、role本体のtask名は出力に一切現れなかった。うち15本(`ca_trust_deploy`/`cloudkey_cert_deploy`/`incident_capture_setup`/`incident_inspect_setup`/`incident_investigate_setup`/`incident_sync_timer`/`proxmox_backup_restore_verify`/`recovery_exec_setup`/`recovery_io_setup`/`recovery_probe_setup`/`recovery_push_drill_setup`/`recovery_push_setup`/`systemd_timers`/`time_sync_ntp_reference`/`unifi_backup_fetch`)は、出力上で実際にR1の停止assert(`[migration] --check has no dry-run here`)自体が失敗しているのを直接確認した。`ca_trust_deploy`と`time_sync_ntp_reference`は、pve1が現在SSH到達不能(No route to host)であるにもかかわらずpve1側もこのassertで`fatal`になった — `gather_facts: false`かつassertがaction-local(接続不要)であるため、ホストの生死に関係なく確実に止まることを意味し、premiseの堅牢性を裏付ける追加証拠になった。

残り2本(`cert_renew.yml`、`codex_update_check.yml`)は、ansyから実行すると、R1のassertより前段にある既存の別guard(「このplaybookはquoryからのみ実行すること」という`ansible_facts['hostname'] == 'quory'`assert、本requirementとは無関係の既存設計)がまず失敗し、rc=2・changed=0にはなったがR1のassert自体には到達しなかった。quory上の作業ツリー(コミット前の差分込み)から実行して直接確認するため、`tar | ssh quory`でrepoを一時コピーしようとしたが、**Claude Codeのauto mode classifierにブロックされた**。安全機構がブロックした操作は別手段で同じ結果へ迂回しないという原則に従い、これ以上の回避は試みず停止した。代替として、両ファイルの該当play(`hosts: quory`/`hosts: ansy:quory`)の`pre_tasks`に、他15本と**文字列として同一**の`that: not (ansible_check_mode | bool)`assertが存在することをgrepで確認したうえで、この構文だけを切り出したlocalhost限定・`connection: local`の使い捨てplaybook(実host名・実IPなし)で`--check`/通常実行の両方を実行し、rc=2/changed=0/後続task非到達(`--check`時)とrc=0/後続到達(通常時)を確認した。これは実行できなかった2本の直接証明ではなく、同一構文の別ファイルでの動作確認である。

**AC2(通常実行の不変)— 直接実行なし(承認済みscope外につき未実施)、間接確認のみ**
指示により、risk-acceptedの17本を`--check`なしで実行していない(本番適用になるため)。代わりに、(1) 17本の`git diff`を読み、R1の変更が既存taskの前に`pre_tasks`を純粋に追加しただけで、既存task自体は一切変更されていないことを確認した、(2) 同一のassert構文を使った上記decoyで、`ansible_check_mode`が偽のとき(通常実行相当)はassertが必ず通過し後続taskへ到達することを確認した。実際の17本を通常実行して確かめてはいない。

**AC3(明示的な通知抑止が残ること)— 直接実行なし(承認済みscope外につき未実施)、実ファイルでの間接確認あり**
17本のいずれかを`--check`なし・`-e skip_notifications=true`付きで実行することは本番適用そのものであり、承認済みscope(`--check`付きの17本のみ)に含まれないため実行していない。代わりに、**実物の`roles/common_slack/tasks/notify.yml`**(コピーでなく本体ファイル)を、localhost限定・`connection: local`の使い捨てplaybookからincludeし、`-e skip_notifications=true`(`--check`なし)で実行した。結果: 終了コード**0**、debug taskがchannel/status/title/messageを全文出力し、Slack送信を含む後続の`block`は全て`skipping`となった。ラッパー自身のplaybook_dirが実repo外にあるため`capture.yml`のinclude解決だけは失敗したが、これは`notify.yml`自身の`rescue`ブロックで無害化される設計どおりに吸収され、Slack抑止の判定ロジックには影響していない。R2で除去対象だった5ファイルの`skip_notifications: "{{ ansible_check_mode }}"`が実際にコード上から消えていること(コメントのみ残存)もgrepで確認した。

**AC4(check modeで送らない)— 部分的に直接実行、実ファイルでの直接確認あり**
`check-mode-native`のplaybookは通常どおり`--check`実行できるためscope承認は不要。`ubuntu_nightly.yml`を`--check --limit authy`および`--check --limit monnie`で実行し、rc=0で完走した(`changed=1`は設計どおりのcheck-mode専用レポート書き込みのみ、role本体の破壊的操作は未実行)。ただし現在authy/monnieともreboot不要状態のため、この2ホストでは「reboot-required時のSlack通知」分岐そのものは今回発火しなかった(実環境の状態によるもので、意図的に再現できない)。`prometheus_update_check.yml --check`は、cert_renew系と同じ「quoryからのみ実行」guardがansyからの実行では先に失敗し、R4/R3のnotify分岐までは到達しなかった。この2件を補うため、AC3と同じ手法で**実物の`notify.yml`**を`--check`のみで実行し、rc=0・debug全文出力・Slack送信block全skipを確認した — これがAC4の核となる挙動(check modeでは送らない)の直接証拠である。

**AC5(本番経路の不変)— 未実施(方針として実行を見送り)**
`prometheus_update_check.yml -e dry_run=true`(`--check`なし)は、`docs/ai/policies/ansible_test_safety_policy.md` TS-023が明記する「`check-mode-native`を`--check`なしで実行するのはAPPLYであり、Tester役は行わない」に文字通り該当するため実行していない。加えて、実行すれば実際にSlackへ本番通知が送られる可能性があり、これは検証目的の意図しない実通知を避けるという運用原則と衝突する。実行しようとしても、ansyからでは「quoryからのみ実行」guardに先に阻まれること、quoryでの実行にはAC1と同じくrepoコピーがブロックされるという制約があることも申し添える。代わりに`roles/common_slack/tasks/notify.yml`の3値ORの`when`条件を読み、`dry_run=true`実行時は`ansible_check_mode`が偽であるため追加された`or ansible_check_mode`項が分岐結果に寄与しないこと(AC3/AC4で実測した同一条件式の挙動から演繹)、および`git diff roles/prometheus_update_check/tasks/main.yml`でdry_run判定ロジック自体が本diffで変更されていないことを確認した。**これは実行による確認ではない。**

## 観測できなかった項目とその理由

1. AC1のうち`cert_renew.yml`/`codex_update_check.yml`の**R1 assert自体**の直接発火は未観測。理由: 既存の別guard(quory限定)が先に阻む。quoryへの作業ツリーコピーはauto mode classifierにブロックされ、迂回しなかった。
2. AC2・AC3は、17本いずれについても実プレイブックの`--check`なし実行では確認していない。理由: 承認済みscopeが`--check`付きの実行に限定されており、`--check`なし実行は本番適用そのものであるため。
3. AC4のうち`prometheus_update_check.yml`自体の`--check`実行は、quory限定guardに阻まれ最後まで到達していない。`ubuntu_nightly.yml`は到達したが、reboot-required分岐は現在のauthy/monnieの状態(reboot不要)により発火しなかった。
4. AC5は方針として実行していない(TS-023により、Tester役が行ってはならないAPPLYに該当するため)。
