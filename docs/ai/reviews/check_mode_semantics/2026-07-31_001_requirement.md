# requirement: `--check` の意味の一本化

日付: 2026-07-31
起票: Coordinator(Yoshinobuとの対話で方向を確定)
関連Incident: `docs/ai/memory/incidents/2026-07-31_subagent-unintended-deploy-risk-accepted-check.md`、`docs/ai/memory/incidents/2026-07-29_tester-slack-notify-misfire.md`

## 1. 問題定義

`--check` が、このリポジトリの中で**2つの逆の意味**を持っている。

| 分類 | 本数 | `--check` の意味 |
|---|---|---|
| `check-mode-native` | 19 | シミュレート(破壊的taskを `ansible_check_mode` でゲート) |
| `risk-accepted` | 17 | **無効**。role import 等に `check_mode: false` が付いており、全taskが本適用される |

さらに `risk-accepted` のうち **5本**(`recovery_exec_setup` / `recovery_io_setup` / `cert_renew` / `ca_trust_deploy` / `incident_inspect_setup`)は `skip_notifications: "{{ ansible_check_mode }}"` を併用しており、`--check` を渡すと「**本適用したうえにSlack通知も出ない**」という最悪の組合せになる。

2026-07-31、Implementer subagentが `playbooks/incident_inspect_setup.yml` を decoy inventory + `--check` で実行し、**dry runのつもりでansy上にユーザー・sudoers・ACL・wrapperを実際に作った**。原因は実行者の注意力ではなく、フラグの多重定義である(2026-07-31 Yoshinobu:「`--check` を付けたから安全と思うな、は無理がある。環境が悪い」)。

独立した第2の欠陥として、`roles/common_slack/tasks/notify.yml` の抑止条件は `tester_mode` / `skip_notifications` が真のときだけで、**渡し忘れた場合の既定が「本番へ送信」**である。`ansible_check_mode` は判定に入っていない。検証実行が本番Slackを鳴らす事故が2026-07-26と2026-07-29に発生している。

### 観測した事実(実測、2026-07-31)

- `ansible_check_mode` は `check_mode: false` を付けたblockの**内側でも `True` のまま**である(localhost検証)。`check_mode: false` はtaskを実走させるだけで、この変数の値を落とさない。
- `roles/prometheus_update_check/tasks/main.yml` は notify を `check_mode: false` のblockで包み、コメントで「Slack is the intentional check-mode exception」と宣言している。同playbookの `tester-gate` 行も「成果物であるSlack通知は `--check` でも実走する」と書いている。
- `notify.yml` の抑止経路は、抑止時に channel / status / title / message を `debug` で**全文出力する**。
- notify の呼び出しは 41箇所 / 27ファイル。うち呼び出しの直前20行に `check_mode: false` があるものは 7ファイル(`cert_renew`、`cert_renew_quory`、`proxmox_patch_weekly_full`、`ubuntu_nightly`、`incident_sync/finalize`、`prometheus_update_check`、`ubuntu_vm_full_upgrade`)。**これは痕跡による一次抽出であり、各箇所の意図を確定したものではない。**
- `skip_notifications` は extra-vars で上書きできる(`-e skip_notifications=true` は play vars より優先される)。

## 2. ゴール

1. `--check` の意味を、playbook冒頭の `tester-gate` マーカーが**単独で**決める状態にする。第3の状態を作らない。
2. `risk-accepted` に `--check` を渡したら、適用せずに**停止**する。
3. check modeでは Slack へ**送らない**。分類によらず一貫させる。

## 3. 非ゴール

- `risk-accepted` の17本を check-mode-safe 化すること。**昇格の経路だけ用意し、本ラウンドでは1本も昇格させない。**
- `tester_mode` 変数の廃止・整理。
- Semaphore 側の設定変更(repo外)。
- `--check` 実行から本物のSlack配信を得る手段を残すこと。**検討して不採用とした** — escape hatch用の変数を足すと、それ自体が「一貫性を崩してよい穴」になる。配信そのものを試したい場合は、抑止時の `debug` 全文出力で内容を確認するか、通知だけを送る使い捨てplaybookを別途書く。

## 4. ユーザーストーリー

- Testerとして、dry-runのつもりで実行したものが本番へ適用される経路を無くしたい。
- Testerとして、検証実行が本番Slackを鳴らさないことを、変数を覚えていなくても成り立たせたい。
- Yoshinobuとして、`--check` を付けたときに何が起きるかを、playbook冒頭の1行だけで判断したい。

## 6. 受入条件

**AC1(risk-accepted の停止)**
Given `tester-gate: risk-accepted` のplaybook17本のいずれか
When `--check` を付けて `ansible-playbook` を起動する
Then pre_tasks の assert で失敗して停止し、**終了コードは 2**。`PLAY RECAP` の `changed` は **0**。role本体のtaskは1つも実行されない(出力に role 内タスク名が現れない)

**AC2(通常実行の不変)**
Given 同じ17本のいずれか
When `--check` を付けずに起動する
Then 従来どおり本適用され、**終了コードは 0**。通知の有無も従来と変わらない

**AC3(明示的な通知抑止が残ること)**
Given 同じ17本のうち通知を出すもの
When `--check` を付けず `-e skip_notifications=true` を付けて起動する
Then 本適用され、Slackへは送信されず、`debug` に通知本文が全文出力される。**終了コードは 0**

**AC4(check mode で送らない)**
Given `tester-gate: check-mode-native` のplaybookで通知を出すもの
When `--check` を付けて起動する
Then Slackへの送信taskが実行されず、`debug` に channel / status / title / message が全文出力される。**終了コードは 0**

**AC5(本番経路の不変)**
Given `prometheus_update_check` を Semaphore と同じ引数(`-e dry_run=true`、`--check` なし)で起動する
When 実行する
Then 従来どおりSlackへ送信される。**終了コードは 0**

**AC6(静的な網羅)**
Given リポジトリの作業ツリー
When `tester-gate: risk-accepted` を持つplaybookを列挙する
Then **17本すべて**に R1 の停止条件が入っている。1本も欠けていない
