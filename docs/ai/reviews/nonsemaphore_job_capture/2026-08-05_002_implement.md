## 2. R1の実装判断 — OQ1・収集器の現物確認・AC2の満たし方

**OQ1の答え: 既存のspoolレコードの形(T1 = `roles/common_slack/tasks/capture.yml`のrecord_version 1契約)へ厳密に合わせた。** 別形式にしなかった理由:

- 収集器(`roles/incident_capture/files/incident-capture-collector.py`)の`load_spool_record()`は`record_version==1`と`REQUIRED_SPOOL_FIELDS`の完全一致を要求する。合わせない形にすると`_rejected/`へ退避されるだけの空バンドルになり、AC1が要求する「捕捉した事実が残る」の質が落ちる。
- 合わせれば、**収集器のstep4(相関しなかったspoolのうちnotableなもの)が新しい分岐を1行も足さずにそのまま処理する** — 次節で現物のコードを読んで確認した。

**「対応するSemaphoreジョブ行が無いレコードをどう扱うか」を実装前に現物で確認した(AC3、要件の明示指定)。** `incident-capture-collector.py`のmain()を読み、`slack_status`が`{"", "ok"}`以外(=notable)で、Semaphoreの失敗ジョブと時間窓相関しなかったレコードは、731〜759行目の経路で**単独バンドル(`source: "spool"`)としてそのまま`reports/incidents/`配下に書かれ、収集器はクラッシュしない**(exit codeは2=collection_errorsあり、3=内部例外ではない)ことを確認した。**この経路は既に存在しており、今回新設していない** — ハンドラが書くレコードをこの契約に合わせることで、この既存の安全な経路にそのまま乗せた。実際に確認した手段:

1. `incident-capture-collector.py`を丸ごと読み、`slack_status not in NON_NOTABLE_SLACK_STATUS`の分岐(731〜759行)が単独バンドルを作りexit 2で終わることをコードから確認。
2. リポジトリの実ファイル(`roles/incident_capture/files/incident-capture-collector.py`をコピー)を、`/tmp`配下のスクラッチにfakeのspool/bundle/state dirと設定JSONを用意して実行し、実際に`source: "spool"`のバンドルが`reports/incidents/`相当のディレクトリへ書かれ、exit codeが2(3=内部例外ではない)であることを確認した(§5参照)。

**AC2(flockの排他を異常として扱わない)は、ハンドラ側のロジックではなく、`SuccessExitStatus=75`によって構造的に満たしている。** flockが排他した場合、serviceはexit 75で終わり、`SuccessExitStatus=75`によりsystemdはこれを`inactive`(成功)として扱う。systemdの`OnFailure=`は**unitが`failed`状態に入ったときにのみ発火する**ため、排他による見送りではそもそも`ansible-timer-failure-capture@.service`が起動されない。ハンドラスクリプト側に「これは排他だから無視する」という分岐を書く必要が無い(書けば、判定ロジックの二重化になる)。

この`-E 75`+`SuccessExitStatus=75`の組み合わせは新規発明ではなく、`roles/incident_investigate/templates/incident-investigate.service.j2`と`roles/worktree_sync/templates/worktree-sync.service.j2`の既存前例に倣った。前者のコメントは「実測: systemd-run --user でSuccessExitStatus=75の有無によるis-failedの違いを確認済み」と記録しており、この区別が本リポジトリで既に実地検証済みであることを踏まえている(今回はテンプレートのJinjaレンダリングと`systemd-analyze verify`によるunit構文の妥当性のみをローカルで再確認し、is-failedの実地観測そのものは再現していない — 既存前例からの借用として扱う)。

**ハンドラは「収集器が配備されているホストでだけ書く」形にした。** ゲートはT1(`capture.yml`)と全く同じマーカーファイル(`/etc/homelab-recovery/incident-capture.json`)の存在確認。spool_dirも同じファイルの`spool_dir`キーから読む(値の二重管理をしない — `roles/incident_capture/templates/incident-capture.json.j2`が書く値そのもの)。マーカーが無い/読めない/spool_dirが取れない/存在しない場合は何もせずexit 0(このホストに収集器が無ければ書いても誰も読まない、T1と同じ設計判断)。

**Slackは送らない。** `skip_notifications: true`とし、実際にSlackへ送信する経路はハンドラに一切無い(非ゴール§4「通知の新設をしない」)。`slack_status: "error"`は、収集器の「notable」判定(単独バンドル化のトリガー)に使うためだけの値であり、通知の可否を意味しない(T1のコメント「skip_notifications bool flag only, not a filter」と同じ扱い)。

**「roles/systemd_timers が生成する全ジョブに効く形」(要件R1)を満たす設計:** OnFailure=は`ansible-timer.service.j2`(全timerが共有するテンプレート)へ足したため、`systemd_ansible_timers`カタログに新しいエントリを足す人は捕捉の配線を意識しなくてよい。ハンドラunit・スクリプトの配備タスクもカタログのループの**外**に置き、カタログの件数に関わらず1回だけ配備される。

## 3. R2の実装判断 — enabled/activeの根拠

`ansible-cert-renew-quory.timer`を`deployment_drift_check_units`へ追加した。`playbook: playbooks/systemd_timers.yml`を持たせた根拠(R1-a基準): 同playbookの「Enable and start timers」taskはカタログの全エントリへ`when`ガード無しで`enabled: true / state: started`を適用するため、流せば実際にこの状態へ復元される。

**`enabled: enabled` / `active: active`は実ホストの直接照会(`systemctl is-enabled`/`is-active`)では確認していない。** requirement §2でCoordinatorが確認した事実は`unit-cat`によるunit定義の内容(OnCalendar/Persistent)であり、enable/active状態そのものではない。以下を根拠に採用したが、**直接確認ではないことを明示する**:

- `roles/systemd_timers/tasks/main.yml`の「Enable and start timers」taskに`when`によるgateが無く、カタログの唯一のエントリ(cert-renew-quory)が現に配備済みであれば必ずenabled/startedになる設計。
- requirement §2の間接証拠(quoryの`semaphore.service`のActive sinceが`OnCalendar=*-*-01 00:35:00`と一致する2026-08-01 00:35:14 JST) — enabled/activeでなければこの時刻には発火し得ない。

配備後、Testerが`systemctl is-enabled`/`is-active`で直接確認できる(AC4/AC5はこの案件では実ホスト未検証)。

## 4. R3の実装判断 — SEMI-SAFE・survey/argumentsは追加せず、実行元ガードで制約を満たす

`playbooks/systemd_timers.yml`を`semaphore_templates_catalog`へ`class: SEMI-SAFE`・survey/arguments無しで追加した(R7の9本と同じ形)。この判断自体は変更していない。

**当初の実装(初版)は「quoryの自Semaphoreから押される」ケースしか検討しておらず、独立レビューSuggestion #1(Medium)がこの抜けを指摘した。** `playbooks/semaphore_templates_setup.yml`はヘッダ自身が、同じカタログをansy(検証用Semaphoreインスタンス)へ`-e semaphore_templates_api_base_url=https://ansy.internal:3000/api`で適用する運用を文書化しており、既存id=4等の非破壊にしか注意書きが無い(新規カタログ追加を止める記述は無い)。この経路でカタログをansyへ適用すると、ansyのSemaphore UIにも「Configure Ansible systemd timers」ボタンが新設される。それを押すと、Semaphoreの実行プロセス自体がansy上で動くため、`playbooks/systemd_timers.yml`の`connection: local`(無条件、host_varsの`ansible_connection`条件式のような「実行元ホストに応じて切り替える」ガードを経由しない)がそのままansy自身へ作用し、**quory向けのunit定義(既定target_hosts=control_nodesが指すquoryのcert-renew-quory timer/service一式、および本案件で新設したfailure-captureハンドラ)を、ansyの実ファイルシステムへ`become: true`のroot権限で配備してしまう。** ansyのSemaphoreインスタンスがSSH鍵を持たないこと(system context doc `docs/ai/context/system/semaphore.md`が「鍵が無いことによる無害さ」と明記する前提)は、`connection: local`を一切防がないため、この経路はその既存の安全前提の**外側**にある。**到達には「ansyへカタログ適用」+「ansyでボタンを押す」という2段の意図的操作が要るため即座に事故る形ではないが、requirement R3が明示的に要求した「connection: local制約をテンプレートの形で満たす」検討としては初版は未完了だった。**

**対応: R3は落とさず、`playbooks/systemd_timers.yml`自身に実行元ホストを検証するguard playを追加して満たす形にした。** `codex_update_check.yml`・`cert_renew_quory.yml`・`cert_renew.yml`・`cloudkey_cert_deploy.yml`・`prometheus_update_check.yml`が既に確立している「verify execution host」パターン(`hosts: localhost` + `connection: local` + `ansible.builtin.assert`)と同型:

```
- name: systemd_timers - verify execution host
  hosts: localhost
  gather_facts: true
  connection: local
  tasks:
    - name: Ensure this playbook is running on a host that belongs to target_hosts
      ansible.builtin.assert:
        that:
          - ansible_facts['hostname'] in (groups[target_hosts | default('control_nodes')] | default([]))
        fail_msg: >- (実行元ホスト名・target_hosts・解決先groupを含む具体的なエラーメッセージ)
```

既存の個別ホスト固定パターン(`ansible_facts['hostname'] == 'quory'`)とは異なり、`systemd_timers.yml`はquory/ansyの両方から使い分ける設計(`target_hosts`切り替え)であるため、`groups[target_hosts | default('control_nodes')]`という**target_hosts自体が指すgroupのメンバーに実行元ホストが含まれるか**という一般化した形にした。この1つのplayで、default(quory向け)・`-e target_hosts=dev_nodes`(ansy向け)の両方の正規経路を許可しつつ、host/target_hostsの組み合わせが食い違う実行(ansyのSemaphoreがdefaultのまま押した場合を含む)を一律で止める。

**ローカルで3シナリオを再現し、意図どおりの分岐を確認した(§7):**

| シナリオ | 実行元(想定) | target_hosts | 結果 |
|---|---|---|---|
| A | quory | (既定) control_nodes | PASS(正規、quory本番) |
| B | **ansy** | **(既定) control_nodes** | **BLOCKED**(独立レビューが指摘した危険経路。修正前は素通りしていた) |
| C | ansy | dev_nodes(明示指定) | PASS(正規、ansy検証用) |

**残る前提:** この guard は「実行元ホストが`target_hosts`の指すgroupのメンバーであること」だけを見る。Semaphoreの実行ユーザーがそのホスト上でローカルにsudoできるかどうか(§8で引き続き未解決事項として保持)とは独立の話であり、今回のガードはこの点を検証しない——ただし、Suggestion #1が指摘した「誤ったホストへの配備」というクラスの危険は、実ホストでの検証を経ずに、この静的ガードによって構造的に閉じている(§7でローカル実行により確認済み)。

## 6. AC1の「残ったことを観測する手段」(要件が明示的に要求)

配備後、`ansible-cert-renew-quory.service`が異常終了すると、次回の`homelab-incident-capture.timer`周期(5分間隔)以内に以下のいずれかで確認できる:

1. **`reports/incidents/`直下に`spool-<epoch>-<hex>/`ディレクトリが新規に増える。** 中の`summary.json`の`spool_records[0].play_name`が`ansible-cert-renew-quory.service`、`slack_status`が`error`。
2. **`reports/incidents/_heartbeat.json`**(収集器が毎周期上書きする)の`bundles_created`が0より大きい周期がある。
3. `journalctl -u ansible-timer-failure-capture@ansible-cert-renew-quory.service.service`(ハンドラ自身の実行ログ)。ハンドラは常にexit 0を返すため、この単体では成功/失敗を区別できない — 1・2が一次的な観測手段。

- **【2026-08-05更新】R3の「ansyのSemaphoreから誤って配備される」リスク(独立レビューSuggestion #1)は§4のguard playで構造的に閉じた。** 一方、**Semaphoreの実行ユーザーがローカルにsudoできるかどうかという別の懸念(初版から引き続き未解決)は残る。** これは既存テンプレートの稼働実績からの類推であり、直接検証していない。誤っていた場合の影響は「Semaphoreからのボタン配備が失敗する」(guardを通過した後、`become: true`の段階で失敗する)に留まり、cert-renewの現状維持を壊す方向ではない。失敗時はYoshinobuの手作業配備が引き続き必要になる。
