## AC2 — 外部到達性に関係しうる記録の有無

**結論: 06:00–06:15 JST の窓に、WAN / uplink / 名前解決 / リンク断を示す記録は「見つからなかった」。一方で、通知の直接原因となった記録は quory 側に「見つかった」。**

### 探索方法と結果

1. 全 job 横断のキーワード掃引(`unreachable|time(d)? ?out|no route to host|dns|resolv|nxdomain|link.?down|no.?carrier|disconnect|gateway|wan|uplink|dhcp|ping:|icmp|down/down`、大文字小文字無視、窓全体、limit=200)がヒットした6ストリームを確認した。内容は次の通りで、いずれも外部到達性の異常を示すものではない:
   - `pve-nodes/pve2`: `sshd-session` の切断ログ2件、`user=recovery-exec` による正常なセッション終了
   - `sophos-fw/sophos-fw`: DHCP リース更新ログ1件(内部 LAN のリース、WAN 障害と無関係)
   - `ubuntu-nodes/ansy`: incident_sync playbook(定期同期)の実行ログ
   - `ubuntu-nodes/quory`: 後述のサービス再起動群(`systemd-resolved` の再起動含むが、これは再起動シーケンスの一部で DNS 障害の兆候ではない)
   - `network-devices/u7-1f`, `u7-2f`: 同一クライアント MAC の Wi-Fi ローミング(`AP-STA-DISCONNECTED` / 再接続)。窓の前後にも同種のイベントが継続しており、この窓に固有の異常ではない

2. `sophos-fw` job の窓内全件(50件上限)を別途確認したところ結果は上記の DHCP レコード1件のみで、他に何も無かった(=空queryではなく、実際に少ない)。

3. quory の journal(`job=ubuntu-nodes, host=quory`、キーワード無し、`21:06:30Z`–`21:07:40Z`)を確認したところ、以下の順序を確認した:
   - `21:06:58Z` `apt-daily-upgrade.service` 開始
   - `21:07:07Z` `systemd[1] Received SIGRTMIN+25 from PID 97174 (kill)` → `systemd[1] Reexecuting`(systemd の daemon-reexec)
   - `21:07:14Z` 前後、`chrony` / `corosync-qnetd` / `cron` / `multipathd` / `fwupd` / `ModemManager` / `polkit` / **`recovery-probe.service`** など多数のサービスが一斉に Stop→Start(reexec に伴う再起動)。`recovery-probe.service` は「6d 3h 6min 46.864s wall clock time」稼働していたと記録されており、直前まで継続稼働していたプロセスが reexec で入れ替わったことを示す。
   - `recovery-probe` の新プロセス(pid 97366)の最初のログ行が `2026-07-29T06:07:14+09:00 EXTERNAL unreachable (ISP または FW 断) — 監視のみ、発火しない`。プロセス起動直後・1回目の probe サイクルでの判定。
   - 次の probe サイクル(60秒後、`06:08:15+09:00`)で成功し、`NOTIFY queued: [warning] [recovery-probe] 外部到達性の回復` を記録。

これは `external_reachable()`(`roles/recovery_probe/files/recovery-probe.py:107-118`)が1サンプルの成否だけで判定する実装(閾値無し)であることと整合する。**観測された「約1分で回復」という warning は、systemd の daemon-reexec によって `recovery-probe.service` が再起動し、再起動直後・最初の1サイクルの HEAD リクエストが(理由は特定できないが)失敗し、次のサイクルで成功した、という単発サンプルの揺らぎで説明できる。** sophos-fw / network-devices / pve-nodes のいずれにも、この時刻帯に対応する WAN 障害・リンク断の記録は無い。

daemon-reexec を引き起こした直接のトリガー(`PID 97174 (kill)` が何のプロセスか)までは特定していない。`apt-daily-upgrade.service` の直後というタイミングから unattended-upgrades による systemd パッケージ更新後の `systemctl daemon-reexec` 相当の可能性が高いが、これは推測であり実測ではない。**未解決事項**として扱う(必要ならさらに `dpkg.log` 相当の記録を追う余地があるが、今回の受入条件の範囲外と判断し停止した)。

- daemon-reexec の直接トリガー(`PID 97174`)の正体は未特定。unattended-upgrades 起因の可能性が高いが推測。
- pve1 が当該時刻に稼働していたかどうかは未確認(平日シャットダウン運用と整合はしているが、本調査では直接確認していない)。
