# requirement — Slack/Codex から Loki 横断ログを調査できるようにする

Tier 4(軸A=4 / 軸B は Tier 3/4 のため `+R` なし)。調査段階は `2026-07-29_001_measurement.md` で完了済み。

## 1. 問題定義

recovery-probe や Slack 起点で異常の連絡を受けたとき、**Codex は Loki を引けない**。現在 Codex が持つ調査手段は各ホストの `systemctl status` / `journalctl`(`roles/recovery_exec/templates/recovery-investigate-dispatch.sh.j2`)と Proxmox の read-only check(同 `-pve.sh.j2`)、reports、Semaphore に限られ、いずれも**単一ホストの、単一 unit の、相対時刻の窓**しか見られない。

2026-07-29 06:07 JST の「外部到達性の回復」warning では、決定的な証拠(quory の systemd daemon-reexec と recovery-probe.service の再起動)は Loki の `job=ubuntu-nodes, host=quory` にあった。人間が scratch playbook を書いて初めて到達できた。**Loki には答えがあるのに、Codex からは構造的に見えない**状態である。

## 2. ゴール

Slack から Codex へ「いつ頃、何が記録されているか」を尋ねると、Codex が Loki を横断して引き、要約して返せるようにする。過去の任意の時刻を指定できること。

## 3. 非ゴール

- **自由文字列によるログ本文フィルタ(grep 相当)** — 初版に含めない。job / 時刻 / level の絞り込みで足りるかを実運用で見てから判断する。
- **recovery-io の Slack 投稿分割**(`roles/recovery_io/templates/recovery-io.py.j2:97` の 3800 文字打ち切り)— 別案件。認可層の変更であり risk クラスが異なる(2026-07-29 Yoshinobu 判断)。
- **recovery-probe の誤検知修正** — 別案件として起票済み(2026-07-29 Yoshinobu 判断)。
- ログを quory 等へステージングしてから絞る経路 — 採らない。Loki のサーバサイドフィルタで完結させる。
- 復旧アクションの追加 — read-only 調査のみ(`AR-024`)。

## 4. ユーザーストーリー

Yoshinobu として、外部断や障害の連絡を受けたとき、Slack で `@Homelab 今朝6時頃のログを見て` と頼むだけで、Codex が Loki を横断して当該時刻の記録を調べ、異常の有無を日本語で返してほしい。scratch playbook を人が書く工程を挟まずに済ませたい。

## 5. 要件

### P0

**R1. 2つの named check を monnie 経路へ追加する。**

| check | arity | parameter |
|---|---|---|
| `loki-count <since> <window>` | 固定2 | — |
| `loki-window <job> <since> <window> <level>` | 固定4 | — |

- `<since>`: `YYYY-MM-DDTHH:MM`(分精度)。**JST 固定解釈**とし、実行ホストの TZ 設定に依存させない。
- `<window>`: `loki-count` は `5m|10m|15m|30m|1h|3h|6h|12h|24h`、`loki-window` は `5m|10m|15m|30m|1h`。列挙のみ。
- `<job>`: `unifi|network-devices|pve-nodes|sophos-fw|ubuntu-nodes`。列挙のみ。
- `<level>`: `any|error|warning|info`。**`any` は必須指定**(省略可の任意引数にしない — arity を固定するため)。

**R2. `loki-count` は job / host / level 別の件数だけを返す。**
`sum by (job, host, level) (count_over_time({job=~".+"}[<window>]))` 相当。**level ラベルが存在しない系列を、存在して空である系列と区別して表示する**(実測で `network-devices` の 2 host が該当し、15分で 343 行=全体の3分の1を占めた)。

**R3. `loki-window` は `<level>` が `any` のとき level ラベルを selector に入れない。**
`{job="...", level=~"..."}` で絞ると**ラベル無しの行が黙って消える**。`any` は「level で絞らない」であって「全 level を列挙する」ではない。

**R4. 出力量を 3 点で固定する。** Loki への `limit`、返す行数、1 行の長さ。**dispatch を正本、wrapper を mirror** とする(`AR-047` と同じ規律)。実測に基づく初期値は `limit=300` / 300 行 / 300 文字とする。

**R5. quory 側 wrapper を一次 filter、monnie 側 dispatch を権限の本 gate とし、dispatch が独立に再 parse・再検証する。** 検証済み operand だけを位置で組み立て、`eval` と shell 再解釈を行わない(`AR-046` / `AR-048` / `AR-088` と同じ規律)。

**R6. Codex への説明(AGENTS.md)を同期する**(`AR-028`)。**この check が返すのは monnie の状態ではなく homelab 全体の集約ログである**旨を明記する。2 段構え(まず `loki-count` で当たりをつけ、次に `loki-window` で本文)を手順として書く。

**R7. Policy を改訂する。** 逐語案は §9。

### P1

**R8. `docs/ai/context/system/autonomous-recovery.md` を同期する。** 現行の表は monnie を「target 内の許可 service を扱う」と記述しており、homelab 全体のログ参照点になる事実が落ちる。

### P2

**R9. `loki-count` の系列数に上限を設ける**(実測 11 系列。将来 job/host が増えたときの保険)。

## 6. 成功指標

2026-07-29 06:07 JST の事象について、**Slack から Codex に尋ねるだけで**、人が scratch playbook を書いた場合と同じ結論(外部断ではなく recovery-probe.service の再起動起因)へ到達できること。

## 7. 受入条件

**AC1(count の基本動作)**
Given monnie の Loki に 2026-07-29 06:00–06:15 JST のデータが存在する
When `homelab-investigate-monnie loki-count 2026-07-29T06:00 15m` を実行する
Then 終了コード `0`、job / host / level 別の件数が表形式で出力され、**level ラベル無しの系列がそれと分かる形で含まれる**。出力は 50 行以内。

**AC2(window の基本動作)**
Given 同上
When `homelab-investigate-monnie loki-window ubuntu-nodes 2026-07-29T06:00 15m any` を実行する
Then 終了コード `0`、当該窓の quory の journal 行が時刻昇順で出力され、**行数が R4 の上限を超えない**。`recovery-probe` の `EXTERNAL unreachable` 行が含まれる。

**AC3(level=any でラベル無し行が消えない)**
Given `network-devices` job に level ラベルの無い行が存在する
When `homelab-investigate-monnie loki-window network-devices <該当窓> any` を実行する
Then それらの行が**出力に含まれる**。同じ窓に `<level>=info` を指定した場合は含まれない。

**AC4(不正 parameter の拒否)**
Given 任意
When arity 違い / 列挙外の job・window・level / 書式違反の since / 余分なトークン / shell メタ文字 / 改行を含む値を渡す
Then **wrapper 側と dispatch 側の双方が独立に**拒否し、終了コード非 `0`、`denied:` で始まるメッセージを stderr へ出す。**Loki への問い合わせも `date` の実行も発生しない**。

**AC5(TZ 非依存)**
Given monnie の TZ 設定が JST 以外であっても
When 同じ `<since>` を渡す
Then 同一の時間範囲が問い合わせられる。

**AC6(既存 check の非退行)**
Given 既存の monnie / authy 向け check(`status`、`journal-*`、`loki-health` 等)
When それぞれを実行する
Then 変更前と同じ出力・終了コードを返す。**引数機構の新設が既存の無引数 check を壊していない**こと。

**AC7(Codex 経路の通し)**
Given recovery-io 経由で Slack から依頼する
When 06:07 JST 前後の調査を日本語で依頼する
Then Codex が `loki-count` → `loki-window` の順に呼び、日本語の要約を Slack へ返す。**execpolicy の default deny に阻まれない**こと。

## 11. オープンクエスチョン

- `loki-window` の 300 行上限が実運用で足りるか。実測では job 絞り 15 分で最大 364 行(quory、reexec の異常時)であり、**平常時は収まるが異常時は切れうる**。切れたことが分かる出力にする必要がある(Implementer の裁量ではなく AC2 の「上限を超えない」に含める)。
- 自由文字列 filter の要否。初版の運用で判断する。
