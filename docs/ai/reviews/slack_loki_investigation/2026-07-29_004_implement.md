## R1〜R8の対応

**R1(2つのnamed check、固定arity)**: `recovery-investigate-dispatch.sh.j2`に`loki-count|loki-count\ *)`と`loki-window|loki-window\ *)`の2 case armを追加。`read -r ... extra <<<"$cmd"`で宣言した個数を超えるtokenを`extra`へ吸収し、非空なら`deny`(arity固定)。`<since>`はbash正規表現`^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}$`、`<window>`/`<job>`/`<level>`は`case`の列挙一致で検証。`homelab-investigate.sh.j2`側も同じ規約(`argc==3`/`argc==5`)で先に検証する。

**R2(loki-countの件数、level無し系列の区別)**: `recovery-loki-helper`の`cmd_count()`が`sum by (job, host, level) (count_over_time({job=~".+"}[<window>]))`を発行し(requirement記載のクエリと文字列一致)、Lokiが返す`metric`辞書に`"level"`キーが存在するかどうかで判定する。存在しなければ`(no level label)`、存在して空文字列なら`(empty)`、存在すればその値、の3値を区別して表示する。mockしたLoki応答(absent-level / empty-string-level / normal-levelの3パターン混在)で単体テスト済み(下記「自己検証」参照)。

**R3(anyはlevelをselectorへ入れない)**: `cmd_window()`で`level == "any"`のときだけ`{job="<job>"}`、それ以外は`{job="<job>", level="<level>"}`を組み立てる。

**R4(出力量を3点で固定、dispatchが正本・wrapperがmirror)**: `recovery-loki-helper`に`QUERY_LIMIT=300`(Lokiへの`limit`)、`MAX_LINES=300`(stdout行数)、`MAX_LINE_LENGTH=300`(1行の文字数)を定数として持たせた。AR-047の「mirror」は実際にはPVE系の先例で「parameter検証(形式・範囲・allowlist)をwrapperも同じ規約で行う」ことを指し、出力量の実値(limit等)はwrapper側には元々存在しない(wrapperはLokiへ問い合わせないため)。このためwrapper側は3つの数値を持たず、`since`/`window`/`job`/`level`の検証規約をdispatchと同一にすることでmirrorしている。数値そのものの正本は`recovery-loki-helper`の定数(dispatchから呼ばれる実体)。

**R5(wrapperは一次filter、dispatchが本gate、独立re-parse、eval/shell再解釈なし)**: dispatch側は`SSH_ORIGINAL_COMMAND`を`read`で分解し検証した後、`exec /usr/local/sbin/recovery-loki-helper count "$since" "$window"`のようにargvへ位置渡しする(`eval`や文字列連結でのshell再実行は無い)。wrapper側も同様に検証後`run_remote "$check $p1 $p2"`で1本のSSHコマンド文字列を組むが、これは検証済みoperandの結合であり、dispatch側は届いた文字列を独立に再parse・再検証してから初めて動く。シェルメタ文字(`$(id)`等)を含む`since`を注入するテストでは、正規表現不一致により`date`にもLokiにも到達せず`denied:`で拒否されることを確認済み(下記参照)。

**R6(AGENTS.md同期)**: `AGENTS.md.j2`のmonnie sectionへ`loki-count`/`loki-window`の使用法を追加。「monnie自身の状態ではなくhomelab全体で収集済みの集約ログである」旨、および「まず`loki-count`で当たりをつけ、次に`loki-window`で本文」という2段構えの手順を明記した。

**R7(Policy改訂)**: requirement §9の逐語案をそのまま適用した。AR-026の追記、AR-095〜AR-101の新設節(`### Report / Semaphore調査`の直前)、変更履歴への1行追加。適用前にAR-095〜AR-101が未使用であることを`grep -o "AR-[0-9]\{3\}"`で自分でも再確認し(既存最大値AR-094、次の空きAR-095から)、適用後も`<!-- AR-XXX -->`アンカー行に重複が無いことを確認した。**逐語指定箇所は文言を一切変更していない。**

**R8(Context同期、P1)**: `docs/ai/context/system/autonomous-recovery.md`の対象テーブルへ「Loki横断ログ調査対象 | `monnie` | homelab全体で収集済みの集約ログ(job/host問わず)をLoki経由で参照する起点。target自身のログに限らない」の1行を追加した。

## 未決定だった1件(JSON整形処理の置き場)の判断

requirement §8が挙げた判断材料に基づき、**JSON整形処理(Lokiへの問い合わせ+応答parse+出力整形)を新規のpython3 helper `roles/recovery_exec/files/recovery-loki-helper`として実装し、`ansible.builtin.copy`でJinja2化せずに配備する**ことにした。理由:

1. `jq`の有無は未確認、`python3`はAnsible管理対象host全てに存在が保証されている(requirement記載の前提をそのまま採用)。
2. 既存roleに`recovery-reports-helper`(bash、`files/`配下、`copy`で配備、privileged側で再検証)という「別ファイルのhelperをprivileged側に置く」前例があり、今回はその形をpythonに置き換えた形。
3. Jinja2 → bashのcase arm → 整形処理という多層エスケープは本リポジトリで過去4連敗している失敗class(Alloy Phase 2)。`files/`配下は`copy`で配備されJinja2render自体を経由しないため、この失敗classを構造的に避けられる。dispatch側(`.j2`)が触るのは「検証済みoperandをargvとして渡す1行のexec」だけで、JSON構造やLogQLクエリ文字列の組み立てはJinja2の外(pythonの中)で完結する。
4. level無し系列の判定(`metric`辞書に`"level"`キーが存在するか)はJSON構造を型で扱える言語でないと安全に書けない(bash/jqのテキストマッチでは「キー不在」と「値が空文字列」を確実に区別するのが難しい)。

この判断による副次的な発見: JSTはDSTを持たない固定UTC+9オフセットであるため、`zoneinfo.ZoneInfo("Asia/Tokyo")`(IANA tzdataデータベースに依存)ではなく`datetime.timezone(timedelta(hours=9))`(stdlibのみ、外部データファイル不要)を採用した。当初zoneinfoで実装していたが、monnieのtzdataパッケージの有無を確認する手段が無いことに気づき、依存そのものを無くす方向へ書き直した(実装記録として残す。この変更にAC5の結果差は無い — 下記TZ非依存の自己検証は書き直し後のコードで再実行し、同じ結果を確認済み)。

## 自己検証で確認したこと

すべてscratchディレクトリで実施。実host・実ネットワークへは一切接続していない。

1. **`recovery-loki-helper`の構文**: `python3 -m py_compile`でエラー無し。
2. **引数検証の分岐(deny系)**: サブプロセスとして実行し、arity違反・sinceの書式違反・window/job/levelの列挙外・未知subcommand・subcommand省略の7パターンすべてが`denied:`prefix + 非0終了で即座に(HTTP接続を試みず)拒否されることを確認した。
3. **JSON整形ロジック**: Loki応答をmockして`cmd_count`/`cmd_window`を直接呼び出し、以下を確認した。
   - levelラベル「不在」「存在して空文字列」「存在して通常値」の3パターンが出力上で異なる表記(`(no level label)` / `(empty)` / 値そのもの)になること(R2)。
   - `loki-count`のLokiクエリ文字列とtimeパラメータがrequirement記載のクエリと一致すること。
   - `loki-window`で複数streamにまたがるentryがtimestamp昇順にmergeされて出力されること(AC2の時刻昇順要件)。
   - 1行が300文字を超える場合、ちょうど300文字(末尾`...`込み)に切り詰められること(R4)。
   - 300件を超えるentryが一致した場合、`QUERY_LIMIT+1`(301)を要求してoverflowを検出し、実際の出力は先頭299件+切り詰め通知1行の**ちょうど300行**に収まること(オープンクエスチョンOQ1への対応、AC2の「上限を超えない」を満たす形)。
4. **TZ非依存(AC5)**: プロセスの`TZ`環境変数を`UTC`/`America/New_York`/`Asia/Tokyo`に変えて同じ`<since>`を渡し、変換後のUTC時刻(RFC3339)が常に同一であることを確認した。
5. **Jinja2テンプレートの描画**: `ansible.builtin.template`モジュールを実際に使う scratch playbook(`hosts: localhost`, `connection: local`)で、`recovery_exec/defaults/main.yml`の実際の`recovery_exec_targets`(authy/monnie)を使って`recovery-investigate-dispatch.sh.j2`・`homelab-investigate.sh.j2`・`AGENTS.md.j2`をAnsibleの実テンプレートエンジンで描画した。renderされた4ファイル全てが`bash -n`で構文エラー無しであることを確認した(monnie側はloki armを含む236行、authy側はloki armを含まない126行 — `'loki' in investigate_services`によるgateが意図通り機能していることも同時に確認)。
6. **wrapper/dispatchの検証内容の一致(R5)**: renderしたdispatch scriptを`SSH_ORIGINAL_COMMAND`環境変数経由で、renderしたwrapper scriptをCLI引数経由で、それぞれ`/usr/local/sbin/recovery-loki-helper`と`ssh`をfakebin(argvをechoするだけのstub)に差し替えて実行した。
   - 正常系(`loki-count 2026-07-29T06:00 15m`、`loki-window ubuntu-nodes 2026-07-29T06:00 15m any`)で、wrapperが組み立てるSSHコマンド文字列と、dispatchがそれを`read`で分解した結果が一致することを確認した。
   - 異常系(arity違反、sinceの書式違反、window/job/levelの列挙外、shellメタ文字`$(id)`を含むsince)で、wrapper側・dispatch側の**両方**が独立に`denied:`で拒否し、helper(=Loki問い合わせの入口)が一切呼ばれていないことをfakebin側の呼び出しログの有無で確認した(AC4)。
   - `since`に`$(id)`を混入させたケースでは、正規表現不一致により「invalid since」で拒否され、コマンド置換は一切実行されなかった(evalしていないことの直接的な確認)。
7. **既存check(AC6)への非退行**: renderしたdispatch/wrapperへ既存の無引数check(`status`、`loki`のようなservice check)を渡し、変更前と同一のSSHコマンド文字列・同一のdispatch分岐(literal case match)になることを確認した。**唯一の挙動変化**: wrapper側が以前は`$2`以降の余分な引数を黙って無視していたのに対し、変更後は`argc`厳格化により`denied: invalid parameter count`で明示的に拒否するようになった(dispatch側は変更前から暗黙に同等の拒否をしていた — 全文字列一致のcase patternのため、末尾に余分なtokenが付くと元々どの分岐にもmatchせず`denied: unknown command`だった)。正常系(1引数ちょうど)の出力・終了コードは不変。
8. **AR番号の重複無し**: `docs/ai/policies/autonomous_recovery_policy.md`の`<!-- AR-XXX -->`アンカー行を全件抽出し、適用後も重複が無いことを確認した(AR-095〜AR-101が新規、他は変更していない)。
9. **IPアドレス・時刻表記**: 変更した全ファイルの差分・新規ファイルにIPv4リテラルが含まれないことを`grep`で確認した(Lokiへの接続先は`localhost:3100`とホスト名で記述)。`recovery-loki-helper`が出力するtimestampは常に`+09:00`固定のJST表記。
