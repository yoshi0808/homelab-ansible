## 検証方法

- `git diff` で全対象ファイルの逐行差分を読んだ。
- Jinja2(python3の`jinja2`パッケージ)で `recovery-investigate-dispatch.sh.j2` / `homelab-investigate.sh.j2` を monnie(loki あり)・authy(loki なし)の実際の `recovery_exec_targets` 変数でレンダリングし、`bash -n` で構文検証した(実装者の自己申告と同じ手法を独立に再実行し、同じ結果を得た)。
- レンダリングした wrapper を fake `ssh`(argv を echo するだけの stub)で、dispatch を `SSH_ORIGINAL_COMMAND` 環境変数経由でそれぞれ単体実行し、正常系・arity違反・enum違反・shellメタ文字(`$(id)`)・改行・extra token・セミコロン注入の各ケースで拒否/許可が要件どおりかを確認した。
- dispatch はさらに「wrapper を経由しない直接呼び出し」(SSH forced command が実際に受け取る形)を模して、wrapper 側の検証を素通りしたと仮定した攻撃入力でも独立に拒否することを確認した(R5/AC4の核心)。
- `recovery-loki-helper` は `python3 -m py_compile` に加え、`loki_get` をモックして `cmd_count` / `cmd_window` を直接呼び出し、level ラベル無し/空文字列/通常値の3値区別、`level=any` 時に selector へ level を含めないこと、1行300文字への切り詰めを確認した。
- Policy差分は requirement §9 の逐語案と `diff` 相当で突き合わせ、AR番号アンカーの重複を `grep -o "AR-[0-9]\{3\}" | sort | uniq -c` で全文書に対し確認した。
- 生成した一時ファイル(`/tmp/dispatch-*.sh` 等)と、実装者の自己検証で `roles/recovery_exec/files/` 配下に残っていた `__pycache__/`(git管理外・.gitignore対象で無害だが作業ツリーには残存していた)は本レビューの過程で削除済み。

## 実ホスト待ちとして残した項目(Tester工程)

- **AC1**: `loki-count`の実出力が実データで「50行以内」かつlevelラベル無し系列を含むことの数値的確認。構造上は満たせる設計だが、実データ量はTester確認が必要。
- **AC2**: 実際のmonnieのLoki APIに対する`loki-window ubuntu-nodes ... any`実行で、`recovery-probe`の`EXTERNAL unreachable`行が実際に含まれ、行数がR4上限を超えないこと。
- **AC3**: `network-devices`の実データでlevelラベル無し行が実際に`any`で含まれ`info`指定で除外されることの実データ確認。
- **AC5**: monnieのTZ設定が実際にJST以外である場合の実機確認(本レビューではロジックの静的・単体確認のみ)。
- **AC7**: recovery-io経由でSlackから依頼した際、Codexが`loki-count`→`loki-window`の順に呼び、execpolicyのdefault denyに阻まれずCodex sandbox内から`homelab-investigate-monnie loki-count ...`を実行できること。execpolicyの構造(コマンド名単位の許可)からは阻まれない可能性が高いと判断できるが、実行確認はしていない。
- **配備**: `target_setup.yml`の新規copy taskが実際に`ansible-playbook`実行でmonnieへ`/usr/local/sbin/recovery-loki-helper`を配置すること、権限・所有者(root:root, 0755)が意図どおりであること。
- **monnieのpython3実行環境**: `urllib.request`のみに依存する設計だが、実際のmonnieのpython3バージョン・SSL/証明書設定(Lokiは`http://localhost:3100`のためTLS絡みの懸念は無いはずだが、実接続そのものの確認)。
