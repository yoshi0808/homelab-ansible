## 2. `unifi_backup_fetch.yml` Play 1のノード選択

### 分類確認

```
$ grep -n "^# tester-gate" playbooks/unifi_backup_fetch.yml
playbooks/unifi_backup_fetch.yml:19:# tester-gate: risk-accepted — tester_mode/tester_gate を廃止。この playbook に
```

**`check-mode-native`ではなく`risk-accepted`**(playbookヘッダ実測)。依頼文が言及した「`check-mode-native`なら`--check`」は本playbookには適用されない。`risk-accepted`は`--check`を渡すとpre_tasksの停止assert(TS-030、playbook本文20〜21行目のコメントで明記)で止まる設計であり、`--check`を付けなかった。

### 実行しなかった理由(Play 2を含むフル実行)

Play 2はCloudKey(UniFi機器)へバックアップ生成APIを叩く非冪等操作であり、`docs/ai/roles/tester.md`「UniFi機器への非冪等操作は着手前に計画をCoordinatorへ提示して承認を得る」に該当する。今回の依頼文は「Play 1のノード選択」を検証対象として明示しており、Play 2の実行(および承認)は依頼の範囲に含まれていないと判断し、フル実行はしなかった。

### 実行内容

Play 1(`roles/proxmox_exec_node`呼び出し、`hosts: proxmox`、`gather_facts: false`、`become: false`、SSH ping probeと`add_host`のみで対象ホストへの変更を一切伴わない)を、playbook本文から逐語コピーしたscratch playbookとして切り出し、**実inventory(実host名pve1/pve2、decoyではない)**に対して実行した。Play 1自体が非破壊的read-only操作(SSH到達性確認+control node側のグルーピング)のみで構成されるため、事前提示は不要と判断した(`docs/ai/roles/tester.md`「読み取り専用の確認...は提示不要」)。

```

```

### 言えること・言えないこと

- **言えること**: restore後の現在の配置は、`prefer<node>`タグと矛盾しない状態になっている。`roles/proxmox_exec_node`および`proxmox_backup_restore_verify`が`prefer<node>`タグを「その名のノードで動いているのが正常」という前提で読む設計(`_brv_preferred_node`ロジック)と、観測された実配置は整合している。
- **言えないこと**: これは**現時点のスナップショット観測**であり、`proxmox_backup_restore_verify.yml`を実行した場合に何が起きるかは推測にとどまる。`verify`タグを持つVM(1000, 101, 211)のうち当月対象になる1台が、`_brv_preferred_node`(タグの指すノード)上で到達可能であればfallbackなしでそのノード上にrestoreされ、2026-07-29のfallback発生時(pve1停止中でpve2へ代替)とは異なる経路を通ることが**設計から**推測されるが、実行して確認したわけではない(推測として明記)。
- 8月分の対象VM選定ロジック(`(month-1) % len`)を本セッションでは再計算していない(前回記録のQ2相当の確認は今回のスコープに含めていないため未実施)。

## 4. 未実施・pve1が落ちる前に追加で取っておくべき観測

- **`unifi_backup_fetch.yml`のPlay 2を含むフル実行(両ノード健全時)**: 未実施。承認があれば、実行すると実バックアップ生成・Synology保存・世代ローテーション(既存バックアップの削除)・Slack通知(`skip_notifications=true`必須)が発生する非冪等操作になる。ノード選択自体は本記録§2で実機確認済みのため、フル実行の価値は「pve1が選定された状態でのPhase 2以降が両ノード健全時にも正常動作するか」の確認に限られる。
- **`proxmox_backup_restore_verify.yml`の両ノード健全時実行**: 指示により未実施。実行すればAC4(`proxmox_exec_node_selection` requirement、2026-07-29記録で「pve1起動時のフォロー」と記載されていた項目)が消化できるが、risk-acceptedの実restore操作であり、Yoshinobu判断が要る。
- **8月分対象VM(`(month-1) % len`)の再計算**: 上記restore実行時に必要になるが、観測だけなら安全に先取りできる(read-only)。今回のスコープでは行っていない。
- **weekly_full系(patch)の両ノード健全時の自然発火観測**: 2026-07-30記録のAC5残存事項と同じ。次の平日/週末スケジュールでの自然観測が引き続き最終確認になる。
