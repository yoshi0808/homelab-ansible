# requirement: 保持した conffile を特定して通知に出す

起案: Coordinator / 2026-08-22 / 分割元: `docs/ai/reviews/ubuntu_vm_apply_conffile_prompt/`

**着手時期は未定。** 先行案件で `--force-confold` が入り、無期限停止という危険は消えている。本件は**報告の質**を上げるものである。

## 1. 問題定義

`roles/ubuntu_vm_full_upgrade/tasks/apply.yml` は `--force-confold` で conffile を保持するが、**どのファイルを保持したかを誰も知らない。** 現在の通知は「保持する設定で適用した」という静的な一文だけである。

保持されたということは、**配布元が更新版を出したのに、この環境の設定がそれを受け取っていない**ことを意味する。積み重なると、いつか設定形式が実際に非互換になったときに気づけない。

## 2. 先行案件で分かった、届かなかったこと

**3ラウンド実装し、レビューを3本(`../ubuntu_vm_apply_conffile_prompt/2026-08-22_003〜005_review.md`)通した結果、apply 前後のスナップショット比較という方式は原理的に届かないと確定した。**

| # | 届かなかったもの | 出典 |
|---|---|---|
| 1 | **旧版を保持した後に postinst がそのファイルを変更した**場合と、**新既定値を適用した後に postinst が第三の値を書いた**場合を、前後の最終状態だけでは区別できない。**これが天井である** | 005 finding 2 |
| 2 | 新規導入 package が、既に存在する通常ファイルを conffile として取り込む経路。pre 側に baseline が作れない | 005 finding 1 |
| 3 | `${Conffiles}` の hash が `newconffile` 等の内部 marker のとき、digest 比較そのものが成立しない | 005 finding 3 |
| 4 | conffile entry を1件も持たない package が snapshot から消える | 004 finding 2 |
| 5 | pre 時点の現物 digest を持たないと「局所版が残った」を証明できない | 004 finding 3 |

**次の試みは、ファイルの状態を比べるのではなく、dpkg の判断そのものを観測する方式で設計すること。** 1〜5 は状態比較に固有の限界であり、方式を変えなければ同じ順序で再び現れる。

## 3. 引き継げるもの

- `${Conffiles}` の parse と、32桁hex / 既知marker / 未知値の分類(005 finding 3 に仕様がある)
- 判定不能を `indeterminate` として明示分類し fail-closed にする構造(004 で妥当と判定された)
- **`--force-confold` 発火時に dpkg が recorded hash をどう更新するかは、Reviewer が dpkg の source で裏付けている**(005 の参照リンク)

## 4. 満たすべきこと(先行案件から引き継ぐ)

- **証明できない「該当なし」を出さない。** 保持されたのに「保持なし」と述べる経路を作らない。これが分割の直接の理由である
- **判定不能で apply を中断しない。** 判定は報告系であり、成功した apply の reboot と復帰確認を止めてよい理由にならない(005 finding 1 / 先行案件 G1)
- **自由文の解析に依存しない。** 実出力は日本語だった実績がある(2026-08-22 の `up.conf`)

## 5. 未決

- **失敗の頻度と報告の精度の釣り合い。** 厳密にするほど判定不能が増え、緩めるほど偽陰性が増える。どちらへ倒すかは着手時に決める
- そもそも保持の検出が要るのか。**「配布元が新版を出した conffile がある」までで足りるなら、保持されたかどうかを判定する必要は無い**。この線で足りるかを先に問うこと
