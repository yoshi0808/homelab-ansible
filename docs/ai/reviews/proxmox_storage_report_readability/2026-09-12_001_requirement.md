# ストレージ月次点検レポートの可読性改善

状態: 要件確定。2026-09-12のYoshinobuとの対話を反映。

## 1. 問題定義

現行の正式レポートは、ZFS scrub・vdev・NVMeの内部JSONを本文へ直接出力しており、人が結論、対応要否、前回差分を読み取れない。

## 2. ゴール

ストレージ知識やJSON構造を知らなくても、冒頭で対応要否を判断でき、必要ならhost別の根拠へ読み進められる日本語レポートにする。

## 3. 非ゴール

収集項目、閾値、健康判定、JSON正本、保存・Notion公開・scheduleの契約は変更しない。Notionページの構造やデータベース化も行わない。

## 4. ユーザーストーリー

管理者はNotionまたは保存Markdownを開き、まず結論と対応事項を読み、その後にZFS/NVMeの値と前回差分を確認する。

## 5. 要件

### P0 / Must

- 冒頭に日本語の総合判定、収集成否、対応事項を置く。
- hostごとにZFS状態、最終scrub、vdev error、NVMe温度・消耗・予備領域・media error・error-log累積と増減をラベル付きで示す。
- 内部JSONを本文へ直接出力しない。内部状態語は日本語の説明と併記または翻訳する。
- 初回基準、前回比較、交換・追加、counter reset、比較不能を区別する。
- report ID、serial、device path、比較元は末尾の詳細情報へ置く。
- SlackはJSON配列ではなく、日本語の結論、最大3件の注意事項、Notionリンクを送る。

### P1 / Should

- 正常時は「異常なし」と明示し、読者に異常項目の探索を要求しない。
- 既存JSON schemaと判定結果を変えず、過去reportのreplayでも新しい本文を生成できる。

## 6. 成功指標・受入条件

- AC1: Given 正常な初回report、When 本文生成、Then 冒頭に「異常は見つかりませんでした」、初回比較である説明、ラベル付きZFS/NVMe値があり、JSON objectのdumpがない。
- AC2: Given error-logが前回より増えたreport、When 本文と短報を生成、Then 対象host/deviceと増加数、要確認であることが日本語で分かる。
- AC3: Given 収集不能・履歴破損・ZFS/NVMe異常、When 本文生成、Then 判定不能または異常の理由を隠さず、対応事項の先頭側に表示する。
- AC4: Given 保存済み旧report、When replay、Then JSONを変更せず新形式のMarkdown/Notion本文とSlack短報を生成できる。
- AC5: Given native checkまたは通知抑止、When 検証、Then既存どおり本番Notion/Slackへ送信せずrc=0となる。

## 7. オープンクエスチョン

なし。表示文言の細部は実装・レビューで調整する。
