## AC4: 保存済み旧reportのreplay

要件: 「Given 保存済み旧report、When replay、Then JSONを変更せず新形式のMarkdown/Notion本文とSlack短報を生成できる」。

### 旧reportの素性

`make_old_report.py`で手作業構成した`report_id=20260601T090000000000+0900-aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa`（collected_at=2026-06-01T09:00:00+09:00、month=2026-06）。`build_report()`の出力schema（`roles/proxmox_storage_monthly/module_utils/storage_monthly.py`）に手で適合させたJSONで、**本Testerセッション中のcollect/archiveでは一切生成していない** — `ansible-playbook`実行前にファイルとして先に配置し、`operation=replay`でのみ読ませた。本案件の非ゴール「JSON schema不変」の通り現行schemaと同一のため、旧schema固有の差分は存在しない（AC4もJSON schema変更を要求していない）。

### 実施内容

```
ansible-playbook -i <decoy inventory> playbooks/proxmox_storage_monthly.yml \
  -e proxmox_storage_monthly_operation=replay \
  -e proxmox_storage_monthly_report_id=<上記ID> \
  -e proxmox_storage_monthly_report_dir=<scratch>/reports \
  -e skip_notifications=true
```
（このケースはAC4の生成物確認が目的で、通知抑止経路自体はAC5側で別途確認するため`skip_notifications=true`を付けて切り分けた。）

decoy inventoryは`proxmox`グループに`decoy-storage-host`（`ansible_connection: local`）を1台のみ持ち、`operation=replay`では`storage_monthly_targets`グループが空になり実収集は走らない（play2は`skipping: no hosts matched`）。

## AC5: `--check`単独（`skip_notifications`なし）での送信抑止

要件: 「Given native checkまたは通知抑止、When 検証、Then既存どおり本番Notion/Slackへ送信せずrc=0となる」。

`_007`は通常実行に常に`skip_notifications=true`を付けており、D5も`--check`と`skip_notifications=true`の同時使用1ケースのみだった。今回は**`--check`のみを与え`skip_notifications`を一切渡さず**（デフォルトfalse）、かつ`CLAUDECODE`を外して実行し、`ansible_check_mode`単体の効果を切り分けた。

### 実施内容

```
env -u CLAUDECODE ansible-playbook -i <decoy inventory> playbooks/proxmox_storage_monthly.yml \
  --check \
  -e proxmox_storage_monthly_operation=replay \
  -e proxmox_storage_monthly_report_id=<AC4と同じ旧report ID> \
  -e proxmox_storage_monthly_report_dir=<scratch>/ac5_reports \
  -e proxmox_storage_monthly_notion_token_file=/tmp/nonexistent-decoy-token \
  -e proxmox_storage_monthly_notion_parent=decoy-parent-not-real
```

`operation`は`replay`のまま使った。理由: `report.yml`の通知抑止機構（`storage_notion`モジュールの`suppress`引数と`module.check_mode`、`common_slack/tasks/notify.yml`の3trigger）はcollect/replayどちらの経路でも同一のreport段で実行される（`collect.yml`は通知に一切関与しない）。collect段を経由させると`become: true`のsudo到達性という別の問題が入るため、通知抑止機構の検証に無関係な変数を持ち込まないためにreplayへ寄せた。token_fileとNotion parentは実際には存在しない値を与えている（`--check`のcheck_mode gateがトークンIOより先に効くことを確認する主目的とは別に、万一の防御層として）。

### 結果

- **rc=0を確認**（`echo RC=$?`で明示的に取得、`RC=0`）。
- 通知抑止機構内の3trigger値を`common_slack`の`[suppressed]`デバッグ出力で直接観測した。

  ```
  trigger1 skip_notifications      : False
  trigger2 ansible_check_mode      : True
  trigger3 agent_session_detected  : False
  ```

  `skip_notifications`を渡していない（trigger1=False）、`CLAUDECODE`を外した（trigger3=False）状態で`trigger2 ansible_check_mode=True`のみが立ち、それだけで抑止されたことを確認した。これが今回埋めた「`--check`単独での切り分け」にあたる。
- `storage_notion`タスク（`Publish archived monthly report unless notifications are suppressed`）の戻り値は`{"changed": false, "publication": "suppressed", "url": ""}`。`storage_notion.py`の`main()`は`if module.check_mode or module.params["suppress"]:`で即`exit_json`する経路であり、存在しない`token_file`（`/tmp/nonexistent-decoy-token`）を開こうとした形跡（エラー）が一切無かったことから、トークン読み取り・HTTP IOへ到達する前に止まったことを確認できる。
- `common_slack`の`Send Slack notification`タスクは`skipping`（条件不成立）で、その手前の`Load Slack variables`（`vars/slack.yml`読込＝実webhook URL取得）も`skipping`。実webhookを一切読み込んでいないことを実行ログで確認した。
- `ac5_reports/`配下は実行前後でファイルが増えておらず（既存の旧reportファイル1件のみ、md5不変）、`.lock`・`.publication.json`等の新規書込みも発生していない。

**Verdict: PASS**（`--check`単独が`skip_notifications`と独立に送信を抑止しrc=0になることを、他のtriggerをFalseにした状態で切り分けて確認した）

## 未解決事項

- AC4のNotion本文確認は、ソースコード上の`publish()`が`markdown(report)`をそのまま使うという参照による導出であり、実行（チャンク分割処理や実Notion APIへの到達前チェック）による確認ではない。今回のAC4検証はAC4自体がNotion送信を要求しないため範囲外としたが、実行による確認が要る場合は別途、実Client部分だけをスタブ化したpublish()単体呼び出しのfixtureが必要になる。
- AC5の切り分けは`operation=replay`経路で行った。`operation=collect`経路でも`report.yml`のarchive/notion/notify区間は同一コードを通るためAC5の趣旨は満たすと判断したが、`operation=collect`かつ`--check`単独という組み合わせそのものを別途実行してはいない（collect段のbecome/sudo到達性は本案件の対象外）。
