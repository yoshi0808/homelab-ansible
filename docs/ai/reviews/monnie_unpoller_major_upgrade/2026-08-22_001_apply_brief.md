## 0. 結論

**当ててよい。** unpoller の `3.3.4+git → 4.0.0+git` は、メジャー番号が上がっているが**破壊的変更ではない**。上流の 4.0.0 は UNAS Pro 対応の追加(既定 off)とそれに伴うフラグ名の整理で番号が上がっており、既存の設定・メトリクスを壊す変更は 3.4.0〜4.0.0 のどこにも無い。

**ただし、この操作で入るのは unpoller だけではない。** `apt-get -y full-upgrade` はホスト全体に当たり、**grafana 13.1.1 → 13.2.0** と **apparmor 5.0.0~beta1 → 5.0.2** が同時に入り、**再起動する**(`reboot_expected: true`)。注意を向けるべきはむしろこちら側である。

## 1. 押すもの

Semaphore テンプレート **`UN-SAFE:Ubuntu vm full upgrade(Manual)`**、入力3つ。

| 入力 | 値 |
|---|---|
| `dry_run` | `false` |
| `node` | `monnie` |
| `ubuntu_vm_full_upgrade_confirm` | `monnie` |

正本は `roles/semaphore_templates/defaults/main.yml`。`node` と `confirm` が一致しないと着手前に落ちる(`roles/ubuntu_vm_full_upgrade/tasks/main.yml`)。

**`REVIEW_REQUIRED` は適用を止めない。** 適用が拒否されるのは `BLOCKED` と `MAJOR_UPGRADE_DETECTED` だけである(同 main.yml)。つまりこの1枚の人間判断が、そのまま門になっている。

playbook が自動でやること — 適用前に **recovery mute 120分**(monnie は自律復旧の対象なので、apply 中のサービス再起動で誤発火しない)、適用後に `/var/run/reboot-required` を見て再起動と復帰確認。

## 3. unpoller 3.3.4 → 4.0.0 に実際に入るもの

`3.3.4` からは **3.4.0 / 3.4.1 / 3.5.0 / 4.0.0** の4版を飛び越える。GitHub Releases の本文(API で取得)が持っている内容は次のとおり。

| 版 | 日付 | 中身 |
|---|---|---|
| v3.4.0 | 2026-08-07 | **UniFi クライアントライブラリを v5.30.0 へ**、依存更新 |
| v3.4.1 | 2026-08-07 | WAN speedtest の `save_speedtest` トグル追加 |
| v3.5.0 | 2026-08-18 | **input plugin の nil-pointer panic 修復と panic recovery**、alarms endpoint が 400 のとき skip、**`wan_interface_state` に `state` ラベル追加** |
| v4.0.0 | **2026-08-19** | **UNAS Pro 対応(opt-in、既定 off)**、そのフラグを disable→enable へ整理、`AppendMetrics` が SpeedTest とバッチ時刻を落としていた修正 |

### 判定

| 論点 | 判定 | 根拠 |
|---|---|---|
| **設定ファイル形式の非互換** | **無い。** 4.0.0 で名前が変わったフラグは UNAS 用で、**3.x には存在しなかった**(同じ 4.0.0 で新設された機能のフラグ)。既定 off なので `/etc/unpoller/up.conf` に手を入れる必要は無い | 4.0.0 の変更2件が同一リリース内にある |
| **conffile が上書きされるか** | **上書きはされないが、当日ここで停止した。** `DEBIAN_FRONTEND=noninteractive` が抑止するのは **debconf** であって、**dpkg の conffile プロンプトではない**。`up.conf` はローカル変更があったため dpkg が Y/N を尋ね、その stdin は Ansible の SSH セッションにあり誰も答えられなかった。**本ブリーフ作成時のこの行は誤りである** | `2026-08-22_002_result.md` |
| **Prometheus メトリクスが壊れるか** | **壊れない。** 3.4〜4.0 で変わったメトリクスは `wan_interface_state` の**ラベル追加1件だけ**で、repo 正本の dashboard 6本と alert rule 4件が使う **unpoller メトリクス113種のどれにも `wan_interface_state` は含まれていない** | `roles/grafana_provisioning/files/` を全文検索 |
| **alert rule への影響** | 無い。4ルールが見るのは `unpoller_device_port_{receive,transmit}_{dropped,errors}_total` のみ | `files/alerting/unifi-switch-port-errors.yaml` |
| **UniFi コントローラ側の要求版** | **問題なし(適用後に判明)。** CloudKey は **10.5.67** で、4.0.0 は正常に接続した。上流は最低要求版を宣言していない | 適用後の unpoller 起動ログ |

## 6. 壊れたときの戻し方

**unpoller だけを戻す場合** — v3.3.4 の deb が GitHub Releases に残っていることを確認済み(`unpoller_Tux_64-bit.deb`、v3.3.4 タグの asset)。apt リポジトリに旧版が残っているかは**開発側から確かめられない**ので、確実なのは deb を取って `dpkg -i` する経路である。設定は §3 のとおり保持されるので、戻すのはバイナリだけでよい。

**それ以外** — 削除 0件なので、apt 側で失われるものは無い。再起動から戻らない場合は VM 側の操作(Proxmox)になる。

## 7. 未確認 / この経路では確かめられないこと

- **`/etc/unpoller/up.conf` の中身**。Ansible 管理下に無く(repo に template が無い)、read 専用チェックも ExecStart と待受ポートしか返さない。設定は手動管理(Notion の手順書)
- **apt リポジトリに 3.3.4+git が残っているか**。monnie の apt index を読む手段が無い
- **検索で出た2件のうち1件は実在した(適用後に判明)** — 「60 秒のバックグラウンド更新」は実在する。起動ログに `Prometheus scrape cache enabled, refresh interval: 1m0s` が出る。**GitHub Releases の本文に無いことを根拠に判断材料から外したのは誤りだった** — release 本文は挙動の網羅ではない。もう1件「UniFi 9.x 系では動かない」は、CloudKey が 10.5.67 のため当環境では問われない
- **scrape cache が 3.3.4 から在ったのかは未確認。** 4.0.0 で入ったのなら、Prometheus の scrape 間隔(15秒)に対して値の更新が 60 秒になり、**メトリクスの時間分解能が落ちる**。counter の総量は保たれるため alert rule 4本の発火条件は成立したままだが、rate 表示は階段状になる

## 8. 判断が要る点

**unpoller だけ見送りたい場合、この経路では分けられない。** `apt-get -y full-upgrade` はホスト全体に当たるため、外すなら事前に monnie 上で `apt-mark hold unpoller` を打つ必要があり、**それは Semaphore のテンプレートに無い手動操作**である(レポートの `hold` は現在空)。

**推奨は、分けずにそのまま当てること。** 4.0.0 の中身は §3 のとおり小さく、3.5.0 の panic 修復はむしろ入れたい側である。番号が示すほどの変更ではない。
