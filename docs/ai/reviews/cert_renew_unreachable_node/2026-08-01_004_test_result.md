## 0. 検証方針

対象 `playbooks/cert_renew.yml` は `tester-gate: check-mode-native` かつ第1playが `hostname == quory` をassertするため、このansy上では実playbook自体を実行できない(commit前・quory未反映)。実装記録§4の確認とは独立に、自分で構成した decoy inventory と、対象差分の構造(probe 4task + summary Jinjaテンプレート)を再現した最小replica playbookに対して検証した。実host名・実IPは一切使用せず、`ansible_connection=local`(到達可能)と、ローカルの閉ポート(127.0.0.1:1 / :2、`ssh: connect ... Connection refused` を確認済み)を到達不能として使った。`become` 付きで実システムを変更するモジュールは使用していない。

検証成果物一式: `/tmp/claude-1000/-home-yoshi-homelab-ansible/3ff5e873-c9c6-4214-8c93-b95e61e54e55/scratchpad/cert_renew_test/`(inventory 3種、`replica_new.yml`/`replica_old.yml`、`ac4_ac5_summary_compare.yml`、`ac3_fact_check.yml`、各実行の出力ファイル)。このパスは `/tmp` 配下であり本報告の対象パスとしてのみ言及する(リポジトリへは含めていない)。

## 1. AC別判定

### AC1 — 片方到達不能・片方到達可能

**PASS**(実測)。`replica_new.yml` を `inventory.ini`(decoy-a: local / decoy-b: 閉ポート)に対し `serial: 1` で実行。
- decoy-bは `ansible.builtin.ping` 失敗→`UNREACHABLE`→`ignore_unreachable`で継続→`cert_host_unreachable=true`→`meta: end_host`で当該hostのみ後続task省略。
- decoy-aは通常どおり issue_check相当→destructive相当タスクまで到達(`destructive_ran_decoy-a` 生成を確認)。
- cleanup相当play・notify相当playとも実行された(`cleanup_ran` / `notify_ran` 生成)。
- 終了コード: **rc=0**(実測)。
- 後続playから `hostvars['decoy-b'].cert_host_unreachable` を読み、summaryに `WARNING: decoy-b was unreachable...` 行が出力されることを確認(hostvars永続の実測)。

### AC2 — 両方到達不能

**PASS**(実測)。`inventory_both_unreachable.ini`(decoy-a/b とも閉ポート)で同playbookを実行。
- 両hostとも `end_host` で落ち、destructive相当ファイルは一切生成されない(`destructive_ran_*` なし、実測)。
- cleanup相当・notify相当playとも実行(`cleanup_ran` / `notify_ran` 生成)。
- 終了コード: **rc=0**(実測)。

### AC3 — 両方到達可能

**PASS**(実測)。`inventory_all_reachable.ini`(decoy-a/b とも `ansible_connection=local`)で実行。
- `Warn` / `Drop` タスクはともに `skipping`(条件成立せず)。
- issue_check相当・destructive相当タスクとも両hostで到達・実行(`destructive_ran_decoy-a` / `destructive_ran_decoy-b` 生成)。
- 追加で `cert_host_unreachable` の実値を明示的にdebug出力し確認: **`decoy-a: cert_host_unreachable=False`、`decoy-b: cert_host_unreachable=False`**(実測、`ac3_fact_check.yml`)。requirementの「どちらも `false`」を文字列一致でなく実際のPythonブール値として確認した。

### AC4 — 到達不能nodeがある場合のsummary/通知分岐

**PASS**(実測)。`ac4_ac5_summary_compare.yml` で、新テンプレート(host list をdecoy名に置換しただけで本体のJinjaは対象diffと同一)を「decoy-bのみ到達不能」というhostvarsで評価。
- 出力(`new_summary_unreachable.txt`):
  ```
  decoy-a: renewed and deployed
  decoy-b: skipped (host unreachable)
  decoy-c: renewed and deployed
  WARNING: decoy-b was unreachable and its certificate was not renewed.
  CA cleanup: OK
  ```
  - decoy-bの行は `check FAILED` ではなく `skipped (host unreachable)`(実測、`grep -c FAILED` → 0)。
  - `WARNING` を含む(実測、`grep -c WARNING` → 1)。
  - `FAILED` を含まない(実測、0件)。
- 同じ出力から本番と同一の式で計算した `slack_channel` / `slack_status`: **`channel=alerts` / `status=warning`**(実測、debugタスク出力)。AC4の期待値と一致。
- 別途 AC1/AC2 の実行(destructive相当が擬似ステータスを残さないため `issue FAILED` を含む簡略replica)でも、到達不能host分の行が `check FAILED` に落ちず `skipped (host unreachable)` になることは同様に確認済み。

### AC5 — 全host正常時、summaryが変更前とバイト一致

**PASS**(実測)。diff前のテンプレートは `git show HEAD:playbooks/cert_renew.yml` から該当Jinjaブロックを抽出し(このコミットが現在のワーキングツリー差分の親であることは `git diff` の対象ファイルと一致する形で確認済み)、host list以外は無改変のまま `ac4_ac5_summary_compare.yml` の `old_summary` として同一hostvars(全host `cert_needs_renewal/renewed/deployed=true`)で評価した。新テンプレート側は同じhostvarsで `cert_host_unreachable` が全host未定義(`default(false)` 経由でfalse相当)の場合を評価した。
- `diff old_summary.txt new_summary_allok.txt` → 差分なし。
- `md5sum`: 両ファイルとも `04bd173e028761c7f11debee2fa10b03`(バイト一致、実測)。
- 同シナリオの `slack_channel=info` / `slack_status=ok`(実測、debugタスク出力)。

### AC6 — syntax-check / ansible-lint で新規エラーなし

**PASS**(実測)。対象は実ファイル `playbooks/cert_renew.yml`(read-only静的解析のみ、host接続なし)。
- `ansible-playbook -i <ダミーinventory(localhostのみ)> --syntax-check playbooks/cert_renew.yml` → **rc=0**。`quory` / `ansy` / `proxmox` / `monnie` のhost pattern不一致WARNINGのみ(inventory側の話でありplaybookの構文エラーではない)。
- `ansible-lint playbooks/cert_renew.yml` → **rc=2**、`Failed: 63 failure(s)`。`git stash` で変更前の状態に戻し同コマンドを実行したところ、**変更前も同じ `Failed: 63 failure(s)`**。差分は行番号のシフトのみ(追加した34行ぶん、既存指摘行が`+6`ずれた9箇所)で、指摘内容・件数の増減なし。追加した4probe task・summaryテンプレートを指す新規指摘は無い(実測、`diff lint_old.txt lint_new.txt` で内容差分なしを確認)。`git stash pop` 後に `git status` で作業ツリーが元の差分に復元されていることを確認済み。

### AC7 — `--check` 実行時の挙動

**PASS**(実測、decoy replicaでの確認。実playbookそのものへの `--check` はconstraint上不可)。`replica_new.yml` を `inventory.ini`(片方到達不能)に対し `ansible-playbook ... --check` で実行。
- probeタスク(`ansible.builtin.ping`)は `--check` 下でも実際に実行され、到達可能host・到達不能hostとも正しく判定(decoy-bで `UNREACHABLE` → `WARNING` debug出力を確認)。
- destructive相当タグ付きタスク(issue apply相当、cleanup相当のファイル書き込み)は `skipping` となり、`destructive_ran_*` / `cleanup_ran` / `summary_new_output.txt` はいずれも生成されなかった(実測、`ls` で不在確認)。
- 終了コード: **rc=0**(実測)。
- `check-mode-native` の前提(read-only診断は`--check`でも本実行、破壊的操作のみ`not ansible_check_mode`でゲート)を崩していないことを確認した。

## 3. 契約に書かれていない副作用・残存リスク

- **`become: false` の分離効果は未検証。** probeタスクは `become: false` で「SSH到達性」と「sudo正常性」を意図的に分離する設計(実装記録§2)だが、decoy環境では「SSHは通るがsudoが壊れているnode」を安全に再現する手段がなく、この分離が実際に機能するかは静的な設計確認に留まる。
- **`ignore_errors: true` が拾う「unreachable以外の失敗」経路は未検証。** 判定式 `(unreachable) or (is failed)` のうち `is failed` 側(python interpreter不在など、接続はできるがpingモジュール自体が失敗するケース)を再現するdecoyを用意しておらず、この経路は実装記録の説明のみに依拠する。
- **AC7は実playbookでなくreplicaでの確認。** 実際の `playbooks/cert_renew.yml` に対する `--check` 実行は、`hostname == quory` assertとcommit前提により本検証のscope外(requirement OQ2どおり)。追加したprobeタスク自体(`ansible.builtin.ping`、`ansible.builtin.set_fact`、`ansible.builtin.debug`、`ansible.builtin.meta: end_host`)はいずれもcheck-mode対応が明確なmoduleであり、replica上の挙動から実ファイルでも同様に働くと推測されるが、実ファイル上での直接確認ではない。
- **Policy差分(`cert_renew_policy.md` CERT-023)の記述自体は本検証の対象外。** 契約(P0-4)の充足はレビュー工程の役割であり、本test_resultはACとして列挙された6項目相当の技術的挙動(AC1〜AC3、AC6、AC7)とsummary/通知ロジック(AC4、AC5)のみを検証した。
- **`ansible-lint` はplaybook全体に対する実行であり、対象diff以外の役(role側)の既存指摘(var-naming、risky-shell-pipe等)を多数含む。** これらは変更前から存在し、diffの対象ではないため判定に含めていない。

## 4. 未検証事項

- 実ホスト(quory→pve1/pve2)への実際の到達性判定・SSH接続タイムアウトの実測時間(decoyではConnectTimeout=2秒を明示指定したため、実運用でのSSHタイムアウト挙動とは異なる可能性がある)。
- `roles/homelab_cert_renew` 側(issue_check/issue_apply/prepare_ca等)の実装自体は本件の変更対象外であり検証していない。
- CA cleanup(`cleanup` role task)がCA秘密鍵を実際にtmpfsから削除する処理そのものの検証は、本件のdiff範囲外(既存動作)のため実施していない。「cleanup playが実行されること」のみを確認した。

## 5. 結論

AC1〜AC7すべてPASS。実行identityはansyのリポジトリ作業ツリーと `/tmp` 配下に閉じており、実ホストへの接続は一切発生していない。`git status` は着手前と同じ2ファイル(`playbooks/cert_renew.yml` / `docs/ai/policies/cert_renew_policy.md`)の変更のみを保持しており、本検証によるリポジトリ内ファイルの変更はない(本ファイルの新規追加を除く)。
