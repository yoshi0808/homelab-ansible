### What Looks Good

- **P0-1(probe追加)**: `playbooks/cert_renew.yml:129-151`。`ansible.builtin.ping` + `ignore_unreachable: true` + `ignore_errors: true` + `become: false` → `set_fact` → `debug`(WARNING) → `meta: end_host` の4タスク構成は要件の指定通り。
- **技術的主張の独立検証(自己検証)**: 実装記録は「decoyで`rc=4`→`rc=0`を確認した」と主張するのみで根拠のdecoy自体は残していないため、本レビューで独立にdecoy再現した(`/tmp`配下、閉ポート127.0.0.1:1 = 到達不能、`ansible_connection: local` = 到達可能。実host名・実IP不使用)。
  - 両host到達不能・`serial: 1`・task-level `ignore_unreachable`のみ(play-level`ignore_unreachable`なし)の構成で`rc=0`、後続play(cleanup相当・notify相当)とも実行されることを確認した。
  - **これは`roles/proxmox_reachable_nodes`の頭コメントおよびADR-008(`docs/ai/adr/008-proxmox-readonly-check-unreachable-node.md`)が「呼び出し側playにplay-level `ignore_unreachable: true`が無いと`rcが4のまま`になる」と明記しているのと矛盾するように見えたため、特に厳密に検証した。** 結論: 矛盾ではない。ADR-008/`proxmox_reachable_nodes`の前提は`gather_facts: true`による暗黙のfact gathering(task-level `ignore_unreachable`を設定できない)を到達性判定の起点にしているため、play-levelの指定が必須になる。本差分は明示的な`ansible.builtin.ping`タスクに直接`ignore_unreachable: true`を付与しており、この場合はtask-levelの指定だけで十分であることを実測した(host-batch全滅でも`rc=0`)。実装記録の主張は妥当であり、混同のおそれがあった箇所を切り分けられた。
  - 片方到達不能・片方到達可能(AC1相当)の構成で、到達可能host側は後続タスクへ到達し、到達不能host側の`cert_host_unreachable`ファクトが後続playの`hostvars[]`から読めることを確認した(`meta: end_host`後もfactが残る)。
  - `become: false`はplay-levelの`become: true`(`playbooks/cert_renew.yml:114`)を正しく上書きしている。
- **AC5(summary byte一致)**: 到達不能hostが0件のとき、追加した`{% if hostvars[h].cert_host_unreachable ... %}`分岐と末尾の`{% for h in [...] if ... %}`ループが実際に0回転し出力に現れることを、変更前後のテンプレートを同一hostvarsで並べてAnsible上でレンダリングし`assert`で突合、バイト一致を確認した(`trim_blocks`前提の主張どおり)。
- **AC4(summary/通知ロジック)**: `cert_renew.yml:233-236,254-256`で`skipped (host unreachable)`と`WARNING: ...`が既存の`check FAILED`分岐より先に評価されるため、到達不能hostが`check FAILED`扱いになることはない。`slack_channel`/`slack_status`式(`cert_renew.yml:282-283`)は本差分で変更されておらず、`WARNING`文字列が追加されることで既存ロジックのまま`alerts`/`warning`に正しく評価される。
- **check-mode-nativeの前提維持**: 追加した4タスクはいずれも`when: not ansible_check_mode`や`tags: [destructive]`を持たず、`ping`/`set_fact`/`debug`/`meta`のみで構成される非破壊タスクであり、既存の破壊的操作ゲート(`issue_apply`/`deploy_proxmox`等、`cert_renew.yml:158-170`)より前に置かれている。`--check`実行時もprobeは通常どおり動作し、破壊的操作のゲート構造(`not ansible_check_mode`)自体は変更されていない(AC7の前提に合致)。
- **既存role非流用の判断(P0-1注記/requirement §5)**: `roles/proxmox_reachable_nodes`はcandidate groupの到達可能nodeが0件の場合にfailする設計であり、本要件(両node到達不能でもWARNINGで正常終了)と正面から矛盾する。実装は同roleを再利用せず、必要な部分だけをplaybook内に直書きしており、requirement §5の非流用理由と整合する。duplication-reuse-checkの観点では、既存roleとの重複ではなく、要件が非流用を明示決定した上での意図的な再実装であることをコード側からも確認した。
- **静的検査の独立再実行**: `ansible-playbook --syntax-check`(`rc=0`)、`ansible-lint playbooks/cert_renew.yml`を独立に再実行した。`cert_renew.yml`側の指摘は既存のplay名casing(43/67/85/111/172/208/222行、いずれも変更前から存在する既存play名)と`no-changed-when`(193/203行、monitoring pause/resume、既存)のみで、新規追加タスク(129-151行)を指す指摘は無い。実装記録の主張と一致。
