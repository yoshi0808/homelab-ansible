# cert_renew.yml — 到達不能なProxmox nodeを警告扱いにする(requirement)

作成: 2026-08-01 / Coordinator
起点: Yoshinobuの依頼「夏場は片ノードを落とす運用をするので、pve1 / pve2がダウンしていた場合はplaybookをエラーとせず、ワーニングでジョブ自体は正常終了させたい」

## 1. 問題定義

夏季のpve1平日シャットダウン運用下で `playbooks/cert_renew.yml` を実行すると、証明書更新が失敗するだけでなく **playbook全体が打ち切られる**。

`cert_renew - issue and deploy proxmox certs` は `serial: 1` を持つ。`serial` 指定のplayでバッチ内の全hostが到達不能になると、Ansibleはそのバッチでplayを終了し、**以降のplayを一切実行しない**(実測: 本ファイル §6 の観測手段と同じdecoyで確認、`rc=4`)。その結果、

1. pve2 と monnie の証明書更新playが実行されない(pve1がバッチ1のため)
2. **`cert_renew - cleanup CA key from quory` playが実行されない** — 中間CA秘密鍵が quory の `/run/semaphore-ca/`(tmpfs)に残置される。cert_renew_policy §5 が定める「処理後に削除」が満たされない
3. `cert_renew - send completion notification` playも実行されず、Slack通知が飛ばない(Semaphoreジョブが赤くなるだけで、何が起きたかは通知されない)

依頼者が求めたのは (1) の解消だが、実測により (2) が同時に発生していることが判明した。(2) は秘密情報の残置であり、本件で塞ぐ。

## 2. ゴール

- pve1 / pve2 の一方または両方が到達不能でも、到達できたnodeと他host(ansy / monnie)の証明書更新を完走し、CA cleanupと完了通知を必ず実行する。
- 到達不能nodeがあった実行の終了コードを `0` にし、Semaphoreジョブを緑で終える。
- 到達不能nodeがあった事実を、通知で人間が気づける形(WARNING)で残す。

## 3. 非ゴール

- `ansy` / `monnie` の到達不能を許容しない。両hostは常時稼働が前提(monnieはHA guest)であり、そこでのunreachableは本物の異常として従来どおり赤くする。**適用範囲はproxmox playに限る。**
- `cert_renew_quory.yml` は対象外(quory単独、`serial` なし)。
- 到達不能だったnodeの証明書が失効しないようにする仕組み(復帰時の追いかけ更新)は本件では作らない。§7 OQ1として残す。
- 既存 `roles/proxmox_reachable_nodes` への統合・寄せ替えは行わない(§5 P0-1の理由を参照)。

## 4. ユーザーストーリー

運用者として、夏季に片ノードを落としている期間でも、月次のcert_renewジョブが緑で完走し、「どのnodeが更新されなかったか」だけがSlackのalertsチャンネルで分かってほしい。そうすれば、赤いジョブを毎回確認して「これは計画停止によるもの」と読み替える手間がなくなり、本物の失敗だけが赤として残る。

## 5. 要件

| ID | 優先度 | 要件 |
|---|---|---|
| P0-1 | Must | proxmox playの先頭で、当該host自身のSSH到達性を明示的な `ansible.builtin.ping` でprobeする。到達不能なら `cert_host_unreachable` factを立て、WARNINGを出力し、`meta: end_host` でそのhostをplayから落とす。probeタスクは `ignore_unreachable: true` / `ignore_errors: true` / `become: false` とする |
| P0-2 | Must | 到達不能nodeがあっても後続のplay(monnie / cleanup / notification)が実行され、playbook全体の終了コードが `0` になる |
| P0-3 | Must | 最終playのsummaryで、到達不能nodeを `check FAILED` ではなく到達不能として区別して表示し、`WARNING` を含む行を出す(既存の分岐により `slack_status=warning` / `slack_channel=alerts` になる) |
| P0-4 | Must | Policy(`docs/ai/policies/cert_renew_policy.md`)に、到達不能hostのスキップ・WARNING通知・正常終了と、その適用範囲がpve1 / pve2に限られることを明記する(Yoshinobu承認済み、2026-08-01) |
| P1-1 | Should | playbook header commentに、この挙動と `serial` との関係(なぜ既存roleを使わないか)を残す |
| P2-1 | Could | 到達不能nodeの証明書残日数を通知に含める — **採らない**。到達できないnodeの証明書は読めないため原理的に不可能 |

### P0-1で `roles/proxmox_reachable_nodes` を再利用しない理由

同roleは「候補groupに到達可能nodeが1つも無ければ `fail` する」設計(T5)であり、本件の要求(両node到達不能でもWARNINGで正常終了)と正面から矛盾する。加えて `serial: 1` 下ではバッチ1の時点でpve2が未probeであり、T4/T5が参照する `ansible_play_hosts_all` 由来の到達可能リストが空になるため、**pve1がdownしただけでT5が誤発火する**。probe→`meta: end_host` という機構は同roleと同型のものを個別に書く。統合の是非はADR-008 Consequencesが既に「probeの消費者が3つ目に増えた時点で共通化を再検討する」としており、本件はその再検討の入力として記録に残すに留める。

## 6. 成功指標(受入条件)

観測は decoy inventory(実host名を含まない。閉ポート=到達不能、`ansible_connection: local`=到達可能)に対する実行で行う。**実ホストでの `--check` 検証は、playbook自身が `hostname == quory` をassertするため、commitとquoryへのpullが済むまで実施できない**(残存リスクとして §7 OQ2)。

| AC | Given / When / Then |
|---|---|
| AC1 | **Given** proxmox groupの片方が到達不能、もう片方が到達可能 **When** 修正後のproxmox play相当をdecoyに対し `serial: 1` で実行する **Then** 到達不能側は `meta: end_host` で落ち、到達可能側は後続タスクを実行し、**後続のplayがすべて実行され**、`ansible-playbook` の終了コードは `0` である |
| AC2 | **Given** proxmox groupの両方が到達不能 **When** 同上 **Then** playbookは打ち切られず後続のplayがすべて実行され、終了コードは `0` である |
| AC3 | **Given** proxmox groupの両方が到達可能 **When** 同上 **Then** `cert_host_unreachable` はどちらも `false` となり、probe以外の挙動(issue_check以降のタスク到達)は変更前と変わらない |
| AC4 | **Given** 到達不能nodeが1つ以上あった実行 **When** 最終playのsummary生成テンプレートを評価する **Then** 当該nodeの行は `check FAILED` ではなく到達不能である旨を示し、summary全体は文字列 `WARNING` を含み、文字列 `FAILED` を含まない。結果として `slack_status` は `warning`、`slack_channel` は `alerts` に評価される |
| AC5 | **Given** 全host正常な実行 **When** 同上 **Then** summaryは変更前とバイト一致し、`slack_status` は `ok`、`slack_channel` は `info` のままである |
| AC6 | **Given** 修正後のリポジトリ **When** `ansible-playbook --syntax-check` と `ansible-lint` を `playbooks/cert_renew.yml` に対し実行する **Then** いずれも新規のエラーを出さない |
| AC7 | **Given** 修正後の `playbooks/cert_renew.yml` **When** `--check` 実行時の挙動を確認する **Then** 追加したprobeタスクは `--check` でも実行され(`ping` はcheck mode対応)、`tester-gate: check-mode-native` の前提(破壊的操作は `not ansible_check_mode` でゲート)を崩さない |

## 7. オープンクエスチョン

- **OQ1(scope外・申し送り)**: 到達不能だったnodeは証明書が更新されない。運用は月次force_renew、証明書有効期間は45日であるため、復帰時に失効済みの証明書で稼働する期間が生じ得る。復帰時の追いかけ更新をどう扱うかは別案件。本requirementでは通知のWARNINGで人間が気づくことのみを担保する。
- **OQ2(残存リスク)**: 本件のACはすべてdecoyでの検証であり、実ホスト(quory→pve1 / pve2)での `--check` 実行は commit + quory pull の後にしか行えない。次回の実運用実行が実質的な初回の実地確認になる。

## 8. タイムライン考慮

夏季の平日シャットダウン運用が継続中であり、月次のcert_renew実行までに反映されていることが望ましい。実装差分は小さく、工程は「Coordinator実装 → Reviewer独立レビュー → Tester decoy検証 → Auditor」で足りると判断した。
