# 工数実績(見積もりの基準)

状態: **蓄積中**(2026-07-27に開始。データ点1)

## この文書の目的

**Tech Leadが見積もりを出し、Coordinatorがその妥当性を問うための比較対象**を持つ。

経験のある人間の管理職は「その機能でこの工数はおかしい」を経験値で判断する。AIの各Roleはコールドスタートで経験を持ち越せないため、**経験値をリポジトリ側に蓄積する**。案件を1件終えるたびに1行足す。

3〜4件溜まるまでは基準として弱い。それまでは「数字が無いこと」を自覚したうえで使う。

## 使い方

1. **着手時**: Tech Leadが見積もり(subagent起動回数、Role別の想定規模、工程配分)を出す。Coordinatorは本表と突き合わせ、乖離があれば根拠を問う
2. **増分の切れ目**: 実績を測り、見積もりとの差を出す。**逸脱10%までは吸収、超えたら止めて再計画を検討**する
3. **完了時**: 本表へ1行足す

## 測り方

| 指標 | 取得方法 |
|---|---|
| subagentのトークン・実時間 | 各subagentの最終報告(`subagent_tokens` / `duration_ms`)。**差し戻しで再開したagentは値が単調増加するため、agentごとに最終値のみを採る**(各回を足すと二重計上) |
| Coordinatorのコンテキスト量・出力 | セッションtranscript `~/.claude/projects/<repo>/<session>.jsonl` の `message.usage` を集計。**内容は読まない**(コンテキストが溢れる)。数値のみ |
| 変更規模 | `git diff --shortstat <起点>..HEAD` |

Coordinatorのコンテキスト増加率(1ターンあたり)は、**計画の質を測る指標**として特に有用である。計画が機能していれば実行フェーズの後半は「報告を読む→判断する→次を出す」に収束し、1ターンが軽くなるはずである。**平坦なら計画が足りていない信号**として扱う。

**工程配分(実時間ベース)**: 計画8.8% / 製造45.6% / レビュー25.9% / 検証19.7%

**この案件の評価**: 上流(計画・設計)が薄く、製造に手戻りとして現れた。`capture.yml` だけでImplementerを5回差し戻し、うち2回はCoordinatorの指示の誤りと仕様の詰め不足が原因。**見積もりが存在しなかったため、逸脱の判定ができなかった。** 検証工程の配分(19.7%)は参照モデル(20%)とほぼ一致しており、狂っていたのは上流と製造の比率。詳細は `docs/ai/reviews/process_retrospective/2026-07-27_001_retrospective.md`。

**次回この規模を見積もるときの叩き台**: Tier 4の新規仕組み1件で subagent 15〜20体・200万トークン前後。ただし**この実績は上流不足による手戻りを含む**ため、そのまま目標値にしない。上流を厚くすれば製造側が減る想定で、総量は下がりうる。

## 参照モデル(人間の実務値、2026-07-27 Yoshinobu提供)

200名規模プロジェクトの日程配分。予算配分ではない点に注意。

| 工程 | 日程比 | 備考 |
|---|---|---|
| 計画(CIO・部長) | 15% | 予算確保、ベンダー選定 |
| 要件定義・基本設計 | 35% | 20名程度。少人数だが高単価。**日程50%時点で予算消費は約20%** |
| 製造 | 20% | 最大人数を投入 |
| 結合・総合テスト | 20% | 製造15%/テスト25%になる案件もある |
| UAT | 10% | |

**上流に時間を、下流に金を。** この形が崩れているときは配分を疑う。
