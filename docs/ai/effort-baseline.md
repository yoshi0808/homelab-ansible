# 工数実績(見積もりの基準)

状態: **蓄積中**(2026-07-27に開始。データ点1)

## この文書の目的

**Tech Leadが見積もりを出し、Coordinatorがその妥当性を問うための比較対象**を持つ。

経験のある人間の管理職は「その機能でこの工数はおかしい」を経験値で判断する。AIの各Roleはコールドスタートで経験を持ち越せないため、**経験値をリポジトリ側に蓄積する**。案件を1件終えるたびに1行足す。

3〜4件溜まるまでは基準として弱い。それまでは「数字が無いこと」を自覚したうえで使う。

## 使い方

1. **着手時**: Tech Leadが見積もり(subagent起動回数、Role別の想定規模、工程配分)を出す。Coordinatorは本表と突き合わせ、乖離があれば根拠を問う
2. **増分の切れ目**: 実績を測り、見積もりとの差を出す。**逸脱10%までは吸収、超えたら止めて再計画を検討**する
3. **完了時**: 本表へ1行足す

## 測り方

| 指標 | 取得方法 |
|---|---|
| subagentのトークン・実時間 | 各subagentの最終報告(`subagent_tokens` / `duration_ms` / `tool_uses`)。**subagent自身が成果物へ書いた自己申告値は採らない** — 2026-07-28、計画査読のsubagentが自己申告した `tool_uses` 14 に対し、harnessの実測は30だった |
| 差し戻しで再開したagentの扱い | **harnessの版によって累積で返るか増分で返るかが違う。着手時に確かめること。** 2026-07-27の観測は「単調増加(累積)」で最終値のみを採る規定だったが、2026-07-28の`subagent_briefing`案件では**増分で返った**(U1が28→7、U3が21→6)。同案件は加算して集計している。**判別法**: 2回目の値が1回目より小さければ増分である |
| Coordinatorのコンテキスト量・出力 | セッションtranscript `~/.claude/projects/<repo>/<session>.jsonl` の `message.usage` を集計。**内容は読まない**(コンテキストが溢れる)。数値のみ |
| 変更規模 | `git diff --shortstat <起点>..HEAD` |

Coordinatorのコンテキスト増加率(1ターンあたり)は、**計画の質を測る指標**として特に有用である。計画が機能していれば実行フェーズの後半は「報告を読む→判断する→次を出す」に収束し、1ターンが軽くなるはずである。**平坦なら計画が足りていない信号**として扱う。

## 見積もりの単位を「分」から `tool_uses` へ(2026-07-28、実測により変更)

### なぜ変えたか

2026-07-28のTier 3案件(`docs/ai/reviews/incident_auto_capture/`、`_spool/` のACL mask切り詰め)で、**「分」による見積もりが単位の大小を予測できていない**ことが実測で判明した。

| 単位 | 見積もり | 実績 | 比 |
|---|---|---|---|
| Tech Lead(計画) | 25分 | 13.9分 | 0.56 |
| U0(Tester) | 10分 | 1.8分 | 0.18 |
| U1(Implementer) | 20分 | 3.7分 | 0.19 |
| U2(Implementer) | 30分 | 11.6分 | 0.39 |
| U3(Reviewer) | 20分 | 5.3分 | 0.27 |
| U4(Reviewer) | 30分 | 5.4分 | 0.18 |

平均で-72%ずれているだけなら係数で補正できる。しかし**比そのものが0.18〜0.56の3.1倍ばらついており、定数倍では直らない**。

これが問題なのは、**計画レビューの「1単位60分を超えない・理想30分」という基準が見積もりの数字に対して働いている**ためである。見積もりが相対的に3倍ずれるなら、その基準は実際の単位の大きさを制御していない。**ルールが、目的の量ではない別の量を見張っている状態**だった。

Yoshinobuの指摘(2026-07-28): 「分」で見積もらせたのは人間の実務感覚の持ち込みであり、AIの作業量の単位ではない。

### 採用する単位

**実行単位と計画・管理単位を分ける。** 同じ案件の実測で、両者は明確に別クラスだった。

| 分類 | 分 / tool_use | レンジ | 性質 |
|---|---|---|---|
| **実行単位**(Implementer / Reviewer / Tester) | 0.110〜0.194 | **1.8倍** | tool主体。読む・書く・検証するの回数が時間を決める |
| **計画・査読単位**(Tech Lead、および計画査読) | 0.263〜0.463 | 1.8倍 | 思考主体。tool回数が少なく時間が長い |

実行単位に限れば `tool_uses` のばらつきは1.8倍で、「分」の3.1倍より良い。

- **実行単位は `tool_uses` で見積もる。** 単位の大きさの基準は **80 tool_uses を超えない、理想30〜40**(同案件の最大がU2の60、最小がU0の11)。
- **計画・査読単位は大きさの基準の対象外**とする。Tech Leadは案件に1体、計画査読も1体で、構造的に個数が抑えられているため。

**想定Step数(コード行数)は採らない。** この案件はU2の差分が小さいのに11.6分かかっており、時間はコードを書くことではなく検証(decoy実験、ansibleモジュールのソース読解)に消えた。**調査主体の作業でLOCは構造的に過小に出る。**

### この変更自体の確度

**データ点は1案件・6単位のみ。** 欠陥クラスも1種類(ACL/権限)に偏っている。**基準値(80 / 30〜40)は暫定であり、3〜4案件の実績が溜まるまで確定としない。** Coordinatorは各案件で `tool_uses` の実績を `progress.md` へ記録し、本ファイルへ記帳する。レンジが1.8倍から広がるようなら単位選択自体を見直す。

将来: Yoshinobuの表明(2026-07-28)として、**計画査読が想定Step数とテスト工数の妥当性まで見る**段階がありうる。これは本ファイルの実績蓄積を前提とする。現時点では不要であり、査読は `docs/ai/roles/techlead.md`「計画査読」の層1(数える)・層2(技術的前提の反証)に留める。

## 常設の工程管理役の費用(2026-07-28、退役の根拠の一部)

2026-07-27に新設し2026-07-28に退役したPMO役について、唯一の実走で測った値を残す。**同種の常設役を再び置きたくなったときの判断材料**である。

PMOは3回起動し9.7分、案件全体51.4分の**18.9%**を占め、システムを変える成果物はゼロだった。費用は**チェックポイント単位でほぼ固定**であり、案件の作業量に比例しない。したがって**小さい案件ほど割高になる**(2026-07-27のTier 4規模=194分なら、同じ3回で約5%)。

退役の理由は費用ではなく**機能しなかったこと**である。詳細は `docs/ai/reviews/process_retrospective/2026-07-28_003_pmo_retirement.md`。

**公平のために、この役が実際に拾ったものも残す。** 費用だけを見て判断すると、次に同種の役を検討するときに材料が偏る。

- Coordinatorの記録管理の欠陥4件(P-1〜P-4)。うちP-1とP-3は同型の再発で、注意力ではなく「同じ状態を2箇所に持つ構造」が原因と判明し、重複を削除する形で構造的に対処した
- 走行中のチェックポイントが**後続チェックポイントのゲート自体を補正**した(Q-U2-1の再決定確認の追加)
- 計画の技術的引用の誤り3件への訂正注記を、実地検証の起動前提として課した

**それでも退役させたのは、これらがいずれも「記録の整合性」に留まり、同日に実際に危険だった誤り(誤った因果モデル、反転した論証)には構造的に触れられなかったためである。** 後者は技術判断を許された役でなければ検出できない。代替として計画査読を2人目のTech Leadへ移し、技術的前提の反証まで行わせる形にした。

**チェックポイント数を案件規模に応じて減らすかは、3〜4案件後に判断する。** データ点1件で削らない。
