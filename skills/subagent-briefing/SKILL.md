# Subagent依頼文の型

Coordinatorがsubagentを起動するとき、および差し戻しで再起動するときに使う。**章名・順序・語調は指定しない。** 各章が持つ「書くもの / 書かないもの」の対応だけが契約であり、規範の中身は正本を参照する(下記「参照」)。

## 実行identityと権限境界

**全subagentへ常に適用される共通則は `docs/ai/core.md`「subagentが共通して守ること」が正本であり、依頼文へ複製しない。** 依頼文に書くのは、そこに無いもの — 案件固有の書込先と、Role文書より**狭める**制限だけである。

- **書くもの**: どのidentityで実行してよいか、書込先パス、触れてよいホスト。**すべて「到達してはいけない状態」として書く** — 昇格した状態に到達しない、指定外パスが変更された状態で報告が返らない、実ホストに触れた状態で報告が返らない、のように結果で書く。
- **書かないもの**: 禁じたい個々の手段の列挙。手段を塞いでも別の手段で同じ結果に到達され、しかも「迂回ではない」と整合的に説明されうる。

## 渡すもの / 渡さないもの

- **書くもの**: 受入条件、制約、**観測された現象**。
- **書かないもの**: 実装方法、章立て以下の作り方、**因果メカニズムを完成形まで組み立てたもの**。「未検証」「反証してよい」と断っても、完成した因果は検証の出発点を固定してしまうため免罪符にならない。**この2点(実装方法を指定しない / 因果を完成形で渡さない)は本Skillが正本である。**

## 並行作業の境界(複数subagentを同時に立てる場合)

- **書くもの**: 各subagentが触れてよいパス、`git status`に現れる他方の未追跡ファイルを**自分の成果物として報告・削除・整形しない**旨、`git add`/`commit`/`push`を行わない旨。
- **書かないもの**: 他subagentの作業内容そのものの詳細。調整はCoordinatorが担い、subagent間の直接連携を前提にしない。

## 自己検証

- **書くもの**: 何を確認できれば十分か(契約要素の充足、参照先の実在、量的上限の充足など)。
- **書かないもの**: 確認の具体的な手順・コマンド列。手段はsubagentに委ねる。

## 報告形式

- **書くもの**: 対象パス、契約の充足状況、自己検証で確認したこと(参照先の実在を含む)、未解決事項。
- **書かないもの**: 中間ログ、長い引用。判断の根拠は成果物ファイル側へ書かせ、報告本文には要点だけを書かせる。

## Role別の差分

章立てはRole非依存。差分はこの表だけで持つ(Role追加時にここだけ直せばよい形にする)。

| Role | 依頼文の要点 |
|---|---|
| Reviewer(計画査読) | Coordinator自身が確定した詳細分解・見積もりをそのまま渡す(要約・再解釈しない)。査読観点は`docs/ai/roles/reviewer.md`「計画査読」(2026-07-29、Tech Lead廃止に伴い新設。詳細設計・機能分割・インターフェースの確定は現在Coordinator自身の責務であり、subagentへは渡さない) |
| Implementer | 確定したrequirement/契約(概要設計を含む)を渡す。実装方法・章立て以下の作り方は指定しない |
| Reviewer | 対象diffと、requirement/契約上の**観測事実**を渡す。他のsubagentが導いた**因果の結論**は渡さない — 独立照合の出発点を固定しないため |
| Tester | 実ホストへの到達性、承認済みscope、decoy/`--check`可否を明示する。実装方法は指定しない |
| Auditor | 案件フォルダのパスと「どこから読み始めるか」だけを渡す。Coordinatorの説明・要約は渡さない(コールドスタートで再構成できるかどうか自体が検査対象になる。`docs/ai/roles/auditor.md`「入力を絞る理由」) |

## 差し戻し時の再起動

差し戻しは新規起動ではない。**初回用の型を再掲しない** — 差し替え・追加する項目だけを書く。

- **差し戻す理由**: どのACのどの章が不足・誤りだったか(観測事実で書く。原因の完成形は渡さない — 上の「渡すもの/渡さないもの」と同じ制約が適用される)
- **再確認条件**: 何を満たせば再度差し戻されずに済むか
- **変わった契約要素だけ**: 今回変更・追加された要素だけを明示する。変更のない要素は「変更なし」とだけ書き、内容を再掲しない
- **前回成果物との関係**: 新規に書き直させるのか、既存の実装記録へ追記させるのかを明示する

初回起動より**書きすぎる方向**が強く出る局面である(失敗のたびに指示を細かくする悪循環)。差し戻し時こそ「渡さないもの」を確認する。

## 型が塞がないもの

この型が塞ぐのは書き落としまでで、解釈による逸脱は塞がない。**型どおりの依頼文が返ってきたことをもって、権限境界の問題が解決したと読まない。** 実効的な境界は文章ではなく、能力の不在(鍵・到達先・wrapperが存在しないこと)で作る。

## AC1対応表

過去に実際起きた3クラスの逸脱を、どの章がどう塞ぐか。

| AC1のクラス | 塞ぐ章 | どう塞ぐか |
|---|---|---|
| ① 実行identityと権限境界の未明示 | 実行identityと権限境界 | identity・書込先・触れてよいホストを「到達してはいけない状態」として書く欄を必須にし、書き落としを防ぐ |
| ② 方法の指定 | 渡すもの / 渡さないもの | 「渡さないもの」に実装方法・章立て以下の作り方を明記し、指定できなくする |
| ③ 原因を完成形で渡す | 渡すもの / 渡さないもの | 「渡さないもの」に因果メカニズムの完成形を明記し、「未検証」の断り書きは免罪符にならないと明示する |
