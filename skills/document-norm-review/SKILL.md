# 規範文書レビュー(欠陥クラス・チェックリスト)

`skills/code-review/SKILL.md`はコード差分向けの出力型、`skills/ansible-security-review/SKILL.md`はAnsible実装の攻撃面を扱う。本Skillは**規範文書そのものの変更**を対象とし、反復して検出された欠陥クラスを項目化したもの。

**適用対象**: 規範の移設・削除・正本の差し替え、判定基準の改訂、安全境界・責任分界の変更、Policy群の横断的な再配置。いずれも**「結果の検証は通るのに、対象の選定が間違っている」が成立する形**であり、書いた本人には見えない。

## 前提: 掃引は目視でなく機械的に行う

**「直した箇所を数える」のではなく「古い記述が1つも無いことを示す」。** 撤回した文言そのものを検索語にして残存ゼロを確認する。

```
grep -rn "<撤回した文言>" docs/ai/ skills/ roles/ playbooks/ inventories/ CLAUDE.md AGENTS.md
```

目視の掃引は失敗する。2026-07-27の1セッションで、いずれも「直したつもりで目視確認した」状態から3件の残存が出た(`docs/ai/memory/lessons/sweep-all-documents-stating-a-changed-boundary.md` 根拠2)。変更した箇所の周辺だけを見ると必ず漏れる。

**検索対象にはAIが読むファイルを必ず含める**(prompt テンプレート、`skills/*/SKILL.md`、`CLAUDE.md`、`AGENTS.md`、実装コメント)。ここに古い規範が残ると、人間が気づかないまま以後の全Role・全subagentの判断が汚染され続ける。

## 欠陥クラス

### 1. 宙ぶらりん参照(dangling reference)

移設・削除した節を指す参照が残る。**完全パス表記だけを置換して略記形を検索しない**のが典型的な取り残し方。

- 完全パス(`docs/ai/prompts/core.md §18`)と略記(`core.md §18`、`§18.2`)を**別々に**検索する。
- markdownリンク形式だけでなく散文中の言及も掃く(`[Repository Context](...)`と「Repository Contextを正本とする」は別物)。
- 参照元は文書だけではない。`roles/*/defaults/main.yml`・`tasks/*.yml`のコメント、`playbooks/*.yml`の`fail_msg`(実行時にオペレータへ表示される)、`inventories/*/group_vars/*.yml`も対象。

根拠: 2026-07-26の旧`core.md`退役で、完全パス表記のみをsedした結果、略記形24箇所/20ファイルが宙ぶらりんになった。うちlive Policy 4本、稼働コード、およびオペレータへ表示される`fail_msg` 4箇所を含む(`docs/ai/reviews/core_md_retirement/2026-07-26_001_review.md` Critical #2/#3/#8)。

### 2. 規範の消失(移設宣言と実内容の不一致)

「§Xから移設した」と宣言している箇所は、**移設元を逐行で読んで項目単位に突き合わせる**。宣言を信じない。

明示禁止が暗黙導出へ後退するのも消失として扱う(「AもBもCも禁止」→「Aのみを行う」への言い換えは、Bの明示禁止を失っている)。

根拠: 同上 Critical #1。「変更操作を入れない」という禁止1件が、移設宣言のある文書のどの項目にも到達していなかった。

### 3. 撤回した規範・廃止した根拠の残存

規範を撤回したら、**それを根拠として引用している箇所**も同時に消す。機構を変えたら、旧機構を安全の根拠として述べている記述も消す。

- 「`--disallowedTools`で技術的に塞いである」— 機構をallowlistへ変えた後も残っていた(**無人LLMが毎月読むprompt**に残存)。
- 「settings.jsonのdenyが効く」— `--setting-sources`を空にして読み込まなくした後も残っていた。
- 撤回した記録タイミング規範が、正本の別セクションにだけ残っていた。

根拠: `docs/ai/memory/lessons/sweep-all-documents-stating-a-changed-boundary.md` 根拠2の3件。

### 3.5 規範が依拠している事実の未検証

規範が事実を根拠にしているとき、**その事実を何が支えているかを問う。** 支えが機構(assert、forced command、ACL、機械検査)なら破れない。支えが誰かの申告や過去の作業なら、**気づかれずに崩れうる。**

- **文面からは両者を区別できない。** 「〜を禁止しているため」「〜を持たないため」は、機構に支えられていても願望に支えられていても同じ強さに見える。
- **支えを名指ししていない根拠は、指摘の対象である。** 名指しできるなら1句で足りる。名指しできないなら、それは根拠として使えない。
- **機械検査が支えていると書かれている場合は、その検査が対象を実際に含むかを確かめる。** カタログ・対象ホスト・パスを開いて突き合わせる。

根拠: 2026-08-18。`docs/ai/policies/execution_boundary_policy.md` EXEC-002 が「ansyが認証情報を1つも持たない」を境界の根拠として述べていたが、実測すると秘密鍵は ansy にあり、境界は受け側の `authorized_keys` にあった。**その `authorized_keys` は日次ドリフト検査の対象外**であり、崩れても検出されない。同日の `cert_renew_policy.md` CERT-017「両 Playbook とも quory 以外での実行を禁止しているため」は同じ文型だが、支えが `assert: ansible_facts['hostname'] == 'quory'` という実在する機構だったため成立していた(`docs/ai/reviews/role_prompt_optimization/2026-08-18_004_layer_survey.md`)。

### 4. 判定ラダーの全域性・一意性

上から順に問い最初のYesで止める形式の判定手順は、**先取り**と**到達不能分岐**が生じる。

- **先取り**: 上位項目の条件が広すぎて、下位項目が名指しする対象を先に捕まえ、下位項目が到達不能になる。
- **全域性の欠落**: どの項目にも当たらない入力がある。
- **一意性の欠落**: 複数項目に当たり、並び順だけで結果が決まる(除外文言が無いまま「軽い作業」と「危険な操作」の両方に当たる入力が、先に書かれた側で確定する)。
- **矛盾を消すと穴ができる**。修正のたびに、矛盾の解消と全域性の維持を**別々に**確認する。

**最良の反例は「今やっている作業自体」**。判定基準を書き換えたら、その基準で自分の今の変更を判定してみる。2026-07-26の2巡目レビューは、Coordinatorがその瞬間編集していた`reviewer.md`/`coordinator.md`を反例として突きつけた。

根拠: `docs/ai/reviews/delegation_tier_two_axis/2026-07-26_001_review.md`・`002_review.md`。

### 5. 文書内の自己整合(新概念の部分反映)

新しい概念・例外を導入したとき、**同じ文書の他の節が旧前提のまま**残る。指摘された箇所だけを直すと必ず起きる。

`+R`(Tech Leadが介在しない工程)を`reviewer.md`の返却先節にだけ追記した結果、同じ文書の「禁止・エスカレーション」節が無条件に「担当Tech Lead」を宛先として書いたまま残り、`+R`で起動されたReviewerが実在しない宛先へエスカレーションする経路ができた。

**確認方法**: 導入した概念名(`+R`等)ではなく、**それが覆す旧前提の語**(「担当Tech Lead」「Yoshinobuが承認」)で文書内を検索する。新概念で検索すると、追記した箇所しかヒットしない。

根拠: `docs/ai/reviews/delegation_tier_two_axis/2026-07-26_002_review.md` Critical #4。

### 6. 追跡表・索引のドリフト

移行表・索引・マップが実態と逆を主張する。着地済みの項目が`[予定]`のままだと、棚卸しリストとして使ったときに**既に存在する規範を再移設して重複させる**。

表の意味を再定義したら(「この記法はどの正本にも無いことを意味する」等)、**全行をその定義で読み直す**。

根拠: `docs/ai/reviews/core_md_retirement/2026-07-26_001_review.md` Critical #4/#5。同一commit内の2つのstagedファイルが正面から矛盾していた。

### 7. 適用範囲(scope)の広狭変化

規範の移設先が、**自分の適用範囲を元の規範より狭く(または広く)宣言している**ことがある。到達経路は成立していても、適用条件が変わる。

check系shell全般に掛かる規範が、「6 roleを対象とする最小サブセット」と自称する文書へ移された結果、その6 roleの外側にある実コードが、自分に掛かる規範が自分を対象外と宣言する文書を根拠にする状態になった。

根拠: 同上 Critical #7。あわせて、義務の主体が縮む形(「全実行者の義務」→「Codexが検証する場合」)も同クラス(Critical #6)。

## 参照先を誤らないための作法

検証手段が正しく機能していても、当てる対象を誤れば結論は反転する。この型は「検証した」感覚が伴うため自己検出できない。

1. **文書内の位置は安定識別子で指す**。`SB-nnn` / `AR-nnn` / `TS-nnn` / `BRV-nnn`等が存在する文書では行番号を使わない。
2. **構造化マーカーはマーカー形式で数える**。`grep -c "SB-049"`ではなく`<!-- SB-049 -->`。変更履歴での「言及」と規範としての「実体」を数の上で混同しない。
3. **「Xが消えたか」ではなく「参照されている用語に定義があるか」を問う**。特定文字列の名指しは派生形・汎用形を取りこぼす(`Mode A`/`Mode B`を検索して「Mode別」が残存した)。
4. **同名の機能が複数経路に存在する領域(mute、通知、認証、実行許可)では、片方で「無い」ことを確認しても他経路の存在を否定しない**。否定的結論は追加検証の動機が湧かず、そのまま断定へ進みやすい。

詳細と失敗例は`docs/ai/memory/lessons/verification-referent-and-path-mismatch.md`。

## 出力

`skills/code-review/SKILL.md`の構造(Summary / Critical Issues / Suggestions / What Looks Good / Verdict)に差し込んで報告する。重大度分類・返却先は`docs/ai/roles/reviewer.md`が正本(返却先は常にCoordinator)。

**「規範本体に消失・意味変化・条件の緩みは無い」ことを確認できた項目はWhat Looks Goodへ明記する。** 規範レビューでは「変わっていないこと」の確認が成果物であり、書かないと再照合が必要になる。

## 適用条件

- IPアドレス・VLAN ID・VM ID・認証情報の実値は書かない(`docs/ai/context-classification.md` §3/§4)。
- 本Skillは手順の正本。根拠となる個別事例は`docs/ai/memory/lessons/`側にあり、そちらへ手順を複製しない。
